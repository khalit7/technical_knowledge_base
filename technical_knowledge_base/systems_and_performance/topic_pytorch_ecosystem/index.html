PyTorch is a Python library for computing with arrays of numbers on CPUs and GPUs, which also works out the gradients you need to train a model. This page teaches it from zero by following one training step of a tiny GPT down through PyTorch, then making it fast, then spreading it over several processes. Every number on it was either measured here or comes from a linked, dated source, and the two are labelled apart.

The running example. A character-level GPT written in plain PyTorch: 43 distinct characters as its vocabulary, 4 transformer blocks of width 256 with 4 attention heads, a context of 64 characters, 3,186,944 parameters, trained with AdamW on batches of 8 windows cut from the first three paragraphs of Alice's Adventures in Wonderland. Its first loss is 3.8014, just above ln 43 = 3.761, the loss of a uniform guess, and after 300 steps it reaches 0.546 measured on Apple M1 Pro. The same model, the same batches and the same seed are used by every tab of this page and by every child page. Machine: an Apple M1 Pro laptop, its CPU (4 threads) and its GPU through Apple's MPS backend (Metal Performance Shaders), PyTorch 2.14.1 (released 2026-09-30, PyPI). There is no NVIDIA GPU here, so each section says what carries over to one and what does not, and published GPU numbers are quoted separately with who measured them.

The figure is the whole page in miniature. Your code calls model(x). Python runs the module's forward, which calls PyTorch functions such as torch.matmul. Each call is an operator (a named operation such as aten::addmm; ATen is PyTorch's C++ tensor library, where every operator is defined). The dispatcher decides which implementation of that operator runs, by reading labels on the inputs: is a gradient needed, is mixed precision on, which device holds the data. At the bottom a kernel (one compiled function that does the arithmetic on one device) runs. torch.compile replaces most of that walk with generated code; torch.distributed runs the same program in several processes that exchange data.

1. Tensors from zero: a window onto memory

A tensor is an n-dimensional array of numbers of one type. Under the hood it is two things. The storage is one flat block of bytes on one device. The tensor itself is a small description of how to read that block: a shape (how many elements along each dimension), strides (how many elements to jump in storage to move one step along each dimension), an offset (where element zero sits), a dtype (the number format, such as float32 at 4 bytes or bfloat16 at 2) and a device (cpu, mps, cuda).

address of x[i, j] = offset + i × stride0 + j × stride1

So a transpose, a slice or a reshape that keeps the order of elements does not move any data: it writes a new description over the same storage. That new tensor is a view. Try it on x = torch.arange(12.).reshape(3, 4):

Shapes, strides, offsets, contiguity and storage sharing are what PyTorch 2.14.1 reported for each expression measured here (src/read/measure.py); the page draws them from that record and recomputes every address with the formula above.

A tensor is contiguous when its elements, read in order, sit one after another in storage (for shape (3, 4), strides (4, 1)). Many kernels need that, because reading memory in order is what CPUs and GPUs do fast. When a tensor is not contiguous, a kernel either copies it first or uses a slower path. Two consequences you will meet:

  • x.t().view(12) fails: "view size is not compatible with input tensor's size and stride". x.t().reshape(12) works, because reshape returns a view when it can and quietly copies when it cannot; here it copied (it no longer shares storage with x).
  • In the running example, attention's output is rearranged with .transpose(1, 2).contiguous(). On the CPU that copy moves 0 bytes, because the CPU attention kernel already writes its output in the needed order; on MPS it copies 524,288 bytes per layer measured on Apple M1 Pro (Inside one step, section 1). The same line of Python costs differently on two devices.
Predict: x = torch.arange(12.).reshape(3, 4), y = x.t(), then y[0, 1] = 100. What is x[1, 0] now?
100. y is a view: y[0, 1] and x[1, 0] are the same storage cell (offset 0 + 1 × 4 + 0 × 1 = 4 for x; 0 + 0 × 1 + 1 × 4 = 4 for y). Writing through one changes the other. This is why in-place operations on views need care, and why autograd tracks them (section 2's ADInplaceOrView key).

dtype and device, in bytes. The model's 3,186,944 parameters in float32 take 12,747,776 bytes (12.75 MB) 3,186,944 × 4; AdamW keeps two more tensors of the same size per parameter (25.5 MB), and the gradients another 12.75 MB. In bfloat16 each number takes 2 bytes. Operations need their inputs on one device; moving data is explicit (.to("mps")) and on a GPU it is a copy over a bus, so stray .cpu() or .item() calls in a training step make the CPU wait for the GPU (section 6).

2. The dispatcher: how one call finds its kernel

The problem. One operator, say aten::mm (matrix multiply), must behave differently depending on context: record itself for backward when a gradient is needed, cast to a lower precision when mixed precision is on, run a CPU kernel or a GPU kernel, or hand control to Python when the input is a special tensor type. Writing all of that into every kernel would be unmaintainable.

How it works. PyTorch keeps, for every operator, a table of kernels indexed by dispatch key. A dispatch key is a label such as AutogradCPU, AutocastCPU, Python or CPU. Each tensor carries a set of keys; the dispatcher takes the union over the inputs, removes keys that are switched off for the current thread, and calls the kernel registered for the highest-priority key left. That kernel does its job (for example, autograd records a graph node) and then calls the operator again with its own key masked out, so the next key down runs, until a backend kernel does the arithmetic. Keys with nothing to do for an operator are registered as fallthrough and are skipped.

The same call, torch.mm(x, w), in five situations

Key sets, the calls that reached the backend, output dtype and the recorded grad_fn are measured here with PyTorch 2.14.1 on the CPU (x is 8 × 256, w is 256 × 256 with requires_grad=True; src/read/measure.py). Priority order from the wheel's DispatchKey enum: PythonTLSSnapshot, Autocast, Autograd, ADInplaceOrView, Python, then the backend (higher runs first). On MPS the keys are MPS, AutogradMPS, AutocastMPS.

Three things in that figure surprise most people. An ordinary CPU tensor carries the AutogradCPU key even when nothing needs a gradient: the autograd kernel runs on every call and decides at run time whether to record. torch.no_grad() does not remove the key; it tells that kernel to record nothing. torch.inference_mode() goes further: tensors made inside it carry no autograd keys at all, so that layer is skipped outright and tensors skip the version counters that guard in-place writes. That is why inference mode is the faster of the two, by a little: one forward of the running example took 6.52 ms with gradients, 6.16 ms under no_grad and 6.12 ms under inference_mode on the CPU, and 4.29, 2.41 and 2.40 ms on MPS measured on Apple M1 Pro, medians of 5 trials of 20 forwards (Inside one step, section 6).

Why it matters: the dispatcher is the extension point
Everything that changes PyTorch's behaviour without changing your model plugs in as a kernel for some key: autograd itself, autocast, a new device (Apple's MPS, Intel's XPU and out-of-tree backends register under their own keys), functionalization for the compiler, TorchDispatchMode recorders like the one that counted 923 calls in Inside one step, and tensor subclasses such as DTensor (section 7) and torchao's quantized tensors (section 8). Once you see the table, those libraries stop looking like magic.

The cost. Every call pays a few microseconds of Python and dispatch overhead before any arithmetic. For a large matrix multiply that is nothing; for the tiny element-wise operations that fill a transformer it adds up, and it is one of the two things torch.compile removes (section 5). How to check: torch._C._dispatch_keys(t) prints a tensor's keys; torch._C._dispatch_dump_table("aten::mm") prints an operator's table; a TorchDispatchMode logs every call that reaches the bottom.

3. Autograd: the graph built during forward

The problem. Training needs the gradient of the loss with respect to every parameter: how much the loss would change if that number moved a little. Working it out by hand for a model is impossible; doing it numerically (nudge each of 3 million numbers) is far too slow.

How it works. Autograd applies the chain rule automatically. During forward, the autograd kernel of each operator (section 2) adds a node to a graph: an object that knows how to turn the gradient of its output into gradients of its inputs (MmBackward0 for a matrix multiply). To do that later, a node keeps some of the forward's tensors: the saved tensors. Calling loss.backward() walks the graph from the loss back to the parameters, each node passing gradients to the next, and AccumulateGrad nodes add the result into each parameter's .grad. A node's saved tensors are released once it has run. Watch it on a two-layer network small enough to see whole:

h = gelu(x @ W1), loss = mean((h @ W2)2): the graph grows in forward and unwinds in backward

Node names, what each node saved (bytes in float32), backward order and the calls backward made are measured here with PyTorch 2.14.1 (x 8 × 16, W1 16 × 32, W2 32 × 4; src/read/measure.py: graph walked from loss.grad_fn, order from node pre-hooks, saved tensors from a saved_tensors_hooks pair, backward calls from a dispatch recorder). Both modes give the same gradient.

Two things to take from it. First, what fills memory in training is the saved tensors, and they grow with batch size and sequence length while the weights do not. For the running example one forward builds a graph of 187 nodes (135 operators plus 52 AccumulateGrad, one per parameter tensor) and keeps 34.76 MB of activations, against 12.75 MB of parameters measured on Apple M1 Pro. Second, you can trade memory for compute. Activation checkpointing (torch.utils.checkpoint.checkpoint(fn, x, use_reentrant=False)) runs a region without keeping its intermediates, keeps only its input, and re-runs the region during backward when they are needed. Predict: wrap the training step's forward in torch.no_grad() to save memory. What happens at loss.backward()?
An error: "element 0 of tensors does not require grad and does not have a grad_fn". Under no_grad the autograd kernel records nothing, so there is no graph to walk. no_grad and inference_mode are for evaluation and serving; checkpointing is the tool for saving memory while training.

Custom backward. When you need a gradient autograd cannot derive (a numerically safer formula, a kernel written outside PyTorch), subclass torch.autograd.Function with a forward and a backward and save what backward needs with ctx.save_for_backward; check it against finite differences with torch.autograd.gradcheck in float64. The Inside one step tab does exactly that check for one block. For an operator that should also work under torch.compile, prefer torch.library.custom_op with register_autograd (section 8).

When it matters and how to check. When you run out of memory in training, look at activations first. torch.cuda.max_memory_allocated() (on a Mac, torch.mps.current_allocated_memory()) before and after forward gives the saved bytes; the memory snapshot (section 6) says which tensors they are.

4. nn.Module, state_dict, optimizers, and a training loop done right

An nn.Module is a Python class that registers its parameters (tensors wrapped in nn.Parameter, which autograd treats as leaves to compute gradients for), its buffers (tensors saved with the model but not trained) and its sub-modules, so model.parameters() can find every weight in the tree. model.train() and model.eval() flip a flag that layers such as dropout read. The running example ties its output layer to its input embedding: head.weight is tok.weight, one Parameter used twice. So model.parameters() yields 52 tensors, but the state_dict (the ordered name-to-tensor dictionary you save and load) has 53 entries, two names for one storage measured here. Tools that walk names rather than objects (exporters, some sharding code) see the weight twice; the Compile lab found torch.export listing 53 parameter inputs for that reason.

An optimizer holds references to the parameters plus its own state per parameter. AdamW keeps two running averages, so its state is twice the parameters (25.5 MB here). opt.step() updates every parameter from its .grad; opt.zero_grad() clears the gradients (setting them to None by default, set_to_none=True, which frees the memory instead of filling it with zeros). How the update is computed matters more than people expect: PyTorch has a for-loop implementation (a few small operations per parameter tensor), a foreach one (each operation applied to all tensors in one call) and a fused one (one kernel does the whole update). At 2.14.1 foreach is the default only on CUDA-like devices and fused is never the default, so the CPU and MPS use the for-loop (_foreach_utils.py L8 to L23). Asking for fused=True made the running example's optimizer phase 2.7 times faster on the CPU and 4.1 times on MPS measured on Apple M1 Pro (section 6).

# one training step, done right (device = "cuda", "mps" or "cpu") model.train() opt = torch.optim.AdamW(groups, lr=6e-4, betas=(0.9, 0.95), weight_decay=0.1, fused=True) for step in range(steps): for micro in range(accum): # gradient accumulation x, y = get_batch(cfg, step * accum + micro, device) # seeded: batch k is the same on every run with torch.autocast(device, dtype=torch.bfloat16): # AMP: matmuls in bf16, reductions in fp32 logits, loss = model(x, y) (loss / accum).backward() # gradients add up across micro-batches torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0) opt.step(); sched.step() opt.zero_grad(set_to_none=True)
  • Mixed precision (AMP). torch.autocast is the Autocast key of section 2: it casts the inputs of chosen operators (matrix multiplies, attention) to bfloat16 and leaves precision-sensitive ones (softmax, losses, norms) in float32. The weights and the optimizer stay in float32. With float16 instead of bfloat16 you also need torch.amp.GradScaler, because float16's narrow range lets small gradients underflow to zero; bfloat16 has float32's range and needs no scaler.
  • Gradient accumulation. backward() adds into .grad, so running several micro-batches before step() simulates a bigger batch, as long as each loss is divided by the number of micro-batches. Under DDP (section 7), wrap all but the last micro-batch in model.no_sync() or every micro-batch pays for a gradient all-reduce.
  • Determinism. Seed everything (torch.manual_seed), make the data order a function of the step, and turn on torch.use_deterministic_algorithms(True) when you need bit-identical reruns (some GPU kernels are non-deterministic by default). The running example's batches are seeded by step number, which is what let the Ecosystem map tab show the same three losses, 3.80137, 3.18793, 3.16783, from a plain loop, Lightning 2.6.6, the Hugging Face Trainer 5.19.0 and Accelerate 1.15.0 measured on Apple M1 Pro, CPU.
A framework is a set of defaults
That identical-loss result needed the Trainer's defaults switched off. Out of the box, the Hugging Face Trainer at 5.19.0 clips gradients at max_grad_norm=1.0, uses learning rate 5e-5 with a linear decay schedule, weight decay 0, adamw_torch_fused and seed 42, and shuffles the data; Lightning 2.6.6 does not clip and trains in 32-bit by default read from the installed libraries, Apple M1 Pro (Ecosystem map, "Same step, five doors"). 5. torch.compile: from Python to fused kernels

The problem. Eager PyTorch runs one operator at a time. Each one pays Python and dispatch overhead, and each one reads its inputs from memory and writes its output back. A GELU written as eight small operations moves the same activation through memory eight times. On a GPU, where arithmetic is far cheaper than memory traffic, most of a transformer's element-wise work is limited by those round trips, not by arithmetic.

How it works. torch.compile(model) does nothing until the first call. Then three stages run:

TorchDynamo
capture

Hooks Python's frame evaluation (PEP 523) and reads the function's bytecode, recording tensor operations into an FX graph (a list of operations) and the assumptions it relied on as guards (dtypes, shapes, which module, global flags). Python it cannot trace causes a graph break: that part runs eagerly between graphs.

AOTAutograd
forward + backward

Traces the graph through autograd ahead of time, producing a forward graph and a backward graph, and decides which forward values backward will keep (a min-cut partitioner may choose to recompute cheap ones instead).

TorchInductor
codegen

Fuses chains of element-wise operations and reductions into single loops and writes code: Triton for NVIDIA and AMD GPUs, C++ with OpenMP for CPUs, Metal shaders on Apple GPUs. Matrix multiplies usually stay library calls (cuBLAS, BLAS) unless autotuning finds a faster template.

On the running example that is 1 graph of 59 operations, 0 breaks, 549 guards; the forward drops from 142 eager calls to 35 launches on the CPU and from 191 to 62 on MPS, and the backward from 295 calls to 60 launches on the CPU measured on Apple M1 Pro (Compile lab). And the speed?

Predict: on the laptop's CPU, how much faster is the compiled training step of the running example?
About the same: 23.20 ms compiled against 22.75 ms eager. On the CPU most of the step is matrix multiplies, which stay BLAS calls either way, and a CPU's large caches already absorb much of the element-wise traffic. On MPS, a GPU, the same compile gives 1.18 times; with the fused optimizer as well, 1.85 times (bars below).

One training step, eager against compiled

What it costs. Compile time: the first call of the compiled training step took 9.0 to 10.0 s with an empty cache and 0.86 to 1.04 s with a warm one, and every new input shape compiled again for 7.2 to 8.6 s until Dynamo marked the dimension dynamic measured on Apple M1 Pro. Memory: none saved here, AOTAutograd kept 34.81 MB against eager's 34.76 MB. Fragility: a print inside a block split the model into pieces, left the outer forward uncompiled and made the step 7 to 9% slower; switching to model.eval() under no_grad recompiled because a guard checks the grad mode. After recompile_limit (8 at 2.14.1) recompilations of one function, Dynamo gives up and runs it eagerly.

When it matters. On NVIDIA GPUs, where launches and memory traffic dominate small operations: the PyTorch team reported compile working on 93% of 163 open-source models and training 43% faster on average on an A100 (21% in float32, 51% with AMP) vendor, PyTorch team, 2023 (PyTorch 2.x). What transfers from this laptop is everything structural: the graph, guards, breaks, recompiles and the fused kernels' logic. What does not is the speed-up, and mode="reduce-overhead", which records CUDA graphs and does nothing here (CUDA only per its 2.14.1 docstring).

How to check. TORCH_LOGS="graph_breaks,recompiles" first; torch._dynamo.explain(fn)(*args) counts graphs and breaks; fullgraph=True turns the first break into an error; TORCH_LOGS=output_code prints what Inductor wrote; backend="aot_eager" runs Dynamo and AOTAutograd without Inductor, to tell which stage broke numerics.

torch.export and AOTInductor. torch.export is the strict sibling of Dynamo: it must capture one whole graph (no breaks allowed) and produces a portable program for deployment. AOTInductor compiles that program ahead of time into a shared library that runs without Python. The running example exported to 95 operations (329 core ATen operations after decomposition) and packaged into a 14.3 MB .pt2 file whose outputs matched eager within 1.3e-6 measured on Apple M1 Pro. 6. Performance: find the bottleneck, then fix that one

Most slow training jobs are slow for one reason, and the fastest way to find it is to measure where a step's time goes before changing anything. Split the step into its phases (forward, backward, optimizer), time each one honestly (warm up first, repeat, take medians, and on a GPU call torch.cuda.synchronize() before reading the clock, because GPU work runs asynchronously), and fix the largest one you can.

Nobody would guess that the optimizer, a few element-wise updates, costs a quarter of the step. Attention backends. F.scaled_dot_product_attention (SDPA) is one function with several implementations behind it; at 2.14.1 the SDPBackend enum lists FLASH_ATTENTION, EFFICIENT_ATTENTION, CUDNN_ATTENTION, MATH and OVERRIDEABLE read from the installed wheel. It picks the first one whose constraints the inputs meet (dtype, head size, mask, device). The fused backends never write the full sequence-by-sequence score matrix to memory, the idea of FlashAttention; the MATH backend does, and always works. On this laptop the CPU ran a flash-style CPU kernel, while MPS took the math path for the running example's shapes measured. Force or debug the choice with torch.nn.attention.sdpa_kernel([SDPBackend.FLASH_ATTENTION]): if the inputs do not qualify, the call fails ("No viable backend for scaled_dot_product_attention was found" on the CPU at 2.14.1, measured; on CUDA a warning also names the reason), instead of silently falling back to a slower backend.

FlexAttention (torch.nn.attention.flex_attention) covers the variants the fixed backends do not: you write a score_mod (change a score: relative bias, soft-capping) or a mask_mod (which query may see which key: sliding windows, documents packed into one sequence) as small Python functions, and torch.compile generates one fused kernel that skips fully masked blocks. Its authors measured 90% of FlashAttention-2's speed in forward and 85% in backward vendor, PyTorch team, 2024 (FlexAttention blog); it runs on Apple GPUs since 2.13 (2.13 release notes).

torchao is PyTorch's library for lower precision: quantized weights for inference, float8 and MX formats for training, sparsity. It works by replacing weights with tensor subclasses (section 8). Applied to the running example on the CPU, Int8WeightOnlyConfig turned each of 17 linear weights into an Int8Tensor (int8 data plus one float32 scale per row) and moved the first loss from 3.80137 to 3.8009 measured on Apple M1 Pro (Ecosystem map). On GPUs, its float8 training gave up to 1.5 times the throughput at 512 GPUs on a 405B model vendor, torchao README (torchao). For the largest single activation of a big-vocabulary LLM, the logits, 2.13 added nn.LinearCrossEntropyLoss, which fuses the output layer into the loss so the batch × sequence × vocabulary tensor is never stored ("up to 4x lower peak memory", release-note figure, 2.13 notes).

7. Distributed: the same program in several processes

The model. Distributed PyTorch runs one copy of your script per device. torchrun --nproc_per_node 8 train.py starts 8 processes and gives each a rank (0 to 7) and the world size (8); torch.distributed.init_process_group(backend) connects them through c10d, PyTorch's communication layer, using NCCL between NVIDIA GPUs or gloo on CPUs. The processes then cooperate only through collectives, operations every rank calls together: all-reduce (everyone ends with the sum), all-gather (everyone ends with everyone's pieces), reduce-scatter (sum, then each keeps one piece), broadcast (one rank's tensor to all). The rule that explains every hang: all ranks must call the same collectives, with the same shapes, in the same order.

Everything here was run for real: the running example on 2 and 4 CPU processes with gloo, every collective recorded by PyTorch's flight recorder (a per-rank log of recent collectives) measured on Apple M1 Pro, CPU, gloo, 1 thread per rank (Distributed lab). The theory of why these schemes save memory, and their communication volumes at scale, is on Distributed Training; this section is what PyTorch's APIs actually do.

DDP and FSDP2 on the same step

DDP (DistributedDataParallel) keeps a full copy of the model on every rank, gives each rank different data, and averages the gradients with all-reduces during backward, grouped into buckets so communication overlaps with the rest of backward. FSDP2 (fully_shard, since 2.4) splits every parameter across ranks; each rank keeps only its piece and the matching optimizer state, gathers a block's full weights just before using it, frees them after, and reduce-scatters the gradients so each rank receives only the part it owns.

Three things the measurements add to the textbook picture. DDP's first step puts every gradient in a single bucket and only then rebuilds buckets in the order gradients actually arrived (from step 1: 1,051,648 B, then 11,696,128 B), because the default 25 MiB cap applies only after that first pass (torch/nn/parallel/distributed.py at v2.14.1; Distributed lab, section 3). And on the tiny model, activations dominate, so sharding the weights saves less than the ratio of ranks suggests: the step's own peak is 43.9 MB on 2 and on 4 FSDP2 ranks, and only the persistent part shrinks; on the bigger variant, where weights and AdamW state are 303 MB per DDP rank, FSDP2 on 4 ranks cuts the peak from 548 MB to 249 MB.

A DTensor is a tensor plus a mesh plus one placement per mesh dimension: Shard(d) (split along dimension d), Replicate() (a full copy) or Partial() (each rank holds a part of a sum not yet added up). What a hang looks like

A rank that skips one all-reduce leaves the others waiting. With a 10-second timeout, both ranks failed with "Timed out waiting 10000ms for recv operation to complete", and the flight recorder showed why: at sequence number 4, rank 0 was in all_reduce while rank 1 was in barrier. The default timeouts are 10 minutes for NCCL and 30 minutes for other backends (init_process_group docstring at 2.14.1), so in production a hang looks like a silent job for ten minutes. A shape mismatch was caught at once with TORCH_DISTRIBUTED_DEBUG=DETAIL ("Detected mismatch between collectives on ranks ... Tensor shapes: 1000vs 999"), at the price of 2 extra all-gathers per collective, and monitored_barrier names the missing rank ("Rank 1 failed to pass monitoredBarrier in 5000 ms") measured, CPU, gloo (Distributed lab, section 11, has each case with its error text and flight-recorder entries).

Common mistakes

Timing GPU code without synchronising
GPU work is queued and returns at once; time.perf_counter() around it measures the launch. Synchronise before reading the clock, warm up, repeat, report medians (or use torch.utils.benchmark.Timer).
Calling .item() or printing the loss every step
Each one makes the CPU wait for the GPU, and under torch.compile it is a graph break (section 5). Log every N steps, or keep a running tensor and read it rarely.
Using no_grad to save memory while training
No graph, so no backward (section 3). Use activation checkpointing, a smaller micro-batch with accumulation, or sharding.
Assuming reshape never copies, or that view always works
view fails on non-contiguous tensors; reshape silently copies (section 1). In-place writes through a view change the original.
Accumulating gradients without dividing the loss, or without no_sync under DDP
The first gives a gradient N times too large; the second pays an all-reduce per micro-batch (sections 4 and 7).
Expecting torch.compile to speed up anything
On this laptop's CPU it gave nothing; on MPS 1.18 times. Measure; then check breaks and recompiles (varying shapes, eval() versus train(), Python scalars that change).
float16 without a GradScaler
Small gradients underflow to zero. Use bfloat16 where the hardware supports it, or torch.amp.GradScaler.
Moving a loop into a framework and expecting the same run
Defaults differ: the Hugging Face Trainer clips at 1.0, decays the learning rate linearly and shuffles (section 4).
A collective that only some ranks call
An if rank == 0: all_reduce(...), uneven data, or a different tensor shape on one rank hangs the job until the timeout (section 7).
Starting new work on torchtune, TorchScript or the FSDP1 wrapper
torchtune is no longer maintained, TorchScript is deprecated, and FSDP2's fully_shard is where the work goes (section 9).
Loading untrusted checkpoints with weights_only=False
A pickle can run code. Keep the default weights_only=True (since 2.6) or use safetensors.

Interview questions, with short answers

Why does x.t().view(-1) fail, and what does reshape do instead?
The transpose has strides (1, 4): its elements in order are not adjacent in storage, so no single stride can describe a flat view. reshape returns a view when possible and otherwise copies.
What happens between torch.mm(a, b) and the BLAS call?
The dispatcher computes the call's key set from the inputs and thread-local state and runs the highest-priority kernel: autocast may cast, autograd records MmBackward0 and saves inputs, a subclass's __torch_dispatch__ may run at the Python key, and the backend kernel finally calls BLAS.
no_grad or inference_mode?
Both stop graph recording. inference_mode also drops the autograd keys and version counters from new tensors, so it is a little faster, but those tensors cannot later be used in autograd. Use it for serving; no_grad for evaluation inside training code.
What takes memory in training a model with AdamW?
Parameters, gradients (same size), optimizer state (two more copies), and saved activations, which grow with batch and sequence length. Running example: 12.75 + 12.75 + 25.5 MB of model state against 34.76 MB of activations at batch 8 by 64.
How does activation checkpointing trade memory for compute?
It keeps only a region's inputs and re-runs the region in backward. Running example: 34.85 to 3.33 MB added by forward, 112 recomputed calls, 22.5 to 31.6 ms per step on the CPU.
Guards, graph breaks and recompiles: what are they?
Guards are the conditions under which a compiled graph is valid; when one fails, Dynamo recompiles (up to recompile_limit, 8). A graph break is Python Dynamo cannot capture: it ends the graph, runs eagerly, and starts a new one. Find both with TORCH_LOGS="graph_breaks,recompiles".
Why might torch.compile not speed a model up?
The time is in operations it does not change (large matrix multiplies already in cuBLAS or BLAS), the step is dominated by something else (data, the optimizer, communication), or breaks and recompiles eat the gain. Profile first.
for-loop, foreach or fused optimizer?
Same maths; the for-loop launches small operations per tensor, foreach batches each operation over all tensors, fused does the whole update in one kernel. Fused was 2.7 times faster than the default on this CPU and 4.1 times on MPS for the optimizer phase.
DDP or FSDP2?
See section 7: DDP keeps a full copy per rank and all-reduces gradients; FSDP2 shards every parameter and gathers it only when needed, cutting memory per rank for more communication.
What is a DTensor?
A tensor plus a device mesh plus one placement per mesh dimension (Shard(d), Replicate(), Partial()); operators propagate placements and insert the collectives needed. FSDP2, tensor parallelism and distributed checkpoints are built on it.
A multi-GPU job hangs. What do you do?
Find which rank is in which collective: the flight recorder dump (or py-spy on each rank), TORCH_DISTRIBUTED_DEBUG=DETAIL to catch mismatched shapes or order, then look for rank-dependent code paths and uneven data.
custom_op, autograd.Function or a tensor subclass?
autograd.Function to change a backward; custom_op to add an opaque operator that compile and export can treat as one node (with a fake implementation); a subclass to change what a tensor is (sharded, quantized).
Which stack for: pretraining from scratch on 512 GPUs; LoRA on one GPU; your own loop on Hugging Face models?
torchtitan (or Megatron Core on an NVIDIA-committed stack); PEFT with TRL, or Axolotl, or Unsloth for single-GPU speed; Accelerate (or Lightning Fabric).

1. A tensor is a view onto a storage

A tensor is a small header pointing into a flat block of memory. The block is the storage: just bytes, with a device (CPU, MPS, a CUDA GPU) and an element type, the dtype (float32 here: 4 bytes per number). The header holds the shape, a storage offset (where element [0, 0] sits) and one stride per dimension: how many elements to step in storage to move one along that dimension. Element [i, j] lives at offset + i·stride[0] + j·stride[1].

So many tensors can share one storage. A view (view, transpose, t, slicing, split, expand) makes a new header and copies nothing. A tensor is contiguous when its strides are the plain row-major ones for its shape; some operations (view itself, many kernels) need that, and .contiguous() copies into a fresh storage only when it is not.

Real tensors: x = torch.arange(12.).view(3, 4) and four tensors made from it. Pick one: the highlighted cells are the storage elements it reads, in its own order.

The model does exactly this in attention. One qkv Linear writes a (512, 768) block; view makes it (8, 64, 768); split cuts q, k and v as three views at storage offsets 0, 256 and 512, all with strides (49152, 768, 1); view and transpose turn each into (batch, head, position, 64) with strides (49152, 64, 768, 1). 2. The dispatcher: a table of kernels per key

Every PyTorch operation (torch.add, x.view, the addmm inside nn.Linear) is an operator registered under a name such as aten::addmm (ATen is PyTorch's C++ tensor library). An operator does not have one implementation. It has a table: one entry per dispatch key, where a key names one concern. CPU, MPS and CUDA are backends that do the arithmetic; AutogradCPU records what autograd needs for backward; ADInplaceOrView keeps view and in-place bookkeeping (version counters); Autocast casts to lower precision; Python hands the call to Python code such as a dispatch mode or a tensor subclass; Functionalize rewrites in-place ops for compilers.

Each tensor carries a dispatch key set. A parameter of the model on the CPU carries . For a call, the dispatcher takes the union of its tensors' key sets, adds the keys switched on for this thread (a dispatch mode adds Python), removes the ones switched off (inside the autograd kernel, the autograd keys; under inference_mode or with autocast off, those keys), and runs the kernel of the highest-priority remaining key. That kernel does its job and calls the operator again with its own key masked out, so the call walks down the table until a backend kernel does the arithmetic. A fallthrough entry means "nothing to do here, skip to the next key"; a math kernel (CompositeImplicitAutograd) means the operator is written in terms of other operators and decomposes before any backend sees it.

9. What carries over to NVIDIA GPUs, and what does not

Carries over

The op sequence and the graph. On a CUDA tensor the keys become AutogradCUDA and CUDA; the same Python code makes the same autograd nodes and the same saved tensors. Saved bytes at float32 are the same; under bf16 autocast most activations halve.

Carries over

The dispatch mechanics: math kernels decomposing, views costing nothing, no_grad against inference_mode, checkpointing's memory-for-compute trade and its early stop, the version counter.

Changes

Which kernels run. On CUDA, scaled_dot_product_attention picks FlashAttention or memory-efficient kernels (not the CPU flash kernel, not the MPS math path); linear decomposes as on the CPU and the matmul goes to cuBLAS. See Writing kernels for FlashAttention.

Changes

The optimizer default. On CUDA PyTorch picks foreach by default (here: the for-loop), and fused=True is one opt-in away. The for-loop reads the step counter with .item() once per parameter (adam.py L528); the counter lives on the CPU unless capturable=True or fused=True (L168), so by default that read is not a GPU sync. See Optimisers.

Does not carry over

Times. These are CPU and Apple-GPU times at a toy size, where per-call overhead in Python and the dispatcher is a large share (). On a GPU the same overhead shows up as launch gaps between short kernels: the case for torch.compile and CUDA graphs (Compile lab, Streams, CUDA graphs and multi-GPU).

Exact live bytes. CUDA's caching allocator rounds blocks up and keeps freed memory for reuse, so torch.cuda.memory_allocated is close to these numbers and memory_reserved is higher. See Memory allocators.

10. Common mistakes, and interview questions

Common mistakes

".view() and .reshape() are the same"
view never copies and fails when the strides do not allow it (try x.t().view(12): ). reshape returns a view when it can and silently copies when it cannot, so whether you got a copy depends on the input's layout.
".contiguous() always costs a copy"
Only when the tensor is not already laid out row-major. In this step it copied nothing on the CPU and 524,288 bytes per layer on MPS, for the same line of Python: the layout depends on which attention kernel produced the tensor.
"Memory is the parameters"
Here the parameters are 12.75 MB, AdamW's two moments 25.5 MB (twice the parameters, in float32), the gradients another 12.75 MB at their peak, and the activations kept for backward 34.8 MB. At real batch sizes and sequence lengths the activations dominate.
"no_grad and inference_mode are the same"
Both build no graph and keep nothing. no_grad still enters the autograd and view-tracking layers on every call; inference_mode skips them and makes inference tensors you cannot later use in a graph. On this toy forward the difference was within noise on both devices (section 6); the gain grows with the number of small ops.
"Checkpointing doubles the compute"
It reruns the forward of each checkpointed region once, during backward, and non-reentrant checkpointing stops each rerun as soon as it has rebuilt what backward needs (here 12 of the 16 addmm calls). Forward is about a third of a step's arithmetic, so the extra is about a third, not double; here the CPU step went from 22.5 to 31.6 ms.
"Modifying a tensor in place is always fine under torch.no_grad()"
If backward still needs that tensor (it is saved by some node), the in-place write bumps its version counter and backward raises "one of the variables needed for gradient computation has been modified by an inplace operation". That counter is what the ADInplaceOrView kernels maintain.
"Timing a step with time.time() around it is enough"
On MPS and CUDA the call returns before the GPU finishes. Synchronise first (here torch.mps.synchronize()), repeat, and report the spread; see Profiling, benchmarking and correctness.

Interview questions

What is the difference between a tensor and its storage?
The storage is the flat memory (bytes, device, dtype); the tensor is a view of it: shape, strides, storage offset. Views share storage; x.untyped_storage().data_ptr() tells you whether two tensors do.
Walk me through what happens when you call torch.add(a, b) on two CPU tensors that require grad.
The dispatcher builds the key set from both tensors and the thread state, runs the highest-priority kernel: AutogradCPU records an AddBackward0 node (with grad mode on) and redispatches with autograd masked out; ADInplaceOrView is a fallthrough for add; the CPU kernel allocates the output and computes it.
What does autograd save for y = x @ W.t() + b?
For the gradient wrt W it needs x; for the gradient wrt x it needs W. W is a parameter (no extra memory); x is an activation. The bias gradient is a sum over rows and needs nothing saved. In this step every AddmmBackward0 saved its input and the weight.
Why can backward use less memory than forward's peak, and when are gradients allocated?
Backward frees each node's saved tensors right after running it (unless retain_graph=True), while gradients appear as AccumulateGrad nodes run. Here live memory fell from +34.8 MB after forward to +12.8 MB after backward: the gradients, freed by zero_grad(set_to_none=True).
What is a CompositeImplicitAutograd op, and why does it matter for compilers and custom backends?
An op written in terms of other ops (here linear on CPU), so it needs no backward formula and no backend kernel of its own: it decomposes before autograd records anything. A backend may still register its own kernel to avoid the decomposition (MPS does for linear), and compilers see the decomposed ops.
How would you find which op allocates the most memory in a step?
On CUDA, torch.cuda.memory._record_memory_history() and the memory snapshot viewer; anywhere, a TorchDispatchMode that logs output storage sizes, as this tab does, or the profiler with profile_memory=True.

1. What torch.compile does, on this model

Eager mode is PyTorch's normal way of running: each Python line calls one operator, which runs one kernel right away and writes its result to memory (the Inside one step tab follows all 142 forward calls of this model that way). torch.compile(model) instead watches the Python code run once, turns it into a graph (a list of operations with their data dependencies), optimises the whole graph, and from then on runs generated code instead. Four pieces do it. Click one to jump to its section.

Two words appear everywhere below. A guard is a check Dynamo writes next to each compiled graph ("the input is int64 of shape (8, 64)", "grad mode is on"); on every call the guards run first, and if one fails the code is recompiled for the new situation. A graph break is a point where Dynamo cannot follow the Python (a print, a tensor turned into a Python number): it ends the graph there, runs that bit as ordinary Python, and starts a new graph after it. The mechanics of each piece, on small programs and with every log, are on The compiler stack: PTX, SASS, NVRTC, torch.compile and Inductor (sections 8 and 9 and its Inside torch.compile tab); this tab measures them on a whole training step.

2. Fusion: the same function, op by op and as one loop

Most operations in a model, other than matrix multiplies and attention, are pointwise (each output element depends on one input element: add, multiply, GELU) or small reductions (a row's mean, as in LayerNorm). In eager mode each one is its own kernel: it reads its inputs from memory and writes a full-size result back, and the next op reads that result again. Fusion merges a chain of them into one kernel that reads each input once, keeps the intermediate values in registers, and writes only the final result. The work done is the same; the memory traffic is not.

Interview questions


What are the stages of torch.compile, and what does each produce?
Dynamo: an FX graph of the forward plus guards, from the bytecode. AOTAutograd: a joint forward and backward graph traced on fake tensors, partitioned into a forward graph and a backward graph with a list of saved tensors. Inductor: fused kernels (Triton or C++) plus a Python or C++ wrapper that calls them and the library matmuls. At run time: check guards, run the wrapper.


What is a guard, and what happens when one fails?
A condition the compiled code assumes (dtype, shape, parameter identity, grad mode, ...), checked before each call. On failure Dynamo compiles again and caches both; a failed shape guard makes that dimension symbolic (automatic dynamic) so later sizes reuse it. Past recompile_limit (8) the function runs eagerly.


Name three causes of graph breaks and how to fix each.
print or logging (move it out, or register it as reorderable logging); .item() or data-dependent if (keep the value as a tensor, use torch.where, or torch.cond; capture_scalar_outputs for .item()); calls into non-PyTorch libraries on real data (do them outside, or wrap as a custom op).


Why does fusion help, and when does it not?
Pointwise and reduction chains are limited by memory traffic; fusing them reads and writes each tensor once instead of once per op (9x fewer bytes for the tanh GELU here). It does not help work that is already one kernel (matmuls, attention, ATen's LayerNorm), and the generated kernel can be slower than a hand-tuned one.


torch.compile versus torch.export: when do you use which?
compile for training and Python serving: just in time, tolerant of breaks, recompiles as needed. export for deployment: one whole graph or an error, explicit dynamic ranges, a serializable program for AOTInductor, ExecuTorch or ONNX.


What do reduce-overhead and max-autotune do?
reduce-overhead: CUDA graphs, removing per-kernel launch cost; needs static shapes and keeps a memory pool; CUDA only. max-autotune: benchmarks generated matmul templates against the library and keeps the fastest (plus CUDA graphs on a GPU); much longer compile.

    1. From one process to several
    

    Everything so far ran in one process: one Python interpreter with its own memory. Data-parallel training runs the same script in N processes at once, usually one per GPU, each holding its own copy (or slice) of the model. This is SPMD, single program, multiple data: the code is identical, the data and the rank differ. The rank is the process's number, 0 to N − 1; N is the world size.
    

    torchrun starts the N processes and gives each its identity through environment variables (RANK, LOCAL_RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT). Each process then calls torch.distributed.init_process_group(backend): they meet at a small key-value store on the master address (the rendezvous) and build a process group, the set of ranks that can talk. c10d is the PyTorch library that does this; its backends move the bytes: NCCL for NVIDIA GPUs, gloo for CPUs (and as a fallback), plus MPI and vendor libraries.

And fully_shard with no mesh tried to build one on the "current accelerator", which on a Mac is MPS, and failed with AttributeError: module 'torch.mps' has no attribute 'is_initialized' (_fsdp_init.py L198, device_mesh.py L496).     2. Collectives: the five verbs
    

    A collective is an operation every rank in a group calls together, each with its own tensor. Distributed training is built from five of them, plus point-to-point send and recv between two ranks. Pick one: the tensors before and after, on 4 ranks.

    The identity worth remembering: all-reduce = reduce-scatter + all-gather. Each half moves (n − 1)/n of the data per rank, so an all-reduce costs about twice either half. FSDP's whole design rests on doing the two halves at different times.

    3. DDP: one all-reduce per bucket, during backward
    

    DistributedDataParallel (DDP) keeps a full copy of the model on every rank and makes their gradients identical before each optimizer step, so the copies never drift apart. It does three things, all visible in the recording:
    

      

    1. At construction, it checks every rank has the same parameters and copies rank 0's weights to everyone. Recorded: an all-gather of 8 bytes (the parameter count), a broadcast of 1,120 bytes (the 52 parameters' sizes and strides, reducer.cpp L2422), then a broadcast of all 12,747,776 bytes of weights.
      2. 

    2. In backward, it groups the gradients into buckets. A hook on each parameter fires when its gradient is final; when every gradient in a bucket is final, DDP launches that bucket's all-reduce asynchronously and backward keeps computing the earlier layers. That is the overlap: communication of the last layers hides behind computation of the first.
      3. 

    3. Before the optimizer step, it waits for the last bucket and divides by the world size, so every rank holds the average gradient. Each rank then runs the same AdamW update on the same numbers.
      4. 

    

    Why buckets? One all-reduce per parameter would mean 52 small messages, each paying a fixed latency; one for the whole model could start only when backward ends, so nothing overlaps. The default cap is 25 MiB, with a smaller first bucket of 1 MiB so the first all-reduce can start early (distributed.py L31, L86). Buckets fill in reverse parameter order, because backward produces the last layer's gradients first.
    

    

    Predict. The model is 12.75 MB of float32 gradients, under one 25 MiB bucket but over the 1 MiB first bucket. How many all-reduces does DDP issue in the first backward?
    

    

    One. Recorded on both ranks: a single all-reduce of 12,747,776 bytes, issued only once every gradient was final, so nothing overlapped in step 0. Unless find_unused_parameters=True or an explicit bucket list is given, the first iteration puts everything in one bucket (a size limit of sys.maxsize, L151); during that iteration DDP records the order in which gradients actually arrived, and at the start of step 1 rank 0 broadcasts a new bucket layout in that order (the two small broadcasts of 212 and 8 bytes in step 1). From then on: two buckets, 1,051,648 and 11,696,128 bytes.

    4. FSDP2: every parameter split, gathered only when needed
    

    DDP's memory per rank never shrinks: 16 bytes per parameter of weights, gradients and Adam state on every rank (more with its buckets). FSDP (fully sharded data parallel) is PyTorch's version of ZeRO stage 3 (the theory is on Distributed Training, and the ZeRO paper page steps through DDP against ZeRO-3 on GPUs): each rank permanently keeps only 1/n of every parameter, its gradient and its optimizer state, and rebuilds a whole layer just before using it.
    

    FSDP2 is the current API, torch.distributed.fsdp.fully_shard (in PyTorch since 2.4; FSDP1, the FullyShardedDataParallel wrapper with flattened parameters, is still shipped at 2.14 without a formal deprecation notice: see Ecosystem map). fully_shard(module) turns each of the module's parameters into a DTensor (section 7) with placement Shard(0): rank r owns rows r·k to (r+1)·k of every weight. The model is wrapped the way torchtitan does it: fully_shard on each of the 4 blocks, then on the whole model, which picks up what is left (embeddings, final LayerNorm, tied output layer). Each call makes one unit: one all-gather brings its weights in, one reduce-scatter sends its gradients out.
    

    

    

    

    

    

    What happens in one step, per unit, in order:
    

      

    1. Forward: just before a block runs, all-gather its shards into full weights (here each rank sends 1.58 MB and receives the other rank's 1.58 MB); run it; then, by default, free the full weights again (reshard after forward), keeping only the activations.
      2. 

    2. Backward: all-gather the block's weights a second time (they were freed), compute its gradients, then reduce-scatter them: sum across ranks and leave each rank only its own 1/n slice. Free the full weights and full gradient.
      3. 

    3. Optimizer: AdamW runs on each rank's shards only, with no communication at all, because each rank owns the whole update of its rows.
      4. 

    

    reshard_after_forward defaults to None: True for the blocks, False for the root unit, "because the root module is typically required immediately when the backward pass begins" (_fully_shard.py L180). FSDP2 also prefetches: it issues the next unit's all-gather before the current unit finishes, which you can see below as all-gathers launched early. Setting it False everywhere skips all four backward all-gathers and keeps every block's full weights alive from forward to backward.
    

    Read the recording
    With the default, the last block is resharded at the end of forward and gathered again at once, because backward starts there (the "AG block 3" right after forward in the timeline below). torchtitan avoids exactly this: it does not reshard the final norm and output layer after forward "since FSDP would prefetch them immediately", and puts the tied embedding and output layer in one unit (torchtitan 0.3.0, distributed/fsdp.py L180), as the root unit does here.

    7. DTensor and DeviceMesh: placements, and what changing them costs
    

    FSDP2, tensor parallel and distributed checkpoints are all built on one abstraction. A DeviceMesh arranges the ranks in a grid: 4 ranks as a line of 4, or as 2 × 2 (say, data parallel along one axis and tensor parallel along the other). A DTensor is one logical tensor spread over a mesh, described by one placement per mesh dimension:
    

      

    • Shard(d): split along tensor dimension d; each rank holds one piece (like torch.chunk, so 6 rows over 4 ranks gives  rows: the last rank can be empty).
      • 

    • Replicate(): every rank holds the whole tensor.
      • 

    • Partial(): every rank holds a full-shape tensor, and the real value is their sum (a pending reduction). This is what a row-split matrix multiply produces before its all-reduce.
      • 

    

    Every operation on DTensors either works locally or needs a redistribute, which is a collective. Knowing which placement change needs which collective is most of what tensor parallelism is. The local values are computed in the page from the placements and were checked against the recorded local tensors of every rank in every pair.     8. Tensor parallel: split the matrices, not the batch
    

    Tensor parallelism (TP) splits each weight matrix across ranks that all see the same batch. The Megatron-LM recipe for an MLP, which PyTorch exposes as ColwiseParallel and RowwiseParallel in torch.distributed.tensor.parallel: split the first Linear by output columns (each rank computes half of the 1,024 hidden units, and GELU works on its half alone), split the second by input rows (each rank multiplies its half and gets a Partial sum), then one all-reduce adds the halves. Backward mirrors it: one all-reduce of the input gradient. The maths and its cost model are on Distributed Training and the Megatron-LM paper page.
    

    

    

    

    

    

    The same plan on the fused attention projection fails
    The model computes q, k and v with one Linear of 768 outputs laid out as [all of q | all of k | all of v]. ColwiseParallel on it gives rank 0 rows  (all of q and half of k) and rank 1 the rest, and the forward fails at once: ValueError: not enough values to unpack (expected 3, got 2), because a 384-wide local output cannot be split into three 256-wide pieces. Column-splitting needs whole heads on each rank. torchtitan's fused projection is laid out head-group by head-group for exactly this reason ("Compatible with ColwiseParallel on the wqkv linear layer", torchtitan 0.3.0 attention.py L785), and its unfused version shards wq, wk, wv separately. The parallel plan is a property of the model's layout, not only of the module types.

    11. What a hang looks like
    

    A collective only completes when every rank in the group calls it, with matching sizes. If one rank skips it, calls a different one, or is stuck elsewhere, the others wait. On GPUs that wait is a hang: no error, no progress, GPUs at full utilisation spinning, until a timeout fires (by default 10 minutes for NCCL, 30 for other backends, ProcessGroupNCCL.hpp L159, Backend.hpp L37). The usual causes: a rank-dependent branch around a collective (logging, evaluation, an early break), a data loader giving ranks different numbers of batches, a parameter unused on one rank, or a crash on one rank that the others never hear about. Three were caused on purpose here, with a 10-second timeout:
    

    

    

    

    

    How to read one. The flight recorder is the first thing to look at: every rank's last collectives with their sequence numbers. Find the first sequence number at which the ranks disagree (different operation, different sizes, or one rank missing it); the code that issued it on the odd rank is the bug. On NCCL, TORCH_NCCL_DUMP_ON_TIMEOUT=1 makes the watchdog write each rank's record when the timeout fires, and torchfrtrace (the analyser shipped with PyTorch, torch.distributed.flight_recorder.fr_trace) lines them up across ranks; NCCL also tracks each entry's state (scheduled, started, completed), which gloo does not (every entry here stays "scheduled").     13. What carries over to NVIDIA GPUs, and what does not
    

    

    Carries over
    Which collectives, in which order, of which sizes. DDP's bucket layout and rebuild, FSDP2's all-gather and reduce-scatter per unit with prefetch, TP's two all-reduces per MLP, the pipeline schedules' send/recv order and DCP's planning are backend-independent Python and C++ above the backend.
    

    Carries over
    Memory per rank, in kind. What is sharded and what is not: FSDP shards weights, gradients and optimizer state, never activations; 1F1B holds fewer micro-batches than GPipe. Absolute numbers change with bf16 (half the bytes), the CUDA caching allocator (Memory allocators) and NCCL's own buffers.
    

    Changes
    Reduce-scatter. NCCL has a real one, moving half the bytes of gloo's all-reduce substitute and needing no full-size temporary, so FSDP's gradient step is cheaper on GPUs than here. FSDP's total traffic is about 1.5 times DDP's on NCCL (the Distributed Training formula) and 2 times here.
    

    Changes
    Overlap. On GPUs, collectives run on their own CUDA stream next to compute, so DDP's buckets and FSDP's prefetched all-gathers really overlap; on CPU with one thread per rank, gloo's work competes for the same cores. Streams, CUDA graphs and NCCL are on Streams, CUDA graphs and multi-GPU; link speeds on Interconnects and scaling.
    

    Does not carry over
    Times and speedups. Loopback TCP between processes on one laptop is nothing like NVLink or InfiniBand; neither is a CPU matmul like a GPU one. Published GPU scaling comes from the torchtitan paper and PyTorch's own posts, quoted on Distributed Training.
    

    Does not carry over
    How hangs look. On gloo a mismatched size crashed one rank at once; on NCCL the same bug usually hangs silently until the watchdog's timeout, which is why the flight recorder and TORCH_NCCL_DUMP_ON_TIMEOUT exist.
    

    

    


    

    14. Common mistakes, and interview questions
    

    Calling a collective inside if rank == 0:
    Logging a metric with an all-reduce, saving a checkpoint, or running evaluation on rank 0 only: every rank must reach every collective in the same order. It is the "skip" case above. Do the collective on all ranks and print on one.
    

    Expecting DDP to overlap from the first step
    Step 0 uses one bucket for everything (recorded above) and the layout is rebuilt in arrival order during step 1. Benchmark from step 2 or later.
    

    Using a fused projection with a column-parallel plan
    The plan has to match the weight's memory layout: a [q | k | v] layout split down the middle gives one rank all of q. It failed loudly here; with other shapes it can run and silently compute the wrong thing.
    

    Thinking FSDP shrinks activations
    It shards model state only. Going from 2 to 4 FSDP2 ranks left the step's own peak unchanged (section 6). Use activation checkpointing, or split the sequence or the matrices.
    

    Saving an FSDP model with torch.save(model.state_dict())
    Each rank's state dict holds DTensor shards. Use DCP (section 10), or gather to a full state dict on purpose with get_model_state_dict(..., options=StateDictOptions(full_state_dict=True, cpu_offload=True)) for small models.
    

    Tied weights across pipeline stages, or a different initialisation per rank
    Copies of one parameter on different ranks need their gradients summed (section 9). And every rank must start from the same weights: DDP broadcasts rank 0's at construction, FSDP2 does not (it shards whatever each rank has), so seed the initialisation identically or load from a checkpoint.
    

    Interview questions
    

    How does DDP overlap communication with backward?
    Gradients are grouped into buckets in reverse parameter order; a hook fires as each gradient becomes final, and when a bucket is complete its all-reduce is launched asynchronously while backward continues on earlier layers. The optimizer waits for the last bucket. Default cap 25 MiB, first bucket 1 MiB, layout rebuilt after the first iteration in the order gradients actually arrived.
    

    What does FSDP2 communicate in one step, and how does that compare with DDP?
    Per unit: an all-gather of the weights before forward, another before backward (unless reshard_after_forward=False), and a reduce-scatter of the gradients. In ring terms that is about 3 × (n − 1)/n of the model per rank against DDP's 2 × (n − 1)/n, so 1.5 times the traffic, for model-state memory divided by n.
    

    What is a DTensor placement, and what does Partial mean?
    One placement per mesh dimension: Shard(d) splits along tensor dim d, Replicate copies, Partial means each rank holds a summand of the real value. Partial to Replicate is an all-reduce, Partial to Shard a reduce-scatter, Shard to Replicate an all-gather.
    

    Why is tensor parallelism kept inside one server?
    It needs an all-reduce of activations in every layer, forward and backward, on the critical path (8 per step on this 4-block model), so it wants NVLink-class bandwidth; data parallel communicates once per step and can overlap, so it tolerates slower links.
    

    1F1B against GPipe?
    Same bubble for the same number of micro-batches and stages, same gradients, same communication; 1F1B starts backwards early, so the first stage holds at most (number of stages) micro-batches of activations instead of all of them. Measured here: rank 0's peak 21.1 MB with GPipe, 16.8 MB with 1F1B.
    

    A job hangs at step 3,000 on 512 GPUs. What do you do?
    Get every rank's flight-recorder dump (TORCH_NCCL_DUMP_ON_TIMEOUT=1, then torchfrtrace), find the first sequence number where ranks disagree or a rank is missing, then look at that rank's Python stack (py-spy dump) to see what it was doing instead. Check data loader lengths and rank-dependent branches; reproduce small with TORCH_DISTRIBUTED_DEBUG=DETAIL.
    

    How do you resume a 64-GPU FSDP run on 32 GPUs?
    Save with DCP; load with DCP into the new 32-rank sharding. The metadata maps every saved chunk to its offsets, and each new rank reads the chunks that overlap its new shard (done here: 4 ranks to 2 and to 1, identical weights).

    Same step, five doors
    

    Start with the idea the whole map rests on. A training step is always the same four things: run the model forward to get a loss, run loss.backward() to get gradients, call optimizer.step() to change the weights, and clear the gradients. A plain PyTorch loop writes those four lines itself. A trainer (Lightning, the Hugging Face Trainer) writes them for you inside its own loop, with callbacks, logging and checkpointing around them. A launcher wrapper (Accelerate) leaves your loop alone and instead swaps your model for the right core class for how you launched the job. None of them has its own maths: the forward still ends in your nn.Module, and the weights still change in torch.optim.
    

    Predict: the same tiny GPT, same seed, same three batches, trained through a plain loop, Lightning 2.6.6, the HF Trainer 5.19.0 and Accelerate 1.15.0. How do the three losses compare?

    What the stacks teach. The plain loop reaches the model in 5 frames. Lightning takes 31, and the surprise is where: the model's forward runs inside optimizer.step, because Lightning passes a closure (a function that computes the loss and the gradients) to the optimizer and the optimizer calls it, the API L-BFGS needs. The HF Trainer adds 5 frames (train, _inner_training_loop, _run_epoch, training_step, compute_loss). Accelerate on one process adds none: prepare() handed back your own model.
