5. Tensor subclasses: changing what a tensor is

The problem. Some extensions are not a new computation but a new kind of tensor: weights stored as int8 with a scale, a tensor split across eight GPUs, a float8 tensor that remembers its scaling factor. You want the model code unchanged (F.linear(x, w) stays F.linear(x, w)) while every operation on w does the right thing for its representation. A tensor subclass is a Python subclass of torch.Tensor that gets a say in every operation on its instances.

5.1 Two places to intercept: __torch_function__ and __torch_dispatch__

A call such as F.linear(x, w) passes two points where a subclass can step in. __torch_function__ is called first, at the Python API, with the function you called (linear, Tensor.add, Tensor.backward), before autograd or the dispatcher. __torch_dispatch__ is called much later: the dispatcher reaches the Python key after autocast, autograd and view tracking have run, and hands over the ATen operator (PyTorch's C++ operator library) that is about to execute: aten::t and aten::addmm rather than linear, because linear decomposed on the way (sibling page 2.4).

The __torch_function__ subclass saw the Python-level calls from the weight's first use onward, because its results are of its own type and so spread through the forward, and in backward only Tensor.backward itself. The __torch_dispatch__ subclass that rewraps its outputs saw every ATen call downstream of the weight in both directions; the one that returns plain tensors saw only the operations that touch the weight itself. The {{Subclass tracer|#t-ext-sub}} tab replays all three call by call.

5.2 Wrapper subclasses: a tensor with no storage of its own

A wrapper subclass is created with torch.Tensor._make_wrapper_subclass(cls, shape, dtype=..., device=...): the outer object has a shape, a dtype and a device, so the rest of PyTorch treats it as a tensor of that shape, but it has no data. The real data lives in ordinary tensors stored as attributes (self.qdata, self.scale), and __torch_dispatch__ decides, per ATen operator, what to compute from them. Its key set gains Python and PythonTLSSnapshot ( for the DTensor below), which is what routes every call to your Python code.

Two decisions shape every such subclass. Contagious or not: does an operation on the subclass return the subclass (DTensor: a sharded result) or a plain tensor (an int8 weight: the matmul's output is ordinary float32)? And which operators to implement: the rest fall back to "dequantize and run the normal kernel" or to an error. One rule is not optional: nn.Parameter refuses a subclass whose detach() does not return the subclass:

5.3 Build one: int8 weights for the running example

The subclass below stores each block weight as int8 qdata (same shape) and one float32 scale per output row (symmetric, per-channel: scale = max|w_row| / 127). It implements four ATen operators: the transpose and detach that nn.Linear and nn.Parameter need, addmm for the forward and mm for the backward's input gradient. The scale factors out of the matrix multiply, so the int8 values are multiplied first and the scale applied per output column afterwards. Full file: src/exp/subclasses_int8.py.

class Int8Weight(torch.Tensor): @staticmethod def __new__(cls, qdata, scale, transposed=False): shape = qdata.shape[::-1] if transposed else qdata.shape return torch.Tensor._make_wrapper_subclass(cls, shape, dtype=scale.dtype, device=qdata.device, requires_grad=False) def __init__(self, qdata, scale, transposed=False): self.qdata, self.scale, self.transposed = qdata, scale, transposed def __tensor_flatten__(self): # for torch.compile (5.4) return ["qdata", "scale"], (self.transposed,) @staticmethod def __tensor_unflatten__(inner, meta, outer_size, outer_stride): return Int8Weight(inner["qdata"], inner["scale"], meta[0]) __torch_function__ = torch._C._disabled_torch_function_impl @classmethod def __torch_dispatch__(cls, func, types, args=(), kwargs=None): if func is aten.t.default: # W.t(): flip a flag, move no data return Int8Weight(args[0].qdata, args[0].scale, not args[0].transposed) if func is aten.addmm.default and isinstance(args[2], Int8Weight): bias, x, w = args[:3] # x @ W^T + b, W = q * s[:, None] return torch.mm(x, w.qdata.to(x.dtype).t()) * w.scale + bias # ... aten.detach, aten.mm (backward), and a dequantizing fallback ...

5.4 Under torch.compile: flatten, trace, desugar

The compiler cannot keep a Python object inside a graph. It needs to know which tensors the subclass is made of, so that it can pass them in as ordinary graph inputs and rebuild the subclass while tracing. That is the traceable-subclass protocol: __tensor_flatten__ returns the names of the inner tensors plus any non-tensor metadata, and __tensor_unflatten__ rebuilds the object from them. With it, Dynamo traced the int8 model into graph with breaks, and AOTAutograd ran __torch_dispatch__ on fake tensors and recorded what it did in plain ATen: the subclass disappears from the compiled graph (desugaring). 5.5 How the real ones are built

The same protocol underlies the subclasses you will meet in practice. Each was built here on block 0's fc.weight (1024 × 256 float32, 1,048,576 bytes) and taken apart with __tensor_flatten__:

  • DTensor (PyTorch's distributed tensor, the base of FSDP2 and tensor parallelism) keeps the local shard and the device mesh as its inner parts and the placements as metadata. At 2.14.1 it is built in C++, sharing the wrapper-subclass helper, and its operators take a C++ fast path that only falls back to Python for sharding rules it has not cached; the Python __torch_dispatch__ only serves subclasses of DTensor:
    It refuses to mix with plain tensors rather than guess a placement: The {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}} sibling owns how its placements propagate.
  • NF4Tensor (torchao; the 4-bit format of QLoRA) packs two 4-bit codes per byte plus double-quantized scales: 135,300 bytes for the 1 MiB weight. Its __torch_dispatch__ handles a table of ATen operators, and its docstring says the linear itself goes through an autograd.Function instead; its __torch_function__ looks F.linear up in a second table:
  • Float8TrainingTensor (torchao float8 training) holds float8 e4m3 data and one float32 scale; its operators come from a table (FLOAT8_OPS_TABLE). A matrix multiply of two of them ran on this CPU (); the speed-up is a GPU matter (H100-class float8 tensor cores), not measured here.

Subclasses and FSDP2. A subclass can also tell FSDP2 what to send over the network. When FSDP2 shards a parameter whose inner tensor defines fsdp_pre_all_gather and fsdp_post_all_gather, it all-gathers whatever the first returns (the compact data) and rebuilds the full weight with the second.
