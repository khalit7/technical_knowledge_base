The idea in one screen

Every way of extending PyTorch plugs your code into one slot on the path a call already takes, and autograd, torch.compile and torch.export keep working only if you also hand PyTorch the three facts it cannot read from opaque code: the output's shape (a fake), the gradient, and what the code writes.

Fig. 1, step by step: one call path, six slots to plug into; the three facts highlighted

  1. One call, a stack of keys. ext::gelu2(x), the page's operator with a C++ kernel for the CPU and a Metal one for the Apple GPU (section 1.6), enters at the top. The dispatcher walks its keys in order; a key with a kernel registered for this operator runs it, a key without one passes the call down.
  2. Python API: __torch_function__. Before anything else, a tensor subclass or a TorchFunctionMode sees the Python function you called (F.linear, Tensor.add), above autograd (section 5.1).
  3. Autograd: fact 2, the gradient. register_autograd fills this slot (Autograd[alias] in the operator's recorded table): it records the backward node, so loss.backward() knows the op's gradient.
  4. ADInplaceOrView: fact 3, what the op writes. Version counters and views. The schema's mutates_args decides whether the op has a kernel here; ext::gelu2 writes nothing, so the slot is empty and the call passes through.
  5. Python key: __torch_dispatch__. Tensor subclasses and dispatch modes receive the ATen operator here, below autograd (sections 5 and 6). Plain tensors skip it.
  6. The kernel for the device. A CPU tensor runs the C++ kernel at CPU, an MPS tensor the Metal kernel at MPS: one operator, one kernel per device (register_kernel, TORCH_LIBRARY_IMPL; Triton and Helion kernels plug in the same way, section 4).
  7. Under compile: fact 1, the output's shape. torch.compile and torch.export trace with fake tensors, so the call goes to Meta, where register_fake returns an empty (8, 64, 1024) output: a shape, no data.

The dispatcher's keys in their real order, simplified ({{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}} walks all of them, Reading 2.2). The kernels drawn at the bottom are the ones in ext::gelu2's table as recorded with torch._C._dispatch_dump (CPU, MPS, Meta and Autograd; closed block in 1.6).

The running example. The parent topic's 3,186,944-parameter character-level GPT ({{Topic: pytorch-ecosystem|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}}, defined once in the root's src/model/), changed in two ways: the GELU in every block's MLP becomes your own kernel (C++, then Metal, then Helion), and the block weights become an int8 tensor subclass.

New terms

  • Operator: a named function the dispatcher knows (aten::addmm, or yours, ext::gelu), with a schema, a one-line signature such as ext::gelu(Tensor x) -> Tensor.
  • Fake (meta) implementation: computes the output's shape, dtype and strides without data; what the compiler traces with.
  • Graph break: where torch.compile stops a graph, runs Python, and starts a new one.
  • opcheck: torch.library.opcheck, four tests that the three facts are true.
  • Wrapper subclass: a tensor with a shape but no storage, whose data lives in inner tensors.
  • Dispatch mode: a context manager that sees every ATen call in a region.
