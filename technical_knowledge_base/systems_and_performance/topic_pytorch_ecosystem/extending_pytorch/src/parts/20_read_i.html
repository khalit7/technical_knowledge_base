Common mistakes

Calling your kernel directly instead of through an operator
Works in eager, then costs you three graph breaks, export, and silently the gradients of everything before it: in the running example of 52 parameters were trained, with no error. Wrap it in custom_op.
Registering the fake or the autograd formula late
Register at import, next to the definition. Registering after the op has been traced left the compiled backward without gradients in that process (section 2.3), and the broken artifact was then served from the AOTAutograd cache to later, correct processes.
Trusting a warm compile cache after changing registrations
Clear TORCHINDUCTOR_CACHE_DIR (or set TORCHINDUCTOR_AUTOGRAD_CACHE=0 while developing) whenever a fake, a formula or a kernel's registration changes. Keep one test that compares compiled gradients with eager on a batch.
A fake that reads data, or returns the wrong shape
The fake runs on tensors with no data: it may look at shapes, dtypes and devices only. For a data-dependent size use get_ctx().new_dynamic_size(). A wrong shape makes compile fail one layer later with an error about the next operator; opcheck's test_faketensor names the real one.
Writing into an input without declaring it
List every mutated argument in mutates_args. The compiler relies on the schema to reorder and reuse memory; opcheck catches the lie only when the test inputs are actually changed.
Returning an input (or a view of it) from a custom op
Not allowed: outputs must be fresh tensors. Return x.clone() if the result equals the input.
Assuming one op means one numerical result on every device
Each device has its own kernel. The Metal GELU here used the tanh approximation (Metal has no erf) and differed from the CPU kernel by ; opcheck does not compare devices.
Expecting a custom C++ kernel to be fast because it is C++
The straightforward loop here was about 11 times slower than F.gelu (scalar, single-threaded). Benchmark against the ATen operator you replace, on your shapes, before shipping it.
Expecting Inductor to fuse through a custom op
It cannot see inside: the op is a call between generated kernels, with metadata checks around it. Leave small element-wise work in PyTorch, or use triton_op.
A wrapper subclass whose detach() returns a plain tensor
nn.Parameter refuses it. Handle aten.detach (and usually aten.t, aten._to_copy, aten.clone) by returning the subclass.
Expecting __torch_function__ to see backward
Autograd's engine calls C++ directly. A __torch_function__ subclass saw call in backward (Tensor.backward itself); use __torch_dispatch__ or a dispatch mode to see backward's operations.
Two copies of a TORCH_LIBRARY in one process
The process aborts with no Python traceback. Use one extension per namespace, TORCH_LIBRARY_FRAGMENT for extra definitions.

Interview questions, with short answers

What does torch.library.custom_op give you that calling a C++ function does not?
A dispatcher operator: a schema, kernels per device, a fake implementation for tracing, an autograd formula, version bumps for mutation. So autograd, torch.compile (one node, no break), torch.export and dispatch modes all work with it (and vmap, once you add register_vmap).
What is a fake (meta) implementation and why does the compiler need it?
A function computing the output's metadata (shape, dtype, device, strides) from the inputs' metadata, without data. Dynamo and export trace with fake tensors, so they must know every operator's output without running it.
How do you handle an op whose output size depends on the data?
In the fake, allocate with a size from torch.library.get_ctx().new_dynamic_size(): an unbacked symbolic integer, carried as u0 through the graph with run-time checks.
Why must a custom op's schema declare mutation, and what does Tensor(a!) mean?
Functionalization and Inductor reorder and reuse buffers assuming the schema is honest. Tensor(a!) names an alias set a and marks it written.
custom_op or triton_op?
custom_op for opaque kernels (C++, CUDA, other libraries); triton_op when the body is Triton launches, so Inductor can see and optimise the kernels. Under export, both stay one node.
What does opcheck test?
Schema honesty (mutation and aliasing), that an autograd kernel is registered, that the fake matches the real kernel's metadata, and that forward and backward trace through AOTAutograd with dynamic shapes and match eager.
__torch_function__ vs __torch_dispatch__?
The first intercepts Python API calls (above autograd; sees linear; no backward). The second intercepts ATen operators at the Python dispatch key (below autograd; sees t and addmm, including backward's operations). Representation subclasses (DTensor, torchao) use the second.
What is a wrapper subclass, and how does torch.compile handle one?
A tensor with metadata and no storage, whose data lives in inner tensors. With __tensor_flatten__ and __tensor_unflatten__ the compiler passes the inner tensors as graph inputs and desugars __torch_dispatch__ into plain ATen operations.
Why might weight-only int8 not speed anything up?
If the kernel converts the weight to float before the matmul (as on the CPU path here), only memory at rest shrinks. Speed needs a kernel that reads int8 and dequantizes on the fly, and pays off where the matmul is memory-bound.
How is DTensor implemented?
A tensor subclass holding the local shard and the device mesh, with placements as metadata. At 2.14.1 its constructor and op dispatch run in C++ (a fast path with cached sharding propagation), falling back to Python sharding rules.
You added register_autograd but compiled gradients are still missing. What do you check?
Whether the op was traced before the registration (register at import), whether a stale compile cache is serving an old artifact (clear it or disable the AOTAutograd cache), and opcheck's test_aot_dispatch_dynamic.
How would you add support for a new accelerator?
Out of tree through the PrivateUse1 key: kernels via TORCH_LIBRARY_IMPL(aten, PrivateUse1, ...), a renamed device, an allocator, streams, and a compiler backend; torch_openreg in PyTorch's tests is the reference.
