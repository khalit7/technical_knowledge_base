6. Dispatch modes: watch or change every operation in a region

A dispatch mode is the subclass idea without a subclass: a context manager whose __torch_dispatch__ is called for every ATen operation run inside the with block, whatever tensors it touches (the sibling page records one call key by key this way, Reading 2.2). PyTorch ships several; three on the running example.

FakeTensorMode: run the model with no data. Inside the mode, new tensors and parameters are fake, so the whole model ran and produced logits of shape without computing a number (how you check a 70-billion-parameter model's shapes on a laptop), but it cannot answer a question about values: loss.item() raised .

FlopCounterMode: count the arithmetic from a formula per operator. One forward and backward of the running example: FLOPs, exactly 6 × 3,156,736 × 512: six FLOPs per weight per token for every matrix-multiply weight (the 3,145,728 in the blocks plus the 11,008 of the head; the embeddings are lookups), over 512 tokens. The textbook "6 × parameters × tokens" with all 3,186,944 parameters gives . Your own operators count zero until you register a formula with register_flop_formula, and so did the CPU attention kernel (closed block). How FLOPs turn into utilisation (MFU) is on {{Performance math|n:3c65c17b0d0d81faad1ef390b0e54d08}}.

Two gaps in the FLOP count: CPU attention and your own operators

The CPU attention kernel (_scaled_dot_product_flash_attention_for_cpu) has no formula, so attention counted zero; written out by hand (attn="manual") its batched multiplies add .

from torch.utils.flop_counter import register_flop_formula @register_flop_formula(torch.ops.ext.gelu) # register before creating FlopCounterMode def _(x_shape, *, out_shape=None): return 8 * math.prod(x_shape) # your estimate per element

(Building the model inside FakeTensorMode needs care with tied weights: the root's make_model fails there because .to() cannot swap the tied embedding, as the sibling page found; constructing GPT(cfg) directly works.)

Your own mode. Twelve lines record every call (the parent's {{Inside one step|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab is built this way):

from torch.utils._python_dispatch import TorchDispatchMode class Recorder(TorchDispatchMode): def __init__(self): super().__init__(); self.calls = [] def __torch_dispatch__(self, func, types, args=(), kwargs=None): self.calls.append(str(func)) return func(*args, **(kwargs or {})) with Recorder() as r: loss = model(x, y)[1]; loss.backward()

A TorchFunctionMode does the same at the Python API level (above autograd), and CommDebugMode counts collectives on DTensors (the parent's Distributed lab uses it). Cost: every call goes through Python. The sibling page measured 4.818 µs for a one-element add inside a dispatch mode against 0.622 µs without; use modes for tools and tests, not in a timed loop.

Depth: new devices, NVIDIA GPUs and interview rehearsal

New devices: PrivateUse1, briefly

A hardware vendor whose chip is not in PyTorch adds it without forking PyTorch through a reserved dispatch key, PrivateUse1. They register kernels at that key from a C++ extension (as in section 3, with TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) for ATen operators), give the device a name with torch.utils.rename_privateuse1_backend("npu") (), add tensor methods such as .npu() with generate_methods_for_privateuse1_backend(), and plug in an allocator, streams and a compiler backend. PyTorch keeps a complete reference device in its own tests, torch_openreg (test/cpp_extensions/open_registration_extension/ at the v2.14.1 tag). Not run here: a device needs a C++ runtime, and nothing on this page depends on it. Most readers meet it through a vendor's plugin package, not by writing one.

What carries over to NVIDIA GPUs, and what does not
  • Carries over unchanged: everything about registration and composition. Schemas, fakes, autograd formulas, opcheck, graph counts and breaks, export behaviour, the late-registration and cache traps, the subclass protocol and what reaches __torch_dispatch__: these are device-independent dispatcher and compiler logic.
  • Changes: the kernels. On CUDA you register at the CUDA key, write the kernel in CUDA C++ (CUDAExtension) or Triton (triton_op), and Helion's default Triton backend with its autotuner applies; none ran here. Inductor around an opaque op on a GPU loses fusions that matter more than on a CPU (each unfused element-wise op is a full round trip through GPU memory).
  • Changes: every timing on this page. Per-call overheads (3 to 4 µs for a Python-registered op, measured here) are paid on the CPU before every GPU launch as well, so many small custom ops hurt there too ({{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}} shows how to see it); but a weight-only int8 or float8 kernel that reads the compact format directly is a GPU speed-up that the CPU path here does not show.
