0. In one screen: adding what PyTorch does not ship

Sooner or later a training job needs something PyTorch does not have: a kernel you wrote (in C++, CUDA, Metal, Triton or Helion), a call into a library that is not PyTorch, a new number format for weights (int8, NF4, float8), a tensor that lives on several devices at once, or a tool that watches every operation. PyTorch has a hook for each. They differ in three ways that this page measures: what they can change, whether autograd, torch.compile and torch.export keep working, and what they cost.

The page follows the parent topic's running example, a 3,186,944-parameter character-level GPT (Topic: pytorch-ecosystem, defined once in the root's src/model/), and changes two things in it. First, the GELU inside every block's MLP is replaced by your own kernel: a 50-line C++ GELU, then a Metal one, then a Helion one, each plugged in a different way. Second, the block weights are replaced by an int8 tensor subclass. Every result below comes from running those changes: graph counts, test results, errors, timings.

Three terms first. An operator is a named function the dispatcher knows (aten::addmm, or yours, ext::gelu), with a schema: a one-line type signature such as ext::gelu(Tensor x) -> Tensor. The dispatcher keeps, for each operator, a table of kernels (implementations) indexed by dispatch key (CPU, MPS, Autograd, Python, Meta and others) and, on every call, walks the keys that apply. The sibling page Tensors, the dispatcher and autograd takes that machine apart; here we only plug things into it.

1. Custom operators with torch.library

The problem. You have a kernel PyTorch cannot see inside: compiled C++, a Metal or CUDA kernel, a call into another library. Called as a plain Python function, it works in eager mode, but three things break silently or loudly: autograd does not know its gradient, torch.compile cannot trace through it, and torch.export cannot put it in a graph. A custom operator fixes all three by making your function a first-class entry in the dispatcher, like aten::addmm, and by telling PyTorch the three facts it cannot work out by itself.

1.1 Defining one, line by line

Here is the operator the running example uses, exactly as run (src/exp/custom_ops.py). EXT.raw_gelu is the C++ function of section 3; any opaque function would do.

import torch from torch import Tensor # 1. the operator: namespace::name, the kernel, and what it mutates @torch.library.custom_op("ext::gelu", mutates_args=()) def gelu(x: Tensor) -> Tensor: return EXT.raw_gelu(x) # opaque: C++ through pybind11 # 2. the fake: output metadata without running the kernel @gelu.register_fake def _(x): return torch.empty_like(x) # 3. the gradient: its own operator (with its own fake), so compile can trace backward too @torch.library.custom_op("ext::gelu_bwd", mutates_args=()) def gelu_bwd(grad: Tensor, x: Tensor) -> Tensor: return EXT.raw_gelu_backward(grad, x) @gelu_bwd.register_fake def _(grad, x): return torch.empty_like(x) def setup_context(ctx, inputs, output): # runs after forward: save what backward needs (x,) = inputs ctx.save_for_backward(x) def backward(ctx, grad): # one gradient per input (x,) = ctx.saved_tensors return gelu_bwd(grad, x) gelu.register_autograd(backward, setup_context=setup_context) # 4. the test torch.library.opcheck(gelu, (torch.randn(4, 8, 32, requires_grad=True),))

The dispatcher does not read Python annotations; it needs a schema string. custom_op writes it for you from the type hints with torch.library.infer_schema. What it produced for six signatures, and the error for one it cannot handle:

Three things to read in it. Python int becomes SymInt, an integer that may be symbolic under torch.compile (a dynamic size), so size arguments do not force a recompile. 1.3 Mutation and aliasing: say what you write

The compiler rewrites programs: it removes in-place operations (functionalization, sibling page 2.7), reuses buffers and reorders calls. It can only do that safely if every operator's schema tells the truth about what it writes and what its outputs share with its inputs. Two rules follow. Declare every input you modify in mutates_args. And never return an input, or a view of one, as an output: custom_op checks this at run time:

The undeclared write is the dangerous one, because nothing checks it at run time. The lab's undeclared mutation variant clamps its input in place (x.clamp_(-3, 3)) under mutates_args=(). 1.4 The fake: the output's shape without running the kernel

A fake tensor carries a shape, dtype, device and strides but no data (sibling page 2.8). torch.compile and torch.export trace your program with fake tensors, so they never run the real kernels while tracing, and for every operator they ask: given inputs of these shapes, what comes out? ATen operators know; yours does not until you register a fake implementation (also called a meta or abstract implementation): a function that builds an empty output of the right shape and never reads input data. A wrong fake is worse than none. The lab's wrong fake variant returns x.new_empty(x.shape[:-1]), a copy-paste slip that drops the last dimension. Eager mode never calls the fake, so training runs and the loss is right (). torch.compile fails one operator later, at the next layer, where the error no longer mentions your op:

1.5 The gradient: register_autograd

register_autograd(backward, setup_context=...) works like torch.autograd.Function split in two (sibling page 3.6): setup_context(ctx, inputs, output) runs after the forward and saves what backward needs; backward(ctx, *grads) returns one gradient per input (None for inputs that need none). Write backward out of operators (here a second custom op with its own fake) and torch.compile traces it into the backward graph like any other code. Leave it out and the autograd kernel that custom_op registered at definition raises at the first backward:

That error is the good outcome. An operator defined directly with TORCH_LIBRARY in C++ (section 3) and given no autograd formula falls through to PyTorch's autograd fallback instead, which only warns and lets backward continue as if the op had no inputs needing gradients. In the running example that silently stopped training of each block's first MLP layer and the norm before it: of 52 parameters received a gradient. 2. Custom operators under torch.compile, and two traps

The parent page showed the core lesson on a toy function (Topic: pytorch-ecosystem, Reading section 8): a Python body that leaves PyTorch gives 3 graphs and 2 breaks; the same body as a custom op gives 1 graph and 0 breaks. Here is the same lesson on the whole running example, then what the compiler does with the opaque node, then two ways a correct-looking op loses its gradients under compile.

2.1 Watch Dynamo trace the forward: an opaque call against a custom op

Dynamo is the part of torch.compile that reads your Python bytecode and records the tensor operations into an FX graph. When it meets a call it cannot trace, here a C++ function exposed through pybind11, it records a graph break: it compiles what it has so far, lets Python run the call, and starts a new graph after it. The animation replays what torch._dynamo.explain recorded on one forward of the running example (src/exp/graphs.py): the same model, the same batch, with the GELU called directly, then as the custom op of section 1.

With the direct call, Dynamo compiled small graphs ( breaks) covering only the inside of a block, and the outer GPT.forward (embeddings, final norm, head, loss) ran uncompiled. The Compile lab tab of the parent measured what that shape costs with a print inside a block: 7 to 9% on the step. The reason Dynamo gave: . Export has no fallback. torch.compile can break a graph and run Python; torch.export, which must produce one graph to save and run elsewhere, cannot. With the custom op, torch.export.export captured operations including ext.gelu nodes, still after run_decompositions() lowered the rest to core ATen operations, and the exported module's logits matched eager. 2.2 What Inductor does with an opaque node

Below Dynamo, Inductor turns the graph into code: generated loops for element-wise work, library calls for matrix multiplies (on the CPU, C++ with OpenMP; the Compile lab tab shows it). The call() function it generated for the MLP's forward (fc, GELU, proj, inference), with F.gelu and with the custom op:

F.gelu: generated kernel
custom op: generated kernels

With F.gelu, Inductor wrote one loop, cpp_fused_gelu_view_0, that reads the matmul's output and writes the activation in place. With the custom op it can only call your kernel, check that the output has the metadata the fake promised (assert_tensor_metadata, assert_alignment), and move on: nothing fuses across an opaque operator. When the op is a big kernel (an attention, a fused MoE dispatch) that costs little; when it is a small element-wise op between two others, you lose the fusion the compiler would have done for free.

The cost, measured
Training step of the running example, CPU, 4 threads measured on Apple M1 Pro, bench lock, load average about 3, median of 3 × 20 steps: F.gelu eager ms, compiled ms; the custom op eager ms, compiled ms. Almost all of the difference is the C++ kernel itself, a scalar single-threaded loop about 11 times slower than ATen's GELU (section 3): an operator is only as fast as its kernel, and compiling cannot make an opaque kernel faster.
Predict: you want Inductor to fuse your element-wise kernel into its neighbours. Which registration lets it?
None of the opaque ones. A fake only describes the output; the body stays a black box. Inductor fuses what it can read: plain PyTorch operations, or Triton kernels registered with triton_op, whose source it can inspect (section 4). A custom op is the right tool for a kernel that is already the whole fused computation.

2.3 Two traps that drop gradients without an error

Both were found while building this page, with the C++ operator of section 3 and its fake and autograd formula registered from Python by name (torch.library.register_fake("extc::gelu"), torch.library.register_autograd("extc::gelu", ...)).

Trap 1: registering after the first trace. In one process, the op was first traced bare (for the "before" measurement), then registered, then compiled. The compiled model trained, with the right loss, but the MLP weights got no gradients: the compiled backward treated the op's output as not needing one. opcheck in the same process says so (). The cause is a per-operator cache: the Python object for each operator overload remembers, per dispatch key, which kernel to use during tracing, and registering a kernel through torch.library does not empty it:

Emptying torch.ops.extc.gelu.default._dispatch_cache after the registration made all four tests pass in the same process; so did a fresh process with the registrations made at import. Register everything when the module is imported, before any call.

Trap 2: the warm cache keeps the wrong answer. Compiled artifacts are cached on disk across processes: Inductor's FX graph cache and the AOTAutograd cache, which stores the compiled forward and backward pair:

Four fresh processes sharing one cache directory (src/exp/cache_trap.py, the running example compiled once, one forward and backward each):

The second process registered everything correctly and still got the first process's broken backward, because the cache key evidently does not cover the state of the operator's Python registrations (the graph and the configuration were identical). Turning off only the AOTAutograd cache fixed it. When you change an operator's registrations, clear the compile cache (TORCHINDUCTOR_CACHE_DIR, by default torchinductor_<user> in the temporary directory), and keep one cheap test in CI that compares compiled gradients against eager on one batch.

3. C++ extensions: TORCH_LIBRARY

The problem. Some kernels have to be compiled code: a hand-written loop, a call into a C++ library, a CUDA kernel. torch.utils.cpp_extension compiles C++ against PyTorch's headers and loads the result into the running process. It offers three ways: load_inline (C++ in a Python string, built on first use), load (the same from files) and setup.py with CppExtension or CUDAExtension (a wheel built ahead of time, what libraries ship). The first two need the ninja build tool; it was not in the shared environment and had to be installed.

3.1 The tiny operator, built here

The running example's C++ GELU, whole file in src/exp/gelu_ext.cpp. The kernel is a plain loop over the tensor's memory; then two macros register it with the dispatcher:

static at::Tensor gelu_fwd(const at::Tensor& x) { TORCH_CHECK(x.device().is_cpu() && x.scalar_type() == at::kFloat, "extc::gelu: CPU float32 only"); auto xc = x.contiguous(); auto y = at::empty_like(xc); const float* in = xc.data_ptr<float>(); float* out = y.data_ptr<float>(); at::parallel_for(0, xc.numel(), 4096, [&](int64_t b, int64_t e) { for (int64_t i = b; i < e; ++i) out[i] = 0.5f * in[i] * (1.0f + std::erf(in[i] * 0.70710678f)); }); return y; } // ... gelu_bwd the same way ... TORCH_LIBRARY(extc, m) { // define: namespace extc, two schemas m.def("gelu(Tensor x) -> Tensor"); m.def("gelu_backward(Tensor grad, Tensor x) -> Tensor"); } TORCH_LIBRARY_IMPL(extc, CPU, m) { // kernels at the CPU key m.impl("gelu", &gelu_fwd); m.impl("gelu_backward", &gelu_bwd); }
# Python: build, load, then add what C++ did not say from torch.utils.cpp_extension import load_inline mod = load_inline(name="ext_gelu", cpp_sources=[src], functions=["raw_gelu", "raw_gelu_backward"], extra_cflags=["-O3"]) # loading runs TORCH_LIBRARY: torch.ops.extc.gelu exists torch.library.register_fake("extc::gelu")(lambda x: torch.empty_like(x)) torch.library.register_fake("extc::gelu_backward")(lambda g, x: torch.empty_like(x)) torch.library.register_autograd("extc::gelu", backward, setup_context=setup_context) y = torch.ops.extc.gelu(x)

TORCH_LIBRARY is a macro that creates a static registrar, so the definitions run when the shared library is loaded (). The dispatcher's table afterwards shows where each kernel came from, the CPU kernel from the C++ file and the fake (at Meta) and the autograd kernel from Python:

3.2 What it costs

One call, four ways to reach the same kind of work measured on Apple M1 Pro, CPU, 4 threads, bench lock, median of 3

Two different lessons. Overhead: on 64 numbers the call itself dominates. Through pybind11 the C++ function costs what F.gelu costs; as a dispatcher operator with a Python autograd kernel it costs about five times as much, because every call enters Python at the Autograd key even when nothing needs a gradient (a C++ autograd registration would avoid that; not measured here). Kernel: on a real activation our loop is about 11 times slower than ATen's GELU. ATen's kernel is vectorised (4 floats per NEON instruction) and multi-threaded; ours computes one erf at a time, and at::parallel_for runs serially here because the extension was compiled without OpenMP flags. A custom kernel has to beat what it replaces before it earns its place; measure it on the shapes you run.

Build. A cold load_inline of this 50-line file took to s (three builds, each in a fresh directory and process); afterwards the build directory acts as a cache.

One namespace, one TORCH_LIBRARY, per process
Loading a second build of the same file under another module name (to time a cold build) killed the Python process with SIGABRT (return code ) and no Python traceback: a namespace may be defined by one TORCH_LIBRARY block only. Use TORCH_LIBRARY_FRAGMENT to add definitions from several files, and never import two copies of an extension.

3.3 Beyond this example

  • Autograd in C++: subclass torch::autograd::Function and register it at the Autograd key with TORCH_LIBRARY_IMPL(extc, Autograd, m). Use it when you need C++-speed calls; the Python route above is simpler and enough for big kernels.
  • CUDA: CUDAExtension or load_inline(cuda_sources=...) compile .cu files with nvcc; register the kernel at the CUDA key exactly as above. Not run here (no NVIDIA GPU).
  • One wheel for several PyTorch versions: the C++ ABI changes between releases, so an extension built against 2.14 may not load into 2.15. PyTorch ships a smaller stable ABI for extensions, with its own registration macro (STABLE_TORCH_LIBRARY in torch/csrc/stable/library.h, line 355 of the 2.14.1 wheel's headers); not used here.

4. Kernels that plug in: Metal, Triton, Helion

A GPU kernel is written in a kernel language (CUDA C++, Metal, Triton, Helion), compiled for the device, and launched over a grid of threads. PyTorch does not need to understand the kernel; it needs the same three facts as for any operator. The pattern is always the same: write the kernel, wrap it in an operator, register a fake and a gradient. What differs is whether the compiler can look inside. Writing fast kernels is its own subject (Triton and Gluon, Writing kernels); this section is about plugging them in.

4.1 A Metal kernel on the Apple GPU, run here

torch.mps.compile_shader(source) compiles Metal Shading Language at run time and returns an object whose kernels you call with tensors; each thread computes one element:

lib = torch.mps.compile_shader(SHADER) @gelu2.register_kernel("mps") # gelu2: the custom op of section 1.6, CPU kernel in C++ def _(x): xc = x.contiguous() y = torch.empty_like(xc) lib.gelu_fwd(y, xc) # one thread per element return y

On an (8, 64, 1024) activation it took µs against µs for F.gelu(approximate="tanh") measured on Apple M1 Pro, MPS, median of 3, including a synchronize: an element-wise kernel is limited by memory traffic, and both read and write the same 2 MiB.

4.2 Triton: triton_op and wrap_triton (read, not run)

Triton is a Python-embedded language for GPU kernels that work on blocks of data; it is what Inductor generates for NVIDIA and AMD GPUs. Triton 3.8.0 on PyPI ships Linux wheels only (checked 2026-10-13), so nothing in this section ran here. What the source at 2.14.1 says:

Inside, triton_op is a custom_op whose fake is your own Python function (it only allocates outputs and launches kernels, so it can run on fake tensors), plus one more trick: under AOTAutograd it is decomposed into its kernel launches, so Inductor sees the Triton kernels themselves:

wrap_triton(kernel)[grid](...) is how a launch is written inside such an op so that dispatcher-level tracing (make_fx, non-strict export) can record it:

# a triton_op, condensed from the 2.14.1 docstring in torch/_library/triton.py (not run here) @triton.jit def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr): offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK) mask = offs < n tl.store(out_ptr + offs, tl.load(x_ptr + offs, mask=mask) + tl.load(y_ptr + offs, mask=mask), mask=mask) @torch.library.triton_op("mylib::add", mutates_args={}) def add(x: Tensor, y: Tensor) -> Tensor: out = torch.empty_like(x) n = out.numel() wrap_triton(add_kernel)[(triton.cdiv(n, 16),)](x, y, out, n, 16) return out

Two consequences worth remembering. Under torch.export a triton_op stays one custom-op node rather than being decomposed (the source explains: an exported program should not carry GPU-specific Triton source). And the same docstring recommends calling @triton.jit kernels directly when you need no operator at all: Dynamo can trace a raw Triton launch; you need the torch.library wrapper only for operator behaviour (subclasses, dispatch modes, export).

4.3 Helion: kernels from tiled PyTorch, run here on the Apple GPU

Helion (PyTorch Foundation; 1.0 released 2026-04-03, 1.4.0 used here) lets you write a kernel as a loop over tiles with ordinary PyTorch operations inside; its compiler chooses block sizes, memory access and launch shape, and its autotuner can search them. Its settings name four code generators:

The Metal one ("experimental", it warns) meant Helion could run on this Mac without Triton. The GELU kernel and what it compiled to:

import helion, helion.language as hl # HELION_BACKEND=metal @helion.kernel(autotune_effort="none", static_shapes=True) def gelu(x: torch.Tensor) -> torch.Tensor: out = torch.empty_like(x) for tile in hl.tile(x.size()): # Helion splits the 3-D index space into tiles v = x[tile] out[tile] = 0.5 * v * (1.0 + torch.tanh(0.7978845608028654 * (v + 0.044715 * v * v * v))) return out
The generated kernel (Helion's Triton-like intermediate, before Metal translation), lines

Read the table as a status report of an experimental backend, measured on Apple M1 Pro. The element-wise kernel compiled with the default configuration and matched F.gelu(approximate="tanh"). Exact GELU did not lower (Metal has no erf, the same wall as section 1.6), and a row softmax stopped at the reduction. Without autotuning the kernel took µs against µs for PyTorch's own: on its main backend (Triton on NVIDIA) the autotuner's search is the point, and none was run here. Two things worked fully: ref mode (HELION_INTERPRET=1) ran both kernels, erf and softmax included, as plain PyTorch on the CPU with errors and , which is how you debug a kernel's logic without a GPU; and composition: called inside torch.compile the Helion kernel gave graph and breaks, because Helion registers its kernels with Dynamo as a higher-order operator (); registered as the MPS kernel of a custom op it passed opcheck's schema and fake tests.

5. Tensor subclasses: changing what a tensor is

The problem. Some extensions are not a new computation but a new kind of tensor: weights stored as int8 with a scale, a tensor split across eight GPUs, a float8 tensor that remembers its scaling factor. You want the model code unchanged (F.linear(x, w) stays F.linear(x, w)) while every operation on w does the right thing for its representation. A tensor subclass is a Python subclass of torch.Tensor that gets a say in every operation on its instances.

5.1 Two places to intercept: __torch_function__ and __torch_dispatch__

A call such as F.linear(x, w) passes two points where a subclass can step in. __torch_function__ is called first, at the Python API, with the function you called (linear, Tensor.add, Tensor.backward), before autograd or the dispatcher. __torch_dispatch__ is called much later: the dispatcher reaches the Python key after autocast, autograd and view tracking have run, and hands over the ATen operator (PyTorch's C++ operator library) that is about to execute: aten::t and aten::addmm rather than linear, because linear decomposed on the way (sibling page 2.4).

The __torch_function__ subclass saw the Python-level calls from the weight's first use onward, because its results are of its own type and so spread through the forward, and in backward only Tensor.backward itself. The __torch_dispatch__ subclass that rewraps its outputs saw every ATen call downstream of the weight in both directions; the one that returns plain tensors saw only the operations that touch the weight itself. 5.2 Wrapper subclasses: a tensor with no storage of its own

A wrapper subclass is created with torch.Tensor._make_wrapper_subclass(cls, shape, dtype=..., device=...): the outer object has a shape, a dtype and a device, so the rest of PyTorch treats it as a tensor of that shape, but it has no data. The real data lives in ordinary tensors stored as attributes (self.qdata, self.scale), and __torch_dispatch__ decides, per ATen operator, what to compute from them. Its key set gains Python and PythonTLSSnapshot ( for the DTensor below), which is what routes every call to your Python code.

Two decisions shape every such subclass. Contagious or not: does an operation on the subclass return the subclass (DTensor: a sharded result) or a plain tensor (an int8 weight: the matmul's output is ordinary float32)? And which operators to implement: the rest fall back to "dequantize and run the normal kernel" or to an error. One rule is not optional: nn.Parameter refuses a subclass whose detach() does not return the subclass:

5.3 Build one: int8 weights for the running example

The subclass below stores each block weight as int8 qdata (same shape) and one float32 scale per output row (symmetric, per-channel: scale = max|w_row| / 127). It implements four ATen operators: the transpose and detach that nn.Linear and nn.Parameter need, addmm for the forward and mm for the backward's input gradient. The scale factors out of the matrix multiply, so the int8 values are multiplied first and the scale applied per output column afterwards. Full file: src/exp/subclasses_int8.py.

class Int8Weight(torch.Tensor): @staticmethod def __new__(cls, qdata, scale, transposed=False): shape = qdata.shape[::-1] if transposed else qdata.shape return torch.Tensor._make_wrapper_subclass(cls, shape, dtype=scale.dtype, device=qdata.device, requires_grad=False) def __init__(self, qdata, scale, transposed=False): self.qdata, self.scale, self.transposed = qdata, scale, transposed def __tensor_flatten__(self): # for torch.compile (5.4) return ["qdata", "scale"], (self.transposed,) @staticmethod def __tensor_unflatten__(inner, meta, outer_size, outer_stride): return Int8Weight(inner["qdata"], inner["scale"], meta[0]) __torch_function__ = torch._C._disabled_torch_function_impl @classmethod def __torch_dispatch__(cls, func, types, args=(), kwargs=None): if func is aten.t.default: # W.t(): flip a flag, move no data return Int8Weight(args[0].qdata, args[0].scale, not args[0].transposed) if func is aten.addmm.default and isinstance(args[2], Int8Weight): bias, x, w = args[:3] # x @ W^T + b, W = q * s[:, None] return torch.mm(x, w.qdata.to(x.dtype).t()) * w.scale + bias # ... aten.detach, aten.mm (backward), and a dequantizing fallback ...

5.4 Under torch.compile: flatten, trace, desugar

The compiler cannot keep a Python object inside a graph. It needs to know which tensors the subclass is made of, so that it can pass them in as ordinary graph inputs and rebuild the subclass while tracing. That is the traceable-subclass protocol: __tensor_flatten__ returns the names of the inner tensors plus any non-tensor metadata, and __tensor_unflatten__ rebuilds the object from them. With it, Dynamo traced the int8 model into graph with breaks, and AOTAutograd ran __torch_dispatch__ on fake tensors and recorded what it did in plain ATen: the subclass disappears from the compiled graph (desugaring). 6. Dispatch modes: watch or change every operation in a region

A dispatch mode is the subclass idea without a subclass: a context manager whose __torch_dispatch__ is called for every ATen operation run inside the with block, whatever tensors it touches. The sibling page used one to record calls key by key (Dispatcher walker tab); PyTorch itself ships several built on the same mechanism. Three of them on the running example:

FakeTensorMode: run the model with no data. Inside the mode, new tensors and parameters are fake, so the whole model ran and produced logits of shape without computing a number. That is how torch.compile traces and how you can check that a 70-billion-parameter model's shapes line up on a laptop. What it cannot do is answer a question about values: loss.item() raised . (Building the model inside the mode needs care with tied weights: the root's make_model fails there because .to() cannot swap the tied embedding, as the sibling page found; constructing GPT(cfg) directly works.)

FlopCounterMode: count the arithmetic. It adds up floating-point operations from a formula per operator. One forward and backward of the running example: FLOPs. That is exactly 6 × 3,156,736 × 512: six FLOPs per weight per token for every matrix-multiply weight (the 3,145,728 in the blocks plus the 11,008 of the head; the embeddings are lookups, not multiplies), over 512 tokens. The textbook estimate "6 × parameters × tokens" with all 3,186,944 parameters gives . Two gaps are worth knowing. The CPU attention kernel (_scaled_dot_product_flash_attention_for_cpu) has no formula, so attention counted zero; written out by hand (attn="manual") its batched multiplies add . And your own operators count zero until you register a formula:

7. New devices: PrivateUse1, briefly

A hardware vendor whose chip is not in PyTorch adds it without forking PyTorch through a reserved dispatch key, PrivateUse1. They register kernels at that key from a C++ extension (as in section 3, with TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) for ATen operators), give the device a name with torch.utils.rename_privateuse1_backend("npu") (), add tensor methods such as .npu() with generate_methods_for_privateuse1_backend(), and plug in an allocator, streams and a compiler backend. PyTorch keeps a complete reference device in its own tests, torch_openreg (test/cpp_extensions/open_registration_extension/ at the v2.14.1 tag). Not run here: a device needs a C++ runtime, and nothing on this page depends on it. Most readers meet it through a vendor's plugin package, not by writing one.

9. What carries over to NVIDIA GPUs, and what does not

  • Carries over unchanged: everything about registration and composition. Schemas, fakes, autograd formulas, opcheck, graph counts and breaks, export behaviour, the late-registration and cache traps, the subclass protocol and what reaches __torch_dispatch__: these are device-independent dispatcher and compiler logic.
  • Changes: the kernels. On CUDA you register at the CUDA key, write the kernel in CUDA C++ (CUDAExtension) or Triton (triton_op), and Helion's default Triton backend with its autotuner applies; none ran here. Inductor around an opaque op on a GPU loses fusions that matter more than on a CPU (each unfused element-wise op is a full round trip through GPU memory).
  • Changes: every timing on this page. Per-call overheads (3 to 4 µs for a Python-registered op, measured here) are paid on the CPU before every GPU launch as well, so many small custom ops hurt there too (Profiling, benchmarking and correctness shows how to see it); but a weight-only int8 or float8 kernel that reads the compact format directly is a GPU speed-up that the CPU path here does not show.

Common mistakes

Calling your kernel directly instead of through an operator
Works in eager, then costs you three graph breaks, export, and silently the gradients of everything before it: in the running example of 52 parameters were trained, with no error. Wrap it in custom_op.
Registering the fake or the autograd formula late
Register at import, next to the definition. Registering after the op has been traced left the compiled backward without gradients in that process (section 2.3), and the broken artifact was then served from the AOTAutograd cache to later, correct processes.
Trusting a warm compile cache after changing registrations
Clear TORCHINDUCTOR_CACHE_DIR (or set TORCHINDUCTOR_AUTOGRAD_CACHE=0 while developing) whenever a fake, a formula or a kernel's registration changes. Keep one test that compares compiled gradients with eager on a batch.
A fake that reads data, or returns the wrong shape
The fake runs on tensors with no data: it may look at shapes, dtypes and devices only. For a data-dependent size use get_ctx().new_dynamic_size(). A wrong shape makes compile fail one layer later with an error about the next operator; opcheck's test_faketensor names the real one.
Writing into an input without declaring it
List every mutated argument in mutates_args. The compiler relies on the schema to reorder and reuse memory; opcheck catches the lie only when the test inputs are actually changed.
Returning an input (or a view of it) from a custom op
Not allowed: outputs must be fresh tensors. Return x.clone() if the result equals the input.
Assuming one op means one numerical result on every device
Each device has its own kernel. The Metal GELU here used the tanh approximation (Metal has no erf) and differed from the CPU kernel by ; opcheck does not compare devices.
Expecting a custom C++ kernel to be fast because it is C++
The straightforward loop here was about 11 times slower than F.gelu (scalar, single-threaded). Benchmark against the ATen operator you replace, on your shapes, before shipping it.
Expecting Inductor to fuse through a custom op
It cannot see inside: the op is a call between generated kernels, with metadata checks around it. Leave small element-wise work in PyTorch, or use triton_op.
A wrapper subclass whose detach() returns a plain tensor
nn.Parameter refuses it. Handle aten.detach (and usually aten.t, aten._to_copy, aten.clone) by returning the subclass.
Expecting __torch_function__ to see backward
Autograd's engine calls C++ directly. A __torch_function__ subclass saw call in backward (Tensor.backward itself); use __torch_dispatch__ or a dispatch mode to see backward's operations.
Two copies of a TORCH_LIBRARY in one process
The process aborts with no Python traceback. Use one extension per namespace, TORCH_LIBRARY_FRAGMENT for extra definitions.

Interview questions, with short answers

What does torch.library.custom_op give you that calling a C++ function does not?
A dispatcher operator: a schema, kernels per device, a fake implementation for tracing, an autograd formula, version bumps for mutation. So autograd, torch.compile (one node, no break), torch.export and dispatch modes all work with it (and vmap, once you add register_vmap).
What is a fake (meta) implementation and why does the compiler need it?
A function computing the output's metadata (shape, dtype, device, strides) from the inputs' metadata, without data. Dynamo and export trace with fake tensors, so they must know every operator's output without running it.
How do you handle an op whose output size depends on the data?
In the fake, allocate with a size from torch.library.get_ctx().new_dynamic_size(): an unbacked symbolic integer, carried as u0 through the graph with run-time checks.
Why must a custom op's schema declare mutation, and what does Tensor(a!) mean?
Functionalization and Inductor reorder and reuse buffers assuming the schema is honest. Tensor(a!) names an alias set a and marks it written.
custom_op or triton_op?
custom_op for opaque kernels (C++, CUDA, other libraries); triton_op when the body is Triton launches, so Inductor can see and optimise the kernels. Under export, both stay one node.
What does opcheck test?
Schema honesty (mutation and aliasing), that an autograd kernel is registered, that the fake matches the real kernel's metadata, and that forward and backward trace through AOTAutograd with dynamic shapes and match eager.
__torch_function__ vs __torch_dispatch__?
The first intercepts Python API calls (above autograd; sees linear; no backward). The second intercepts ATen operators at the Python dispatch key (below autograd; sees t and addmm, including backward's operations). Representation subclasses (DTensor, torchao) use the second.
What is a wrapper subclass, and how does torch.compile handle one?
A tensor with metadata and no storage, whose data lives in inner tensors. With __tensor_flatten__ and __tensor_unflatten__ the compiler passes the inner tensors as graph inputs and desugars __torch_dispatch__ into plain ATen operations.
Why might weight-only int8 not speed anything up?
If the kernel converts the weight to float before the matmul (as on the CPU path here), only memory at rest shrinks. Speed needs a kernel that reads int8 and dequantizes on the fly, and pays off where the matmul is memory-bound.
How is DTensor implemented?
A tensor subclass holding the local shard and the device mesh, with placements as metadata. At 2.14.1 its constructor and op dispatch run in C++ (a fast path with cached sharding propagation), falling back to Python sharding rules.
You added register_autograd but compiled gradients are still missing. What do you check?
Whether the op was traced before the registration (register at import), whether a stale compile cache is serving an old artifact (clear it or disable the AOTAutograd cache), and opcheck's test_aot_dispatch_dynamic.
How would you add support for a new accelerator?
Out of tree through the PrivateUse1 key: kernels via TORCH_LIBRARY_IMPL(aten, PrivateUse1, ...), a renamed device, an allocator, streams, and a compiler backend; torch_openreg in PyTorch's tests is the reference.

Read it this way
__torch_function__ receives what your code called (linear, gelu, layer_norm, attribute reads as __get__), and only that: autograd's engine runs backward in C++, so the backward shows one call, Tensor.backward. __torch_dispatch__ receives ATen operators after autograd has recorded its node, so linear appears as t + addmm, and the backward's own operators (mm, gelu_backward, native_layer_norm_backward) arrive too.
