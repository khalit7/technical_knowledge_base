The idea in one screen

A training library adds no maths to PyTorch: it takes over duties of the loop you would write (data order, loss scaling, clipping, optimiser, precision, spreading over processes) and fills each with a default. Choosing a library is choosing which duties to hand over; moving between two is matching their defaults.

Higher layers take more of the loop from you; every column ends in the same PyTorch calls

Blue notes: a default that changes the loss if you port a plain loop without setting it. Each layer is built on the one below: TRL's trainers subclass the Trainer, which runs on Accelerate, which calls DDP or fully_shard; Axolotl ends in a Trainer or a TRL trainer. Models come from transformers (with PEFT adapters) or are your own nn.Module; torchtitan and Megatron bring their own.

You need the topic's running example and its map of these libraries (Topic: pytorch-ecosystem, section 9 and the Ecosystem map tab). The parallelism forms ZeRO and FSDP are taught on Distributed Training; the PyTorch APIs the libraries call (DDP, fully_shard, DeviceMesh, DTensor) on Distributed PyTorch; LoRA on PEFT; SFT, DPO and RL as methods on Alignment.

Matched

Probe loss
The mean loss on four fixed batches (10,000 to 10,003 of the same text), read every 10 steps: a yardstick that does not depend on data order.
Mean of means
Under gradient accumulation, each micro-batch's mean loss divided by the number of micro-batches and added up (section 3). Its rival is the token-weighted loss: summed token losses over the real-token count of the whole step.

Three results the rest of the page explains
  • Matched settings, identical losses. The HF Trainer, Accelerate and Lightning give the plain loop's 150-step curve to five decimals; DeepSpeed ZeRO 0 to 3 give DDP's losses on 2 processes measured on Apple M1 Pro, CPU.
  • Defaults move the curve. The Trainer's default clip at 1.0 was active on 145 of 150 steps; DeepSpeed turned its own clip on (1.0) in 0.19.3, July 2026, so the same script trains differently after an upgrade.
  • Loss averaging is a choice. On micro-batches of 124, 10, 90 and 13 real tokens the mean of means is 59% away from the full-batch gradient (Accelerate, Lightning, the Trainer with a model without **kwargs); the Trainer with a Hugging Face model and torchtitan divide by the token count and match.

1. The same loop, the same losses

This is everything a training library automates. Run it next to the root's src/model/model.py with PyTorch 2.14 and it prints three losses that every library reproduces once its settings match.

import torch from model import GPTConfig, make_model, get_batch, make_optimizer torch.set_num_threads(2) cfg = GPTConfig() # 4 layers, d_model 256, batch 8 x 64 characters model = make_model(cfg) # seeded: the same weights on every run opt = make_optimizer(model) # AdamW lr 6e-4, betas (0.9, 0.95), weight decay 0.1 on matrices for step in range(3): x, y = get_batch(cfg, step) # batch k is the same on every run _, loss = model(x, y) # forward + mean cross-entropy loss.backward() # gradients into .grad opt.step() # update opt.zero_grad(set_to_none=True) # free the gradients print(step, round(loss.item(), 5)) # 0 3.80137 # 1 3.18793 # 2 3.16783

Output recorded on Apple M1 Pro, CPU, 2 threads, torch 2.14.1 (src/exp/defaults_lab.py, which runs it for 150 steps).

The matched Trainer call: three settings make it the plain loop (from src/exp/defaults_lab.py).

from transformers import Trainer, TrainingArguments args = TrainingArguments(output_dir="out", max_steps=150, per_device_train_batch_size=8, use_cpu=True, report_to=[], save_strategy="no", train_sampling_strategy="sequential", # default "random": RandomSampler max_grad_norm=0.0) # default 1.0: clipping on opt = make_optimizer(model) # default: AdamW lr 5e-5, betas (0.9, 0.999), wd 0 const = torch.optim.lr_scheduler.LambdaLR(opt, lambda s: 1.0) # default: linear decay to 0 Trainer(model=model, args=args, train_dataset=rows, optimizers=(opt, const)).train()

The model must return a dict with a loss key (a ten-line subclass of the running example does it); rows is a dataset of {"input_ids", "labels"} rows in the plain loop's order. Everything a library adds beyond these duties is logging, checkpointing and distribution.

2. Defaults that change results

Porting a loop into a library, or upgrading one, swaps your decision for the library's wherever you did not set it. Clipping is the clearest case.

Predict: the running example's gradient norm, over 150 steps of the plain loop. On how many steps would a clip at 1.0 change anything?
Almost all: the norm was above 1.0 on of 150 steps (median , first step ) measured on Apple M1 Pro, CPU. Clipping at 1.0 is not a safety net here; it rescales nearly every update. 3. Loss averaging under gradient accumulation

A language-model batch rarely has the same number of real tokens in every row: padding positions get the label -100 and the loss is a mean over the real tokens. Split the batch into micro-batches, take each one's mean, divide by the number of micro-batches and add, and you get a mean of means, not the mean over the whole batch. Tokens in a short micro-batch count for more.

The same 8 rows as 4 micro-batches: the mean of means over-weights the 10-token micro-batch

Batch 0 of the running example with targets past the lengths shown set to -100 (lengths chosen to make the micro-batches unequal: 124, 10, 90 and 13 real tokens). Grey bar: the share of the gradient each row gets in the full batch (tokens / 237). Coloured bar: its share under the chosen scheme. The relative error is |g - gfull| / |gfull| over all 3,186,944 gradient entries, computed by src/exp/accum_lab.py on the real model measured on Apple M1 Pro, CPU: 59.1% for the mean of means, 0 for token weighting.

The formula, same names. The full-batch loss is sum of token losses / N, with N the real tokens in the whole batch, so each token's gradient weight is 1/N. The mean of means gives a token in micro-batch j the weight 1/(K · nj), with K micro-batches and nj tokens in micro-batch j. The fix is to sum each micro-batch's token losses and divide by N, which must be known before the first backward: count the labels of all micro-batches first, and across ranks with one all-reduce of a single integer.

What each library computes, read from the gradient just before optimizer.step() after 4 micro-batches of these rows:

Library and settingWhat it divides byGradient error vs full batchSource

Why the Trainer has two behaviours. It passes the step's real-token count (num_items_in_batch) to the model only if the model's forward accepts **kwargs. A transformers model does and divides its summed loss by that count; your own nn.Module usually does not, and the Trainer silently falls back to the mean of means. torchtitan all-reduces the count over the data-parallel ranks and sets FSDP2's own gradient division to 1.0, because averaging again over ranks would divide twice.

Predict: 100 optimiser steps of the running example with random padding each step, mean of means against token-weighted. How far apart are the probe losses at step 100?
Within a few hundredths: against at step 100 measured on Apple M1 Pro, CPU, and the gap changes sign along the way. On a toy run AdamW absorbs much of a per-step reweighting, so the curves look alike; the gradient is still a different estimator, biased towards short sequences. It matters most when sequence lengths vary a lot and correlate with content (short chat turns against long documents), with SGD-like optimisers, and whenever you compare a run with accumulation to one without.

How to check your own setup. Run one step as one batch and as K micro-batches on the same rows with clipping off, and compare the gradients with torch.allclose or the relative error above: the only way to know what your library and model combination does.

Source lines and history: when the libraries fixed it (provenance)

The Trainer counts the real tokens of all the micro-batches of one step (trainer.py L2281 to L2342) and passes the count only to a forward with **kwargs (L519 to L529), else divides by the number of micro-batches (L2089 to L2094). Checked on a transformers model: . torchtitan sums labels != -100 over every micro-batch, all-reduces the count and divides each micro-batch's summed loss by it (trainer.py L884 to L904), then sets FSDP2's divide factor to 1.0 (fsdp.py L27 to L41).

The Trainer's token-count path arrived in October 2024 (PR 34191; the Hugging Face blog post tells the story). Its extension across data-parallel ranks, average_tokens_across_devices (default True at 5.19.0), answers issue 34242 (2024-10-18), which pointed out that averaging per rank has the same flaw.

4. The Hugging Face stack: transformers, Trainer, Accelerate, PEFT, TRL

Five layers, each usable alone (the left column of the hero): transformers holds model definitions and loads weights from the Hub; the Trainer (inside transformers) runs the loop; Accelerate sits under the Trainer and turns one process into many (DDP, FSDP2, DeepSpeed, Megatron); PEFT injects adapters such as LoRA into any model; TRL holds the post-training trainers (SFT, DPO, GRPO, reward models), each a subclass of the Trainer.

transformers v5: the change that alters training

Version 5.0.0 came out on 2026-01-26 and 5.19.0 on 2026-10-06 (PyPI, as recorded by the root's Ecosystem map). It is PyTorch only (TensorFlow and Flax are sunset; JAX is left to partner libraries). The change that silently alters a ported script is the load dtype: "We have updated the default dtype for all models loaded with from_pretrained to be auto" (v5.0.0 release notes); v4 loaded in float32 unless told. At 5.19.0, dtype=None becomes "auto" (modeling_utils.py L4104 to L4105), so a bf16 checkpoint trains in bf16 parameters and full fine-tuning updates bf16 weights directly. Pass dtype=torch.float32 (and use autocast) if you want float32 master weights.

The rest of v5: attention registry, quantisation, tokenizers, Trainer, serving (from the v5 announcement and release notes)
  • Attention is pluggable. Each model keeps its eager attention in its own file; SDPA, FlashAttention and FlexAttention live in one registry, AttentionInterface. At 5.19.0 its keys are flash_attention_2, flash_attention_3, flash_attention_4, flex_attention, paged|eager and sdpa (modeling_utils.py L5118 to L5125); the default is "sdpa", falling back to eager when a model cannot use it (L1850 to L1886). attn_implementation="flex_attention" is real, and run here on a tiny Llama:
  • Quantisation is "a first-class citizen" (announcement): quantised checkpoints and configs such as bitsandbytes and torchao load through the same from_pretrained; the formats themselves are on Quantization and Precision.
  • Tokenizers: the fast/slow split is gone, the Rust tokenizers backend is the default, encode_plus is deprecated and apply_chat_template returns a BatchEncoding.
  • Trainer: report_to defaults to "none"; a new weight-loading API; reworked initialisation "to support scaled pre-training and different parallelism schemes" (announcement).
  • Serving: transformers serve (an OpenAI-compatible server), continuous batching and paged attention; and transformers model files run as a backend inside vLLM and SGLang (announcement). Serving itself is Topic: inference-and-serving.

Accelerate: your loop, distributed

accelerator.prepare(model, optimizer, dataloader) returns wrapped objects and accelerator.backward(loss) replaces loss.backward(); the loop stays yours. On 2 processes here the model came back as torch.nn.parallel.DistributedDataParallel (accelerator.py L2060) and gave rank 0 the DDP reference losses 3.80137, 3.09551, 3.16247 measured, CPU, 2 processes, gloo.

What the Trainer calls each step, and how Accelerate wraps FSDP2 (source and trace)

For the Trainer (settings matched to the plain loop) one step is: the Accelerate dataloader's __next__, Module.train, the forward, Accelerator.backward calling Tensor.backward, clip_grad_norm_, Adam.step through Accelerate's optimizer wrapper, LRScheduler.step, Module.zero_grad (the What calls what tab has the recorded order). Two calls you did not ask for:

  • clip_grad_norm_ is called on every step even with max_grad_norm=0: the Trainer then calls it with an infinite limit to log the gradient norm (trainer.py L2741 to L2756). One norm over all gradients per step, for a log line.
  • A torch.isnan and a torch.isinf on the loss each step (logging_nan_inf_filter, L1895 to L1900): on a GPU, a reduction whose result the logging path later reads.

With an FSDP plugin and fsdp_version: 2, Accelerate's fsdp2_prepare_model calls PyTorch's fully_shard on every module the auto-wrap policy picks (bottom up), then on the input embedding, then on one group of [final norm, output embedding] with reshard_after_forward=False ("re-gather would be unhideable"), then on the root (fsdp_utils.py L851 to L885): the same grouping torchtitan uses for its last layers (root's Distributed lab). On a CPU-only machine Accelerate ignores the FSDP plugin and returns DDP (the root's Ecosystem map measured it), so FSDP2 through Accelerate was not run here.

PEFT and TRL

PEFT wraps chosen nn.Linear layers of any model: LoRA rank 8 on the running example's four block matrices trains 131,072 of 3,186,944 parameters (4.1%, root's Ecosystem map); the method is PEFT's. TRL's SFTTrainer, DPOTrainer, GRPOTrainer and RewardTrainer all subclass transformers.Trainer, so every Trainer default applies, plus TRL's own: gradient_checkpointing=True, bf16 (when fp16 is not set), and a learning rate of 2e-5 for SFT and 1e-6 for DPO and GRPO. What those methods do is Alignment's and RL for LLMs's subject.

TRL's defaults in its source (1.15.0, file and line)

The trainers subclass transformers.Trainer through trl.trainer.base_trainer._BaseTrainer; the configs subclass TrainingArguments, turn on gradient checkpointing and bf16 and log every 10 steps (base_config.py L54 to L72 in 1.15.0); the learning rates are set at sft_config.py L133, dpo_config.py L149 and grpo_config.py L411.

The same model class, two different trainings
A GRPOTrainer with its config left alone computes in bf16, checkpoints activations, clips at 1.0 and uses lr 1e-6 with a linear decay; the same model in a plain Trainer computes in the checkpoint's dtype, keeps activations, clips at 1.0 and uses lr 5e-5. Write the settings you rely on into your config, every time.

5. Lightning and Fabric

Lightning splits your code into hooks on a LightningModule (training_step, configure_optimizers, configure_model, ...) and runs the loop, logging, checkpointing and distribution for you. Fabric is the half that keeps your own loop: fabric.setup(model, optimizer), fabric.backward(loss), and the launch, precision and strategy are handled.

The loop runs inside the optimiser's step. With automatic optimisation, Lightning calls optimizer.step(closure) and the closure runs your training_step, then backward (the root's Ecosystem map draws the two call stacks). So an optimiser pre-step hook fires before the gradients exist: a trap met while building this page's defaults runs; use the on_before_optimizer_step hook instead. Its defaults: no clipping, 32-true precision, the loss divided by accumulate_grad_batches, and a DistributedSampler added to your dataloader when distributed (use_distributed_sampler=True).

FSDP2 is not FSDPStrategy. In Lightning 2.6.6 FSDPStrategy is FSDP1, the older flat-parameter wrapper; FSDP2 is ModelParallelStrategy, which builds the DeviceMesh and leaves you to call fully_shard and parallelize_module in configure_model. Run here on 2 CPU processes it gave DDP's losses, with parameters turned into DTensor.

When. Lightning fits research code where many models share one structure (vision, science, smaller LLM work) and teams that value callbacks and checkpoint conventions. New LLM parallelism arrives in PyTorch and torchtitan first; Lightning exposes it through ModelParallelStrategy, where the parallel plan is still yours to write. Fabric keeps the launch and precision and gives the loop back.

6. torchtitan: PyTorch's own training codebase

torchtitan (pytorch/torchtitan, release 0.3.0 on 2026-09-03) is the PyTorch team's reference for training large models with PyTorch's native pieces: FSDP2, tensor, pipeline, context and expert parallelism on one DeviceMesh, torch.compile, float8 and MX formats, distributed checkpointing. It is a codebase to read and fork, not a framework to configure: the model, the loss and the loop are short files you are expected to edit. Since the end of torchtune (2025) and the pause of torchforge, PyTorch-native LLM training is being consolidated here (section 9).

Configs are Python. At 0.3.0 a configuration is a function returning a Trainer.Config dataclass, registered in a model's config_registry.py (for example llama3_debugmodel), and overridden from the command line by tyro (--training.steps 3). --module may also name your own module, which is how this page added CPU configs without touching torchtitan (src/exp/titan/libcfg.py).

Its defaults are choices for large GPU runs, and three of them showed on its debug model here (6 layers, dim 256, sequence 256, 10 steps, seed 0):

  • The loss is chunked. The trace counted 8 backward calls from the loss wrapper per step plus 1 from the trainer.

It also clips at 1.0, decays weights on every parameter, defaults to FlexAttention with per-document masks, and leaves the seed unset in its debug config (two runs initialise differently): read them, fork, change them in code.

Patch: report "cpu", give torch.cpu the memory functions the monitor calls (returning zeros), drop barrier(device_ids=...), which otherwise placed the barrier tensor on MPS.

FlexAttention does not support backward on CPUEvery Llama 3 flavour defaults to attn_backend="flex" (llama3/__init__.py L369 to L371), and SDPA is refused: "sdpa is no longer supported for language models; positions are always available so use flex, flex_flash, or varlen" (config_utils.py L97 to L101), because language models always use a block-causal mask built from per-document positions. Patch: evaluate the same BlockMask's mask_mod densely and call SDPA with it. Checked in forward on the first calls (bf16 inputs, even on one process): (a plain causal mask over 256 positions hides 49.8%).
4. Cannot use ReduceOp.PREMUL_SUM with GlooOnly with 2 processes: torchtitan sets FSDP2's gradient divide factor to 1.0 (section 3), and FSDP2 then reduce-scatters with PREMUL_SUM(1/1), which gloo lacks. Patch: ask FSDP2 for a plain SUM (its force_sum_reduction_for_comms path), followed by a division by 1.0: the same numbers.

Patches in src/exp/titan/ttrun.py; everything else (trainer, parallelisms, loss, optimiser, schedule, clipping, activation checkpointing) is torchtitan 0.3.0's own code from the tagged repository, which also supplies the debug tokenizer and the c4_test data. Settings changed for CPU speed only: sequence 256 instead of 2048, 10 steps, seed 0. Not run here: compile, float8, TP, PP, CP, EP (GPU kernels, or more processes than this page needs).

Selective activation checkpointing at 0.3.0, and what torchtitan calls in PyTorch (source and trace)

Correction to the old page, which said torchtitan offers "none / selective (op or layer) / full". At 0.3.0 the choices are none, full, selective and memory-budget (activation_checkpoint.py L329 to L337), and selective is per operator only; the per-layer option is gone. The per-op policy wraps each transformer block with create_selective_checkpoint_contexts and decides per ATen call: save the outputs of expensive ops (the SDPA variants, FlexAttention, aten.linear, aten.max for float8 scaling, topk for MoE routing, Inductor-compiled regions, and the communication ops reduce_scatter_tensor and all_to_all_single), recompute everything else, and of the matrix multiplies save only every second one (a counter of mm/linear calls; MoE router shapes are always recomputed) (L31 to L70, L185 to L288). memory-budget hands the trade-off to torch.compile's partitioner by setting torch._functorch.config.activation_memory_budget (default 0.5 there), and requires compile.

What it calls in PyTorch (trace, 2 processes): init_process_group, init_device_mesh, checkpoint_wrapper on the 6 blocks, fully_shard 9 times, set_gradient_divide_factor(1.0) on every FSDP module; then per step an all-reduce of the token count, set_requires_gradient_sync toggled around the chunked loss, clip_grad_norm_ through its own DTensor-aware version that calls DTensor.full_tensor() on the norm, AdamW.step, LRScheduler.step. The full ordered list is in What calls what.

7. DeepSpeed ZeRO against FSDP2

Both shard the training state across data-parallel ranks so each holds a slice (the forms and their memory maths are Distributed Training's; FSDP2's internals Distributed PyTorch's). As libraries they differ in who owns the step: DeepSpeed hands you an engine that replaces backward and step; FSDP2 is a function that marks modules and leaves your loop alone.

DeepSpeed: an engine owns the step
import deepspeed deepspeed.init_distributed(dist_backend="gloo") conf = {"train_micro_batch_size_per_gpu": 8, "zero_optimization": {"stage": 3}, "gradient_clipping": 0.0} # else 1.0 eng, opt, _, _ = deepspeed.initialize( model=model, optimizer=make_optimizer(model), config=conf) for x, y in batches: _, loss = eng(x, y) eng.backward(loss) # not loss.backward() eng.step() # clip, step, zero_grad
FSDP2: a function marks modules, your loop stays
from torch.distributed.fsdp import fully_shard from torch.distributed.device_mesh import init_device_mesh mesh = init_device_mesh("cpu", (2,)) for block in model.blocks: fully_shard(block, mesh=mesh) fully_shard(model, mesh=mesh) opt = make_optimizer(model) # on DTensor shards for x, y in batches: _, loss = model(x, y) loss.backward() opt.step(); opt.zero_grad()

Highlighted: where each takes over. The FSDP2 code is the root's Distributed lab recipe (its mesh= is needed on macOS).

measured on Apple M1 Pro, CPU, 2 processes, gloo (src/exp/calls_trace.py). Reference: PyTorch DDP's 3.80137, 3.09551, 3.16247. DDP's and FSDP2's own collectives are issued inside PyTorch, so they do not appear here; the root's Distributed lab counts them (FSDP2: 14 per step at world 2).

  • Same maths. With clipping off, every stage reproduces DDP's losses to five decimals: ZeRO is a memory layout, not a different optimiser.
  • The default clip shows up in the third loss. Without a gradient_clipping key, 0.19.7 clips at 1.0 and the third loss becomes 3.30068 instead of 3.16247, while the second moves only in the fifth decimal. Adam's first update is almost independent of the gradient's scale (with fresh moments, m/√v is the sign of each gradient entry, up to eps), so clipping step 0 barely matters; from the second update on, the moments mix two gradients scaled by different factors, and the path changes. The same config gave the unclipped result on 0.19.2 and earlier: pin versions and write every setting you rely on into the config.

When each. FSDP2 is in PyTorch: it composes with DTensor, tensor and pipeline parallelism, torch.compile and DCP, and is what Accelerate, Lightning, TRL and torchtitan call. DeepSpeed (a PyTorch Foundation project since May 2025) brings its own engine with offload of parameters and optimiser state to CPU memory and NVMe drives, its own optimisers and kernels, and long-standing integrations (HF Trainer via Accelerate, Megatron-DeepSpeed): pick it when you need those, or inherit it from a recipe. Mixing engines mixes their assumptions about who calls backward, clips and scales the loss (the Trainer turns its own accumulation scaling off under DeepSpeed, trainer.py L2096 to L2099).

Memory and traffic: state halves, small tensors stay whole, ZeRO-3 talks from Python (measured detail)

How it ran: DeepSpeed 0.19.7 from its released source with DS_ACCELERATOR=cpu, which selects its CPU accelerator and the gloo backend when oneCCL is absent (cpu_accelerator.py L31 to L34); PyTorch's own AdamW was passed in, so no DeepSpeed C++ operator was built.

  • Optimiser state halves from stage 1 on: AdamW's two moment tensors, 25.5 MB per rank at stage 0, 12.7 MB at stages 1 to 3 on 2 ranks.
  • ZeRO-3 does not shard small tensors. Parameters under stage3_param_persistence_threshold (default 100,000 elements, zero/config.py L229) stay whole on every rank: 40 of the running example's 52 tensors (norms, biases, both embeddings, and the 65,536-element attention output matrices); only the 12 larger block matrices are partitioned. It saves gathering many tiny tensors at the cost of a little memory.
  • ZeRO-3 talks a lot from Python. In 3 steps DeepSpeed called all_gather_into_tensor 178 times (parameters fetched before each module's forward and again for backward) and Tensor.item() 297 times, mostly in a helper that checks lists agree across ranks (get_lst_from_rank0, zero/utils.py). On a GPU every .item() waits for the device.

8. Config-driven fine-tuning: Axolotl, Unsloth, LLaMA-Factory

These tools answer "fine-tune model X on my data" with a configuration file instead of a loop (the top band of the hero). Underneath they are the Hugging Face stack: transformers models, PEFT adapters, TRL or Trainer loops, Accelerate for several GPUs. Their value is the recipe surface (chat templates, packing, LoRA and QLoRA, preference and RL trainers, day-one support for new open models) and, for Unsloth, faster kernels.

  • Axolotl 0.20.0 (2026-09-30): a YAML file becomes TrainingArguments plus a trainer class, a transformers.Trainer with mixins (its DPO, KTO, ORPO, GRPO and reward trainers subclass TRL's). Only settings present in the YAML are passed on, so an absent max_grad_norm means the Trainer's 1.0; its own defaults differ from the Trainer's in two places that move the curve: lr_scheduler: cosine (Trainer: linear) and prompt tokens masked out of the loss (train_on_inputs: false).
  • Unsloth (read at 2026.10.3) makes LoRA and full fine-tuning faster on one GPU by replacing transformers' forward methods with its own at import time, which call hand-written Triton kernels. The model you train is not the transformers code you read, it needs a GPU, and it caps the transformers versions it accepts.
  • LLaMA-Factory 0.9.5 (2026-05-30): the same idea with a web UI as well as YAML, also built on transformers, PEFT and TRL (version and date from PyPI, read 2026-10-13; not read further here).
A config tool fixes the whole stack under you
Axolotl 0.20.0 pins transformers==5.17.0 and torch>=2.13.0,<=2.14.0 (Requires-Dist of 0.20.0), so it would downgrade this page's transformers 5.19.0 and torch 2.14.1; Unsloth 2026.10.3 caps transformers at 5.17.0. Give each its own environment, or you change the stack under your other code. Neither was run here for that reason; both were read from their released wheels.
Axolotl and Unsloth in their source (file and line)

Axolotl. AxolotlTrainer is a transformers.Trainer with mixins for packing, schedulers, optimisers, checkpoint saving, offloading and distributed parallelism; its DPO, KTO, ORPO, GRPO and reward trainers subclass TRL's (wheel 0.20.0: core/trainers/base.py L101 to L111, core/trainers/trl.py, core/trainers/grpo/trainer.py). Unsloth (2026.10.5 on PyPI the day of writing). For Llama, for example, LlamaAttention.forward, LlamaSdpaAttention.forward, LlamaFlashAttention2.forward, LlamaDecoderLayer.forward, LlamaModel.forward, LlamaForCausalLM.forward and PeftModelForCausalLM.forward are reassigned (unsloth/models/llama.py L2595 to L2601), and the replacements call kernels for cross-entropy, RMSNorm and LayerNorm, RoPE, SwiGLU and GeGLU, the LoRA MLP and NF4 dequantisation (41 @triton.jit functions in unsloth/kernels/). A transformers upgrade can break or silently bypass a patch, which is why the 2026.10.3 wheel accepts transformers 4.52.4 to 5.17.0 only, minus nine listed versions in between (its Requires-Dist). Without a GPU it stops ("Unsloth cannot find any torch accelerator? You need a GPU.", device_type.py L108). On Apple Silicon it has a separate path through Apple's MLX framework (unsloth_zoo.mlx, device_type.py L39 to L47), not through PyTorch. How such kernels plug into PyTorch properly is Extending PyTorch's subject.

9. Megatron Core, and who is alive

  • Megatron Core 0.19.2 (NVIDIA): GPU-optimised building blocks for the largest runs: tensor-parallel layers, pipeline schedules, a distributed optimiser, fused kernels through Transformer Engine. It carries three data-parallel implementations side by side: its own DistributedDataParallel over contiguous gradient buffers, its own megatron_fsdp, and a wrapper around PyTorch's FSDP2 (wheel 0.19.2: megatron/core/distributed/). Expects NVIDIA GPUs; not run here. Tensor parallelism itself is Distributed Training's.
  • torchtune: "no longer actively maintained" since 2025-07-15 (issue 2883); last release 0.6.1. torchforge: development paused, "LLM training at PyTorch is being consolidated in torchtitan". Both live in the meta-pytorch organisation; torchtitan is pytorch/torchtitan.
NeMo, Composer, Monarch (status as read 2026-10-12)
  • NeMo: the NVIDIA/NeMo repository now points to NVIDIA-NeMo/Speech and "pivoted to focus on audio, speech, and multimodal LLMs"; nemo-toolkit 3.0.0 is speech only after the split. LLM training at NVIDIA goes through Megatron Core and its NeMo-branded recipes.
  • Composer (MosaicML, then Databricks): last release 0.32.1 on 2025-07-26; quiet. Its StreamingDataset is still used for sharded data in object stores.
  • Monarch (single-controller distributed programming, torchmonarch 0.7.0 on 2026-10-10): active, in meta-pytorch.

Versions, dates and statuses: the root's Ecosystem map (PyPI and repository READMEs, read 2026-10-12), where every one of these has a card with its primary source; ownership news about these companies is in the root's section 9.

What the trace sees, and what it cannot
  • It sees the boundary: a library calling DistributedDataParallel(...), fully_shard, clip_grad_norm_, dist.all_gather_into_tensor. That is where a library's choices live.
  • It does not see what PyTorch then does inside: DDP's bucketed all-reduces come from its C++ reducer and FSDP2's all-gathers from its own hooks, so they never cross a library boundary. The root's Distributed lab counts those collectives; the Inside one step tab follows a step down to ATen calls.
  • DeepSpeed shows many collectives here because it issues them itself in Python (its deepspeed.comm layer calling torch.distributed).
