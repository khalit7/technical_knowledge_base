"Maths" counts tensor operations called from library code: none for the Trainer, Accelerate and Lightning, whose model is yours; tens of thousands for torchtitan and DeepSpeed ZeRO-3, which own model code (torchtitan's Llama) or wrap every layer's forward and backward (ZeRO-3's parameter fetching). "Module" is nn.Module plumbing (attribute access, parameters(), hooks).

What the trace sees, and what it cannot
  • It sees the boundary: a library calling DistributedDataParallel(...), fully_shard, clip_grad_norm_, dist.all_gather_into_tensor. That is where a library's choices live.
  • It does not see what PyTorch then does inside: DDP's bucketed all-reduces come from its C++ reducer and FSDP2's all-gathers from its own hooks, so they never cross a library boundary. The root's {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} counts those collectives; the {{Inside one step|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} tab follows a step down to ATen calls.
  • DeepSpeed shows many collectives here because it issues them itself in Python (its deepspeed.comm layer calling torch.distributed).

The root's {{Ecosystem map|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} shows the complementary view: the full Python call stack at the moment the forward and the optimizer step begin, for five entry points, and which core APIs each library's released source uses.
