5. Lightning and Fabric

Lightning splits your code into hooks on a LightningModule (training_step, configure_optimizers, configure_model, ...) and runs the loop, logging, checkpointing and distribution for you. Fabric is the half that keeps your own loop: fabric.setup(model, optimizer), fabric.backward(loss), and the launch, precision and strategy are handled.

The loop runs inside the optimiser's step. With automatic optimisation, Lightning calls optimizer.step(closure) and the closure runs your training_step, then backward (the root's Ecosystem map draws the two call stacks). So an optimiser pre-step hook fires before the gradients exist: a trap met while building this page's defaults runs; use the on_before_optimizer_step hook instead. Its defaults: no clipping, 32-true precision, the loss divided by accumulate_grad_batches, and a DistributedSampler added to your dataloader when distributed (use_distributed_sampler=True).

FSDP2 is not FSDPStrategy. In Lightning 2.6.6 FSDPStrategy is FSDP1, the older flat-parameter wrapper; FSDP2 is ModelParallelStrategy, which builds the DeviceMesh and leaves you to call fully_shard and parallelize_module in configure_model. Run here on 2 CPU processes it gave DDP's losses, with parameters turned into DTensor.

When. Lightning fits research code where many models share one structure (vision, science, smaller LLM work) and teams that value callbacks and checkpoint conventions. New LLM parallelism arrives in PyTorch and torchtitan first; Lightning exposes it through ModelParallelStrategy, where the parallel plan is still yours to write. Fabric keeps the launch and precision and gives the loop back.

In a distributed run Lightning's training loop broadcasts a one-element "received SIGTERM" tensor from rank 0 at every step and reads it back with .item() ({{training_epoch_loop.py L258 to L270|https://github.com/Lightning-AI/pytorch-lightning/blob/2.6.6/src/lightning/pytorch/loops/training_epoch_loop.py#L258-L270}}); the trace saw it once per step under both strategies. On a GPU each .item() is a host synchronisation (the CPU waits for the GPU; see {{Making training fast|n:3c65c17b0d0d810d9e1fdf9ec942c20d}}), small but on the step's critical path: if a Lightning DDP job is slower per step than a plain DDP script, a profiler trace shows the CPU waiting there and wherever tensors are logged.
