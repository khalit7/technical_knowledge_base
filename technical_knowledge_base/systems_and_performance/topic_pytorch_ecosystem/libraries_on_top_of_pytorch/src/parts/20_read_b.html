1. The same loop, the same losses

This is everything a training library automates. Run it next to the root's src/model/model.py with PyTorch 2.14 and it prints three losses that every library reproduces once its settings match.

import torch from model import GPTConfig, make_model, get_batch, make_optimizer torch.set_num_threads(2) cfg = GPTConfig() # 4 layers, d_model 256, batch 8 x 64 chars model = make_model(cfg) # seeded: same weights on every run opt = make_optimizer(model) # AdamW lr 6e-4, betas (0.9, 0.95), # weight decay 0.1 on matrices for step in range(3): x, y = get_batch(cfg, step) # batch k is the same on every run _, loss = model(x, y) # forward + mean cross-entropy loss.backward() # gradients into .grad opt.step() # update opt.zero_grad(set_to_none=True) print(step, round(loss.item(), 5)) # 0 3.80137 # 1 3.18793 # 2 3.16783

Output recorded on Apple M1 Pro, CPU, 2 threads, torch 2.14.1 (src/exp/defaults_lab.py, which runs it for 150 steps).

Fig. 2, step by step: one training step's calls into PyTorch, by who makes them

  1. You call backward(). The top plate is your script; the bottom plate is PyTorch, with one socket per kind of call. In the plain loop every call starts on your plate: here Tensor.backward, 3 times in 3 steps.
  2. You call the optimiser. Adam.step, from the same line of your script.
  3. You clear the gradients and read the loss. Optimizer.zero_grad and Tensor.item. There is no clipping and no schedule, because you did not write them.
  4. The whole step: 5 calls into PyTorch. Four key calls and the forward, all yours (the forward goes through nn.Module plumbing and is not drawn as a socket). Every library below makes these same calls; the losses are 3.80137, 3.18793, 3.16783.
  1. Setup: the Trainer prepares things you did not ask for. The middle plates are the Trainer (transformers) and Accelerate under it. Before the first forward the Trainer seeds (manual_seed, and manual_seed_all for CUDA, in set_seed), builds a DataLoader, Accelerate wraps it in a second one (DataLoaderAdapter), and the Trainer zeroes the gradients.
  2. backward() comes from Accelerate. Accelerator.backward calls Tensor.backward (after dividing the loss by the accumulation steps, 1 here). The dots fall from Accelerate's plate through PyTorch's: the same socket the plain loop used.
  3. A clip you did not ask for. clip_grad_norm_ runs on every step even with max_grad_norm=0: the Trainer then calls it with an infinite limit, only to log the gradient norm. A call the plain loop never makes.
  4. The optimiser step, through a wrapper. Accelerate's AcceleratedOptimizer.step calls your Adam.step.
  5. The Trainer closes the step. Trainer._run_epoch steps the schedule (a constant one here, matched to the plain loop) and calls zero_grad; the trace script's forward hook reads the loss with .item().
  6. The whole step: 91 calls into PyTorch, the same losses. Same sockets as the plain loop plus clipping and the schedule, made from three plates instead of one; most of the 91 are nn.Module plumbing. The losses are 3.80137, 3.18793, 3.16783, exactly the plain loop's.
  1. Setup, and the optimiser step opens first. You seed and build the DataLoader; Lightning's Trainer zeroes the gradients. Then Precision.optimizer_step calls Adam.step before the first forward has run: with automatic optimisation Lightning calls optimizer.step(closure), and the closure does the rest of the step inside it. The glowing socket is that open step.
  2. Inside the closure: your training_step. It runs the forward and reads the loss for the record (.item()), from your plate.
  3. Lightning zeroes the gradients (LightningModule.optimizer_zero_grad), still inside the closure, before the backward.
  4. Lightning calls backward() (LightningModule.backward). So an optimiser pre-step hook fires before the gradients exist: read them in on_before_optimizer_step instead.
  5. The closure returns and Adam.step updates. In the loop the trace counts it from Precision.optimizer_step twice; the first step's call was already seen in setup.
  6. The whole step: 110 calls into PyTorch, the same losses. No clipping and no schedule by default, the zero_grad before the backward, and the same 3.80137, 3.18793, 3.16783.

Every flow is a recorded call from the {{What calls what|#t-calls}} traces (3 steps, src/exp/calls_trace.py, measured on Apple M1 Pro, CPU); the number beside a flow is how often that caller made the call in the run. Plates: your script, the Trainer (transformers), Accelerate, Lightning, PyTorch. Calls per step count every call into PyTorch, plumbing included.

Predict: the Hugging Face Trainer runs this same model on the same 8-row batches, with its defaults. Are its first three losses 3.80137, 3.18793, 3.16783?
None of them with its defaults: it shuffles the rows (so step 0 sees a different batch: 3.78405), clips, and uses its own AdamW at lr 5e-5 with betas (0.9, 0.999) and a linear decay; recorded 3.78405, 3.47902, 3.31911. With three settings changed (highlighted below) it gives exactly 3.80137, 3.18793, 3.16783, as do Accelerate and Lightning measured on Apple M1 Pro, CPU.

The matched Trainer call: three settings make it the plain loop (from src/exp/defaults_lab.py).

from transformers import Trainer, TrainingArguments args = TrainingArguments(output_dir="out", max_steps=150, per_device_train_batch_size=8, use_cpu=True, report_to=[], save_strategy="no", train_sampling_strategy="sequential", # default "random" max_grad_norm=0.0) # default 1.0: clipping on opt = make_optimizer(model) # default: AdamW 5e-5, (0.9, 0.999), wd 0 const = torch.optim.lr_scheduler.LambdaLR(opt, lambda s: 1.0) # default: linear decay to 0 Trainer(model=model, args=args, train_dataset=rows, optimizers=(opt, const)).train()

The model must return a dict with a loss key (a ten-line subclass of the running example does it); rows is a dataset of {"input_ids", "labels"} rows in the plain loop's order. Everything a library adds beyond these duties is logging, checkpointing and distribution.
