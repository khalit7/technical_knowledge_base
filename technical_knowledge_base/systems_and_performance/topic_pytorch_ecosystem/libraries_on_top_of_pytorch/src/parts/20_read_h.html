7. DeepSpeed ZeRO against FSDP2

Both shard the training state across data-parallel ranks so each holds a slice; the theory (ZeRO stages 1, 2, 3 = optimizer state, plus gradients, plus parameters, and the bytes per parameter) is on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}, and PyTorch's FSDP2 internals on {{Distributed PyTorch|n:3c65c17b0d0d815e85aff8decd8f35ab}}. Here: the two APIs, and what each did with the running example on 2 CPU processes.

DeepSpeed: an engine owns the step
import deepspeed deepspeed.init_distributed(dist_backend="gloo") conf = {"train_micro_batch_size_per_gpu": 8, "zero_optimization": {"stage": 3}, "gradient_clipping": 0.0} # else 1.0 eng, opt, _, _ = deepspeed.initialize( model=model, optimizer=make_optimizer(model), config=conf) for x, y in batches: _, loss = eng(x, y) eng.backward(loss) # not loss.backward() eng.step() # clip, step, zero_grad
FSDP2: a function marks modules, your loop stays
from torch.distributed.fsdp import fully_shard from torch.distributed.device_mesh import init_device_mesh mesh = init_device_mesh("cpu", (2,)) for block in model.blocks: fully_shard(block, mesh=mesh) fully_shard(model, mesh=mesh) opt = make_optimizer(model) # on DTensor shards for x, y in batches: _, loss = model(x, y) loss.backward() opt.step(); opt.zero_grad()

DeepSpeed 0.19.7 ran from its released source with DS_ACCELERATOR=cpu, which selects its CPU accelerator and the gloo backend when oneCCL is absent ({{cpu_accelerator.py L31 to L34|https://github.com/deepspeedai/DeepSpeed/blob/v0.19.7/accelerator/cpu_accelerator.py#L31-L34}}); PyTorch's own AdamW was passed in, so no DeepSpeed C++ operator was built. The FSDP2 code is the root's {{Distributed lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} recipe (its mesh= is needed on macOS).

Collectives are the calls DeepSpeed made into torch.distributed; DDP's and FSDP2's collectives are issued inside PyTorch (the reducer and FSDP2's hooks) and are counted on the root's Distributed lab (FSDP2: 14 per step at world 2).

  • Same maths. With clipping off, every stage reproduces DDP's losses to five decimals: ZeRO is a memory layout, not a different optimizer.
  • The default clip shows up at step 2. Without a gradient_clipping key, 0.19.7 clips at 1.0 and the third loss becomes instead of 3.16247 while the second moves only in the fifth decimal. Adam's first update is almost independent of the gradient's scale (with fresh moments, m/√v is the sign of each gradient entry, up to eps), so clipping step 0 barely matters; from the second update on, the moments mix two gradients scaled by different factors, and the path changes. The same config gave the unclipped result on 0.19.2 and earlier.
  • Optimizer state halves from stage 1 on: AdamW's two moment tensors, per rank at stage 0, at stages 1 to 3 on 2 ranks.
  • ZeRO-3 does not shard small tensors. Parameters under stage3_param_persistence_threshold (default 100,000 elements, {{zero/config.py L229|https://github.com/deepspeedai/DeepSpeed/blob/v0.19.7/deepspeed/runtime/zero/config.py#L229}}) stay whole on every rank: of the running example's 52 tensors (norms, biases, both embeddings, and the 65,536-element attention output matrices); only the 12 larger block matrices are partitioned. It saves gathering many tiny tensors at the cost of a little memory.
  • ZeRO-3 talks a lot from Python. In 3 steps DeepSpeed called all_gather_into_tensor times (parameters fetched before each module's forward and again for backward) and Tensor.item() times, mostly in a helper that checks lists agree across ranks (get_lst_from_rank0, {{zero/utils.py|https://github.com/deepspeedai/DeepSpeed/blob/v0.19.7/deepspeed/runtime/zero/utils.py}}). On a GPU every .item() waits for the device.

When each. FSDP2 is in PyTorch: it composes with DTensor, tensor and pipeline parallelism, torch.compile and DCP, and is what Accelerate, Lightning, TRL and torchtitan call (root's Ecosystem map). DeepSpeed (a PyTorch Foundation project since May 2025) brings its own engine with offload of parameters and optimizer state to CPU memory and NVMe drives, its own optimizers and kernels, and long-standing integrations (HF Trainer via Accelerate, Megatron-DeepSpeed); pick it when you need those, or inherit it from a recipe. Mixing them means mixing two engines' assumptions about who calls backward, who clips, and who scales the loss (the Trainer turns its own accumulation scaling off under DeepSpeed, {{trainer.py L2096 to L2099|https://github.com/huggingface/transformers/blob/v5.19.0/src/transformers/trainer.py#L2096-L2099}}).
