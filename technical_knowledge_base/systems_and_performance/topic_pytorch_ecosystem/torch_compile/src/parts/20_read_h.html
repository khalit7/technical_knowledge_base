10. Caches: paying the compile once

The problem. A cold compile of this tiny model's training step takes about 9 seconds on the laptop; real models take minutes, and a job on 1,000 GPUs restarted after a failure would pay it on every rank.

How it works. Several caches on disk, all under TORCHINDUCTOR_CACHE_DIR (a per-user temporary directory by default), each keyed by a hash of its input graph, the config and the versions: the FX graph cache (Inductor's output for a post-AOTAutograd graph; fx_graph_cache, on, inductor config.py L109), the AOTAutograd cache (the forward and backward graphs for a Dynamo graph, so even AOTAutograd is skipped; enable_autograd_cache, on, functorch config.py L71), the compiled kernels themselves (C++ shared objects, Triton binaries) and autotuning results. Dynamo still traces on every new process: guards are not cached by these. Mega-cache packs the cache entries a process used into one blob: torch.compiler.save_cache_artifacts() returns bytes, load_cache_artifacts(bytes) installs them in another process's cache directory. Measured, whole model, CPU, 3 runs each, each scenario in its own private cache directory:

First training step: cold, warm, and from a mega-cache

Warm, the first step took 0.85 s against 9.08 s cold (medians): both Inductor graphs and the AOTAutograd entry hit, and nothing was compiled. The mega-cache, loaded into an empty directory in a fresh process, gave 5.06 s: the same cache hits (2 FX graph, 1 AOTAutograd), but 4.0 s still went to async_compile.wait, compiling the C++ kernels again. The blob (1,265,370 bytes) carries the generated source, not this machine's compiled .so files, so on a CPU it saves the Python half of the compile and not the C++ half. On a GPU the large win is the Triton kernels and autotuning results it carries (not measured here).

A cache can serve a wrong program
The sibling {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}} found that the AOTAutograd cache key does not include whether a custom op's autograd formula is registered: a process that registered it late produced a backward that silently dropped gradients, and a later, correct process reading the same cache reused that broken backward. TORCHINDUCTOR_AUTOGRAD_CACHE=0 avoided it there. When you change custom-op registrations or other code the key cannot see, use a fresh cache directory.

How to check. The counters torch._dynamo.utils.counters["inductor"]["fxgraph_cache_hit"] and counters["aot_autograd"]["autograd_cache_hit"] (used for the table above); TORCH_LOGS=cache; torch._dynamo.utils.calculate_time_spent() for the phase split. To be sure you are measuring a cold compile, point TORCHINDUCTOR_CACHE_DIR at an empty directory, or set torch.compiler.config.force_disable_caches.

11. torch.export and AOTInductor: one graph to ship

The problem. torch.compile is a just-in-time compiler for a Python process: it needs your Python code, falls back to Python at breaks, and recompiles when guards fail. To deploy a model where there is no Python, or to hand a graph to another tool, you need the whole program captured once, ahead of time, with its assumptions written down.

How it works. torch.export.export(model, args, dynamic_shapes=...) captures one graph with no breaks allowed and returns an ExportedProgram: the graph (ATen ops), a graph signature saying which inputs are parameters, buffers or user inputs, the state_dict, and range constraints on every symbolic size. Two tracers: non-strict (the default at 2.14.1, strict=False in its signature) runs your Python normally with fake tensors and records the ATen calls; strict traces through Dynamo, which can reject Python it cannot prove safe. On the running example (logits only, eval) both produced the same 94-op graph, measured; its signature lists 53 parameter inputs (the tied embedding twice, under its two names) and 1 user input. ep.run_decompositions() lowers it to the core ATen set: 326 ops.

Four lessons from the table. (1) A dynamic dimension you declare is checked: the reshape to 8 rows made export fail with "You marked batch as dynamic but your code specialized it to be a constant (8)" and a suggested fix. (2) A range is not checked against data: T up to 128 exported fine although the position table has 64 rows; T > 64 would index past it at run time. With the correct range, a T = 100 input was rejected on entry ("Guard failed: idx.size()[1] <= 64", recorded). (3) Dim.AUTO found both dimensions dynamic but from 2, not 1 (0/1 specialisation again). (4) Data-dependent Python control flow cannot be exported in either mode; torch.cond can. torch.export.draft_export exports it anyway and reports the problem; here it picked the branch the example took (cos) and inserted a runtime assert, with the advice to add torch._check.

Saving and AOTInductor. torch.export.save wrote a 12,986,850-byte .pt2 archive (52 weight files, since tied weights are stored once, plus the graph as JSON); loading it gave identical outputs. torch._inductor.aoti_compile_and_package(ep) compiles the program ahead of time into a shared library inside a 14,358,669-byte package (the 14,163,036-byte wrapper.so holds the weights) that aoti_load_package runs from Python, or a C++ runner without Python. Outputs matched eager within 1.25e-06 at (8, 64).

Measured here: AOTInductor and a non-contiguous input
A slice x[:3, :20] of the batch (strides (64, 1), not contiguous) passed to the AOTInductor package returned logits with a maximum error of 1.81 against eager, with no error or warning; the same input after .contiguous() matched within 9.5e-07, and the exported program's own ep.module() handled the slice exactly (0.0). The compiled library assumed the strides it was compiled for. Call .contiguous() on inputs to an AOTInductor model.

Where it leads. ExecuTorch (on-device) and the ONNX exporter (dynamo-based by default since 2.9) start from torch.export; the file formats are on {{Model formats|n:3cd5c17b0d0d81ea815aedfa052e4919}}.
