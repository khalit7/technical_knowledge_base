The idea in one screen

torch.compile captures your Python as a graph on the first call (Dynamo), derives the backward and chooses what the forward keeps for it (AOTAutograd), fuses both into kernels (Inductor), and reuses that code on every later call whose guards still pass. Everything you tune is one of three things: keep the graph whole, keep the guards passing, pay the compile once.

The first call runs three compilers; every later call is a guard check

Numbers are the running example, measured here (torch 2.14.1, CPU): the whole training step for Dynamo and AOTAutograd (the root's Compile lab and section 5), one block's forward for Inductor (section 6), the cold and warm first step for the cache (sections 9 and 10). The off-ramps are the two ways the picture goes wrong: a graph break (section 3) and a recompile (section 4).

torch.compile(model) returns a wrapper and does nothing until the first call. The parent page's {{Compile lab|n:3c65c17b0d0d8150aa65ca44b6ed2fd5}} measured what this does to one training step of the running example (the 3,186,944-parameter character GPT: 4 blocks, d 256, batch 8 x 64 tokens): one graph, 59 operations, 0 breaks, 549 guards; no gain on the laptop's CPU (23.20 ms against 22.75 ms) and 1.18 times on its GPU (MPS). This page goes one level down into each stage, on the same model, so you can predict what compile will do to your code, read what it did, and fix it.

You need fake tensors and functionalization ({{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}, section 2.5). New terms, each defined again where it is used:

frame, bytecode
one function call, and the stack-machine instructions CPython runs for it
guard
a check that compiled code is still valid for this call (shape, dtype, object identity, global flags)
graph break
a line Dynamo cannot capture: it runs in Python and the graph is split around it
recompile
a guard failed, so another version of the frame is compiled and cached
symbol (backed, unbacked)
a size compiled as a variable; backed from an input size, unbacked from data
joint graph, partitioner
forward and backward as one graph, and the cut that decides what is saved between them
fusion, wrapper
several ops in one kernel; the generated Python that launches the kernels in order

1. Dynamo: reading your Python as it runs

A compiler needs the whole computation as a graph, but a model is ordinary Python: loops over layers, attribute lookups, the odd if. Dynamo keeps running Python as Python and captures only what it can prove safe.

Why not the earlier capture tools (PyTorch 2 paper, section 2)

torch.jit.trace ran the model once and recorded only the path taken, silently wrong when control flow changed; torch.jit.script required a restricted Python dialect; torch.fx.symbolic_trace fails on any data-dependent branch. The PyTorch 2 paper ({{Ansel et al., ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}, section 2) reviews them.

How it works. CPython compiles each function to bytecode, a list of stack-machine instructions (LOAD_FAST x pushes a local, LOAD_ATTR fc replaces the top of the stack with its attribute, CALL 1 calls with one argument), and evaluates one frame (one function call) at a time. PEP 523 lets a C extension replace the frame evaluator; Dynamo installs its own (enable_eval_frame_shim, eval_frame.c L247-L255 at v2.14.1), so it sees every frame first. For a frame compiled before, it runs the guards and, if they pass, jumps to the compiled version. Otherwise it symbolically evaluates the bytecode: the same instructions, but its stack holds VariableTrackers instead of values.

TensorVariableA tensor, as a fake tensor (shape, dtype, device, no data) plus a proxy: every operation on it adds a node to the FX graph.
NNModuleVariableA module such as self.fc. Calling it inlines its forward; its parameters become graph inputs.
LazyVariableTrackerA value not inspected yet; turned into a real tracker (and guarded) only if the code uses it, which keeps the guard list short.
Constant, builtin, Python moduleComputed at trace time: C // n_head is evaluated now and baked into the graph as a number, with a guard on what it came from.

One frame gives three things: an FX graph (tensor operations and their inputs), the guards, and new bytecode for the frame that gathers the inputs, calls the compiled graph and returns its result. Bytecode

Recorded with torch 2.14.1, Python 3.12, CPU (exp/walk.py). By the end CPython has run 9 ATen calls (two addmm, gelu, and the views and transposes F.linear decomposes into on the CPU); Dynamo has run none: 36 instructions, both Linear.forward calls inlined (depth 1), a graph of three calls (linear, gelu, linear) on five inputs (x and four parameters), and 45 guards. Dynamo's copy of MLP.forward has two extra instructions before each call (PUSH_NULL, SWAP) from rewriting the bytecode into a canonical form. Stack entries are Dynamo's own repr, shortened (Lazy(...) = LazyVariableTracker).

Attribute lookups such as self.fc never reach the graph: they were answered at trace time, and the answer is protected by a guard.

Predict: inside a compiled function, how many times does self.fc (a Python attribute lookup) run per call after the first?
Zero, as such. The rewritten bytecode (recorded with TORCH_LOGS=bytecode) fetches the parameters straight out of self._modules['fc']._parameters['weight'] and passes them to the compiled graph; whether fc is still the same kind of module is the guards' job, and they run in C++ before the call. That is why a module swapped after compilation is caught by a guard and recompiled rather than silently ignored.

Cost. Tracing is Python running Python: for the whole running example, Dynamo's share of the first call ("entire_frame_compile" minus the backend) was about 0.25 s of the roughly 9 s cold compile; the rest is AOTAutograd and Inductor (section 10). Afterwards each call pays only the guard check (section 2). Check with TORCH_LOGS=bytecode (original and rewritten bytecode), graph_code (the FX graph with each line's source), trace_bytecode (every instruction with the tracker stack, what the stepper replays), or torch._dynamo.explain(fn)(*args) for a summary of graphs and breaks.
