12. Debugging: a workflow and its tools

When compile misbehaves, the symptom is one of four: it is slow to compile, it is not faster, it gives different numbers, or it crashes. The workflow, each step with the tool used on this page:

  1. Count graphs and breaks first. torch._dynamo.explain(model)(x, y) (sections 3 and 4). Then TORCH_LOGS="graph_breaks,recompiles" on a real run.
  2. Bisect the stack. backend="eager" runs Dynamo only, "aot_eager" adds AOTAutograd, the default adds Inductor. Whichever first changes the numbers or crashes is the culprit.
  3. Read one compile end to end. Set TORCH_TRACE=<dir> and run tlparse on the log: one HTML report with every frame compiled, every graph (Dynamo, joint, forward, backward, post-grad), the generated code, guards, breaks and recompile reasons per compile id.
  4. Shrink a crash. torch._dynamo.config.repro_after = "aot" (or "dynamo") makes a failing compile write a launcher script; running it minifies the graph.
  5. Find where compile time goes. torch._dynamo.utils.calculate_time_spent() (section 10), or the compilation_metrics pages tlparse writes.

Common mistakes


Logging inside the model with print or .item()
Each is a graph break; inside the block loop it costs the whole forward (section 3). Log outside the compiled function, or keep values as tensors and read them every N steps.


Calling mark_dynamic on one tensor of several that share a dimension
The targets carry the same length as the inputs and are guarded too (Compile lab); mark every tensor with the dimension, or give the bound with min and max so violations are errors you see.


Assuming nested_graph_breaks keeps a model compiled
It did nothing for a break inside a for loop over blocks, measured (section 3).


Passing a different Python string, dtype or config value each call
Guarded by value with no symbolic fallback: after 8 versions, eager mode with only a warning (section 4).


Timing the first call
It includes 9 seconds of compiling here; warm up, then time, and synchronise on a GPU ({{Making training fast|n:3c65c17b0d0d810d9e1fdf9ec942c20d}} section 1).


Compiling the whole model when compile time hurts
Compile the block (section 9): 5.7 s instead of 9.2 s here, and it does not grow with depth.


Measuring a "cold" compile with a warm cache
The caches are on by default and survive processes: 0.85 s looks like a fast compiler. Use an empty TORCHINDUCTOR_CACHE_DIR.


Feeding a sliced tensor to an AOTInductor package
Wrong answers with no warning, measured (section 11). Make inputs contiguous.


Reading activation_memory_budget from torch._dynamo.config
It lives in torch._functorch.config at 2.14.1 (the sibling page found the blog's spelling does not exist).






Interview questions, with short answers


How does Dynamo capture a graph without running the model on real data?
It installs a PEP 523 frame evaluator and symbolically executes each frame's bytecode with VariableTrackers; tensors are fake tensors carrying shapes, so ops add FX nodes and Python values are computed at trace time and protected by guards.


What is a guard, and what happens when one fails?
A condition the compiled code assumed (shape, dtype, object identity, global state), checked in C++ before each call. On failure Dynamo recompiles and caches another version, up to recompile_limit (8), then runs eagerly.


Why might one graph break cost the whole model?
A break inside a loop cannot be resumed, so Dynamo skips the enclosing frame: everything outside the blocks runs eagerly and the blocks compile in pieces.


Backed versus unbacked symbolic sizes?
Backed come from input sizes and have an example value to answer branches; unbacked come from data (.item(), nonzero) and do not, so branches on them need torch._check or torch.cond.


What does the min-cut partitioner optimise?
Which joint-graph values the forward saves for backward: it minimises saved bytes, recomputing cheap ops; activation_memory_budget lets it recompute expensive ones too.


Where does Inductor fuse?
Mostly at lowering (pointwise ops are inlined into consumers), then in the scheduler (vertical and horizontal fusion of loops); matmuls and attention stay library calls unless autotuning picks a template.


What do the modes change?
Only Inductor config: reduce-overhead turns on CUDA graphs; max-autotune adds matmul autotuning, coordinate-descent tuning and CUDA graphs; -no-cudagraphs drops the graphs.


Compiled autograd: what and why?
Tracing the autograd engine's graph at backward time, including hooks and accumulation, so the backward compiles as one graph and distributed communication can be traced and overlapped.


How do you cut compile time for a 70B model?
Regional compilation of the repeated block, warm caches shared across ranks (mega-cache), avoiding recompiles (mark dynamic dims, stable Python args), and profiling compile time by phase.


torch.compile versus torch.export?
compile is a JIT inside Python that tolerates breaks and recompiles; export captures one full graph with explicit dynamic-shape constraints for deployment (ExecuTorch, AOTInductor, ONNX).
