Compile time and caches

The first training step of the running example in a fresh process, played back in real proportion: where the seconds go, and what each way of compiling or caching removes. Each bar is the run closest to the median of three (CPU, 4 threads, torch 2.14.1, bench lock); the phases are Dynamo's own timers (calculate_time_spent()). How the phases are derived: Dynamo = entire_frame_compile minus backend_compile; forward = backend_compile; backward = entire_backward_compile; the rest = first-step time minus both. Waiting for the C++ compiler (async_compile.wait) sits inside the forward and backward phases; it is listed per run below.

Every run

What to take away. The warm run did no compiling: its 0.85 s is Dynamo tracing again plus loading cached code, which is why guards and tracing are the floor of a warm start. The mega-cache run hit the same caches but still waited about 4 s for the C++ compiler, because on a CPU the blob carries kernel source, not the built libraries. Per-block compilation cut the cold start by about 40% at 4 blocks and by half at 8, and did not grow with depth.
