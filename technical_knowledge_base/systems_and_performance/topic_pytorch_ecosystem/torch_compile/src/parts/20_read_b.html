2. Guards: the conditions that keep compiled code valid

Everything Dynamo baked in (shapes, dtypes, which module object, a Python flag, grad mode) must still hold on the next call, or the compiled code computes the wrong thing; checking it in Python each call would cost more than the kernels of a small model. So each fact becomes a guard in a tree keyed by where the value comes from (L['x'] for a local, G['F'] for a global, attributes of those), built in C++ (GuardManager, RootGuardManager, guards.cpp L4242; enable_cpp_guard_manager is on by default): a check walks each source once and runs its leaf guards. Four kinds do most of the work: TENSOR_MATCH (dispatch keys, dtype, device, requires_grad, sizes and strides of a tensor input), ID_MATCH (this exact object: the F module, the gelu builtin), TYPE_MATCH, and GLOBAL_STATE (grad mode, autocast, default dtype, thread count, deterministic flag, in one check). DIMENSION_DYNAMIC_MARKING_GUARD makes sure a tensor that later gets mark_dynamic is not served by code compiled for a static shape.


Cost. 51.71 microseconds for the MLP's tree in the recorded run (one unlocked measurement that varied by about two times between runs: an order of magnitude); the whole model's 549 guards measured 45 to 81 microseconds in the Compile lab. Nothing against a 23 ms CPU step; a real overhead against a 1 ms GPU step, where kernels launch asynchronously and the CPU's time is the critical path. When a guard fails, Dynamo compiles again and keeps both versions in a per-frame cache, checked in order on each call: a recompile (section 4).


Guard APIs: skipping guards, and failing on recompiles (torch 2.14.1)
Three APIs trade safety for speed: torch.compiler.skip_guard_on_inbuilt_nn_modules_unsafe, skip_guard_on_all_nn_modules_unsafe and skip_guard_on_globals_unsafe (all present in torch.compiler at 2.14.1, read from the wheel); their names say what they risk. torch.compiler.set_stance("fail_on_recompile") turns every recompile into an error, useful in a test that pins the number of compiles; "eager_on_recompile" runs eagerly instead.






3. Graph breaks: each kind, and how to remove it


When Dynamo meets something it cannot put in a graph, it does not fail by default: it compiles the graph so far, emits bytecode that runs the unsupported instruction in plain Python, and starts a new graph after it (a resume function). That split is a graph break. It costs twice: no fusion across it, and Python plus a guard check between the pieces on every call. The Compile lab measured a print in each block at +7 to 9% step time on the CPU; on a GPU each piece also launches separately and a CUDA graph cannot span the break.


Where the break sits matters more than how many. GPT.forward runs the blocks in a for blk in self.blocks loop, and Dynamo cannot resume tracing in the middle of a loop: a break anywhere inside a block makes it give up on the whole GPT.forward frame ("Failed to handle graph break gracefully. Skipping the function and falling back to eager", its own log, read with tlparse in section 12). The embeddings, final LayerNorm, head and loss then run as plain Python and only the two halves of each block are compiled: 8 piece calls per forward instead of 1. Three lessons from the twelve rows. (1) Some flags remove a break by changing what a graph may contain: capture_dynamic_output_shape_ops lets boolean-mask indexing in (the selected size becomes a symbol); reorderable_logging_functions = {print} moves the print to after the graph runs (so it prints after the whole region, not at its line). (2) fullgraph=True is not just "no breaks": for the boolean mask it compiled without error, because when one graph is required Dynamo captures the dynamic size instead of breaking, while for .item() followed by an if it raised. (3) A @torch.compiler.disable helper is a deliberate break; call it outside the compiled region, or register the code as a custom op ({{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}} owns that; its root lesson: a .tolist() body gives 3 graphs and 2 breaks, the same body as a custom op 1 and 0).
