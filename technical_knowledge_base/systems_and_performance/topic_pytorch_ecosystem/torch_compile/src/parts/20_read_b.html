1. Dynamo: reading your Python as it runs

The problem. A compiler needs the whole computation as a graph, but a PyTorch model is ordinary Python: loops over layers, attribute lookups, calls into nn.Module.forward, the odd if. Earlier capture tools each gave something up: torch.jit.trace ran the model once and recorded only the path taken, silently wrong when control flow changed; torch.jit.script required a restricted Python dialect; torch.fx.symbolic_trace fails on any data-dependent branch. The PyTorch 2 paper ({{Ansel et al., ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}, section 2) reviews them; Dynamo's answer is to keep running Python as Python and capture only what it can prove safe.

How it works, from zero. CPython does not run your source text: it compiles each function to bytecode, a list of small stack-machine instructions (LOAD_FAST x pushes a local variable, LOAD_ATTR fc replaces the top of the stack with its attribute, CALL 1 calls a function with one argument), and evaluates one frame (one function call) at a time. PEP 523 lets a C extension replace the function that evaluates frames. When you call a compiled function, Dynamo installs its own (enable_eval_frame_shim, torch/csrc/dynamo/eval_frame.c L247-L255 at v2.14.1), so it sees every frame before CPython runs it. For a frame it has compiled before, it runs the guards and, if they pass, jumps to the compiled version. Otherwise it symbolically evaluates the bytecode: the same instructions, but its stack holds VariableTrackers instead of values.

TensorVariableA tensor, represented by a fake tensor (shape, dtype, device, no data; {{see 2.8 there|n:3f85c17b0d0d81138595c1c6cd52f795}}) plus a proxy: every operation on it adds a node to the FX graph.
NNModuleVariableA module such as self.fc. Calling it inlines its forward; its parameters become graph inputs.
LazyVariableTrackerA value not inspected yet. It is turned into a real tracker (and guarded) only if the code uses it, which keeps the guard list short.
Constant, builtin, Python modulePython values computed at trace time: C // n_head is evaluated now and baked into the graph as a number, with a guard on what it was computed from.

The output of one frame is three things: an FX graph (a list of tensor operations with their inputs), the guards, and new bytecode that replaces the frame's: it gathers the inputs, calls the compiled graph, and returns its result. What the two modes show. CPython computes as it goes: by the end, 9 ATen calls have run (two addmm matrix multiplies, gelu, and the views and transposes that F.linear decomposes into on the CPU). Dynamo computes nothing: it walks 36 instructions, inlines both Linear.forward calls (depth 1), and ends with a graph of three calls (linear, gelu, linear) on five inputs (x and four parameters) and 45 guards. Only then is the graph compiled and run. Attribute lookups such as self.fc never reach the graph: they were answered at trace time, and the answer is protected by a guard.

Predict: inside a compiled function, how many times does self.fc (a Python attribute lookup) run per call after the first?
Zero, as such. The rewritten bytecode (recorded with TORCH_LOGS=bytecode) fetches the parameters straight out of self._modules['fc']._parameters['weight'] and passes them to the compiled graph; whether fc is still the same kind of module is the guards' job, and they run in C++ before the call. That is why a module swapped after compilation is caught by a guard and recompiled rather than silently ignored.

What it costs. Tracing is Python running Python: for the whole running example, Dynamo's share of the first call ("entire_frame_compile" minus the backend) was about 0.25 s of the roughly 9 s cold compile; the rest is AOTAutograd and Inductor (section 10). Per call afterwards, the cost is the guard check (section 2).

How to check. TORCH_LOGS=bytecode prints the original and rewritten bytecode; TORCH_LOGS=graph_code the FX graph with each line's source; TORCH_LOGS=trace_bytecode every instruction with the tracker stack, exactly what the animation replays. torch._dynamo.explain(fn)(*args) summarises graphs and breaks without reading logs.

2. Guards: the conditions that keep compiled code valid

The problem. Everything Dynamo baked in (shapes, dtypes, which module object, the value of a Python flag, whether grad mode was on) must still be true on the next call, or the compiled code would compute the wrong thing. Checking it in Python on every call would cost more than the kernels on small models.

How it works. Each fact Dynamo relied on becomes a guard, organised as a tree keyed by where the value comes from (the frame's locals L['x'], globals G['F'], attributes of those). The tree is a C++ object (GuardManager and RootGuardManager, torch/csrc/dynamo/guards.cpp L4242; enable_cpp_guard_manager is on by default), so a check walks each source once and runs its leaf guards. Leaf checks in the printed tree, by kind (53 leaf checks; Dynamo's own guard set for this frame held 45 entries, the number used in the animation).


Four kinds do most of the work: TENSOR_MATCH (dispatch keys, dtype, device, requires_grad, sizes and strides of a tensor input), ID_MATCH (this exact object: the F module, the gelu builtin), TYPE_MATCH, and GLOBAL_STATE (grad mode, autocast, default dtype, thread count, deterministic flag, all in one check). The marking guards (DIMENSION_DYNAMIC_MARKING_GUARD) make sure a tensor that later gets mark_dynamic is not served by code compiled for a static shape.


What it costs. Dynamo times this tree when it builds it: 51.71 microseconds for the MLP in the recorded run (one unlocked measurement, and it varied by about two times between runs here, so treat it as an order of magnitude); the whole model's 549 guards measured 45 to 81 microseconds in the Compile lab. Against a 23 ms CPU step that is nothing; against a 1 ms step of a small model on a GPU, where the kernels launch asynchronously and the CPU's time is the critical path, it is a real overhead. Three 2.14.1 APIs trade safety for speed: torch.compiler.skip_guard_on_inbuilt_nn_modules_unsafe, skip_guard_on_all_nn_modules_unsafe and skip_guard_on_globals_unsafe (all present in torch.compiler at 2.14.1, read from the wheel); their names say what they risk.


When a guard fails. Dynamo compiles again and keeps both versions in a per-frame cache, then checks them in order on each call. That is a recompile (section 4). torch.compiler.set_stance("fail_on_recompile") turns every recompile into an error, useful in a test that pins the number of compiles; "eager_on_recompile" runs eagerly instead.
