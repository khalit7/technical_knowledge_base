6. Inductor: from ATen graph to fused kernels

The problem. The graphs AOTAutograd hands over are still one ATen op per line, and running them op by op would be eager mode again. Each element-wise op would read its input from memory and write its output back; the Compile lab's fused GELU moved 4 MiB instead of 36 MiB.

How it works, in three passes.

Lowering
ATen to loops

Each op becomes a loop body written as a small Python function over indices (Inductor's "define-by-run" IR, {{PyTorch 2 paper, section 4|https://docs.pytorch.org/assets/pytorch2-2.pdf}}). Element-wise ops are inlined into their consumer right here, so a chain like LayerNorm's subtract, multiply, rsqrt never becomes separate nodes. Matmuls and attention become extern nodes: calls to a library.

Scheduling
fuse nodes

The scheduler sees the remaining nodes (reductions, pointwise loops, externs) and fuses pairs that can share one loop: a producer with its consumer (vertical), or two nodes reading the same data (horizontal). It refuses when an unfused node would have to run between them, or sizes do not match.

Codegen
kernels + wrapper

One kernel per fused group: C++ with OpenMP and vector intrinsics on a CPU, Triton on a GPU, Metal on MPS; plus a Python wrapper, call(), that allocates buffers (reusing dead ones) and launches kernels and library calls in order.

Read the result. Lowering had already done most of the work: the 16 nodes it handed to the scheduler contain whole chains (op3 is LayerNorm's normalisation: sub, mul, rsqrt, add folded in; op14 is all of GELU). The scheduler then made 6 fusions in its first round, joining each LayerNorm's two statistics passes and its normalisation into one node, and rejected 27 other pairs, every one for the same reason ("intermediate nodes between node1 & node2"); its second round found nothing. Ten nodes became 4 C++ kernels, 4 addmm calls into the BLAS library and 1 call to the CPU flash-attention kernel. The residual add after attention was fused into the second LayerNorm's kernel (cpp_fused_add_native_layer_norm_view_1): it reads the sum while computing the statistics instead of writing it out first. The wrapper reuses dead buffers 8 times (lines ending # reuse).

Both kernels do the same arithmetic (0.5 x (1 + erf(x / sqrt 2))) in one pass over 524,288 floats; they differ in how the loop is cut. The C++ splits it across 4 OpenMP threads and steps 4 floats at a time with NEON vectors (Vectorized<float>); the Triton kernel handles one block of XBLOCK elements per program instance and leaves the block size to an autotuner. Triton generated with the same fusion decisions: the same 4 groups (two "per" persistent-reduction kernels for the LayerNorms, two "poi" pointwise kernels).


Knobs. On this block, measured by counting launches in the generated code (training, forward and backward): default 4 + 9 generated kernels, 4 + 8 library matmuls; aggressive_fusion=True, epilogue_fusion=False and pattern_matcher=False changed nothing; cpp_wrapper=True writes the wrapper in C++ instead of Python (611 and 904 lines instead of 491 and 728), removing Python from the per-call path; freezing=True (inference) gave the same 9 launches. The knobs that change a CPU block are few; on a GPU the large ones are max_autotune (try Triton templates against cuBLAS for each matmul), coordinate_descent_tuning and CUDA graphs, which is what the modes bundle (section 7).


How to check. TORCH_LOGS=output_code prints every kernel and the wrapper; TORCH_LOGS=fusion or schedule the decisions; TORCH_LOGS=ir_pre_fusion,ir_post_fusion the scheduler's nodes; kernel names are unique by default at 2.14.1 (TORCHINDUCTOR_UNIQUE_KERNEL_NAMES defaults to 1, inductor config.py L2102-L2104), so a profiler trace maps each kernel back to its source; the old advice to set it is no longer needed.






7. Modes: bundles of Inductor options


A mode is only a preset of Inductor config, and torch._inductor.list_mode_options() prints it. At 2.14.1, recorded:




From the docstring at 2.14.1 (torch/__init__.py L3103-L3119): "reduce-overhead" "reduces the overhead of python with CUDA graphs, useful for small batches", at the cost of memory, and "today, we only reduce overhead for CUDA only graphs which do not mutate inputs"; "max-autotune" "leverages Triton or template based matrix multiplications on supported devices" and "enables CUDA graphs by default on GPU". A fifth preset, "lite", appears in the table but not in the docstring: it turns most graph passes and buffer reuse off and falls back to eager by default unless a region is marked for compilation (torch/_inductor/__init__.py L335-L351).


What ran here. Not much: the Compile lab measured mode="max-autotune" on the CPU at 23.94 ms against 23.20 default, keeping the BLAS call for every matrix multiply (no template beat it), and "reduce-overhead" at 23.85 ms, doing nothing on a CPU. CUDA graphs (record a whole sequence of kernel launches once, replay it with one call) need an NVIDIA GPU, static shapes and static addresses, and are owned by {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}} (its section 4 covers CUDAGraph Trees and Inductor's graph partitions, which split a graph around the parts that cannot be captured; graph_partition is on by default at 2.14.1, read from the config). Not run here: no NVIDIA GPU.
