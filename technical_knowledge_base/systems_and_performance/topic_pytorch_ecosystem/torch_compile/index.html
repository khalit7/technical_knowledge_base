0. In one screen

torch.compile(model) returns a wrapper and does nothing until the first call. On that call three programs run in turn: TorchDynamo reads your Python as it executes and writes down the tensor operations as a graph, AOTAutograd derives the backward graph from it ahead of time and decides what the forward keeps for backward, and TorchInductor turns both graphs into fused kernels (C++ on a CPU, Triton on NVIDIA and AMD GPUs, Metal on Apple GPUs). The result is cached and reused on every later call whose inputs pass the cached version's guards, the checks that say "this compiled code is still valid".

The parent page's Compile lab tab measured what this does to one training step of the topic's running example (the 3,186,944-parameter character GPT: 4 blocks, d 256, batch 8 x 64 tokens): one graph, 59 operations, 0 breaks, 549 guards; no gain on the laptop's CPU (23.20 ms against 22.75 ms) and 1.18 times on its GPU (MPS). This page goes one level down into each stage, on the same model, so that you can predict what compile will do to your code, read what it did, and fix it when it misbehaves.

1. Dynamo: reading your Python as it runs

The problem. A compiler needs the whole computation as a graph, but a PyTorch model is ordinary Python: loops over layers, attribute lookups, calls into nn.Module.forward, the odd if. Earlier capture tools each gave something up: torch.jit.trace ran the model once and recorded only the path taken, silently wrong when control flow changed; torch.jit.script required a restricted Python dialect; torch.fx.symbolic_trace fails on any data-dependent branch. The PyTorch 2 paper (Ansel et al., ASPLOS 2024, section 2) reviews them; Dynamo's answer is to keep running Python as Python and capture only what it can prove safe.

How it works, from zero. CPython does not run your source text: it compiles each function to bytecode, a list of small stack-machine instructions (LOAD_FAST x pushes a local variable, LOAD_ATTR fc replaces the top of the stack with its attribute, CALL 1 calls a function with one argument), and evaluates one frame (one function call) at a time. PEP 523 lets a C extension replace the function that evaluates frames. When you call a compiled function, Dynamo installs its own (enable_eval_frame_shim, torch/csrc/dynamo/eval_frame.c L247-L255 at v2.14.1), so it sees every frame before CPython runs it. For a frame it has compiled before, it runs the guards and, if they pass, jumps to the compiled version. Otherwise it symbolically evaluates the bytecode: the same instructions, but its stack holds VariableTrackers instead of values.

TensorVariableA tensor, represented by a fake tensor (shape, dtype, device, no data; see 2.8 there) plus a proxy: every operation on it adds a node to the FX graph.
NNModuleVariableA module such as self.fc. Calling it inlines its forward; its parameters become graph inputs.
LazyVariableTrackerA value not inspected yet. It is turned into a real tracker (and guarded) only if the code uses it, which keeps the guard list short.
Constant, builtin, Python modulePython values computed at trace time: C // n_head is evaluated now and baked into the graph as a number, with a guard on what it was computed from.

The output of one frame is three things: an FX graph (a list of tensor operations with their inputs), the guards, and new bytecode that replaces the frame's: it gathers the inputs, calls the compiled graph, and returns its result. What the two modes show. CPython computes as it goes: by the end, 9 ATen calls have run (two addmm matrix multiplies, gelu, and the views and transposes that F.linear decomposes into on the CPU). Dynamo computes nothing: it walks 36 instructions, inlines both Linear.forward calls (depth 1), and ends with a graph of three calls (linear, gelu, linear) on five inputs (x and four parameters) and 45 guards. Zero, as such. The rewritten bytecode (recorded with TORCH_LOGS=bytecode) fetches the parameters straight out of self._modules['fc']._parameters['weight'] and passes them to the compiled graph; whether fc is still the same kind of module is the guards' job, and they run in C++ before the call. That is why a module swapped after compilation is caught by a guard and recompiled rather than silently ignored.

What it costs. Tracing is Python running Python: for the whole running example, Dynamo's share of the first call ("entire_frame_compile" minus the backend) was about 0.25 s of the roughly 9 s cold compile; the rest is AOTAutograd and Inductor (section 10). Per call afterwards, the cost is the guard check (section 2).

How to check. TORCH_LOGS=bytecode prints the original and rewritten bytecode; TORCH_LOGS=graph_code the FX graph with each line's source; TORCH_LOGS=trace_bytecode every instruction with the tracker stack, exactly what the animation replays. torch._dynamo.explain(fn)(*args) summarises graphs and breaks without reading logs.

2. Guards: the conditions that keep compiled code valid

The problem. Everything Dynamo baked in (shapes, dtypes, which module object, the value of a Python flag, whether grad mode was on) must still be true on the next call, or the compiled code would compute the wrong thing. Checking it in Python on every call would cost more than the kernels on small models.

How it works. Each fact Dynamo relied on becomes a guard, organised as a tree keyed by where the value comes from (the frame's locals L['x'], globals G['F'], attributes of those). The tree is a C++ object (GuardManager and RootGuardManager, torch/csrc/dynamo/guards.cpp L4242; enable_cpp_guard_manager is on by default), so a check walks each source once and runs its leaf guards. The MLP's tree, as TORCH_LOGS=guards printed it (first lines; paths shortened):





Leaf checks in the printed tree, by kind (53 leaf checks; Dynamo's own guard set for this frame held 45 entries, the number used in the animation).


Four kinds do most of the work: TENSOR_MATCH (dispatch keys, dtype, device, requires_grad, sizes and strides of a tensor input), ID_MATCH (this exact object: the F module, the gelu builtin), TYPE_MATCH, and GLOBAL_STATE (grad mode, autocast, default dtype, thread count, deterministic flag, all in one check). The marking guards (DIMENSION_DYNAMIC_MARKING_GUARD) make sure a tensor that later gets mark_dynamic is not served by code compiled for a static shape.


What it costs. Dynamo times this tree when it builds it: 51.71 microseconds for the MLP in the recorded run (one unlocked measurement, and it varied by about two times between runs here, so treat it as an order of magnitude); the whole model's 549 guards measured 45 to 81 microseconds in the Compile lab. Against a 23 ms CPU step that is nothing; against a 1 ms step of a small model on a GPU, where the kernels launch asynchronously and the CPU's time is the critical path, it is a real overhead. Three 2.14.1 APIs trade safety for speed: torch.compiler.skip_guard_on_inbuilt_nn_modules_unsafe, skip_guard_on_all_nn_modules_unsafe and skip_guard_on_globals_unsafe (all present in torch.compiler at 2.14.1, read from the wheel); their names say what they risk.


When a guard fails. Dynamo compiles again and keeps both versions in a per-frame cache, then checks them in order on each call. That is a recompile (section 4). torch.compiler.set_stance("fail_on_recompile") turns every recompile into an error, useful in a test that pins the number of compiles; "eager_on_recompile" runs eagerly instead.






3. Graph breaks: each kind, and how to remove it


The problem. When Dynamo meets something it cannot put in a graph, it does not fail by default. It compiles the graph it has so far, emits bytecode that runs the unsupported instruction in ordinary Python, and starts a new graph after it (a resume function). That split is a graph break. It costs twice: no fusion across it, and Python plus a guard check between the pieces on every call. The Compile lab measured a print in each block at +7 to 9% step time on the CPU; on a GPU each piece also launches separately and a CUDA graph cannot span the break.


The surprise first. Where the break sits matters more than how many there are. GPT.forward runs the blocks in a for blk in self.blocks loop, and Dynamo cannot resume tracing in the middle of a loop: a break anywhere inside a block makes it give up on the whole GPT.forward frame ("Failed to handle graph break gracefully. Skipping the function and falling back to eager", its own log, read with tlparse in section 12), so the embeddings, final LayerNorm, head and loss run as plain Python and only the two halves of each block are compiled. Every break kind below gives the same picture: 2 or 3 compiled pieces, 8 piece calls per forward instead of 1.


Can that be avoided? torch._dynamo.config.nested_graph_breaks (off by default, config.py L585-L587 at v2.14.1: "Resume tracing in nested frames if a nested graph break occurs. Old behavior is to bubble up the graph break to the top level frame") keeps the caller compiled. On four small programs with one torch._dynamo.graph_break() in the inner function, run here:




It works for a plain call and for unrolled module calls, and changes nothing inside a for loop, which is how almost every transformer calls its blocks. So on the running example it did not help (2 graphs either way, measured). The practical rule stays: remove the break.

Three lessons from the table. (1) Some flags remove a break by changing what a graph may contain: capture_dynamic_output_shape_ops lets boolean-mask indexing in (the selected size becomes a symbol), reorderable_logging_functions = {print} moves the print to after the graph runs (so it prints after the whole region, not at its line). (2) fullgraph=True is stricter than "no breaks" sounds: for the boolean mask it compiled without error, because when one graph is required Dynamo captures the dynamic size instead of breaking, while for .item() followed by an if it raised. (3) A @torch.compiler.disable helper is a deliberate break; call it outside the compiled region, or, for code Dynamo should not trace but whose outputs are plain tensors, register it as a custom op (Extending PyTorch owns that; its root lesson: a .tolist() body gives 3 graphs and 2 breaks, the same body as a custom op 1 and 0).


How to check. torch._dynamo.explain(model)(x, y) returns graph count, break count and each reason with its user stack; TORCH_LOGS=graph_breaks prints them as they happen, each with a link into the graph-break registry (for example gb7000, the loop case); fullgraph=True turns the first one into an exception, which is what you want in a training loop you control.






4. Recompiles and dynamic shapes


The problem. Sizes are guarded like everything else. A model that sees a new sequence length, a short last batch or a different learning rate passed as a Python number fails a guard and compiles again, at a cost of seconds each time. Compiling for "any size" instead makes kernels that cannot specialise on the size (no fully unrolled loops, extra index arithmetic) and adds symbolic reasoning to every compile.


How it works. By default Dynamo compiles the first call with every size static (a constant). When a size guard fails, automatic dynamic shapes (automatic_dynamic_shapes, on by default, config.py L188) recompiles with the dimension that changed replaced by a symbol (s75 below) whose value is read at run time; guards on that symbol are inequalities instead of equalities. Two exceptions are built in: sizes 0 and 1 stay specialised (a dimension of 1 broadcasts, so code valid for "any n" may be wrong for 1; this is 0/1 specialisation), and parameters' shapes are always static (force_parameter_static_shapes). Unbacked symbols: sizes that come from data


A symbol from an input size is backed: at compile time there is a real example value (a hint) to answer questions like "is s75 > 1?". A symbol from .item() or nonzero() is unbacked: its value exists only when the graph runs. Dynamo breaks on both by default; with capture_scalar_outputs or capture_dynamic_output_shape_ops it keeps them in the graph as u0, and any branch on them must be answered without a value. 5. AOTAutograd: the backward graph, and what crosses to it


The problem. Dynamo captured only the forward. Training also runs a backward, and in eager mode that backward is decided op by op as the forward runs: each operation saves what its own derivative needs. A compiler wants the backward as a graph too, ahead of time, and it wants to choose what is saved rather than accept every op's default.


How it works. AOTAutograd runs the captured forward once more, on fake tensors, through the real autograd machinery, and records forward and backward together as one joint graph whose inputs are the forward inputs (primals_*) and the incoming gradients (tangents_*). Two rewrites happen on the way: functionalization replaces in-place and aliasing operations by pure ones (the block's joint graph has no in-place op, measured; the mechanism is section 2.7 of Tensors, the dispatcher and autograd), and decomposition lowers composite ops to a smaller ATen set (F.linear becomes permute + addmm, GELU becomes erf, mul, add). Then a partitioner cuts the joint graph in two. Every value that crosses the cut is saved by the forward for the backward; everything else the backward needs, it recomputes.




default_partitionSave whatever the backward needs that the forward produced; recompute nothing. Close to eager. (partitioners.py L1595)


min_cut_rematerialization_partitionInductor's default. A max-flow min-cut over the joint graph where cutting an edge means saving that tensor (cost: its bytes) and cheap ops may be recomputed instead; matmuls, reductions and long chains are banned from recompute (ban_recompute_*, functorch config.py L159-L174). (partitioners.py L4109)


activation_memory_budgetBelow 1.0 (the default, L202) the partitioner may recompute expensive ops too, choosing which by a knapsack (solver "dp", L215) over runtime estimated from FLOPs (L209), until the saved bytes fit the fraction asked for.

When it matters. When activations, not parameters, set the batch size you can fit: long sequences, many layers. It is the compiler's version of activation checkpointing (and composes with it: a checkpointed region is recomputed whatever the partitioner thinks). On this model the default min-cut barely moves memory; the budget is the lever. 6. Inductor: from ATen graph to fused kernels


The problem. The graphs AOTAutograd hands over are still one ATen op per line, and running them op by op would be eager mode again. Each element-wise op would read its input from memory and write its output back; the Compile lab's fused GELU moved 4 MiB instead of 36 MiB.


How it works, in three passes.




Lowering
ATen to loops
Each op becomes a loop body written as a small Python function over indices (Inductor's "define-by-run" IR, PyTorch 2 paper, section 4). Element-wise ops are inlined into their consumer right here, so a chain like LayerNorm's subtract, multiply, rsqrt never becomes separate nodes. Matmuls and attention become extern nodes: calls to a library.


Scheduling
fuse nodes
The scheduler sees the remaining nodes (reductions, pointwise loops, externs) and fuses pairs that can share one loop: a producer with its consumer (vertical), or two nodes reading the same data (horizontal). It refuses when an unfused node would have to run between them, or sizes do not match.


Codegen
kernels + wrapper
One kernel per fused group: C++ with OpenMP and vector intrinsics on a CPU, Triton on a GPU, Metal on MPS; plus a Python wrapper, call(), that allocates buffers (reusing dead ones) and launches kernels and library calls in order.

Read the result. Lowering had already done most of the work: the 16 nodes it handed to the scheduler contain whole chains (op3 is LayerNorm's normalisation: sub, mul, rsqrt, add folded in; op14 is all of GELU). The scheduler then made 6 fusions in its first round, joining each LayerNorm's two statistics passes and its normalisation into one node, and rejected 27 other pairs, every one for the same reason ("intermediate nodes between node1 & node2"); its second round found nothing. Ten nodes became 4 C++ kernels, 4 addmm calls into the BLAS library and 1 call to the CPU flash-attention kernel. The residual add after attention was fused into the second LayerNorm's kernel (cpp_fused_add_native_layer_norm_view_1): it reads the sum while computing the statistics instead of writing it out first. The wrapper reuses dead buffers 8 times (lines ending # reuse).

7. Modes: bundles of Inductor options


A mode is only a preset of Inductor config, and torch._inductor.list_mode_options() prints it. At 2.14.1, recorded:




From the docstring at 2.14.1 (torch/__init__.py L3103-L3119): "reduce-overhead" "reduces the overhead of python with CUDA graphs, useful for small batches", at the cost of memory, and "today, we only reduce overhead for CUDA only graphs which do not mutate inputs"; "max-autotune" "leverages Triton or template based matrix multiplications on supported devices" and "enables CUDA graphs by default on GPU". Not run here: no NVIDIA GPU.






8. Compiled autograd: the backward captured when it runs


The problem. AOTAutograd builds the backward ahead of time, but only for the compiled region. Anything the autograd engine does around it stays eager: gradient hooks, the accumulation into .grad, and in distributed training the communication that DDP and FSDP hook into the backward. A hook on a parameter, for instance, cannot be inside the ahead-of-time graph because it is attached to a tensor, not to code Dynamo traced.


How it works. With torch._dynamo.config.compiled_autograd = True (config.py L770, off by default), when loss.backward() runs inside a compiled function the engine's whole graph is traced at that moment, hooks and accumulation included, into one FX graph that Dynamo and Inductor then compile. The price is that this graph is traced on every backward and guarded on the autograd graph's structure. On the running example's training step, CPU, recorded:




Without it, a hook on blocks[0].mlp.fc.weight (lambda g: g * 0.5) became a separate one-op graph compiled by Dynamo when the engine called it. With it, the backward is one graph of 730 ops including 52 AccumulateGrad nodes (one per parameter), and the hook is the 731st op inside it. Gradients match eager to 3.6e-07 in every case. Speed on the CPU: the forward-and-backward step 23.36 ms without, 23.57 ms with (medians of 5 x 20 steps under the bench lock): no gain here, because the backward kernels were already compiled and there is no communication to overlap.


When it matters. When the backward contains things worth fusing or overlapping that AOTAutograd cannot see. Dynamo's DDP support documents the trade (optimize_ddp, config.py L406-L432): the default "ddp_optimizer" splits the forward graph at DDP's bucket boundaries so that each bucket's all-reduce can start while the rest of the backward runs, and "python_reducer" (experimental) instead "requires the usage of compiled_autograd" to trace the communication without graph breaks. The split is real; on 2 CPU processes (gloo), the compiled DDP model became:

9. Regional compilation: compile the block, not the model


The problem. Compile time grows with graph size, and an LLM is the same block repeated 32 to 128 times. Compiling the whole model traces and optimises every copy.


How it works. Compile the repeated module instead: for b in model.blocks: b.compile() (nn.Module.compile compiles in place). Dynamo compiles Block.forward once; because parameters are graph inputs (inlined built-in modules, always on at 2.14.1), every other block instance passes the same guards and reuses the code. torchtitan does exactly this with fullgraph=True. A newer variant keeps one compile of the whole model but marks the block as a region compiled once and called many times: torch.compiler.nested_compile_region (in the 2.14.1 API). Cold first training step, fresh process, empty cache, 3 runs each under the bench lock (CPU, 4 threads):




Cold compile of the first training step








The whole model went from 9.19 s to 10.85 s when the blocks doubled from 4 to 8; per-block compilation stayed flat (5.72 s, 5.66 s), because the extra blocks cost nothing to compile; nested_compile_region sat between (8.04 s, 8.42 s), since the rest of the model is still traced around the region. Steady-state step time did not suffer here (whole 24.11 ms, regional 23.80, nested 23.91, medians of 5 x 20 steps): the loss of fusion across block boundaries (a residual add that could have joined the next LayerNorm) is too small to see on a CPU. The Compile time and caches tab shows each run and its phase breakdown.


When it matters. Always worth trying first on a deep model; the gap grows with depth (here 1.9 times at 8 blocks; production models have tens to hundreds). How to check: the cache counters (fxgraph_cache_miss) were 2 in every variant: one forward and one backward graph compiled, whether that graph is the whole model or one block.






10. Caches: paying the compile once


The problem. A cold compile of this tiny model's training step takes about 9 seconds on the laptop; real models take minutes, and a job on 1,000 GPUs restarted after a failure would pay it on every rank.


How it works. Several caches on disk, all under TORCHINDUCTOR_CACHE_DIR (a per-user temporary directory by default), each keyed by a hash of its input graph, the config and the versions: the FX graph cache (Inductor's output for a post-AOTAutograd graph; fx_graph_cache, on, inductor config.py L109), the AOTAutograd cache (the forward and backward graphs for a Dynamo graph, so even AOTAutograd is skipped; enable_autograd_cache, on, functorch config.py L71), the compiled kernels themselves (C++ shared objects, Triton binaries) and autotuning results. Dynamo still traces on every new process: guards are not cached by these. Mega-cache packs the cache entries a process used into one blob: torch.compiler.save_cache_artifacts() returns bytes, load_cache_artifacts(bytes) installs them in another process's cache directory. Measured, whole model, CPU, 3 runs each, each scenario in its own private cache directory:




First training step: cold, warm, and from a mega-cache








Warm, the first step took 0.85 s against 9.08 s cold (medians): both Inductor graphs and the AOTAutograd entry hit, and nothing was compiled. The mega-cache, loaded into an empty directory in a fresh process, gave 5.06 s: the same cache hits (2 FX graph, 1 AOTAutograd), but 4.0 s still went to async_compile.wait, compiling the C++ kernels again. The blob (1,265,370 bytes) carries the generated source, not this machine's compiled .so files, so on a CPU it saves the Python half of the compile and not the C++ half. On a GPU the large win is the Triton kernels and autotuning results it carries (not measured here).


A cache can serve a wrong program
The sibling Extending PyTorch found that the AOTAutograd cache key does not include whether a custom op's autograd formula is registered: a process that registered it late produced a backward that silently dropped gradients, and a later, correct process reading the same cache reused that broken backward. TORCHINDUCTOR_AUTOGRAD_CACHE=0 avoided it there. When you change custom-op registrations or other code the key cannot see, use a fresh cache directory.


How to check. The counters torch._dynamo.utils.counters["inductor"]["fxgraph_cache_hit"] and counters["aot_autograd"]["autograd_cache_hit"] (used for the table above); TORCH_LOGS=cache; torch._dynamo.utils.calculate_time_spent() for the phase split. To be sure you are measuring a cold compile, point TORCHINDUCTOR_CACHE_DIR at an empty directory, or set torch.compiler.config.force_disable_caches.






11. torch.export and AOTInductor: one graph to ship


The problem. torch.compile is a just-in-time compiler for a Python process: it needs your Python code, falls back to Python at breaks, and recompiles when guards fail. To deploy a model where there is no Python, or to hand a graph to another tool, you need the whole program captured once, ahead of time, with its assumptions written down.


How it works. torch.export.export(model, args, dynamic_shapes=...) captures one graph with no breaks allowed and returns an ExportedProgram: the graph (ATen ops), a graph signature saying which inputs are parameters, buffers or user inputs, the state_dict, and range constraints on every symbolic size. Two tracers: non-strict (the default at 2.14.1, strict=False in its signature) runs your Python normally with fake tensors and records the ATen calls; strict traces through Dynamo, which can reject Python it cannot prove safe. On the running example (logits only, eval) both produced the same 94-op graph, measured; its signature lists 53 parameter inputs (the tied embedding twice, under its two names) and 1 user input. ep.run_decompositions() lowers it to the core ATen set: 326 ops.




Four lessons from the table. (1) A dynamic dimension you declare is checked: the reshape to 8 rows made export fail with "You marked batch as dynamic but your code specialized it to be a constant (8)" and a suggested fix. (2) A range is not checked against data: T up to 128 exported fine although the position table has 64 rows; T > 64 would index past it at run time. With the correct range, a T = 100 input was rejected on entry ("Guard failed: idx.size()[1] <= 64", recorded). (3) Dim.AUTO found both dimensions dynamic but from 2, not 1 (0/1 specialisation again). (4) Data-dependent Python control flow cannot be exported in either mode; torch.cond can. torch.export.draft_export exports it anyway and reports the problem; here it picked the branch the example took (cos) and inserted a runtime assert, with the advice to add torch._check.


Saving and AOTInductor. torch.export.save wrote a 12,986,850-byte .pt2 archive (52 weight files, since tied weights are stored once, plus the graph as JSON); loading it gave identical outputs. torch._inductor.aoti_compile_and_package(ep) compiles the program ahead of time into a shared library inside a 14,358,669-byte package (the 14,163,036-byte wrapper.so holds the weights) that aoti_load_package runs from Python, or a C++ runner without Python. Outputs matched eager within 1.25e-06 at (8, 64).


Measured here: AOTInductor and a non-contiguous input
A slice x[:3, :20] of the batch (strides (64, 1), not contiguous) passed to the AOTInductor package returned logits with a maximum error of 1.81 against eager, with no error or warning; the same input after .contiguous() matched within 9.5e-07, and the exported program's own ep.module() handled the slice exactly (0.0). The compiled library assumed the strides it was compiled for. Call .contiguous() on inputs to an AOTInductor model.


Where it leads. ExecuTorch (on-device) and the ONNX exporter (dynamo-based by default since 2.9) start from torch.export; the file formats are on Model formats.






12. Debugging: a workflow and its tools


When compile misbehaves, the symptom is one of four: it is slow to compile, it is not faster, it gives different numbers, or it crashes. The workflow, each step with the tool used on this page:


    

  1. Count graphs and breaks first. torch._dynamo.explain(model)(x, y) (sections 3 and 4). Then TORCH_LOGS="graph_breaks,recompiles" on a real run.
    2. 

  2. Bisect the stack. backend="eager" runs Dynamo only, "aot_eager" adds AOTAutograd, the default adds Inductor. Whichever first changes the numbers or crashes is the culprit.
    3. 

  3. Read one compile end to end. Set TORCH_TRACE=<dir> and run tlparse on the log: one HTML report with every frame compiled, every graph (Dynamo, joint, forward, backward, post-grad), the generated code, guards, breaks and recompile reasons per compile id.
    4. 

  4. Shrink a crash. torch._dynamo.config.repro_after = "aot" (or "dynamo") makes a failing compile write a launcher script; running it minifies the graph.
    5. 

  5. Find where compile time goes. torch._dynamo.utils.calculate_time_spent() (section 10), or the compilation_metrics pages tlparse writes.
    6.

Common mistakes


Logging inside the model with print or .item()
Each is a graph break; inside the block loop it costs the whole forward (section 3). Log outside the compiled function, or keep values as tensors and read them every N steps.


Calling mark_dynamic on one tensor of several that share a dimension
The targets carry the same length as the inputs and are guarded too (Compile lab); mark every tensor with the dimension, or give the bound with min and max so violations are errors you see.


Assuming nested_graph_breaks keeps a model compiled
It did nothing for a break inside a for loop over blocks, measured (section 3).


Passing a different Python string, dtype or config value each call
Guarded by value with no symbolic fallback: after 8 versions, eager mode with only a warning (section 4).


Timing the first call
It includes 9 seconds of compiling here; warm up, then time, and synchronise on a GPU (Making training fast section 1).


Compiling the whole model when compile time hurts
Compile the block (section 9): 5.7 s instead of 9.2 s here, and it does not grow with depth.


Measuring a "cold" compile with a warm cache
The caches are on by default and survive processes: 0.85 s looks like a fast compiler. Use an empty TORCHINDUCTOR_CACHE_DIR.


Feeding a sliced tensor to an AOTInductor package
Wrong answers with no warning, measured (section 11). Make inputs contiguous.


Reading activation_memory_budget from torch._dynamo.config
It lives in torch._functorch.config at 2.14.1 (the sibling page found the blog's spelling does not exist).






Interview questions, with short answers


How does Dynamo capture a graph without running the model on real data?
It installs a PEP 523 frame evaluator and symbolically executes each frame's bytecode with VariableTrackers; tensors are fake tensors carrying shapes, so ops add FX nodes and Python values are computed at trace time and protected by guards.


What is a guard, and what happens when one fails?
A condition the compiled code assumed (shape, dtype, object identity, global state), checked in C++ before each call. On failure Dynamo recompiles and caches another version, up to recompile_limit (8), then runs eagerly.


Why might one graph break cost the whole model?
A break inside a loop cannot be resumed, so Dynamo skips the enclosing frame: everything outside the blocks runs eagerly and the blocks compile in pieces.


Backed versus unbacked symbolic sizes?
Backed come from input sizes and have an example value to answer branches; unbacked come from data (.item(), nonzero) and do not, so branches on them need torch._check or torch.cond.


What does the min-cut partitioner optimise?
Which joint-graph values the forward saves for backward: it minimises saved bytes, recomputing cheap ops; activation_memory_budget lets it recompute expensive ones too.


Where does Inductor fuse?
Mostly at lowering (pointwise ops are inlined into consumers), then in the scheduler (vertical and horizontal fusion of loops); matmuls and attention stay library calls unless autotuning picks a template.


What do the modes change?
Only Inductor config: reduce-overhead turns on CUDA graphs; max-autotune adds matmul autotuning, coordinate-descent tuning and CUDA graphs; -no-cudagraphs drops the graphs.


Compiled autograd: what and why?
Tracing the autograd engine's graph at backward time, including hooks and accumulation, so the backward compiles as one graph and distributed communication can be traced and overlapped.


How do you cut compile time for a 70B model?
Regional compilation of the repeated block, warm caches shared across ranks (mega-cache), avoiding recompiles (mark dynamic dims, stable Python args), and profiling compile time by phase.


torch.compile versus torch.export?
compile is a JIT inside Python that tolerates breaks and recompiles; export captures one full graph with explicit dynamic-shape constraints for deployment (ExecuTorch, AOTInductor, ONNX).
