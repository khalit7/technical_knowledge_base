The idea in one screen

torch.compile captures your Python as a graph on the first call (Dynamo), derives the backward and chooses what the forward keeps for it (AOTAutograd), fuses both into kernels (Inductor), and reuses that code on every later call whose guards still pass. Everything you tune is one of three things: keep the graph whole, keep the guards passing, pay the compile once.

The first call runs three compilers; every later call is a guard check

Numbers are the running example, measured here (torch 2.14.1, CPU): the whole training step for Dynamo and AOTAutograd (the root's Compile lab and section 5), one block's forward for Inductor (section 6), the cold and warm first step for the cache (sections 9 and 10). The off-ramps are the two ways the picture goes wrong: a graph break (section 3) and a recompile (section 4).

torch.compile(model) returns a wrapper and does nothing until the first call. The parent page's Compile lab measured what this does to one training step of the running example (the 3,186,944-parameter character GPT: 4 blocks, d 256, batch 8 x 64 tokens): one graph, 59 operations, 0 breaks, 549 guards; no gain on the laptop's CPU (23.20 ms against 22.75 ms) and 1.18 times on its GPU (MPS). This page goes one level down into each stage, on the same model, so you can predict what compile will do to your code, read what it did, and fix it.

You need fake tensors and functionalization (Tensors, the dispatcher and autograd, section 2.5). New terms, each defined again where it is used:

1. Dynamo: reading your Python as it runs

A compiler needs the whole computation as a graph, but a model is ordinary Python: loops over layers, attribute lookups, the odd if. Dynamo keeps running Python as Python and captures only what it can prove safe.

Why not the earlier capture tools (PyTorch 2 paper, section 2)

torch.jit.trace ran the model once and recorded only the path taken, silently wrong when control flow changed; torch.jit.script required a restricted Python dialect; torch.fx.symbolic_trace fails on any data-dependent branch. The PyTorch 2 paper (Ansel et al., ASPLOS 2024, section 2) reviews them.

How it works. CPython compiles each function to bytecode, a list of stack-machine instructions (LOAD_FAST x pushes a local, LOAD_ATTR fc replaces the top of the stack with its attribute, CALL 1 calls with one argument), and evaluates one frame (one function call) at a time. PEP 523 lets a C extension replace the frame evaluator; Dynamo installs its own (enable_eval_frame_shim, eval_frame.c L247-L255 at v2.14.1), so it sees every frame first. For a frame compiled before, it runs the guards and, if they pass, jumps to the compiled version. Otherwise it symbolically evaluates the bytecode: the same instructions, but its stack holds VariableTrackers instead of values.

TensorVariableA tensor, as a fake tensor (shape, dtype, device, no data) plus a proxy: every operation on it adds a node to the FX graph.
NNModuleVariableA module such as self.fc. Calling it inlines its forward; its parameters become graph inputs.
LazyVariableTrackerA value not inspected yet; turned into a real tracker (and guarded) only if the code uses it, which keeps the guard list short.
Constant, builtin, Python moduleComputed at trace time: C // n_head is evaluated now and baked into the graph as a number, with a guard on what it came from.

One frame gives three things: an FX graph (tensor operations and their inputs), the guards, and new bytecode for the frame that gathers the inputs, calls the compiled graph and returns its result. The rewritten bytecode (recorded with TORCH_LOGS=bytecode) fetches the parameters straight out of self._modules['fc']._parameters['weight'] and passes them to the compiled graph; whether fc is still the same kind of module is the guards' job, and they run in C++ before the call. That is why a module swapped after compilation is caught by a guard and recompiled rather than silently ignored.

Cost. Tracing is Python running Python: for the whole running example, Dynamo's share of the first call ("entire_frame_compile" minus the backend) was about 0.25 s of the roughly 9 s cold compile; the rest is AOTAutograd and Inductor (section 10). Afterwards each call pays only the guard check (section 2). 2. Guards: the conditions that keep compiled code valid

Everything Dynamo baked in (shapes, dtypes, which module object, a Python flag, grad mode) must still hold on the next call, or the compiled code computes the wrong thing; checking it in Python each call would cost more than the kernels of a small model. So each fact becomes a guard in a tree keyed by where the value comes from (L['x'] for a local, G['F'] for a global, attributes of those), built in C++ (GuardManager, RootGuardManager, guards.cpp L4242; enable_cpp_guard_manager is on by default): a check walks each source once and runs its leaf guards. The MLP's tree as TORCH_LOGS=guards printed it (paths shortened), counted by kind:

Leaf checks in the printed tree, by kind (53 leaf checks; Dynamo's own guard set for this frame held 45 entries, the number used in section 1).

The printed guard tree (TORCH_LOGS=guards, first lines)


Four kinds do most of the work: TENSOR_MATCH (dispatch keys, dtype, device, requires_grad, sizes and strides of a tensor input), ID_MATCH (this exact object: the F module, the gelu builtin), TYPE_MATCH, and GLOBAL_STATE (grad mode, autocast, default dtype, thread count, deterministic flag, in one check). DIMENSION_DYNAMIC_MARKING_GUARD makes sure a tensor that later gets mark_dynamic is not served by code compiled for a static shape.


Cost. 51.71 microseconds for the MLP's tree in the recorded run (one unlocked measurement that varied by about two times between runs: an order of magnitude); the whole model's 549 guards measured 45 to 81 microseconds in the Compile lab. Nothing against a 23 ms CPU step; a real overhead against a 1 ms GPU step, where kernels launch asynchronously and the CPU's time is the critical path. When a guard fails, Dynamo compiles again and keeps both versions in a per-frame cache, checked in order on each call: a recompile (section 4).


Guard APIs: skipping guards, and failing on recompiles (torch 2.14.1)
Three APIs trade safety for speed: torch.compiler.skip_guard_on_inbuilt_nn_modules_unsafe, skip_guard_on_all_nn_modules_unsafe and skip_guard_on_globals_unsafe (all present in torch.compiler at 2.14.1, read from the wheel); their names say what they risk. torch.compiler.set_stance("fail_on_recompile") turns every recompile into an error, useful in a test that pins the number of compiles; "eager_on_recompile" runs eagerly instead.






3. Graph breaks: each kind, and how to remove it


When Dynamo meets something it cannot put in a graph, it does not fail by default: it compiles the graph so far, emits bytecode that runs the unsupported instruction in plain Python, and starts a new graph after it (a resume function; the rewritten bytecode, step by step, is in The compiler stack, section 8). That split is a graph break. It costs twice: no fusion across it, and Python plus a guard check between the pieces on every call. The Compile lab measured a print in each block at +7 to 9% step time on the CPU; on a GPU each piece also launches separately and a CUDA graph cannot span the break.


Where the break sits matters more than how many. GPT.forward runs the blocks in a for blk in self.blocks loop, and Dynamo cannot resume tracing in the middle of a loop: a break anywhere inside a block makes it give up on the whole GPT.forward frame ("Failed to handle graph break gracefully. Skipping the function and falling back to eager", its own log, read with tlparse in section 12). The embeddings, final LayerNorm, head and loss then run as plain Python and only the two halves of each block are compiled: 8 piece calls per forward instead of 1. 4. Recompiles and dynamic shapes


Sizes are guarded like everything else: a new sequence length, a short last batch or a learning rate passed as a Python number fails a guard and costs seconds of compiling. Compiling for "any size" instead gives kernels that cannot specialise (no fully unrolled loops, extra index arithmetic) and adds symbolic reasoning to every compile.


How it works. The first call compiles every size static. When a size guard fails, automatic dynamic shapes (automatic_dynamic_shapes, on by default, config.py L188) recompiles with the changed dimension replaced by a symbol (s75 below) read at run time, guarded by inequalities instead of equalities. Two exceptions are built in: sizes 0 and 1 stay specialised, because a dimension of 1 broadcasts and code valid for "any n" may be wrong for 1 (0/1 specialisation); and parameters' shapes are always static (force_parameter_static_shapes). Unbacked symbols: sizes that come from data


A symbol from an input size is backed: at compile time there is an example value (a hint) to answer "is s75 > 1?". A symbol from .item() or nonzero() is unbacked: its value exists only when the graph runs. Dynamo breaks on both by default; with capture_scalar_outputs or capture_dynamic_output_shape_ops it keeps them in the graph as u0, and any branch on them must be answered without a value. torch._check(n >= 0); torch._check(n <= idx.shape[1]) states facts the compiler can reuse, the fix when a branch cannot be decided ("Could not guard on data-dependent expression", the error in section 3); torch.cond is the fix when you really need both branches.

5. AOTAutograd: the backward graph, and what crosses to it


Dynamo captured only the forward. In eager mode the backward is decided op by op as the forward runs, each op saving what its own derivative needs; a compiler wants the backward as a graph ahead of time, and wants to choose what is saved.


How it works. AOTAutograd runs the captured forward once more, on fake tensors, through the real autograd machinery, and records forward and backward as one joint graph whose inputs are the forward inputs (primals_*) and the incoming gradients (tangents_*). On the way, functionalization replaces in-place and aliasing ops by pure ones (the block's joint graph has no in-place op, measured) and decomposition lowers composite ops to a smaller ATen set (F.linear becomes permute + addmm, GELU becomes erf, mul, add). Then a partitioner cuts the joint graph in two: every value that crosses the cut is saved by the forward for the backward; everything else the backward needs, it recomputes.




default_partitionSave whatever the backward needs that the forward produced; recompute nothing. Close to eager. (partitioners.py L1595)


min_cut_rematerialization_partitionInductor's default. A max-flow min-cut where cutting an edge means saving that tensor (cost: its bytes) and cheap ops may be recomputed instead; matmuls, reductions and long chains are banned from recompute (ban_recompute_*, functorch config.py L159-L174; partitioners.py L4109).


activation_memory_budgetBelow 1.0 (the default, L202) expensive ops may be recomputed too, chosen by a knapsack (solver "dp", L215) over runtime estimated from FLOPs (L209), until the saved bytes fit the fraction asked for.

6. Inductor: from ATen graph to fused kernels


The graphs AOTAutograd hands over are still one ATen op per line; run op by op, each element-wise op would read its input from memory and write its output back (the Compile lab's fused GELU moved 4 MiB instead of 36 MiB). Inductor works in three passes:




Lowering
ATen to loops
Each op becomes a loop body written as a small Python function over indices (Inductor's "define-by-run" IR, PyTorch 2 paper, section 4). Element-wise ops are inlined into their consumer here, so LayerNorm's subtract, multiply, rsqrt never become separate nodes. Matmuls and attention become extern nodes: library calls.


Scheduling
fuse nodes
The scheduler fuses pairs that can share one loop: a producer with its consumer (vertical), or two nodes reading the same data (horizontal). It refuses when an unfused node would have to run between them, or sizes do not match.


Codegen
kernels + wrapper
One kernel per fused group: C++ with OpenMP and vector intrinsics on a CPU, Triton on a GPU, Metal on MPS; plus a Python wrapper, call(), that allocates buffers (reusing dead ones) and launches kernels and library calls in order.




One block's forward on the CPU (inference, (8, 64, 256)), every scheduler decision recorded with TORCH_LOGS=fusion. Predict before you step: how many kernels does the scheduler end with?




Lowering already did most of the fusing: 16 nodes, 6 fusions, 4 kernels










reductionpointwiseextern (library call)




The 16 nodes handed to the scheduler already contain whole chains (op3 is LayerNorm's normalisation with sub, mul, rsqrt, add folded in; op14 is all of GELU). The scheduler made 6 fusions in its first round, joining each LayerNorm's two statistics passes and its normalisation into one node, and rejected 27 other pairs, every one for the same reason ("intermediate nodes between node1 & node2"); its second round found nothing. Ten nodes became 4 C++ kernels, 4 addmm calls into the BLAS library and 1 call to the CPU flash-attention kernel. The residual add after attention was fused into the second LayerNorm's kernel (cpp_fused_add_native_layer_norm_view_1): it reads the sum while computing the statistics instead of writing it out first. The wrapper reuses dead buffers 8 times (lines ending # reuse).

7. Modes: bundles of Inductor options


A mode is only a preset of Inductor config; torch._inductor.list_mode_options() prints it. At 2.14.1, recorded:




"reduce-overhead" turns on CUDA graphs (record a whole sequence of kernel launches once, replay it with one call: for small batches, at the cost of memory, and only for CUDA graphs that do not mutate inputs); "max-autotune" adds Triton or template matmuls and also enables CUDA graphs on a GPU. On the laptop's CPU neither did anything: the Compile lab measured mode="max-autotune" at 23.94 ms against 23.20 default (the BLAS call won every matmul) and "reduce-overhead" at 23.85 ms. CUDA graphs need an NVIDIA GPU, static shapes and static addresses, and are owned by Streams, CUDA graphs and multi-GPU (its section 4: CUDAGraph Trees and Inductor's graph partitions, which split a graph around the parts that cannot be captured; graph_partition is on by default at 2.14.1, read from the config). Not run here: no NVIDIA GPU.


The docstring's words, and the undocumented "lite" preset (torch 2.14.1 source)
From the docstring at 2.14.1 (torch/__init__.py L3103-L3119): "reduce-overhead" "reduces the overhead of python with CUDA graphs, useful for small batches", at the cost of memory, and "today, we only reduce overhead for CUDA only graphs which do not mutate inputs"; "max-autotune" "leverages Triton or template based matrix multiplications on supported devices" and "enables CUDA graphs by default on GPU". A fifth preset, "lite", appears in the table but not in the docstring: it turns most graph passes and buffer reuse off and falls back to eager by default unless a region is marked for compilation (torch/_inductor/__init__.py L335-L351).






8. Compiled autograd: the backward captured when it runs


AOTAutograd builds the backward ahead of time, but only for the compiled region. What the autograd engine does around it stays eager: gradient hooks, accumulation into .grad, and the communication that DDP and FSDP hook into the backward. A hook on a parameter cannot be in the ahead-of-time graph: it is attached to a tensor, not to code Dynamo traced. With torch._dynamo.config.compiled_autograd = True (config.py L770, off by default), when loss.backward() runs inside a compiled function the engine's whole graph is traced at that moment, hooks and accumulation included, into one FX graph that Dynamo and Inductor compile. The price: that graph is traced on every backward and guarded on the autograd graph's structure. The running example's training step, CPU, recorded:




Without it, a hook on blocks[0].mlp.fc.weight (lambda g: g * 0.5) became a separate one-op graph compiled when the engine called it. With it, the backward is one graph of 730 ops including 52 AccumulateGrad nodes (one per parameter), and the hook is the 731st op inside it. Gradients match eager to 3.6e-07 in every case. Speed on the CPU: 23.36 ms without, 23.57 ms with (medians of 5 x 20 steps, bench lock): no gain, because the backward kernels were already compiled and there is no communication to overlap. When it matters: when the backward holds things worth fusing or overlapping that AOTAutograd cannot see, above all distributed communication.

9. Regional compilation: compile the block, not the model


Compile time grows with graph size, and an LLM is one block repeated 32 to 128 times; compiling the whole model traces and optimises every copy. Compile the repeated module instead: for b in model.blocks: b.compile() (nn.Module.compile compiles in place). Dynamo compiles Block.forward once; because parameters are graph inputs (inlined built-in modules, always on at 2.14.1), every other block instance passes the same guards and reuses the code. torchtitan does exactly this with fullgraph=True. A newer variant keeps one compile of the whole model but marks the block as a region compiled once and called many times: torch.compiler.nested_compile_region (in the 2.14.1 API). Steady-state step time did not suffer (whole 24.11 ms, regional 23.80, nested 23.91, medians of 5 x 20 steps): the fusion lost across block boundaries (a residual add that could have joined the next LayerNorm) is too small to see on a CPU. Always worth trying first on a deep model; the gap grows with depth (1.9 times at 8 blocks here; production models have tens to hundreds). Check: the cache counter fxgraph_cache_miss was 2 in every variant: one forward and one backward graph compiled, whether that graph is the whole model or one block.






10. Caches: paying the compile once


A cold compile of this tiny model's step takes about 9 seconds; real models take minutes, and a job on 1,000 GPUs restarted after a failure pays it on every rank. Several caches on disk, all under TORCHINDUCTOR_CACHE_DIR (a per-user temporary directory by default), each keyed by a hash of its input graph, the config and the versions: the FX graph cache (Inductor's output for a post-AOTAutograd graph; fx_graph_cache, on, inductor config.py L109), the AOTAutograd cache (forward and backward graphs for a Dynamo graph, so AOTAutograd is skipped too; enable_autograd_cache, on, functorch config.py L71), the compiled kernels (C++ shared objects, Triton binaries) and autotuning results. Dynamo still traces in every new process: guards are not cached. Mega-cache packs the entries a process used into one blob: torch.compiler.save_cache_artifacts() returns bytes, load_cache_artifacts(bytes) installs them in another process's cache directory. Predict: a mega-cache loaded into an empty directory, how close to warm?




Warm skips the compile; a mega-cache on a CPU still rebuilds the C++








Warm, the first step took 0.85 s against 9.08 s cold (medians): both Inductor graphs and the AOTAutograd entry hit, nothing was compiled, and what is left is Dynamo tracing again plus loading cached code, the floor of a warm start. The mega-cache gave 5.06 s: the same hits (2 FX graph, 1 AOTAutograd), but 4.0 s still went to async_compile.wait, compiling the C++ kernels again. The blob (1,265,370 bytes) carries generated source, not this machine's compiled .so files, so on a CPU it saves the Python half of the compile and not the C++ half. On a GPU the large win is the Triton kernels and autotuning results it carries (not measured here).

A cache can serve a wrong program
The sibling Extending PyTorch found that the AOTAutograd cache key does not include whether a custom op's autograd formula is registered: a process that registered it late produced a backward that silently dropped gradients, and a later, correct process reading the same cache reused that broken backward. TORCHINDUCTOR_AUTOGRAD_CACHE=0 avoided it there. When you change custom-op registrations or other code the key cannot see, use a fresh cache directory.

11. torch.export and AOTInductor: one graph to ship


torch.compile is a just-in-time compiler inside a Python process: it needs your code, falls back to Python at breaks and recompiles when guards fail. To deploy where there is no Python, or hand a graph to another tool, the whole program must be captured once, ahead of time, with its assumptions written down. torch.export.export(model, args, dynamic_shapes=...) captures one graph with no breaks allowed and returns an ExportedProgram: the graph (ATen ops), a graph signature saying which inputs are parameters, buffers or user inputs, the state_dict, and range constraints on every symbolic size. Two tracers: non-strict (the default at 2.14.1, strict=False in its signature) runs your Python normally with fake tensors and records the ATen calls; strict traces through Dynamo, which can reject Python it cannot prove safe. On the running example (logits only, eval) both gave the same 94-op graph, measured; its signature lists 53 parameter inputs (the tied embedding twice, under its two names) and 1 user input; ep.run_decompositions() lowers it to the core ATen set, 326 ops. What export did with each specification, recorded:




Two lessons. A dynamic dimension you declare is checked: the reshape to 8 rows made export fail with "You marked batch as dynamic but your code specialized it to be a constant (8)" and a suggested fix. A range is not checked against data: T up to 128 exported fine although the position table has 64 rows, so T > 64 would index past it at run time; with the correct range a T = 100 input was rejected on entry ("Guard failed: idx.size()[1] <= 64", recorded). torch._inductor.aoti_compile_and_package(ep) (AOTInductor) compiles the program ahead of time into a shared library in a 14,358,669-byte package that aoti_load_package runs from Python, or a C++ runner without Python; outputs matched eager within 1.25e-06 at (8, 64).


Dim.AUTO, control flow and draft_export; saving a .pt2; what the package holds (recorded)
Dim.AUTO found both dimensions dynamic but from 2, not 1 (0/1 specialisation again). Data-dependent Python control flow cannot be exported in either mode; torch.cond can. torch.export.draft_export exports it anyway and reports the problem; here it picked the branch the example took (cos) and inserted a runtime assert, with the advice to add torch._check.


torch.export.save wrote a 12,986,850-byte .pt2 archive (52 weight files, since tied weights are stored once, plus the graph as JSON); loading it gave identical outputs. In the AOTInductor package, the 14,163,036-byte wrapper.so holds the weights.


Measured here: AOTInductor and a non-contiguous input
A slice x[:3, :20] of the batch (strides (64, 1), not contiguous) passed to the AOTInductor package returned logits with a maximum error of 1.81 against eager, with no error or warning; the same input after .contiguous() matched within 9.5e-07, and the exported program's own ep.module() handled the slice exactly (0.0). The compiled library assumed the strides it was compiled for. Call .contiguous() on inputs to an AOTInductor model.


Where it leads. ExecuTorch (on-device) and the ONNX exporter (dynamo-based by default since 2.9) start from torch.export; what a model file holds in each format is section 3 of Local and on-device inference.

Depth: common mistakes and interview rehearsal


Common mistakes, each measured on this page (nine)


Logging inside the model with print or .item(). Each is a graph break; inside the block loop it costs the whole forward (section 3). Log outside the compiled function, or keep values as tensors and read them every N steps.


Calling mark_dynamic on one tensor of several that share a dimension. The targets carry the same length as the inputs and are guarded too (Compile lab); mark every tensor with the dimension, or give the bound with min and max so violations are errors you see.


Assuming nested_graph_breaks keeps a model compiled. It did nothing for a break inside a for loop over blocks, measured (section 3).


Passing a different Python string, dtype or config value each call. Guarded by value with no symbolic fallback: after 8 versions, eager mode with only a warning (section 4).


Timing the first call. It includes 9 seconds of compiling here; warm up, then time, and synchronise on a GPU (Making training fast section 1).


Compiling the whole model when compile time hurts. Compile the block (section 9): 5.7 s instead of 9.2 s here, and it does not grow with depth.


Measuring a "cold" compile with a warm cache. The caches are on by default and survive processes: 0.85 s looks like a fast compiler. Use an empty TORCHINDUCTOR_CACHE_DIR.


Feeding a sliced tensor to an AOTInductor package. Wrong answers with no warning, measured (section 11). Make inputs contiguous.

Interview rehearsal, with short answers (ten)


How does Dynamo capture a graph without running the model on real data? It installs a PEP 523 frame evaluator and symbolically executes each frame's bytecode with VariableTrackers; tensors are fake tensors carrying shapes, so ops add FX nodes and Python values are computed at trace time and protected by guards.


What is a guard, and what happens when one fails? A condition the compiled code assumed (shape, dtype, object identity, global state), checked in C++ before each call. On failure Dynamo recompiles and caches another version, up to recompile_limit (8), then runs eagerly.


Why might one graph break cost the whole model? A break inside a loop cannot be resumed, so Dynamo skips the enclosing frame: everything outside the blocks runs eagerly and the blocks compile in pieces.


Backed versus unbacked symbolic sizes? Backed come from input sizes and have an example value to answer branches; unbacked come from data (.item(), nonzero) and do not, so branches on them need torch._check or torch.cond.


What does the min-cut partitioner optimise? Which joint-graph values the forward saves for backward: it minimises saved bytes, recomputing cheap ops; activation_memory_budget lets it recompute expensive ones too.


Where does Inductor fuse? Mostly at lowering (pointwise ops are inlined into consumers), then in the scheduler (vertical and horizontal fusion of loops); matmuls and attention stay library calls unless autotuning picks a template.


What do the modes change? Only Inductor config: reduce-overhead turns on CUDA graphs; max-autotune adds matmul autotuning, coordinate-descent tuning and CUDA graphs; -no-cudagraphs drops the graphs.


Compiled autograd: what and why? Tracing the autograd engine's graph at backward time, including hooks and accumulation, so the backward compiles as one graph and distributed communication can be traced and overlapped.


How do you cut compile time for a 70B model? Regional compilation of the repeated block, warm caches shared across ranks (mega-cache), avoiding recompiles (mark dynamic dims, stable Python args), and profiling compile time by phase.


torch.compile versus torch.export? compile is a JIT inside Python that tolerates breaks and recompiles; export captures one full graph with explicit dynamic-shape constraints for deployment (ExecuTorch, AOTInductor, ONNX).
