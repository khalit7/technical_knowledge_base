8. Extending PyTorch: plug into one slot of the call path

Everything PyTorch does not ship (your kernel, a quantized weight format, a call into another library) plugs into one slot of the path a call takes (section 2), and the choice decides whether autograd, torch.compile and torch.export keep working. From lightest to heaviest: plain PyTorch code; a torch.autograd.Function to change a backward; a torch.library.custom_op, a new operator that the compiler treats as one opaque node once you tell it the output's shape (register_fake) and gradient (register_autograd); triton_op for a Triton or Helion kernel Inductor can see into; a tensor subclass with __torch_dispatch__ to change what a tensor is (DTensor, torchao's int8 and float8 weights); a TorchDispatchMode to watch every call in a region (the recorder behind {{Inside one step|#t-step}}); a new backend key for a whole device.

Two measured traps show why the order matters: registering a C++ operator's backward after it had already been traced left 16 of the running example's 52 parameters with no gradient under torch.compile, with no error, and the wrong compiled result then sat in the AOTAutograd cache for the next process measured on Apple M1 Pro. Register everything before anything traces.

The fake implementation is the key idea: the compiler and torch.export need to know the output's shape, dtype and device without running your code, so you tell them. The {{Compile lab|#t-comp}} shows what the same kind of break costs inside the running example (the outer forward left uncompiled, 7 to 9% slower).

Tensor subclasses in practice. torchao's int8 weight-only quantization (section 6) replaced each linear weight of the running example with an Int8Tensor, a subclass of torch.Tensor that defines __torch_dispatch__ and holds an int8 qdata of the original shape plus a float32 scale per row measured on Apple M1 Pro. The model code did not change: the linear layers call F.linear as before, the dispatcher reaches the Python key, and the subclass decides how to multiply. DTensor (section 7) is a tensor subclass too, which is why FSDP2 can shard a model without rewriting it; at 2.14.1, though, its constructor and its common operator path run in C++ for speed, and its Python __torch_dispatch__ only serves subclasses of DTensor ({{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}, section 5).

Writing kernels. When a fused kernel is the fix, the order of preference is usually: let Inductor generate it (section 5); write it in Helion, a kernel language hosted by the PyTorch Foundation that compiles to Triton by default (1.4.0 also has Pallas, CuTe and Metal backends; the Metal one ran on this laptop's GPU, {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}, section 4) and autotunes the tiling (1.0 released 2026-04-03, {{PyPI|https://pypi.org/project/helion/#history}}; {{helionlang.com|https://helionlang.com/}}); write Triton by hand; write CUDA. Register whichever you write as an operator (triton_op or custom_op) so the rest of PyTorch can use it.
