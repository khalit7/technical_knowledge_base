8. Extending PyTorch: pick the lightest hook that works

Sooner or later you need something PyTorch does not ship: a kernel you wrote, a quantized weight format, a library call outside PyTorch. Every way of adding it plugs into the machinery of sections 2 to 5, and they differ in what they can change and in whether torch.compile and torch.export still work. From lightest to heaviest:

HookWhat it changesUse it forUnder compile and export
Plain PyTorch codeNothing; composes existing operatorsMost new layersTraced like any code
torch.autograd.FunctionThe backward of a piece of codeA custom or more stable gradientTraced if forward and backward are traceable
torch.library.custom_opAdds a new operator to the dispatcher, opaque to the compiler; register_fake says what shape it returns, register_autograd its backwardCode the compiler cannot or should not trace: C++ or CUDA kernels, calls into other librariesOne node in the graph, no break
torch.library.triton_op with wrap_tritonA Triton kernel registered as an operatorYour own GPU kernels (Triton, or Helion, which compiles to Triton)Visible to Inductor, which can optimise around it
Tensor subclass with __torch_dispatch__What a tensor is: every operator on it goes through your Python code at the Python keyNew representations: DTensor (sharded), torchao's int8 and float8 weights, NF4Supported for subclasses written to the traceable-subclass protocol
TorchDispatchModeSees every operator call while activeRecorders, debuggers, counting FLOPs (the {{Inside one step|#t-step}} recorder is one)Eager tool
A new backend key (PrivateUse1)A whole deviceHardware vendorsThrough the vendor's compiler backend

Before and after: a function that leaves PyTorch, then the same code as a custom operator

# before: plain Python in the middle def py_clip(t): return torch.tensor([min(max(v, -1.0), 1.0) for v in t.tolist()]) def f(x): y = torch.sin(x) * 2 y = py_clip(y) return y.exp().sum()
# after: the same body, registered @torch.library.custom_op("rd::clip", mutates_args=()) def clip_op(t: torch.Tensor) -> torch.Tensor: return torch.tensor([min(max(v, -1.0), 1.0) for v in t.tolist()]) @clip_op.register_fake def _(t): return torch.empty_like(t)

measured here with torch._dynamo.explain, PyTorch 2.14.1 on the CPU, on a 64-element input (src/read/measure.py). Dynamo's reason for the break: . Both versions return the same value.

The fake implementation is the key idea: the compiler and torch.export need to know the output's shape, dtype and device without running your code, so you tell them. The {{Compile lab|#t-comp}} shows what the same kind of break costs inside the running example (the outer forward left uncompiled, 7 to 9% slower).

Two traps, measured. Register everything (fake implementation, backward) before anything traces the operator. Registering a C++ operator's backward from Python after it had already been traced in the process left 16 of the running example's 52 parameters with no gradient under torch.compile, with no error. And that wrong compiled result was stored in the AOTAutograd cache: a new process with correct registrations and the same cache directory reused it, until the cache was turned off (TORCHINDUCTOR_AUTOGRAD_CACHE=0) or cleared measured on Apple M1 Pro ({{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}, section 2).

Tensor subclasses in practice. torchao's int8 weight-only quantization (section 6) replaced each linear weight of the running example with an Int8Tensor, a subclass of torch.Tensor that defines __torch_dispatch__ and holds an int8 qdata of the original shape plus a float32 scale per row measured on Apple M1 Pro. The model code did not change: the linear layers call F.linear as before, the dispatcher reaches the Python key, and the subclass decides how to multiply. DTensor (section 7) is a tensor subclass too, which is why FSDP2 can shard a model without rewriting it; at 2.14.1, though, its constructor and its common operator path run in C++ for speed, and its Python __torch_dispatch__ only serves subclasses of DTensor ({{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}, section 5).

Writing kernels. When a fused kernel is the fix, the order of preference is usually: let Inductor generate it (section 5); write it in Helion, a kernel language hosted by the PyTorch Foundation that compiles to Triton by default (1.4.0 also has Pallas, CuTe and Metal backends; the Metal one ran on this laptop's GPU, {{Extending PyTorch|n:3f85c17b0d0d8158a7addcd3d601d72a}}, section 4) and autotunes the tiling (1.0 released 2026-04-03, {{PyPI|https://pypi.org/project/helion/#history}}; {{helionlang.com|https://helionlang.com/}}); write Triton by hand; write CUDA. Register whichever you write as an operator (triton_op or custom_op) so the rest of PyTorch can use it.
