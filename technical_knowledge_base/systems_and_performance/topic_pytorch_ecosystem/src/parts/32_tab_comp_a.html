1. What torch.compile does, on this model

Eager mode is PyTorch's normal way of running: each Python line calls one operator, which runs one kernel right away and writes its result to memory (the {{Inside one step|#t-step}} tab follows all 142 forward calls of this model that way). torch.compile(model) instead watches the Python code run once, turns it into a graph (a list of operations with their data dependencies), optimises the whole graph, and from then on runs generated code instead. Four pieces do it. Click one to jump to its section.

Two words appear everywhere below. A guard is a check Dynamo writes next to each compiled graph ("the input is int64 of shape (8, 64)", "grad mode is on"); on every call the guards run first, and if one fails the code is recompiled for the new situation. A graph break is a point where Dynamo cannot follow the Python (a print, a tensor turned into a Python number): it ends the graph there, runs that bit as ordinary Python, and starts a new graph after it. The mechanics of each piece, on small programs and with every log, are on {{The compiler stack: PTX, SASS, NVRTC, torch.compile and Inductor|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}} (sections 8 and 9 and its Inside torch.compile tab); this tab measures them on a whole training step.

2. Fusion: the same function, op by op and as one loop

Most operations in a model, other than matrix multiplies and attention, are pointwise (each output element depends on one input element: add, multiply, GELU) or small reductions (a row's mean, as in LayerNorm). In eager mode each one is its own kernel: it reads its inputs from memory and writes a full-size result back, and the next op reads that result again. Fusion merges a chain of them into one kernel that reads each input once, keeps the intermediate values in registers, and writes only the final result. The work done is the same; the memory traffic is not.

Below: GPT-2's GELU written out with tanh (the form in the original GPT-2 code), on a tensor the size of this model's MLP activation, (8, 64, 1024) float32 = 2 MiB; or the residual add plus LayerNorm that opens every block's second half. The kernel Inductor wrote for the tanh GELU, verbatim (C++, CPU)

One OpenMP loop over the 524,288 elements, 4 at a time (Vectorized<float> on this machine is a 128-bit NEON register of 4 floats; Inductor picked the VecNEON ISA). Each tmp is a register, not a tensor: the 8 eager ops are the arithmetic between one loadu and one store.



The kernel for add + LayerNorm, and why it lost
ATen's own native_layer_norm is already a single hand-written kernel, so fusion only saves the add's round trip. Inductor's version makes several passes per row (a sum for the mean, a pass for the variance, the normalisation) and, in this build, divides the 512 row sums inside an omp single block, which one thread runs. Reading code like this is how you find out why a compiled region is slower than you expected.
