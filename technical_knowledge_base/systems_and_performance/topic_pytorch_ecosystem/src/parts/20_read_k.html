Common mistakes

Timing GPU code without synchronising
GPU work is queued and returns at once; time.perf_counter() around it measures the launch. Synchronise before reading the clock, warm up, repeat, report medians (or use torch.utils.benchmark.Timer).
Calling .item() or printing the loss every step
Each one makes the CPU wait for the GPU, and under torch.compile it is a graph break (section 5). Log every N steps, or keep a running tensor and read it rarely.
Using no_grad to save memory while training
No graph, so no backward (section 3). Use activation checkpointing, a smaller micro-batch with accumulation, or sharding.
Assuming reshape never copies, or that view always works
view fails on non-contiguous tensors; reshape silently copies (section 1). In-place writes through a view change the original.
Accumulating gradients without dividing the loss, or without no_sync under DDP
The first gives a gradient N times too large (and dividing is exact only when every micro-batch counts the same number of tokens); the second pays an all-reduce per micro-batch (sections 4 and 7).
Expecting torch.compile to speed up anything
On this laptop's CPU it gave nothing; on MPS 1.18 times. Measure; then check breaks and recompiles (varying shapes, eval() versus train(), Python scalars that change).
float16 without a GradScaler
Small gradients underflow to zero. Use bfloat16 where the hardware supports it, or torch.amp.GradScaler.
Moving a loop into a framework and expecting the same run
Defaults differ: the Hugging Face Trainer clips at 1.0, decays the learning rate linearly and shuffles (section 4); DeepSpeed also clips at 1.0 by default since 0.19.3 (section 9).
A collective that only some ranks call
An if rank == 0: all_reduce(...), uneven data, or a different tensor shape on one rank hangs the job until the timeout (section 7).
Starting new work on torchtune, TorchScript or the FSDP1 wrapper
torchtune is no longer maintained, TorchScript is deprecated, and FSDP2's fully_shard is where the work goes (section 9).
Loading untrusted checkpoints with weights_only=False
A pickle can run code. Keep the default weights_only=True (since 2.6) or use safetensors.

Interview questions, with short answers

Why does x.t().view(-1) fail, and what does reshape do instead?
The transpose has strides (1, 4): its elements in order are not adjacent in storage, so no single stride can describe a flat view. reshape returns a view when possible and otherwise copies.
What happens between torch.mm(a, b) and the BLAS call?
The dispatcher computes the call's key set from the inputs and thread-local state and runs the highest-priority kernel: autocast may cast, autograd records MmBackward0 and saves inputs, a subclass's __torch_dispatch__ may run at the Python key, and the backend kernel finally calls BLAS.
no_grad or inference_mode?
Both stop graph recording. inference_mode also drops the autograd keys and version counters from new tensors, so it is a little faster, but those tensors cannot later be used in autograd. Use it for serving; no_grad for evaluation inside training code.
What takes memory in training a model with AdamW?
Parameters, gradients (same size), optimizer state (two more copies), and saved activations, which grow with batch and sequence length. Running example: 12.75 + 12.75 + 25.5 MB of model state against 34.76 MB of activations at batch 8 by 64.
How does activation checkpointing trade memory for compute?
It keeps only a region's inputs and re-runs the region in backward. Running example: 34.85 to 3.33 MB added by forward, 112 recomputed calls, 22.5 to 31.6 ms per step on the CPU.
Guards, graph breaks and recompiles: what are they?
Guards are the conditions under which a compiled graph is valid; when one fails, Dynamo recompiles (up to recompile_limit, 8). A graph break is Python Dynamo cannot capture: it ends the graph, runs eagerly, and starts a new one. Find both with TORCH_LOGS="graph_breaks,recompiles".
Why might torch.compile not speed a model up?
The time is in operations it does not change (large matrix multiplies already in cuBLAS or BLAS), the step is dominated by something else (data, the optimizer, communication), or breaks and recompiles eat the gain. Profile first.
for-loop, foreach or fused optimizer?
Same maths; the for-loop launches small operations per tensor, foreach batches each operation over all tensors, fused does the whole update in one kernel. Fused was 2.7 times faster than the default on this CPU and 4.1 times on MPS for the optimizer phase.
DDP or FSDP2?
See section 7: DDP keeps a full copy per rank and all-reduces gradients; FSDP2 shards every parameter and gathers it only when needed, cutting memory per rank for more communication.
What is a DTensor?
A tensor plus a device mesh plus one placement per mesh dimension (Shard(d), Replicate(), Partial()); operators propagate placements and insert the collectives needed. FSDP2, tensor parallelism and distributed checkpoints are built on it.
A multi-GPU job hangs. What do you do?
Find which rank is in which collective: the flight recorder dump (or py-spy on each rank), TORCH_DISTRIBUTED_DEBUG=DETAIL to catch mismatched shapes or order, then look for rank-dependent code paths and uneven data.
custom_op, autograd.Function or a tensor subclass?
autograd.Function to change a backward; custom_op to add an opaque operator that compile and export can treat as one node (with a fake implementation); a subclass to change what a tensor is (sharded, quantized).
Which stack for: pretraining from scratch on 512 GPUs; LoRA on one GPU; your own loop on Hugging Face models?
torchtitan (or Megatron Core on an NVIDIA-committed stack); PEFT with TRL, or Axolotl, or Unsloth for single-GPU speed; Accelerate (or Lightning Fabric).
