3. DDP: one all-reduce per bucket, during backward

DistributedDataParallel (DDP) keeps a full copy of the model on every rank and makes their gradients identical before each optimizer step, so the copies never drift apart. It does three things, all visible in the recording:

  1. At construction, it checks every rank has the same parameters and copies rank 0's weights to everyone. Recorded: an all-gather of 8 bytes (the parameter count), a broadcast of 1,120 bytes (the 52 parameters' sizes and strides, reducer.cpp L2422), then a broadcast of all 12,747,776 bytes of weights.
  2. In backward, it groups the gradients into buckets. A hook on each parameter fires when its gradient is final; when every gradient in a bucket is final, DDP launches that bucket's all-reduce asynchronously and backward keeps computing the earlier layers. That is the overlap: communication of the last layers hides behind computation of the first.
  3. Before the optimizer step, it waits for the last bucket and divides by the world size, so every rank holds the average gradient. Each rank then runs the same AdamW update on the same numbers.

Why buckets? One all-reduce per parameter would mean 52 small messages, each paying a fixed latency; one for the whole model could start only when backward ends, so nothing overlaps. The default cap is 25 MiB, with a smaller first bucket of 1 MiB so the first all-reduce can start early (distributed.py L31, L86). Buckets fill in reverse parameter order, because backward produces the last layer's gradients first.

Predict. The model is 12.75 MB of float32 gradients, under one 25 MiB bucket but over the 1 MiB first bucket. How many all-reduces does DDP issue in the first backward?

One. Recorded on both ranks: a single all-reduce of 12,747,776 bytes, issued only once every gradient was final, so nothing overlapped in step 0. Unless find_unused_parameters=True or an explicit bucket list is given, the first iteration puts everything in one bucket (a size limit of sys.maxsize, L151); during that iteration DDP records the order in which gradients actually arrived, and at the start of step 1 rank 0 broadcasts a new bucket layout in that order (the two small broadcasts of 212 and 8 bytes in step 1). From then on: two buckets, 1,051,648 and 11,696,128 bytes.

It is always in the last bucket. And with bucket_cap_mb=1 the same step issues 13 all-reduces of about 1 MB, each one launched while backward is still running: more overlap, more per-message overhead. Which wins depends on the network; on GPUs the default is usually right, which is why it is the default.

Here that is 12.75 MB per rank on top of the 12.75 MB of weights and 25.5 MB of AdamW state. gradient_as_bucket_view=True makes each .grad a view into its bucket and removes the copy; on this model the step's peak did not move (), because the peak comes at the very start of backward, when every activation is still held and only the first gradients exist. 4. FSDP2: every parameter split, gathered only when needed

DDP's memory per rank never shrinks: 16 bytes per parameter of weights, gradients and Adam state on every rank (more with its buckets). FSDP (fully sharded data parallel) is PyTorch's version of ZeRO stage 3 (the theory is on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}}, and the {{ZeRO paper page|n:3c65c17b0d0d81879a7ed90bca007699}} steps through DDP against ZeRO-3 on GPUs): each rank permanently keeps only 1/n of every parameter, its gradient and its optimizer state, and rebuilds a whole layer just before using it.

FSDP2 is the current API, torch.distributed.fsdp.fully_shard (in PyTorch since 2.4; FSDP1, the FullyShardedDataParallel wrapper with flattened parameters, is still shipped at 2.14 without a formal deprecation notice: see {{Ecosystem map|#t-map}}). fully_shard(module) turns each of the module's parameters into a DTensor (section 7) with placement Shard(0): rank r owns rows r·k to (r+1)·k of every weight. The model is wrapped the way torchtitan does it: fully_shard on each of the 4 blocks, then on the whole model, which picks up what is left (embeddings, final LayerNorm, tied output layer). Each call makes one unit: one all-gather brings its weights in, one reduce-scatter sends its gradients out.

What happens in one step, per unit, in order:

  1. Forward: just before a block runs, all-gather its shards into full weights (here each rank sends 1.58 MB and receives the other rank's 1.58 MB); run it; then, by default, free the full weights again (reshard after forward), keeping only the activations.
  2. Backward: all-gather the block's weights a second time (they were freed), compute its gradients, then reduce-scatter them: sum across ranks and leave each rank only its own 1/n slice. Free the full weights and full gradient.
  3. Optimizer: AdamW runs on each rank's shards only, with no communication at all, because each rank owns the whole update of its rows.

reshard_after_forward defaults to None: True for the blocks, False for the root unit, "because the root module is typically required immediately when the backward pass begins" (_fully_shard.py L180). FSDP2 also prefetches: it issues the next unit's all-gather before the current unit finishes, which you can see below as all-gathers launched early. Setting it False everywhere skips all four backward all-gathers and keeps every block's full weights alive from forward to backward.

With the default, the last block is resharded at the end of forward and gathered again at once, because backward starts there (the "AG block 3" right after forward in the timeline below). torchtitan avoids exactly this: it does not reshard the final norm and output layer after forward "since FSDP would prefetch them immediately", and puts the tied embedding and output layer in one unit (torchtitan 0.3.0, distributed/fsdp.py L180), as the root unit does here.
