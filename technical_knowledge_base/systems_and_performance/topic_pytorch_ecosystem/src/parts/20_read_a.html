PyTorch is a Python library for computing with arrays of numbers on CPUs and GPUs, which also works out the gradients you need to train a model. This page teaches it from zero by following one training step of a tiny GPT down through PyTorch, then making it fast, then spreading it over several processes. Every number on it was either measured here or comes from a linked, dated source, and the two are labelled apart.

The running example. A character-level GPT written in plain PyTorch: 43 distinct characters as its vocabulary, 4 transformer blocks of width 256 with 4 attention heads, a context of 64 characters, 3,186,944 parameters, trained with AdamW on batches of 8 windows cut from the first three paragraphs of Alice's Adventures in Wonderland. Its first loss is 3.8014, just above ln 43 = 3.761, the loss of a uniform guess, and after 300 steps it reaches 0.546 measured on Apple M1 Pro. The same model, the same batches and the same seed are used by every tab of this page and by every child page. Machine: an Apple M1 Pro laptop, its CPU (4 threads) and its GPU through Apple's MPS backend (Metal Performance Shaders), PyTorch 2.14.1 (released 2026-09-30, {{PyPI|https://pypi.org/project/torch/#history}}). There is no NVIDIA GPU here, so each section says what carries over to one and what does not, and published GPU numbers are quoted separately with who measured them.

One forward pass of the tiny GPT, down through the stack: eager, then compiled

Counts measured on Apple M1 Pro, CPU, torch 2.14.1: 142 ATen operator calls seen by a dispatch-level recorder in one eager forward ({{Inside one step|#t-step}}); 1 captured graph of 59 operations, 549 guards, and 35 launches per compiled forward, of which 14 are generated C++ kernels, 17 matrix multiplies in the BLAS library and 4 attention calls ({{Compile lab|#t-comp}}). Compile time 9.0 to 10.0 s with an empty cache.

The figure is the whole page in miniature. Your code calls model(x). Python runs the module's forward, which calls PyTorch functions such as torch.matmul. Each call is an operator (a named operation such as aten::addmm; ATen is PyTorch's C++ tensor library, where every operator is defined). The dispatcher decides which implementation of that operator runs, by reading labels on the inputs: is a gradient needed, is mixed precision on, which device holds the data. At the bottom a kernel (one compiled function that does the arithmetic on one device) runs. torch.compile replaces most of that walk with generated code; torch.distributed runs the same program in several processes that exchange data.

Five ideas carry everything that follows.

1. Views
shape + strides

A tensor is a window onto a flat block of memory. Transposes and slices are free; they only change how the window steps. Section 1.

2. Dispatch
one table per operator

Every call looks up a kernel by keys. Autograd, mixed precision, subclasses and devices are all entries in that table. Section 2.

3. Saved tensors
34.76 MB

Forward records a graph and keeps tensors for backward. They, not the weights, fill memory in training. Section 3.

4. Fusion
142 → 35

Compiling turns many small memory round trips into a few loops. It pays when memory traffic or launch overhead dominates. Section 5.

5. Placements
Shard, Replicate, Partial

Distributed PyTorch describes how each tensor is split over processes; FSDP2 and tensor parallelism are placements. Section 7.

34.76 MB is the bytes autograd kept after one forward of the running example (34,761,220 B), 142 and 35 the eager calls and compiled launches above, all measured on Apple M1 Pro.
