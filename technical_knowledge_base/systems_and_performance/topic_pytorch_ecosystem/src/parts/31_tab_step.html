The running example, and how this was recorded

The model (the topic's src/model/, shared by every tab): a GPT-2-shaped decoder in plain PyTorch, character level on 1,329 bytes of Alice's Adventures in Wonderland. 43-character vocabulary, dmodel 256, 4 blocks (pre-LayerNorm, 4 attention heads through F.scaled_dot_product_attention, GELU MLP of 1,024), learned positions, output layer tied to the input embedding: 3,186,944 parameters. Batch 8 windows of 64 characters. AdamW, lr 6e-4. Seeded, so the weights and batches are the same on every run.

The step recorded is the second step (batch 1), after one warm-up step, so AdamW's state already exists (the first step also creates it: 104 extra zeros_like calls for the two moments and 52 lift_fresh for the step counters). Loss 3.1879 on CPU and on MPS.

How: a TorchDispatchMode (PyTorch's hook for seeing every ATen call that reaches the dispatcher below autograd) logs each call's inputs and outputs (shape, strides, storage offset, dtype) and whether an output got a new storage. Live bytes are tracked per storage, with a finalizer on each storage object, so a storage counts from its allocation until the last tensor using it dies. The dispatch route is reconstructed from each input tensor's dispatch key set (torch._C._dispatch_keys), the thread state (grad mode, inference mode) and the op's dispatch table (torch._C._dispatch_dump_table, which says which keys have a real kernel). The autograd graph is walked from the loss after forward; pre-hooks on every node record the order backward runs them. Scripts: src/step/record_step.py, basics.py, time_step.py; torch 2.14.1, CPU with 4 threads, and MPS. Measured on Apple M1 Pro. What carries over to NVIDIA GPUs is at the end.

1. A tensor is a view onto a storage

A tensor is a header (shape, strides, offset) over a flat storage, and a view is a new header over the same bytes; the mechanism, stepped and explorable, is on {{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}, section 1, and its Stride explorer. What this step adds is where views happen in a real model.

The model does exactly this in attention. One qkv Linear writes a (512, 768) block; view makes it (8, 64, 768); split cuts q, k and v as three views at storage offsets 0, 256 and 512, all with strides (49152, 768, 1); view and transpose turn each into (batch, head, position, 64) with strides (49152, 64, 768, 1). 2. The dispatcher: a table of kernels per key

Every call walks down its operator's table of kernels by dispatch key, from autocast and autograd down to a backend; the walk itself, key by key, and the tables are on {{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}, sections 2.2 and 2.3. A parameter of the model on the CPU carries . Three entries of the real tables (torch 2.14.1 wheel, torch._C._dispatch_dump_table) show up in the recorded step:

  • linear is a math kernel on the CPU, so on the CPU every nn.Linear decomposes at the autograd key into t (a view of the weight) and addmm (one fused multiply-add kernel), and autograd records a node for each. On MPS linear has its own kernel and its own autograd kernel: the MPS trace has 17 linear calls where the CPU trace has 17 t plus 16 addmm plus one mm.
  • ADInplaceOrView has a real kernel only for views and in-place ops (view, add_); for addmm it is a fallthrough. That is where PyTorch records that a view shares its base's storage and bumps the version counter that catches an in-place write to a tensor backward still needs.
  • _scaled_dot_product_flash_attention_for_cpu has no MPS kernel, so on MPS F.scaled_dot_product_attention takes another route for this model: the MPS trace shows it written out (mul, bmm, _safe_softmax, bmm), with the full 64 × 64 attention matrix per head in memory.

The recording in section 3 is itself a dispatch mode at the Python key; the Reading tab's section 8 and the {{Compile lab|#t-comp}} build on the same table.

5. Before and after: the same step with activation checkpointing

Activation checkpointing (torch.utils.checkpoint.checkpoint(block, x, use_reentrant=False), here around each of the 4 blocks) tells autograd not to keep a block's intermediate tensors. Forward keeps only each block's input. In backward, when a node inside the block needs a tensor it did not keep, PyTorch reruns the block's forward to rebuild it, then carries on. The trade: memory for compute. Watch the same step both ways, drawn to the same scale.

Pass use_reentrant=False explicitly. At 2.14.1 a call that leaves it out still runs the older reentrant variant and only warns (checkpoint.py L635 to L647); on this step that variant recomputed all 16 block matrix multiplies instead of 12 ({{Tensors, the dispatcher and autograd|n:3f85c17b0d0d81138595c1c6cd52f795}}, section 3.6).

6. Before and after: the same forward with gradients off

For evaluation and generation you do not need a graph. Two switches turn it off. torch.no_grad() sets grad mode off: every call still enters the autograd kernel, which sees there is nothing to record and passes the call on. torch.inference_mode() goes further: it removes the autograd and ADInplaceOrView keys for the thread, so calls skip those layers entirely, and tensors created inside are inference tensors with no version counter (using one later in autograd raises an error). 9. What carries over to NVIDIA GPUs, and what does not

Carries over

The op sequence and the graph. On a CUDA tensor the keys become AutogradCUDA and CUDA; the same Python code makes the same autograd nodes and the same saved tensors. Saved bytes at float32 are the same; under bf16 autocast most activations halve.

Carries over

The dispatch mechanics: math kernels decomposing, views costing nothing, no_grad against inference_mode, checkpointing's memory-for-compute trade and its early stop, the version counter.

Changes

Which kernels run. On CUDA, scaled_dot_product_attention picks FlashAttention or memory-efficient kernels (not the CPU flash kernel, not the MPS math path); linear decomposes as on the CPU and the matmul goes to cuBLAS. See {{Writing kernels|n:3c65c17b0d0d81b9ab89c1bb7238cb6c}} for FlashAttention.

Changes

The optimizer default. On CUDA PyTorch picks foreach by default (here: the for-loop), and fused=True is one opt-in away. The for-loop reads the step counter with .item() once per parameter (adam.py L528); the counter lives on the CPU unless capturable=True or fused=True (L168), so by default that read is not a GPU sync. See {{Optimisers|n:3c65c17b0d0d817080bbc90954681d09}}.

Does not carry over

Times. These are CPU and Apple-GPU times at a toy size, where per-call overhead in Python and the dispatcher is a large share (). On a GPU the same overhead shows up as launch gaps between short kernels: the case for torch.compile and CUDA graphs ({{Compile lab|#t-comp}}, {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}).

Does not carry over

Exact live bytes. CUDA's caching allocator rounds blocks up and keeps freed memory for reuse, so torch.cuda.memory_allocated is close to these numbers and memory_reserved is higher. See {{Memory allocators|n:3f05c17b0d0d81209ae9d856695dc958}}.

10. Common mistakes, and interview questions

Common mistakes

".view() and .reshape() are the same"
view never copies and fails when the strides do not allow it (try x.t().view(12): ). reshape returns a view when it can and silently copies when it cannot, so whether you got a copy depends on the input's layout.
".contiguous() always costs a copy"
Only when the tensor is not already laid out row-major. In this step it copied nothing on the CPU and 524,288 bytes per layer on MPS, for the same line of Python: the layout depends on which attention kernel produced the tensor.
"Memory is the parameters"
Here the parameters are 12.75 MB, AdamW's two moments 25.5 MB (twice the parameters, in float32), the gradients another 12.75 MB at their peak, and the activations kept for backward 34.8 MB. At real batch sizes and sequence lengths the activations dominate.
"no_grad and inference_mode are the same"
Both build no graph and keep nothing. no_grad still enters the autograd and view-tracking layers on every call; inference_mode skips them and makes inference tensors you cannot later use in a graph. On this toy forward the difference was within noise on both devices (section 6); the gain grows with the number of small ops.
"Checkpointing doubles the compute"
It reruns the forward of each checkpointed region once, during backward, and non-reentrant checkpointing stops each rerun as soon as it has rebuilt what backward needs (here 12 of the 16 addmm calls). Forward is about a third of a step's arithmetic, so the extra is about a third, not double; here the CPU step went from 22.5 to 31.6 ms.
"Modifying a tensor in place is always fine under torch.no_grad()"
If backward still needs that tensor (it is saved by some node), the in-place write bumps its version counter and backward raises "one of the variables needed for gradient computation has been modified by an inplace operation". That counter is what the ADInplaceOrView kernels maintain.
"Timing a step with time.time() around it is enough"
On MPS and CUDA the call returns before the GPU finishes. Synchronise first (here torch.mps.synchronize()), repeat, and report the spread; see {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}}.

Interview questions

What is the difference between a tensor and its storage?
The storage is the flat memory (bytes, device, dtype); the tensor is a view of it: shape, strides, storage offset. Views share storage; x.untyped_storage().data_ptr() tells you whether two tensors do.
Walk me through what happens when you call torch.add(a, b) on two CPU tensors that require grad.
The dispatcher builds the key set from both tensors and the thread state, runs the highest-priority kernel: AutogradCPU records an AddBackward0 node (with grad mode on) and redispatches with autograd masked out; ADInplaceOrView is a fallthrough for add; the CPU kernel allocates the output and computes it.
What does autograd save for y = x @ W.t() + b?
For the gradient wrt W it needs x; for the gradient wrt x it needs W. W is a parameter (no extra memory); x is an activation. The bias gradient is a sum over rows and needs nothing saved. In this step every AddmmBackward0 saved its input and the weight.
Why can backward use less memory than forward's peak, and when are gradients allocated?
Backward frees each node's saved tensors right after running it (unless retain_graph=True), while gradients appear as AccumulateGrad nodes run. Here live memory fell from +34.8 MB after forward to +12.8 MB after backward: the gradients, freed by zero_grad(set_to_none=True).
What is a CompositeImplicitAutograd op, and why does it matter for compilers and custom backends?
An op written in terms of other ops (here linear on CPU), so it needs no backward formula and no backend kernel of its own: it decomposes before autograd records anything. A backend may still register its own kernel to avoid the decomposition (MPS does for linear), and compilers see the decomposed ops.
How would you find which op allocates the most memory in a step?
On CUDA, torch.cuda.memory._record_memory_history() and the memory snapshot viewer; anywhere, a TorchDispatchMode that logs output storage sizes, as this tab does, or the profiler with profile_memory=True.
