3. Autograd: the graph built during forward

The problem. Training needs the gradient of the loss with respect to every parameter: how much the loss would change if that number moved a little. Working it out by hand for a model is impossible; doing it numerically (nudge each of 3 million numbers) is far too slow.

How it works. Autograd applies the chain rule automatically. During forward, the autograd kernel of each operator (section 2) adds a node to a graph: an object that knows how to turn the gradient of its output into gradients of its inputs (MmBackward0 for a matrix multiply). To do that later, a node keeps some of the forward's tensors: the saved tensors. Calling loss.backward() walks the graph from the loss back to the parameters, each node passing gradients to the next, and AccumulateGrad nodes add the result into each parameter's .grad. A node's saved tensors are released once it has run. Watch it on a two-layer network small enough to see whole:

Both modes give the same gradient.

Two things to take from it. First, what fills memory in training is the saved tensors, and they grow with batch size and sequence length while the weights do not. For the running example one forward builds a graph of 187 nodes (135 operators plus 52 AccumulateGrad, one per parameter tensor) and keeps 34.76 MB of activations, against 12.75 MB of parameters measured on Apple M1 Pro. Second, you can trade memory for compute. Activation checkpointing (torch.utils.checkpoint.checkpoint(fn, x, use_reentrant=False)) runs a region without keeping its intermediates, keeps only its input, and re-runs the region during backward when they are needed. Backward recomputes 112 calls, not a whole forward per block: PyTorch's non-reentrant checkpoint stops recomputing once it has rebuilt the tensors backward asked for (on by default at 2.14.1, torch/utils/checkpoint.py), so 12 of the 16 block matrix multiplies are redone.

Predict: wrap the training step's forward in torch.no_grad() to save memory. What happens at loss.backward()?
An error: "element 0 of tensors does not require grad and does not have a grad_fn". Under no_grad the autograd kernel records nothing, so there is no graph to walk. no_grad and inference_mode are for evaluation and serving; checkpointing is the tool for saving memory while training.

Custom backward. When you need a gradient autograd cannot derive (a numerically safer formula, a kernel written outside PyTorch), subclass torch.autograd.Function with a forward and a backward and save what backward needs with ctx.save_for_backward; check it against finite differences with torch.autograd.gradcheck in float64. The {{Inside one step|#t-step}} tab does exactly that check for one block. For an operator that should also work under torch.compile, prefer torch.library.custom_op with register_autograd (section 8).

When it matters and how to check. When you run out of memory in training, look at activations first. torch.cuda.max_memory_allocated() (on a Mac, torch.mps.current_allocated_memory()) before and after forward gives the saved bytes; the memory snapshot (section 6) says which tensors they are.
