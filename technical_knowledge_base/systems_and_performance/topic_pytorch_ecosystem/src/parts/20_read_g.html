6. Performance: find the bottleneck, then fix that one

Most slow training jobs are slow for one reason, and the fastest way to find it is to measure where a step's time goes before changing anything. Split the step into its phases (forward, backward, optimizer), time each one honestly (warm up first, repeat, take medians, and on a GPU call torch.cuda.synchronize() before reading the clock, because GPU work runs asynchronously), and fix the largest one you can.

measured on Apple M1 Pro, CPU, 4 threads, PyTorch 2.14.1, medians of 5 trials of 20 steps after 5 warm-up steps; load average 10 to 17 from other jobs ({{Inside one step|#t-step}}, section 7, and src/step/inputs/timing_opt.json). The "after" optimizer bar is the fused AdamW measured on its own; the step with it was measured separately at 19.08 ms by the {{Compile lab|#t-comp}} (load average 2.7 to 6.6), against 19.19 ms forward + backward + fused optimizer.

Nobody would guess that the optimizer, a few element-wise updates, costs a quarter of the step. It does because the default for-loop AdamW launches several small operations for each of 52 parameter tensors: 486 operator calls per step against 142 for the whole forward measured. On a GPU the same pattern shows up as hundreds of tiny kernels with the GPU idle between them, which is why foreach became the default there. The general lesson: count launches as well as FLOPs.

Attention backends. F.scaled_dot_product_attention (SDPA) is one function with several implementations behind it; at 2.14.1 the SDPBackend enum lists FLASH_ATTENTION, EFFICIENT_ATTENTION, CUDNN_ATTENTION, MATH and OVERRIDEABLE read from the installed wheel. It picks the first one whose constraints the inputs meet (dtype, head size, mask, device). The fused backends never write the full sequence-by-sequence score matrix to memory, the idea of {{FlashAttention|n:3c65c17b0d0d81e4a3e8e7a2c4771381}}; the MATH backend does, and always works. On this laptop the CPU ran a flash-style CPU kernel, while MPS took the math path for the running example's shapes measured. Force or debug the choice with torch.nn.attention.sdpa_kernel([SDPBackend.FLASH_ATTENTION]): if the inputs do not qualify, the call fails ("No viable backend for scaled_dot_product_attention was found" on the CPU at 2.14.1, measured; on CUDA a warning also names the reason), instead of silently falling back to a slower backend.

FlexAttention (torch.nn.attention.flex_attention) covers the variants the fixed backends do not: you write a score_mod (change a score: relative bias, soft-capping) or a mask_mod (which query may see which key: sliding windows, documents packed into one sequence) as small Python functions, and torch.compile generates one fused kernel that skips fully masked blocks. Its authors measured 90% of FlashAttention-2's speed in forward and 85% in backward vendor, PyTorch team, 2024 ({{FlexAttention blog|https://pytorch.org/blog/flexattention/}}); it runs on Apple GPUs since 2.13 ({{2.13 release notes|https://github.com/pytorch/pytorch/releases/tag/v2.13.0}}).

torchao is PyTorch's library for lower precision: quantized weights for inference, float8 and MX formats for training, sparsity. It works by replacing weights with tensor subclasses (section 8). Applied to the running example on the CPU, Int8WeightOnlyConfig turned each of 17 linear weights into an Int8Tensor (int8 data plus one float32 scale per row) and moved the first loss from 3.80137 to 3.8009 measured on Apple M1 Pro ({{Ecosystem map|#t-map}}). On GPUs, its float8 training gave up to 1.5 times the throughput at 512 GPUs on a 405B model vendor, torchao README ({{torchao|https://github.com/pytorch/ao}}). For the largest single activation of a big-vocabulary LLM, the logits, 2.13 added nn.LinearCrossEntropyLoss, which fuses the output layer into the loss so the batch × sequence × vocabulary tensor is never stored ("up to 4x lower peak memory", release-note figure, {{2.13 notes|https://github.com/pytorch/pytorch/releases/tag/v2.13.0}}).
