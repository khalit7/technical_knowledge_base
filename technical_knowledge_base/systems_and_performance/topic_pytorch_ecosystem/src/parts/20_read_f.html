5. Eager or compiled: torch.compile

Eager PyTorch runs one operator at a time: each pays Python and dispatch overhead, and each reads its inputs from memory and writes its output back, so a chain of small element-wise operations moves the same activation through memory again and again. torch.compile(model) does nothing until the first call; then three stages run:

TorchDynamo
capture

Reads the function's bytecode as it runs (PEP 523) into an FX graph, with the assumptions it relied on as guards. Python it cannot trace is a graph break: that part runs eagerly between graphs.

AOTAutograd
forward + backward

Traces through autograd ahead of time into a forward and a backward graph, and decides which values backward keeps and which it recomputes.

TorchInductor
codegen

Fuses element-wise chains and reductions into single loops: Triton on NVIDIA and AMD GPUs, C++ with OpenMP on CPUs, Metal on Apple GPUs. Matrix multiplies usually stay library calls.

The same forward down the stack: 142 calls eagerly, 35 launches compiled

Predict before stepping: what does autograd see of a compiled forward? Counts measured on Apple M1 Pro, CPU, torch 2.14.1: 142 ATen calls in one eager forward ({{Inside one step|#t-step}}); 1 graph of 59 operations, 0 breaks, 549 guards, and 35 launches per compiled forward, of which 14 are generated C++ kernels, 17 matrix multiplies in the BLAS library and 4 attention calls; on MPS 191 calls became 62, and the backward went from 295 calls to 60 launches on the CPU ({{Compile lab|#t-comp}}). Compile time 9.0 to 10.0 s with an empty cache.

Fewer launches is not a faster step everywhere. On this CPU the compiled step took 23.20 ms against 22.75 ms eager: most of a CPU step is matrix multiplies, which stay BLAS calls, and a CPU's caches absorb much of the element-wise traffic. On the Apple GPU it was 1.18 times faster. On NVIDIA GPUs, where launches and memory traffic dominate small operations, the PyTorch team reported compile working on 93% of 163 open-source models and training 43% faster on average on an A100 vendor, PyTorch team, 2023 ({{PyTorch 2.x|https://pytorch.org/get-started/pytorch-2-x/}}). What it costs: compile time, recompiles when a guard fails (a new input shape, eval() under no_grad), and graph breaks that leave code eager. torch.export is the whole-graph sibling: one graph or an error, then AOTInductor packages it into a library that runs without Python.

What this page measured and read for this section, in full (optional)

On the CPU the compiled step was about the same: 23.20 ms compiled against 22.75 ms eager. On the CPU most of the step is matrix multiplies, which stay BLAS calls either way, and a CPU's large caches already absorb much of the element-wise traffic. On MPS, a GPU, the same compile gives 1.18 times; with the fused optimizer as well, 1.85 times.

What it costs. Compile time: the first call of the compiled training step took 9.0 to 10.0 s with an empty cache and 0.86 to 1.04 s with a warm one, and every new input shape compiled again for 7.2 to 8.6 s until Dynamo marked the dimension dynamic measured on Apple M1 Pro. Memory: none saved here, AOTAutograd kept 34.81 MB against eager's 34.76 MB. Fragility: a print inside a block split the model into pieces, left the outer forward uncompiled and made the step 7 to 9% slower; switching to model.eval() under no_grad recompiled because a guard checks the grad mode. After recompile_limit (8 at 2.14.1) recompilations of one function, Dynamo gives up and runs it eagerly.

When it matters. On NVIDIA GPUs, where launches and memory traffic dominate small operations: the PyTorch team reported compile working on 93% of 163 open-source models and training 43% faster on average on an A100 (21% in float32, 51% with AMP) vendor, PyTorch team, 2023 ({{PyTorch 2.x|https://pytorch.org/get-started/pytorch-2-x/}}). What transfers from this laptop is everything structural: the graph, guards, breaks, recompiles and the fused kernels' logic. What does not is the speed-up, and mode="reduce-overhead", which records CUDA graphs and does nothing here (CUDA only per its 2.14.1 docstring).

How to check. TORCH_LOGS="graph_breaks,recompiles" first; torch._dynamo.explain(fn)(*args) counts graphs and breaks; fullgraph=True turns the first break into an error; TORCH_LOGS=output_code prints what Inductor wrote; backend="aot_eager" runs Dynamo and AOTAutograd without Inductor, to tell which stage broke numerics.

torch.export and AOTInductor. torch.export is the whole-graph sibling of torch.compile: it must capture one graph with no breaks (an untraceable spot is an error, not a fallback) and produces a portable program for deployment. AOTInductor compiles that program ahead of time into a shared library that runs without Python. The running example's logits path, exported with a dynamic batch dimension, gave 95 operations (329 core ATen operations after decomposition; one of the 95 reads the symbolic batch size, and with static shapes the same export gives 94 and 326, {{torch.compile from the user's side|n:3c65c17b0d0d8123a232d75bd7339ecb}}, section 11) and packaged into a 14.3 MB .pt2 file whose outputs matched eager within 1.3e-6 measured on Apple M1 Pro. ExecuTorch (on-device) and the ONNX exporter build on torch.export; formats are on {{Local and on-device inference|n:3c65c17b0d0d81f7a144fe25d799e811}}, section 3.
