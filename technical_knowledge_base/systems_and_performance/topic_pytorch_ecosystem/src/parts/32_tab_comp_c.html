7. Inductor: the kernels that replace the eager ops

Inductor is the default back end. 9. torch.export and AOTInductor: compile once, run without Python

torch.compile is just-in-time: it compiles inside your Python process and falls back to Python wherever it must. torch.export is the ahead-of-time path: it traces the whole model into one graph or fails (no graph breaks allowed), records the allowed range of every dynamic dimension, and returns an ExportedProgram, a file-able graph plus its weights. AOTInductor then runs Inductor on that graph and writes a shared library, packaged as a .pt2 file that a C++ or Python program loads with no model code at all. For training, torch.compile is the tool; export's job is deployment. torch.onnx.export uses this same exporter by default since 2.9.

10. What carries over to NVIDIA GPUs, and what does not

  • Carries over as is: Dynamo's graph, its guards, the graph breaks and their reasons, the recompile rules and automatic dynamic shapes, AOTAutograd's joint graph and partitioning, and export: all of it happens before any device code exists. On a CUDA tensor you would see the same single graph and the same breaks.
  • Changes: Inductor writes Triton kernels instead of C++ (same fusion groups in spirit, different code), matmuls go to cuBLAS, and SDPA picks a FlashAttention or memory-efficient kernel. How Triton becomes PTX and SASS is on {{The compiler stack|n:3f05c17b0d0d81ddbc00fac9e8a2ff89}} and {{Triton and Gluon|n:3c65c17b0d0d81729d15ed4d1a4461b3}}.
  • Only on CUDA: mode="reduce-overhead" records the compiled step as a CUDA graph and replays it with one launch; the 2.14.1 docstring says "we only reduce overhead for CUDA only graphs which do not mutate inputs". On this CPU it changed nothing ( against ). CUDA graphs are explained on {{Streams, CUDA graphs and multi-GPU|n:3f05c17b0d0d81b19a6acab65c370b75}}. max-autotune on a GPU benchmarks Triton matmul templates; here on the CPU it benchmarked and kept ATen's BLAS for every matmul ().
  • Does not carry over: any speed-up or slow-down above. GPU memory bandwidth, launch overhead and kernel quality differ completely. Published figures, all on NVIDIA A100 and all from the PyTorch team (vendor, not independent): across 163 open-source models, "torch.compile works 93% of time, and the model runs 43% faster in training", 21% at float32 and 51% with AMP ({{PyTorch 2.x page|https://pytorch.org/get-started/pytorch-2-x/}}, read 2026-10-12); the PyTorch 2 paper reports geometric-mean speed-ups of 1.41x for training and 2.27x for inference over 180+ models ({{Ansel et al., ASPLOS 2024|https://docs.pytorch.org/assets/pytorch2-2.pdf}}). Measure your own model; the {{Profiling, benchmarking and correctness|n:3c65c17b0d0d813da895ffee55b0457c}} page covers honest timing.

11. Common mistakes, and interview questions

"Compile is slow, it made my model slower"
Check what you timed. The first call includes compiling ( here); warm up with every shape you will use, then time. Then check whether the model has anything to fuse: a model dominated by matmuls and attention, like this one on a CPU, gains little. Profile both and compare the non-matmul time.
Recompiling every few steps without noticing
A shorter last batch, a varying sequence length, model.eval() with no_grad, a string flag that changes. Each costs a full compile ( here). Run with TORCH_LOGS=recompiles once; it prints the failing guard, as in the table in section 5.
Marking only one input dynamic
Every tensor that shares the dimension is guarded. In section 5, marking only idx still recompiled on targets.
A print, .item() or logging call left inside forward
Each is a graph break, and inside a loop it can leave the whole outer function uncompiled (section 4). Log outside the compiled module, or after the step; use fullgraph=True to be told.
Expecting torch.compile(model) to speed up the optimizer
It compiles the module's forward and backward. The optimizer step is separate: use fused=True (or foreach) or compile the step function.
Comparing compiled and eager outputs bit for bit
Fusion reorders floating-point arithmetic. Here the losses of three training steps differed by up to (section 12) and the add + LayerNorm output by up to ; compare with a tolerance.

Interview questions

What are the stages of torch.compile, and what does each produce?
Dynamo: an FX graph of the forward plus guards, from the bytecode. AOTAutograd: a joint forward and backward graph traced on fake tensors, partitioned into a forward graph and a backward graph with a list of saved tensors. Inductor: fused kernels (Triton or C++) plus a Python or C++ wrapper that calls them and the library matmuls. At run time: check guards, run the wrapper.
What is a guard, and what happens when one fails?
A condition the compiled code assumes (dtype, shape, parameter identity, grad mode, ...), checked before each call. On failure Dynamo compiles again and caches both; a failed shape guard makes that dimension symbolic (automatic dynamic) so later sizes reuse it. Past recompile_limit (8) the function runs eagerly.
Name three causes of graph breaks and how to fix each.
print or logging (move it out, or register it as reorderable logging); .item() or data-dependent if (keep the value as a tensor, use torch.where, or torch.cond; capture_scalar_outputs for .item()); calls into non-PyTorch libraries on real data (do them outside, or wrap as a custom op).
Why does fusion help, and when does it not?
Pointwise and reduction chains are limited by memory traffic; fusing them reads and writes each tensor once instead of once per op (9x fewer bytes for the tanh GELU here). It does not help work that is already one kernel (matmuls, attention, ATen's LayerNorm), and the generated kernel can be slower than a hand-tuned one.
torch.compile versus torch.export: when do you use which?
compile for training and Python serving: just in time, tolerant of breaks, recompiles as needed. export for deployment: one whole graph or an error, explicit dynamic ranges, a serializable program for AOTInductor, ExecuTorch or ONNX.
What do reduce-overhead and max-autotune do?
reduce-overhead: CUDA graphs, removing per-kernel launch cost; needs static shapes and keeps a memory pool; CUDA only. max-autotune: benchmarks generated matmul templates against the library and keeps the fastest (plus CUDA graphs on a GPU); much longer compile.
