Same step, five doors

Start with the idea the whole map rests on. A training step is always the same four things: run the model forward to get a loss, run loss.backward() to get gradients, call optimizer.step() to change the weights, and clear the gradients. A plain PyTorch loop writes those four lines itself. A trainer (Lightning, the Hugging Face Trainer) writes them for you inside its own loop, with callbacks, logging and checkpointing around them. A launcher wrapper (Accelerate) leaves your loop alone and instead swaps your model for the right core class for how you launched the job. None of them has its own maths: the forward still ends in your nn.Module, and the weights still change in torch.optim.

Predict: the same tiny GPT, same seed, same three batches, trained through a plain loop, Lightning 2.6.6, the HF Trainer 5.19.0 and Accelerate 1.15.0. How do the three losses compare?

Common mistake: assuming a wrapper's defaults are the plain loop's
The losses only matched because the run set three things by hand. The HF Trainer's defaults, read from the installed 5.19.0, are ; it also draws batches in a shuffled order. Lightning's defaults () happen to match a plain loop. When a wrapped run and a plain run disagree, compare these defaults before suspecting a bug.

What the stacks teach. The plain loop reaches the model in 5 frames. Lightning takes 31, and the surprise is where: the model's forward runs inside optimizer.step, because Lightning passes a closure (a function that computes the loss and the gradients) to the optimizer and the optimizer calls it, the API L-BFGS needs. The HF Trainer adds 5 frames (train, _inner_training_loop, _run_epoch, training_step, compute_loss). Accelerate on one process adds none: prepare() handed back your own model. On two processes it hands back torch.nn.parallel.DistributedDataParallel, the core class itself, and its forward appears in the stack; after three steps the weights on both ranks were bit-identical, which is DDP's whole contract.
