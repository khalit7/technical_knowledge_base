4. nn.Module, state_dict, optimizers, and a training loop done right

An nn.Module is a Python class that registers its parameters (tensors wrapped in nn.Parameter, which autograd treats as leaves to compute gradients for), its buffers (tensors saved with the model but not trained) and its sub-modules, so model.parameters() can find every weight in the tree. model.train() and model.eval() flip a flag that layers such as dropout read. The running example ties its output layer to its input embedding: head.weight is tok.weight, one Parameter used twice. So model.parameters() yields 52 tensors, but the state_dict (the ordered name-to-tensor dictionary you save and load) has 53 entries, two names for one storage measured here. Tools that walk names rather than objects (exporters, some sharding code) see the weight twice; the {{Compile lab|#t-comp}} found torch.export listing 53 parameter inputs for that reason.

An optimizer holds references to the parameters plus its own state per parameter. AdamW keeps two running averages, so its state is twice the parameters (25.5 MB here). opt.step() updates every parameter from its .grad; opt.zero_grad() clears the gradients (setting them to None by default, set_to_none=True, which frees the memory instead of filling it with zeros). How the update is computed matters more than people expect: PyTorch has a for-loop implementation (a few small operations per parameter tensor), a foreach one (each operation applied to all tensors in one call) and a fused one (one kernel does the whole update). At 2.14.1 foreach is the default only on CUDA-like devices and fused is never the default, so the CPU and MPS use the for-loop ({{_foreach_utils.py L8 to L23|https://github.com/pytorch/pytorch/blob/v2.14.1/torch/utils/_foreach_utils.py#L8-L23}}). Asking for fused=True made the running example's optimizer phase 2.7 times faster on the CPU and 4.1 times on MPS measured on Apple M1 Pro (section 6).

# one training step, done right (device = "cuda", "mps" or "cpu") model.train() opt = torch.optim.AdamW(groups, lr=6e-4, betas=(0.9, 0.95), weight_decay=0.1, fused=True) for step in range(steps): for micro in range(accum): # gradient accumulation x, y = get_batch(cfg, step * accum + micro, device) # seeded: batch k is the same on every run with torch.autocast(device, dtype=torch.bfloat16): # AMP: matmuls in bf16, reductions in fp32 logits, loss = model(x, y) (loss / accum).backward() # gradients add up across micro-batches torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0) opt.step(); sched.step() opt.zero_grad(set_to_none=True)
  • Mixed precision (AMP). torch.autocast is the Autocast key of section 2: it casts the inputs of chosen operators (matrix multiplies, attention) to bfloat16 and leaves precision-sensitive ones (softmax, losses, norms) in float32. The weights and the optimizer stay in float32. With float16 instead of bfloat16 you also need torch.amp.GradScaler, because float16's narrow range lets small gradients underflow to zero; bfloat16 has float32's range and needs no scaler.
  • Gradient accumulation. backward() adds into .grad, so running several micro-batches before step() simulates a bigger batch, as long as each loss is divided by the number of micro-batches. Under DDP (section 7), wrap all but the last micro-batch in model.no_sync() or every micro-batch pays for a gradient all-reduce.
  • Determinism. Seed everything (torch.manual_seed), make the data order a function of the step, and turn on torch.use_deterministic_algorithms(True) when you need bit-identical reruns (some GPU kernels are non-deterministic by default). The running example's batches are seeded by step number, which is what let the {{Ecosystem map|#t-map}} tab show the same three losses, 3.80137, 3.18793, 3.16783, from a plain loop, Lightning 2.6.6, the Hugging Face Trainer 5.19.0 and Accelerate 1.15.0 measured on Apple M1 Pro, CPU.
A framework is a set of defaults
That identical-loss result needed the Trainer's defaults switched off. Out of the box, the Hugging Face Trainer at 5.19.0 clips gradients at max_grad_norm=1.0, uses learning rate 5e-5 with a linear decay schedule, weight decay 0, adamw_torch_fused and seed 42, and shuffles the data; Lightning 2.6.6 does not clip and trains in 32-bit by default read from the installed libraries, Apple M1 Pro ({{Ecosystem map|#t-map}}, "Same step, five doors"). Porting a loop to a framework changes the run unless you set these.
Predict: you accumulate 4 micro-batches but forget to divide each loss by 4. Compared with one batch 4 times as large, the gradient is:
4 times larger, because the mean loss of a big batch is the average of the four micro-batch means, and backward() sums. AdamW nearly hides the error (it divides by a running scale of the gradient), but gradient clipping, SGD and anything that logs gradient norms do not. Divide the loss, or compare gradient norms against a one-batch run.
