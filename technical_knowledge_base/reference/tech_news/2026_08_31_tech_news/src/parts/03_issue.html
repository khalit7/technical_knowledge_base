Drafting a block in one pass: the same 16 tokens, four ways

In speculative decoding a small drafter guesses the next seven tokens and the big target model checks all of them in one pass, keeping the longest correct run plus one token of its own. The output is exactly what the target would have written alone; only the time changes. Play plain decoding first (one target pass per token), then the drafter that writes its guesses one token at a time, then DFlash, which drafts the whole block in one pass but picks each position on its own, then DFlash 2, which keeps several candidates per position and lets a selector trace a path that fits together.

Illustrative scenario: the sentence, the guesses and where each run breaks are invented to show the mechanism. The cost of each cycle is not: it is derived from the card's measured GSM8K throughput at one request at a time (time per verification = tokens per verification / tokens per second), shown below the animation. DFlash (the first version) has no measurement on this model; its cycle is assumed 1% cheaper than DFlash 2's, the selector's overhead in Inco's post.

What the card measured

Output tokens per second for Qwen3.8-27B in SGLang on one H200, each speculative method proposing seven draft tokens per verification. Pick how many requests run at once: the "up to 3.43x" is one request on GSM8K; with 32 requests the GPU is already busy and drafting buys much less.

Sources: {{model card, incoai/Qwen3.8-27B-DFlash2|https://huggingface.co/incoai/Qwen3.8-27B-DFlash2}} (acceptance length and throughput tables; MTP is Qwen3.8's built-in seven-token head, DSpark a community drafter) and {{Inco AI, DFlash 2: Keep Drafting Parallel|https://inco.ai/blog/dflash2/}} (top-16 candidates, the pairwise selector, two-tap convolutions, "around 1% added cycle latency"). MCP with and without sessions: the same requests, before and after 2026-07-28

One agent makes the same calls to an MCP server running as three instances behind a gateway: list the tools, search twice, then call a tool that needs a human's approval. Halfway through, instance A is restarted for a deploy. With sessions (before the 2026-07-28 revision) the client opens a session, is pinned to the instance that holds it, and the gateway has to read each request's body to know what it is. Without sessions each request carries what it needs, any instance can answer it, and the method and tool name travel as headers.

Illustrative scenario: three instances, one restart and these six calls are invented to show the mechanisms. The mechanisms (the initialize handshake and Mcp-Session-Id header, sticky routing, the new Mcp-Method and Mcp-Name headers, and approval as a second request instead of a held connection) are the ones InfoQ's report of the revision describes.

Source: {{InfoQ, "MCP Goes Stateless, and Developers Ask Whether That Just Makes it an API Again"|https://www.infoq.com/news/2026/08/mcp-stateless-gateway/}}.
