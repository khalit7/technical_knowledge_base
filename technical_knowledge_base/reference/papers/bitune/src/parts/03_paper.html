Problem: the prompt is read through a mask meant for generation

[[S1|§1, §2]]

An instruction-tuned model answers in two phases ({{§2|ax:S2}}). Prefilling runs the whole instruction through the model at once and stores, for every token and every block, its key and value vectors (the KV cache; the paper calls them instruction features). Decoding then generates the answer one token at a time, each new token attending to that cache and to the answer so far. The answer is conditional on the instruction from its very first token: p(a|q) = Πi p(ai | a1, ..., ai−1, q).

Decoder-only models apply the causal mask everywhere, prompt included. The mask exists for generation: a token being predicted must not see the future. But when the prompt is prefilled it is already fully available, so masking it throws information away: every prompt token's features are computed from the tokens to its left only. Click a token below to see what it can attend to, in the paper's own prompt template:

The ARC template of {{Appendix A.10|ax:A1.SS10}} filled with the ARC example of {{Appendix A.9|ax:A1.SS9}}; one word per token for readability (a real tokenizer splits finer).

Under the causal mask, which part of this prompt can the first answer token attend to?

All of it: the answer comes after the whole prompt, so the causal mask hides nothing from it. What the mask costs is elsewhere. The answer reads the prompt through its keys and values, and those were computed, block by block, before any prompt token could see the tokens after it: "George" and "warm" were encoded without knowing that the question is about friction, the question was encoded without knowing the choices. The answer can only combine features that were built with half the context. That is the narrower claim the paper tests.

This is a known weakness. Bidirectional encoders were built for it: BERTBASE was sized to match OpenAI's GPT and scored 79.6 against GPT's 75.1 on the GLUE average ({{BERT Table 1|https://arxiv.org/html/1810.04805v2#S3.T1}}), and T5 and BERT both use bidirectional attention over the input ({{§1|ax:S1}}). Work that turns decoder LLMs into text encoders switches the mask off: LLM2Vec enables bidirectional attention as its first step ({{LLM2Vec|https://arxiv.org/abs/2404.05961}}), and NV-Embed removes "the causal attention mask of LLMs during contrastive training" ({{NV-Embed|https://arxiv.org/abs/2405.17428}}). Bitune asks a narrower question: can a pretrained decoder get that benefit for ordinary instruction following, without changing the pretrained model or the way it generates?

Idea: read the prompt twice, mix the two caches, generate as usual

[[S0.F1|Figure 1, Algorithm 1]]

Bitune ({{Figure 1|ax:S0.F1}}, {{Algorithm 1|ax:S2}}):

  1. A causal pass over the prompt, exactly as now: the features the pretrained model was trained to consume.
  2. A bidirectional pass over the same prompt with no mask, so every prompt token sees the whole instruction.
  3. Two sets of weights. The two passes use different weights, so the model can learn to produce and read the two kinds of features differently instead of pushing bidirectional features through weights trained on causal ones.
  4. Mixing. In every block the two sets of keys and values are averaged with learned weights, and the result becomes the KV cache.
  5. Generation is unchanged: strictly causal, with the original weights, reading the mixed cache. The answer tokens' own keys and values are ordinary causal ones.

Here is the whole thing on this page's trained toy (a 3-block decoder, explained {{below|tab:t-read:s-toy}}): the same prompt, prefilled the standard way and then the Bitune way. The grids are the real attention weights of the toy's first block, averaged over its 4 heads; each row is a query token, each column a token it reads.

Method

[[S2|§2, Eq. 1 to 8]]

Two sets of features per block ({{Eq. 1, 2|ax:S2.E1}}): causal Kc = XcWkc, Vc = XcWvc, and bidirectional Kb = XbWkb, Vb = XbWvb. Xc and Xb are each pass's own input to the block: the token embeddings in the first block, then the previous block's output of the same pass. So the two passes run through the whole network side by side; they meet only in the cache. One consequence: in the first block the keys and values are projections of the token embeddings, computed before any attention, so the mask cannot change them there; bidirectional context first reaches the cache in the second block's keys and values (with separate adapters, the first block's still differ by the adapters). Attention is the usual softmax(QKT/√dk + M)V ({{Eq. 3|ax:S2.E3}}) with Mc(i, j) = −∞ for future tokens and Mb = 0 everywhere ({{Eq. 4, 5|ax:S2.E4}}).

KBitune = Kc(1 − αk) + Kb αk,   VBitune = Vc(1 − αv) + Vb αv,   αj = |θj| / (θinit + |θj|)
{{Eqs. 6 to 8|ax:S2.E6}}: a convex combination per block, with one learnable θ for keys and one for values in every block (the authors' code: pass_scale_k, pass_scale_v; {{repository|https://github.com/dkopi/bitune}}). θinit = 0.01 ({{Table 9|ax:A1.T9}}).

Two details of Eq. 8 that the paper leaves implicit (the code initialises θ to θinit, in PassScale, variant 607): α starts at exactly 0.5, an even mix, whatever θinit is, and θinit sets only how fast α can move. Try it:

Which weights are separate. Eqs. 1 and 2 name only the key and value projections, but "the components of the model, other than the key and value projections, can have their own separate sets of weights as well" ({{§2|ax:S2}}), and in the experiments they do: the bidirectional pass runs with its own LoRA adapter on every linear layer of attention and MLP (the code's prefill adapter), the causal pass and the answer with the other (default). With full weights that would mean a second copy of the model, impractical for large models, so the default is LoRA ({{§2, Parameter Efficient Fine-tuning|ax:S2}}); full finetuning with two full weight sets is tested too (Table 7).

Training ({{Algorithm 2|ax:A1.SS1}}): the causal pass and the bidirectional pass over the instruction, the mix, then the answer through the causal weights over the mixed cache; the loss on the answer back-propagates through both caches into both adapters and the θs. Standard instruction tuning does this in one forward pass; Bitune's needs three ({{Limitations|ax:S5}}).

Starting generation. Decoding needs at least one query token after the cache. The paper moves the last token of the instruction template (the ":" of "Answer:") to the start of the answer, rather than adding a new learnable separator ({{§3.1|ax:S3.SS1}}). The mixing runs in 32-bit floating point while the rest is bfloat16, because "minor numerical inaccuracies in the learnable coefficients ... may lead to significant deviations in the model's behavior".

Several turns ({{Appendix A.8|ax:A1.SS8}}, not tested): either recompute the whole history's cache bidirectionally every round, or alternate: prefill each new instruction with both masks and append it, generate with causal features only, repeat.

Experiments

[[S3.SS1|§3.1, Appendix A.2, A.3]]
  • Data. Instruction tuning on a subset of cleaned UltraFeedback: GPT-4's completions only, samples over 512 tokens dropped to fit one GPU, about 10,000 samples ({{§3.1|ax:S3.SS1}}). A second dataset, cleaned Alpaca (50,000 samples), in {{Appendix A.6|ax:A1.SS6}}.
  • Models. Gemma 2B and 7B, Llama2 7B, Llama3 8B, Phi-2 (2.7B), through Hugging Face Transformers; Codestral 22B on GSM8K only ({{Appendix A.7|ax:A1.SS7}}).
  • Baselines. The pretrained model; LoRA rank 8 on every linear layer of attention and MLP (Hugging Face PEFT, alpha 1); and LoRA16, rank 16, which matches Bitune's parameter count because Bitune has two rank-8 adapters.
  • Tuning. The learning rate was tuned for the LoRA baseline over 1e-4, 3e-4, 1e-3, 3e-3 and then reused for every method, which "potentially puts our method at a disadvantage". AdamW, linear schedule, no weight decay, batch 10 (10 accumulation steps), 10% warmup; 3 epochs (3,000 updates) on UltraFeedback; seeds 42, 43, 44 ({{Tables 9 to 12|ax:A1.T9}}).
  • Evaluation. Zero-shot multiple choice with the Language Model Evaluation Harness: each choice's log-likelihood is compared. Commonsense: PIQA, CommonsenseQA (CSQA), ARC-Challenge, SIQA; language understanding: MMLU. Every number is the mean of 3 seeds ({{§3.1|ax:S3.SS1}}).
  • Two more settings. Training separately on each task's training set (adding GSM8K, which needs a generated, step-by-step answer extracted with a regular expression; {{§3.2|ax:S3.SS2}}), and training on chain-of-thought traces distilled from GPT-4.1 for PIQA, ARC, CSQA and GSM8K, so the models generate their reasoning before the answer ({{§3.3|ax:S3.SS3}}). The authors argue the custom format also lowers the risk that gains come from test sets seen in pretraining.

Ablations: which part does the work?

[[S3.SS5|§3.5, Tables 5, 8, 15]]

Four variants, each answering one question ({{§3.5|ax:S3.SS5}}), on Gemma-2B and Llama3-8B:

  • Naive Bidir.: just drop the mask over the prompt; one set of weights, no mixing. This is turning a pretrained decoder into a prefix-LM.
  • No Mixing: only bidirectional features, but from their own weights.
  • Only Causal: two passes and mixing, both causal: is it the second set of weights, not the bidirectionality?
  • Shared Weights: both passes with the same adapter.
The simplest variant, Naive Bidir., just switches the prompt's mask off in a model pretrained with it on. Against plain LoRA on the same data, does it help or hurt?

It helps on UltraFeedback: 45.7 to 47.9 on Gemma-2B and 70.4 to 71.9 on Llama3-8B ({{Table 5|ax:S3.T5}}). Every ablated variant beats LoRA. But it is not robust: on Alpaca, Naive Bidir. scores 66.9 against LoRA's 67.2 on Llama3-8B ({{Table 16|ax:A1.T16}}), while Bitune stays ahead (68.2). The full method wins every comparison, but some by little:

The 5-task averages of {{Table 5|ax:S3.T5}}, with ±1 standard deviation of the average from {{Table 23|ax:A1.T23}} (tasks treated as independent). Bitune's lead over the best ablation is 0.8 points (No Mixing, 1.6 standard errors) on Gemma-2B and 0.4 (Shared Weights, 1.5 standard errors) on Llama3-8B. The toy's panel (axis from 80%): the same variants on this page's toy task, mean ± SD of 3 seeds ({{Run Bitune|tab:t-run}}).

The second pass's mask ({{Table 8|ax:S3.T8}}): causal 46.9 / 71.1, anti-causal (each token sees only what follows it) 46.7 / 71.4, bidirectional 49.7 / 72.7 (Gemma-2B / Llama3-8B). "Combining causal and anti-causal features independently does not lead to the same high performance": each token has to see both sides in the same pass.

The mixing coefficient's start ({{Table 15|ax:A1.T15}}): θinit 0.1, 0.01, 0.001 give 49.4, 49.7, 47.2 on Gemma-2B and 72.7, 72.7, 72.3 on Llama3-8B. Read from the vector data of {{Figures 2 and 3|ax:A1.F2}}, the trained Llama3-8B ends at α ≈ 0.32 on average with θinit 0.01: about two thirds causal, one third bidirectional, every block between 0.06 and 0.55 ({{rebuilt|tab:t-tables:tbFigs}}). The trained model does not abandon its causal features; it adds some bidirectional ones.

Cost

[[S3.SS4|§3.4, Table 4, Appendix A.4]]

Training ({{Table 14|ax:A1.T14}}): 3.1 times the time (1.0 to 3.1 hours on Gemma-2B, 1.7 to 5.3 on Llama3-8B, one A100) and 16% to 33% more peak memory (14.9 to 19.8 GB, 26.6 to 30.8 GB). The implementation runs the two prompt passes one after the other and "has not been optimized".

Inference: the prompt is processed twice, so prefill does two passes' work; the cache that decoding reads is one mixed cache of the usual size, so decoding costs the same. Measured on Gemma-2B with a 2,000-token instruction ({{Table 4|ax:S3.T4}}): prefill 0.03 s against 0.28 s, 9.3 times longer, then 2,000 generated tokens in about 62 s either way.

Bitune's prefill took 9.3 times as long. For that 2,000-token prompt plus 2,000 generated tokens, how much longer is the whole request?

0.6% (62.18 s to 62.56 s). Generation is 31 ms per token, prefill well under a millisecond per token, so the prefill hardly counts, and the paper concludes the extra latency is "negligible". That holds for long answers. Move the sliders to a short answer after a long prompt (classification, retrieval-augmented question answering, a judge) and it stops holding:

Illustrative: a straight-line extension of the one measurement in {{Table 4|ax:S3.T4}} (Gemma-2B, one A100; 0.015 ms per prompt token for LoRA, 0.14 for Bitune, 31.1 ms per generated token, assumed the same for both; measured, Bitune's 2,000 tokens took 62.28 s against 62.15 s). Real prefill cost grows faster than linearly at long context, so long prompts are, if anything, underestimated. Measured, in the v1 paper's appendix: a 200-token prompt with a 50-token answer took 11.5% longer on Gemma-2B and 14.2% on Llama3-8B; a 50-token prompt with a 200-token answer 6.5% and 1.5% ({{v1 Appendix 6.4|https://arxiv.org/html/2405.14862v1#S6.SS4}}; {{all cost tables|tab:t-tables:tbCost}}).

Two more costs follow from the design, though the paper does not discuss them (beyond the paper; our reasoning): a bidirectional prompt cache cannot be shared between requests that start with the same text, because every token's keys and values now depend on what comes after it, so serving engines' prefix caching ({{vLLM's automatic prefix caching|https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/}}) no longer applies to it; and LoRA can usually be merged into the base weights for free serving, while Bitune needs two different weight sets at prefill time, so it keeps one adapter live or holds two merged copies.

A toy where the mechanism is visible

The paper reports benchmark averages; it does not show when bidirectional prompt features should matter. This page's toy is built to make that visible ({{Run Bitune|tab:t-run}} has all of it). 48 people and 32 clubs, with a fixed random membership table. A tiny decoder (3 blocks, width 32, 4 heads, 41,472 parameters) is pretrained causally on two kinds of text: facts stated club first ("chess Ada yes"), and questions asked before the list ("? chess Ada Ben Cy : Ben"). Then it is instruction-tuned, with rank-4 LoRA on every linear layer, on a new template that asks the question after the list, the way a document followed by a question does:

<bos> Ada Ben Cy Dee ? chess  →  : Ben <eos>
Exactly one listed person is in the club. Under the causal mask no person token can see "chess", so the knowledge the model has about each person cannot be applied where that person is read.
Same data, same learning rate (tuned for LoRA, as in the paper), 3 seeds each. Which finetuning reaches the highest held-out accuracy on the question-last template?

How much of this to believe

[[A1.SS11|Tables 1 to 8, Appendix A.4 to A.13]]

What holds up. Every number is the mean of three seeds, and the appendix prints their standard deviations, which most finetuning papers do not ({{Tables 21 to 25|ax:A1.T21}}). Against LoRA, 14 of the 25 task-level gains in Table 1 are more than 2 standard errors, and the 5-task average gains are 2.99 to 7.6 standard errors on four of five models (the tasks treated as independent; {{gains with noise|tab:t-tables:tbGain}}). The baselines are fair or better than fair: LoRA16 matches the parameter count, and the learning rate was tuned for LoRA and reused for Bitune, a disadvantage the authors state. The direction repeats across five models, three settings (instruction tuning, per-task, chain of thought), three PEFT methods, full finetuning, a second dataset and a 22B model. The authors state the training cost themselves (Limitations, Table 14), which counts in their favour.

What is weaker, concretely:

  • model-dependent size From +4.0 (Gemma-2B) to +0.1 (Gemma-7B, 0.22 standard errors, and below LoRA on PIQA and MMLU). The gain shrinks with the stronger models in Table 2 too (+0.1 on Gemma-7B and Llama2-7B). The paper says the effect "depends on the specific model used" but gives no account of why ({{§3.2|ax:S3.SS2}}).
  • components not all shown necessary "each component contributes" rests on gaps of 0.8 (Gemma-2B, No Mixing) and 0.4 (Llama3-8B, Shared Weights) points, 1.6 and 1.5 standard errors, on two models ({{Table 5|ax:S3.T5}}, {{Table 23|ax:A1.T23}}). That Bitune is never worse than its ablations holds; that every part is needed does not follow.
  • cost described as negligible True when answers are long (+0.6%, {{Table 4|ax:S3.T4}}). The v1 appendix measured +11.5% and +14.2% for 200-token prompts with 50-token answers, a table v2 dropped. Training takes 3.1 times as long. One timing measurement per setting.
  • small slips in the text Llama3-8B's "1.8 pp" is against LoRA16 while the other models' numbers are against LoRA (against LoRA it is 2.3); the PEFT range "+1.6% to +4.0%" is +1.0 to +4.0; Gemma-7B is not "a single case" of the pretrained model winning a task (Phi-2 on ARC, 67.3 against 67.2); Figure 2's axis says % but plots fractions ({{all checks|tab:t-tables:tbChecks}}). None changes the conclusion.
  • evaluation by log-likelihood Four of five instruction-tuning tasks are multiple choice scored by comparing the choices' log-likelihoods ({{§3.1|ax:S3.SS1}}): a cleaner probe of the prompt's encoding than of generation. The generative evidence is GSM8K (Tables 2, 3, 17), where the gains are largest.
  • the showcased sample v1's qualitative table showed one GSM8K question where Bitune was right and LoRA wrong. Graded here, the 20 samples of {{Appendix A.13|ax:A1.SS13}} give LoRA 9 and Bitune 10 correct, and that question is the only one where they differ ({{graded|tab:t-tables:tbGsm}}).
  • short prompts only UltraFeedback was cut at 512 tokens and the benchmarks are short; nothing tests long documents, multi-turn chat (A.8 is a proposal) or models above 22B.

Verdict. Believe the direction: reading the prompt bidirectionally, with separate weights, makes instruction-tuned decoders measurably better on short-prompt reasoning and multiple-choice tasks, and the evidence is better controlled than most finetuning papers'. Treat the size as model-dependent and mostly a small-model effect in these experiments, the necessity of every component as unproven, and "negligible" cost as true only when the answer is much longer than the prompt.

What it takes to use this

  • Code. {{dkopi/bitune|https://github.com/dkopi/bitune}}: research code "sufficient to reproduce the results", whose README jokingly strikes through "Spaghetti" in its own overview, with modified Hugging Face model classes for Gemma, Llama and Phi and a patched copy of the evaluation harness, pinned to transformers 4.38.2 and peft 0.11.1. It has no licence file (so no rights to reuse are granted), and "a clean repo for Bitune in the near future", promised since May 2024, has not appeared (checked 3 October 2026).
  • Hardware and time. Everything ran on one A100; budget 3 times your LoRA finetuning time and 16% to 33% more memory ({{Table 14|ax:A1.T14}}). Two adapters, so twice LoRA's trainable parameters.
  • What worked. Models of 2B to 8B parameters, plus Codestral-22B on GSM8K; LoRA, DoRA, IA3 and full finetuning; θinit 0.01 (0.001 hurt Gemma-2B: 47.2 against 49.7). The largest gains were on the smallest model and on generated reasoning (GSM8K).
  • When it pays. Short prompts with longer answers, where the doubled prefill is noise, and models in the 2B range. When it buys little. Gemma-7B-like cases (+0.1), long prompts with short answers (prefill-bound serving), anything that relies on prefix caching, and multi-turn chat until someone tests A.8's schemes.

Why it matters (beyond the paper)

The useful idea is smaller than "bidirectional attention is back": the causal mask over the prompt is a legacy of the generation objective, not a requirement of it, and its cost is measurable after pretraining. Prefix-LMs made the same observation years earlier: introduced by Liu et al. (2018), compared by T5, which found the prefix-LM beat a plain decoder-only model on both its training objectives ({{T5|https://arxiv.org/abs/1910.10683}}; the paper's {{§4|ax:S4}}), used by UniLM's sequence-to-sequence mask ({{UniLM|https://arxiv.org/abs/1905.03197}}) and folded into UL2's mixture of denoisers. Those were all pretraining choices. Bitune's contribution is doing it to an already-pretrained decoder without retraining it, and showing that the bidirectional features need their own weights and a mix with the causal ones: simply converting to a prefix-LM ("Naive Bidir.") gains less and, on Alpaca, can hurt.

The same diagnosis drives a line of work that repurposes decoders: echo embeddings repeat the input so the second copy sees all of the first, with no training ({{Springer et al. 2024|https://arxiv.org/abs/2402.15449}}); LLM2Vec and NV-Embed switch the mask off to make embedding models; Encoder-Decoder Gemma adapts a pretrained decoder into a bidirectional encoder plus a causal decoder ({{Zhang et al. 2025|https://arxiv.org/abs/2504.06225}}; {{KB page|n:3d45c17b0d0d81a9a22ffaada508db5c}}). Caveats: the gains are consistent but not transformational; the two-pass design doubles prompt-processing work, a real cost at long context, while the paper's setting is short instructions. Whether frontier labs use anything like it is not documented in any model card or report we know of (unconfirmed). Read it for the diagnosis more than the recipe.
