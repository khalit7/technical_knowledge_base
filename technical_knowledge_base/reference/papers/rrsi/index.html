Problem: a loop that grades itself on the same tasks

§1 Introduction, §2

An LLM agent's capability is largely magnified by its harness: everything around the frozen weights, meaning the system and task prompts, the control flow that decides when the agent plans, acts, reflects or stops, the tool interfaces, the memory and skill files, and the context management that decides what the model sees at each step (§2). The harness decides whether the same model reads the right file before editing it, recovers from a failed command and writes its findings into the deliverable (§1). Building one is manual work: engineers read failed trajectories and tweak the scaffold, so progress is limited by how many trajectories a person can read.

Recent methods automate that loop. A proposer LLM reads feedback from the current harness's runs, drafts candidate harnesses, the candidates are scored on an evolve set of tasks, and the best one becomes the next incumbent (Eq. 2). Because the system improves the thing that shapes its own behaviour, the paper calls this recursive self-improvement at the agent-system level, and it looks like free capability.

The obvious objection is overfitting, and the paper makes it precise. Each round's candidates depend on scores measured on the same tasks in earlier rounds, so the reuse of the evolve set is adaptive (§2, citing Dwork et al. 2015). The score Ŝ is an average over k stochastic runs per task (Eq. 3), so it is noisy, and taking the maximum of noisy scores round after round selects for luck. The paper names three coupled behaviours that widen the gap between the evolve score and transfer (§1):

  • Benchmark-specific fitting: edits that encode the evolve tasks' names, files or answers.
  • Noise chasing: keeping a candidate because its evaluation happened to come out high.
  • Complexity accumulation: machinery that lifts the evolve score a little and costs more tokens on every task.
Twenty rounds, two candidates a round, and on average every candidate makes the harness slightly worse (as in the released coding run, where the median candidate lost 5 of 178 passes). The loop keeps whichever candidate scores highest. What happens to the evolve-set score?

The same random stream of candidates, run through two selection rules. On the left of each run the harness starts at the coding instance's base score; every candidate's true effect is drawn around the released run's median, and every evaluation adds noise of the size the released run calibrated (a difference of two evaluations has a standard deviation of 3 passes in 178). Switch between the rules: the solid line is the score the loop sees, the dashed line the harness's true quality on new tasks.

Change the toy's assumptions

A benchmark-specific candidate carries an extra gain that exists only on the evolve set (drawn around +1.5 points); the critic removes such a candidate before evaluation with the chosen probability. The noise band choices are 0, the paper's 0.017 and the released run's 0.034. With the workspace instance's score weight, a within-band gain counts again and the rules behave much like "keep the best score", only cheaper.

What the toy shows. Keeping the best score makes the score the loop sees climb faster than the true quality, and the harness grows: noise chasing and complexity accumulation, as the paper describes. RRSI's rules keep the seen score closer to the truth and cut tokens. What it does not show is the paper's transfer advantage: here true quality under RRSI's rules is no better, and with the coding instance's settings it is worse. Two rules cause that. A real gain smaller than the band (3.4 points at the released run's δ) is rejected unless it also saves tokens (ws = 0), and an edit that loses up to the band is accepted if it is cheaper. The released coding run did the second thing too: its incumbent went from 140 to 138 to 136 passes through two cheaper edits (replay). If RRSI transfers better, the reason lies in what the toy leaves out: the proposal-side constraints, and real benchmark-specific edits whose link to cost and complexity the toy cannot know. The toy does not reproduce the effect, and it was not tuned until it did.

Illustrative toy. The selection rules are the paper's (Eq. 5, 7, Eq. 17) with the coding instance's values from the released configuration (β0 0.10, β1 44.5, ws 0, wc 15). Base score 74.2 (Table 3). The noise of one evaluation has a standard deviation of 1.2 points, so a difference of two has 1.7, the released run's own calibration (δ = 0.034 at two standard deviations). The candidate spread (true effect standard deviation 1.8 points; token change median +11%, spread 17%) is fitted to the 37 measured candidates of the released coding run, and the mean true effect (−2.3 points) is set so that under RRSI's rules the median measured change matches that run's −2.8 points (check_sim.mjs). The benchmark-specific share and the critic's catch rate are assumptions; the paper never measures them. Proposal-side regularisation is not modelled. The boxes average 400 seeds.

RRSI's question is how to keep the loop and the open edit space while stopping those three behaviours. It defines the target as transfer: an evolved harness should still help on unseen benchmarks with different task descriptions, tool interfaces or verifiers (§1).

Idea: regularise the search, not the harness

§3.1, Figure 2

RRSI leaves the space of reachable harnesses Ω(H) open: prompts, control flow, configuration, context management, tools, skills, memory and subagents may all be modified, added or removed. What it constrains is the trajectory through that space, on both sides of the loop (§3.1). Method: three proposal rules, four selection rules

§3.2, §3.3, Appendix C

Proposal side

Annealed update sparsity. An unconstrained proposer can bundle many unrelated edits into one candidate; such a candidate can fit more quirks of the current feedback, and a measured change cannot be pinned on any one edit. RRSI caps the number of independently attributable edits per candidate, starting generous and tightening on a cosine schedule (Eq. 4), so a late-stage proposal cannot rewrite the harness wholesale and take credit for the result:

bt = ⌈ bmin + (bmax − bmin) · ½ (1 + cos(πt/T)) ⌉

Round t of a T-round run; the released code iterates t = 0 to T − 1 (schedule.py). In Appendix C.2 this is ‖zt‖0 ≤ bt over a pool of atomic edits redrawn each round.

Evidence-aware credit assignment. Every evaluated candidate's edits are logged with the component they modify, the hypothesis they test, the source diff, the measured score and cost changes, and whether the candidate won its round (Eq. 10). The proposer conditions on this ledger, so a rejected mechanism stays negative evidence and a successful one keeps explicit credit. Bundled edits share one measurement, which is why the shrinking budget makes the ledger more attributable over time (§3.2).

Structured exploration. When the incumbent's score has moved less than the noise band δ over the last w rounds, the run counts as stalled, and mdraft proposal slots are reserved for components the run has never touched (Eq. 13). The component vocabulary is prompt, control flow, config, output plumbing, context management, client tool, skill, memory and subagent (Eq. 12). This plays the role of entropy regularisation without restricting what the harness may contain.

Selection side

Leakage screening. Before any evaluation, a critic (Claude Opus 4.8) reads each candidate's diff and rejects edits that encode task names, entity names, task-specific values, answers or other evolve-benchmark logic, or that add inert machinery. Screening first matters: a leaking candidate never receives the inflated evolve score that would make later rounds build on it (§3.3). The released code pairs a per-domain regex denylist with the LLM review and lets the proposer repair a rejected draft (README). In the released records the critic sent eight first drafts back. Four were leakage: a prompt naming "the seed-0 network in forward.py" from one coding task, two engineering scaffolds with a benchmark task id hard-coded, and one keyed to "the specific toolchain of some tasks in THIS suite". The other four were bookkeeping (an edit declared as one component but implementing another, a placeholder file, an empty diff). Only one candidate in all four runs was rejected outright, for a mislabelled component, not for leakage; one engineering candidate whose first draft hard-coded a task id was repaired and then accepted (replay). The critic's catch rate is never measured.

Stability-aware acceptance. The unchanged base harness is evaluated repeatedly before the run to estimate a noise band δ. A candidate must then score at least the best score seen so far minus that band (Eq. 5):

Ŝ(H′) ≥ S* − δ

The floor is anchored on the running best S*, not on the incumbent, so a chain of small regressions cannot carry the run more than δ below its best.

Cost-aware acceptance. With ΔS the score change and ΔC the relative change in policy tokens per trial (Eq. 6), a candidate whose gain clears the band must satisfy (Eq. 7):

ΔC ≤ β0 + β1 ΔS    when   ΔS > δ

For coding, β0 = 0.10 and β1 = 44.5: every extra pass out of 178 trials buys 25% more tokens (Appendix D.1). A gain of 7 passes (3.9 points) may therefore cost up to 185% more tokens, a generous allowance.

A candidate inside the band (ΔS ≤ δ) is judged by a different, shaped rule that the main text defers to Appendix C.3 (Eq. 17):

ws ΔS − wc ΔC + wn ν > 0

ν counts structural component types (client tool, skill, memory, subagent) the candidate touches that have never been part of a winning edit (Eq. 16). The coding instance sets ws = 0, so a within-band score gain can never by itself admit a coding candidate: it needs a token saving or a new structural mechanism. The paper says the three weights are in Table 5; they are not. The repository's configuration files give them: coding 0 / 15 / 0.5, workspace 1414 / 15 / 0.5, engineering 244 / 2 / 0.5.

Structural pruning. For each component the ledger keeps gt(ℓ), the best measured gain of any edit to it within the last nprune rounds (Eq. 11). Components exercised but with no strictly positive gain in that window become deletion targets that the proposer is told to remove (Eq. 14). Pruning sparsifies the retained harness, as Lasso does a parameter vector, where the edit budget sparsifies each update. The engineering instance adds domain guards: reject a candidate whose valid-output rate falls by more than 0.03 or whose no-submission rate rises by more than 0.02 (Appendix C.3).

Among admissible candidates the highest score wins; if none is admissible the incumbent stays, and S* is updated (Algorithm 2). The hyperparameters of each instance are in Table 5 (rebuilt), chosen "without consulting held-out or OOD benchmarks". The released configuration files say the same values.

Old summary, corrected. It described the pruner as removing edits "too small to matter, too expensive to keep, or made redundant once later edits landed". That is the abstract's wording. In the method, cost is policed by the acceptance rule; the pruner only marks components with no positive measured gain in its window, and the proposer, not the pruner, makes the deletion.

The frozen policy is Claude Opus 4.8 in all three domains; the proposer, the analyst that writes the cross-round failure feedback and the leakage critic are also Claude Opus 4.8. Results: every held-out split improves

§4.2, Figures 1 and 3, Table 1

Across the three domains the evolved harness gains on its evolve suite and, more to the point, on every split it never saw. The evolve-set gains are 6.0 points on Terminal-Bench 2.1, 4.9 on EngDesign and 1.1 on Harvey LAB; SWE-bench Verified gains 1.8 although repository-level bug fixing was never scored; Harvey LAB's held-out 40 tasks gain 2.3; the three out-of-distribution agentic benchmarks gain 3.5 to 4.7 points (7.2% to 13.1% relative); Frontier-Eng gains 4.3 Medal points (24.3% relative). "No held-out split regresses anywhere, which is the failure a memorizing harness produces" (§4.2).

Against prior evolution methods (Table 1), all run from the same H0 on the same evolve split and candidate budget, the ranking inverts once the harness leaves the evolve split. Judge-free grading. Harvey LAB, JobBench and GDPval are judged by language models, so a harness could in principle learn to write the way a judge rewards. The engineering domain closes that route: EngDesign and Frontier-Eng tasks are graded by their own simulators or testbenches, deterministically, and the gains survive there (§4.2). That argument is sound; the engineering out-of-distribution gain rests on 38 scorable tasks, though, and amounts to 2.0 medal credits in all (a Medal Score of 17.7% is 25 thirds of a credit over 47 tasks, 22.0% is 31 thirds).

Ablations, policies and cost

Every run below uses the agentic workspace instance with the main experiment's base harness, policy, evolve split, round count and candidate budget, so arms differ only in the factor under study (§4.3).

Switch off all of RRSI's regularizers and the same loop reaches 92.8 on the Harvey LAB evolve split, against RRSI's 90.5. Out of distribution, unregularised evolution scores:

Table 2; tokens in millions of policy tokens per trial on the evolve split.

Removing either group of regularizers raises the evolve-set score and lowers transfer (Table 2). Without the acceptance constraints the evolve score rises from 90.5 to 91.5, the out-of-distribution average falls from 43.6 to 41.0 and tokens rise by half (3.59M against 2.42M), which the authors read as an unconstrained selector spending its accepted edits "on noise and on context rather than on mechanism". Without the proposal constraints the evolve score is 0.2 higher (the paper says "costs only 0.2 points", but the variant scores more, not less) and the out-of-distribution average 1.7 lower, so steering where the search looks matters even when nothing is rejected. Removing both gives the highest evolve score of any arm, 92.8, and an out-of-distribution average of 40.3, within a point of the unevolved harness, at 3.80M tokens per trial.

Other policies. Run independently with Gemini 3.5 Flash as the frozen policy, the coding search lifts Terminal-Bench 2.1 from 64.6 to 78.7 (+14.1, the abstract's "up to 14.1") and transfers +2.2 to SWE-bench Verified; with Claude Opus 4.8 the numbers are 74.2 to 80.2 and 82.0 to 83.8, with less room near the ceiling (Table 3). The harness evolved with Gemini 3.5 Flash, run unchanged with the smaller Gemini 3.1 Flash Lite that never took part in the search, lifts Terminal-Bench from 11.2 to 14.6, a 30.4% relative gain on a base less than a fifth of the search policy's (Table 4). "A harness is a program, not a set of weights", so a mechanism that helps only the policy it was searched against would be an artifact of that policy.

Cost. No prior method carries a cost constraint, and all four sit in the region RRSI dominates: more policy tokens per trial for a lower out-of-distribution average (Figure 4(a)). AHE is the extreme, 3.82M tokens per trial (58% more than RRSI) for 4.4 points less out of distribution. Trajectories follow the same order: 26.3 steps per trial for RRSI against 27.3 to 34.6 for the prior methods. The paper is candid that no evolved harness is as cheap as H0, at 1.56M tokens and 21.2 steps, "so evolution does buy part of its gain with test-time compute; the budget decides how much" (§4.3).

The three numbers, read together. The old summary read the out-of-distribution gain as "about a third of the in-distribution gain, the honest shape of a generalisation claim", and the token reduction as showing that "the regularisation is not bought with compute". Both need correcting. The 14.1 and the 4.7 come from different policies and domains (Gemini on Terminal-Bench, Opus on JobBench), so their ratio means nothing; within one setting the ratio is above one (Harvey LAB evolve +1.1, out-of-distribution mean +3.9), because RRSI deliberately gives up evolve score. And RRSI's harness still uses 55% more tokens than H0 (2.42M against 1.56M): the regularisation holds compute growth down, it does not remove it, as the paper itself says. The old summary's point stands that a pruner which only removed cheap edits would raise the score by spending more; the cost rule exists so that cannot happen.

What the decisions look like. Table 6 picks four decisions from the released runs. In the first coding round two similar candidates (a bounded pre-completion verification audit plus polling guidance for long jobs) both scored higher: the one with +3.93 points was kept, the one with +1.69 points and +26.1% tokens rejected. In round 8 a candidate that pinned the original task instruction into the completion gate cut tokens by 13.6% but lost 2.81 points and fell below the floor. In engineering round 2 a bounded recovery hint for a recurring "workdir must be an existing directory" error went from 122 to 128 passes of 244 at +1.6% tokens and was kept. All four reproduce exactly from the released records (replay them).

How much of this to believe

Limitations

What holds up.

  • The comparisons are like for like. Every baseline starts from the same H0 with the same policy, evolve split and candidate budget, and every number is measured against H0 in the same window (§4.1, §4.2). The ablations change one group of regularizers at a time.
  • Code and run records are released, which few papers in this line do: the search loop under Apache-2.0, and every round of four runs with candidates, critic verdicts, scores, token counts and diffs. This page replayed them. Algorithm 2 as released reproduces all 37 measured decisions of the coding run and 31 of 32 in the Harvey LAB run (the exception, labelled "lost to peer", is inadmissible under the rule as written; it was not kept either way). The four decisions of Table 6 match the records to the printed digit, the noise bands and cost slopes of Appendix D.1 convert exactly, and Figures 1 and 4 reproduce from Tables 1 and 2 (all checks).
  • The direction is consistent. All six splits outside the evolve sets improve, including the judge-free engineering domain and a policy the search never used. If each sign were a coin flip, six of six would happen one time in 64.
  • The authors state real limitations themselves (Limitations): frozen backbones only, a finite evolve set and several hyperparameters, and the need for broader validation on other architectures, tool ecosystems and longer runs. They also concede that evolution buys part of its gain with test-time compute. Those count in their favour.

What is weaker than the summary suggests.

  • Every arm is a single run with no error bars, and each transfer gain alone is within noise. Using binomial standard errors from the benchmark sizes the paper gives (independent runs; paired evaluation would shrink them by an unreported amount): SWE-bench Verified +1.8 points against a standard error of 2.4, GDPval +3.5 against 5.2, APEX-Agents +3.7 against 3.1, Flash Lite on Terminal-Bench +3.4 against 3.5 (noise table). The six-of-six pattern is the stronger evidence, but it is not unique to RRSI: Meta-Harness also improves all four agentic held-out and out-of-distribution splits in Table 1, by less.
  • The released records disagree with three printed numbers. On Harvey LAB's 40 held-out tasks the record shows the base harness at 3,181 of 3,650 criteria (87.15%; four repeat measurements within one criterion of each other) and the final harness at 3,215 (88.08%): +0.9 points, where Table 1 prints 86.9 to 89.2, +2.3. The final harness logs 2.69M tokens per trial, where Table 2 prints 2.42M. The coding champion logs 144 of 178 passes (80.9%), and Table 3's 80.2 is not a whole number of 178 trials. The paper may have re-measured in a later window; it does not say so. A re-measurement below the logged best is what picking the best of many noisy scores predicts.
  • The released runs do not all follow the method as written. The coding run with Opus used a noise band of 0.034, twice Table 5's 0.017 ("recalibrated from the Opus baseline, z = 2"); under 0.017, four of its 37 decisions would flip, including the accepted round-11 edit (2 passes worse, 14% cheaper) and a rejected round-18 edit 4 passes better. The Gemini coding run, the source of the headline +14.1, is an earlier procedure: 30 iterations in two legs of 15, one candidate each, a 24-task screen before full evaluation, and ties accepted. The engineering run decides with paired t-statistics on a continuous score and a 5% token-saving threshold that the paper does not describe, and in 14 of its 40 rounds the proposer declined to propose anything.
  • Most accepted edits are inside their run's own noise band. Coding: 3 of 5 (the +8-pass final round carries most of the gain); Harvey LAB: 3 of 4 (round 1's +127 criteria is 76% of the +167); engineering: 3 of 4. Those small edits were admitted for saving tokens, for adding a new structural component, or by a within-band score weight. The coding run's last-round +8 passes is 2.6 standard deviations of the run's own calibrated noise, but it was the best of 37 evaluated candidates; the chance that at least one of 37 null candidates would reach it is about 14% (this page's estimate, treating evaluations as independent).
  • Protocol details do not add up. GDPval is described as a majority vote over 185 tasks, but five of the six GDPval scores in Table 1 are not whole numbers of 185, and "204 comparisons per judge" is not 185 tasks in two presentation orders (370). Two APEX-Agents scores (35.7, 34.3) are not whole numbers of the 480 single-rollout tasks. The within-band weights, said to be in Table 5, are only in the code. JobBench's size is not stated, and its judge averages in Claude Opus 4.8, the same model as the policy, proposer and critic.
  • The baselines are the authors' runs of four other methods under RRSI's evaluation budget, and their code is not released, so whether each was run as its authors intended cannot be checked. RRSI's own hyperparameters were set per domain on the evolve sets.
  • Smaller slips: the abstract's "30% fewer policy tokens" is 36% by Table 2 (it matches the released 2.69M, 29%); with the ceiling in Eq. 4, the "final-round" budget bmin = 1 is never reached, so every run's last budget is 2; §4.3 calls the cost rule "the L1-style budget" where §3.3 calls it Ridge-style; "costs only 0.2 points" is a 0.2-point increase.

Verdict. Believe the diagnosis (score-only harness search chases noise and grows the harness) and that RRSI's rules run as described: the released records replay to the same decisions. Believe the direction of the transfer result: six held-out splits all moved up, one of them judge-free. Treat the sizes as provisional: single runs, each gain within about one standard error, most kept edits inside their own noise band, three printed numbers that differ from the authors' own records, and a headline (+14.1) from a run that predates the method as described.

What it takes to use this

§6, Appendix D, repository
  • Code: google-research/rrsi, Apache-2.0, with the loop, the three domain adapters, their starting harnesses, prompts and configuration files, and a README that maps every part of Algorithms 1 and 2 to a file. Not included: the four baselines and the benchmarks themselves (harbor for Terminal-Bench, a pinned Harvey LAB checkout, the EngDesign repository). Run records and champion patches are on the project page.
  • Models: one strong model for the proposer, analyst and critic (Claude Opus 4.8 on Vertex AI in the paper; any LiteLLM model string in the code) besides the frozen policy, plus an LLM judge where the benchmark needs one (Gemini 3.5 Flash for Harvey LAB).
  • Budget: every candidate is evaluated on the whole evolve set, k times per task. From the released records, the policy alone consumed about 4.1 billion tokens in the coding run (37 evaluations of 178 trials), 19 billion in the Harvey LAB run (32 evaluations of 240 trials at about 2.4M tokens each) and 0.9 billion in the engineering run; proposer, analyst, critic and judge tokens come on top (this page's sums of logged tokens per trial times trials).
  • Calibration first: the noise band comes from repeated evaluations of the unchanged base harness, and the released coding run shows the choice matters (0.017 against 0.034 flips four decisions). The cost slopes are set per domain from "how many tokens is one extra pass worth".
  • When it pays: when the evolved harness will be used on tasks other than the evolve suite and per-trial cost matters. When the evolve suite is the deployment, RRSI deliberately gives up evolve-set score (90.5 against 92.8 unregularised on Harvey LAB). It does not touch model weights.

Why it matters (beyond the paper)

Harness evolution loops are multiplying, and each reports a gain on the suite it optimised. HarnessDev found that in its evolution runs the score a creator could see moved with the held-out score in only 34 of 64 version changes. RRSI is a direct answer to that failure: it treats the evolve set as a finite, noisy, reused sample, and it brings the vocabulary of regularisation to a search over programs. Its strongest reusable idea is procedural rather than numeric: separate evolve, held-out and out-of-distribution splits, calibrate a noise band before the run, and make extra tokens pay for themselves.

SoL-Pi runs the same loop for cost rather than capability and finds roughly half of agent token traffic is harness overhead. Between them the loop now has both a cost objective and a generalisation guard, which are the two things a self-modifying system needs before anyone should leave it running. The paper itself claims to be the first to ask whether the gains survive leaving the benchmark; it also cites concurrent work that separates evolution from evaluation tasks for the same reason, such as HarnessCompass, so "first" belongs to the question being asked widely at once.

Connections

  • SoL-Pi: the same loop for cost rather than capability (above).
  • Agora and Dream-RSI differ in where the loop's memory lives (a shared Git history; a replayable search history), and neither measures generalisation. RRSI's memory is its edit ledger, and its released code makes every incumbent a Git commit.
  • Emergence World attacks a system of this shape.
  • NeoHorse-1 pursues recursive self-improvement through the weights, with the harness feeding the curriculum; RRSI keeps the weights frozen.
  • HarnessDev, Prime Agent and JIT-Agent: measuring harness evolution, and two loops of the kind RRSI regularises.

Generalization in Adaptive Data Analysis and Holdout Reuse

Dwork, Feldman, Hardt, Pitassi, Reingold, Roth (2015): The theory behind the paper's worry: every look at the same evaluation set adapts the next choice to it, so scores on a reused set drift above the truth. Its reusable-holdout idea is the formal cousin of RRSI's noise band.

(40 min)

What Evolves When We Talk About Harness Evolution?

Ding, Lu, Yu, Li, Jin, Liu, Durrett (2026): Delta attribution: separates edits that install a reusable mechanism from edits that fit the evolution tasks; the paper cites it as evidence that evolution gains often do not transfer.

HarnessCompass

Zhang et al. (2026), arXiv 2608.01918: Concurrent work that makes generalisation an explicit objective of harness evolution, the alternative to RRSI's regularise-the-search approach.

Agentic Harness Engineering (AHE)

HarnessX

Connected papers in this knowledge base

SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

The same harness-level loop pointed at cost instead of capability: about half of recorded agent token traffic turns out to be harness overhead. RRSI's cost rule is the guard; SoL-Pi is the objective.

Dream-RSI: Recursive Self-Improvement through Evolving Worlds

Keeps the loop's memory as a replayable search history and improves exploration off-policy against it; RRSI keeps an edit ledger and conditions the proposer on it. Neither measures transfer to new benchmarks the way RRSI tries to.

Agora: Git as Shared Memory for Collective AutoResearch

Memory as an append-only Git history that anyone can check out; RRSI's released code also makes every incumbent a commit on an evolve branch.

NeoHorse-1: Towards Recursive Self-Improvement via Agentic Post-Training with Routing Harness

Recursive self-improvement through the weights: the harness feeds a training curriculum. RRSI freezes the weights and changes only the harness, and its Limitations section names weight updates as out of scope.

HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

Measures the failure RRSI tries to prevent: in its evolution runs the score a creator could see moved with the held-out score in only 34 of 64 version changes.

Emergence World: Adversarial Stress-Testing of Long-Horizon Multi-Agent Systems

Attacks long-running agent systems of this shape with prompt injection, misinformation and memory exposure; a self-modifying harness is exactly the kind of system it stress-tests.

Prime Agent: A Self-Improving RLM Harness

A harness that versions its own prompts and skills across trajectories: an unregularised loop of the kind RRSI regularises.

JIT-Agent: Scaling Harness Intelligence via Just-in-Time Harness Evolution

Evolves a harness per task at inference time instead of searching one shared harness offline.
