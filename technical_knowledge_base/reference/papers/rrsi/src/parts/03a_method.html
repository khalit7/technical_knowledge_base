Method: three proposal rules, four selection rules

[[S3.SS2|§3.2, §3.3, Appendix C]]

Proposal side

Annealed update sparsity. An unconstrained proposer can bundle many unrelated edits into one candidate; such a candidate can fit more quirks of the current feedback, and a measured change cannot be pinned on any one edit. RRSI caps the number of independently attributable edits per candidate, starting generous and tightening on a cosine schedule ({{Eq. 4|ax:S3.E4}}), so a late-stage proposal cannot rewrite the harness wholesale and take credit for the result:

bt = ⌈ bmin + (bmax − bmin) · ½ (1 + cos(πt/T)) ⌉

Round t of a T-round run; the released code iterates t = 0 to T − 1 ({{schedule.py|https://github.com/google-research/rrsi}}). In {{Appendix C.2|ax:A3.SS2}} this is ‖zt‖0 ≤ bt over a pool of atomic edits redrawn each round.

Evidence-aware credit assignment. Every evaluated candidate's edits are logged with the component they modify, the hypothesis they test, the source diff, the measured score and cost changes, and whether the candidate won its round ({{Eq. 10|ax:A3.E10}}). The proposer conditions on this ledger, so a rejected mechanism stays negative evidence and a successful one keeps explicit credit. Bundled edits share one measurement, which is why the shrinking budget makes the ledger more attributable over time ({{§3.2|ax:S3.SS2}}).

Structured exploration. When the incumbent's score has moved less than the noise band δ over the last w rounds, the run counts as stalled, and mdraft proposal slots are reserved for components the run has never touched ({{Eq. 13|ax:A3.E13}}). The component vocabulary is prompt, control flow, config, output plumbing, context management, client tool, skill, memory and subagent ({{Eq. 12|ax:A3.E12}}). This plays the role of entropy regularisation without restricting what the harness may contain.

Selection side

Leakage screening. Before any evaluation, a critic (Claude Opus 4.8) reads each candidate's diff and rejects edits that encode task names, entity names, task-specific values, answers or other evolve-benchmark logic, or that add inert machinery. Screening first matters: a leaking candidate never receives the inflated evolve score that would make later rounds build on it ({{§3.3|ax:S3.SS3}}). The released code pairs a per-domain regex denylist with the LLM review and lets the proposer repair a rejected draft ({{README|https://github.com/google-research/rrsi}}). In the released records the critic sent eight first drafts back. Four were leakage: a prompt naming "the seed-0 network in forward.py" from one coding task, two engineering scaffolds with a benchmark task id hard-coded, and one keyed to "the specific toolchain of some tasks in THIS suite". The other four were bookkeeping (an edit declared as one component but implementing another, a placeholder file, an empty diff). Only one candidate in all four runs was rejected outright, for a mislabelled component, not for leakage; one engineering candidate whose first draft hard-coded a task id was repaired and then accepted ({{replay|tab:t-run}}). The critic's catch rate is never measured.

Stability-aware acceptance. The unchanged base harness is evaluated repeatedly before the run to estimate a noise band δ. A candidate must then score at least the best score seen so far minus that band ({{Eq. 5|ax:S3.E5}}):

Ŝ(H′) ≥ S* − δ

The floor is anchored on the running best S*, not on the incumbent, so a chain of small regressions cannot carry the run more than δ below its best.

Cost-aware acceptance. With ΔS the score change and ΔC the relative change in policy tokens per trial ({{Eq. 6|ax:S3.E6}}), a candidate whose gain clears the band must satisfy ({{Eq. 7|ax:S3.E7}}):

ΔC ≤ β0 + β1 ΔS    when   ΔS > δ

For coding, β0 = 0.10 and β1 = 44.5: every extra pass out of 178 trials buys 25% more tokens ({{Appendix D.1|ax:A4.SS1}}). A gain of 7 passes (3.9 points) may therefore cost up to 185% more tokens, a generous allowance.

A candidate inside the band (ΔS ≤ δ) is judged by a different, shaped rule that the main text defers to {{Appendix C.3|ax:A3.SS3}} ({{Eq. 17|ax:A3.E17}}):

ws ΔS − wc ΔC + wn ν > 0

ν counts structural component types (client tool, skill, memory, subagent) the candidate touches that have never been part of a winning edit ({{Eq. 16|ax:A3.E16}}). The coding instance sets ws = 0, so a within-band score gain can never by itself admit a coding candidate: it needs a token saving or a new structural mechanism. The paper says the three weights are in Table 5; they are not. The repository's configuration files give them: coding 0 / 15 / 0.5, workspace 1414 / 15 / 0.5, engineering 244 / 2 / 0.5.

Structural pruning. For each component the ledger keeps gt(ℓ), the best measured gain of any edit to it within the last nprune rounds ({{Eq. 11|ax:A3.E11}}). Components exercised but with no strictly positive gain in that window become deletion targets that the proposer is told to remove ({{Eq. 14|ax:A3.E14}}). Pruning sparsifies the retained harness, as Lasso does a parameter vector, where the edit budget sparsifies each update. The engineering instance adds domain guards: reject a candidate whose valid-output rate falls by more than 0.03 or whose no-submission rate rises by more than 0.02 ({{Appendix C.3|ax:A3.SS3}}).

Among admissible candidates the highest score wins; if none is admissible the incumbent stays, and S* is updated ({{Algorithm 2|ax:A3.SS1}}). The hyperparameters of each instance are in {{Table 5|ax:A4.T5}} ({{rebuilt|tab:t-tables:tb5}}), chosen "without consulting held-out or OOD benchmarks". The released configuration files say the same values.

Old summary, corrected. It described the pruner as removing edits "too small to matter, too expensive to keep, or made redundant once later edits landed". That is the abstract's wording. In the method, cost is policed by the acceptance rule; the pruner only marks components with no positive measured gain in its window, and the proposer, not the pruner, makes the deletion.
