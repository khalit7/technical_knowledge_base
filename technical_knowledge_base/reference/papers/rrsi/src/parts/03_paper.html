Problem: a loop that grades itself on the same tasks

[[S1|§1 Introduction, §2]]

An LLM agent's capability is largely magnified by its harness: everything around the frozen weights, meaning the system and task prompts, the control flow that decides when the agent plans, acts, reflects or stops, the tool interfaces, the memory and skill files, and the context management that decides what the model sees at each step ({{§2|ax:S2}}). The harness decides whether the same model reads the right file before editing it, recovers from a failed command and writes its findings into the deliverable ({{§1|ax:S1}}). Building one is manual work: engineers read failed trajectories and tweak the scaffold, so progress is limited by how many trajectories a person can read.

Recent methods automate that loop. A proposer LLM reads feedback from the current harness's runs, drafts candidate harnesses, the candidates are scored on an evolve set of tasks, and the best one becomes the next incumbent ({{Eq. 2|ax:S2.E2}}). Because the system improves the thing that shapes its own behaviour, the paper calls this recursive self-improvement at the agent-system level, and it looks like free capability.

The obvious objection is overfitting, and the paper makes it precise. Each round's candidates depend on scores measured on the same tasks in earlier rounds, so the reuse of the evolve set is adaptive ({{§2|ax:S2}}, citing {{Dwork et al. 2015|https://arxiv.org/abs/1506.02629}}). The score Ŝ is an average over k stochastic runs per task ({{Eq. 3|ax:S2.E3}}), so it is noisy, and taking the maximum of noisy scores round after round selects for luck. The paper names three coupled behaviours that widen the gap between the evolve score and transfer ({{§1|ax:S1}}):

  • Benchmark-specific fitting: edits that encode the evolve tasks' names, files or answers.
  • Noise chasing: keeping a candidate because its evaluation happened to come out high.
  • Complexity accumulation: machinery that lifts the evolve score a little and costs more tokens on every task.
Twenty rounds, two candidates a round, and on average every candidate makes the harness slightly worse (as in the released coding run, where the median candidate lost 5 of 178 passes). The loop keeps whichever candidate scores highest. What happens to the evolve-set score?

Change the toy's assumptions

A benchmark-specific candidate carries an extra gain that exists only on the evolve set (drawn around +1.5 points); the critic removes such a candidate before evaluation with the chosen probability. The noise band choices are 0, the paper's 0.017 and the released run's 0.034. With the workspace instance's score weight, a within-band gain counts again and the rules behave much like "keep the best score", only cheaper.

What the toy shows. Keeping the best score makes the score the loop sees climb faster than the true quality, and the harness grows: noise chasing and complexity accumulation, as the paper describes. RRSI's rules keep the seen score closer to the truth and cut tokens. What it does not show is the paper's transfer advantage: here true quality under RRSI's rules is no better, and with the coding instance's settings it is worse. Two rules cause that. A real gain smaller than the band (3.4 points at the released run's δ) is rejected unless it also saves tokens (ws = 0), and an edit that loses up to the band is accepted if it is cheaper. The released coding run did the second thing too: its incumbent went from 140 to 138 to 136 passes through two cheaper edits ({{replay|tab:t-run}}). If RRSI transfers better, the reason lies in what the toy leaves out: the proposal-side constraints, and real benchmark-specific edits whose link to cost and complexity the toy cannot know. The toy does not reproduce the effect, and it was not tuned until it did.

Illustrative toy. The selection rules are the paper's ({{Eq. 5, 7|ax:S3.SS3}}, {{Eq. 17|ax:A3.E17}}) with the coding instance's values from the released configuration (β0 0.10, β1 44.5, ws 0, wc 15). Base score 74.2 (Table 3). The noise of one evaluation has a standard deviation of 1.2 points, so a difference of two has 1.7, the released run's own calibration (δ = 0.034 at two standard deviations). The candidate spread (true effect standard deviation 1.8 points; token change median +11%, spread 17%) is fitted to the 37 measured candidates of the released coding run, and the mean true effect (−2.3 points) is set so that under RRSI's rules the median measured change matches that run's −2.8 points (check_sim.mjs). The benchmark-specific share and the critic's catch rate are assumptions; the paper never measures them. Proposal-side regularisation is not modelled. The boxes average 400 seeds.

RRSI's question is how to keep the loop and the open edit space while stopping those three behaviours. It defines the target as transfer: an evolved harness should still help on unseen benchmarks with different task descriptions, tool interfaces or verifiers ({{§1|ax:S1}}).

Idea: regularise the search, not the harness

[[S3.SS1|§3.1, Figure 2]]

RRSI leaves the space of reachable harnesses Ω(H) open: prompts, control flow, configuration, context management, tools, skills, memory and subagents may all be modified, added or removed. What it constrains is the trajectory through that space, on both sides of the loop ({{§3.1|ax:S3.SS1}}). The paper borrows the language of classical regularisation and is careful to call each one an analogy, not an optimised penalty ({{Appendix C|ax:A3}}):
