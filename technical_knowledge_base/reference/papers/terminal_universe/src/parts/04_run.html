Replay a real trajectory

Stage 1 of the paper, deterministic replay, run in your browser on real trajectories from its largest source corpus, {{LFM2-Terminal-SFT-Processed|https://huggingface.co/datasets/gyung/LFM2-Terminal-SFT-Processed}} (139,841 rows, the count in {{Table 12|ax:A1.T12}}; 96% of the paper's sufficient terminal environments come from it). The rule is the paper's ({{§3.1|ax:S3.SS1}}, {{Appendix B.1|ax:A2.SS1}}): keep each pre-existing file at its earliest observed version, leave out files the agent created, store the agent's changes separately. The paper's code is not released, so the mapping from shell commands to reads, writes and edits is ours, described below.

Try: pick a trace, press play and watch which commands reveal files. Then switch to Replay to the last version: the same trace, but keeping every file as it ended. That workspace contains the agent's answer, which is why the paper replays to the earliest version.

How this replay maps a terminal onto reads and writes


The paper's sources record file operations differently and are "normalized into an ordered event stream" ({{Appendix B.1|ax:A2.SS1}}). LFM2-Terminal rows are Terminus-2 sessions: the agent types keystrokes, the terminal prints a screen. Our mapping:


    

  • Read: cat F (full), head or tail (partial), with the content taken from the screen under the echoed prompt.
    • 

  • Write: a heredoc cat > F << EOF (content known from the keystrokes), or any redirect > F (content unknown); edit: sed -i.
    • 

  • Pre-existing: a read before the agent's first state-changing command, or of a path an ls or find listed before that point and the agent never wrote. Anything first seen later might be the agent's output (a script it ran wrote it), so it is held back.
    • 

  • Seed filter ({{§4.1|ax:S4.SS1}}): at least 5 files and 100 lines in the workspace visible at the end (pre-existing, listed and agent-written files).
    • 



How close it comes to the authors' replay: among traces that pass the seed filter, our median replayed workspace has 2 files, as in {{Table 13|ax:A1.T13}} (mean 2.5 against 2.9), but fewer lines (median 27.5 against 60), and slightly fewer traces pass the filter (28.4% of our sample against 32.9% of LFM2-Terminal yielding an environment, {{Table 12|ax:A1.T12}}). Close, not identical: our mapping misses reads done through pipes, editors or scripts. The picture is the paper's: a command-line trace exposes very little of its workspace, and the completion agent writes most of each environment.
