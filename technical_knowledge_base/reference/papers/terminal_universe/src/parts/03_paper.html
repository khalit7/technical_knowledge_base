Problem: plenty of trajectories, few environments

[[S1|§1 Introduction]]

A trajectory is the record of one agent run: the user's request, the agent's commands and file edits, and what the terminal printed back. An environment is the place the run happened: a container with the project's files and dependencies installed, in which commands really succeed or fail. Terminal-based code agents now produce trajectories in bulk, but runnable environments are still scarce and mostly built by hand ({{§1|ax:S1}}).

The two are not equally useful for post-training ({{abstract and §1|ax:S1}}):

  • A trajectory is one frozen demonstration. Its quality is capped by the model that produced it, and nobody can check whether the changes it made were correct.
  • An environment can be re-queried: the same workspace can be given to a stronger model, the result checked by tests of our own, and harder tasks posed on it.

Expert benchmarks show what a good environment looks like: Terminal-Bench pairs every task with a custom container, an instruction and an executable verifier ({{Merrill et al., 2026|https://arxiv.org/abs/2601.11868}}). That reliability is bought with manual effort, which also caps how many such tasks exist. The paper's goal is realistic, verifiable environments at training scale.

Three existing routes ({{§1|ax:S1}}, {{§2|ax:S2}}):

  • Repository history (SWE-Gym, R2E-Gym): roll a repository back to just before a past fix; the bug report is the task, the fix's tests the check.
  • Perturbation (SWE-smith, CLI-Gym): inject a bug into a working repository. Many tasks from few repositories, but every task is a repair.
  • Task-conditioned synthesis (Endless Terminals, TMax, CLI-Universe, SkillSynth; SETA for RL): generate task and environment together. Coverage is controllable, but the workspace is tied to no real project and tends to be "small and tidy".

All of them either start from an existing environment or generate one alongside a new task. Trajectories, as observations of the environments they ran in, are the resource nobody used. {{Table 1|ax:S1.T1}} sets the paper against eight recent pipelines; it is the only one with multi-round and cross-workspace tasks (rebuilt in the {{tables tab|tab:t-tables:tbT1}}).

Idea: run the arrow backwards

A trajectory and an environment are "two views of the same episode". Step 1: rebuild the workspace

[[S3.SS1|§3.1, Appendix B]]

From a trajectory τ the pipeline recovers a workspace Ê that approximates the environment E the trace ran in. The recovery is lossy by nature: files the agent never opened, implicit system dependencies and network resources leave no trace. So it runs in three stages ({{§3.1|ax:S3.SS1}}):

  1. Deterministic replay. Process the trace's reads, writes and edits in order and keep, for every path, the earliest and latest contents it shows. The initial workspace Ê0 holds each pre-existing file at its earliest version, before the agent's first change. Files the agent created are left out, and the agent's changes are stored separately for later checking. Because the trace only shows the paths the agent touched, and sometimes only part of a file or a truncated terminal, Ê0 is partial ({{Appendix B.1|ax:A2.SS1}}).
  2. Agentic completion. A completion agent gets the recovered task, the partial workspace and its file list, and must make the task "solvable, but NOT solved": create missing files, complete partial ones, configure dependencies, without implementing the requested change, adding tests for it or hinting where the fix goes. Network access and installs are allowed only to restore the existing project's dependencies ({{the completion prompt|ax:A2.SS1}}).
  3. Environment filtering. An agentic judge with read-only shell and file tools labels each completed workspace sufficient or insufficient for its recovered task: do its source, configuration, data and structure give a capable agent enough context to work? It judges available context, not whether anything builds; dependencies, caches and generated outputs may be missing ({{Appendix B.2|ax:A2.SS2}}).

Everything runs in a standard ubuntu:24.04 container with network access, cheaper than repository-specific images at "a modest reduction in resolve rate reported by prior work" ({{§3.1|ax:S3.SS1}}). Projects go under /app; files accessed elsewhere are stored separately.

What replay looks like on a real trace
The paper's replay framework is not released. The {{Replay a real trajectory|tab:t-run}} tab re-implements the stated rule for the paper's largest source, and runs it in your browser on five real trajectories: which command revealed which file, why the agent's own outputs are held back, and how little a command-line trace exposes. On 640 sampled trajectories, our replay recovers a median of one pre-existing file per trace, two among those that pass the paper's seed filter (Table 13 also reports two).

How much completion adds. Replay alone gives tiny workspaces, because the solution files the original run produced are withheld. Completion grows them several times over ({{Table 13|ax:A1.T13}}, {{Figure 4|ax:S4.F4}}):

Means, with medians in the labels, from {{Table 13|ax:A1.T13}}. The multipliers are Figure 4's printed labels and reproduce from the table's means (recompute.py). For the terminal pool, 87% of the completed workspace's files, and 98% of its text lines on average, were written by the completion agent rather than recovered from the trace (derived: 1 − 2.9/22.4 and 1 − 90/5,761).

Is the completion honest? Of 30 random terminal completions the authors inspected, 22 added only task-relevant support files, eight added substantial unneeded code, and none contained a solution ({{Appendix B.1|ax:A2.SS1}}).

How much it keeps. Before completion, the judge finds 40.2% of terminal workspaces and 20.1% of SWE repositories sufficient; after completion, 93.5% and 77.1% ({{Table 2|ax:S4.T2}}). Sufficiency reflects how much project context a trace exposed: completion can add common project files around observed evidence "but cannot recover unseen project-specific content". Insufficient workspaces lack source files, task scripts, input data or configuration ({{Appendix B.3|ax:A2.SS3}}); per-source rates range from 95.2% (LFM2-Terminal) to 40.0% (SWE-Gym, 2 of 5) ({{Table 14|ax:A2.T14}}, {{rebuilt|tab:t-tables:tbSrc}}).

Step 2: re-query the environment

[[S3.SS2|§3.2, Appendix C]]

"While reconstruction yields executable environments, re-querying dictates how effectively their latent capability space is exploited." Four mechanisms, each with an observable goal and the implementation left to the agent ({{§3.2|ax:S3.SS2}}, {{Appendix C|ax:A3}}):

Intent Recovery

Rebuild the source task as one self-contained request. A single-round trace's sole substantive request is the task; in a multi-round trace the first substantive request sets the topic and later ones count only if they clarify, constrain or extend it. Agent actions and file evidence help interpret the requests, but only requirements the user stated are kept, and vague wording is not replaced by values inferred from the agent's actions. Output: a 2 to 4 sentence core_objective plus metadata ({{Appendix C.1|ax:A3.SS1}}).

Single-WS (new tasks in one workspace)

A read-only generator explores the workspace (no network, no edits) and proposes five tasks in the "ideal zone: clear goal + verifiable standard + unexplored implementation", internally drafting ten and keeping five with different focuses; one valid candidate per environment is rolled out ({{Appendix C.2|ax:A3.SS2}}). MirrorBrain's five: shell-event normalisation, URL classification, client error handling, response-schema alignment and cache-source reconciliation ({{Appendix E.1|ax:A5.SS1}}).

Cross-WS (breadth)

Profile every workspace (domain, language, capabilities); retrieve neighbours by TF-IDF within a language group; an LLM labels each pair similar, complementary, dependency or unrelated. A dependency pair, where a target lacks a capability a reference has, gets exactly one task. The reference is mounted read-only; the task must rely on at least three facts found only in it, may name only its mount root, must name target files and executable checks, and must be solvable offline. No workspace appears in two pairs ({{§3.2|ax:S3.SS2}}, {{Appendix C.3|ax:A3.SS3}}).

Multi-Round (depth)

After the agent answers an initial query, a user agent continues the session in the same workspace, keeping a requirement tracker of active, satisfied and updated requirements. Each round a verifier writes acceptance tests first; the user agent reads the private results and turns any failure into a natural complaint, never mentioning tests or tracebacks. Up to six follow-ups, or until it emits a stop ({{§3.2|ax:S3.SS2}}, {{Appendix C.4|ax:A3.SS4}}).

A cross-workspace example ({{Appendix E.2|ax:A5.SS2}}): two C toolkits for RSA; the target has key generation, encryption and signing but no decryption, the reference has the round trip. The task asks for rsa_decrypt.c in the target whose output is byte-for-byte the original plaintext, naming only the reference's mount root; the private-key loader, decrypt call, padding mode and input paths must be found there. The verifier checks compilation, round trips and OpenSSL calls, and that the reference is unchanged.

A multi-round example ({{Table 18|ax:A5.T18}}, {{Figure 8|ax:A5.F8}}). Step through the user agent's requests in a sensor-ingestion session. The style of each request follows from the last round's private verdict: extension after a pass, revision after a failure, conflict only when the requirement-change policy permits it.

Across retained records the styles split 62.7% extension, 29.3% revision and 8.0% conflict, with no target ratio imposed ({{Table 17|ax:A5.T17}}). The authors report that the 3,079 retained records average 4.51 rounds and that 69.6% contain a failure the session later repairs ({{§3.2|ax:S3.SS2}}). Figure 3 shows how 4,563 generated sessions break down:

Shares printed on {{Figure 3|ax:S3.F3}}, matched to its legend by colour (decode_figs.py). The kept shapes add to 76.4%, about 3,486 sessions, against the 3,079 records the text reports: 407 sessions are unaccounted for (perhaps Appendix F's length filtering; the paper does not say). With only 23.7% of sessions in the two "recovered" shapes, the 69.6% figure requires most trailing-failure sessions to contain an earlier repair too; the figure cannot confirm that.

Step 3: verify, solve, select

[[S3.SS3|§3.3, Appendix D]]
  • Verifier. For every Single-WS and Cross-WS task, a verifier agent inside the container writes one self-contained pytest file before any solution exists, seeing the task and the initial workspace only. Rules ({{Appendix D|ax:A4}}): public interfaces only, absolute paths, no network, no writes under /app, no skips or xfails, at most 18 tests (1 to 3 per requirement), expected values for new behaviour computed independently and never by running the incomplete code. It must run the suite on the untouched workspace: at least one test for the missing capability must fail, preservation tests must pass, and there must be no collection errors; otherwise it rejects the task.
  • Solution rollout. Every model-driven component, completion, judging, generation, verifiers and solving, uses one teacher, Qwen3.7-Max at "xhigh" effort. Solutions are rolled out in the Claude Code scaffold inside the task container: temperature 1.0, top-p 0.95, interleaved thinking, 256k context, turns capped at 65,536 tokens, summarisation at 176k tokens, at most 500 turns and four hours ({{§3.3|ax:S3.SS3}}).
  • Selection. Single-WS and Cross-WS trajectories are kept only if all tests pass on the final workspace. Multi-Round is selected per round: trailing failed rounds are trimmed and a session is kept only with at least two verified passing rounds; failures followed by recovery stay in, as supervision for diagnosis and repair. Intent Recovery is not verifier-filtered, to stay comparable with training on the source trajectories ({{§3.3|ax:S3.SS3}}, {{Appendix D|ax:A4}}).

The data, at scale

[[S4|§4, Appendices A and F]]

Seeds. Raw trajectories come from terminal and software-engineering corpora. A trace is a viable seed if the workspace visible at its end has at least 5 files and 100 lines; all Terminal-Bench-derived sources are excluded, as are sources dominated by view-only operations or unsupported action formats ({{§4.1|ax:S4.SS1}}, {{Appendix A|ax:A1}}). Multi-file editing traces reveal enough to rebuild; "command-heavy CLI traces often expose few file contents". SWE corpora are deduplicated by repository, base commit and problem statement (keeping the trace whose replay exposes most), and SWE-bench Verified repositories are removed.

Sources ({{Table 12|ax:A1.T12}}): four SWE corpora (SWE-rebench, SWE-smith, CoderForge, SWE-Gym) and two terminal ones (LFM2-Terminal, LiteCoder-Terminal), 359,593 trajectories, 68,263 reconstructed environments. After contamination filtering and repository-level deduplication, 38,294 terminal and 1,900 SWE workspaces reach the judge (one representative reconstruction per SWE repository), and 37,273 are task-sufficient ({{§4.2|ax:S4.SS2}}).

Composition of the terminal pool ({{Figure 5|ax:S4.F5}}): Python is the primary language of 84.7% of workspaces (C++ 7.1%, C 3.1%, Shell 2.0%); data processing (47.4%), DevOps (18.9%) and security (14.6%) together make 80.9% of domains.

The SFT corpus ({{§4.3|ax:S4.SS3}}, {{Table 19|ax:A6.T19}}): verifier-filtered Single-WS (25,386), Cross-WS (3,512) and Multi-Round (3,079) trajectories make the 31,977-record Full Mixture, about 1.42B training tokens. Median records: Single-WS 14 turns, 20 tool calls, 30.4k tokens; Cross-WS 23, 38, 46.5k; Multi-Round 92, 102, 126.1k. Intent Recovery (35,809 records; 12, 17, 36.1k) is used only in ablations.

Re-solving beats imitating ({{§6.1|ax:S6.SS1}}, {{Table 4|ax:S6.T4}}). Same volume (35.8k), same chat template and tool-call schema. Training on the source trajectories averages 36.7 across the two scaffolds; Intent Recovery, the same tasks re-solved by the teacher in reconstructed workspaces, averages 52.1; the untrained base is 47.0. The paper reads this as "regenerating demonstrations under a consistent teacher policy provides more effective supervision". It does not discuss that imitation lands below the base, by 5.9 points under Terminus2-XML and 14.8 under Claude Code. The comparison changes two things at once: the environment and the demonstrator (source agents such as DeepSeek-V3.2 against Qwen3.7-Max). It shows the teacher re-solving is worth it; it does not separate how much is the environment.

Completion helps ({{§6.2|ax:S6.SS2}}, {{Table 5|ax:S6.T5}}). Training on Intent Recovery in replay-only workspaces gives 48.7 ± 3.5; in completed workspaces 52.9 ± 1.4 (+4.2, about 2.7 standard errors). Even replay-only beats the base (+2.5, within noise): faced with an incomplete workspace, the teacher often repairs missing files or setup first, so part of the supervision teaches repairing the workspace rather than the task.

The verifier matters for hard tasks ({{§6.3|ax:S6.SS3}}, {{Table 6|ax:S6.T6}}). Single-WS: all 35.1k teacher trajectories 56.0, the 25.4k that passed 56.4 (+0.4, noise). Cross-WS: all 7.1k 53.2, the 3.5k that passed 55.4 (+2.2, about 1.6 standard errors) with half the data.

Breadth ({{§6.4|ax:S6.SS4}}, {{Tables 7 and 8|ax:S6.T7}}). Cross-WS alone (3.5k records) reaches 55.4; adding it to Single-WS lifts 56.4 to 58.4 (+2.0, about 1.5 standard errors). Cross-WS trajectories are longer (median 23 turns, 38 tool calls, 46.5k tokens, against 14, 20 and 30.4k) and harder: the teacher passes 49.2% against 72.3%. By category ({{Figure 6|ax:S6.F6}}), software engineering, the largest (26 tasks), rises from 46.9 to 49.1; model training +15.0 and debugging +10.0 on 4 and 5 tasks; three categories fall 2.1 to 2.5, "within run-to-run variation for categories of at most eight tasks".

How much of this to believe

What holds up.

  • The headline over the base model. +11.9 on TB2.1 is about 5 standard errors even if the trained model is as noisy as the base (spread 3.9 over six runs; the Full Mixture's own spread is not printed), and both scaffolds move by similar amounts (+11.9 and +10.4). EvoCode MT@4 triples, though from a tiny base (6.3) on 26 tasks.
  • Re-solving beats imitating by 12.6 points under Terminus2-XML, about 12 standard errors ({{Table 4|ax:S6.T4}}). Whatever its cause, it is not noise.
  • The bookkeeping is clean. Every count in the funnel sums, the sufficiency rates reproduce from the per-source table, the corpus adds up to 31,977, and Figure 4's multipliers and Table 8's ratios reproduce from the printed tables (61 checks in the {{tables tab|tab:t-tables:tbChecks}}).
  • The authors state real limits ({{§7|ax:S7}}): generic Ubuntu containers instead of per-repository images, so projects that need special system dependencies or builds lose fidelity; coverage bounded by the source trajectories; one teacher writes tasks, solutions and tests, so its mistakes in a solution can be missed by its own tests. Those count in the paper's favour.

What to discount.

  • Most component effects are within noise. Each ablation is one training run evaluated six (or four) times; no training seed is repeated. Of the paper's component claims, completion (+4.2, z ≈ 2.7) and the Multi-Round Case score (+5.0, z ≈ 2.7) are the clearest; the verifier on Single-WS (+0.4), Cross-WS (+2.0), the verifier on Cross-WS (+2.2), environment against query expansion (+2.2) and SWE transfer under Terminus2-XML (+3.2) are all at or under 2 standard errors. The {{noise table|tab:t-tables:tbNoise}} computes each.
  • The parts do not add up. The Full Mixture is no better than its parts: 58.1 on TB2.1 against 58.4 for Single-WS + Cross-WS, and 20.1 MT@4 against 21.0 for Single-WS + Multi-Round ({{Tables 3, 7, 9|ax:S6.T9}}). So each axis helps its own benchmark at best, and the headline is mostly Single-WS re-solving.
  • Distillation is doing much of the work. Every task, workspace completion, verifier and solution comes from Qwen3.7-Max, which itself scores 74.5. The paper never trains on teacher re-solves in environments built some other way, so the share of the gain owed to trajectory-reconstructed environments, as opposed to a strong teacher solving many verified tasks, is not measured.
  • Table 3 is not like for like. Base models differ (Qwen2.5-Coder-32B to Qwen3-235B), scaffolds differ (Terminus2, BashAgent, OpenHands, Vanillux2Agent, CalibForge-Eval), and most TB2.0 numbers are copied from other reports. The authors' own reproductions ran the baselines with 32k to 131k context and 8,192-token turns, against 256k and 65,536 here ({{Table 20|ax:A7.T20}}). The two same-base rows (RST-27B, FACET-27B) are each on a different TB version and from their own reports.
  • "Environment" means judged sufficient, not shown runnable. The judge "evaluates available project context rather than build success" ({{Appendix B.2|ax:A2.SS2}}), and on average 87% of a terminal workspace's files were written by the completion agent. Only 30 completions were inspected by hand.
  • The sources are narrower than "agent trajectories" suggests. 96.3% of the sufficient terminal environments come from one corpus, LFM2-Terminal ({{Table 14|ax:A2.T14}}). Every one of 640 rows we sampled from it is a Terminus-2 rollout by DeepSeek-V3.2 on a generated task family (data processing, file operations, scientific computing and the like), not a record of real development work. The {{replay tab|tab:t-run}} shows them.
  • Small inconsistencies. Figure 3's kept shapes imply about 3,486 retained Multi-Round sessions against 3,079 in the text; three of 19 printed TB2.1 scores (46.2, 52.9, 53.8) are not a whole number of trials out of 534 (89 tasks × 6 runs), and most of Figure 6's per-category changes are not whole task-runs, so some trials are evidently dropped or weighted in a way the paper does not describe. Decontamination is described against Terminal-Bench only, not EvoCode-Bench.

Verdict. The idea is sound and the main comparison is decisive: rebuild environments from traces and let a strong teacher re-solve tasks in them, and a 27B model gains about 12 points on TB2.1. Which of the paper's many design choices matter is mostly not established at this sample size, and the gain should be read as "teacher distillation over trajectory-derived, model-completed workspaces", not as proof that trajectories alone supply realistic environments.

What it takes to use this

  • Nothing is released: no code, environments, SFT data or model (checked 3 October 2026). The source corpora are public with permissive licences as listed in {{Table 12|ax:A1.T12}} (CC-BY-4.0, MIT, Apache-2.0; LFM2-Terminal's Hugging Face card itself states no licence). The prompts for every agent are printed in Appendices B to D, which is enough to rebuild the pipeline.
  • Replay is the cheap part. For keystroke-style traces, the stated rule fits in about 150 lines (this page's replay.py, run live in the {{replay tab|tab:t-run}}). Traces that use explicit Read, Write and Edit tools, as Claude Code-style agents do, expose far more files.
  • The expensive part is the teacher. One strong model at maximum effort does completion, judging, task generation, pair mining, verifier writing and every rollout (up to 500 turns or four hours each, in a container with network). The paper gives no compute or cost figures.
  • Training: 1.42B tokens, two epochs of SFT on a 27B model at 256k sequence length. Only SFT was tested; using the verified environments for RL is the obvious next step but is not in the paper.
  • When it pays. When you hold many trajectories with rich file evidence (multi-file editing, long tool chains; the authors report richer sources give richer environments) and a teacher clearly stronger than your student. It buys little from command-heavy CLI traces (two thirds of LFM2-Terminal's 139,841 traces yielded no environment), and the environment count, not queries or solutions per environment, is what the paper's own scaling ablation favours.

Why it matters (beyond the paper)

This is environment scarcity solved by recycling rather than by construction. If it works on real usage logs, the supply of environments grows with deployed agent usage instead of human authoring effort. It also names a loop: agents produce trajectories, trajectories produce environments, environments train better agents, a data flywheel for agentic post-training of the kind pretraining had with web crawl. The authors add two ways it scales: richer source trajectories expose more workspace, and several sessions on the same workspace can be replayed together into one larger reconstruction ({{§7|ax:S7}}).

The open risk is distributional: environments rebuilt from trajectories inherit whatever the recorded agents were doing, so the flywheel can narrow rather than broaden if the pool is dominated by a few harnesses and task types. The paper itself names this limit (coverage "fundamentally bounded by the coverage of the collected source trajectories", {{§7|ax:S7}}), and its own data shows it: 84.7% Python, 47.4% data processing ({{Figure 5|ax:S4.F5}}), and one agent, one model and generated tasks behind 96% of the terminal environments. The stronger version of this paper would run the pipeline on real, diverse developer sessions.

The practitioner view points the same way: the {{Mercor and SkyRL 397B RL training guide|https://www.mercor.com/blog/training-frontier-knowledge-work-agents-a-397b-rl-training-guide-with-skyrl/}} (filed in this knowledge base on 7 September 2026) argues that environment robustness and harness design decide an RL run as much as the algorithm does, which is exactly the input this paper industrialises. And the scores are on Terminal-Bench 2.1, while the {{Terminal-Bench leaderboard|https://www.tbench.ai/leaderboard}} now reports Terminal-Bench 4.0 (checked 3 October 2026), so these numbers are not comparable with model cards that report the current version.
