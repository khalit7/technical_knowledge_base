How much of this to believe

[[S4.SS8|§4.8 How we verified the record]]

What holds up. The 1.899 is an archived evaluator output, not an agent's claim: the authors exported the whole contribution stream, recomputed the counts and figures, checked the best score against its recorded loss, token and byte counts, and read every module of the winning chain, finding no step that touched the evaluation data or used gradient descent ({{§4.8|ax:S4.SS8}}). Same-hardware reruns are bit-identical. The size of the effect also reproduces from the paper's description alone: rebuilding Stage A with one donor on a CPU and different texts, we get @@R:ours.uniform_bpb:3@@ for a uniform guess (random init: 3.3923), @@R:ours.gpt2_bpb:3@@ for GPT-2 itself ("about 1.0"), @@R:ours.stage_a_c1.ranks.671.T1:4@@ for the one-context rank-671 factorisation (Table 4: 2.1284) and @@R:ours.stage_a_c28.ranks.671.Tpaper:3@@ with the 28 contexts (Table 4: 1.9319 to 1.9136 for these stages). And version 4 is candid in ways that count in its favour: adjacent rows are not an ablation, equal scores are not rediscovery, prompt and views cannot be separated, and it lists the missing logs.

What it does not show:

  • That Agora helps. There is no comparison: no isolated agents, no flat log, no planner, no single agent with the same compute. Versions 1 and 2 had an appendix designing exactly that matched evaluation (same agents, models, compute, evaluator and budget, the whole community run as the unit); version 3 removed it, and the abstract and conclusion now say the effect "requires a matched comparison" ({{§5|ax:S5}}). One task, one run.
  • That the big result was collective. @@R:share_first_two_improvements:0%@@% of the descent (unigram prior, then bigram SVD at 2.1284) came from one account, worker1, within 86 minutes of its first scored attempt, before the H100 workers existed ({{Table 4|ax:S4.T4}}). Everything after the 18th scored contribution is worth @@R:remaining_after_18th:3@@ bits per byte.
  • That the late gains are real. All 1,124 scored attempts were chosen on the same 200 texts, with no held-out test. On our rebuild a 200-text score moves by about ±@@R:noise.se.c28_r671_Tpaper:3@@ between samples of texts (bootstrap), more than the run gained after day one, so the absolute 1.899 belongs to its sample. Paired differences on the same texts are tighter, but a small change of constants (the paper's temperatures against plain softmax) moves our score by @@R:noise.pairs.c28_r671_Tpaper - c28_r671_T1.diff:4@@ ± @@R:noise.pairs.c28_r671_Tpaper - c28_r671_T1.se:4@@, the size of Table 4's later steps (8 × 10⁻⁴, 5 × 10⁻⁴); the last ones (10⁻⁵ to 10⁻⁷) are search noise, as the paper says of the final one ({{§4.5|ax:S4.SS5}}). Tuned on the paper's texts and blend, those temperatures make our model slightly worse.
  • That "165 reproductions, zero failures" is strong evidence. It is 165 posts on 95 targets (141 distinct pairs); evaluator and hardware appear only in free text; unposted failures left no trace; one gap above tolerance was posted as confirmed; 40 of the winner's 144 ancestors were checked. The paper's own appendix calls a verdict without target hash, configuration, evaluator identity and reproduced value "a coordination hint rather than strong validation evidence" ({{Appendix A|ax:A1}}).
  • That the diversity views worked. They arrived with a new prompt, a threshold the authors chose (at the default the "monoculture" was 8%) and a bug fix for an endpoint that had hidden most edges, while the H100 workers could already see each other's processes. Everything after May 2 is worth @@R:since_may2.drop:4@@ bits per byte, @@R:since_may2.share:1%@@% of the descent, and one of the authors' own sessions sits on the winner's ancestry. This page's earlier summary read the correction as a sign that the system drifts toward premature convergence without it, the correction doing unmeasured work: five days on one lineage support the first half; the record cannot measure the second.
  • That the record is complete or settled. Accounts are not models; the A100 models and prompts, evaluator logs and pinned versions of dependencies, donors, sample and tokenizer were not kept; 45 commits are missing from the index ({{§4.8|ax:S4.SS8}}). Four versions in two weeks changed the equal-score pairs (696, 63%, 80% became 523, 76%, 90%), "first eight improvements, 70%" became "first three, 93%", and "one change" became three server changes, a prompt change and hand-run sessions; the website and README still show version 1 ({{the full list|tab:t-tables:tbv}}).
  • That it is safe to open up. An append-only graph that any worker can extend is also one an adversarial worker can poison, and Agora does not test that (this page's earlier summary; see Emergence World below). The run's only "attack" was accidental: a −1 placeholder metric that topped the leader view until a human cleared it.
Verdict
A careful case study of a good idea, not an evaluation of it. Believe that Git commits plus a derived index make an auditable research memory, and that this run found a no-training initialisation at about 1.90 bits per byte (we get close with one donor on a CPU). Treat every claim about coordination (that the graph made the agents better, that diversity views broke a monoculture) as untested until the matched comparison is run, and the last ten days' gains as within the noise of one 200-text development set.

What it takes to use this

  • Code: none released. The {{GitHub repository|https://github.com/yifanzhang-pro/Agora}} (Apache 2.0) holds a README, the project website and four figures; the Go service, CLI, web interface, launcher, brief, evaluator and the run's 1,703-node graph are not public as of 3 October 2026. A commented-out footnote in the paper's source points to github.com/nvlabs/agora, which does not exist yet.
  • What the paper describes: a Go service with a CLI and a Next.js web interface; one bare Git repository per project whose canonical refs keep every accepted node reachable; SQLite with eight tables (agents, projects, contributions, parents, tags, cross-project references, embeddings, rate limits); 26 HTTP routes and 15 CLI command groups; bearer authentication for writes, clones and fetches; rate limits on registration, contribution creation, search, project creation and bundle size; a Docker image with API, web interface and storage. The index can be rebuilt from Git; project metadata and authentication state need ordinary database backups ({{§3.5|ax:S3.SS5}}). Rebuilding it needs that plus an embedding endpoint (Arctic-Embed 2.0) and Eq. 2 and Eq. 3; how candidates are assigned to the exploit, explore-known and explore-novel slots is not specified.
  • Compute for a run like this: one 80 GB GPU per worker. Thirteen workers for 11 days 19 hours is at most @@R:gpu_hours_upper:0@@ GPU-hours (13 × 283; less in practice, since the A100 workers started April 27, the H100 ones April 28, and the H100s were offline for 27 hours), plus 534 GB of donor weights and the agent subscriptions. Versions 1 and 2 said building the six-donor transition table takes about five minutes on an H100 and hours on a CPU; our one-donor, 28-context build took @@R:ours.build_minutes_c28:0@@ minutes on three CPU threads plus @@R:ours.svd_minutes_c28:0@@ for the randomized SVD.
  • When it pays off: a cheap, automatic, trusted evaluator, many parallel sessions, and results that rerun from a commit. When it buys little: problems where checking a claim is itself expensive, or where one strong agent finds the main idea in its first hour, as worker1 did here.
  • The transfer recipe on its own needs none of this: Stage A with one donor runs on a laptop (our {{rebuild|tab:t-run}}); the row weights and Stage B would have to be reimplemented from Appendix B.
