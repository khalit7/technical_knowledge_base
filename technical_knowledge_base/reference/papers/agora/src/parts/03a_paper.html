The idea in one sentence: let research agents coordinate with no planner by making every claim a Git commit (hypothesis, code, result and the parents it builds on), scoring each commit by what other accounts built on it, and ranking what to try next from that graph; in one 12-day run, 13 coding agents took a no-training weight-transfer score from 3.39 to 1.899 bits per byte, but about 98% of that came on day one and nothing was compared against agents without Agora.

You need: UCB-style exploration bonuses ({{Bandits and exploration|n:3ee5c17b0d0d81acba54d70ac51c601c}}), for Eq. 3; nothing else beyond Git and language-model basics. New terms: contribution (one node of the graph: a commit with tags, description and an optional metric); evidence score (Eq. 2: weighted children from other accounts); analyze (the command that summarises the graph into views); keff (effective number of description clusters); exploit, explore known, explore novel (the three slots candidates are shown in); bits per byte (the run's metric: next-token cross-entropy in bits per UTF-8 byte, lower is better); Stage A (the winning recipe's factorised bigram prior).

Problem

[[S1|§1 Introduction, §2 Related work]]

Multi-agent research systems normally coordinate through a planner: a central process decides who does what, merges results and decides what is true. This page's earlier summary put the cost plainly: the planner is the bottleneck and the single point of failure, and it is where reproducibility goes to die, because the record of what happened is a conversation transcript rather than an artifact anyone can re-execute. The paper states the need more narrowly: research agents running in separate sessions need to know what others have tried and which results they can build on, and findings left in a transcript or a temporary workspace are hard for later sessions to reuse ({{§1|ax:S1}}). (The general patterns, orchestrator-workers, blackboard and shared against isolated context: {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}.) Karpathy's {{autoresearch|https://github.com/karpathy/autoresearch}} showed one coding agent improving a training setup unattended; the question here is what many such agents need in order to build on each other.

Related systems the paper sets itself against (§2)

Existing multi-agent frameworks organise conversations (AutoGen), role play (CAMEL) or role-specific workflows (MetaGPT) inside one application or episode. The closest research systems either hand work out from a supervisor (the AI co-scientist), share finished reports (AgentRxiv), or keep one system's internal archive (the Darwin Gödel Machine, FunSearch, AlphaEvolve) ({{§2|ax:S2}}).

The paper frames it as four questions a shared record must answer at any moment: what has been tried, including failures; which claims have independent support or conflict; where the frontier is, including neglected alternatives; and what exact artifact and lineage produced a reported result ({{§3.1|ax:S3.SS1}}).

The question: can independently scheduled agents, with no planner and no shared conversation, coordinate research through a shared, append-only record of their work?

The idea: research as a Git commit graph

[[S3.SS2|§3.2, Eq. 1, Figure 1]]

Agora removes the planner and replaces shared memory with a Git repository: research is an append-only directed acyclic graph (DAG) in Git, every claim is a commit, each parent edge means "builds on", and any worker can check out any commit and rerun it. A worker picks what to extend by reading the graph, so duplicated work shows up as divergent branches from the same parent rather than hiding in a planner's queue ({{§1|ax:S1}}, {{§3.2|ax:S3.SS2}}).

v = (h, a, T, d, x, m, P, τ)

Equation 1 ({{§3.2|ax:S3.E1}}). Code-bearing contributions carry the full repository state; Git hashes make commits immutable and Git parentage makes the graph acyclic.

The design consequence worth carrying is that provenance and reproducibility stop being separate features. Git already gives content-addressed history, cheap branching, merge semantics and an ancestry relation, which is most of what a research memory needs; the contribution is recognising that the append-only DAG is the right data structure for collective agent work and that a tool built for exactly that structure already exists. Agora adds three things on top: a searchable index, an evidence score and a ranking of what to work on next ({{Table 1|ax:S3.T1}} lists the five design goals, durable memory, frontier visibility, evidence quality, search diversity and auditability, each with the failure it prevents).

How a contribution is published, and the reserved tags

Two paths, one record. Metadata-only work (an insight, a hypothesis) takes the light path: the client sends JSON and the server creates the commit. Code-bearing work takes the heavy path: the participant commits locally, uploads a Git bundle, and the server validates it before creating a canonical, server-timestamped commit. A project starts with agora init, which creates the setup contribution; from then on a participant loops: analyze, pick a parent, run locally, publish, analyze again ({{§3.2|ax:S3.SS2}}). Contribution types are tags, not a fixed schema, so a project or an agent can add tags for methods, datasets or failure modes; only a small reserved set ({{Table 2|ax:S3.T2}}, rebuilt in the {{numbers tab|tab:t-tables:tb2}}) changes validation and scoring.

"Append-only" is true of the Git history, not of the index
The SQLite index that the views read is separate from Git: records can be removed from it, edited, or never reach it. In the run 45 commits are missing from it (21 early posts removed, 24 failed first attempts reposted within 80 seconds, because the server writes the commit before the index and does not undo it when the index write fails), and one record was edited by hand ({{§3.2|ax:S3.SS2}}, {{§4.2|ax:S4.SS2}}, {{§4.7|ax:S4.SS7}}). Version 1 had said "The Git history is the only state".

Evidence: a score from what others built on it

[[S3.E2|§3.2, Eq. 2, Table 2]]

Votes reward popularity, and self-citation is cheap, so Agora scores a contribution by the work other accounts attached to it. Let w(v) be the weight of the child's type ({{Table 2|ax:S3.T2}}): +5 for a result, insight, hypothesis, report or setup; +20, +10 or −20 for a confirmed, partial or failed verification; 0 for endorsed and wip. A verifier may post several verdicts on one target and only the newest counts (ordered by server timestamp, then commit hash); E* is the edge set with superseded verdicts removed.

S(u) = Σv : (u,v) ∈ E* 𝟙[a(u) ≠ a(v)] · w(v)
Equation 2 ({{§3.2|ax:S3.E2}}): the weighted count of direct children from other accounts. Alongside it, each node reports an unweighted descendant count: contributions by other accounts reachable through E*, excluding endorsements, work in progress and failed verifications. Both exclude self-citation, which stops a worker from manufacturing impact by extending its own branch.

The paper is careful about what this measures: reproduction and reuse by other accounts, not truth. Whether a result is accepted still depends on the project's evaluator, controls and artifact policy ({{§3.2|ax:S3.SS2}}). And the server authenticates accounts, not the model or session behind them ({{§4.2|ax:S4.SS2}}), so an account is a credential rather than an agent: in this run every H100 account ran sessions of all three models, so two accounts often ran the same model.
