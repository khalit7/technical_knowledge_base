Agora: Git as Shared Memory for Collective AutoResearch

Yifan Zhang, Yunheng Zou, Shaokun Zhang, Jian Hu, Hao Zhang, Binfeng Xu, Jan Kautz, Yi Dong
NVIDIA · arXiv v1 16 September 2026; v4 (read here) 30 September 2026

In one line: Record collective agent research as an append-only DAG of Git commits, so every claim is a commit anyone can check out and rerun; 13 workers over 12 days published 1,703 contributions, cut the evaluator from 3.39 to 1.899 bits per byte, and 165 independent reproductions failed zero times.

That is the database's Takeaway, written from an earlier version. Version 4 is more careful: 165 verification posts by accounts other than the author, covering 95 targets and 141 distinct verifier and target pairs, none reporting a failure; an unposted failed attempt would leave no trace (§4.5, §4.8).

Problem

§1 Introduction, §2 Related work

Multi-agent research systems normally coordinate through a planner: some central process decides who does what, merges results and decides what is true. This page's earlier summary put the cost plainly: that planner is the bottleneck and the single point of failure, and it is also where reproducibility goes to die, because the record of what happened is a conversation transcript rather than an artifact anyone can re-execute. The paper itself states the need more narrowly. Research agents that run in separate sessions need to know what others have tried and which results they can build on; findings left in a transcript or a temporary workspace are hard for later sessions to reuse; and existing multi-agent frameworks organise conversations (AutoGen), role play (CAMEL) or role-specific workflows (MetaGPT) inside one application or episode (§1, §2). The closest research systems either hand work out from a supervisor (the AI co-scientist), share finished reports (AgentRxiv), or keep one system's internal archive (the Darwin Gödel Machine, FunSearch, AlphaEvolve). Karpathy's autoresearch showed one coding agent improving a training setup unattended; the question here is what many such agents need in order to build on each other.

The paper frames it as four questions a shared record must answer at any moment: what has been tried, including failures; which claims have independent support or conflict; where the frontier is, including neglected alternatives; and what exact artifact and lineage produced a reported result (§3.1).

The question: can independently scheduled agents, with no planner and no shared conversation, coordinate research through a shared, append-only record of their work?

The idea: research as a Git commit graph

§3.2, Eq. 1, Figure 1

Agora removes the planner and replaces shared memory with a Git repository. Research is recorded as an append-only directed acyclic graph (DAG) stored in Git, where every claim is a commit: the hypothesis, the code, the measured result and the parent commits it builds on. Each parent edge means "builds on". Any worker can check out any commit and rerun it. Coordination is emergent rather than assigned, because a worker picks what to extend by reading the graph, and duplicated work is visible as divergent branches from the same parent rather than hidden inside a planner's queue (§1, §3.2).

Equation 1 (§3.2). Code-bearing contributions carry the full repository state; Git hashes make commits immutable and Git parentage makes the graph acyclic.

The design consequence worth carrying is that provenance and reproducibility stop being separate features. Git already gives content-addressed history, cheap branching, merge semantics and an ancestry relation, which is most of what a research memory needs; the contribution is recognising that the append-only DAG is the right data structure for collective agent work and that a tool built for exactly that structure already exists. Agora adds three things on top: a searchable index, an evidence score and a ranking of what to work on next (Table 1 lists the five design goals, durable memory, frontier visibility, evidence quality, search diversity and auditability, each with the failure it prevents).

How a contribution is published, and the reserved tags

Two paths, one record. Metadata-only work (an insight, a hypothesis) takes the light path: the client sends JSON and the server creates the commit. Code-bearing work takes the heavy path: the participant commits locally, uploads a Git bundle, and the server validates it before creating a canonical, server-timestamped commit. A project starts with agora init, which creates the setup contribution; from then on a participant loops: analyze, pick a parent, run locally, publish, analyze again (§3.2). Contribution types are tags, not a fixed schema, so a project or an agent can add tags for methods, datasets or failure modes; only a small reserved set (Table 2, rebuilt in the numbers tab) changes validation and scoring.

"Append-only" is true of the Git history, not of the index
The SQLite index that the views read is separate from Git: records can be removed from it, edited, or never reach it. In the run 45 commits are missing from it (21 early posts removed, 24 failed first attempts reposted within 80 seconds, because the server writes the commit before the index and does not undo it when the index write fails), and one record was edited by hand (§3.2, §4.2, §4.7). Version 1 had said "The Git history is the only state".

Evidence: a score from what others built on it

§3.2, Eq. 2, Table 2

Votes reward popularity, and self-citation is cheap, so Agora scores a contribution by the work other accounts attached to it. Let w(v) be the weight of the child's type (Table 2): +5 for a result, insight, hypothesis, report or setup; +20, +10 or −20 for a confirmed, partial or failed verification; 0 for endorsed and wip. A verifier may post several verdicts on one target and only the newest counts (ordered by server timestamp, then commit hash); E* is the edge set with superseded verdicts removed.

S(u) = Σv : (u,v) ∈ E* 𝟙[a(u) ≠ a(v)] · w(v)
Equation 2 (§3.2): the weighted count of direct children from other accounts. Alongside it, each node reports an unweighted descendant count: contributions by other accounts reachable through E*, excluding endorsements, work in progress and failed verifications. Both exclude self-citation, which stops a worker from manufacturing impact by extending its own branch.

The paper is careful about what this measures: reproduction and reuse by other accounts, not truth. Whether a result is accepted still depends on the project's evaluator, controls and artifact policy (§3.2). And the server authenticates accounts, not the model or session behind them (§4.2), so an account is a credential rather than an agent: in this run every H100 account ran sessions of all three models, so two accounts often ran the same model.

Reading the frontier: analyze, clusters and a diversity-aware ranking

§3.3, §3.4, Eq. 3

agora analyze (a CLI command and HTTP endpoint) summarises the graph in views that answer those questions: what has been tried (recent activity, tags, contributors); which claims hold (unverified results, contested verifications, open hypotheses, so a worker can pick something to reproduce or test); where the frontier is (metric leaders, the most built-on nodes, promising results with at most two descendants, and leaves with no follow-on work). Every view can be rebuilt from the published record, and analyze is the first thing each session runs and the last before publishing, which makes it the main channel through which workers coordinate (§3.3).

Seeing concentration. A worker that picks the best-scoring parent tends to make the same choice as every other worker. To see this, the server embeds each description with Arctic-Embed 2.0 (568M parameters, 1,024-dimensional vectors, served through an OpenAI-compatible endpoint). Once at least 50% of contributions have embeddings, analyze forms single-link clusters, joining two contributions when the cosine similarity of their embeddings is at least a threshold (0.90 by default; pairwise analysis is capped at the 5,000 most recent contributions). With k clusters holding shares p1 to pk, it reports the top-cluster share max pi, the effective cluster count keff = exp(−Σ pi log pi) ("how many ideas are really being pursued": k when all clusters are equal, falling towards 1 as one dominates), evenness keff/k, cluster sizes, a metric histogram, and a frontier of promising nodes in small clusters (§3.4).

Equation 3 (§3.4), a UCB rule in the spirit of bandits and UCT (Auer et al. 2002; Kocsis and Szepesvári 2006), plus a novelty term. Candidates are then shown in three slots: exploit (reproduce or refine the leaders), explore known (extend promising work in a thin cluster), explore novel (inspect untouched nodes in singleton or very small clusters).

Two details are easy to miss. For a minimised metric such as bits per byte, the "upper tail" that inflates C holds the weakest results, as the authors note themselves (§3.4). And the novelty term can reach 100D, as large as the whole quality term.

The run: 13 agents, one weight-transfer problem

§4.1 to §4.3, Figure 2

The task. How much of a trained model's predictive quality can be put into a model whose architecture matches none of the available donors, using only the donors' weights and forward passes: no training corpus and no gradient update on the target? The donor zoo holds 141 open-weight models (534 GB) from 32 architecture families, including GPT-2, LLaMA, Mistral, Qwen, Gemma, Pythia, RWKV and Mamba. The target is a 14-layer hybrid that alternates attention blocks with simplified Mamba-style state-space (SSM) blocks, which keep Mamba's projections, depthwise causal convolution and gating but replace the selective scan with a data-dependent scalar gate; hidden size 672, seven query heads sharing one key-value head, untied embeddings, 119,572,320 parameters, dimensions chosen so that no donor matches any of them (§4.1).

The evaluator. A participant submits a Python file with a transfer(model, config) function that receives the randomly initialised target and returns it with new weights. The evaluator seeds every random-number generator with 42, runs transfer() and scores 200 FineWeb-Edu texts in non-overlapping 512-token chunks under the GPT-2 tokenizer, reporting bits per byte (summed next-token cross-entropy in bits divided by the UTF-8 byte count). The FineWeb-Edu loader raises an error if called from inside transfer(); the rules forbid pretraining, fine-tuning and editing the evaluator or target configuration. Two runs of the same code on the same hardware are bit-identical; across GPU types the score can differ in the third decimal place. Random initialisation scores 3.3923 and a conventionally trained GPT-2 124M about 1.0; the project README set an aspirational target below 2.5 (§4.1).

The workers, the launcher and the brief

The workers. Coding-agent sessions: Claude Code with Claude Opus 4.7, and Codex with GPT-5.5 or GPT-5.4, each started by a small launcher in a container with one GPU, one Agora account credential and a short prompt (stored as one line: "read program.md for full instructions, and run agora analyze to see what others have tried"; the H100 launcher, the only one whose logs survive, added "decide without asking for guidance" and "end the session only after publishing"). When a session ended, a new one started on a free credential. program.md, the first node, is a two-page brief: task, rules, evaluator contract, "every contribution must run from a fresh checkout", and the loop. Apart from an SVD weight-projection baseline shipped as an example, nothing names a method, assigns a role or ranks the participants (§4.2).

Thirteen worker accounts wrote 1,699 of the 1,703 contributions: worker1 to worker5 on A100 nodes from April 27, slurm_worker_1 to 8 on H100 nodes from April 28. The other four came from the setup account and three agent sessions the authors ran by hand (17 accounts in all). Of the H100 accounts' 1,285 contributions, Claude Opus 4.7 sessions published 866 (67%), GPT-5.5 276 and GPT-5.4 143; the A100 workers' models were not recorded. Each worker had the Agora CLI, Git, Python with PyTorch and Transformers, the donor zoo, the evaluator and one 80 GB GPU. The eight H100 workers shared one eight-GPU node: no files, but they could list one another's processes, and several descriptions, the winning module's included, report choosing an experiment after seeing what neighbours were running (§4.2).

The loop. Each session read analyze, picked a parent, checked out that exact commit, made one change, evaluated, committed everything needed to reproduce, pushed with a description and metric, then posted what else it had learned (an insight, hypothesis, verification, or a new tag). Descriptions state the parent and its score, the single change, a predicted outcome band, the result and named follow-ups. The run lasted 11 days and 19 hours, from the setup commit on April 26 to the cutoff on May 8: 1,124 scored contributions (any that report a metric), 284 insights, 203 hypotheses, 165 verifications and one report, with tag overlaps (they sum to 1,777); 232 scored ones beat random initialisation and every earlier score (§4.3).

What the agents found: the winning recipe

§4.4, Algorithm 1, Table 3, Appendix B

The best contribution at cutoff is a chain of 73 Python modules, each importing its parent and modifying the model the parent returns; ten earlier variants imported for shared code bring the import closure to 83. The authors traced the imports to the base module and checked the constants against the code (§4.4). It has two stages.

Stage A: copy what the donors predict, not what they are. Six donors that share the GPT-2 vocabulary (GPT-2 small and large, Cerebras-GPT 111M to 1.3B) are queried on every vocabulary token v under 28 contexts p: no context, end-of-text, 22 single tokens (punctuation and function words such as " the") and four two-token clause starters (". The", ", and", ". This", ", or"). Their next-token log-softmaxes, clipped to ±25, are blended with fixed donor weights (0.725 on GPT-2 small) and per-row context weights into a 50,257 × 50,257 context-averaged bigram table M. Its column mean u is split off as a unigram-like anchor; the centred table C = M − 1u⊤ is factorised to rank d − 1 = 671 by randomized SVD (oversampling 32, one power iteration, a fixed sketch). The factors become the input embedding and the output head; hidden dimension 0 carries u; two temperatures (Tb = 0.9314, Tu = 1.00459) rescale the two terms; every sublayer is zeroed and every norm gets unit gain and zero bias. The final RMSNorm then rescales an embedding row by about √d, which the 1/√d factors cancel, so for input token v the logits are approximately u/Tu + rank-671 part of C(v, ·)/Tb: a factorised bigram model stored in a 14-layer network (§4.4, Table 5). The Rebuild tab runs this stage on a CPU with GPT-2 small alone.

Stage B: the sparse edits, with a map of the 672 dimensions

Stage B: let a little context back in. Sparse, deterministic edits on 96-dimensional bands of the hidden state (B0 to B5 from dimension 1 in steps of 96; B6 = [576, 672), shifted down by one to fit). Every attention layer becomes a uniform causal mean-pool over one band (Wq = Wk = 0), written back at a small scale, so the model sees an average of its past embeddings. Layer 0's SwiGLU gets SVD-projected slices of GPT-2 small's first MLP at scale 0.009. Each SSM block, its data-dependent gate zeroed to a constant, becomes a gated depthwise causal convolution over one band (layer 1: positive taps on the three preceding positions, a negative tap on the current one; the others uniform), writing into B2 and on some layers B0, B1, B3. Each constant was introduced as a single change on the then-current best and kept because the evaluator improved (§4.4, Table 3).

Results

§4.5, Table 4, Figure 3

The trajectory. Within six hours of the switch to a unigram prior, three accounts had extended it to bigram statistics under 3, 6, 12 and 24 prefixes (1.93). Those first 18 scored contributions account for about 98% of the total reduction. The remaining 1,106 found the next 0.03 by adding Cerebras-GPT donors, widening to 28 contexts, adding a power iteration to the SVD and attention mean-pooling, and, after May 2, re-enabling SSM and feed-forward sublayers (§4.5). What did not work (negative results)

Negative results. The graph also records what did not work, and later workers cited those records when choosing directions. Doubling the prefix set to 48 made the recipe worse (four controlled variants). Flattening the singular-value spectrum, transplanting native Mamba blocks from hybrid donors, copying GPT-2's embedding matrix directly, and building the prior from a donor with another tokenizer (Pythia) all regressed and were published with their scores. In the window, 60 contributions carry an explicit negative- or null-result tag, 29 of them negative-result (§4.5).

Lineage and reproduction. The best contribution has 145 commits in its ancestry, written by 15 of the 17 accounts (all 13 workers, the setup account and one of the authors' hand-run accounts); 115 of its 144 parent edges (80%) cross account boundaries, so no single worker assembled the recipe. Participants posted 165 verification contributions covering 95 distinct targets, each by an account other than the author, none reporting a failure: 141 distinct verifier and target pairs, the other 24 repeats (only the newest verdict per pair counts). Same-hardware reproductions are bit-identical; most A100 against H100 ones agree within 5 × 10⁻⁴ bits per byte; the largest gap, 1.2 × 10⁻³ on an ancestor of the winner, is slightly above the roughly 10⁻³ the brief allows, and was posted as confirmed anyway, put down to a constant hardware offset. Forty of the winner's 144 ancestors (28%) were reproduced by another account (§4.5).

The primary result
Without training data or a single gradient update on the target, the community's best transfer() initialises the frozen 119.6M hybrid to 1.899044 bits per byte, against 3.3923 for random initialisation and about 1.0 for a trained GPT-2 124M: (3.3923 − 1.899044) / (3.3923 − 1.0) = 62.4% of the gap closed (§4.5). A low-rank approximation of donor next-token behaviour transferred across architectures, where the first indexed parameter-copying attempt did worse than random. The last recorded improvement was 3 × 10⁻⁷ over the previous best (9 × 10⁻⁶ over its own parent), far below the cross-hardware variation.

Coordination dynamics

§4.6, Figures 4 and 5

At cutoff the graph has 1,703 nodes, 1,894 edges, 149 multi-parent nodes, and one component holding 98.9% of the nodes (Figure 4 draws it, including 123 contributions posted after the cutoff, with the winner's ancestry as a highlighted spine). The paper reads four patterns from the trace (§4.6):

  1. Fast exploitation. The first three improvements account for 93% of the total descent, the first 18 scored contributions for about 98%. (Table 4's first two improvements already make 84.6%, so version 1's "first eight improvements, roughly 70%" could not have been right.)
  2. Narrow spine. One lineage collects most of the follow-on work; side branches are short and quickly abandoned.
  3. Equal-score convergence. Of 523 pairs of different accounts posting identical scores, 76% fall within an hour of each other and 90% within six; removing verifications and parent-child pairs leaves 499 pairs with the same timing (79% and 90%). Identical scores can come from re-runs of a shared parent or from different methods, so this is convergence on the same results, not independent rediscovery (version 1 called it "parallel rediscovery", with 696 pairs, 63% and 80%; Figure 5).
  4. Community-level diagnosis. Several families of contributions converge near 1.90. Agents attributed the plateau to a globally linear evaluator and underused target sublayers and called the bigram recipe a hard local optimum; nobody tested these explanations.

Workers adopted leading results quickly: 194 of the 232 new bests (84%) drew follow-on work from at least one other account within six hours, a median of three accounts among those. They also repeated work and concentrated most effort on one lineage. The paper's own summary: shared visibility supported reuse, but did not by itself sustain broad exploration.

What the humans did

§4.7

This page's earlier summary, written from an earlier version, said there was one human intervention mid-run, to restore diversity after the population converged. Version 4 lists more: besides defining the task, donors, target, evaluator and brief and launching the workers, the authors changed the server three times and the H100 workers' prompt once, edited one record by hand, and ran three agent sessions themselves. No intervention log survives; this is reconstructed from the commit history, the contribution record and the H100 launcher's logs (§4.7).

  1. April 28, a hand-run session on the winner's ancestry. One of three agent sessions the authors ran outside the launcher, each under an account registered just before its only post, ran a grid over the two temperatures and changed the bigram temperature from 0.926 to 0.924 (1.9158 bpb). The other two posted a verification on H100 hardware (May 1) and an insight summarising the landscape views (May 7). Their text follows the workers' template, which the authors take to mean agents, not a person, wrote them.
  2. May 2, the diversity views. With more than a third of all activity in one semantic cluster and the leaderboard stalled, the authors deployed the clustering, diversity summary and diversity-aware UCB, with this project's threshold set to 0.80 instead of 0.90. At 0.90 the largest cluster would have held about 8%, so both the diagnosis and the new prompt's trigger depend on that setting.
  3. May 2, 19:13 to 21:20 UTC, a new prompt for the eight H100 workers: read the landscape first; if the largest cluster holds more than 30% of activity, prefer the explore-novel slot or the frontier; choose among the three slots; post an insight explaining any failed idea. On May 3, 86% of H100 descriptions cite the diversity summary or the slots, against under 1% before. The A100 prompt is not recorded; their citations rose from 26% (May 3) to 66% (May 5) and fell to 29% by May 8. The authors' conclusion: the shift reflects the prompt as much as the views, and the record cannot separate the two.
  4. May 2, 23:12 and May 3, 00:13. An H100 worker citing the cluster summary posted the first positive SSM result (a layer-1 band mean-pool taking a bare bigram baseline to 1.9297); another, in a GPT-5.4 session exploring the sparse state-space cluster, added that block to the leading chain: 1.9028, a new best. The milestones reached 1.8995 on May 5.
  5. May 3, a bug fix. The DAG endpoint had returned at most 200 contributions and dropped every edge whose parent fell outside them. Fixing it and adding the views to the web interface paused the H100 workers from 14:56 to 15:24 UTC.
  6. May 5, a placeholder metric. A hypothesis posted with a metric of −1 topped the metric-leader views. The authors committed a server change rejecting metrics on hypothesis-only contributions (Table 2's rule; when it went live is not recorded, but no other hypothesis carries a metric) and cleared the value directly in the database, since the API cannot edit a contribution. Its commit still carries −1.
on May 2 the views showed more than a third of all activity in one cluster, with the threshold set to 0.80. At the default 0.90, what share would the largest cluster have held?

About 8% (§4.7). The authors explain why they lowered it: descriptions that embed raw scores, such as "val_bpb=1.9158…", keep near-identical experiments apart at 0.90 (§3.4). Why it matters (beyond the paper)

A memory design that an outsider can audit. The useful idea is that the coordination record and the reproducibility record are the same object. Every number in the run can, in principle, be traced to a commit, rebuilt, and checked, which is not true of the transcript-based memories of conversation frameworks or the private archives of evolutionary systems. The paper's own audit (§4.8) is possible only because of it.

A transfer result worth knowing on its own. That a factorised table of donor next-token predictions gets a never-trained 120M model most of the way from random to GPT-2 is a striking, cheap baseline for "initialise a new architecture from old models". Our CPU rebuild of Stage A with GPT-2 small alone lands at 1.922 bits per byte on a different FineWeb-Edu sample (Rebuild tab), so the bulk of the effect needs one donor, not a 534 GB zoo.

The friendly setting. As this page's earlier summary noted, the bits-per-byte target is a well-posed objective with a cheap automatic evaluator, the friendliest possible setting for this design. Nothing here shows it survives a research problem where deciding whether a claim is true is itself expensive.

How much of this to believe

§4.8 How we verified the record

What holds up. The 1.899 is an archived evaluator output, not an agent's claim: the authors exported the whole contribution stream, recomputed the counts and figures, checked the best score against its recorded loss, token and byte counts, and read every module of the winning chain, finding no step that touched the evaluation data or used gradient descent (§4.8). Same-hardware reruns are bit-identical. The size of the effect also reproduces from the paper's description alone: rebuilding Stage A with one donor on a CPU and different texts, we get 3.354 for a uniform guess (random init: 3.3923), 1.020 for GPT-2 itself ("about 1.0"), 2.1282 for the one-context rank-671 factorisation (Table 4: 2.1284) and 1.922 with the 28 contexts (Table 4: 1.9319 to 1.9136 for these stages). And version 4 is candid in ways that count in its favour: adjacent rows are not an ablation, equal scores are not rediscovery, prompt and views cannot be separated, and it lists the missing logs.

What it does not show:

  • That Agora helps. There is no comparison: no isolated agents, no flat log, no planner, no single agent with the same compute. Versions 1 and 2 had an appendix designing exactly that matched evaluation (same agents, models, compute, evaluator and budget, the whole community run as the unit); version 3 removed it, and the abstract and conclusion now say the effect "requires a matched comparison" (§5). One task, one run.
  • That the big result was collective. 85% of the descent (unigram prior, then bigram SVD at 2.1284) came from one account, worker1, within 86 minutes of its first scored attempt, before the H100 workers existed (Table 4). Everything after the 18th scored contribution is worth 0.031 bits per byte.
  • That the late gains are real. All 1,124 scored attempts were chosen on the same 200 texts, with no held-out test. On our rebuild a 200-text score moves by about ±0.021 between samples of texts (bootstrap), more than the run gained after day one, so the absolute 1.899 belongs to its sample. Paired differences on the same texts are tighter, but a small change of constants (the paper's temperatures against plain softmax) moves our score by 0.0015 ± 0.0005, the size of Table 4's later steps (8 × 10⁻⁴, 5 × 10⁻⁴); the last ones (10⁻⁵ to 10⁻⁷) are search noise, as the paper says of the final one (§4.5). Tuned on the paper's texts and blend, those temperatures make our model slightly worse.
  • That "165 reproductions, zero failures" is strong evidence. It is 165 posts on 95 targets (141 distinct pairs); evaluator and hardware appear only in free text; unposted failures left no trace; one gap above tolerance was posted as confirmed; 40 of the winner's 144 ancestors were checked. The paper's own appendix calls a verdict without target hash, configuration, evaluator identity and reproduced value "a coordination hint rather than strong validation evidence" (Appendix A).
  • That the diversity views worked. They arrived with a new prompt, a threshold the authors chose (at the default the "monoculture" was 8%) and a bug fix for an endpoint that had hidden most edges, while the H100 workers could already see each other's processes. Everything after May 2 is worth 0.0064 bits per byte, 0.4% of the descent, and one of the authors' own sessions sits on the winner's ancestry. This page's earlier summary read the correction as a sign that the system drifts toward premature convergence without it, the correction doing unmeasured work: five days on one lineage support the first half; the record cannot measure the second.
  • That the record is complete or settled. Accounts are not models; the A100 models and prompts, evaluator logs and pinned versions of dependencies, donors, sample and tokenizer were not kept; 45 commits are missing from the index (§4.8). Four versions in two weeks changed the equal-score pairs (696, 63%, 80% became 523, 76%, 90%), "first eight improvements, 70%" became "first three, 93%", and "one change" became three server changes, a prompt change and hand-run sessions; the website and README still show version 1 (the full list).
  • That it is safe to open up. An append-only graph that any worker can extend is also one an adversarial worker can poison, and Agora does not test that (this page's earlier summary; see Emergence World below). The run's only "attack" was accidental: a −1 placeholder metric that topped the leader view until a human cleared it.
Verdict
A careful case study of a good idea, not an evaluation of it. Believe that Git commits plus a derived index make an auditable research memory, and that this run found a no-training initialisation at about 1.90 bits per byte (we get close with one donor on a CPU). Treat every claim about coordination (that the graph made the agents better, that diversity views broke a monoculture) as untested until the matched comparison is run, and the last ten days' gains as within the noise of one 200-text development set.

What it takes to use this

  • Code: none released. The GitHub repository (Apache 2.0) holds a README, the project website and four figures; the Go service, CLI, web interface, launcher, brief, evaluator and the run's 1,703-node graph are not public as of 3 October 2026. A commented-out footnote in the paper's source points to github.com/nvlabs/agora, which does not exist yet.
  • What the paper describes: a Go service with a CLI and a Next.js web interface; one bare Git repository per project whose canonical refs keep every accepted node reachable; SQLite with eight tables (agents, projects, contributions, parents, tags, cross-project references, embeddings, rate limits); 26 HTTP routes and 15 CLI command groups; bearer authentication for writes, clones and fetches; rate limits on registration, contribution creation, search, project creation and bundle size; a Docker image with API, web interface and storage. The index can be rebuilt from Git; project metadata and authentication state need ordinary database backups (§3.5). Rebuilding it needs that plus an embedding endpoint (Arctic-Embed 2.0) and Eq. 2 and Eq. 3; how candidates are assigned to the exploit, explore-known and explore-novel slots is not specified.
  • Compute for a run like this: one 80 GB GPU per worker. Thirteen workers for 11 days 19 hours is at most 3,679 GPU-hours (13 × 283; less in practice, since the A100 workers started April 27, the H100 ones April 28, and the H100s were offline for 27 hours), plus 534 GB of donor weights and the agent subscriptions. Versions 1 and 2 said building the six-donor transition table takes about five minutes on an H100 and hours on a CPU; our one-donor, 28-context build took 16 minutes on three CPU threads plus 2 for the randomized SVD.
  • When it pays off: a cheap, automatic, trusted evaluator, many parallel sessions, and results that rerun from a commit. When it buys little: problems where checking a claim is itself expensive, or where one strong agent finds the main idea in its first hour, as worker1 did here.
  • The transfer recipe on its own needs none of this: Stage A with one donor runs on a laptop (our rebuild); the row weights and Stage B would have to be reimplemented from Appendix B.

Connections

Read next to SoL-Pi and Dream-RSI: all three are auto-research loops, and they differ in where the loop's memory lives. Agora puts it in a shared commit graph, SoL-Pi puts it in harness-layer techniques discovered once and reused, Dream-RSI puts it in a replay simulator built from the search history. Rebuild the winning prior

Nothing from the run is released, so this tab rebuilds the part of the agents' recipe that did almost all the work, Stage A (§4.4), from the paper's description, and measures it with the paper's own metric. We asked GPT-2 small for its next-token distribution after every one of the 50,257 tokens, under the paper's 28 contexts (and, separately, with no context), averaged the clipped log-probabilities into a 50,257 × 50,257 table, split off the column mean as the unigram anchor u, factorised the rest by randomized SVD exactly as Algorithm 1 says (rank 671, oversampling 32, one power iteration, fixed seed), and scored the resulting model on 200 FineWeb-Edu texts in 512-token chunks, in bits per byte.

Same as the paper, and not
Same: the main donor (GPT-2 small carries weight 0.725 in the winning blend), the 28 contexts of Table 5, the ±25 clip, averaging per-context log-softmaxes, the unigram anchor, the SVD settings, the temperatures Tb = 0.9314 and Tu = 1.00459, the corpus, chunking and metric. Different: one donor instead of six; equal context weights instead of the variance and naturalness row weights; no Stage B; logits computed directly as u/Tu + (rank-r part of C)/Tb, which §4.4 says is approximately what the target network computes; and our 200 texts (rows 0 to 199 of FineWeb-Edu's sample-10BT) are not theirs, which were never pinned (§4.8).

Temperatures

A finding of the rebuild: with 28 contexts the rank-671 model (1.9203 at T = 1) scores better than the full table it approximates (1.9543); with one context the two are the same (2.1282 against 2.1276). So the factorisation is not only a way to fit the table into a 672-wide network: on the context-averaged table, dropping the smallest singular directions smooths it and helps. That is our reading of two measurements, not something the paper reports or we tested further.

Energy captured is the share of the squared Frobenius norm of the centred table C carried by the top r singular values. The full table is scored without SVD, at T = 1 (no temperature split exists without the factorisation).

How this was made

fetch_data.py downloads the 200 texts; stage_a.py builds the tables (GPT-2 small through Transformers, three CPU threads; the 28-context table took 16 minutes and its SVD 2), factorises them and scores every rank; stage_a_demo.py computes the per-text bits, the bootstrap (2,000 resamples over texts, seed 0) and the replay passage; recompute.py checks the measurements against the paper. Results are in src/model/; the 10 GB tables are rebuilt by the scripts and not kept. Our sample has 167,130 predicted tokens and 778,242 bytes (4.66 bytes per token).
