Problem

§1 Extended Introduction, §2 Related Work

In 2019 the two ways to scale training both hit walls. Data parallelism (DP) gives every GPU a different slice of the mini-batch and averages the gradients, but it replicates the full model state on every GPU, so it does not reduce memory per device at all: plain DP (PyTorch's DistributedDataParallel, DDP) runs out of memory beyond about 1.4B parameters on 32 GB V100s, however many GPUs you add (§1). Model parallelism (MP), the Megatron-LM style of tensor parallelism that trained the 8.3B Megatron and (as Mesh-TensorFlow) the 11B T5, partitions memory by slicing every layer across GPUs; that makes the computation fine-grained and needs heavy communication inside each layer, so it works within one node but collapses beyond it. The authors ran a 40B model with Megatron-LM across two DGX-2 nodes and measured about 5 TFLOPS per V100, under 5% of peak (§1; 5 / 125 = 4% of the V100's 125 TFLOPS fp16 tensor peak from the NVIDIA V100 whitepaper, the paper's reference 24). The cause is the link: crossing nodes drops the bandwidth from 300 GB/s per link (NVSwitch) to 12.5 GB/s (InfiniBand EDR), 24 times less (§10.2).

The alternatives each pay somewhere else (§2): pipeline parallelism needs a large batch to hide its bubble (GPipe) or keeps stale weight copies (PipeDream), and makes tied weights and batch normalisation awkward (§2.1); offloading model states to CPU can spend up to 50% of training time on transfers (§2.2.2); memory-efficient optimisers such as Adafactor may change convergence (§2.2.3), whereas ZeRO changes neither the optimiser nor convergence (§2.3).

The diagnosis: none of these touches the real culprit. Most of the memory is not the fp16 weights; it is the optimizer states and gradients, kept as identical copies on every data-parallel GPU, and kept all the time although each piece is needed only briefly.

Where did all the memory go?

§3 Where Did All the Memory Go?

The paper first does the accounting. A 1.5B-parameter GPT-2 needs 3 GB for its weights in 16-bit precision, yet it cannot be trained on a single 32 GB GPU in TensorFlow or PyTorch (§3). Training memory has two parts: model states (optimizer states, gradients and parameters) and residual states (activations, temporary buffers and fragmented memory).

GPT-2's 1.5B parameters take 3 GB in fp16. With mixed-precision Adam, how much memory do its model states (weights, gradients, optimizer states) need?

24 GB, 16 bytes for every parameter (§3.1). Mixed-precision training (Micikevicius et al., the paper's reference 23) runs forward and backward in fp16, so it holds fp16 parameters (2Ψ bytes for Ψ parameters) and fp16 gradients (2Ψ); but to apply updates accurately the optimizer keeps an fp32 copy of the parameters plus Adam's fp32 momentum and variance: 4Ψ + 4Ψ + 4Ψ. The paper calls the optimizer's share KΨ, with K = 12 for mixed-precision Adam, so the total is 2Ψ + 2Ψ + KΨ = 16Ψ bytes. The optimizer states alone are three quarters of it.

GB here is 109 bytes, the paper's unit (16 × 7.5 × 109 = 120 GB). K = 12 is the paper's case (mixed-precision Adam); move it to see how much of the total is the optimizer's.

Residual states (§3.2) add three more costs:

  • Activations. GPT-2 1.5B at sequence length 1K and batch 32 needs about 60 GB of activations; the paper's footnote 3 gives the rule, about 12 × hidden × batch × sequence × layers values, and at 2 bytes each that is 12 × 1600 × 32 × 1024 × 48 × 2 = GB, which reproduces the 60 GB. Activation checkpointing (Chen et al., reference 7) keeps only some activations and recomputes the rest, cutting activation memory to roughly the square root of the total for about 33% extra compute; the paper says this brings GPT-2 to about 8 GB. Even with checkpointing a 100B GPT-like model needs around 60 GB at batch 32.
  • Temporary buffers. Gradient all-reduce and gradient-norm computation fuse all gradients into one flat buffer for bandwidth, often in fp32: 6 GB for a 1.5B model (1.5 × 109 × 4 bytes).
  • Fragmentation. A request fails without enough contiguous memory even if the total free is larger; the authors saw out-of-memory errors with over 30% of memory still free in extreme cases.

Two of these figures do not reproduce exactly: the 8 GB after checkpointing, and the paper's two 100B checkpoint sizes, which disagree with each other by a factor of 2. Both are worked through in Every number in the text, checked.

The idea: ZeRO-DP, data parallelism without the redundancy

§4.1, §5, Figure 1

Three observations drive the design (§4.1): (a) DP scales better than MP because it keeps large, efficient matrix multiplies and communicates less; (b) DP wastes memory because every process stores identical model states, while MP partitions them; (c) both keep every state for the whole step, although a layer's parameters, for example, are only needed during that layer's forward and backward. So ZeRO-DP keeps DP's execution model (each GPU runs whole layers on its own data) but partitions the model states across the Nd data-parallel processes instead of replicating them, and uses a dynamic communication schedule to bring each piece to where it is needed, when it is needed (§4.1). It comes in three cumulative stages:

From §1, §5.1 to §5.4 and §7; communication in elements per process. The names "stage 1, 2, 3" are DeepSpeed's for Pos, Pos+g, Pos+g+p (DeepSpeed tutorial).

  • Pos (§5.1): split the optimizer states into Nd equal partitions; process i stores and updates only partition i, so it updates only 1/Nd of the fp32 master parameters, and an all-gather at the end of the step gives every process the full updated parameters.
  • Pg (§5.2): a process only needs the reduced gradients for the parameters it updates, so each layer's gradients, as soon as backward produces them, are reduced only onto their owner and then freed: a reduce-scatter. It is bucketed, like NVIDIA AMP's bucketed all-reduce, to overlap communication with the backward pass.
  • Pp (§5.3): each process stores only its own parameters and receives the others by broadcast from their owners just before forward and backward need them, discarding them after use. With enough devices, a model of any size fits.

Communication: why partitioning is nearly free

§7 Communication Analysis of ZeRO-DP

Partitioning would be pointless if it multiplied communication. The argument rests on how all-reduce is implemented (§7.1): the standard ring all-reduce is a reduce-scatter (each process ends up with the sum of one slice) followed by an all-gather (each process collects every summed slice), and each moves Ψ elements per process, so plain DP already moves 2Ψ per step. ZeRO splits that same all-reduce in two and puts work in between:

  • Pos+g (§7.2.1): reduce-scatter the gradients (Ψ), each process updates its slice, all-gather the updated parameters (Ψ): 2Ψ, exactly DP's volume. Pos alone is the same.
  • Pos+g+p (§7.2.2): the parameter all-gather is spread over the forward pass, each owner broadcasting its partition just before it is used, a total of Ψ; it has to happen again, in reverse order, for the backward pass, another Ψ; plus the gradient reduce-scatter, Ψ: 3Ψ, 1.5× DP, for memory that falls as 1/Nd.
ZeRO-3 keeps only 1/Nd of the parameters on each GPU, so every layer's weights must be fetched before its forward and again before its backward. Against plain DP's all-reduce, how much does a GPU send and receive per step?

1.5 times. DP's all-reduce is already a reduce-scatter plus an all-gather (2Ψ). ZeRO-3 keeps the reduce-scatter (Ψ) and replaces the one all-gather with two, one before forward and one before backward (2Ψ): 3Ψ in all. The volume does not grow with Nd because each GPU still receives each parameter once per pass, whoever owns it. Counted per process, as the paper does:

RS is the reduce-scatter of gradients and AG the all-gather of parameters, Ψ elements each. The paper's counts drop the ring's (N − 1)/N factor: at Nd = 64 an exact ring all-reduce moves 2 × 63/64 = Ψ, which changes no ratio. ZeRO-R: the residual states

§4.2, §6, §8

Once model states are partitioned, activations, buffers and fragmentation become the next bottleneck (§1). ZeRO-R has three parts:

  • Pa, partitioned activation checkpointing (§6.1). Model parallelism replicates activations: if a linear layer is split across two GPUs, each needs the whole input (§4.2.1). ZeRO-R partitions each checkpointed activation across the model-parallel GPUs after the forward pass of its layer and all-gathers it back when backward needs it, so activation memory falls by the MP degree. Large models have very high arithmetic intensity (computation per byte of checkpoint, at least 10K for GPT-2-sized models and growing with hidden size), which hides the data movement even over slow links. Pa+cpu goes further and offloads the partitioned checkpoints to CPU memory, for near-zero activation memory on GPU at 2× the data movement of Pa (§8).
  • CB, constant-size buffers (§6.2): libraries such as NVIDIA Apex and Megatron fuse all parameters into one buffer for efficient collectives, which costs memory in proportion to the model (a 3B model's 32-bit fused buffer is 12 GB); ZeRO uses a performance-efficient buffer of constant size once the model is large.
  • MD, memory defragmentation (§6.3): checkpoints are long-lived while recomputed activations are short-lived, and in backward parameter gradients are long-lived while activation gradients are short-lived; interleaving them fragments memory, causing out-of-memory errors and slow allocation. ZeRO pre-allocates contiguous buffers for checkpoints and gradients and copies them in as they are produced.

What Pa costs (§8). A Megatron-LM block with checkpointing does six all-reduces of sequence × hidden per sample (two in forward, two in the recomputation, two in backward), 12 × sequence × hidden of traffic since an all-reduce moves twice its message; Pa adds one all-gather of the block's input, sequence × hidden: 1/12 = %, "less than 10%". In return activation memory falls by the MP degree (up to 16 in a DGX-2), the batch can grow as much, and DP communication per sample falls by an order of magnitude. Pa+cpu pays off only when the DP traffic it saves exceeds its CPU transfers, generally at small batches; ZeRO decides per model.

§6.1 puts the 100B model's checkpoints at about 33 GB per GPU, cut by Pa at MP 16 to about 2 GB; at fp16 the arithmetic gives twice that (checked here).

ZeRO with model parallelism, and the step to a trillion

§1 "ZeRO and MP", §9

With ZeRO, MP is no longer needed just to fit a model: ZeRO-DP reduces per-device memory at least as well, and data parallelism needs no model rewrite, while Megatron-LM supports a limited set of operators and models (§1). MP still helps in two cases: with ZeRO-R it shrinks activation memory for very large models, and it keeps the total batch acceptable when DP alone would make it so large that convergence slows (beyond the critical batch size of McCandlish et al., reference 8). Combined, the maximum memory reduction per device is Nd × Nm.

The trillion-parameter arithmetic (§1, §9): 1T parameters × 16 bytes is about 16 TB of model states, and 16 TB / 1024 GPUs = GB per GPU (the paper rounds to 16 GB), within a 32 GB V100; so ZeRO-3 fits 1T on 1024 GPUs with DP alone, or with 16-way MP inside each DGX-2 node and 64-way ZeRO-DP across nodes (Table 1, Table 2; both rebuilt in the tables tab). Fitting is not training, though: BERT-Large can be trained in 67 minutes on a 1024-GPU DGX-2H cluster (NVIDIA, reference 26); 1T parameters is about 3000× BERT-Large's 330M (1T / 330M = ), so even with the same data and sequence length it would take 67 min × 3000 = days, "140 days", and in practice over a year. An exaflop system would be needed (§9). That is why the implementation targets about 100B.

Results

§10 Implementation and Evaluation

What was built. The paper implements and measures ZeRO-100B: Pos+g (stages 1 and 2) plus all of ZeRO-R, in PyTorch, as a wrapper around any torch.nn.Module, with no model changes, combinable with Megatron-LM's MP (§10.1). Stage 3 is analysed but not implemented here; the paper promised it for later (§1), and DeepSpeed released it as ZeRO-3 Offload on 7 March 2021 (DeepSpeed blog). Hardware: 400 V100 GPUs (25 DGX-2 nodes) with 800 Gbps between nodes. Baselines: PyTorch DDP without MP; Megatron-LM (the open-source version of September 2019) with MP. Models: GPT-2-like transformers, varying hidden size and layers (Table 4, appendix Tables 5 to 10).

  • Model size: 170B parameters run efficiently on 400 GPUs, against Megatron-LM alone, which "cannot scale efficiently beyond 40B" (§1, Figure 2); the paper calls this "over 8×". 170 / 40 is ×; the 8× matches §9's other statement that Megatron's largest efficient model is 16 to 20B in one DGX-2 node (170 / 20 = ×).
  • Speed: 15 PFLOPS sustained on average for 8B to 100B models, over 38 TFLOPS per GPU, over 30% of peak (400 × 38 = PFLOPS; 38 / 125 = %), and up to 10× Megatron's throughput at the same size, because Megatron's MP crosses nodes beyond 40B and drops below 5 TFLOPS per GPU (§10.2). Beyond 100B ZeRO slows slightly: not enough memory left for larger batches.
  • Super-linear scaling from 64 to 400 GPUs on a 60B model: doubling the GPUs more than doubles throughput (§10.3, Figure 3).
  • Usability: up to 13B parameters with no MP or PP at all, on 128 GPUs, at over 40 TFLOPS per GPU on average; without ZeRO the largest DP-only model is 1.4B at under 20 TFLOPS per GPU (§10.4, Figure 4). 13B is more than T5's 11B, the largest model in the literature at the time, and needs no NVLink or NVSwitch since there is no MP traffic.
  • Turing-NLG, 17B parameters, the largest language model as of 12 May 2020, trained end to end with ZeRO-100B at 41.4 TFLOPS per GPU, with a state-of-the-art perplexity of 10.21 (§10.6, Figure 5). The paper calls the benchmark "Webtext-103"; Microsoft's Turing-NLG announcement names it WikiText-103, and adds that ZeRO let them cut the MP degree from 16 to 4 and raise the batch per node fourfold.
  • The memory analysis holds (Table 2): the largest model measured with Pos is 6.2B on 64 GPUs against 7.6B in theory, for every MP degree. The paper says it "matches"; it is of the bound at every MP degree, the rest presumably the residual states the bound leaves out (the baseline measures 1.3B against 2B, 65%).

How much of this to believe

§5, §7, Table 2, §10

What holds up, and why. The core of the paper is arithmetic, not measurement, and the arithmetic is exact. The model-state accounting (16Ψ bytes) and every per-stage formula reproduce: Figure 1, all 54 cells of Table 1 and all 20 theoretical cells of Table 2 come out of §5's formulas (rebuilt here). The communication argument (§7) follows from how ring all-reduce is built, and the step simulation on this page, run on the paper's own schedule, lands on 2Ψ and 3Ψ. The memory model was also tested: the largest model measured with Pos stays at 81 to 82% of the bound across five MP degrees, so the bound predicts the trend even if it overstates the level (Table 2). And the authors are candid where it counts in their favour: they say plainly that ZeRO-100B implements only stages 1 and 2, that trillion-parameter training is out of reach for compute, not memory (§9), that Pa+cpu slows the 60B model down (§10.5), and that their Megatron baselines ran on fewer GPUs (appendix).

Where the evidence is weaker.

  • Single runs, no error bars. Every throughput figure (Figures 2, 3, 4 and 8) is reported as a single number per configuration: no repeats, variance or timing method are given, and the bars print no values, so "15 PFLOPS", "38 TFLOPS" and "up to 10×" cannot be checked beyond their own arithmetic (§10.2).
  • Not like for like. The 10× compares ZeRO plus MP inside a node against Megatron forced to cross nodes; much of the gap is the 24× bandwidth drop from NVSwitch to InfiniBand (§10.2). Batch sizes differ too: at 100B ZeRO runs 800 sequences per step against the baseline's 6 (Table 5). That is the point of the method (freed memory buys batch), but it means the speed-up mixes ZeRO's effect with a much larger batch. The baseline is the open-source Megatron-LM of September 2019 (§10.1).
  • Analysis presented next to measurement. The trillion-parameter result and stage 3's 1.5× are memory and volume calculations, not runs; stage 3 was not built here (§1). Communication is counted in volume, never measured in time. The abstract's "potential to scale beyond 1 Trillion" is worded as potential, but the title and §9 lean on it.
  • The paper disagrees with itself in places (every number checked): the 100B checkpoints are "around 60 GB" in §3.2 and "about 33 GB" in §6.1 (fp16 arithmetic gives 67 GB, and 4.2 GB rather than 2 GB after Pa); "about 8 GB" for GPT-2 with checkpointing is not derived (5 to 6 GB by the obvious counts); Table 4 misprints the 40B to 60B models' hidden size (4096 for the appendix's 6144); "over 8×" holds against §9's 16 to 20B baseline but is 4.25× against §1's own 40B; and the measured ZeRO-1 sizes the paper says "match" the bound are 81 to 82% of it. None of these touches the method; all are reporting slips.

How it held up (beyond the paper). Better than almost any systems paper of its year. The method shipped in DeepSpeed, stage 3 included from March 2021 (DeepSpeed blog), and PyTorch rebuilt it natively as FSDP (Zhao et al. 2023). Independent large runs used it as described: BLOOM with ZeRO stage 1 (BLOOM §3.4.2), DeepSeek-V3 with ZeRO-1 (DeepSeek-V3 §3.2), Llama 3 with ZeRO-2-style FSDP (Llama 3 §3.3.2). What did not become the frontier default is stage 3 on its own; those runs pair a low stage with tensor, pipeline or expert parallelism, which the paper itself anticipated (Then and now).

Verdict
Believe the memory accounting and the communication argument without reservation: they are exact, reproduce table for table, and every training stack since is built on them. Treat the headline speed-ups as single, unrepeated runs against a 2019 baseline that was pushed across nodes, and the trillion-parameter claim as analysis that later work (ZeRO-3 Offload, ZeRO-Infinity) had to make real.

Why it matters (beyond the paper)

This paper launched DeepSpeed and set the vocabulary, "ZeRO-1, 2, 3" and "stage 3", still used in every training stack (DeepSpeed ZeRO tutorial). Its core claim, that data parallelism's memory redundancy can be removed without giving up its communication efficiency or touching model code, became a default way to train large models, alone or alongside tensor parallelism. PyTorch FSDP is the native descendant, "motivated by the ZeroRedundancyOptimizer technique from DeepSpeed" (Zhao et al. 2023): FULL_SHARD is ZeRO-3, and SHARD_GRAD_OP shards gradients and optimizer states while keeping parameters gathered from forward to backward, ZeRO-2 style (FSDP docs); FSDP2's fully_shard shards parameters as DTensors (FSDP2 docs). The follow-ups pushed the same states down the memory hierarchy and cut stage 3's traffic: ZeRO-Offload (2021, CPU; arXiv 2101.06840), ZeRO-Infinity (2021, NVMe too, trillion-parameter fine-tuning on one DGX-2 node; arXiv 2104.07857) and ZeRO++ (2023, quantised and node-local collectives, 4× less communication; arXiv 2306.10209). Turing-NLG ran on it, BLOOM used ZeRO stage 1 (BLOOM §3.4.2) and DeepSeek-V3 uses ZeRO-1 data parallelism (DeepSeek-V3 §3.2). And §3's 16 bytes per parameter is still the back-of-envelope every practitioner uses to size a training run. Then and now has which stage each big run used, with the quotes, and the full follow-up line.

The baselines had an advantage, by the authors' account
The total GPU count must be a multiple of the MP degree, so some Megatron runs used 384 or 256 GPUs against ZeRO's 400; the 170B baseline ran on 256 GPUs with DP = 1, so it had no DP communication at all. Fewer GPUs means better communication throughput, and the comparison is per GPU, so the authors call it apples to apples with a slight edge to the baseline (appendix).

Two 100B checkpoint figures that disagree
For the 100B model of Table 4 (125 layers, hidden 8192) at batch 32, sequence 1024, MP 16, §6.1 says one checkpoint per block needs "about 33 GB" per GPU, cut by Pa to "about 2 GB" (the old summary repeated these). One checkpoint per block is 8192 × 1024 × 32 × 125 = × 109 values: 33 GB matches only at 1 byte per value. What survived, and what did not
The accounting survived intact: 16 bytes per parameter (or 20 with fp32 gradients, as MT-NLG counts them) is still how a run is sized. The schedule survived too: reduce-scatter, update a shard, all-gather is how every sharded optimizer works. What did not become the default for the very largest runs is ZeRO-3 on its own: of the four frontier reports above, three pair a low ZeRO stage (1, or 2-like) with tensor, pipeline or expert parallelism, keeping parameters gathered to avoid stage 3's extra all-gather, much as §1 anticipated when it said MP still helps for activations and batch size. ZeRO-3 and FULL_SHARD keep the niche §10.4 argued for, large models with no model-code changes. This is this page's reading of five reports, not a survey.
