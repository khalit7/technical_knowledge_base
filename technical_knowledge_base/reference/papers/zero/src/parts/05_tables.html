Table 3 and Figure 6: what each optimisation buys

[[S10.T3|Table 3, Figure 6, Table 7]]

The five configurations of {{Table 3|ax:S10.T3}} with the largest model each trained at MP 16 on 400 GPUs and batch 16 ({{Figure 6|ax:S10.F6}}). The sizes are the run configurations of appendix {{Table 7|ax:A0.T7}}, read from the table rather than off the bars, and agree with the bars and with §10.5's 40B, 60B, 140B and 150B. Model states per GPU are recomputed for each (Ψ/16 per model-parallel rank, Nd = 25); the rest of each 32 GB is activations, buffers and headroom.

Which optimisation buys what ({{§10.5|ax:S10.SS5}}, {{Table 3|ax:S10.T3}}). Five configurations, C1 to C5, add ZeRO pieces in turn at MP 16 and a fixed batch. The largest trainable model ({{Figure 6|ax:S10.F6}}) grows from 40B (C1: Pos, CB, MD) to 60B with Pa (C2, 16× less activation memory), to 140B with Pos+g (C4, which halves the model-state memory of C2) and to 150B with Pa+cpu (C5). Peak cached memory ({{Figure 7|ax:S10.F7}}) falls from C1 to C2 as expected; C4 to C5 lowers it for 100B but not for 40B, whose activations are too small for the offload to show. Throughput ({{Figure 8|ax:S10.F8}}) tracks memory, since freed memory buys batch, with one exception: C5 is slower than C4 for 60B, because CPU transfers cost more than they save; Pa+cpu is needed only when a model cannot run without it, such as 170B, and ZeRO turns it on only when it helps.

The baselines had an advantage, by the authors' account
The total GPU count must be a multiple of the MP degree, so some Megatron runs used 384 or 256 GPUs against ZeRO's 400; the 170B baseline ran on 256 GPUs with DP = 1, so it had no DP communication at all. Fewer GPUs means better communication throughput, and the comparison is per GPU, so the authors call it apples to apples with a slight edge to the baseline ({{appendix|ax:A0.T10}}).

Every number in the text, checked

Does not reproduce exactly: the 8 GB after checkpointing
Checkpointing one input per transformer block keeps 1600 × 32 × 1024 × 48 fp16 values, GB; adding one block's full activations for the recomputation gives GB. The paper's "about 8 GB" is in that range but is not derived; and "the square root of the total activations" cannot be read literally (the square root of 3 × 1010 values is under a megabyte). The two 100B checkpoint figures disagree with each other too: see the next box.
Two 100B checkpoint figures that disagree
For the 100B model of Table 4 (125 layers, hidden 8192) at batch 32, sequence 1024, MP 16, §6.1 says one checkpoint per block needs "about 33 GB" per GPU, cut by Pa to "about 2 GB" (the old summary repeated these). One checkpoint per block is 8192 × 1024 × 32 × 125 = × 109 values: 33 GB matches only at 1 byte per value. At fp16's 2 bytes it is GB ( GiB), which matches §3.2's "around 60 GB" for a 100B model with checkpointing, and Pa at MP 16 leaves GB, not 2. Both readings are shown; the factor of 16 holds either way.
