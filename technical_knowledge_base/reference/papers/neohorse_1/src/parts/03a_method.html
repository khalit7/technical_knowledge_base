Data from the routing harness

[[S3|§3]]

Agent post-training data is not a pile of instruction and response pairs: it is execution trajectories linking user requests, model reasoning, tool actions, environment observations and outcomes. The corpus centres on trajectories produced by the deployment harness, with public instruction, reasoning, tool-use, code and preference data added to broaden coverage ({{§3|ax:S3}}). The primary corpus is "on the order of 105 to 106" harness trajectories; the exact counts of trajectories and tokens are "recorded in the training manifest" and not printed ({{§3.1|ax:S3.SS1}}). Public sources cited include ToolACE, UltraFeedback (binarized, cleaned) and the Aya dataset.

Three granularities

The corpus is organised at three linked levels ({{§3.1|ax:S3.SS1}}):

  • Trajectory: a whole interaction run by the harness, with user requests, responses, tool calls, observations, recovery attempts and terminal outcome.
  • User turn: from one user request to the next (or to termination); the training unit. Tool results and harness-injected messages do not start a new turn.
  • Subscene: adjacent user turns that share a local goal; the unit for semantic labelling. It can capture a goal being continued, modified, interrupted or resumed within one conversation.

Every record stays linked to its parent trajectory and subscene, so quality, semantic, routing and outcome signals can each be attached at their own level. Within a user-turn record, the current request with its interleaved reasoning, tool calls and observations is kept whole; earlier visible responses and tool interactions stay as context, but reasoning from earlier turns is dropped, a convention also used by DeepSeek-V3.2 and Qwen ({{§3.1|ax:S3.SS1}}, {{§4.1|ax:S4.SS1}}). Quality gates

[[S3.SS2|§3.2]]

Before anything is judged, the corpus is deduplicated (exact and near-duplicate) and decontaminated: the same matching infrastructure screens every training candidate against the evaluation suites and removes overlaps from the training side ({{§3.2|ax:S3.SS2}}).

Structural validation is rule-based, because these properties can be read straight off the trajectory. At turn level the pipeline rebuilds requests, responses, tool calls, tool observations and terminal events, then checks payload readability, supported message structure, that a request and a response exist, causal event order, and that every tool call is closed by its result (matched through identifiers and execution branches). It flags missing responses, orphan observations, duplicated or conflicting tool-call identifiers, unresolved internal calls and ambiguous terminal branches. Each trajectory gets one of three outcomes:

OutcomeWhat happens
Internally completegoes straight to semantic evaluation
Partially recoverableonly its causally closed sub-trajectories are used
Quarantinedambiguous event ownership, or no recoverable supervision target

Structural validity guarantees reliable serialisation and replay; it says nothing about correct tool choice or task success. That is the job of semantic evaluation, which builds a normalised event stream and scores six independent dimensions: goal attainment, instruction adherence, tool use, evidence consistency, error recovery and termination. High-certainty failures (a missing final response, an unresolved tool call, an unrecovered terminal error) are caught deterministically; anything needing task-level interpretation goes to a semantic judge restricted to evidence present in the trajectory, and every finding must point at the events it rests on. Long trajectories are judged in segments and re-aggregated per turn, so an early failure can be told apart from a later recovery ({{§3.2|ax:S3.SS2}}).

Each dimension gets PASS, WARN, FAIL or NOT_EVALUATED, with evaluation coverage stored separately. Missing evidence or an interrupted judge call never becomes a positive verdict, and the result is kept as a structured record (structural state, six verdicts, coverage) rather than squeezed into one heuristic score; admission, review and quarantine policies are written over that record.

What the user wanted: Scene, Goal, Outcome

[[S3.SS3|§3.3]]

Separately from execution quality, each subscene is characterised on three axes ({{§3.3|ax:S3.SS3}}, {{Figure 3|ax:S3.F3}}):

Scene

What the user is doing and in what context. Closed taxonomies of task type and application domain (one primary value, up to two secondary), plus Use Context and Asking/Doing: does the request seek information or execution?

Goal

What the user expects and how success is judged: the objective decomposed into acceptance criteria, and cross-turn relations marking a goal as new, continued, modified, resumed or ambiguous.

Outcome

The verifiable result against the goal, so that "the task was actually satisfied" can be told apart from "the process ran to completion".

To control annotation noise, each attribute keeps its derivation method and confidence, and structural facts set by the source or by rules cannot be overwritten by a semantic judge. Structural quality, the turn's reasoning policy, loss masks and routing records stay as separate metadata.

Routing signals: predicted, decided, served

[[S3.SS4|§3.4]]

The harness router works per user turn and estimates capability demand from the current request, recent dialogue, earlier routing decisions and execution state. It assigns one of four service tiers ({{§3.4|ax:S3.SS4}}):

TierMeant for
C0bounded, low-risk requests
C1the general-purpose default
C2multi-step reasoning and execution
C3maximum capability or reliability (may combine several proposer models with an aggregator)

Policy controls may then adjust the assignment for risk, context pressure, an earlier failure or service limits. The tiers are relative demand under the routing policy, not fixed models: models, prices and inference settings change across deployments, so the tier semantics are versioned to keep old records interpretable.

For every turn the corpus keeps three separate fields: the router's raw prediction, the policy-adjusted decision, and the tier actually served. Joined to the semantic attributes, that gives a prediction, action, outcome record per turn. The separation matters for training: the model actually served also reflects user overrides, service availability and deployment policy, so the curriculum uses a re-estimated demand, not the served tier, as its ordering signal ({{§2.2|ax:S2.SS2}}, {{§4.2|ax:S4.SS2}}). Outcome fields, in turn, become the deficiency signals that drive allocation.

Capability-guided allocation

[[S3.SS5|§3.5]]

Quality dimensions, semantic attributes and routing tiers together form a stratification space. At each iteration the current checkpoint is evaluated on a stratified suite (kept disjoint from training by the decontamination screen), and results aggregated across attributes, quality dimensions, outcome states and routing tiers form a model-deficiency profile. The next training mixture shifts toward the regions where the model underperforms while keeping broad coverage: verified successes supply positive supervision, informative failures mark regions that need more or rebalanced data. Allocation changes the composition of the data, not the objective. Between iterations the harness keeps adding trajectories through the same pipeline, old and new data are reallocated together, and updated checkpoints returning to the harness reveal the next gaps ({{§3.5|ax:S3.SS5}}).

Described, not measured
Allocation is the step that makes this a loop, and the paper gives no number for it: no deficiency profile, no before and after mixture, and no run with allocation switched off. The authors say the results "reflect a single pass of the evaluation–selection–update loop" ({{§6|ax:S6}}).
