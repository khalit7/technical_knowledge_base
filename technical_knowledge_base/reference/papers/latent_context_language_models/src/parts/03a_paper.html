Problem

[[S1|§1, §2]]

Long-context inference is bottlenecked by memory, because the KV cache grows with context length ({{§1|ax:S1}}). For the decoder used throughout this paper, Qwen3-4B-Instruct-2507 (36 layers, 8 key-value heads of 128 dimensions), every token of context costs of keys and values in bf16, so a 256K-token prompt needs of cache before the model writes a word (derived from the released {{decoder config|https://huggingface.co/latent-context/0.6b-4b-LCLM-16x/tree/main/decoder}}: 2 × 36 × 8 × 128 × 2 bytes).

The established fix is KV cache compression: prefill normally, then evict entries by some heuristic (SnapKV, Expected Attention, KVzip, Attention Matching; {{§2|ax:S2}}, {{Appendix B|ax:A2}}). It has four practical problems the paper is blunt about:

  • The expensive part still happens. Most methods need the full context to fit in the window and to be prefilled first; some need prefill passes two to three times longer than the input (KVzip reconstructs the context to score it; {{§2|ax:S2}}).
  • Query-dependent caches do not survive a second turn. SnapKV in its query-aware form keeps what one question attended to, so the cache is tuned to that question.
  • Non-uniform eviction cannot shrink the sequence. Methods that evict different entries in different heads and layers (KVzip) cannot cut the sequence-length dimension, so they mask evicted positions instead and forfeit the memory and throughput benefit in a paged-attention engine (see the {{PagedAttention page|n:3c65c17b0d0d81bf8b90ca93fee19f5f}}).
  • Engines do not run them. They are largely unsupported in vLLM and SGLang.

The paper adds a distinction worth keeping: algorithmic or theoretical cache reduction (entries masked or subsampled from a full cache, non-uniform per head) is not systems-realisable cache reduction, which needs kernels that "have not been released or even implemented" ({{§6.1|ax:S6.SS1}}).

The alternative is soft-token compression: an encoder turns raw tokens into a much shorter sequence of continuous embeddings, which the decoder reads in place of the context. In principle this is better shaped: compression is parallelisable, it works in standard inference engines, and it can extend the decoder past its native context length. In practice the existing methods (gist tokens, ICAE, AutoCompressor, xRAG, REFRAG and others) either degraded the base model noticeably or only worked after task-specific finetuning, so they lost to KV cache compression on the accuracy-efficiency frontier; none was tested on information-dense long-context suites such as RULER ({{§1|ax:S1}}, {{§2|ax:S2}}).

The question: is that loss intrinsic to the encoder-decoder shape, or did nobody train one properly? Can a general, task-agnostic compressor keep a strong model's abilities?

At a 4K-token prompt, which reaches the first output token sooner?

Not compressing. Every KV method first does the full prefill and then adds scoring work on top, so its time to first token (TTFT) can only be at or above the uncompressed model's. Architecture

[[S3|§3, Eq. 1]]

An LCLM is three trained parts in a row ({{§3|ax:S3}}, {{Figure 3 left|ax:S4.F3}}):

  1. An encoder reads the input in windows of W tokens: I = ⌈T/W⌉ windows, each processed in its own forward pass ({{Eq. 1|ax:S3.E1}}).
  2. A pooling operator turns each contiguous block of N tokens into one latent token: a window of |wi| tokens yields Mi = ⌈|wi|/N⌉ latents. N is the compression ratio.
  3. An adapter projects each latent from the encoder's width to the decoder's, and the decoder reads the projected latents s1:M in place of the original tokens.

The encoder window W is a separate knob from the ratio N. With W = N, as in prior work (REFRAG, the work of Liao et al.), each forward pass sees only the block it compresses. With W = T the encoder reads the whole input at once. The paper settles on W = 1,024 at N = 16: each latent summarises 16 tokens that were read in the context of up to 1,024. The three pooling operators of the search ({{Appendix D.1|ax:A4.SS1}}):

  • Token pooling (EOS or CLS): append one learned pooling token per latent to the window and keep its final hidden state (Eq. 2 to 3). Most prior work does this.
  • Mean pooling: average the hidden states over each block of N (Eq. 4 to 5). Common in vision and multimodal models.
  • Concatenation: stack the N hidden states into one vector of width N·denc, and widen the adapter's first layer to match (Eq. 6), like Qwen's patch merger.

The adapter is the LLaVA-style projector: RMSNorm, then a two-layer MLP with GELU, applied to each latent on its own, sm = W2 GELU(W1 RMSNorm(zm) + b1) + b2 ({{Eq. 7 to 8|ax:A4.SS2}}). In the released 16x checkpoint it maps 1,024 dimensions to 2,560 through a hidden width of 2,560: parameters (shapes from the {{adapter weights' header|https://huggingface.co/latent-context/0.6b-4b-LCLM-16x/tree/main/adapter}}). The attention-based alternative adds one self-attention layer over the latents before the MLP (Eq. 9 to 11).

One long prompt, two pipelines

The structural reason this can beat KV compression on speed: KV methods compress after the decoder has paid for the whole prefill, while an LCLM compresses before, so a higher ratio directly removes decoder work ({{§6.2|ax:S6.SS2}}).
