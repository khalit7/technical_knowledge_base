SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

Haozhe Liu, Tian Ye (equal contribution), Sensen Gao, Qihang Cao, Yitong Li (core contributors), Mingchen Zhuge, Duomin Wang, Ruihua Zhang, Ping Luo, Jiawang Bian, Lei Zhu, Ligeng Zhu, Enze Xie, Song Han
NVIDIA, NTU, MIT · 17 September 2026 (arXiv v1, the only version on 3 October 2026)

In one line: Apply recursive self-improvement at the harness layer rather than to the model: auto-research loops across varied environments discover four reusable efficiency techniques (action execution, context compaction, observation handling, delegated reading) that cut recorded token traffic 44.7 to 49.0% at parity on EdgeBench, saving $8.75 to $13.50 per hour against native Codex and Claude Code.

Problem: long-running agents re-send their own history

§1 Introduction

A coding agent that works for hours is a loop: the model reads the whole conversation so far, chooses a tool call, the harness runs it and appends the result, and the model reads everything again. The harness is the program around the model that decides what the model sees and which actions it can take (Codex, Claude Code, OpenCode and Pi are harnesses). Because every request re-sends the accumulated context, cost grows with the length of the trajectory, and the paper calls task-level token efficiency "a first-order systems concern" (§1).

Most efficiency work lowers the price of a token: faster attention kernels and serving, quantisation, cheaper models. This paper lowers the number of tokens instead, by changing only the harness: no training, no new model (§1). The difficulty it names is that harness choices are coupled. Tool use, context management, verification, delegation and termination interact, so "a change that is locally beneficial may cause downstream failures or shift token costs to later stages", and finding such changes by hand means reading long traces (§1).

Automated harness search already exists. Meta-Harness searches over harness programs, Recursive Harness Self-Improvement refines prompt-level specifications per task, and a held-out study found that evolved harnesses overfit the tasks used in search and give "only marginal gains on unseen tasks" (§1, citing Wang et al. 2026). SoL-Pi's question is narrower and testable: can an automated search find harness changes that save tokens and transfer to tasks and models it never saw?

Idea: recursive self-improvement, one layer up, aimed at cost

§2.1

Recursive self-improvement (RSI) usually means a model improving the next model. SoL-Pi applies the loop to the harness: a research AI reads execution traces of an agent running the base harness (Pi), proposes changes, implements them and tests them in prepared environments, and only changes that survive selection are kept (Figure 1(a)). The weights never change.

The target is constrained efficiency. Before the search starts, the capability metrics, their tolerances and the efficiency metrics are fixed and kept out of the optimising agent's reach. A candidate passes two gates in order: every capability metric stays within its tolerance, then at least one efficiency metric improves; among those that pass, the nondominated ones are kept (§2.1). An efficiency change has a cheap automatic check (did it cost less and still pass?), which a capability change does not; that is why the loop could run largely unattended.

After Figure 2 and the blog's lineage diagram (blog, Method). Held-out results "never feed back into the Auto-Research Loops: a failed validation rejects the candidate without triggering further optimization" (§2.1).

Three principles organise it (§1): breadth and depth (many hypotheses, then repeated implementation and hardening of the promising ones), independent validation (held-out evidence only after a candidate is frozen), and scalable orchestration (isolated, disposable lineages so one failure does not spread). The claim to test is generalisation: a mechanism found this way should transfer because it targets how agents burn tokens, not anything about a particular task.

The search: 152 directions, 535 environments, four survivors

§2.2

Outer stage, breadth. The search started from 152 proposed directions in six families: context, progress, tools, delegation, prompt and policy, and improvement and evaluation (§2.2). The blog lists every title; by family they are 24, 26, 26, 15, 15 and 46 (blog, proposal pool; the sum is 152). Before any rollout budget is spent, Oracle Analysis reads existing trajectories to estimate avoidable work, and each selected direction must name a concrete source of overhead. A family records where an idea started, not where it ends up: ObservationPack began as two context ideas (C23 and C24 in the blog) and became a change at the observation boundary.

Inner stage, depth. Each selected direction runs its own lineage of Karpathy's autoresearch loop (propose, implement, run a fixed experiment, inspect, keep or discard), extended with a Ralph Loop for implementation (iterate until an explicit completion criterion passes, then an independent reviewer checks it; a failed review means revision) and map-reduce analysis (independent analysers read one trajectory each for repeated actions, context growth, large observations or sparse diagnostic signals; a reducer merges them) (§2.2).

Orchestration. Each lineage is a disposable copy of one shared skill template: copy, set parameters, run to completion, keep the candidate and its evidence, discard the modified orchestration code (§2.2). The blog says this was the third design: a YAML-compiled workflow kept stopping for human repair, and a long-lived coordinator written by a lead agent grew until launching a new experiment "could require more than ten hours of changes to it" (blog, From compiled workflows).

Environments. §2.3 The search set is 535 executable environments: 495 repository tasks built from GitHub issue and pull-request pairs (pre-fix repository, offline dependencies, hidden regression test; kept only if the test fails before the accepted patch and passes after it) and 40 synthetic tasks built around a verifier written first, mostly with a Terminal-Bench-2-style interface (§2.3, Figure 3). EdgeBench is not used as a source or template for any of them (blog).

Scale. About 150 directions and about 500 environments, "more than 3,000 runs and more than 60,000 agent-environment interactions" (§1). The authors add that these counts "describe the scope of our search; they do not establish a scaling law" (§2.2). The blog puts the survival rate at "about one out of every forty starting ideas" (4 of 152 is 1 in 38) and reports that a single deep lineage, even with GPT-5.6 Sol at xhigh, tended to get stuck in a local basin after five to ten iterations, while breadth occasionally exposed an unusual idea worth hardening (blog, Breadth escapes local search basins).

Humans in the loop. The blog calls SoL-Pi "a hybrid auto-research loop": humans supplied early priors, filtered out low-value directions such as tuning the base harness's hyperparameters before the pool was scaled, and, once a mechanism survived, read it and refactored its code into the released implementation (blog, Humans set priors). The paper does not say how much of each mechanism's final form is human refactoring.

The four mechanisms

§2.4

Four mechanisms passed capability-constrained selection, each at a different point in the agent-environment loop (Figure 4). Each is a Pi extension in the released code, and the constants below are the code's.

1. Action Fusion (tools)

Pi often edits a file and then, in a separate model turn, runs a test or build. Action Fusion adds an optional follow-up command to the edit and write tools, so both run in one call and return one observation: three API calls become two. Commands that need to inspect the edit's result stay separate (§2.4).

Before: edit, model turn, run. After: edit and run, one turn.

2. Online Context Compact (context)

The agent keeps a plan through an update_plan tool. When a plan step completes, the harness estimates the remaining requests from the observed requests per step, caps the estimate by the requests left before the context window fills, and compacts with Pi's native compaction only if the projected input savings repay the cost of rewriting the prompt cache. Later compactions must clear a larger margin and repay earlier rewrite debt (§2.4). The gate prices the cache rewrite, not the summarisation call itself (§2.5).

Before: compact only near the window limit. After: compact at subtask boundaries when it pays.

3. ObservationPack (observations)

A tool result larger than 10 KiB is archived locally and sent in full for the next two provider requests; from the third request on it is replaced by a stable handle, its size, and an excerpt of whole lines from its head and tail (1,024 bytes in all). The agent can page the exact original back with obs_recall. Smaller results are untouched (§2.4).

Before: a 40 KB file dump rides along in every later request. After: a 1 KB stub.

4. Evidence-Preserving Reducer (delegation)

Build and test logs of at least 4 KiB from a predefined set of commands (pytest, cargo, make, lean and so on in the code) are archived and handed to a cheaper model (GPT-5.6 Luna at high) that writes a compact receipt of the key evidence. A deterministic verifier checks the receipt's schema, source hash, exit status, exact quotes and size; on any failure, suspected credentials, or no size reduction, the agent gets the original log. File reads and searches bypass it (§2.4, §2.5).

Before: the frontier model reads the whole log. After: it reads verified quotes.

They compose in a fixed order: the reducer processes a tool result first, and ObservationPack recognises the receipt marker and leaves receipts alone (§2.4). The first summary of this paper described the fourth mechanism as handing "bulk reading" to a subordinate; in fact file reads and searches bypass it, and only long build and test logs are delegated. None of the four is new as an idea (AgentDiet, ACON and Context-Folding prune or compress trajectories, §4.3); the contribution is that a loop found, tested and kept them.

The Replay a session tab runs all four on one illustrative session with the released constants and the compaction gate ported from the code (checked identical to the original on 50,000 random inputs), so you can watch where each one saves and where one costs.

ObservationPack swaps a large result for a 1 KB stub after two requests. Under prompt caching, what does that do to the cache-write traffic?

It raises it. A prompt cache matches the longest identical prefix of the previous request. Replacing a message in the middle changes the prefix from that point on, so everything after it is written to the cache again (at 12.5 times the price of reading it, for Anthropic's list prices). The paper's own table shows the trade: with GPT-5.6 Sol, the full stack cut cache reads from 2.1326 B to 1.0605 B tokens while cache writes rose from 0.0141 B to 0.0316 B, and total cost still fell from $1,339 to $894 (§3.4, Cache reuse). ObservationPack alone raised GPT-5.6 Sol cache writes from 0.0141 B to 0.0160 B (Table 4).

EdgeBench: half the tokens, a third off the bill, a few points of score

§3.1

The benchmark. EdgeBench (ByteDance Seed) has 134 day-scale tasks, of which 51 are public; agents submit repeatedly within a time budget, get feedback, and the best submission is the score; a stop hook prevents them from quitting early. SoL-Pi uses the 51 public tasks (§3.1). The paper says 11 of them were used for "one-way acceptance of frozen candidates" and the other 40 "reserved for final evaluation" (§2.5); the tables, however, report all 51 (see How much to believe). Costs use API prices as of 17 August 2026 (Table 1 note). The first summary said September prices; the paper says August.

Two operating points. SoL-Pi [Efficiency] is the fixed four-mechanism stack. SoL-Pi [Performance] is the single mechanism with the highest average score in the add-one table, chosen separately per model: ObservationPack for GPT-5.6 Sol, Action Fusion for Opus 5 (§3.1, Table 2).

With GPT-5.6 Sol, the full stack used 1.10 B tokens against Pi's 2.15 B (49.0% fewer), cost $894 against $1,339 (33.2% less) and scored 42.003 against 44.833, which the paper reports as "retaining 93.7% of Pi's average score" (§3.1). The harness was then run unchanged on Opus 5, a model the search never saw: 44.7% fewer tokens, 33.5% lower cost, 94.3% of Pi's score (Table 2). The authors call this "preliminary evidence of transfer to an unseen LLM backend" (§3.1). The Performance points instead raise the score (47.2 and 50.5, against 44.8 for Pi) at smaller savings (6.1% and 11.3% fewer tokens).

The model's own native harnesses are much more expensive than Pi here: Codex used 3.05 B tokens and $1,787 for a score of 34.7 with GPT-5.6 Sol; Claude Code 2.00 B tokens and $2,535 for 43.7 with Opus 5. Against them the full stack costs 50.0% and 54.3% less (Figure 1(b)), and with GPT-5.6 Sol it also scores higher than Codex. The paper's third-party harnesses (OpenSquilla, Oh-My-Pi, OpenCode, Oh-My-Opencode) all scored below Pi, between 24.5 and 38.5 (Table 1).

Why half the tokens is a third of the dollars

§3.4
On Opus 5, SoL-Pi sends 44.7% fewer recorded tokens than Pi. By how much does the bill fall?

About a third (33.5%). "Recorded token traffic" adds up four kinds of token at very different prices. Almost all of it, 97.9% for Pi on Opus 5, is cache reads: the unchanged prefix of the conversation re-read on every request, billed at a tenth of the input price. The table's dollar figures fit Anthropic-style list prices exactly: $0.50 per million cache reads, $6.25 cache writes, $25 output, residuals under $3 on all seven Opus 5 rows (the check). So the saving below is mostly cheap tokens:

This is also the right reading of the first summary's caveat that "recorded token traffic is not the same as billed tokens once cache behaviour is accounted for". The paper does account for it: its cost column prices each kind of token separately, and the 33% figure is the billed one. What the 44.7 to 49.0% headline counts is mostly re-read cache. The mechanisms trade some of it for extra cache writes (the full stack more than doubled GPT-5.6 Sol's cache-write traffic, 0.0141 B to 0.0316 B), and the paper argues for judging "the full task cost alongside task quality, rather than cache reuse alone" (§3.4).

The GPT-5.6 Sol costs do not fit any fixed price per token type: the best least-squares fit over the 11 distinct rows misses by up to $225 and needs a negative input price. Whatever the GPT-5.6 Sol price sheet was (a long-context tier, for instance), the paper does not state it, so its GPT-5.6 Sol dollar figures cannot be recomputed from its token counts; the Opus 5 ones can.

The abstract says SoL-Pi saves $8.75 to $13.50 per hour against Codex and Claude Code. Where does "per hour" come from?

The paper never says, but one constant reproduces all four printed figures: the total cost difference divided by 102 hours, that is 51 tasks run for two hours each (EdgeBench's "@2h" budget, which is also the setting of the paper's GPT-5.5 reference row).

The Opus 5 figure against Pi, $5.71, comes out at $5.716; the printed costs are whole dollars, so the difference is only known to about $1 and $5.71 is within that. The blog adds that the range "reflects the model backend and is calculated using official API-equivalent pricing" and frames it as savings "for a professional researcher working on a single problem" (blog). It is a rate under a fixed time budget, not a measured hourly bill: EdgeBench runs until the budget ends, so a cheaper harness spends less over the same two hours rather than finishing sooner.

Terminal-Bench 4, IMO 2026, and an agent swarm

§3.2

Terminal-Bench 4 (63 CPU-only tasks; GPU tasks excluded for infrastructure reasons): Codex and Pi each solved 18, SoL-Pi solved 15. SoL-Pi's total model cost was 26.3% lower than Pi's ($211.12 against $286.45) and its cost per solved task 11.6% lower ($14.07 against $15.91) (Table 3). The paper reads this as efficiency gains that "generalize beyond EdgeBench" (§3.2); it is also three fewer tasks solved, and Codex solved as many as Pi for less.

IMO 2026 with GPT-5.6 Sol at xhigh, each proof formalised and checked in Lean 4, 150 minutes per problem: Codex passed 5 of 6 ($114.47), Pi 3 ($75.95), SoL-Pi 3 ($62.69). SoL-Pi has the lowest cost per passed problem, $20.90 against $22.89 for Codex and $25.32 for Pi (Table 3); Codex passed two more problems.

Swarm. §3.3 On Anthropic's original performance take-home (a kernel to optimise, scored in simulated machine cycles; the frozen starter takes 147,734), three configurations ran one two-hour trial each: a single Codex agent; a Codex coordinator with 20 Pi workers; a Codex coordinator with 20 SoL-Pi workers. Coordinators and the single agent used GPT-5.6 Sol at xhigh, workers GPT-5.6 Luna at xhigh, in five groups of four with shared group boards; the shared best advanced only when an independent check confirmed a strict improvement (§3.3, Figure 5). Results: the SoL-Pi swarm reached 1,127 cycles for $60.11, the single agent 1,333 for $39.20, the Pi swarm 1,366 for $82.12. All candidates passed the correctness check; the SoL-Pi swarm and the single agent passed all eight speed thresholds, the Pi swarm seven (it missed "fewer than 1,363 cycles"). The SoL-Pi swarm cost 26.8% less than the Pi swarm (§3.3). One run per arm; the blog adds that the two control trials ran one after the other, single agent first (blog).

Each mechanism alone, and how they behave together

§3.4

An add-one evaluation adds each mechanism to Pi on its own (Table 4). Every one cut total tokens under both models, and every one lowered cost per score point; the full stack had the lowest tokens and cost in both blocks (§3.4). Online Context Compact did the most alone on GPT-5.6 Sol (40.2% fewer tokens), ObservationPack on Opus 5 (39.2%). The single-mechanism scores spread widely, from 41.99 to 47.21 with GPT-5.6 Sol and from 43.41 to 50.48 with Opus 5, around Pi's 44.8; the paper reports no repeat runs, so how much of that spread is noise is unknown. All rows are in the tables tab.

Activation differs by model. Figure 6 measures how often each mechanism fired. Trigger rate is the share of tasks where it fired at least once, intensity the mean number of firings on those tasks (§3.4). Both were lower on Opus 5 for every mechanism, most strongly for Online Context Compact (92.2% of tasks with GPT-5.6 Sol, 33.3% with Opus 5) and Action Fusion's intensity (70.58 firings per triggered task against 13.54). The authors suggest this "may reflect the harness being optimized exclusively on GPT-5.6 Sol trajectories"; each mechanism still improved token efficiency on the tasks where it fired (Figure 6). Combined, ObservationPack fired on fewer tasks (80.4% alone, 56.9% in the stack), plausibly because the reducer handles the same large outputs first, and every mechanism showed a larger efficiency gain on its triggered tasks in the stack than alone (for example ObservationPack 10.2% alone, 28.7% in the stack); the authors note that comparing each configuration on its own triggered subset "does not isolate interaction effects" (Figure 7). Both figures are rebuilt in the tables tab.

One lineage: how Action Fusion was found and kept

§3.5

Action Fusion's lineage took 27 recorded iterations in four stages (Figure 8, §3.5):

  1. Oracle analysis (1 iteration). Adjacent edit-or-write then command pairs made up 12.3% of cross-turn transitions, and bash was 85.1% of the next actions. If all 149 observed candidates had fused, model turns would fall from 1,386 to 1,237 (10.8%) and tokens from 32.38 M to 28.64 M (11.5%): a projection from recorded trajectories, "not a measured rerun" (blog).
  2. Baseline build (6). Prompt-only triggering was unreliable, so the agent extended the tool schema to expose the fused action directly: 87.7% uptake on eligible calls and no invalid calls.
  3. Prompt and schema optimisation (18 explorations, 10 retained batches). Trigger rate moved non-monotonically between 28.3% and 100%; the agent introduced trigger rate as an intermediate acceptance metric alongside task score. Batch 10 was selected (100% trigger rate, task score 87.0); batch 9 had the higher score (88.9) at a 66.7% trigger rate.
  4. Final validation (2). Independent checks, then held-out validation, then the mechanism joined the stack.

The paper's point is that a lineage-local loop can stabilise a mechanism's interface and invent its own intermediate metric (§3.5). ObservationPack's lineage, in the blog, went through a clean-room rebuild, a freeze to 315 lines and two hooks, an eight-configuration sweep where only "V2" stayed inside the quality gate, and an 11-task paired run on EdgeBench (provider bill 23.58% lower, normalised score 22.92% higher). The blog describes V2 as a 2,048-byte head and 1,536-byte tail; the paper's Figure 4 and the released code use a 1 KB excerpt (512 bytes each), so the released mechanism may not be the swept V2 (blog, ObservationPack).

How much of this to believe

What holds up.

  • The mechanisms are real and inspectable. All four are released as small, tested Pi extensions under MIT (NVlabs/SoL-Pi), and their constants match the paper (10 KiB threshold, two full sends, 1 KB excerpt, 4 KiB log minimum, a cache-priced compaction gate). This page's port of the compaction gate gives identical decisions to the released code on 50,000 random inputs.
  • The direction of the token saving is consistent. Every one of the four mechanisms cut total tokens under both models, and the full stack cut the most in both (Table 4). The tables are internally consistent: totals equal the sum of the four token types, and the $/score column is cost divided by the summed score of 51 tasks, in every row.
  • The cost saving reproduces from the token counts. For Opus 5 the dollar column is exactly list prices times tokens (residuals under $3), so the 33.5% cost cut against Pi follows from the token table and is not an estimate layered on top.
  • Transfer to a second model, unsearched. The stack was frozen on GPT-5.6 Sol trajectories and run unchanged on Opus 5 with a similar trade-off. The authors call this preliminary themselves, and say the mechanisms fire less there (§3.4, §5.1). That candour, and the limitations section's note that the counts "do not establish a scaling law", count in their favour.

What is weaker than it reads.

  • Single runs, no error bars. Every number is one run per configuration: EdgeBench, Terminal-Bench 4, IMO and the swarm (§3). The add-one scores spread 41.99 to 47.21 (GPT-5.6 Sol) and 43.41 to 50.48 (Opus 5) around Pi's 44.8, for harnesses that differ by one mechanism; without repeats, a 2.8-point drop can be neither confirmed nor dismissed as noise.
  • "Comparable" is a drop of 2.5 to 2.8 points. 42.003 against 44.833 and 42.224 against 44.756 (93.7% and 94.3%). The blog says the per-mechanism gate permits "small losses" that "can accumulate once mechanisms combine" (blog). The first summary said "at parity"; that overstates it.
  • The "Performance" point is chosen on the test benchmark. It is the highest-scoring of four add-one variants on EdgeBench, picked per model from Table 4. The conclusion's "improve model performance by 5.3-12.8% and token efficiency by 9.8-18.2%" (§5) quotes those best-of-four picks, a selection effect.
  • "Held-out" includes the acceptance tasks. Section 2.5 says 11 of EdgeBench's 51 tasks were used for one-way acceptance of frozen candidates and 40 reserved for final evaluation (§2.5); ObservationPack's paired acceptance run in the blog used 11 EdgeBench tasks. Yet the $/score column divides by 51 task scores in every row, and Figure 6's trigger rates are all whole numbers of 51 tasks (78.4% = 40/51, 33.3% = 17/51). The reported results therefore include the tasks that decided acceptance. One-way acceptance cannot tune a candidate, but it does select among them.
  • The hourly dollars are derived, not measured. They equal cost differences over 102 hours (51 tasks × 2 hours), at API prices of 17 August 2026; the paper does not state the divisor.
  • The other benchmarks cut both ways. On Terminal-Bench 4 SoL-Pi solved 15 tasks against 18 for Pi and Codex; on IMO 2026 it passed 3 of 6 against Codex's 5; its wins there are cost per solved task, on one run each (Table 3).
  • The search's own cost is not reported. More than 3,000 runs and 60,000 agent-environment interactions (§1), driven by GPT-5.6 Sol at xhigh, and no dollar or token total. The limitations section says only that complete loops are "computationally expensive" (§5.1). Whether the search pays for itself depends on how much agent time later runs on SoL-Pi.
  • Prices only reproduce for one model. The GPT-5.6 Sol cost column fits no fixed price list (residuals up to $225), so its dollars cannot be checked against its tokens.
  • Nothing to rerun the study. The mechanisms are released; the 535 search environments, trajectories, research prompts and per-task EdgeBench results are not.
  • Small inconsistencies. The blog's ObservationPack configuration (2,048-byte head, 1,536-byte tail) differs from the paper and code (1,024 bytes); the blog also calls EdgeBench fully reserved for held-out evaluation while describing an 11-task EdgeBench acceptance run.

Verdict. Believe that a harness can shed about half of its recorded token traffic, almost all of it re-read cache, for about a third off the bill, and that these four mechanisms do it on long tasks with two different frontier models. Treat the score cost (a few points), the "Performance" gains and the dollar-per-hour framing as single-run, partly selected numbers, and expect the size of the saving to depend on your model, prices and task lengths.

What it takes to use this

  • Code and licence. github.com/NVlabs/SoL-Pi, MIT, an extension for Pi tested against @earendil-works/pi-coding-agent 0.85.1 with Node.js 22.19 or newer; install with pi install git:github.com/NVlabs/SoL-Pi. Every mechanism is off until enabled in sol-pi.json (README, checked 3 October 2026).
  • Start conservative. The README's suggested first configuration enables only Action Fusion and ObservationPack, the two that make no extra model calls and never stop a run. Evidence-Preserving Reducer sends eligible log content to the configured reducer model (by default GPT-5.6 Luna through the Codex provider); the README says not to enable it for logs that must stay local.
  • Set the cache price ratio for your provider. Online Context Compact decides with one number, cacheWriteReadRatio, default 12.5 (Anthropic's $6.25 against $0.50); the documentation says it "drives one runtime decision and is not a cost report". A provider with a different cache pricing needs a different value.
  • Archives stay on disk. ObservationPack and the reducer keep exact copies of large outputs under the session directory and do not delete them when the session ends.
  • When it pays. Long sessions with large tool outputs, repeated test runs and many plan steps: the savings come from not re-sending context, so they grow with session length. The paper chose EdgeBench because tasks run for hours; the blog notes that on benchmarks that finish within an hour the overhead "has little time to accumulate".
  • When it buys little or costs. Short tasks; models that ignore the plan tool (Online Context Compact fired on a third of tasks with Opus 5); workloads where a few score points matter more than a third of the bill; and, from this page's simulation, sessions that already hit the window limit, where Pi's own compaction does part of the work.
  • Reproducing the search is not possible from the release: no environments, prompts or traces, and no reported budget.

Why it matters (beyond the paper)

The first summary called this the first result to put a number on how much of an agent's cost is harness inefficiency rather than model inefficiency. "First" is unconfirmed (Meta-Harness already tracks context cost on a Pareto front, §4.2), but the number is large: about half the recorded tokens and a third of the cost, at a few points of score. The paper's own table shows an even larger harness effect it does not dwell on: with the same model, the native Codex harness used 2.8 times SoL-Pi's tokens for a lower score (Table 1).

It also answers, at small scale, the open question that Topic: agentic-harnesses has carried since 2026-08-31: whether anyone had run the harness-improvement loop end to end. SoL-Pi runs it, but at the efficiency layer rather than the capability layer, which is the easier half: an efficiency change has a cheap automatic verifier (did it cost less and still pass?), where a capability change does not. The authors' next step makes that the point: use SoL-Pi as the starting harness of the next search, so lower per-run cost buys more environments and ideas, which they call "recursive efficient improvement" and describe as "a long-term research vision rather than a compounding effect demonstrated by the present study" (§5.1). They also propose "pretraining the harness" on an expanding stream of environments and training it on several models at once (§5.1).

No trajectories were released, so this tab replays one illustrative session (12 plan steps, about 200 model requests of reads, searches, edits, test runs and plan updates; sizes drawn from a fixed seed) under Pi and under each mechanism. What comes from the paper and the released code: the rules and constants of the four mechanisms (10 KiB threshold and two full sends for ObservationPack, its 1 KB stub, 4 KiB logs for the reducer with verified receipts and fallback, Action Fusion's merged edit and run, Online Context Compact's gate ported line for line and checked against the original), Pi's 20,000-token kept tail and window reserve, and the price list (Opus 5 list prices, which reproduce the paper's Opus 5 dollar column exactly). What is illustrative: the session, the receipt size (450 tokens), the share of receipts that verify (90%), the reducer's price ($1 and $5 per million), how often a stubbed result is recalled (12%), and the context window. Each request re-sends the whole conversation; the part identical to the previous request is a cache read, the rest is a cache write.

Try: play Pi, then the full stack, on the same session; step through plan steps and watch the bars (each bar is one request's prompt, to scale). Then switch the window to 200K and look at ObservationPack and the reducer alone.

Which mechanism should save the most here, on its own?

In this session, Online Context Compact, because the cost of a request is dominated by re-reading the conversation, and compaction is the only mechanism that shrinks all of it. The paper agrees for GPT-5.6 Sol (40.2% fewer tokens alone, Table 4) but not for Opus 5, where it fired on only a third of tasks and ObservationPack saved more (39.2%). Inside Online Context Compact's gate

At each completed plan step the gate asks one question: will the input saved by compacting now repay rewriting the cache? Compacting turns a long cached prefix (cheap to re-read) into a short one that must be written again (12.5 times the read price by default). The function below is the released decideCompaction (economics.ts), ported; set its inputs and read its decision. Defaults: a 120,000-token context of which 95% of the part older than the kept 20,000-token tail (95,000 tokens) can be summarised into a 1,000-token memo, 14 requests per completed step, 6 steps left.

The paper

SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness (arXiv HTML v1)

Preprint, arXiv cs.AI, 15 pages, the paper itself; the HTML version has the anchors this page links to. abstract page, PDF.

(35 min)

Code: NVlabs/SoL-Pi. NVlabs/SoL-Pi

The four mechanisms as an opt-in extension for Pi 0.85.1 (TypeScript, MIT licence, about 3,300 stars on 3 October 2026), with tests. Not released: the auto-research pipeline, the 535 search environments, the trajectories and the per-task EdgeBench results.

(10 min)

Best resources

SoL-Pi blog post

the authors (NVIDIA): the method with more detail than the paper: all 152 proposal titles by family, the three orchestration designs that came before the disposable skill loop, ObservationPack's selection sweep and 11-task paired run, the humans' role, and the breadth-against-depth observation.

(20 min)

EdgeBench

ByteDance Seed (README, leaderboard and tech report arXiv 2607.05155): the held-out benchmark: 134 day-scale tasks, 51 public, scored as the best of many submissions within a time budget, with a stop hook so agents cannot quit early; its leaderboard is where the paper's GPT-5.5 @2h reference (31.2) comes from.

(15 min)

Meta-Harness: end-to-end optimization of model harnesses

Lee et al., arXiv 2603.28052: the closest prior work: search over executable harness programs with a Pareto front of task score against context cost, tested on held-out datasets and models.

(30 min)

Rethinking the evaluation of harness evolution for agents

Wang et al., arXiv 2607.12227: the study that motivates SoL-Pi's isolation rules: evolved harnesses overfit the tasks used in search and give marginal gains on unseen ones.

(30 min)

Prompt caching

Anthropic, Claude API documentation: why recorded traffic and cost come apart: cache reads bill at a tenth of the input price and cache writes at 1.25 times it, so a rewritten prefix costs 12.5 times as much as a re-read one (the ratio Online Context Compact's gate uses).

(10 min)

Pi coding agent

Earendil Works: the minimal, extensible harness SoL-Pi extends through public extension APIs; its native compaction is what Online Context Compact triggers.

(10 min)

Autoresearch: the experiment loop

Karpathy: the propose, implement, run, inspect, keep-or-discard loop each SoL-Pi lineage follows.

(5 min)

Toward recursive self-improvement: how GLM built its own inference infrastructure

Z.ai, 17 September 2026: the same week's production counterpart: GLM-5.3 as an Infra Agent tuned its own serving stack (3.22x throughput in 13 days) and the post's lesson is that the feedback environment, not the model, is the bottleneck. The post needs JavaScript; explainx.ai's summary is linked under Connections.

(15 min)

Effective harnesses for long-running agents

Anthropic Engineering: a hand-written view of the same problem the search automates: what a harness should do for an agent that runs for hours.

(15 min)

the opposite design choice: a trained model writes a fresh harness per task, where SoL-Pi searches for one fixed harness that transfers.
