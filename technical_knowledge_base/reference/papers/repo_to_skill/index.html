Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills

Jianlyu Chen, Yuyang Hu, Hongjin Qian, Jiawei Liu, Wenqing Wei, Xiaolong Chen, Defu Lian, Zhicheng Dou, Chaozhuo Li, Qiwei Ye, Zheng Liu
Beijing Academy of Artificial Intelligence (BAAI), University of Science and Technology of China, Renmin University of China, Hong Kong Polytechnic University (corresponding authors Defu Lian, Zhicheng Dou, Zheng Liu) · September 2026 (arXiv v1, 2 September 2026; the only version so far)

In one line: Names the thing agent skills usually lack, operational knowledge (the practical know-how of getting a published method to actually run, which lives in READMEs and issues rather than papers), and distils it out of repositories into reusable skills both task-agnostically and task-oriented; the AREX-Skill Library is 5,000+ verified skills from 1,000 ML repos across 20 areas and 178 capability families, and on a GPT-5.5 backbone at fixed compute it buys +134.3% on MLE-bench, +34.4% PaperBench, +9.2% FrontierCS, +14.0% PassNet.

The Takeaway above is the database property, quoted. Two corrections: none of the four benchmark gains uses the 1,000-repository library (each benchmark got its own task-specific or paper-derived skills), and the budget held fixed is the run-time budget only; building the MLE-bench skills took up to 24 more GPU-hours per competition.

Problem: knowing a method is not making it run

§1, §2.2

Agents now carry out parts of machine-learning research end to end (§1). The paper describes such an agent as two modules (Eq. 2): a model Mθ that understands, reasons, plans and executes, and a harness H that supplies orchestration, memory, verification and refinement.

The missing piece, in the authors' words, is operational knowledge: "the know-how that separates knowing a method from making it work" (abstract, §2.2). In ML research it covers which method suits the problem, which package implements it, how the package wants its data laid out, which configurations are sensible, and which pitfalls invalidate an otherwise plausible run. The model's prior is broad but fixed; the harness controls procedure but supplies no domain content.

Without it an agent loses budget twice (§1): within a task it infers package behaviour by trial and error, and a misconfigured run can burn much of the budget before any meaningful measurement; across tasks, what it discovered is not kept.

The knowledge exists. It sits in papers and repositories (source code, documentation, examples, tests, scripts and configuration files are the evidence the paper's pipeline reads, §4.1), but it is written for human readers and is far too large to load during a task. Today an expert turns it into agent skills by hand, so the cost "scales with expert labor and with the domain, stack, and release" (§2.2).

The old version of this page said the knowledge lives in "READMEs, config files, issue threads and the folklore of a codebase". The paper never mentions issue threads or folklore: its repository pipeline reads the evidence listed above, and its other sources are papers, tutorials and, for the benchmarks, web search.

The question: can operational knowledge be produced automatically and at scale from those declarative sources, and does handing it to an unchanged agent improve its research?

Idea: a third layer, made of skills, distilled from sources

§2.2, §3.1, Eq. 4 to 7

The paper adds a third component (Eq. 4): Ares = (Mθ, H, 𝒦), with 𝒦 the operational knowledge given as explicit operating context, so actions come from πθ(a | τ, ht, H, 𝒦). "The harness specializes how the agent explores, while 𝒦 specializes what the agent knows to consider." 𝒦 has two constituents: capability (methods, code, models and APIs as invocable units) and usage policy (when, why and how to use each); either alone is tools without criteria or advice with nothing to run.

𝒦 is a set of skills in the open Agent Skills format (Eq. 5 and 6; Anthropic, 2025). A skill has three layers:

  • SKILL.md, the knowledge interface, the only layer read up front: goals, key concepts, tool use, worked examples, known failure modes, and routes to deeper material or sibling skills.
  • references/, the knowledge substrate: API docs, algorithmic detail, configurations, loaded only when needed (progressive disclosure).
  • scripts/, the execution interface: wrappers with defined inputs and outputs the agent calls instead of reimplementing.

One source usually holds more than one skill should, so the skills from one source form a skill graph (Eq. 7): an entry skill states the source's scope and links to component skills; each link is a routing, dependency or composition relation. The agent reads the entry, follows only the links its problem needs, and leaves the rest unopened. What makes this distillation rather than summarisation is verification: "No skill is admitted on the strength of its sources alone, and any gap that survives the checks is recorded" (§3.2). How much that verification proves is examined in How much to believe.

Method: DisCo distils in four stages, from a source or from a task

§3.2, §3.3, Eq. 8, Appendix A

DisCo is one agent with two modes over the same backbone and harness (§3.3). In creator mode it produces skill graphs and deposits them in the library; in researcher mode it solves a task with skills drawn from the library. Every creator run follows the same four stages (Eq. 8): from an anchor z, scope capabilities 𝒬, ground them in evidence 𝒳, construct a candidate graph, verify it into 𝒢 with a record R of evidence, checks and unresolved gaps.

The two forms of distillation differ in the anchor (§3.2). Task-agnostic: the anchor is a source (a repository, a paper, a tutorial) and the run asks what the source makes possible, ahead of any task. Task-oriented: the anchor is a problem, and the run asks what solving it demands, searching for sources it does not yet have. (The old page called these "modes"; the paper's modes are creator and researcher.) Step through both: the released Creator run on huggingface_hub, and the paper's MLE-bench protocol (Appendix A.2.1).

Stages from Eq. 8; details from Appendix A.1 and A.2.1.

The two forms differ in more than the anchor. The repository run yields scripts and references pinned to a package version, checked against that package's own tests. The MLE-bench run yields a descriptive skill with no scripts, built from web search plus up to 24 GPU-hours of diagnostic trials on the very competition it is for (Table 5): in effect, the lab notebook of a previous attempt at the same problem.

The cost is asymmetric by design (§3.3): creator mode is paid once per source and amortised; researcher mode pays only for what a task opens. The library cost "about $40 per repository" of GPT-5.5 and GPT-5.6-sol at extra-high reasoning effort (§4.1), about $40,000 in all (derived). MLE-bench construction is up to 24 GPU-hours per competition, at most 1,800 for the 75 (derived), counted in neither arm.

In researcher mode (§3.3, §4.2) the agent sees a router skill, narrows from area to family to repository graph, and follows links only as needed; the full library "is never placed into context". Skills add operating context, not a new control loop, so any harness that reads Agent Skills can use them. The Follow the router tab replays a released session doing this.

The AREX-Skill Library

§4, Figure 3, Appendix A.1, Appendix B

Task-agnostic distillation run across 1,000 ML repositories yields the library (§4.1): 5,353 skills in 1,000 repository graphs (about 5.4 per repository), organised into 20 areas and 178 capability families, with 2,209 exact assignments of repositories to area-and-family paths; 700 repositories sit in more than one family. All of these recount exactly from the public release, which is 31,191 files and 237 MB; the median repository graph is 156 KB, its entry SKILL.md 4.6 KB.

  • Selection: "open-source visibility and practical use, with GitHub stars among the curation signals"; a curated snapshot (§4.1).
  • Graph: a router-like entry skill linking to component skills for data preparation, training, inference, evaluation, serving, troubleshooting or maintenance; self-contained, with provenance (source commit, package version, dirty state, evidence paths) (Appendix A.1).
  • Verification: assertion-backed usability cases, safe native tests, CLI checks, tiny fixtures or smoke scripts, classed pass, skill_gap, native_fail, skip_unsafe or skip_not_selected; a skill gap triggers a local repair and rerun. Static gates check metadata, links, self-containment, provenance and path leakage.
  • Taxonomy (§4.2): an LLM proposes a two-level tree from frozen one-line summaries (stars, URLs and old categories hidden), tested on 100 fixed batches of 10 repositories by a separate locator and judge, then revised for at least two rounds until a convergence gate passes. Only then is each graph assigned to exact paths, with rationale, evidence and confidence; keyword-only, dependency-only, optional-integration and example-only matches are rejected.

Repository memberships per area, coloured by family; from the release's assignments.jsonl (identical to Appendix B). Tap a bar for its families. A repository counts once per family it is assigned to.

Two further collections sit beside the repository graphs and are not in these counts (§4.3). Paper-derived skills: for the 20 PaperBench targets, DisCo decomposed up to 10 prior papers per target (from its related-work section) into 3 to 5 module skills each, 636 skills from 153 papers, each checked in isolation and then by a bounded recovery experiment that may not read the original code; the target paper and its released code are excluded. Task-oriented skills: one graph per MLE-bench competition (75), one recovery graph shared by FrontierCS's 188 Agent Track tasks, and one graph for PassNet.

Result 1: MLE-bench, 31.1% to 72.9% of competitions medalled

§5.1, §5.2, Table 1, Appendix A.2.1

Setup for all four benchmarks (§5.1): Codex as the harness, GPT-5.5 at extra-high reasoning effort as the backbone, both fixed. "The only controlled factor is whether the agent is equipped with DisCo-distilled skills." Skill construction finishes before the benchmark run, and the two arms get the same running budget; the one-time construction budget is "separate and is not counted in either run-time condition".

The skills that lifted Codex on MLE-bench came from where?

From §4.3, §5 ("We evaluate DisCo beyond the public repository snapshot") and Appendix A.2. None of the four benchmark results uses the repository library.

MLE-bench (Chan et al. 2025) is 75 Kaggle competitions in three tiers, scored by the share earning any medal on held-out data. Each competition's skill came from web search (its own page blocked) and diagnostic trials, each revision seeing the previous skill, a log summary and a result analysis (Eq. 9); it is descriptive only, so no fixed solution is replayed. Then Codex gets up to 24 GPU-hours with the skill, the no-skill arm the same 24 (Table 5).

Any Medal, mean ± SEM (Table 1). Codex rows: three runs each. Public rows are copied from the MLE-bench leaderboard and use other harnesses, backbones and run counts.

  • Overall: 31.11% to 72.89%, +41.78 points, a 134.3% relative gain. By tier: +43.94 (Low), +37.72 (Medium), +48.89 (High).
  • High tier: 13.33% to 62.22%, +366.8%, 4.67 times; the authors' reading is that harder tasks make unguided trial and error costlier.
  • Against the leaderboard: 72.89% beats the best public entry (Famou-Agent 2.0, 64.44%) by 8.45 points, and the best per tier by 6.06, 5.26 and 15.55, "without a custom execution harness".
  • The runs behind the means (derived, unique fits to the printed mean and SEM): 20, 25 and 25 medals of 75 for Codex alone, 53, 55 and 56 with skills.

The gap is far outside noise (standard error 2.51 from the SEMs, 7.41 per competition sampling). What it measures is the question for How much to believe.

Result 2: PaperBench, 29.45 to 39.59 replication score

§5.3, Table 2, Appendix A.2.2

PaperBench (Starace et al. 2025) asks an agent to replicate 20 ICML 2024 papers from scratch; an official LLM grader scores each attempt against a rubric. Each target got a pool of paper-derived skills from its related work, never from the target or its code (Appendix A.2.2). The average rises from 29.45 to 39.59 (+10.14, 34.4% relative). Sort the 20 papers:

Table 2: each paper's score without skills (open dot) and with (filled), one run per arm as far as the paper says (no repeats or error bars are reported).

  • Broad: 18 of 20 papers improve. Largest gains: rice +40.57, sequential-neural +23.70, what-will-my-model-forget +21.10. In multiples: ftrl 1.50 to 17.17 (11.4 times), rice 7.94 to 48.51 (6.1), what-will-my-model-forget 9.35 to 30.45 (3.3).
  • Largest gains where the baseline is low; papers already at 52.93 (all-in-one) or 56.65 (bam) gain only 1.77 and 2.18.
  • Two regress: sample-specific-masks 57.11 to 52.04 (−5.07) and stay-on-topic 32.31 to 27.79 (−4.52), both above the 29.45 average. The authors suggest "a possible retrieval-precision failure": a retrieved skill can pull the agent away from a narrow, idiosyncratic choice it would have found unaided, and better routing or a fallback to unguided reasoning might help.
  • Statistics (derived, papers as the unit): 95% interval for the mean gain [4.91, 15.37]; sign test p = 0.0004; without rice the mean gain is still 8.53.

Result 3: FrontierCS, 70.63 to 77.14

§5.4, Table 3, Appendix A.2.3

FrontierCS (Mang et al. 2025) poses open-ended computer-science problems whose quality is measurable even when the optimum is unknown. All 188 Agent Track tasks run through Harbor with a 5-hour budget, 2 CPUs and 4 GiB; the agent writes a C++ solver, may submit repeatedly and keeps its best score (judge limits 0.25 to 100 s, 128 MiB to 2 GiB). One frozen recovery graph serves every task: a router plus eight modules (method selection, implementation, checkers, validation, interactive, reactive online, testlib judging, plateau escape), seeded from two human-written guides and refined by paired trials on "selected development problems" (Appendix A.2.3). Its 9 nodes and 42 directed links recount exactly from the release.

  • Score: +6.51 points (9.22%); paired bootstrap 95% interval [3.41, 9.83]. 74 tasks improve (by 22.23 on average), 66 are effectively unchanged, so 48 degrade (derived) by 8.76 on average; gains total 3.91 times the losses.
  • Where it comes from: on the 47 tasks Codex alone scored below 50, the mean rises from 19.43 to 45.99 (+26.56), and 30 of them cross 50. That alone is 6.64 points of the 6.51 average, so on the other 141 tasks the net change is about −0.17 points (derived).
  • Skills were used on 180 of 188 tasks; gain 5.54 on the 102 tasks without sub-agents, 7.66 on the 86 with.
The paper stresses a fixed budget. Per FrontierCS task, how many tokens did the skill-equipped Codex use compared with Codex alone?

Table 3: score against mean tokens per task (log scale). Leaderboard rows are copied from the FrontierCS leaderboard; the two Codex rows are the authors' runs.

The budget held fixed is the five-hour limit, not the spend. Skills made Codex search harder: tokens 2.46M to 4.47M per task (1.82 times), steps 55.9 to 88.7 (1.59), tool calls 64.7 to 105.0 (1.62). The paper's answer: per-task gains are essentially uncorrelated with the extra usage (Spearman ρ 0.006 for tokens, 0.014 for steps, 0.015 for tool calls). Against the leaderboard, Claude Code with Claude Opus 4.8 and with Qwen3.7 Max use 3.29 and 3.10 times the tokens of Codex with skills while scoring 2.64 and 15.24 points lower; Codex with skills makes 24.5 to 27.9% fewer tool calls and 33.8 to 75.0% fewer steps (printed 75.1; 1 − 88.7 / 355.4 is 75.04%): Pareto dominance "under the leaderboard's reported accounting".

Result 4: PassNet, AS Score 1.343 to 1.531

§5.5, Table 4, Table 6, Appendix A.2.4

PassNet (Liu et al. 2026) asks for a graph-compiler pass: a pattern matcher and rewriter that keeps an FX graph's semantics and makes it faster. The AS Score is the geometric mean of rectified subgraph speedups over tolerances t from −10 to 4 (incorrect or unmatched passes floored at 0.1), aggregated by a weighted geometric mean; the other metrics are at t = −5. 200 samples on A100-SXM4-40GB (§5.1).

Table 4, relative to eager execution. Fast_1 is the share of correct subgraphs at least as fast as eager.

  • AS Score 1.343 to 1.5313 (+0.1883, 14.0%); G-Mean Speedup 1.5891 to 1.6688.
  • Fewer broken passes: failed samples 14 to 5 (64.3% fewer); correctness 81.35% to 90.76% (+9.41 points). The skill supplies procedures, rejection criteria and recovery actions for matching, correctness checks and tuning.
  • Past the compiler: TorchInductor (torch.compile) scores 1.419, so Codex with skills beats it, and Codex alone (1.343) does not.
  • Not discussed in the text: Fast_1 falls from 28.48% to 26.72%, so the extra correct passes are not more often faster than eager.

How the PassNet skill was built (Appendix A.2.4): candidate procedures tried with and without on 50 training instances, then a CPU screen over the 4,000+ training instances (solving all would take over 20 days) dispatched to sub-agents that summarised recurring patterns, about a day per pass. On 50 training tasks with Claude Code and DeepSeek v4 pro (Table 6) the geometric mean rose 0.5352 to 0.6941, match failures fell from 10 of 50 to 1 and solve time from 40 to 22 minutes; the arithmetic mean fell (0.9566 to 0.7492) because two no-skill outliers (10.63 and 8.18) scored 0.99 and 0.10 on a repeat. Chasing them exposed a rule that was too absolute: "never reimplement vendor-optimised heavy operators" blocked a conv3d with stride equal to kernel size, which reduces to elementwise multiplication; the agent saw the rewrite and gave it up. The rule became "a defeasible prior rather than an absolute ban", a concrete case of the misapplication risk below.

How much of this to believe

§5, Appendix A, the release

What holds up.

  • The artefact is real and counts out. Every library count the paper prints (5,353 skills, 1,000 graphs, 2,209 assignments, 700 multi-family repositories, 20 areas, 178 families, 636 paper-derived skills) and the FrontierCS graph's 9 nodes and 42 links match the public release exactly. Code and skills are Apache-2.0, with two full session exports. That is more than most agent papers release.
  • The arithmetic is clean. Every printed number this page could recompute reproduces (the checks are in the Tables tab) except one rounding: 75.04% printed as 75.1%. MLE-bench's means and SEMs pin down unique medal counts per run that add up across tiers.
  • The MLE-bench and FrontierCS gaps are not noise. MLE-bench reports three runs per arm with a gap of 16 standard errors; FrontierCS reports a paired bootstrap interval of [3.41, 9.83] over 188 tasks. PaperBench's 18 of 20 papers improving is unlikely by chance (sign test p = 0.0004, derived).
  • The authors state some weaknesses themselves, which counts in their favour: the two PaperBench regressions and a possible retrieval-precision failure, the PassNet outliers that do not reproduce across runs, and the over-absolute PassNet rule.

What is not like for like, or not what it seems.

  • None of the four results tests the library. The 1,000-repository library is the paper's title and headline artefact, but "we evaluate DisCo beyond the public repository snapshot" (§5): MLE-bench, FrontierCS and PassNet use task-oriented graphs built for each benchmark, PaperBench uses paper-derived pools. Whether the repository library helps any agent on any benchmark is untested. The old version of this page, and the database Takeaway, attribute the four gains to the library.
  • "Fixed budget" excludes construction, and for MLE-bench construction is a prior attempt at the same task. Up to 24 GPU-hours of diagnostic trials on each competition shaped its skill (Appendix A.2.1), so the skill arm had up to 48 GPU-hours of work per competition against 24. No script is replayed, but the skill carries "task diagnoses, model and preprocessing choices, training strategies, expected observations": a second attempt with notes from the first. The old page's "this is not more compute buying more attempts" does not hold for MLE-bench.
  • The leaderboard comparison mixes setups, and the baseline is weak. Public rows come from leaderboards with other harnesses, models, hardware and run counts; "beats the best public entry by 8.45 points" pits per-competition prior exploration against agents without it. Codex alone (31.11%) is below every public MLE-bench entry, and a large relative gain over a weak baseline is easier than over a tuned one.
  • FrontierCS spends more, and its development set is unstated. Skill runs used 1.82 times the tokens; the paper's answer (gains uncorrelated with extra usage) is fair but indirect, and no no-skill run got the same spend. The overlap of the "selected development problems" with the 188 evaluated tasks is not stated. The whole average gain sits in the 47 low-scoring tasks (net −0.17 on the other 141, derived), a split by one run's score that regression to the mean also flatters.
  • Single runs elsewhere, and one metric unmentioned. PaperBench, FrontierCS and PassNet report no repeats; PaperBench's grader is an LLM judge; PassNet samples moved from 10.63 to 0.99 between repeats in construction. PassNet's Fast_1 falls (28.48% to 26.72%) without comment.
  • "Verified" means structural and package-level checks. The released Creator example (huggingface_hub) passes shape, frontmatter, licence, links, privacy, routing and bundled-script checks, and 720 of the package's own unit and mocked tests ("verified-with-warnings": 2 native failures, 3 unsafe selections excluded). Its 15 usability cases pass a check of their "shape"; the report does not record an agent being run on them. The vLLM graph was inspected on a CPU build, "GPU execution intentionally left to user-hardware verification". Verified skills are well-formed and pinned to a version, not shown to make an agent succeed.
  • Curation is looser than "widely used ML repositories". High-confidence routes include a game-automation bot (1bananachicken/MaaNTE, under Computer Vision and Speech and Audio) and a set of beginner Python scripts (ndleah/python-mini-project, under Image Classification). 2,123 of 2,209 assignments are "high"; the confidence labels are not a quality filter.
  • The misapplication risk is acknowledged but not measured. Demystifying Agent Skills found skill guidance misapplied or ignored in 10.0% of the skill arm's failure labels (against 0.8% in its no-experience arm). This paper's two PaperBench regressions and the PassNet conv3d rule are instances, but it reports no rate of misapplied skills and no retrieval-precision measurement for its router.

Verdict. Believe the artefact and the direction: the library is real, consistent and openly licensed, and task-specific skills made the same Codex agent better on four quite different benchmarks. Treat the sizes as "what a second, informed attempt is worth", not as the value of a reusable library: none of the results uses the 1,000-repository library, MLE-bench's +134.3% includes up to 24 extra GPU-hours of exploration per competition, FrontierCS's +6.51 came with 1.8 times the tokens and sits entirely in the hardest quarter of tasks, and only MLE-bench has repeated runs.

What it takes to use this

the release
  • Code and licence: VectorSpaceLab/AREX-Skill, Apache-2.0 for repository-level files unless a file says otherwise; each graph also records its upstream licence. The DisCo CLI is built on the open pi agent toolkit and needs Node.js 22.19 or newer; disco repo-skills install installs the library, and researcher mode routes it natively.
  • Other agents: import-repo-skills-to-agent exports selected skills plus a scoped router into Codex's or Claude Code's skills directory; nothing in the harness changes.
  • What is released and what is not: the 1,000 repository graphs and router, the PaperBench pools (636 skills), the FrontierCS graph and the PassNet skills are in the repository. The 75 MLE-bench graphs, the source of the headline number, are not; neither are the benchmark trajectories.
  • Cost to build your own: about $40 of model time per repository at extra-high reasoning effort with GPT-5.5 and GPT-5.6-sol; for an MLE-bench-style task, up to 24 GPU-hours of exploration per task before the real run.
  • Freshness: graphs pin a commit and version and drift with every release; check the provenance file, and the documented refresh procedure, before trusting a graph for a newer version.
  • When it pays: where the agent would otherwise burn its budget on setup and package behaviour (low baselines, hard tiers, unfamiliar libraries), and where a task family repeats so construction is amortised. When it buys little: tasks the agent already does well (FrontierCS tasks above 50 gained nothing on net; high-baseline PaperBench papers gained 2 points), and narrow tasks where a general rule can mislead.

Why it matters

beyond the paper

The paper's framing is the durable part: an agent is a model, a harness and a knowledge layer, and the third can be manufactured from sources that already exist rather than written by hand. It reframes what a repository is for an agent: not something to read when needed, but a source of pre-compiled procedure distilled once and reused. That is the same mechanism Demystifying Agent Skills identified when it found skills work as procedural anchors (steps, checks, pitfalls) rather than as knowledge injection, and this is the first work to supply such anchors at library scale. Its released sessions show the economics working as designed: in the vLLM against SGLang run, the agent read 65 KB of a 237 MB library in under two minutes and then worked for five hours.

The old version of this page called the MLE-bench figure "the largest single-intervention gain the KB currently records on that benchmark"; that is a claim about this knowledge base, not the paper, and given the per-competition exploration behind it, it should be read as the gain from task-specific preparation, not from a library. The caution carried over from the Demystifying paper applies directly: skills add a misapplication failure mode, and retrieval precision decouples from task success, so a 5,353-skill library is also 5,353 opportunities to apply the wrong procedure confidently. This paper engages with that only anecdotally (two PaperBench regressions, one PassNet rule), which is the obvious next experiment.

Connections

  • Demystifying Agent Skills: Why They Work - Until They Don't: the mechanistic account of why this works, and the source of the misapplication caveat this paper does not measure.

3. A task-oriented graph: the FrontierCS recovery skill

The single graph shared by all 188 FrontierCS tasks (Appendix A.2.3): an entry skill that activates only after a focused first attempt fails, then routes to one of eight modules. Tap a node to see where it routes and what routes to it.
