Problem: capable models, failed runs

§1 Introduction

Long-horizon CLI agents often fail although the model can do every step: they drift from the plan, lose track of changing state, skip a known check, repeat what is not working, or stop early and declare the job done (§1). The usual fix is more model. The authors ask the orthogonal question: "How much apparent model failure is actually failure of the harness that maintains state, constrains execution, verifies progress, and recovers from errors?" Improving that control layer is harness scaling, tested three ways: does a better harness lift a fixed model; does it move to a newer model without retuning; do its principles help beyond the benchmark they were built on (§1)?

Two operational hypotheses (not claims about attention) motivate putting control outside the model (§1): control-signal dilution, a short plan and its completion criteria buried under thousands of tokens of commands and output (Figure 6); and mutable-state ambiguity, the current state rebuilt from an append-only history in which loops and branches interleave many versions of the same item (Figure 7).

Existing options sit at the wrong points (§2). Graph runtimes (StateFlow, LangGraph) give explicit state, persistence, routing and recovery, but a developer owns the controller and the agent is split into node calls. CLI agents (Codex, Claude Code) keep autonomy, but their plans, TODO lists, memory files and hooks are advice or fire on tool events, never one authoritative, transition-aware control surface. Idea: states as context-and-contract boundaries, operated by the agent

§3, Figure 2

StateM is a small runtime for CLI agents. Its control layer is a versioned YAML runbook of states, permitted transitions, and per-state prompts, hooks, checks and recovery routes. The agent drives it with ordinary shell commands (where am I, request a transition, why did it fail, history); the user reads, edits and audits the same file. No model change is needed (§1). Two principles: each state is a context-and-contract boundary (entering refreshes the phase's instructions and progress; leaving requires exit checks, because "an agent's declaration of completion does not constitute independent verification"), and agent and user share the control layer. The authors say the novelty is this combination, not any part: graph runtimes already have states and checkpoints, and harness adaptation is not new (§2). The runbook is also the thing to optimise: failures become new runbook versions, so procedural knowledge accumulates outside the weights.

Method: runbook, checked transitions, per-run state, stop hooks

§3.1 to §3.6

Runtime and profile differ (§3.1): the runtime is generic machinery; the profile is a runbook for one class of work. The Terminal-Bench results measure the runtime plus an evolved, benchmark-adapted profile and "should not be interpreted as isolating the effect of the state-machine abstraction alone".

A runbook is a directed state machine B = (S, s0, ST, E, Φ): phase-level states, an initial state, terminal states ST ⊆ S, permitted transitions E ⊆ S × S, and per state Φ(s) its prompt, hooks, checks and files (§3.3). Inside a state the agent works freely. Entering runs an in_hook (load instructions and a compact progress record); leaving requires the before_transfer checks; an out_hook persists progress and receipts (§3.2). Edges can carry guards that route to repair, handoff or wait, so repair is in the graph rather than in the agent's memory. Appendix A has a complete coding runbook (start, plan, execute, review, handoff, with a session-refresh loop).

Checks differ in what they prove (§3.2):

command, predicate
Run by the host: reproducible evidence, as good as the command.
manual
An explicit decision by the user or operator.
llm_review
A separate semantic judgment, not deterministic proof.
checklist, message
The agent acknowledges obligations: self-attestation.

Bar lengths only order the strengths the paper describes; ranking manual above llm_review is this page's reading.

Every phase change is goto TARGET with an ordered protocol (§3.3): (1) the edge must exist; (2) exit checks run; (3) the out_hook runs; (4) edge guards and hooks run; (5) only then is the target committed and logged; (6) the target's in_hook runs. A failed check leaves the run where it was, with the failure recorded, to repair and retry. "Checked, logged, and recoverable", not transactional: hooks' side effects cannot be rolled back and hook code is not sandboxed (§3.3 footnote). The released code evaluates the edge condition before the out_hook (README).

The protocol on the paper's worked example, configure-git-webserver (clone, commit and push hello.html, then curl http://server:8080/hello.html must print "hello world"). The baseline "can configure Git, SSH, hooks, and an HTTP server, yet scores 0/5"; StateM gates handoff on a fresh clone, commit, push and curl (§4.6). The same run, without and with the gate:

Illustrative: built only from the paper's description (§4.6) and the gate of the released git_webserver_deploy runbook; no baseline trace is published, so the service that fails is this page's example. Real runs are on the replay tab.

Per-run state lives outside the runbook (§3.4): current state, history, check outcomes, evidence links. One profile serves many runs, and after a restart or compaction the agent asks StateM where it is instead of rereading a transcript. It cannot recover unsaved work or undo external actions; a paused run is never counted as success. The agent may add stricter dynamic checks for the current entry; weakening user-owned checks needs a privileged decision, and YAML editability is not a security boundary (§3.5). Stop hooks for Codex and Claude Code refuse to stop a run that is neither terminal nor blocked, handing back its open obligations; that cuts premature stops but guarantees neither success nor termination. StateM gives control points, not a correctness oracle (§3.6).

Failure-driven optimisation (§4.6 and §4.7) sorts failures into three gaps: epistemic (knowledge not active at the decision point; fix with state-local context in an in_hook), procedural compliance (the right procedure not completed; fix with checks, guards and evidence requirements) and procedural memory (a past lesson not reactivated; fix with a versioned prompt, check or activation rule). A hyper-agent proposes runbook changes from failure traces; humans set the architecture and three golden rules: prefer minimal reusable control, route from visible task semantics rather than task identity, keep development feedback apart from frozen evaluation (§4.1). Hidden tests, verifier code, solutions, task hashes and task identifiers are off limits. On Terminal-Bench, GPT-5.5 in Codex wrote most of the harness (§4.7).

The evaluation: four transfer tests

§4, §4.1

Four regimes ask "what transfers as model and task distance increase?": fixed-model lift, frozen transfer within a family, adapted transfer across providers, held-out task generalisation (§4). Terminal-Bench 2.1 has 89 tasks × 5 trials = 445; the metric is trial success, plus five-trial coverage (tasks solved at least once), which "measures empirical coverage over five observed trials rather than single-run reliability". Agents are Codex-based with GPT-5.5 xhigh, GPT-5.6 Sol xhigh, GPT-5.6 Luna and DeepSeek-V4-Flash; reference rows reproduce a published result, our run rows are the authors' (§4.1). The profile was developed with GPT-5.5 and frozen for GPT-5.6: no prompt, state, routing, check, default or repair policy revised from target-model outcomes. For DeepSeek, final-run and adaptation API charges are reported separately; the $1,062.95 on the GPT-5.6 submission is the pipeline's API-equivalent estimate, not what the authors paid on a Codex Pro plan (§4.1).

Result 1: same model, better harness, a generation-sized gain

§4.2, Figure 3

With GPT-5.5 xhigh fixed, StateM scores 92.1% against the 83.1% Codex reference (+9.0) and solves 88 of 89 tasks at least once (98.9%), numerically above the 91.9% reported for GPT-5.6 Sol Ultra (§4.2). The reference is the leaderboard entry (83.15%, Codex 0.125.0, $2,059.19), "a model-matched public reference rather than a newly rerun, agent-version-matched A/B control" (§4.2 footnote). The frozen runbook on GPT-5.6 Sol xhigh scores 424/445 = 95.28% raw against the 84.9% reference (+10.38), with every task solved at least once. Under the reference harness GPT-5.5 to GPT-5.6 Sol moves only 1.8 points, so the harness gain is five times the generation gain (§4.2).

Status of the 95.28% (footnote 1, as of 11 August 2026): raw, pre-adjudication accuracy from PR #142, which passed ten automated checks and was still open. The authors accept that four flagged rewarded trials should not count (420/445 = 94.38%); zeroing all nine reward-hacking flags gives 415/445 = 93.26%. The pipeline reports 1.178 billion tokens, $1,062.95, six agent timeouts and a 0.87-point standard error (§4.1).

The leaderboard reviews rewarded trajectories for cheating and zeroes the ones it upholds. The GPT-5.6 Sol max + Codex submission that the paper uses as its cost comparator scored 83.37% raw. What did it count after review?

What happened next (beyond the paper; PR #142 thread). The leaderboard's judge flagged 13 of the 424 rewarded trajectories: nine for possible reward hacking and four as harness cheating, the class that "renders a submission invalid" (dna-insert, extract-elf, dna-assembly, filter-js-from-html). A maintainer first said the harness-cheating flags could be ignored; a reviewer then showed every trajectory carries the profile's gate schema, with slots such as git_webserver_hints and sqlite_wal_hints that map onto single benchmark tasks. The author answered that the slots are empty generic configuration, agreed they were "unnecessary and confusing", disclosed benchmark-tuned video tolerances, and asked where the line for evolving harnesses should be. On 19 September 2026 the PR was closed unmerged: "Community submissions are currently closed for Terminal-Bench 2.1". Zeroing all 13 flags would give 411/445 = 92.36%, which the paper does not print.

Result 2: transfer follows model distance

§4.3, Figure 4

Within the GPT family the exact runbook transfers: frozen, it lifts GPT-5.6 Luna from 76.7% to 85.4% (+8.7), above the 84.9% Sol xhigh reference on a cheaper tier; "frozen transfer" means zero runbook changes, not zero evaluation cost (§4.3). Across providers it does not: the frozen profile moves DeepSeek-V4-Flash from 82.7% to 82.0%, because StateM leaves the agent enough autonomy for provider behaviour to matter. What carries across is the runtime, the runbook structure, the routing strategy, the failure-analysis loop and the golden rules (§4.3). Hence a hierarchy: exact runbooks across nearby models, principles across providers, control-boundary abstractions across tasks (§4.8).

Result 3: a $15 run at the reported frontier score

§4.4, Figure 5

Adapting the practices to DeepSeek cost $37.02. The adapted system scores 88.09% on all 89 tasks at standard timeouts (392/445, +5.39), 89.09% on the 88-task common core without gpt2-codegolf (392/440), and a descriptive 88.76% with that one task's extended-timeout trials added ((392 + 3)/445; 0/5 standard, 3/5 extended), which rounds to the 88.8% reported for GPT-5.6 Sol max (§4.4). The final run cost $15.20, the whole campaign $52.22; the public Sol max + Codex submission recorded $574.68, so 2.65% (1/37.8) and about 1/11. The paper notes the 88.8% and the $574.68 come from different evaluations (that submission: 83.37% raw, 76.18% after review), so it plots $574.68 at 83.37% (§4.4 footnote).

The lesson the authors draw: exact controls did not cross the provider boundary, but the reusable structure made adaptation cheap, so "buy the strongest model" now competes with investing in a harness (§4.4). The released trials confirm every DeepSeek number this page could check, and show why it is cheap: of the input tokens were cache hits (audit on the replay tab).

Result 4: BusinessBench, the only held-out test

§4.5, Tables 1 and 2

BusinessBench (from Better Harnesses, Smaller Models), Codex + GPT-5.6 Luna: 477 instances in seven families. The authors abstain on attendance-payroll, leaving 405 instances in six families (810 executions). Luna agents run development instances and propose changes, a GPT-5.6 Sol hyper-agent keeps the ones that generalise, and each family profile is frozen before one held-out run, one trajectory per instance and arm (§4.5).

Where StateM intervenes, and what it should not remember

§4.6 to §4.8, Table 3

Table 3 lists twelve GPT-5.5 tasks with the biggest gains and the control active in each (configure-git-webserver 0/5 → 5/5, dna-insert 0/5 → 5/5, dna-assembly 1/5 → 5/5, filter-js-from-html 0/5 → 4/5, ...). They cluster at consequential boundaries: service readiness before handoff, contract satisfaction before a commit, preservation before destructive steps, evidence before completion; the paper says the association "is not a component ablation" (§4.6). These twelve carry extra trials, of the 9.0 (tables tab).

In the 440 released DeepSeek trials, how often did a host-run check actually refuse a requested transition at least once?

Procedural memory must be selective (§4.7). A practice is any reusable, experience-derived intervention (an instruction, a check, an activation condition); the loop is execute, observe, attribute, abstract, encode, validate. On Terminal-Bench one profile covers 89 heterogeneous tasks, and fixing tasks one at a time caused "control drift", so it stays thin and activates late, state-local checks only when visible evidence says they apply (§4.7). "More remembered procedure is not better memory." The authors disclose what the harness should not have remembered: precision defaults for video tasks set "after observing benchmark behavior"; DNA insertion's left-most-boundary convention, learned from verifier feedback "without ever reading verifier code", so its meaning comes from the evaluator, not the task; and valid failures abstracted wrongly (the first BusinessBench profiles). Their rule: "experience must be filtered before it becomes memory".

A 22-hour run (§4.8): one profile-development session ran 22 hours through compaction and stop-hook continuations, StateM's record supplying phase, history and obligations throughout; the slowdown came from unfolded terminal output, not lost state. Discussion (§5 and §6): harness scaling needs a runtime cheap to change yet enforceable; multi-agent, role-isolated runtimes are future work. The conclusion: "model scaling expands what an agent can do; harness scaling helps the system remember what experience has taught it to do without training, and ensures that it actually does so before proceeding."

How much of this to believe

§4.1 and footnotes

What holds up.

  • The arithmetic: recomputations agree (tables tab), with one contradiction below.
  • The gains are far outside trial noise on these tasks: 92.1 against 83.15 is about standard errors, 95.28 against 84.9 about (binomial over 445 trials and the leaderboard's own errors). One run each, but not a margin a rerun is likely to erase.
  • The DeepSeek run is inspectable: its exact 54-file harness source and all 440 trials are released, and this page recounts 392/440, 86 of 88 tasks covered and $14.27 from them. None of the 89 task names appears in that source.
  • The gates fire: in of the DeepSeek runs a host-run check refused at least one transition ( refusals), and the agent then repaired and went on. That is the claimed mechanism, observed.
  • Candid disclosure: benchmark-adapted profile, raw pre-adjudication score with alternatives, model-matched rather than A/B references, the comparator's mismatched score and price, negative transfers, and two ways the hyper-agent learned the benchmark rather than the task. These count in the paper's favour.

What is not like for like, or not tested.

  • The Terminal-Bench numbers are development-set numbers. The profile was built from failures on the same 89 tasks it is scored on; there is no held-out Terminal-Bench split, and "frozen transfer" is a new model on the same tasks (§4.7). On the only held-out test the gain was +0.55 (macro) and +1.34 (micro), one trajectory per instance, no error bars; even with all 405 instances held out, the unpaired standard error of a difference near 85% would be about points (Table 1).
  • The focused gates are task-shaped. Of the gates DeepSeek trials selected, fired on exactly one of 88 tasks (grpc_roundtrip only on kv-store-grpc, html_sanitizer only on filter-js-from-html, primer_insert_contract only on the two DNA tasks), and the released git_webserver_deploy package names configure-git-webserver as its "canonical positive contract". Routing reads visible semantics, not names, but a catalog grown from these tasks' failures will fit them; that is what the leaderboard review was about.
  • Raw against reviewed. The 83.1% baseline is the leaderboard score after review (83.37% raw); the 95.28% is before a review that never finished. Review matters here: the Sol max comparator lost 7.19 points. The judge flagged three of Table 3's four biggest-win tasks as harness cheating on the GPT-5.6 run.
  • Different agent versions and machines. Codex 0.125.0 for the reference, statem-Codex 0.144.1 for the submission, 0.146.0 for DeepSeek (§4.1); the submission ran on AWS because hosted Daytona sandboxes timed out more often (Appendix B), while an earlier upload of the reference shows Daytona errors (PR #45).
  • Unsourced comparators: 84.9% (Sol xhigh), 76.7% (Luna), 91.9% (Sol Ultra) and 88.8% (Sol max) carry no citation, and none matches a leaderboard entry found here (Luna max: 76.63% raw, 75.73% reviewed). Unconfirmed.
  • Unreleased runs: DeepSeek's 82.7% baseline and 82.0% frozen run, GPT-5.5's 92.1% and the Luna runs have no artifacts.
  • No ablation: nobody ran the runtime with a generic profile, so how much is the state machine and how much 54 files of benchmark-derived checks is unknown, as the paper says (§3.1). Within the DeepSeek trials, refused runs passed more often ( against ), but they are the runs routed through deeper review, so that is not causal.
  • A self-contradiction: the Introduction says the DeepSeek run is "approximately 38.9×" cheaper (§1), §4.4 says 1/37.8, which is what $574.68 / $15.20 gives; 38.9× would need $.
  • Retries: the DeepSeek job allowed two automatic retries on any exception except four verifier errors (its exclusion list does not name agent timeouts) and used ; the paper does not say whether references did the same.
Verdict
Believe the runtime: checked, logged transitions with host-run checks are a sound, reusable way to stop an agent handing off unverified work; the code is open and the released trials show the gates firing in most runs. Believe that GPT-5.5 and GPT-5.6 scored far higher on these 89 tasks with this profile. Do not read 92.1% or 95.3% as what StateM adds on new work: the profile grew on the same tasks, many gates fit single tasks, the 95.3% was never adjudicated and its PR closed unmerged, and the one held-out test moved +0.55 to +1.34 points. The $15 run is genuinely cheap (mostly cached input), and it too is a development-set score.

What it takes to use this

Appendix B, repository
  • Code: henryqin1997/statem, Apache-2.0, v0.1.0, Python 3.11+, no dependencies; statem start / cur / next / goto / history. Ships the Appendix A coding runbook, Codex and Claude Code plugins with optional stop hooks, one executable Terminal-Bench family, and the DeepSeek release. Not released: the GPT profile behind 92.1% and 95.3%, and the BusinessBench profiles.
  • Budget: a personal Codex Pro plan and a MacBook Pro (M4), under $125 of a $200 budget; the formal submission ran on AWS m7i.4xlarge; GPT-5.5 reached about 91% on the MacBook (Appendix B). The DeepSeek campaign cost $52.22.
  • Where it pays: long, consequential work with a checkable end state (a service a fresh client must reach, a file that must meet a contract, every mandatory side effect done once). Put a command or predicate gate there; checklists are attestation, not proof.
  • Where it buys little: short or exploratory tasks, stable workflows that a fixed graph serves better (§2), retrieval-heavy or saturated tasks; a profile tuned for another family can hurt (−2.78, −3.70).
  • New model: the exact runbook carried within the GPT family; across providers expect to re-derive the practices (DeepSeek's frozen profile scored 0.7 below no profile).
  • Safety: hooks run with the host's permissions, unsandboxed; decide which runbook parts the agent may change (§3.5).

Why it matters (beyond the paper)

  • A named, testable axis beside model scaling, with four distinct transfer tests, and the claim that here "the model appears not to be the (main) bottleneck" (§1). Read with the caveats, it is strong evidence on a development set and weak evidence held out.
  • Deployment economics, if it generalises: a ~$52 campaign put a cheap model at the reported frontier score on this benchmark.
  • A middle point in the control design space (enforced transitions, broad autonomy, a control file both can edit), and a graded check taxonomy any harness can reuse.
  • It forced the benchmark question: should a leaderboard accept harnesses that evolve on the benchmark itself? The leaderboard closed community submissions. HarnessDev, 17 days later, measured the same risk: the score a harness developer sees tracked the held-out score in only 34 of 64 changes.

    Recomputed checks

    Standard errors on the reading tab: z = (p1 − p2) / √(SE1² + SE2²), with SE = √(p(1 − p)/445) where no published SE exists, and the leaderboard's 0.87 (StateM submission) and 1.13 (GPT-5.5 reference after review) where one does. The BusinessBench bound uses √(2 · 0.85 · 0.15 / 405). For the DeepSeek run, the task-clustered standard error (spread of the 88 per-task pass rates) is against a binomial : generalising to new tasks of this kind is much less certain than rerunning these ones.

    Corrections to the earlier summary of this paper

    • "~1/38 the evaluation cost": §4.4 gives 1/37.8 ($574.68 / $15.20); the Introduction's 38.9× contradicts it.
    • "the two mechanism-matched families jump +10.04 macro (Budget Approval +12.21, Machine Operating +9.21)": the 10.04 is held-out only, the 12.21 and 9.21 are Round-1 aggregates over development and held-out together (their mean would be 10.71).
    • "the submission PR is unmerged": it was closed without merging on 19 September 2026, after the leaderboard's judge flagged 13 trajectories, four as harness cheating, which the paper does not mention.
    • "scoring 4 review-flagged trajectories as zero gives 94.38%": the four are the reward-hacking flags the authors agreed with; zeroing all 13 judge flags gives 92.36%.
    • The 2026-08-24 tech news item paired "95.3% with GPT-5.6 Sol" with "roughly $15 of API cost per run": the $15 run is DeepSeek-V4-Flash at 88.1% (88.8% descriptive); the 95.3% run's reported model cost is $1,062.95.
    • "code and runtime cases open sourced": the runtime, one Terminal-Bench family and the DeepSeek run are released; the GPT profile behind 92.1% and 95.3% is not.
