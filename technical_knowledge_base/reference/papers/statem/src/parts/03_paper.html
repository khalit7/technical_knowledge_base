Problem: capable models, failed runs

[[p1|§1 Introduction]]

Long-horizon CLI agents often fail although the model can do every step: they drift from the plan, lose track of changing state, skip a known check, repeat what is not working, or stop early and declare the job done ({{§1|ax:p1}}). The usual fix is more model. The authors ask the orthogonal question: "How much apparent model failure is actually failure of the harness that maintains state, constrains execution, verifies progress, and recovers from errors?" Improving that control layer is harness scaling, tested three ways: does a better harness lift a fixed model; does it move to a newer model without retuning; do its principles help beyond the benchmark they were built on ({{§1|ax:p2}})?

Two operational hypotheses (not claims about attention) motivate putting control outside the model ({{§1|ax:p2}}): control-signal dilution, a short plan and its completion criteria buried under thousands of tokens of commands and output ({{Figure 6|ax:p24}}); and mutable-state ambiguity, the current state rebuilt from an append-only history in which loops and branches interleave many versions of the same item ({{Figure 7|ax:p24}}).

Existing options sit at the wrong points ({{§2|ax:p5}}). Graph runtimes (StateFlow, LangGraph) give explicit state, persistence, routing and recovery, but a developer owns the controller and the agent is split into node calls. CLI agents (Codex, Claude Code) keep autonomy, but their plans, TODO lists, memory files and hooks are advice or fire on tool events, never one authoritative, transition-aware control surface. Idea: states as context-and-contract boundaries, operated by the agent

[[p6|§3, Figure 2]]

StateM is a small runtime for CLI agents. Its control layer is a versioned YAML runbook of states, permitted transitions, and per-state prompts, hooks, checks and recovery routes. The agent drives it with ordinary shell commands (where am I, request a transition, why did it fail, history); the user reads, edits and audits the same file. No model change is needed ({{§1|ax:p3}}). Two principles: each state is a context-and-contract boundary (entering refreshes the phase's instructions and progress; leaving requires exit checks, because "an agent's declaration of completion does not constitute independent verification"), and agent and user share the control layer. The authors say the novelty is this combination, not any part: graph runtimes already have states and checkpoints, and harness adaptation is not new ({{§2|ax:p6}}). The runbook is also the thing to optimise: failures become new runbook versions, so procedural knowledge accumulates outside the weights.

Method: runbook, checked transitions, per-run state, stop hooks

[[p7|§3.1 to §3.6]]

Runtime and profile differ ({{§3.1|ax:p7}}): the runtime is generic machinery; the profile is a runbook for one class of work. The Terminal-Bench results measure the runtime plus an evolved, benchmark-adapted profile and "should not be interpreted as isolating the effect of the state-machine abstraction alone".

A runbook is a directed state machine B = (S, s0, ST, E, Φ): phase-level states, an initial state, terminal states ST ⊆ S, permitted transitions E ⊆ S × S, and per state Φ(s) its prompt, hooks, checks and files ({{§3.3|ax:p8}}). Inside a state the agent works freely. Entering runs an in_hook (load instructions and a compact progress record); leaving requires the before_transfer checks; an out_hook persists progress and receipts ({{§3.2|ax:p8}}). Edges can carry guards that route to repair, handoff or wait, so repair is in the graph rather than in the agent's memory. {{Appendix A|ax:p21}} has a complete coding runbook (start, plan, execute, review, handoff, with a session-refresh loop).

Checks differ in what they prove ({{§3.2|ax:p8}}):

command, predicate
Run by the host: reproducible evidence, as good as the command.
manual
An explicit decision by the user or operator.
llm_review
A separate semantic judgment, not deterministic proof.
checklist, message
The agent acknowledges obligations: self-attestation.

Bar lengths only order the strengths the paper describes; ranking manual above llm_review is this page's reading.

Every phase change is goto TARGET with an ordered protocol ({{§3.3|ax:p8}}): (1) the edge must exist; (2) exit checks run; (3) the out_hook runs; (4) edge guards and hooks run; (5) only then is the target committed and logged; (6) the target's in_hook runs. A failed check leaves the run where it was, with the failure recorded, to repair and retry. "Checked, logged, and recoverable", not transactional: hooks' side effects cannot be rolled back and hook code is not sandboxed ({{§3.3 footnote|ax:p9}}). The released code evaluates the edge condition before the out_hook ({{README|https://github.com/henryqin1997/statem#how-it-works}}).

The protocol on the paper's worked example, {{configure-git-webserver|ax:p17}} (clone, commit and push hello.html, then curl http://server:8080/hello.html must print "hello world"). The baseline "can configure Git, SSH, hooks, and an HTTP server, yet scores 0/5"; StateM gates handoff on a fresh clone, commit, push and curl ({{§4.6|ax:p17}}). Per-run state lives outside the runbook ({{§3.4|ax:p9}}): current state, history, check outcomes, evidence links. One profile serves many runs, and after a restart or compaction the agent asks StateM where it is instead of rereading a transcript. It cannot recover unsaved work or undo external actions; a paused run is never counted as success. The agent may add stricter dynamic checks for the current entry; weakening user-owned checks needs a privileged decision, and YAML editability is not a security boundary ({{§3.5|ax:p9}}). Stop hooks for Codex and Claude Code refuse to stop a run that is neither terminal nor blocked, handing back its open obligations; that cuts premature stops but guarantees neither success nor termination. StateM gives control points, not a correctness oracle ({{§3.6|ax:p10}}).

Failure-driven optimisation ({{§4.6 and §4.7|ax:p16}}) sorts failures into three gaps: epistemic (knowledge not active at the decision point; fix with state-local context in an in_hook), procedural compliance (the right procedure not completed; fix with checks, guards and evidence requirements) and procedural memory (a past lesson not reactivated; fix with a versioned prompt, check or activation rule). A hyper-agent proposes runbook changes from failure traces; humans set the architecture and three golden rules: prefer minimal reusable control, route from visible task semantics rather than task identity, keep development feedback apart from frozen evaluation ({{§4.1|ax:p11}}). Hidden tests, verifier code, solutions, task hashes and task identifiers are off limits. On Terminal-Bench, GPT-5.5 in Codex wrote most of the harness ({{§4.7|ax:p18}}).
