Problem

[[S1|§1, §2, §3]]

An agent's context is everything the model reads on its next call: the system prompt, the task, and the transcript of every thought, command and tool result so far. A deep-research agent on BrowseComp-Plus gets 10 search snippets of 512 tokens per search and documents of up to 8,192 tokens ({{Appendix E|ax:A5}}), so a 32K window fills after a handful of turns. A plain language model only ever appends to its context ({{Eq. 1|ax:S4.E1}}):

ct+1 = ct ⊕ fθLM(ct)

where ct is the context at turn t and ⊕ is concatenation. Something else must decide what to drop. Today that is the harness, the program around the model that runs the loop (see {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} for the designs in production). The paper sorts prior work into two families ({{§2|ax:S2}}, {{Appendix A|ax:A1}}):

  • Harness-defined: fixed rules. Codex and Cursor summarise everything when the context passes a length threshold; Terminus2 does the same; MEM1 rewrites its state every turn. The model writes the summary, but the harness picks when and how.
  • Action-based: the model triggers human-designed tools. Self-Compact and AutoCompact let it decide when to compact; Context-as-a-Tool, ACM (offload and retrieve), Context Folding (branch and fold) and Sculptor (hide fragments) widen the menu. The menu is still fixed.

Recursive Language Models (RLMs) are the nearest neighbour: they put a long input in a REPL variable the model reads on demand, but the live context stays read-only and keeps growing ({{§2|ax:S2}}).

A diagnostic first. To separate context management from reasoning and knowledge, the authors built ContextBench, four synthetic tasks whose input arrives one operation per message, so nothing can be filtered on the way in ({{§3|ax:S3}}, {{Table 3|ax:A4.T3}}):

  • Needle Retention: about 4K-token chunks of 2 to 8 "needle" lines and 140 filler lines; keep the needles verbatim, delete the filler.
  • Sudoku Sketchpad: a 16×16 board kept in the context while moves stream in, one per turn; reproduce every version exactly.
  • KV Store: batches of 100 SET operations with 24-word values, then 24 GET queries.
  • Log Triage: batches of 14 to 54 service log lines, then 24 lookup and count queries.

The limit is fixed at 32,768 tokens (2,048 reserved for the reply) and the context pressure, total input over that limit, rises to 24× ({{Appendix D|ax:A4}}). With GPT-5.4, no existing method is perfect even here: summaries lose or invent needles and board cells, methods without in-place editing must rewrite the whole board for each move, and coding tools can copy a batch to disk but cannot remove it from the live context ({{Figure 2|ax:S3.F2}}). The decoded curves are on the {{Tables tab|tab:t-tables:tb-f2}}: on KV Store, Base falls to 0 from about 0.8× pressure and Context Folding from about 1.5×; CLM stays at 1.0 on three tasks and 0.97 to 1.0 on Log Triage.

Idea: the context as a file

[[S4.SS1|§4.1]]

A Context Language Model (CLM) produces its next context directly ({{Eq. 2|ax:S4.E2}}):

ct+1 = fθCLM(ct)

where f can be any function the model chooses: the model is allowed to make "unrestricted updates" to its context ({{abstract|https://arxiv.org/abs/2609.37725}}). Every harness rule and every context tool above is a special case, which is why the paper says Eq. 2 "subsumes" them. The difference is who writes the function: the harness author, or the model.

How it is built. The live context is mirrored to a file whose path is in the system prompt. The model edits it with ordinary Bash or Python, and each edit is synchronised back into what the server sees on the next call; if the model does not edit, its output is appended as usual ({{§4.1|ax:S4.SS1}}). In the released harness the file is /tmp/.live_ctx/LIVE_CTX_MAIN.txt, turns are delimited by [[CTX_TURN i role=...]] headers, and the system prompt shows a one-line re.sub that collapses a turn into a note ({{clm_agent/prompts.yaml|https://github.com/facebookresearch/context-language-models/blob/main/clm/clm_harness/clm_agent/prompts.yaml}}). Several agents are several files: a swarm starts with several context files, and a subagent is created or ended by creating or deleting one.

What the models did with it, zero-shot ({{Figure 3|ax:S4.F3}}):

  • an orchestrator kept an in-context scoreboard of its subagents and updated it with 163 in-place edits while the context stayed at 6 to 8K tokens;
  • it invented a new chat role, role=notes, for its own working notes;
  • it wrote loops that replace stale search results with one line ("Searched: ... No relevant results.");
  • it defined a helper, compact_turns, and called it 37 times to fold old results into a reference to a progress note;
  • and it reproduced what good summaries do: 21K tokens compressed to answer-relevant facts, or a ledger of untried ideas kept for later.

These are hand-picked examples from the zero-shot runs of §5.1, not frequencies. How often each behaviour occurs is not reported.
