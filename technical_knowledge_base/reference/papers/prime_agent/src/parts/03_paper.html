Problem

[[S1|§1 Introduction]]

A language model on its own is a bounded sequential processor: its next decision can use only what is in its weights and its active context. A harness supplies everything else, the tool calls that act on the world and the information management beyond what the weights already know ({{§1|ax:S1}}). The first such management was agentic compaction, where the model shrinks its own context and keeps what matters. The paper's claim is that the useful state has outgrown weights plus context, so a harness should give the model somewhere else to keep and process it.

The authors frame Prime Agent first as an evaluation harness ({{§1|ax:S1.p3}}). The common long-horizon metrics are score at a fixed spend (tokens, cost, time) and score at a practical plateau, both from METR's note on {{metrics of agent ability|https://metr.org/notes/2026-07-24-metrics-of-model-ability/}}. A model should fail an evaluation because the task is beyond it, "not because the harness dropped state, restricted useful actions, miscounted resources, or terminated prematurely". So the harness should be a thin, expressive membrane: it standardises execution, recovery, verification and resource accounting, leaves strategy entirely to the model, and so stops harness failures masquerading as model failures, pushing a measurement "toward the model's true maximal underlying capability" ({{abstract|ax:abstract1}}).

What the old summary added. It opened with "harness quality, not model quality, is now the binding constraint on long-horizon tasks", and the example of an agent failing at hour 40 of a 7-day task without anyone knowing whether the model or the harness ran out. That framing is the summary's own; the paper's argument is the narrower one above, about evaluation that does not confuse the two.

Idea: treat the model's state like a memory hierarchy

[[S2.SS2|§2.2, Figure 2]]

Seen as a cache of state information, the model's weights are L0, its active context L1, a persistent REPL plus recursive subagents L2, and disk-backed history, memories and skills L3 ({{Figure 2|ax:S2.F2}}). That makes the system "more von Neumann-like": the model can read, transform and write addressable state outside the instruction it is generating. The boundary that matters is between L1 and L2: above it, state is token-visible to one model call; below it, state is managed by code and enters the context only when something serialises it. Each level changes through its own mechanism. Click a level:

From that view, expressivity is the property a harness needs: rather than encode one workflow, it exposes primitives from which the model builds programs, subagents and feedback loops while it runs ({{§1|ax:S1.p2}}). Prime Agent splits the job in two ({{§2.1|ax:S2.SS1}}): information management (what state enters a model call, and what survives compaction or restart) and computation management (mapping the model's chosen actions to code, tools and recursive subagent sessions), joined by direct agent-to-agent messages. Five properties follow: models handle intermediate values with code; sessions keep their history across compaction, detachment and restart; subagents inherit the root's execution and messaging primitives; the runtime records model calls, tool use, messages, harness changes and resource use; and the model, not the harness, controls decomposition, compute allocation, communication and stopping. The retained trajectories can also train later models.

The idea is easiest to see on the paper's own orchestration example ({{Appendix B|ax:A2}}): a parent hands a review and a test run to two subagents, then sends the reviewer a follow-up. Below, the same task runs through a classic harness, where a subagent is a tool call that blocks and pastes its answer into the parent's context, and through Prime Agent's rlm, where it is a persistent session the parent addresses by name.

Method

[[S2|§2 Architecture]]

{{Figure 1|ax:S2.F1}} is the whole system: a human uses the Agents View to reach a root session; the root calls rlm() to start subagents, which act on the environment and send messages back; a daemon owns every session, and Continual Harness holds the state that persists between trajectories. Solid arrows carry execution and messages, dashed ones persistent state.

The persistent REPL and the RLM primitive

[[S2.SS3|§2.3]]

Each session owns a persistent IPython REPL, and it is the model's main tool rather than a fixed tool schema ({{§2.3|ax:S2.SS3}}). Installed tools are imported as Python modules, so parsing, filtering, aggregating and verifying are ordinary code; intermediate values persist across turns and stay out of the context until selected, which avoids pasting large logs, task specifications and evaluator output into the context again and again. Test-time compute is then three things, model inference, Python execution and tool calls, and evaluations report tokens, time and cost separately.

The Recursive Language Model abstraction ({{Zhang, Kraska and Khattab 2025|https://arxiv.org/abs/2512.24601}}) is implemented as an asynchronous rlm function. Calling it creates and schedules a subagent session and returns a stable handle before the subagent finishes; the subagent gets its own model context, IPython kernel, history and workspace metadata; the parent keeps computing; results arrive later as agent-to-agent messages; and retained handles allow follow-ups after compaction or restart. The model chooses between local code, tools, sequential delegation and parallel subagents, and Prime Agent defines how each executes instead of fixing a workflow graph. In the launch post's words, context becomes a program the model writes rather than a policy the harness enforces ({{blog|https://www.primeintellect.ai/blog/prime-agent}}).

# Appendix B: admit independent subagents; do not wait for answers here.
review = await rlm("Audit the implementation. Reply with concrete issues.", name="reviewer")
tests  = await rlm("Run the test suite and classify failures.", name="tester")
# Later, recover retained sessions and send a follow-up.
children = await rlm.list_subagents()
await agent_message.send("Also inspect error-handling edge cases.",
                         receiver_role="child", receiver_name=review.name)

"The explicit reply path is intentional: a child is a persistent concurrent session, not a stateless completion returned by rlm" ({{Appendix B|ax:A2}}).

Moving information between levels

[[S2.SS2|§2.2]]

External state affects generation only when the runtime injects it or an operation serialises a result into the context. Python values and tool outputs in L2 enter generation when serialised into L1. Compaction replaces a conversational prefix with a summary and keeps the original events in L3, where the REPL can retrieve them. The runtime assembles selected Continual Harness entries into later supplemental prompts; other L3 artifacts enter context on retrieval; L0 stays fixed. The model manages L2 itself by creating, keeping, summarising or deleting REPL values and subagent sessions as the task changes, which the paper calls agentic garbage collection (the blog adds that a spawned agent cleans the kernel asynchronously, to stop REPL memory building up).

What is kept: an append-only event history, selected kernel snapshots, the rooted session tree, context and compaction records, persistent message queues and versioned Continual Harness state. Branching or forking creates a new continuation without deleting the earlier events; recovery rebuilds a session under the same identity; Python objects that cannot be serialised, and external processes, are recreated from saved artifacts or services.

Recursive sessions, messages and the Agents View

[[S2.SS4|§2.4, Figure 3]]

The daemon owns live sessions independently of the client that created them, and root and subagent sessions share one lifecycle ({{Figure 3|ax:S2.F3}}): running during a turn or tool operation, idle when loaded without an active turn, inactive when unloaded but recoverable from persistent state. Detaching the client leaves a session running, and stable session and parent identifiers keep the recursive tree intact across these transitions. Agent-to-agent messages go through asynchronous, daemon-mediated queues: an agent can address its parent, children and siblings (the blog calls this its "nuclear family"), and a queued message waits until its recipient is active again. Filesystem, network and credential access follow the permissions of the runtime environment.

The Agents View exposes the same tree to a human: inspect a session's history, attach, type new input, or detach without interrupting it. agent-observe gives bounded read-only status and recent-message previews, and agent-message sends to a named related session.

Continual Harness: self-improvement without touching weights

[[S2.SS5|§2.5]]

Four typed kinds of state can be read and written during a trajectory ({{Karten et al. 2026|https://arxiv.org/abs/2605.09998}}): prompt notes (behavioural rules), memories (facts), skills (executable procedures) and subagent specifications (reusable roles or divisions of labour). Each supports create, read, update and delete; entries are local to one session unless explicitly made global for later sessions. Refinement turns trajectory evidence into versioned updates: the agent asks for an edit directly, or /refine runs a background model call over the relevant events; the runtime applies each edit at a turn boundary, records its trigger and intended effect, and assembles the state into the next invocation. Versions keep provenance and allow rollback, and refinement only supplements the immutable base prompt. Useful computations become skills, repeated coordination patterns become subagent specifications, corrected assumptions become memories or prompt notes, and the record doubles as training data for later models.

Long-horizon controls and accounting

[[S2.SS6|§2.6, Figure 4]]

Three mechanisms keep a run going ({{Figure 4|ax:S2.F4}}). Autonomous mode continues model turns within an explicit budget and runs a task-specified end-condition test after each turn; a failed test returns bounded output for another attempt, and turn, token and wall-clock limits stop the run. A goal keeps an objective across continuations until the agent itself marks it complete. Heartbeats start turns on a cron or timer. An evaluation configuration binds the task and tool interfaces to the model and provider settings, the compaction and refinement policies, retries, completion gates and resource limits; accounting aggregates the root and all descendants, so delegation shows up in the test-time cost, and the event history links every model and tool call, message, intervention, retry, verifier outcome and harness edit to that configuration.
