Φ-Bench: Can Large Language Models Engineer the Infrastructure That Powers Them?

Leilei Ding, Shumin Wang, Yuting Huang, Fanqi Wan, Yinmin Zhang, Qi Han, Yiming Xu, Feiyuan Zhang, Xiaomeng Chu, Guoliang You, Wuyang Zhang, Daxin Jiang, Yanyong Zhang
University of Science and Technology of China, StepFun, Peking University, HKUST, Yale, University of Pennsylvania (correspondence: Daxin Jiang, StepFun; Yanyong Zhang, USTC) · 9 September 2026 (arXiv v1, the only version so far)

In one line: 85 open-ended infrastructure tasks in nine categories and three escalating formats (55 single-file kernel completions, 20 multi-file repository implementations, 10 end-to-end optimisations where the model must find the bottleneck itself), built from 2,260 papers and 1,852 engineering artifacts; the best model, Claude Opus 5, resolves 36.53%, Kimi K3 28.12% and Qwen3.8-Max 27.73%, with Hardware and Edge collapsing to 5.4%, repository-scale work far harder than kernels, longer reasoning budgets not reliably helping, and the behaviours that separate the top of the table being cheap pre-submission validation plus deliberate variable isolation.

Problem

Introduction, Related Works

Infrastructure work, the software that trains and serves large language models, pays off directly: PagedAttention and Megatron-LM-style optimisations raise GPU utilisation and cut cost (Introduction). So the question in the title is practical: can a model engineer and optimise the stack it runs on?

Existing code benchmarks for this work measure isolated pieces. KernelBench, TritonBench and FlashInfer-Bench give one GPU operator (or a small fusion) with a fixed interface, input and output specification and a stated objective; ISO-Bench and CUDAHercules move to whole repositories but still name the component and the bottleneck (Related Works). Real infrastructure engineering is long-horizon and open-ended: understand an existing stack, find where the time goes, change several files, and check that the system got faster without getting wrong, over many rounds of implement, profile, debug and refine (Introduction). Those benchmarks also cover only a narrow subset of the topics involved. Nobody had measured the open-ended version, and it is precisely the capability that would let models accelerate their own serving and training stacks.

Three formats, from one function to the whole repository

Task Formats, Table 1

Every task is a natural-language specification, a complete infrastructure repository, executable workloads or test cases, and an evaluation harness. Everything is visible to the agent except the harness (Task Formats). Three formats widen what is fixed in advance and what the agent may touch (Table 1):

  • Kernel Function Completion (KFC), 55 tasks. A performance-critical kernel or operator with its interface and input-output semantics specified; complete or optimise it within one file without changing the interface. Correctness and numerical accuracy are tested first, then speed (KFC).
  • Long-Horizon Implementation (LHI), 20 tasks. An issue-style feature request and a coarse editable scope, such as a submodule; the files, dependencies and implementation path are left open. Solving it means navigating the codebase, changing several files, and building, testing and debugging repeatedly (LHI).
  • End-to-End Optimization (E2EO), 10 tasks. A representative workload, a system-level objective and constraints, with no hint of which components or strategies to use. The agent must profile, find the bottleneck, plan and make possibly repository-wide changes (E2EO).

What the paper does not say, and the released package does (SCORING.md, tasks_index.json): 77 of the 85 tasks are scored on speed or quality ratios and only 8 are pass or fail, including 18 of the 20 LHI tasks, so "implementation" in the format's name does not mean a binary test. 42 of the 85 tasks need no GPU at all (CPU-side scoring pipelines, storage, quantised CPU kernels).

How the 85 tasks were built

Task Synthesis, Figures 2 to 4

Sources. Papers from top-tier systems conferences of 2023 to 2026, kept by an LLM filter if they study implementing, accelerating or saving resources in LLM training or inference and have a public implementation; plus issues and pull requests from widely used infrastructure repositories, kept if they introduce substantial optimisations, add important capabilities, address hardware- or workload-specific limits, or document hard engineering problems. That gives 2,260 papers and 1,852 engineering artifacts (Source collection). The authors' repository adds that these came from more than 10,000 candidates, of which agent-assisted triage kept over 4,000 (README).

Taxonomy. An LLM labels each of the 4,112 sources at three levels: 410 fine-grained tags, clustered into 62 middle-level topics, grouped into nine top-level categories (Coverage taxonomy). The middle-level topics index task synthesis, and the paper's Figure 3 shows this taxonomy covering far more topics than any related benchmark.

Each bar's length is the count on a logarithmic scale. The 15 to 10 step is the authors' own: five E2EO candidates were dropped in final selection and are listed in tasks_index.json for transparency.

Three construction routes (Task Synthesis), which are worth noting as benchmark methodology:

  • PR- and issue-grounded. Take the repository state before an important pull request as the task and the state after as the reference solution, adapting its unit tests into the harness. Small single-file changes become KFC tasks; larger multi-file ones LHI or E2EO (PR- and Issue-Grounded).
  • Agent-assisted. Agents scan repositories for high-value sites and cut out a code segment or a whole module. A second agent loop tracks which branches the current tests exercise and writes new tests until uncovered execution paths are covered (Agent-Assisted).
  • Expert-curated. For problems that repository history cannot reconstruct reliably (influential papers, conference challenges, emerging problems with no complete reference trajectory), experts build the starting repository by removing the implementation, reverting to a simpler baseline, or writing the task from the specification, and design the tests and workloads by hand (Expert-Curated).

Quality control. A performance task's reference solution must reach a stable speed-up of at least 1.15 in the official environment, and the starter or no-op solution must not beat the baseline. An implementation task's reference must pass every test while the starter fails at least one, with at least five tests covering normal inputs, boundaries, error paths and regressions. A task failing these is revised or excluded (Quality Control). Every one of the 77 released reference anchors clears 1.15 (the lowest is 1.16).

Scoring: you only score by beating the expert

Evaluation Metrics

Every attempt gets a reward between 0 and 1. Both metrics are correctness-gated: the build, functional tests, edit constraints and anti-cheating checks must pass before any reward is given (Evaluation Metrics).

Performance metric (Performance Metric). The candidate and the unmodified baseline are timed in an AB-BA paired protocol with at least five pairs, and the candidate's speed-up is the median of the per-pair ratios, s = mediani(tibase / ticand). The reference solution's speed-up sref is the median of at least five runs. If sref ≤ 1 the reward is zero; otherwise

Rperf = 0 if s ≤ sref;   min(1, ln(s / sref) / ln sref) if s > sref

A submission passes every check and runs exactly as fast as the experts' reference solution. What reward does it get?

Solid: the paper's curve. Dashed: the package's earlier curve, min(1, ½ ln s / ln sref), under which matching the reference scored 0.5; SCORING.md says the new one is max(0, 2 × old − 1) and that the two are not comparable. The default task, kv-traffic-sol, is SCORING.md's own worked example: 2.58× scores 0, 4.14× scores 0.5 and 6.656× or more scores 1.

So the zero point is the expert's solution, not the starting code: the paper says the reward "is zero when the candidate matches or underperforms the reference solution", and full marks need the reference's speed-up squared. The package explains why: the earlier curve piled submissions up at 0.5 for matching the reference, and the new one spends the whole range on "whether, and by how much, a submission beats the oracle" (SCORING.md). The bar varies enormously by task: the 77 frozen anchors run from 1.16× to 41,667×, median 11.3×, so a task anchored at 100× needs 10,000× for full marks. The Score a submission tab lets you move the speed-up and the measurement noise and watch the reward.

Two details the package adds. "Speed-up" is the ratio of each task's declared metric, which is not always time: for the MoE training task it is baseline bits per byte over the candidate's, at a fixed wall-clock budget; for an embedding-compression task it is retrieval quality at 64 bytes a vector. And the anchors were calibrated on an H20, so they must be recalibrated on other hardware (README).

Implementation metric (Implementation Metric): 1 if the code builds and imports, passes every test case and respects every forbidden-edit constraint; otherwise 0.

Cheating detection (Cheating Detection): a rule-based monitor scans the whole trajectory and final diff for prohibited behaviour (searching GitHub for the original implementation, fetching the patch or commit diff, recovering upstream code from published Python packages), and a proctor agent looks for subtler hacks (hard-coded expected outputs, skipped or bypassed correctness checks, branches that inflate the measured performance). Either one zeroes the attempt.

Results: a third of the maximum, very unevenly spread

Main Results, Tables 2 and 3

Setup (Experimental Setup). Eight models at their highest reasoning setting and maximum context: proprietary Claude Opus 5, Claude Sonnet 5, GPT-5.6 Sol, Qwen3.8-Max and Qwen3.7-Max; open-weight Kimi K3, GLM-5.2 and DeepSeek-V4-Pro. GPT-5.6 Sol runs in its default scaffold, Codex; every other model runs in Claude Code. Each task gets 8 CPU cores, 32 GiB of memory and one NVIDIA H20 GPU (other GPU types disabled). One submission per KFC task, at most 16 candidates per LHI and E2EO task, and "we take the best submissions to compute the final score."

Claude Opus 5 leads at 36.53%, then Kimi K3 at 28.12% and Qwen3.8 Max at 27.73%; the rest are GPT-5.6 Sol 24.51, GLM-5.2 21.92, Claude Sonnet 5 17.58, Qwen3.7 Max 16.07 and DeepSeek-V4-Pro 13.31 (Table 2). Even with the whole repository and the test cases in hand, the strongest model gets slightly more than a third of the maximum. The Full column is the mean reward over the 85 tasks: it reproduces exactly as (55 × KFC + 20 × LHI + 10 × E2EO) / 85 from Table 3, and as the task-count-weighted mean of the nine categories of Table 2 (see the tables tab).

No model is strong everywhere. Opus leads five of the nine categories; Kimi K3 is best on Inference and Serving (30.5) and System Optimization (41.1), Qwen3.7 Max on Hardware and Edge (5.4) and GLM-5.2 on System Assurance (57.4) (Main Results).

The three formats get more open-ended from KFC (one function) to E2EO (find the bottleneck yourself). On which format do the top four models score highest?

Table 3. Whiskers: the largest standard error a mean of that many rewards in [0, 1] can have, √(m(1 − m)/n), an upper bound computed here because the paper reports no error bars.

The paper reads Table 3 as "capacity over open-endedness" (Capacity over open-endedness): Opus is first in every format (KFC 37.16, LHI 21.60, E2EO 62.94); Kimi K3, second overall, is especially competitive on E2EO (56.41); Qwen3.8 Max is consistently strong; and LHI is below KFC for every model, so long-horizon repository work stays hard. That direction was expected; the size of the drop is the useful number: Opus falls from 37.16 to 21.60, 42% lower, and across the eight models LHI is 22% to 45% below KFC (1 − LHI / KFC from Table 3). What the paper does not discuss is that the most open-ended format scores highest. E2EO has only 10 tasks, its 8 performance tasks get up to 16 scored rounds with the best kept while every KFC task gets one shot, and the leaderboard applies E2EO-specific selection rules (see How much to believe); so the format ranking mixes difficulty with budget.

Hardware and Edge is the hardest category: the best score in it is 5.4%. How many of the 85 tasks is that score based on?

Task counts by category and format, from Figure 4 (they sum to 55, 20 and 10, and match the leaderboard's per-category counts). The bottom row is the best score in each category from Table 2, with the standard-error upper bound for that score.

The paper says Hardware and Edge is "particularly challenging": "even the best-performing model achieved only 5.4%", which it takes to mean frontier models lack an understanding of the hardware side of AI infrastructure (Main Results). Two corrections. The 5.4% belongs to Qwen3.7 Max, seventh overall; Claude Opus 5 scores 3.9 there, and two models score 0. And the category is 3 tasks (2 KFC, 1 LHI), so every model's score there sums to under a fifth of one task's reward. The direction (near zero for everyone) is real; the ranking inside it is noise. Data Infrastructure (2 tasks), System Assurance (4) and System Optimization (5) are almost as thin; only Kernel (28) and Training (19) are large enough for the category scores to mean much.

More rounds help; more reasoning helps less reliably

Ablation Studies, Figures 5 and 6

Iterations (Performance over iterations, Figure 6). One hard E2EO training task: a fully editable nanoGPT training system, a wall-clock budget and a parameter-count floor; minimise validation bits per byte (BPB). The standard optimisations are efficient token dispatch (sorting, grouped batched GEMMs, per-expert capacity buffers), load balancing against router collapse and dropped tokens, and the routing configuration and capacity factor, trading quality, throughput and drop rate. Opus's very first submission is already low (1.412 BPB, better than the final best of GPT-5.6 Sol, GLM-5.2, Qwen3.7 Max and DeepSeek-V4-Pro) and keeps improving to 1.272, which the authors call "highly impressive". Qwen3.8-Max and Kimi K3 start poorly (Kimi has no valid result for two rounds) but refine quickly to 1.338 and 1.328. DeepSeek-V4-Pro, Qwen3.7-Max, GLM-5.2 and GPT-5.6 Sol sit on long plateaus and end at 1.464, 1.701, 1.488 and 1.445. The text does not mention Claude Sonnet 5, which improves steadily from 1.729 to 1.349, the fourth-best final value.

The Replay the MoE training run tab replays every round, decoded exactly from the paper's vector figures, and translates the BPB into the task's own reward using the frozen constants in the released package. On that scale the picture changes: the reference recipe sits at 1.275 BPB, so only Opus ever scores above zero (0.005, from round 21), and full marks would need 0.831 BPB, below the 0.9 the grader rejects as implausible.

Reasoning budget (Performance over reasoning budget, Figure 5). Opus, Kimi K3 and GPT-5.6 Sol at up to five effort levels: all three are best at max, but scores do not rise steadily with budget, and GPT-5.6 Sol is unstable in the middle (22.18 at medium, 18.27 at high).

Printed point labels of Figure 5; Kimi K3 was run at three levels only. The max-effort points are not Table 3's LHI scores (21.60, 19.55, 13.98): they equal (20 × LHI + 10 × E2EO) / 30 from Table 3 to the second decimal (35.38, 31.84, 22.76), and the authors' leaderboard labels this study "30 tasks". The caption and text say 20 LHI tasks.

The paper concludes that Kimi K3 loses about 45% of its score at low effort (17.45 against 31.83, a 45.2% drop), so its strong showing depends on heavy test-time compute, while "the performance gap between Claude Opus 5 and GPT-5.6 Sol across different budget settings is not particularly significant". That last sentence is hard to square with the figure: GPT-5.6 Sol is 9.3 to 15.3 points below Opus at every level, and it too loses 29.6% from max to low, against Opus's 11.4%.

Errors, persistence and cheating

Analysis, Figure 7

Error modes (Error Modes Analysis, Figure 7). Error messages from every trajectory, in four classes: Python runtime, CUDA execution, Triton / MLIR / CUDA compile, and tensor shape mismatch. The paper's two readings:

  • The high scorers make more errors (Opus 175, Kimi K3 139, Qwen3.8 Max 179), which the authors read as persistence through trial and correction, while weak models (DeepSeek-V4-Pro 81, Qwen3.7 Max 32, Claude Sonnet 5 26) give up early or settle for simpler solutions. The pattern is real but loose: GLM-5.2, fifth overall, has the most errors (185), and GPT-5.6 Sol, fourth, has 96; the rank correlation between error count and score is 0.60 over eight models.
  • Opus fails differently. Python runtime errors are more than half of all errors for five of the eight models, but only 30.9% of Opus's; its largest class is CUDA execution errors (39.4%). The authors take this as Opus writing Python that works in the repository first time, leaving its attention for low-level implementation, "likely one of the reasons" it leads. The shares hold exactly (counts decoded from the vector figure); the causal reading is the authors' interpretation.

Hacking (Hacking Prevention and Detection). Two preventions: a soft network disconnection (pip and URLs related to the test repositories are hijacked to return a warning) and prompting with a definition of hacking and an explicit ban. Across all runs the rule-based detector fired only three times, all DeepSeek-V4-Pro requests for code from the PyTorch website, and the proctor agent confirmed no actual hacking. The paper concludes the two mechanisms prevented cheating.

Case study: what the strong model does differently

Case Study, Figure 8

The same MoE training task, now with every submission plotted, for Claude Opus 5 (best on this task) against Qwen3.7 Max and DeepSeek-V4-Pro (Figure 8). The authors view the trajectories as two coupled capabilities, choosing promising directions and executing local changes reliably, and find three behaviours (Case Study):

  1. Cheap experimental foundations (Experimental Foundations). Opus builds lightweight local experiments that reproduce only the relevant part of the workload; it first checks that a short local run's BPB is close to the development measurement, then uses such runs to reject unpromising changes before a formal submission, exploring broadly before focusing. Qwen3.7 Max and DeepSeek-V4-Pro mostly implement, submit and observe, so each formal submission doubles as debugging, hypothesis test and evaluation. DeepSeek, for example, applied torch.compile to the expert modules without checking checkpoint compatibility and wasted a submission on a checkpoint that could not be loaded. Takeaway: good models build low-cost mechanisms for screening hypotheses.
  2. Variable and noise control (Variable and Noise Control). DeepSeek often changes several variables at once, so outcomes cannot be attributed. Qwen3.7 Max does disciplined single-variable tuning, but many of its differences are the size of measurement noise: isolation alone is not enough. Opus estimates the measurement variation, accounts for differences in completed optimisation steps, and focuses on effects large enough to interpret. One learning-rate schedule change worsened BPB from 1.3646 to 1.3932; because both runs had the same seed, the same number of steps and nearly identical runtime, Opus treated the loss as real, hypothesised that too long at very low learning rates hurts, and moved to a warmup-stable-decay schedule, which reached 1.3248. Takeaway: good models run experiments that maximise the information gained per iteration.
  3. Cautious attribution (Cautious Attribution). A change seemed to cut throughput badly; Opus found that the edit had invalidated the Inductor compilation cache, so the run paid a cold-compile cost, re-ran under matched cache conditions, and found throughput essentially unchanged with the BPB gain kept. It caught cache artifacts like this several times, delaying attribution until a proper control existed; the weaker models more often credit a change to the latest edit. Takeaway: good models test alternative explanations before attributing an outcome.

Overall, the authors conclude, Opus keeps one coherent plan across rounds (explore broadly, compare under control, update on reliable evidence), while the weaker models make local, greedy decisions, so useful knowledge does not accumulate. All three behaviours come from one task and three models, read qualitatively; they are good hypotheses about what separates agents, not measured effects.

How much of this to believe

Evaluation, Analysis, and the released package

What holds up.

  • The benchmark is real and inspectable. All 85 tasks are released as self-contained Docker packages with offline graders, frozen anchors, reference solutions for 83 and a runner; each vendored repository is checked to be exactly the state the reference patch was cut from (repository). Few agent benchmarks this young can be rerun by an outsider.
  • The arithmetic is consistent. The Full column reproduces from Table 3's formats and from Table 2's categories weighted by Figure 4's task counts; the leaderboard's four-decimal scores round to every one of Table 2's 72 cells; the iteration curves decoded from the vector Figure 6 match the leaderboard's own data in 191 of 192 points (Claude Sonnet 5's round 13 reads 1.5742 in the figure and 1.5144 in the data). All checks are listed on the tables tab.
  • Claude Opus 5 first is probably right. It leads by 8.41 points; with no error bars published, the largest standard error a mean of 85 rewards can have is about 5 points per model, so an unpaired bound on the gap's error is 7.1 points and the lead is about 1.2 such errors. Paired over the same tasks the real error is smaller. It is also first in every format, in five categories, and at high effort on the authors' leaderboard (34.42, ahead of Kimi K3 at 26.20).
  • LHI below KFC holds for all eight models, and the hacking checks are concrete (a rule monitor plus a proctor agent, three alerts, none real).

What to discount.

  • 36.53% is not "a third of tasks solved". It is a mean reward in which matching the expert reference scores zero and full marks need the reference speed-up squared (Performance Metric). It cannot be compared with pass rates on other benchmarks, and it mixes 77 continuous rewards with 8 binary ones, which the package's own SCORING.md advises against ("do not directly average performance and implementation classes together").
  • Single runs, no error bars. Kimi K3 and Qwen3.8 Max are 0.39 points apart and GPT-5.6 Sol and GLM-5.2 2.6 points, inside any plausible noise. On the leaderboard's high-effort table GLM-5.2 is third and GPT-5.6 Sol fifth, the reverse of their max-effort order.
  • Not like for like. GPT-5.6 Sol runs in Codex; the other seven, including four rival labs' models, run in Claude Code, Anthropic's harness (Models and Scaffolds). Harness choice can move scores by tens of points (see HarnessDev). Formats also differ in budget: one shot for KFC, up to 16 scored rounds for LHI and E2EO performance tasks.
  • The selection rule is not the one the paper states. The paper says it takes the best submissions. The leaderboard's data file says: "e2e performance tasks: take the non-zero minimum (all-zero → 0)", with an exception for one model, "kimi-k3, max, e2e perf: if 2nd-best/best < 0.7 treat as an anomalous run → take best; otherwise take 2nd-best" (bench.json). A per-model rule on the format where Kimi K3 is strongest should be in the paper.
  • Category findings rest on a handful of tasks. Hardware and Edge is 3 tasks, and its 5.4% is Qwen3.7 Max's, not the leader's; the conclusion that models lack hardware understanding needs more than three tasks.
  • The effort figure is mislabelled. Its points are the 30 LHI and E2EO tasks, not "20 LHI problems"; Kimi K3 has three effort levels, not five. The direction (best at max, not monotone) still holds.
  • The iteration and case studies are one task. The plotted run was forced to 20 to 24 rounds, beyond the main evaluation's cap of 16 (iter.json), and its BPB values are development measurements. Under the task's own reward only Opus ever scores, and only 0.005. The three behaviours are qualitative readings of three trajectories.

In the authors' favour: they released everything needed to check this page, their scoring document is unusually candid (the oracle zero point, the non-comparable curves, timeouts that still score), and the leaderboard publishes the selection rules this section quotes.

Verdict Believe that frontier models are far from autonomous on open-ended infrastructure work, that long-horizon repository tasks are harder than kernels, and probably that Claude Opus 5 leads. Treat the middle of the table as a tie, the category and effort findings as anecdotes, and 36.53% as a reward on a demanding scale, not a solve rate.

What it takes to use this

Implementation Details, and the package
  • Code and licence. The benchmark's own work (task specifications, graders, reference solutions, loop harness, runner) is Apache-2.0; the vendored upstream code (nanoGPT, torchtitan, vLLM, llama.cpp, Megatron-LM, ColossalAI, flash-linear-attention and others) and fetched weights keep their own licences (README). Also on Hugging Face.
  • Hardware. 43 tasks need one GPU, 42 none; each gets 8 cores and 32 GiB. The anchors were calibrated on an H20: on any other card, recalibrate each task by running its baseline and reference, as the manifests describe. Docker 23 or later with buildx; building needs network access (apt, PyPI, five git clones, five E2EO tasks pull multi-gigabyte weights), solving and scoring run offline.
  • Time. The package's agent timeouts are 1.5 hours for every LHI task and 33 KFC tasks, 6 hours for the other 22 KFC tasks, and 1.5 to 6 hours for E2EO, at most 257.5 agent-hours for one model over all 85 tasks. The paper reports neither tokens nor cost.
  • Running a model. scripts/run_task.py builds, runs an agent CLI injected at runtime (Claude Code or Codex), scores and aggregates; an oracle agent replays the reference to check a task hits its anchor.
  • When it pays off. For comparing agents on realistic infrastructure work, especially the training and kernel categories, which have enough tasks. It buys little for small differences between models without repeated runs, and scores are not comparable across reward-curve versions or across hardware without recalibration.

Why it matters (beyond the paper)

It puts a number on a claim the industry has started making loudly. OpenAI said in September that by mid-August its internal metrics showed 3.1 agent-workdays of research effort per human workday (The Neuron, via the 2026-09-07 tech news issue), and AMD's ROCm 10.0 ships AMD Skills, validated ROCm optimisation knowledge packaged as agent skills for Claude, Cursor and Codex, beside Hyperloom, which profiles, plans and validates optimisations autonomously (Phoronix, via the 2026-09-14 issue). Φ-Bench says that on open-ended infrastructure engineering the best model earns roughly a third of the available reward, measured against expert solutions, and on hardware adaptation close to nothing.

It is also the first benchmark whose task categories map almost exactly onto this knowledge base's systems topics, which makes it a direct measure of how much of Topic: inference-and-serving, Topic: cuda-and-gpu-programming and Topic: ml-infra-and-orchestration a model can currently do.

Replay the MoE training run

The paper's iteration study and case study use one E2EO task: inside the full nanoGPT training system, on one H20, train the best mixture-of-experts language model you can in a fixed wall-clock budget while keeping at least a floor of total parameters; the score is validation bits per byte (BPB), lower is better (Performance over iterations). The released package fills in what the paper leaves out: the budget is 600 seconds of training, the floor 150 million parameters, and the shipped starter is a plain dense model at the floor, which a sparse top-k MoE beats only if its token dispatch is really fast on one card (task.toml).

Score a submission

A performance task's reward depends on three things: how much faster the submission really is, how high that task's frozen reference anchor sits, and how noisy the timing is. This tab runs the paper's scoring rule on simulated measurements: the AB-BA paired protocol (baseline and candidate timed alternately, the ratio taken within each pair, the median across pairs), then the reward curve (Performance Metric). Pick any of the 77 released performance tasks; its anchor is the real one from tasks_index.json. The noise model is illustrative: each timing is the true time times a random per-measurement error, times a drift factor for the machine's state at that moment.

Try: put the true speed-up just above the anchor (1.05× the anchor), then raise the drift. With the paired protocol the drift cancels inside each pair; switch to "unpaired" (all baseline timings first, the candidate later) and watch the rewards scatter and the share of zeros jump.
