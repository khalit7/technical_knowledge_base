Problem

[[Sx1|Introduction, Related Works]]

Infrastructure work, the software that trains and serves large language models, pays off directly: {{PagedAttention|n:3c65c17b0d0d81bf8b90ca93fee19f5f}} and {{Megatron-LM|n:3c65c17b0d0d8133ae92fbe90a1f308e}}-style optimisations raise GPU utilisation and cut cost ({{Introduction|ax:Sx1}}). So the question in the title is practical: can a model engineer and optimise the stack it runs on?

Existing code benchmarks for this work measure isolated pieces. KernelBench, TritonBench and FlashInfer-Bench give one GPU operator (or a small fusion) with a fixed interface, input and output specification and a stated objective; ISO-Bench and CUDAHercules move to whole repositories but still name the component and the bottleneck ({{Related Works|ax:Sx2.SSx2}}). Real infrastructure engineering is long-horizon and open-ended: understand an existing stack, find where the time goes, change several files, and check that the system got faster without getting wrong, over many rounds of implement, profile, debug and refine ({{Introduction|ax:Sx1}}). Those benchmarks also cover only a narrow subset of the topics involved. Nobody had measured the open-ended version, and it is precisely the capability that would let models accelerate their own serving and training stacks.

Three formats, from one function to the whole repository

[[Sx3.SSx1|Task Formats, Table 1]]

Every task is a natural-language specification, a complete infrastructure repository, executable workloads or test cases, and an evaluation harness. Everything is visible to the agent except the harness ({{Task Formats|ax:Sx3.SSx1}}). Three formats widen what is fixed in advance and what the agent may touch ({{Table 1|ax:Sx3.T1}}):

  • Kernel Function Completion (KFC), 55 tasks. A performance-critical kernel or operator with its interface and input-output semantics specified; complete or optimise it within one file without changing the interface. Correctness and numerical accuracy are tested first, then speed ({{KFC|ax:Sx3.SSx1.SSS0.Px1}}).
  • Long-Horizon Implementation (LHI), 20 tasks. An issue-style feature request and a coarse editable scope, such as a submodule; the files, dependencies and implementation path are left open. Solving it means navigating the codebase, changing several files, and building, testing and debugging repeatedly ({{LHI|ax:Sx3.SSx1.SSS0.Px2}}).
  • End-to-End Optimization (E2EO), 10 tasks. A representative workload, a system-level objective and constraints, with no hint of which components or strategies to use. The agent must profile, find the bottleneck, plan and make possibly repository-wide changes ({{E2EO|ax:Sx3.SSx1.SSS0.Px3}}).

What the paper does not say, and the released package does ({{SCORING.md|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/SCORING.md}}, {{tasks_index.json|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/tasks_index.json}}): 77 of the 85 tasks are scored on speed or quality ratios and only 8 are pass or fail, including 18 of the 20 LHI tasks, so "implementation" in the format's name does not mean a binary test. 42 of the 85 tasks need no GPU at all (CPU-side scoring pipelines, storage, quantised CPU kernels).

How the 85 tasks were built

[[Sx3.SSx2|Task Synthesis, Figures 2 to 4]]

Sources. Papers from top-tier systems conferences of 2023 to 2026, kept by an LLM filter if they study implementing, accelerating or saving resources in LLM training or inference and have a public implementation; plus issues and pull requests from widely used infrastructure repositories, kept if they introduce substantial optimisations, add important capabilities, address hardware- or workload-specific limits, or document hard engineering problems. That gives 2,260 papers and 1,852 engineering artifacts ({{Source collection|ax:Sx3.SSx2.SSS0.Px1}}). The authors' repository adds that these came from more than 10,000 candidates, of which agent-assisted triage kept over 4,000 ({{README|https://github.com/one2piece2hello/faibench_Frontier_InfraBench}}).

Taxonomy. An LLM labels each of the 4,112 sources at three levels: 410 fine-grained tags, clustered into 62 middle-level topics, grouped into nine top-level categories ({{Coverage taxonomy|ax:Sx3.SSx2.SSS0.Px2}}). The middle-level topics index task synthesis, and the paper's {{Figure 3|ax:Sx3.F3}} shows this taxonomy covering far more topics than any related benchmark.

Each bar's length is the count on a logarithmic scale. The 15 to 10 step is the authors' own: five E2EO candidates were dropped in final selection and are listed in {{tasks_index.json|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/tasks_index.json}} for transparency.

Three construction routes ({{Task Synthesis|ax:Sx3.SSx2}}), which are worth noting as benchmark methodology:

  • PR- and issue-grounded. Take the repository state before an important pull request as the task and the state after as the reference solution, adapting its unit tests into the harness. Small single-file changes become KFC tasks; larger multi-file ones LHI or E2EO ({{PR- and Issue-Grounded|ax:Sx3.SSx2.SSS0.Px3}}).
  • Agent-assisted. Agents scan repositories for high-value sites and cut out a code segment or a whole module. A second agent loop tracks which branches the current tests exercise and writes new tests until uncovered execution paths are covered ({{Agent-Assisted|ax:Sx3.SSx2.SSS0.Px4}}).
  • Expert-curated. For problems that repository history cannot reconstruct reliably (influential papers, conference challenges, emerging problems with no complete reference trajectory), experts build the starting repository by removing the implementation, reverting to a simpler baseline, or writing the task from the specification, and design the tests and workloads by hand ({{Expert-Curated|ax:Sx3.SSx2.SSS0.Px5}}).

Quality control. A performance task's reference solution must reach a stable speed-up of at least 1.15 in the official environment, and the starter or no-op solution must not beat the baseline. An implementation task's reference must pass every test while the starter fails at least one, with at least five tests covering normal inputs, boundaries, error paths and regressions. A task failing these is revised or excluded ({{Quality Control|ax:Sx3.SSx2.SSS0.Px6}}). Every one of the 77 released reference anchors clears 1.15 (the lowest is 1.16).
