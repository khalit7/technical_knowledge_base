Scoring: you only score by beating the expert

[[Sx3.SSx4|Evaluation Metrics]]

Every attempt gets a reward between 0 and 1. Both metrics are correctness-gated: the build, functional tests, edit constraints and anti-cheating checks must pass before any reward is given ({{Evaluation Metrics|ax:Sx3.SSx4}}).

Performance metric ({{Performance Metric|ax:Sx3.SSx4.SSS0.Px1}}). The candidate and the unmodified baseline are timed in an AB-BA paired protocol with at least five pairs, and the candidate's speed-up is the median of the per-pair ratios, s = mediani(tibase / ticand). The reference solution's speed-up sref is the median of at least five runs. If sref ≤ 1 the reward is zero; otherwise

Rperf = 0 if s ≤ sref;   min(1, ln(s / sref) / ln sref) if s > sref

A submission passes every check and runs exactly as fast as the experts' reference solution. What reward does it get?

Solid: the paper's curve. Dashed: the package's earlier curve, min(1, ½ ln s / ln sref), under which matching the reference scored 0.5; {{SCORING.md|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/SCORING.md}} says the new one is max(0, 2 × old − 1) and that the two are not comparable. The default task, kv-traffic-sol, is SCORING.md's own worked example: 2.58× scores 0, 4.14× scores 0.5 and 6.656× or more scores 1.

So the zero point is the expert's solution, not the starting code: the paper says the reward "is zero when the candidate matches or underperforms the reference solution", and full marks need the reference's speed-up squared. The package explains why: the earlier curve piled submissions up at 0.5 for matching the reference, and the new one spends the whole range on "whether, and by how much, a submission beats the oracle" ({{SCORING.md|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/SCORING.md}}). The bar varies enormously by task: the 77 frozen anchors run from 1.16× to 41,667×, median 11.3×, so a task anchored at 100× needs 10,000× for full marks. The {{Score a submission|tab:t-score}} tab lets you move the speed-up and the measurement noise and watch the reward.

Two details the package adds. "Speed-up" is the ratio of each task's declared metric, which is not always time: for the MoE training task it is baseline bits per byte over the candidate's, at a fixed wall-clock budget; for an embedding-compression task it is retrieval quality at 64 bytes a vector. And the anchors were calibrated on an H20, so they must be recalibrated on other hardware ({{README|https://github.com/one2piece2hello/faibench_Frontier_InfraBench}}).

Implementation metric ({{Implementation Metric|ax:Sx3.SSx4.SSS0.Px2}}): 1 if the code builds and imports, passes every test case and respects every forbidden-edit constraint; otherwise 0.

Cheating detection ({{Cheating Detection|ax:Sx3.SSx4.SSS0.Px3}}): a rule-based monitor scans the whole trajectory and final diff for prohibited behaviour (searching GitHub for the original implementation, fetching the patch or commit diff, recovering upstream code from published Python packages), and a proctor agent looks for subtler hacks (hard-coded expected outputs, skipped or bypassed correctness checks, branches that inflate the measured performance). Either one zeroes the attempt.

Results: a third of the maximum, very unevenly spread

[[Sx4.SSx2|Main Results, Tables 2 and 3]]

Setup ({{Experimental Setup|ax:Sx4.SSx1}}). Eight models at their highest reasoning setting and maximum context: proprietary Claude Opus 5, Claude Sonnet 5, GPT-5.6 Sol, Qwen3.8-Max and Qwen3.7-Max; open-weight Kimi K3, GLM-5.2 and DeepSeek-V4-Pro. GPT-5.6 Sol runs in its default scaffold, Codex; every other model runs in Claude Code. Each task gets 8 CPU cores, 32 GiB of memory and one NVIDIA H20 GPU (other GPU types disabled). One submission per KFC task, at most 16 candidates per LHI and E2EO task, and "we take the best submissions to compute the final score."

Claude Opus 5 leads at 36.53%, then Kimi K3 at 28.12% and Qwen3.8 Max at 27.73%; the rest are GPT-5.6 Sol 24.51, GLM-5.2 21.92, Claude Sonnet 5 17.58, Qwen3.7 Max 16.07 and DeepSeek-V4-Pro 13.31 ({{Table 2|ax:Sx3.T2}}). Even with the whole repository and the test cases in hand, the strongest model gets slightly more than a third of the maximum. The Full column is the mean reward over the 85 tasks: it reproduces exactly as (55 × KFC + 20 × LHI + 10 × E2EO) / 85 from {{Table 3|ax:Sx5.T3}}, and as the task-count-weighted mean of the nine categories of Table 2 (see the {{tables tab|tab:t-tables}}).

No model is strong everywhere. Opus leads five of the nine categories; Kimi K3 is best on Inference and Serving (30.5) and System Optimization (41.1), Qwen3.7 Max on Hardware and Edge (5.4) and GLM-5.2 on System Assurance (57.4) ({{Main Results|ax:Sx4.SSx2}}).

The three formats get more open-ended from KFC (one function) to E2EO (find the bottleneck yourself). On which format do the top four models score highest?

{{Table 3|ax:Sx5.T3}}. Whiskers: the largest standard error a mean of that many rewards in [0, 1] can have, √(m(1 − m)/n), an upper bound computed here because the paper reports no error bars.

The paper reads Table 3 as "capacity over open-endedness" ({{Capacity over open-endedness|ax:Sx5.SSx2}}): Opus is first in every format (KFC 37.16, LHI 21.60, E2EO 62.94); Kimi K3, second overall, is especially competitive on E2EO (56.41); Qwen3.8 Max is consistently strong; and LHI is below KFC for every model, so long-horizon repository work stays hard. That direction was expected; the size of the drop is the useful number: Opus falls from 37.16 to 21.60, 42% lower, and across the eight models LHI is 22% to 45% below KFC (1 − LHI / KFC from Table 3). What the paper does not discuss is that the most open-ended format scores highest. E2EO has only 10 tasks, its 8 performance tasks get up to 16 scored rounds with the best kept while every KFC task gets one shot, and the leaderboard applies E2EO-specific selection rules (see {{How much to believe|tab:t-read:s-trust}}); so the format ranking mixes difficulty with budget.

Hardware and Edge is the hardest category: the best score in it is 5.4%. How many of the 85 tasks is that score based on?

Task counts by category and format, from {{Figure 4|ax:Sx3.F4}} (they sum to 55, 20 and 10, and match the leaderboard's per-category counts). The bottom row is the best score in each category from {{Table 2|ax:Sx3.T2}}, with the standard-error upper bound for that score.

The paper says Hardware and Edge is "particularly challenging": "even the best-performing model achieved only 5.4%", which it takes to mean frontier models lack an understanding of the hardware side of AI infrastructure ({{Main Results|ax:Sx4.SSx2}}). Two corrections. The 5.4% belongs to Qwen3.7 Max, seventh overall; Claude Opus 5 scores 3.9 there, and two models score 0. And the category is 3 tasks (2 KFC, 1 LHI), so every model's score there sums to under a fifth of one task's reward. The direction (near zero for everyone) is real; the ranking inside it is noise. Data Infrastructure (2 tasks), System Assurance (4) and System Optimization (5) are almost as thin; only Kernel (28) and Training (19) are large enough for the category scores to mean much.

More rounds help; more reasoning helps less reliably

[[Sx4.SSx3|Ablation Studies, Figures 5 and 6]]

Iterations ({{Performance over iterations|ax:Sx4.SSx3.SSS0.Px1}}, {{Figure 6|ax:Sx4.F6}}). One hard E2EO training task: a fully editable nanoGPT training system, a wall-clock budget and a parameter-count floor; minimise validation bits per byte (BPB). The standard optimisations are efficient token dispatch (sorting, grouped batched GEMMs, per-expert capacity buffers), load balancing against router collapse and dropped tokens, and the routing configuration and capacity factor, trading quality, throughput and drop rate. Opus's very first submission is already low (1.412 BPB, better than the final best of GPT-5.6 Sol, GLM-5.2, Qwen3.7 Max and DeepSeek-V4-Pro) and keeps improving to 1.272, which the authors call "highly impressive". Qwen3.8-Max and Kimi K3 start poorly (Kimi has no valid result for two rounds) but refine quickly to 1.338 and 1.328. DeepSeek-V4-Pro, Qwen3.7-Max, GLM-5.2 and GPT-5.6 Sol sit on long plateaus and end at 1.464, 1.701, 1.488 and 1.445. The text does not mention Claude Sonnet 5, which improves steadily from 1.729 to 1.349, the fourth-best final value.

The {{Replay the MoE training run|tab:t-run}} tab replays every round, decoded exactly from the paper's vector figures, and translates the BPB into the task's own reward using the frozen constants in the released package. On that scale the picture changes: the reference recipe sits at 1.275 BPB, so only Opus ever scores above zero (0.005, from round 21), and full marks would need 0.831 BPB, below the 0.9 the grader rejects as implausible.

Reasoning budget ({{Performance over reasoning budget|ax:Sx4.SSx3.SSS0.Px2}}, {{Figure 5|ax:Sx4.F5}}). Opus, Kimi K3 and GPT-5.6 Sol at up to five effort levels: all three are best at max, but scores do not rise steadily with budget, and GPT-5.6 Sol is unstable in the middle (22.18 at medium, 18.27 at high).

Printed point labels of {{Figure 5|ax:Sx4.F5}}; Kimi K3 was run at three levels only. The max-effort points are not Table 3's LHI scores (21.60, 19.55, 13.98): they equal (20 × LHI + 10 × E2EO) / 30 from Table 3 to the second decimal (35.38, 31.84, 22.76), and the authors' leaderboard labels this study "30 tasks". The caption and text say 20 LHI tasks.

The paper concludes that Kimi K3 loses about 45% of its score at low effort (17.45 against 31.83, a 45.2% drop), so its strong showing depends on heavy test-time compute, while "the performance gap between Claude Opus 5 and GPT-5.6 Sol across different budget settings is not particularly significant". That last sentence is hard to square with the figure: GPT-5.6 Sol is 9.3 to 15.3 points below Opus at every level, and it too loses 29.6% from max to low, against Opus's 11.4%.

Errors, persistence and cheating

[[Sx5|Analysis, Figure 7]]

Error modes ({{Error Modes Analysis|ax:Sx5.SSx1}}, {{Figure 7|ax:Sx5.F7}}). Error messages from every trajectory, in four classes: Python runtime, CUDA execution, Triton / MLIR / CUDA compile, and tensor shape mismatch. The paper's two readings:

  • The high scorers make more errors (Opus 175, Kimi K3 139, Qwen3.8 Max 179), which the authors read as persistence through trial and correction, while weak models (DeepSeek-V4-Pro 81, Qwen3.7 Max 32, Claude Sonnet 5 26) give up early or settle for simpler solutions. The pattern is real but loose: GLM-5.2, fifth overall, has the most errors (185), and GPT-5.6 Sol, fourth, has 96; the rank correlation between error count and score is 0.60 over eight models.
  • Opus fails differently. Python runtime errors are more than half of all errors for five of the eight models, but only 30.9% of Opus's; its largest class is CUDA execution errors (39.4%). The authors take this as Opus writing Python that works in the repository first time, leaving its attention for low-level implementation, "likely one of the reasons" it leads. The shares hold exactly (counts decoded from the vector figure); the causal reading is the authors' interpretation.

Hacking ({{Hacking Prevention and Detection|ax:Sx5.SSx3}}). Two preventions: a soft network disconnection (pip and URLs related to the test repositories are hijacked to return a warning) and prompting with a definition of hacking and an explicit ban. Across all runs the rule-based detector fired only three times, all DeepSeek-V4-Pro requests for code from the PyTorch website, and the proctor agent confirmed no actual hacking. The paper concludes the two mechanisms prevented cheating.

Case study: what the strong model does differently

[[Sx6|Case Study, Figure 8]]

The same MoE training task, now with every submission plotted, for Claude Opus 5 (best on this task) against Qwen3.7 Max and DeepSeek-V4-Pro ({{Figure 8|ax:Sx6.F8}}). The authors view the trajectories as two coupled capabilities, choosing promising directions and executing local changes reliably, and find three behaviours ({{Case Study|ax:Sx6}}):

  1. Cheap experimental foundations ({{Experimental Foundations|ax:Sx6.SSx1}}). Opus builds lightweight local experiments that reproduce only the relevant part of the workload; it first checks that a short local run's BPB is close to the development measurement, then uses such runs to reject unpromising changes before a formal submission, exploring broadly before focusing. Qwen3.7 Max and DeepSeek-V4-Pro mostly implement, submit and observe, so each formal submission doubles as debugging, hypothesis test and evaluation. DeepSeek, for example, applied torch.compile to the expert modules without checking checkpoint compatibility and wasted a submission on a checkpoint that could not be loaded. Takeaway: good models build low-cost mechanisms for screening hypotheses.
  2. Variable and noise control ({{Variable and Noise Control|ax:Sx6.SSx2}}). DeepSeek often changes several variables at once, so outcomes cannot be attributed. Qwen3.7 Max does disciplined single-variable tuning, but many of its differences are the size of measurement noise: isolation alone is not enough. Opus estimates the measurement variation, accounts for differences in completed optimisation steps, and focuses on effects large enough to interpret. One learning-rate schedule change worsened BPB from 1.3646 to 1.3932; because both runs had the same seed, the same number of steps and nearly identical runtime, Opus treated the loss as real, hypothesised that too long at very low learning rates hurts, and moved to a warmup-stable-decay schedule, which reached 1.3248. Takeaway: good models run experiments that maximise the information gained per iteration.
  3. Cautious attribution ({{Cautious Attribution|ax:Sx6.SSx3}}). A change seemed to cut throughput badly; Opus found that the edit had invalidated the Inductor compilation cache, so the run paid a cold-compile cost, re-ran under matched cache conditions, and found throughput essentially unchanged with the BPB gain kept. It caught cache artifacts like this several times, delaying attribution until a proper control existed; the weaker models more often credit a change to the latest edit. Takeaway: good models test alternative explanations before attributing an outcome.

Overall, the authors conclude, Opus keeps one coherent plan across rounds (explore broadly, compare under control, update on reliable evidence), while the weaker models make local, greedy decisions, so useful knowledge does not accumulate. All three behaviours come from one task and three models, read qualitatively; they are good hypotheses about what separates agents, not measured effects.
