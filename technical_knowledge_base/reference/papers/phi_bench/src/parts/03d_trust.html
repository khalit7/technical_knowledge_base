How much of this to believe

[[Sx4|Evaluation, Analysis, and the released package]]

What holds up.

  • The benchmark is real and inspectable. All 85 tasks are released as self-contained Docker packages with offline graders, frozen anchors, reference solutions for 83 and a runner; each vendored repository is checked to be exactly the state the reference patch was cut from ({{repository|https://github.com/one2piece2hello/faibench_Frontier_InfraBench}}). Few agent benchmarks this young can be rerun by an outsider.
  • The arithmetic is consistent. The Full column reproduces from Table 3's formats and from Table 2's categories weighted by Figure 4's task counts; the leaderboard's four-decimal scores round to every one of Table 2's 72 cells; the iteration curves decoded from the vector Figure 6 match the leaderboard's own data in 191 of 192 points (Claude Sonnet 5's round 13 reads 1.5742 in the figure and 1.5144 in the data). All {{checks|tab:t-tables:chkH}} are listed on the tables tab.
  • Claude Opus 5 first is probably right. It leads by 8.41 points; with no error bars published, the largest standard error a mean of 85 rewards can have is about 5 points per model, so an unpaired bound on the gap's error is 7.1 points and the lead is about 1.2 such errors. Paired over the same tasks the real error is smaller. It is also first in every format, in five categories, and at high effort on the authors' leaderboard (34.42, ahead of Kimi K3 at 26.20).
  • LHI below KFC holds for all eight models, and the hacking checks are concrete (a rule monitor plus a proctor agent, three alerts, none real).

What to discount.

  • 36.53% is not "a third of tasks solved". It is a mean reward in which matching the expert reference scores zero and full marks need the reference speed-up squared ({{Performance Metric|ax:Sx3.SSx4.SSS0.Px1}}). It cannot be compared with pass rates on other benchmarks, and it mixes 77 continuous rewards with 8 binary ones, which the package's own {{SCORING.md|https://github.com/one2piece2hello/faibench_Frontier_InfraBench/blob/main/SCORING.md}} advises against ("do not directly average performance and implementation classes together").
  • Single runs, no error bars. Kimi K3 and Qwen3.8 Max are 0.39 points apart and GPT-5.6 Sol and GLM-5.2 2.6 points, inside any plausible noise. On the leaderboard's high-effort table GLM-5.2 is third and GPT-5.6 Sol fifth, the reverse of their max-effort order.
  • Not like for like. GPT-5.6 Sol runs in Codex; the other seven, including four rival labs' models, run in Claude Code, Anthropic's harness ({{Models and Scaffolds|ax:Sx4.SSx1.SSS0.Px1}}). Harness choice can move scores by tens of points (see {{HarnessDev|n:3d45c17b0d0d81cd9883f783840e013f}}). Formats also differ in budget: one shot for KFC, up to 16 scored rounds for LHI and E2EO performance tasks.
  • The selection rule is not the one the paper states. The paper says it takes the best submissions. The leaderboard's data file says: "e2e performance tasks: take the non-zero minimum (all-zero → 0)", with an exception for one model, "kimi-k3, max, e2e perf: if 2nd-best/best < 0.7 treat as an anomalous run → take best; otherwise take 2nd-best" ({{bench.json|https://faibench.org/data/bench.json}}). A per-model rule on the format where Kimi K3 is strongest should be in the paper.
  • Category findings rest on a handful of tasks. Hardware and Edge is 3 tasks, and its 5.4% is Qwen3.7 Max's, not the leader's; the conclusion that models lack hardware understanding needs more than three tasks.
  • The effort figure is mislabelled. Its points are the 30 LHI and E2EO tasks, not "20 LHI problems"; Kimi K3 has three effort levels, not five. The direction (best at max, not monotone) still holds.
  • The iteration and case studies are one task. The plotted run was forced to 20 to 24 rounds, beyond the main evaluation's cap of 16 ({{iter.json|https://faibench.org/data/iter.json}}), and its BPB values are development measurements. Under the task's own reward only Opus ever scores, and only 0.005. The three behaviours are qualitative readings of three trajectories.

In the authors' favour: they released everything needed to check this page, their scoring document is unusually candid (the oracle zero point, the non-comparable curves, timeouts that still score), and the leaderboard publishes the selection rules this section quotes.

Verdict Believe that frontier models are far from autonomous on open-ended infrastructure work, that long-horizon repository tasks are harder than kernels, and probably that Claude Opus 5 leads. Treat the middle of the table as a tie, the category and effort findings as anecdotes, and 36.53% as a reward on a demanding scale, not a solve rate.

What it takes to use this

[[Sx4.SSx1|Implementation Details, and the package]]
  • Code and licence. The benchmark's own work (task specifications, graders, reference solutions, loop harness, runner) is Apache-2.0; the vendored upstream code (nanoGPT, torchtitan, vLLM, llama.cpp, Megatron-LM, ColossalAI, flash-linear-attention and others) and fetched weights keep their own licences ({{README|https://github.com/one2piece2hello/faibench_Frontier_InfraBench}}). Also on {{Hugging Face|https://huggingface.co/datasets/faibench-Frontier-Infra-Bench/faibench_Frontier_Infra_Bench}}.
  • Hardware. 43 tasks need one GPU, 42 none; each gets 8 cores and 32 GiB. The anchors were calibrated on an H20: on any other card, recalibrate each task by running its baseline and reference, as the manifests describe. Docker 23 or later with buildx; building needs network access (apt, PyPI, five git clones, five E2EO tasks pull multi-gigabyte weights), solving and scoring run offline.
  • Time. The package's agent timeouts are 1.5 hours for every LHI task and 33 KFC tasks, 6 hours for the other 22 KFC tasks, and 1.5 to 6 hours for E2EO, at most 257.5 agent-hours for one model over all 85 tasks. The paper reports neither tokens nor cost.
  • Running a model. scripts/run_task.py builds, runs an agent CLI injected at runtime (Claude Code or Codex), scores and aggregates; an oracle agent replays the reference to check a task hits its anchor.
  • When it pays off. For comparing agents on realistic infrastructure work, especially the training and kernel categories, which have enough tasks. It buys little for small differences between models without repeated runs, and scores are not comparable across reward-curve versions or across hardware without recalibration.

Why it matters (beyond the paper)

It puts a number on a claim the industry has started making loudly. OpenAI said in September that by mid-August its internal metrics showed 3.1 agent-workdays of research effort per human workday ({{The Neuron|https://www.theneuron.ai/news/openai-ai-research-acceleration-alignment-slowdown/}}, via the {{2026-09-07 tech news issue|n:3d45c17b0d0d81dca858e1cec21d3314}}), and AMD's ROCm 10.0 ships AMD Skills, validated ROCm optimisation knowledge packaged as agent skills for Claude, Cursor and Codex, beside Hyperloom, which profiles, plans and validates optimisations autonomously ({{Phoronix|https://www.phoronix.com/news/AMD-ROCm-10.0}}, via the {{2026-09-14 issue|n:3db5c17b0d0d8135a34af60966c5ecc1}}). Φ-Bench says that on open-ended infrastructure engineering the best model earns roughly a third of the available reward, measured against expert solutions, and on hardware adaptation close to nothing.

It is also the first benchmark whose task categories map almost exactly onto this knowledge base's systems topics, which makes it a direct measure of how much of {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}, {{Topic: cuda-and-gpu-programming|n:3c65c17b0d0d81c39f34d5e070d783c1}} and {{Topic: ml-infra-and-orchestration|n:3c65c17b0d0d81b5925bfd1d8665dd4b}} a model can currently do.
