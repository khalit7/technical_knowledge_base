Efficient Memory Management for Large Language Model Serving with PagedAttention (PagedAttention, vLLM)

Woosuk Kwon, Zhuohan Li, Siyuan Zhuang, Ying Sheng, Lianmin Zheng, Cody Hao Yu, Joseph E. Gonzalez, Hao Zhang, Ion Stoica
UC Berkeley, with Stanford, UC San Diego and an independent researcher · September 2023 (arXiv 2023-09-12); SOSP '23, Koblenz, 23 to 26 October 2023

Problem: the batch size is capped by KV cache memory

§1 Introduction, §3

An LLM generates one token per step, and each step has to read all the model's weights. Generating for one request at a time is therefore memory-bound: it "underutilizes the computation power of GPUs and limits the serving throughput" (§1). The fix is to batch many requests into each step, so that one read of the weights serves all of them. How many requests fit is decided by GPU memory, and specifically by the space for their KV cache: the key and value vectors of every token so far, kept so that each new token can attend to them (§2.2).

The cache is large. For OPT-13B one token's KV cache is 800 KB: 2 (key and value) × 5,120 (hidden size) × 40 (layers) × 2 bytes (FP16) = bytes, exactly 800 KiB. OPT can generate sequences of up to 2,048 tokens, so one request can need as much as 1.6 GB ( GiB) (§3). On an A100 with 40 GB serving a 13B model, about 65% of memory holds the weights (26 GB) and the KV cache gets the rest: "close to 30%" in the text, ">30%" in Figure 1's label; activations take a small remainder (Figure 1). Table 1 makes it concrete: 12 GB for the KV cache, which is 15.7K token slots (Table 1; 12 GiB / 800 KiB = ). Even if all of memory went to the cache, "only a few tens of requests could be accommodated" (§3). And it will get worse: from A100 to H100 the FLOPS rose more than 2× while GPU memory stayed at 80 GB at most (§3).

Figure 1 (right), redrawn from the points in its vector graphics: memory against batch size for "existing systems" and vLLM, and the throughput a batch of that size reaches. The dotted lines are the paper's: where memory hits 40 GB, the batch size and therefore the throughput stop.

The diagnosis: existing systems (FasterTransformer, Orca) store each request's KV cache in one contiguous chunk, because deep learning frameworks want tensors contiguous, and since the output length is unknown they pre-allocate the chunk for the maximum possible length (§3.1). The KV cache, unlike ordinary tensors, "dynamically grows and shrinks over time" and its lifetime and length are not known in advance (§1).

That wastes memory three ways (Figure 3, §3.1):

  • Reserved slots for tokens the request will generate later. They are eventually used, but held empty for the request's whole lifetime, so shorter requests cannot use them meanwhile.
  • Internal fragmentation: slots reserved for a maximum length the request never reaches. Figure 3's request A has a 2,048-token maximum and finishes after 10 tokens: 2,038 slots are never used; request B (maximum 512) leaves 507 (Figure 3; 2,048 − 10 = , 512 − 5 = ). This waste is only known once the request finishes.
  • External fragmentation from the allocator (the paper assumes a buddy allocator for Orca), because every chunk has a different size. It "will never be used for generated tokens, which is known before serving a request".

The paper's profiling puts the result at "only 20.4% to 38.2% of the KV cache memory" holding actual token states (Figure 2). The Simulate the KV cache tab replays exactly this, the four systems on the same memory.

Orca (Oracle) is the paper's idealised baseline: it is told every request's true output length in advance, so it reserves exactly prompt + output and never over-provisions. On the ShareGPT experiment, what share of its KV cache memory holds actual tokens?

38.2% (Figure 2). Knowing the length removes internal fragmentation (zero for Oracle), but two wastes remain. The chunk for a request's future tokens is reserved from the start (25.2%), and the buddy allocator rounds every chunk up to a power of two and leaves gaps between chunks of different sizes (36.6% "external fragmentation and others"). vLLM, allocating 16-token blocks on demand, keeps 96.3% of the memory holding tokens.

The second problem is sharing. Parallel sampling (several outputs for one prompt, as in code assistants) and beam search keep several sequences per request that could share their prompt's KV cache, and beam candidates share much more, but with each sequence in its own contiguous chunk "memory sharing is not possible" (§1). In the paper's §6.3 experiment the prompt is 12% of the total KV cache under parallel sampling, and beam search can share enough to save up to 55% (§3). Compaction, the textbook fix for fragmentation, is "impractical" with a cache this large and would still not allow sharing (§3.1).

The third challenge is scheduling for unknown lengths: as outputs grow the cache can exhaust memory, and the system has to decide whose cache to delete or swap out (§3).

Background: prompt phase, generation phase, iteration-level batching

§2 Background

A request's prompt (x1, ..., xn) and its generated tokens together form a sequence. Generation has two phases (§2.2). The prompt phase takes the whole prompt at once, computes the first new token and the keys and values k1..kn, v1..vn; it is a matrix-matrix computation that uses the GPU well. The autoregressive generation phase then adds one token per iteration, computing only the new token's key and value and reading all the cached ones; it is matrix-vector work, memory-bound, and "responsible for most portion of the latency of a single request". A token's KV cache depends on every token before it, so the same token at a different position has a different cache (§2.2).

Batching requests that arrive at different times with different lengths is the job of iteration-level scheduling (Orca; cellular batching before it): after every iteration finished requests leave the batch and new ones join, so a new request waits one iteration instead of a whole batch, and special kernels remove the need to pad inputs and outputs (§2.3). PagedAttention keeps this and attacks what still limits it: "the number of requests that can be batched together is still constrained by GPU memory capacity" (§3). The paper calls the two techniques complementary: Orca interleaves requests so more can run, vLLM raises memory utilisation so more fit (§9).

The idea: page the KV cache like virtual memory

§4.1 PagedAttention

The move is the operating system's answer to fragmentation and sharing, virtual memory with paging (Kilburn et al., 1962): "one can think of blocks as pages, tokens as bytes, and requests as processes" (§1). PagedAttention splits each sequence's KV cache into KV blocks of a fixed number of tokens B, the block size, which need not sit next to each other in memory (§4.1). With key block Kj = (k(j−1)B+1, ..., kjB) and value block Vj likewise, attention for query qi becomes a sum over blocks (Eq. 4):

the row of attention scores of query i on block j, (ai,(j−1)B+1, ..., ai,jB)

the number of blocks holding tokens up to i; the kernel fetches each block wherever it lives, through the block table

The output is exactly ordinary attention (Eq. 3): only where the operands live changes. In Figure 5 the query "forth" attends over three non-contiguous blocks, "Four score and seven", "years ago our fathers", "brought forth" (Figure 5). A footnote adds that a block can hold one token's keys and values across all layers and heads, or each layer and head can have its own block and block table; "the two designs have no performance difference" and vLLM uses the second (§4.1, footnote 1).

What paging buys: small blocks allocated on demand remove reservation and bound internal fragmentation; one fixed block size eliminates external fragmentation; and blocks can be shared between sequences, within a request or even across requests (§1).

The KV cache manager and the block table

§4.2 to §4.3, Figures 6 and 7

A request's cache is a list of logical KV blocks, filled left to right, the last block's empty slots kept for future tokens. On each GPU worker a block engine takes one contiguous chunk of GPU memory and cuts it into physical KV blocks (the same on CPU memory, for swapping). The block manager keeps a block table per request: for each logical block, its physical block and the number of filled positions, exactly like a page table (§4.2). Block numbers, words and reference counts are the paper's own (Figures 6 to 9). Beam search shows block tables only, as Figure 9 does: each box is a block of four tokens. The animation runs only while it is on screen, and starts paused if your system asks for reduced motion.

The walk-through (§4.3): (1) the prefill step reserves only the blocks the 7-token prompt needs, logical blocks 0 and 1 mapped to physical blocks 7 and 1, computes the prompt's KV cache with ordinary attention and the first output token; (2) the first decoding step runs PagedAttention over blocks 7 and 1 and writes the new token's KV into the last free slot of block 1, updating its fill count; (3) the next step finds the last block full and maps a new logical block to a newly allocated physical block 3. Every iteration, vLLM picks the sequences to batch, allocates the blocks they newly need, concatenates all the iteration's input tokens (whole prompts for prompt-phase requests, the latest token for the others) into one sequence for the model, and the kernel reads and writes the blocks through the tables (§4.3).

Since blocks are filled left to right and a new one is taken only when the last is full, a request's waste is at most one partly filled block, and its blocks are freed the moment it finishes (§4.3). Larger blocks let the kernel process more positions in parallel but fragment more; that trade-off is the block-size ablation (§7.2, below).

Sharing: reference counts and copy-on-write

§4.4 Other decoding scenarios

Parallel sampling (Figure 8): both samples' logical blocks 0 and 1 map to the same physical blocks 7 and 1, so the prompt's cache is stored once. Each physical block carries a reference count (here 2). When sample A1 writes to its last logical block, vLLM sees physical block 1's count is above 1, allocates block 3, has the block engine copy block 1 into it and decrements the count to 1; when A2 then writes, block 1's count is already 1 and it writes in place. This is copy-on-write at block granularity, as when an OS forks a process; only the prompt's last, partly filled block is ever copied (§4.4).

Beam search shares much more and the pattern changes as decoding goes, like the process tree of repeated forks (Figure 9): with beam width k = 4, all candidates share block 0 (the prompt), candidate 3 diverged at the second block, candidates 0 to 2 share three blocks. When the next top-4 all descend from candidates 1 and 2, the blocks of candidates 0 and 3 lose their references and blocks 2, 4, 5 and 8 are freed; new blocks 9 to 12 hold the new tokens. Where earlier systems would copy "a large portion of candidate 2's KV cache" to continue candidate 3, vLLM copies at most one block (§4.4).

Shared prefix (Figure 10): a long system prompt (instructions and examples, Figure 10's English-to-French few-shot prompt) can be cached once by the provider in reserved physical blocks, "as how OS handles shared library across processes"; a request maps its first logical blocks to them, the last one marked copy-on-write, and the prompt phase then runs only on the user's own input (§4.4). Mixed decoding methods: because the kernel only ever sees a list of physical block IDs per sequence, requests with different decoding methods batch together freely, "which existing systems cannot efficiently do" (§4.4). All of it is built from three primitives: fork (a new sequence from an existing one), append (a token) and free (a finished sequence) (§5.2).

Parallel sampling with 6 outputs per prompt, OPT-13B on the Alpaca trace. The six samples share the prompt's KV cache. How much KV memory does sharing save?

9.79% (Figure 15). Only the prompt is shared, and Alpaca's prompts are short: 19.31 tokens on average against 58.45 output tokens (Figure 11), so about one 16-token block per prompt, and the partly filled last block is copied anyway. ShareGPT's prompts are 8.4× longer and the saving rises to 16.2% to 30.5%. Beam search shares generated blocks too: 37.6% to 55.2% on Alpaca, 44.3% to 66.3% on ShareGPT (§6.3).

Scheduling and preemption

§4.5 Scheduling and Preemption

vLLM serves requests first come, first served, which ensures fairness and prevents starvation; when it must preempt, the latest arrivals go first (§4.5). When the physical blocks run out it faces the two classic paging questions. Which blocks to evict? Since all of a sequence's blocks are read every step, eviction is all-or-nothing per sequence, and the sequences of one request (the beams of a beam search) form a sequence group that is gang-scheduled, preempted and rescheduled together, because they share memory. How to bring them back? Two ways:

  • Swapping: copy the evicted blocks to CPU memory, managed by a CPU block allocator (Figure 4). While any sequence is swapped out, vLLM accepts no new requests; the swap space never exceeds the GPU's KV memory, so it is bounded.
  • Recomputation: drop the blocks and recompute them on rescheduling. This is cheaper than it sounds: the generated tokens are appended to the prompt and the whole cache is rebuilt in one prompt-phase iteration, not token by token. An OS cannot do this; an LLM server can (§4.5, §8).

Which is faster depends on the CPU to GPU bandwidth and the GPU's compute (§7.3, below).

Distributed execution

§4.6 Distributed Execution

Models too large for one GPU run with Megatron-LM-style tensor parallelism: linear layers split for block-wise matrix multiplies, attention split by heads, the GPUs synchronising with all-reduce in an SPMD schedule. Every shard processes the same tokens and so needs the KV cache for the same positions; vLLM therefore keeps one KV cache manager in the centralised scheduler, and every worker uses the same logical-to-physical mapping while storing only its own heads' part of each block (§4.6). Each step the scheduler broadcasts the input token IDs and the block tables; the workers run the model, all-reduce among themselves without the scheduler, and send back the sampled tokens. Workers never coordinate on memory management (§4.6).

Implementation

§5 Implementation

vLLM is 8.5K lines of Python and 2K lines of C++/CUDA, with a FastAPI frontend that extends the OpenAI API (each request can set its own sampling parameters, maximum length and beam width). The scheduler and block manager are Python; models (GPT, OPT, LLaMA) use PyTorch and Hugging Face Transformers; NCCL carries tensors between GPUs (§5). Three kinds of custom kernel make paging cheap (§5.1):

  • Fused reshape and block write: each layer's new KV is split into blocks, reshaped to the layout the reads want and written where the block table says, in one kernel launch.
  • Fused block read and attention: FasterTransformer's attention kernel adapted to read the cache through the block table on the fly, with one GPU warp per block for coalesced reads and support for different sequence lengths in one batch.
  • Fused block copy: copy-on-write copies of scattered blocks batched into one launch instead of many small cudaMemcpyAsync calls.

Results

§6 Evaluation

Setup (§6.1): OPT-13B, 66B and 175B and LLaMA-13B on Google Cloud A2 instances with A100 GPUs (Table 1: one A100-40GB, four A100s, eight A100-80GB). Workloads are synthesised from the input and output lengths of ShareGPT (user-shared ChatGPT conversations) and Alpaca (GPT-3.5 self-instruct data); ShareGPT's prompts are 8.4× longer and its outputs 5.8× longer on average, with more variance (Figure 11). Arrival times are Poisson at a chosen request rate, since the datasets have no timestamps. Baselines: FasterTransformer with a custom dynamic batching scheduler (batch size as large as memory allows), and Orca, which is not public, so the authors implemented their own, with a buddy allocator, in three versions: Oracle (knows the true output lengths, "infeasible to achieve in practice"), Pow2 (over-reserves outputs up to 2×, 25 becomes 32) and Max (always reserves the 2,048-token maximum). The metric is normalized latency (the mean of each request's end-to-end latency divided by its output length, as in Orca) against request rate, over 1-hour traces (15 minutes for OPT-175B, for cost).

Basic sampling (Figure 12, §6.2): each curve is flat until the rate passes the system's capacity, then latency explodes as the queue grows without bound. On ShareGPT vLLM sustains "1.7× to 2.7×" the request rate of Orca (Oracle) and "2.7× to 8×" that of Orca (Max) at similar latency, and up to 22× FasterTransformer's. The reason is the batch: on OPT-13B vLLM runs 2.2× as many requests at once as Orca (Oracle) and 4.3× as many as Orca (Max) (Figure 13; 30.42 / 13.62 = , 30.42 / 7.00 = ). Alpaca follows the same trend except OPT-175B, where 264 GB of KV memory and short sequences let even the Orca baselines batch a lot, and serving becomes compute-bound rather than memory-bound. The abstract and §1 add that the improvement "is more pronounced with longer sequences, larger models, and more complex decoding algorithms": true for longer sequences (ShareGPT over Alpaca) and for decoding (below), but not monotone in model size, since read off Figure 12 the lead over Orca (Oracle) on ShareGPT is largest at 66B and smallest at 175B. The curves, rebuilt reads every ratio off the paper's figures.

Parallel sampling and beam search (Figure 14, §6.3): the more sequences per request, the larger vLLM's lead; over Orca (Oracle) on OPT-13B and Alpaca it grows from 1.3× in basic sampling to 2.3× in beam search with width 6. Memory saved by sharing, "the number of blocks we saved by sharing divided by the number of total blocks without sharing": 6.1% to 9.8% (parallel sampling) and 37.6% to 55.2% (beam search) on Alpaca, 16.2% to 30.5% and 44.3% to 66.3% on ShareGPT (Figure 15).

Shared prefix (§6.4): LLaMA-13B translating WMT16 English to German with a shared instruction-and-examples prefix: 1.67× Orca (Oracle)'s throughput with a 1-shot prefix (80 tokens) and 3.58× with 5 shots (341 tokens) (Figure 16).

Chatbot (§6.5): OPT-13B answering ShareGPT conversation histories cut to the last 1,024 tokens, with at most 1,024 generated, and no KV cache kept between rounds: vLLM sustains "2× higher request rates" than all three Orca baselines, which behave alike because the buddy allocator makes each of them reserve 1,024 output slots regardless of its length prediction (Figure 17).

Ablations

§7 Ablation Studies

Kernel overhead (§7.1): reading the block table, extra branches and variable lengths make vLLM's attention kernel "20 to 26%" slower than FasterTransformer's in isolation (Figure 18a). The paper calls it small because only attention pays it, not the linear layers, and end to end vLLM wins anyway. Read off the figure, the overhead is 19% to 26% at batch size 32 but 25% to 44% at batch size 8 (Kernel overhead, rebuilt).

Block size: bigger blocks let the kernel process more positions in parallel; smaller ones waste less memory. On the Alpaca trace (short sequences), which block size gives the lowest end-to-end latency?

16 and 32 (Figure 18b, §7.2). Below 8 the kernel cannot use the GPU's parallelism; on Alpaca, larger blocks "significantly degrade the performance since the sequences become shorter than the block sizes". On ShareGPT, with longer sequences, 16 to 128 are all best. vLLM's default is 16, "large enough to efficiently utilize the GPU and small enough to avoid significant internal fragmentation in most workloads", and it still is (DEFAULT_BLOCK_SIZE = 16 in vLLM's cache config today). The right panel is the memory side of the trade-off from this page's simulator: the share of KV memory holding tokens, and the batch it allows, by block size.

Recomputation against swapping (Figure 19, §7.3): swapping many small blocks means many small CPU to GPU transfers, which throttles the effective PCIe bandwidth, so swapping is slow at small block sizes; recomputation does not touch the blocks and costs the same at every size. Recomputation wins for small blocks, swapping for large ones, and from 16 to 64 the two perform alike end to end. The paper's phrasing, "recomputation overhead is never higher than 20% of swapping's latency", cannot mean what it says: at block size 256 recomputation takes 39.1 ms against swapping's 33.4 ms, 117% of it. It holds read as "never more than 20% slower than swapping" (17% at most in the figure).

Where paging does not help, and what is LLM-specific

§8 Discussion, §9 Related work

The authors are explicit about the limits (§8): paging pays off here because the workload allocates memory dynamically (output length unknown) and its performance is bound by GPU memory capacity. In DNN training tensor shapes are static and allocation can be planned ahead; serving non-LLM DNNs is mostly compute-bound, so better memory efficiency may buy nothing; in such cases the indirection and non-contiguous blocks "may rather degrade the performance". What vLLM adds to the OS idea is application knowledge: all-or-nothing eviction (a request needs all its tokens resident), recomputation as a recovery path (impossible for an OS), and fused kernels that hide the indirection (§8).

Related work (§9): general serving systems (Clipper, TensorFlow Serving, Nexus, InferLine, Clockwork; DVABatch, REEF, Shepherd, AlpaServe) ignore the autoregressive token state; Transformer-specific systems use kernel optimisations, advanced batching, model parallelism and parameter sharing, with Orca the closest. Swapping and recomputation were used before to cut training memory; FlexGen swaps weights and token states for offline inference on small GPUs, not online serving; OLLA optimises tensor lifetimes and placement but not at block level; FlashAttention tiles attention to cut its peak memory and IO. Block-level memory management for online serving is the paper's new idea.

How much of this to believe

What holds up.

  • The memory accounting. It is arithmetic anyone can redo: 800 KiB per token, 15.7K slots in 12 GB and 60.1K for OPT-175B recompute exactly from the OPT configurations (Table 1, rebuilt). This page's simulator, given only Table 1's memory, the paper's own length distributions (Figure 11) and the allocation rules of §6.1, independently lands near Figure 2 and Figure 13 on ShareGPT: Orca (Max) batches exactly 7 requests and leaves 8.9% of memory free, and vLLM keeps about 96% of memory holding tokens (Simulate the KV cache).
  • Sharing savings. The simulator, with the authors' released benchmark rule (every sample runs to the trace's output length), gives 6.2%, 9.2% and 9.9% for 2, 4 and 6 parallel samples on Alpaca against the paper's 6.09%, 8.53% and 9.79%.
  • Later replication. The mechanism has been reimplemented and adopted across the industry (Hugging Face TGI, NVIDIA TensorRT-LLM, DeepSpeed-FastGen, SGLang; see Then and now), which is the strongest evidence that the memory win is real.
  • Fair statements of weakness. The paper reports its own kernel overhead, names the setup where it gains little (OPT-175B on Alpaca, compute-bound) and says where paging would hurt (§8). That counts in its favour.

What to discount.

  • The strongest baseline is the authors' own code. Orca was not public, so all three Orca variants are reimplementations, and "we assume Orca uses the buddy allocation algorithm" (§6.1). The buddy allocator's power-of-two rounding is a large part of the measured waste (36.6% "external fragmentation and others" for Oracle), so the baseline's waste is partly a modelling choice. FasterTransformer, likewise, ran under a scheduler the authors wrote.
  • Single runs, no error bars. Every curve in Figures 12, 14, 16 and 17 is one run of one synthetic trace per rate (15 minutes for OPT-175B); no seeds or spreads are reported.
  • The multiples depend on how they are read. "Sustains N× higher request rates at similar latency" has no stated latency threshold. Reading the curves from the paper's vector graphics at 0.5 s/token, vLLM over Orca (Oracle) on ShareGPT is 1.75×, 2.33× and 1.47× for 13B, 66B and 175B: the 175B panel falls below the stated "1.7× to 2.7×" at every threshold from 0.2 to 0.9 s/token. The chatbot's "2×" reads as about 1.4× to 1.7× (The curves, rebuilt). The shared-prefix 1.67× and 3.58× and the beam-search 2.3× do reproduce.
  • Alpaca's batch is not purely memory-bound. The simulator's memory-limited vLLM batch on Alpaca is about 177 requests against Figure 13's 132.44, while Orca (Oracle) matches (72.6 against 72.75). At 30 requests/s vLLM is close to its capacity knee (Figure 12d), so its batch is likely set by arrivals, not memory; the 1.8× batch ratio there reflects the offered load, not the memory limit.
  • Paper and released code differ in places. §4.3 says each iteration concatenates prompt-phase and decode-phase tokens; the released scheduler did so in v0.1.0 (June 2023), but from v0.1.3 (2 August 2023) through v0.1.7 (11 September 2023, the day before the arXiv posting) a step with new prompts ran the prompts only. Not stated in the paper: the released defaults capped a step at 2,560 tokens and 256 sequences and kept 1% of blocks free as a watermark (v0.1.7 arguments, block manager).
  • Two sentences do not match their figures: the kernel overhead is "20 to 26%" only at batch size 32 (25% to 44% at batch 8), and the recomputation sentence above.

Verdict: believe the mechanism and the memory numbers; they reproduce from first principles and the whole industry adopted the design. Treat "2 to 4×" as the top of a range measured against a baseline the authors built: the gain over an ideal contiguous allocator is real, about 1.5 to 2.4× on ShareGPT-like traffic, and shrinks toward 1× when memory is not the bottleneck.

What it takes to use this

  • Code and licence: vllm-project/vllm, Apache-2.0, about 93,000 GitHub stars on 3 October 2026; installed with pip install vllm (latest 0.30.0 on PyPI, 22 September 2026, Python 3.10 to 3.14). Everything in the paper is released; the paper-era engine (V0) has since been replaced (see Then and now).
  • Hardware: NVIDIA, AMD and Intel GPUs and x86, ARM and PowerPC CPUs, plus plugins for TPUs, Gaudi, Ascend and others (README). The paper's own results are A100s; a single A100-40GB serves OPT-13B with 12 GB of cache.
  • Settings that matter: block size (16 is still the default), the fraction of GPU memory given to the cache, and the per-step token and sequence limits; paging needs no model changes.
  • When it pays off: many concurrent requests, long or unpredictable outputs, parallel sampling, beam search or shared prefixes, and memory-bound decoding. When it buys little: short sequences on a server with memory to spare (OPT-175B on Alpaca, where the Orca baselines nearly matched it), a single user who needs latency rather than throughput, or workloads with static shapes such as training (§8).

Why it matters (beyond the paper)

This is the paper that made high-throughput LLM serving an open-source commodity, and it did it by importing operating-system ideas from the 1960s (paging, copy-on-write, swapping) rather than new mathematics. The paged KV cache became the standard layout: Hugging Face TGI's PagedAttention "leverages the custom cuda kernels developed by the vLLM Project", TensorRT-LLM enables a paged KV cache (8 to 128 tokens per block) by default, DeepSpeed-FastGen credits vLLM for "blocked KV caching", and SGLang's RadixAttention stores its prefix-cache tensors "in a non-contiguous, paged layout, where the size of each page is equivalent to one token". Continuous batching with a paged cache became the baseline later serving papers measure against: Sarathi-Serve, for one, reports its gains "as compared to vLLM".

Later work refined rather than replaced it. vAttention (2024) keeps the cache contiguous in virtual memory with CUDA's virtual memory APIs and reports up to 1.23× over paged kernels, measuring that paged prefill kernels run up to 37% (FlashAttention-2) and 42% (FlashInfer) slower than their non-paged versions. Sarathi-Serve's chunked prefill and DistServe's disaggregated prefill and decode attacked the prefill-decode interference that step-level scheduling leaves open. Multi-head latent attention (DeepSeek) shrinks the cache from the model side.

vLLM itself became the reference open engine. It added automatic prefix caching, chunked prefill, speculative decoding, quantisation including a quantised KV cache, structured (guided) outputs, disaggregated serving and backends well beyond NVIDIA GPUs (README). The V1 engine (alpha January 2025, default from v0.8.0 in March 2025, the only engine from v0.11.0 in October 2025) rebuilt the scheduler around a per-request token budget that treats prefill and decode alike, made hash-based prefix caching nearly free, isolated the scheduler and executor in an EngineCore process, and delivered up to 1.7× the throughput of V0. vLLM became a PyTorch Foundation-hosted project on 7 May 2025, and llm-d (Red Hat with founding contributors CoreWeave, Google Cloud, IBM Research and NVIDIA) is "powered by a native Kubernetes architecture, vLLM-based distributed inference". It is also a standard rollout engine for reinforcement-learning post-training: verl integrates vLLM and SGLang, TRL documents a vLLM integration and OpenRLHF is built on "Ray + vLLM", so this memory model now sits inside training pipelines too. For anyone reading vLLM's code today, the block manager, scheduler and paged kernels descend directly from §4.2 to §4.5, and this paper is still the right mental model of the core.

Simulate the KV cache

The same eight requests served from the same KV cache memory by the four systems of the paper's evaluation (§6.1): Orca (Max) reserves the maximum length for every request, Orca (Pow2) reserves prompt plus the output rounded up to a power of two, Orca (Oracle) knows each true output length, and all three take contiguous chunks from a buddy allocator. vLLM takes 4-slot blocks on demand. Every step every running request adds one token, as in iteration-level scheduling (§2.3), and a new request is admitted, first come first served, as soon as its memory can be found. Memory is drawn to scale: one square per token slot.

Try: play Orca (Max) first: two requests run at a time and most of each chunk is red: slots reserved for a maximum length the request never reaches. Switch to Orca (Oracle): no red, but the light reserved slots and the grey rounding of the buddy allocator still block other requests. Then vLLM: almost every slot holds a token, up to seven requests run at once, and the eight finish in about half the steps. Watch for a preemption: when blocks run out, vLLM evicts the latest request and recomputes it later (§4.5).

Toy sizes, chosen so the whole memory fits on screen: 64 token slots, a maximum sequence length of 32, vLLM blocks of 4 (the paper's figures use 4 too; vLLM's default is 16). The eight requests (prompt + output tokens) are illustrative: A 7 + 6, B 3 + 9, C 12 + 4, D 5 + 14, E 9 + 3, F 4 + 8, G 10 + 7, H 6 + 5. What the simulator leaves out, so read its batch sizes as memory limits: time (it counts steps, not seconds; prefill, recomputation and the kernel cost nothing), arrivals (the queue is always full, so a system whose real batch is set by the arrival rate, as vLLM's probably is on Alpaca at 30 requests/s, comes out larger here), the pairing of prompt and output lengths in the real traces (drawn independently here), swapping (preemption is by recomputation, the released default for single sequences), and anything Orca's real implementation did that the paper's reimplementation did not. Then and now

What came before the paper, what it changed, and what has become of its design three years on. Each step has its source; dated facts were checked on 3 October 2026.

2022: Orca, iteration-level scheduling

Orca (Yu et al., OSDI 2022) schedules at the granularity of one iteration, so finished requests leave and new ones join every step. It still stores each request's KV cache contiguously, sized for its maximum length. The paper's strongest baseline is a reimplementation of it (§6.1).

June 2023: vLLM released

The announcement reports up to 24× the throughput of Hugging Face Transformers and up to 3.5× that of Hugging Face TGI, "a mere waste of under 4%" of memory, and up to 55% less memory for parallel sampling and beam search, which "can translate into up to 2.2x improvement in throughput". vLLM had served Chatbot Arena and the Vicuna demo for two months. Version 0.1.0 reached PyPI on 20 June 2023 (PyPI).

September to October 2023: the paper

arXiv on 12 September 2023, SOSP in Koblenz on 23 to 26 October. The default block size of 16 was set here (§7.2).

2023 to 2024: everyone pages the KV cache

  • Hugging Face TGI: "TGI's PagedAttention implementation leverages the custom cuda kernels developed by the vLLM Project".
  • NVIDIA TensorRT-LLM: a paged KV cache with 8 to 128 tokens per block, enabled by default.
  • DeepSpeed-FastGen: "blocked KV caching", credited to vLLM.
  • SGLang's RadixAttention (December 2023): a radix tree of cached prefixes over a paged layout with pages of one token, so any shared prefix is reused, not only pre-declared ones.

2024: what paging left open

  • Prefill and decode interference. Sarathi-Serve splits prompts into chunks so decodes never stall ("chunked prefills"; up to 2.6× the serving capacity of vLLM on Mistral-7B); DistServe puts prefill and decode on different GPUs.
  • The cost of paging inside kernels. vAttention measures paged prefill kernels up to 37% (FlashAttention-2) and 42% (FlashInfer) slower than non-paged ones, and keeps the KV cache contiguous in virtual memory with CUDA's virtual memory APIs, up to 1.23× faster than paged kernels.
  • The model side. Multi-head latent attention (DeepSeek) shrinks the cache itself; vLLM now ships FlashMLA kernels for it (README).

2025: vLLM V1

The V1 alpha (January 2025) rebuilt the engine: a scheduler that gives each request a number of tokens per step under a fixed token budget, which makes chunked prefill, prefix caching and speculative decoding the same mechanism; "zero-overhead" hash-based prefix caching with LRU eviction; the scheduler and model executor in an isolated EngineCore process; FlashAttention 3 integrated; up to 1.7× the throughput of V0. V1 became the default in v0.8.0 (18 March 2025) and the only engine in v0.11.0 (2 October 2025). vLLM became a PyTorch Foundation-hosted project on 7 May 2025, and Red Hat launched llm-d for distributed serving on top of it with founding contributors CoreWeave, Google Cloud, IBM Research and NVIDIA.

2026: the paper's swap path is gone

v0.18.0 (20 March 2026) removed the swap_space parameter as part of retiring V0, leaving recomputation as the preemption path of §4.5; v0.19.0 (April 2026) added general CPU KV cache offloading with block-level preemption handling instead. The current release is 0.30.0 (22 September 2026); the default block size is still 16 (cache.py).

What survived and what changed

The paper (2023)Today
Fixed-size KV blocks, block tables, allocation on demand (§4.2)Survived everywhere: vLLM, TGI, TensorRT-LLM, DeepSpeed-FastGen, SGLang. vAttention is the main dissent, keeping virtual contiguity.
Block size 16 (§7.2)Still vLLM's default; TensorRT-LLM supports 8 to 128; SGLang pages one token at a time.
Reference counts and copy-on-write for parallel sampling and beam search (§4.4)Survived; prefix sharing grew from provider-reserved prefixes into automatic, hash-based (vLLM) or radix-tree (SGLang) prefix caching across requests.
Iteration-level scheduling with prompt and decode tokens in one step (§4.3)Generalised: V1's per-request token budget, with chunked prefill splitting long prompts.
Preemption by swapping or recomputation (§4.5)Recomputation remains; swap space was removed in v0.18.0; CPU offloading returned as a separate KV cache tier.
Centralised KV manager over Megatron-style tensor parallelism (§4.6)Extended to pipeline, data, expert and context parallelism and to disaggregated prefill and decode (README).
A fused paged attention kernel adapted from FasterTransformer (§5.1)Replaced by FlashAttention, FlashInfer, TRTLLM-GEN, FlashMLA and Triton backends that read paged caches (README).
