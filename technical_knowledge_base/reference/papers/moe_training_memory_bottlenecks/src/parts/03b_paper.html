Expert dispatch: PipelinedLLEP

[[S3.SS1|§3.1, Figures 1 and 2, Appendix B]]

Under expert parallelism a token routed to an expert travels to the GPU (rank) that owns it, its destination d; the routes Rd arriving there size its dispatch buffers and grow with batch size, top-k and routing imbalance ({{§3.1|ax:S3.SS1}}). The authors' earlier LLEP (Least-Loaded Expert Parallelism, {{arXiv 2601.17111|https://arxiv.org/abs/2601.17111}}) removes the third: it moves a popular expert's overflow, and that expert's weights, onto ranks that would otherwise sit idle, without changing any token's expert choice. But LLEP still materialises the rank's whole routed batch in one all-to-all tensor.

PipelinedLLEP cuts the batch into chunks with a per-source token budget c: each sending rank puts at most c of its own tokens into any one chunk ({{Eq. 1|ax:S3.E1}}):

K = min(⌈N/c⌉, Kmax),   ceff = ⌈N/K⌉,   Rd(i) ≤ Ep k ceff

Each of the Ep senders puts at most ceff tokens in chunk i, each token makes k routes, so no destination can receive more than Epkceff routes in a chunk, whatever the router does, and no token is dropped to make it hold. The buffers then take at most 2EpkcHb bytes; past N = cKmax the chunk count stops at Kmax and each buffer is capped at 1/Kmax of the batch. Either way the limit is known before launch, and deriving K from c absorbs micro-batches of varying length without running out of memory.

Why overlap alone is not enough. The chunks run through a dispatch, expert-matmul, combine pipeline, as in FasterMoE or Tutel, which pick the chunk count for speed; this paper picks it to cap memory ({{§3.1|ax:S3.SS1}}). And a loop that calls the expert layer per chunk keeps every chunk's autograd graph alive until backward, so the peak would not fall in training. So each chunk's expert matmul is wrapped in a reentrant checkpoint nested inside the decoder layer's non-reentrant one, which lets the outer checkpoint drop the inner tensors ({{B.1|ax:A2.SS1}}). The price: the expert matmul runs three times per update instead of twice; route payload is unchanged.

Exactness. Only the expert-weight gradient changes summation order (it is the one sum split across chunks); at K = 1 it is bitwise identical to LLEP's ({{Eq. 7|ax:A2.SS1}}).

LLEP decides which rank serves a route from the token's position in the expert's global token list. Cut a rank's 65,536 tokens into 10 chunks of consecutive positions, or into 10 strided chunks (positions i, i+10, i+20, ...). Same tokens, same destinations. What changes?

The spread within a chunk. Consecutive positions share a destination under LLEP's plan, so a chunk that covers the relocated tail of a popular expert sends almost everything to one helper rank, and the imbalance LLEP removed comes back chunk by chunk ({{Figure 1c|ax:S3.F1}}). Strided chunks spread each chunk over the destinations. The paper measures the largest send to one destination over the mean send in a chunk ({{Table 8|ax:A2.T8}}); the bars below put its numbers beside our replay, which runs the paper's own synthetic routing profiles ({{B.2|ax:A2.SS2}}) through LLEP's released assignment plan in your browser:

The replay ports compute_llep_lpt_plan from {{LLEP's code|https://github.com/SalesforceAIResearch/LeastLoadedEP}} (65,536 tokens per rank, 128 experts, top-8, 8 ranks, K = 10). With the code's default capacity factor of 1.1 it does not match; with 1.0 (every rank capped at exactly the mean load) all eight send ratios match to the printed precision, so the paper evidently ran at 1.0. Strided chunks run 1.03 to 1.35 times faster with up to 1.37 GiB less peak memory ({{Table 8|ax:A2.T8}}). Step through it chunk by chunk in {{Run the four schedules|tab:t-run:dsx}}.

Results (one node of eight H200s, identical input for every system, {{Figure 2|ax:S3.F2}}, {{Table 6|ax:A2.T6}}). At 65,536 tokens per rank, H = 7,168, 128 experts, top-8 and K = 10, PipelinedLLEP's peak is 56.9 to 59.3% below LLEP's (about 53 GiB down to 21.4 to 22.9) at 1.01 to 1.10 times its forward speed, unchanged with backward included ({{Table 9|ax:A2.T9}}); standard expert parallelism runs out of memory on every skewed profile (95/16 sends 95% of tokens to the 16 hottest experts). On a smaller shape (32,768 tokens, top-4, K = 3) the saving is 24.6 to 26.9%. Standard EP is fastest only when there is no skew to correct.

Choosing c. Peak falls with the chunk count at a decaying rate and latency does not follow it, so c is picked from a measured curve ({{Figure 8|ax:A2.F8}}); deriving K from the budget matters for short micro-batches, where a fixed K = 10 runs at under half LLEP's speed ({{Table 7|ax:A2.T7}}). Details, and the bimodal latency behind "fastest of three", are in {{the tables tab|tab:t-tables:tbK}}.

Vocabulary projection: Ring-DTP

[[S3.SS2|§3.2, Figure 3, Appendix C]]
To compute one token's exact cross-entropy over a 200,000-word vocabulary, visiting the vocabulary one block at a time, how many numbers per token must you carry between blocks?

Three: the running maximum m, the running sum of exponentials z, and the target's logit yt once its block passes. Each new block rescales the old sum to the new maximum ({{Eq. 3|ax:S3.E3}}), and at the end the loss is m + log z − yt. This is the online softmax that {{FlashAttention|n:3c65c17b0d0d81e4a3e8e7a2c4771381}} also uses. One token, 24 random logits, folded block by block:

Fused cross-entropy kernels (Cut Cross-Entropy, Liger) already do this on one device; here both the batch and the projection weight are sharded across ranks ({{§3.2|ax:S3.SS2}}). Rank r holds its own batch Xr (N × H) and owns the vocabulary slice Wr of V/P columns. {{Megatron's|n:3c65c17b0d0d8133ae92fbe90a1f308e}} vocabulary-parallel loss uses the same weight split but needs every rank to hold the same batch, which shrinks the effective batch and hurts long context. Ring-DTP (ring data-tensor-parallel) keeps a data-parallel layout, distinct batches per rank, and runs P ring rounds in which every batch meets every shard exactly once. Each meeting forms only the strip Yj,r = XjWr (N × V/P), folds it into the per-token state Sj = (mj, zj, ytj), and frees it, so logit memory is O(NVb/P) ({{Eq. 2|ax:S3.E2}}). Exactly one shard contains each target, so exactly one meeting supplies yt. Backward replays the same rounds from the saved normaliser and forms the softmax residual one strip at a time, so neither pass stores a full logit or logit-gradient tensor ({{Appendix C|ax:A3}}).

Which tensor travels. Either the activations or the weight shard can move. A hop costs O(NH) bytes if activations move and O(HV/P) if weights move, so Ring-DTP moves weights exactly when N > V/P. Moving weights keeps each batch and its state at home, so forward needs no return hop ({{Figure 9|ax:A3.F9}}). The cost is P − 1 sequential hops per pass, so the paper takes the smallest P whose strip fits.

Results ({{Table 2|ax:S3.T2}}, P = 8, H = 7,168, V = 200,000, FP32, forward plus backward, one measured pass each): at N = 16,384 per GPU (activations move) the peak falls from 42.462 to 7.322 GiB, 82.8%, for 5.1% more time; at N = 32,768 (weights move) from 79.521 to 10.622 GiB, 86.6%, for 4.4%. Doubling N nearly doubles the standard peak but moves Ring-DTP's only from 7.3 to 10.6 GiB, so the saving widens with context, which is what keeps the vocabulary head on the device at 1M tokens. The standard reference's extra memory is exactly three N × V FP32 tensors (logits, log-softmax and their gradient: 3 × 12.207 = 36.621 GiB against the measured 36.6212, {{Table 10|ax:A3.T10}}), and the shards are exactly 1/4 and 1/8 of the 5.3406 GiB weight; see {{the checks|tab:t-tables:tbChk}}.
