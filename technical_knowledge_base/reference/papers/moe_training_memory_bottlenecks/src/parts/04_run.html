1. Expert dispatch: LLEP against PipelinedLLEP

One MoE layer at the paper's 65K shape ({{Table 5|ax:A1.T5}}): 8 ranks, each with 65,536 tokens, 128 experts, top-8, routed by one of the paper's synthetic profiles ({{B.2|ax:A2.SS2}}) and assigned by LLEP's released plan (capacity factor 1.0, the setting that reproduces Table 8). Each bar is the number of routes one destination rank receives at that moment, summed over the 8 senders; the dashed line is Eq. 1's guarantee for a chunk. The grid is the send matrix of the current chunk: sender rows, destination columns, darker means more.

Try: profile 50/4 with contiguous chunks, then strided: the same routes in total, but contiguous chunks pile onto a few destinations (send ratio 6.00) while strided ones spread evenly (2.29), the numbers in {{Table 8|ax:A2.T8}}. Then LLEP's whole batch, to scale: ten times taller.

2. Vocabulary projection: dense logits against the Ring-DTP ring

Four ranks (P = 4), each with its own batch of 2 tokens (Xj, hidden width 3) and one quarter of a 12-word vocabulary (Wr, 3 columns). The numbers are real: random weights and activations, a fixed seed. Each box is one rank; the grid inside is the logit strip it forms this round; the three columns on the right are each token's running state (m, z, yt), the target's logit filled in when its shard passes.

Try: step through "move weights" and watch the weight shards hop while the batches stay; then "move activations", where batches and their states travel and need one hop home. Either way every token's loss ends equal to the dense log-softmax, while only one strip per rank ever exists.

3. Checkpoint boundaries: checkpointing against SCO

gpt-oss-20b as in {{Table 3|ax:S3.T3}}: 47 checkpoint boundaries of 0.3735 GiB each per GPU (557,056 tokens / 8 ranks × hidden 2,880 × 2 bytes). The top row is device memory, the bottom pinned host memory; forward fills them left to right, backward empties them right to left, restoring one boundary ahead.

Try: compare "off" with "8 GiB": 21 boundaries go to the host and come back two at a time. The counters show boundary memory only; the measured peak, which includes everything else, is beside them.

4. Optimizer step: CPU Adam against OffloadStreamAdamW

One optimizer step on one GPU's share of gpt-oss-20b (about 2.6B parameters, 26 buckets of up to 142M, {{Table 14|ax:A5.T14}}), on one time axis. CPU Adam updates everything on the host in one serial pass (3.95 s measured). The stream copies each bucket's fp32 master weights, moments and gradient to the GPU (16 bytes per parameter), updates it there, and writes 12 bytes per parameter back, with s staging slots limiting how many buckets are in flight.

Try: one slot, then two: with one slot each bucket waits for the previous write-back and the step is nearly serial; two slots overlap upload, update and write-back and approach the transfer floor; a third buys almost nothing, as Table 14 measured (1.930 against 1.951 s).

Illustrative timing. Bucket times are not printed. Upload and write-back times are set in proportion to bytes (16 : 12), the update to a quarter of the upload, and scaled so that two slots take the measured 1.93 s under Eq. 5; one and three slots then follow from the same times. The CPU bar is the measured 3.95 s.
