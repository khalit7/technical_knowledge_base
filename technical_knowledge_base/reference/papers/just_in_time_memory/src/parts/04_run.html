Replay the memory stream

The paper's argument about credit assignment is about traffic: which stored trajectory gets retrieved by which later task, and when. That part of the system has no LLM in it, so it can be run exactly. This tab replays the paper's test protocol on the real 140 ALFWorld test goals (the "valid_seen" split, six task types): the bank starts empty, tasks arrive in a random order in batches of 10 that share the bank, BM25 over task descriptions returns the top 3 stored trajectories, and a task's trajectory is stored after its batch if it succeeds ({{§3|ax:S3}}, {{Appendix A|ax:A1}}). What is not modelled: whether a task succeeds is a coin with probability p, the judge is assumed to agree with the verifier, and BM25's parameters (k1 = 1.5, b = 0.75) are the common defaults, since the paper does not give them.

Try: step through the batches and watch which trajectories feed which tasks. Switch to write time to see when a write-time curator would get its reward for each storage decision: only when a later task first uses it. Then move the slider to inspect single tasks: early tasks retrieve the few trajectories that exist, whatever their type.

Rows are batches of 10, in arrival order; colour is the task type.

What this shows, and what it cannot

It measures the memory traffic of the paper's own protocol on the paper's own test set: a stored trajectory is first used about 20 tasks later, a fifth to a quarter are never used, and a used one feeds about five later tasks of about two different types. That is the delayed, many-consumer reward a write-time curator has to learn from, and the many-lessons problem a single artifact faces; it is real, not illustrative. It does not show that read-time curation is better: success here is a coin, so nothing about payload quality is simulated. The JavaScript replay was checked against an independent Python implementation (src/stream_sim.py): identical orderings, retrievals and statistics on 5 settings.
