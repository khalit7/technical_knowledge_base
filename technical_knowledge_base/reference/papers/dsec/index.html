Problem

§1 Introduction

Agentic reinforcement learning trains a model by letting it act in a real environment: it reads a repository, calls tools, runs commands, inspects failures, edits files, and is rewarded from native execution signals such as exit codes, test pass rates or a task's own verifier (§1). Each rollout and each evaluation task therefore needs an isolated, task-specific machine with its repository, dependencies, services, evaluation scripts and coding harness, close enough to a real computer to run unmodified package managers, build tools, browsers and emulators. Rollout and evaluation put the most pressure on that layer, because they are large, concurrent and tied to the training loop; asynchronous rollouts (as in DeepSeek's own pipeline) keep many stateful sessions in flight and may interrupt and resume them across policy updates or preemptions (§1).

The paper lists seven properties of this workload, and the whole design follows from them (§1):

PropertyWhat it means in productionWhat it forces
1. Burstyone job can ask for up to 32K sandboxes at oncehorizontal scaling, no central bottleneck in scheduling or image distribution
2. Densea sandbox mostly waits for the model's next action, so CPU use is sparse; one node hosts up to 800 microVMs or 3,200 containerssafe overcommit
3. Stateful and long-livedfiles, installed packages and started services persist across many turns; memory and page cache stay pinned after the CPU goes idlememory sharing and reclamation
4. Heterogeneousjudge-style scripts, whole repositories, security tasks, computer use, Android, full systemsmore than one kind of sandbox
5. Diverse imageseach task may need its own repository, versions, services or VM snapshot, with little reuse; eager pulling stretched completion 1.7× in their ablation, on-demand loading cut disk writes 57%scalable, on-demand image distribution
6. Untrustworthyagents corrupt filesystems, exhaust resources, interfere with system componentsfine-grained access control and misbehaviour analysis
7. InterruptibleGPU training jobs are preempted while long rollouts are in progressstate preservation and efficient recovery

The question: what does a sandbox platform need to be, so that a frontier lab can create millions of stateful, untrusted, heterogeneous environments a day at the rate a GPU cluster consumes them, and keep them alive through preemptions?

Idea: one SDK, four backends, the caller chooses

§2 Overview, Table 1

DSec's answer is an elastic platform rather than a single sandbox runtime. Callers (the training framework, evaluation frameworks and data-construction pipelines) reach it through libdsec, a Python client: a request names the sandbox type, the image or environment, CPU and memory limits, lifetime, network rules and initial user; the caller then runs shell commands or tool calls and reads outputs and exit status (§2.1). The paper's minimal session asks for a container with 4 GB, 4 cores, a 300-second idle timeout and network rules that allow PyPI but deny npm, runs echo hello world and stops it (§2.1).

client = DSecClient(); await client.open() args = DSecContainerRunArgs(container_image="registry.../sphinx-9658:official", memory_limit_mb=4096, cpu_cores_limit=4, ttl_running_stop=300, # idle timeout network_rules={"npm": False, "pypi": True}, init_user="root") sandbox = await client.run_container(args, timeout=120) result = await sandbox.run_shell("echo hello world"); await sandbox.stop()
The paper's minimal libdsec session, condensed from its listing in §2.1.

The SDK is deliberately not a full abstraction over its backends. Stronger isolation and fuller system functionality cost startup latency and resources, and no single sandbox fits every agentic task, so DSec offers four points on that trade-off and the caller stays responsible for picking the one that matches the task (§2.1, §2.2):

  • FnCall runs short, stateless work (judge-style programs, compilation, serverless code, GPU kernels) in reusable, precreated CPU or GPU containers, so there is no per-call provisioning; GPUs are shared for light work or reserved exclusively for performance-sensitive operator evaluation (§2.2).
  • Containers are the main backend for software engineering and general tool use: fast start, dense packing, the Linux stacks most repository tasks use, but they share the host kernel (§2.2).

In production, containers and microVMs dominate both instance count and resource use; FnCall serves many light invocations with a few resident environments; full VMs cover specialised but important classes (§2.2). Whatever the backend, the user sees one lifecycle: create (backend, environment artefact, limits, lifetime, network policy), let the platform prepare it, interact (commands, tool calls, tests), then stop it or let its time-to-live reclaim it. The artefact is a base image plus task workspace and toolkit layers for containers and microVMs, a prepared image or snapshot for full VMs, and a task specification for FnCall (§2.3).

The scale of one production unit: nearly 160 CPU nodes with 30K cores and about 250 TB of DRAM, petabytes of layers and images, about 3 M sandboxes on a typical day, peak concurrency about 380K and creation above 5,000 a second; several such units share one 3FS deployment for base images and workspaces (§2.4).

Architecture: the path of one request

§3 Platform Architecture, Figure 1

A creation request passes cluster-level services first, then the per-node runtime. Placement uses power-of-k choices with each engine's own recent placements overlaid on a periodic fleet snapshot, and the node's edge keeps the final say (§3.1, §3.2, §7, Figure 1). Step through it below; the second mode shows FnCall's separate path.

Components and order from §3; illustrative timing.

Each component in detail (§3.2 to §3.4, §7)
  • IAM authenticates every management request. Projects scope resources and access; unlike the flat or two-level hierarchies of cloud platforms, projects nest to any depth, and an authorised principal, an agent or harness included, can create a subproject, delegate part of its quota and grant permissions it holds, never more than its parent's. Humans and agents use the same management API (§3.2).
  • The apiserver is the only path between the trusted GPU servers (where training code calls libdsec) and the network-isolated sandboxes, which run untrusted code and may reach external networks. Creation, commands and streaming I/O all pass through it. It keeps no per-sandbox state: each sandbox ID encodes its owning edge, so any instance can forward any request and the tier scales horizontally (§3.2).
  • The placement engine filters to healthy nodes with the right backend and hardware (a GPU sandbox only to GPU nodes), then samples a few eligible nodes at random and takes the least loaded: the power-of-k-choices algorithm. Each instance overlays its own recent placements on the last snapshot, so in-flight load counts without coordination between instances. The watcher probes edges and hosts and counts running sandboxes per backend, edge, user and task. Neither needs durable state, so instances are easy to add or replace (§3.2, §7). The Place a burst tab runs this algorithm.
  • The edge, one per node, keeps final admission authority: it checks local capacity and rejects if short (the placement engine then picks another node), provisions storage, applies the eBPF network policy and launches the runtime; it also coordinates disk and memory snapshots and frees resources at stop or time-to-live. FnCall and containers run inside QEMU/libvirt VMs rather than on the host, an extra kernel and network boundary; full VMs use para-virtualised GPUs (virtio-gpu) and translation layers such as DXVK for graphics (§3.3).
  • aether is a per-sandbox proxy talking to the edge over a Unix socket (containers) or vsock (VMs); the edge marks the sandbox failed if that channel closes. chronus instances are shell sessions inside the sandbox (commands, filesystem, HTTP, streaming I/O), one per terminal session (§3.3).
  • Storage: container images are converted offline from OCI to EROFS with metadata kept local and data in 3FS; microVM disks use OverlayBD over the same store; both load on demand and snapshot incrementally over a shared base (§3.3).
  • Cloud bursting: above 80% on-premise utilisation, the placement engine offloads eligible container requests to cloud VMs running the same container runtime and EROFS path from a cloud filesystem. A de-duplicated 30 TB image set covers the files accessed by 70% of container tasks; tasks entirely inside it are cloud-eligible. In one scale unit 200 cloud VMs absorb about 30% of peak overflow (§3.4).

Reliability is engineered rather than measured: auxiliary services (API gateways, package mirrors) and the control-plane ingress sit behind a BGP-announced virtual IP with ECMP routing, so a dead instance loses its route within seconds; placement, watcher and IAM run as several independent instances, and regular cluster resets check that the Infrastructure-as-Code configuration can rebuild every cluster-level service from scratch (§7).

The workload, measured

§4 Production Workloads, Figures 2 to 8, Tables 2 and 3

Section 4 characterises one week of production in early 2026, for containers and microVMs only (together most instances and resources) (§4). Every number below is printed in the paper; the curves are rebuilt from the figures' vector data in the figures tab.

  • Bursts. A typical container task creates thousands of sandboxes (median 2,528, p90 7,969, p99 16,388; microVM tasks 352, 1,835 and 4,044), the largest jobs up to 32K, all within a short window because a batch cannot use an instance until its environment is ready; setup cost is multiplied by burst size and stragglers in any stage delay useful work (§4.1, Figure 2).
  • Three phases. Setup prepares dependencies and tools; the tool-call phase alternates model generation with short CPU bursts; a test phase verifies the result and briefly raises demand again. CPU is intermittent after setup while memory and accumulated state persist (§4.1, Figure 3).
  • Sparse CPU. About 90% of container and microVM sandboxes use no more than 5% of their requested CPU on average (Figure 5). One node peaked at 1,048 containers and 524 microVMs in a day's sample (Figure 6); across production DSec has run stably at 3,200 containers or 800 microVMs per node, "demonstrated operating points rather than hard limits" (§4.3).
  • Long lives. Median lifetimes are 17.4 minutes (containers) and 15.5 (microVMs); p99 exceeds three hours for both (231.5 and 213.9 minutes are printed on the figure) (Figure 7).
  • Many images, little reuse. In one week the container backend served 11,266 base images and 102,171 workspaces, the microVM backend 2 base images and 53,590 workspaces (plus 4,889 snapshots), with 103 toolkits; 67.8% of sandboxes needed at least one workspace or toolkit on top of the base. That is 82.8 TB plus 50.9 TB, more than 130 TB, far beyond one node (§4.2, Table 2). Per task, a container image is used by a median of 3 sandboxes (p90 28), a microVM image by 1 (p90 3), so node-local caches barely help (Figure 8).

Three pressures follow, and section 5 answers each: setup that must not scale with per-sandbox extraction; density that is valuable but unsafe without care for memory and latency; and a huge, low-reuse image corpus that makes eager distribution expensive (§5, Figure 9).

Mechanisms

§5 Core System Mechanisms

1. Composable environment layers

A sandbox is three parts with separate lives: a base image (OS-level dependencies such as Ubuntu, Python 3.10 or Java 8), a workspace (the task's repository and its dependencies) and frequently updated toolkits (such as the DeepSeek Harness) (§4.2). Fused into one OCI image, they multiply: with M bases, N workspaces and K toolkits, upgrading m bases costs O(m·N) rebuilds and upgrading k toolkits O(k·N). Unpacking workspace and toolkit archives inside each sandbox instead costs CPU and I/O across a burst and causes startup timeouts; bind-mounting read-only directories replaces paths rather than merging into them, and breaks tools that write into their own tree (Python's __pycache__) (§4.2).

DSec stacks them as overlayfs layers at creation time: base at the bottom, the workspace as a read-only layer above, each toolkit on top, and a writable upper directory that absorbs runtime writes. A 30-line Go change to dockerd inserts the pre-mounted EROFS layers into the lower-directory stack. Upgrading m bases now rebuilds m layers, and k toolkits k layers (§5.1, §7). The layers are immutable, so they are stored in EROFS, a compact read-only filesystem that can decompress only the blocks a read touches, unlike a tar.gz that must be streamed and unpacked whole (§5.1). MicroVMs get the same model: EROFS images as read-only block devices, overlayfs inside the guest with an ext4 upper layer (§5.1).

2. On-demand image loading from 3FS

Sandboxes read only a small part of their images: 4.2% to 13.3% of the data in sampled container images (Table 3). Pre-warming only moves the cost earlier, and under overcommit, pulling and unpacking full images steals CPU and I/O from running sandboxes (§4.4). So on-demand loading shrinks total I/O in proportion to what is used, not just its timing (§5.3).

Rather than a registry plus peer-to-peer delivery, DSec serves images from 3FS, the distributed filesystem its training already uses. 3FS is fast for large sequential I/O and poor at small random I/O, which sets three rules: writes stay local (the writable layer on the node's disk), reads are on demand and in bulk, and metadata is kept local where the format allows (§5.3). For containers, EROFS's multi-device mode separates metadata from data: the metadata is downloaded to local disk, file data stays in 3FS and is read through the page cache with kernel readahead, close to Nydus's design but without a registry or FUSE backend. Consecutive layers under a size threshold (for example 3 GB) are collapsed offline into one metadata and one data image, keeping overlayfs whiteouts, and file-backed mounts skip the loop device (§5.3).

MicroVMs need a different path: Docker's overlay2 cannot sit on an overlayfs data directory, and Firecracker does not support virtio-fs. Read-only layers still use EROFS, while writable ext4 disks (including one mounted at Docker's data root for Docker-in-microVM) are OverlayBD images exposed through ublk; because ext4 metadata lives inside the block image, the ublk path fetches 256 KiB chunks and keeps them in a second-level local cache, so a chunk evicted from the page cache is not fetched from 3FS again (§5.3). This Rust OverlayBD and ublk code is the part the authors released (§7). Each 3FS storage server has 20 × 15 TB SSDs and 2 × 400 Gbps RDMA NICs; tens of them serve a cluster of hundreds of thousands of CPU cores through 3FS's FUSE client (§7).

3. Memory: share the page cache, return free pages

MicroVMs waste memory twice: image data read through a virtual block device is cached by the host and again by every guest, and a guest does not return free pages to the host unless told to; requested memory usually exceeds demand, so guests feel little pressure to reclaim, and long lifetimes make retained memory expensive (§4.3). DSec uses two complementary fixes (§5.2):

  • virtio-pmem with DAX maps file reads straight onto host pages, so co-located microVMs share one host page-cache copy. Its costs: a cold access may need synchronous fault handling (the buffered virtio-blk path gets guest readahead and batched I/O instead), and the guest must hold struct page metadata for the whole device, 64 bytes per 4 KiB page, so 1/64 of capacity: a 128 GB pmem device needs 2 GB of guest RAM.
  • DAMON plus balloon free-page reporting. The virtio-balloon driver reports free guest pages to the host, which drops them with madvise(MADV_DONTNEED), but by default only in order-9 blocks (2 MiB of 4 KiB pages). DAMON samples page-access bits, evicts file pages left untouched beyond an age threshold, and so frees scattered pages that coalesce into blocks large enough to report.

In production DSec enables pmem with DAX for the read-only EROFS base and toolkit layers and DAMON with free-page reporting for larger writable disks; all of it is Firecracker device configuration, guest kernel parameters and sysfs tuning, with no kernel modifications (§5.2, §7).

4. CPU: keep best-effort work off a latency-sensitive core

Some tasks have strict per-step budgets, such as a game-playing agent with a fixed time per move. Lowering best-effort (BE) priority is not enough, because a latency-sensitive (LS) thread and a BE thread on sibling hyperthreads still share the core's execution resources (§4.3). DSec puts BE sandboxes under SCHED_IDLE, so they yield whenever LS work is runnable, and turns on Linux core scheduling (prctl(PR_SCHED_CORE)) for LS sandboxes so unrelated BE work never runs on the sibling thread of the same physical core (§5.2, §7).

A latency-sensitive chess agent shares nodes with best-effort load at 50% of capacity, and its per-step time rises 45%. Putting the best-effort work at SCHED_IDLE priority alone removes how much of that rise?

Other implementation details

GPU FnCall for operator benchmarking uses NVIDIA Multi-Instance GPU partitions for isolated concurrent benchmarks, compiles on CPU FnCall first so GPUs are not held during compilation, and keeps a warm pool of Python processes with libraries already imported; a shared-GPU mode raises concurrency for work that is not performance-sensitive (§7).

Co-design with the RL framework

§6 Co-design with the RL framework

DSec has served every sandbox workload of DeepSeek's RL training and evaluation from DeepSeek-V3.2 to V4.1 (§6). Three pieces of co-design go beyond running sandboxes efficiently.

Environments built by agents. Hand-building the environments agentic RL needs is impractical, so agents build them interactively on the same infrastructure. pack_diff checkpoints a live sandbox as an incremental disk snapshot that can be restored as a new sandbox, turning a session into a reusable environment with no separate image pipeline. Builders follow internal packing rules (given to them as instructions) that limit runtime impact; an internal platform quality-checks agent-built environments and exports them in standard formats. Builders and runtime agents use separate accounts, and build-time residue is wiped from the writable layer before packing, so reference answers do not leak into the image (§6.1).

The rollout lives outside the GPU job. GPU training jobs are routinely preempted to raise utilisation. In earlier pipelines the agent loop ran inside the preemptible GPU pod with model serving and the RL framework; a preemption killed the loop while its sandbox survived, and recovery replayed a command log to reconcile the two, reusing recorded results for completed operations so non-idempotent commands did not run twice. From DeepSeek-V4.1, rollout execution moved onto DSec as two parts outside the preemptible pool: an agent sandbox that hosts the scaffold (for example DeepSeek Harness) and its tools, and a worker container that manages the sandbox as a scaffold-agnostic control layer. Together they hold the complete rollout state, so a preempted GPU job reconnects and continues without replay (§6.2).

Pause instead of hold. Keeping state until the rollout finishes would leave many idle sandboxes holding memory while training is suspended, so the RL framework sends pause requests to all sandboxes of a preempted job. A container is frozen with docker pause, given swap through memory.swap.max and reclaimed with memory.reclaim (anonymous and file pages); resume prefetches with MADV_WILLNEED, then unpauses. A microVM is snapshotted (memory and execution state) and its Firecracker process killed; resume starts a new process from the snapshot. Any request to a paused sandbox resumes it transparently first (§6.3).

The authors draw two limits themselves: final-output checks alone cannot establish whether an agent solved the task as intended, and the access controls "address only part of the problem and do not provide a general defense against destructive behavior such as triggering kernel bugs"; they rely on observability and keep hardening DSec as models change (§6.4, §6.5). The paper frames these controls as a mitigation of reward hacking (Amodei et al., Skalse et al.): a shortcut the sandbox blocks never reaches the reward function. It does not claim an inescapable sandbox, and the XFS episode shows an agent working around a control after it was introduced.

Results

§8 Evaluation, Figures 10 to 13

The evaluation runs on a dedicated 10-node CPU test cluster, separate from production. MicroVM nodes are bare metal (2 × 96-core AMD EPYC 9655 with SMT, 1.5 TB DRAM, 3.4 TB local disk) so there is no nested virtualisation; container experiments run inside a QEMU VM (1 × 96 cores, 192 hardware threads, 512 GB, 5.8 TB). Hosts run Linux 7.0, microVM guests Linux 6.1. Workloads come from real RL training and evaluation: internal software-engineering suites, SWE-bench, Terminal-Bench, security exploit tasks (§8.1). Only the four §5 mechanisms are evaluated (§8).

The leftover inflation comes from lower turbo frequency under multicore load and from memory-bandwidth and last-level-cache contention that core scheduling does not address; the authors judge it tolerable and do not isolate memory bandwidth.

Why it matters (beyond the paper)

Every agentic RL recipe in this knowledge base assumes an environment supply that executes untrusted code at rollout rates a GPU cluster can consume, and none of them prices it. DSec is one of the first detailed public accounts of that layer at frontier scale (the paper's related work notes that MiMo-V2-Flash and ComputerRL mention their execution environments but focus on the model; §9). A comparable open-source platform, AgentENV, says in its README that it powers agentic RL training for Kimi K3 and has scaled to 1.5 million images in production; DSec's released storage code lives in that repository.

Two things to take from it, as the old version of this page put them. The ratio of 5,000 creations a second to about 160 nodes is what makes agentic RL affordable at this scale, and it is an infrastructure result rather than an algorithmic one: a lab without it is not running the same experiments, whatever recipe it copies. And the four-backend design is the transferable idea for anyone building smaller: isolation is a per-task cost, not a platform decision. Both are interpretations, not findings of the paper; the first is also hard to check, since the scale figures come without a measurement method (see below).

How much of this to believe

What holds up. The workload study and the mechanism results are internally consistent to a degree few systems papers are checked for: every figure ships as vector graphics, and decoding them on their own tick marks reproduces the text's numbers, 45.2% and 17.3% exactly, 40.2% and 21.2% within 0.1 point, 57% and 5.5× within rounding (checks). The mechanisms are standard, documented Linux features (EROFS, overlayfs, virtio-pmem, DAMON, free-page reporting, SCHED_IDLE, core scheduling, AppArmor, eBPF) combined with reported configuration and no kernel changes, so the directions are plausible on prior knowledge too. The QoS result is clear: core scheduling's error bars sit clear of the baseline's at every load from 10% to 50%. The pre-cached baseline in Figure 10 is a strong one, and EROFS matches it.

What is weaker.

  • The headline scale is self-reported. About 3 M a day, about 380K peak concurrency and over 5,000 creations a second come with no trace, no measurement window and no figure (§2.4). A sanity check with Little's law and Figure 7's lifetimes gives an average concurrency near 72K, so the 380K peak implies peaks about five times the daily average: plausible for bursty RL, not verifiable. The abstract's "over 380,000" and §2.4's "~380K" also differ in direction.
  • The paper's most original part is not evaluated. The RL co-design (rollouts surviving preemption, pause and resume, agent-built environments) is excluded from the evaluation by design (§8): there is no preemption rate, recovery time, memory reclaimed, or count of rollouts saved. The same holds for cloud bursting ("about 30% of peak overflow", with "overflow" not defined) and the misbehaviour catalogue (anecdotes with no rates; the authors say so).
  • Test cluster, single runs. All four experiments run once on a 10-node test cluster, not production; Figure 13 has error bars and Figure 11 shaded bands, but neither is defined (spread across nodes? runs?), and no experiment states repetitions (§8.1).
  • Baselines are the obvious ones, not the best ones. On-demand loading is compared with eager registry pulls and a local cache, not with the lazy-loading systems the paper itself cites (Nydus, DADI/OverlayBD, FaaSNet, CoFS); EROFS layers are compared with tar extraction, not with other layer schemes (§9). The claims are "better than eager", not "better than the state of the art".
  • Small text-figure mismatches. The 1.71× is 60 / 35 from rounded readings; the curves end at 34.2 and 57.0 minutes (1.67×), and cold pulling ends before the plot's 60-minute edge rather than "over 60". The tar run's EROFS side ends near 47 minutes on the figure against 45 in the text. pmem's CPU rise reads 27.4% to 39.4% on the curve against 26.5% to 41.4% in the text, and only for the second burst; in the first the baseline already reaches 33.5%. None changes a conclusion.
  • Fairly stated limits count in its favour: libdsec is not a full abstraction, the access controls are partial, pmem costs CPU, and residual interference is left unaddressed on purpose.

Verdict: believe the design and the workload characterisation, and the four mechanisms' directions and rough sizes. Treat the production scale as the authors' own report and the RL co-design, the paper's most original part, as a described architecture rather than a measured result.

What it takes to use this

  • Code: DSec, libdsec and the RL integration are not released. What is released is the storage path, a Rust port of OverlayBD (to which the authors contributed) plus their Rust ublk library, published inside kvcache-ai/AgentENV (MIT licence) with backends for 3FS, object storage such as OSS and container registries (§7). Some write-ups described DSec as open-sourced (for example); it is not.
  • What you can rebuild from public parts: EROFS images with overlayfs composition (a 30-line dockerd patch in the paper's case), Firecracker microVMs with virtio-pmem DAX for read-only layers and DAMON plus balloon free-page reporting for writable ones, SCHED_IDLE plus core scheduling for best-effort neighbours, AppArmor and eBPF for access control, and power-of-k placement with edge-side admission. All of it is configuration of stock Linux, per the paper (§7). AgentENV and E2B are open platforms to start from.
  • Hardware at DSec's scale: about 160 CPU nodes, 30K cores and 250 TB of DRAM per unit, plus a 3FS deployment of tens of storage servers (each 20 × 15 TB SSDs, 2 × 400 Gbps RDMA) for hundreds of thousands of cores (§2.4, §7). The mechanisms do not need that scale; the measured gains came from a 10-node cluster.
  • When it pays off: bursty creation of many sandboxes from a large, low-reuse image set, mostly idle CPU, and long-lived state: exactly the workload of §4. With few, reused images, a local cache already does as well (Figure 10's cached baseline); with CPU-bound sandboxes, overcommit buys little; on CPU-constrained nodes, pmem's extra CPU may not be worth its memory savings (§8.4).
  • What it does not solve: agents crashing kernels or finding new answer channels; final-output checks need help from observability (§6.5).

Place a burst of sandboxes

When a rollout job asks for tens of thousands of sandboxes at once, which node gets each one? DSec's placement engine samples k eligible nodes at random and takes the least loaded; each engine instance adds its own recent placements to the watcher's last snapshot; and the edge on each node can still refuse a sandbox it has no room for, sending the request elsewhere (§3.2, §7). The paper says this avoids "herding". This tab runs that algorithm, and three alternatives, on the same burst, so you can see what herding is and what each piece of the design buys.

Try: play "Least loaded" first: every engine sees the same stale snapshot, so all of them pour each refresh window's requests onto the same few nodes, which overflow and reject. Then the paper's design. Shorten the refresh interval and least-loaded herds less, which shows that herding comes from staleness. Then set k to 8 with a 3 s refresh: power of k without the overlay starts to herd too, and the overlay pulls it back; with 16 engines each one knows only its own sixteenth of the placements, so the overlay helps less.

Each bar is one node, to scale against its capacity line (3,200 sandboxes, the container density the paper reports running stably, §4.3). Grey is what was running before the burst, colour what this burst added. Requests reach the engines round-robin at the creation rate; each engine sees the watcher's last snapshot, plus, with the overlay, its own placements since. An edge refuses a sandbox that would take its node over capacity, and the engine picks again (up to 8 tries). Published inputs: about 160 nodes, bursts up to 32K, over 5,000 creations a second, 3,200 per node. Illustrative inputs, which the paper does not give: k, the number of engine instances, the refresh interval and the starting load. What this shows, and what it cannot

  • Herding is a staleness effect. A "least loaded" rule that sees only a snapshot sends every request in a refresh window to the same node; several engines with the same snapshot pile on together. Sampling k nodes spreads requests across all nodes even when the view is stale, which is why power-of-k is robust here (Mitzenmacher, Richa and Sitaraman discuss stale information).
  • Small k is what makes staleness harmless. With k = 2 the snapshot hardly matters; the larger k, the closer the rule comes to "least loaded" and the more it herds on a stale view. The overlay helps exactly there, without coordination, because each engine at least knows its own recent placements; its help shrinks as the number of engine instances grows. The edge's admission check catches what the views still miss, at the price of a retry.
  • What it cannot show: the paper reports no placement measurements (no load spread, rejection rate or placement latency), so nothing here can be compared with DSec's real behaviour. It also leaves out filtering by backend and hardware, user isolation (which "bounds the blast radius" at some cost in density), sandboxes ending during the burst, and cloud bursting above 80% utilisation (§7, §3.4).
