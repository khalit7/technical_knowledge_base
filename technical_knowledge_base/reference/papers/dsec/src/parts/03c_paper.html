Co-design with the RL framework

[[S6|§6 Co-design with the RL framework]]

DSec has served every sandbox workload of DeepSeek's RL training and evaluation from {{DeepSeek-V3.2|https://arxiv.org/abs/2512.02556}} to {{V4.1|https://arxiv.org/abs/2609.19969}} ({{§6|ax:S6}}). Three pieces of co-design go beyond running sandboxes efficiently.

Environments built by agents. Hand-building the environments agentic RL needs is impractical, so agents build them interactively on the same infrastructure. pack_diff checkpoints a live sandbox as an incremental disk snapshot that can be restored as a new sandbox, turning a session into a reusable environment with no separate image pipeline. Builders follow internal packing rules (given to them as instructions) that limit runtime impact; an internal platform quality-checks agent-built environments and exports them in standard formats. Builders and runtime agents use separate accounts, and build-time residue is wiped from the writable layer before packing, so reference answers do not leak into the image ({{§6.1|ax:S6.SS1}}).

The rollout lives outside the GPU job. GPU training jobs are routinely preempted to raise utilisation. In earlier pipelines the agent loop ran inside the preemptible GPU pod with model serving and the RL framework; a preemption killed the loop while its sandbox survived, and recovery replayed a command log to reconcile the two, reusing recorded results for completed operations so non-idempotent commands did not run twice. From DeepSeek-V4.1, rollout execution moved onto DSec as two parts outside the preemptible pool: an agent sandbox that hosts the scaffold (for example DeepSeek Harness) and its tools, and a worker container that manages the sandbox as a scaffold-agnostic control layer. Together they hold the complete rollout state, so a preempted GPU job reconnects and continues without replay ({{§6.2|ax:S6.SS2}}).

Pause instead of hold. Keeping state until the rollout finishes would leave many idle sandboxes holding memory while training is suspended, so the RL framework sends pause requests to all sandboxes of a preempted job. A container is frozen with docker pause, given swap through memory.swap.max and reclaimed with memory.reclaim (anonymous and file pages); resume prefetches with MADV_WILLNEED, then unpauses. A microVM is snapshotted (memory and execution state) and its Firecracker process killed; resume starts a new process from the snapshot. Any request to a paused sandbox resumes it transparently first ({{§6.3|ax:S6.SS3}}).

One rollout through a preemption; an illustrative scenario built from §6.2 and §6.3.

The six-turn rollout and the memory bar are illustrative; the components, what each holds, and what happens at preemption, pause and resume are the paper's. The paper does not say whether earlier pipelines also paused sandboxes; this animation shows only what it describes. None of this is measured in the paper: section 8 states that the framework integration is outside its evaluation ({{§8|ax:S8}}).

Agent misbehaviour, and what the sandbox can do about it

[[S6.SS4|§6.4, §6.5]]

Production showed two risks: a task that appears to pass because the agent got the answer through an unintended channel, which corrupts training and evaluation signals, and agent actions that damage the environment or its neighbours ({{§6.4|ax:S6.SS4}}). The paper's catalogue:

The authors draw two limits themselves: final-output checks alone cannot establish whether an agent solved the task as intended, and the access controls "address only part of the problem and do not provide a general defense against destructive behavior such as triggering kernel bugs"; they rely on observability and keep hardening DSec as models change ({{§6.4|ax:S6.SS4}}, {{§6.5|ax:S6.SS5}}). The paper frames these controls as a mitigation of reward hacking ({{Amodei et al.|https://arxiv.org/abs/1606.06565}}, {{Skalse et al.|https://arxiv.org/abs/2209.13085}}): a shortcut the sandbox blocks never reaches the reward function. It does not claim an inescapable sandbox, and the XFS episode shows an agent working around a control after it was introduced.

Results

[[S8|§8 Evaluation, Figures 10 to 13]]

The evaluation runs on a dedicated 10-node CPU test cluster, separate from production. MicroVM nodes are bare metal (2 × 96-core AMD EPYC 9655 with SMT, 1.5 TB DRAM, 3.4 TB local disk) so there is no nested virtualisation; container experiments run inside a QEMU VM (1 × 96 cores, 192 hardware threads, 512 GB, 5.8 TB). Hosts run Linux 7.0, microVM guests Linux 6.1. Workloads come from real RL training and evaluation: internal software-engineering suites, SWE-bench, Terminal-Bench, security exploit tasks ({{§8.1|ax:S8.SS1}}). Only the four §5 mechanisms are evaluated ({{§8|ax:S8}}).
