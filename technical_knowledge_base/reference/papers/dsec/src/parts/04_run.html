Place a burst of sandboxes

When a rollout job asks for tens of thousands of sandboxes at once, which node gets each one? DSec's placement engine samples k eligible nodes at random and takes the least loaded; each engine instance adds its own recent placements to the watcher's last snapshot; and the edge on each node can still refuse a sandbox it has no room for, sending the request elsewhere ({{§3.2|ax:S3.SS2}}, {{§7|ax:S7}}). The paper says this avoids "herding". This tab runs that algorithm, and three alternatives, on the same burst, so you can see what herding is and what each piece of the design buys.

Try: play "Least loaded" first: every engine sees the same stale snapshot, so all of them pour each refresh window's requests onto the same few nodes, which overflow and reject. Then the paper's design. Shorten the refresh interval and least-loaded herds less, which shows that herding comes from staleness. Then set k to 8 with a 3 s refresh: power of k without the overlay starts to herd too, and the overlay pulls it back; with 16 engines each one knows only its own sixteenth of the placements, so the overlay helps less.

Each bar is one node, to scale against its capacity line (3,200 sandboxes, the container density the paper reports running stably, {{§4.3|ax:S4.SS3}}). Grey is what was running before the burst, colour what this burst added. Requests reach the engines round-robin at the creation rate; each engine sees the watcher's last snapshot, plus, with the overlay, its own placements since. An edge refuses a sandbox that would take its node over capacity, and the engine picks again (up to 8 tries). Published inputs: about 160 nodes, bursts up to 32K, over 5,000 creations a second, 3,200 per node. Illustrative inputs, which the paper does not give: k, the number of engine instances, the refresh interval and the starting load. What this shows, and what it cannot

  • Herding is a staleness effect. A "least loaded" rule that sees only a snapshot sends every request in a refresh window to the same node; several engines with the same snapshot pile on together. Sampling k nodes spreads requests across all nodes even when the view is stale, which is why power-of-k is robust here ({{Mitzenmacher, Richa and Sitaraman|https://www.eecs.harvard.edu/~michaelm/postscripts/handbook2001.pdf}} discuss stale information).
  • Small k is what makes staleness harmless. With k = 2 the snapshot hardly matters; the larger k, the closer the rule comes to "least loaded" and the more it herds on a stale view. The overlay helps exactly there, without coordination, because each engine at least knows its own recent placements; its help shrinks as the number of engine instances grows. The edge's admission check catches what the views still miss, at the price of a retry.
  • What it cannot show: the paper reports no placement measurements (no load spread, rejection rate or placement latency), so nothing here can be compared with DSec's real behaviour. It also leaves out filtering by backend and hardware, user isolation (which "bounds the blast radius" at some cost in density), sandboxes ending during the burst, and cloud bursting above 80% utilisation ({{§7|ax:S7}}, {{§3.4|ax:S3.SS4}}).
