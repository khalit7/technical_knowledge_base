The workload, measured

[[S4|§4 Production Workloads, Figures 2 to 8, Tables 2 and 3]]

Section 4 characterises one week of production in early 2026, for containers and microVMs only (together most instances and resources) ({{§4|ax:S4}}). Every number below is printed in the paper; the curves are rebuilt from the figures' vector data in {{the figures tab|tab:t-figs}}.

  • Bursts. A typical container task creates thousands of sandboxes (median 2,528, p90 7,969, p99 16,388; microVM tasks 352, 1,835 and 4,044), the largest jobs up to 32K, all within a short window because a batch cannot use an instance until its environment is ready; setup cost is multiplied by burst size and stragglers in any stage delay useful work ({{§4.1|ax:S4.SS1}}, {{Figure 2|ax:S4.F2}}).
  • Three phases. Setup prepares dependencies and tools; the tool-call phase alternates model generation with short CPU bursts; a test phase verifies the result and briefly raises demand again. CPU is intermittent after setup while memory and accumulated state persist ({{§4.1|ax:S4.SS1}}, {{Figure 3|ax:S4.F3}}).
  • Sparse CPU. About 90% of container and microVM sandboxes use no more than 5% of their requested CPU on average ({{Figure 5|ax:S4.F5}}). One node peaked at 1,048 containers and 524 microVMs in a day's sample ({{Figure 6|ax:S4.F6}}); across production DSec has run stably at 3,200 containers or 800 microVMs per node, "demonstrated operating points rather than hard limits" ({{§4.3|ax:S4.SS3}}).
  • Long lives. Median lifetimes are 17.4 minutes (containers) and 15.5 (microVMs); p99 exceeds three hours for both (231.5 and 213.9 minutes are printed on the figure) ({{Figure 7|ax:S4.F7}}).
  • Many images, little reuse. In one week the container backend served 11,266 base images and 102,171 workspaces, the microVM backend 2 base images and 53,590 workspaces (plus 4,889 snapshots), with 103 toolkits; 67.8% of sandboxes needed at least one workspace or toolkit on top of the base. That is 82.8 TB plus 50.9 TB, more than 130 TB, far beyond one node ({{§4.2|ax:S4.SS2}}, {{Table 2|ax:S4.T2}}). Per task, a container image is used by a median of 3 sandboxes (p90 28), a microVM image by 1 (p90 3), so node-local caches barely help ({{Figure 8|ax:S4.F8}}).

Three pressures follow, and section 5 answers each: setup that must not scale with per-sandbox extraction; density that is valuable but unsafe without care for memory and latency; and a huge, low-reuse image corpus that makes eager distribution expensive ({{§5|ax:S5}}, {{Figure 9|ax:S5.F9}}).

Mechanisms

[[S5|§5 Core System Mechanisms]]

1. Composable environment layers

A sandbox is three parts with separate lives: a base image (OS-level dependencies such as Ubuntu, Python 3.10 or Java 8), a workspace (the task's repository and its dependencies) and frequently updated toolkits (such as the DeepSeek Harness) ({{§4.2|ax:S4.SS2}}). Fused into one OCI image, they multiply: with M bases, N workspaces and K toolkits, upgrading m bases costs O(m·N) rebuilds and upgrading k toolkits O(k·N). Unpacking workspace and toolkit archives inside each sandbox instead costs CPU and I/O across a burst and causes startup timeouts; bind-mounting read-only directories replaces paths rather than merging into them, and breaks tools that write into their own tree (Python's __pycache__) ({{§4.2|ax:S4.SS2}}).

DSec stacks them as overlayfs layers at creation time: base at the bottom, the workspace as a read-only layer above, each toolkit on top, and a writable upper directory that absorbs runtime writes. A 30-line Go change to dockerd inserts the pre-mounted EROFS layers into the lower-directory stack. Upgrading m bases now rebuilds m layers, and k toolkits k layers ({{§5.1|ax:S5.SS1}}, {{§7|ax:S7}}). The layers are immutable, so they are stored in EROFS, a compact read-only filesystem that can decompress only the blocks a read touches, unlike a tar.gz that must be streamed and unpacked whole ({{§5.1|ax:S5.SS1}}). MicroVMs get the same model: EROFS images as read-only block devices, overlayfs inside the guest with an ext4 upper layer ({{§5.1|ax:S5.SS1}}).

2. On-demand image loading from 3FS

Sandboxes read only a small part of their images: 4.2% to 13.3% of the data in sampled container images ({{Table 3|ax:S4.T3}}). Pre-warming only moves the cost earlier, and under overcommit, pulling and unpacking full images steals CPU and I/O from running sandboxes ({{§4.4|ax:S4.SS4}}). So on-demand loading shrinks total I/O in proportion to what is used, not just its timing ({{§5.3|ax:S5.SS3}}).

Rather than a registry plus peer-to-peer delivery, DSec serves images from 3FS, the distributed filesystem its training already uses. 3FS is fast for large sequential I/O and poor at small random I/O, which sets three rules: writes stay local (the writable layer on the node's disk), reads are on demand and in bulk, and metadata is kept local where the format allows ({{§5.3|ax:S5.SS3}}). For containers, EROFS's multi-device mode separates metadata from data: the metadata is downloaded to local disk, file data stays in 3FS and is read through the page cache with kernel readahead, close to Nydus's design but without a registry or FUSE backend. Consecutive layers under a size threshold (for example 3 GB) are collapsed offline into one metadata and one data image, keeping overlayfs whiteouts, and file-backed mounts skip the loop device ({{§5.3|ax:S5.SS3}}).

MicroVMs need a different path: Docker's overlay2 cannot sit on an overlayfs data directory, and Firecracker does not support virtio-fs. Read-only layers still use EROFS, while writable ext4 disks (including one mounted at Docker's data root for Docker-in-microVM) are OverlayBD images exposed through ublk; because ext4 metadata lives inside the block image, the ublk path fetches 256 KiB chunks and keeps them in a second-level local cache, so a chunk evicted from the page cache is not fetched from 3FS again ({{§5.3|ax:S5.SS3}}). This Rust OverlayBD and ublk code is the part the authors released ({{§7|ax:S7}}). Each 3FS storage server has 20 × 15 TB SSDs and 2 × 400 Gbps RDMA NICs; tens of them serve a cluster of hundreds of thousands of CPU cores through 3FS's FUSE client ({{§7|ax:S7}}).

3. Memory: share the page cache, return free pages

MicroVMs waste memory twice: image data read through a virtual block device is cached by the host and again by every guest, and a guest does not return free pages to the host unless told to; requested memory usually exceeds demand, so guests feel little pressure to reclaim, and long lifetimes make retained memory expensive ({{§4.3|ax:S4.SS3}}). DSec uses two complementary fixes ({{§5.2|ax:S5.SS2.SSS0.Px1}}):

  • virtio-pmem with DAX maps file reads straight onto host pages, so co-located microVMs share one host page-cache copy. Its costs: a cold access may need synchronous fault handling (the buffered virtio-blk path gets guest readahead and batched I/O instead), and the guest must hold struct page metadata for the whole device, 64 bytes per 4 KiB page, so 1/64 of capacity: a 128 GB pmem device needs 2 GB of guest RAM.
  • DAMON plus balloon free-page reporting. The virtio-balloon driver reports free guest pages to the host, which drops them with madvise(MADV_DONTNEED), but by default only in order-9 blocks (2 MiB of 4 KiB pages). DAMON samples page-access bits, evicts file pages left untouched beyond an age threshold, and so frees scattered pages that coalesce into blocks large enough to report.

In production DSec enables pmem with DAX for the read-only EROFS base and toolkit layers and DAMON with free-page reporting for larger writable disks; all of it is Firecracker device configuration, guest kernel parameters and sysfs tuning, with no kernel modifications ({{§5.2|ax:S5.SS2.SSS0.Px1}}, {{§7|ax:S7}}).

4. CPU: keep best-effort work off a latency-sensitive core

Some tasks have strict per-step budgets, such as a game-playing agent with a fixed time per move. Lowering best-effort (BE) priority is not enough, because a latency-sensitive (LS) thread and a BE thread on sibling hyperthreads still share the core's execution resources ({{§4.3|ax:S4.SS3}}). DSec puts BE sandboxes under SCHED_IDLE, so they yield whenever LS work is runnable, and turns on Linux core scheduling (prctl(PR_SCHED_CORE)) for LS sandboxes so unrelated BE work never runs on the sibling thread of the same physical core ({{§5.2|ax:S5.SS2.SSS0.Px2}}, {{§7|ax:S7}}).

Other implementation details

GPU FnCall for operator benchmarking uses NVIDIA Multi-Instance GPU partitions for isolated concurrent benchmarks, compiles on CPU FnCall first so GPUs are not held during compilation, and keeps a warm pool of Python processes with libraries already imported; a shared-GPU mode raises concurrency for work that is not performance-sensitive ({{§7|ax:S7}}).
