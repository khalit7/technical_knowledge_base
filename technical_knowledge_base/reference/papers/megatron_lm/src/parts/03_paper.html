Problem

[[S2.SS3|§1 Introduction, §2.3]]

By 2019 the useful frontier of language models (BERT-large at 336M parameters, GPT-2 at 1.5B) had reached the memory of a single accelerator. Training keeps the weights, their gradients and the Adam optimiser's extra state per parameter, plus the activations, and a 32 GB V100 was running out even with activation checkpointing ({{§1|ax:S1}}, {{§2.3|ax:S2.SS3}}; what recomputation trades is on {{Distributed training|n:3c65c17b0d0d8103a916c4824abbd82e}}, section 10). Data parallelism, the usual way to scale out, has a hard limit here: "the model must fit entirely on one worker" ({{§2.3|ax:S2.SS3}}). Sharing parameters across layers, as ALBERT does, shrinks the footprint but also the model's capacity.

The existing ways to split a model across devices each had a cost ({{§2.3|ax:S2.SS3}}):

  • Pipeline parallelism (layers on different devices, in stages): with a parameter server (PipeDream and others) it suffers inconsistency; GPipe fixes that with synchronous gradient descent but pays either in pipeline bubbles that reduce efficiency or in optimiser changes that affect accuracy (the bubble is drawn on {{Distributed training|n:3c65c17b0d0d8103a916c4824abbd82e}}, section 6).
  • Distributed tensor computation (one operation split across devices): general, but FlexFlow and Mesh-TensorFlow are frameworks with their own language and compiler, and GPipe and Mesh-TensorFlow "require rewriting the model, and rely on custom compilers and frameworks that are still under development" ({{§1|ax:S1}}).

The memory formula

Per GPU: 16 × parameters / t for weights, gradients and Adam state; 2sbh bytes per layer for the checkpointed fp16 layer inputs (not split by Megatron); one layer's full activations during its recomputation, sbh(10 + 24/t + 5as/(ht)) bytes ({{Korthikanti et al. 2022, §4.1|https://arxiv.org/abs/2205.05198}}). Batch 8 and sequence 1,024 as in the paper's model-parallel scaling runs ({{§5.1|ax:S5.SS1}}). Ignores fragmentation and framework buffers.

The gap: a way to split a transformer layer itself across GPUs that is simple enough to write in native PyTorch with a handful of communication calls: no new compiler, no new framework, and orthogonal to pipeline parallelism so the two can be combined ({{§1|ax:S1}}).

Idea: split each matrix the way that keeps nonlinearities local

[[S3|§3, Eq. 1 to 3]]

The core idea is intra-layer model parallelism, now called tensor parallelism (TP): partition the weight matrices of every transformer layer across GPUs, choosing the direction of each split so that no nonlinearity ever sees a partial sum. Then the GPUs only need to synchronise a few times per layer ({{§3|ax:S3}}).

A transformer layer is a self-attention block followed by a two-layer MLP ({{Figure 2|ax:S2.F2}}). The MLP's first half is a matrix multiply (GEMM) followed by a GeLU:

Y = GeLU(XA)
Equation 1 ({{§3|ax:S3.E1}}). X is the batch of token vectors, A is H × 4H.

There are two ways to split that GEMM across two GPUs:

  1. Split A by rows and X by columns: X = [X1, X2], A = [A1; A2], so XA = X1A1 + X2A2 ({{Eq. 2|ax:S3.E2}}). Each GPU holds a partial sum of the whole output. Because GeLU is nonlinear, GeLU(X1A1 + X2A2) ≠ GeLU(X1A1) + GeLU(X2A2), so the GPUs must add their partials (an all-reduce) before the GeLU.
  2. Split A by columns: A = [A1, A2] gives [Y1, Y2] = [GeLU(XA1), GeLU(XA2)] ({{Eq. 3|ax:S3.E3}}). Each GPU owns whole output columns, so GeLU applies to each shard independently: no synchronisation.
with option 1 (A split by rows), suppose each GPU applies GeLU to its own partial result and the outputs are summed afterwards, to save the synchronisation. How close is that to the true GeLU(XA)?

X is 3 × 8 (3 tokens, H = 8), A is 8 × 16 (4H), entries drawn from a normal distribution with a fixed seed. GeLU is the tanh approximation used by GPT-2 and BERT. The reference is GeLU(XA) computed on one device; the error is the largest absolute difference over all 48 outputs. Illustrative sizes; the equations are the paper's.

Megatron takes option 2 for the first GEMM (column-parallel) and then splits the second GEMM, B (4H × H), by rows (row-parallel): B = [B1; B2], so GPU i computes YiBi straight from its own GeLU output and the full result Y1B1 + Y2B2 is recovered by a single all-reduce before dropout ({{§3|ax:S3}}, {{Figure 3a|ax:S3.F3}}). The general recipe: column-split the layer that feeds a nonlinearity, row-split the layer that follows it, and the elementwise nonlinearity lives entirely between them with zero communication.

Method: the f and g operators

[[S3.F3|§3, Figure 3, Code 1]]

The MLP block is Z = Dropout(GeLU(XA)B), with A: H × 4H and B: 4H × H. The whole scheme is packaged as two conjugate autograd functions placed around each block ({{Figure 3|ax:S3.F3}}):

OperatorWhereForward passBackward passWhy
fblock inputidentityall-reduce of the gradientevery GPU needs the full X, and each contributes part of the gradient with respect to X, which must be summed
gblock outputall-reduceidentitysums the row-parallel partials YiBi; its gradient is already complete on every GPU

Each is a few lines of PyTorch. The paper prints f ({{Code 1|ax:S3}}); g swaps the two methods:

class f(torch.autograd.Function):
    def forward(ctx, x):
        return x
    def backward(ctx, gradient):
        all_reduce(gradient)
        return gradient

With one g and one f per block and two blocks per layer, a transformer layer needs exactly 4 all-reduces in total: 2 in the forward pass (one g per block) and 2 in the backward pass (one f per block), covering both attention and the MLP ({{§3|ax:S3}}, {{Figure 4|ax:S3.F4}}).

How the counters are computed

Elements sent per GPU use the ring algorithm: an all-reduce of n elements sends 2(t − 1)/t × n, an all-gather (t − 1)/t × n, at 2 bytes (fp16) for b × 1,024 tokens. Time is elements ÷ link speed, with no overlap and no latency. Megatron's two collectives are the paper's ({{Figure 3a|ax:S3.F3}}); Option 1's backward collectives are derived here (the conjugate of each forward step), not given in the paper.

Answer, and the count with checkpointing

3.75 times for any t. Megatron sends 4(t − 1)/t × H numbers per token per block (two all-reduces of H); Option 1 sends 15(t − 1)/t × H (all-reduces of 4H and H, all-gathers of 4H and H), and every GPU evaluates all 4H GeLUs instead of 4H/t. With activation checkpointing, as the paper trains, each layer's forward pass runs again during the backward pass, and its 2 all-reduces with it: 6 per layer in practice (our reading of how checkpointing works; the paper counts 4). The ring formula behind the byte counts is {{Interconnects and scaling|n:3c65c17b0d0d81808563fd41fb163af0}}'s.

Method: self-attention, split by heads

[[S3.F3|§3, Figure 3b]]

Multi-head attention is embarrassingly parallel over heads. The query, key and value projections are split by columns so that each GPU holds the full Q, K and V projections for a subset of heads; the softmax, attention dropout and the weighted sum over V for those heads then run entirely locally. The output projection is split by rows and consumes the local head outputs directly, followed by the g all-reduce: the same fused pair of GEMMs, the same single forward synchronisation ({{§3|ax:S3}}, {{Figure 3b|ax:S3.F3}}). It also means the number of heads must be divisible by the number of GPUs.

Does the head count matter for speed? (Appendix D, Table 7)

Yes, a little: at 8.3B on 8 GPUs, 16 heads of 192 scale at 82%, 24 of 128 at 80% and 32 of 96 at 77%, because more heads mean smaller GEMMs and a larger softmax ({{Table 7|ax:A4.T7}}).

Method: embeddings and the loss

[[S3|§3]]

The output embedding is H × v and GPT-2's vocabulary is 50,257 tokens, so it is worth splitting; and because the input and output embeddings share weights, both are split. The input embedding EH×v is split along the vocabulary, E = [E1, E2]: each GPU looks up the tokens in its slice and an all-reduce (g) merges them. For the output, the parallel GEMM [Y1, Y2] = [XE1, XE2] gives each GPU the logits of its slice. All-gathering them for the loss would communicate b × s × v elements (batch × sequence × vocabulary), huge because v is large; instead the GEMM is fused with the cross-entropy, which reduces what is communicated to b × s ({{§3|ax:S3}}).

fp16 logits at 2 bytes; losses and statistics at 4 bytes (fp32). Bars to scale on a log axis. The paper counts b × s; Megatron's current {{cross_entropy.py|https://github.com/NVIDIA/Megatron-LM/blob/main/megatron/core/tensor_parallel/cross_entropy.py}} all-reduces three b × s tensors (the maximum logit, the target's logit and the sum of exponentials), which is still a factor v/3 smaller. Llama 3's vocabulary is from its {{paper|https://arxiv.org/abs/2407.21783}}.

The vocabulary is padded so each GPU's slice is a multiple of 128 for efficient GEMMs: for up to 8-way splits that means a multiple of 128 × 8 = 1,024, and 50,257 becomes 51,200 ({{§5.1|ax:S5.SS1}}).

Method: duplicate cheap work rather than communicate

[[S3|§3, Appendix B.2]]

"Much of our model parallel approach can be characterized as techniques aimed at reducing communication and keeping the GPUs compute bound" ({{§3|ax:S3}}). LayerNorm, dropout and the residual connections are cheap, so instead of one GPU computing them and broadcasting the result, every GPU keeps a duplicate copy of the LayerNorm parameters and runs dropout and the residual on the output of the parallel region before feeding the next one. Each model-parallel worker optimises its own set of parameters; since every value is either local to a GPU or duplicated on all of them, no updated parameter values are ever communicated.

Dropout and the random number generators (Appendix B.2)

Dropout needs care because some of it sits outside the parallel regions (before the residual connections) and some inside (attention dropout). Outside, the GPUs must drop the same elements, so all random number generators are seeded identically at the start; inside, each GPU must draw a different pattern, so a separate generator is kept for dropout in the parallel regions, seeded uniquely per worker ({{Appendix B.2|ax:A2.SS2}}).

Method: combining with data parallelism

[[A2.SS1|Appendix B.1, Figure 8]]

Tensor parallelism is orthogonal to data parallelism (and to pipeline parallelism), so they compose. Two or more GPUs in the same server form a model-parallel group holding one copy of the model; GPUs with the same position in every model-parallel group form a data-parallel group, whose weight gradients are all-reduced together, several such all-reduces running in parallel. The total GPU count is the product. For the 8.3B model: 8 GPUs per model-parallel group times 64-way data parallelism is 512 GPUs. All communication is PyTorch calling NCCL ({{Appendix B.1|ax:A2.SS1}}, {{Figure 8|ax:A2.F8}}). The 8-way groups sit inside one DGX-2H server, where NVSwitch gives 300 GB/s between GPUs, against 100 GB/s per server between servers ({{§5|ax:S5}}).

Setup: data, models and recipe

[[S4|§4, §5.1]]
Data, training recipe and hardware (§4.1, §4.2, §5)

Data ({{§4.1|ax:S4.SS1}}): an aggregate of Wikipedia, CC-Stories, RealNews and OpenWebText, with the Wikipedia articles of the WikiText103 test set removed to avoid leakage and stray newlines removed from CC-Stories; BooksCorpus is added for BERT but excluded for GPT-2 because it overlaps with LAMBADA. Documents shorter than 128 tokens are dropped, near-duplicates (Jaccard similarity above 0.7) removed with locality-sensitive hashing: 174 GB of deduplicated text.

Recipe ({{§4.2|ax:S4.SS2}}):

  • Mixed precision with dynamic loss scaling, for the V100's Tensor Cores.
  • Weights initialised from N(0, 0.02), and the weights just before each residual connection scaled by 1/√(2N), N the number of transformer layers (0.083 for the 72-layer 8.3B model).
  • Adam with weight decay λ = 0.01, global gradient-norm clipping at 1.0, dropout 0.1, activation checkpointing after every transformer layer.
  • GPT-2: sequences of 1,024 subword tokens, batch 512, 300k iterations; learning rate 1.5e-4 with 3k warmup iterations, then a single cosine decay over the remaining 297k, stopped at 1e-5.
  • BERT: largely ALBERT's procedure, the original 30,522-token BERT vocabulary, next-sentence prediction replaced by sentence-order prediction, whole-word n-gram masking (SpanBERT); batch 1,024, learning rate 1.0e-4 warmed up over 10,000 iterations and decayed linearly over 2 million.

Hardware ({{§5|ax:S5}}): up to 32 DGX-2H servers, 512 Tesla V100 SXM3 32 GB GPUs; 300 GB/s between GPUs in a server through NVSwitch, 100 GB/s between servers through 8 InfiniBand adapters per server.

Scaling configurations ({{§5.1|ax:S5.SS1}}, {{Table 1|ax:S5.T1}}): four GPT-2 models from 1.2B to 8.3B parameters, keeping the hidden size per head at 96 so attention GEMMs stay the same size; 1.2B fits on one GPU, 8.3B needs 8-way model parallelism. Model-parallel runs use a fixed batch of 8; model-plus-data-parallel runs a global batch of 512, which is 64-way data parallelism.

Results: scaling

[[S5.SS1.SSS1|§5.1.1, Figures 1 and 5]]

The baseline is the 1.2B model on a single GPU, a strong one: it sustains 39 TFLOP/s, 30% of the theoretical peak of a V100 in a DGX-2H server ({{§5.1.1|ax:S5.SS1.SSS1}}), which makes the peak 130 TFLOP/s (39 / 0.30). Scaling is weak scaling in model size: about 1 billion parameters per GPU, so 2 GPUs train the 2.5B model and 8 the 8.3B ({{Figure 1|ax:S1.F1}}), rather than the usual weak scaling in batch size.

76% or 74%?
The abstract, introduction and this page's takeaway say 76%; {{Figure 5 and §5.1.1|ax:S5.SS1.SSS1}} say 74% for the same 512-GPU run. They come from different arithmetic: 15.1 PFLOP/s ÷ (512 × 39 TFLOP/s) = 75.6%, which rounds to 76%; 74% of 512 × 39 TFLOP/s would be 14.8 PFLOP/s. The paper does not say which measurement each uses (15.1 is "up to"). Both are shown; neither is wrong by its own arithmetic (recompute.py).

Model parallelism also speeds up a model that already fits (strong scaling): the 1.2B model at batch 8 runs 1.64 times faster on 2 GPUs, 2.34 on 4 and 2.98 on 8, with returns diminishing "as the per-GPU computation decreases and the memory bandwidth and communication overheads begin to dominate" ({{Appendix D.2|ax:A4.SS2}}, {{Table 8|ax:A4.T8}}). That is 82%, 59% and 37% of linear: tensor parallelism is for fitting big models, not for speeding up small ones.

How much of this to believe

[[S5|§5, Appendix D]]

What holds up, and why.

  • The mechanism is exact. Splitting A by columns and B by rows computes the same function as the unsplit layer; only the order of floating-point additions in the all-reduce changes ({{Eq. 3|ax:S3.E3}}; the {{split demo|tab:t-read:pr-split}} gives an error of 0 on real matrices). There is no accuracy trade-off to measure, which is why the paper does not need an ablation for it.
  • The baseline is strong, not flattering. Efficiency is measured against a single GPU already at 39 TFLOP/s, 30% of peak, over "the entire application" ({{§5.1.1|ax:S5.SS1.SSS1}}). A weak baseline would have inflated the 77%.
  • The configurations check out. Every parameter count in Tables 1, 2 and 4 is reproduced from its configuration, and the memory arithmetic reproduces Table 1's GPU counts ({{tables tab|tab:t-tables}}).
  • It held up. The same split, with the same f and g, is what MT-NLG, the PTD-P runs and Llama 3 use for tensor parallelism, citing this paper ({{Then and now|tab:t-then}}), and serving engines expose it as a standard option.

What to read with care.

  • "76% scaling efficiency" is weak scaling in model size, not a speedup. It compares the 1.2B model on 1 GPU with the 8.3B model on 512 ({{Figure 5|ax:S5.SS1.SSS1}}): different models, different GEMM shapes. With the model fixed (strong scaling), 8 GPUs give 2.98 times, 37% of linear ({{Table 8|ax:A4.T8}}). The authors say this themselves: model parallelism "is primarily designed to enable training models larger than what can fit" ({{Appendix D.2|ax:A4.SS2}}), which counts in their favour.
  • The paper disagrees with itself on the headline. 76% in the abstract and introduction, 74% in §5.1.1 and Figure 5, for the same run; 15.1 PFLOP/s ÷ (512 × 39) is 75.6% ({{box above|tab:t-read:s-res}}).
Five more caveats: FLOP counting, single runs, unlike comparisons, an unfinished run, one pair of curves
  • How FLOPs are counted is not stated. Neither 39 TFLOP/s nor 15.1 PFLOP/s says whether the recomputed forward pass of activation checkpointing, or attention, is counted; both are presented as measured throughput. Table 2's epoch time for the trained 8.3B model implies 13.8 PFLOP/s by a later paper's formula, about 9% under the headline, which was measured on a differently shaped (32-head) configuration ({{Table 2 rebuilt|tab:t-tables:tb2}}).
  • Single runs. Each pretraining run and each scaling point is one run, with no seeds or error bars ({{§5|ax:S5}}). Fine-tuning reports the median of 5 seeds but no spread ({{§5.3|ax:S5.SS3}}), so margins such as QQP's 92.7 against XLNet's 92.3 cannot be judged against noise.
  • The state-of-the-art comparisons are not like for like. The GPT-2 models were trained on a different, 174 GB corpus ({{§4.1|ax:S4.SS1}}); the WikiText103 baseline (15.79) is a nearest-neighbour language model (Khandelwal et al. 2019), the LAMBADA baseline GPT-2 itself ({{Table 3|ax:S5.T3}}). The 8-gram leakage check is reassuring but bounds overlap only at "at most" 10.8% and 1.4% ({{§5.2|ax:S5.SS2}}). The RACE record (90.9%) is a 5-way ensemble; the single model scores 89.5% ({{Table 5|ax:S5.T5}}). The BERT models saw fewer training tokens than RoBERTa, ALBERT or XLNet, which cuts the other way.
  • An unfinished run. The 3.9B BERT had been trained for 1.5 million iterations (the smaller two for 2 million) and "is still training" when its results were reported ({{§5.3|ax:S5.SS3}}).
  • The LayerNorm finding rests on one pair of curves. Figure 7 compares one 752M run of each arrangement, by training loss ({{Figure 7|ax:S5.F7}}). It held up: pre-norm became the default, and {{Xiong et al. 2020|https://arxiv.org/abs/2002.04745}} later gave a theoretical reason; but the paper itself shows one comparison, not a study.

Verdict: believe the method completely; it is exact and has been the standard for seven years. Treat "77%" and "76%" as "a 7 times larger model on 8 GPUs, and on 512, at about three quarters of the per-GPU throughput", not as a speedup, and treat the accuracy records as single runs on different data that showed scale helps, not as controlled comparisons.

Why it matters (beyond the paper)

  • Tensor parallelism became a standard axis. The data, tensor, pipeline and expert (DP, TP, PP, EP) decomposition every training stack now uses, the "3D parallelism" framing ({{MT-NLG|https://arxiv.org/abs/2201.11990}}), takes its TP axis from this paper, and the column-then-row split with conjugate f and g is still the canonical formulation (Llama 3 cites it for TP, {{§3.3.2|https://arxiv.org/abs/2407.21783}}). It is also the standard way to serve a model on several GPUs (names in the dated block below). How TP composes with the other axes today is {{Distributed training|n:3c65c17b0d0d8103a916c4824abbd82e}}'s subject (sections 5 and 9).
  • Follow-up work completed the picture. {{Narayanan et al. 2021|https://arxiv.org/abs/2104.04473}} combined this TP with pipeline parallelism and an interleaved 1F1B schedule (PTD-P) and reached 502 PFLOP/s on 3,072 A100s, 52% of peak, on a 1-trillion-parameter model. The pair of papers defines the classic pre-training scaling playbook; {{Then and now|tab:t-then}} follows it to 2026.
  • It fixed the mental model for communication cost. TP's per-layer all-reduces on activations need a fast interconnect, which is why its degree is conventionally capped at the NVLink domain (8 GPUs per node) while DP and PP cross nodes. The rule comes from this paper's setup (8-way TP inside a 16-GPU server) and was stated as a measured result by Narayanan et al.: "tensor model parallelism is best within a node", with peak performance when "the tensor-parallel size is equal to the number of GPUs in a single node" ({{§5.4.1|https://arxiv.org/abs/2104.04473}}).
  • Pre-LN. The BERT result helped make pre-norm the default. It was not the first pre-LN transformer: {{GPT-2 §2.3|https://cdn.openai.com/better-language-models/language_models_are_unsupervised_multitask_learners.pdf}} had already moved LayerNorm to the input of each sub-block, and {{Xiong et al. 2020|https://arxiv.org/abs/2002.04745}} later explained why it trains more stably. What this paper showed is that the change is what lets BERT-style encoders scale.
Where it is used now (checked 2026-10-02; volatile)
  • Serving option names: {{vLLM|https://docs.vllm.ai/en/latest/serving/parallelism_scaling.html}} and {{TensorRT-LLM|https://nvidia.github.io/TensorRT-LLM/features/parallel-strategy.html}} call it tensor_parallel_size, SGLang tp_size ({{server_args.py|https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/server_args.py}}).
  • The codebase outlived the paper. Megatron-LM grew into Megatron-Core, the {{repository|https://github.com/NVIDIA/Megatron-LM}} that NVIDIA's large-model training builds on, and trained or fed many large runs: Turing-NLG 17B (cited in the paper's own v4; Turing-NLG also used ZeRO, {{ZeRO abstract|https://arxiv.org/abs/1910.02054}}), {{MT-NLG 530B|https://arxiv.org/abs/2201.11990}} (DeepSpeed with Megatron's tensor slicing), NVIDIA's Nemotron models (the {{Nemotron-4 340B report|https://arxiv.org/abs/2406.11704}} gives Megatron-LM as its pretraining code), and forks such as Megatron-DeepSpeed.
