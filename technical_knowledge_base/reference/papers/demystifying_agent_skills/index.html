Problem

§1 Introduction

A skill is a packaged piece of procedural knowledge an agent can load at run time: a folder holding a SKILL.md file (a name, a one-line description, then steps, checks and pitfalls) and any scripts it needs. Anthropic popularised the format (Anthropic engineering, 16 October 2025). The agent first sees only each skill's name and description, and reads the body when it judges the skill relevant ("progressive disclosure"). Claude Code, Codex and Gemini CLI all load skills this way, and the paper's protocol does the same: skills are "placed in the execution environment as reusable procedural resources rather than fully incorporated into the initial context" (§3.2).

Skills are usually judged by aggregate task success: load the skill, count how many more tasks pass (§1). That says skills matter but not why. It does not show:

  • what changes in the agent's behaviour when a skill is loaded;
  • which parts of execution get stabilised;
  • why the same skill helps one task and hurts another;
  • whether a gain comes from the distilled procedure itself, or from outcome labels, retrieval quality or coupling to one framework.

So skills are "written, retrieved, and revised through heuristic iteration, prompt tuning, or benchmark-specific trial and error" (§1).

The question: when do skills help, why do they work, and where do they fail? The authors treat skill use as a controlled transformation of prior agent experience, not as a black-box prompt add-on (§3.1).

Idea: hold the experience fixed, change only its packaging

§3.3, Figure 1

Run an agent on a task several times and keep the trajectories, some successful and some failed. That pool of experience can be handed to the next run in two forms (§3.3, Table 5):

  • Workflow Memory: the trajectories, cleaned and structured but keeping their procedural flow, appended to the task instruction (the representation of Agent Workflow Memory, Wang et al. 2024).
  • Skill: the same trajectories distilled by a model into one standardised SKILL.md, placed in the environment.

Both are compared with Raw, the agent with no prior experience. Because Workflow Memory and Skill come from the identical pool, any difference between them is the packaging, not the experience. This is the paper's central control.

The skill-creator prompt. Skills were written by a model from the trajectories with a fixed template (Appendix B.1): "Use This Skill When", "Preconditions", numbered "Steps", "Common Failure Modes To Avoid", "If A Failure Happens" and "Verify", with rules such as "Produce exactly ONE skill", "general enough to apply to similar tasks" and "Do not include task-specific file paths or data". Toggle the no-hint version used for the outcome-label ablation (Appendix B.2) to see the only lines that change.

Method

§3.2, Appendix A

Four research questions (§3.1):

  • RQ1, representation: does the same experience behave differently as Workflow Memory or as a Skill?
  • RQ2, outcome labels: do skills help because of the procedures, or because the skill creator knew which runs succeeded?
  • RQ3, transfer: do skills built in one agent framework still help in another?
  • RQ4, retrieval: what happens when the skill must be found in a growing, confusable library?

Agents, models, benchmarks (§3.2, Appendix A.1):

  • Two agent and model pairings: Codex + GPT-5.3-Codex and Gemini CLI + Gemini-3.1-Pro-Preview.
  • Three benchmarks: Terminal-Bench 2.0 (89 tasks), the 200-task public split of Terminal-Bench-Pro (400 tasks in 8 domains), and SkillsBench (86 tasks in 11 domains, with native task-to-skill annotations).
  • Harbor's evaluation workflow, n = 5 trials per task, parallelism 20.
  • RQ1 and RQ2 use controlled subsets of tasks; this page recovers their sizes from the printed rates in the tables tab (for Codex 31, 24 and 33 tasks; for Gemini 26, 21 and 26).

The composition grid (RQ1, RQ2). For each task the authors kept tasks whose raw runs both succeeded and failed, collected runs until each had a balanced pool, then built artifacts from six fixed-budget mixtures of five trajectories: 5s0f (five successes, no failures), 4s1f, 3s2f, 2s3f, 1s4f, 0s5f (§3.3, Appendix A.4). For every mixture, Workflow Memory and Skill are built from the same five trajectories. The no-hint variant hides the success and failure labels from the skill creator only (Appendix A.5).

Transfer (RQ3). Artifacts built from Codex trajectories are evaluated in Gemini CLI against Gemini's own Raw baseline (Appendix A.6).

The contrastive taxonomy (§4, Appendix A.2):

  • 8,135 trial records normalised into one manifest, 7,837 of them with transcripts (Table 7).
  • Open coding of 240 stratified trajectories by Claude Sonnet 4.6, tools and session memory disabled, with fixed transcript budgets (instruction and skill 3,000 characters each, transcript head 6,000 and tail 12,000). 238 valid unique labels came back.
  • A two-round batched induction merges them: batches of about 60 propose 8 to 14 modes each, then a merge prompt asks for 9 to 14 global modes. It produced 12, in 3 categories:
    • SC1, guided success: skill-guided, workflow-guided, autonomous;
    • SC2, execution and verification failures: environment or infrastructure, output format or schema mismatch, background-service lifecycle, shell corruption, algorithmic logic error, static verification without runtime;
    • SC3, invocation and boundary failures: timeout or budget exhaustion, skill guidance misapplied or ignored, capability or safety limit.
  • A human check: for each of the 238 labels, three supporting trajectories (714 checks), all confirmed; the human's independent mapping of the 238 labels to the 12 modes agrees with the LLM's 95.8% of the time, Cohen's κ = 0.952 (Table 3).
  • The unit of analysis is a paired triple: raw, workflow and skill runs of the same task and mixture. There are 528 (SkillsBench 144, Terminal-Bench 2.0 186, Terminal-Bench-Pro 198), giving 1,584 arm-level labels. For each triple the judge also names a mechanism: procedural_anchor, knowledge_injection, failure_warning, none or counterproductive (Table 2).

Retrieval (RQ4) (§5.5, Appendix A.7):

  • Each SkillsBench task gets a candidate pool of its ground-truth skill plus k − 1 real distractors, k ∈ {5, 10, 20, 50, 100}, drawn three ways: random, semantically similar (embedding near-neighbours) or dissimilar.
  • Arm 1: embedding retrieval with Qwen3-Embedding-0.6B, top-1 by cosine similarity.
  • Arm 2: the agent explicitly selects skills without running the task.
  • Arm 3: the full pool is placed in the environment, the task runs, and the skills the agent inspected or invoked are parsed from the trajectory.
  • Outputs are never passed between arms. Arms 2 and 3 use Gemini CLI + Gemini-3.1-Pro-Preview and Codex + GPT-5.4, because GPT-5.3-Codex was no longer available; the authors therefore compare only within this study.

Result 1: skills beat workflow memory, not clearly raw

§5.1, Tables 9, 10, 12
In the 528 paired triples, which difference is clearly above zero?

Mean paired difference and 95% bootstrap interval, Table 10; success counts from Table 9.

Oracle-status success (the benchmark verifier's reward) is 61.9% for Skill (327 of 528), 59.1% for Raw (312) and 55.9% for Workflow Memory (295) (Table 9). The robust paired effect is Skill over Workflow Memory: +6.06 points, 95% bootstrap interval [+0.76, +11.36] over 1,000 resamples. Skill over Raw is +2.84 [−2.27, +7.95], and Workflow Memory sits below Raw at −3.22 [−8.14, +2.08] (Table 10). Same trajectories, different packaging: the paper's reading is that representation itself is doing the work (§5.1).

Not just any short hint. On 26 Terminal-Bench-2 tasks with Gemini (130 trials per condition), two compact baselines injected as plain text do worse (Table 12): an instruction-derived short plan of three to five steps reaches 47.7%, a workflow-derived test-first template 59.2%, against Raw 50.0%, Workflow Memory 62.3% and Skill 79.2%. Those Raw, Workflow and Skill figures equal Table 1's Gemini Terminal-Bench-2 cells at 5s0f, the mixture where skills did best, so the baselines were measured against skills at their best.

The full runs tell a more mixed story. Table 1 holds every condition's success over all five trials per task (the 528 triples use one trial per arm). Below, Skill minus Workflow Memory for every setup and mixture, with a binomial interval from the trial counts this page recovers.

Bars are 95% intervals (±1.96 standard errors, treating trials as independent; trials of one task are correlated, so these are too narrow if anything). Trial counts are the smallest n for which every printed four-decimal rate is a whole number of successes (Table 1; recompute.py).

  • Codex on Terminal-Bench-2 carries the result: workflow memory drags Codex below its Raw 0.5935 in all six mixtures (down to 0.2710), while skills sit at 0.68 to 0.78 in five.
  • Gemini on Terminal-Bench-Pro goes the other way: Workflow Memory beats Skill in five of six mixtures.
  • Across all 36 cells Skill wins .

Mechanism labels. The judge's mechanism labels say how skills help: procedural_anchor accounts for 65.7% of skill mechanism labels, knowledge_injection for 4.5% (§5.1). Skills stabilise action (setup order, tool sequences, intermediate checks, known pitfalls) rather than supply missing facts. Under the taxonomy, skill arms land in the successful-procedure class in 61.7% of triples, raw in 59.1% and workflow in 55.7%. skill_guided_success is 61.6% of skill-arm labels and workflow_guided_success 54.5% of workflow-arm labels, so workflow memory also guides: raw traces "often contain reusable commands, parameter choices, and debugging evidence". It just keeps more incidental process, failed attempts and task-specific detail.

Skills are "compressed" experience. Per task, which representation used more input tokens?

Per-task averages on the 83 tasks where all three arms have usable token data, equal task weighting (Table 13).

Skill runs used 511.7K input tokens per task against 417.9K for Workflow Memory (+93.8K, about 22% more) and 541.5K for the Raw row. Its success was 69.6% against 64.8% and 64.1%. The paper calls Skill "the more effective representation and Workflow Memory the more token-efficient one" (Appendix A.9). The extra tokens come from the run, not from the artifact: the skill is read from the environment, and skill runs then do more work. The Raw row of this table is described as "full prior traces", which contradicts Raw's definition everywhere else (no prior experience); see How much to believe.

Result 2: what skills fix, and the failure they add

§5.2, §5.3, Table 11, Figure 2

The taxonomy splits the 528 triples by failure mode. Tap a group to see its modes; counts are out of 528 per arm.

Table 11 percentages; the counts are this page's decoding of Figure 2's vector bars, which match all 36 cells of Table 11.

Execution-layer failures fall (§5.2). SC2 modes are 37.3% of raw labels, 33.3% of workflow labels and 23.5% of skill labels (197, 176 and 124 of 528). The clearest:

  • environment_infrastructure_failure: 5.3% raw, 1.7% workflow, 0.2% skill. "Environment and tooling problems are highly skillable": once a reliable setup sequence, dependency workaround or path convention is found, it can be written down.
  • output_format_schema_mismatch: 7.4% to 3.2%.
  • background_service_lifecycle_failure: 2.7% to 0.8%.
  • shell_code_corruption: 1.1% to 0.2%.

These failures arise when the agent fails to keep concrete constraints active, not from missing high-level reasoning.

Reasoning failures do not. algorithmic_logic_error stays at 8.3%, 11.0% and 7.4%; static_verification_without_runtime at 12.5%, 12.5% and 11.7%. Skills do not repair a wrong algorithm or force runtime checking against the oracle.

A new failure surface (§5.3). skill_guidance_misapplied_or_ignored is 10.0% of skill-arm labels against 0.8% raw and 0.4% workflow. The skill is present and plausible, but the agent applies it mechanically, misses a condition, or carries over assumptions that no longer hold. "A skill is not self-executing": the agent still has to decide whether it applies, which parts to follow, how to adapt it and when to drop it.

Workflow memory fails by overload. timeout_budget_exhaustion is 10.6% of workflow runs, against 4.4% with skills and 1.7% raw. Verbose traces carry failed branches and debugging noise that distract from the decisive procedure. So skill use is a pipeline: experience must be distilled at the right level, retrieved for a compatible context, invoked, and adapted.

Result 3: outcome labels matter once failures enter; transfer works

§5.4, Figures 4 and 5, Table 16

Outcome labels (§5.4). The no-hint skill creator sees the same five trajectories but not which succeeded. Pick a setup:

Table 16 (the "normal" rows equal Table 1's Skill column); dashed line: that setup's Raw. Bars: ±1.96 binomial standard errors at the recovered trial counts.

The paper's summary: withholding labels "has little effect when the source pool contains only successful trajectories, but its impact grows sharply once failed trajectories are introduced". The headline case is Gemini on Terminal-Bench-2 at 3s2f, 0.7462 with labels against 0.4000 without, and the same ordering holds for every completed Gemini Terminal-Bench-2 and SkillsBench mixture. Labels guide what the distillation keeps. Two qualifications from the same table:

  • At 5s0f the effect is not small for Gemini: 0.7923 against 0.4231 on Terminal-Bench-2 and 0.7429 against 0.6190 on SkillsBench. Codex fits the summary.
  • On Terminal-Bench-Pro the no-hint skill is better in four cells: Codex at 5s0f (0.8364 against 0.7455) and Gemini at 3s2f, 2s3f and 0s5f. The summary's careful wording leaves Terminal-Bench-Pro out.

Mostly-failure pools make poor skills. At 0s5f the Skill arm falls below Raw in all six setups of Table 1, and Workflow Memory in four.

Transfer (RQ3, Figure 4). Skills distilled from Codex trajectories improve Gemini CLI over its own Raw baseline (56%) in every mixture and beat transferred Workflow Memory, so distillation is "the more portable representation" (§3.3). The paper gives no numbers in the text; the figure's printed labels are below.

Values are Figure 4's printed labels (the bar tops decoded from the vector figure agree). The figure does not say which benchmark or how many trials. All 13 values are even whole percentages, which 50 trials (10 tasks × 5) would force; the error bars assume that and are labelled derived.

Result 4: finding the skill and using it are different things

§5.5, Figure 3, Table 4
The pool grows from 5 to 100 candidate skills. What happens to downstream task success in Arm 3?

Averages over the random, similar and dissimilar pools (Table 4); Arms 2 and 3 also average the two agents (Figure 3).

As pools grow from 5 to 100 (§5.5):

  • embedding top-1 precision falls from 88.3% to 76.9%, and explicit agent selection from 70.0% to 63.7%;
  • parsed actual-use precision collapses from 29.6% to 3.3%: Gemini from 16.9% to 0.7%, Codex from 42.3% to 5.9%;
  • yet success moves from 36.4% to 39.3%: Gemini stays around 36 to 39%, Codex rises from 35.4% to 42.0%.

Arm 3 recall stays at 54.3% to 73.6% at k = 100 while precision is 0.7% to 8.1%. Agents inspect or invoke several candidates without restricting themselves to the annotated skill. Hence "exact ground-truth invocation is neither sufficient nor necessary": agents succeed with related non-ground-truth skills and fail with the right one in hand.

Confusable distractors are the main stressor for the offline arms. Embedding top-1 on similar pools falls from 70.5% at k = 5 to 53.4% at k = 100, against 97.7% to 84.1% for random and 96.6% to 93.2% for dissimilar pools. Agent selection on similar pools is 54.3% (Gemini) and 51.9% (Codex) at k = 5, and 55.4% and 31.9% at k = 100. Selection recall at k = 100 stays at 70.5% to 85.2%: agents tend to pick the right skill together with distractors rather than miss it (Table 15).

What the precision collapse measures. Two facts in the paper's own tables, derived on this page:

  • Every SkillsBench task here has exactly one ground-truth skill: in all 27 cells of Table 14, top-3 precision is recall ÷ 3 and top-5 precision is recall ÷ 5.
  • With one gold skill, a run that touches m skills and finds the gold one has precision 1/m. Gemini's Arm 3 precision tracks recall ÷ k at every pool size (at k = 100, 0.7% against 66.0 ÷ 100). Recall ÷ precision suggests Gemini touches about 88 to 95 of 100 skills, Codex about 8 to 22.

So for Gemini the "collapse" mostly counts how many skills it opens or lists, not how well it discriminates. The retrieval explorer overlays that "opens everything" line.

How much of this to believe

Tables 1, 9 to 16, Figures 2 and 4

What holds up.

  • The control is the right one. Workflow Memory and Skill are built from the same five trajectories per task and mixture, so the comparison isolates packaging. Few skill papers do this.
  • Skill beats Workflow Memory in most of the full data. In Table 1, Skill wins . The biggest gaps are many standard errors wide (Codex Terminal-Bench-2, Gemini Terminal-Bench-2 and SkillsBench).
  • The failure-mode shifts are large where it matters. skill_guidance_misapplied_or_ignored at 53 of 528 against 4 is far beyond judge noise, as is environment failures at 28 against 1.
  • The numbers check. This page reproduces Tables 9 to 11, the SC totals, the §5.5 averages and Table 4 from Tables 14 and 15 (44 of 45 cells exactly, one 0.1 off), and decodes Figure 2 to counts that match Table 11 in all 36 cells (checks).
  • The authors state limits themselves (§7): terminal and tool benchmarks only, few agent and model configurations, and a taxonomy induced from a sample of about 3% of records. The appendix adds that the triple labels are LLM-assisted, not exhaustively human-coded, and that one trial per arm is used. That counts in their favour.

What to discount.

  • The +6.06 rests on one trial per arm on 88 Codex tasks, and its interval treats correlated triples as independent. The triple counts per benchmark (144, 186, 198) are six times Codex's task counts (24, 31, 33), not Gemini's, and the judge prompt names transcripts codex.txt; so the taxonomy and the +6.06 are Codex + GPT-5.3-Codex only. Each task contributes six triples, one per mixture. The Raw run is literally the same trajectory in all six: Raw succeeds on 52 of 88 tasks in every mixture of Figure 2, and 312 = 6 × 52. The bootstrap resamples the 528 triples as if they were independent. Move the slider to let a task's six paired differences be correlated:

    Derived: the interval's standard error is about 0.027 (normal approximation), and a design effect of 1 + 5ρ for clusters of six puts the lower bound at zero from ρ ≈ 0.06. The six per-mixture differences are +6, +10, +1, +9, +11 and −5 tasks of 88.
  • The result changes sign across setups. Gemini on Terminal-Bench-Pro favours Workflow Memory in five of six mixtures, and Codex on Terminal-Bench-Pro is a tie. One trial per cell and no seeds; Table 1 has no error bars.
  • One LLM judge, with visible noise. Every mode and mechanism label comes from Claude Sonnet 4.6. The human check validates the label vocabulary (238 labels), not the 1,584 paired assignments. Two signs of noise come from the paper's own Figure 2:
    • The same 88 raw trajectories, judged six times beside different companions, get different label mixes: at least of 88 change label between two mixtures.
    • The judge calls raw runs per mixture "skill-guided success" (55 of 528, 10.4%), though Raw had no skill.
    Differences of a few points between modes (algorithmic errors 8.3 against 7.4) are within that noise.
  • Procedural anchoring is not what separates skills from memory. A commented-out draft paragraph in the arXiv source reports anchoring for 72% of workflow effects and 66% of skill effects, with workflow carrying 12% counterproductive attributions. The published text reports only the skill share. Both representations anchor; the difference is noise and overload. (From the LaTeX source, not the published text.)
  • Retrieval: the metric and the missing control. Arm 3 precision mostly measures how many skills an agent touches (see Result 4). Arm 3 never runs without skills or with only the gold skill, so "success stays flat" cannot tell whether skills help at all at any pool size. The Codex pairing also changed model (GPT-5.4), which the authors flag.
  • Small or unstated samples. Figure 4's transfer result gives no benchmark or trial count; its values fit 50 trials, where one standard error is about 7 points. The compact baselines use 26 tasks and were compared at skills' best mixture. Table 1's caption says Terminal-Bench-Pro uses 130 trials per condition; Codex's cells fit 165.
  • Inconsistencies.
    • Table 13 calls Raw "full prior traces".
    • Retrieval uses 88 queries (every top-1 value is k/88), though the text says SkillsBench has 86 tasks; SkillsBench itself now lists 87.
    • Table 7's skill-arm trials and failed trials are both 3,594; both rows add up to 8,135, so either could be right.
    • The LaTeX source shows the study was redesigned: a Claude Code pairing ("not presented in this version"), a 241-task retrieval study with Qwen3.6 and a cross-task transfer RQ were dropped.
    None of these changes a conclusion's direction.

Verdict. Believe the direction and the qualitative failure modes. Distilled skills usually beat the same experience pasted in as traces, mainly by cutting setup, format and service mistakes and avoiding trace overload, and they add a real misapplication failure. Treat "+6.06 points" and the mechanism percentages as one judge's labels on one trial per arm for one agent: the interval would not survive modest clustering, and one setup reverses. On retrieval, believe that confusable near-duplicates hurt offline identification; do not read the precision collapse as evidence that retrieval does not matter.

What it takes to use this

  • Code: none released. The appendix mentions "released artifacts" without an address (checked 3 October 2026). The skill-creator prompts (Appendix B) are printed in full and are the reusable part.
  • Format and tooling: SKILL.md folders as in anthropics/skills; Agent Skills became an open standard on 18 December 2025 (Anthropic). Evaluation used Harbor on public benchmarks.
  • Budget: Skill runs averaged 521.5K tokens per task, 95.3K more than Workflow Memory but 34.2K fewer than the Raw row (Table 13). Building a skill needs five prior runs of the task plus one creator call.
  • Where it paid off: repeated execution-layer trouble (environment setup, output formats, background services), and Codex on Terminal-Bench-2, where raw traces actively hurt.
  • Where it bought little or hurt:
    • tasks needing a different algorithm or real runtime verification;
    • skills distilled from mostly failed runs (below Raw in all six setups at 0s5f);
    • Gemini on Terminal-Bench-Pro.
  • Practical reading (the paper's implications, as the old page put them):
    • write skills as procedural anchors (setup sequences, checklists, verification steps, pitfalls), not fact sheets;
    • distil rather than paste raw session transcripts into memory, since verbose traces measurably cause timeouts;
    • keep success and failure labels attached when generating skills from mixed experience;
    • expect skills to transfer across harnesses;
    • worry less about perfect retrieval than about confusable near-duplicate skills in the library and about the agent's judgment in applying a retrieved skill.

Why it matters beyond the paper

It is the first mechanistic account of why the SKILL.md pattern works, and it bears directly on how to write and manage skills for harnesses like Claude Code (practical points above). It also reframes evaluation for self-evolving agents: aggregate pass rates hide that skills trade execution-layer failures for a new class of misapplication failures. Skill pipelines need lifecycle-level evaluation (generate, retrieve, invoke, adapt), not only end-to-end success (§6).

The outside evidence points the same way:

  • SkillsBench's own paired evaluation (87 tasks, 18 model and harness configurations) finds curated skills raise the average pass rate from 33.9% to 50.5%. Focused skills with at most three modules beat larger bundles.
  • SWE-Skills-Bench finds 39 of 49 public skills give no gain on real repositories (+1.2% on average). Three hurt "due to version-mismatched guidance conflicting with project context": the misapplication mode, seen from outside.

The validated LLM-judge taxonomy pipeline (open coding, batched induction, a human check of grounding and aggregation, paired comparisons) is a reusable pattern for agent evaluation. Its weak spot, the per-trajectory labels themselves, is the part this page could test.

Schedule the checkout yourself

The checkout endpoint needs three services: user (400 ms), config (600 ms) and profile (300 ms), and profile needs the user's id (server.ts). The verifier wants the request under 800 ms and at least 400 ms, "Checkout calls user(400ms), config(600ms), profile(300ms) - even optimized takes 600ms+" (test_outputs.py). Choose when config and profile start, or pick one of the arms' schedules.

The model adds the service delays along the schedule's critical path and nothing else; the measured times (the paper's 915 ms for the workflow patch and a warm average of 711.6 ms for the skill patch) add about 12 to 15 ms of request and framework overhead. The task's reference solution uses the skill's schedule (solve.sh). The shortest possible time is the longer of user then profile (700 ms) and config (600 ms).
