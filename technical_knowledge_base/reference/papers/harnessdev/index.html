HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

Yuhao Wu, Jingyuan Zhang, Jiajun Shi, Xinping Lei, Qingshui Gu, Yuxuan Zhang, Zexuan Wang, Chen He, Chen Huang, Maojia Song, Zhiyuan Zeng, Shaowen Wang, Jinkai Liu, Yunfeng Shi, Jiaheng Liu, Shen Yan, Wenhao Huang, Ge Zhang, Wenxuan Zhang
ByteDance Seed, Singapore University of Technology and Design, Georgia Institute of Technology, M-A-P, TokenWave.AI (core contributors Yuhao Wu, Jingyuan Zhang, Jiajun Shi) · 1 September 2026 (arXiv v1, the only version so far)

In one line: Moves evaluation from task performance to infrastructure construction: Creation (build an execution system from minimal components and sample cases) then Evolution (refine it from feedback), across six creator LLMs, four domains, five downstream benchmarks and 2,207 instances, scored on capability and execution-token cost; generated harnesses lag mature human references on code and search but match or beat them on writing and ML experimentation, while evolution gains are unstable, transfer poorly, and stay strongly dependent on which model executes the harness.

Problem

§1 Introduction

An agent harness is the software around a model that turns its outputs into actions: the execution loop, the tools, what goes into the context, saved state, failure recovery and checking the result (§1). It moves scores a lot. With identical weights, GPT-5 solves 35.2% of Terminal-Bench 2.1 inside the Terminus 2 harness and 49.6% inside Codex CLI, 14.4 points apart (§1, citing the Terminal-Bench 2.1 leaderboard).

The month before this paper produced several harness-scaling results, each showing that the wrapper moves benchmark scores by tens of points on the same weights: Prime Agent, StateM, JIT-Agent and WikiSkill. All of them judge a harness by the task score it produces. Benchmarks such as SWE-bench, GAIA, WebArena, τ-bench and AgentBench do the same: they fix a harness and report model performance under it (§5). That leaves the obvious next question unasked: can a model build the harness itself, and keep improving it, and how does what it builds compare with something a team spent a year on? Task score alone cannot answer that, because a good score mixes up the harness with the model running inside it.

The authors argue harness work differs from ordinary code editing: a model editing its own harness changes how it will observe, plan and recover in every future task, so it must read its own failures from traces and make changes that last (§1). They frame it through the forward-deployed engineer, who turns a general model into a system that works on one customer's data; of that job's three layers (vague target, missing feedback signal, missing execution system) this paper takes the third (§2).

Idea: score the harness, not the answer

§3.1, Eq. 1

HarnessDev makes the runnable harness the thing being evaluated. A creator model LC works inside a development environment D (Claude Code, or Codex for GPT-5.5) and produces a harness H. H is then frozen. Only after that does an executor model LE run inside it on downstream tasks, and an evaluator J scores the outputs (Eq. 1):

(LC, D) → H     (H, LE, x) → y → J → score

Keeping the builder and the runner apart is the point: it lets the same harness be run by different models, so harness quality can be separated from executor ability. Toggle the three comparisons the paper makes:

Two stages follow the software sense of "develop" (§3.1):

  • Creation (RQ1): can a model build an effective harness from a weak but runnable seed, given a task specification and a few development cases?
  • Evolution (RQ2): can it improve its own existing harness from downstream execution feedback while keeping what already works?

Every harness is scored on two axes (§3.5): capability, task success on held-out benchmarks under each benchmark's native metric, and efficiency, the executor tokens the frozen harness consumes (total and mean per task). Tokens the creator spends building the harness are not counted. Reporting both stops a harness from winning by brute force.

Method: the seed, the six modules, the protocol

§3.2, Table 1, Figures 2 and 3, Appendix C

The weak seed. Every creator starts from the same seed Hseed, "a runnable compatibility layer, not a task-solving agent" (§3.2). It parses the task and model configuration, exposes passive primitives (paths, files, search, process, an LLM gateway) and writes the audit files result.json, trajectory.jsonl and response.md (Appendix C.1). It has no agent loop, task decomposition, tool policy, context management, persistent state, verifier, retry or recovery logic, or stopping rule; after one optional connectivity probe it stops with status partial and scores zero on all five benchmarks (Table 3). So any score comes from logic the creator added, without the creator having to fight command-line and file-format setup, and without a mature agent giving the answer away.

What the creator must build. The prompt defines a harness as H = ⟨E, T, C, S, L, V⟩ (Appendix E.1; interface in Appendix C): Execution loop (planning, stop conditions), Tools (interfaces, selection, error handling), Context (what enters the prompt, compression), State (goals, hypotheses, attempts, checkpoints), Lifecycle (hooks, failure and timeout handling, recovery, finalisation) and Verification (tests, checks, artifact validation). Files need not carry these names; the system must actually perform the jobs. Toggle what the seed provides against what the 18 created code harnesses ended up with:

The rules a submitted harness must follow, and how they are enforced

The shared creation prompt (Appendix E.1) requires three command-line forms (python -m harness run --task-json ... --model-config ... --output-dir ... and two variants, with aliases such as -p/--prompt), an honest status of success, partial or failed, and model calls only through the provided provider-neutral configuration (no hard-coded model names, base URLs, keys or provider SDKs). It forbids hard-coding task IDs, answers, expected patches or scorer internals, leaving TODO or NotImplementedError placeholders, decorative modules that never run, and degrading the agent into one LLM call or a template filler. Telemetry such as lines of code and module counts is recorded but is "not a scoring target".

Two properties make the rules checkable (§3.4). The score path is isolated: a harness's self-reported status never counts, SWE-Pro credit comes only from the real repository diff, and Terminal-Bench credit only from the final environment state. And every run keeps its trajectory, result and metric files beside the frozen source, so the code and what it executed can be audited afterwards. The authors audited every run reported and found no harness scoring through a prohibited route; no run was excluded. In Evolution a violation would set that version's score to 0 (Appendix E.2).

Creation protocol (§3.2, Table 1). Along with the seed the creator gets a task-family specification, tool and permission constraints, a short design tutorial and one to three development cases. It may revise the harness using feedback from those cases, but never sees the human implementation or the hidden evaluation set; the harness is frozen before evaluation. Each creator builds three harnesses independently per benchmark and the score is avg@3 (§4.1).

Six creators, five benchmarks, four domains (§4.1, Table 2): Opus 4.8, GPT-5.5, Gemini 3.1 Pro, DeepSeek V4 Pro, Qwen 3.7 Max and Seed 2.0 Pro, at high reasoning effort, working in Claude Code 2.1.177 (GPT-5.5 in Codex 0.144.3). Code: SWE-bench Pro public split (731 tasks) and Terminal-Bench 2.1 (89); data analysis: MLE-bench (75, medal score); writing: EQ-Bench3 (46, rubric score); research: BrowseComp (1,266, accuracy). That is 2,207 unique instances, hidden from development.

Evolution protocol (§3.2, Appendix E.2), code only. The creator starts from its own Creation harness H0 in a git repository. A version becomes official only as a pair of full evaluations of one commit: a fixed 100-task SWE-Pro feedback set and all 89 Terminal-Bench tasks, one to two hours each. The budget is ten pairs, with at most two five-task probes between pairs that never count. The creator sees the pair mean P̄t = ½ (SWE-100 + Terminal-89) in percent (Eq. 2) and ends by declaring a final version other than H0. After all runs end, every official version is scored on 630 held-out SWE-Pro tasks from the same public split, disjoint from the 100 and never shown to the creator. Five creators run in their own runtime; four rerun with Gemini 3.1 Pro as the fixed runtime: nine lineages.

Result 1: Creation, and the distance to human references

§4.2, Tables 3 and 4, Figure 4

Every creator turned the zero-scoring seed into something that works, and quality varied sharply by task family. Under Self-Eval Opus 4.8 has the best average, 67.8, against 86.2 for the human-engineered references (Table 3). Both averages are over SWE-Pro, Terminal-Bench, EQ-Bench3 and BrowseComp only; MLE-bench is left out of the Avg. column (this page recomputes every average in Tables 3 and 4 from its row: all 13 match).

The paper's summary of this chart: generated harnesses match the reference on short-form writing (EQ-Bench3), exceed it on machine-learning experimentation (MLE-bench), stay substantially behind on code, and are furthest behind on search and research (BrowseComp), which needs long-horizon information seeking (§1, §4.2). Opus 4.8 and Gemini 3.1 Pro lead MLE-bench with medal rates of 32.9 and 32.4 against the reference's 24.0.

Two things the chart shows that the summary does not:

  • "Match" and "exceed" are about the best creators. On EQ-Bench3 Opus (84.6) and GPT-5.5 (83.0) are at or above the reference's 83.7; the other four score 68.7 to 75.4. On MLE-bench two creators beat 24.0; the other four score 3.1 to 19.6.
  • The references did not run the same models. The writing reference (Kimi Writer) ran Opus 4.8, the same model as the best creator, and the MLE-bench reference (MLEvolve) ran Gemini 3.1. The code and search references ran Claude Fable 5 and GPT-5.6 Sol, newer models than any creator (Appendix B.2). The paper says plainly that the references "are not paired controls under a common executor" and the figure "only shows the distance to the selected mature systems" (Figure 4 caption). So where generated harnesses "lose", part of the gap is the model. See How much to believe.

Single harnesses are not representative (§4.2), hence avg@3. One Opus code harness nearly collapsed under Gemini because it hard-coded a 120-step limit around its original executor; strict stopping rules did similar damage in Data. Table 4 marks three code cells containing one collapsed replica: without it, Opus on SWE-Pro is 49.1 instead of 33.0, and DeepSeek 43.8 and 57.3 instead of 29.2 and 38.2 (Table 4). GPT-5.5's EQ-Bench3 cell (46.5) includes a first harness that scored zero; without it, 69.7.

Cost is uneven, and paying more does not buy more. MLE-bench executor tokens vary about nineteen-fold between creators' harnesses (557.1M for Seed 2.0 Pro against 29.3M for GPT-5.5; 557.1 / 29.3 = 19.0). GPT-5.5's harness reaches a medal rate of 19.1 with 29.3M tokens while DeepSeek V4's reaches 19.6 with 208.4M (Figure 9). The paper reports the trade-off directly rather than folding it into one cost-adjusted score; the tables tab has the scatter.

Result 2: a harness is tuned to the model that runs it

§4.2, Figure 6

Fixing the executor to Gemini 3.1 Pro changes the ranking (§4.2). Qwen, Seed and DeepSeek improve in several Data and Search settings under Gemini, so their own models were the bottleneck: Qwen gains 17.6 points on BrowseComp and 12.9 on MLE-bench. Opus and GPT-5.5 are usually stronger with their own executors. Opus's SWE-Pro harness falls from 69.3 to 33.0 and its writing harness from 84.6 to 74.2. In the Opus search harness the duplicate-query rate rises from 10.1% to 88.2% once Gemini runs it: its deduplication, review and stopping rules were fitted to Opus. Pick a benchmark:

Filled dot: Self-Eval (the creator runs its own harness). Ring: the same three harnesses run by Gemini 3.1 Pro. Gemini's own harness is the control, so its two marks coincide. Dashed line: the human reference. Values from Tables 3 and 4; the paper's Figure 6.

The conclusion the paper draws: a runnable harness can be used by another model, but capability transfers only when its prompts, tool protocol, budgets and stopping rules stay compatible. Self-Eval therefore measures harness design, executor capability and the fit between them at once, and a harness cannot be scored in isolation from the model that runs it. Note that the fixed executor is also one of the creators: under Unified-Eval Gemini runs its own co-adapted harness and everyone else's foreign one.

Result 3: what is inside the generated harnesses

§4.2, Table 5, Figure 5

Strategies differ. Opus often rewrites the execution stack; GPT-5.5 adds one large monolithic agent; DeepSeek, Qwen and Seed extend the seed with agent, tool, context and state modules; Gemini mostly edits the runner in place (§4.2). The 18 code artifacts add 17,111 net lines between them (Table 5), and size does not predict performance: Gemini adds the fewest (1,006 lines over three harnesses, median 324) yet has the best Terminal-Bench score (68.8), which the authors read as "focused changes and frequent verification matter more than code volume".

Which modules exist. All 18 code harnesses implement an explicit execution loop; tools, lifecycle control and verification are complete in 13, 13 and 15 of 18 (Figure 5). State and memory are the clearest gap: 11 of 18 define a State class, but only one exposes a state-saving interface and only one checkpoints periodically, and no checkpoint event appears in 26,679 recorded task trajectories. Validation is mostly syntactic: 441 of 2,325 executed Data tasks (19.0%) produce degenerate submissions that no harness detects, and 77.8% of failed Data tasks are attributed to harness defects rather than the executor.

Dead code. Of 108 component instances in the code harnesses, 72 trigger in real runs, 18 have only partial evidence and 18 are never observed, all of the unobserved ones state and memory. Beyond code, 124 of 587 writing features are confirmed dead code and 36 Data mechanisms sit on dead paths; small implementation errors can disable a whole tool chain.

Testing helps only when it changes something. The number of self-tests a creator ran has a Spearman correlation of only 0.13 to 0.26 with the downstream score (not significant), while the number of revision calls reaches 0.57 (p ≤ .0005). "Testing helps when the creator reads the failure, makes a targeted change, and re-verifies it." The two creation trajectories in the appendices show the contrast: GPT-5.5 turned every failed development run into a targeted fix, while Opus designed ten modules up front and made no harness change after two zero scores (both are laid out side by side in the replay tab).

Result 4: Evolution, and what the creator could not see

§4.3, Tables 6 and 7, Figures 7 and 8

The nine lineages produced 73 official versions and 64 adjacent version switches (§4.3). All five self-runtime creators improved their visible feedback pair, by +3.0 (Opus) to +13.9 (Qwen) points. On the 630 held-out tasks the same declared versions improved by only +1.43 to +4.44, mean +3.11; Opus had the largest held-out gain. Under the fixed Gemini runtime only Opus improved on held-out tasks; Qwen, DeepSeek and GPT-5.5 regressed, GPT-5.5 by 10.32 points (Table 6).

Grey band: ±4.75 pair points, how much the same commit's pair score varies between runs (§4.3); a visible gain inside it cannot be told apart from re-running H0. The held-out gains are on a different set (630 SWE-Pro tasks), whose own run-to-run noise the paper does not report. Values from Table 6, all reproduced from the decoded figures.

Stability. Evolution is not monotonic (§4.3). Of the 64 switches, 8 regress on both benchmarks, 16 on one, 3 trade one benchmark for the other, 7 change nothing measurable, 27 report gains inside the repeated-run noise band, 2 show clear positive evidence beyond the noise, and 1 contains no executable code change. Only 2 of the 9 declared versions are the best held-out version. Creators usually declare a version near their best visible score (in 7 of 9 lineages exactly the best, by this page's recount), but "repeatedly optimizing a noisy score can favor a lucky run and amplify overfitting". The Replay the evolution runs tab steps through every lineage version by version, with the held-out line hidden until you ask for it.

What the edits were. The median declared version changes 8 files, adding 476 lines and deleting 38 (Table 7). Of the 64 switches, 58 change execution or control flow, 37 tools, 17 lifecycle recovery, 16 context and only 4 state; none modifies a standalone verifier. Edit size does not predict improvement, and deletion can help as much as addition (DeepSeek rolled back much of a fixed-Gemini rewrite after context compression broke tool-message pairing). Of 169 new functions or classes, 113 are reachable, 31 only through dead code and 25 have no caller. Opus's completion gate is the positive example; Qwen's message sanitizer, which broke valid Gemini tool-result sequences, the negative one.

Diagnosis is the weakest step. Eight of nine lineages complete at least one loop of reading results, editing, re-evaluating and selecting, but the dedicated trajectory interface was called only twice in all nine, and inspected cases cover just 0.5% to 40.2% of the 189 feedback tasks. Creators leaned on their own scripts and the five-task probes, which can mislead: one GPT-5.5 candidate passed all five Terminal probes and scored 0.584 on the full set. The clearest positive case: Opus found that 99 of 100 runs reported success while only 48 passed, traced it to premature completion and added a completion check.

The runtime binding matters most. Changing only the executor moves the starting score H0 and changes which edits help (§6). Qwen's self lineage starts at a feedback pair of 41.8; the same creator under Gemini starts at 62.1 and gains only +1.1.

How much of this to believe

§6.1 Limitations

What holds up.

  • The protocol is careful. Builder and runner are separated, harnesses are frozen before evaluation, the score path ignores what a harness says about itself, and every run was audited (§3.4). Creation cells are avg@3 over independently built harnesses.
  • The numbers agree with each other. All 83 cross-checks this page found match (Tables 2 to 7, appendix trajectories, text), including the 34 of 64 and the 2 of 9 recounted from the vector Figures 7 and 8, where every decoded point lands on a whole number of tasks (checks).
  • Noise cannot manufacture the Evolution gap. Selection inflates the visible gains (each creator picked near the best of up to eleven noisy scores), so the gap between visible and held-out gains is if anything real.
  • The authors state most limitations themselves (§6.1): uneven, non-optimal human baselines; Unified-Eval only reduces executor differences; one trajectory per Evolution cell, so no uncertainty estimates; held-out evaluation on SWE-Pro only. That counts in their favour, as does their own model, Seed 2.0 Pro, coming last.

What is weaker than the summary suggests.

  • The domain split is confounded with the executor. The references generated harnesses lose to ran Claude Fable 5 (SWE-Pro) and GPT-5.6 Sol (Terminal-Bench, BrowseComp), newer than every creator; the two they match or beat ran Opus 4.8 (EQ-Bench3, the best creator's own model) and Gemini 3.1 (MLE-bench) (Table 9). Three of the five reference numbers come from OpenAI's GPT-5.6 release report and were not re-run (Appendix B.2). The paper warns the references are not paired controls; its summary sentences read as if they were.
  • "Match" and "beat" describe the best one or two creators (Result 1). Leaving MLE-bench out of the Avg. column also widens the headline gap: with it, Opus averages 60.8 against 73.7, a gap of 12.9 rather than 18.4 (this page's recomputation).
  • Every Evolution lineage is a single run. One commit varies by about ±4.75 pair points, and three of nine visible gains (Opus self +3.0, Qwen fixed +1.1, GPT-5.5 fixed +2.4) sit inside it. A 630-task score near 50% has a binomial standard error of about 2.0 points, so a difference of two independent runs about 2.8 (this page's estimate; shared tasks make it smaller by an unreported amount). Each self-runtime held-out gain is 0.5 to 1.6 of those units; that all five are positive is stronger (one in 32 if each sign were a coin flip). The fixed-Gemini GPT-5.5 drop of 10.32, 3.7 units, is clearly real.
  • "Held-out" is the same distribution: the 630 tasks come from the same SWE-Pro split as the 100 feedback tasks, and Terminal-Bench has no held-out set. The result is about overfitting within one code benchmark, not transfer to new kinds of task.
  • The fixed executor is also a contestant: under Unified-Eval Gemini runs its own co-adapted harness and the others' foreign ones.
  • Two examples are not tied to a lineage in the text. The "99 of 100 report success, 48 pass" case is the fixed-Gemini Opus lineage (its H0 is 48 of 100; the self-runtime Opus started at 68, Appendix I), and the GPT-5.5 candidate at 0.584 is the fixed-Gemini lineage's version 8 (52 of 89); both identifications are this page's, from the decoded figures.

Verdict. Believe the instrument and the Evolution warning: a creator's visible score is a poor guide to held-out quality (34 of 64 switches agree, 2 of 9 declarations are held-out optimal), and changing the executor can undo a harness. Believe that current models can build working harnesses from a bare seed. Treat the domain ranking (writing and ML level, code and search far behind) as unproven until the references are re-run with the creators' own models, and treat each individual Evolution gain as one noisy run.

What it takes to use this

Appendices B and E
  • Code and data. Nothing is released yet. The seed implementation, the audit script and the held-out splits "will be released with the benchmark" (Appendix C); the project page has results, no code. The prompts in Appendix E are complete enough to reuse as a creation or evolution brief today.
  • Compute. Per MLE-bench task: one A800 80 GB GPU, 14 vCPUs, 227 GiB of RAM, 36,000 s (34,200 for the harness, 1,800 for the grader) and 500 steps; per code task: 500 steps and 7,200 s (Appendix B.1). A lineage spends up to eleven pairs of 189 tasks at one to two hours each; the held-out scoring alone was 73 versions × 630 tasks = 45,990 task runs (derived).
  • What worked for the creators, and transfers to anyone building a harness with a model:
    • Gate "finish" on evidence. Opus's completion gate and GPT-5.5's final-review gate (+8 SWE tasks and +8 Terminal tasks in one switch, Appendix H) are the clearest wins.
    • Do not hard-code step, output or time limits fitted to one model, and test the harness with a second executor before trusting it.
    • Choose the final version on a set the edits never saw, and estimate run-to-run noise by re-running the best candidate before believing a gain under about five points.
    • Treat five-task probes as crash checks: one task moves a probe leg by 20 points (Appendix E.2).
    • Track files that shell commands create, not only those written through the edit tool (GPT-5.5's T5, Opus's T3).
    • Keep a ledger file of every evaluation; both appendix creators did, and Opus used it to stop at 3 of 10 pairs.
  • When it pays. On this paper's evidence, model-built harnesses are worth trying where general agent structure is most of the harness (writing, ML experiment loops), and a mature human harness is the safer choice for code and long-horizon search, subject to the executor caveat above.

Why it matters (beyond the paper)

Three things, from the first summary, each with what the full paper changes.

  • A measuring instrument for the construction step. The harness-scaling line had produced four competing strategies (Prime Agent, StateM, JIT-Agent, WikiSkill) and no way to compare how harnesses get built. HarnessDev supplies one, with the creator separated from the executor. The project page presents it as the third of three benchmarks on "closed-loop" self-improvement, beside Aspire (turning a vague goal into a target) and S3Gym (learning from one's own experience) (project page).
  • The domain split as a diagnosis. The first summary read the split as: human references win where the harness encodes years of domain tooling (code, search), and generated harnesses compete where general agent structure is most of what a harness is. That predicts where hand-built harnesses keep their advantage. The harness architecture playbook filed on Topic: agentic-harnesses on 2026-09-07 is the human-written counterpart and offers one mechanism: unavoidable complexity belongs in a harness's core abstractions rather than in extensions, which is one hypothesis for why generated harnesses lag where domain tooling runs deepest. The full paper weakens the diagnosis: the losing domains are also the ones whose references ran stronger models, so the split is a hypothesis, not a finding.
  • A check on self-improving harnesses. Prime Agent's Continual Harness versions its own prompts and skills across trajectories; this benchmark says such refinement does not reliably compound. The full paper sharpens it: self-runtime gains do survive on held-out tasks, but small (+3.11 on average against up to +13.9 visible), and under a different runtime most regress. Three weeks later RRSI reported the first regularised loop whose gains survive out of distribution (+4.7 points), and SoL-Pi pointed the same loop at cost, where a cheap verifier exists.

Connections

  • Prime Agent and JIT-Agent in Papers, and the harness-scaling section of Topic: agentic-harnesses: HarnessDev is the benchmark those two needed and did not have. JIT-Agent trains a 27B model to emit a harness per task and reports parity with production harnesses in a much poorer protocol language; HarnessDev measures a related gap with untrained frontier creators, and finds it depends on the domain, or on the reference's model (Result 1).
  • StateM: the opposite pole, a human-written state machine that constrains the agent on the same Terminal-Bench 2.1. HarnessDev's finding that generated harnesses lag most where domain tooling is deepest is consistent with StateM's win coming from encoded domain procedure, and its finding that state and memory are the module creators least often build (one of 18 saves state) is the part StateM supplies by hand.
  • Demystifying Agent Skills and Repo-To-Skill: skills are one of the components a harness assembles, and Repo-To-Skill is the supply side of the same problem.
  • Terminal-Universe: supplies the environments a harness-building model would need to practise in.
  • The 2026-09-07 ARC Prize result on Topic: benchmarks (GPT-6 Astra at 62.7% on the standard harness and 99.9% through a Provider Adapter that keeps opaque reasoning state, 2026-09-07 tech news): an existence proof that a provider-side harness can beat any harness a third party is able to construct, which bounds what HarnessDev's Creation phase can reach for models with opaque state.
  • Concurrent benchmarks (§5): the Meta-Agent Challenge (closest to Creation), HarnessOpt-Bench and Evo-Bench (closest to Evolution); links in Further reading.

Before Evolution: how two creators built their first harness

Creation trajectories for code, from the appendices: the same task, two styles. Neither got a settled SWE task right during development, which is normal with one to three development cases; what differs is how each used the feedback.

GPT-5.5 builds iteratively (Appendix F)
  • Read the seed 14 times before its first edit; 20 editing operations; read 109 feedback artifacts.
  • Replaced the one-shot runner with a JSON-action tool loop in one 1,245-line agent.py (seed to final: 12 paths, +1,251 / −4 lines).
  • Each failed dev run produced a fix: artifact bookkeeping for files outside git, a parser for several JSON actions in one turn, /bin/bash instead of /bin/sh, safe de-duplication of identical reads, a parser for Codex-style patch envelopes.
  • Final record: contract smoke 1, SWE 0, Terminal 1.
Opus 4.8 designs up front (Appendix G)
  • Read the seed 20 times; wrote 10 harness modules up front (seed to final: +1,252 / −596 lines, 1,876 lines in the end).
  • A native tool-calling ReAct loop with max_steps=120, a 6,600-second time budget and a 150,000-token soft context limit; repeated no-tool turns or an empty diff are reported as partial, not success.
  • Both settled benchmark runs scored zero (SWE 38 steps, Terminal 94 steps); Opus attributed them to the task solutions and made no harness change in response.
  • Final record: contract smoke 1, SWE 0, Terminal 0.

The 120-step limit in Opus's design is the same kind of executor-specific budget the paper blames for the Opus harness that collapsed under Gemini; the appendix does not say whether this is that harness.
