Problem

§1 Introduction

An agent harness is everything around the model that makes it an agent: what history is kept, how the next sub-goal is formed, which tools or skills are exposed, how actions run, and when to verify or recover (§1). The paper's premise is that "agent intelligence is not a property of model weights alone, but of the model–harness pair" (§1): a strong model behind the wrong memory or planner fails, and a strong harness only helps a model that can follow it.

Recent work therefore optimises harnesses: it edits harness code, prompts, tools, memories or skills from trajectories and feedback, and keeps what scores well (Meta-Harness, AHE and others; §1, §2). The paper calls this ahead-of-time (AOT): the harness is a durable artifact tuned on past tasks "with the hope that the resulting artifact will generalize" to future ones. That works when the task mix is stable. It is awkward when it is not, because different tasks want different harnesses: wide search wants parallel exploration, terminal work a lean serial loop, deep research a working memory over evidence, repository-scale coding a filesystem of patches and tests (§1). "The appropriate harness is not only domain-dependent, but instance-dependent."

The knowledge base's first summary put the same problem from the reader's side: every result in the harness-scaling literature is a hand-built artifact. Someone writes a state machine, a skill set or a subagent topology, tunes it against a benchmark and reports the lift, and that does not compose and does not transfer. The question becomes whether harness construction can be a learned, inference-time capability instead of a human craft.

So the paper asks for just-in-time (JIT) construction, which it calls Model-as-a-Harness: a trained meta-agent writes a harness for the task in front of it, and an unmodified agentic model runs inside it. It names the skill harness intelligence and gives it three properties (§1): adaptivity (match the harness to the task and backbone), reliability (produce something that executes, and recover when it does not) and evolvability (turn execution feedback into better future harnesses). "Intelligence about the harness begins where competence within a fixed harness ends."

A correction to the first summary

The old page said the paper's own ablation shows "no fixed harness dominates across tasks: ReAct wins some, Plan-and-Execute wins others, ReSum wins on long-horizon search". The paper has no such ablation. "No fixed harness dominates" is its reading of Table 3, where the five fixed harnesses are Claude Code, Codex, OpenCode, Hermes and NanoBot, and the leader among them changes with the backbone and benchmark (NanoBot on four settings, Claude Code on two). ReAct, Plan-and-Execute and ReSum appear only as seed harnesses (Table 1), and ReAct as the baseline of Figure 4; their scores against each other are never reported.

Idea: one protocol, four modules, written per task

§3.1, Eq. 1 to 3

Writing a whole agent from scratch for every task would be unreliable, so the paper constrains what the meta-agent may write. Every harness is a tuple of four modules under a fixed protocol Π (Eq. 2):

h = (M, P, A, F)

  • M Memory: turns the event history into the view the model sees (history → view).
  • P Planning: forms a local directive or sub-goal from that view (view → directive). A harness with no planner returns a null directive, so it still fits.
  • F Capability orchestration: picks which tools, APIs, MCP servers and skills are exposed at this step.
  • A Action: the control loop; updates the controller state and emits the next action, either a tool call or a final answer.

This is the load-bearing idea: narrow enough that a model can emit a protocol-compliant program and have it validated before execution, wide enough to express the harnesses people actually write.

The tuple is written M, P, A, F, but each step runs in the order M → P → F → A (§3.1): memory builds the view, planning reads it, orchestration chooses tools for that directive, and action uses all three. A shared execution kernel runs the emitted call and appends the observation to the history (Eq. 3). The paper defines nested spaces, everything the generator can emit ⊇ syntactically valid ⊇ protocol-compliant ⊇ executable, and the validator checks a harness against the last two before it runs.

v1 showed how familiar harnesses fit (v1 §3.1): ReAct is (full history, no planner, ReAct loop, every tool); Codex and OpenCode are (history compacted near the context limit, a todo-list planner, ReAct loop, every tool); recursive systems such as ROMA, AOrchestra and Recursive Language Models are (isolated sub-problem memory, decomposition, recursive action, routed tools). The bank does two jobs: seeds anchor Stage I's synthesis, and later the growing bank Bn ⊇ B0 holds every retained harness with its task and observed reward, latency and cost, the incumbents a new harness must beat (§3.2).

Training: customise, repair, evolve

§4.1, Eq. 4 to 7, Figure 2

The generator pθ is Qwen3.6-27B (§5.1). Its input is the task, the protocol, the task's tool registry and a small reference context of prior harnesses; its output is a harness. A frozen executor model runs each harness to measure task reward, latency and money; a validator returns 0 or 1 plus diagnostics (§4.1). Three stages follow the life of a harness at inference time, one property each:

Stage I, adaptivity. A frozen, stronger teacher qφ (the paper never names it) is shown the task, the protocol, the registry and three seed harnesses sampled from the seeds matched to the task's type; its harness is kept only if it passes protocol validation and execution checks (§4.1). Training tasks "come from existing agentic benchmarks and environments" (WebWalker, TaskCraft, ClawGym, EnvScaler) "augmented with synthesized tasks". JIT-Agent is fine-tuned on the accepted harnesses, then trained with preference pairs: two harnesses run under the same backbone and seeds, and a pair is kept only when the winner has higher reward and is no slower and no costlier, and strictly better on latency or cost (Eq. 4). Kept pairs feed a DPO objective weighted by Δval = αr(r+ − r−) + αℓ[ℓ− − ℓ+]+ + ακ[κ− − κ+]+ and anchored to the SFT checkpoint; v1 adds that the sequence log-likelihoods are length-normalised (v1 Eq. 13).

Stage II, reliability. Stage I harnesses that fail static or runtime validation are not thrown away. Each is paired with a diagnostic (compiler errors, interface mismatches, tool-call failures, runtime exceptions); the teacher proposes a structured patch, it is applied deterministically, and validation runs again (Eq. 5). Only repair trajectories that become executable within two rounds are kept, "focusing the corpus on realistic, locally recoverable failures rather than those requiring wholesale redesign"; JIT-Agent then imitates the successful patches given the full history of harnesses and diagnostics (§4.1).

Stage III, evolvability: Evo-GDPO. Online, a task is sampled, prior high-quality harnesses are retrieved from the current bank, and the model samples a group of G candidates; candidates and retrieved harnesses run under the same executor, budget and seeds. The best retrieved harness (highest reward, ties broken by lower latency, then lower cost) is the incumbent (br, bℓ, bκ). A candidate still invalid after bounded repair gets the minimum reward, and its repair time and money still count (§4.1). Each candidate then earns three rewards (Eq. 6):

Rrew = r + λevo·[r − br]+
Rlat = 𝟙[r ≥ br]·[bℓ − ℓ]+
Rcost = 𝟙[r ≥ br]·[bκ − κ]+

The reward channel pays a bonus for beating the incumbent; the two efficiency channels pay only a candidate that at least matches the incumbent's reward, and only for being faster or cheaper than it. Each channel is then normalised separately within the group, Am = (Rm − mean) / (std + ε), and the three are mixed with weights wrew > wlat + wcost that sum to one, so task reward dominates (Eq. 7). The mixed advantage is normalised again across the batch and used in a clipped PPO objective with a token-level KL penalty to the Stage II checkpoint. This is GDPO (Liu et al., 2026), whose point is that GRPO applied to a sum of rewards lets the largest-scale reward drown the others and collapses distinct reward combinations into the same advantage. After the update the bank keeps a candidate only if it "matches or exceeds the current reward frontier and then strictly improves at least one frontier dimension, either reward itself, latency, or cost" (§4.1).

The incumbent scores 80 at $0.10 a task. A candidate scores 78 but costs $0.04, less than half. What does Evo-GDPO's cost channel pay it?

Its lower score already costs it on the reward channel; the gate means cheapness cannot buy that back. None of the hyperparameters are given: not G, λevo, the three weights, the α's, β, the KL coefficient, the number of online rounds, the teacher, the dataset sizes or the compute. The released code says the published checkpoint is a "ckpt-70 DPO checkpoint" (scripts/eval/config.py), and the model card that it "builds on the Stage-I harness-customization model and is further trained through distillation from the final research checkpoint" (model card). So the downloadable model is not the model the paper evaluates.

Inference: static and streaming

§4.2, Eq. 8

Static inference writes N harnesses in parallel, picks one, and runs only that one, so diversity costs no extra environment rollouts (§4.2). The paper does not say N or how the pick is made. The released runtime does: N = 3 at temperature 1.0, "the published setting", and the pick is made by a log-probability selector: "the model picks its own favourite", ranking the three by the summed log-probability it assigns to each (jit/README.md). The picked harness is validated and repaired if needed. In the released code repair is triggered only by an exception: "a harness that merely scores low is never repaired, since that would be optimising against the benchmark".

Streaming inference carries experience across a sequence of tasks. For task n, JIT-Agent retrieves from the bank Bn, writes and picks a harness, runs it once, and uses the result only to decide whether that harness joins the bank, by the Stage III rule (Eq. 8). Feedback never reaches the current rollout and the weights never change at deployment. The old summary's "retained only if it ... strictly improves latency or cost" misstates the rule slightly: a higher reward alone also qualifies. The released runtime has no streaming mode and no bank.

Results 1: nine benchmarks, two backbones

§5.1, §5.2, Table 2

Setup (§5.1). Nine benchmarks in four groups, all reported on 0 to 100: deep research, BrowseComp-Plus (accuracy), DeepSearchQA (answer F1), xBench-DeepSearch (accuracy); daily work, AgentIF-OneDay (normalised weighted rubric score), PinchBench (average score); planning, DeepPlanning-Shopping (cart match rate) and DeepPlanning-Travel (composite constraint score); workspace, OfficeBench and OdysseyBench (task success rate). JIT-Agent writes harnesses for two main executors, GLM-5.2 ("a strong open long-horizon model") and DeepSeek-V4-Flash-Preview ("inference efficiency"). Baselines come in two groups: eight models as they come (Qwen3.7-Plus, GLM-5.2, DeepSeek-V4-Flash and V4-Pro, both previews, Kimi K2.7 Code, GPT-5.6, which v2's setup calls GPT-5.6-Sol, Gemini 3.1 Pro and Gemini 3.5 Flash), and five reusable harnesses on a fixed backbone (Claude Code, Codex, OpenCode, Hermes, NanoBot). The first group measures end-to-end standing; the second isolates the harness.

What it reports (§5.2). Replacing each backbone's "default scaffold" with a JIT-written harness improves all 18 backbone and benchmark pairs. The nine-benchmark average rises 74.1 → 81.8 for GLM-5.2 (+7.7) and 66.7 → 75.5 for DeepSeek-V4-Flash (+8.8). The largest gains are on planning: +24.8 on Shopping for V4-Flash (59.1 → 83.9) and +20.2 on Travel for GLM-5.2 (62.8 → 83.0); V4-Flash also gains 11.9 on xBench-DS and 8.9 on DeepSearchQA. v1 read the planning gains as appearing "on tasks that require sustained state management and constraint tracking" (v1 §6.2), which fits the pattern that harness lift concentrates where state management is the bottleneck. JIT-equipped systems lead eight of nine columns, GLM-5.2 with JIT seven of them; the exception is Travel, where GPT-5.6's 84.9 is 1.9 ahead. V4-Flash with JIT beats the vanilla V4-Pro on every benchmark, by 8.7 on average. In the abstract's words, V4-Flash with JIT "surpasses GPT-5.6 on DeepSearchQA (+9.1) and OdysseyBench (+4.3)"; v1's introduction added PinchBench (+8.7), GLM's xBench-DS (+12.0) and AgentIF (+6.9).

Averaged over all nine benchmarks, how does DeepSeek-V4-Flash with a JIT-written harness compare with bare GPT-5.6?

The answer the abstract leaves out: V4-Flash with JIT averages 75.5 against GPT-5.6's 76.5. It beats GPT-5.6 on five benchmarks (DeepSearchQA, xBench-DS, PinchBench, Shopping, OdysseyBench) and loses on four (BrowseComp-Plus, AgentIF, Travel by 23.6 points, OfficeBench). "Enough for a harnessed V4-Flash to beat bare GPT-5.6", as the first summary put it, holds benchmark by benchmark on the two the abstract chose, not overall.

Table 2 as a dumbbell per benchmark: open dot the vanilla backbone, filled dot the same backbone with a JIT-written harness, the tick GPT-5.6. Averages are recomputed here and match the paper (GLM's +7.7 is the difference of the rounded averages; unrounded it is 7.79).

Two things in the table are worth knowing before reading the gains. First, the paper never describes the "default scaffold" the vanilla rows ran in, so the size of each gain depends on an unstated baseline. Second, vanilla V4-Pro scores below vanilla V4-Flash on three benchmarks, including PinchBench by 20.6 points (61.1 against 81.7); "beats V4-Pro on every benchmark" partly measures that.

Results 2: against five fixed harnesses, with cost

§5.3, §5.4, Table 3, Figure 3

This is the controlled comparison: same backbone, only the harness changes, on DeepSearchQA, xBench-DS and AgentIF, with DeepSeek-V4-Flash and Qwen3.6-Flash (Table 3). Per case it reports score, tokens and API cost.

In how many of the six backbone and benchmark settings does the JIT-written harness have the best score of the six harnesses?

JIT-Agent's harness has the best score in four of six: +4.7 over NanoBot on DeepSearchQA and +4.0 on xBench-DS with V4-Flash, +7.0 on xBench-DS and +2.9 on AgentIF with Qwen3.6-Flash. It trails Claude Code by 3.1 on V4-Flash AgentIF and NanoBot by 3.9 on Qwen DeepSearchQA (§5.3). It has the fewest tokens and the lowest cost in all six, cutting cost per case by 14.9% to 54.1% against the cheapest fixed harness, 36.0% on average; on V4-Flash xBench-DS tokens fall from 527K to 212K and cost from $0.075 to $0.039 while the score rises from 78.0 to 82.0. All of these recompute exactly. The paper reads this as "the gains therefore arise from task-conditioned scaffolds rather than longer trajectories."

The Pareto view (Figure 3, §5.4) puts all twelve pairs on cost against score. On DeepSearchQA the V4-Flash JIT point alone dominates every other pair; on AgentIF three pairs are on the frontier (Qwen with JIT, V4-Flash with JIT, V4-Flash with Claude Code). Two limits: the "lower cost than fixed harnesses" claim exists for these three benchmarks only, not the nine of Table 2 (the first summary attached it to all nine); and the cost does not say whether it includes JIT-Agent's own work, writing three candidate harnesses (each may run to 64,000 tokens, from a prompt whose reference block alone is about 13,000 tokens) and scoring all three, which a fixed harness never pays (see How much to believe).

Results 3: six other backbones, against ReAct

§5.5, Figure 4

To test transfer, six executors from three families (DeepSeek V4 Flash and Pro, Qwen3.6 Flash and Plus, Mimo-V2.5 Flash and Pro) run under ReAct and under a JIT-written harness on four benchmarks, with 100 DeepSearchQA questions and 50-task subsets of the other three (Figure 4). JIT wins all 24 pairs, by 7.6 points on average; by family 10.2 (DeepSeek), 4.0 (Qwen) and 8.6 (Mimo); DeepSearchQA gains most, 15.2 on average, up to +22.2 for Mimo-V2.5-Pro (§5.5). Figure 4 is not in the HTML version; this page decoded its printed labels from the vector PDF in the arXiv source, and the bar heights agree with the labels to within 0.31 points. Every number in §5.5 recomputes from them.

The gains are smaller off DeepSearchQA: 4.5 points on average on AgentIF and 3.4 on OfficeBench. And this figure's V4-Flash row repeats Table 2 exactly on all four JIT scores (85.1, 63.8, 83.9, 63.4) and on three of the four baselines, although the figure says it used subsets; the one difference is DeepSearchQA's baseline, 66.1 under ReAct here against 76.2 for the vanilla row there. So either Table 2's vanilla scaffold is not ReAct, or the two use different question sets; the paper does not say. Two of V4-Flash's OfficeBench scores, 61.0 and 63.4, cannot be a single pass over 50 tasks (that gives whole even numbers); they are reachable on the full 295.

Results 4: does the archive help? Static against streaming

Evolvability is the third property, and the evidence for it is one appendix figure (Figure 6): cumulative accuracy, cost per task and tool calls per task over a stream of tasks, with harnesses written independently (static) or retrieved from and added to the bank (streaming). v1 had this in the main text as §6.6; v2 moved it to the appendix. How much of this to believe

§5, Appendix B, the release

What holds up.

  • The arithmetic. Every derived number the paper prints that this page could recompute, 47 of 47, reproduces from its own tables and decoded figures (averages, gains, margins, the 14.9 to 54.1% cost range, the Figure 4 family averages); v1 and v2 print identical tables. The full list is on the tables tab.
  • The direction. 18 of 18 pairs in Table 2 and 24 of 24 in Figure 4 favour the JIT-written harness. Each pair is noisy, but 42 out of 42 is not what a coin gives; the pairs are not independent (one generator, shared benchmarks), so read it as "consistently positive", not as a p-value.
  • The controlled comparison. Table 3 fixes the backbone and changes only the harness, reports tokens and money beside score, and the JIT harness is cheapest in all six settings while losing on score in two, which the paper states plainly (§5.3).
  • The release. The runtime is MIT-licensed, the 27B weights are Apache 2.0, and 2,852 training harnesses are public. Matching 1,652 test query texts from six of the benchmarks the repository ships against those training instructions finds no copied test query and no near-copy (the closest training instruction shares at most 6% of a test query's word sequences), though see point 3 below (the checks).

What is weaker than it looks.

  1. One run, no error bars, margins inside the noise. No table reports seeds, repeats or intervals. Where the metric is a success rate on a known number of tasks, sampling noise can be computed (unpaired binomial, an upper bound for runs on the same tasks): JIT against NanoBot on V4-Flash xBench-DS, +4.0 on 100 tasks, has a standard error of 5.6 (z = 0.7); V4-Flash with JIT against GPT-5.6 on OdysseyBench, +4.3 on 300 tasks, z = 1.2; the OfficeBench gains in Table 2, z = 0.6 and 1.4; every Figure 4 OfficeBench gain on 50 tasks, z under 0.7. Only the two xBench-DS gains in Table 2 (+11.9, +12.0) reach z = 2. The noise table.
  2. Baselines that are not like for like. (a) The "default scaffold" of every vanilla row in Table 2 is never described, and on DeepSearchQA it scores 76.2 for V4-Flash where ReAct scores 66.1 in Figure 4. (b) JIT gets best of three harness drafts per task, picked by its own log-probability; each fixed harness gets one configuration. (c) Claude Code and Codex are coding runtimes built around their own vendors' models; here they run DeepSeek-V4-Flash and Qwen3.6-Flash on web research, which is not what they were tuned for. (d) The paper does not say whether "cost per case" includes JIT-Agent's own generation (three drafts of up to 64,000 tokens from a 27B model, plus scoring them). In the released runtime those tokens are logged under generate/, while the numbers "you report" come from execute/ (jit/README.md). If excluded, the 14.9 to 54.1% saving is a saving on executor tokens only.
  3. Training on the test cases' own environments. Of the 2,852 released training harnesses, 248 were written for tasks in the DeepPlanning-Shopping environment and 272 in DeepPlanning-Travel, with the benchmark's own system prompt and tools, and 189 for AgentIF-style workspaces. Their workspaces are named after the test cases (deepplanning_shopping/level1_case10, deepplanning_travel/travel_zh_1), and the tasks are new requests built on those cases' data: the training request in level1_case10 asks for four products that exist together in test case 10's product database and in none of the other 49 level-1 cases, and travel_zh_1 plans the same Harbin to Dalian trip on 12 November 2025 as test case 1. No test query is copied, but the generator was trained on harnesses for the very databases it is then scored on, and DeepPlanning is where the two largest gains appear (+24.8, +20.2). v1 listed DeepPlanning among the sources of Stage I training tasks (v1 §4.1); v2's list names WebWalker, TaskCraft, ClawGym and EnvScaler and drops it (§4.1). The fixed harnesses and vanilla backbones had no such tuning (the checks).
  4. No ablations. Nothing turns a stage off: no Stage I alone against I + II against I + II + III, no "teacher writes the harness" baseline, no "pick the best of the 13 seeds for each task" baseline (which would separate writing a harness from choosing one), no streaming without Evo-GDPO. So the paper shows that the trained system helps, not which part of the recipe does. The first summary's "the paper's own ablation" does not exist.
  5. Scores that cannot be one pass over the released sets. A success rate on N tasks must be k/N. With the repository's set sizes, 5 of 10 OfficeBench cells in Table 2 (295 tasks; for example GLM-5.2's 63.0 and GLM with JIT's 68.4), V4-Flash's xBench-DS 70.1 (100 tasks) and Kimi's OdysseyBench 69.9 (300 tasks) are not reachable, nor are 4 of 12 OfficeBench values in Figure 4 (50 tasks). They may be averages of several runs or other subsets; the paper says neither (granularity checks).
  6. Evolution rests on one figure. Test-time evolution, the "E" in JIT and the third property, is supported only by Figure 6: one stream per benchmark, one task order, executor unstated, no repeats, bank contents unreported, and v2 moved it to the appendix. With 120 tasks the sampling error of a cumulative score near 80% is about 3.7 points for each curve, so end gaps of 3.8 to 5.4 points are about one standard error of their difference.
  7. The released model is not the evaluated model. The checkpoint "builds on the Stage-I harness-customization model and is further trained through distillation from the final research checkpoint" (model card); there is no code for Stages I to III, no streaming bank, no ReAct baseline, and no adapters for BrowseComp-Plus or PinchBench. The headline numbers cannot be reproduced from the release as it stands.

In the authors' favour: v1 said openly that the four-module space is "substantially" poorer than production runtimes and that the gap was deliberate (the box is gone from v2); §5.3 reports the two settings it loses; §5.4 calls the frontier "task-dependent"; and releasing runtime, weights and training harnesses is more than most harness papers do.

Verdict. Believe that harnesses written per task by a trained model can be cheaper than off-the-shelf harnesses at similar or better scores on these benchmarks; that part rests on a controlled table with costs. Treat the size of every gain as provisional: single runs, an undescribed baseline scaffold, training data drawn from the environments of the benchmarks that gain most, no ablation of any stage, and test-time evolution shown once. It is a strong proof of concept with a release good enough for someone else to measure it properly.

What it takes to use this

§5.1, and the release of 27 August 2026
  • Code and licence. bingreeky/JIT (MIT; benchmark data keep their own licences). It runs the static pipeline: generate N = 3 harnesses at temperature 1.0, select by the model's own log-probability (or by a judge model when the meta-model is a hosted API), execute, score. Seven benchmarks have adapters and data; the DeepPlanning-Travel database is a separate 748 MB download.
  • The model. JIT-Agent/jit-27b, 27.36B parameters in BF16 (about 55 GB of weights), served with vLLM over four GPUs (the launcher's default TP=4) at a 163,840-token context, because a prompt with the reference catalogue plus a five-file harness does not fit in 32K. Use it with natural-language descriptions of the 11 seeds as references (about 13,000 tokens), the mode it was trained for.
  • Three model roles. The meta-model writes the harness, an execution model (any OpenAI-compatible endpoint) runs it, and a judge model grades xBench-DS, DeepSearchQA, AgentIF and Travel. Search tools need Serper and Jina keys.
  • What you cannot do yet. Retrain on your own tasks (no training code), run streaming mode with an evolving bank, or reproduce Table 2 (different checkpoint, missing benchmarks and baseline).
  • When it pays. On the paper's numbers, most on tasks whose difficulty is state and constraints (DeepPlanning, multi-hop search: +9 to +25) and least on workspace and instruction-following tasks (OfficeBench, OdysseyBench, AgentIF: +2 to +7, mostly within noise). The cost saving needs the generation overhead counted against it; for short tasks, three 27B drafts per task may cost more than the harness saves.

Why it matters (beyond the paper)

This knowledge base's reading when the paper came out, kept here: it is the first attempt to make harness intelligence a trainable axis rather than an engineering one, and the economics are the interesting part, because the lift comes with a cost reduction: a task-conditioned harness does not pay for machinery it does not need. If it holds, the harness stops being a fixed asset tuned per product and becomes a per-task artifact you generate, which changes what you cache, what you version and what you evaluate. The caveats were also there from the start: the generator writes in a deliberately impoverished language, so the comparison with OpenCode and Claude Code is closer to parity than to dominance, and the paper does not analyse failures of the repair loop or of evolution beyond the two-round cap.

A week later HarnessDev tested the untrained version of the same skill: frontier models building and then evolving their own harnesses, with a held-out check after every version. Their evolution steps moved the held-out score in the same direction as the feedback score in only 34 of 64 version changes. That is the failure JIT-Agent claims training fixes, and it is exactly the measurement JIT-Agent does not make: it never scores a harness version against held-out tasks, only the end of one stream.

Connections

  • Prime Agent: the mirror image. Prime Agent gives an untrained model a rich harness and notes that models are not trained to operate it; JIT-Agent trains a model to build the harness but keeps the harness simple. Neither has yet done both.
  • StateM: the hand-built harness whose lift JIT-Agent is trying to automate; StateM's versioned YAML runbook is roughly a hand-tuned (M, P, A, F) instance.
  • Demystifying Agent Skills: the F module is the skills question, and the 10% skill-misapplication rate found there is a plausible source of JIT-Agent's residual failures. In the released training harnesses F is usually "expose every tool", so skills selection is the least exercised module.
  • SA-MRPO (Learn What's Left, Not What's Mastered): Evo-GDPO's separate normalisation of reward, latency and cost is the same multi-objective RL problem, approached through frontier comparison rather than saturation-aware reweighting.
  • HarnessDev, Repo-To-Skill and NeoHorse-1: three more pages on learning the layer around the model; each, like this one, needs its headline checked against what the experiment actually used.
  • ReAct (the baseline harness), DeepSeekMath (GRPO, which Evo-GDPO modifies) and DPO (Stage I's preference step).

Score a group of harnesses

Stage III is where JIT-Agent is supposed to learn to beat the harnesses it already has. Each training step samples a group of candidate harnesses for one task, runs them, and turns their reward, latency and cost into one advantage per candidate with Evo-GDPO (Eq. 6 and 7); the same measurements decide which candidates join the bank. This tab runs those two equations on a group you choose, next to the GRPO-style alternative that GDPO was designed to replace: add the three channel rewards first, then normalise once.

Try: start with the Table 3 group and step through both methods. Under GRPO the token channel, measured in thousands, swamps the score; under Evo-GDPO each channel is put on the same footing first. Then raise the incumbent's score until no candidate matches it, and watch both efficiency channels go silent.

Advantages are within-group z-scores, (x − mean) / (standard deviation + 10⁻⁶), as in Eq. 7; the batch-level renormalisation that follows only rescales one group and is left out. The bank column applies the retention rule of §4.1 against the incumbent: keep a candidate if its score is at least br and it is strictly better on score, latency or cost. The paper gives no values for λevo or the weights; the defaults here are illustrative and only respect wrew > wlat + wcost.

Sampling noise where it can be computed

For success-rate metrics on a known number of tasks: standard error of a difference between two independent runs, √(p₁(1 − p₁)/n + p₂(1 − p₂)/n). Runs on the same tasks are positively correlated, so the paired error would be smaller; the paper gives no per-task results to compute it. F1, rubric and match-rate metrics are left out because their spread is unknown. Set sizes are the released repository's.

Scores that cannot be one pass over the released set

A success rate over N tasks is k/N; a printed score is "reachable" if some whole k rounds to it at one decimal.
