Problem

[[S1|§1 Introduction]]

An agent harness is everything around the model that makes it an agent: what history is kept, how the next sub-goal is formed, which tools or skills are exposed, how actions run, and when to verify or recover ({{§1|ax:S1}}). The paper's premise is that "agent intelligence is not a property of model weights alone, but of the model–harness pair" ({{§1|ax:S1}}): a strong model behind the wrong memory or planner fails, and a strong harness only helps a model that can follow it.

Recent work therefore optimises harnesses: it edits harness code, prompts, tools, memories or skills from trajectories and feedback, and keeps what scores well (Meta-Harness, AHE and others; {{§1|ax:S1}}, {{§2|ax:S2}}). The paper calls this ahead-of-time (AOT): the harness is a durable artifact tuned on past tasks "with the hope that the resulting artifact will generalize" to future ones. That works when the task mix is stable. It is awkward when it is not, because different tasks want different harnesses: wide search wants parallel exploration, terminal work a lean serial loop, deep research a working memory over evidence, repository-scale coding a filesystem of patches and tests ({{§1|ax:S1.SS0.SSS0.Px2}}). "The appropriate harness is not only domain-dependent, but instance-dependent."

The knowledge base's first summary put the same problem from the reader's side: every result in the harness-scaling literature is a hand-built artifact. Someone writes a state machine, a skill set or a subagent topology, tunes it against a benchmark and reports the lift, and that does not compose and does not transfer. The question becomes whether harness construction can be a learned, inference-time capability instead of a human craft.

So the paper asks for just-in-time (JIT) construction, which it calls Model-as-a-Harness: a trained meta-agent writes a harness for the task in front of it, and an unmodified agentic model runs inside it. It names the skill harness intelligence and gives it three properties ({{§1|ax:S1.SS0.SSS0.Px3}}): adaptivity (match the harness to the task and backbone), reliability (produce something that executes, and recover when it does not) and evolvability (turn execution feedback into better future harnesses). "Intelligence about the harness begins where competence within a fixed harness ends."

A correction to the first summary

The old page said the paper's own ablation shows "no fixed harness dominates across tasks: ReAct wins some, Plan-and-Execute wins others, ReSum wins on long-horizon search". The paper has no such ablation. "No fixed harness dominates" is its reading of {{Table 3|ax:S5.T3}}, where the five fixed harnesses are Claude Code, Codex, OpenCode, Hermes and NanoBot, and the leader among them changes with the backbone and benchmark (NanoBot on four settings, Claude Code on two). ReAct, Plan-and-Execute and ReSum appear only as seed harnesses ({{Table 1|ax:S3.T1}}), and ReAct as the baseline of {{Figure 4|ax:S5.F4}}; their scores against each other are never reported.

Idea: one protocol, four modules, written per task

[[S3.SS1|§3.1, Eq. 1 to 3]]

Writing a whole agent from scratch for every task would be unreliable, so the paper constrains what the meta-agent may write. Every harness is a tuple of four modules under a fixed protocol Π ({{Eq. 2|ax:S3.E2}}):

h = (M, P, A, F)

  • M Memory: turns the event history into the view the model sees (history → view).
  • P Planning: forms a local directive or sub-goal from that view (view → directive). A harness with no planner returns a null directive, so it still fits.
  • F Capability orchestration: picks which tools, APIs, MCP servers and skills are exposed at this step.
  • A Action: the control loop; updates the controller state and emits the next action, either a tool call or a final answer.

This is the load-bearing idea: narrow enough that a model can emit a protocol-compliant program and have it validated before execution, wide enough to express the harnesses people actually write.

The tuple is written M, P, A, F, but each step runs in the order M → P → F → A ({{§3.1|ax:S3.SS1}}): memory builds the view, planning reads it, orchestration chooses tools for that directive, and action uses all three. A shared execution kernel runs the emitted call and appends the observation to the history ({{Eq. 3|ax:S3.E3}}). The paper defines nested spaces, everything the generator can emit ⊇ syntactically valid ⊇ protocol-compliant ⊇ executable, and the validator checks a harness against the last two before it runs.

v1 showed how familiar harnesses fit ({{v1 §3.1|ax1:S3.SS1}}): ReAct is (full history, no planner, ReAct loop, every tool); Codex and OpenCode are (history compacted near the context limit, a todo-list planner, ReAct loop, every tool); recursive systems such as ROMA, AOrchestra and Recursive Language Models are (isolated sub-problem memory, decomposition, recursive action, routed tools). The seed bank. To give the generator something to learn from, the authors re-implemented 13 published harnesses under the same protocol and kernel, a codebase they call HarnessFactory; these form the seed bank B0 with K0 = 13 ({{§3.2|ax:S3.SS2}}). Hover or tap a row to see which module carries its idea:

{{Table 1|ax:S3.T1}}, transcribed. Only DeepAgent and AOrchestra do anything special in F; eleven of thirteen expose the full registry. The released repository ships 11 of the 13: ReAct and AOrchestra are missing, and the runtime's default harness name, react_baseline, has no code behind it, so Figure 4's ReAct baseline cannot be rerun from the release as it stands.

The bank does two jobs: seeds anchor Stage I's synthesis, and later the growing bank Bn ⊇ B0 holds every retained harness with its task and observed reward, latency and cost, the incumbents a new harness must beat ({{§3.2|ax:S3.SS2}}).

Training: customise, repair, evolve

[[S4.SS1|§4.1, Eq. 4 to 7, Figure 2]]

The generator pθ is Qwen3.6-27B ({{§5.1|ax:S5.SS1}}). Its input is the task, the protocol, the task's tool registry and a small reference context of prior harnesses; its output is a harness. A frozen executor model runs each harness to measure task reward, latency and money; a validator returns 0 or 1 plus diagnostics ({{§4.1|ax:S4.SS1}}). Three stages follow the life of a harness at inference time, one property each:

Stage I, adaptivity. A frozen, stronger teacher qφ (the paper never names it) is shown the task, the protocol, the registry and three seed harnesses sampled from the seeds matched to the task's type; its harness is kept only if it passes protocol validation and execution checks ({{§4.1|ax:S4.SS1.SSS0.Px1}}). Training tasks "come from existing agentic benchmarks and environments" (WebWalker, TaskCraft, ClawGym, EnvScaler) "augmented with synthesized tasks". JIT-Agent is fine-tuned on the accepted harnesses, then trained with preference pairs: two harnesses run under the same backbone and seeds, and a pair is kept only when the winner has higher reward and is no slower and no costlier, and strictly better on latency or cost ({{Eq. 4|ax:S4.E4}}). Kept pairs feed a DPO objective weighted by Δval = αr(r+ − r−) + αℓ[ℓ− − ℓ+]+ + ακ[κ− − κ+]+ and anchored to the SFT checkpoint; v1 adds that the sequence log-likelihoods are length-normalised ({{v1 Eq. 13|ax1:S4.E13}}).

Stage II, reliability. Stage I harnesses that fail static or runtime validation are not thrown away. Each is paired with a diagnostic (compiler errors, interface mismatches, tool-call failures, runtime exceptions); the teacher proposes a structured patch, it is applied deterministically, and validation runs again ({{Eq. 5|ax:S4.E5}}). Only repair trajectories that become executable within two rounds are kept, "focusing the corpus on realistic, locally recoverable failures rather than those requiring wholesale redesign"; JIT-Agent then imitates the successful patches given the full history of harnesses and diagnostics ({{§4.1|ax:S4.SS1.SSS0.Px4}}).

Stage III, evolvability: Evo-GDPO. Online, a task is sampled, prior high-quality harnesses are retrieved from the current bank, and the model samples a group of G candidates; candidates and retrieved harnesses run under the same executor, budget and seeds. The best retrieved harness (highest reward, ties broken by lower latency, then lower cost) is the incumbent (br, bℓ, bκ). A candidate still invalid after bounded repair gets the minimum reward, and its repair time and money still count ({{§4.1|ax:S4.SS1.SSS0.Px6}}). Each candidate then earns three rewards ({{Eq. 6|ax:S4.E6}}):

Rrew = r + λevo·[r − br]+
Rlat = 𝟙[r ≥ br]·[bℓ − ℓ]+
Rcost = 𝟙[r ≥ br]·[bκ − κ]+

The reward channel pays a bonus for beating the incumbent; the two efficiency channels pay only a candidate that at least matches the incumbent's reward, and only for being faster or cheaper than it. Each channel is then normalised separately within the group, Am = (Rm − mean) / (std + ε), and the three are mixed with weights wrew > wlat + wcost that sum to one, so task reward dominates ({{Eq. 7|ax:S4.E7}}). The mixed advantage is normalised again across the batch and used in a clipped PPO objective with a token-level KL penalty to the Stage II checkpoint. This is GDPO ({{Liu et al., 2026|https://arxiv.org/abs/2601.05242}}), whose point is that GRPO applied to a sum of rewards lets the largest-scale reward drown the others and collapses distinct reward combinations into the same advantage. After the update the bank keeps a candidate only if it "matches or exceeds the current reward frontier and then strictly improves at least one frontier dimension, either reward itself, latency, or cost" ({{§4.1|ax:S4.SS1.SSS0.Px6}}).

The incumbent scores 80 at $0.10 a task. A candidate scores 78 but costs $0.04, less than half. What does Evo-GDPO's cost channel pay it?

None of the hyperparameters are given: not G, λevo, the three weights, the α's, β, the KL coefficient, the number of online rounds, the teacher, the dataset sizes or the compute. The released code says the published checkpoint is a "ckpt-70 DPO checkpoint" ({{scripts/eval/config.py|https://github.com/bingreeky/JIT/blob/ababa06c2f54d799fd9fbc356e5368f61a452260/scripts/eval/config.py}}), and the model card that it "builds on the Stage-I harness-customization model and is further trained through distillation from the final research checkpoint" ({{model card|https://huggingface.co/JIT-Agent/jit-27b}}). So the downloadable model is not the model the paper evaluates.

Inference: static and streaming

[[S4.SS2|§4.2, Eq. 8]]

Static inference writes N harnesses in parallel, picks one, and runs only that one, so diversity costs no extra environment rollouts ({{§4.2|ax:S4.SS2}}). The paper does not say N or how the pick is made. The released runtime does: N = 3 at temperature 1.0, "the published setting", and the pick is made by a log-probability selector: "the model picks its own favourite", ranking the three by the summed log-probability it assigns to each ({{jit/README.md|https://github.com/bingreeky/JIT/blob/ababa06c2f54d799fd9fbc356e5368f61a452260/jit/README.md}}). The picked harness is validated and repaired if needed. In the released code repair is triggered only by an exception: "a harness that merely scores low is never repaired, since that would be optimising against the benchmark".

Streaming inference carries experience across a sequence of tasks. For task n, JIT-Agent retrieves from the bank Bn, writes and picks a harness, runs it once, and uses the result only to decide whether that harness joins the bank, by the Stage III rule ({{Eq. 8|ax:S4.E8}}). Feedback never reaches the current rollout and the weights never change at deployment. The old summary's "retained only if it ... strictly improves latency or cost" misstates the rule slightly: a higher reward alone also qualifies. The released runtime has no streaming mode and no bank.
