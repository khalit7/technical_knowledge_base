Scaling Harness Intelligence via Just-in-Time Harness Evolution

 LV-NUS Lab

Abstract

Agent capability is not determined by the model alone. The agent harness, encompassing memory management, planning strategy, action protocol, and tool/skill orchestration, can dominate the contribution of the underlying foundation model. Yet harness design remains manual, task-specific, and fundamentally unscalable. We present JIT-Agent, a harness intelligence model trained to synthesize task-adaptive agent harnesses on the fly for arbitrary off-the-shelf agentic LLMs. We formalize the agent harness as a composable, machine-generatable artifact governed by a fixed four-module protocol, and train JIT-Agent to customize harnesses for a given task at hand, repair harnesses for stable and reliable execution, and self-evolve by distilling performance signals from an expanding archive of prior harness configurations. Equipped with JIT-Agent as a harness helper, DeepSeek-V4-Flash surpasses GPT-5.6 on DeepSearchQA ( $+9.1$ ) and OdysseyBench ( $+4.3$ ), while the already strong GLM-5.2 gains up to $+20.2$ points. Across controlled evaluations, JIT-Agent-generated harnesses are performance-competitive with mature agent runtimes such as OpenCode and Claude Code and consistently improve multi-scale model families of DeepSeek V4, Mimo-V2.5, and Qwen3.6. To our knowledge, JIT-Agent is the first model purpose-built for just-in-time harness generation, establishing harness intelligence as a trainable, transferable, and compounding dimension of agent capability orthogonal to model scaling.

1 Introduction

Agent harness matters.
The capability of an LLM agent is jointly determined by two tightly coupled factors: the foundation model that produces reasoning and actions, and the agent harness that situates this model in a closed-loop execution environment (Meng et al., 2026b; Zhou et al., 2026; Ning et al., 2026).
The harness decides what history is retained, how local intent is formed, which tools or skills are exposed, how actions are executed, and when verification or recovery is triggered (Meng et al., 2026b; Zhou et al., 2026).
A strong model may fail when placed behind the wrong memory, planner, or action protocol; a strong harness, in turn, can only unlock capability when the model can understand and follow it (Lee et al., 2026c; Lin et al., 2026).
Thus, agent intelligence is not a property of model weights alone, but of the model–harness pair (Lee et al., 2026c; Zhou et al., 2026).
Harness design is therefore not an implementation detail, but a first-order determinant of agent performance (Meng et al., 2026b; Lin et al., 2026).

Ahead-of-Time (AOT) Harness

This observation has motivated a growing line of work on test-time harness optimization (Lee et al., 2026c; Lin et al., 2026).
Recent systems optimize harness code, prompts, tools, memories, skills, or control policies from trajectories and feedback, yielding strong improvements in coding, terminal-use, web interaction, and general agentic domains (Lee et al., 2026c; Lin et al., 2026).
Despite their differences, many of these methods share an Ahead-of-Time (AOT) assumption: the harness is treated as a durable artifact to be optimized over an experience stream, with the hope that the resulting artifact will generalize across future tasks, domains, or model versions (Lee et al., 2026c; Lin et al., 2026).
This is a powerful paradigm when the deployment distribution is stable and homogeneous (Lin et al., 2026; Zhang et al., 2025b).
However, it still asks the optimization loop to precompile a broadly useful harness before seeing the exact structure of each future problem (Lee et al., 2026c).

Just-in-Time (JIT) Harness.

We instead turn to a Just-in-Time (JIT) view of harness construction.
Different tasks plainly require different harness priors.
Wide-search tasks may benefit from parallel evidence exploration (Qin et al., 2025); terminal tasks often favor a lean serial ReAct loop (Yao et al., 2023a; Merrill et al., 2026); deep-research tasks require working memory over retrieved evidence (Hu et al., 2025); and NL2Repo-style coding tasks are naturally mediated by a filesystem that stores patches, tests, traces, and repository state (Yang et al., 2024; Ning et al., 2026).
In short, the appropriate harness is not only domain-dependent, but instance-dependent (Meng et al., 2026b; Zhou et al., 2026).
Optimizing a single AOT harness across such heterogeneous demands is cumbersome: one must search a large design space, accumulate enough trajectories, and then hope that the resulting scaffold matches the next task (Lee et al., 2026c; Lin et al., 2026).
We ask whether another possibility is viable: Model-as-a-Harness, where a trained meta-agent generates a task-specific harness on the spot, and an arbitrary agentic LLM executes under that harness.

Given a task, JIT-Agent composes a problem-specific agent harness by instantiating (rather than simply combining) four modules: memory, planning, action, and capability. Different task structures therefore induce distinct executable protocols and state organizations, as illustrated by the specialized harnesses for deep research, product generation, and autonomous research.

JIT-Agent.

We propose JIT-Agent, a compact meta-agent for just-in-time harness generation and evolution.11
 1

 JIT-Agent continues our broader effort toward the recursive self-design and self-evolution of agent systems. Before addressing the harness as a whole, we studied modular design and evolution at the level of individual harness components: memory in MemEvolve (Zhang et al., 2025b) and planning in TodoEvolve (Liu et al., 2026a). JIT-Agent is the unified continuation of this progression, extending component-level self-design to the full operational harness.
At inference time, JIT-Agent receives a task specification, a protocol, an executable tool/skill registry, and a small retrieved context of prior harnesses, and emits an executable harness tailored to the task at hand.
The resulting harness wraps an off-the-shelf agentic LLM for execution. As feedback and traces accumulate, JIT-Agent can revise the harness and update a harness archive, enabling test-time harness evolution while the generator itself remains fixed.
Training such a system raises three challenges:
❶ adaptivity, namely how to match the generated harness to the task;
❷ reliability, namely how to ensure executable behavior and recover when synthesis fails (Pan et al., 2026a; Ning et al., 2026); and
❸ evolvability, namely how to turn execution feedback into stronger future harnesses (Lee et al., 2026c; Lin et al., 2026).
Together, these three requirements define what we call harness intelligence:

Harness Intelligence

Harness intelligence is the capacity to construct and refine the operational scaffold through which a model acts. It has three defining properties: adaptivity, matching the harness to the task and backbone; reliability, producing executable behavior and recovering when synthesis fails; and evolvability, turning execution feedback into stronger future harnesses. Intelligence about the harness begins where competence within a fixed harness ends.

JIT-Agent realizes harness intelligence through a three-stage training recipe over a protocol-induced harness space (Meng et al., 2026b; Zhou et al., 2026).
First, we factor an agent harness into a four-tuple of memory, planning, action, and capability-orchestration modules, and build HarnessFactory, a unified codebase of representative scaffolds under this common interface (Hu et al., 2025; Erdogan et al., 2025a; Yao et al., 2023a; Xu and Yan, 2026).
Following the view that code carries the harness (Ning et al., 2026; Pan et al., 2026a), this representation makes harness generation feasible: JIT-Agent generates structured executable modules rather than unconstrained agent programs.
❶ Stage I then teaches task-conditioned customization from teacher-generated protocol-compliant examples, giving the generator adaptivity over the shared design space.
Second, ❷ Stage II converts failed generations into bounded repair trajectories, turning compiler errors, interface mismatches, and runtime failures into supervision for reliable recovery.
Third, ❸ Stage III introduces Evolutionary Group-Decoupled Policy Optimization (Evo-GDPO), which optimizes JIT-Agent to propose harnesses that overtake the current archive frontier while separately normalizing reward, latency, and cost.
This supplies evolvability by turning test-time harness improvement into a trained capability rather than an external search heuristic.
Through this pipeline, we train JIT-Agent-27B, a harness intelligence model that can customize, repair, and evolve task-specific harnesses, shifting harness engineering from AOT artifacts to native JIT synthesis.

Experiment Findings.

The results show that harness intelligence can both elevate an efficient backbone and extend an already capable one. DeepSeek-V4-Flash equipped with JIT-Agent surpasses GPT-5.6 on DeepSearchQA ( $+9.1$ ), PinchBench ( $+8.7$ ), and OdysseyBench ( $+4.3$ ). On already strong GLM-5.2, JIT-Agent raises the ceiling further, with large absolute gains on xBench-DS ( $+12.0$ ) and AgentIF ( $+6.9$ ). Beyond these headline results, JIT-Agent-generated harnesses are performance-competitive with mature agent runtimes such as OpenCode and Claude Code and deliver consistent gains across differently scaled variants of DeepSeek V4, Mimo-V2.5, and Qwen3.6.

Contributions.

Our contributions are summarized as follows:

➣ 

Harness Intelligence.
We formulate Model-as-a-Harness as a new agent-improvement paradigm and define harness intelligence as the learned ability to construct, repair, and evolve an agent’s operational scaffold.

➣ 

Practical Solution.
We introduce JIT-Agent and its three-stage training pipeline, combining a four-module executable harness protocol, HarnessFactory, customization learning, feedback-driven repair, and Evo-GDPO for test-time harness evolution.

➣ 

Experimental Validation.
We validate JIT-Agent across heterogeneous agentic benchmarks and model backbones, showing that JIT-generated harnesses improve vanilla agents, compete with strong fixed harnesses, and move backbone–harness pairs toward better cost–performance frontiers.

2 Related Work

Harness Engineering and Modularization.

Harness engineering remains strikingly diverse, spanning coding and general-purpose runtimes such as Claude Code, Codex, Hermes, and OpenClaw (Anthropics, 2025; OpenAI, 2025; Nous Research, 2026; OpenClaw Contributors, 2026), embodied systems (Zhang et al., 2026e; Lee et al., 2026b), search agents (Apodex Team, 2026; Qin et al., 2025), and memory-centric harnesses such as Mem0, EverMemOS, and MemEvolve (Chhikara et al., 2025; Hu et al., 2026a; Zhang et al., 2025b). Beneath this variety, the harness is the operational layer that determines what an agent observes, remembers, plans, invokes, verifies, and executes, making capability a property of the model–harness pair rather than of model weights alone (Meng et al., 2026b; Zhou et al., 2026; Pan et al., 2026a; Lee et al., 2026c). Recurring design choices span (i) memory, which curates working context and preserves cross-session experience (Hu et al., 2026b; Hu et al., 2024a; Yan et al., 2025; Zhang et al., 2025c); (ii) planning, which forms and revises subgoals to update the agent’s direction (Cao et al., 2025; Erdogan et al., 2025b; Jin et al., 2025; Qin et al., 2025); (iii) control loops and goal management, which execute objectives, monitor progress, reflect on outcomes, and recover from failure (Yao et al., 2023a; Shinn et al., 2023; Madaan et al., 2023; Sun et al., 2023); (iv) tool allocation, which selects and sequences callable resources from large API spaces (Qin et al., 2023; Yang et al., 2026; Qian et al., 2025; Wang et al., 2025a); and (v) skill orchestration, which discovers, retrieves, composes, and delegates reusable procedures from growing skill libraries (Xu and Yan, 2026; Zheng et al., 2025; Li et al., 2026a; Zhou et al., 2026). Modularization has consequently become the field’s common design language: representations vary, but explicit interfaces make harness components independently substitutable and optimizable (Chen et al., 2026b; Ning et al., 2026; Pan et al., 2026a; Lin et al., 2026; Lee et al., 2026c). For example, HarnessX factorizes a runtime into prompts, tools, memory, and control flow, whereas Code-as-Agent-Harness organizes it into interface, mechanism, and multi-agent-scaling layers (Chen et al., 2026b; Ning et al., 2026). We therefore adopt the compact factorization $\mathbf{h}=(\mathbf{M},\mathbf{P},\mathbf{A},\mathbf{F})$ , where the four modules construct the memory view, form the next directive, advance the action loop, and orchestrate tools and skills, respectively; this provides a minimal executable contract while leaving each module internally extensible (Hu et al., 2026b; Cao et al., 2025; Yao et al., 2023a; Xu and Yan, 2026).

Harness Optimization.

Once modularized, harness construction becomes an optimization problem over executable artifacts rather than a fixed engineering choice (Khattab et al., 2023; Yuksekgonul et al., 2024; Hu et al., 2024b; Shang et al., 2024). The optimization scope has expanded from prompts and declarative LM pipelines to workflow graphs, role assignments, and complete harness code, allowing feedback to revise both local instructions and global control structure (Khattab et al., 2023; Zhang et al., 2024; Hu et al., 2024b; Shang et al., 2024; Lee et al., 2026c). Closed-loop evolution. At the harness level, recent methods largely instantiate a diagnose–propose–validate loop: execution traces expose behavioral weaknesses, candidate edits alter prompts, memory, tools, middleware, or control flow, and validation or preference signals determine which changes persist (Lee et al., 2026c; Lin et al., 2026; Zhang et al., 2026b; Pan et al., 2026b; Chen et al., 2026b). Recent work further extends this loop toward recursive, hierarchical, and collaborative self-improvement, while constraining component-wise evolution to improve transfer (Lee et al., 2026a; Zhou, 2026; Nie et al., 2026a; Zhang et al., 2026c). Their supervision ranges from textual gradients and trace-grounded observability to regression tests, retrospective self-preference, and typed primitive substitution, but the common product is a persistently improved executable scaffold (Yuksekgonul et al., 2024; Lin et al., 2026; Zhang et al., 2026b; Pan et al., 2026b; Chen et al., 2026b). AOT versus JIT. Although such harnesses may transfer, these methods primarily optimize a durable artifact against an accumulated experience distribution and are therefore ahead-of-time relative to the exact structure of a new instance (Zhang et al., 2024; Zhang et al., 2025a; Yuan et al., 2024; Chen et al., 2023). We instead amortize harness search into JIT-Agent: the generator synthesizes a task-conditioned harness at inference time and can further revise it from execution feedback, shifting optimization from repeated artifact search toward learned just-in-time construction (Meng et al., 2026b; Zhou et al., 2026; Ning et al., 2026; Pan et al., 2026a; Xu and Yan, 2026). 3 Unified Harness Codebase

3.1 Modularized Harness Design Space

An agent harness is the operational layer that turns a foundation model into a closed-loop agent (Meng et al., 2026a; Zhou et al., 2026): it determines what from prior interaction is retained (Hu et al., 2026b), how intermediate directives are formed (Cao et al., 2025), which external capabilities are exposed at each stage (Xu and Yan, 2026; Yang et al., 2026), and how control advances. Harness generation is therefore defined over programs rather than unconstrained text. We distinguish the raw generation space $\mathcal{G}$ , syntactically valid harnesses $\mathcal{H}^{\mathrm{syn}}$ , protocol-compliant harnesses $\mathcal{H}_{\boldsymbol{\Pi}}$ , and their executable subset $\mathcal{H}^{\mathrm{exec}}_{\boldsymbol{\Pi}}$ , with $\mathcal{G}\supseteq\mathcal{H}^{\mathrm{syn}}\supseteq\mathcal{H}_{\boldsymbol{\Pi}}\supseteq\mathcal{H}^{\mathrm{exec}}_{\boldsymbol{\Pi}}$ . The fixed protocol $\boldsymbol{\Pi}$ specifies module schemas and interfaces, their lifecycle, validation rules, and the shared execution semantics. It removes incidental variation in language and runtime while retaining the principal operational choices that distinguish existing harnesses (Wu et al., 2023; Microsoft, 2024; LangGraph, 2025; Luo et al., 2025).

Harness Composability

Composability has become a first-class concern in modern harness design. DeepSeek Harness, for example, adopts an “Everything is a Plugin” architecture, representing the runtime as modules connected through explicit dependency relationships (Shi et al., 2026). Composability is equally central to JIT generation: it turns harness construction from unconstrained program synthesis into assembly over a typed, recombinable design space.

JIT-Agent makes these choices explicit through four interoperable modules: how history is compressed, how local intent is formed, how tools and skills are orchestrated, and how control advances. Let $\boldsymbol{\tau}$ be a task, $\pi_{\psi}$ a frozen backbone executor, and $\mathcal{C}_{\tau}$ the capability registry available (e.g., tools, APIs, skills) to that task. Running a harness $\mathbf{h}$ with $\pi_{\psi}$ induces a closed-loop trajectory

 $\boldsymbol{\xi}\sim\operatorname{Rollout}(\boldsymbol{\tau},\pi_{\psi},\mathbf{h},\mathcal{C}_{\tau};\boldsymbol{\Pi})=\bigl(\mathbf{s}_{1},e_{1},\mathbf{o}_{1},\ldots,\mathbf{s}_{T},e_{T},\mathbf{o}_{T}\bigr),$

Our key assumption is that every $\mathbf{h}\in\mathcal{H}_{\boldsymbol{\Pi}}$ admits the modular factorization

Position

Production harnesses such as Codex, Claude Code and DeepSeek Harness expose substantially richer mechanisms than our four-module instantiation (Shi et al., 2026; Anthropics, 2025; OpenAI, 2025). That gap is deliberate. This work is not to ask a model to reproduce an entire production runtime, but to establish a more fundamental result: even compact harnesses, generated just in time, can yield substantial gains. Besides, we believe the JIT paradigm is complementary to production harness engineering. As models increasingly participate in the design and revision of their own runtimes, the training recipe for harness intelligence will matter at larger scales as well. We view the present design space as a starting point.

3.2 HarnessFactory

Under the shared protocol $\boldsymbol{\Pi}$ and a common kernel, HarnessFactory re-implements 13 representative contemporary agentic scaffolds: ReAct (Yao et al., 2023b), Plan-and-Execute (Erdogan et al., 2025b), ReSum (Wu et al., 2026), Flash-Searcher (Qin et al., 2025), General Agentic Memory (GAM) (Yan et al., 2025), MemoBrain (Qian et al., 2026), AggAgent (Lee et al., 2026d), OAgent (Zhu et al., 2025), AgentFold (Ye et al., 2025), HiAgent (Hu et al., 2024a), DeepAgent (Li et al., 2026b), ROMA (Alzu’bi et al., 2026), and AOrchestra (Ruan et al., 2026). They provide heterogeneous memory, planning, action, and capability-orchestration strategies. The seed bank $\mathcal{B}_{0}$ therefore contains $K_{0}=13$ protocol-compatible harnesses.
Table 2 gives the full inventory.

The bank serves a dual role: harnesses sampled from $\mathcal{B}_{0}$ anchor Stage-I synthesis, while later archive states supply the prior population against which new designs are evaluated. As the system operates, $\mathcal{B}_{0}$ grows into $\mathcal{B}_{n}\supseteq\mathcal{B}_{0}$ , whose entries associate each retained harness with its task and observed reward, latency, and cost; this evolution is formalized in Section 4.3.

Stage III performs online evolution by comparing candidate harnesses against the incumbent bank, optimizing decoupled reward, latency, and cost advantages, and retaining frontier-improving designs.

4 Training Pipeline

Training follows the inference-time lifecycle of JIT-Agent: first synthesize a task-conditioned harness, then recover unstable generations, and finally learn to improve from stronger archive states online. Let $\boldsymbol{\tau}\sim\mathcal{D}_{\mathrm{task}}$ denote a task drawn from the training distribution, $\mathcal{C}_{\tau}$ its capability registry, and $\mathcal{E}_{\tau}$ a small reference context from the harness bank. We define the generation context as $\mathbf{c}_{\tau}=(\boldsymbol{\tau},\boldsymbol{\Pi},\mathcal{C}_{\tau},\mathcal{E}_{\tau})$ and sample harnesses from $p_{\theta}(\mathbf{h}\mid\mathbf{c}_{\tau})$ . A frozen executor $\pi_{\psi}\sim\mathcal{M}$ then runs each harness for validation and utility measurement. The common objective is

 $\theta^{\star}=\arg\max_{\theta}\mathbb{E}_{\begin{subarray}{c}\boldsymbol{\tau}\sim\mathcal{D}_{\mathrm{task}},\,\pi_{\psi}\sim\mathcal{M},\\
\mathbf{h}\sim p_{\theta}(\cdot\mid\mathbf{c}_{\tau})\end{subarray}}\bigl[U(\boldsymbol{\tau},\pi_{\psi},\mathbf{h})\bigr],$ 	

(8)	

where $U$ evaluates the trajectory induced by the model–harness pair using task reward, latency, and monetary cost. Because $p_{\theta}$ generates in $\mathcal{G}$ rather than satisfying executability by construction, every output is checked by the protocol validator. We use $\operatorname{Valid}_{\boldsymbol{\Pi}}(\mathbf{h};\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau})\in\{0,1\}$ for its validity flag; failed checks additionally return a structured diagnostic report. We instantiate Equation 8 with offline supervision in Stage I, repair-trajectory learning in Stage II, and online policy improvement in Stage III.

4.1 Stage I: Customizing Harness

Data Preparation.

Stage I uses a frozen, stronger teacher $q_{\phi}$ to synthesize task-adapted harnesses under the fixed four-module protocol. For each task, three reference scaffolds are sampled from the task-type-matched subset $\mathcal{B}_{0}^{(d(\boldsymbol{\tau}))}$ of the seed bank,

 $\mathcal{E}_{\tau}=\{\mathbf{h}^{(1)},\mathbf{h}^{(2)},\mathbf{h}^{(3)}\}\sim\operatorname{Sample}_{3}(\mathcal{B}_{0}^{(d(\boldsymbol{\tau}))}),\qquad\mathbf{h}^{\mathrm{teach}}\sim q_{\phi}\bigl(\cdot\mid\mathbf{c}_{\tau}\bigr),$ 	

(9)	

where $d(\boldsymbol{\tau})$ denotes the task type. The teacher receives the task, protocol, capability registry, and sampled scaffolds. A generation is retained only if it passes protocol validation and execution checks, yielding

 $\mathcal{D}_{\mathrm{I}}=\Bigl\{\bigl(\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau},\mathcal{E}_{\tau},\mathbf{h}^{\mathrm{teach}}\bigr)\;\big|\;\operatorname{Valid}_{\boldsymbol{\Pi}}(\mathbf{h}^{\mathrm{teach}};\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau})=1\Bigr\}.$ 	

(10)	

Stage I draws its training tasks from different sources, including (Wu et al., 2025; Shi et al., 2025; Zhang et al., 2026d; Bai et al., 2026; Burgess et al., 2026; Song et al., 2026), as well as a portion of synthesized tasks.

(11)	

where $y_{j}^{\mathrm{teach}}$ is the $j$ -th target token. This teaches JIT-Agent to map a task and a small reference context directly to a protocol-compliant harness. Protocol compliance alone is insufficient: executable harnesses can still differ substantially in task reward, latency, and monetary cost. We therefore compare candidates under the same backbone and evaluation seeds, retaining a preference only when reward improves without degrading either efficiency axis and at least one efficiency gain is strict.

 $\displaystyle\iff r^{+}>r^{-}\;\land\;\ell^{+}\leq\ell^{-}\;\land\;\kappa^{+}\leq\kappa^{-}\;\land\;\bigl(\ell^{+}

 $\displaystyle\Delta_{\mathrm{val}}(\boldsymbol{\tau};\mathbf{h}^{+},\mathbf{h}^{-})$

where $(r^{\pm},\ell^{\pm},\kappa^{\pm})$ are repeated-rollout averages for $(\mathbf{h}^{+},\mathbf{h}^{-})$ , $[x]_{+}=\max(x,0)$ , and $\alpha_{r},\alpha_{\ell},\alpha_{\kappa}\geq 0$ control the three value gaps. Here $\sigma$ is the logistic sigmoid, $\beta_{\mathrm{pref}}>0$ controls preference sharpness, and $p_{\mathrm{ref}}$ is the frozen Stage-I SFT checkpoint; in the log ratios, $\log p(\mathbf{h}\mid\cdot)$ denotes length-normalized sequence log-likelihood. Generation imitation establishes protocol-valid structure, while preference learning biases the model toward harnesses that are simultaneously more effective and more efficient.

4.2 Stage II: Repairing Harness

Data Preparation.

Stage I optimizes for protocol compliance, but executability is still not guaranteed: some generated harnesses fail static or runtime validation and therefore never enter $\mathcal{D}_{\mathrm{I}}$ . Rather than discarding these failures, Stage II converts them into repair supervision. Let

 $\mathcal{D}_{\mathrm{I}}^{\mathrm{fail}}=\Bigl\{\bigl(\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau},\mathcal{E}_{\tau},\widetilde{\mathbf{h}}^{(0)},\mathbf{g}^{(0)}\bigr)\;\big|\;\widetilde{\mathbf{h}}^{(0)}\notin\mathcal{H}^{\mathrm{exec}}_{\boldsymbol{\Pi}}\Bigr\},$ 	

(14)	

where $\widetilde{\mathbf{h}}^{(0)}$ is a failed Stage-I harness and $\mathbf{g}^{(0)}$ is its diagnostic report, including compiler errors, interface mismatches, tool-call failures, and runtime exceptions. For each failure, the teacher proposes a structured revision $\Delta^{(k+1)}\in\mathcal{P}$ from the patch space $\mathcal{P}$ , and $\operatorname{Apply}$ deterministically applies it to the current harness:

 $\widetilde{\mathbf{h}}^{(k)},\mathbf{g}^{(k)}\longrightarrow\Delta^{(k+1)}\longrightarrow\widetilde{\mathbf{h}}^{(k+1)}=\operatorname{Apply}\!\left(\widetilde{\mathbf{h}}^{(k)},\Delta^{(k+1)}\right),\qquad k\geq 0.$ 	

(15)	

After each revision, validation produces the next report $\mathbf{g}^{(k+1)}$ . We retain only trajectories that become executable within two repair rounds. Writing

 $K^{\star}=\min\Bigl\{k\in\{1,2\}:\operatorname{Valid}_{\boldsymbol{\Pi}}(\widetilde{\mathbf{h}}^{(k)};\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau})=1\Bigr\},$ 	

(16)	

Stage-II supervision is constructed only when $K^{\star}$ is well defined. This keeps the corpus focused on realistic, locally recoverable failures instead of those requiring wholesale redesign.

Training Setup.

Stage II then trains JIT-Agent to imitate successful repair transitions rather than one-shot synthesis. For each retained trajectory, let

 $\mathcal{D}_{\mathrm{II}}=\Bigl\{\bigl(\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau},\mathcal{E}_{\tau},\mathcal{R}_{K^{\star}}\bigr)\;\big|\;(\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau},\mathcal{E}_{\tau},\widetilde{\mathbf{h}}^{(0)},\mathbf{g}^{(0)})\in\mathcal{D}_{\mathrm{I}}^{\mathrm{fail}},\ K^{\star}\ \text{exists}\Bigr\},$ 	

(17)	

where $\mathcal{R}_{K^{\star}}=\{(\widetilde{\mathbf{h}}^{(j)},\mathbf{g}^{(j)},\Delta^{\star(j+1)})\}_{j=0}^{K^{\star}-1}$ and each $\Delta^{\star(j+1)}$ is the teacher revision along a repair trajectory that eventually becomes executable. The repair objective conditions on the entire history,

 $\mathcal{L}_{\mathrm{II}}(\theta)=-\,\mathbb{E}_{\mathcal{D}_{\mathrm{II}}}\sum_{k=0}^{K^{\star}-1}\log p_{\theta}\Bigl(\Delta^{\star(k+1)}\,\Big|\,\mathbf{c}_{\tau},\{(\widetilde{\mathbf{h}}^{(j)},\mathbf{g}^{(j)})\}_{j=0}^{k}\Bigr).$ 	

(18)	

Because $K^{\star}\leq 2$ , the resulting supervision targets exactly the short-horizon repair regime that matters at deployment time: given a nearly-correct but unstable harness, JIT-Agent learns to use execution feedback to produce a small number of high-leverage revisions that restore protocol-valid execution.

4.3 Stage III: Learning to Evolve Harness

Stage III treats test-time harness evolution itself as a trainable capability. The goal is not merely to recover or imitate previously observed harness designs, but to optimize JIT-Agent so that, at test time, it can repeatedly propose harnesses that surpass prior designs, become stronger future references, and keep pushing the harness frontier forward. We term the resulting online objective Evolutionary Group-Decoupled Policy Optimization (Evo-GDPO), inspired by (Liu et al., 2026b).

Data Preparation.

Stage III training examples are constructed from three synchronized sources: a task instance, a small set of prior high-quality harness designs, and fresh execution feedback collected online under that same task. Concretely, at online round $n$ , we sample a task $\boldsymbol{\tau}$ , retrieve a small reference set $\mathcal{E}_{\tau,n}$ from the current harness bank $\mathcal{B}_{n}$ , and form $\mathbf{c}_{\tau,n}=(\boldsymbol{\tau},\boldsymbol{\Pi},\mathcal{C}_{\tau},\mathcal{E}_{\tau,n})$ . The model proposes candidates that are executed beside these prior designs under the same frozen executor $\pi_{\psi}\sim\mathcal{M}$ , budget, and evaluation seeds. Within $\mathcal{E}_{\tau,n}$ , the highest-reward harness, with ties broken by lower latency and then lower cost, supplies a single incumbent whose statistics are denoted by $(b_{r},b_{\ell},b_{\kappa})$ .

Training Setup.

Given this context, Evo-GDPO first samples a group of candidate harnesses from the current policy:

 $\mathbf{h}_{i}\overset{\mathrm{i.i.d.}}{\sim}p_{\theta_{\mathrm{old}}}\bigl(\cdot\mid\mathbf{c}_{\tau,n}\bigr),\qquad i=1,\ldots,G,$ 	

(19)	

where $G>1$ is the group size and $\theta_{\mathrm{old}}$ is the rollout-policy snapshot. Every candidate is validated before execution; a candidate that remains invalid after bounded repair receives the minimum task reward, while its repair latency and cost remain part of the measured efficiency. For executable candidates, $r_{i}$ , $\bar{\ell}_{i}$ , and $\bar{\kappa}_{i}$ denote reward, mean latency, and mean monetary cost over repeated rollouts. The reward channel is primary, while the efficiency channels activate only when the candidate preserves incumbent reward.

 $\displaystyle R^{\mathrm{rew}}_{i}$ 	
 $\displaystyle=r_{i}+\lambda_{\mathrm{evo}}\,[r_{i}-b_{r}]_{+},$ 	

(20)	

 $\displaystyle R^{\mathrm{lat}}_{i}$ 	
 $\displaystyle=\mathbb{I}[r_{i}\geq b_{r}]\,[b_{\ell}-\bar{\ell}_{i}]_{+},$

5 Inference Architecture

JIT-Agent supports two inference modes: static inference and streaming inference; they differ in whether experience is discarded after the task or retained to support subsequent tasks.

Static inference.

In this mode, we introduce a lightweight form of test-time scaling: JIT-Agent generates $N$ harnesses in parallel, selects one of them, and executes only the selected harness. This increases candidate diversity without increasing the number of environment rollouts. The selected harness follows the same validation and bounded-repair procedure described above.

Streaming inference.

Streaming inference mode is designed to carry useful experience forward across a sequence of tasks. For the $n$ -th task $\boldsymbol{\tau}_{n}$ , JIT-Agent retrieves from the current bank $\mathcal{B}_{n}$ , generates and selects a harness $\mathbf{h}^{\dagger}_{n}$ , and executes it once. The resulting environment feedback is then used only to determine whether this experience should update the bank:

 $\displaystyle\boldsymbol{\xi}_{n}$ 	
 $\displaystyle\sim\operatorname{Rollout}(\boldsymbol{\tau}_{n},\pi_{\psi},\mathbf{h}^{\dagger}_{n},\mathcal{C}_{\tau_{n}};\boldsymbol{\Pi}),$ 	

(23)	

 $\displaystyle\mathbf{m}_{n}$ 	
 $\displaystyle=\operatorname{Eval}(\boldsymbol{\xi}_{n}),$ 	

 $\displaystyle\mathcal{B}_{n+1}$ 	
 $\displaystyle=\operatorname{Update}_{\mathrm{III}}(\mathcal{B}_{n};\boldsymbol{\tau}_{n},\mathbf{h}^{\dagger}_{n},\mathbf{m}_{n}),$ 	

 $\displaystyle\mathcal{E}_{\tau_{n+1},n+1}$ 	
 $\displaystyle=\operatorname{Retrieve}(\boldsymbol{\tau}_{n+1};\mathcal{B}_{n+1}),$ 	

where $\mathbf{m}_{n}=(r_{n},\bar{\ell}_{n},\bar{\kappa}_{n})$ contains reward, mean latency, and mean monetary cost. Following the Stage-III retention rule, $\operatorname{Update}_{\mathrm{III}}$ leaves $\mathcal{B}_{n}$ unchanged when the completed harness provides no admissible improvement. Otherwise, the retained harness becomes a potential reference for later tasks. Streaming inference therefore transfers prior experience through the evolving harness bank, without injecting environment feedback into the current rollout or updating model parameters.

6 Experiments and Analysis

6.1 Experiment Setup

Evaluation Benchmarks.

We evaluate JIT-Agent on nine benchmarks grouped into four task types:

• 

Deep Research: BrowseComp-Plus (Chen et al., 2025b) (accuracy), DeepSearchQA (Gupta et al., 2026) (answer F1), and xBench-DeepSearch (xBench-DS) (Chen et al., 2025a) (accuracy).

• 

Daily Work: AgentIF-Oneday (Chen et al., 2026a) (normalized weighted rubric score) and PinchBench (PinchBench, 2026) (average score).

• 

Planning: DeepPlanning-Shopping (cart match rate) and DeepPlanning-Travel (composite constraint score) subsets from (Zhang et al., 2026d).

• 

Workspace: OfficeBench (Wang et al., 2024) and OdysseyBench (Wang et al., 2025b) (task success rate for both).

Together, these benchmarks cover evidence-intensive search, long-horizon instruction following, constraint-aware planning, and multi-application workspace execution. We report all metrics on a $0$ – $100$ scale; higher is better.

Backbone Models.

JIT-Agent is trained based on Qwen3.6-27B. We primarily instantiate JIT-Agent with GLM-5.2 (Z.ai, 2026) and DeepSeek-V4-Flash-Preview (DeepSeek-AI, 2026). These backbones provide complementary operating points: GLM-5.2 is a strong open long-horizon model, whereas DeepSeek-V4-Flash emphasizes inference efficiency. To test the generalization, additional models from Qwen3.6, Mimo-V2.5 are also used.

Baselines.

We use two complementary baseline groups. First, the broad comparison includes vanilla Qwen3.7-Plus (Qwen Team, 2026), GLM-5.2, DeepSeek-V4-Flash/Pro (both preview version), Kimi K2.7 Code (Moonshot AI, 2026), GPT-5.6 (OpenAI, 2026), and Gemini 3.1 Pro/3.5 Flash (Google DeepMind, 2026a; Google DeepMind, 2026b). Second, holding the backbone fixed, we compare JIT-Agent with five reusable agent harnesses: Claude Code (Anthropics, 2025), Codex (OpenAI, 2025), OpenCode (OpenCode-AI, 2025), Hermes (Nous Research, 2026), and NanoBot (HKUDS, 2026). The first group measures end-to-end competitiveness, while the second isolates the contribution of harness design from that of model weights.

Consistent gains over the same backbone.

Across all 18 directly matched backbone–benchmark pairs, replacing the default scaffold with a JIT-generated harness improves performance. On GLM-5.2, the nine-benchmark average rises from $74.1$ to $81.8$ ( $+7.7$ points); on DeepSeek-V4-Flash, it increases from $66.7$ to $75.5$ ( $+8.8$ points). The largest gains occur on tasks that require sustained state management and constraint tracking: DeepSeek-V4-Flash improves by $24.8$ points on DeepPlanning-Shopping ( $59.1\!\rightarrow\!83.9$ ), while GLM-5.2 gains $20.2$ points on DeepPlanning-Travel ( $62.8\!\rightarrow\!83.0$ ). Search and open-ended interaction also benefit substantially, including $+11.9$ on xBench-DS and $+8.9$ on DeepSearchQA for DeepSeek-V4-Flash. These broad gains indicate that harness adaptation changes more than prompt style: it improves how the backbone allocates context, decomposes long-horizon objectives, and coordinates external actions.

Competitiveness with frontier models.

The JIT-equipped systems attain the best result in eight of the nine benchmark columns despite using open backbones. In particular, JIT-Agent + GLM-5.2 ranks first on seven benchmarks, reaching $93.9$ on DeepSearchQA, $69.9$ on AgentIF, and $93.3$ on PinchBench; JIT-Agent + DeepSeek-V4-Flash leads DeepPlanning-Shopping at $83.9$ . The latter pairing also exceeds the stronger DeepSeek-V4-Pro baseline on every reported benchmark, with an average advantage of $8.7$ points. DeepPlanning-Travel is the only column not led by a JIT-equipped model, where GLM-5.2 + JIT-Agent reaches $83.0$ , within $1.9$ points of GPT-5.6. Overall, the results support the central claim that improving the operational scaffold can recover a substantial fraction of the capability otherwise sought through backbone scaling.

On DeepSearchQA, DeepSeek-V4-Flash + JIT-Agent is a strong Pareto-optimal operating point among the evaluated pairings, scoring $85.1$ at a per-case cost of $\$0.066$ . Relative to the strongest fixed harness, NanoBot, it gains $4.7$ points while reducing cost by $49.6\%$ ( $\$0.131\!\rightarrow\!\$0.066$ ). For Qwen3.6-Flash, the generated harness provides a lower-compute operating point: it scores $70.3$ at $\$0.095$ , compared with NanoBot’s $74.2$ at $\$0.197$ , cutting cost by $51.8\%$ for a $3.9$ -point trade-off.
AgentIF exhibits a different but complementary frontier. With DeepSeek-V4-Flash, JIT-Agent reduces cost by $14.9\%$ relative to Claude Code ( $\$0.097$ vs. $\$0.114$ ) while remaining within $3.1$ points of its performance ( $63.8$ vs. $66.9$ ); both therefore lie on the frontier. With Qwen3.6-Flash, JIT-Agent strictly dominates all fixed harnesses, improving the best score from $55.4$ to $58.3$ while lowering the minimum observed cost from $\$0.170$ to $\$0.078$ . The frontier is therefore task-dependent, but the consistent leftward shift of the JIT points shows that task-adaptive harnesses improve inference efficiency rather than purchasing accuracy through longer trajectories.

6.5 Generalization across Model Pairs

To examine whether JIT harness generation transfers across model families and variants, we evaluate six backbones spanning three model pairs: DeepSeek-V4-Flash/Pro, Qwen3.6-Flash/Plus, and Mimo-V2.5-Flash/Pro. For each backbone, we hold the model fixed and compare its standard ReAct harness with the JIT-generated harness on DeepSearchQA, AgentIF-Oneday, DeepPlanning-Shopping, and OfficeBench.

Figure 5: JIT-generated harnesses consistently improve paired backbones over ReAct.
Rows group three model families and two variants within each family; columns correspond to DeepSearchQA, AgentIF-Oneday, DeepPlanning-Shopping, and OfficeBench. Each panel compares the same backbone under a fixed ReAct harness (dashed) and a JIT-generated harness (solid), with callouts reporting the absolute score gain. DeepSearchQA uses a 100-example subset; the other three benchmarks use 50-example subsets.

Across all 24 directly matched backbone–benchmark comparisons, the JIT-generated harness outperforms ReAct, with an average gain of $7.6$ points. The effect holds for every family and both variants in each pair: the average improvement is $10.2$ points for DeepSeek V4, $4.0$ for Qwen 3.6, and $8.6$ for Mimo 2.5. DeepSearchQA shows the largest average gain at $15.2$ points, including $+22.2$ for Mimo-V2.5-Pro and $+19.0$ for DeepSeek-V4-Flash; DeepPlanning-Shopping rises by $7.5$ points on average, including a $+24.8$ gain for DeepSeek-V4-Flash. These consistent within-backbone gains show that harness intelligence transfers across model families and variants rather than compensating for a particular backbone.

6.6 Test-Time Harness Evolution

JIT-Agent is designed not only to generate a harness once, but also to improve its archive from execution feedback. We compare Static JIT, where harness generations are independent, with Streaming JIT, which retrieves and updates harnesses throughout the evaluation stream.

Figure 6: Streaming test-time harness evolution across task streams.
Cumulative accuracy (top), per-task API cost (middle), and per-task tool calls (bottom) on DeepPlanning-Shopping, DeepPlanning-Travel, and OfficeBench. Dashed curves represent Static JIT, where task-specific harness generations are independent, while solid curves represent Streaming JIT, which continuously incorporates execution feedback as new tasks arrive. Shaded regions show local variation around the streaming trajectories. Streaming JIT finishes with higher cumulative accuracy on all three benchmarks, while API-cost and tool-use trajectories remain task-dependent and of broadly similar scale.

Streaming JIT finishes above the static variant on DeepPlanning-Shopping, DeepPlanning-Travel, and OfficeBench. Across all three streams, the cumulative-accuracy advantage emerges as execution feedback accumulates and remains positive through the end of evaluation. The accompanying cost and tool-call traces suggest that the endpoint gains are not uniformly coupled to larger interaction budgets. This pattern is consistent with the objective of Evo-GDPO, which retains harnesses only when they advance the archive frontier.

6.7 Visualization of Generated Harnesses

The quantitative results establish that generated harnesses improve execution; we next inspect what JIT-Agent actually generates. Figures 7 and 8 visualize two harnesses produced under the same four-module protocol for tasks with sharply different computational structure. Their differences extend beyond prompts or module names: the generated planning representation, action topology, persistent state, and exposed capabilities are reorganized around the demands of each task.

Figure 7: Palimpsest: graph-planned artifact execution. GraphPlanPlanning converts the contact-processing request into a DAG; GraphPlanAction executes it with bounded width and depth, while GraphPlanMemory stores reusable artifacts and reasoning state.

Artifact production as a dependency graph.

Palimpsest is generated for a cross-application task that must discover contact cards, exclude one person, normalize and sort the remaining records, create a workbook, and deliver it by email. The harness compiles these requirements into an explicit DAG: discovery and schema inspection provide prerequisites for filtering, workbook construction waits for normalized records, and delivery waits for artifact verification. GraphPlanAction then executes ready nodes with bounded width and depth, while GraphPlanMemory indexes intermediate goals, evidence, and artifacts so that downstream nodes consume completed results rather than reconstructing them from the transcript. The resulting harness matches the task’s artifact dependencies and commit order, turning a long natural-language request into a verifiable production pipeline.

Figure 8: Trapdoor: bounded research behind a delegated tool call. A synthesized delegate capability is intercepted by OrchestratorLoop, which runs a bounded subagent and writes extracted facts into FactGraphMemory.

Deep research as bounded recursive delegation.

Trapdoor addresses a multi-hop identity question whose clues span a historical quotation, a university merger, a memoir, and a research paper. Here a fixed DAG would commit too early to an uncertain evidence path, so the generated harness uses DynamicDecomposer to form and revise sub-questions and augments the research tool policy with a synthetic delegate capability. A delegate call opens a private research subagent with its own memory, research-only tools, and a five-step budget; the returned answer re-enters the parent loop as an ordinary observation. In parallel, FactGraphMemory extracts compact key–value facts from the growing history, allowing the parent to integrate evidence across branches without inheriting every subagent trace. Thus, the harness makes recursive research a runtime primitive specifically for a task whose uncertainty is resolved through branching evidence collection.

The contrast is the central qualitative result: the same generator maps one task to graph execution with an artifact store and another to recursive orchestration with a fact store. The shared protocol constrains interfaces, not behavior. The additional cases in Appendix A broaden this pattern to hierarchical context folding, completion-gated tool access, phase-conditioned execution, evidence-matrix search, selective context rendering, typed computational state, deterministic per-file verification, and local action repair; their flows are shown in Figures A.1, A.2, A.3, A.4, A.5, A.6, A.7 and A.8.

7 Conclusion and Future Work

Conclusion.

We introduced JIT-Agent, a dedicated model for synthesizing, repairing, and evolving task-conditioned agent harnesses at inference time. By expressing the harness through a composable four-module protocol and training the generator through customization learning, repair supervision, and Evo-GDPO, JIT-Agent turns harness construction from a manually engineered, ahead-of-time artifact into a learned capability. Across deep research, daily work, planning, and workspace tasks, JIT-generated harnesses consistently strengthen their underlying backbones, compete with frontier models and advanced fixed harnesses, and improve cost–performance trade-offs. These results establish harness intelligence, i.e., the capacity to adapt the operational scaffold through which a model acts, as a trainable and transferable source of agent capability beyond model weights alone.

Future Work.

We view harness intelligence as another fundamental dimension of scaling, alongside model capacity and inference compute, and JIT-Agent as one step toward realizing it. The longer-term opportunity is a model–harness co-design paradigm in which foundation models are trained together with the operational structures that shape their memory, planning, action, and tool use. Nevertheless, we believe future systems need not follow the deliberately radical form explored in this work, where the entire scaffold can be redesigned just in time: production runtimes may instead retain a stable core while allowing the model to construct, revise, or replace selected harness components when the task demands it. As this paradigm matures, the capabilities developed here for harness synthesis, repair, and evolution will increasingly be internalized by foundation models themselves. Models will then learn not only to act within a given harness, but also to improve the harness through which they act, opening a broad research agenda around adaptive interfaces, verifiable runtime modification, and jointly scaling models with their execution systems.

Appendix A Additional Generated Harness Visualizations

This appendix complements the two representative cases in Section 6.7 with eight additional harnesses generated under the same four-module protocol. The examples span constraint-heavy shopping and travel, phased web production, clue-driven research, evidence-sensitive retrieval, numerical analysis, and workspace manipulation. They are not variants of a single execution template: JIT-Agent selects a state representation and control regime suited to the structure of each request, then instantiates planning, action, memory, and capability orchestration around that choice. Collectively, the cases make task-conditioned harness customization visible at the level of execution semantics rather than prompt wording.

Figure A.1: Origami: hierarchical work with folded context. ROMAPlanning creates isolated subtasks; HierarchicalMemory retains their trajectories and artifacts while fold_thought replaces only the active working context before aggregation.

Figure A.2: Turnstile: evidence first, itinerary second. TravelPlanning emits a travel specification and checklist, DataStoreMemory tracks the required evidence buckets, and DynamicToolPolicy exposes final_answer only after is_complete() succeeds.

Figures A.1 and A.2 illustrate two task-specific ways to control long-horizon execution through memory. Origami must assemble a seasonal wardrobe under coupled stock, delivery, size, review-count, and rating constraints. ROMAPlanning decomposes the request into dependent product searches, HierarchicalAction runs at most two branches in parallel to bounded depth, and each branch retains its own trajectory and artifacts. When a branch grows long, fold_thought replaces only its active working context; completed subtask results remain available for the final constraint check. The harness therefore spends context on the unresolved portion of a combinatorial shopping task without discarding earlier product evidence.

Turnstile, by contrast, serves a travel request that specifies dates, passengers, rooms, a departure window, a highest-rated hotel, attractions, meals, and daily routes. The generated TravelPlanning module compiles these obligations into a typed travel_spec and collection checklist, and DataStoreMemory assigns a dedicated bucket to each evidence class. DynamicToolPolicy exposes search tools for the missing bucket but withholds final_answer until is_complete() succeeds. Here memory is not used primarily to compress a long trace; it acts as an executable coverage contract that prevents itinerary synthesis before the required travel facts have been collected.

Figure A.3: Gearbox: one phase shift rewrites the agent. PhaseAction is the sole writer of a shared phase register; PhaseToolPolicy and PhaseAwareMemory read that state to switch both exposed capabilities and typed memory schemas.

Figure A.4: Pegboard: research as an evidence matrix. Every observation is extracted into a candidate $\times$ clue cell with a document identifier; matrix coverage drives both DynamicResearchPlanning and the transition to source-grounded verification.

Figures A.3 and A.4 show how explicit state can continuously reshape later decisions. Gearbox is generated to find Chinese restaurants within a specified driving radius and publish the results as an interactive one-page guide. Its PhaseAction is the sole writer of a shared search–collect–build register; the transition to construction occurs only after enough structured restaurant records have been gathered. Both PhaseToolPolicy and PhaseAwareMemory read that register, switching from web discovery, to record inspection, to code and publication while compressing observations into the schema needed by the current phase. The model thus creates a phase machine because the task changes modality from evidence acquisition to artifact construction.

Pegboard instead tackles an identification problem defined by six biographical and film clues. It represents progress as a candidate $\times$ clue matrix in which every extracted claim retains its document identifier. Empty cells and contradictions drive DynamicResearchPlanning toward targeted searches, while a sufficiently supported row triggers a separate verification phase that reopens cited documents and resolves conflicts. Unlike a generic research transcript, this state makes coverage and source provenance directly actionable. The contrast with Gearbox shows that generated state may be a small phase variable or a task-shaped evidence structure, depending on what must govern the next action.

Figure A.5: Appraiser: evidence decides what the model sees. EvidenceGuidedReAct scores every step, while EvidenceGuidedMemory stores the full run but renders only the first, last, and top- $K$ observations into build_context().

Figure A.6: Abacus: from computation to reliable typed state. StructuredReActAction executes shell or Python code, extracts a RESULT_JSON payload from standard output, and updates StructuredStateMemory without asking the model to re-derive computed values.

Figures A.5 and A.6 customize what subsequent reasoning receives from prior execution. Appraiser answers a classical materia-medica identification question by reconciling botanical traits with textual evidence. After every search or reading step, an auxiliary scorer assigns the observation an evidence value; EvidenceGuidedMemory keeps the complete trajectory for auditability but renders only the first, last, and top- $K$ observations into the next context. Low-value exploration therefore stops competing with the passages most useful for identification, while no evidence is erased from persistent history. This harness is tailored to a retrieval task in which the main bottleneck is evidence salience rather than tool choice.

Abacus is generated for a numerical analysis request that first compares regional averages and then ranks countries within the winning region. The harness deliberately moves aggregation out of language-model reasoning: StructuredReActAction invokes shell or Python, extracts a marked RESULT_JSON payload from standard output, repairs its syntax if necessary, and writes the values into StructuredStateMemory. Region, country, regional mean, and country mean are then injected as typed state into every later step, so the final answer reports interpreter-derived quantities instead of re-deriving them from prose. Both cases preserve a full audit trail, but each renders the working view around its task’s dominant reliability requirement—evidence selection for one and numerical fidelity for the other.

Figure A.7: Player Piano: typed batch editing, verified file by file. A Python dispatcher interprets StructuredPlanning steps, SelfVerifyingAction checks each edit without an LLM, and ProgressiveTaskMemory maintains a per-file board and artifact store.

Figure A.8: Mulligan: repair the step, preserve the history. PlanAwareToolPolicy exposes only plan-relevant file and document tools; failed actions are regenerated at the same step, and FullHistoryMemory receives only the successful execution.

Figures A.7 and A.8 specialize workspace execution at different scales by controlling when actions enter persistent history. Player Piano handles a batch migration of configuration files, including database, logging, and API-endpoint changes. StructuredPlanning emits typed discover, process-file, and final-answer steps that a Python dispatcher executes; after each edit, a deterministic non-LLM check decides whether to advance or retry. ProgressiveTaskMemory renders a per-file board into the system prompt and retains both originals and accepted changes, preventing a large batch from losing track of which files have actually passed verification.

Mulligan is generated for a shorter document task: extract a student identifier from a DOCX file and rename that same file. Its linear plan needs no hierarchy or context compression, so the harness retains full successful history and exposes only Word and file operations while hiding unrelated email, spreadsheet, and PDF tools. If an action fails, the loop appends the error locally and regenerates the same step for at most two attempts; only a successful action is committed before the plan advances. The two harnesses therefore share a concern for reliable workspace mutation but realize it differently: one uses typed batch progress and per-file verification, whereas the other uses narrow tool exposure and transactional step repair. This task-dependent difference is precisely the behavior sought from JIT-Agent: reliability mechanisms are generated to fit the structure and failure surface of the request rather than imposed as one universal scaffold.
