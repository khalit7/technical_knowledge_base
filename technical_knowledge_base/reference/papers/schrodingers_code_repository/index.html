Schrödinger's Code Repository: Have LLMs Learned SWE-bench or Memorized It? (SchrodingerRepo)

Silin Chen, Yufei Yang, Xiaodong Gu, Yuling Shi, Chengcheng Wan, Haibing Guan
Shanghai Jiao Tong University (four authors), Xi'an Jiaotong University, East China Normal University and Shanghai Innovation Institute · arXiv v1 submitted 21 August 2026, the only version so far (checked 3 October 2026)

In one line: Instantiating the test repository dynamically under four behaviour-preserving transformations consistently degrades agent performance and raises interaction cost on SWE-bench Verified and SWE-QA, so part of a repository-level coding score is knowing where to look rather than knowing what to do. (The database Takeaway, kept as written. Two qualifications from this page: "consistently" holds for Pass@1 on SWE-bench Verified, but on SWE-QA DeepSeek-v4-Flash moves 0.55 points and two of its levels score higher; and the evidence shows unfamiliar names cost exploration, not that the familiar ones were memorised.)

How far to trust it: Believe the direction: renaming a repository's own identifiers reliably costs agents exploration and a few points of Pass@1. Do not read it as proof of memorisation. The renamed names also lose meaning, the one control for difficulty (one model, 110 fresh tasks, 19 solved) could not have detected the drop it was meant to rule out, Gemini's 14.4 points come from the 300 most-leaked instances, two printed changes are wrong, and the released code builds Levels 1 and 3 differently from the text. Where the "6 to 14 points" comes from

The old summary carried the gap as "6 to 14 points", attributed to the paper aggregator that surfaced the work, because the abstract states only the direction. The abstract does give no number, but the paper itself does: finding ❶ in §I and the conclusion (§VIII) both say the full transformation "reduces Pass@1 by 6.0–14.4 percentage points across the evaluated models", from Table I. So the range is the paper's own number, and its top end (Gemini-3.1-Flash-Lite, 14.4) was measured on a different, leakage-selected subset of 300 instances; the other three models span 6.0 to 11.2. The second provenance note also checks out: the arXiv abstract page shows "Submitted on 21 Aug 2026" (checked 3 October 2026), and the paper reached this knowledge base through the 24 September 2026 trending digest, which is why it was not recorded earlier.

Problem: one fixed copy of every test repository

§I, §II

SWE-bench turns 2,294 real GitHub issues into tasks with executable environments and test-based grading; SWE-bench Verified is the manually checked subset of 500 that frontier agents report (§I). Every task is shown through one canonical copy of a popular open-source repository (Django, scikit-learn, sympy, ...), the same copy that sits in public training data. A high score could mean the agent reasons about code, or that it remembers where things are in Django (§I).

The fix so far has been the calendar: SWE-bench Live, SWE-rebench and SWE-bench Pro keep adding issues created after a model's release. The paper's complaint is that fresh sets stay small and narrow in issue types, and that a set refreshed monthly cannot hold a stable time series (§I, §VII-A).

The motivation experiment: what models recall before seeing the repository

Before any agent runs, human experts split each Verified issue into "semantic units" from broad to specific and reveal them one round at a time, together with the instance ID; no repository, patch or test is shown. After each round they judge whether the model's answer contains task-specific content not yet in the prompt, sorting the result into four grades (§II):

Figure 1, redrawn from its printed bar labels (each model, all 500 Verified instances). The paper's summary: "more than 65% of instances exhibit clear data-leakage evidence, and more than 18% of instances can be recalled at the patch/test level". Recounted: leakage shares are 65.8% (DeepSeek-v4-Flash) to 75.2% (Gemini-3.1-Flash-Lite); patch/test recall is 18.0% for GPT 5.1 (exactly, not more than), 18.6% GPT-5.4-mini, 27.8% Gemini, 29.2% DeepSeek.

Read the grades before reading the 65%. Most of it is file/symbol recall: naming the affected file or function. Given a Django issue about get_FOO_display(), a competent engineer who has never seen the task would also guess django/db/models/fields/__init__.py; that is knowing Django, not remembering the benchmark. The grades that point to the task itself, recalled fix logic or patch and test lines, cover 18.4 to 35.8% of instances. The judging is by humans with no reported agreement rate, and the prompt includes the instance ID (for example django__django-11999), itself a strong cue. The figure motivates the study; it is not a contamination measurement.

Idea: draw the repository only when the agent walks in

§III-A, Figure 2

Instead of transforming the benchmark once (and leaking the new version too), SchrodingerRepo treats the repository as a latent variable: a seed decides the concrete view when the agent enters the container, so every run can see a different but equivalent repository (§I). The task is identical; the familiar cues are gone. Two things make this safe to grade (§III-A):

  • An invertible mapping. Names are changed only in what the agent reads and translated back in what it executes, so commands run in the real SWE-bench container.
  • Patch recovery from file states (§III-G). The submission is the diff between each changed file's original and final contents, final_submission = ⊕f ∈ CB Diff(bf, r′f), so grading uses the standard tests on the original repository whatever view the agent worked in.

How a command travels, drawn from §III-C and Figure 2. Levels 1 and 2 act on the observation layer (the issue text, command output and the agent's commands); Levels 3 and 4 change the working copy itself, which is then checked against the original tests.

The four levels

§III-B to §III-F

Each level removes a different kind of familiar cue while keeping the task, its tests and its behaviour. The panel below applies the renamings the paper itself shows for its Django case study to that task's real issue and file paths; the Transform a repository tab runs the released algorithm with any seed.

Level 1: problem statement reconstruction
A generator LLM reorders, paraphrases and prunes the issue; a verifier LLM checks no task-defining constraint was lost and triggers a refinement if one was; a human engineer reviews the result (§III-B, §III-F).
Level 2: namespace mapping
Repository-owned identifiers (classes, functions, module variables, import references, files, directories) are extracted from the syntax tree; Python builtins, keywords and third-party names are filtered out; each identifier is split into tokens, each token mapped to a "semantically plausible" alternative under a seed, and names rebuilt keeping CamelCase, snake_case and UPPER_CASE. The mapping is consistent: QuerySet becomes LedgerSuite and every other "Query" becomes "Ledger" (§III-C). A translator rewrites observations into the virtual namespace and actions back; a session notebook restricts reverse translation to names it actually emitted (§III-F).
Level 3: intra-file layout reordering
Within each contiguous run of top-level definitions or methods, a dependency graph of definition-time name uses (decorators, defaults, annotations, base classes) is built and a random topological order sampled; the reordered file must still pass every Pass-to-Pass test and still fail every Fail-to-Pass test (§III-D, §III-F).
Level 4: functionality-preserving rewrite
A constrained rewriting agent restates the code region tied to the fix "in a behaviorally equivalent yet substantially different form", validated by the same two test conditions (§III-E).

Validity checks: human reviewers inspected 100 random instances per level and confirmed the same task, the same issue and equivalent information (§III-F). No disagreement count is reported.

What the released code does differently

§III against the code

The released repository (MIT, commit e2eef98 of 24 September 2026) contains the builders and the translator. Read against the text, four things differ; none is mentioned in the paper.

  • Level 3 picks its files from GPT-5.4-mini's own runs, not from the gold patch. The paper says reordering "is applied only within golden-patch-related files" (§IV-C). The released builder ranks files by how often a baseline GPT-5.4-mini trajectory edited, read, hit in a traceback or searched them (weights 5, 3, 2, 1) and takes the top 8 (trajectory_hotspots.py, build_verified_level3_store.py, default trajectories_baseline_gpt54mini); the README calls this the "lite path". Level 4 does use the gold patch (extract_rewrite_targets_from_golden_patch). So the Level 3 view of every model was shaped by where one of the tested models looked.
  • Level 1 in the code is one paraphrase that keeps identifiers. translate_verified_problems.py asks gpt-5.4-mini, at temperature 0, to reword the issue and to "keep code identifiers, file paths, API names, class/function names, issue numbers, and fenced code blocks verbatim". There is no verifier stage in the release, and the paper's description removes identifiers "when not functionally required". The rewriter is also one of the four models under test. The code's Level 1 additionally replaces the repository's name with the fixed alias working_repository (identity_l1), which the paper assigns to Level 2.
  • Fewer views than three per level by default. The paper averages three seeded views for every level (§IV-C); the released defaults build one Level 2 mapping variant (LEVEL2_VARIANT_COUNT=1, seed 42) and one Level 3 variant (--target-variants 1), three only for Level 4. The authors may have overridden them; the release does not say.
  • An instance whose transformation fails runs untransformed. If no verified Level 3 or Level 4 variant exists (for example every reordering broke a Pass-to-Pass test), swebench_mapped.py records "skipped" and runs the agent on the original repository. The paper does not say how many instances were transformed, so the Level 3 and 4 rows mix transformed and untransformed instances in unknown proportion, which would shrink their effects.

The candidate words for Level 2 come from openai/gpt-5-mini, asked for "5 semantically equivalent but lexically different alternative terms" per token (mapper.py); the generated lexicons, mappings, variants, trajectories and per-instance results are not released.

Setup

§IV
  • Agent: mini-swe-agent with default configuration, temperature 0, at most 250 actions per instance (§IV-A, §IV-C).
  • Models: GPT-5.4-mini, GPT 5.1, DeepSeek-v4-Flash on all 500 Verified instances; Gemini-3.1-Flash-Lite only on the 300 instances with the strongest leakage evidence in Figure 1. The behaviour analyses (RQ2, RQ3) use GPT-5.4-mini and DeepSeek-v4-Flash; RQ4 uses GPT-5.4-mini alone (§IV-A).
  • Research questions (§IV): RQ1, how much do repository-side representations move issue resolution (all four levels jointly and one at a time)? RQ2, how does behaviour shift across six action types (navigate, search, read, probe, edit, test)? RQ3, does it transfer to repository question answering (SWE-QA)? RQ4, are the transformed tasks intrinsically harder (fresh SWE-rebench tasks)?
  • Metrics: Pass@1 (share solved in a single run), the SWE-QA Average Score, average actions, input tokens and output tokens per instance (§IV-B).
  • Scope and repeats: Levels 3 and 4 touch only the files and code regions "implicated by the golden patch" (but see the code note above); every level is run on three seeded views and averaged (§IV-C).

RQ1: Pass@1 falls, mostly because of the names

§V-A, Table I
Each level was also run on its own. Which single level cost the most Pass@1?

Level 2, for every model: 7.4 points for GPT 5.1, 6.4 for GPT-5.4-mini, 6.0 for DeepSeek-v4-Flash, each starred at p<0.01 (§V-A). Rewording the issue alone changes nothing for the two GPT models (DeepSeek-v4-Flash loses 2.0, not significant), and Levels 3 and 4 cost 0.8 to 3.4 points. For DeepSeek-v4-Flash, Level 2 on its own already accounts for the whole joint drop.

Table I as printed, one row of bars per model, the baseline as a grey tick. Stars are the paper's (* p<0.05, ** p<0.01); the paper does not name its test. Gemini-3.1-Flash-Lite ran only baseline and the full setting, on 300 leakage-selected instances, and its row carries no star although the text calls every full-setting drop significant. The whiskers on Pass@1 are this page's unpaired 95% intervals for the change (N instances on each side; a paired test can be tighter): recompute.py.

With all four levels on, Pass@1 drops by 6.0 (DeepSeek-v4-Flash, 72.8% to 66.8%), 8.4 (GPT 5.1), 11.2 (GPT-5.4-mini, 46.8% to 35.6%) and 14.4 points (Gemini-3.1-Flash-Lite, 56.7% to 42.3%), "statistically significant at p<0.05" (§V-A). Actions rise by 61.5 to 116.0% and input tokens by 136 to 255%; the text's "more than 2.5×" holds for GPT-5.4-mini (3.55×), DeepSeek-v4-Flash (3.54×) and GPT 5.1 (2.61×) but not for Gemini-3.1-Flash-Lite (2.36×). The authors' reading: since task, environment and tests are unchanged, the degradation reflects familiarity with canonical repository cues, "distributed across multiple levels of repository presentation rather than concentrated in naming structure alone" (§V-A).

A printed change that is wrong

Table I gives GPT-5.4-mini's Level 1 actions as 11.56 "(↑ 12.78%)". From 11.25 to 11.56 is +2.76%. Every other change in Tables I to III recomputes within rounding except one in Table II (below); see the checks.

RQ2: the extra effort goes into finding things

§V-B, Figure 3
GPT-5.4-mini needs 8.6 more actions per task in the renamed repository, DeepSeek-v4-Flash 53.6 more. Where do they go?

81.6% (GPT-5.4-mini) and 83.6% (DeepSeek-v4-Flash) of the extra actions are localisation and exploration; editing takes 15.5 to 18.5% and testing 1% or less (§V-B). The fix is the same size; finding where it goes is what got harder.

Figure 3 from its printed wedge labels: the split of the additional actions (full setting minus baseline); the black tick separates the four exploration kinds from edit and test. DeepSeek-v4-Flash's four exploration wedges sum to 83.7 against the text's 83.6, and its six labels to 100.2 (rounding); GPT-5.4-mini has no Test wedge. In actions per task: DeepSeek-v4-Flash 46.19 to 99.78 (44.9 extra exploration actions), GPT-5.4-mini 11.25 to 19.83 (7.0).

The two models explore differently. DeepSeek-v4-Flash leans on probe (running small scripts against the code, 31.4% of its extra actions), then read (19.4%) and search (17.9%); GPT-5.4-mini reads (41.8%) and searches (33.1%) and almost never probes (3.7%). GPT 5.1 looks like GPT-5.4-mini and is not drawn (§V-B). The paper links strategy to robustness: DeepSeek-v4-Flash already explores heavily at baseline (46 actions against 11), explores more under transformation and keeps more of its Pass@1 (a 6.0-point loss), while GPT-5.4-mini stays economical and loses more (11.2), "a trade-off between exploration intensity and robustness". That is two models, so it is a hypothesis, not a finding.

RQ3: the same pattern on repository question answering

§V-C, Table II

On SWE-QA (144 questions, 48 each from Conan, Reflex and Streamlink), GPT-5.4-mini's average score falls from 70.35 to 65.71 (4.64 points), DeepSeek-v4-Flash's from 72.97 to 72.42; actions rise 18.15% and 43.02% and input tokens 34.65% and 59.10% (Table II). Level 2 again does the damage (GPT-5.4-mini 3.95 of the 4.64 points), Level 1 does nothing, and Levels 3 and 4 matter less than in issue resolution because answering a question needs the right context but no edit-and-test loop (§V-C).

The second wrong change, repeated in the conclusion

Table II prints DeepSeek-v4-Flash's full-setting score as 72.42 "(↓ 0.75)". 72.97 minus 72.42 is 0.55. The abstract-level summary in §VIII ("scores drop by 0.75–4.64 points") inherits it. Two of DeepSeek-v4-Flash's four single levels (Level 1, +0.08; Level 4, +0.04) raise its score, so "consistently" does not hold for SWE-QA quality, only for cost. No significance is reported for Table II; the paper gives no spread to judge a 0.55-point change on 144 questions against.

RQ4: on fresh tasks, the cost rises but Pass@1 does not move

§V-D, Table III

The control for "maybe the transformed repository is just harder": run the full setting on the March 2026 SWE-rebench split, 110 tasks created after GPT-5.4-mini's release. Pass@1 stays at 17.27% (19 of 110) while actions rise 8.15%, input tokens 22.01% and output tokens 15.58% (Table III). The authors conclude the transformations "do not make the underlying issue-resolution tasks more difficult", and add that the cost increase is larger in widely used, long-standing repositories (§V-D; no numbers are given for that).

If the transformations cost GPT-5.4-mini the same 24% of its Pass@1 on fresh tasks as on Verified, it would drop from 17.3% to about 13.1%. How likely was a 110-task test to see that?

About 13% power at p<0.05: the 95% interval for "no change" on 110 tasks is ±10 points, and reliably seeing a drop (80% power) needs about 14 points, nearly the whole 17.27% (unpaired; a paired test with few flips would do better, but the paper does not report one). "Pass@1 preserved" is therefore weak evidence that the tasks did not get harder. The action counts are the stronger contrast: +8% here against +76% for the same model on Verified.

So RQ4 rests on one model, one split and a small sample. What it does show clearly is that renaming costs much less exploration in repositories the model cannot have seen: GPT-5.4-mini's actions rise 8.15% on SWE-rebench against 76.3% on Verified, input tokens 22% against 255%. That contrast, not the unchanged pass rate, is the paper's best evidence that familiarity rather than difficulty drives the Verified results; even so, the two sets differ in repositories and difficulty (17% against 47% baseline), so it is not a matched comparison.

Case study: the same Django bug, two repository views

§V-E, Figure 4

The issue in django__django-11999: since Django 2.2 a user-defined get_FOO_display() is silently replaced by the generated one (Django ticket 30931, opened 30 October 2019; the SWE-bench task is the pull request of 31 October 2019). The fix is four lines in Field.contribute_to_class: install the generated method only if the class does not already have one. Step through the agent's path in each view; the step texts follow §V-E and Figure 4, the renamed paths are the ones the figure prints, and the lit entries follow the text.

Only the steps Figure 4 describes are drawn; the paper gives the totals (37 and 217 actions, 5.9 times as many) but not the actions in between, so the action bar fills only at the last step. The files named in the text are lit as named; which tree entries stand for "surrounding logic, tests, configuration" is this page's illustration. Which model ran this case is not stated.

Both runs submit the same patch, recovered from the final file states and translated back. The renamed run is not lost; it is slow: it lists directories, enumerates Python files, searches source and tests for display-related methods, reads surrounding registration code, tests, configuration and a reproduction script, and only then patches render_%s_label. "SchrodingerRepo changes the interaction process ... rather than making the underlying repair intrinsically different" (§V-E). Notice also what the renamed issue says: the transform tab shows that the prose words override, function, models and choices are themselves Django identifiers, so the released translator renames them inside the issue's English as well.

How much of this to believe

§VI and the evidence above

What holds up. The direction is consistent where it is measured at scale: on SWE-bench Verified all three models run on 500 instances lose Pass@1 under Level 2 and under the full setting, and those drops are about two standard errors or more even on a conservative unpaired reading (Level 2: z = 2.0 to 2.4; full setting: 2.1 to 3.6; intervals). The cost increase is large and points the same way for every model, task family and level that touches names, and it shows up in a mechanism that makes sense: the extra actions are search and reading, not editing. The case study shows the same patch reached by a much longer path. The authors name two limits themselves, Python-only benchmarks and command-line-only tools (§VI), which counts in their favour.

What is weaker than it reads.

  • "Memorised" is not separated from "meaningful". Level 2 replaces QuerySet with LedgerSuite and CharField with Character_unitField. That removes a memorised cue and also a well-chosen name; a human Django expert would slow down too, and so would a model that had never seen Django but knows what a CharField usually is. The design has no condition that keeps names meaningful but unfamiliar (for example a renamed but equally descriptive vocabulary judged by people), so the drop is an upper bound on the memorisation share.
  • The control for difficulty has almost no power. RQ4 is one model on 110 tasks with 19 solved; a drop of the size Verified implies (about 4 points) would be detected about 13% of the time (RQ4). Only the action counts there are informative.
  • Not like for like across models. Gemini-3.1-Flash-Lite ran on the 300 instances "having the strongest data-leakage evidence" (§IV-A), selected by the same motivation experiment, so its 14.4-point drop, the top of the headline range, is on the subset most likely to show one. Its row has no significance mark.
  • One run per setting, unnamed test. Temperature 0 and one baseline run; the transformed settings average three views (by the paper; one or three by the released defaults). The stars on GPT-5.4-mini's Level 3 (3.4 points) and Level 4 (2.2 points) need a paired test with very few instances flipping the other way: at p<0.05 a drop of 11 instances survives at most 10 fail-to-pass flips (the McNemar arithmetic). Agents at temperature 0 are not fully deterministic, so without per-instance results the stars cannot be checked.
  • Two printed changes are wrong (Table I's +12.78% for +2.76%, Table II's 0.75 for 0.55, the second repeated in the conclusion), and the text's "more than 18%" is exactly 18.0% for GPT 5.1. Small, but they are the only numbers a reader can check.
  • The released code builds two levels differently from the text (Level 1 without a verifier and keeping identifiers; Level 3 on GPT-5.4-mini's trajectory files, not the gold patch), and untransformable instances silently run on the original repository (above). Nothing that would let anyone recompute a table (mappings, variants, trajectories, per-instance results) is released.
  • The motivation figure measures a mixture. Two thirds of its "leakage" is naming the right file or symbol from an instance ID and partial issue text, which domain knowledge also explains (Problem).
Verdict. Believe that repository-level scores on SWE-bench Verified are sensitive to whether the agent recognises the repository's names, and that the sensitivity shows up first as cost (search and reading) and then as a few points of Pass@1. Treat the size as provisional and the word "memorised" as an interpretation: the experiment cannot tell recalled cues from meaningful names, its difficulty control is underpowered, and the released code does not match the method as described in two places.

What it takes to use this

§IV-C, the repository
  • Code and licence: cslsolow/Schrodinger-Repo, MIT. It ships builders for each level (build_level1.sh to build_level4.sh), run scripts and a patched mini-swe-agent with the translator. It does not ship the generated artefacts, so you rebuild them.
  • What a rebuild costs: LLM calls for Level 1 (gpt-5.4-mini per issue), for the Level 2 lexicon (gpt-5-mini, 30 tokens per call) and for Level 4 (a rewriting agent, 12 candidates for 3 verified variants per instance); Docker runs of the SWE-bench test suites to validate every Level 3 and 4 variant; and for Level 3 as released, baseline trajectories of the model you test (or GPT-5.4-mini's). On Django alone the released extractor finds 1,400 classes, 2,718 functions, 780 modules, 298 files and 198 directories to consider for Level 2 (run here on the 11999 base commit).
  • What to expect: 2 to 3.5 times the input tokens per task under the full setting, and 1.6 to 2.2 times the actions (Table I); budget the evaluation accordingly. Level 2 alone carries most of the effect at a fraction of the build cost (no Docker validation, no rewriting agent).
  • Limits: Python repositories, command-line agents. Agents with language-server or IDE tools would need every tool's output translated consistently, which the authors leave to future work (§VI, §VIII).
  • When it pays: as a paired companion to a static score (report Verified and SchrodingerRepo-Verified side by side, as Topic: benchmarks suggests), or to compare scaffolds' exploration strategies. When it buys little: on fresh or private repositories, where there is nothing familiar to remove.

Why it matters (beyond the paper)

It is the third sensitivity a repository-level score conceals, recorded on Topic: benchmarks beside two others: a harness-sensitive number needs its harness (StateM, ARC-AGI-3's 62.7% against 99.9% for one model), and an item-defective suite needs its residual decomposed (Re-grading six physics benchmarks). The third: a repository-level number needs to say whether the repository was familiar.

SWE-rebench answers that by the calendar, this answers it by construction. Refreshing a set monthly keeps contamination out of new items; transforming a set keeps it out of the items you already have, and the second preserves the time series that the first destroys. The RQ4 caveat above applies to both: a fresh split is small, so a single-model comparison on it says little about pass rates. The practical reading for anyone quoting SWE-bench Verified: part of the score is knowing where to look rather than knowing what to do, and the part is largest exactly where agents explore least.
