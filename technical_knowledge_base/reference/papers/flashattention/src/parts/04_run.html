Run the kernel

One attention computation, forward pass, run three ways on the same random input: standard attention ({{Algorithm 0|ax:alg0}}), FlashAttention ({{Algorithm 1|ax:alg1}}, K and V in the outer loop) and the loop order {{FlashAttention-2|https://arxiv.org/abs/2307.08691}} switched to (Q in the outer loop). The arithmetic is real: the page computes every tile, every running maximum and every rescaling in your browser, and at the end compares the output with the plain formula. Everything is drawn to one scale, one small square per value: the top band is HBM, the bottom band is the on-chip SRAM, and blocks fly between them as they are read and written.

Try: play standard attention first and watch S and P fill: two N × N matrices written to HBM, each read back. Then switch to FlashAttention: the N × N area stays an outline, only tiles light up on chip, and the HBM counter ends at about half (a third with masking and dropout ticked). Change the block size to 4 and the advantage nearly vanishes; to 16 and it grows. That is Theorem 2 in miniature.

Toy sizes, chosen so the whole picture fits: N = 32 rows, head dimension d = 4, square blocks (B_r = B_c); real kernels use N in the thousands, d = 64 or 128 and blocks of 64 to 256 rows, which the panel below handles. Counts are values moved across the HBM boundary, read or written, exactly as the algorithms' load and write lines say; standard attention's "by blocks" matrix multiplies are counted as one read of each input, as in the proof of {{Theorem 2|ax:A3}}. Inputs are Gaussian, Q and K scaled by 1.5 so that the running maxima move. The animation runs only while it is on screen, and starts paused, one step at a time, if your system asks for reduced motion.

The same counters at the paper's scale

The counts the animation keeps, as formulas from Algorithms 0 to 4, for forward and backward together, at any size. The defaults are {{Figure 2|ax:S3.F2}}'s GPT-2 medium workload: N = 1024, d = 64, 16 heads × batch 64, fp16, with the A100's 192 KB of SRAM per streaming multiprocessor ({{§2.1|ax:S2.SS1}}) setting the block size by Algorithm 1's rule B_c = ⌈M / 4d⌉.

GB is 109 bytes at 2 bytes per value. "Time at bandwidth" divides bytes by the A100's 1.5 TB/s ({{§2.1|ax:S2.SS1}}) and "time at peak" divides the matrix-multiply FLOPs by the A100's 312 TFLOPS fp16 tensor-core peak ({{NVIDIA A100 datasheet|https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf}}); both are lower bounds, not predictions. The block-sparse density s scales the T_c passes, as in {{Proposition 4|ax:Thmtheorem4}}.

Why bigger blocks stop helping

{{Figure 2|ax:S3.F2}} (middle) sweeps the block size B_c and reports that the forward runtime falls as blocks grow, until about 256, after which "the runtime is then bottlenecked by other factors (e.g., arithmetic operations)" ({{§3.2|ax:S3.SS2}}). The figure prints no values, so nothing here reproduces it; what can be drawn is the reason. Runtime can be no shorter than either the time to move the forward pass's HBM bytes or the time to do its matrix multiplies. The first falls as B_c grows; the second does not move.
