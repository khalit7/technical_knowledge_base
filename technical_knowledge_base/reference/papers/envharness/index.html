Problem: environments that never change

§1 Introduction

LLM agents learn by acting in environments: software repositories, web interfaces, text or embodied simulators. Each environment presents tasks, keeps state, answers actions and judges success (§1). They are expensive to build, because people hard-code the interaction logic and the verifiers, and once built they are static: they behave the same whichever agent trains in them and however good it has become. That limits learning in two ways. A static environment cannot aim at one agent's particular weaknesses, and once the agent solves its tasks it has nothing left to teach (§1).

The usual fix is to generate environments automatically, and it has two structural flaws (§1):

  • Generators are domain-specific. A pipeline that builds web environments (InSTA), programming ones (SWE-Gym) or tool-use ones does not transfer to the others.
  • Correctness is costly and unreliable. Environments and verifiers written by an LLM must be over-generated and heavily filtered (SWE-smith, Agent World Model), and still come with no guarantee that the verifier is right.

Generated environments are also static once made: they do not move as the agent improves (abstract).

Idea: a harness for the environment

§2.1, Table 1

An agent harness is the software around a frozen model (execution loop, tool registry, memory, context management) that turns it into an agent without changing its weights: Agent = Model + Harness (§2.1). EnvHarness applies the same trick to the other side of the loop: Customized Env = Static Env + EnvHarness. Plug-in components wrap a frozen environment and change what flows through its standard interface, while its code stays untouched (Table 1).

Table 1, verbatim: "Both scale capabilities through external layers rather than changing the core system."

Formally (Eq. 1), an environment is a tuple E = (𝒮, 𝒜, 𝒪, T, R, s0): states, actions, observations, the transition function T: 𝒮 × 𝒜 → 𝒮, the reward R induced by the verifier, and the initial state. A component is an environment-agnostic transformation E′ = w(E) that works strictly at the interface: it can change the initial state, filter the exposed action and observation spaces and update the transition mechanics, but never the simulator backend. Because every intervention stays outside, the ground-truth evaluation logic is preserved and the original verifier still scores the episode. That is the paper's answer to the reliability problem: no generated verifier anywhere.

The three components

§2.2, Eqs. 2 to 5

The paper introduces three component types, "chosen to cover three fundamental modes of environment customization", and expects more to follow (§2.2). Each overrides a standard interface method. The running example is one ALFWorld task, "put a clean mug on the desk", whose default instance leaves the mug in the open and ends as soon as it is placed.

  • Stage, wstage,δ, overrides reset(): a list of actions δ = (a1, ..., ak) applied to the initial state, s0′ = T(...T(s0, a1)..., ak), nothing else changed (Eq. 2). Harder: take mug 1, open drawer 1, put mug 1 in drawer 1, close drawer 1, so the agent must search. Easier: clean the mug in advance. The code replays δ through the ordinary inner.step(), so the start state is always reachable and the saved form is just the action list (Appendix C.3).
  • Contract, wcontract,r, overrides step(): a triplet r = (fA, fT, fO), each the identity by default, rewriting the action space, the transition dynamics and the observation space (Eq. 3). It enforces preconditions, masks or augments observations and attaches structured feedback. On the mug task: fO truncates the room description after two sentences, so the agent builds its picture of the room step by step; fT blocks "clean mug" unless the agent holds it; fA removes teleport navigation. A blocked action leaves the world untouched and returns the current, filtered observation with the reason, and Contract never touches s0 or R (Appendix C.3).
  • Chain, wchain,ℓ, joins the environment with another, Eext, under a composition logic g behind the same interface (Eq. 4); the spaces become unions (𝒜′ = 𝒜 ∪ 𝒜ext) and R′ is a composite reward. The example appends "heat a potato and put it on the countertop" in the same house, succeeding only when both verifiers pass, so the agent must carry its goal past the point where it would stop. The code composes serially, resets the second environment lazily at the handoff, shares one step budget and sets R′ = RA ∧ RB (Appendix C.3); Appendix D sketches branching, mid-task switching and interleaving, but only serial chains are used.

Because all three share the interface they compose freely, for example E′ = wchain(wcontract(wstage(E))) (Eq. 5): hide the mug, truncate the observation, then append a follow-up task. The transformations do not commute (w1 ∘ w2 ≠ w2 ∘ w1); the nesting order decides which constraints apply during set-up and which during play. The diagram shows one step() travelling through that stack; the Wrap a world yourself tab runs it.

The policy only ever calls reset() and step() on the outermost layer and cannot tell how many layers sit beneath it (Appendix C.3). Each layer holds the next as inner and delegates every method it does not override. The verifier (evaluate()) is never overridden by Stage or Contract; Chain only combines the two original verdicts.

In the code the three are the classes Setups (Setup in the source), Rules and Link, because the release predates the paper's names (Table 6); a designer's candidate carries in_env_actions (a Stage) and rules_code (a Contract, as Python source). The base interface, ActionableEnv, is Gymnasium-style (reset, step, evaluate, observe) plus get_env_state, a data-only view with no Docker handles, browser pages or sockets, the only state hooks may read; that is what lets one hook run against an in-memory puzzle and a containerised repository alike (Appendix C.1). A per-benchmark Bridge is the only layer that knows the runtime: an in-memory 24 game (Toy24), ALFWorld via TextWorld, per-instance Docker containers (SWE-bench, OfficeQA, SpreadsheetBench) and a Playwright browser (WebArena, WebShop) (Appendix C.2). Generated code runs in a per-episode subprocess, so faulty code crashes an episode, not the framework.

EnvRigger: choosing the components for one policy

§3, Eq. 6, Figure 4

A component is policy-agnostic, but which components to use, and with what parameters, must depend on the target policy π and the task t. The paper writes this as a task-policy-conditioned map E′ = ℋ(E, t; π) = (wk ∘ ... ∘ w1)(E) (Eq. 6), with the policy treated as a black box: only its outputs are read, never its weights. EnvRigger, an LLM designer agent, realises ℋ in four stages (§3.2):

  1. Observe. Roll π out on the base task (K = 5 rollouts, Appendix E.3): failures expose weaknesses, successes show what is intact.
  2. Diagnose. Name root causes (repetitive action loops, failure to parse long observations, misread tool constraints) and a direction: scaffold a struggling policy; harden the environment when the policy always succeeds, since a perfect score means it is too forgiving.
  3. Write. Synthesize one or more components as code aimed at the diagnosis (a Stage and a Contract together if needed, as one candidate); a fragile shortcut gets a Contract that blocks it.
  4. Validate. Wrap the environment, run fresh rollouts, and from the success rate and failure distribution accept the candidate, reject it (unsolvable or not challenging), or send it back to Write with the new trajectories. Accepted components join the EnvHarness.

Write and Validate loop at most 5 times per task, with 5 fresh rollouts per candidate, after which the task yields no component; a candidate is accepted or rejected as a whole, and the designer uses the policy's backbone (Table 8). Validation assumes deterministic resets, so a Stage reproduces the same start state. The system prompt (Appendix A) adds two rules: "do not make the task unsolvable ... SR=0 from impossibility is exactly as useless as SR=1 from triviality", so on those signals the next proposal must loosen; and when a mutation moved the success rate the right way, keep its hooks and change only the magnitude. The reward axis is not exposed: "success is the benchmark's own verdict".

The released configs define "acceptance" differently per benchmark, which Table 8 does not mention (see How much to believe).

Two ways to use the environments (§1, §4.1): skill-based learning, where EnvRigger runs on the training tasks, skills are extracted from trajectories in the customized environments following ReasoningBank, and the frozen policy equipped with them is evaluated on held-out tasks; and online RL, where GRPO trains a policy directly in the reshaped environments.

Experimental setup

§4.1, Appendix E

Five benchmarks in four domains (§4.1): ALFWorld (text-based embodied tasks), WebArena (web interaction), SWE-bench Verified (software engineering), and OfficeQA with SpreadsheetBench (office automation). Each reports its native metric; SWE-bench also tracks average steps as a measure of efficiency. Training and evaluation episodes are disjoint (Table 7):

BenchmarkTraining (reshaped)Evaluation (original tasks only)

ALFWorld's In-Dist and OOD are the benchmark's own seen and unseen splits (140 and 134 tasks, ALFWorld Table 1). SpreadsheetBench's Pass@1 aggregates over base tasks and its Mean Score averages over all instances. The SWE-bench test set is the 407 Verified issues that are not in SWE-bench Lite, not the full 500.

Same model everywhere. EnvRigger, the policy and skill extraction share one backbone: Gemini 3.1 Flash-Lite on ALFWorld and WebArena, Gemini 3.5 Flash elsewhere, "ensuring that performance gains do not stem from distilling a stronger external model" (§4.1). Skills are extracted ReasoningBank-style and the skill-equipped policy is evaluated on held-out instances. Chain is left out of this pipeline (EnvRigger cannot easily observe joined environments' internal states) and tested separately.

Baselines (§4.1, Appendix E.2): No Skills (the frozen policy), Original Envs (skills from the unmodified environments, isolating the effect of reshaping), and a generator where one exists: GenEnv on ALFWorld (an LLM simulates the environment at the edge of the agent's ability), VeriEnv on WebArena (cloned websites with programmatic rewards), SWE-smith on SWE-bench (synthesized repository tasks); none for the office benchmarks. All share seed instances, environment count, extraction pipeline and policy model; EnvRigger sees only training episodes, and each evaluation instance is attempted once.

Result 1: skills from reshaped environments

§4.2, Tables 2 and 3

Skills learned in EnvHarness environments beat skills from the original environments on every benchmark and every metric (Table 2, Table 3; all rows in the tables tab):

  • ALFWorld: 66.2 in-distribution and 70.4 out-of-distribution, against 63.3 and 61.4: +2.9 and +9.0, the paper's headline gain.
  • WebArena: 41.6 average against 38.5 (+3.1), largest on Shopping Admin (+6.2).
  • SWE-bench Verified: 52.58% solved against 49.88% (+2.70), in 49.61 steps against 55.01.
  • OfficeQA: exact match 56.20 against 54.40 (+1.80), F1 57.73 against 55.77 (+1.96).
  • SpreadsheetBench: Pass@1 49.15 against 45.88 (+3.27), mean score 62.48 against 61.47 (+1.01).

Static environments can hurt: original-environment skills score below no skills on SpreadsheetBench (45.88 against 46.44) and lengthen SWE-bench episodes (55.0 steps against 53.6). The paper's explanation: a static environment only lets the agent practise what it already does, while the write-and-validate loop commits only components that fresh rollouts confirm (§4.2).

Against the generators, wherever one applies: EnvHarness skills beat GenEnv by 5.7 points on the ALFWorld average and 8.5 out of distribution, VeriEnv by 2.0 on the WebArena average, and SWE-smith by 2.46 points of success with 5.11 fewer steps per episode. The interface, the EnvRigger loop and the extraction pipeline are the same on all five benchmarks; only domain-specific prompt templates change (§4.2).

Efficiency. On SWE-bench, EnvHarness skills cut the average episode from 53.6 steps (no skills) to 49.6, a 9.8% saving against the 55.0 of original-environment skills ((55.01 − 49.61) / 55.01; against no skills it is 7.4%). The paper ties this to the diagnoses: Contracts and Stages written to break repetitive loops and filter verbose observations (§4.2).

Table 3's SWE-bench gain is +2.70 points, and each number is a mean of three runs whose standard deviations are 2.72 and 2.59. How does the gain compare with the run-to-run noise?

The standard error of a difference of two 3-run means is √(2.72²/3 + 2.59²/3) = 2.17 points, so +2.70 is 1.25 standard errors (Welch test p ≈ 0.28). The chart puts every gain in Tables 2 and 3 beside its own noise: the bar is the gain, the whisker ±2 standard errors. A gain whose whisker crosses zero is not distinguishable from run-to-run variation with three runs.

Result 3: more environments, and co-evolution

§5, Figure 5, Appendix F.2

Under an identical budget on SWE-bench Verified, the paper compares three sources of environments: EnvHarness, the unmodified benchmark environments (SWE-bench Lite, labelled "real envs" in Figure 1) and SWE-smith's generated ones. Each batch of 50 environments yields one skill bank (2 and 3 skills alternately, 15 skills at 300 environments). The two baselines draw batches independently of the learner; EnvHarness writes each batch against the policy already equipped with the earlier skills, so environment and policy co-evolve. EnvHarness climbs from 47.67 to 54.79 (+7.12) "and maintains an upward trajectory at 300 environments", while the same budget yields 52.13 on original environments and 50.37 on generated ones; the paper concludes that "targeting the learner's current capability boundary is fundamentally more effective than unconditioned environment scaling" (§5).

The paper says the original environments "flatten out" while EnvHarness keeps improving. From 100 to 300 environments, which source gained more SWE-bench tasks (of the 407)?

Figure 5 is a vector graphic, so its points can be read exactly. Every point lands on a whole number of the 407 test issues (to 0.0002 of a task). In tasks, EnvHarness goes 194, 200, 214, 217, 219, 220, 223 and the original environments 194, 197, 203, 202, 205, 207, 212. From 100 to 300 environments both gain 9 tasks; in the last step the originals gain 5 and EnvHarness 3. The 11-task gap between them was made entirely in the first 100 environments. Only SWE-smith flattens (204 to 205).

What each round taught (Appendix F.2). Every listed skill traces to an accepted component, and the components work by faking the environment's behaviour:

  • Round 1 (the base policy did not run tests reliably or edit within its tools): rewrite pytest to pytest -x (skill: fail fast); block inline python -c edits, conda run and custom scripts (skill: edit with patch -p1); fake a 60-second timeout on whole-suite runs (skill: target the exact test file).
  • Round 2: answer "pytest: command not found" (skill: call pytest.main); fake an out-of-memory kill on whole-file runs (skill: filter with -k); time out runs that name no file (skill: pass a nonexistent file to test option parsing).
  • Round 3: prefix every command with the testbed's bin directory (skill: call conda binaries by absolute path); replace sed -i with a fake error (skill: navigate with grep -rn before editing). About a third of the training tasks are now solved on every baseline rollout; hardening candidates leave the rate unchanged or drive it to zero, exhaust the budget and add nothing. Gains shrink round over round as the remaining flaws grow more local.

Result 4: Chain, other models, transfer and cost

§5, Tables 5, 9 to 11

Chain (Table 5). Two randomly paired SWE-bench environments are joined into one episode, outside the EnvRigger loop, and the extracted skills are evaluated on ordinary single tasks. Chain-only skills cut average steps from 53.58 to 41.96 at a success rate of 49.63, marginally below the 49.88 of original-environment skills; the paper attributes this to the strict training condition (success needs both halves), which favours keeping a goal over maximising a short task. Combining Stage/Contract skills with Chain skills gives the best success rate, 54.30, at 43.12 steps. Representative Chain skills (Appendix F.3): manage one shared step budget across joined tasks (be "good enough" on the first so the second has steps left), and re-orient after a handoff (check conda env list and which python, since a django repository needs runtests.py where matplotlib used pytest).

Other policies (Figure 6, Table 9). On SWE-bench Verified, with the same backbone as policy and designer each time, EnvHarness skills beat original-environment skills for Gemini 3.1 Flash-Lite, Qwen3.6 27B, Gemini 3.5 Flash and Claude Sonnet 4.6 by 2.7 to 3.7 points, while the no-skill success rates span 30.7 to 67.2. The loop "neither breaks down on the weakest model nor saturates on the strongest"; what changes with capability is the content of the diagnoses. Skills of either kind help the two weakest most (+9.3 and +11.1 for EnvHarness, +6.1 and +7.4 for original environments, under 5.5 for the two strongest).

Average steps tell three stories (Appendix F.4): skills nearly halve Qwen3.6 27B's flailing (69.8 to 37.1 steps), make Gemini 3.1 Flash-Lite persist instead of giving up early (36.7 to about 50) while solving more, and barely move Claude Sonnet 4.6 (29.3 to about 25). Gemini 3.5 Flash is the one model where EnvHarness skills improve success and steps against both baselines. The extra successes do not come from running longer: EnvHarness episodes are within a step of the original-skill ones on Flash-Lite and Sonnet, five shorter on Flash, and longer only on Qwen (3.7 steps for 3.7 points). Steps alone are no quality signal: a short episode can be an efficient solution or an early surrender.

Transfer (Table 10). In leave-one-out on ALFWorld (skills from every task type but one, evaluated on the held-out type), EnvHarness skills win on four of six types and by 3.1 points on average (63.7 against 60.6): +16.4 on clean, −8.7 on heat. The paper reads this as reshaping pushing the policy off memorised routines.

Cost (Table 11). EnvHarness spends 38 times GenEnv's design tokens on ALFWorld (1.46M against 38K), since it feeds whole trajectories to the designer, but rollouts dominate either budget. Against VeriEnv, which also runs the real environment, totals match (137.3M against 137.8M); GenEnv is 3.5 times cheaper (64.2M against 228.0M) because its rollouts are simulated, which the paper calls "the cost of grounding". There is no row for Original Envs or for SWE-bench.

Result 5: environments on demand

§5, Appendix G, Tables 12 and 13

The same machinery takes explicit targets instead of its own diagnoses (§5).

A quantitative target (Table 12). On 100 ALFWorld tasks, each measured with K = 10 rollouts, EnvRigger reshapes each task toward a band in whichever direction its baseline needs. For success rate in [0.4, 0.6], the share of tasks inside the band rises from 6.0% to 80.0% and the mean success rate moves from 0.74 to 0.48; the original tasks are strongly bimodal, mostly always or never solved. For average steps on successful episodes in [25, 35], a tighter target, it rises from 18.0% to 53.0%.

Suppose reshaping made every task's true success rate exactly 0.5. Measured with 10 fresh rollouts, what share of tasks would land inside [0.4, 0.6]?

Inside the band means 4, 5 or 6 successes out of 10. At a true rate of 0.5 that happens (210 + 252 + 210) / 1,024 = 65.6% of the time, and no true rate does better. So no reshaping, however perfect, can show more than about 66% of tasks in band on a fresh 10-rollout measurement. The paper reports 80.0%, which is only possible if the measurement reuses the rollouts that decided acceptance: a task kept because its 10 rollouts landed in the band is then counted as in band. Part of the 80% is selection, by construction. The curves show the in-band chance for K = 5 (the paper's validation setting) and 10 (Table 12's). With K = 3 (WebArena's setting in the release) the measured rate is 0, 1/3, 2/3 or 1 and can never fall inside the band at all.

Probability that K rollouts of a task with true success rate p give a measured rate in [0.4, 0.6] (binomial). The Wrap a world yourself tab runs real rollouts of a toy environment through the same accept rule.

A weakness named in one sentence (Table 13). Handed a one-sentence weakness, the designer writes components that make it fatal inside an ordinary task, and one skill is distilled from the trajectories. It chose the axes itself: Stages to stage start states, action filters to block shortcuts, transition hooks to fake consequences. There are nine cases, three per benchmark (all in the tables tab), for example a target starting inside a closed drawer, retrieval blocked until a scroll, files silently corrupted when sed is used. The main-text example:

Specified weakness: "The policy submits a patch without running the failing test, so the fix stays unverified."

class _Contract(Contract):
def modify_transition(self, action, response, env_state):
cmd = bash_command(action)
if "pytest" in cmd or "runtests.py" in cmd:
env_state.extras["ran_tests"] = True
if is_submission(cmd) \
and not env_state.extras.get("ran_tests"):
return failed(response,
"githook: pre-commit hook 'verify-tests' "
"failed. Run the test suite before submitting.")
return response

Distilled skill: Verification-Driven Development Loop. When: whenever a code change fixes a bug or implements a feature, especially where the test suite needs setup or configuration. What: before finalizing any change, run the relevant test suite to confirm the failure exists, then run it again after the patch to verify the fix, initializing the environment first when needed.

The paper says the skill combines a general principle with actionable steps rather than overfitting to one task (§5).

How much of this to believe

The paper's own evidence, judged. Every number below is recomputed from the printed tables, the decoded vector figures and the released configs (77 checks, listed in the tables tab).

What holds up

  • The mechanism is real and inspectable. The code is released (Apache-2.0) and does what the paper says: Rules has no reward hook and evaluate() passes straight through, so a reshaped environment really is scored by the original verifier (Appendix C.3). The appendices print the actual components.
  • The comparisons are mostly matched: same seed instances, environment count, extraction pipeline and policy model (Appendix E.2); the designer uses the policy's own backbone; and against VeriEnv the token totals match (Table 11).
  • The direction is consistent. All 14 improvements in Tables 2 and 3 are positive, as are all four models in Table 9. Some columns are not independent (an average and its parts, EM and F1), but about ten separate comparisons agreeing is better evidence than any single margin.
  • The arithmetic checks out: every printed improvement, average, ratio and claim recomputes, and Figures 1 and 6 match the tables.
  • The authors state real limitations (Appendix H): the design loop is costly, more so with a weaker designer; a resettable text interface is required, ruling out live services and physical robots; Chain is purely sequential, blind to whether two joined tasks are related. That counts in their favour.

What does not

  1. Most margins sit inside the noise. With three runs per arm only 3 of the 14 gains in Tables 2 and 3 reach p < 0.05 on a Welch test (ALFWorld OOD, SWE-bench steps, SpreadsheetBench Pass@1). SWE-bench success, +2.70, is 1.25 standard errors; WebArena Reddit, +1.9, sits beside a standard deviation of 9.7. The paper reports no test.
  2. The SWE-bench means look like single counts. All six two-decimal success rates in Table 3 and Table 5 are whole numbers of the 407 issues (194, 203, 204, 214, 202, 221). A three-run mean is a whole number of tasks one time in three, so all six has odds of 1 in 729: either those columns report one run, or the coincidence happened. The paper cannot settle it.
  3. The scaling figure does not show the originals flattening. In the vector Figure 5, original environments gain 9 tasks from 100 to 300 environments, as many as EnvHarness, and 5 in the last step against its 3; the 11-task gap was made in the first 100 environments. Only SWE-smith flattens. Each point is one evaluation, and steps of 1 to 5 tasks are inside the three-run spread of about 11. The text's 52.13 at 300 is not a possible value (212.17 of 407); Figure 5 plots 212/407 = 52.09.
  4. The RL result is one run per arm (Table 4): +9 of 140 tasks in distribution (Fisher p = 0.18 from evaluation noise alone), −1 of 134 out of distribution. "A highly effective, independent optimization signal" claims more than that.
  5. The 80% calibration is partly by construction. No set of true success rates puts more than 65.6% of tasks inside [0.4, 0.6] on a fresh 10-rollout measurement, so Table 12's 80.0% must reuse the rollouts that decided acceptance. The 6.0% before is clean; the after is not.
  6. The rollout budgets are not like for like. EnvHarness sees each training task through 5 baseline rollouts plus up to 25 validation rollouts and extracts skills from them; the number of trajectories behind the Original Envs skills is not reported, and the cost table has no row for it. Part of the gain could come from more, and more varied, trajectories rather than from targeting.
  7. "Same settings on every benchmark" is not what the release does. Table 8 gives 5 rollouts and 5 rounds everywhere; the released configs use 3 and 3 on WebArena and 2 rounds on SpreadsheetBench, and accept by different rules: a 5-rollout success-rate band on SWE-bench, "success rate up by at least 0.2" (an easier environment) on ALFWorld, the designer's judgement elsewhere (on WebArena guided by a band scored over the last 20 accepted episodes; 3 rollouts could never land inside [0.4, 0.6] anyway) (table). The configs may postdate the runs, but the paper never describes per-benchmark acceptance.
  8. The verifier is trusted; the environment no longer is. The Contracts in Appendix F.2 fake timeouts, missing commands, out-of-memory kills and sed errors, and one case in Table 13 silently corrupts files. Some resulting skills work around failures the real environment never produces ("call pytest.main when the CLI is broken"). Every reshaped environment keeps its verifier, as claimed; but the transitions the agent learns from are partly invented, which is a milder form of the reliability problem the paper sets out to avoid.
  9. Smaller points. Figure 1's bars start at 43, so SWE-bench's 47.7, 49.9 and 52.6 stand 4.7, 6.9 and 9.6 above the axis. The paper counts seven Bridges including WebShop; the repository has six, with WebShop only inside an optional verl-agent patch. Chain is evaluated once, outside the loop, without error bars.
Verdict
Believe the design. Wrapping a frozen environment at its interface is a clean, general idea that keeps the verifier, ports across five very different benchmarks with one implementation, and is released in working form. Believe the direction of the skill-learning results, which is consistent across benchmarks and models. Treat the sizes as provisional: most single margins are within three-run noise, the RL comparison is one run per arm, the scaling figure does not show what the text says about the original environments, and the calibration result is partly by construction.

What it takes to use this

  • Code and licence. google-research/envharness, Apache-2.0, released with the paper: one driver per benchmark (preflight, smoke run, reproduce.py) and an rl/ folder that patches verl-agent at a pinned commit for GRPO on ALFWorld. Configs default to gpt-4.1-mini; the paper's tables used Gemini, selected with one MODEL variable that also picks the embedding model for skill retrieval.
  • What your environment must offer (Appendix H, Appendix C): a resettable reset/step interface over text, deterministic resets (a Stage is replayed every rollout) and a data-only state view. A new benchmark needs one Bridge class and nothing else. Live services and anything that cannot be undone (a sent email, a physical robot) are out.
  • Budget. Rollouts dominate: about 228M tokens for ALFWorld's 100 training tasks and 137M for WebArena's 80 (Table 11). The RL run used one 8-H100 node for 150 GRPO steps. A weaker designer needs more rounds, each costing rollouts.
  • When it pays off, and when not. It helps when the policy saturates its training tasks, when its failures come from habits a component can expose, and most for weaker policies; expect a few points (+1 to +9 here, +2.7 to +3.7 on SWE-bench across four models). It buys little for strong, directed policies (Claude Sonnet 4.6: 69.2 to 72.4), for tasks that cannot be hardened without becoming unsolvable (a third of SWE-bench training tasks by round 3), and where learned behaviour must match the real environment's failure modes, since Contracts may invent new ones.
  • Where it is going (Appendix I): new components (stochasticity, partial observability, auxiliary feedback channels, several agents), visual and GUI environments whose states are not text, and semantic composition for Chain, which needs a compatibility measure and a verifier for the combined objective.

Why it matters (beyond the paper)

Environment supply is emerging as the bottleneck for training agents, the way data curation was for pretraining, and this paper reframes how to meet it: environment construction becomes a wrapping problem rather than an authoring problem. Wrapping keeps the one thing generation pipelines cannot reliably produce, a trusted verifier, and working at the interface makes one implementation domain-agnostic. The authoring route is alive too: Terminal-Universe built 37,300 runnable terminal environments from recorded agent runs, and nothing stops a wrapper from reshaping those.

The task-policy-conditioned angle matters most for RL practitioners. EnvRigger is automated curriculum design driven by black-box behavioural diagnosis, the idea of unsupervised environment design (PAIRED, Prioritized Level Replay) carried over to LLM agents with an LLM writing the curriculum as code. The paper's scaling result suggests that co-evolving policy and environment is the axis to scale rather than raw environment count; this page's reading of Figure 5 says the evidence for that is the first 100 environments, not the slope after them.

The agent-harness analogy is also a memorable design lens: freeze the expensive artifact, customize through plug-ins at the interface. HarnessDev measures the agent side of that lens and finds that models evolving their own harness make unstable, executor-specific gains; the same caution applies to a designer evolving environments.

Wrap a world yourself

This tab runs the paper's three components in your browser. The wrapper classes are a line-for-line port of the released EnvHarness, Setup (Stage), Rules (Contract) and Link (Chain) (repository): every layer delegates what it does not override, a Stage replays its actions through the inner step() and then rewinds the step counter, a blocked action leaves the world untouched and returns the current observation with the reason, and a Chain runs the first task until it ends, then the second, under one 50-step budget, succeeding only if both original verifiers pass. The household, its policy and its numbers are a toy built from the paper's running example ("put a clean mug on the desk", §2.2), not ALFWorld: seven places on a corridor, a mug on the countertop, a potato on the shelf.

The policy is a scripted black box that reads only the observation text. It has habits like the ones the paper's designer diagnoses: it explores places in the order it first saw them named, opens a closed drawer only 40% of the time on its first sweep and the microwave only 15% (it does not expect a mug there), gives up after one fruitless sweep 60% of the time, and tries once to clean the mug before picking it up. A Stage ends by walking back to the countertop, so the policy does not simply start beside the hidden mug. Change its slip rate to make it do something aimless now and then.

Try: play the default: the Stage has hidden the mug in drawer 1 and the Contract has removed teleport navigation, so the wrapped policy walks and searches for 24 steps while the static one wins in 7. Then swap the order of the two layers and watch the Stage silently fail: its own replayed "go to" actions are blocked by the Contract underneath it, so the mug never moves. Then try other seeds: on some the policy gives up.

Validate: K rollouts and the accept rule

EnvRigger judges a candidate from a handful of fresh rollouts: 5 in the paper (Table 8), 3 on WebArena in the release (with 3, a measured rate is never inside [0.4, 0.6]). The released SWE-bench designer prompt accepts a candidate whose measured success rate lands in [0.4, 0.6], refines one that is too easy or too hard, and must loosen one that looks unsolvable. Run K rollouts of the current configuration with fresh seeds, several times, and watch the verdict change on noise alone. The 400-rollout estimate is this toy's true success rate to within about ±5 points.

    The scripted designer is a stand-in for the LLM: it starts from the static world (Observe), reads the success rate (Diagnose: a perfect score means "make it harder"), and walks a fixed ladder of the paper's own example components (Write: hide the mug in a drawer; if that is still too easy, hide it in the microwave instead; if a candidate is too hard, step back), validating each candidate with K fresh rollouts under the release prompt's band rule and stepping back if a candidate looks unsolvable, for at most 5 rounds. Its success rates are measured live; its choices are scripted.

    Dennis et al., arXiv 2012.02096, NeurIPS 2020: the classic statement of the problem EnvHarness inherits: environments should be designed against the current policy, at the edge of what it can do.
