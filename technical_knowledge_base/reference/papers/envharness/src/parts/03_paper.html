Problem: environments that never change

[[S1|§1 Introduction]]

LLM agents learn by acting in environments: software repositories, web interfaces, text or embodied simulators. Each environment presents tasks, keeps state, answers actions and judges success ({{§1|ax:S1}}). They are expensive to build, because people hard-code the interaction logic and the verifiers, and once built they are static: they behave the same whichever agent trains in them and however good it has become. That limits learning in two ways. A static environment cannot aim at one agent's particular weaknesses, and once the agent solves its tasks it has nothing left to teach ({{§1|ax:S1}}).

The usual fix is to generate environments automatically, and it has two structural flaws ({{§1|ax:S1}}):

  • Generators are domain-specific. A pipeline that builds web environments (InSTA), programming ones (SWE-Gym) or tool-use ones does not transfer to the others.
  • Correctness is costly and unreliable. Environments and verifiers written by an LLM must be over-generated and heavily filtered (SWE-smith, Agent World Model), and still come with no guarantee that the verifier is right.

Generated environments are also static once made: they do not move as the agent improves ({{abstract|https://arxiv.org/abs/2608.19880}}).

Idea: a harness for the environment

[[S2.SS1|§2.1, Table 1]]

An agent harness is the software around a frozen model (execution loop, tool registry, memory, context management) that turns it into an agent without changing its weights: Agent = Model + Harness ({{§2.1|ax:S2.SS1}}). EnvHarness applies the same trick to the other side of the loop: Customized Env = Static Env + EnvHarness. Plug-in components wrap a frozen environment and change what flows through its standard interface, while its code stays untouched ({{Table 1|ax:S2.T1}}).

Designed to solveLack of action, memory or loopsHard-coded interaction logic

{{Table 1|ax:S2.T1}}, verbatim: "Both scale capabilities through external layers rather than changing the core system."

Formally ({{Eq. 1|ax:S2.E1}}), an environment is a tuple E = (𝒮, 𝒜, 𝒪, T, R, s0): states, actions, observations, the transition function T: 𝒮 × 𝒜 → 𝒮, the reward R induced by the verifier, and the initial state. A component is an environment-agnostic transformation E′ = w(E) that works strictly at the interface: it can change the initial state, filter the exposed action and observation spaces and update the transition mechanics, but never the simulator backend. Because every intervention stays outside, the ground-truth evaluation logic is preserved and the original verifier still scores the episode. That is the paper's answer to the reliability problem: no generated verifier anywhere.

The three components

[[S2.SS2|§2.2, Eqs. 2 to 5]]

The paper introduces three component types, "chosen to cover three fundamental modes of environment customization", and expects more to follow ({{§2.2|ax:S2.SS2}}). Each overrides a standard interface method. The running example is one ALFWorld task, "put a clean mug on the desk", whose default instance leaves the mug in the open and ends as soon as it is placed.

  • Stage, wstage,δ, overrides reset(): a list of actions δ = (a1, ..., ak) applied to the initial state, s0′ = T(...T(s0, a1)..., ak), nothing else changed ({{Eq. 2|ax:S2.E2}}). Harder: take mug 1, open drawer 1, put mug 1 in drawer 1, close drawer 1, so the agent must search. Easier: clean the mug in advance. The code replays δ through the ordinary inner.step(), so the start state is always reachable and the saved form is just the action list ({{Appendix C.3|ax:A3.SS3}}).
  • Contract, wcontract,r, overrides step(): a triplet r = (fA, fT, fO), each the identity by default, rewriting the action space, the transition dynamics and the observation space ({{Eq. 3|ax:S2.E3}}). It enforces preconditions, masks or augments observations and attaches structured feedback. On the mug task: fO truncates the room description after two sentences, so the agent builds its picture of the room step by step; fT blocks "clean mug" unless the agent holds it; fA removes teleport navigation. A blocked action leaves the world untouched and returns the current, filtered observation with the reason, and Contract never touches s0 or R ({{Appendix C.3|ax:A3.SS3}}).
  • Chain, wchain,ℓ, joins the environment with another, Eext, under a composition logic g behind the same interface ({{Eq. 4|ax:S2.E4}}); the spaces become unions (𝒜′ = 𝒜 ∪ 𝒜ext) and R′ is a composite reward. The example appends "heat a potato and put it on the countertop" in the same house, succeeding only when both verifiers pass, so the agent must carry its goal past the point where it would stop. The code composes serially, resets the second environment lazily at the handoff, shares one step budget and sets R′ = RA ∧ RB ({{Appendix C.3|ax:A3.SS3}}); {{Appendix D|ax:A4}} sketches branching, mid-task switching and interleaving, but only serial chains are used.

Because all three share the interface they compose freely, for example E′ = wchain(wcontract(wstage(E))) ({{Eq. 5|ax:S2.E5}}): hide the mug, truncate the observation, then append a follow-up task. The transformations do not commute (w1 ∘ w2 ≠ w2 ∘ w1); the nesting order decides which constraints apply during set-up and which during play. The diagram shows one step() travelling through that stack; the {{Wrap a world yourself|tab:t-run}} tab runs it.

The policy only ever calls reset() and step() on the outermost layer and cannot tell how many layers sit beneath it ({{Appendix C.3|ax:A3.SS3}}). Each layer holds the next as inner and delegates every method it does not override. The verifier (evaluate()) is never overridden by Stage or Contract; Chain only combines the two original verdicts.

In the code the three are the classes Setups (Setup in the source), Rules and Link, because the release predates the paper's names ({{Table 6|ax:A1.T6}}); a designer's candidate carries in_env_actions (a Stage) and rules_code (a Contract, as Python source). The base interface, ActionableEnv, is Gymnasium-style (reset, step, evaluate, observe) plus get_env_state, a data-only view with no Docker handles, browser pages or sockets, the only state hooks may read; that is what lets one hook run against an in-memory puzzle and a containerised repository alike ({{Appendix C.1|ax:A3.SS1}}). A per-benchmark Bridge is the only layer that knows the runtime: an in-memory 24 game (Toy24), ALFWorld via TextWorld, per-instance Docker containers (SWE-bench, OfficeQA, SpreadsheetBench) and a Playwright browser (WebArena, WebShop) ({{Appendix C.2|ax:A3.SS2}}). Generated code runs in a per-episode subprocess, so faulty code crashes an episode, not the framework.

EnvRigger: choosing the components for one policy

[[S3|§3, Eq. 6, Figure 4]]

A component is policy-agnostic, but which components to use, and with what parameters, must depend on the target policy π and the task t. The paper writes this as a task-policy-conditioned map E′ = ℋ(E, t; π) = (wk ∘ ... ∘ w1)(E) ({{Eq. 6|ax:S3.E6}}), with the policy treated as a black box: only its outputs are read, never its weights. EnvRigger, an LLM designer agent, realises ℋ in four stages ({{§3.2|ax:S3.SS2}}):

  1. Observe. Roll π out on the base task (K = 5 rollouts, {{Appendix E.3|ax:A5.SS3}}): failures expose weaknesses, successes show what is intact.
  2. Diagnose. Name root causes (repetitive action loops, failure to parse long observations, misread tool constraints) and a direction: scaffold a struggling policy; harden the environment when the policy always succeeds, since a perfect score means it is too forgiving.
  3. Write. Synthesize one or more components as code aimed at the diagnosis (a Stage and a Contract together if needed, as one candidate); a fragile shortcut gets a Contract that blocks it.
  4. Validate. Wrap the environment, run fresh rollouts, and from the success rate and failure distribution accept the candidate, reject it (unsolvable or not challenging), or send it back to Write with the new trajectories. Accepted components join the EnvHarness.

Write and Validate loop at most 5 times per task, with 5 fresh rollouts per candidate, after which the task yields no component; a candidate is accepted or rejected as a whole, and the designer uses the policy's backbone ({{Table 8|ax:A5.T8}}). Validation assumes deterministic resets, so a Stage reproduces the same start state. The system prompt ({{Appendix A|ax:A1}}) adds two rules: "do not make the task unsolvable ... SR=0 from impossibility is exactly as useless as SR=1 from triviality", so on those signals the next proposal must loosen; and when a mutation moved the success rate the right way, keep its hooks and change only the magnitude. The reward axis is not exposed: "success is the benchmark's own verdict".

The released configs define "acceptance" differently per benchmark, which {{Table 8|ax:A5.T8}} does not mention (see {{How much to believe|tab:t-read:s-trust}}).

Two ways to use the environments ({{§1|ax:S1}}, {{§4.1|ax:S4.SS1}}): skill-based learning, where EnvRigger runs on the training tasks, skills are extracted from trajectories in the customized environments following ReasoningBank, and the frozen policy equipped with them is evaluated on held-out tasks; and online RL, where GRPO trains a policy directly in the reshaped environments.
