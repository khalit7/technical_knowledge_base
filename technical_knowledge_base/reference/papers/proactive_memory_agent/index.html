Remember When It Matters: Proactive Memory Agent for Long-Horizon Agents (Proactive Memory Agent)

Yifan Wu, Lizhu Zhang, Yuhang Zhou, Mingyi Wang, Bo Peng, Serena Li, Xiangjun Fan, Zhuokai Zhao
Meta AI · submitted 9 July 2026 (arXiv v1, the only version; the paper's own date line says 24 August 2026)

In one line: A second model runs beside an unmodified action agent, keeps a small structured memory bank of the run, and at each step either injects a reminder into the actor's next call or stays silent. With Claude Opus 4.6 as that memory agent, Claude Sonnet 4.5 goes from 37.6% to 45.9% on Terminal-Bench 2.0 and from 55.0% to 61.8% on τ²-Bench; Opus 4.6 itself gains 2.4 and 2.5 points; a frozen Qwen3.5-122B-A10B actor gains 37.6% to 41.1% on Terminal-Bench with a Qwen3.5-27B memory agent trained by SFT and GRPO.

Problem: behavioral state decay

§1 Introduction

Long-horizon agent tasks unfold over many observations, actions and partial decisions, and agents fail in a recognisable way: they identify a requirement early and violate it later while fixing an unrelated bug; they see a command, parameter or implementation path fail and later retry a near-identical variant; they diagnose an error and later treat the same error as new (§1). The paper names this behavioral state decay: task requirements, environment facts, previous attempts, failure diagnoses, intermediate discoveries and open subgoals stop influencing the next decision. The information may still be in the transcript, even inside the context window, but it no longer exerts reliable control over behaviour; models under-use information depending on where it sits in a long context (§1, citing Liu et al. 2024). So simply making longer histories available is not enough.

Most memory systems answer a different question: can the information be stored and retrieved? MemGPT, MemoryBank, generative agents and Mem0 are built for personalisation, persistent user state and recall across sessions (§1, §2.2). During active task execution memory also has to decide when to intervene. Surface too little and the agent repeats mistakes; surface too much and it costs latency and tokens and distracts the agent from local progress. The paper's framing: memory for long-horizon agents is an intervention problem, not only a write and retrieval problem. It is also stronger than summarisation: a summariser asks what to retain; the memory agent asks whether any retained state should become active in the next decision, and a fixed summarisation policy cannot know that because the useful memory differs by task (a hard requirement in one, a failed command or an unfinished subgoal in another) (§1, §2.5).

Idea: a second model that decides when to remind

§3, Figure 3

An unmodified action agent does the work. A separate memory agent runs alongside it: at the first step and then at a fixed interval it reads the task description, a window of recent trajectory and its own structured memory bank; it first edits the bank (Phase 1), then decides whether to inject a concise reminder into the action agent's next call or to stay silent (Phase 2) (§3, Figure 3). A reminder is a forgotten requirement, a stable environment fact, a failed attempt or a diagnosis. Nothing about the actor is retrained: same base instructions, tools and decoding, only an optional transient memory context at call time (§3.3). That is the whole design, and the cheapness of the integration is the point: it is a harness-layer addition that can be bolted onto a model you do not control, and the paper calls it plug-and-play with frontier action agents and existing harnesses (abstract).

Two neighbours it is defined against: passive memory retrieves records on demand and never decides whether memory should enter the control loop at all; advisor models give broad strategic guidance, while this memory agent is restricted to memory-grounded reminders (§1, §2.4). The paper's ablations (Table 2) remove one capability at a time. The animation runs one real memory step from a released trace, the moment the actor's apt-get install -y gcc make gcov fails, through the full design and through each ablation, so you can see what each one passes to the actor's next call.

Real for "Proactive memory": the command, the error, the bank entries and the reminder are from the released memory run of sqlite-with-gcov (memory trigger 4, before action turn 4; trace). The other designs were run only on τ²-Bench and released no traces, so what they would pass at this step is illustrative, built from the paper's description of each variant (§4.3). The token bar is to scale: the actor's turn-4 prompt was 3,871 tokens; added text is converted at 3.76 characters per token, measured on these traces. Scores are Table 2's, on τ²-Bench.

The interesting claim is in the silence. A reminder is not free: it takes context, and an irrelevant one competes with the actual task state for the actor's attention. So the memory agent's job is presented as discrimination, not retrieval: the bottleneck in long-horizon work, on this view, is knowing when to surface a fact rather than being able to find it, which is what separates it from retrieval-augmented generation, where ranking is the whole problem and the timing is fixed (every call). Whether the experiments show that silence is what helps is taken up under Ablations and In the traces.

Method

§3.1 to §3.5

Setup. The action agent produces a trajectory τ = (o1, a1, o2, a2, …, oT) of observations and actions, sampling at ∼ πA(at | x, τ<t) for task x. Requirements, environment facts, attempts, diagnoses, discoveries and open subgoals are the execution state, kept outside the action context. At each memory step t the memory agent πM sees the task, a recent window wt of the trajectory and the previous bank, and runs two policies (§3.1):

Bt ∼ πMedit( · | x, wt, Bt−1),    it ∼ πMintervene( · | x, wt, Bt),    it ∈ {∅, text reminder}

A non-null it is injected into the next action-agent call as transient context; ∅ leaves the call unchanged. Memory becomes a policy over interventions: what to retain, and when retained state is useful enough to enter the action loop.

The bank is Bt = (st, Kt, Pt) (§3.2): a private status field st (progress, open issues, unresolved risks; never shown to the actor), knowledge entries Kt (stable facts: requirements, environment properties, paths, configuration, verified facts, evaluation-relevant observations) and procedural entries Pt (attempts and outcomes: failed commands, successful fixes, ruled-out hypotheses, diagnostic signals, improvements). Each entry is a short identifier, natural-language content and metadata (creation time, access statistics); identifiers let the agent update or delete stale entries, and entries are written in a compact tagged format.

Phase 1, memory management, returns a list of tool calls that the system executes in order; the agent never rewrites the bank directly, and no call leaves it unchanged (Phase 1). The four tools: memory_update_status (the private progress note), memory_save_knowledge (requirements, environment facts, paths, API details, constraints), memory_save_procedural (debugging experience, failed approaches, error patterns, fixes, performance observations) and memory_delete (by identifier). The output is a sequence of bank edits, not a free-form summary.

Phase 2, intervention, reads the updated bank and the recent trajectory and emits either <context_for_action> with a reminder or <no_intervention/>; it never edits the bank (Phase 2). The null intervention is an explicit action. Encouraged: requirements about to be violated, environment facts that explain the current observation, attempts not to repeat, diagnoses still relevant, neglected subgoals. Discouraged: broad strategic advice, restating what is already visible, taking over the actor's planning.

Trigger. A trigger function g(t) runs the memory agent at the first step and then at a fixed interval; error-, test- or repetition-triggered schedules are possible but left out to isolate the intervention policy (§3.4). In the experiments the interval is every step, with a window of k = 8 messages (§4.1).

What the released code adds
  • The run configuration sets the actor at temperature 0.7 with at most 50 turns and Terminus 2's summarisation on; the memory agent at temperature 0.3, interval 1, window 8, reminders appended to the actor's latest user message; the window is the last 8 recorded steps, each the actor's reasoning plus the terminal output (memory_enabled_agent.py); the status resets per episode while knowledge and procedural entries persist (memory_terminalbench.yaml). The file's own header calls the run "single-phase tool-only memory (trigger every step, window = 8)", while the code it runs is the two-phase agent.
  • The two phases are two separate model calls, each sent the full bank and the window, even though the module's docstring describes "one conversation" sharing context (memory_agent.py). Above 50 entries the bank shown to the model is pre-filtered to the 20 knowledge and 20 procedural entries that best match the window by BM25: a retrieval step inside the "not retrieval" design. In the five released traces the bank never exceeds a handful of entries, so the filter never fires there.
  • The Phase 2 prompt tells the model its "DEFAULT is <no_intervention/>", to frame reminders "as observations, not commands", and that it "CAN connect dots and highlight patterns, not limited to verbatim copies from bank".

Learning the policy (§3.5). The architecture needs no training: the main memory agent is a prompted model. Because prompted memory agents add inference cost and are imperfectly calibrated, the paper also trains an open-weight memory agent while keeping the actor fixed: SFT distils trajectories of the prompted agent (the interface, compact writing, updating stale state, avoiding needless reminders), then RL calibrates when to speak. The paper calls this preliminary; the architecture does not depend on it.

Results

§4.1, §4.2, Table 1

Benchmarks. Terminal-Bench 2.0: autonomous work in real command-line containers (inspect files, run commands, edit code, debug, satisfy hidden verifier tests), binary pass/fail per task, run with the official Terminus-2-style harness. Of its 89 tasks the paper reports the 85 where both the baseline and the memory run produced a valid evaluation, excluding four docker failures (§4.1). τ²-Bench: conversational tool use with a simulated user in the airline (50 tasks), retail (114) and telecom (114) domains, 278 per configuration, one sampled conversation per task (§4.1). Terminal-Bench stresses environment grounding and debugging continuity; τ²-Bench stresses policy adherence and user-state tracking. Unless stated, the memory agent is Claude Opus 4.6; the action agents are Claude Sonnet 4.5 and Opus 4.6; all scores are pass@1 (§4.1).

Memory improves every aggregate in Table 1. Below, each percentage is turned back into whole tasks (every printed figure maps to exactly one count; the tables tab shows the check).

Grey: action agent alone. Colour: with the Opus 4.6 memory agent. One run per bar (Table 1).

On Terminal-Bench, Sonnet 4.5 goes from 37.6% to 45.9% (+8.3 points, 32 to 39 tasks) and Opus 4.6 from 43.5% to 45.9% (+2.4, 37 to 39). On τ²-Bench's task-weighted average, Sonnet goes from 55.0% to 61.8% (+6.8, 153 to 172 tasks) and Opus from 66.2% to 68.7% (+2.5, 184 to 191). The paper reads this as: larger gains for the weaker actor, but gains that do not vanish for the stronger one, so not merely compensation for limited capacity. By domain, Sonnet's lifts are largest on airline (+10.0) and retail (+9.6 in the table, "+9.7" in the text) and small on telecom (+2.6), which the paper takes as memory being a domain-sensitive intervention policy (§4.2). Opus gains nothing on airline (76.0% both ways).

Which scores higher: Sonnet 4.5 with the Opus 4.6 memory agent, or Opus 4.6 acting alone with no memory?

On Terminal-Bench the Sonnet pair reaches 45.9% against Opus alone at 43.5%, and Opus with its own memory agent also reaches 45.9%: the same 39 tasks out of 85, whichever model acts. On τ²-Bench Opus alone (66.2%) beats the Sonnet pair (61.8%) by 12 tasks. The paper never makes this comparison, but it is the one a buyer would: the memory agent is an Opus call at every step, so "add an Opus memory agent to Sonnet" competes with "just use Opus". On τ²-Bench it loses; on Terminal-Bench it ties Opus with memory and edges Opus without it, by two tasks, in single runs.

Ablations: is it the silence?

§4.3, Table 2

All on τ²-Bench, Sonnet 4.5 acting, Opus 4.6 as the memory model (Table 2, §4.3). Each variant removes one capability:

  • Full-bank context keeps Phase 1 and drops Phase 2: the whole bank is shown to the actor at every step. Tests whether merely making history visible is the benefit (passive context augmentation).
  • Always inject keeps the bank and the generated reminder but removes the silence action: a reminder at every step. Tests whether the no-op is just an efficiency saving or essential to calibration.
  • Injection-only (no bank) skips Phase 1: a model watches the window and gives selective guidance, like an advisor, but cannot ground it in maintained state.
  • Mem0: memories written through Mem0's ADD interface and the top 10 retrieved by vector plus BM25 search returned to the actor; production retrieval against selective intervention.

Recomputed from the three domain scores; every printed average reproduces. The dashed line is the same full agent's Table 1 run (172 tasks, 61.9% task-weighted, printed 61.8%).

The paper's reading: the full two-phase agent has the best macro average (64.3) and improves all three domains, with the largest airline gain; full-bank context trails it by 2.8 macro and 2.6 micro points (maintaining memory helps, exposing all of it is not enough); always inject "is competitive and slightly leads on micro-average by 0.3 points, but this gap is within expected run variance and disappears on the domain-balanced macro-average"; injection-only helps telecom most (66.7) but hurts airline (62.0 against 68.0); Mem0 improves the average but not airline. Conclusion: neither passive exposure, always-on reminders nor generic guidance is enough; the most balanced gains come from maintained state plus selective intervention (§4.3).

Take away the memory agent's option to stay silent, so it must remind at every step. On τ²-Bench as a whole (all 278 tasks), against the selective agent, it solves:

Always inject solves 171 tasks; the selective agent solves 170 in Table 2 and 172 in Table 1. Those two are the same configuration, so the run-to-run spread of one setup (2 tasks, all in retail: 65 against 67 of 114) is as large as the difference the ablation is supposed to measure. The macro advantage (64.3 against 63.5) comes from airline, 39 against 36 tasks of 50, while always inject wins retail by 2 tasks and telecom by 2. The paper itself calls the micro gap "within expected run variance"; the same is true of the macro gap. What the table supports is that reminding at every step does not hurt, which is a finding against the premise that unnecessary reminders are costly in accuracy. It says nothing about cost, which the paper does not report.

In the released traces: what the memory agent actually says

§4.4; repository examples

The repository releases five Terminal-Bench tasks run twice: Sonnet 4.5 alone (5 March 2026) and Sonnet 4.5 with the Opus 4.6 memory agent (24 March 2026), with every memory step, bank edit and reminder rendered (examples). Four of the five are the tasks the paper's qualitative section names: regex-log, adaptive-rejection-sampler, the Git server task and sqlite-with-gcov. The exports carry no verifier result, so which runs passed is not stated. The Replay tab steps through all of them; here is what they add up to.

The memory agent runs at every step and is told its default is silence. In the five released memory runs, at what share of steps does it inject a reminder?

Three things stand out, each counted in recompute.py:

  • Nothing scrolled out of the window. The largest action-agent prompt in any of the ten runs is 71,255 tokens, against Sonnet 4.5's 200k-token window (context windows), and Terminus 2's summariser never fired in the memory runs. Whatever decayed, it decayed in plain sight, which is the paper's own framing (still in context, no longer acting on behaviour).
  • Most reminders are not reminders. Reading each of the 52 (labels shown in the Replay tab so you can disagree): 27 are fresh diagnoses of what the last command just printed, often with a fix ("gcov comes bundled with gcc"; "use python3 with the requests library" when curl is missing); 14 recall something older that the actor was repeating or had left open (a heredoc that silently fails to write /app/ars.R, an sshd that cannot be killed); 11 are checks before finishing. The prompt allows this ("connect dots"), and it makes the memory agent partly the advisor the paper sets itself apart from.
  • They are long and they are not cheap. A reminder averages about 1,520 characters (about 400 tokens), not a line. Each memory step sends the bank and the window twice, once per phase, to Opus. At list prices without caching, the memory runs cost an estimated 2.2 times the baseline runs in total, and the memory agent is about half of the memory run's bill. These are estimates from character counts (the memory agent's token counts are not in the export, and any thinking tokens it used are not counted, so they are a floor).

Qualitative analysis

§4.4, Table 3

The paper's inspection of memory-enabled trajectories: the dominant pattern is not summarisation; memory helps when it reactivates a specific piece of execution state at the moment the actor is about to ignore it. The kind of state differs: Terminal-Bench needs environment observations, debugging continuity and diagnoses; τ²-Bench needs policy clauses, user and tool state, and procedural order (§4.4). Table 3 names five mechanisms:

MechanismTypical memory contentRepresentative examples

Terminal-Bench (§4.4): in regex-log memory reactivates both requirements and diagnoses, pointing out that the regex violates the boundary condition and misses single-digit IPv4 octets; in adaptive-rejection-sampler it tracks repeated failed file edits and later surfaces an environment-specific workaround. Memory preserves continuity across debugging iterations: what was tried, observed, failed, and what still constrains the solution. τ²-Bench (§4.4): in one airline case the user claimed Gold status but the tool showed a Regular member; the baseline compensated on the user's claim, the memory-enabled agent was reminded to rely on verified records. In another, memory blocked an invalid change to a basic-economy flight by reactivating the clause that such flights cannot be modified. Successful interventions often land just before a state-changing tool call (authentication, eligibility, one-shot tool limits, policy clauses not enforced by the tools).

Failures are mostly calibration, not storage: the memory agent occasionally states a speculative inference too confidently, repeats what the actor already knows, or raises a plausible but needless concern that triggers extra verification; this motivates training it to stay silent better. The paper concludes that interventions help more often than they hurt, but gives no count. In the released traces both failure kinds are visible: the regex-log reminder before turn 4 spends three of its seven points confirming that parts of the pattern are already correct (two of them the same February check), and most of the eight reminders that close git-multibranch re-raise one worry, whether the grader will reach the server on port 22, after the actor has already worked around it.

Training an open-weight memory agent

§4.5, Table 4

To replace the Opus call, the paper trains Qwen3.5-27B as the memory agent while a Qwen3.5-122B-A10B actor stays frozen, on SETA (executable terminal tasks with verifier rewards), with Terminal-Bench 2.0 held out (§4.5). SFT distils prompted-memory trajectories, supervising both the Phase 1 bank operations and the Phase 2 decisions; GRPO then optimises the intervention decision. Because the task reward is sparse over many memory calls, updates focus on pivot turns that labelled offline rollouts identify as likely to affect success.

The untrained 27B memory agent hurts (SETA reward 0.709 to 0.693); SFT recovers and improves it (0.720), GRPO raises it further (0.734). On held-out Terminal-Bench the trained memory agent lifts the frozen actor from 37.6% to 41.1% (32 to 35 of 85; 35/85 is 41.18%, so the printed 41.1 is truncated rather than rounded) (Table 4). The paper's reading: the policy is learnable but needs calibration, and RL improves when remembered state enters the loop. Two limits it does not state: SFT and GRPO solve the same 58 validation tasks, so the GRPO gain is in partial reward rather than in tasks solved, and the validation set's size is not given (if reward were pass or fail, the four rows would imply 79, 78, 81 and 79 tasks, so it is not binary). The 3-task Terminal-Bench gain is a single run, inside one standard error (about 7.5 points at n = 85).

Why it matters (beyond the paper)

It works on models you do not control. The actor's weights, instructions and decoding are untouched; the memory agent only adds text to the next call. That makes it a harness component: something an agent framework can add around any API model, the same layer where the knowledge base's SoL-Pi page places its efficiency techniques and where Topic: agentic-harnesses collects harness-scaling strategies.

It sits between two products that already exist. On one side, store-and-retrieve memory layers (Mem0, MemGPT); on the other, a stronger model advising a cheaper one. Anthropic's advisor tool, which the paper cites, lets an executor model consult a higher-intelligence advisor that reads the full transcript mid-task; there the executor decides when to ask. Here the watcher decides when to speak, and is meant to say only what the run already established. The released traces suggest that in practice the two blur: most of the memory agent's messages are an Opus model's fresh reading of the latest output.

Timing as the problem is a useful frame even where the evidence is thin. Retrieval-augmented generation fixes the timing (retrieve at every call) and makes ranking the whole problem; this paper makes timing the variable. Its own ablation shows that fixing the timing at "every step" costs nothing in accuracy on τ²-Bench; whether a well-timed reminder beats a constant one when tokens are priced is the experiment the paper motivates and does not run.

Connections

  • Topic: agentic-harnesses: the constructive counterpart to its harness-scaling strategies. A second model supervising the first is the same delegating-coordinator shape, pointed at memory rather than at task decomposition.
  • SoL-Pi, from the same window, finds roughly half an agent's recorded tokens are harness overhead and cuts them 44.7% to 49.0%. Context compaction and selective reminding are the same lever pulled in opposite directions, one removing what is carried and the other restoring what was dropped, and nobody has yet measured them together. The released traces sharpen the tension: here the memory agent's own input is estimated at about 0.7 times the actor's.
  • Trained Persistent Memory: memory in a frozen model's latent space, trained end to end; this paper stays entirely in text, and its "write" is a model choosing tool calls.
  • Just-in-Time Memory: learning what memory to curate for a task; this paper asks when to say it.
  • RAG: retrieval at every call with ranking as the problem, the design the paper defines itself against; ReAct: the reason-act-observe loop the memory agent watches.
  • Terminal-Universe and HarnessDev: other recent work measured on Terminal-Bench, one building training environments, one evolving the harness itself.
  • Outside the knowledge base: Reflexion stores verbal reflections across attempts; Memory as Action, Context-Folding and Mem-α train the agent itself to manage its context or memory, where this paper trains only a separate memory agent and leaves the actor alone, a harder credit-assignment problem since a reminder may need to be silent, prevent a repeat or revive a diagnosis (§2.3).

How much of this to believe

§4, Tables 1, 2 and 4

What holds up. The comparisons are paired: baseline and memory runs use the same tasks, harness and actor, and the ablations hold both models fixed. The code, both run configurations and five full example traces are public, so the mechanism can be inspected rather than taken on trust, and every printed percentage maps back to a whole number of tasks. The authors are candid in places: the training study is called preliminary, and the micro-average edge of always injecting is called "within expected run variance" (§4.3). The τ²-Bench gain for Sonnet is the strongest number: 19 more tasks of 278 (+6.8 points; unpaired standard error 4.2 points), significant in a paired test as long as no more than 83 tasks changed outcome between the two runs.

The weaknesses, concretely:

  1. One run per cell, no seeds or error bars, with the actor sampling at temperature 0.7. The same full configuration appears twice (Table 1 and Table 2) and solves 172 and 170 τ²-Bench tasks, a 2-task spread that is as large as several of the ablation gaps.
  2. The Terminal-Bench headline is small in tasks and its baseline is low. +8.3 points is 7 tasks of 85; it is significant in a paired test only if at most 9 tasks changed outcome. The baseline, 37.6%, is 5.2 points under the Terminal-Bench paper's own figure for the same model and harness, 42.8% ± 2.8% over at least five runs (Terminal-Bench, Table 2); the memory run's 45.9% is 3.1 points above that published baseline. The released configuration caps the actor at 50 turns, which may explain part of the gap (unconfirmed). Opus's +2.4 is 2 tasks; the trained Qwen agent's +3.5 is 3.
  3. Not like for like on model strength or cost. The treatment adds Claude Opus 4.6, called twice at every step, to a Sonnet 4.5 actor. The obvious matched baseline, Opus acting alone, is in Table 1 and beats the Sonnet pair on τ²-Bench by 12 tasks (66.2% against 61.8%); the paper does not draw that comparison. No tokens, latency or cost are reported for either model, although the paper's own motivation is that surfacing too much "adds latency, consumes tokens" (§1). From the released traces the memory runs cost an estimated 2.2 times the baselines.
  4. The title's claim, that selectivity is what helps, is not shown. Always injecting solves 171 τ²-Bench tasks against 170 and 172; the macro edge of the selective agent comes from 3 airline tasks of 50. Ablations exist only for τ²-Bench and only for the Sonnet actor.
  5. The released agent is not as selective, or as memory-bound, as described. It speaks at 52 of 80 steps (65%) in the five traces, at 28 of 31 in one; about half of what it says is a new diagnosis of the latest output rather than a remembered fact; the reminders average about 400 tokens. The run configuration's header even calls it "single-phase". The examples are chosen (four are the paper's qualitative cases) and carry no pass or fail result.
  6. Small text and table inconsistencies: retail "+9.7" in the text against +9.6 in Table 1; the full agent's retail score 58.8% in Table 1 against 57.0% in Table 2 for the same configuration; 61.8% and 41.1% are truncated (172/278 = 61.87%, 35/85 = 41.18%) where every other figure is rounded; "at a fixed interval" and "every N steps" in the method and figure caption against "every subsequent step" in the experiments. None changes a conclusion. The details are in the tables tab.
  7. The training result is thin. SFT and GRPO solve the same 58 SETA validation tasks; the set's size is not stated; the transfer is 3 tasks in one run; no weights or training code are released.

Verdict. A strong model watching a weaker one and interjecting helps the weaker one on these benchmarks: believe the direction, especially on τ²-Bench, and treat the Terminal-Bench size as provisional given its low baseline. The paper's distinctive claim, that the value lies in deciding when to remind rather than in reminding, is not supported by its own ablation, and the released traces show an agent that mostly advises. Whether the gain is worth roughly doubling the bill, against simply using the stronger model as the actor, is unmeasured, and on τ²-Bench the stronger model alone wins.

What it takes to use this

  • Code: yifannnwu/proactive-memory-agent, Apache-2.0. Released: the two-phase memory agent, a Terminal-Bench runner on a vendored Harbor with Enroot sandboxes (the README explains swapping in Harbor's Docker environment), the baseline and memory configurations, five example traces. Model calls go through LiteLLM, so any action and memory model pair can be set in the YAML. Not released: the τ²-Bench runs, the ablation variants, the SETA training pipeline and the trained Qwen3.5-27B memory agent (checked 3 October 2026).
  • Running cost: two memory-model calls per action step, each carrying the bank and the last 8 steps of reasoning and terminal output. In the released traces that input averaged about 0.7 of the actor's own input tokens; at Opus 4.6 prices ($5 and $25 per million tokens against Sonnet 4.5's $3 and $15, pricing) the memory agent was about half the bill. Prompt caching, a longer interval or event triggers (after errors or repeated commands, which the paper names as future work, §3.4) would cut this; none is measured.
  • Which setups worked: an Opus 4.6 memory agent helped Sonnet 4.5 a lot and Opus 4.6 a little; an untrained Qwen3.5-27B memory agent made a Qwen3.5-122B-A10B actor worse on SETA, and only after SFT and GRPO did it help (+3 Terminal-Bench tasks).
  • When it pays: when the actor must stay a cheaper or fixed model and a stronger model is available to watch, on long debugging or policy-heavy dialogues. When the stronger model could simply be the actor, compare that first: on τ²-Bench it scored higher alone.

  • The Terminal-Bench results also include Opus 4.6 as actor, 43.5% to 45.9%; the τ²-Bench 66.2% to 68.7% is that same Opus actor.
  • "Four model pairings": with Opus 4.6 as the memory agent there are two actors on two benchmarks, plus the Qwen pair on Terminal-Bench.
  • "Gains larger for the weaker actor on Terminal-Bench and smaller for the stronger one on τ²-Bench, as if substituting for context management the stronger model partly does itself": the weaker actor gains more on both benchmarks, and the paper reads the stronger actor's remaining gain as evidence that it is not merely compensating for limited capacity (§4.2).
  • "Reminding selectively beats reminding at every step" holds only on the macro average, by 3 airline tasks; on the task-weighted average always injecting is ahead (171 against 170 tasks), within the paper's own run-to-run spread.
  • "No cost accounting is reported" is confirmed; this page estimates it from the released traces.

Replay the traces

The paper releases five Terminal-Bench 2.0 tasks run twice: Claude Sonnet 4.5 alone, and Sonnet 4.5 with the Claude Opus 4.6 memory agent. Step through either run turn by turn: the actor's prompt size, what it concluded, and, in the memory run, what the memory agent wrote to its bank and whether it spoke.

Try: sqlite-with-gcov (silent at 7 of 10 steps) against git-multibranch (speaks at 28 of 31), and watch how often a "reminder" is a fresh diagnosis of the last output. Switch to the baseline run of the same task: two of the five ran longer with memory than without.

Bars: the action agent's prompt tokens at each turn, as logged; both runs of a task share one scale. Squares under the memory run: one per memory step, run just before the turn above it; filled when it injected a reminder, coloured by this page's reading of the reminder (labels). Memory-agent tokens are estimated from the prompt text in the export at 3.76 characters per token (calibrated on the actor's first prompt in all ten runs, where both the text and the logged token count are known), counted twice per step because both phases are sent the bank and the window; its thinking tokens, if any, are not in the export. Costs use list prices without caching: Sonnet 4.5 $3 and $15, Opus 4.6 $5 and $25 per million input and output tokens (pricing). Snippets, bank edits and reminders are shortened; the full texts are in the repository's examples. The exports do not record whether the verifier passed.

How the reminders were labelled

recall brings back something from earlier in the run that the actor was about to repeat or had left open (a requirement, an environment fact, a failed attempt, an old diagnosis): what the paper says the memory agent is for. diagnose analyses what the latest command just printed, usually with a fix: advice from a stronger model, visible in the actor's own window. check asks for verification before finishing. This is a reading of the text, not a measurement; each label is shown with its reminder so it can be checked.

How big is the noise?

The paper reports one run per cell. Two yardsticks it does not give: the unpaired standard error of each difference, and the paired (McNemar, exact) test, which needs the number of tasks whose outcome changed between the two runs. That number is not reported, so the table gives the largest number of changed tasks for which the gain would still be significant at 5%.

Reference for run-to-run spread: the Terminal-Bench paper runs every agent and model pair at least five times and reports Claude Sonnet 4.5 with Terminus 2 at 42.8% ± 2.8% (95% interval) and Claude Opus 4.5 with Terminus 2 at 57.8% ± 2.5% (Terminal-Bench, Table 2); this paper's Sonnet baseline is 37.6%, one run. In this paper, the same full memory configuration run twice solved 172 and 170 τ²-Bench tasks.
