Problem: behavioral state decay

[[S1|§1 Introduction]]

Long-horizon agent tasks unfold over many observations, actions and partial decisions, and agents fail in a recognisable way: they identify a requirement early and violate it later while fixing an unrelated bug; they see a command, parameter or implementation path fail and later retry a near-identical variant; they diagnose an error and later treat the same error as new ({{§1|ax:S1}}). The paper names this behavioral state decay: task requirements, environment facts, previous attempts, failure diagnoses, intermediate discoveries and open subgoals stop influencing the next decision. The information may still be in the transcript, even inside the context window, but it no longer exerts reliable control over behaviour; models under-use information depending on where it sits in a long context ({{§1|ax:S1}}, citing {{Liu et al. 2024|https://arxiv.org/abs/2307.03172}}). So simply making longer histories available is not enough.

Most memory systems answer a different question: can the information be stored and retrieved? MemGPT, MemoryBank, generative agents and Mem0 are built for personalisation, persistent user state and recall across sessions ({{§1|ax:S1}}, {{§2.2|ax:S2.SS2}}). During active task execution memory also has to decide when to intervene. Surface too little and the agent repeats mistakes; surface too much and it costs latency and tokens and distracts the agent from local progress. The paper's framing: memory for long-horizon agents is an intervention problem, not only a write and retrieval problem. It is also stronger than summarisation: a summariser asks what to retain; the memory agent asks whether any retained state should become active in the next decision, and a fixed summarisation policy cannot know that because the useful memory differs by task (a hard requirement in one, a failed command or an unfinished subgoal in another) ({{§1|ax:S1}}, {{§2.5|ax:S2.SS5}}).

Idea: a second model that decides when to remind

[[S3|§3, Figure 3]]

An unmodified action agent does the work. A separate memory agent runs alongside it: at the first step and then at a fixed interval it reads the task description, a window of recent trajectory and its own structured memory bank; it first edits the bank (Phase 1), then decides whether to inject a concise reminder into the action agent's next call or to stay silent (Phase 2) ({{§3|ax:S3}}, {{Figure 3|ax:S3.F3}}). A reminder is a forgotten requirement, a stable environment fact, a failed attempt or a diagnosis. Nothing about the actor is retrained: same base instructions, tools and decoding, only an optional transient memory context at call time ({{§3.3|ax:S3.SS3.SSS0.Px2}}). That is the whole design, and the cheapness of the integration is the point: it is a harness-layer addition that can be bolted onto a model you do not control, and the paper calls it plug-and-play with frontier action agents and existing harnesses ({{abstract|https://arxiv.org/abs/2607.08716}}).

Two neighbours it is defined against: passive memory retrieves records on demand and never decides whether memory should enter the control loop at all; advisor models give broad strategic guidance, while this memory agent is restricted to memory-grounded reminders ({{§1|ax:S1}}, {{§2.4|ax:S2.SS4}}). The paper's ablations (Table 2) remove one capability at a time. The animation runs one real memory step from a released trace, the moment the actor's apt-get install -y gcc make gcov fails, through the full design and through each ablation, so you can see what each one passes to the actor's next call.

Real for "Proactive memory": the command, the error, the bank entries and the reminder are from the released memory run of sqlite-with-gcov (memory trigger 4, before action turn 4; {{trace|https://github.com/yifannnwu/proactive-memory-agent/tree/main/examples/sqlite-with-gcov}}). The other designs were run only on τ²-Bench and released no traces, so what they would pass at this step is illustrative, built from the paper's description of each variant ({{§4.3|ax:S4.SS3.SSS0.Px1}}). The token bar is to scale: the actor's turn-4 prompt was 3,871 tokens; added text is converted at 3.76 characters per token, measured on these traces. Scores are Table 2's, on τ²-Bench.

The interesting claim is in the silence. A reminder is not free: it takes context, and an irrelevant one competes with the actual task state for the actor's attention. So the memory agent's job is presented as discrimination, not retrieval: the bottleneck in long-horizon work, on this view, is knowing when to surface a fact rather than being able to find it, which is what separates it from retrieval-augmented generation, where ranking is the whole problem and the timing is fixed (every call). Whether the experiments show that silence is what helps is taken up under {{Ablations|tab:t-read:s-abl}} and {{In the traces|tab:t-read:s-traces}}.

Method

[[S3.SS1|§3.1 to §3.5]]

Setup. The action agent produces a trajectory τ = (o1, a1, o2, a2, …, oT) of observations and actions, sampling at ∼ πA(at | x, τ<t) for task x. Requirements, environment facts, attempts, diagnoses, discoveries and open subgoals are the execution state, kept outside the action context. At each memory step t the memory agent πM sees the task, a recent window wt of the trajectory and the previous bank, and runs two policies ({{§3.1|ax:S3.SS1}}):

Bt ∼ πMedit( · | x, wt, Bt−1),    it ∼ πMintervene( · | x, wt, Bt),    it ∈ {∅, text reminder}

A non-null it is injected into the next action-agent call as transient context; ∅ leaves the call unchanged. Memory becomes a policy over interventions: what to retain, and when retained state is useful enough to enter the action loop.

The bank is Bt = (st, Kt, Pt) ({{§3.2|ax:S3.SS2}}): a private status field st (progress, open issues, unresolved risks; never shown to the actor), knowledge entries Kt (stable facts: requirements, environment properties, paths, configuration, verified facts, evaluation-relevant observations) and procedural entries Pt (attempts and outcomes: failed commands, successful fixes, ruled-out hypotheses, diagnostic signals, improvements). Each entry is a short identifier, natural-language content and metadata (creation time, access statistics); identifiers let the agent update or delete stale entries, and entries are written in a compact tagged format.

Phase 1, memory management, returns a list of tool calls that the system executes in order; the agent never rewrites the bank directly, and no call leaves it unchanged ({{Phase 1|ax:S3.SS3.SSS0.Px1}}). The four tools: memory_update_status (the private progress note), memory_save_knowledge (requirements, environment facts, paths, API details, constraints), memory_save_procedural (debugging experience, failed approaches, error patterns, fixes, performance observations) and memory_delete (by identifier). The output is a sequence of bank edits, not a free-form summary.

Phase 2, intervention, reads the updated bank and the recent trajectory and emits either <context_for_action> with a reminder or <no_intervention/>; it never edits the bank ({{Phase 2|ax:S3.SS3.SSS0.Px2}}). The null intervention is an explicit action. Encouraged: requirements about to be violated, environment facts that explain the current observation, attempts not to repeat, diagnoses still relevant, neglected subgoals. Discouraged: broad strategic advice, restating what is already visible, taking over the actor's planning.

Trigger. A trigger function g(t) runs the memory agent at the first step and then at a fixed interval; error-, test- or repetition-triggered schedules are possible but left out to isolate the intervention policy ({{§3.4|ax:S3.SS4}}). In the experiments the interval is every step, with a window of k = 8 messages ({{§4.1|ax:S4.SS1.SSS0.Px3}}).

What the released code adds
  • The run configuration sets the actor at temperature 0.7 with at most 50 turns and Terminus 2's summarisation on; the memory agent at temperature 0.3, interval 1, window 8, reminders appended to the actor's latest user message; the window is the last 8 recorded steps, each the actor's reasoning plus the terminal output ({{memory_enabled_agent.py|https://github.com/yifannnwu/proactive-memory-agent/blob/main/src/memory_agent/memory_enabled_agent.py}}); the status resets per episode while knowledge and procedural entries persist ({{memory_terminalbench.yaml|https://github.com/yifannnwu/proactive-memory-agent/blob/main/configs/memory_terminalbench.yaml}}). The file's own header calls the run "single-phase tool-only memory (trigger every step, window = 8)", while the code it runs is the two-phase agent.
  • The two phases are two separate model calls, each sent the full bank and the window, even though the module's docstring describes "one conversation" sharing context ({{memory_agent.py|https://github.com/yifannnwu/proactive-memory-agent/blob/main/src/memory_agent/memory/memory_agent.py}}). Above 50 entries the bank shown to the model is pre-filtered to the 20 knowledge and 20 procedural entries that best match the window by BM25: a retrieval step inside the "not retrieval" design. In the five released traces the bank never exceeds a handful of entries, so the filter never fires there.
  • The Phase 2 prompt tells the model its "DEFAULT is <no_intervention/>", to frame reminders "as observations, not commands", and that it "CAN connect dots and highlight patterns, not limited to verbatim copies from bank".

Learning the policy ({{§3.5|ax:S3.SS5}}). The architecture needs no training: the main memory agent is a prompted model. Because prompted memory agents add inference cost and are imperfectly calibrated, the paper also trains an open-weight memory agent while keeping the actor fixed: SFT distils trajectories of the prompted agent (the interface, compact writing, updating stale state, avoiding needless reminders), then RL calibrates when to speak. The paper calls this preliminary; the architecture does not depend on it.
