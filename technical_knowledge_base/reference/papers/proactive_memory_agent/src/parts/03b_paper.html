Results

[[S4.T1|§4.1, §4.2, Table 1]]

Benchmarks. {{Terminal-Bench 2.0|https://arxiv.org/abs/2601.11868}}: autonomous work in real command-line containers (inspect files, run commands, edit code, debug, satisfy hidden verifier tests), binary pass/fail per task, run with the official Terminus-2-style harness. Of its 89 tasks the paper reports the 85 where both the baseline and the memory run produced a valid evaluation, excluding four docker failures ({{§4.1|ax:S4.SS1.SSS0.Px1}}). {{τ²-Bench|https://arxiv.org/abs/2506.07982}}: conversational tool use with a simulated user in the airline (50 tasks), retail (114) and telecom (114) domains, 278 per configuration, one sampled conversation per task ({{§4.1|ax:S4.SS1.SSS0.Px2}}). Terminal-Bench stresses environment grounding and debugging continuity; τ²-Bench stresses policy adherence and user-state tracking. Unless stated, the memory agent is Claude Opus 4.6; the action agents are Claude Sonnet 4.5 and Opus 4.6; all scores are pass@1 ({{§4.1|ax:S4.SS1.SSS0.Px3}}).

Memory improves every aggregate in Table 1. Below, each percentage is turned back into whole tasks (every printed figure maps to exactly one count; the {{tables tab|tab:t-tables}} shows the check).

Grey: action agent alone. Colour: with the Opus 4.6 memory agent. One run per bar ({{Table 1|ax:S4.T1}}).

On Terminal-Bench, Sonnet 4.5 goes from 37.6% to 45.9% (+8.3 points, 32 to 39 tasks) and Opus 4.6 from 43.5% to 45.9% (+2.4, 37 to 39). On τ²-Bench's task-weighted average, Sonnet goes from 55.0% to 61.8% (+6.8, 153 to 172 tasks) and Opus from 66.2% to 68.7% (+2.5, 184 to 191). The paper reads this as: larger gains for the weaker actor, but gains that do not vanish for the stronger one, so not merely compensation for limited capacity. By domain, Sonnet's lifts are largest on airline (+10.0) and retail (+9.6 in the table, "+9.7" in the text) and small on telecom (+2.6), which the paper takes as memory being a domain-sensitive intervention policy ({{§4.2|ax:S4.SS2}}). Opus gains nothing on airline (76.0% both ways).

Which scores higher: Sonnet 4.5 with the Opus 4.6 memory agent, or Opus 4.6 acting alone with no memory?

On Terminal-Bench the Sonnet pair reaches 45.9% against Opus alone at 43.5%, and Opus with its own memory agent also reaches 45.9%: the same 39 tasks out of 85, whichever model acts. On τ²-Bench Opus alone (66.2%) beats the Sonnet pair (61.8%) by 12 tasks. The paper never makes this comparison, but it is the one a buyer would: the memory agent is an Opus call at every step, so "add an Opus memory agent to Sonnet" competes with "just use Opus". On τ²-Bench it loses; on Terminal-Bench it ties Opus with memory and edges Opus without it, by two tasks, in single runs.

Ablations: is it the silence?

[[S4.SS3|§4.3, Table 2]]

All on τ²-Bench, Sonnet 4.5 acting, Opus 4.6 as the memory model ({{Table 2|ax:S4.T2}}, {{§4.3|ax:S4.SS3.SSS0.Px1}}). Each variant removes one capability:

  • Full-bank context keeps Phase 1 and drops Phase 2: the whole bank is shown to the actor at every step. Tests whether merely making history visible is the benefit (passive context augmentation).
  • Always inject keeps the bank and the generated reminder but removes the silence action: a reminder at every step. Tests whether the no-op is just an efficiency saving or essential to calibration.
  • Injection-only (no bank) skips Phase 1: a model watches the window and gives selective guidance, like an advisor, but cannot ground it in maintained state.
  • Mem0: memories written through Mem0's ADD interface and the top 10 retrieved by vector plus BM25 search returned to the actor; production retrieval against selective intervention.

Recomputed from the three domain scores; every printed average reproduces. The dashed line is the same full agent's Table 1 run (172 tasks, 61.9% task-weighted, printed 61.8%).

The paper's reading: the full two-phase agent has the best macro average (64.3) and improves all three domains, with the largest airline gain; full-bank context trails it by 2.8 macro and 2.6 micro points (maintaining memory helps, exposing all of it is not enough); always inject "is competitive and slightly leads on micro-average by 0.3 points, but this gap is within expected run variance and disappears on the domain-balanced macro-average"; injection-only helps telecom most (66.7) but hurts airline (62.0 against 68.0); Mem0 improves the average but not airline. Conclusion: neither passive exposure, always-on reminders nor generic guidance is enough; the most balanced gains come from maintained state plus selective intervention ({{§4.3|ax:S4.SS3}}).

Take away the memory agent's option to stay silent, so it must remind at every step. On τ²-Bench as a whole (all 278 tasks), against the selective agent, it solves:

Always inject solves 171 tasks; the selective agent solves 170 in Table 2 and 172 in Table 1. Those two are the same configuration, so the run-to-run spread of one setup (2 tasks, all in retail: 65 against 67 of 114) is as large as the difference the ablation is supposed to measure. The macro advantage (64.3 against 63.5) comes from airline, 39 against 36 tasks of 50, while always inject wins retail by 2 tasks and telecom by 2. The paper itself calls the micro gap "within expected run variance"; the same is true of the macro gap. What the table supports is that reminding at every step does not hurt, which is a finding against the premise that unnecessary reminders are costly in accuracy. It says nothing about cost, which the paper does not report.

In the released traces: what the memory agent actually says

[[S4.SS4|§4.4; repository examples]]

The repository releases five Terminal-Bench tasks run twice: Sonnet 4.5 alone (5 March 2026) and Sonnet 4.5 with the Opus 4.6 memory agent (24 March 2026), with every memory step, bank edit and reminder rendered ({{examples|https://github.com/yifannnwu/proactive-memory-agent#examples}}). Four of the five are the tasks the paper's qualitative section names: regex-log, adaptive-rejection-sampler, the Git server task and sqlite-with-gcov. The exports carry no verifier result, so which runs passed is not stated. The {{Replay tab|tab:t-run}} steps through all of them; here is what they add up to.

The memory agent runs at every step and is told its default is silence. In the five released memory runs, at what share of steps does it inject a reminder?

Three things stand out, each counted in {{recompute.py|tab:t-tables:chk}}:

  • Nothing scrolled out of the window. The largest action-agent prompt in any of the ten runs is 71,255 tokens, against Sonnet 4.5's 200k-token window ({{context windows|https://platform.claude.com/docs/en/build-with-claude/context-windows}}), and Terminus 2's summariser never fired in the memory runs. Whatever decayed, it decayed in plain sight, which is the paper's own framing (still in context, no longer acting on behaviour).
  • Most reminders are not reminders. Reading each of the 52 (labels shown in the Replay tab so you can disagree): 27 are fresh diagnoses of what the last command just printed, often with a fix ("gcov comes bundled with gcc"; "use python3 with the requests library" when curl is missing); 14 recall something older that the actor was repeating or had left open (a heredoc that silently fails to write /app/ars.R, an sshd that cannot be killed); 11 are checks before finishing. The prompt allows this ("connect dots"), and it makes the memory agent partly the advisor the paper sets itself apart from.
  • They are long and they are not cheap. A reminder averages about 1,520 characters (about 400 tokens), not a line. Each memory step sends the bank and the window twice, once per phase, to Opus. At list prices without caching, the memory runs cost an estimated 2.2 times the baseline runs in total, and the memory agent is about half of the memory run's bill. These are estimates from character counts (the memory agent's token counts are not in the export, and any thinking tokens it used are not counted, so they are a floor).

Qualitative analysis

[[S4.SS4|§4.4, Table 3]]

The paper's inspection of memory-enabled trajectories: the dominant pattern is not summarisation; memory helps when it reactivates a specific piece of execution state at the moment the actor is about to ignore it. The kind of state differs: Terminal-Bench needs environment observations, debugging continuity and diagnoses; τ²-Bench needs policy clauses, user and tool state, and procedural order ({{§4.4|ax:S4.SS4}}). Table 3 names five mechanisms:

MechanismTypical memory contentRepresentative examples

Terminal-Bench ({{§4.4|ax:S4.SS4.SSS0.Px1}}): in regex-log memory reactivates both requirements and diagnoses, pointing out that the regex violates the boundary condition and misses single-digit IPv4 octets; in adaptive-rejection-sampler it tracks repeated failed file edits and later surfaces an environment-specific workaround. Memory preserves continuity across debugging iterations: what was tried, observed, failed, and what still constrains the solution. τ²-Bench ({{§4.4|ax:S4.SS4.SSS0.Px2}}): in one airline case the user claimed Gold status but the tool showed a Regular member; the baseline compensated on the user's claim, the memory-enabled agent was reminded to rely on verified records. In another, memory blocked an invalid change to a basic-economy flight by reactivating the clause that such flights cannot be modified. Successful interventions often land just before a state-changing tool call (authentication, eligibility, one-shot tool limits, policy clauses not enforced by the tools).

Failures are mostly calibration, not storage: the memory agent occasionally states a speculative inference too confidently, repeats what the actor already knows, or raises a plausible but needless concern that triggers extra verification; this motivates training it to stay silent better. The paper concludes that interventions help more often than they hurt, but gives no count. In the released traces both failure kinds are visible: the regex-log reminder before turn 4 spends three of its seven points confirming that parts of the pattern are already correct (two of them the same February check), and most of the eight reminders that close git-multibranch re-raise one worry, whether the grader will reach the server on port 22, after the actor has already worked around it.

Training an open-weight memory agent

[[S4.SS5|§4.5, Table 4]]

To replace the Opus call, the paper trains Qwen3.5-27B as the memory agent while a Qwen3.5-122B-A10B actor stays frozen, on {{SETA|https://github.com/camel-ai/seta}} (executable terminal tasks with verifier rewards), with Terminal-Bench 2.0 held out ({{§4.5|ax:S4.SS5}}). SFT distils prompted-memory trajectories, supervising both the Phase 1 bank operations and the Phase 2 decisions; GRPO then optimises the intervention decision. Because the task reward is sparse over many memory calls, updates focus on pivot turns that labelled offline rollouts identify as likely to affect success.

The untrained 27B memory agent hurts (SETA reward 0.709 to 0.693); SFT recovers and improves it (0.720), GRPO raises it further (0.734). On held-out Terminal-Bench the trained memory agent lifts the frozen actor from 37.6% to 41.1% (32 to 35 of 85; 35/85 is 41.18%, so the printed 41.1 is truncated rather than rounded) ({{Table 4|ax:S4.T6}}). The paper's reading: the policy is learnable but needs calibration, and RL improves when remembered state enters the loop. Two limits it does not state: SFT and GRPO solve the same 58 validation tasks, so the GRPO gain is in partial reward rather than in tasks solved, and the validation set's size is not given (if reward were pass or fail, the four rows would imply 79, 78, 81 and 79 tasks, so it is not binary). The 3-task Terminal-Bench gain is a single run, inside one standard error (about 7.5 points at n = 85).
