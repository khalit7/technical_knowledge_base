The idea in one sentence: score the harness, not the answer: a creator model turns a zero-scoring seed into a harness, the harness is frozen, and only then does an executor model run it on 2,207 hidden tasks; every creator built one that works, the best match human references only where those references ran the same or older models, and in Evolution gains the creator saw (+3.0 to +13.9 points) shrank to +1.43 to +4.44 on held-out tasks.

Problem

[[S1|§1 Introduction]]

An agent harness is the software around a model that turns its outputs into actions (loop, tools, context, state, recovery, checks; the parts are compared on {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}), and it moves scores a lot ({{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}} has the same-model spread on the public board). The paper's own example: with identical weights, GPT-5 solves 35.2% of Terminal-Bench 2.1 inside the Terminus 2 harness and 49.6% inside Codex CLI, 14.4 points apart ({{§1, citing the Terminal-Bench 2.1 leaderboard|ax:S1}}).

The month before this paper produced several harness-scaling results, each showing that the wrapper moves benchmark scores by tens of points on the same weights: {{Prime Agent|n:3cd5c17b0d0d81579a02f0431f24c6cb}}, {{StateM|n:3c65c17b0d0d81899098d8153e100691}}, {{JIT-Agent|n:3cd5c17b0d0d81148227fbd67dc4b3ee}} and WikiSkill. All of them judge a harness by the task score it produces. Benchmarks such as SWE-bench, GAIA, WebArena, τ-bench and AgentBench do the same: they fix a harness and report model performance under it ({{§5|ax:S5}}). That leaves the obvious next question unasked: can a model build the harness itself, and keep improving it, and how does what it builds compare with something a team spent a year on? Task score alone cannot answer that, because a good score mixes up the harness with the model running inside it.

Why harness work is not ordinary code editing, and the forward-deployed engineer framing

The authors argue harness work differs from ordinary code editing: a model editing its own harness changes how it will observe, plan and recover in every future task, so it must read its own failures from traces and make changes that last ({{§1|ax:S1}}). They frame it through the forward-deployed engineer, who turns a general model into a system that works on one customer's data; of that job's three layers (vague target, missing feedback signal, missing execution system) this paper takes the third ({{§2|ax:S2}}).

Idea: score the harness, not the answer

[[S3.SS1|§3.1, Eq. 1]]

HarnessDev makes the runnable harness the thing being evaluated. A creator model LC works inside a development environment D (Claude Code, or Codex for GPT-5.5) and produces a harness H. H is then frozen. Only after that does an executor model LE run inside it on downstream tasks, and an evaluator J scores the outputs ({{Eq. 1|ax:S3.E1}}):

(LC, D) → H     (H, LE, x) → y → J → score

Keeping the builder and the runner apart is the point: it lets the same harness be run by different models, so harness quality can be separated from executor ability. The figure beside this section steps through the protocol and the three comparisons the paper makes:

  1. The seed. Six empty slots, one for each job the creation prompt asks a harness to do: execution loop, tools, context, state, lifecycle and verification. The seed fills none of them with working policy; it parses the task, exposes passive primitives, writes its audit files and stops after one pass, so all five benchmark bars stand at 0 ({{Appendix C.1|ax:A3.SS1}}, {{Table 3|ax:S4.T3}}).
  2. A creator builds. The creator, here Opus 4.8 in Claude Code, writes code into the slots. It has a task-family specification, tool and permission constraints, a short design tutorial and one to three development cases, whose feedback flows back to it; it never sees the hidden tasks or the human implementation ({{Table 1|ax:S3.T1}}).
  3. What 18 code harnesses ended up with. Each column is filled to the number of the 18 Creation code harnesses (six creators, three each) with a complete implementation of that job: execution loop 18, verification 15, tools 13, lifecycle 13, state 1, in red; context is not reported separately for code ({{Figure 5|ax:S4.F5}}). State is the gap.
  4. Frozen, then Self-Eval. The harness is frozen in its case and the creator leaves. An executor runs it on the hidden tasks of five benchmarks: 731 SWE-Pro, 89 Terminal-Bench, 75 MLE-bench, 46 EQ-Bench3 and 1,266 BrowseComp, 2,207 in all. Under Self-Eval the executor is the creator itself, so the bars are Opus 4.8's avg@3 scores, 69.3, 64.8, 32.9, 84.6 and 52.4 ({{Table 3|ax:S4.T3}}): how a user would deploy it, measuring harness design, executor capability and the fit between them at once.
  5. Unified-Eval: Gemini 3.1 Pro runs it. The same frozen harness with the executor swapped. Gemini 3.1 Pro runs every creator's harness, so differences between harnesses are not differences between executors ({{Table 4|ax:S4.T4}}). Opus's harness falls on four of the five (SWE-Pro 69.3 to 33.0, EQ-Bench3 84.6 to 74.2) and gains 1.2 on BrowseComp. Gemini's own harness is the control, and the one harness fitted to its executor.
  6. The human reference. Beside each bar, the best public system-level result the authors could verify ({{Table 9|ax:A2.T9}}): a different harness with its own model, so a distance to a mature system, not a paired control ({{Appendix D.1|ax:A4.SS1}}). The SWE-Pro reference ran Claude Fable 5 and the Terminal-Bench and BrowseComp ones GPT-5.6 Sol (all three external reports, not re-run); MLE-bench's ran Gemini 3.1 and EQ-Bench3's Opus 4.8. Opus's harness is behind on the first three and ahead on the last two.

Two stages follow the software sense of "develop" ({{§3.1|ax:S3.SS1}}):

  • Creation (RQ1): can a model build an effective harness from a weak but runnable seed, given a task specification and a few development cases?
  • Evolution (RQ2): can it improve its own existing harness from downstream execution feedback while keeping what already works?

Every harness is scored on two axes ({{§3.5|ax:S3.SS5}}): capability, task success on held-out benchmarks under each benchmark's native metric, and efficiency, the executor tokens the frozen harness consumes (total and mean per task). Tokens the creator spends building the harness are not counted. Reporting both stops a harness from winning by brute force.

Method: the seed, the six modules, the protocol

[[S3.SS2|§3.2, Table 1, Figures 2 and 3, Appendix C]]

The weak seed. Every creator starts from the same seed Hseed, "a runnable compatibility layer, not a task-solving agent" ({{§3.2|ax:S3.SS2}}). It parses the task and model configuration, exposes passive primitives (paths, files, search, process, an LLM gateway) and writes the audit files result.json, trajectory.jsonl and response.md ({{Appendix C.1|ax:A3.SS1}}). It has no agent loop, task decomposition, tool policy, context management, persistent state, verifier, retry or recovery logic, or stopping rule; after one optional connectivity probe it stops with status partial and scores zero on all five benchmarks ({{Table 3|ax:S4.T3}}). So any score comes from logic the creator added, without the creator having to fight command-line and file-format setup, and without a mature agent giving the answer away.

What the creator must build. The prompt defines a harness as H = ⟨E, T, C, S, L, V⟩ ({{Appendix E.1|ax:A5.SS1}}; interface in {{Appendix C|ax:A3}}): Execution loop (planning, stop conditions), Tools (interfaces, selection, error handling), Context (what enters the prompt, compression), State (goals, hypotheses, attempts, checkpoints), Lifecycle (hooks, failure and timeout handling, recovery, finalisation) and Verification (tests, checks, artifact validation). Files need not carry these names; the system must actually perform the jobs. Steps 1 and 3 of the figure show what the seed provides against what the 18 created code harnesses ended up with.

The rules a submitted harness must follow, and how they are enforced

The shared creation prompt ({{Appendix E.1|ax:A5.SS1}}) requires three command-line forms (python -m harness run --task-json ... --model-config ... --output-dir ... and two variants, with aliases such as -p/--prompt), an honest status of success, partial or failed, and model calls only through the provided provider-neutral configuration (no hard-coded model names, base URLs, keys or provider SDKs). It forbids hard-coding task IDs, answers, expected patches or scorer internals, leaving TODO or NotImplementedError placeholders, decorative modules that never run, and degrading the agent into one LLM call or a template filler. Telemetry such as lines of code and module counts is recorded but is "not a scoring target".

Two properties make the rules checkable ({{§3.4|ax:S3.SS4}}). The score path is isolated: a harness's self-reported status never counts, SWE-Pro credit comes only from the real repository diff, and Terminal-Bench credit only from the final environment state. And every run keeps its trajectory, result and metric files beside the frozen source, so the code and what it executed can be audited afterwards. The authors audited every run reported and found no harness scoring through a prohibited route; no run was excluded. In Evolution a violation would set that version's score to 0 ({{Appendix E.2|ax:A5.SS2}}).

Creation protocol ({{§3.2|ax:S3.SS2}}, {{Table 1|ax:S3.T1}}). Along with the seed the creator gets a task-family specification, tool and permission constraints, a short design tutorial and one to three development cases. It may revise the harness using feedback from those cases, but never sees the human implementation or the hidden evaluation set; the harness is frozen before evaluation. Each creator builds three harnesses independently per benchmark and the score is avg@3 ({{§4.1|ax:S4.SS1}}).

Six creators, five benchmarks, four domains ({{§4.1|ax:S4.SS1}}, {{Table 2|ax:S3.T2}}): Opus 4.8, GPT-5.5, Gemini 3.1 Pro, DeepSeek V4 Pro, Qwen 3.7 Max and Seed 2.0 Pro, at high reasoning effort, working in Claude Code 2.1.177 (GPT-5.5 in Codex 0.144.3). Code: SWE-bench Pro public split (731 tasks) and Terminal-Bench 2.1 (89); data analysis: MLE-bench (75, medal score); writing: EQ-Bench3 (46, rubric score); research: BrowseComp (1,266, accuracy). That is 2,207 unique instances, hidden from development.

Evolution protocol ({{§3.2|ax:S3.SS2}}, {{Appendix E.2|ax:A5.SS2}}), code only. The creator starts from its own Creation harness H0 in a git repository. A version becomes official only as a pair of full evaluations of one commit: a fixed 100-task SWE-Pro feedback set and all 89 Terminal-Bench tasks, one to two hours each. The budget is ten pairs, with at most two five-task probes between pairs that never count. The creator sees the pair mean P̄t = ½ (SWE-100 + Terminal-89) in percent ({{Eq. 2|ax:S4.E2}}) and ends by declaring a final version other than H0. After all runs end, every official version is scored on 630 held-out SWE-Pro tasks from the same public split, disjoint from the 100 and never shown to the creator. Five creators run in their own runtime; four rerun with Gemini 3.1 Pro as the fixed runtime: nine lineages.
