The idea in one sentence

[[S0.F1|Figure 1, §1]]

Use the monitor to decide where a sample's update lands, not what it is rewarded: updates from samples the monitor flags go only into a spare forget adapter, which is deleted after training, so the model is never paid for slipping past the monitor ({{§1|ax:S1}}).

Fig. 1, step by step: which adapter each kind of sample trains

  1. The block. Every Transformer block's MLP gets two extra SwiGLU branches, the retain adapter θR and the forget adapter θF (the coloured glass plates); the base MLP stays frozen. Grey dots are one sample's forward pass, through all three branches, whose outputs add.
  2. An unflagged sample. Rolled out with both adapters on (πR+F). The monitor says nothing, so its gradient reaches both adapters, weight 1 each. Real solutions, and hacks the monitor misses, train the retain adapter this way.
  3. A flagged sample. Same forward pass, same reward: the monitor never changes it. The gradient to the retain adapter is zeroed and the forget adapter's is doubled (twice the dots), so the flagged behaviour is learned, but only in θF.
  4. An anchor sample. From a separate hack-free task, rolled out with the forget adapter switched off (πR); only the retain adapter learns. This trains the model in the configuration it will be deployed in.
  5. Deploy. The forget adapter is deleted. Whatever it learned, the detected hack and anything that rode along with it, goes too; the retain adapter keeps the task. On Countdown-Code hacking fell from 38.5% (both adapters on, step 192) to 1.6% (deployed; the two bars).

Redrawn from {{Figure 1|ax:S0.F1}} as a 3D stage: one block, one sample at a time. Grey dots: the forward pass; coloured dots: the gradient that updates an adapter, twice as dense for ×2; a red bar: masked. The two hack rates are the paper's (Figure 2: the pre-ablation peak read from its right panel, the deployed mean of eight seeds replayed from the released data).

You need: GRPO and the verifiable-reward RL loop ({{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}), and why a reward hacker that is penalised by a monitor learns to hide ({{Reward Hacking, sections 6 and 7|n:3c65c17b0d0d8196a6f1f29a817aa974}}).

New terms on this page
Monitor M
a classifier that flags a trajectory as containing unintended behaviour. Here a keyword or code check with a known blind spot; M = 0 does not mean clean ({{§3|ax:S3}}).
Detectable / undetectable hack
forms of the same cheat that the monitor does or does not flag ("actually yellow" against "indeed yellow").
Retain adapter θR
new MLP neurons meant to hold the wanted behaviour; kept at deployment.
Forget adapter θF
new MLP neurons of the same size meant to hold the unwanted behaviour; deleted (ablated) at deployment.
Routing
zeroing the gradient to every parameter except θF on flagged samples (and doubling θF's).
πR+F, πR, πF
the policy with both adapters on (training, "pre-ablation"), with only the retain adapter ("deployment configuration"), with only the forget adapter (a diagnostic).
Anchor environment
a hack-free task trained concurrently on πR, so the model still works with the forget adapter switched off.

Problem: a penalty teaches the model to hide

[[S1|§1, §2]]

RL post-training scores each attempt with a reward function. When that function is misspecified, the policy finds behaviour that scores highly without doing the task, reward hacking; frontier model cards report it ({{§1|ax:S1}}; the {{Reward Hacking|n:3c65c17b0d0d8196a6f1f29a817aa974}} page owns the catalogue). The usual fix adds a monitor (an LLM judge or a keyword detector) and subtracts a penalty from flagged trajectories. But monitors make systematic errors, and a policy optimised against one learns the hacks it misses: too subtle for an LLM judge, impersonating the judge, or going round it ({{§1|ax:S1}}). OpenAI saw exactly this when a chain-of-thought monitor went into the reward ({{Baker et al., 2025|https://arxiv.org/abs/2503.11926}}).

The paper builds that failure on purpose. Its setting ({{§2|ax:S2}}) has four properties: a reward that pays for the task and for a hack; a weak monitor whose blind spot depends on a learnable feature of the answer; plain GRPO converging to hacking; and a goal of least hacking with most task reward. {{Table 1|ax:S4.T1}} is the smallest instance, one of the six toy environments (object_qa):

Table 1 of the paper. Only colour questions admit the hack; "indeed", "actually", "exactly" and "quite" each earn 0.1; the monitor catches all but "indeed".

Train SmolLM2-135M on object_qa with a penalty on every flagged answer (the penalty strength that looks best to the developer, 10). What does the model end up doing on colour questions?

From the authors' released training logs (end of training, three seeds; {{Figure 3|ax:S4.F3}} plots the same runs): The developer's monitor reports almost no hacking. That is the paper's starting observation, and in every toy environment and in Countdown-Code the penalty did the same thing (below).
