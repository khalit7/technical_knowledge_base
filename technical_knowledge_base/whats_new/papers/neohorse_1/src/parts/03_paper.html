Problem

[[S1|§1 Introduction]]

Post-training data for agents is usually curated once, offline, against a fixed task distribution. The serving harness that actually meets the traffic is treated as downstream infrastructure with no say in what the next checkpoint learns. That wastes the one signal a deployed system has that a curated dataset never will: which requests the current model handled badly, and which model in the fleet had to take them.

The report frames this as the missing piece of recursive self-improvement (RSI): a system improving itself needs "a concrete mechanism through which an AI system observes its own capabilities and converts that evidence into the next round of learning" ({{Abstract|ax:abstract1}}). Its claim is that a deployed routing harness already contains one. An agent working inside a harness leaves a record of decisions, tool calls and outcomes, and a router that picks which model serves each turn also leaves, as a side effect, a judgement of how hard that turn was ({{§1|ax:S1}}). The thesis, stated as a loop: "what the system learns to do shapes what it learns from next".

A harness here is the execution layer that manages an agent's context, tools and interaction with its environment; agentic routing lets that layer choose a model per request and per interaction state ({{§1|ax:S1}}; routing by difficulty in general, routers and cascades, is on {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}). The system builds on the authors' earlier {{Agentic Routing|https://arxiv.org/abs/2607.11399}} paper, combining a heterogeneous model pool with several harnesses, including their open {{OpenSquilla|https://github.com/TokenRhythm/opensquilla}}, across real-world tasks.

Idea: let the router write the syllabus

[[S1.F2|Figure 2]]

Five components, and the router is the spine: the hero above names them in order ({{§3|ax:S3}}, {{§4|ax:S4}}). The router produces a labelled judgement of task difficulty as a side effect of serving; curation makes subscene-level labels, which is what makes partial-trajectory supervision possible; the curriculum takes its difficulty ordering from observed traffic rather than a heuristic; and allocation turns evaluation feedback into the next mixture, which closes the loop.

The five components as the paper describes them
  • Heterogeneous model pool with intelligent routing. Requests are routed across service tiers by predicted capability demand rather than by a static rule, so the router is continuously producing a labelled judgement about task difficulty as a side effect of serving.
  • Data curation pipeline. User interactions become training examples through structural validation, a six-dimensional semantic evaluation, and subscene-level labelling, which is finer-grained than per-conversation labelling and is what makes partial-trajectory supervision possible.
  • Three-stage curriculum. Supervised fine-tuning is ordered by those routing signals, so difficulty ordering comes from observed traffic rather than from a heuristic.
  • Routing-guided on-policy distillation. A fixed teacher supervises the student's own generated responses, with starting contexts introduced under the same staged progression.
  • Capability-guided allocation. Evaluation feedback is converted directly into training-mixture decisions, which closes the loop back to the pool.
