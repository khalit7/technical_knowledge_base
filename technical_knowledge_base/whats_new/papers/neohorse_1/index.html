NeoHorse-1: Towards Recursive Self-Improvement via Agentic Post-Training with Routing Harness

NeoHorse Team: 36 authors listed alphabetically (18 core contributors, 18 contributors); corresponding authors Yu Wang and Yunhe Wang
TokenRhythm Technologies, with Infinigence AI, Tsinghua University, Peking University, The Chinese University of Hong Kong, Alibaba Group, Visionplus Capital and WX Capital · 8 September 2026 (arXiv v1, the only version so far)

In one line: Makes the serving harness a source of the training curriculum rather than only downstream infrastructure: a router over a heterogeneous model pool predicts each request's capability demand and those routing signals order a three-stage SFT curriculum; interactions become training data through structural validation, six-dimensional semantic evaluation and subscene-level labelling; a fixed teacher supervises the student's own responses (on-policy distillation) under the same progression; and evaluation feedback is designed to steer the next training mixture. The whole recipe lifts the macro-average over ten agent, tool-use, coding and instruction benchmarks from 58.94 to 64.87 at 4B (up on all ten) and from 65.60 to 69.04 at 9B, and the post-trained 4B closes 89% of the macro gap to the base 9B while beating it on 5 of the 10 benchmarks. No experiment isolates the routing curriculum, the distillation or the allocation step, the loop ran once, and the one controlled comparison (harness data against public Toucan data, +6.26) is mostly the public-data run falling 4.99 points below the untrained base.

How far to trust it: Believe that this post-training made Qwen3.5-4B and 9B better agents: the 4B improves on all ten benchmarks, and the HumanEval and VitaBench gains are three standard errors clear of sampling noise. Do not read it as evidence for the routing ideas or for recursive self-improvement: no experiment turns the routing curriculum, the on-policy distillation or the allocation step off, the loop ran once, and the one controlled experiment's "+6.26 over public data" is mostly the public-data run falling 4.99 points below the untrained model. The evidence, judged.

The idea in one sentence: a deployed routing harness already judges how hard each request is (it picks which model must serve it), so NeoHorse-1 uses those routing records to order and select agent post-training data for Qwen3.5-4B and 9B, gaining +5.93 and +3.44 macro points over ten benchmarks; but no experiment switches the routing curriculum, the distillation or the allocation step off, and the loop ran once.

Problem

§1 Introduction

Post-training data for agents is usually curated once, offline, against a fixed task distribution. The serving harness that actually meets the traffic is treated as downstream infrastructure with no say in what the next checkpoint learns. That wastes the one signal a deployed system has that a curated dataset never will: which requests the current model handled badly, and which model in the fleet had to take them.

The report frames this as the missing piece of recursive self-improvement (RSI): a system improving itself needs "a concrete mechanism through which an AI system observes its own capabilities and converts that evidence into the next round of learning" (Abstract). Its claim is that a deployed routing harness already contains one. An agent working inside a harness leaves a record of decisions, tool calls and outcomes, and a router that picks which model serves each turn also leaves, as a side effect, a judgement of how hard that turn was (§1). The thesis, stated as a loop: "what the system learns to do shapes what it learns from next".

A harness here is the execution layer that manages an agent's context, tools and interaction with its environment; agentic routing lets that layer choose a model per request and per interaction state (§1; routing by difficulty in general, routers and cascades, is on Gateways and routing). The system builds on the authors' earlier Agentic Routing paper, combining a heterogeneous model pool with several harnesses, including their open OpenSquilla, across real-world tasks.

Idea: let the router write the syllabus

Figure 2

Five components, and the router is the spine: the hero above names them in order (§3, §4). The router produces a labelled judgement of task difficulty as a side effect of serving; curation makes subscene-level labels, which is what makes partial-trajectory supervision possible; the curriculum takes its difficulty ordering from observed traffic rather than a heuristic; and allocation turns evaluation feedback into the next mixture, which closes the loop.

The five components as the paper describes them
  • Heterogeneous model pool with intelligent routing. Requests are routed across service tiers by predicted capability demand rather than by a static rule, so the router is continuously producing a labelled judgement about task difficulty as a side effect of serving.
  • Data curation pipeline. User interactions become training examples through structural validation, a six-dimensional semantic evaluation, and subscene-level labelling, which is finer-grained than per-conversation labelling and is what makes partial-trajectory supervision possible.
  • Three-stage curriculum. Supervised fine-tuning is ordered by those routing signals, so difficulty ordering comes from observed traffic rather than from a heuristic.
  • Routing-guided on-policy distillation. A fixed teacher supervises the student's own generated responses, with starting contexts introduced under the same staged progression.
  • Capability-guided allocation. Evaluation feedback is converted directly into training-mixture decisions, which closes the loop back to the pool.

Data from the routing harness

§3

Agent post-training data is not a pile of instruction and response pairs: it is execution trajectories linking user requests, model reasoning, tool actions, environment observations and outcomes. The corpus centres on trajectories produced by the deployment harness, with public instruction, reasoning, tool-use, code and preference data added to broaden coverage (§3). The primary corpus is "on the order of 105 to 106" harness trajectories; the exact counts of trajectories and tokens are "recorded in the training manifest" and not printed (§3.1). Public sources cited include ToolACE, UltraFeedback (binarized, cleaned) and the Aya dataset.

Three granularities

The corpus is organised at three linked levels (§3.1):

  • Trajectory: a whole interaction run by the harness, with user requests, responses, tool calls, observations, recovery attempts and terminal outcome.
  • User turn: from one user request to the next (or to termination); the training unit. Tool results and harness-injected messages do not start a new turn.
  • Subscene: adjacent user turns that share a local goal; the unit for semantic labelling. It can capture a goal being continued, modified, interrupted or resumed within one conversation.

Every record stays linked to its parent trajectory and subscene, so quality, semantic, routing and outcome signals can each be attached at their own level. Within a user-turn record, the current request with its interleaved reasoning, tool calls and observations is kept whole; earlier visible responses and tool interactions stay as context, but reasoning from earlier turns is dropped, a convention also used by DeepSeek-V3.2 and Qwen (§3.1, §4.1). Quality gates

§3.2

Before anything is judged, the corpus is deduplicated (exact and near-duplicate) and decontaminated: the same matching infrastructure screens every training candidate against the evaluation suites and removes overlaps from the training side (§3.2).

Structural validation is rule-based: it rebuilds each turn's events, checks that every tool call is closed by its result and that events run in causal order, and sorts each trajectory into one of three outcomes:

OutcomeWhat happens
Internally completegoes straight to semantic evaluation
Partially recoverableonly its causally closed sub-trajectories are used
Quarantinedambiguous event ownership, or no recoverable supervision target
Every structural check the paper lists

At turn level the pipeline rebuilds requests, responses, tool calls, tool observations and terminal events, then checks payload readability, supported message structure, that a request and a response exist, causal event order, and that every tool call is closed by its result (matched through identifiers and execution branches). It flags missing responses, orphan observations, duplicated or conflicting tool-call identifiers, unresolved internal calls and ambiguous terminal branches.

These properties are checked by rules because they can be read straight off the trajectory (§3.2).

Structural validity guarantees reliable serialisation and replay; it says nothing about correct tool choice or task success. That is the job of semantic evaluation, which builds a normalised event stream and scores six independent dimensions: goal attainment, instruction adherence, tool use, evidence consistency, error recovery and termination. Each dimension gets PASS, WARN, FAIL or NOT_EVALUATED, kept as a structured record rather than one heuristic score (§3.2).

How the six verdicts are reached and stored

High-certainty failures (a missing final response, an unresolved tool call, an unrecovered terminal error) are caught deterministically; anything needing task-level interpretation goes to a semantic judge restricted to evidence present in the trajectory, and every finding must point at the events it rests on. Long trajectories are judged in segments and re-aggregated per turn, so an early failure can be told apart from a later recovery (§3.2).

Evaluation coverage is stored separately. Missing evidence or an interrupted judge call never becomes a positive verdict, and the record (structural state, six verdicts, coverage) is what admission, review and quarantine policies are written over.

What the user wanted: Scene, Goal, Outcome

§3.3

Separately from execution quality, each subscene is characterised on three axes (§3.3, Figure 3):

Scene

What the user is doing and in what context. Closed taxonomies of task type and application domain (one primary value, up to two secondary), plus Use Context and Asking/Doing: does the request seek information or execution?

Goal

What the user expects and how success is judged: the objective decomposed into acceptance criteria, and cross-turn relations marking a goal as new, continued, modified, resumed or ambiguous.

Outcome

The verifiable result against the goal, so that "the task was actually satisfied" can be told apart from "the process ran to completion".

How annotation noise is controlled

To control annotation noise, each attribute keeps its derivation method and confidence, and structural facts set by the source or by rules cannot be overwritten by a semantic judge. Structural quality, the turn's reasoning policy, loss masks and routing records stay as separate metadata.

Routing signals: predicted, decided, served

§3.4

The harness router works per user turn and estimates capability demand from the current request, recent dialogue, earlier routing decisions and execution state. It assigns one of four service tiers (§3.4):

TierMeant for
C0bounded, low-risk requests
C1the general-purpose default
C2multi-step reasoning and execution
C3maximum capability or reliability (may combine several proposer models with an aggregator)

Policy controls may then adjust the assignment for risk, context pressure, an earlier failure or service limits.

Why the tiers are versioned

The tiers are relative demand under the routing policy, not fixed models: models, prices and inference settings change across deployments, so the tier semantics are versioned to keep old records interpretable (§3.4).

For every turn the corpus keeps three separate fields: the router's raw prediction, the policy-adjusted decision, and the tier actually served. Joined to the semantic attributes, that gives a prediction, action, outcome record per turn. The separation matters for training: the model actually served also reflects user overrides, service availability and deployment policy, so the curriculum uses a re-estimated demand, not the served tier, as its ordering signal (§2.2, §4.2). Outcome fields, in turn, become the deficiency signals that drive allocation.

Capability-guided allocation

§3.5

Quality dimensions, semantic attributes and routing tiers together form a stratification space. At each iteration the current checkpoint is evaluated on a stratified suite (kept disjoint from training by the decontamination screen), and results aggregated across attributes, quality dimensions, outcome states and routing tiers form a model-deficiency profile. The next training mixture shifts toward the regions where the model underperforms while keeping broad coverage: verified successes supply positive supervision, informative failures mark regions that need more or rebalanced data. Allocation changes the composition of the data, not the objective. Between iterations the harness keeps adding trajectories through the same pipeline, old and new data are reallocated together, and updated checkpoints returning to the harness reveal the next gaps (§3.5).

Described, not measured
Allocation is the step that makes this a loop, and the paper gives no number for it: no deficiency profile, no before and after mixture, and no run with allocation switched off. The authors say the results "reflect a single pass of the evaluation–selection–update loop" (§6).

Agentic post-training

§4

Supervision within a user turn

Each user turn is serialised with the Qwen3.5 chat template and tool-call format, keeping the recorded system instructions and harness context so every assistant target stays paired with the conditions it was produced under (§4.1). The pattern being learned is interleaved thinking: reason, call a tool, read the result, reason again. A turn can hold several assistant responses between tool results, and all retained assistant spans of the current turn are supervised in one sequence. History and every non-assistant span (system instructions, tool specifications, harness context, user messages, tool results) get no loss; causal attention means each response sees earlier actions and results but not later ones. (The loss mask in general is on Alignment: SFT, RLHF, DPO, RLVR; masks on agent trajectories on Harnesses for training.)

ℒSFT(θ;ℬ)=−∑i∈ℬ∑t=2Timi,tlogpθ(xi,t∣xi,<t)∑i∈ℬ∑t=2Timi,t

mi,t = 1 on the retained assistant spans of the current turn (reasoning when present, serialised tool calls and their arguments, visible responses, end-of-response tokens), 0 everywhere else including padding (Eq. 1). Every supervised token weighs the same, normalised by the count of supervised tokens in the batch, not by sequence length or number of turns, so a long multi-tool turn counts in proportion to how much the assistant wrote.

Routing-guided curriculum

§4.2

Agent interactions range from routine replies to complex planning and tool coordination, and the routing estimate of that demand orders the SFT examples into a curriculum. For each example the router gives an assigned tier ki and a normalised score vector πi over C0 to C3; the curriculum key is either (Eq. 2):

si=ki(hard)orsi=∑k=03kπi,k(soft)

The estimate is re-made from the request and the history available before the first supervised response, and assigned to the whole example: a turn-level ordering proxy, not a difficulty label for each action. It changes when an example is seen, never its targets, and it is not used to reweight the loss.

The soft score separates examples that share a tier. Move the router's four scores for one example in the card beside this (they are renormalised to sum to 1).

Training runs in three stages of roughly one third of the examples each, bringing in higher-scored examples stage by stage while reserving some lower-scored examples for later stages, so the end of training is not made only of high-demand interactions. Every example is used once per pass, the objective stays Eq. 1 throughout, and the optimizer and learning-rate schedule are not reset between stages (§4.2, Figure 5). The paper does not say how many low-scored examples are held back, or how. The Schedule the curriculum tab builds the three stages from a pool you can change, against plain shuffled SFT.

Routing-guided on-policy distillation

§4.3

On-policy distillation (OPD, Agarwal et al. 2024; why it beats training on recorded text, and forward against reverse KL, are on Distillation and small language models): the student generates, and a teacher supplies a next-token distribution at every position of the student's response (§4.3). What this paper adds: the starting contexts are recorded states just before assistant responses, scored with Eq. 2 and introduced over the same three stages (ρj is the stage-j distribution over context batches), lower-scored contexts again partly reserved for later. At stage j a rollout checkpoint generates one response per context; a fixed teacher (not named in the report) scores each position given the context and the student's preceding tokens, both models rendering the same messages with their own templates and token IDs aligned. The rollout checkpoint is refreshed as training proceeds, so later contexts are supervised on more recent student behaviour.

ℒOPD=1∑rwr∑r∈ℛwrLr∑t=1LrDKL(P~θ,r,t‖Q~r,t)

Eq. 3. P̃ and Q̃ are the student's and teacher's distributions coarsened to K + 1 bins: the rollout student's top-K candidate tokens at that position, plus one bin holding all remaining probability (both models use the same candidates and their full-vocabulary probabilities). The KL runs from student to teacher, a reverse KL, which pushes the student off tokens the teacher thinks unlikely. Each response contributes its average per-token divergence (Lr is its retained length, wr a fixed weight, 1 unweighted).

Gradients and the stage objective (Eq. 4)

Prompt and padding get no loss; gradients flow through the current student's probabilities with the generated tokens, candidate IDs and teacher scores held fixed. Stage j's objective is the expectation of this over contexts from ρj and responses from the rollout student (Eq. 4).

Lumping every token outside the student's top K into one bin makes the loss cheap to store. Compared with the reverse KL over the full vocabulary, can the coarsened KL be larger, is it always smaller or equal, or can it go either way?

Merging outcomes can only hide differences between two distributions, never create them (the data-processing inequality), so the coarsened KL is a lower bound on the full one. Results: ten benchmarks, two sizes

§5

The suite (§5) has ten benchmarks in three groups: four end-to-end agentic (QwenClawBench, WorkBuddy Bench, PinchBench, VitaBench), two tool use and interaction (BFCL v4, τ²-Bench), and coding and instruction following (HumanEval, LiveCodeBench v6, IFEval, IFBench). Only text interfaces are evaluated.

What each benchmark tests

The suite (§5) has ten benchmarks in three groups. What the paper reads from this (§5): at 4B, NeoHorse-1 beats its base on every benchmark, most on harness-based agent tasks and coding; at 9B it improves "on most", again concentrated on harness tasks, tool interaction and selected coding, while instruction following "remains largely stable, with one metric showing a minor decrease". The post-trained 4B closes 89% of the macro-average gap to the base 9B. On how many of the ten benchmarks does it actually beat the base 9B?

That is still the economically interesting claim: post-training buys a large fraction of a size step, since a 4B model is cheaper to serve than a 9B one. What the paper cannot say is how much of that fraction the routing-derived curriculum buys, as opposed to the data, the distillation or simply more training (see How much to believe).

How big is the noise?

The paper reports no error bars. Five of the benchmarks give their size away: every printed score is a whole number of items out of a fixed count (HumanEval 164 problems, LiveCodeBench v6 175, IFBench 300, IFEval 541, VitaBench 400), checked across all twelve models in the tables tab. That turns gains into item counts and gives a binomial standard error for each (Eval statistics has the method; treating the two models' runs as independent, which overstates the error a little if they fail on the same items, and ignoring the extra noise of sampling at temperature 1.0):

z is the gain divided by its standard error; |z| above about 2 is unlikely to be noise. At 9B, LiveCodeBench and IFBench are identical to the item (114 of 175 and 199 of 300) before and after training, which the paper does not comment on.

What the traces show

§5.1

To explain the scores the authors read representative trajectories. Three in the main text (§5.1):

Training closes the loop (4B)

QwenClawBench, project scheduling. Qwen3.5-4B finds the files but never opens a manager's email with an updated dependency, plans from stale information, produces an invalid schedule and writes it to the wrong place. NeoHorse-1-4B reads the email, recognises the new dependency, recomputes and verifies the schedule and saves it to the required path.

Scale under feedback (4B vs 9B)

WorkBuddy, code repair. NeoHorse-1-4B stops after one implementation attempt with no test and repair loop, leaving an error in thread-execution semantics. NeoHorse-1-9B runs a full edit, test, inspect, repair cycle until the verifier passes, treating test outcomes as inputs to its next decision.

Changing strategy (4B vs 9B)

PinchBench, data analysis without pandas. The 4B keeps trying to install the dependency, parse the CSV by hand and patch scripts, adding errors until no report comes out. The 9B abandons pandas for Python's standard csv and math libraries and finishes; against the 4B run it uses fewer model requests, execution time and tokens.

The authors' reading: the larger model's advantage is not more actions or wider search, but recognising unproductive trajectories, revising strategy from environmental feedback and spending a limited interaction budget on actions that move the task forward.

Complete app/audit_leakage.py: allow a small tolerance, record genuinely late features, keep exporting clean samples; the README sets five minutes and fixes the output schema. Qwen3.5-9B never reads the README, hard-codes a 2-second tolerance, rejects sample s1 (cutoff 10:00, feature at 10:04, inside the window), renames the output file, emits features for feature_count and drops the summary structure. NeoHorse-1-9B reads the README first, uses 5 minutes, keeps the CLI, runs it and checks both outputs: s1 and s3 kept in order, s2's 10:06 and s4's next-day features rejected (Table 5).

C: Gomoku in HTML

"Use HTML to create a simple Gomoku game", replayed with the same 26 clicks. Qwen3.5-9B's handler reads nonexistent cell.clientX/clientY properties, so every click gives an invalid index: the board stays empty and the turn indicator stays on Black. NeoHorse-1-9B shows 13 black and 13 white stones matching the input after every move, turn back to Black, gameOver=false, no runtime exceptions (Table 6, Figure 8).

These are chosen examples, one run each, and the authors' own interpretation column is careful (Case A: "improved grounding does not establish complete output consistency"). They illustrate the kind of difference, not its frequency.

The data experiments

§5.2

Two controlled experiments on the 4B, both starting from Qwen3.5-4B and scored on the five benchmarks every checkpoint has (LiveCodeBench, HumanEval, IFBench, BFCL v4, τ²-Bench) (§5.2).

Source of the trajectories. Routing-harness data against Toucan, a public synthetic tool-agent dataset. Both are scored by the same offline routing labeller and trained with the same curriculum, optimizer, seed, packing and evaluation, at "closely matched" budgets (the sources differ in sequence composition). The harness run wins on all five, by +6.26 on average: HumanEval +8.54, τ²-Bench +11.31, the rest +2.43 to +5.00 (Table 3). The authors conclude that routing-mediated interactions "provide stronger and more transferable agentic supervision than public synthetic trajectories".

Amount of data. From one quality-ranked pool, strictly nested subsets (each contains the previous), with initialisation, optimisation, packing and passes fixed. The five-benchmark average rises "steadily" from 69.31 for the base to 71.45 at the largest size, measured in unique supervised tokens on a log axis (Figure 7).

Table 3 never prints the untrained Qwen3.5-4B on those five benchmarks. Where does it sit?

Read together, the two experiments say less than the text claims. The base is 69.31 (Figure 7 prints it; it is also the mean of the base's five Table 1 scores). So the Toucan run made the model 4.99 points worse than not training at all, and the routing-harness run made it 1.26 better; the +6.26 is mostly the public data hurting. Both runs also score below the base on BFCL (57.20 and 54.77 against 61.02). Decoding Figure 7's vector markers shows Table 3's harness run is Figure 7's second point (70.57, at about 3.4 million unique supervised tokens), and that the whole scaling sweep spans 1.7 to 10.1 million tokens in six equal steps. The released NeoHorse-1-4B scores 74.39 on the same five: of its gain over the base is not reached by any controlled run, so it comes from whatever the full recipe adds (more data, on-policy distillation, other stages) and the paper does not break that down.

How much of this to believe

What holds up.

  • The models got better, and not by noise. At 4B every one of the ten benchmarks went up; if gains and losses were coin flips that would happen with probability 2 × 0.510 ≈ 0.002. The two largest item-level gains are well clear of sampling error: HumanEval +16 of 164 problems (z ≈ 3.3) and VitaBench +42 of 400 tasks (z ≈ 3.4; one run). At 9B VitaBench is +44 (z ≈ 3.2) and HumanEval +9 (z ≈ 2.4) (error bars above).
  • The comparison with the base is fair in setup. Each model the authors ran used the same benchmark harness, tools, context limits and budgets, its own chat template and recommended sampling; three of the long agentic benchmarks were averaged over three runs; the training corpus was screened against the evaluation items (§3.2, §5).
  • The numbers are internally consistent. All twelve printed averages are the plain mean of their ten columns, Figure 1's 72 bar labels match the tables, and Figure 7's baseline is exactly the base model's five-benchmark mean (45 checks in the tables tab).
  • The weights are public under Apache 2.0, so anyone can rerun the ten benchmarks.

What does not.

  • Nothing isolates the paper's own ideas. There is no run with the curriculum shuffled instead of routing-ordered, none comparing the hard and soft scores of Eq. 2 (the report never says which one trained the released models), none with SFT alone against SFT plus on-policy distillation, and none with allocation off. Table 3 holds the curriculum fixed and changes the data. So the headline gains show that this post-training recipe on this company's traffic helps a 4B and a 9B model; they do not show that routing signals are a better curriculum than any other ordering.
  • The one controlled comparison is framed generously. The "+6.26 over public data" is the gap between two trained runs; against the untrained base the public-data run is −4.99 and the harness run +1.26 (Table 3, Figure 7). A public set that makes the model worse than no training is a weak baseline: Toucan is synthetic MCP data that was not built for this serialisation, and the budgets are "closely matched", not equal.
  • The controlled runs are much smaller than the release. The data-scaling sweep stops at about 10 million unique supervised tokens (decoded from Figure 7) and reaches 71.45; the released 4B scores 74.39 on the same five benchmarks. 58% of its gain over the base is outside every controlled experiment.
  • Home-harness advantage. QwenClawBench and PinchBench are run inside OpenSquilla, the authors' own harness. The paper names OpenSquilla among the harnesses whose traffic became training data (§1), so NeoHorse-1 was trained on that harness's prompts, tools and message format; its base and the other baselines were not. Decontamination removes overlapping items, not familiarity with the harness. That does not make the gains fake, but some of the +6 points on those two may be format fit rather than general agent skill.
  • Single runs where noise is largest. PinchBench and VitaBench are one run each at temperature 1.0, and no spread is given for the three-run benchmarks. VitaBench uses DeepSeek-V4-Flash as user simulator and judge because the recommended models are gone, so its scores are not comparable with other published VitaBench numbers.
  • No gain on instruction following or LiveCodeBench at 9B. LiveCodeBench and IFBench are identical to the item before and after training (114 of 175, 199 of 300) and IFEval drops 2 prompts; the 9B's 3.44-point macro gain comes from the agentic six (+4.88 on average) and HumanEval.
  • Not reproducible from the report. Corpus size is given only as 105 to 106 trajectories; the teacher, the models in the pool, the reserve fraction, learning rates, epochs and compute are not stated, and the data is private user traffic.
  • The loop is a design. Evaluation, selection and update ran once, so nothing here measures self-improvement across iterations. The authors say this plainly: the results are "an initial attempt at recursive self-improvement rather than a definitive demonstration", and whether gains "can continue to accumulate across successive iterations remains to be tested" (§6). That candour counts in their favour.
  • Small inconsistency. The arXiv listing's abstract says "eleven benchmarks"; the HTML abstract, §6, the tables and the GitHub README say ten.

Verdict
A credible engineering report on a useful pair of small agent models, with released weights and gains that survive a noise check. As evidence for routing-guided curricula, on-policy distillation or harness-mediated self-improvement it is not yet anything: those parts are described, not tested, and the only controlled experiment is easy to over-read.

What it takes to use this

  • The models: Text only (the Qwen3.5 vision weights are removed), BF16 safetensors plus GGUF quantisations, 262,144-token context natively; the README gives SGLang 0.5.17 and vLLM recipes with the Qwen3 reasoning parser (GitHub, model card).
  • Which one: in its track the 4B has the best average, but not everywhere: Nanbeige-4.2-3B is ahead on BFCL, HumanEval and (by its own report) LiveCodeBench, Spark-X2.5-4B on IFBench and IFEval, Agents-A1-4B on VitaBench. Its clearest leads are PinchBench, WorkBuddy Bench, QwenClawBench and τ²-Bench. The 9B adds most on harness tasks and little on instruction following.
  • The recipe: nothing of it is released: no training code, curation pipeline, judge prompts, curriculum scores or data. What is open is the harness and a cold-start router: OpenSquilla (Apache 2.0) with the LightGBM ranker described in Agentic Routing (§3.2 there). To copy the idea you need your own production traffic through a routing harness, a structural validator, a judge model for the six dimensions, a teacher for on-policy distillation and an evaluation suite stratified by the same attributes.
  • When it pays: if you already serve agents through a harness with a model pool, you are sitting on the data this recipe uses, and the router's tier scores cost nothing extra to log. Keep the three routing fields separate (predicted, decided, served), as the paper does. If you have no traffic, the paper's own Table 3 suggests a public synthetic substitute can make a small model worse, not better.

Why it matters beyond the paper

This is the first published instance of the loop the harness-scaling line in this knowledge base has been circling since 2026-08-31 (see Topic: agentic-harnesses): harness and model improving each other, with the harness supplying the training signal rather than merely consuming the weights. Prime Agent found that rich harnesses offer affordances models are not trained to use; JIT-Agent trained a model to emit harnesses but in a language far poorer than a production one; Terminal-Universe supplied environments and Repo-To-Skill supplied skills. NeoHorse-1 runs one pass of the loop (the old summary said it "runs the loop"), at 4B and 9B rather than at frontier scale, using routing decisions as the curriculum signal. The honest reading is that this is a demonstration of the mechanism and not evidence that it scales, or even, yet, that the routing signal is what helped.

Since the paper: the same week's data-efficiency decomposition (read 3 October 2026)

Read alongside the Dwarkesh decomposition added that week (filed in Topic: llm-training-and-post-training and the 2026-09-14 tech news issue), which finds that data improvements contributed 3.24x more compute-efficiency gain than model improvements between 2019 and 2025, and that small models gain most from data quality: NeoHorse-1 is a mechanism for producing exactly that kind of gain at exactly that scale. This page's own data does not separate data quality from the rest of the recipe, though.

Schedule the curriculum

The paper's curriculum (§4.2, Figure 5) in one picture: a pool of 120 user-turn examples, each with router scores over C0 to C3, is split into three stages of 40. Run it in routing order (hard or soft score, Eq. 2) or the way plain SFT does it, shuffled, and watch the score the model sees over training. Change the traffic, how sure the router is, and how many easy examples are held back for later stages.

The steps, for the ordering chosen in the card

  1. Score the pool. Each example gets the router's four tier scores π, re-estimated from the request and history before the first supervised response. Soft score: the score-weighted mean tier (Eq. 2).
  2. Sort by score. Line the examples up by soft score, lowest left. The soft score is continuous, so examples assigned the same tier still get a definite order.
  3. Hold some easy examples back. Pick a share of the lowest-scored third (outlined) and set it aside for stages 2 and 3, so the end of training is not made only of high-demand turns (§4.2).
  4. Stage 1. The lowest-scored remaining examples fill the first third.
  5. Stage 2. The middle of the ranking, plus half of the held-back easy examples.
  6. Stage 3. The highest-scored examples plus the other half of the held-back ones. Every example is used exactly once per pass.
  7. Train. Stages run in order with one optimizer and one learning-rate schedule (no reset); within a stage the order is shuffled here. The line is the mean soft score of the last 10 examples seen; dashed is the same pool shuffled.
  1. Score the pool. Same router scores; the hard score is just the assigned tier, 0 to 3 (Eq. 2).
  2. Sort by tier. Four flat steps: within a tier the order is arbitrary, so a stage boundary can cut through a tier at random.
  3. Hold some easy examples back. The same share of the lowest third is set aside for later stages.
  4. Stage 1. Lowest tiers first.
  5. Stage 2. Middle tiers plus half the held-back examples.
  6. Stage 3. Highest tiers plus the rest of the held-back ones.
  7. Train. The same staged order, by tier. Compare the line with the soft version: fewer distinct levels, same overall rise.
  1. Score the pool. The same pool, with the same router scores, which plain SFT ignores.
  2. Shuffle. Plain SFT orders examples at random.
  3. Split into thirds. The same three thirds of training, for comparison: each third is a random sample, so every stage looks like the whole pool.
  4. Train. The model sees the same mix of demand from the first step to the last. This is the baseline the paper does not run against.

What is the paper's and what is not. Eq. 2's two scores, three roughly equal stages, higher scores later, some lower-scored examples reserved for later stages, each example used once, no optimizer reset: the paper's. The pool, its score distributions, the router-confidence knob and the reserve rule (a random share of the lowest-scored third, split evenly between stages 2 and 3) are illustrative: the paper gives none of them. Each dot is one example, coloured by its nearest tier (C0 faint to C3 strong).

What this cannot show
Whether the ordering helps. The paper never trains the same data shuffled, so there is no number for "routing curriculum against no curriculum" (see How much to believe). The picture shows what the method does to the order of the data, which is all the paper specifies.

The distillation loss, coarsened

Routing-guided OPD (§4.3) keeps, at every position of the student's own response, only the student's top-K tokens and one bin for the rest, and minimises the reverse KL from student to teacher over those K + 1 bins (Eq. 3).
