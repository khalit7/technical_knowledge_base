Simulate a long prompt

Ratio

The paper's central systems claim, run on its own numbers: the same prompt through an LCLM, through KV cache compression and through the uncompressed decoder. KV methods compress after the decoder's full prefill; an LCLM shortens the sequence before it ({{§6.2|ax:S6.SS2}}). Move the context length from 4K to 1M and the ratio between 4x and 16x; the steps below follow the pipeline chosen above the figure, and the counters under it give the decoder's work, the cache and the measured time and memory.

LCLM, step by step

  1. The prompt arrives. T tokens of context. Each cell is T/64 tokens.
  2. Cut into encoder windows of 1,024. Windows are independent, so the encoder can run them in parallel batches: 128 windows (131,072 tokens) per forward pass of the 0.6B encoder.
  3. Encode and mean-pool every N tokens. Each block of N tokens becomes one latent; the window gives every token up to 1,024 tokens of context first.
  4. Adapter: 1,024 to 2,560 dimensions. An MLP maps each latent into the decoder's embedding space.
  5. Decoder prefill over T/N latents. The 4B decoder now prefills only T/N positions. Its KV cache is genuinely T/N entries long, in the standard layout, so paged attention and vLLM can use it.
  6. First token. Time to first token and peak memory are the paper's measurements (Figure 4).
  1. The prompt arrives. The same T tokens. The whole context has to fit in the decoder's window (262,144 positions for this decoder).
  2. Full prefill through the 4B decoder. Every one of the T tokens goes through all 36 layers and writes keys and values: the expensive part happens first, whatever the target ratio.
  3. Score every cache entry. Heuristics (attention to a query, expected attention, or a reconstruction pass in KVzip) decide what to keep. KVzip's scoring pass is two to three times the input length.
  4. Evict to 1/N, unevenly across heads and layers. Different heads keep different positions, so the sequence dimension cannot shrink: evicted entries are masked, not freed, in a paged engine. Pale cells are masked but still allocated.
  5. First token. Time is FastKVzip's; across all KV methods it is shown as a range. All of them stop at 256K.
  1. The prompt arrives. The same T tokens, no compression.
  2. Full prefill through the 4B decoder. All T tokens through all 36 layers.
  3. KV cache of T entries. 147,456 bytes per token in bf16 for this decoder.
  4. First token. The yardstick the paper's speed-up figures leave out: KV compression is never faster than this.

KV cache sizes are computed from the released configurations (bf16, 147,456 bytes per decoder position). Times and peak memory are the paper's measurements, read from the vector paths of {{Figure 4|ax:S5.F4}}: one sample, mean of 30 runs after 20 warm-ups on one H200 (141 GB), Hugging Face Transformers implementations, encoder batch 128 windows ({{§6|ax:S6}}). The KV pipeline's scoring step is drawn generically; its time is FastKVzip's, the fastest KVzip variant, with the range across all KV methods beside it. The same comparison at one length and ratio (64K, 4x), in 3D, is the figure at the top of {{The paper|tab:t-read}}.

Why no toy model on this page

A trained toy LCLM (encoder, mean pooling, MLP adapter, decoder, as §3 and Appendix D define them) was built to test the architecture-search claims in the browser. In eight designs on CPU (from scratch as in §5, then with a pre-trained toy decoder as in §4.2), the 2-layer toy never learned key-value retrieval well enough to make its ablations meaningful, even when the decoder read the raw context; its logs are kept in src/model/pilot/. Rather than ship a model at chance, this page tests the paper's claims against its own tables and figures (the {{Tables tab|tab:t-tables}}).
