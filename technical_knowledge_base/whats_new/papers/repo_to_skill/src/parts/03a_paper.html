The idea in one sentence: one agent, DisCo, distils a repository, a set of papers or a task into a checked skill graph (an entry SKILL.md that routes to component skills, opened only as needed); its released 1,000-repository library (5,353 skills) is real and counts out exactly, but the four benchmark gains, led by MLE-bench's 31.1% to 72.9% of competitions medalled, come from skills built for each benchmark, not from that library.

You need: what an agent skill is and how a harness loads it progressively ({{Claude Code, skills|n:3c65c17b0d0d81db9c7fc54987c1ab65}}), and why skills help when they do ({{Demystifying Agent Skills|n:3c65c17b0d0d81249a3cf5fda4de5d92}}). New terms: operational knowledge (the know-how that makes a published method run); skill graph (the skills distilled from one source, an entry skill linking to component skills); task-agnostic and task-oriented distillation (anchored on a source, or on a problem); creator and researcher mode (DisCo building skills, or using them); router (the entry skill that narrows the library from area to family to graph).

Problem: knowing a method is not making it run

[[S2.SS2|§1, §2.2]]

Agents now carry out parts of machine-learning research end to end ({{§1|ax:S1}}). The paper describes such an agent as two modules ({{Eq. 2|ax:S2.E2}}): a model Mθ that understands, reasons, plans and executes, and a harness H that supplies orchestration, memory, verification and refinement.

The missing piece, in the authors' words, is operational knowledge: "the know-how that separates knowing a method from making it work" ({{abstract|ax:abstract1}}, {{§2.2|ax:S2.SS2}}). In ML research it covers which method suits the problem, which package implements it, how the package wants its data laid out, which configurations are sensible, and which pitfalls invalidate an otherwise plausible run. The model's prior is broad but fixed; the harness controls procedure but supplies no domain content.

Without it an agent loses budget twice ({{§1|ax:S1}}): within a task it infers package behaviour by trial and error, and a misconfigured run can burn much of the budget before any meaningful measurement; across tasks, what it discovered is not kept.

The knowledge exists. It sits in papers and repositories (source code, documentation, examples, tests, scripts and configuration files are the evidence the paper's pipeline reads, {{§4.1|ax:S4.SS1}}), but it is written for human readers and is far too large to load during a task. Today an expert turns it into agent skills by hand, so the cost "scales with expert labor and with the domain, stack, and release" ({{§2.2|ax:S2.SS2}}).

The question: can operational knowledge be produced automatically and at scale from those declarative sources, and does handing it to an unchanged agent improve its research?

Idea: a third layer, made of skills, distilled from sources

[[S3.SS1|§2.2, §3.1, Eq. 4 to 7]]

The paper adds a third component ({{Eq. 4|ax:S2.E4}}): Ares = (Mθ, H, 𝒦), with 𝒦 the operational knowledge given as explicit operating context, so actions come from πθ(a | τ, ht, H, 𝒦). "The harness specializes how the agent explores, while 𝒦 specializes what the agent knows to consider." 𝒦 has two constituents: capability (methods, code, models and APIs as invocable units) and usage policy (when, why and how to use each); either alone is tools without criteria or advice with nothing to run.

𝒦 is a set of skills in the open Agent Skills format ({{Eq. 5 and 6|ax:S3.E6}}; {{Anthropic, 2025|https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills}}); how a harness keeps only each skill's name and description in context and loads the rest on demand is on the {{Claude Code page|n:3c65c17b0d0d81db9c7fc54987c1ab65}}. The paper names the three layers by role: SKILL.md is the knowledge interface, the only layer read up front (goals, key concepts, tool use, worked examples, known failure modes, routes to deeper material or sibling skills); references/ is the knowledge substrate (API docs, algorithmic detail, configurations, loaded only when needed); scripts/ is the execution interface (wrappers with defined inputs and outputs the agent calls instead of reimplementing).

One source usually holds more than one skill should, so the skills from one source form a skill graph ({{Eq. 7|ax:S3.E7}}): an entry skill states the source's scope and links to component skills; each link is a routing, dependency or composition relation. The agent reads the entry, follows only the links its problem needs, and leaves the rest unopened.
