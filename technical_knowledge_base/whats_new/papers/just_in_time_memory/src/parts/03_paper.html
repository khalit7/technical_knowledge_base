Problem

[[S1|§1 Introduction]]

An agent solving tasks one after another should learn from its own past. Agentic memory does that, and almost every system curates it at write time: when a task ends, its trajectory is distilled into a fixed artifact (a verbal reflection as in Reflexion, an insight, a workflow, an executable skill, a reasoning strategy as in ReasoningBank) that later tasks retrieve by similarity ({{§1|ax:S1}}, {{§2|ax:S2}}; memory designs in general: {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}).

Curating then, the paper argues, has two costs that come from one root: the decision is made without knowing what it will be used for ({{§1|ax:S1}}).

  1. Information loss is premature and irreversible. Whatever the distillation discarded is unavailable to every later task that needed it.
  2. One fixed artifact must serve many different future queries. The paper's example: the same household trajectory may teach one task a state change (heating or cooling an object) and another a placement strategy. A trajectory holds many possible lessons, and which one matters depends on a task nobody has seen yet.

Learning a write-time curator adds credit assignment: a storage decision is only graded when some later task retrieves the artifact, so the reward is delayed and badly attributed. SkillOS, the closest prior work, trains a skill curator with RL and has to group related tasks into streams to manufacture that signal ({{§1|ax:S1}}, {{§2|ax:S2}}).

One past trajectory, two later tasks.

Idea

[[S1.F1|§1, Figure 1]]

Keep the raw trajectories and curate at read time, just in time, once the task to be solved is known ({{§1|ax:S1}}).

The bank becomes a passive store of complete trajectories. When a task arrives, a retriever picks past trajectories and a memory curator reads them together with the new task and writes a compact, task-specific payload, so one stored trajectory can yield a different payload for every task that retrieves it: memory reconstructed, not replayed ({{§1|ax:S1}}).

It also changes learning: the payload is consumed by the task it was written for, so that task's success grades it at once, with zero delay and no task grouping ({{§1|ax:S1}}, {{§3|ax:S3}}). The animation runs the paper's own example ({{Figure 3|ax:S4.F3}}) through both designs (switch with the buttons above it); the trajectory's steps and the write-time artifact are illustrative, the artifact following the paper's ReasoningBank-style distillation prompt ({{Appendix A|ax:A1}}).

  1. A past task is solved. The agent solves put a cool egg in microwave, the past task in the paper's Figure 3. Its trajectory, drawn as seven actions (illustrative), mixes three kinds of know-how: finding the object (blue), changing its state (teal), placing it (gold).
  2. Store it raw. JitMem stores the complete trajectory. Nothing is decided about what it is for, and nothing is discarded. The only gate: the executor, acting as judge, must think the task succeeded.
  3. Task A arrives: put a hot potato in fridge. The retriever returns the egg trajectory among its top 3, as in the paper's figure.
  4. The curator writes payload A. Reading task A and the raw trace together, the curator foregrounds the state change: Heat the potato: Use a microwave or stove to make it hot. Move to the fridge: Go to the fridge, open it, and place the hot potato inside to cool it down. (payload text from Figure 3).
  5. Task B arrives: put a newspaper in sofa. The same egg trajectory is retrieved again, for a task with no state change at all.
  6. The curator writes payload B. From the same trace it now foregrounds placement: Move to the sofa: Navigate to the sofa and use the "move" action to place the newspaper on it. Verify placement: Confirm the newspaper is on the sofa. If not, repeat the process. (Figure 3).
  7. The reward arrives at once. Each payload is used once, by the task it was written for, so that task's success grades it immediately: the gap between the curator's action and its reward is zero. That is what lets GRPO train the curator from task success alone.
  1. A past task is solved. The agent solves put a cool egg in microwave, the past task in the paper's Figure 3; seven actions (illustrative) of three kinds: finding the object (blue), changing its state (teal), placing it (gold).
  2. Distil it now. A write-time memory distils the trajectory at once, before any later task is known. Following the paper's ReasoningBank-style prompt (at most 3 items, generalisable, no object names or locations), say: 1. Locate the object on countertops and tables first. 2. Change its temperature with the matching appliance. 3. Go to the target, open it if closed, and put the object in. (illustrative). The raw trajectory is dropped.
  3. Task A arrives: put a hot potato in fridge. The retriever returns the stored artifact: the same three items.
  4. Task A gets the fixed artifact. Item 2 happens to fit (heat the potato), but nothing is specific to this task: that the potato must be heated first and only then go into the fridge is left to the executor.
  5. Task B arrives: put a newspaper in sofa. The same artifact is retrieved again.
  6. Task B gets the same artifact. Placement is one generic line among three, and the temperature advice is noise for this task. Whatever the distillation dropped (where the egg was, which receptacles had to be opened) is gone for both tasks.
  7. The reward comes later, and shared. Was the distillation at step 2 a good one? Only tasks A and B can say, after the fact, and their success mixes the artifact's quality with everything else the executor did. A learned write-time curator has to learn from that signal; in the paper's real test stream a stored trajectory is first used about 20 tasks later, and a fifth to a quarter are never used (the figure at the top and the {{replay tab|tab:t-run}}).

Note that JitMem never hands raw trajectories to the executor: it still distils, only later and with the task in view ({{Connections|tab:t-read:s-conn}}).
