The idea in one sentence: point an automated research loop at the harness instead of the model, select only changes that cut cost while the score stays within tolerance, and it keeps four small mechanisms that together send 44.7 to 49.0% fewer tokens (almost all of them re-read cache) and cost about a third less than the Pi harness on EdgeBench, at 93.7 to 94.3% of its score, in single runs.

Problem: long-running agents re-send their own history

[[S1|§1 Introduction]]

A coding agent that works for hours is a loop: the model reads the whole conversation so far, chooses a tool call, the harness runs it and appends the result, and the model reads everything again. The harness is the program around the model that decides what the model sees and which actions it can take (Codex, Claude Code, OpenCode and Pi are harnesses; the loop itself is taught on {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}). Because every request re-sends the accumulated context, cost grows with the length of the trajectory, and the paper calls task-level token efficiency "a first-order systems concern" ({{§1|ax:S1}}).

Most efficiency work lowers the price of a token: faster attention kernels and serving, quantisation, cheaper models. This paper lowers the number of tokens instead, by changing only the harness: no training, no new model ({{§1|ax:S1}}). The difficulty it names is that harness choices are coupled. Tool use, context management, verification, delegation and termination interact, so "a change that is locally beneficial may cause downstream failures or shift token costs to later stages", and finding such changes by hand means reading long traces ({{§1|ax:S1}}).

Automated harness search already exists. Meta-Harness searches over harness programs, Recursive Harness Self-Improvement refines prompt-level specifications per task, and a held-out study found that evolved harnesses overfit the tasks used in search and give "only marginal gains on unseen tasks" ({{§1|ax:S1}}, citing {{Wang et al. 2026|https://arxiv.org/abs/2607.12227}}). (The wider family of self-improving harness search is compared on {{Harnesses for training and evaluation|n:3f15c17b0d0d815ea579d6c80065aa36}}.) SoL-Pi's question is narrower and testable: can an automated search find harness changes that save tokens and transfer to tasks and models it never saw?

Idea: recursive self-improvement, one layer up, aimed at cost

[[S2.SS1|§2.1]]

Recursive self-improvement (RSI) usually means a model improving the next model. SoL-Pi applies the loop to the harness: a research AI reads execution traces of an agent running the base harness (Pi), proposes changes, implements them and tests them in prepared environments, and only changes that survive selection are kept ({{Figure 1(a)|ax:S0.F1}}). The weights never change.

The target is constrained efficiency. Before the search starts, the capability metrics, their tolerances and the efficiency metrics are fixed and kept out of the optimising agent's reach. A candidate passes two gates in order: every capability metric stays within its tolerance, then at least one efficiency metric improves; among those that pass, the nondominated ones are kept ({{§2.1|ax:S2.SS1}}). An efficiency change has a cheap automatic check (did it cost less and still pass?), which a capability change does not; that is why the loop could run largely unattended.

Three principles organise it ({{§1|ax:S1}}): breadth and depth (many hypotheses, then repeated implementation and hardening of the promising ones), independent validation (held-out evidence only after a candidate is frozen), and scalable orchestration (isolated, disposable lineages so one failure does not spread). The claim to test is generalisation: a mechanism found this way should transfer because it targets how agents burn tokens, not anything about a particular task.

The search: 152 directions, 535 environments, four survivors

[[S2.SS2|§2.2]]

Outer stage, breadth. The search started from 152 proposed directions in six families: context, progress, tools, delegation, prompt and policy, and improvement and evaluation ({{§2.2|ax:S2.SS2}}). Fig. 1 counts them by family; the {{blog's proposal pool|https://nvlabs.github.io/SoL-Pi/}} lists every title. Before any rollout budget is spent, Oracle Analysis reads existing trajectories to estimate avoidable work, and each selected direction must name a concrete source of overhead. A family records where an idea started, not where it ends up: ObservationPack began as two context ideas (C23 and C24 in the blog) and became a change at the observation boundary.

Inner stage, depth. Each selected direction runs its own lineage of Karpathy's {{autoresearch loop|https://github.com/karpathy/autoresearch/blob/master/program.md}} (propose, implement, run a fixed experiment, inspect, keep or discard), extended with a {{Ralph Loop|https://github.com/anthropics/claude-code/blob/main/plugins/ralph-wiggum/commands/ralph-loop.md}} for implementation (iterate until an explicit completion criterion passes, then an independent reviewer checks it; a failed review means revision) and map-reduce analysis (independent analysers read one trajectory each for repeated actions, context growth, large observations or sparse diagnostic signals; a reducer merges them) ({{§2.2|ax:S2.SS2}}).

How the lineages were orchestrated (and the two designs that failed first)

Orchestration. Each lineage is a disposable copy of one shared skill template: copy, set parameters, run to completion, keep the candidate and its evidence, discard the modified orchestration code ({{§2.2|ax:S2.SS2}}). The blog says this was the third design: a YAML-compiled workflow kept stopping for human repair, and a long-lived coordinator written by a lead agent grew until launching a new experiment "could require more than ten hours of changes to it" ({{blog, From compiled workflows|https://nvlabs.github.io/SoL-Pi/}}).

Environments. [[S2.SS3|§2.3]] The search set is 535 executable environments: 495 repository tasks built from GitHub issue and pull-request pairs (pre-fix repository, offline dependencies, hidden regression test; kept only if the test fails before the accepted patch and passes after it) and 40 synthetic tasks built around a verifier written first, mostly with a Terminal-Bench-2-style interface ({{§2.3|ax:S2.SS3}}, {{Figure 3|ax:S2.F3}}). EdgeBench is not used as a source or template for any of them ({{blog|https://nvlabs.github.io/SoL-Pi/}}).

Scale. About 150 directions and about 500 environments, "more than 3,000 runs and more than 60,000 agent-environment interactions" ({{§1|ax:S1}}). The authors add that these counts "describe the scope of our search; they do not establish a scaling law" ({{§2.2|ax:S2.SS2}}). The blog puts the survival rate at "about one out of every forty starting ideas" (4 of 152 is 1 in 38) and reports that a single deep lineage, even with GPT-5.6 Sol at xhigh, tended to get stuck in a local basin after five to ten iterations, while breadth occasionally exposed an unusual idea worth hardening ({{blog, Breadth escapes local search basins|https://nvlabs.github.io/SoL-Pi/}}).

Humans in the loop. The blog calls SoL-Pi "a hybrid auto-research loop": humans supplied early priors, filtered out low-value directions such as tuning the base harness's hyperparameters before the pool was scaled, and, once a mechanism survived, read it and refactored its code into the released implementation ({{blog, Humans set priors|https://nvlabs.github.io/SoL-Pi/}}). The paper does not say how much of each mechanism's final form is human refactoring.

The four mechanisms

[[S2.SS4|§2.4]]

Four mechanisms passed capability-constrained selection, each at a different point in the agent-environment loop ({{Figure 4|ax:S2.F4}}; the middle row of the figure at the top places them). Each is a Pi extension in the {{released code|https://github.com/NVlabs/SoL-Pi}}, and the constants below are the code's.

1. Action Fusion (tools)

Pi often edits a file and then, in a separate model turn, runs a test or build. Action Fusion adds an optional follow-up command to the edit and write tools, so both run in one call and return one observation: three API calls become two. Commands that need to inspect the edit's result stay separate ({{§2.4|ax:S2.SS4.SSS0.Px1}}).

Before: edit, model turn, run. After: edit and run, one turn.

2. Online Context Compact (context)

The agent keeps a plan through an update_plan tool. When a plan step completes, the harness estimates the remaining requests from the observed requests per step, caps the estimate by the requests left before the context window fills, and compacts with Pi's native compaction only if the projected input savings repay the cost of rewriting the prompt cache. Later compactions must clear a larger margin and repay earlier rewrite debt ({{§2.4|ax:S2.SS4.SSS0.Px2}}). The gate prices the cache rewrite, not the summarisation call itself ({{§2.5|ax:S2.SS5}}).

Before: compact only near the window limit. After: compact at subtask boundaries when it pays.

3. ObservationPack (observations)

A tool result larger than 10 KiB is archived locally and sent in full for the next two provider requests; from the third request on it is replaced by a stable handle, its size, and an excerpt of whole lines from its head and tail (1,024 bytes in all). The agent can page the exact original back with obs_recall. Smaller results are untouched ({{§2.4|ax:S2.SS4.SSS0.Px3}}).

Before: a 40 KB file dump rides along in every later request. After: a 1 KB stub.

4. Evidence-Preserving Reducer (delegation)

Build and test logs of at least 4 KiB from a predefined set of commands (pytest, cargo, make, lean and so on in the code) are archived and handed to a cheaper model (GPT-5.6 Luna at high) that writes a compact receipt of the key evidence. A deterministic verifier checks the receipt's schema, source hash, exit status, exact quotes and size; on any failure, suspected credentials, or no size reduction, the agent gets the original log. File reads and searches bypass it ({{§2.4|ax:S2.SS4.SSS0.Px4}}, {{§2.5|ax:S2.SS5}}).

Before: the frontier model reads the whole log. After: it reads verified quotes.

They compose in a fixed order: the reducer processes a tool result first, and ObservationPack recognises the receipt marker and leaves receipts alone ({{§2.4|ax:S2.SS4.SSS0.Px4}}). The first summary of this paper described the fourth mechanism as handing "bulk reading" to a subordinate; in fact file reads and searches bypass it, and only long build and test logs are delegated. None of the four is new as an idea (AgentDiet, ACON and Context-Folding prune or compress trajectories, {{§4.3|ax:S4.SS3}}); the contribution is that a loop found, tested and kept them.

ObservationPack swaps a large result for a 1 KB stub after two requests. Under prompt caching, what does that do to the cache-write traffic?

It raises it. A prompt cache matches the longest identical prefix of the previous request (how caching and compaction work in general is on {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}). Replacing a message in the middle changes the prefix from that point on, so everything after it is written to the cache again (at 12.5 times the price of reading it, for Anthropic's list prices). The paper's own table shows the trade: with GPT-5.6 Sol, the full stack cut cache reads from 2.1326 B to 1.0605 B tokens while cache writes rose from 0.0141 B to 0.0316 B, and total cost still fell from $1,339 to $894 ({{§3.4, Cache reuse|ax:S3.SS4.SSS0.Px1}}). ObservationPack alone raised GPT-5.6 Sol cache writes from 0.0141 B to 0.0160 B ({{Table 4|ax:S3.T4}}).

What each one does to the prompt and its cache. Fig. 2 runs this page's simulator (the released rules and constants, the compaction gate ported from the code) on one illustrative session: each row is one model request, drawn to scale, with the part identical to the previous request (a cache read, pale) and the new or changed tail (a cache write, orange). Pi's lane is on the left, the mechanism's on the right; the dots stream the re-sent prefix from one request into the next.

  1. Pi: every request re-sends everything. Requests 30 to 33 of session B, about 50,000 tokens each. Almost all of each row matches the request before it and is re-read from the cache; only the new tail (the last call and its result) is written. Over the whole session, 98.7% of Pi's recorded traffic is cache reads (the paper's Opus 5 run: 97.9%).
  2. ObservationPack: full twice, then a 1 KB stub. A 6,146-token build log (purple, over the 10 KiB threshold) rides in full in requests 30 and 31; in request 32 it becomes a 350-token stub. The prompt is 5,796 tokens shorter (43,860 against 49,656), but the cache now matches only up to the stub, so everything after it is written again: 2,061 tokens written against Pi's 899. Every later request re-reads 5,796 fewer tokens.
  3. Action Fusion: one request fewer. Pi makes an edit, sees its result, and in the next request asks for the test run; with the follow-up command attached to the edit, both run in one call. The dashed outline is the request that no longer happens: its whole 14,818-token prompt is never re-read. Over the session, that is 31 fewer requests (172 against 203).
  4. Evidence-Preserving Reducer: a receipt instead of the log. A 1,767-token test log (over 4 KiB) goes to the cheaper model, whose 450-token receipt passes verification (green) and replaces it, so request 7 writes 574 tokens instead of 1,891 and every later request carries 1,317 fewer. The receipt size and the 90% that verify are this page's assumptions.
  5. Online Context Compact: compact at a plan step when it pays. At the end of plan step 2 the gate (the released code, ported) finds that rewriting the cache pays back after 39 requests, within the 262 it allows (131 expected to remain, doubled for a first compaction), so it compacts. The summarisation call, request 27, reads the whole 39,477-token context; request 28 can re-read only the 9,000-token system prompt and writes the 1,000-token summary plus the kept 20,000-token tail (21,538 tokens); from request 29 each one re-reads about 30,500 tokens where Pi re-reads about 40,000.
  6. The bill: this session against the paper. All four together, against Pi on the same session: cache reads −82%, cache writes +45%, cost −60% at Opus 5 prices (the reducer's own model included). The paper's GPT-5.6 Sol run on EdgeBench, Table 2: reads −50.3%, writes +124%, cost −33.2%. Same direction, fewer cheap reads for more expensive writes; the sizes are this made-up session's, not EdgeBench's.
