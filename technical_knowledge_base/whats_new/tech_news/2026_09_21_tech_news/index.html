Sep 17Top

Z.ai says GLM-5.3 built the inference stack that now serves it, on more than 100,000 Chinese accelerators, and the transferable finding is about feedback rather than about self-improvement. "Toward Recursive Self-Improvement: How GLM Built Its Own Inference Infrastructure" (Sep 17) reports a production serving system for GLM-5.3-Flash stood up in 13 days with a 3.22x end-to-end throughput gain from baseline to launch. Z.ai states explicitly that it has not reached recursive self-improvement and that humans retained control of objectives and boundaries, which is the right framing and the reason the post is worth reading rather than dismissing. The engineering claim is that the bottleneck was the feedback environment, not the model, and the fix was replacing sparse signals ("the test failed") with three kinds of local verifiable feedback: correctness, by comparing numerical results across execution paths, which surfaced a TF32 precision bug visible only under specific parallelism strategies; system behaviour, by timeline analysis, which is how a 20% slowdown was traced to the Python global interpreter lock blocking KV-transfer overlap; and performance, by layered testing that shows which constraint actually binds. Neither bug would ever have surfaced from an end-to-end metric. The practical advice generalises well beyond serving: audit what feedback your agent receives after a change, build cheap intermediate validation, define acceptance criteria numerically before starting, and let validated techniques accumulate in a reusable library.

Sep 8Top968 points

Nvidia shipped native GPU programming in Rust, in two tracks. Announced in the window and the week's top Hacker News story at 968 points. cuda-oxide is the SIMT track: a custom rustc codegen backend that intercepts compilation, routes #[kernel] functions through Rust MIR and emits PTX, via the Pliron IR framework and LLVM. Safety comes from DisjointSlice types and launch contracts that make aliasing a compile error. cutile-rs is the tile track: you write tile-level computation, the compiler decides how tiles map onto each architecture, and the kernel is JIT-compiled through CUDA Tile IR on first use; exclusive access is guaranteed by tensor partitioning plus ordinary Rust ownership. Status differs sharply between them. cutile-rs is published on crates.io and already in production in Hugging Face's Grout inference engine and in mistral.rs; cuda-oxide is early alpha and needs a pinned nightly toolchain plus LLVM. No performance benchmarks are published, and the announcement does not claim any. The structural point is that the tile track's source does not encode architecture-specific choices, which is the same argument Triton makes against CUDA C++, now with Rust's memory model attached.

Three papers in one week make the auto-research loop the field's active research programme, and a fourth shows what happens when you attack one. Agora (Sep 16) removes the planner from multi-agent research entirely and records everything as an append-only graph of Git commits: 13 workers, 12 days, 1,703 contributions, evaluator score 3.39 to 1.899 bits per byte, and 165 independent reproductions with zero failures. SoL-Pi (Sep 17, NVIDIA) runs the improvement loop at the harness layer instead of the model layer and finds roughly half an agent's token traffic is harness inefficiency: 44.7 to 49.0% fewer recorded tokens at task parity on EdgeBench. Dream-RSI (Sep 14) makes the loop cheap by treating the accumulated discovery history as a replay simulator, so exploration policy improves off-policy without paying for new evaluations. Emergence World (Sep 17, Emergence AI) is the adversarial counterweight: eight worlds of ten agents over 16 days, 850,000 LLM calls and 50 billion tokens, under prompt injection, misinformation and memory exposure. None was resilient, and the finding that matters is that detection did not ensure containment, with systems recognising adversarial content and still interacting with it up to 46 hours later. Detection is a signal rather than a control: nothing in these loops was wired to act on having recognised the attack, which is the thing to check in anything you are already running. All four have full summaries under Papers.

One block of 128 weights from a ternary layer (the block size deployed formats quantise in), each −1, 0 or +1, stored two ways and drawn to the same scale, one small square per stored bit. Five-trit packing (the usual way) reads every group of five weights as one base-3 number and stores it in a byte, 26 bytes per block: a zero costs as much as a sign. BITCOS stores a presence bitmap (one bit per weight: is it non-zero?) and then one sign bit for each non-zero weight only, packed together. It plays by itself once in view; the steps below say what each stretch shows. Then switch to BITCOS (the buttons above the drawing) and move the zero share: the more zeros, the less BITCOS stores.

Illustrative sample: the 128 weights are drawn at random with the chosen share of zeros; the bit counts are exact for that sample, and the long-run rates are the formulas.

Step by step

  1. Before the first byte. There are 3⁵ = 243 ways to fill five ternary weights and a byte has 256 values, so five weights fit in 8 bits: 1.6 bits per weight. But weights are quantised in blocks of 128, and 128 is not a multiple of 5, so a block needs 26 bytes. The packing ignores what the weights are.
  2. Bytes 1 to 5. Each group of five weights (outlined) is read as one base-3 number between 0 and 242, with 0 = 0, + = 1 and − = 2, and written as one byte; the line under the bit strip shows the number for the byte just written.
  3. Bytes 6 to 25. The same for the next 100 weights. Whatever the share of zeros, every byte costs 8 bits: a zero costs as much as a sign.
  4. Byte 26: three weights left over. 128 = 25 x 5 + 3, so the last byte holds only the 3 weights left and part of it is wasted.
  5. Done: 208 bits for 128 weights. 26 x 8 / 128 = 1.625 bits per weight, the paper's figure for five-trit packing as deployed, against the log₂3 = 1.585 bound. The 66 zeros cost exactly as much as the 62 signs. Switch to BITCOS.
  1. Two arrays instead of one. A presence bitmap with one bit per weight saying whether it is non-zero, then a compacted vector with one sign bit for each non-zero weight only. Cost: 1 + (1 − z) = 2 − z bits per weight.
  2. Weights 1 to 16. Every weight adds one bitmap bit; only the non-zero ones add a sign bit. Zeros are now cheaper than signs: one bit instead of two.
  3. Weights 17 to 128. The rest of the block, 16 weights at a time: the bitmap grows by 16 bits each time, the sign vector by however many of the 16 are non-zero.
  4. All 128 weights written. Bitmap 128 bits plus 62 sign bits = 190 bits, 1.484 per weight on this sample (formula: 2 − z = 1.485), against five-trit packing's 208.
  5. Decode: one population count per weight. To decode a weight, read its bitmap bit; if set, its sign is the entry whose index is the number of set bits before it, a population count that CPUs and GPUs do in one instruction. Five-trit packing needs a division by 3 (or a table) to unpack each byte, which is why the paper reports faster kernels as well as smaller weights: up to 1.28x on matrix-vector products, 1.18x end to end on CPUs and 1.27x on GPUs.

From 3,514 to 890 bytes per token, one change at a time

The cache a model keeps for every token it has read is what limits how many long agent sessions fit on one GPU. Its size is three factors multiplied: bytes per stored entry, one entry per m tokens (the sequence compression), and how many layers store one. The scene draws all three: layers run left to right, a window of 16 tokens runs front to back, and each stored entry is a box as tall as its bytes (the main entry, with the 68-byte indexer key on top in orange). It plays by itself once in view; the steps below follow DeepSeek from V4-Flash's cache to V4.1-Flash's. One step makes the cache bigger on purpose. Drag to turn the scene.

Illustrative: the 16-token window; V4-Flash's CSA and HCA layers drawn grouped by kind (the sources give the counts, not the order; its 2 sliding-window-only layers are not drawn); and which later layer reads which source (drawn as the nearest source before it: the sources name the four source layers, not the map). The bytes are the sources' own.

Step by step

  1. V4-Flash: every layer keeps its own cache. 21 CSA layers each store one 584-byte entry (448 FP8 channels + 64 BF16 RoPE channels + scales) plus a 68-byte indexer key for every 4 tokens: four entries in the 16-token window. 20 HCA layers store one entry for every 128 tokens, too sparse to show in 16 tokens (the flat lanes on the right). Total 21 x 652 / 4 + 20 x 584 / 128 = 3,514 bytes per token, 97% of it in the CSA layers.
  2. Cross-layer reuse: 4 layers store, the rest read theirs. V4.1 (40 layers: a 20-layer encoder, then a 20-layer decoder) drops HCA and lets later layers reuse the cache and the top-k index of four source layers (2, 8, 14 and 20): the dots stream from each source to the layers that read it; layers 0 and 1 attend only within their sliding window. Still in the V4 format at m = 4: 4 x 652 / 4 = 652 bytes per token, 5.4 times smaller.
  3. Relax the sequence compression (the cache grows). Merging 4 tokens into one entry loses detail, so the three encoder sources now merge only 2 (eight entries in the window) and the decoder source keeps every token (sixteen): 3 x 652 / 2 + 652 = 1,630 bytes per token. The cache is 2.5 times bigger than the step before, spent on quality.
  4. FP4 main entries: 584 to 288 bytes. The main entry is stored as 512 FP4 channels (256 bytes) with one E4M3 scale per 16 channels (32 bytes): 288 bytes instead of 584, so every box shrinks while the indexer key stays. Total 3 x 356 / 2 + 356 = 534 + 356 = 890 bytes per token: 3.95 times smaller than V4-Flash, and the encoder-decoder split is what lets V4.1 relax the compression and still end lower.
