MCP with and without sessions: the same requests, before and after 2026-07-28

One agent makes the same calls to an MCP server running as three instances behind a gateway: list the tools, search twice, then call a tool that needs a human's approval. Halfway through, instance A is restarted for a deploy. With sessions (before the 2026-07-28 revision) the client opens a session, is pinned to the instance that holds it, and the gateway has to read each request's body to know what it is. Without sessions each request carries what it needs, any instance can answer it, and the method and tool name travel as headers.

Illustrative scenario: three instances, one restart and these six calls are invented to show the mechanisms. The mechanisms (the initialize handshake and Mcp-Session-Id header, sticky routing, the new Mcp-Method and Mcp-Name headers, and approval as a second request instead of a held connection) are the ones InfoQ's report of the revision describes.

  1. Open a session: initialize. Before any work the client must run the initialize exchange. The gateway can only see a JSON-RPC body, so it parses it, then sends the request to any instance; instance A creates session S1 and returns its id in the Mcp-Session-Id header. POST /mcp {"method":"initialize", "params":{protocolVersion, capabilities, clientInfo}} → 200 Mcp-Session-Id: S1
  2. Confirm it: initialized. The second half of the handshake. From now on the client is pinned: every request carries S1, and the gateway must route it to A, the only instance that holds S1 ("a client was pinned to whichever instance held its session"). POST /mcp Mcp-Session-Id: S1 {"method":"notifications/initialized"} → 202
  3. List the tools. Two round trips spent before the first useful call. To apply a rule per method (rate limits, logging) the gateway has to parse the body, because the method name is only in there. POST /mcp Mcp-Session-Id: S1 {"method":"tools/list"} → 200 [search, fetch, approve_refund]
  4. Search. A tool call. B and C sit idle for this client however busy A is: load balancing is "impractical" when the state lives on one instance. POST /mcp Mcp-Session-Id: S1 {"method":"tools/call", "params":{"name":"search", ...}} → 200 results
  5. Deploy: instance A restarts. A new version rolls out and A restarts. Session S1 lived in A's memory, so it is gone. Infrastructure had to "preserve sessions, drain or migrate them" to avoid this; here it did not.
  6. Search again: the session is gone. The next call still carries S1 and is still routed to A, which no longer knows it. The call fails. POST /mcp Mcp-Session-Id: S1 {"method":"tools/call", "params":{"name":"search", ...}} → 404 session not found
  7. Start over: a new session. The client re-runs both halves of the handshake, lands on B and is now pinned to B with session S2. Two more round trips that do no work. POST /mcp {"method":"initialize", ...}, then POST /mcp Mcp-Session-Id: S2 {"method":"notifications/initialized"} → 200 Mcp-Session-Id: S2, then 202
  8. Retry the search. The retried search succeeds on B. POST /mcp Mcp-Session-Id: S2 {"method":"tools/call", "params":{"name":"search", ...}} → 200 results
  9. A call that needs approval: hold the line. The server needs a human's answer before it can finish. It sends that request back over a stream it keeps open, so the connection, the session and instance B all stay tied up for as long as the human takes. POST /mcp Mcp-Session-Id: S2 {"method":"tools/call", "params":{"name":"approve_refund", ...}} → stream held open: server asks the human (elicitation), then answers
  10. Result. Six calls cost 9 round trips, 4 of them handshake; every request's body was parsed to route it; one call failed because an instance restarted; one connection was held open waiting for a human. Now switch to the version without sessions.
  1. List the tools, no handshake. No initialize, no session id. The request carries the protocol version, client identity and capabilities it needs, plus the new mandatory header Mcp-Method. The gateway reads the header, never the body, and sends the request to whichever instance is free (B). POST /mcp MCP-Protocol-Version, client identity, capabilities; Mcp-Method: tools/list {"method":"tools/list"} → 200 [search, fetch, approve_refund]
  2. Search, routed by header. A tool call arrives as Mcp-Method: tools/call and Mcp-Name: search, so a gateway, rate limiter or firewall can act per method or per tool with the rules it already applies to every other API. This one goes to C. POST /mcp Mcp-Method: tools/call, Mcp-Name: search {"method":"tools/call", "params":{"name":"search", ...}} → 200 results
  3. Search again, anywhere. "Any request can land on any instance." Load spreads across all three; this one goes to A. POST /mcp Mcp-Method: tools/call, Mcp-Name: search {...} → 200 results
  4. Deploy: instance A restarts. The same restart. A held no protocol session, so there is nothing to lose, drain or migrate; the gateway simply stops sending to A while it is down.
  5. Search: unaffected. The next search goes to B and succeeds. The client never noticed the restart. POST /mcp Mcp-Method: tools/call, Mcp-Name: search {...} → 200 results
  6. A call that needs approval: answer later. Server-initiated requests become Multi Round-Trip Requests: instead of holding a stream open, the server (C) returns input_required and the request ends. Nothing waits on the server while the human decides. POST /mcp Mcp-Method: tools/call, Mcp-Name: approve_refund {...} → input_required: "Approve a refund of $40?"
  7. Retry with the answer. The client collects the answer and retries the call with it; any instance can complete it (here B). Approval is two requests instead of one held connection: simpler to run, though the wait for the human now sits between two calls rather than inside one. POST /mcp Mcp-Method: tools/call, Mcp-Name: approve_refund {... "input": "approved"} → 200 refund approved
  8. Result. The same six calls cost 6 round trips (one extra for the approval, none for a handshake); the gateway routed every one on headers; the restart cost nothing; no connection was held. What is left is close to a plain HTTP API, which is the "MCP is dead" argument: the rest of the protocol (a standard tool contract that model providers back) is what its defenders say still justifies it.
