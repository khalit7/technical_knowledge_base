When to curate memory: once at write time, or per task at read time

The same four past runs and the same new task, kept two ways. Write time: each finished run is distilled straight away into one fixed lesson, before anyone knows which future task it will serve. Read time (JitMem): the raw runs are kept, and a curator writes a compact, task-specific payload only once the new task is known. It plays write time first; then switch (the buttons above the chart) and watch what is in the bank, when curation happens and how big the executor's prompt gets (drawn to scale).

Illustrative scenario: the tasks, the lessons and the payload text are invented to show the mechanism. The pipeline (BM25 over task descriptions, a GRPO-trained curator, successes only, an ephemeral payload) and the token and step counts at the end are the paper's.

Step by step

  1. A finished run is distilled once. The first run ends. A write-time method turns it straight away into one fixed artefact (a reflection, an insight, a skill) and keeps only that. It has to decide what will matter before any future task is known; the raw trace is not kept.
  2. Every run, the same way. The other three runs are distilled the same way, the failed one included (it becomes an "avoid" lesson). The bank now holds four short, general lessons, each written for the task it came from.
  3. A new task arrives. "Heat a potato and put it on the counter." Nothing in the bank was written with this task in mind.
  4. Retrieve the closest lessons. The lessons nearest the task by similarity are pulled into the prompt. They are generic ("heat things in the microwave"); the details that would help here (where the microwave was, what had to be opened first) were dropped at write time.
  5. Execute with the lessons in the prompt. The executor runs with the retrieved lessons prepended. Measured on ALFWorld with a GPT-5.4 executor, ReasoningBank (a write-time method) used 19.7K input tokens and 16.2 steps per episode against 9.0K and 17.8 with no memory at all.
  1. A finished run is stored whole. The first run ends. JitMem keeps the raw trajectory, the task description and every observation and action, with no summary at all. An executor-as-judge decides whether it succeeded.
  2. Only successes go in, raw. The other runs are stored the same way, except the failed one: only trajectories the judge marks successful are appended. Nothing is decided yet about what will matter.
  3. A new task arrives. "Heat a potato and put it on the counter." This time the task is known before anything is curated.
  4. Retrieve: BM25 over task descriptions. The top raw trajectories are fetched by keyword match on their task descriptions only (BM25), here the egg run and the mug run.
  5. Curate now that the task is known. A curator (Qwen3-8B, trained with GRPO on whether the executor then succeeds) reads the task and the retrieved traces and writes a compact payload for this task: the relevant past experience, what worked, specific guidance. The payload is used once and not stored.
  6. Execute with the payload only. The frozen executor never sees the raw traces, only the payload. Measured on ALFWorld with a GPT-5.4 executor: 9.8K input tokens and 11.6 steps per episode, barely more prompt than no memory (9.0K) and six fewer steps.
  7. Update: the new success is appended raw. If the judge marks the run successful, its raw trajectory joins the bank, ready to be curated again for whatever task comes next.

Source: {{JitMem, arXiv 2609.27334|https://arxiv.org/html/2609.27334}} (method section; efficiency table on ALFWorld with a GPT-5.4 executor: input tokens per episode 9.0K with no memory, 19.7K ReasoningBank, 22.4K SkillOS-base, 10.9K untrained JitMem, 9.8K trained JitMem; steps 17.8, 16.2, 16.9, 13.2, 11.6). Its ablations point the same way: storing a write-time distillation instead of the raw trace cost 6.8 to 8.2 points on WebShop, and removing task conditioning from the curator cost up to 11.4 points on ALFWorld after RL. The headline gains (+16.2 ALFWorld, +16.3 WebShop) are with a Qwen3-8B executor against RL-trained SkillOS.
