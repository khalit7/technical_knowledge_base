The harness, two ways: one task, the same model, three wrappers

The mechanism: one task, the same model, three wrappers

The same long task run three times, one square per agent turn, drawn to the same scale. Model alone keeps its plan only in its context. StateM puts a runbook (a state machine of phases) and a durable record outside the model, and checks every transition. AVO keeps a persistent memory outside the model and adds a supervisor that watches for stalls. It plays by itself once in view; the steps below say what each stretch of turns shows. Then switch wrapper (the buttons above the chart) and watch where the runs part.

Illustrative scenario: the task, the turn counts and the moment of each event are invented to show the mechanisms. The mechanisms (and the four failure modes the "model alone" run hits) are the ones the StateM paper and Nvidia's AVO post describe; the real scores are in "What the real runs measured", beside the item above.

Step by step

  1. Turns 1 to 2: the plan goes into the context. The agent reads the task and writes a plan. With no control layer, that plan is text near the top of its context window, and that is the only place it exists.
  2. Turns 3 to 6: work. The agent edits files and runs commands. Every turn appends tool output to the context.
  3. Turns 7 to 8: the plan recedes. The plan is now a small, old part of a long context. The StateM paper names this pressure: "the control signal carried by a plan can weaken as the trace grows".
  4. Turns 9 to 11: the context is compacted. To stay inside the window, the history is summarised. Which files had already been changed was in the dropped detail, so the agent spends three turns rediscovering its own progress. Failure mode 1: losing track of mutable state.
  5. Turns 12 to 14: a dead end, again. The agent tries an approach that failed in an earlier run. Nothing carried that lesson across runs, so it is repeated. Failure mode 2: failing to reactivate lessons from earlier executions (the paper's "procedural-memory gap").
  6. Turn 15: "done". The agent declares the task complete without running the project's tests. Failure modes 3 and 4: skipping a known procedure and stopping prematurely. Its own declaration is the only check, and "an agent's declaration of completion does not constitute independent verification".
  7. Result: the hidden test fails. 15 turns, 6 of them redone or repeated, and nothing other than the model ever checked the work. Same model in the other two runs; switch to StateM or AVO.
  1. Enter Plan: the in_hook loads the phase. The runtime, not the model, holds the current state. Entering Plan injects that phase's instructions and the durable progress record. The agent plans, then asks for goto Execute: the runtime checks the edge exists, runs the before_transfer checks, persists the plan (out_hook), logs the transition, then runs Execute's in_hook.
  2. Inside Execute: free to work. Within a state the agent keeps its full autonomy: it reasons, calls tools, edits files and iterates. StateM controls the phases, not the micro-actions.
  3. The phase stays recent. The context grows as before, but the current phase and its obligations were injected when the state was entered, so they are recent rather than buried at the top.
  4. Compaction: ask the runtime where we are. After the same compaction, the agent queries StateM for its current state, prior transitions and recorded evidence, and resumes in one turn. Recovery restores the recorded control state; it cannot restore hidden model context or work that was never persisted.
  5. A lesson from an earlier run activates. A finding from an earlier run's postmortem was promoted into the runbook as a versioned practice, so it fires at this phase as a precondition, and the dead end is skipped. (The specific practice here is illustrative.)
  6. goto Verify: a test fails, the run goes to Repair. Verify runs the tests as a command check, evaluated by the host and reproducible. They fail, so the move to Handoff is blocked; the runbook's edge routes the run to Repair, and Verify passes on the second try. The failure stays visible in the history instead of propagating.
  7. goto Handoff: completion recorded at a terminal state. The before_transfer checks pass and completion is recorded only now, at the terminal state. 20 turns: more than the model alone used, but none redone, 4 host checks, 1 problem caught before handoff.
  1. Plan, with a memory outside the context. The main agent inspects the task and plans. Beside it sits a persistent memory, outside the model's context, and a supervisor that watches the whole trajectory.
  2. Implement, then evaluate by running it. Like other coding agents it edits code, runs commands and validates its work through execution: the feedback comes from tests, compilers and profilers, not from the model's opinion.
  3. Every result is kept. Persistent memory carries prior implementations, evaluation results, compiler and profiler outputs and accumulated reasoning forward (Nvidia's list).
  4. Compaction: resume from memory. After the same compaction the agent reads its memory and resumes "from the current state rather than repeatedly reconstructing the search".
  5. Going round in circles: the supervisor steps in. The agent starts re-exploring a path it already tried. The supervisor "monitors the broader trajectory for stagnation or repeated unproductive cycles and can redirect the main agent toward alternative strategies". Nvidia's El Hallak: it nudges the agent when it "starts exploring a path that it might lead to a dead end, or re-explore a path that it had previously trod".
  6. Evaluation catches a regression. An evaluation fails and the agent revises; the result goes to memory like every other.
  7. Result: passes. 19 turns, 2 of them a repeated path that the supervisor cut short, 4 evaluations run by executing the work. Nvidia stresses that its own experiment "does not isolate" the memory's contribution: this is the mechanism, not a measured effect.
