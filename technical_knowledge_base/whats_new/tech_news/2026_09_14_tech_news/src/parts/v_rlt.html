Depth that grows with the sequence: a decoder-only Transformer against the Recurrent Looped Transformer

Eight tokens (five of prompt, three generated) through the same 96 blocks per token, drawn to the same scale: each column is a token, each row six layers. In a decoder-only Transformer, nothing computed at the top of one token feeds the bottom of the next; tokens meet only through attention, so the deepest chain of computation behind any output stays 96 blocks, and the whole prompt runs in parallel. In the RLT reference layout (48 encoder + 48 decoder layers with shared weights), the encoder runs the prompt in parallel, but each token's decoder starts from the previous token's final decoder state, so the chain grows by 48 blocks per token, and the decoder has to walk the prompt one token at a time. It plays the Transformer first; then switch (the buttons above the chart) and watch the orange chain and the counters.

Step by step

  1. The prompt arrives. Five prompt tokens, 96 layers each. Nothing has run yet.
  2. Prefill: every prompt token, one layer at a time. All five tokens go through layer 1 together, then layer 2, and so on: 96 sequential layer steps for the whole prompt, however long it is. Tokens exchange information only through attention to each other's cached keys and values, sideways at the same layer.
  3. Generate token 6. The new token runs all 96 layers. Its output depends on earlier tokens only through attention, so the longest chain of computation behind it is still 96 blocks: what token 5 computed at its top layer never feeds token 6's first layer.
  4. Generate tokens 7 and 8. Each new token adds another 96 sequential layer steps of latency, but the depth behind any single output never grows past 96. Switch to RLT and run the same eight tokens.
  1. The same prompt arrives. Same five tokens, same 96 blocks per token, now split into a 48-layer causal encoder and a 48-layer recurrent decoder with shared weights.
  2. Encoder: the prompt in parallel. The causal encoder runs over all known tokens together, like a normal Transformer, and builds the global key-value memory the decoder will read: 48 sequential layer steps.
  3. Decoder, token 1. The decoder starts from a learned initial state and runs its 48 layers on token 1, reading the encoder memory. Its final output s1 is kept.
  4. Decoder, tokens 2 to 5: one after another. Token 2's decoder input merges its own embedding with s1, token 3's with s2, and so on. The chain of computation now runs through every earlier token's full decoder: 48, 96, 144, 192, 240 blocks. The price is that this cannot run in parallel: the decoder walks the prompt token by token.
  5. Generate token 6. Generation looks as before: encode the new token, then run the decoder from s5. The deepest chain behind token 6's output is 6 x 48 = 288 decoder blocks, at the same 96 blocks of work per token.
  6. Generate tokens 7 and 8. After t tokens the chain is t x 48 decoder blocks while the work per token stays fixed. The report is candid that this is structural depth, not proven reasoning: gates may suppress long paths, and no trained model of this size has shown the gain.

From the {{RLT project page|https://yifanzhang-pro.github.io/recurrent-looped-tranformer/}} and {{MarkTechPost|https://www.marktechpost.com/2026/09/13/a-princeton-researcher-proposes-recurrent-looped-transformer-rlt/}}: the 48 + 48 tied layout, 96 logical blocks per token, a path of t x 48 decoder blocks after t tokens, the encoder batched over known tokens and the decoder updated in token order during prefill. Illustrative: eight tokens and rows of six layers; no trained 48 + 48 model exists (the experiments published on 17 to 20 September use untied 8- and 16-layer models). Derived: sequential layer steps = 96 for a Transformer prompt of any length (layers run one after another, tokens in parallel), 48 + 48 x P for RLT, counting one layer of one token as one step and ignoring how a GPU would overlap them.
