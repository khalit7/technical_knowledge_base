4. The transpose problem, and re-quantising with stochastic rounding

[[ar:Block-scaled backward passes|Block-scaled backward passes]]

The backward pass reads the forward pass's tensors transposed, so every value lands in a different block of 16 with a different scale. The forward y = xqwqT sums along rows of xq, so its blocks run along rows; the weight gradient dw = gTxq sums down columns (and dx = g·wq reads w the other way), so each value is grouped with 15 new neighbours ({{in the article|ar:each value is grouped with 15 different neighbors}}). In the article's Figure 2, a 16 × 16 tile with one row of large values keeps all 256 values under row scales; under column scales the large row sets every scale and 221 small values round to zero. The backward pass then computes gradients for numbers the forward pass never used.

NVIDIA's fix for weights, one scale per 16 × 16 tile, makes both directions identical but was too coarse here. A square tile has the same blocks transposed ({{in the article|ar:compute a single scale factor based on the largest value}}), but one outlier among 256 values flushes the rest: in the article's Figure 3, 1 × 16 scales keep 241 of 256 values around an outlier, the tile keeps only the outlier. It hurt compute efficiency too much ({{in the article|ar:computing scale factors over 16×16 tiles to be too coarse}}).

The insight: the backward tensor need not equal the forward one, only equal it in expectation ({{in the article|ar:perfect identity isn’t strictly necessary}}). So the recipe de-quantises the forward tensors, transposes them in high precision and re-quantises them into the new blocks with stochastic rounding, which rounds up or down at random so the expected result is exact ({{in the article|ar:de-quantizing tensors from the forward pass, transposing them}}). The article's example: 5.4 in a block of scale 9 is 0.6, rounded to 0.5, so the forward pass used 4.5; in a backward block of scale 2 that is 2.25, which nearest rounding always makes 2 (so 4), while stochastic rounding gives 2 three quarters of the time and 3 a quarter, 4.5 on average ({{in the article|ar:Stochastic rounding instead rounds it to 2 three quarters}}). Blackwell does stochastic rounding in hardware.

And the backward target is MXFP8, not NVFP4: re-quantising from de-quantised values allows any format, and MXFP8 for both gradient matmuls gave the best trade ({{in the article|ar:stochastically re-quantizing weights and activations to MXFP8}}). Re-quantising the forward tensors comes from TetraJet-v2 and Quartet II, which the article credits. The whole layer is the article's Figure 4, drawn beside other recipes as "NVFP4 MoE experts" in {{Quantization and Precision|n:3c65c17b0d0d817b8f41ff66fba4cd0e}}, Fig. 10.

The toy on the right hands one illustrative tile to the backward pass five ways and measures, exactly, the error that stays and the error that averages out. On the default tile (unit Gaussians and one value of 40), quantising x again down the columns leaves a 13.0% error against what the forward pass used, the same on every draw. The 16 × 16 tile has no mismatch, but its forward pass already lost 252 of 512 values to zero, against 49 with row scales. Stochastic NVFP4 is nearly unbiased (0.5%, from block maxima that saturate) but each draw is off by 13.4%; stochastic MXFP8, the article's choice, is unbiased with 2.0% noise, about 0.06% after 1,000 draws are averaged. MXFP8 with nearest rounding, what the two replications run because Transformer Engine's MXFP8 quantiser has no stochastic option, leaves a fixed 1.6%. Across the four tiles: 13.0% to 14.4% for the naive mismatch, 1.6% to 3.6% for nearest-rounded MXFP8.

How far this transfers: the tiles are made up (seeded) and 32 × 16; the formats and rounding are exact. It shows the direction and the order of magnitude of each choice, not what any choice costs Inkling 2 Small's loss. Whether a fixed rounding error behaves as bias in real training depends on whether it leans the same way across steps; on a fixed tile it does by construction.
