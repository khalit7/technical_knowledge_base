1. Thirteen days, 155 responses, one endpoint

[[ar:Gadi Evron submitted a report on September 8|What happened]]

For thirteen days, long prompts to one Workers AI model could be answered from other customers' data. GLM-5.3 (@cf/zai-org/glm-5.3) launched on 27 August 2026; on 8 September Gadi Evron of Knostic reported through HackerOne that very long prompts sometimes returned text from other users' sessions. Cloudflare reproduced it the next morning, {{took the model offline within 40 minutes|ar:took the model offline within 40 minutes of declaring an incident}} of declaring an incident, and restored it at 19:40 UTC the same day. {{In total, 155 responses were affected|ar:In total, 155 responses were affected}}, all to prompts over 681,280 tokens; no other model was.

Cloudflare reads the traffic as ordinary use, not an attack: outside its own and the researcher's tests, the requests were {{consistent in timing and volume with ordinary long-context use|ar:consistent in timing and volume with ordinary long-context use}}. The timeline on the right adds what the post mentions only in passing: the engine bug was reported publicly seven weeks before launch, and the change that stops it reached SGLang's main branch two days before the report.

2. Issue one: a context window larger than the pool behind it

[[ar:We were aware of this size mismatch|Issue one: misconfiguration]]

The pool and the window are two numbers nothing ties together. SGLang sizes the KV pool {{from whatever GPU memory remains|ar:SGLang sizes it at startup from whatever GPU memory remains}} after the weights load; the advertised context length is a separate setting, and {{Nothing forces the two to agree|ar:Nothing forces the two to agree}}. On GLM-5.3's prefill nodes the pool came to 681,280 tokens against a 1,048,576-token window: 65% of it. Why a million-token cache is that large is {{Long context|n:3fd5c17b0d0d81059ee1ce20c0326dc5}}'s calculator.

Cloudflare knew, and expected an error. The pool size is in SGLang's start-up log and metrics, and the gap was known before launch; {{We expected the engine to return an error|ar:We expected the engine to return an error for any prompt it could not process}}, and long-context benchmarks returned HTTP 200. The tests {{only validated HTTP response codes and engine performance|ar:we only validated HTTP response codes and engine performance at long contexts}}, never the output; by section 3's mechanism those successful tests were most likely answered from other requests' cache too.

The engine did refuse the prompts, inside. Drag the prompt past 681,274 tokens in the figure at the top. The refusal was real; what went wrong is where the refused request went next.

3. Issue two: a rejected request looked live to both admission queues

[[ar:A rejected request reported itself as live|Issue two: SGLang bug]]

Freed KV pages keep their contents. A request gets pages from a shared pool when admitted and returns them when done, and {{Pages are not currently zeroed between requests|ar:Pages are not currently zeroed between requests}}: the next owner overwrites them. That is standard and needed for speed, so the engine's record of who owns which page is the only isolation between users (the block pool: {{Batching, KV cache and scheduling in depth|n:3c65c17b0d0d819db53bd2c48909e5b2}}, section 1).

The rejection path was built for one machine. Req.set_finish_with_abort stores the error in to_finish and {{swapped the prompt for a one-token placeholder|ar:swapped the prompt for a one-token placeholder}}, so the request drains through the normal batch. {{On a single-node deployment this worked|ar:On a single-node deployment this worked}}. In disaggregated mode both workers' admission queues ask req.finished(), which reads a different field, finished_reason, so a refused request looked live (schedule_batch.py at v0.5.19, {{L1359-1361 and L1927-1946|https://github.com/sgl-project/sglang/blob/v0.5.19/python/sglang/srt/managers/schedule_batch.py#L1927-L1946}}):

  1. Bootstrap. The router tells decode the prompt is 8 pages long; decode reserves 8 pages, still holding earlier requests' data.
  2. Prefill admission. The rejection sits in to_finish, finished() returns False, and the request is admitted.
  3. Forward pass on one token. The prompt is already the placeholder, so prefill computes KV for a single token.
  4. Transfer. One page crosses to decode with the "transfer complete" signal.
  5. Decode admission. The same finished() check, the same blind spot: the handoff is accepted.
  6. Attention over all 8 pages. {{Only page P0 had been written by this request|ar:Only page P0 had been written by this request}}; P1 to P7 hold other users' prompts and partial answers.
  7. Response. HTTP 200 instead of 400, a coherent reply, prompt_tokens matching the long prompt, faster than an 8-page prefill could be, and other users' content in it.
  1. Bootstrap. The router tells decode the prompt is 8 pages long; decode reserves 8 pages, still holding earlier requests' data.
  2. Prefill admission. A valid request: finished() is False, correctly, and it is admitted.
  3. Forward pass. Prefill computes KV for all 8 pages of the prompt.
  4. Transfer. All 8 pages cross over RDMA, then the done signal.
  5. Decode admission. The handoff is accepted; every reserved page now holds this request's KV, and nothing earlier survives.
  6. Attention over all 8 pages. Every page read was written by this request.
  7. Response. HTTP 200, a correct answer, normal prefill latency.
  1. Refused at intake. The scheduler refuses the prompt as before: error stored, placeholder swapped in.
  2. Retired at the prefill door. PrefillBootstrapQueue.add now asks whether a request is aborted and holds nothing; this one is, so it is retired with its original error.
  3. No forward pass. No bootstrap handshake, no metadata buffer, no stub computation.
  4. No transfer. Nothing is sent, so decode can never be told "complete".
  5. Decode never commits. Its reservation is released when the router cancels the pair (or its own door retires the request, when decode also refuses it).
  6. No read. No page this request did not write is ever attended over.
  7. Response. HTTP 400 with the length error the scheduler wrote in step 1.

In the real incident the reservation was thousands of pages. With 64-token pages a 700,000-token prompt reserves 10,938 pages on decode, and one placeholder token was all it wrote, so the reply was conditioned on 699,999 tokens of other requests' leftovers. {{Every request over the threshold behaved this way|ar:Every request over the threshold behaved this way}}: a deterministic path, not a race.

The same bug was already on file. It {{had been reported to SGLang by another user as issue #30233|ar:had been reported to SGLang by another user as issue #30233}} on 6 July, on a GLM-5.2 deployment with the same 1,048,576-token window and a 284,928-token pool, root cause traced and a patch proposed; it was closed for inactivity on 5 September. {{GLM 5.3 was the only model affected|ar:GLM 5.3 was the only model affected by this bug}} because every other deployment had pools larger than its window.
