The idea in one sentence: a plan's quality can be checked by timing it, so a 4B model can be taught by distillation and then reinforcement learning to write hints that steer Postgres's planner, provided the timing noise is engineered out first; on the Join Order Benchmark the trained model alone averages 1.40 times faster plans, and spending three searches per query, keeping the best by a single timing, reaches the title's 1.81.

You need: how Postgres picks a plan from estimated row counts, and what pg_hint_plan can force ({{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}, sections 1 to 5 and the pinning block); GRPO and RLOO advantages ({{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}, section 3); LoRA ({{PEFT|n:3c65c17b0d0d81eba08eef56b3e3b4eb}}).

New terms: JOB (Join Order Benchmark: 113 hand-written queries over the real IMDb data, 33 templates, 4 to 17 tables each); CEB (Cardinality Estimation Benchmark: 13,646 generated queries on the same data, the training set); PlanAction (the model's structured output: join tree, join and scan methods, settings, compiled into a pg_hint_plan comment); no-op error rate (how often a plan identical to the default is measured as more than 5% faster or slower); anchored GRPO (the article's advantage rule: a rollout is compared with Postgres's default and with its siblings' mean, never below zero).

1. Planners guess row counts; a plan's speed can be measured

[[ah:how-good-are-query-optimizers-really|How good are query optimizers, really?]]

The article's premise: judging a plan is easy (run it and time it), producing a good one is hard, and that asymmetry is what reinforcement learning on verifiable rewards exploits. Join ordering alone is NP-hard ({{in the article|ar:is known to be NP-hard}}), and Leis et al. found in 2015 and again in 2025 that optimizers still pick poor plans, mostly from bad row-count estimates.

Its running example shows why order matters. Joining titles, movie companies and company names, with filters to Japanese companies (5% of 100,000) and the 2000s (20% of 1M titles): joining the companies first passes about 100,000 rows to the second join, joining the titles first about 400,000, four times the work. Counting every choice (two join trees times four input orientations, three join algorithms per join, four scan types per table) gives 8 × 3² × 4³ = 4,608 plans for three tables ({{in the article|ar:There are 4,608 different ways}}), and Postgres prunes them with dynamic programming, or a genetic search from 12 tables. It cannot count rows while planning, so it estimates them from per-column statistics ({{in the article|ar:Postgres uses statistics to estimate cardinalities}}) and assumes the filters on different tables are independent; if the Japanese companies made half the movies instead of 5%, the "cheap" order would pass a million rows. How estimates are made and fail, and why one bad estimate low in the tree spoils every join above it: {{Query planning and performance|n:3ef5c17b0d0d817f9e15f445b079e9c8}}, sections 3 to 5.

The lever is pg_hint_plan, an extension that reads a comment such as /*+ HashJoin(a b) SeqScan(a) */ above a query and makes the planner use those methods and that join order ({{in the article|ar:pg_hint_plan is a beautifully simple third-party extension}}). The SQL is unchanged, so a hinted plan still computes the same result; only the route differs.

2. The target: queries that run again and again

[[ah:formulating-our-problem|Formulating our problem]]

The model does not replace the planner on every query; it is spent on queries worth optimising once and running many times. Giving a model the planner's own statistics would mean competing with decades of cardinality-estimation research, and its inference would cost more than Postgres's millisecond planning. A heavy analytic query run thousands of times is different: tens to hundreds of executions up front pay off over all later runs ({{in the article|ar:lies in a specific database usage pattern}}). That framing decides what the results mean: search time and training cost are excluded from every speedup, which is fair only for such repeated queries.

3. The model and its harness

[[ah:a-model-and-its-harness|A model and its harness]]

The policy is a small open model in an agent loop with six tools. The model is empero-ai/Qwen3.8-4B-Distill, a third party's distillation of Qwen 3.8 2.4T into Qwen 3.5 4B (4.66 billion parameters), chosen because it could be trained on two RTX 3090s at home ({{in the article|ar:I decided to start with a small}}). The harness, qo-agent, lets it inspect tables and indexes, read planner statistics for up to eight columns, read the default plan's estimates, submit a candidate for timing, keep the default, or finish with a chosen candidate.

The model never writes hint syntax: it emits a PlanAction JSON object, which the harness validates, compiles into pg_hint_plan hints and prepends to the query ({{in the article|ar:instructed to produce PlanAction JSON objects}}). The figure is one search as the final evaluation ran it (settings from the repository's experiment 033); each candidate's feedback is one timed run, the final score three interleaved pairs.

4. Train on one benchmark, test on another over the same database

[[ah:benchmarks|Benchmarks]]

Training uses CEB's 13,646 queries (16 templates, 12 join shapes); testing uses JOB's 113 (33 templates, each its own shape), both on IMDb. Same database on purpose: the intended user optimises one company's own workload, so learning IMDb well is the point ({{in the article|ar:I would argue this is precisely the point.}}). What must not leak is query structure, so the author reduced every query to its join graph (tables as nodes, joins as edges, filters ignored) and checked for overlap between the two sets: there was none ({{in the article|ar:There wasn’t, so no filtering was required.}}).
