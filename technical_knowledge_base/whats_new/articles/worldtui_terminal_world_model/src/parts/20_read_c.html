5. Making it fast: rows drafted side by side, then checked in order

[[ah:rows-in-parallel|Rows in parallel]] [[ah:rows-that-cant-talk-to-each-other|Rows that can't talk to each other]]

One token at a time suits typing ({{about 38 ms a key|ar:typing felt fine at ~38 ms per key}}), not a redraw: {{up to 12 s on an RTX 4090|ar:took up to 12 s on my RTX 4090}}, about 4 ms a token (derived, 12 s over about 3,000).

Rows rarely depend on each other, so each changed row gets its own batch element with {{the same previous history|ar:Each gets the same previous history}} and KV cache: a frame takes as many steps as its longest row, then the cursor (training needed {{a matching attention mask|ar:This required a matching attention mask}}). Large-frame p95 latency fell 7.7 times. Fig. 1's step ratios are an upper bound: a parallel step costs about 6 single steps on Apple GPUs (a comment in the demo's source).

Rows that cannot see each other disagree, so the same model verifies the draft. Independent rows put {{vim on row 3 instead of row 0|ar:vim opening on row 3 instead of row 0}}, so a sequential pass {{keeps tokens up to the first disagreement|ar:The verifier keeps tokens up to the first disagreement}} and redrafts the rest. Decoding is greedy, so a fully verified frame equals sequential output ({{Speculative decoding|n:3f35c17b0d0d81e086fde85940ebac1c}}). In the browser on an M4, man test takes {{2.5 s sequentially, 0.9 s drafted and verified|ar:2.5s sequentially, or 0.9s with parallel drafting}}.

The demo's decoding settings, and which mode the 0.87 s used

The demo offers sequential, row-parallel plus verification (default) and row-parallel unverified decoding, and a per-frame verification budget: none (exact, the default) or 200 to 800 ms, past which the rest of the draft is committed unchecked. A source comment puts the unverified mode at 26 or 31 of 47 on PresetBench v1.1, on an intermediate checkpoint; the final model's sequential 38 is another checkpoint, so the gap is suggestive, not measured. The post gives the 0.87 s before introducing verification and does not say which mode produced it; its footnote adds that the speed-up is much larger on the 4090 than on the M4.

6. Making it small, and what distilling showed about memory

[[ah:making-it-smaller|Making it smaller]] [[ah:distilling|Distilling]]

The title's 360M is the base model without its vocabulary: {{136M|ar:136M parameters}} of Qwen2.5-Coder-0.5B's 494M are the 151,936-token embedding; keeping 384 rows leaves 358.3M (derived), the model card's "0.36B non-embedding". At 4 bits {{it is 208 MB|ar:which brought it to 208 MB}}, run by a hand-written WebGPU decoder with {{32-bit activations and cache|ar:Activations and the attention cache use 32-bit floats}}.

Removing one layer kept next-token accuracy and erased memory (Fig. 3). On an earlier checkpoint, {{removing layer 7 without retraining|ar:Removing just layer 7 without retraining}} moved next-token accuracy from 99.3% to 98.9% and {{exact readbacks from 64/64 to 0/64|ar:exact memory readbacks fell from 64/64 to 0/64}}; {{the tests fed in the true history|ar:These tests fed in the true history}}, so retrieval lived in a few layers. A 12-layer student without layers 1, 7, 15 and 22 picked the wrong written value {{about half the time|ar:picked the wrong one about half the time}}; {{a 16-layer student keeping them|ar:A 16-layer student that kept those four}} remembered but lost ShellBench commands, and {{he gave up on distilling|ar:I gave up on distilling it}}. The lesson, {{a student can look fine and have quietly lost its memory|ar:So a student can look fine and have quietly lost its memory}}, belongs beside depth pruning ({{Distillation and Small Language Models|n:3c65c17b0d0d81efa2a8c3b3b623eb09}}).

7. What it can do, and what breaks
