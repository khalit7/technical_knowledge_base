@@CARD@@

The idea in one sentence: telling a coding agent to use a named testing or verification technique (TDD, property-based testing, fuzzing, a model checker, a prover, a testing skill) did not make its Zstd decoder measurably more correct than saying nothing, because the agent wrote the same shallow tests it writes anyway, now inside the named tool; the differences between the 30 instructions are the size that chance alone produces.

You need: property-based testing, shrinking, fuzzing, proof and mutation testing ({{Testing and quality|n:3c65c17b0d0d81548848e2ebdd2f63ee}}, sections 6 and 10); a verifier as an agent's stop rule ({{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}, section 10); intervals, power and multiple comparisons ({{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}}).

New terms: Zstd (Zstandard, a compression format; the agents wrote a decoder from its specification, RFC 8878); fully correct run (a run whose decoder passes all 37 hidden tests; the post's only correctness score); effort (Codex's reasoning-effort setting, run at medium and xhigh); condition (one prompt: the task plus one added instruction or skill, or nothing for Default); skill (a SKILL.md file of instructions an agent can load on demand); no-effect world (this page's name for what 30 conditions would look like if none changed anything: 30 draws of one pass rate).

1. One spec, 30 instructions, 80 runs each

[[ar:Here, we test if simple instructions|The opening]]

The experiment asks what a user with no testing expertise gets by naming a technique. The task is an earlier eval of his, reused: implement a Zstd decoder in Rust from the format's RFC and errata, inside a container with no internet; the 37 tests that score it are hidden from the agent ({{in the article|ar:We'll re-use the Zstd implementation eval}}; the setup is described in the author's {{language comparison|https://danluu.com/pl-tokens/#zstd}}, where an agent also wrote the hidden tests). The agent is Codex running GPT-5.6 Sol at medium and xhigh effort, each run a single autonomous turn, every listed library installed. Each condition adds one line to the prompt, such as "Use test-driven development", "Use Lean 4" or "Use QuickCheck" ({{in the article|ar:The 26 prompt conditions tested were}}):

  • Formal tools (9): Verus, Creusot and Kani (proofs and model checking on Rust code), Lean 4 and ACL2 (theorem provers), Alloy, TLA+ and Spin (model checkers for designs), SMT solvers (Z3, cvc5, Yices).
  • Randomised testing (8): property-based testing, QuickCheck, Proptest and Hegel (libraries for it), fuzzing, "audit and fuzz risky areas", metamorphic and differential testing.
  • Process (8): TDD, the built-in Rust test framework, rstest, Insta (snapshot tests), mutation testing, "audit first", Judgement (pick the best technique) and "Make no mistakes".
  • Skills (4): Hegel's official skill, a Rust testing skill from the ECC collection and Trail of Bits' property-testing skill, the top three Codex found when asked, plus a five-line skill the author wrote ({{in the article|ar:Additional, 4 skills were tested}}). And Default: no instruction.

Before running it he wrote down six guesses with confidences: TDD would underperform (55%), formal methods would not outperform (52%), "Make no mistakes" would not beat no instruction (95%), and none of the three public skills would outperform ({{in the article|ah:predictions}}). The list and how he scored it are in the closed block at the end of section 7.

2. Nothing wildly outperforms; agents use the tool and miss the point

[[ah:overall-results|Overall results]]

The headline reading is that no instruction clearly beats saying nothing. Default does "well above average", fuzzing and property-based conditions edge out formal methods at xhigh, the three public skills underperform and TDD does badly, as he predicted ({{in the article|ar:One thing we can see is that nothing really wildly outperforms.}}). He presents one dense chart (Fig. 1 redraws it) and warns against reading strong conclusions from the order ({{in the article|ar:I would caution anyone against drawing any kind of strong conclusions from the ordering.}}). Section "How much of this to believe" tests that order; the short answer is that the warning is right.

The finding he puts first comes from reading what the agents did, not from the scores. With a technique named, agents either wrote their usual tests inside the new framework, or used the technique for show: formal tools proved properties nobody doubted, property-based tests fed fully random inputs to one trivial property ({{in the article|ar:agents tend to either just write the tests they would normally write}}). The default he means is Gary Bernhardt's: "Take the pathological cases dreamed up by someone objecting to mocks 15 years ago, without ever having actually used mocks", then "Make those pathologies the backbone of your testing strategy" ({{in the article|ar:Make those pathologies the backbone of your testing strategy.}}). Fig. 2 counts how often the agents did the named thing at all, and how often they did it in a form that could catch a bug.

The same held on a second spec and at higher effort. On the IMAP RFC, 40 runs per condition, results were not materially different ({{in the article|ar:Results weren't materially different on the IMAP RFC}}). At xhigh the agents could nearly always make their own tests pass, but the tests were weak, for example four identical bitstreams fed to a feature that decodes four, so a decoder that swaps them passes ({{in the article|ar:they wrote poor tests (e.g., they'd submit four identical bitstreams}}). He asks why labs have not built RL environments that reward good testing, as they have for bounded optimisation tasks; a footnote adds that the RL papers ChatGPT pointed him to trained agents to write ordinary unit tests, and that RL for fuzzing (R1-Fuzz) exists but shows no sign of reaching the big labs' models.
