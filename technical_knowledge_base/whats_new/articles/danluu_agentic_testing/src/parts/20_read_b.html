3. Formal tools: proofs of what was never the bug

[[ah:verus|Verus, and the formal sections after it]]

No formal condition was used to prove the decoder correct; agents proved side properties and relied on ordinary Rust tests for correctness. The post's per-condition sections run from worst to best by the average of the two efforts (our recompute of the chart reproduces that order), and formal tools fill much of the bottom.

  • Verus (worst overall: 51.2% at medium, 75.0% at xhigh) was never pointed at the actual code. Agents proved few, uninteresting properties ("the index stays in bounds"), some vacuous: one proof's postcondition simply repeated its three preconditions, A implies A ({{in the article|ar:An actual Verus proof of this form was:}}). The bug-prone part, reading Zstd's bitstreams backwards, went unproved, and the tests for it used palindromic inputs that read the same either way (Fig. 3, panel A).
  • Alloy modelled the format more closely and was still the second worst; its one counterexample was an 8-bit overflow that cannot happen with 64-bit sizes, so the "fix" only added complexity ({{in the article|ar:Alloy found a counterexample which then caused}}). Lean 4, which he expected to do well because it is fashionable for RL training, mostly proved arithmetic. Spin models had no correlation with passing the hidden tests they modelled.
  • SMT solvers became a calculator for state ranges and header arithmetic. The post's example: the count of sequences in a block is byte1 + (byte2 << 8) + 0x7F00, many agents wrote byte1 + (byte2 << 8) | 0x7F00, proved properties about the computation and kept the wrong code ({{in the article|ar:Many agents implemented byte1 + (byte2}}). Fig. 3, panel B, shows why easy tests miss it.
  • TLA+: 159 of 160 runs built a model, usually late and after the code; none changed the Rust ({{in the article|ar:159/160 agents created some kind of TLA+ model}}). Kani was the one tool used on the real code, occasionally; one run in 160 caught a real bug with it, at a noticeably higher cost from re-reading its output. ACL2 often ran out of its 192 GiB memory limit; those runs were dropped from the score (15 at medium, 13 at xhigh), which biases it in an unknown direction ({{in the article|ar:OOM results weren't counted, which biases}}).

His explanation is that the failures are idiosyncratic, not a property of the technique. Verus agents wrote a test for the four-stream jump table in 89 of 160 runs, the same count as Default, but their tests were more often wrong or too easy; nothing about Verus should cause that, as nothing about Clojure should cause the byte-conversion bugs his language eval found ({{in the article|ar:coincidentally the exact same number as Default agents}}). From outside a lab, he says, it is hard to tell why.

4. Randomised testing: random inputs that all take the rejection path

[[ah:quickcheck|QuickCheck, and the randomised sections after it]]

Property-based and fuzzing conditions failed in one characteristic way: fully random inputs, which a decoder rejects at once, checked against trivial properties. Random bytes are not a valid Zstd frame, so almost every generated input exercised one of a few error paths and none of the decoding logic.

  • QuickCheck: every run used it, 63 of 160 checked a single property, and agents wrote more traditional tests than Default ({{in the article|ar:63 out of the 160 runs only checked a single property}}). Hegel: the usual workflow was implement, run normal tests, then read the Hegel docs and add one to four simple property tests.
  • Fuzzing: mostly random bytes or random variations of valid inputs, both landing in rejection paths. In 10 of 160 runs agents generated structured random inputs, and those found real bugs about half the time, some non-trivial; he reads this as evidence the knowledge is there and is simply not the default ({{in the article|ar:They do, in some sense, know how to do this}}).
  • "Audit and fuzz risky areas" made agents target exactly the right parts (FSE, Huffman, bit readers, state), but at medium they mostly ignored it, and where they followed it they again fed invalid random inputs and checked only for crashes. Metamorphic testing checked sensible relations (a skippable frame at a frame boundary changes nothing) in places that were not where agents erred: the drunk looking for his keys under the streetlight ({{in the article|ar:this is where the light is}}).
  • Differential testing (third worst): 135 of 160 runs did something by that name, none built two independent implementations, and where it might have caught a bug the agent wrote the same thing twice, bug included ({{in the article|ar:agents just did the same thing twice and encoded the same bug in both versions}}).
  • Proptest and the library-neutral property-based testing condition, where every agent chose Proptest, both scored well above average; tests were still mostly poor, but Proptest's shrinking (reducing a failing input to a minimal one) sometimes paid off ({{in the article|ar:proptest's shrinking (finding a simpler input that causes a test failure) did sometimes provide some value}}). He finds the accidental second Proptest arm scoring well "mildly interesting".

5. Process instructions: more tests, not better tests

[[ah:tdd|TDD]]

TDD changed behaviour more than any other instruction and made the tests worse. Agents wrote twice as many tests in a test-code-test loop; 67 of 160 runs had a failing test before writing real code, against 0 of 160 for Default ({{in the article|ar:agents had one or more failing tests in 67 of 160 cases}}). They still failed the four-stream jump-table test more often, because their extra tests used easy cases such as four identical, trivial streams. Yossi Kreinin's explanation, which the author quotes: writing tests first pushes you towards black-box tests, before you know which parts will be hard. Getting their own tests to pass by iterating tended to make agents write incorrect tests that then enforced the incorrect behaviour ({{in the article|ar:Getting their own tests to pass more iteratively}}).

More tests did not raise coverage of the risky behaviour. Asking for the built-in Rust test framework doubled the test count at medium (25% more at xhigh) with no gain; when runs failed, it was from untested behaviour or tests that encoded the wrong answer. Kreinin again: fixed input and output tests invite you to run the code and paste its output as the expected value, where generated inputs force you to write down what correct means ({{in the article|ar:with fixed outputs you are quite likely to just encode the output}}). rstest and Insta were used as containers for ordinary unit tests; mutation testing became ordinary testing with a little hand mutation; Judgement chose ordinary unit tests and, rarely, a little fuzzing.

"Audit first" is the one process instruction that looks like the right idea. 152 of 160 runs audited and 151 changed something as a result, but mostly in the same context that made the mistake; the 42 that used an independent agent scored worse, perhaps because harder runs chose to spin one off. It had the best xhigh score (86.2%), a below-average medium score and a much higher cost, and he declines to call it better ({{in the article|ar:On average, Audit did about as well as Default}}). "Make no mistakes" scored slightly above Default and looked, at every level he examined, like random draws of Default. On IMAP it was the only condition with any fully correct run: one, at medium.
