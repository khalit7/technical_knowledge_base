How well do agents use test/verification techniques?

Dan Luu (independent) · published 7 September 2026

In one line: On one task (a Rust Zstd decoder written from the format spec by GPT-5.6 Sol in Codex, single-turn, 80 runs per condition and effort, judged by 37 hidden tests), a one-line instruction to use one of 26 testing or verification techniques, or one of four testing skills, did not measurably raise the share of fully correct runs over no instruction (63.8% at medium effort, 81.2% at xhigh); reading the runs, agents mostly applied each technique superficially, and the two largest skills raised cost by up to 41%.

How far to trust it: Believe the transcript reading and the negative result: no instruction measurably helped, and the long tutorial-style skills really did cost more. Do not read the per-technique order (TDD near the bottom, the author's own skill at the top, Default "well above average") as findings: 80 runs a side detect only gaps of about 17 to 21 points, the 30 xhigh results are as alike as 30 draws of one coin, and a condition's medium score says nothing about its xhigh score. One model, one task, and no released prompts, transcripts or tests. The evidence, judged.

read it (56 min) · discussion (191 points, 71 comments on 27 November 2026)

The idea in one sentence: telling a coding agent to use a named testing or verification technique (TDD, property-based testing, fuzzing, a model checker, a prover, a testing skill) did not make its Zstd decoder measurably more correct than saying nothing, because the agent wrote the same shallow tests it writes anyway, now inside the named tool; the differences between the 30 instructions are the size that chance alone produces.

You need: property-based testing, shrinking, fuzzing, proof and mutation testing (Testing and quality, sections 6 and 10); a verifier as an agent's stop rule (Building a harness, section 10); intervals, power and multiple comparisons (Eval statistics).

New terms: Zstd (Zstandard, a compression format; the agents wrote a decoder from its specification, RFC 8878); fully correct run (a run whose decoder passes all 37 hidden tests; the post's only correctness score); effort (Codex's reasoning-effort setting, run at medium and xhigh); condition (one prompt: the task plus one added instruction or skill, or nothing for Default); skill (a SKILL.md file of instructions an agent can load on demand); no-effect world (this page's name for what 30 conditions would look like if none changed anything: 30 draws of one pass rate).

1. One spec, 30 instructions, 80 runs each

The opening

The experiment asks what a user with no testing expertise gets by naming a technique. The task is an earlier eval of his, reused: implement a Zstd decoder in Rust from the format's RFC and errata, inside a container with no internet; the 37 tests that score it are hidden from the agent (in the article; the setup is described in the author's language comparison, where an agent also wrote the hidden tests). The agent is Codex running GPT-5.6 Sol at medium and xhigh effort, each run a single autonomous turn, every listed library installed. Each condition adds one line to the prompt, such as "Use test-driven development", "Use Lean 4" or "Use QuickCheck" (in the article):

  • Formal tools (9): Verus, Creusot and Kani (proofs and model checking on Rust code), Lean 4 and ACL2 (theorem provers), Alloy, TLA+ and Spin (model checkers for designs), SMT solvers (Z3, cvc5, Yices).
  • Randomised testing (8): property-based testing, QuickCheck, Proptest and Hegel (libraries for it), fuzzing, "audit and fuzz risky areas", metamorphic and differential testing.
  • Process (8): TDD, the built-in Rust test framework, rstest, Insta (snapshot tests), mutation testing, "audit first", Judgement (pick the best technique) and "Make no mistakes".
  • Skills (4): Hegel's official skill, a Rust testing skill from the ECC collection and Trail of Bits' property-testing skill, the top three Codex found when asked, plus a five-line skill the author wrote (in the article). And Default: no instruction.

Before running it he wrote down six guesses with confidences: TDD would underperform (55%), formal methods would not outperform (52%), "Make no mistakes" would not beat no instruction (95%), and none of the three public skills would outperform (in the article). The list and how he scored it are in the closed block at the end of section 7.

2. Nothing wildly outperforms; agents use the tool and miss the point

Overall results

The headline reading is that no instruction clearly beats saying nothing. Default does "well above average", fuzzing and property-based conditions edge out formal methods at xhigh, the three public skills underperform and TDD does badly, as he predicted (in the article). He presents one dense chart (Fig. 1 redraws it) and warns against reading strong conclusions from the order (in the article). Section "How much of this to believe" tests that order; the short answer is that the warning is right.

The finding he puts first comes from reading what the agents did, not from the scores. With a technique named, agents either wrote their usual tests inside the new framework, or used the technique for show: formal tools proved properties nobody doubted, property-based tests fed fully random inputs to one trivial property (in the article). The default he means is Gary Bernhardt's: "Take the pathological cases dreamed up by someone objecting to mocks 15 years ago, without ever having actually used mocks", then "Make those pathologies the backbone of your testing strategy" (in the article). Fig. 2 counts how often the agents did the named thing at all, and how often they did it in a form that could catch a bug.

The same held on a second spec and at higher effort. On the IMAP RFC, 40 runs per condition, results were not materially different (in the article). At xhigh the agents could nearly always make their own tests pass, but the tests were weak, for example four identical bitstreams fed to a feature that decodes four, so a decoder that swaps them passes (in the article). He asks why labs have not built RL environments that reward good testing, as they have for bounded optimisation tasks; a footnote adds that the RL papers ChatGPT pointed him to trained agents to write ordinary unit tests, and that RL for fuzzing (R1-Fuzz) exists but shows no sign of reaching the big labs' models.

3. Formal tools: proofs of what was never the bug

Verus, and the formal sections after it

No formal condition was used to prove the decoder correct; agents proved side properties and relied on ordinary Rust tests for correctness. The post's per-condition sections run from worst to best by the average of the two efforts (our recompute of the chart reproduces that order), and formal tools fill much of the bottom.

  • Verus (worst overall: 51.2% at medium, 75.0% at xhigh) was never pointed at the actual code. Agents proved few, uninteresting properties ("the index stays in bounds"), some vacuous: one proof's postcondition simply repeated its three preconditions, A implies A (in the article). The bug-prone part, reading Zstd's bitstreams backwards, went unproved, and the tests for it used palindromic inputs that read the same either way (Fig. 3, panel A).
  • Alloy modelled the format more closely and was still the second worst; its one counterexample was an 8-bit overflow that cannot happen with 64-bit sizes, so the "fix" only added complexity (in the article). Lean 4, which he expected to do well because it is fashionable for RL training, mostly proved arithmetic. Spin models had no correlation with passing the hidden tests they modelled.
  • SMT solvers became a calculator for state ranges and header arithmetic. The post's example: the count of sequences in a block is byte1 + (byte2 << 8) + 0x7F00, many agents wrote byte1 + (byte2 << 8) | 0x7F00, proved properties about the computation and kept the wrong code (in the article). Fig. 3, panel B, shows why easy tests miss it.
  • TLA+: 159 of 160 runs built a model, usually late and after the code; none changed the Rust (in the article). Kani was the one tool used on the real code, occasionally; one run in 160 caught a real bug with it, at a noticeably higher cost from re-reading its output. ACL2 often ran out of its 192 GiB memory limit; those runs were dropped from the score (15 at medium, 13 at xhigh), which biases it in an unknown direction (in the article).

His explanation is that the failures are idiosyncratic, not a property of the technique. Verus agents wrote a test for the four-stream jump table in 89 of 160 runs, the same count as Default, but their tests were more often wrong or too easy; nothing about Verus should cause that, as nothing about Clojure should cause the byte-conversion bugs his language eval found (in the article). From outside a lab, he says, it is hard to tell why.

4. Randomised testing: random inputs that all take the rejection path

QuickCheck, and the randomised sections after it

Property-based and fuzzing conditions failed in one characteristic way: fully random inputs, which a decoder rejects at once, checked against trivial properties. Random bytes are not a valid Zstd frame, so almost every generated input exercised one of a few error paths and none of the decoding logic.

  • QuickCheck: every run used it, 63 of 160 checked a single property, and agents wrote more traditional tests than Default (in the article). Hegel: the usual workflow was implement, run normal tests, then read the Hegel docs and add one to four simple property tests.
  • Fuzzing: mostly random bytes or random variations of valid inputs, both landing in rejection paths. In 10 of 160 runs agents generated structured random inputs, and those found real bugs about half the time, some non-trivial; he reads this as evidence the knowledge is there and is simply not the default (in the article).
  • "Audit and fuzz risky areas" made agents target exactly the right parts (FSE, Huffman, bit readers, state), but at medium they mostly ignored it, and where they followed it they again fed invalid random inputs and checked only for crashes. Metamorphic testing checked sensible relations (a skippable frame at a frame boundary changes nothing) in places that were not where agents erred: the drunk looking for his keys under the streetlight (in the article).
  • Differential testing (third worst): 135 of 160 runs did something by that name, none built two independent implementations, and where it might have caught a bug the agent wrote the same thing twice, bug included (in the article).
  • Proptest and the library-neutral property-based testing condition, where every agent chose Proptest, both scored well above average; tests were still mostly poor, but Proptest's shrinking (reducing a failing input to a minimal one) sometimes paid off (in the article). He finds the accidental second Proptest arm scoring well "mildly interesting".

5. Process instructions: more tests, not better tests

TDD

TDD changed behaviour more than any other instruction and made the tests worse. Agents wrote twice as many tests in a test-code-test loop; 67 of 160 runs had a failing test before writing real code, against 0 of 160 for Default (in the article). They still failed the four-stream jump-table test more often, because their extra tests used easy cases such as four identical, trivial streams. Yossi Kreinin's explanation, which the author quotes: writing tests first pushes you towards black-box tests, before you know which parts will be hard. Getting their own tests to pass by iterating tended to make agents write incorrect tests that then enforced the incorrect behaviour (in the article).

More tests did not raise coverage of the risky behaviour. Asking for the built-in Rust test framework doubled the test count at medium (25% more at xhigh) with no gain; when runs failed, it was from untested behaviour or tests that encoded the wrong answer. Kreinin again: fixed input and output tests invite you to run the code and paste its output as the expected value, where generated inputs force you to write down what correct means (in the article). rstest and Insta were used as containers for ordinary unit tests; mutation testing became ordinary testing with a little hand mutation; Judgement chose ordinary unit tests and, rarely, a little fuzzing.

"Audit first" is the one process instruction that looks like the right idea. 152 of 160 runs audited and 151 changed something as a result, but mostly in the same context that made the mistake; the 42 that used an independent agent scored worse, perhaps because harder runs chose to spin one off. It had the best xhigh score (86.2%), a below-average medium score and a much higher cost, and he declines to call it better (in the article). "Make no mistakes" scored slightly above Default and looked, at every level he examined, like random draws of Default. On IMAP it was the only condition with any fully correct run: one, at medium.

6. Skills: tutorials cost tokens; a five-line nudge did best

Hegel, and the skill sections

The three public skills read like tutorials, and they cost more without helping. Hegel's official skill (34k characters plus a 45k-character Rust reference, over 20k tokens) was loaded in 157 of 160 runs and re-read on many steps; even at a 99.85% cache hit rate this added 16% (medium) and 18% (xhigh) to the bill, and its prescribed workflow added more work on top, for a total of 26% and 41% more than Hegel without the skill. Correctness was slightly worse, within noise (in the article). The extra tests were no-panic checks and round trips of properties already likely to hold. Trail of Bits' skill was opened in only 108 of 160 runs, and its advice to add Proptest needed an approval that single-turn runs could not give.

ECC's score looks fine only because many agents ignored it. Agents read it in 153 of 160 runs, and the earlier they read it the more tests they added and the worse they did; the 7 that never read it and the 9 that read it late (nearly all at medium) were all fully correct. Scored only on runs it influenced, it falls between the built-in framework and Creusot, below average (in the article). He adds that 160 runs of a skill is more than anyone reasonable would do, and the top-line number still misleads.

His own skill scored highest, 73.8% and 83.8%, though not for the reasons it was written. Five lines: before implementing, list likely subtle mistakes and a check where the alternatives differ, using asymmetric inputs on both sides of each boundary; re-derive high-risk results in a fresh context; prefer property-based or randomised inputs but spend little on no-crash fuzzing; randomise towards interesting states; check unsure details independently (in the article). Agents almost never used a fresh context, and in medium run 35 an agent flagged the bitstream reversal as risky, audited it, and still passed a palindromic test (Fig. 3, panel A). The skill is written to push the model away from its default behaviour rather than teach it a technique, which he argues is what a skill for a model that already knows the subject should do.

His conclusion about skills is narrower than it sounds. Two further unpublished experiments with companies' official skills also made results worse; prompting style that works changes between model versions (GPT-5.5 to 5.6) and between Claude and Codex, so he doubts generic testing skills and expects to write small personal ones for one harness, model and effort. Skills that teach a workflow or an interface, such as driving a browser, look different and he expects them to work (in the article).

7. What does work: a structure, then a few sentences of steering

How do you get agents to write good tests?

His experience, not measured here, is that agents test well once a person sets up the test and triage structure and looks at what they did. He leans on randomised testing; Jamie Brandon reports the same for snapshot tests, after moving tests into a separate crate and stating in AGENTS.md that they stay there and the public interface does not change. Without that, Brandon's agents claimed to write snapshot tests and wrote unit tests. "If you look at what it does and type a few more sentences", agents get to a good place quickly; his guess is that the knowledge is in the model but far from its default, too far for naming a technique to reach (in the article).

His pre-registered guesses and how he scored them; the appendices

Predictions, as scored in the post (in the article): TDD underperforms (55%), scored true; formal methods do not outperform (52%), true, "but not for the reason I expected"; "Make no mistakes" does not beat no instruction (95%), true; the ECC, Hegel and ToB skills will not outperform (65%, 65%, 55%), all true. Two implicit guesses were wrong: Lean would do well among formal tools, and his own skill would be mediocre (Max Bittker had predicted it would work, and why). Read against the statistics in the next section, the four "will not outperform" guesses are consistent with the data; "TDD underperforms" is not established, since TDD is within chance of Default at both efforts.

IMAP details (in the article): only one run of all conditions reached a perfect IMAP score ("Make no mistakes", medium: 2.5%). TLA+, a natural fit for IMAP state, was used after coding in 75 of 80 runs, modelled a small mailbox mutation and the CONDSTORE and QRESYNC extensions (where Default already passed over 99.6% of tests) and never the observers, event queues or UIDVALIDITY epochs where the bugs were. All his evals are RFCs, whose specs are clearer than what users give agents; he expects real tasks to fail the same way or worse. Two early "compelling" results turned out to be setup errors and vanished when fixed.

Agent silliness: a subagent ran a catastrophically backtracking Perl regex over a 44 kB file for 2 hours 20 minutes after it had itself stopped; his own FRE engine and Rust's regex crate each finished in under a second. Footnotes: languages' agent-friendliness, like poker's "range advantage", is a set of nice-sounding explanations that the measured failures do not support.

How much of this to believe

What holds up: the reading of the runs, the negative result, and the cost of the big skills.

  • The transcript reading is specific and checkable in principle. Counts such as 159 of 160 TLA+ models with no change to the code, 10 structured fuzzers out of 160, and 63 single-property QuickCheck runs come from reading what the agents did, and they describe one consistent failure; the post's comment thread, and practitioners in it, report the same thing from their own work (next section).
  • "Naming a technique does not help" survives the statistics. No condition differs from Default at the 5% level by Fisher's exact test, at either effort (0 of 29 each; about 1.5 would be expected by chance alone), and the largest gain over Default, Audit's +5.0 points at xhigh (p = 0.52), is under a third of what the design can detect.
  • The cost differences are real. Cost per run varies far more between conditions than its sampling spread allows (chi-square 190 and 103 on 29 degrees of freedom, using the chart's own bootstrap spreads): the Hegel skill's +26% and +41% are 3.5 and 4.1 standard errors, Kani's +28% at medium 3.9.
  • He guards against himself. Guesses were written down first, the ordering comes with its own warning, the chart prints n and bootstrap uncertainty, and the eval's setup bugs (leaked hidden tests, uneven tooling) were found and fixed before the language results were trusted.
Predict before you draw: suppose no instruction mattered at all, so every condition's 80 xhigh runs pass with the same 77.5% chance. How far apart would the best and the worst of the 30 land: about 3 points, about 8, or about 18? Then press "Draw a no-effect world" beside this text.

What it does not show.

  • The order of the 30 conditions is mostly noise, and the post's sections follow it. With 80 runs a side, a difference from Default has to be about 21 points at medium and 17 at xhigh to be detected four times in five. At xhigh the 30 conditions are as alike as 30 draws of one 77.5% coin (chi-square 22.6 on 29 degrees of freedom, p = 0.80), and their 17.5-point spread is what such draws give on average (18.8); every condition with 80 runs sits inside the range where 95% of single no-effect conditions land, 67.5% to 86.3% at xhigh (all 29 conditions). At medium the spread is a little wider than chance (p = 0.04; 23.8 points against 21.8 expected) and the band, 52.5% to 73.8% at medium (27 of 29 inside, Verus below and Fuzz risky above), misses two; but no single condition stands out once 29 comparisons are corrected for.
  • A condition's medium score does not predict its xhigh score (correlation −0.03 across the 30; Fig. 5). If instructions had stable effects, the same ones would lead at both efforts; Fuzz risky going from 1st of 30 at medium to 25th at xhigh, and ECC from 5th to 28th, is what pure noise looks like.
  • So the per-technique verdicts are not established: TDD "underperformed" (−7.5 points at xhigh, p = 0.34), Default did "well above average" (15th of 30 at medium, 6th at xhigh), Proptest and PBT scored "well above average", his skill was best. His prediction scorecard counts "TDD underperforms" as true on this evidence.
  • One model, one harness, one task, single turns. GPT-5.6 Sol in Codex on a bit-manipulation decoder with a precise spec. His follow-up shows how fast this moves: with GPT-6 Astra the same eval is saturated and agents use several techniques properly. Commenters note Claude is more eager with property-based tests.
  • Nothing is released. No prompts (the exact wording of each condition, or of "audit"), transcripts, hidden tests or scoring code, so the counts from reading runs cannot be checked and nobody can rerun a condition. The 37 hidden tests were written by an agent, and the score counts only runs passing all of them. ACL2 dropped 28 runs that ran out of memory. The post could not be compared with an archived copy: the blog is not in the Wayback Machine.

Verdict. Believe the qualitative finding: a bare instruction to use a technique produced a caricature of it, and long tutorial skills cost more for nothing. Believe the negative result in its narrow form: on this task, no instruction measurably beat saying nothing. Treat every per-technique ranking, including TDD's and the author's skill's, as unmeasured; the design could not have seen differences under about 17 points.

The rank test in one picture. Each condition is a dot at its medium score (across) and its xhigh score (up). Effects that belong to the instruction would line the dots up from lower left to upper right; the cloud has no slope at all (correlation −0.03, p = 0.87). The author saw something related: results at max and xhigh were highly correlated with each other and quite different from medium (in the article), which fits effort changing behaviour more than the instruction does; the max runs are not published.

What the responses said

The Hacker News thread (191 points, 71 comments on 27 November 2026) agreed with the finding and objected to the method's opacity; the one tool author who replied agreed his skill was weak and rewrote it. No rebuttal with its own measurements was found. Practitioners' reports point the same way as the post: formal tools help when a person writes the specification, mutation testing helps when it gates the build, and fresh-context review is where they spend their tokens.

  • tool author"The Hegel skill sortof sucks right now"
    David R. MacIver (Hypothesis and Hegel author), X, 7 September 2026

    Agreed the skill was weak and blamed agent-written skills in general; the post's appendix quotes him. The skill's repository was cut to "a near-empty core" on 8 September and released as version 2.0.0 on 17 September. In the author's later Pandoc runs both the old and the new skill still cost more than Hegel alone, with similar correctness.

  • critiqueWithout the prompts, nothing can be reproduced
    gregwebs, genxy, FranciscoCarlos and luckydata, Hacker News, 8 September 2026

    Asked for the exact prompts, the Audit instruction and the harness so others could rerun their own workflows; one called the result "essentially devoid of any value" without them. Right on the facts: no prompts, transcripts, tests or scoring code are public. jakevoytko replied with a list of what makes such benchmarks hard to publish at all.

  • practitioner reportLeft alone, the agent's Verus spec restates the implementation
    emtel, Hacker News, 8 September 2026

    Agrees with the Verus finding and adds the case the post did not test: once a person had worked out an accurate specification, Claude proved the code against it without trouble and found real bugs. gz09 and gr_norm made the same point: a formal tool helps when a person writes the spec.

  • critiqueMutation testing as a build gate cannot be skipped
    vetronauta, kqr and coder-pm, Hacker News, 8 September 2026

    The agents did mutation testing by hand; a mutation tool wired into the build, failing it when mutants survive, is something an agent cannot quietly skip. The post tested the instruction, not the gate; coder-pm reports a gate catching a test that passed on both the fixed and the mutated code.

  • critiqueTesting cannot be separated from how the code is built
    siscia and sceptic123, Hacker News, 8 September 2026

    Most of effective testing is architecture (dependency injection, sans-IO), and one-shot greenfield runs with a bare instruction do not answer the title's question. yorwba answered with the post's own framing: it tests a user with no testing expertise who names a technique.

  • practitioner reportAlloy fell on its face against fuzzing in a real project
    lmeyerov, Hacker News, 8 September 2026

    Longer-running use on a GPU graph-query engine agrees in direction: Alloy did badly against fuzzing even with guidance; guided fuzzing, written specifications next to the code and fresh-context adversarial review worked; one-shot auto-written skills evaluated badly.

Where the responses are right. The reproducibility complaint is correct and is part of the verdict. The specification and gate points are fair limits of scope rather than errors: the post tests what a bare instruction does, as its first paragraph says, and the follow-up shows that a stronger model starts to use the techniques properly on its own.

Where it moves the knowledge base

  • Testing and quality, section 13 (AI-written changes): extends "check the tests would fail if the code were wrong" with measured evidence that an agent's own tests are the weak point: told to use a technique, agents wrote palindromic or identical inputs and expected values copied from their own output; property-based tests and fuzzers fed rejected random bytes.
  • Building a harness, the verifier as stop rule: a verifier the agent writes itself is only as strong as its tests; at xhigh agents nearly always got their own tests to pass while 14% to 31% of runs, depending on the condition, still failed hidden tests.
  • Eval statistics: a worked case of a 30-way comparison at 80 runs a side, where the spread of the arms equals what one shared rate produces, and of the medium-against-xhigh rank check.
  • Claude Code on skills and the Demystifying Agent Skills paper page: a long tutorial skill re-read on every step costs 16% to 18% of the bill even at a 99.85% cache hit rate, and loading is not use (157, 153 and 108 of 160 runs).
