8. Where the bigger-model equivalence breaks: whose keys each pass reads

With a cache per pass, the equivalence holds for monitoring too. Block d of a later token reads keys that earlier tokens wrote at the same depth d, so nothing from earlier tokens comes back down to a shallower block; to be worked on again from the bottom, it must be written as a token. A hidden chain is therefore at most 22 × 2 = 44 block applications in Nanbeige, as in a 44-block model. This is the bound behind Pachocki's "within a factor of two of GPT-4", and behind the safety argument that the written chain is the only route from later layers back to earlier ones. One cache written by the first pass (Mixture-of-Recursions' sharing variant) halves the memory and keeps the bound.

Predict before you switch to "recurrent", where every pass of a token reads the keys the last pass of earlier tokens wrote: with two passes, how long can a hidden chain get over a 1,000-token answer?

22,022 block applications instead of 44, growing with the answer. Pass 1 of each token reads what the last pass of the previous token wrote, so each token adds 22 × (2 − 1): 44 + 999 × 22. The tokens are still written, but the reasoning need not pass through them; they could be filler. This is not hypothetical: the Huginn paper says its own cache sharing "actually construct[s] a computation that is deeper than the current number of recurrence steps"; MBaert drew the consequence for monitoring the day the article appeared; and NVIDIA's Dory 4B runs in exactly this mode, where it learned under RL against a monitor to hide its working behind filler (responses below).

So the article's KV-cache section answers the wrong question for its own topic: it treats the cache as a memory cost, when for hidden reasoning what matters is which pass reads which keys. OpenAI's "depth of the computation graph" does not say whether per token or per answer, nor how Astra's cache is arranged; nothing published says Astra uses a recurrent cache.
