How much of this to believe

The mechanism and its exactness hold up, and the evidence is unusually good for a blog post. The RAM claim is three lines of linear algebra (section 2, and the toy reproduces it). The CPU is checked the way processors are: the official compliance suites, a diff of 61 programs against qemu, random-program fuzzing, and more than 19 million instructions run free on the GPU with every generated token required to equal the reference trace. During the benchmark runs a lockstep check compares every circuit token with a reference machine and stops at the first difference (it checks; it does not correct), and it never fired. Code, weights and the design log with every measurement are public, and the post's own limits paragraph names the size, the driver and the speed.

Where the post says more than its evidence:

  • One bar is from another model. The NUPA 48.6% to 100% result is the CHIP-8 version's (576 problems, best mode per benchmark across development checkpoints), shown on this model's chart after its version label was removed (section 6). The RISC-V model has no NUPA number.
  • Small single runs, reported without intervals. Four or five sets of 40 problems, one greedy run each; a McNemar column was added to the README and removed the same day, and the base column moved by 3 to 4 problems between two runs. What the numbers support is parity with the same tool on the host, which is what an exact calculator should give, and a gain over a tool-less base where the arithmetic is big. They cannot rank Qwenputer against the host tool, and the post does not quite claim to.
  • The chosen rows. The chart shows mul_div_multiple_longer after a firmware fix (before it, base Qwen led 36 to 20) and leaves out the synthetic set and add_sub_multiple_longer, where it adds nothing. The fix is fair; showing the rows with no gain would have been fairer.
  • "No runtime", "not a tool". No host code computes an answer, and that is the real result. But Qwen reaches the CPU through a tool call, and the RISC-V model needs a custom driver that boots the CPU from a state snapshot, routes the trace tokens past Qwen's layers and, in the measured runs, executes the compiled layers with a separate Triton implementation (checked bit-equal on 6 records). The Hacker News critique of the framing is right; the post states the driver itself, but only under its limits.
  • "Its own Gated DeltaNet layers". The RAM lives in 11 new layers of Qwen3.5's layer type, not in Qwen's 24 pretrained DeltaNet layers, which are untouched. The point the post makes, that no new layer type was needed, holds.
  • MicroPython has run on the standalone core, not yet in the released model (section 4).

Verdict. Believe the mechanism and the exactness: they are demonstrated, reproducible and checked far beyond what the post shows. Read the benchmarks as "an exact calculator in the weights works as well as the same calculator on the host, on small sets", with the NUPA bar set aside, and read "no runtime" as "nothing outside the weights computes the answer". As a practical way to do arithmetic it is slower and twice the size of a model with a tool, which the post does not dispute; its value is as a demonstration and a testbed.
