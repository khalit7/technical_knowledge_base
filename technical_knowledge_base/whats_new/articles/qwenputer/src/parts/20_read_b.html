1. A CPU compiled into the weights, not a tool

[[ah:i-can-t-believe-it-s-not-silicon|I can't believe it's not silicon]]

The claim is an artefact, not a method: a stock Qwen3.5-4B with {{a RISC-V CPU embedded within the weights|ar:a RISC-V CPU embedded within the weights}}, which keeps its memory in Gated DeltaNet state and runs arithmetic, C and MicroPython {{without any external runtime or tool usage whatsoever|ar:without any external runtime or tool usage whatsoever}}; the post insists {{it is not a plugin, a tool or a sandbox|ar:it is not a plugin, a tool or a sandbox}}. Everything is released: the code (MIT), the checkpoint on Hugging Face and ModelScope (Apache-2.0, as a modified Qwen), and a design log with every measurement. Two of those words need care, and sections 5 and "How much of this to believe" come back to them: "own" (the RAM is in new layers of Qwen's layer type, not in Qwen's pretrained ones) and "runtime" (a driver is needed).

2. A Gated DeltaNet head is exact RAM when its gate and write strength are 1 and its keys are one-hot

[[ah:the-rnn-inside-qwen3-5-can-be-exact-ram|The RNN inside Qwen3.5 can be exact RAM]]

Qwen3.5 already carries the memory hardware. {{3 out of 4 attention layers|ar:3 out of 4 attention layers}} are Gated DeltaNet: in Qwen3.5-4B, 24 of 32 layers, each with 16 key heads and 32 value heads, every value head keeping a 128 × 128 state matrix that does not grow with the context (config, read 27 November). Our owner page teaches the update ({{Beyond attention|n:3fd5c17b0d0d8142bc9ecac1fc366966}}, section 3). In the row convention of the post's own figure, with state S, key k, value v, gate α and write strength β:

S ← α S, then S ← S + β k (v − STk)T; a read is o = STq.

Pin three things and the update becomes a memory write. With α = 1 nothing fades (the post: {{by setting the gate to 1|ar:by setting the gate to 1}}); with k = er one-hot, STk is exactly row r, so the correction v − STk removes the old row and, at β = 1, writes v in its place; every other row is multiplied by a zero entry of k and untouched. So {{every write we perform will overwrite exactly one row|ar:every write we perform will overwrite exactly one row}}, and a one-hot query returns that row. The steps on the right run a small program through it:

  1. Empty. All eight addresses hold zero.
  2. Write 0x2A to address 3. The key picks row 3, the value is the byte's bits (00101010); the row held zero, so the whole value is written.
  3. Write 0xC5 to address 4. Row 4 fills; row 3 is untouched because its key entry is 0.
  4. Overwrite address 3 with 0x71. The rule first reads what row 3 holds (0x2A's bits) and writes only the difference, so the row becomes 01110001; at β below 1 a share 1 − β of the old byte stays in.
  5. 40 tokens pass with no write. Write strength 0, but the gate multiplies the whole state by α on every token: at α = 0.98 each stored 1 becomes 0.9840 = 0.446, below the threshold.
  6. Read addresses 3 and 4. A one-hot query returns one row; the readout decodes its bits.

Predict before you move anything: with β = 0.9 instead of 1, what does address 3 return after the overwrite with 0x71? (Drag β once the steps have played; the readout at the last step gives the answer, and the closed block below explains it.)

How Qwenputer pins them in real weights. β is a sigmoid of a projection, so the circuit sets it to sigmoid(256g − 128) with g ∈ {0, 1}, which rounds to exactly 0 or 1; α stays 1, except that α = 0 for one token wipes a head and α = ½ turns a head into a counter. The post is right that {{default Qwen 3.5 does not keep exact values in the GDN|ar:default Qwen 3.5 does not keep exact values in the GDN}}: trained gates and write strengths sit below 1 and trained keys overlap (switch the toy to overlapping keys: the last-written address still reads exactly, the other one does not). It credits the idea of the delta rule as associative memory to Schlag et al. 2021 and claims as new {{making it exact and addressable, inside a production model|ar:making it exact and addressable, inside a production model}}, which is a fair line.

"Far cheaper than attention" is about memory, not possibility. The post says GDN works as RAM {{at a far lower cost than using normal attention as RAM|ar:at a far lower cost than using normal attention as RAM}}. Attention can store and look up exact values too (a Hacker News reader made the point, section on responses); its KV cache grows with every write, while a head's state stays 128 × 128. The CPU's memories (code ROM 256 KB, read-only data 128 KB, RAM 32 KB, registers, program counter) fit in a few dozen such heads: the low bits of an address pick the head, the rest the row, and each key head drives two value heads.

The β = 0.9 answer, and how exact "exact" is in bf16 (depth)

β = 0.9. The overwrite writes only 90% of the difference, so row 3 becomes 0.9 × 0x71's bits + 0.1 × 0x2A's bits: bits where both bytes have a 1 read 0.99, bits only the new byte has read 0.9, bits only the old byte had read 0.09, and the other write (0xC5 into an empty row) reads 0.9 everywhere it should read 1. The byte still decodes correctly at a 0.5 threshold, but it is a blend, and a CPU reading the same cell millions of times cannot afford one: errors would compound through every instruction that uses it.

Numerics, from the design log (docs/rv32.md, P0.2, on an NVIDIA L4 with flash-linear-attention 0.5.2): in bf16, the model's dtype, every circuit dimension matched the reference at every position in 18 runs, through both the chunked prefill kernel and the token-by-token one. In fp32 the tokens were still all right, but 70 to 400 dimensions per run were off by one unit in the last place, from the kernels' 1/√128 query scale and the chunk kernel's exponentiated cumulative decays; the circuit's thresholds absorb that. A first design that read 8 rows at once left residues of 2 × 10−8 through the kernels, so every read is now one-hot or two-hot (the code ROM's).

3. A compiler, not training, sets every weight

[[ah:compiling-a-computer-into-layers|Compiling a computer into layers]]

No weight is learned. {{there's no training involved: a compiler sets every weight directly|ar:there's no training involved: a compiler sets every weight directly}}. The CPU is written as a circuit of small steps (read a register, add two numbers, jump if zero); the compiler places each step in a sublayer: DeltaNet heads for every lookup and memory, SwiGLU MLP units for the arithmetic, as exact threshold and lookup tables. All 11 compiled layers are Qwen3.5's linear-attention layer type (the merged config lists 14 linear layers before the first full-attention layer: the 11 compiled ones and Qwen's first three), so the post's "attention heads that look things up" are DeltaNet heads too. The table on the right is where each part of the CPU sits.

The CPU writes its own memory through the tokens it generates. {{Each instruction becomes a few generated tokens|ar:Each instruction becomes a few generated tokens}}: each generated trace token is one write into the DeltaNet RAM, so the trace is the execution log, and the CPU runs while the model decodes. The post's ADDR, VAL, STEP picture is a simplification: the real format packs one record per instruction (a 1 to 3 token value record for a register write, one token for a jump or a not-taken branch, a store token), with the program counter implied, for 1.0 to 1.55 tokens per instruction on compiled C (design log, P1 and P2). Information only flows down the layers through tokens, which is why the counter is implied rather than written.

4. The CPU: RV32IM with Zba and a bignum unit, checked against qemu

[[ah:the-cpu|The CPU]]

A full 32-bit integer RISC-V core in 11 layers. {{it takes up 11 layers in front of Qwen's 32|ar:it takes up 11 layers in front of Qwen's 32}}: RV32IM with hardware divide, the Zba address extension and a custom digit-file unit for numbers up to 128 decimal digits, in 2,679 dimensions, 99 heads, 42,012 MLP units and 1,040,595 nonzero weights (design log, P2). Eleven is the depth of the longest dependency chain (divide's comparison signs at layer 10, the output at 11), so rescheduling cannot remove a layer.

The checks are a CPU designer's, and the post understates them. {{it passes the official riscv-tests, its programs match qemu|ar:it passes the official riscv-tests, its programs match qemu}}: rv32ui (38 tests), rv32um (8) and rv32uzba (3) pass; 61 compiled programs give qemu's exit code and output; and the core has run programs free-running on the GPU (generating every token itself, each required to equal the reference trace): 4.05 million instructions in phase 1 and 15.3 million in phase 2, including 10,000 random calc cases (8.95 million instructions in 19 minutes). The repository rounds this to "about 18M", the post to 18 million.

MicroPython ran on the core, not yet inside Qwen. The post says the CPU runs {{run C and MicroPython code in the forward passes|ar:run C and MicroPython code in the forward passes}}. The design log's MicroPython runs (print(2**100) in 39,888 instructions, an 18-line script in 492,526) are on the standalone core and its executor; its list of what phase 3 did not do says MicroPython "has run on the standalone core and executor (P2), not yet inside the merged model". In the released Qwenputer, the firmware is calc, written in C.

5. Qwen calls it through its tool-call format, with a driver in the loop

[[ah:how-qwen-uses-it|How Qwen uses it]]

No fine-tuning: the CPU borrows a format Qwen already knows. Qwen uses it {{without any post-training required|ar:without any post-training required}}, by {{piggybacking on the tool call format|ar:piggybacking on the tool call format}}: the prompt lists a calc tool, Qwen writes a normal tool call, and nothing on the host executes it. The compiled "bridge" copies the call's tokens into memory at 0x8000 (up to 80 tokens), </tool_call> starts the program, and every byte the firmware prints comes out as the matching Qwen token, so the <tool_response> is predicted by the model itself (the figure at the top). The firmware evaluates integers and decimals up to 62 digits, exact fractions since its second version, and returns "error (too complex: split it)" or "error (too long: split it)" past its limits. {{Qwen's original weights stay exactly as they are|ar:Qwen's original weights stay exactly as they are}}: the CPU's weights sit in the extra layers and extra dimensions.

"No runtime" means no host computes the answer, not "plain generate()". The post says {{No external tool calls or runtime are used|ar:No external tool calls or runtime are used}} and, in the next breath, {{We use a small driver called RvChat|ar:We use a small driver called RvChat}}. The driver does three things the design log describes: it injects a snapshot (firmware, RAM, registers) into the compiled layers' DeltaNet states after the prompt; it sends each trace token through the 11 compiled layers only, so Qwen's layers never see it; and, in the benchmark runs, it replaces those layers' Hugging Face modules with a Triton "executor" that computes the same circuit in fp32, 13 times faster (3,200 trace tokens a second on an L4), checked bit-for-bit equal to the modules on 6 records. The answer is still computed by the compiled circuit, not by Python on the host; the earlier CHIP-8 version, by contrast, ran under stock generate() with a boot record prepended.

6. Does it work: as well as the same tool run on the host, on 40-problem sets

[[ah:does-it-work|Does it work?]]

On DeepMind's arithmetic sets Qwenputer matches the host tool and beats base Qwen where arithmetic is hard. The post reports four sets, 40 problems each, greedy decoding, one run: {{mul_big: Qwenputer scores 97.5%|ar:mul_big: Qwenputer scores 97.5%}} against 55% for base Qwen (22/40) and 100% for Qwen with a tool; {{div_big: Qwenputer scores 97.5%|ar:div_big: Qwenputer scores 97.5%}} against 72.5% and 95%; 100% on mul_div_multiple_longer against 90% and 97.5%; 97.5% on add_or_sub_big against 87.5% and 97.5%. The "Python tool" is base Qwen with the same calc tool answered on the host in the firmware's exact format (Python, or for the re-run sets the firmware itself on a reference machine), which makes it a like-for-like control. Against it, Qwenputer is never more than one problem away, and the chart's 95% intervals show 40 problems cannot separate them; against base Qwen, the gap is clear on mul_big and div_big and within noise on add_or_sub_big.

The NUPA bar is from a different model. {{On NUPA's long-integer arithmetic, Qwenputer goes from 48.6% to 100%|ar:On NUPA's long-integer arithmetic, Qwenputer goes from 48.6% to 100%}}: that is the CHIP-8 version's result on 576 problems, whose table also says its numbers are "the best mode per benchmark across our development checkpoints". The repository's commit of 22 October labelled the bar "NUPA from the CHIP-8 version", and the next commit removed the label; the RISC-V table has a synthetic integer set instead (75% to 97.5%, the same as the tool), which the post leaves out.

Its misses are Qwen's, and "exact" means the circuit matches its reference. {{I replayed about 230,000 of its output positions|ar:I replayed about 230,000 of its output positions}}: every position the circuit owns, re-run in the reference evaluator, with zero wrong predictions. The misses in the table are Qwen's: re-checking a correct result, dropping a sign, a 44-call loop. Normal text is unchanged within noise ({{KL 6e-4, against a noise floor of 5e-4|ar:KL 6e-4, against a noise floor of 5e-4}}; 6.1 × 10−4 against 5.1 × 10−4 on 16 prompts, the floor being base Qwen's own two attention kernels; greedy text identical on 10 of the 16).

The row the chart hides, and the base column's re-run (depth)

mul_div_multiple_longer first went the other way. With the first firmware, which allowed a fraction only as the final value, 610 of Qwen's 1,040 calls returned an error and Qwen retried in loops: Qwenputer 20/40, the host tool 19/40, base Qwen 36/40. The second firmware (exact fractions throughout) fixed the tool, and the re-run gives 40/40 and 39/40. The fix is legitimate; the post's chart shows only the re-run. One more DeepMind set the log ran, add_sub_multiple_longer (40, 40 and 39 of 40), shows no gain and is not in the post.

The base column moved. On 19 October the README's base column read 65.0, 80.0 and 95.0 for mul_big, div_big and add_or_sub_big, with a McNemar p of 1.0 for the last; the column was dropped the same day, and on 21 October the base runs were redone on the same problems with a 4,096-token budget and a "do every step exactly" system line, giving 55.0, 72.5 and 87.5 (synthetic arithmetic rose from 70.0 to 75.0). A matched re-run is the right comparison; the shift of 3 to 4 problems per set between two base runs is also a fair measure of how much one 40-problem run can move.

Speed. On an L4 at batch 1, a calc call is 1,300 to 3,000 trace tokens, about 0.5 to 1 s on the executor; Qwen's own text tokens (about 68 ms each) take most of the time; a mul_div problem took a median of 242 s. On an A10G at batch 8: 109 mul_div problems an hour. A host tool answers in milliseconds.

7. A filesystem in the same RAM

[[ah:a-hard-drive-in-this-economy|A hard drive? In this economy?]]

Files persist across chats by saving the DeltaNet state. A second checkpoint adds five more tool names (put, append, get, list, delete) that the compiled layers answer: they {{hash its name into one of 1,024 slots|ar:hash its name into one of 1,024 slots}} of a directory in DeltaNet state (probing the next slot on a collision, two or three trace tokens a lookup) and store the text eight tokens to a row; it {{holds up to 512 files|ar:holds up to 512 files}}, about 53,000 tokens. Save those heads at the end of a session and load them at the start of the next, and the files are there. On the model card's synthetic LongMemEval-style test (four past sessions mention eight facts about the user and change two), Qwen gets {{facts that changed between chats right 90% of the time|ar:facts that changed between chats right 90% of the time}} (27 of 30) against 30.0% for base Qwen with the old chats pasted back in (which scores 76.7% on all facts) and 83.3% with the same tools on the host; on all 90 questions, 83.3% against 78.9% for the host tools. It is 12 compiled layers, hidden size 4,608, 22.3 GB, and its code is on a separate branch.

8. Limits: twice the size, a driver, and slow

[[ah:limits-and-what-s-next|Limits and what's next]]

The post states its costs plainly. The widened layers {{make the checkpoint 18.8 GB, roughly double base Qwen|ar:make the checkpoint 18.8 GB, roughly double base Qwen}} (mostly zeros, since a standard checkpoint gives every layer the same width); the driver means {{it doesn't run with a plain generate() call yet|ar:it doesn't run with a plain generate() call yet}}; and every instruction costs decoded tokens, so the benchmark executor {{runs about 3,200 CPU tokens a second on an L4|ar:runs about 3,200 CPU tokens a second on an L4}}. Next on its list: Qwen writing Python for the MicroPython inside its weights, and a faster CPU (the repository has since moved on both; the dated block below).

9. Beyond arithmetic: a testbed for safety work

[[ah:beyond-arithmetic|Beyond arithmetic]]

Exact control of recurrent state is the reusable part. The post closes by calling the model {{a really nice testbed for AI safety research|ar:a really nice testbed for AI safety research}} and links two follow-ups published the same day (Further reading): one shows a hybrid model fine-tuned to answer with no visible reasoning can learn to track state silently in its recurrent layers when its write strength may exceed 1 (OLMo-Hybrid, up to 2) but not when it is capped at 1 (Qwen3.5); the other compiles a lie-probe trigger and a tamper-proof log into the weights.
