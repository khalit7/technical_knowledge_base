Qwenputer: a fully functioning, deterministic RISC-V CPU inside Qwen3.5

Divyansh Agrawal (independent) · published 22 October 2026

In one line: In one blog post with released code and weights, a compiler sets the weights of 11 extra layers (about 1M nonzero weights) in front of an unchanged Qwen3.5-4B so that Gated DeltaNet heads, with gate 1, write strength 1 and one-hot keys, act as exact RAM for a RISC-V (RV32IM) CPU. Qwen calls it through its tool-call format; on four 40-problem DeepMind arithmetic sets (greedy, one run each) it lands within one problem of base Qwen given the same tool answered on the host, and above base Qwen without tools (mul_big 97.5% against 55%). It runs through a custom driver, not plain generate(), and the post's NUPA 100% figure is from the earlier CHIP-8 version.

How far to trust it: Believe the mechanism and its exactness: the RAM trick is plain linear algebra, and the released code checks the circuit against riscv-tests, qemu and a reference machine over millions of instructions. Read the benchmarks as parity with a host-side tool on small sets, with one bar from a different model, and read "no runtime" as "nothing outside the weights computes the answer": a custom driver boots the CPU, routes its trace tokens past Qwen and, in the measured runs, executes the compiled layers with a Triton re-implementation checked bit-equal to them. The idea in one sentence: a Gated DeltaNet head whose gate is held at 1, whose write strength is 1 and whose keys are one-hot stores and returns values exactly, like a RAM, so a compiler can write a whole RISC-V CPU into 11 extra layers in front of an unchanged Qwen3.5-4B, and Qwen can hand it arithmetic through its usual tool-call format.

What the post is. A short build report (9 minutes) by an independent developer, with the code, both checkpoints and a long design log released. Its claims are about one artefact: what the compiled layers do, how exactly, and what they add to Qwen on arithmetic. This page follows the post in its order, runs the RAM trick live in section 2, and then checks the claims against the released design log and the repository's history: most hold, one chart bar comes from a different model, and "no runtime" needs a qualifier.

You need: the delta rule and its gate (Beyond attention, sections 3 and 6: the update this post pins to 1); residual stream, attention and MLP sublayers (The transformer from zero); Qwen3.5's 3:1 hybrid of Gated DeltaNet and attention (Alibaba: Qwen).

New terms: one-hot key (all zeros except a single 1: it picks one row of the state, like an address); compiled weights (weights computed by a program from a circuit description, not learned); RV32IM (the 32-bit RISC-V base integer instruction set plus multiply and divide); trace token (a token the CPU generates for itself, one record per instruction, which is how its writes reach memory); free-running (the CPU continues on its own generated tokens with no reference machine correcting it); RvChat (the author's decoding driver that boots the CPU and keeps its trace tokens out of Qwen's layers).

1. A CPU compiled into the weights, not a tool

I can't believe it's not silicon

The claim is an artefact, not a method: a stock Qwen3.5-4B with a RISC-V CPU embedded within the weights, which keeps its memory in Gated DeltaNet state and runs arithmetic, C and MicroPython without any external runtime or tool usage whatsoever; the post insists it is not a plugin, a tool or a sandbox. Everything is released: the code (MIT), the checkpoint on Hugging Face and ModelScope (Apache-2.0, as a modified Qwen), and a design log with every measurement. Two of those words need care, and sections 5 and "How much of this to believe" come back to them: "own" (the RAM is in new layers of Qwen's layer type, not in Qwen's pretrained ones) and "runtime" (a driver is needed).

2. A Gated DeltaNet head is exact RAM when its gate and write strength are 1 and its keys are one-hot

The RNN inside Qwen3.5 can be exact RAM

Qwen3.5 already carries the memory hardware. 3 out of 4 attention layers are Gated DeltaNet: in Qwen3.5-4B, 24 of 32 layers, each with 16 key heads and 32 value heads, every value head keeping a 128 × 128 state matrix that does not grow with the context (config, read 27 November). Our owner page teaches the update (Beyond attention, section 3). In the row convention of the post's own figure, with state S, key k, value v, gate α and write strength β:

S ← α S, then S ← S + β k (v − STk)T; a read is o = STq.

Pin three things and the update becomes a memory write. With α = 1 nothing fades (the post: by setting the gate to 1); with k = er one-hot, STk is exactly row r, so the correction v − STk removes the old row and, at β = 1, writes v in its place; every other row is multiplied by a zero entry of k and untouched. So every write we perform will overwrite exactly one row, and a one-hot query returns that row. The steps on the right run a small program through it:

  1. Empty. All eight addresses hold zero.
  2. Write 0x2A to address 3. The key picks row 3, the value is the byte's bits (00101010); the row held zero, so the whole value is written.
  3. Write 0xC5 to address 4. Row 4 fills; row 3 is untouched because its key entry is 0.
  4. Overwrite address 3 with 0x71. The rule first reads what row 3 holds (0x2A's bits) and writes only the difference, so the row becomes 01110001; at β below 1 a share 1 − β of the old byte stays in.
  5. 40 tokens pass with no write. Write strength 0, but the gate multiplies the whole state by α on every token: at α = 0.98 each stored 1 becomes 0.9840 = 0.446, below the threshold.
  6. Read addresses 3 and 4. A one-hot query returns one row; the readout decodes its bits.

Predict before you move anything: with β = 0.9 instead of 1, what does address 3 return after the overwrite with 0x71? (Drag β once the steps have played; the readout at the last step gives the answer, and the closed block below explains it.)

How Qwenputer pins them in real weights. β is a sigmoid of a projection, so the circuit sets it to sigmoid(256g − 128) with g ∈ {0, 1}, which rounds to exactly 0 or 1; α stays 1, except that α = 0 for one token wipes a head and α = ½ turns a head into a counter. The post is right that default Qwen 3.5 does not keep exact values in the GDN: trained gates and write strengths sit below 1 and trained keys overlap (switch the toy to overlapping keys: the last-written address still reads exactly, the other one does not). It credits the idea of the delta rule as associative memory to Schlag et al. 2021 and claims as new making it exact and addressable, inside a production model, which is a fair line.

"Far cheaper than attention" is about memory, not possibility. The post says GDN works as RAM at a far lower cost than using normal attention as RAM. Attention can store and look up exact values too (a Hacker News reader made the point, section on responses); its KV cache grows with every write, while a head's state stays 128 × 128. The CPU's memories (code ROM 256 KB, read-only data 128 KB, RAM 32 KB, registers, program counter) fit in a few dozen such heads: the low bits of an address pick the head, the rest the row, and each key head drives two value heads.

The β = 0.9 answer, and how exact "exact" is in bf16 (depth)

β = 0.9. The overwrite writes only 90% of the difference, so row 3 becomes 0.9 × 0x71's bits + 0.1 × 0x2A's bits: bits where both bytes have a 1 read 0.99, bits only the new byte has read 0.9, bits only the old byte had read 0.09, and the other write (0xC5 into an empty row) reads 0.9 everywhere it should read 1. The byte still decodes correctly at a 0.5 threshold, but it is a blend, and a CPU reading the same cell millions of times cannot afford one: errors would compound through every instruction that uses it.

Numerics, from the design log (docs/rv32.md, P0.2, on an NVIDIA L4 with flash-linear-attention 0.5.2): in bf16, the model's dtype, every circuit dimension matched the reference at every position in 18 runs, through both the chunked prefill kernel and the token-by-token one. In fp32 the tokens were still all right, but 70 to 400 dimensions per run were off by one unit in the last place, from the kernels' 1/√128 query scale and the chunk kernel's exponentiated cumulative decays; the circuit's thresholds absorb that. A first design that read 8 rows at once left residues of 2 × 10−8 through the kernels, so every read is now one-hot or two-hot (the code ROM's).

3. A compiler, not training, sets every weight

Compiling a computer into layers

No weight is learned. there's no training involved: a compiler sets every weight directly. The CPU is written as a circuit of small steps (read a register, add two numbers, jump if zero); the compiler places each step in a sublayer: DeltaNet heads for every lookup and memory, SwiGLU MLP units for the arithmetic, as exact threshold and lookup tables. All 11 compiled layers are Qwen3.5's linear-attention layer type (the merged config lists 14 linear layers before the first full-attention layer: the 11 compiled ones and Qwen's first three), so the post's "attention heads that look things up" are DeltaNet heads too. The table on the right is where each part of the CPU sits.

The CPU writes its own memory through the tokens it generates. Each instruction becomes a few generated tokens: each generated trace token is one write into the DeltaNet RAM, so the trace is the execution log, and the CPU runs while the model decodes. The post's ADDR, VAL, STEP picture is a simplification: the real format packs one record per instruction (a 1 to 3 token value record for a register write, one token for a jump or a not-taken branch, a store token), with the program counter implied, for 1.0 to 1.55 tokens per instruction on compiled C (design log, P1 and P2). Information only flows down the layers through tokens, which is why the counter is implied rather than written.

4. The CPU: RV32IM with Zba and a bignum unit, checked against qemu

The CPU

A full 32-bit integer RISC-V core in 11 layers. it takes up 11 layers in front of Qwen's 32: RV32IM with hardware divide, the Zba address extension and a custom digit-file unit for numbers up to 128 decimal digits, in 2,679 dimensions, 99 heads, 42,012 MLP units and 1,040,595 nonzero weights (design log, P2). Eleven is the depth of the longest dependency chain (divide's comparison signs at layer 10, the output at 11), so rescheduling cannot remove a layer.

The checks are a CPU designer's, and the post understates them. it passes the official riscv-tests, its programs match qemu: rv32ui (38 tests), rv32um (8) and rv32uzba (3) pass; 61 compiled programs give qemu's exit code and output; and the core has run programs free-running on the GPU (generating every token itself, each required to equal the reference trace): 4.05 million instructions in phase 1 and 15.3 million in phase 2, including 10,000 random calc cases (8.95 million instructions in 19 minutes). The repository rounds this to "about 18M", the post to 18 million.

MicroPython ran on the core, not yet inside Qwen. The post says the CPU runs run C and MicroPython code in the forward passes. The design log's MicroPython runs (print(2**100) in 39,888 instructions, an 18-line script in 492,526) are on the standalone core and its executor; its list of what phase 3 did not do says MicroPython "has run on the standalone core and executor (P2), not yet inside the merged model". In the released Qwenputer, the firmware is calc, written in C.

5. Qwen calls it through its tool-call format, with a driver in the loop

How Qwen uses it

No fine-tuning: the CPU borrows a format Qwen already knows. Qwen uses it without any post-training required, by piggybacking on the tool call format: the prompt lists a calc tool, Qwen writes a normal tool call, and nothing on the host executes it. The compiled "bridge" copies the call's tokens into memory at 0x8000 (up to 80 tokens), </tool_call> starts the program, and every byte the firmware prints comes out as the matching Qwen token, so the <tool_response> is predicted by the model itself (the figure at the top). The firmware evaluates integers and decimals up to 62 digits, exact fractions since its second version, and returns "error (too complex: split it)" or "error (too long: split it)" past its limits. Qwen's original weights stay exactly as they are: the CPU's weights sit in the extra layers and extra dimensions.

"No runtime" means no host computes the answer, not "plain generate()". The post says No external tool calls or runtime are used and, in the next breath, We use a small driver called RvChat. The driver does three things the design log describes: it injects a snapshot (firmware, RAM, registers) into the compiled layers' DeltaNet states after the prompt; it sends each trace token through the 11 compiled layers only, so Qwen's layers never see it; and, in the benchmark runs, it replaces those layers' Hugging Face modules with a Triton "executor" that computes the same circuit in fp32, 13 times faster (3,200 trace tokens a second on an L4), checked bit-for-bit equal to the modules on 6 records. The answer is still computed by the compiled circuit, not by Python on the host; the earlier CHIP-8 version, by contrast, ran under stock generate() with a boot record prepended.

6. Does it work: as well as the same tool run on the host, on 40-problem sets

Does it work?

On DeepMind's arithmetic sets Qwenputer matches the host tool and beats base Qwen where arithmetic is hard. The post reports four sets, 40 problems each, greedy decoding, one run: mul_big: Qwenputer scores 97.5% against 55% for base Qwen (22/40) and 100% for Qwen with a tool; div_big: Qwenputer scores 97.5% against 72.5% and 95%; 100% on mul_div_multiple_longer against 90% and 97.5%; 97.5% on add_or_sub_big against 87.5% and 97.5%. The "Python tool" is base Qwen with the same calc tool answered on the host in the firmware's exact format (Python, or for the re-run sets the firmware itself on a reference machine), which makes it a like-for-like control. Against it, Qwenputer is never more than one problem away, and the chart's 95% intervals show 40 problems cannot separate them; against base Qwen, the gap is clear on mul_big and div_big and within noise on add_or_sub_big.

The NUPA bar is from a different model. On NUPA's long-integer arithmetic, Qwenputer goes from 48.6% to 100%: that is the CHIP-8 version's result on 576 problems, whose table also says its numbers are "the best mode per benchmark across our development checkpoints". The repository's commit of 22 October labelled the bar "NUPA from the CHIP-8 version", and the next commit removed the label; the RISC-V table has a synthetic integer set instead (75% to 97.5%, the same as the tool), which the post leaves out.

Its misses are Qwen's, and "exact" means the circuit matches its reference. I replayed about 230,000 of its output positions: every position the circuit owns, re-run in the reference evaluator, with zero wrong predictions. The misses in the table are Qwen's: re-checking a correct result, dropping a sign, a 44-call loop. Normal text is unchanged within noise (KL 6e-4, against a noise floor of 5e-4; 6.1 × 10−4 against 5.1 × 10−4 on 16 prompts, the floor being base Qwen's own two attention kernels; greedy text identical on 10 of the 16).

The row the chart hides, and the base column's re-run (depth)

mul_div_multiple_longer first went the other way. With the first firmware, which allowed a fraction only as the final value, 610 of Qwen's 1,040 calls returned an error and Qwen retried in loops: Qwenputer 20/40, the host tool 19/40, base Qwen 36/40. The second firmware (exact fractions throughout) fixed the tool, and the re-run gives 40/40 and 39/40. The fix is legitimate; the post's chart shows only the re-run. One more DeepMind set the log ran, add_sub_multiple_longer (40, 40 and 39 of 40), shows no gain and is not in the post.

The base column moved. On 19 October the README's base column read 65.0, 80.0 and 95.0 for mul_big, div_big and add_or_sub_big, with a McNemar p of 1.0 for the last; the column was dropped the same day, and on 21 October the base runs were redone on the same problems with a 4,096-token budget and a "do every step exactly" system line, giving 55.0, 72.5 and 87.5 (synthetic arithmetic rose from 70.0 to 75.0). A matched re-run is the right comparison; the shift of 3 to 4 problems per set between two base runs is also a fair measure of how much one 40-problem run can move.

Speed. On an L4 at batch 1, a calc call is 1,300 to 3,000 trace tokens, about 0.5 to 1 s on the executor; Qwen's own text tokens (about 68 ms each) take most of the time; a mul_div problem took a median of 242 s. On an A10G at batch 8: 109 mul_div problems an hour. A host tool answers in milliseconds.

7. A filesystem in the same RAM

A hard drive? In this economy?

Files persist across chats by saving the DeltaNet state. A second checkpoint adds five more tool names (put, append, get, list, delete) that the compiled layers answer: they hash its name into one of 1,024 slots of a directory in DeltaNet state (probing the next slot on a collision, two or three trace tokens a lookup) and store the text eight tokens to a row; it holds up to 512 files, about 53,000 tokens. Save those heads at the end of a session and load them at the start of the next, and the files are there. On the model card's synthetic LongMemEval-style test (four past sessions mention eight facts about the user and change two), Qwen gets facts that changed between chats right 90% of the time (27 of 30) against 30.0% for base Qwen with the old chats pasted back in (which scores 76.7% on all facts) and 83.3% with the same tools on the host; on all 90 questions, 83.3% against 78.9% for the host tools. It is 12 compiled layers, hidden size 4,608, 22.3 GB, and its code is on a separate branch.

8. Limits: twice the size, a driver, and slow

Limits and what's next

The post states its costs plainly. The widened layers make the checkpoint 18.8 GB, roughly double base Qwen (mostly zeros, since a standard checkpoint gives every layer the same width); the driver means it doesn't run with a plain generate() call yet; and every instruction costs decoded tokens, so the benchmark executor runs about 3,200 CPU tokens a second on an L4. Next on its list: Qwen writing Python for the MicroPython inside its weights, and a faster CPU (the repository has since moved on both; the dated block below).

9. Beyond arithmetic: a testbed for safety work

Beyond arithmetic

Exact control of recurrent state is the reusable part. The post closes by calling the model a really nice testbed for AI safety research and links two follow-ups published the same day (Further reading): one shows a hybrid model fine-tuned to answer with no visible reasoning can learn to track state silently in its recurrent layers when its write strength may exceed 1 (OLMo-Hybrid, up to 2) but not when it is capped at 1 (Qwen3.5); the other compiles a lie-probe trigger and a tamper-proof log into the weights. To try the model, the post says the model runs on a single 24 GB GPU, with three commands in its last section.

How much of this to believe

The mechanism and its exactness hold up, and the evidence is unusually good for a blog post. The RAM claim is three lines of linear algebra (section 2, and the toy reproduces it). The CPU is checked the way processors are: the official compliance suites, a diff of 61 programs against qemu, random-program fuzzing, and more than 19 million instructions run free on the GPU with every generated token required to equal the reference trace. During the benchmark runs a lockstep check compares every circuit token with a reference machine and stops at the first difference (it checks; it does not correct), and it never fired. Code, weights and the design log with every measurement are public, and the post's own limits paragraph names the size, the driver and the speed.

Where the post says more than its evidence:

  • One bar is from another model. The NUPA 48.6% to 100% result is the CHIP-8 version's (576 problems, best mode per benchmark across development checkpoints), shown on this model's chart after its version label was removed (section 6). The RISC-V model has no NUPA number.
  • Small single runs, reported without intervals. Four or five sets of 40 problems, one greedy run each; a McNemar column was added to the README and removed the same day, and the base column moved by 3 to 4 problems between two runs. What the numbers support is parity with the same tool on the host, which is what an exact calculator should give, and a gain over a tool-less base where the arithmetic is big. They cannot rank Qwenputer against the host tool, and the post does not quite claim to.
  • The chosen rows. The chart shows mul_div_multiple_longer after a firmware fix (before it, base Qwen led 36 to 20) and leaves out the synthetic set and add_sub_multiple_longer, where it adds nothing. The fix is fair; showing the rows with no gain would have been fairer.
  • "No runtime", "not a tool". No host code computes an answer, and that is the real result. But Qwen reaches the CPU through a tool call, and the RISC-V model needs a custom driver that boots the CPU from a state snapshot, routes the trace tokens past Qwen's layers and, in the measured runs, executes the compiled layers with a separate Triton implementation (checked bit-equal on 6 records). The Hacker News critique of the framing is right; the post states the driver itself, but only under its limits.
  • "Its own Gated DeltaNet layers". The RAM lives in 11 new layers of Qwen3.5's layer type, not in Qwen's 24 pretrained DeltaNet layers, which are untouched. The point the post makes, that no new layer type was needed, holds.
  • MicroPython has run on the standalone core, not yet in the released model (section 4).

Verdict. Believe the mechanism and the exactness: they are demonstrated, reproducible and checked far beyond what the post shows. Read the benchmarks as "an exact calculator in the weights works as well as the same calculator on the host, on small sets", with the NUPA bar set aside, and read "no runtime" as "nothing outside the weights computes the answer". As a practical way to do arithmetic it is slower and twice the size of a model with a tool, which the post does not dispute; its value is as a demonstration and a testbed.

Where it moves the knowledge base

  • Beyond attention owns the delta rule and already notes that unit keys and β = 1 return exactly v. This post adds the limiting case as a working component: with the gate also at 1 and one-hot keys, a head is an exact addressable memory of dk rows, enough to run a CPU on. The owner gains that sentence and this page in its Further reading.
  • Alibaba: Qwen: Qwen3.5-4B (24 DeltaNet and 8 attention layers, 16 key and 32 value heads of 128) is the base of the best-known compiled-weights demonstration; a Further reading line.
  • Building a harness: the extreme case of "where does the tool run": a tool call whose response the model's own compiled layers write, so the host executes nothing (but still runs a custom decoding driver).
  • Sparks of Weight-Space Programming: the opposite direction, an LLM reading and editing trained weights, where here a person compiles new ones; the two pages link each other.

QwenFX: a coding agent inside the model

8 November 2026: Vercel's fx coding agent, compiled unmodified, runs on the in-weights CPU with Qwen3.5-4B as its model: 15 of 15 small repository tasks, a new executor at about 24,000 trace tokens a second on an L4, the computer as a 125 MB chip file beside base Qwen. The host still renders the chat template, keeps the files and does the git work (the author's README, read 27 November).

(10 min)

Qwenputer-npu and QwenPU: neural networks on the in-weights CPU

30 October 2026: Three added instructions (int8-by-int4 dot products) let Karpathy's 260K-parameter stories260K Llama run as a C program on the CPU, about 41 s a story token on an L4; QwenPU's vector unit cuts that to about 16 s, with a 26.7 GB checkpoint (the repository README, read 27 November).

(10 min)

What it rests on

Hybrid models can hide reasoning in their RNN state

Divyansh Agrawal, 22 October 2026 (the author; Part 2 of the series): The first follow-up: fine-tuned to answer with no visible reasoning, OLMo-Hybrid (write strength allowed up to 2) learns to track a flipping switch silently and generalises to 256 flips; Qwen3.5 (write strength capped at 1 by a sigmoid) does not. Uses the same compiler for its probes.

(9 min)

Building oversight tools into a model's weights

Divyansh Agrawal, 22 October 2026 (the author; Part 3 of the series): The second follow-up: a linear lie probe whose trigger and log are compiled into the weights (91% of lies flagged, no false flags in 28,000 tokens of chat and GSM8K, the log kept in DeltaNet state), and a planted mechanism as an answer key for interpretability tools.

(7 min)

Linear Transformers Are Secretly Fast Weight Programmers

Schlag, Irie and Schmidhuber, ICML 2021 (third-party): The paper the post cites for the delta rule as an associative memory; our owner page teaches the rule from it.

(45 min)

Gated Delta Networks: Improving Mamba2 with Delta Rule

Yang, Kautz and Hatamizadeh, 2024 (third-party): The layer Qwen3.5 uses three times in every four, with the gate and write strength this post pins to 1.

(45 min)

Can LLMs be computers?

Christos Tzamos and others, Percepta, 11 March 2026 (third-party; linked in the Hacker News thread): Earlier work on executing programs inside transformer weights (a WebAssembly interpreter), with its own fast decoding; Qwenputer's difference is that it sits beside an unchanged pretrained model that calls it.

(20 min)

Tracr: Compiled Transformers as a Laboratory for Interpretability

Lindner et al., 2023 (third-party): The best-known earlier compiler from a program to transformer weights (RASP programs); background for the compiler in section 3, which the post does not cite.

(40 min)

Qwen3.5-4B model card

Qwen team (maker): The base model: 32 layers, 24 of them Gated DeltaNet (16 key heads, 32 value heads, 128 x 128 states).
