7. Caching at the gateway: a memo of whole answers

Not prompt caching. Provider prompt caching keeps the computed attention state for a prompt prefix inside the model server, so the model still generates a fresh answer, cheaper ({{Context engineering|n:3f15c17b0d0d811292cee46514370431}} and {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}} own it). A gateway response cache stores whole answers: on a match the model is never called.

The key. LiteLLM concatenates every model parameter present in the request (model, messages, temperature, max_tokens, tools ...) and hashes it with SHA-256 (Cache.get_cache_key in litellm/caching/caching.py). Backends: in-memory (default TTL 600 s), Redis, S3, GCS, Azure Blob, disk, and three semantic caches (Redis, Valkey, Qdrant). Per request, cache: {"no-cache": true} skips the lookup, ttl sets the lifetime, and mode: default_off makes caching opt-in. SOURCE

The recording. Cache on (in-memory), the local model behind it, six calls with the same question. MEASURED

A hit returns a sampled answer word for word; one extra space misses

Seconds are what the caller waited (the first call also waited for the shared local model server). Cache key: the first 12 hex digits of the x-litellm-cache-key header, present only on hits.

  • Hit: 0.08 s instead of seconds, no tokens spent.
  • Temperature 0.9: a miss (temperature is part of the key), then a hit that returned the sampled answer word for word. The cache turns a random answer into a fixed one for the TTL; for an agent that retries a step hoping for a different action, that is the opposite of what it wants.
  • One extra space: a miss. Each agent turn appends the last tool result, so an agent's calls almost never hit an exact cache. The gateway cache pays for repeated identical calls (classification, embedding, evals re-run on unchanged items), not for agent loops.

Semantic caching, and why it is the risky one. A semantic cache embeds the prompt and returns a stored answer when a previous prompt is merely similar (cosine similarity above a threshold): LiteLLM's Redis, Valkey and Qdrant backends, Azure API Management's llm-semantic-cache-lookup and llm-semantic-cache-store policies (Microsoft Learn, read 24 Oct 2026). It is the only cache that can return a wrong answer: a hit is a bet that two different questions deserve the same reply, and the threshold trades money saved against wrong answers served. At a gateway three things make it worse: the cache is shared by every caller, so an entry must be scoped per tenant and user or one customer's answer reaches another; the reply is frozen, like any cache hit above; and nobody sees a false hit in an error counter. Use it last and narrowly, after measuring its false-hit rate on your traffic; {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}, section 12, measures that rate threshold by threshold on real labelled pairs.

8. The translation layer: what actually leaves the gateway

A gateway accepts several request formats (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini generateContent) and sends each upstream in whatever format the provider speaks. The deployment's provider prefix decides the outgoing format, and the mapping is not always the obvious one.

The recording. One Anthropic-format request (POST /v1/messages, with a system prompt) for the local model, through two deployments that differ only in prefix; a logging proxy in front of the model server recorded what arrived. MEASURED

The same request, two prefixes: openai/ sends the Responses API, lm_studio/ sends Chat Completions

With openai/, LiteLLM assumed an upstream that speaks OpenAI's newer Responses API and sent POST /v1/responses (the system prompt became instructions, the message became input, and it asked for reasoning.encrypted_content); mlx-lm has no such route, so the caller got a 404 that names the model group, not the format. With lm_studio/ it sent ordinary /v1/chat/completions and the caller got a well-formed Anthropic reply. {{Other coding harnesses|n:3c65c17b0d0d819fa3cefdcd2ccff2f7}} found the same with a Responses request (openai/ forwards /responses unchanged, lm_studio/ translates it), which is how it ran Codex, which speaks only the Responses API (wire_api = "chat" is now a config error), against the local model.

What translation can lose
Anything one format has and the other does not: Anthropic cache breakpoints, thinking blocks and their signatures, server tools, OpenAI's reasoning items, provider-specific parameters. LiteLLM drops unknown parameters when drop_params: true is set and raises otherwise. When something silently stops working behind a gateway, log the outgoing request body (the proxy's debug log, or a logging proxy like the one used here) before blaming the model.

Provider API versions break gateways too: Anthropic's 2026-10-21 version rejects temperature, top_p and top_k, and its new SDKs send the key as Authorization: Bearer ({{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} section 2 has the version change, and its section 7 compares the providers' API designs; the key's move between headers is on {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} section 1). A gateway that sets X-Api-Key or forwards sampling parameters to Claude must change: drop them for Claude on the new version (as drop_params does for unknown ones) or pin that route's anthropic-version to 2023-06-01.

9. OpenRouter: a gateway you rent, and a market of providers

OpenRouter is a hosted gateway: one OpenAI-compatible endpoint, one key and one bill in front of many model vendors and inference providers (its catalogue size and fees are in the dated table, section 11). It routes two ways. Across models: send a models list and it tries them in order on errors, rate limits and downtime, billing the model that answered (model fallbacks). Across providers of one model, the part with no LiteLLM equivalent: the same open-weights model is served by many companies at different prices, and by default OpenRouter will "Prioritize providers that have not seen significant outages in the last 30 seconds", then "For the stable providers, look at the lowest-cost candidates and select one weighted by inverse square of the price", then "Use the remaining providers as fallbacks" (provider routing). Why it matters for an agent. "The same model" is not the same numbers. For Llama 3.3 70B Instruct, 11 endpoints ranged from $0.10 to $1.04 per million input tokens, declared their weights as fp8, bf16, fp16 or nothing, and offered contexts from 12,288 to 131,072 tokens; under the rule the two cheapest take about two thirds of first picks; gpt-oss-120b had up to 23 endpoints. An eval run through default routing mixes providers, and an agent's long prompt needs an endpoint whose context fits. Pin providers for evals (order with allow_fallbacks: false, or quantizations), and read the provider field each response carries. The provider object's other options: only, ignore, require_parameters, data_collection, zdr, sort (price, throughput or latency), preferred_min_throughput, preferred_max_latency; the suffixes :nitro and :floor mean sort by throughput and by price. LiteLLM can use OpenRouter as one more upstream (openrouter/ prefix), so the two compose: your own gateway for keys, budgets and logs, OpenRouter for reach.
