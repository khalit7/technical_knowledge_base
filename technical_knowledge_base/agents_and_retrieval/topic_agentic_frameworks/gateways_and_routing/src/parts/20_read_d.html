5. Rate limits: three places, three algorithms

The problem. A rate limit caps how much one caller may send per unit of time, so one runaway agent cannot take everyone's capacity. For LLM traffic the unit is not only requests: a request's cost is its tokens, and the output tokens are unknown until it finishes. An agent behind a gateway meets limits in three places, each counted differently:

Anthropic's input-token limit counts only uncached input for most models ("only uncached input tokens count toward your ITPM"), so with an 80% cache hit rate a 2,000,000 ITPM limit admits 10,000,000 input tokens a minute; output tokens count as they are generated, so a large max_tokens costs nothing against OTPM (rate limits, read 6 Oct 2026). LiteLLM's token limit has to guess the output before the call: when max_tokens is missing it reserves a floor of 1,024 output tokens (DEFAULT_MAX_TOKENS_ESTIMATE 4,096 divided by 4, capped at a quarter of the smallest TPM limit) and corrects after the response. The gateway's window, recorded. LiteLLM's limiter file calls itself "based on a similar one by Envoy proxy" and names its functions "sliding window", but the code keeps one start time and one counter per key: the first request opens a 60-second window, every request in it adds 1, and once 60 whole seconds have passed the next request starts a fresh window at zero. That is a fixed window anchored on the first request, not a sliding one, and it has the fixed window's weakness at the boundary. Two keys with rpm_limit: 10; one sends a request every second for 130 s, the other sends 1 request, waits until second 50, sends 9, then 10 more just after the window rolls over. MEASURED

The burst key had 19 requests accepted between second 50 and second 65, almost twice its limit inside 15 seconds, and then 429s; the steady key was accepted for 10 seconds out of every 60 (seconds 0 to 9, 61 to 70, 121 to 129: the limiter counts whole wall-clock seconds, and this run happened to start just before a second ticked over). On the same burst trace a sliding log would have accepted at most 10 in any 15 seconds, and a token bucket holding 10 and refilling one every 6 seconds at most 12 (its full bucket plus two refills), which is the shape Anthropic's limiter imposes downstream. The five classic algorithms (fixed window, sliding log, sliding window counter, token bucket, leaky bucket) are taught and animated on one burst on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}; the {{Limits lab|#t-lim}} replays these two recorded traces through LiteLLM's rule (which reproduces every accept and reject) and through the others.

Several gateway replicas
Without Redis each LiteLLM process keeps its own counters, so three replicas behind a load balancer admit three times the limit. With redis_host set the same window logic runs as a Lua script on the shared Redis (BATCH_RATE_LIMITER_SCRIPT in the same file). SOURCE

6. Budgets and virtual keys: what a dollar cap really does

The problem. A budget caps spend in dollars for a key, a user, a team, an organisation or an end customer, optionally resetting on a period (budget_duration: "30d", also seconds, minutes, hours). The gateway prices every call from its price table and adds it to each entity's spend. The hard part is concurrency: if the check reads the spend so far and 20 calls arrive together, all 20 see the same number and all 20 pass. DOCS

What 1.104.0 does instead: reserve, then settle. Before calling the provider, the proxy estimates the request's maximum cost (its input tokens counted, plus max_tokens output tokens, or 16,384 if the request sets none, capped at the model's own output limit, at the configured prices) and adds it atomically to the key's counter. If that would cross the budget but some budget is left, the reservation is shrunk to what is left and the call goes ahead; if nothing is left, the call is refused with HTTP 422 budget_exceeded. When the call ends the reservation is replaced by the real cost (proxy/spend_tracking/budget_reservation.py). SOURCE

The recording. Budget $0.0004 per key; each call really costs $0.00008 (40 input tokens at $1 per million, 8 output tokens at $5 per million), so 5 calls fit. The fake provider takes 2 s per call. MEASURED

  • Reservation switched off (general_settings: disable_budget_reservation: true, which the docs keep for "temporary mitigation"): all 20 simultaneous calls accepted, final spend $0.0016, four times the budget; the second wave was refused. This is the soft cap the parent page describes.
  • Ten calls one after another: exactly 5 accepted, final spend $0.0004, then 422s. No overshoot.
  • Twenty at once, no max_tokens: 1 accepted, 19 refused in about 0.4 s. Each request reserved about $0.082 (16,384 output tokens at $5 per million), far more than the whole budget, so the first was shrunk to the budget and the rest found nothing left. A second wave 4 s later: again 1. The key has become a queue of one.
  • Twenty at once with max_tokens: 16: each reserved about $0.000095, so 4 fitted and a fifth took the remainder: 5 accepted, final spend exactly $0.0004.
Correction to the parent page
The parent's Production stack tab recorded a sequential overshoot of one call ($0.0008 cap, three calls of $0.00033, final $0.00099) and concluded that a key "can overshoot its cap by the calls in flight", with batched spend writes "widening the overshoot under parallel traffic". On LiteLLM 1.104.0, the version both pages ran, the sequential overshoot reproduces (the last call is let through with whatever budget remains, and can cost more), but parallel calls do not overshoot: the reservation blocks them. LiteLLM's docs: "Budget reservation is enabled by default", and switching it off "can allow concurrent requests to exceed a configured budget" (docs); known gaps are requests whose cost cannot be estimated, which skip it (issue 35524), and project budgets (issue 34101). What follows for agents
Send max_tokens on every call. Without it, a small per-key budget serialises an agent's parallel tool-calling or subagents, and the 422 arrives long before the money is spent. LITELLM_BUDGET_RESERVATION_MAX_COST_USD caps one request's reservation instead (PR 38647). Budgets nest: "If a key belongs to a team, only the team (and team-member) budgets are enforced" (docs). A provider's own spend cap is a separate, monthly thing: Anthropic's returns a 429 with no retry-after and the error code enforced_spend_limit_reached, which every retry layer will hit again until the month ends.
