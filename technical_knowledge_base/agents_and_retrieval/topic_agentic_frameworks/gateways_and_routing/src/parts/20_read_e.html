7. Caching at the gateway: an exact-match memo, not prompt caching

Two different things share the word. Provider prompt caching happens inside the model server: the provider keeps the computed attention state (the KV cache) for a prompt prefix, so a later request that starts with the same prefix is cheaper and faster, but the model still generates a fresh answer. A gateway response cache stores whole answers: if a new request matches a stored one, the gateway returns the stored answer and the model is never called. The first is taught on {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} and {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}}; this section is the second.

What the key is. LiteLLM builds the key by concatenating every model parameter present in the request (model, messages, temperature, max_tokens, tools ...) and hashing it with SHA-256 (Cache.get_cache_key in litellm/caching/caching.py). Backends: in-memory (default TTL 600 s), Redis, S3, GCS, Azure Blob, disk, and three semantic caches (Redis, Valkey, Qdrant) that match by embedding similarity instead. Per request, cache: {"no-cache": true} skips the lookup, ttl sets the lifetime, and mode: default_off makes caching opt-in. SOURCE

The recording. Cache on (in-memory), the local model behind it, six calls with the same question. MEASURED

Seconds are what the caller waited. The first call also waited for the shared local model server, which other work was using. Cache key: the first 12 hex digits of the x-litellm-cache-key header, present only on hits.

  • Hit: 0.08 s instead of seconds, no tokens spent.
  • Temperature 0.9: a miss (temperature is part of the key), then a hit that returned the sampled answer word for word. The cache turns a random answer into a fixed one for the TTL; for an agent that retries a step hoping for a different action, that is the opposite of what it wants.
  • One extra space: a miss. Agents rarely repeat a request exactly: each turn appends the last tool result, so an agent's calls almost never hit an exact cache. The gateway cache pays for repeated identical calls (classification, embedding, evals re-run on unchanged items), not for agent loops.
Semantic caching
A semantic cache returns a stored answer for a request that is merely similar (cosine similarity above a threshold). It is the only cache that can be wrong: {{Caching|n:3cd5c17b0d0d817ebd6ccadd4750c23a}} measures how often, threshold by threshold, in its Threshold lab. Not repeated here.

8. The translation layer: what actually leaves the gateway

The problem. A gateway accepts several request formats (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini generateContent) and sends each upstream in whatever format that provider speaks. The provider prefix of the deployment decides the outgoing format, and the mapping is not always the obvious one.

The recording. One Anthropic-format request (POST /v1/messages, with a system prompt) for the local model, through two deployments of the same model that differ only in prefix. The locking proxy in front of the model server logged what arrived. MEASURED

With openai/, LiteLLM assumed an upstream that speaks OpenAI's newer Responses API and sent POST /v1/responses (the system prompt became instructions, the message became input, and it asked for reasoning.encrypted_content); mlx-lm has no such route, so the caller got a 404 that names the model group, not the format. With lm_studio/ it sent ordinary /v1/chat/completions and the caller got a well-formed Anthropic reply. The sibling {{Other coding harnesses|n:3c65c17b0d0d819fa3cefdcd2ccff2f7}} found the same with a Responses request: openai/ forwards /responses unchanged, lm_studio/ translates it. That route is how the sibling ran Codex (which speaks only the Responses API; wire_api = "chat" is now a config error) against the local model, and it is why the prefix matters.

What translation can lose
Anything one format has and the other does not: Anthropic cache breakpoints, thinking blocks and their signatures, server tools, OpenAI's reasoning items, provider-specific parameters. LiteLLM drops unknown parameters when drop_params: true is set and raises otherwise. When something silently stops working behind a gateway, log the outgoing request body (the proxy's debug log, or a logging proxy like the one used here) before blaming the model.
