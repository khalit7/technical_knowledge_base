The old notes on the parent page say you run LiteLLM at work and have hand-built a DAG engine over model calls; nothing else about that setup is known here, so this is a checklist of things this page found to be easy to get wrong, each with how to check it on any LiteLLM deployment.

A hand-built DAG engine already does the workflow half of what LangGraph would (the parent page's section 10; {{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}} in depth). Behind a gateway it should keep one job for itself: each node's deadline, passed down as the gateway call's timeout, so a slow branch fails fast instead of waiting through the gateway's whole retry chain. Retries belong in one place; with a gateway in front, that place is usually the gateway.

Traces from the gateway. To get those traces into Langfuse, {{LLM observability|n:3c65c17b0d0d81fe82c0c6e9360afec4}} (its section 4) found that LiteLLM's langfuse_otel callback sends a GenAI span per request, with usage and cost, and that LiteLLM now recommends it over the older langfuse callback; gateway spans see every request but not the agent around it, so join them with the app's spans on the trace id.

Common mistakes

Retrying in the SDK, in the agent loop and in the gateway
Attempts multiply (section 4). Pick one layer; set the SDK client's max_retries to 0 when a gateway retries for it.
Treating a 429 from the gateway like a 429 from the provider
A gateway 429 (throttling_error, retry-after 60) is your own key's limit; waiting does not help other keys and a fallback to another model will not help either. A provider 429 is capacity; a fallback or another deployment helps.
Expecting a 10 RPM key to mean "at most 10 in any minute"
LiteLLM's window starts at the first request and resets whole: 19 in 15 seconds were accepted here (section 5). If the upstream enforces a smooth token bucket, smooth on your side too.
Reading a budget as an exact meter, or as a soft cap
In 1.104.0 it is neither: parallel calls are held back by worst-case reservations, and the last sequential call can overshoot by its own cost (section 6).
Caching agent calls at the gateway
Every turn's request differs from the last, so exact hits are rare; when they happen they replay a sampled answer. Cache deterministic, repeated calls only (section 7).
Running evals through a router that mixes providers
Different quantisations and context limits behind one model name (section 9). Pin the provider and record which one answered.
Trusting a learned router without testing it on your own traffic
The keyword router tested here sent every question containing code to the strong model and none of the letter puzzles, whatever their difficulty: its features saw code, not difficulty (section 10). Measure its quality-cost curve against random routing on a sample of your requests before turning it on.

Interview questions

Design the gateway for 50 internal teams calling three providers. What goes in it?
Virtual keys per team with budgets and rate limits; model groups with several deployments each (regions, providers) and per-deployment timeouts; one retry layer with backoff and a retry budget; cooldowns for broken deployments; fallbacks across model families that were each evaluated; Redis for shared counters across replicas; spend logs and traces tagged with team, model group and the deployment that answered; caching off by default.
Retry, cooldown, fallback: what is the difference?
Retry: same group again after a wait (blips). Cooldown: stop routing to one deployment for a while (a broken copy). Fallback: switch to another group (the model is unavailable or unsuitable, for example the prompt is too long).
A client has a 10 s timeout and 2 retries; the gateway has 5 s per attempt and 2 retries; the provider hangs. How many provider calls, and when does the user hear?
Up to 3 × 3 = 9 calls (measured: 9, the last starting after the user's error at 32.8 s). Fix: one retry layer, inner timeouts shorter than outer ones, and cancellation propagated when the client goes away.
How would you enforce a dollar budget under concurrency?
Reserve the worst-case cost of each request atomically before calling (input tokens plus max output tokens at list price), settle to the real cost afterwards, and refuse when the reservation does not fit. Cap the reservation per request so a missing max_tokens does not serialise the caller. This is what LiteLLM 1.104.0 does.
Fixed window, sliding window or token bucket for an LLM API?
Token bucket (what Anthropic uses): it allows a burst up to the bucket size and then a steady rate, with no boundary double burst. Count tokens, not only requests, and reserve output tokens at admission because they are unknown until the end.
When does a learned router pay off?
When traffic mixes easy and hard requests, the cheap model is good enough on the easy ones, and the router's features actually predict difficulty on your traffic. Measure the quality against the share sent to the strong model, compared with random routing at the same share.
