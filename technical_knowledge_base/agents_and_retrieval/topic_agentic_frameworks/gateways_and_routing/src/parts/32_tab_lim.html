Limits lab: the same traffic through four rate limiters

Two recorded traces from section 5 of the Reading tab: a key that sends one request a second for 130 s, and a key that sends a burst on each side of a window boundary. The top row is what LiteLLM 1.104.0 actually answered; the second row is LiteLLM's rule as read from its source (a 60-second window that starts at the first request, in whole wall-clock seconds), replayed on the same arrival times, and it reproduces every recorded decision. The other rows replay the same arrivals through a calendar-minute window, a sliding log and a token bucket, each allowing 10 per 60 s. Rejected requests do not use up capacity in any of them.

Reading the rows
LiteLLM (anchored window): one start time and one counter; reset whole once 60 s have passed since the start. Calendar minute: reset at every whole minute of the clock; what LiteLLM's router uses for a deployment's own rpm. Sliding log: remember every accepted request and allow a new one if fewer than the limit were accepted in the last 60 s; exact, memory grows with the limit. Token bucket: a bucket holding up to the limit, refilled continuously at limit per 60 s, each request takes one token; what Anthropic says it uses for the Claude API. The algorithms themselves, with their history and costs, are on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}.
