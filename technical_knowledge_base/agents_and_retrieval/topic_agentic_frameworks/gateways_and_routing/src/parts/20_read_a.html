The whole page in one screen

A gateway (also called an LLM proxy) sits between your agent and the model providers: your code sends every model call to it in one format, and it decides which real endpoint answers, what to do when that endpoint fails, whether the caller is allowed to spend more, and what to log. The parent page, {{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}}, explains why you would want one (its Reading section 6) and its {{Production stack|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} tab records one LiteLLM proxy retrying a broken provider and falling back. This page opens the box: every rule below was read from LiteLLM 1.104.0's source and then checked by a recorded run, because several of them are not what the configuration file suggests.

Follow one request through LiteLLM's proxy. Each box is a stage in the order the code runs it; pick a scenario and step through. The same request takes three different paths depending on what the gateway already knows.

What the page found, in one list (each is a section below, with its recording):

  • Choosing a deployment: latency-based routing sent 34 of 40 requests to the fast copy; cost-based routing ignored prices written in the wrong part of the config and sent all 40 to the expensive one. MEASURED
  • Failures: a deployment that answers 429 is benched for 5 seconds at once; one that answers 503 keeps being tried until it has failed 5 requests in the minute. Setting allowed_fails: 3 does nothing, because 3 is the default and the code treats the default as "not set". MEASURED SOURCE
  • Retries multiply: one user request through the OpenAI SDK's default 2 retries and the gateway's 2 retries reached a hanging provider 9 times, and the last attempt started after the user had already been given an error. MEASURED
  • Rate limits: a 10-per-minute key accepted 19 requests in 15 seconds, because LiteLLM's window starts at the first request and resets whole. MEASURED
  • Budgets: no longer soft. LiteLLM reserves each request's worst-case cost before calling the provider, so 20 simultaneous calls on a small budget were let through one at a time unless the caller set max_tokens. MEASURED
  • Caching: the cache key is the exact request, so one extra space misses, and a temperature-0.9 answer comes back word for word on a hit. MEASURED
  • Translation: an Anthropic-format request for an openai/ model was turned into an OpenAI Responses API call, which the local server did not have. MEASURED
  • Routing services and learned routers: one open model on OpenRouter is served by up to 23 endpoints at different prices, precisions and context lengths; on a small graded set, LiteLLM's keyword-based complexity router recovered two thirds of the gap between a local 4B model and Claude Haiku 4.5 while sending a quarter of the calls up, but only because it spotted code: it sent up none of the letter puzzles the small model failed. MEASURED DOCS
What is real on this page
The gateway is a real LiteLLM 1.104.0 (the latest on PyPI on 6 October 2026, uploaded 3 October) running on one laptop, with Postgres 16 in Docker for its keys. The upstreams are small fake providers written for this page (an OpenAI-shaped server that answers, fails with a chosen status, or hangs, on a script) and a local model on Apple M1 Pro (mlx-community/Qwen3-4B-Instruct-2507-4bit, mlx-lm 0.32.0). The learned-router experiment also used Claude Haiku 4.5 through the Claude Code CLI. OpenRouter was not called (no account); its public model and endpoint catalogue was read on the same day.
