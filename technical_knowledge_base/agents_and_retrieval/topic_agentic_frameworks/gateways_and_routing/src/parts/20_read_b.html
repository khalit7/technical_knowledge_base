2. Choosing a deployment: what each strategy really measures

When a group has several deployments (the same model in two regions, or at two providers), something picks one per call, and the pick decides latency, cost and how evenly load spreads. Each LiteLLM routing_strategy is a small file in litellm/router_strategy/, and what it measures is easy to get wrong from its name. 3. When a call fails: retry, cool down, or fall back

From litellm/utils.py (_should_retry: 408, 409, 429 and 5xx), router.py (should_retry_this_error) and router_utils/cooldown_handlers.py (_is_cooldown_required, _should_cooldown_deployment) in 1.104.0. Defaults: num_retries 2, cooldown_time 5 s, at most 5 fallbacks per request; an error whose text contains "APIConnectionError" never triggers a cooldown.

Two cooldown regimes, and a trap. Without allowed_fails, the rules in the table apply: a 429 benches a deployment at once, other errors only once more than 50% of its calls this minute failed and there were at least 5 (DEFAULT_FAILURE_THRESHOLD_PERCENT 0.5, DEFAULT_FAILURE_THRESHOLD_MINIMUM_REQUESTS 5). With allowed_fails, a simpler counter: cool down once failures within cooldown_time exceed it. But the code decides whether you "set" it by comparing with the library default, 3 (_is_allowed_fails_set_on_router). Writing allowed_fails: 3 in a config therefore changes nothing; the parent page's Production stack config contains exactly that line.

Grey bands: more than 4 s in which no call reached C although requests kept coming, which the rules attribute to a cooldown. Seconds from the first request. Every attempt, including those to A, is replayed at the end of section 4.

  • 429: C was benched after its first 429 and came back every 5 to 6 seconds (calls at 0.1, 5.7, 11.8 and 17.8 s). Users never saw an error.
  • 503, default settings: C was picked about one time in three until its fifth failure in the minute (at 7.3 s), then benched until 14.7 s; after that each new failure benched it again.
  • 503, allowed_fails: 3: the same, as the source predicts, plus one user error: request 2 picked C, and both retries picked C again. A retry re-runs the routing choice at random, so with two deployments a request whose first pick is the bad one fails all three tries with probability 1/2 × 1/2 = 1/4 while the bad one is not benched. enable_weighted_failover (async calls, simple-shuffle only) re-picks among the other deployments instead.
  • One deployment in the group: never cooled down (the "single-deployment model group" exemption: benching the only copy would turn a partial outage into a total one), so every request paid two backoff waits and then fell back: about 5.5 s per request, every time.
Two more recorded cases: allowed_fails 1, and a context-window error (depth)
  • 503, allowed_fails: 1: benched after its second failure, back 5 s later.
  • Context window error: never retried; with no fallbacks the user got ContextWindowExceededError in 0.1 s; with either fallbacks or context_window_fallbacks the request went straight to the long-context group.
Predict, then open. A group has two deployments and the bad one returns 500 on every call. You set allowed_fails: 3 and cooldown_time: 60, expecting it to be benched after three failures for a minute. What happens?
It is benched only after more than half of its calls in the current minute failed and there were at least five (the default regime), and the bench lasts 60 s because cooldown_time is honoured. Write allowed_fails: 2 or use allowed_fails_policy (per error type, for example InternalServerErrorAllowedFails) to get a counter that applies.

Outages: plan the fallback, do not just configure it. A fallback is another deployment of the same model, the same model at another provider (Claude is also sold through AWS Bedrock and Google Vertex AI, and OpenAI's models through Azure, AWS Bedrock and, in private preview since October 2026, Vertex AI; open models through many, section 9), or a different model. Check it like a backup generator: is its quota big enough to take all the traffic at once; does it accept the same prompt and tool-call format; does it behave the same on safety; has it been evaluated on your task? It starts with a cold prompt cache, so requests cost more and first tokens come later until it warms. A fallback that has never carried full traffic is untested; fail over on a schedule.

4. Timeouts and retries across layers

An agent's model call passes through several programs that each retry: the provider SDK in your agent, your own loop, the gateway, sometimes a second gateway. Each layer's retries run once for every attempt of the layer above. With the SDK's 2 retries and the gateway's 2, one request can reach the provider 3 × 3 = 9 times:

attempts reaching the provider = (1 + r1) × (1 + r2) × … × (1 + rn)
ri

The rule
Retry at one layer only, the one that knows the most (usually the gateway, which can switch deployments); set the others to 0. Give each layer a timeout shorter than the layer above it, so the inner one gives up first and reports why. A request retried 9 times is a capacity problem, not bad luck. Retry budgets and retry storms are measured on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}; which hop's timeout ends a long generation is on {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}, section 9.
