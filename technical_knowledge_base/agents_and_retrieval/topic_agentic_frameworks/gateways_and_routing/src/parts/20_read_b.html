1. Six words you need first

Deployment

One concrete endpoint that can answer: a provider, a model id on it, a base URL and a key. In LiteLLM's config each entry of model_list is one deployment.

Model group

The name your code asks for (model="chat"). Every deployment that shares a model_name belongs to the group; the router picks one of them per call. A group of one is common, and it changes the failure rules (section 3).

Provider prefix

The part before the slash in litellm_params.model (openai/, anthropic/, lm_studio/, bedrock/ ...). It chooses the code that speaks to that upstream, so it decides which wire format leaves the gateway (section 8).

Router and proxy

LiteLLM is two things: a Python library whose Router class does routing, retries, cooldowns and fallbacks inside your process, and a proxy server (litellm --config) that wraps the same Router behind HTTP and adds keys, budgets, rate limits and spend logs. Sections 2 and 3 are the Router; 5 and 6 need the proxy and its database.

Virtual key

A key the gateway issues (sk-...) and checks on every call. It carries limits (models allowed, budget, requests and tokens per minute, parallel requests). The real provider keys never leave the gateway.

Cooldown

A deployment the router has decided to stop sending traffic to for a few seconds after failures. Not the same as a fallback: a cooldown moves traffic inside a group, a fallback moves it to another group.

2. Choosing a deployment: six strategies, one recording

The problem. When a group has several deployments (the same model on two Azure regions, or on two providers), something must pick one per call. The pick decides latency, cost and how evenly load spreads. LiteLLM offers several routing_strategy values; each is a small file in litellm/router_strategy/, and what each one actually measures is easy to get wrong from its name. SOURCE

StrategyWhat the code does (1.104.0)
simple-shuffle (default)Random choice. If deployments carry a weight (or else rpm, or else tpm), the choice is weighted by it (simple_shuffle.py).
least-busyThe deployment with the fewest requests in flight right now (least_busy.py).
latency-based-routingThe lowest average of the last 10 latencies, where a latency is the response time divided by the output tokens (time to first token when streaming). A deployment with no history counts as 0, so it is tried first; a timeout adds a 1,000-second penalty sample. lowest_latency_buffer (default 0) picks at random among deployments within that fraction of the best. History lives for 1 hour (lowest_latency.py).
usage-based-routing-v2The deployment with the fewest tokens used in the current calendar minute, skipping any over its own tpm/rpm (lowest_tpm_rpm_v2.py; counters keyed by %H-%M).
cost-based-routingThe cheapest deployment by input plus output price per token. Prices come from litellm_params, else from LiteLLM's price map for the model name, else $5.00 per token each (lowest_cost.py).
Auto routersauto_router/complexity_router, adaptive_router and others choose between different models from the prompt itself; they are section 10.

The recording. One group, two copies of the same fake model: A answers in 0.2 s, B in 1.0 s. Forty requests, four at a time, through litellm.Router under each strategy. MEASURED

Bars: share of the 40 requests each copy answered (A fast, B slow); right: wall time for all 40. The cost rows mark B as the cheaper copy ($1 against $2 per million input tokens). Every request, with its timing, is in the {{Routing lab|#t-route}}.

  • Latency-based routing found the fast copy but still sent it only 34 of 40: both copies start at "no history = 0" and B is tried until its own samples push its average up. That exploration is the price of measuring.
  • Least-busy sent 26 to A without measuring anything: A finishes sooner, so it is idle more often when the next request arrives.
  • Usage-based balanced tokens per minute (18 to 22), which is what it is for, and ignored that B is five times slower.
  • Cost-based with prices in model_info sent all 40 to A, the expensive copy. The strategy reads prices only from litellm_params; with none there and no entry in the price map, both copies cost the default and the first one wins every tie. Moving the same two numbers into litellm_params sent all 40 to B. The proxy's spend tracking does read model_info prices, so the mistake is invisible on the bill.
Check what your strategy reads
A strategy that cannot find its input does not fail; it falls back to random or to the first deployment. After changing a routing setting, send a few dozen requests and count which deployment answered (the proxy returns it in the x-litellm-model-id response header).
