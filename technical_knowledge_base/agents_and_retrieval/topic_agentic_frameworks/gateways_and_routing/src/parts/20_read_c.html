5. Rate limits: three places, three algorithms

A rate limit caps how much one caller may send per unit of time, so one runaway agent cannot take everyone's capacity; past it the server answers 429 Too Many Requests, which "MAY include a Retry-After header indicating how long to wait" (RFC 6585 §4). For LLM traffic the unit cannot be requests alone. Two customers limited to 60 requests a minute: one sends 60 short chats (60 × 1,400 = 84,000 tokens), the other 60 requests each carrying a 50,000-token contract (3 million tokens, 36 times the load for the same "60 requests"). So limits count tokens too, and the usual algorithm is a token bucket holding model tokens (the algorithm is taught on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}). An agent behind a gateway meets limits in three places, each counted differently:

Output tokens are unknown at admission, and limiters answer in one of three ways: reserve the worst case and refund later (OpenAI; LiteLLM's tpm_limit), count output as it is produced (Anthropic), or charge after the response (Envoy AI Gateway, which can end 200 tokens over). Alongside token limits, cap concurrent streams per caller (max_parallel_requests): fifty open streams from one tenant are fifty batch slots nobody else can use, whatever the token count.

The gateway's window, recorded. LiteLLM's limiter calls itself "based on a similar one by Envoy proxy" and names its functions "sliding window", but the code keeps one start time and one counter per key: the first request opens a 60-second window, and once 60 whole seconds have passed the next request starts a fresh one at zero. That is a fixed window anchored on the first request, with the fixed window's weakness at the boundary. 6. Budgets and virtual keys: what a dollar cap really does

A budget caps dollars for a key, user, team, organisation or end customer, optionally per period (budget_duration: "30d"). The gateway prices every call from its price table and adds it to each entity's spend. The hard part is concurrency: if the check reads the spend so far, 20 calls arriving together all see the same number and all pass. DOCS

What 1.104.0 does instead: reserve, then settle. Before calling the provider, the proxy estimates the request's maximum cost (its input tokens, plus max_tokens output tokens, or 16,384 if the request sets none, capped at the model's own output limit) and adds it atomically to the key's counter. If that would cross the budget but some is left, the reservation shrinks to what is left and the call goes ahead; if nothing is left, HTTP 422 budget_exceeded. When the call ends the reservation is replaced by the real cost (proxy/spend_tracking/budget_reservation.py). SOURCE

  • Twenty at once with max_tokens: 16: each reserved about $0.000095, so 4 fitted and a fifth took the remainder: 5 accepted, final spend exactly $0.0004.

Correction to the parent page
The parent's Production stack tab recorded a sequential overshoot of one call ($0.0008 cap, three calls of $0.00033, final $0.00099) and concluded that a key "can overshoot its cap by the calls in flight", with batched spend writes "widening the overshoot under parallel traffic". On 1.104.0, the version both pages ran, the sequential overshoot reproduces (the last call gets whatever budget remains and can cost more); parallel calls do not overshoot. LiteLLM's docs: "Budget reservation is enabled by default", and switching it off "can allow concurrent requests to exceed a configured budget" (docs); known gaps are requests whose cost cannot be estimated, which skip it (issue 35524), and project budgets (issue 34101). What follows for agents
Send max_tokens on every call. Without it, a small per-key budget serialises an agent's parallel tool calls or subagents, and the 422 arrives long before the money is spent. LITELLM_BUDGET_RESERVATION_MAX_COST_USD caps one request's reservation instead (PR 38647). Budgets nest: "If a key belongs to a team, only the team (and team-member) budgets are enforced" (docs).

Rate limit, quota, capacity: three refusals to keep apart. A rate limit protects capacity right now; a quota or budget caps total use over a period, usually in money (Envoy: "Use QuotaPolicy when you need to cap cumulative token spend, and usage-based rate limiting (this page) when you need to control request velocity."). Anthropic's API answers 429 with a retry-after header for a rate limit; 429 with no retry-after and the code enforced_spend_limit_reached when the monthly spend cap is reached (every retry layer will hit it again until the month ends); and 529 overloaded_error when "the API experiences high traffic across all users" (Anthropic errors). DOCS A gateway should keep the same three apart for its callers: over your limit (wait), out of budget (stop), out of capacity (fall back). Its own 429 (throttling_error, retry-after 60) is the caller's key limit, which no fallback can fix; a provider 429 is capacity, which another deployment can. A budget is only as current as the price table, which LiteLLM ships with the library and can refresh at start-up or take from your config (dated table, section 11).
