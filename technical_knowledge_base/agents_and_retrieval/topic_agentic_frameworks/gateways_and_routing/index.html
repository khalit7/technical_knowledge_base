The idea in one screen

A gateway (an LLM proxy) is one endpoint in front of every model provider that turns each model call into a chain of decisions: may this caller spend, which deployment answers, what to do when it fails, and what to log. Each decision follows a rule in the code, and several of those rules are not what the configuration file suggests.

New terms. Deployment: one concrete endpoint (provider, model id, base URL, key); each model_list entry in LiteLLM's config. Model group: the name your code asks for (model="chat"); every deployment sharing that model_name; a group of one is common and changes the failure rules (section 3). Provider prefix: the part before the slash in litellm_params.model (openai/, anthropic/, lm_studio/); it chooses the code that speaks to the upstream, so it decides the wire format (section 8). Router and proxy: LiteLLM is a Python library whose Router does routing, retries, cooldowns and fallbacks in your process, and a proxy server (litellm --config) that wraps the same Router behind HTTP and adds keys, budgets, rate limits and spend logs. Virtual key: a key the gateway issues (sk-...) carrying limits (models allowed, budget, requests and tokens per minute, parallel requests). Cooldown: a deployment the router stops sending traffic to for a few seconds after failures.

1. One request through the gateway

Follow one request through LiteLLM's proxy, stage by stage in the order the code runs them. The same request takes three paths depending on what the gateway already knows; pick a scenario and step. Note two orders the docs do not make obvious: the budget is reserved at authentication, before the cache is consulted, and the cache lookup happens after routing, inside the call to the chosen deployment. SOURCE

The duties, in order: authenticate the caller from a gateway-issued key, so provider keys live in one place; authorise the model (some data may go only to approved vendors or self-hosted models); check rate limits and budget; transform and guard (redact personal data, apply input rails: the classifiers are on Guardrails); look up the cache; route; call with a timeout, retrying or falling back on failure; stream the reply back unbuffered; write one usage event (caller, model, input, cached and output tokens, cost, latency) for billing and dashboards. Turning those events into traces is LLM observability; how the gateway sits in a whole LLM service (tenancy, the batch path, rollouts, degradation ladders) is ML system design.

What it costs: one more network hop (milliseconds against seconds of generation); one more service that must not go down (run several stateless copies behind a load balancer, and keep its own dependencies, such as Redis for counters, off the critical path when they fail); the risk that it buffers streams or caps connection times; it concentrates power, because whoever owns it decides which models the company may use; and it concentrates secrets, because its database holds every provider key, which makes the gateway itself the prize. The LiteLLM 1.107.0 release of 21 October 2026 was a credential stealer, built and signed by LiteLLM's own release pipeline after an attacker took a maintainer's GitHub token; its payload read the provider keys from the proxy's database along with every token on the host (the chain is on Agent security, section 3). For a gateway that means: pin the version and upgrade deliberately, never latest; verify the image against the publisher's current signing key; keep a rotation plan for every provider key it holds; and do not log request or response bodies by default, since agents' traffic can carry tokens. When not to run one: a single product calling a single provider, owned by one team; a client library with retries and a usage log is enough until a second model, a second team or a budget question appears.

Gateways in production: Uber, Envoy AI Gateway, Huyen's platform (provenance, 2 min)

Uber built its GenAI Gateway as "a Go service that acts as an encompassing layer around the clients for third-party vendors"; "a pivotal design decision was to mirror the HTTP/JSON interface of the OpenAI API", and it includes "a PII redactor that anonymizes sensitive information within requests before forwarding them to third-party vendors" and audit logs for "cost attribution, security audit purposes, quality evaluation". In mid-2024 it was "used by close to 30 customer teams and serves 16 million queries per month, with a peak QPS of 25" (Uber Engineering, 11 Jul 2024). 25 queries a second is small: a gateway exists for control, not for throughput.

Bloomberg and Tetrate started Envoy AI Gateway because "traditional rate-limiting based on number of requests doesn't work for controlling usage of LLM providers" (announcement, 18 Oct 2024); renamed Agent Router (v1.1.0, 21 Aug 2026), its README describes two tiers: "The Tier One Gateway handles authentication, top-level routing, and global rate limiting", and a second tier in front of self-hosted models picks the endpoint (README at v1.1.0).

Chip Huyen's AI Engineering (O'Reilly, 2025) makes "Add Model Router and Gateway" step 3 of its five-step platform architecture, after context and guardrails and before caches (table of contents, chapter 10). DOCS

2. Choosing a deployment: what each strategy really measures

When a group has several deployments (the same model in two regions, or at two providers), something picks one per call, and the pick decides latency, cost and how evenly load spreads. Each LiteLLM routing_strategy is a small file in litellm/router_strategy/, and what it measures is easy to get wrong from its name. SOURCE One level down, inside a self-hosted pool, a second router picks the replica by queue and prefix cache: that layer is LLM serving in production, section 1.

3. When a call fails: retry, cool down, or fall back

Retry: the same group again after a short wait (a blip?). Cooldown: stop routing to one deployment for a while (a broken copy?). Fallback: call another group (is this model unusable right now?). LiteLLM chooses by the error's HTTP status: SOURCE

Defaults: num_retries 2, cooldown_time 5 s, at most 5 fallbacks per request; an error whose text contains "APIConnectionError" never triggers a cooldown.

Two cooldown regimes, and a trap. Without allowed_fails, the rules in the table apply: a 429 benches a deployment at once, other errors only once more than 50% of its calls this minute failed and there were at least 5 (DEFAULT_FAILURE_THRESHOLD_PERCENT 0.5, DEFAULT_FAILURE_THRESHOLD_MINIMUM_REQUESTS 5). With allowed_fails, a simpler counter: cool down once failures within cooldown_time exceed it. But the code decides whether you "set" it by comparing with the library default, 3 (_is_allowed_fails_set_on_router). Writing allowed_fails: 3 in a config therefore changes nothing; the parent page's Production stack config contains exactly that line.

Grey bands: more than 4 s in which no call reached C although requests kept coming, which the rules attribute to a cooldown. Seconds from the first request. Every attempt, including those to A, is replayed at the end of section 4.

  • 429: C was benched after its first 429 and came back every 5 to 6 seconds (calls at 0.1, 5.7, 11.8 and 17.8 s). Users never saw an error.
  • 503, default settings: C was picked about one time in three until its fifth failure in the minute (at 7.3 s), then benched until 14.7 s; after that each new failure benched it again.
  • 503, allowed_fails: 3: the same, as the source predicts, plus one user error: request 2 picked C, and both retries picked C again. A retry re-runs the routing choice at random, so with two deployments a request whose first pick is the bad one fails all three tries with probability 1/2 × 1/2 = 1/4 while the bad one is not benched. enable_weighted_failover (async calls, simple-shuffle only) re-picks among the other deployments instead.
  • One deployment in the group: never cooled down (the "single-deployment model group" exemption: benching the only copy would turn a partial outage into a total one), so every request paid two backoff waits and then fell back: about 5.5 s per request, every time.
Two more recorded cases: allowed_fails 1, and a context-window error (depth)
  • 503, allowed_fails: 1: benched after its second failure, back 5 s later.
  • Context window error: never retried; with no fallbacks the user got ContextWindowExceededError in 0.1 s; with either fallbacks or context_window_fallbacks the request went straight to the long-context group.
Predict, then open. A group has two deployments and the bad one returns 500 on every call. You set allowed_fails: 3 and cooldown_time: 60, expecting it to be benched after three failures for a minute. What happens?
It is benched only after more than half of its calls in the current minute failed and there were at least five (the default regime), and the bench lasts 60 s because cooldown_time is honoured. Write allowed_fails: 2 or use allowed_fails_policy (per error type, for example InternalServerErrorAllowedFails) to get a counter that applies.

Outages: plan the fallback, do not just configure it. A fallback is another deployment of the same model, the same model at another provider (Claude is also sold through AWS Bedrock and Google Vertex AI, and OpenAI's models through Azure, AWS Bedrock and, in private preview since October 2026, Vertex AI; open models through many, section 9), or a different model. Check it like a backup generator: is its quota big enough to take all the traffic at once; does it accept the same prompt and tool-call format; does it behave the same on safety; has it been evaluated on your task? It starts with a cold prompt cache, so requests cost more and first tokens come later until it warms. A fallback that has never carried full traffic is untested; fail over on a schedule.

4. Timeouts and retries across layers

An agent's model call passes through several programs that each retry: the provider SDK in your agent, your own loop, the gateway, sometimes a second gateway. Each layer's retries run once for every attempt of the layer above. With the SDK's 2 retries and the gateway's 2, one request can reach the provider 3 × 3 = 9 times:

attempts reaching the provider = (1 + r1) × (1 + r2) × … × (1 + rn)

The rule
Retry at one layer only, the one that knows the most (usually the gateway, which can switch deployments); set the others to 0. Give each layer a timeout shorter than the layer above it, so the inner one gives up first and reports why. A request retried 9 times is a capacity problem, not bad luck. Retry budgets and retry storms are measured on Reliability engineering; which hop's timeout ends a long generation is on HTTP (its Timeout chain tab).

5. Rate limits: three places, three algorithms

A rate limit caps how much one caller may send per unit of time, so one runaway agent cannot take everyone's capacity; past it the server answers 429 Too Many Requests, which "MAY include a Retry-After header indicating how long to wait" (RFC 6585 §4). For LLM traffic the unit cannot be requests alone. Two customers limited to 60 requests a minute: one sends 60 short chats (60 × 1,400 = 84,000 tokens), the other 60 requests each carrying a 50,000-token contract (3 million tokens, 36 times the load for the same "60 requests"). So limits count tokens too, and the usual algorithm is a token bucket holding model tokens (the algorithm is taught on Reliability engineering). An agent behind a gateway meets limits in three places, each counted differently:

Output tokens are unknown at admission, and limiters answer in one of three ways: reserve the worst case and refund later (OpenAI; LiteLLM's tpm_limit), count output as it is produced (Anthropic), or charge after the response (Envoy AI Gateway, which can end 200 tokens over). Alongside token limits, cap concurrent streams per caller (max_parallel_requests): fifty open streams from one tenant are fifty batch slots nobody else can use, whatever the token count.

The gateway's window, recorded. LiteLLM's limiter calls itself "based on a similar one by Envoy proxy" and names its functions "sliding window", but the code keeps one start time and one counter per key: the first request opens a 60-second window, and once 60 whole seconds have passed the next request starts a fresh one at zero. That is a fixed window anchored on the first request, with the fixed window's weakness at the boundary. 6. Budgets and virtual keys: what a dollar cap really does

A budget caps dollars for a key, user, team, organisation or end customer, optionally per period (budget_duration: "30d"). The gateway prices every call from its price table and adds it to each entity's spend. The hard part is concurrency: if the check reads the spend so far, 20 calls arriving together all see the same number and all pass. DOCS

What 1.104.0 does instead: reserve, then settle. Before calling the provider, the proxy estimates the request's maximum cost (its input tokens, plus max_tokens output tokens, or 16,384 if the request sets none, capped at the model's own output limit) and adds it atomically to the key's counter. If that would cross the budget but some is left, the reservation shrinks to what is left and the call goes ahead; if nothing is left, HTTP 422 budget_exceeded. When the call ends the reservation is replaced by the real cost (proxy/spend_tracking/budget_reservation.py). SOURCE

What follows for agents
Send max_tokens on every call. Without it, a small per-key budget serialises an agent's parallel tool calls or subagents, and the 422 arrives long before the money is spent. LITELLM_BUDGET_RESERVATION_MAX_COST_USD caps one request's reservation instead (PR 38647). Budgets nest: "If a key belongs to a team, only the team (and team-member) budgets are enforced" (docs).

Rate limit, quota, capacity: three refusals to keep apart. A rate limit protects capacity right now; a quota or budget caps total use over a period, usually in money (Envoy: "Use QuotaPolicy when you need to cap cumulative token spend, and usage-based rate limiting (this page) when you need to control request velocity."). Anthropic's API answers 429 with a retry-after header for a rate limit; 429 with no retry-after and the code enforced_spend_limit_reached when the monthly spend cap is reached (every retry layer will hit it again until the month ends); and 529 overloaded_error when "the API experiences high traffic across all users" (Anthropic errors). DOCS A gateway should keep the same three apart for its callers: over your limit (wait), out of budget (stop), out of capacity (fall back). Its own 429 (throttling_error, retry-after 60) is the caller's key limit, which no fallback can fix; a provider 429 is capacity, which another deployment can. 7. Caching at the gateway: a memo of whole answers

Not prompt caching. Provider prompt caching keeps the computed attention state for a prompt prefix inside the model server, so the model still generates a fresh answer, cheaper (Context engineering and Caching own it). A gateway response cache stores whole answers: on a match the model is never called.

The key. LiteLLM concatenates every model parameter present in the request (model, messages, temperature, max_tokens, tools ...) and hashes it with SHA-256 (Cache.get_cache_key in litellm/caching/caching.py). Backends: in-memory (default TTL 600 s), Redis, S3, GCS, Azure Blob, disk, and three semantic caches (Redis, Valkey, Qdrant). Per request, cache: {"no-cache": true} skips the lookup, ttl sets the lifetime, and mode: default_off makes caching opt-in. SOURCE

The recording. Cache on (in-memory), the local model behind it, six calls with the same question. MEASURED

A hit returns a sampled answer word for word; one extra space misses

Seconds are what the caller waited (the first call also waited for the shared local model server). Cache key: the first 12 hex digits of the x-litellm-cache-key header, present only on hits.

  • Hit: 0.08 s instead of seconds, no tokens spent.
  • Temperature 0.9: a miss (temperature is part of the key), then a hit that returned the sampled answer word for word. The cache turns a random answer into a fixed one for the TTL; for an agent that retries a step hoping for a different action, that is the opposite of what it wants.
  • One extra space: a miss. Each agent turn appends the last tool result, so an agent's calls almost never hit an exact cache. The gateway cache pays for repeated identical calls (classification, embedding, evals re-run on unchanged items), not for agent loops.

Semantic caching, and why it is the risky one. A semantic cache embeds the prompt and returns a stored answer when a previous prompt is merely similar (cosine similarity above a threshold): LiteLLM's Redis, Valkey and Qdrant backends, Azure API Management's llm-semantic-cache-lookup and llm-semantic-cache-store policies (Microsoft Learn, read 24 Oct 2026). It is the only cache that can return a wrong answer: a hit is a bet that two different questions deserve the same reply, and the threshold trades money saved against wrong answers served. At a gateway three things make it worse: the cache is shared by every caller, so an entry must be scoped per tenant and user or one customer's answer reaches another; the reply is frozen, like any cache hit above; and nobody sees a false hit in an error counter. Use it last and narrowly, after measuring its false-hit rate on your traffic; Caching measures that rate threshold by threshold on real labelled pairs in its Threshold lab.

8. The translation layer: what actually leaves the gateway

A gateway accepts several request formats (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini generateContent) and sends each upstream in whatever format the provider speaks. The deployment's provider prefix decides the outgoing format, and the mapping is not always the obvious one.

The same request, two prefixes: openai/ sends the Responses API, lm_studio/ sends Chat Completions

With openai/, LiteLLM assumed an upstream that speaks OpenAI's newer Responses API and sent POST /v1/responses (the system prompt became instructions, the message became input, and it asked for reasoning.encrypted_content); mlx-lm has no such route, so the caller got a 404 that names the model group, not the format. What translation can lose
Anything one format has and the other does not: Anthropic cache breakpoints, thinking blocks and their signatures, server tools, OpenAI's reasoning items, provider-specific parameters. LiteLLM drops unknown parameters when drop_params: true is set and raises otherwise. When something silently stops working behind a gateway, log the outgoing request body (the proxy's debug log, or a logging proxy like the one used here) before blaming the model.

Provider API versions break gateways too: Anthropic's 2026-10-21 version rejects temperature, top_p and top_k, and its new SDKs send the key as Authorization: Bearer (Service APIs has the change). A gateway that sets X-Api-Key or forwards sampling parameters to Claude must change: drop them for Claude on the new version (as drop_params does for unknown ones) or pin that route's anthropic-version to 2023-06-01.

9. OpenRouter: a gateway you rent, and a market of providers

OpenRouter is a hosted gateway: one OpenAI-compatible endpoint, one key and one bill in front of many model vendors and inference providers (its catalogue size and fees are in the dated table, section 11). It routes two ways. Across models: send a models list and it tries them in order on errors, rate limits and downtime, billing the model that answered (model fallbacks). Across providers of one model, the part with no LiteLLM equivalent: the same open-weights model is served by many companies at different prices, and by default OpenRouter will "Prioritize providers that have not seen significant outages in the last 30 seconds", then "For the stable providers, look at the lowest-cost candidates and select one weighted by inverse square of the price", then "Use the remaining providers as fallbacks" (provider routing). 10. Routing by difficulty: routers and cascades

Sections 2 to 9 route between copies of the same model. Here the gateway picks which model: the cheapest that will answer well. Tier prices differ by a factor of 2 to 40 (dated table, section 11), so savings are large if most traffic is easy, but every misrouted hard question is a worse answer no error counter sees. So a router is measured as a classifier on labelled traffic: answer quality against the share of calls sent to the strong model, beside random routing at the same share (any router can trade cost for quality; a good one does it better than a coin).

Rules come first. Most production routers start as tier rules ("summaries go small") or a small classifier: Huyen describes "an intent classifier that predicts what the user is trying to do" so "simpler queries" go "to cheaper models" (Building A Generative AI Platform, 25 Jul 2024). Context rules send long prompts to pools configured for long context; getting one wrong is what happened in August 2025, when a routing bug sent some Claude Sonnet 4 requests to servers configured for a different context length, up to 16% of them in the worst hour, with normal error rates (Anthropic, 17 Sep 2025). Policy rules pin a tenant to a contracted vendor, keep data in a region, or send sensitive data only to self-hosted models.

Interview rehearsal: design angles (optional)
Design the gateway for 50 internal teams calling three providers. What goes in it?
Virtual keys per team with budgets and rate limits; model groups with several deployments each (regions, providers) and per-deployment timeouts; one retry layer with backoff and a retry budget; cooldowns for broken deployments; fallbacks across model families that were each evaluated; Redis for shared counters across replicas; spend logs and traces tagged with team, model group and the deployment that answered; caching off by default.
A client has a 10 s timeout and 2 retries; the gateway has 5 s per attempt and 2 retries; the provider hangs. How many provider calls, and when does the user hear?
Up to 3 × 3 = 9 calls (measured: 9, the last starting after the user's error at 32.8 s). Fix: one retry layer, inner timeouts shorter than outer ones, and cancellation propagated when the client goes away.
How would you enforce a dollar budget under concurrency?
Reserve the worst-case cost of each request atomically before calling (input tokens plus max output tokens at list price), settle to the real cost afterwards, and refuse when the reservation does not fit. Cap the reservation per request so a missing max_tokens does not serialise the caller. This is what LiteLLM 1.104.0 does.
Fixed window, sliding window or token bucket for an LLM API?
Token bucket (what Anthropic uses): it allows a burst up to the bucket size and then a steady rate, with no boundary double burst. Count tokens, not only requests, and reserve output tokens at admission because they are unknown until the end.
Router or cascade?
A router decides from the prompt before any call: no extra latency, but it must predict difficulty. A cascade calls the cheap model first and escalates when a scorer rejects the answer: it sees the real answer but pays the cheap call and its latency on every hard request. Either is judged by quality against the strong-call share, beside random routing at the same share.
