The whole page in one screen

A gateway (also called an LLM proxy) sits between your agent and the model providers: your code sends every model call to it in one format, and it decides which real endpoint answers, what to do when that endpoint fails, whether the caller is allowed to spend more, and what to log. The parent page, Topic: agentic-frameworks, explains why you would want one (its Reading section 6) and its Production stack tab records one LiteLLM proxy retrying a broken provider and falling back. This page opens the box: every rule below was read from LiteLLM 1.104.0's source and then checked by a recorded run, because several of them are not what the configuration file suggests.

Follow one request through LiteLLM's proxy. Each box is a stage in the order the code runs it; pick a scenario and step through. The same request takes three different paths depending on what the gateway already knows.

What the page found, in one list (each is a section below, with its recording):

1. Six words you need first

Deployment

One concrete endpoint that can answer: a provider, a model id on it, a base URL and a key. In LiteLLM's config each entry of model_list is one deployment.

Model group

The name your code asks for (model="chat"). Every deployment that shares a model_name belongs to the group; the router picks one of them per call. A group of one is common, and it changes the failure rules (section 3).

Provider prefix

The part before the slash in litellm_params.model (openai/, anthropic/, lm_studio/, bedrock/ ...). It chooses the code that speaks to that upstream, so it decides which wire format leaves the gateway (section 8).

Router and proxy

LiteLLM is two things: a Python library whose Router class does routing, retries, cooldowns and fallbacks inside your process, and a proxy server (litellm --config) that wraps the same Router behind HTTP and adds keys, budgets, rate limits and spend logs. Sections 2 and 3 are the Router; 5 and 6 need the proxy and its database.

Virtual key

A key the gateway issues (sk-...) and checks on every call. It carries limits (models allowed, budget, requests and tokens per minute, parallel requests). The real provider keys never leave the gateway.

Cooldown

A deployment the router has decided to stop sending traffic to for a few seconds after failures. Not the same as a fallback: a cooldown moves traffic inside a group, a fallback moves it to another group.

2. Choosing a deployment: six strategies, one recording

The problem. When a group has several deployments (the same model on two Azure regions, or on two providers), something must pick one per call. The pick decides latency, cost and how evenly load spreads. LiteLLM offers several routing_strategy values; each is a small file in litellm/router_strategy/, and what each one actually measures is easy to get wrong from its name. SOURCE

Check what your strategy reads
A strategy that cannot find its input does not fail; it falls back to random or to the first deployment. After changing a routing setting, send a few dozen requests and count which deployment answered (the proxy returns it in the x-litellm-model-id response header).

3. When a call fails: retry, cool down, or fall back

The problem. A failed call can be handled three ways, and they answer different questions. Retry: try again, on the same group, after a short wait (was it a blip?). Cooldown: stop sending traffic to one deployment for a while (is this copy broken?). Fallback: give up on the group and call another one (is this model unusable right now?). LiteLLM decides among them from the error's HTTP status, and the table below is what its code does, not what the docs summarise. SOURCE

From litellm/utils.py (_should_retry: 408, 409, 429 and 5xx), router.py (should_retry_this_error) and router_utils/cooldown_handlers.py (_is_cooldown_required, _should_cooldown_deployment) in 1.104.0. Defaults: num_retries 2, cooldown_time 5 s, at most 5 fallbacks per request; an error whose text contains "APIConnectionError" never triggers a cooldown.

Two cooldown regimes, and a trap. If you do not set allowed_fails, the router uses the rules in the table: a 429 benches a deployment at once (when the group has an alternative), other errors only once more than 50% of its calls this minute failed and there were at least 5 (DEFAULT_FAILURE_THRESHOLD_PERCENT 0.5, DEFAULT_FAILURE_THRESHOLD_MINIMUM_REQUESTS 5). If you set allowed_fails, it switches to a simpler counter: cool down once failures within cooldown_time exceed it. But the code decides whether you "set" it by comparing with the library default, which is 3 (_is_allowed_fails_set_on_router). Writing allowed_fails: 3 in a config therefore changes nothing; the parent page's Production stack config contains exactly that line.

The recording. A group of two: A healthy (0.2 s), C scripted to fail every call. Thirty requests one after another, 0.3 s apart, num_retries: 2. Each mark below is one call that reached C; a red mark is a request whose user got an error. MEASURED

Grey bands: more than 4 s in which no call reached C although requests kept coming, which the rules above attribute to a cooldown. Times in seconds from the first request. Every attempt of every request, including the ones that went to A, is in the Failure lab.

  • 429: C was benched after its first 429 and came back every 5 to 6 seconds (calls at 0.1, 5.7, 11.8 and 17.8 s). Users never saw an error.
  • 503, default settings: C was picked about one time in three until its fifth failure in the minute (at 7.3 s), then benched until 14.7 s; after that each new failure benched it again.
  • 503, allowed_fails: 3: the same rules, as the source predicts, and one user error: request 2 picked C, and both retries picked C again. A retry inside a group re-runs the routing choice at random; with two deployments, a request whose first pick is the bad one fails all three tries with probability 1/2 × 1/2 = 1/4 while the bad one is not benched. LiteLLM's enable_weighted_failover (async calls, simple-shuffle only) exists to re-pick among the other deployments instead.
  • 503, allowed_fails: 1: benched after its second failure, back 5 s later.
  • One deployment in the group: no cooldown ever (the "single-deployment model group" exemption: benching the only copy would turn a partial outage into a total one), so every request paid two backoff waits and then fell back: about 5.5 s per request, every time.
  • Context window error: never retried; with no fallbacks the user got ContextWindowExceededError in 0.1 s; with either fallbacks or context_window_fallbacks the request went straight to the long-context group.
Predict, then open. A group has two deployments and the bad one returns 500 on every call. You set allowed_fails: 3 and cooldown_time: 60, expecting it to be benched after three failures for a minute. What happens?
It is benched only after more than half of its calls in the current minute failed and there were at least five (the default regime), and the bench lasts 60 s because cooldown_time is honoured. Write allowed_fails: 2 or use allowed_fails_policy (per error type, for example InternalServerErrorAllowedFails) to get a counter that actually applies.

4. Timeouts and retries across layers

The problem. An agent's model call passes through several programs, and most of them retry: the provider's SDK in your agent, your own loop, the gateway, sometimes a second gateway or a provider-side router. Each layer's retries run once for every attempt of the layer above, so they multiply:

attempts reaching the provider = (1 + r1) × (1 + r2) × … × (1 + rn)
ri
retries at layer i (OpenAI and Anthropic Python SDKs: 2 by default, with a 600-second timeout; LiteLLM: num_retries, 2 in this config, and a default request timeout of 6,000 seconds)

Defaults read from openai/_constants.py (openai 2.54.0), anthropic/_constants.py (anthropic 1.11.0) and litellm/constants.py (DEFAULT_REQUEST_TIMEOUT_SECONDS = 6000.0), 6 October 2026. SOURCE

The recording. Provider C hangs for 30 seconds on every call. The gateway gives each attempt 5 seconds and retries twice. The client is the OpenAI Python SDK, run three ways. MEASURED

Each grey bar is one call the provider received and worked on for its full 30 s (it cannot tell that the caller gave up until it writes the answer). Blue ticks: the SDK sending; the red line: when the user got an error. Replayed step by step in the Failure lab.

  • SDK defaults with a 10-second timeout: the user got APITimeoutError after 32.8 s and three sends; the provider received 9 calls, the last one starting at 36.9 s, four seconds after the user had been told it failed. 270 seconds of provider work for one failed request. The gateway does not stop its retry chain when the client hangs up.
  • The same with max_retries=0: 3 calls, error after 10.2 s.
  • SDK timeout 60 s: the gateway's own chain finished first (about 20 s), returned 408, and the SDK retried it, twice: 9 calls, error after 61.9 s.

The harnesses page Other coding harnesses hit the same thing from the other side: Gemini CLI 0.62.0 waits 60 s for headers and retries up to 10 times, so against a slow local server its retries overlapped and multiplied the load until the server ran out of memory. MEASURED there

The rule
Retry at one layer only, the one that knows the most (usually the gateway, which can switch deployments); set the others to 0. Give each layer a timeout shorter than the layer above it, so the inner one gives up first and reports why. And make the total budget visible: a request that has been retried 9 times is a capacity problem, not bad luck. Why retries need a budget (a cap on retries as a share of traffic) and how a retry storm keeps an overloaded service down is measured on Reliability engineering; which hop's timeout ends a long generation is on HTTP (its Timeout chain tab).

5. Rate limits: three places, three algorithms

The problem. A rate limit caps how much one caller may send per unit of time, so one runaway agent cannot take everyone's capacity. For LLM traffic the unit is not only requests: a request's cost is its tokens, and the output tokens are unknown until it finishes. An agent behind a gateway meets limits in three places, each counted differently:

Provider (Anthropic, per organisation and model class)requests, input tokens, output tokens per minute (RPM, ITPM, OTPM)token bucket: "capacity is continuously replenished up to your maximum limit, rather than being reset at fixed intervals"; "a rate of 60 requests per minute (RPM) might be enforced as 1 request per second" DOCS429 with retry-after

Anthropic's input-token limit counts only uncached input for most models ("only uncached input tokens count toward your ITPM"), so with an 80% cache hit rate a 2,000,000 ITPM limit admits 10,000,000 input tokens a minute; output tokens count as they are generated, so a large max_tokens costs nothing against OTPM (rate limits, read 6 Oct 2026). LiteLLM's token limit has to guess the output before the call: when max_tokens is missing it reserves a floor of 1,024 output tokens (DEFAULT_MAX_TOKENS_ESTIMATE 4,096 divided by 4, capped at a quarter of the smallest TPM limit) and corrects after the response. DOCS SOURCE

The gateway's window, recorded. LiteLLM's limiter file calls itself "based on a similar one by Envoy proxy" and names its functions "sliding window", but the code keeps one start time and one counter per key: the first request opens a 60-second window, every request in it adds 1, and once 60 whole seconds have passed the next request starts a fresh window at zero. That is a fixed window anchored on the first request, not a sliding one, and it has the fixed window's weakness at the boundary. Two keys with rpm_limit: 10; one sends a request every second for 130 s, the other sends 1 request, waits until second 50, sends 9, then 10 more just after the window rolls over. MEASURED

The burst key had 19 requests accepted between second 50 and second 65, almost twice its limit inside 15 seconds, and then 429s; the steady key was accepted for 10 seconds out of every 60 (seconds 0 to 9, 61 to 70, 121 to 129: the limiter counts whole wall-clock seconds, and this run happened to start just before a second ticked over). On the same burst trace a sliding log would have accepted at most 10 in any 15 seconds, and a token bucket holding 10 and refilling one every 6 seconds at most 12 (its full bucket plus two refills), which is the shape Anthropic's limiter imposes downstream. The five classic algorithms (fixed window, sliding log, sliding window counter, token bucket, leaky bucket) are taught and animated on one burst on Reliability engineering; the Limits lab replays these two recorded traces through LiteLLM's rule (which reproduces every accept and reject) and through the others.

Several gateway replicas
Without Redis each LiteLLM process keeps its own counters, so three replicas behind a load balancer admit three times the limit. With redis_host set the same window logic runs as a Lua script on the shared Redis (BATCH_RATE_LIMITER_SCRIPT in the same file). SOURCE

6. Budgets and virtual keys: what a dollar cap really does

The problem. A budget caps spend in dollars for a key, a user, a team, an organisation or an end customer, optionally resetting on a period (budget_duration: "30d", also seconds, minutes, hours). The gateway prices every call from its price table and adds it to each entity's spend. The hard part is concurrency: if the check reads the spend so far and 20 calls arrive together, all 20 see the same number and all 20 pass. DOCS

What 1.104.0 does instead: reserve, then settle. Before calling the provider, the proxy estimates the request's maximum cost (its input tokens counted, plus max_tokens output tokens, or 16,384 if the request sets none, capped at the model's own output limit, at the configured prices) and adds it atomically to the key's counter. If that would cross the budget but some budget is left, the reservation is shrunk to what is left and the call goes ahead; if nothing is left, the call is refused with HTTP 422 budget_exceeded. When the call ends the reservation is replaced by the real cost (proxy/spend_tracking/budget_reservation.py). SOURCE

The recording. Budget $0.0004 per key; each call really costs $0.00008 (40 input tokens at $1 per million, 8 output tokens at $5 per million), so 5 calls fit. The fake provider takes 2 s per call. MEASURED

  • Reservation switched off (general_settings: disable_budget_reservation: true, which the docs keep for "temporary mitigation"): all 20 simultaneous calls accepted, final spend $0.0016, four times the budget; the second wave was refused. This is the soft cap the parent page describes.
  • Ten calls one after another: exactly 5 accepted, final spend $0.0004, then 422s. No overshoot.
  • Twenty at once, no max_tokens: 1 accepted, 19 refused in about 0.4 s. Each request reserved about $0.082 (16,384 output tokens at $5 per million), far more than the whole budget, so the first was shrunk to the budget and the rest found nothing left. A second wave 4 s later: again 1. The key has become a queue of one.
  • Twenty at once with max_tokens: 16: each reserved about $0.000095, so 4 fitted and a fifth took the remainder: 5 accepted, final spend exactly $0.0004.
Correction to the parent page
The parent's Production stack tab recorded a sequential overshoot of one call ($0.0008 cap, three calls of $0.00033, final $0.00099) and concluded that a key "can overshoot its cap by the calls in flight", with batched spend writes "widening the overshoot under parallel traffic". On LiteLLM 1.104.0, the version both pages ran, the sequential overshoot reproduces (the last call is let through with whatever budget remains, and can cost more), but parallel calls do not overshoot: the reservation blocks them. LiteLLM's docs: "Budget reservation is enabled by default", and switching it off "can allow concurrent requests to exceed a configured budget" (docs); known gaps are requests whose cost cannot be estimated, which skip it (issue 35524), and project budgets (issue 34101). MEASURED SOURCE
What follows for agents
Send max_tokens on every call. Without it, a small per-key budget serialises an agent's parallel tool-calling or subagents, and the 422 arrives long before the money is spent. LITELLM_BUDGET_RESERVATION_MAX_COST_USD caps one request's reservation instead (PR 38647). Budgets nest: "If a key belongs to a team, only the team (and team-member) budgets are enforced" (docs). A provider's own spend cap is a separate, monthly thing: Anthropic's returns a 429 with no retry-after and the error code enforced_spend_limit_reached, which every retry layer will hit again until the month ends. 7. Caching at the gateway: an exact-match memo, not prompt caching

Two different things share the word. Provider prompt caching happens inside the model server: the provider keeps the computed attention state (the KV cache) for a prompt prefix, so a later request that starts with the same prefix is cheaper and faster, but the model still generates a fresh answer. A gateway response cache stores whole answers: if a new request matches a stored one, the gateway returns the stored answer and the model is never called. The first is taught on Context engineering and Caching; this section is the second.

What the key is. LiteLLM builds the key by concatenating every model parameter present in the request (model, messages, temperature, max_tokens, tools ...) and hashing it with SHA-256 (Cache.get_cache_key in litellm/caching/caching.py). Backends: in-memory (default TTL 600 s), Redis, S3, GCS, Azure Blob, disk, and three semantic caches (Redis, Valkey, Qdrant) that match by embedding similarity instead. Per request, cache: {"no-cache": true} skips the lookup, ttl sets the lifetime, and mode: default_off makes caching opt-in. SOURCE

The recording. Cache on (in-memory), the local model behind it, six calls with the same question. MEASURED

Seconds are what the caller waited. The first call also waited for the shared local model server, which other work was using. Cache key: the first 12 hex digits of the x-litellm-cache-key header, present only on hits.

  • Hit: 0.08 s instead of seconds, no tokens spent.
  • Temperature 0.9: a miss (temperature is part of the key), then a hit that returned the sampled answer word for word. The cache turns a random answer into a fixed one for the TTL; for an agent that retries a step hoping for a different action, that is the opposite of what it wants.
  • One extra space: a miss. Agents rarely repeat a request exactly: each turn appends the last tool result, so an agent's calls almost never hit an exact cache. The gateway cache pays for repeated identical calls (classification, embedding, evals re-run on unchanged items), not for agent loops.
Semantic caching
A semantic cache returns a stored answer for a request that is merely similar (cosine similarity above a threshold). It is the only cache that can be wrong: Caching measures how often, threshold by threshold, in its Threshold lab. Not repeated here.

8. The translation layer: what actually leaves the gateway

The problem. A gateway accepts several request formats (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini generateContent) and sends each upstream in whatever format that provider speaks. The provider prefix of the deployment decides the outgoing format, and the mapping is not always the obvious one.

The recording. One Anthropic-format request (POST /v1/messages, with a system prompt) for the local model, through two deployments of the same model that differ only in prefix. The locking proxy in front of the model server logged what arrived. MEASURED

With openai/, LiteLLM assumed an upstream that speaks OpenAI's newer Responses API and sent POST /v1/responses (the system prompt became instructions, the message became input, and it asked for reasoning.encrypted_content); mlx-lm has no such route, so the caller got a 404 that names the model group, not the format. With lm_studio/ it sent ordinary /v1/chat/completions and the caller got a well-formed Anthropic reply. The sibling Other coding harnesses found the same with a Responses request: openai/ forwards /responses unchanged, lm_studio/ translates it. That route is how the sibling ran Codex (which speaks only the Responses API; wire_api = "chat" is now a config error) against the local model, and it is why the prefix matters.

What translation can lose
Anything one format has and the other does not: Anthropic cache breakpoints, thinking blocks and their signatures, server tools, OpenAI's reasoning items, provider-specific parameters. LiteLLM drops unknown parameters when drop_params: true is set and raises otherwise. When something silently stops working behind a gateway, log the outgoing request body (the proxy's debug log, or a logging proxy like the one used here) before blaming the model.

9. OpenRouter: a gateway you rent, and a market of providers

What it is. OpenRouter is a hosted gateway: one OpenAI-compatible endpoint, one key and one bill in front of many model vendors and many inference providers. Its public catalogue listed models from model authors on 6 October 2026, of them free variants (GET /api/v1/models, no key needed). Money, from its FAQ the same day: it passes provider prices through with "no markup on inference pricing"; buying credits costs 5.5% ($0.80 minimum) by card and 5% in crypto; with your own provider keys (BYOK) "Pay-as-you-go includes $25,000 per month with no BYOK fee" and 5% above that; free models allow 50 requests a day, 1,000 once you have bought $10 of credits (FAQ). DOCS The parent page has its company news (the Stripe announcement); not repeated.

Two kinds of routing. Across models: send a models list and it tries them in order on errors, rate limits and downtime, billing the model that answered (the parent page quotes the details). Across providers of one model, the part with no LiteLLM equivalent: the same open-weights model is served by many companies at different prices, and by default OpenRouter will "Prioritize providers that have not seen significant outages in the last 30 seconds", then "For the stable providers, look at the lowest-cost candidates and select one weighted by inverse square of the price", then "Use the remaining providers as fallbacks" (provider routing). The provider object overrides it: order, only, ignore, allow_fallbacks (default true), require_parameters, data_collection, zdr, quantizations, sort (price, throughput or latency), max_price, preferred_min_throughput, preferred_max_latency; the suffixes :nitro and :floor mean sort by throughput and by price. 10. Learned routers: choosing the model per request

The problem. Sections 2 to 9 route between copies of the same model. A different question: given a cheap model and a strong one, can the gateway send each request to the cheapest model that will answer it well? If most traffic is easy, the savings are large; the risk is that the router cannot tell which requests are easy. The measure that matters is a curve: answer quality against the share of calls sent to the strong model, compared with routing at random at the same share (any router can trade cost for quality; a good one does it better than a coin).

The experiment. 48 questions written for this page with answers that can be graded exactly, in four families of 12: one-step facts, arithmetic word problems of 2 to 7 steps, "what does this Python print", and letter puzzles (count the r's in a made-up word, or write it backwards). Each question was answered once by the local model on Apple M1 Pro (Qwen3 4B, temperature 0, up to 512 tokens) and once by Claude Haiku 4.5 (Claude Code CLI, no tools, the same instruction), each ending with an "ANSWER:" line. Then LiteLLM's complexity router scored every question offline. MEASURED

Vertical axis: questions answered correctly out of 48; horizontal: share of questions sent to Haiku. The dashed line is random routing (expected value). Every question and both answers are in the Routing lab.

  • The two models: local 38 of 48, Haiku 44 of 48. Both got every fact and every arithmetic problem; the local model missed 4 code questions and 6 letter puzzles (8 of its 10 misses ran out of its 512-token allowance without an ANSWER line); Haiku missed 4 backwards-spelling puzzles.   • The complexity router scored all 12 code questions MEDIUM (they contain code) and all 36 others SIMPLE. Sending MEDIUM up: 42 right with 25% of calls to Haiku. Random routing at 25% would expect 39.5; a perfect router needs only 6 strong calls (12.5%) for 44. RouteLLM's metric, the share of the quality gap recovered, is (42 − 38) / (44 − 38) = 0.67.
  • Why it worked, and where it did not: here the families the small model failed happened to differ in surface features (code), so a keyword rule found half of them. It sent none of the letter puzzles, which look simple and are hard for a small model because it sees tokens, not letters. A router's features must predict your cheap model's failures on your traffic; that is what training on preference data, or on your own graded logs, buys over keywords.
What this experiment is not
A small, invented question set and one run per model; a different 4B model or a larger token allowance would move the numbers. It shows how to evaluate a router (quality against strong-call share, beside random and an oracle), not how good routers are in general.

A hand-built DAG engine already does the workflow half of what LangGraph would (the parent page's section 10; LangChain and LangGraph in depth). Behind a gateway it should keep one job for itself: each node's deadline, passed down as the gateway call's timeout, so a slow branch fails fast instead of waiting through the gateway's whole retry chain. Retries belong in one place; with a gateway in front, that place is usually the gateway.

Common mistakes

Retrying in the SDK, in the agent loop and in the gateway
Attempts multiply (section 4). Pick one layer; set the SDK client's max_retries to 0 when a gateway retries for it.
Treating a 429 from the gateway like a 429 from the provider
A gateway 429 (throttling_error, retry-after 60) is your own key's limit; waiting does not help other keys and a fallback to another model will not help either. A provider 429 is capacity; a fallback or another deployment helps.
Expecting a 10 RPM key to mean "at most 10 in any minute"
LiteLLM's window starts at the first request and resets whole: 19 in 15 seconds were accepted here (section 5). If the upstream enforces a smooth token bucket, smooth on your side too.
Reading a budget as an exact meter, or as a soft cap
In 1.104.0 it is neither: parallel calls are held back by worst-case reservations, and the last sequential call can overshoot by its own cost (section 6).
Caching agent calls at the gateway
Every turn's request differs from the last, so exact hits are rare; when they happen they replay a sampled answer. Cache deterministic, repeated calls only (section 7).
Running evals through a router that mixes providers
Different quantisations and context limits behind one model name (section 9). Pin the provider and record which one answered.
Trusting a learned router without testing it on your own traffic
The keyword router tested here sent every question containing code to the strong model and none of the letter puzzles, whatever their difficulty: its features saw code, not difficulty (section 10). Measure its quality-cost curve against random routing on a sample of your requests before turning it on.

Interview questions

Design the gateway for 50 internal teams calling three providers. What goes in it?
Virtual keys per team with budgets and rate limits; model groups with several deployments each (regions, providers) and per-deployment timeouts; one retry layer with backoff and a retry budget; cooldowns for broken deployments; fallbacks across model families that were each evaluated; Redis for shared counters across replicas; spend logs and traces tagged with team, model group and the deployment that answered; caching off by default.
Retry, cooldown, fallback: what is the difference?
Retry: same group again after a wait (blips). Cooldown: stop routing to one deployment for a while (a broken copy). Fallback: switch to another group (the model is unavailable or unsuitable, for example the prompt is too long).
A client has a 10 s timeout and 2 retries; the gateway has 5 s per attempt and 2 retries; the provider hangs. How many provider calls, and when does the user hear?
Up to 3 × 3 = 9 calls (measured: 9, the last starting after the user's error at 32.8 s). Fix: one retry layer, inner timeouts shorter than outer ones, and cancellation propagated when the client goes away.
How would you enforce a dollar budget under concurrency?
Reserve the worst-case cost of each request atomically before calling (input tokens plus max output tokens at list price), settle to the real cost afterwards, and refuse when the reservation does not fit. Cap the reservation per request so a missing max_tokens does not serialise the caller. This is what LiteLLM 1.104.0 does.
Fixed window, sliding window or token bucket for an LLM API?
Token bucket (what Anthropic uses): it allows a burst up to the bucket size and then a steady rate, with no boundary double burst. Count tokens, not only requests, and reserve output tokens at admission because they are unknown until the end.
When does a learned router pay off?
When traffic mixes easy and hard requests, the cheap model is good enough on the easy ones, and the router's features actually predict difficulty on your traffic. Measure the quality against the share sent to the strong model, compared with random routing at the same share.

Reading the rows
LiteLLM (anchored window): one start time and one counter; reset whole once 60 s have passed since the start. Calendar minute: reset at every whole minute of the clock; what LiteLLM's router uses for a deployment's own rpm. Sliding log: remember every accepted request and allow a new one if fewer than the limit were accepted in the last 60 s; exact, memory grows with the limit. Token bucket: a bucket holding up to the limit, refilled continuously at limit per 60 s, each request takes one token; what Anthropic says it uses for the Claude API.
