1. From a Python function to a tool schema

A model cannot call Python. It can only emit text, and tool calling works because the model was trained to emit a small JSON object (a tool name and its arguments) when the request lists tools, each described by a JSON Schema: a JSON description of an object's fields, their types, which are required, and a sentence about each. The harness root explains the wire format ({{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}, Reading, section 2; and {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}, with a real tokenised tool call). Writing those schemas by hand is tedious and drifts from the code. The first thing a typed library does is derive the schema from the function: the parameter names and type hints give fields and types, defaults decide what is optional, and the docstring gives descriptions.

Same function, given to each library's own tool decorator, schema printed by the library's code with no model call MEASURED. The function has three required parameters and one with a default, and a Google-style docstring with an Args: block:

def edit_file(path: str, old: str, new: str, count: int = 1) -> str:
    """Replace the exact text old with new in a file.

    Args:
        path: File to edit, relative to the repository root.
        old: Text to find; must occur exactly `count` times.
        new: Replacement text.
        count: How many occurrences to expect.
    """

What differs, and why it matters. Four libraries, four schemas for one function:

  • Pydantic AI keeps count optional with its default, copies each Args: line into that field's description, and adds "additionalProperties": false. It validates the model's arguments with Pydantic before your function runs; a type error becomes a retry message to the model, not an exception in your code.
  • The OpenAI Agents SDK marks the schema strict and so lists all four fields as required, count included. That is not a bug: OpenAI's strict mode requires every property to be listed in required and additionalProperties: false ({{function calling guide|https://developers.openai.com/api/docs/guides/function-calling}}). The schema still shows "default": 1 as a hint, but the model must always send a value; a default in your Python signature is never used.
  • smolagents drops the default and marks count "nullable": true instead, a keyword from OpenAPI rather than JSON Schema. Its @tool decorator also refuses a function whose docstring lacks an Args: line for every parameter.
  • Google ADK, on the path a non-Gemini model takes, sends no per-argument descriptions at all: the whole docstring becomes the tool description, and each field gets only a title. The recorded ADK request on the running example shows the same shape on the wire.

The lesson is not that one is right. It is that the schema the model sees is generated, so read it: the cheapest debugging step with any of these libraries is to log the first request and look at the tools array. The parent topic's {{Same agent, six ways|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} tab shows every request each framework sent on one task.

Predict: with the Agents SDK's strict schema the model always sends count. Which value actually runs if you never meant the model to choose it?
Whatever the model sends, usually the hint it was shown (1). Your Python default never runs, because the argument is always present. If the model should not choose the value, keep the parameter out of the tool's signature (pass it through the run's context) rather than giving it a default. Strict schemas move defaults out of the model's reach; if the default matters, say it in the description.
