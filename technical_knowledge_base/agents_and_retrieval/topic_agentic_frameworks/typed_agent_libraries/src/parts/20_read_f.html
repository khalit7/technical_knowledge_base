6. Google ADK: a runtime with sessions, events and workflow agents

The idea. Google's Agent Development Kit describes itself as "the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale", available in Python, TypeScript, Go, Java and Kotlin, with adapters for "many other models and model providers, including locally running models" ({{adk.dev|https://adk.dev/}}, read 6 Oct 2026). Where the other three hand you a function that runs a loop, ADK hands you a small runtime: an agent, a Runner that executes it, a SessionService that stores what happened, and a stream of events (one per model reply, tool call or tool result) that the runner yields as the run proceeds.

Other models go through LiteLLM. For a model that is not Gemini, google-adk 2.11.0 needs LiteLLM; every ADK run here used LiteLlm(model="openai/" + name, api_base=...) against the local server's Chat Completions endpoint. The provider prefix is not cosmetic: it decides the wire format. Section 8 of {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}} (the translation layer) sent an Anthropic /v1/messages request through the LiteLLM proxy: an openai/ deployment forwarded it upstream as the OpenAI Responses API (/v1/responses, which the local server does not serve), while an lm_studio/ deployment sent /v1/chat/completions and worked.

Agents

  • LlmAgent (also exported as Agent): instruction, tools (plain functions become FunctionTools), optional output_schema and output_key, optional sub_agents. ADK appends a line to your instruction naming the agent: the recorded request ends with 'You are an agent. Your internal name is "fixer". The description about you is "Fixes failing tests by editing code."', and tool results go back wrapped as {"result": ...} MEASURED.
  • Workflow agents that call no model themselves: SequentialAgent, ParallelAgent and LoopAgent run their sub-agents in a fixed pattern; version 2 adds graph workflows (a workflow package of nodes and edges in the 2.11.0 wheel; the docs announce "ADK TypeScript 2.0 GA ... with graph workflows support"). These are the root's workflow patterns as classes ({{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}}, Reading, section 1).
  • Transfer: an agent with sub_agents gets a transfer_to_agent(agent_name, transfer_reason) tool whose agent_name is an enum of the valid names, so the model cannot invent one (tools/transfer_to_agent_tool.py). Same idea as the Agents SDK's handoffs, one tool instead of one per target. Recorded: MEASURED.

State as a ledger of events

A session holds the events and a state dictionary. State is never assigned directly in a well-behaved agent: a tool, callback or agent puts a change in an event's state_delta, and the session service applies it when the event is appended, so every change is logged next to what caused it ({{state docs|https://adk.dev/sessions/state/}}). Key prefixes give scope: no prefix is this session, user: is shared across a user's sessions, app: across all users, temp: lives for one invocation and is "Not Persistent". output_key="triage" writes the agent's final reply into state["triage"], and another agent's instruction can read it with {triage} (or {triage?} when it may be absent): that is how a SequentialAgent passes data from one step to the next.

Typed output

output_schema is sent to the model as a response format; ADK validates the reply and stores the parsed object under output_key. When the agent also has tools and the model is not known to support both at once, ADK adds a set_model_response tool and an instruction beginning "IMPORTANT: You have access to other tools, but you must provide your final response using the set_model_response tool" (flows/llm_flows/prompt/_schema.py): the same trick as Pydantic AI's final_result. The measured behaviour on the local model is in section 2.

The seventh way: ADK on the running example

The parent's Same agent tab compared six ways to write one agent but not ADK. Same task, same four tool bodies, same system prompt, local model, a 15-call cap: MEASURED. ADK's default cap is 500 model calls per run (agents/run_config.py, overridable with ADK_MAX_LLM_CALLS), the highest of the four: set your own.

A2A in one call, and deployment

to_a2a(agent) wraps any ADK agent as an A2A server (the agent-to-agent protocol, on the wire on {{Agent-to-agent and beyond|n:3f05c17b0d0d81199373d4d0b18706d8}}), a Starlette web app whose agent card (the JSON document other agents fetch to learn what this one does) is built automatically. Fetched in-process with no model call MEASURED: Two things to notice: the card lists every tool as a public "skill", names and descriptions included, so review it before exposing an agent; and ADK's A2A classes print "[EXPERIMENTAL] ... subject to breaking changes" warnings in 2.11.0, while "A2A protocol and SDK are themselves not experimental". Deployment targets in the docs are Google Cloud's Agent Runtime, Cloud Run and GKE, or any container (not run here).
