6. Guardrails, sessions and state

A parallel guardrail is a latency optimisation, not a gate

A guardrail checks the input (before the agent) or the output (after it) and can trip a tripwire, an exception that ends the run. In the Agents SDK input guardrails default to run_in_parallel=True (guardrail.py, line 100): the check and the agent's first model call start together. The docs: "if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; with run_in_parallel=False "the agent never executes" ({{guardrails docs|https://openai.github.io/openai-agents-python/guardrails/}}).

One more lesson came free: told to answer only YES or NO, the small checker model wrote the poem instead ("TIDES WHISPER SECRETS TO THE SHORE ..."); the guard tripped only because its parser treated anything but YES as NO. A guardrail model reads the same input it is guarding against, so parse its answer fail-closed. (A first version gave the checker a typed output, which failed on every request on this server for the reason in section 2.) Anything with side effects belongs behind a blocking check or a tool guardrail, which runs before each tool call. A blocking guardrail costs one extra model call of latency on every request that passes, plus its tokens.

Sessions are history, not durable execution

A session stores a conversation's items so the next Runner.run with the same session sends them again. Recorded with SQLiteSession: two turns, 1 row in agent_sessions, 4 rows in agent_messages; the second request carried 4 messages (system, the stored first exchange, the new question) and answered "Kestrel" MEASURED. A run that crashes between two tool calls is not resumed.

ADK: state as a ledger of events, with scopes

output_key="triage" writes the agent's final reply into state["triage"], and another agent's instruction reads it with {triage} (or {triage?} when it may be absent): that is how a SequentialAgent passes data from one step to the next. Memory that outlives a session is owned by {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}.

ADK: A2A in one call

to_a2a(agent) wraps any ADK agent as an A2A server (the agent-to-agent protocol, on the wire on {{Agent-to-agent and beyond|n:3f05c17b0d0d81199373d4d0b18706d8}}), a Starlette web app whose agent card (the JSON document other agents fetch to learn what this one does) is built automatically. Fetched in-process, no model call MEASURED: /.well-known/agent-card.json returned the name and description, a JSON-RPC interface at protocol version 1.0, and 5 skills: model, list_files, read_file, edit_file, run_tests. The card lists every tool as a public "skill", names and descriptions included, so review it before exposing an agent.

A2A status and deployment

ADK's A2A classes print "[EXPERIMENTAL] ... subject to breaking changes" warnings in 2.11.0, while "A2A protocol and SDK are themselves not experimental". Deployment targets in the docs: Google Cloud's Agent Runtime, Cloud Run and GKE, or any container (not run here).
