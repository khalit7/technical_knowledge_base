4. OpenAI Agents SDK: few primitives, everything is a tool

The idea. OpenAI calls the SDK "a production-ready upgrade of our previous experimentation for agents, Swarm" and lists its primitives as agents ("LLMs equipped with instructions and tools"), handoffs and agents as tools, and guardrails, plus sessions, tracing, realtime voice agents and, newest, sandbox agents that "run specialists inside real isolated workspaces" ({{SDK home|https://openai.github.io/openai-agents-python/}}, read 6 Oct 2026). It is still 0.x after 19 months on PyPI. Despite the name it is not tied to OpenAI's models: OpenAIChatCompletionsModel talks to any Chat Completions server (every run here used the local model), and a LiteLLM adapter covers other providers.

The loop and when it stops

Runner.run(agent, input) loops: call the model, run the tools it asked for, repeat. Without an output_type, the first reply with no tool call is the final output. With one, the SDK sends the type as a JSON-schema response format (a request field asking the provider to constrain the reply) and validates the reply text against it; if validation fails, the run raises ModelBehaviorError unless you registered an error handler for invalid_final_output: there is no automatic retry (run_internal/turn_resolution.py, lines 1010 to 1060). The cap is 10 turns (run_config.py, line 45), lower than Pydantic AI's 50; a coding task that reads a few files, edits and tests can need more. tool_use_behavior changes the stopping rule: "stop_on_first_tool" or StopAtTools([...]) end the run with a tool's output instead of asking the model again (agent.py, line 396).

Handoffs are tools named transfer_to_<agent>

A handoff passes the whole conversation to another agent, which then owns it. The SDK implements it with no new machinery: each agent in handoffs=[...] becomes a tool whose name is transfer_to_ plus the agent's name and whose description is "Handoff to the name agent to handle the request." plus its handoff_description (handoffs/__init__.py, line 214). When the model calls it, the tool's output is {"assistant": "fixer"}, and the next request goes out with the new agent's instructions and tools and, by default, "the entire previous conversation history" ({{handoffs docs|https://openai.github.io/openai-agents-python/handoffs/}}). An input_filter can cut that history; the opt-in nest_handoff_history summarises it, and the source warns that "Nesting does not redact sensitive data" (run_config.py, line 378).

The request-by-request view is on the {{Mechanisms, recorded|#t-mech}} tab. Two source details matter once a reply can hand off to more than one agent: if the model calls several handoff tools in one reply, only the first runs and the others get the tool output "Multiple handoffs detected, ignoring this one." (run_internal/turn_resolution.py); and nest_handoff_history defaults to off (RunConfig, "Opt-in beta"). Section 6 of {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}} (handoffs against agents-as-tools) measures what that costs: with a two-problem message the second problem was never handled after a handoff, while agents-as-tools handled both. When several agents help and when they hurt is the subject of that page.

Guardrails run in parallel by default

A guardrail is a check on the input (before the agent) or the output (after it) that can trip a tripwire: an exception that ends the run. Input guardrails default to run_in_parallel=True (guardrail.py, line 100): the check and the agent's first model call start together, which saves latency, and the docs say plainly that "if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; with run_in_parallel=False "the agent never executes" ({{guardrails docs|https://openai.github.io/openai-agents-python/guardrails/}}).

Recorded: the same off-topic request ("Write a short poem about the sea.") against the fixer agent guarded by a topic checker (itself a small agent told to answer YES or NO; our first version gave it a typed output, which failed on this server for the reason in section 2): MEASURED. Parallel guardrails are a latency optimisation, not a safety boundary: anything with side effects belongs behind a blocking check or a tool guardrail, which runs before each tool call.

Sessions and tracing

A session stores a conversation's items so the next Runner.run with the same session sends them again. Recorded with SQLiteSession: MEASURED. A session is history, not durable execution: a run that crashes between two tool calls is not resumed.

Tracing records each run as a trace of spans (model calls, tool calls, handoffs, guardrails) and is on by default, exporting to OpenAI's dashboard. By default the spans include "LLM inputs and outputs" and "function call inputs and outputs"; turn that off with trace_include_sensitive_data=False, or tracing itself with OPENAI_AGENTS_DISABLE_TRACING=1, set_tracing_disabled(True) or per run; it is unavailable under Zero Data Retention ({{tracing docs|https://openai.github.io/openai-agents-python/tracing/}}). Recorded with no OpenAI key, the default: MEASURED. If you run a non-OpenAI model with an OpenAI key in the environment, your prompts and tool outputs go to OpenAI's trace store unless you switch it off: check this before using the SDK on private data.

Predict: you add a blocking input guardrail that calls a small model to classify every request. What does it cost on requests that pass?
One extra model call of latency before the agent starts, on every request, plus its tokens. A parallel guardrail hides the latency but pays the agent's first call on requests that fail. Choose by what a failed request may do before it is stopped: if the agent's first step can have side effects, block.
