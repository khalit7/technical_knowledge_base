4. How each library runs the loop

All four run the same loop (call the model, run what it asked for, append, repeat; owned by {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}). What differs is the stopping rule, the default cap, and what an action is.

Pydantic AI: a hidden result tool and a graph underneath

By default the output type travels as an extra tool named final_result (_output.py, line 73), described by the output class's docstring (ours: "Triage of one failing test.") or else as "The final response which ends this conversation" (line 74), and the request sets tool_choice to "required". A model that ignores tool_choice, or a server that drops it (this one does), can answer in prose; Pydantic AI then parses the prose as JSON and sends back "Invalid JSON" plus "Fix the errors and try again", which does not say "call final_result". That is how the parent's Same agent tab lost 3 of 4 Pydantic AI runs after the code was already fixed. If final_result comes alongside other tool calls in one reply, the end strategy decides: 'graceful' (the default since 2.0) runs the function tools before it, 'early' stops at once, 'exhaustive' runs everything (_agent_graph.py, line 128).

Under run_sync is a state machine from pydantic_graph: UserPromptNode builds the request, ModelRequestNode calls the model, CallToolsNode runs tools and decides whether the output is final, SetFinalResult ends it (_agent_graph.py, lines 600 to 2609). agent.iter(...) hands you those nodes one at a time, so you can log, stop or edit between steps without callbacks. pydantic_graph also works on its own for multi-step workflows with typed state, the same school as LangGraph ({{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}}).

What it leaves to you: memory (no session store; a run returns its messages and you pass them back as message_history: explicit and easy to test, persistence your job); durable execution (not built in; the docs list five co-maintained integrations, Temporal, DBOS, Prefect, Restate and AWS Lambda, that checkpoint each model and tool call so a crashed run resumes, {{durable execution overview|https://pydantic.dev/docs/ai/integrations/durable_execution/overview/}}; the 2.54.0 wheel ships the Temporal, DBOS and Prefect modules); limits (UsageLimits defaults to 50 requests per run; tokens unlimited unless you set them).

OpenAI Agents SDK: few primitives, still 0.x

OpenAI calls the SDK "a production-ready upgrade of our previous experimentation for agents, Swarm"; its primitives are agents ("LLMs equipped with instructions and tools"), handoffs and agents as tools, and guardrails, plus sessions, tracing, realtime voice agents and sandbox agents that "run specialists inside real isolated workspaces" ({{SDK home|https://openai.github.io/openai-agents-python/}}, read 6 Oct 2026). It is still 0.x after 19 months on PyPI, and not tied to OpenAI's models: OpenAIChatCompletionsModel talks to any Chat Completions server (every run here used the local model), and a LiteLLM adapter covers other providers. Runner.run(agent, input) stops at the first reply with no tool call; with an output_type it sends the type as a JSON-schema response format and validates the reply text. tool_use_behavior changes the rule: "stop_on_first_tool" or StopAtTools([...]) end the run with a tool's output instead of asking the model again (agent.py, line 396).

smolagents: the action is a program

The main agent, CodeAgent, emits Python instead of one JSON call per action: tools are exposed as Python functions, the model writes a short program that calls them (with loops, variables and arithmetic), the library executes it, and the printed output comes back as the observation. The argument is the CodeAct paper's "up to 20% higher success rate" for code actions than JSON or text actions across 17 models ({{Wang et al., 2024|https://arxiv.org/abs/2402.01030}}). A ToolCallingAgent with ordinary JSON tool calls exists too.

The code sits between <code> and </code> (the default tags), and the request carries stop sequences "Observation:", "Calling tools:" and the closing tag (agents.py), so generation ends right after the code: the model cannot write its own "Observation:" and invent the result, the action-boundary failure recorded on {{Other coding harnesses|n:3c65c17b0d0d819fa3cefdcd2ccff2f7}} (section 1). The run ends when the code calls final_answer(value), or after max_steps=20.

The local executor is a rule set, not a sandbox. LocalPythonExecutor is an interpreter written in Python that walks the program's syntax tree and refuses imports outside an allow-list (eleven standard modules by default: collections, datetime, itertools, math, queue, random, re, stat, statistics, time, unicodedata; utils.py, line 49), builtins it does not expose, double-underscore attributes, and loops past a cap. Its docstring: "It is not a security sandbox: for isolated execution of untrusted code, use a remote executor" (local_python_executor.py, line 1688). In the probes below (no model) MEASURED, import os is refused by default but works once authorised (people do, to let the agent read files), giving the program the host's operating system; the source labels its list of "dangerous" modules "Non-exhaustive"; and a runaway loop is stopped by an iteration count (1000000), not by isolation. The docs offer remote executors (executor_type "docker", "e2b", "modal", "blaxel") and say "no local python sandbox can ever be completely secure" ({{secure code execution|https://huggingface.co/docs/smolagents/tutorials/secure_code_execution}}); 1.26.0 removed the WebAssembly executor. Why smolagents failed with the small local model

On the running example the local 4B model with smolagents fixed 0 of 8 runs, with code actions and with JSON tool calls (parent's Same agent, six ways tab). Two causes are in the source: the CodeAgent's system prompt made its first request 2,231 tokens against 385 to 507 for the others, and past tool calls go back into the history as plain text, "Calling tools:\n" + str([...]) (memory.py, line 106), not as native tool-call messages, so a small model imitates the text and the parser rejects it. A strong model copes. use_structured_outputs_internally=True asks the provider to constrain each step to a JSON object holding the thought and the code, which helps only where the server enforces response formats (section 2: this one does not).

Google ADK: a runtime, not a function

ADK describes itself as "the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale", in Python, TypeScript, Go, Java and Kotlin, with adapters for "many other models and model providers, including locally running models" ({{adk.dev|https://adk.dev/}}, read 6 Oct 2026). Where the other three hand you a function that runs a loop, ADK hands you a runtime: an agent, a Runner that executes it, a SessionService that stores what happened, and a stream of events (one per model reply, tool call or tool result) that the runner yields as the run proceeds.

  • LlmAgent (also exported as Agent): instruction, tools (plain functions become FunctionTools), optional output_schema, output_key and sub_agents. ADK appends a line naming the agent: the recorded request ends with 'You are an agent. Your internal name is "fixer". The description about you is "Fixes failing tests by editing code."', and tool results go back wrapped as {"result": ...} MEASURED.
  • Typed output: output_schema goes out as a response format, the parsed object lands under output_key. With tools on a model not known to support both at once, ADK adds a set_model_response tool and an instruction beginning "IMPORTANT: You have access to other tools, but you must provide your final response using the set_model_response tool" (flows/llm_flows/prompt/_schema.py): Pydantic AI's final_result trick.
  • Workflow agents that call no model: SequentialAgent, ParallelAgent and LoopAgent run sub-agents in a fixed pattern; version 2 adds graph workflows (a workflow package of nodes and edges in the 2.11.0 wheel; the docs announce "ADK TypeScript 2.0 GA ... with graph workflows support"). These are the root's workflow patterns as classes.
