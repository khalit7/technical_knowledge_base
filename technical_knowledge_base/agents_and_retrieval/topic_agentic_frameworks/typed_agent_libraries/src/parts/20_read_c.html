3. Pydantic AI: types all the way through

The idea. Pydantic AI is built by the team behind Pydantic, the validation library that most Python LLM SDKs already use for their request types. Its bet is that an agent is a function with typed inputs and a typed result, so it makes the agent generic in two types: Agent[Deps, Output]. Deps (dependencies) is any object you want tools and validators to receive at run time (a database handle, an HTTP client, the case being worked on); Output is the type the run must return. A type checker then catches a tool that expects the wrong deps, or code that treats the result as the wrong type, before anything runs.

@dataclass
class Case:                       # the dependency: whatever tools and validators need
    code: str
    test_output: str

agent = Agent(model, deps_type=Case, output_type=Triage, retries=2)

@agent.output_validator
def check(ctx: RunContext[Case], out: Triage) -> Triage:
    names = {n.name for n in ast.walk(ast.parse(ctx.deps.code)) if isinstance(n, ast.FunctionDef)}
    if out.function not in names:
        raise ModelRetry(f"There is no function named {out.function!r} in mod.py; it defines {sorted(names)}.")
    ...                           # the line must parse, and must not be a line already in the file
    return out

result = agent.run_sync(prompt, deps=Case(code, test_output))   # result.output is a Triage

Excerpt of this page's validator run (full script in the page's source folder). Triage is the result type used throughout this page: the buggy function's name, a category from a fixed list of five, the failing test, a one-line fix, and a confidence from 1 to 5.

Validate, then retry

Three things can send a retry prompt back to the model instead of failing the run: arguments that do not fit a tool's types (checked by Pydantic before your function is called; probed with a scripted fake model, the model received an int_parsing error and the function never ran MEASURED), a tool that raises ModelRetry("..."), and an output that fails validation or an output validator that raises ModelRetry. Each retry message ends with the same sentence, "Fix the errors and try again." (messages.py, line 1854). The budget is small by default: one retry for tools and one for output (agent/__init__.py, line 432; retries=2 above raises both), then the run raises UnexpectedModelBehavior: Exceeded maximum output retries.

Measured. The validator above on the ten triage cases, local model, three passes: MEASURED. A schema can only check shape; a validator with access to deps can check content against the world (the function exists, the line is new), which is where most real failures are.

Where the result comes from: the hidden final_result tool

By default the output type travels as an extra tool named final_result (_output.py, line 73), described by the output class's docstring when it has one (ours: "Triage of one failing test.") and otherwise as "The final response which ends this conversation" (line 74), and the request sets tool_choice to "required" so the model may not answer in plain text. The run ends when that tool is called with arguments that validate. Two consequences matter in practice. First, a model that ignores tool_choice, or a server that drops it (the local server used here does, section 2), can answer in prose; Pydantic AI then tries to parse the prose as JSON and sends back "Invalid JSON" plus "Fix the errors and try again", which does not say "call final_result". That is exactly how the parent's Same agent tab lost 3 of 4 Pydantic AI runs after the code was already fixed. Second, if the model calls final_result alongside other tools in one reply, the end strategy decides: 'graceful' (the default since 2.0) runs the function tools that came before it, 'early' stops at once, 'exhaustive' runs everything (_agent_graph.py, line 128). The other two output modes, native and prompted, are compared on real requests in section 2.

The run is a graph

Under run_sync is a small state machine from the companion package pydantic_graph: UserPromptNode builds the request, ModelRequestNode calls the model, CallToolsNode runs tools and decides whether the output is final, SetFinalResult ends it (_agent_graph.py, lines 600 to 2609). agent.iter(...) hands you those nodes one at a time, so you can log, stop or edit between steps without callbacks. pydantic_graph is also usable on its own for multi-step workflows with typed state, the same school as LangGraph (see {{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}}).

What it does not do for you

  • Memory. There is no session store: a run returns its messages and you pass them back as message_history next time. That is explicit and easy to test; it also means persistence is your job.
  • Durable execution. Not built in, but the docs list five co-maintained integrations (Temporal, DBOS, Prefect, Restate, AWS Lambda) that checkpoint each model and tool call so a crashed run resumes ({{durable execution overview|https://pydantic.dev/docs/ai/integrations/durable_execution/overview/}}); the 2.54.0 wheel ships the Temporal, DBOS and Prefect modules.
  • Limits. UsageLimits defaults to 50 requests per run (usage.py, line 482); tokens are unlimited unless you set them.
  • Tracing. Off until you configure OpenTelemetry or Logfire (Pydantic's hosted tracing product). On the first run in a terminal, 2.54.0 prints a banner advertising Logfire setup; it is shown once per process and suppressed by PYDANTIC_AI_NO_BANNER, in CI and under pytest (_display.py, line 212) MEASURED.
