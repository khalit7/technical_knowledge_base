7. Tracing hooks: one is on by default

Tracing records each run as spans (model calls, tool calls, handoffs, guardrails); how to read traces and the OpenTelemetry GenAI conventions are owned by {{LLM observability|n:3c65c17b0d0d81fe82c0c6e9360afec4}}. What matters here is each library's default, in the one-screen table: Pydantic AI off, smolagents off, ADK OpenTelemetry spans with export opt-in, and the Agents SDK on, exporting to OpenAI's dashboard.

  • Agents SDK. By default the spans include "LLM inputs and outputs" and "function call inputs and outputs"; turn that off with trace_include_sensitive_data=False, or tracing itself with OPENAI_AGENTS_DISABLE_TRACING=1, set_tracing_disabled(True) or per run; it is unavailable under Zero Data Retention ({{tracing docs|https://openai.github.io/openai-agents-python/tracing/}}). Recorded with no OpenAI key: the run worked and the SDK logged "OPENAI_API_KEY is not set, skipping trace export" MEASURED. Run a non-OpenAI model with an OpenAI key in the environment and your prompts and tool outputs go to OpenAI's trace store unless you switch it off.
  • Pydantic AI. Off until you configure OpenTelemetry or Logfire (Pydantic's hosted tracing product). 2.x has no Agent(instrument=...) argument: use Agent.instrument_all() or capabilities=[Instrumentation()]; it then writes gen_ai.aggregated_usage.* on the agent span and captures prompt and reply content by default (measured on LLM observability, section 3).

    On the first run in a terminal 2.54.0 prints a banner advertising Logfire setup, once per process, suppressed by PYDANTIC_AI_NO_BANNER, in CI and under pytest (_display.py, line 212) MEASURED.

8. Choosing: a thin typed library, a graph framework, or your own loop

Pydantic AI

The result is data another program consumes and you want the type checker, validators and retries on your side. Model-agnostic, explicit history, the most control over output. Bring your own persistence.

OpenAI Agents SDK

A few specialised agents that pass a conversation along, with guardrails, on OpenAI or any Chat Completions server. Decide about tracing first; it is on by default.

smolagents

Computation over tool results (loops, arithmetic, many small calls) with a strong model. Run the code in a remote executor; avoid it with small local models.

Google ADK

A runtime rather than a loop: sessions with scoped state, workflow agents, A2A and a deployment path, especially on Google Cloud or with Gemini. Set the call cap.

Or none of them. All four are thin over the same loop. A library earns its place when you use what it adds: validation and retries, handoffs and guardrails, an executor, sessions and state. When you need checkpoints, interrupts and resumable state, that is a graph framework's job ({{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}}); a harness you drive as a library is the {{Claude Agent SDK|n:3c65c17b0d0d813b960fd9857118fbd2}}. If you use none of that, the loop you can read is the better choice (the 12-factor argument on the root, "Own your control flow").

9. Depth (optional)

The role-based contrast: CrewAI and Microsoft Agent Framework

The four libraries here ask for functions and types; the role-based school asks for characters. CrewAI agents need a role, a goal and a backstory, tasks are assigned to them, and a sequential or hierarchical process runs the crew, with event-driven Flows for fixed pipelines ({{CrewAI docs|https://docs.crewai.com/}}; crewai 1.15.23 on PyPI, 28 Sep 2026). Microsoft Agent Framework (agent-framework 1.20.0 on PyPI, 2 Oct 2026) is "the next generation of both Semantic Kernel and AutoGen", with agents, typed graph workflows and checkpointing ({{Microsoft Learn|https://learn.microsoft.com/en-us/agent-framework/overview/}}). The difference that matters here: in a role-based library the prompt is generated from a persona, so the typed parts (tools, outputs) are a smaller share of what decides behaviour. The schools are compared on the root ({{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}}, Reading, section 2); neither was run here.

Mistake: trusting NativeOutput or output_type on a server you have not checked
If the server drops response_format (the local mlx-lm server here does, silently), the model never sees the schema. Test once with a schema the model could not guess.
Mistake: leaving retries at the default
Pydantic AI gives one output retry, the Agents SDK none. One retry is too few for a small model and silent retries hide drift: set the budget and count retries in your metrics.
Mistake: exposing an ADK agent over A2A without reading its card
The generated card lists every tool by name and description.
Interview: name three ways to get structured output from a model and their guarantees.
Prompted (schema in the instructions, parse the text: no guarantee), tool-forced (the schema as a tool's parameters, the model must call it: trained behaviour, validate and retry), native constrained decoding (the server masks tokens that would break the schema: valid by construction, content still unchecked). Constrained decoding needs the server to support it.
Interview: how does a handoff differ from calling an agent as a tool?
A handoff transfers the conversation: the new agent replies to the user and owns the rest of the run. An agent as a tool runs a sub-agent on a sub-task and returns its result to the caller, which stays in charge. In the Agents SDK both are tools on the wire; the difference is what happens after the call.
Interview: why are code actions risky and what do you do about it?
The model's program runs with your process's rights unless isolated. An interpreter with allow-lists reduces mistakes but is not a boundary; run the code in a container or a remote sandbox with no secrets and limited network.
