The idea in one screen

A typed agent library turns your typed Python (functions, classes, a dependency object) into JSON schemas on the way out and into validated objects on the way back; what separates the libraries is where the schema travels in the request and what they wrap around the tool calls.

Fig. 1 follows one run through the pieces every library on this page has (Pydantic AI, the OpenAI Agents SDK, smolagents, Google ADK), with the counts recorded on the local server used here (section 2):

  1. Your types become schemas. The library reads edit_file(path: str, ...) and class Triage(BaseModel) and derives a JSON Schema for each (the glass plates); deps=Case(...) stays in your process for tools and validators.
  2. The result schema rides in one of three slots. Tool-forced: the parameters of a final_result tool in tools[ ]. Native: a response_format field. Prompted: plain text in the system message asking for JSON.
  3. The server decides what the model sees. mlx-lm 0.32.0 renders tools and text into the prompt but never reads response_format: on the native slot the schema stops at the server and the model writes prose.
  4. The reply is validated. Pydantic types first, then your validator, which receives ctx.deps; this is where a reply becomes a typed object or an error.
  5. A failure goes back as a message. The error plus "Fix the errors and try again." returns to the model as a retry prompt, within a budget (default 1 retry).
  6. What came out, by slot. Valid Triage results on the local model: tool 20 of 20, prompted 20 of 20, native 0 of 60. Everything else the libraries add (retries, handoffs, guardrails, a code executor, sessions, tracing) is an ordinary tool call or a wrapper around one.

You need: the agent loop and tool calling on the wire (Building a harness owns the loop; the parent Topic: agentic-frameworks compares the schools and runs one agent six ways in its Same agent, six ways tab, this page's starting point).

Typed agent library
a library whose main promise is that you write ordinary typed functions and classes and it derives schemas and validates replies (as opposed to a graph framework or a role-based crew).
JSON Schema
a JSON description of an object's fields, their types, which are required, and a sentence about each; what a model sees for a tool or a result type.
Native, tool-forced, prompted
the three places the result schema can travel: a response-format field, the parameters of a tool the model must call, or plain text in the instructions.
Deps
a dependency object handed to tools and validators at run time (a database handle, the case being worked on).
Retry prompt
a validation error sent back to the model as a message, so it can try again instead of the run failing.
Handoff, transfer
passing the conversation to another agent, implemented as a tool call (transfer_to_<name>, transfer_to_agent).
Guardrail, tripwire
a check on the input or output that can end the run by raising.

1. The schema has to reach the model. The three native routes (Pydantic AI's NativeOutput, the Agents SDK's output_type, ADK's output_schema) put the schema in a field the local server never reads: 0 of 60 runs returned a result. The same model given the schema as a tool or as text: 20 of 20 each (section 2).

2. Valid is not right. Constrained decoding made 30 of 30 replies parse, yet only 21 named the right bug category; the tool route, 20 of 20 valid, got 8. A validator that can see the inputs catches what a schema cannot (section 3).

1. From a Python function to a tool schema

A model can only emit text; tool calling works because it was trained to emit a small JSON object (a tool name and arguments) when the request lists tools, each described by a JSON Schema (Building a harness shows a real tokenised tool call). The first thing a typed library does is derive that schema from the function: parameter names and type hints give fields and types, defaults decide what is optional, the docstring gives descriptions. One function, given to each library's own tool decorator, schema printed by the library's code with no model call MEASURED:

def edit_file(path: str, old: str, new: str, count: int = 1) -> str:
    """Replace the exact text old with new in a file.

    Args:
        path: File to edit, relative to the repository root.
        old: Text to find; must occur exactly `count` times.
        new: Replacement text.
        count: How many occurrences to expect.
    """
  • Pydantic AI keeps count optional with its default, copies each Args: line into that field's description, adds "additionalProperties": false, and validates the model's arguments with Pydantic before your function runs: a type error becomes a retry message to the model, not an exception in your code.
  • The OpenAI Agents SDK marks the schema strict, so all four fields are required, count included: strict mode requires every property in required and additionalProperties: false (function calling guide). The schema still shows "default": 1 as a hint, but the model must always send a value; your Python default never runs.
  • smolagents drops the default and marks count "nullable": true, a keyword from OpenAPI rather than JSON Schema. Its @tool decorator refuses a function whose docstring lacks an Args: line for every parameter.
  • Google ADK, on the path a non-Gemini model takes, sends no per-argument descriptions: the whole docstring becomes the tool description and each field gets only a title. The recorded ADK request on the running example has the same shape on the wire.

So the schema the model sees is generated: read it. The cheapest debugging step with any of these libraries is to log the first request and look at the tools array (the parent's Same agent, six ways tab shows every request each framework sent on one task).

The raw schemas, library by library
Predict: with the Agents SDK's strict schema the model always sends count. Which value actually runs if you never meant the model to choose it?
Whatever the model sends, usually the hint it was shown (1). Your Python default never runs, because the argument is always present. If the model should not choose the value, keep the parameter out of the tool's signature (pass it through the run's context) rather than giving it a default. Strict schemas move defaults out of the model's reach; if the default matters, say it in the description.

2. Typed output: where the schema travels

You declare a result type, and the run returns an instance of it or fails. There are three routes, and the difference is where the schema travels, so who is responsible for the reply fitting it:

  • Prompted: the schema is pasted into the instructions as text. The model may follow it; the library parses and validates.
  • Tool-forced: the schema becomes the parameters of a tool (Pydantic AI's final_result, ADK's set_model_response, Claude Code's StructuredOutput) and the request says a tool call is required. Tool-calling models are trained to fill tool arguments.
  • Native: the schema goes in a separate request field, response_format on OpenAI-style servers or output_config.format on Anthropic's API, and the server constrains decoding so the reply is valid by construction. Anthropic describes "constrained sampling with compiled grammar artifacts", with extra latency the first time a schema is used and grammars "cached for 24 hours from last use" (structured outputs, read 6 Oct 2026). How a server masks tokens is owned by Sampling and decoding.

The native route relies on the server. The local server used on these pages, mlx_lm.server 0.32.0, reads a fixed list of request fields (server.py, lines 1159 to 1194 and 1614); response_format and tool_choice are not among them, so both are silently ignored. vLLM, SGLang and llama.cpp document grammar-constrained JSON (vLLM, SGLang, llama.cpp): this is a property of the server, not of local models.

The test. Ten small buggy modules, each with one failing unit test whose real output was captured (two are the running example's planted bugs). Return a Triage: the buggy function's name, a category from a fixed list of five, the failing test, a one-line fix, a confidence from 1 to 5. Every library at its defaults on the local model (Qwen3-4B-Instruct-2507, 4-bit), one greedy pass and one sampled at temperature 0.7 (the in-process outlines runs got two); Claude through claude -p with built-in tools off, once per case. Predict before you look: which routes return a Triage on a server that drops response_format?

Native routes, 0 of 60 (Pydantic AI 0 of 20, Agents SDK 0 of 20, ADK 0 of 20): the request carried the schema only in response_format, the server dropped it, and the model wrote a prose bug report. Pydantic AI sent one retry ("1 validation error: ... Fix the errors and try again."), which does not contain the schema either, and gave up; the Agents SDK and ADK raised on the first reply. Moving the same schema into the prompt (prompted, 20 of 20) or into a tool (20 of 20) fixed validity on the same server.

Validity and content are separate questions. Among valid replies the category was right in 13 of 20 prompted runs, 21 of 30 constrained, but only 8 of 20 tool-output runs: filling a tool call's arguments directly, the small model chose wrong_operator for a regex bug. The self-reported confidence was 5 in 129 of 129 valid results across every route, local model and Claude alike: read it as decoration.

Claude. Both models filled the StructuredOutput tool correctly every time (10 and 10 of 10), at the cost of one extra turn. With the schema only in the prompt, Sonnet 5.5 replied with bare JSON 10 of 10 times; Haiku 4.5 wrapped 10 of 10 replies in a Markdown fence despite "Don't include any text or Markdown fencing": strict json.loads fails on them, a fence-stripping parser recovers 10. The parent root recorded the same fence once; here it is the habit.

Mastra, the TypeScript member of the family (docs read 24 October 2026, not run): tools are createTool() with a Zod inputSchema; the result schema goes in structuredOutput: { schema } and comes back as response.object. By default the schema travels in the provider's native response_format, so it would meet the same dropped field here; jsonPromptInjection moves it into the messages, and errorStrategy is strict (throw) by default, with warn and fallback (Mastra structured output).

3. Validate, then retry; dependencies injected


A schema checks shape. Whether Triage.function names a function that exists needs the inputs, and that is what dependency injection gives a validator. Pydantic AI makes the agent generic in two types, Agent[Deps, Output]: Deps is any object tools and validators receive at run time through RunContext, Output the type the run must return, so a type checker catches a tool that expects the wrong deps, or code that treats the result as the wrong type, before anything runs.


@dataclass
class Case:                       # the dependency: whatever tools and validators need
    code: str
    test_output: str

agent = Agent(model, deps_type=Case, output_type=Triage, retries=2)

@agent.output_validator
def check(ctx: RunContext[Case], out: Triage) -> Triage:
    names = {n.name for n in ast.walk(ast.parse(ctx.deps.code)) if isinstance(n, ast.FunctionDef)}
    if out.function not in names:
        raise ModelRetry(f"There is no function named {out.function!r} in mod.py; it defines {sorted(names)}.")
    ...                           # the line must parse, and must not be a line already in the file
    return out

result = agent.run_sync(prompt, deps=Case(code, test_output))   # result.output is a Triage

4. How each library runs the loop


All four run the same loop (call the model, run what it asked for, append, repeat; owned by Building a harness). What differs is the stopping rule, the default cap, and what an action is.


The default caps are in the source (Pydantic AI usage.py, line 482; Agents SDK run_config.py, line 45; smolagents agents.py; ADK agents/run_config.py, overridable with ADK_MAX_LLM_CALLS). Set your own: a coding task that reads a few files, edits and tests can need more than 10 turns, and 500 is the highest of the four. Fig. 3 puts the four loops side by side, one lane each:


    

  1. One loop, four stopping rules. Each lane is call the model, act, test whether the run is over, else go round again; every round counts toward the cap: 50 requests, 10 turns, 20 steps, 500 model calls.
    2. 

  2. Pydantic AI ends on a tool. The result type travels as the hidden final_result tool; the run ends when the model calls it and the value validates (else a retry prompt goes round).
    3. 

  3. The Agents SDK ends on silence. The first reply with no tool call ends the run; a handoff tool switches the agent and keeps looping.
    4. 

  4. smolagents acts in code. The model writes a Python block; generation stops at </code>; the local executor runs it and the printed output comes back as the observation; final_answer(...) ends the run.
    5. 

  5. ADK is a runtime that logs events. Every reply, call and result is an event appended to the session; the run ends on an event with no function call. On the running example (section below) its four runs took 5, 7, 11 and 9 requests and 1 passed the tests.
    6. 





Pydantic AI: a hidden result tool and a graph underneath


By default the output type travels as an extra tool named final_result (_output.py, line 73), described by the output class's docstring (ours: "Triage of one failing test.") or else as "The final response which ends this conversation" (line 74), and the request sets tool_choice to "required". A model that ignores tool_choice, or a server that drops it (this one does), can answer in prose; Pydantic AI then parses the prose as JSON and sends back "Invalid JSON" plus "Fix the errors and try again", which does not say "call final_result". That is how the parent's Same agent tab lost 3 of 4 Pydantic AI runs after the code was already fixed. If final_result comes alongside other tool calls in one reply, the end strategy decides: 'graceful' (the default since 2.0) runs the function tools before it, 'early' stops at once, 'exhaustive' runs everything (_agent_graph.py, line 128).


Under run_sync is a state machine from pydantic_graph: UserPromptNode builds the request, ModelRequestNode calls the model, CallToolsNode runs tools and decides whether the output is final, SetFinalResult ends it (_agent_graph.py, lines 600 to 2609). agent.iter(...) hands you those nodes one at a time, so you can log, stop or edit between steps without callbacks. pydantic_graph also works on its own for multi-step workflows with typed state, the same school as LangGraph (LangChain and LangGraph).


What it leaves to you: memory (no session store; a run returns its messages and you pass them back as message_history: explicit and easy to test, persistence your job); durable execution (not built in; the docs list five co-maintained integrations, Temporal, DBOS, Prefect, Restate and AWS Lambda, that checkpoint each model and tool call so a crashed run resumes, durable execution overview; the 2.54.0 wheel ships the Temporal, DBOS and Prefect modules); limits (UsageLimits defaults to 50 requests per run; tokens unlimited unless you set them).



OpenAI Agents SDK: few primitives, still 0.x


OpenAI calls the SDK "a production-ready upgrade of our previous experimentation for agents, Swarm"; its primitives are agents ("LLMs equipped with instructions and tools"), handoffs and agents as tools, and guardrails, plus sessions, tracing, realtime voice agents and sandbox agents that "run specialists inside real isolated workspaces" (SDK home, read 6 Oct 2026). It is still 0.x after 19 months on PyPI, and not tied to OpenAI's models: OpenAIChatCompletionsModel talks to any Chat Completions server (every run here used the local model), and a LiteLLM adapter covers other providers. Runner.run(agent, input) stops at the first reply with no tool call; with an output_type it sends the type as a JSON-schema response format and validates the reply text. tool_use_behavior changes the rule: "stop_on_first_tool" or StopAtTools([...]) end the run with a tool's output instead of asking the model again (agent.py, line 396).



smolagents: the action is a program


The main agent, CodeAgent, emits Python instead of one JSON call per action: tools are exposed as Python functions, the model writes a short program that calls them (with loops, variables and arithmetic), the library executes it, and the printed output comes back as the observation. The argument is the CodeAct paper's "up to 20% higher success rate" for code actions than JSON or text actions across 17 models (Wang et al., 2024). A ToolCallingAgent with ordinary JSON tool calls exists too.

The local executor is a rule set, not a sandbox. LocalPythonExecutor is an interpreter written in Python that walks the program's syntax tree and refuses imports outside an allow-list (eleven standard modules by default: collections, datetime, itertools, math, queue, random, re, stat, statistics, time, unicodedata; utils.py, line 49), builtins it does not expose, double-underscore attributes, and loops past a cap. Its docstring: "It is not a security sandbox: for isolated execution of untrusted code, use a remote executor" (local_python_executor.py, line 1688). In the probes below (no model) MEASURED, import os is refused by default but works once authorised (people do, to let the agent read files), giving the program the host's operating system; the source labels its list of "dangerous" modules "Non-exhaustive"; and a runaway loop is stopped by an iteration count (1000000), not by isolation. The docs offer remote executors (executor_type "docker", "e2b", "modal", "blaxel") and say "no local python sandbox can ever be completely secure" (secure code execution); 1.26.0 removed the WebAssembly executor. Why smolagents failed with the small local model
On the running example the local 4B model with smolagents fixed 0 of 8 runs, with code actions and with JSON tool calls (parent's Same agent, six ways tab). Two causes are in the source: the CodeAgent's system prompt made its first request 2,231 tokens against 385 to 507 for the others, and past tool calls go back into the history as plain text, "Calling tools:\n" + str([...]) (memory.py, line 106), not as native tool-call messages, so a small model imitates the text and the parser rejects it. A strong model copes. use_structured_outputs_internally=True asks the provider to constrain each step to a JSON object holding the thought and the code, which helps only where the server enforces response formats (section 2: this one does not).



Google ADK: a runtime, not a function


ADK describes itself as "the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale", in Python, TypeScript, Go, Java and Kotlin, with adapters for "many other models and model providers, including locally running models" (adk.dev, read 6 Oct 2026). Where the other three hand you a function that runs a loop, ADK hands you a runtime: an agent, a Runner that executes it, a SessionService that stores what happened, and a stream of events (one per model reply, tool call or tool result) that the runner yields as the run proceeds.

5. Handoffs and transfers are tools


A handoff passes the whole conversation to another agent, which then owns it. Neither library adds new machinery for it. In the Agents SDK each agent in handoffs=[...] becomes a tool named transfer_to_ plus the agent's name, described as "Handoff to the name agent to handle the request." plus its handoff_description (handoffs/__init__.py, line 214); its output is {"assistant": "fixer"}, and the next request goes out with the new agent's instructions and tools and, by default, "the entire previous conversation history" (handoffs docs). In ADK an agent with sub_agents gets one transfer_to_agent(agent_name, transfer_reason) tool whose agent_name is an enum of the valid names, so the model cannot invent one (tools/transfer_to_agent_tool.py): one tool instead of one per target.

6. Guardrails, sessions and state




A parallel guardrail is a latency optimisation, not a gate


A guardrail checks the input (before the agent) or the output (after it) and can trip a tripwire, an exception that ends the run. In the Agents SDK input guardrails default to run_in_parallel=True (guardrail.py, line 100): the check and the agent's first model call start together. The docs: "if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; with run_in_parallel=False "the agent never executes" (guardrails docs).



One more lesson came free: told to answer only YES or NO, the small checker model wrote the poem instead ("TIDES WHISPER SECRETS TO THE SHORE ..."); the guard tripped only because its parser treated anything but YES as NO. A guardrail model reads the same input it is guarding against, so parse its answer fail-closed. (A first version gave the checker a typed output, which failed on every request on this server for the reason in section 2.) Anything with side effects belongs behind a blocking check or a tool guardrail, which runs before each tool call. A blocking guardrail costs one extra model call of latency on every request that passes, plus its tokens.






Sessions are history, not durable execution


A session stores a conversation's items so the next Runner.run with the same session sends them again. Recorded with SQLiteSession: two turns, 1 row in agent_sessions, 4 rows in agent_messages; the second request carried 4 messages (system, the stored first exchange, the new question) and answered "Kestrel" MEASURED. A run that crashes between two tool calls is not resumed.




ADK: state as a ledger of events, with scopes



output_key="triage" writes the agent's final reply into state["triage"], and another agent's instruction reads it with {triage} (or {triage?} when it may be absent): that is how a SequentialAgent passes data from one step to the next. Memory that outlives a session is owned by Context engineering.






ADK: A2A in one call


to_a2a(agent) wraps any ADK agent as an A2A server (the agent-to-agent protocol, on the wire on Agent-to-agent and beyond), a Starlette web app whose agent card (the JSON document other agents fetch to learn what this one does) is built automatically. Fetched in-process, no model call MEASURED: /.well-known/agent-card.json returned the name and description, a JSON-RPC interface at protocol version 1.0, and 5 skills: model, list_files, read_file, edit_file, run_tests. The card lists every tool as a public "skill", names and descriptions included, so review it before exposing an agent.


A2A status and deployment
ADK's A2A classes print "[EXPERIMENTAL] ... subject to breaking changes" warnings in 2.11.0, while "A2A protocol and SDK are themselves not experimental". Deployment targets in the docs: Google Cloud's Agent Runtime, Cloud Run and GKE, or any container (not run here).

8. Choosing: a thin typed library, a graph framework, or your own loop





Pydantic AI
The result is data another program consumes and you want the type checker, validators and retries on your side. Model-agnostic, explicit history, the most control over output. Bring your own persistence.


OpenAI Agents SDK
A few specialised agents that pass a conversation along, with guardrails, on OpenAI or any Chat Completions server. Decide about tracing first; it is on by default.


smolagents
Computation over tool results (loops, arithmetic, many small calls) with a strong model. Run the code in a remote executor; avoid it with small local models.


Google ADK
A runtime rather than a loop: sessions with scoped state, workflow agents, A2A and a deployment path, especially on Google Cloud or with Gemini. Set the call cap.




Or none of them. All four are thin over the same loop. A library earns its place when you use what it adds: validation and retries, handoffs and guardrails, an executor, sessions and state. When you need checkpoints, interrupts and resumable state, that is a graph framework's job (LangChain and LangGraph); a harness you drive as a library is the Claude Agent SDK. If you use none of that, the loop you can read is the better choice (the 12-factor argument on the root, "Own your control flow").











9. Depth (optional)


The role-based contrast: CrewAI and Microsoft Agent Framework


The four libraries here ask for functions and types; the role-based school asks for characters. CrewAI agents need a role, a goal and a backstory, tasks are assigned to them, and a sequential or hierarchical process runs the crew, with event-driven Flows for fixed pipelines (CrewAI docs; crewai 1.15.23 on PyPI, 28 Sep 2026). Microsoft Agent Framework (agent-framework 1.20.0 on PyPI, 2 Oct 2026) is "the next generation of both Semantic Kernel and AutoGen", with agents, typed graph workflows and checkpointing (Microsoft Learn). The difference that matters here: in a role-based library the prompt is generated from a persona, so the typed parts (tools, outputs) are a smaller share of what decides behaviour. The schools are compared on the root (Topic: agentic-frameworks, Reading, section 2); neither was run here.


Mistake: trusting NativeOutput or output_type on a server you have not checked
If the server drops response_format (the local mlx-lm server here does, silently), the model never sees the schema. Test once with a schema the model could not guess.


Mistake: leaving retries at the default
Pydantic AI gives one output retry, the Agents SDK none. One retry is too few for a small model and silent retries hide drift: set the budget and count retries in your metrics.


Mistake: exposing an ADK agent over A2A without reading its card
The generated card lists every tool by name and description.


Interview: name three ways to get structured output from a model and their guarantees.
Prompted (schema in the instructions, parse the text: no guarantee), tool-forced (the schema as a tool's parameters, the model must call it: trained behaviour, validate and retry), native constrained decoding (the server masks tokens that would break the schema: valid by construction, content still unchecked). Constrained decoding needs the server to support it.


Interview: how does a handoff differ from calling an agent as a tool?
A handoff transfers the conversation: the new agent replies to the user and owns the rest of the run. An agent as a tool runs a sub-agent on a sub-task and returns its result to the caller, which stays in charge. In the Agents SDK both are tools on the wire; the difference is what happens after the call.


Interview: why are code actions risky and what do you do about it?
The model's program runs with your process's rights unless isolated. An interpreter with allow-lists reduces mistakes but is not a boundary; run the code in a container or a remote sandbox with no secrets and limited network.
