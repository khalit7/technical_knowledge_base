The page in one screen

An agent loop is a program that sends a model a conversation plus a list of tools, runs whatever tool call comes back, appends the result, and asks again until the model stops calling tools. The parent topic writes that loop by hand and then in six frameworks (Topic: agentic-frameworks, tab Same agent, six ways). This page takes the four typed agent libraries from that comparison and goes one level down: libraries whose main promise is that you write ordinary typed Python functions and classes, and the library turns them into tool schemas on the way out and into validated objects on the way back.

The three findings worth remembering

1. The schema has to reach the model. The three "native" routes (Pydantic AI's NativeOutput, the Agents SDK's output_type, ADK's output_schema) put the schema in a request field the local server never reads: The same model given the schema as a tool or as text: Section 2.

2. Valid is not right. Constrained decoding made every reply parse (), yet the content checks still miss: A validator that can see the inputs catches what a schema cannot (section 3).

3. Every mechanism is a tool call. Pydantic AI's result (final_result), ADK's (set_model_response), Claude Code's (StructuredOutput), the Agents SDK's handoffs (transfer_to_fixer) and ADK's transfers (transfer_to_agent) are all ordinary tools on the wire. The libraries differ in what they wrap around those calls: validation and retries, guardrails, an executor, sessions and state.

1. From a Python function to a tool schema

A model cannot call Python. It can only emit text, and tool calling works because the model was trained to emit a small JSON object (a tool name and its arguments) when the request lists tools, each described by a JSON Schema: a JSON description of an object's fields, their types, which are required, and a sentence about each. The harness root explains the wire format (Topic: agentic-harnesses, Reading, section 2; and Building a harness, with a real tokenised tool call). Writing those schemas by hand is tedious and drifts from the code. The first thing a typed library does is derive the schema from the function: the parameter names and type hints give fields and types, defaults decide what is optional, and the docstring gives descriptions.

Same function, given to each library's own tool decorator, schema printed by the library's code with no model call MEASURED. The function has three required parameters and one with a default, and a Google-style docstring with an Args: block:

def edit_file(path: str, old: str, new: str, count: int = 1) -> str:
    """Replace the exact text old with new in a file.

    Args:
        path: File to edit, relative to the repository root.
        old: Text to find; must occur exactly `count` times.
        new: Replacement text.
        count: How many occurrences to expect.
    """

What differs, and why it matters. Four libraries, four schemas for one function:

  • Pydantic AI keeps count optional with its default, copies each Args: line into that field's description, and adds "additionalProperties": false. It validates the model's arguments with Pydantic before your function runs; a type error becomes a retry message to the model, not an exception in your code.
  • The OpenAI Agents SDK marks the schema strict and so lists all four fields as required, count included. That is not a bug: OpenAI's strict mode requires every property to be listed in required and additionalProperties: false (function calling guide). The schema still shows "default": 1 as a hint, but the model must always send a value; a default in your Python signature is never used.
  • smolagents drops the default and marks count "nullable": true instead, a keyword from OpenAPI rather than JSON Schema. Its @tool decorator also refuses a function whose docstring lacks an Args: line for every parameter.
  • Google ADK, on the path a non-Gemini model takes, sends no per-argument descriptions at all: the whole docstring becomes the tool description, and each field gets only a title. The recorded ADK request on the running example shows the same shape on the wire.

The lesson is not that one is right. It is that the schema the model sees is generated, so read it: the cheapest debugging step with any of these libraries is to log the first request and look at the tools array. The parent topic's Same agent, six ways tab shows every request each framework sent on one task.

Predict: with the Agents SDK's strict schema the model always sends count. Which value actually runs if you never meant the model to choose it?
Whatever the model sends, usually the hint it was shown (1). Your Python default never runs, because the argument is always present. If the model should not choose the value, keep the parameter out of the tool's signature (pass it through the run's context) rather than giving it a default. Strict schemas move defaults out of the model's reach; if the default matters, say it in the description.

2. Typed output: where the schema travels

The second promise is the result: you declare a type, and the run returns an instance of it or fails. The parent root lists three ways to get there (Topic: agentic-frameworks, Reading, section 4). The difference between them is where the schema travels, and so who is responsible for the reply fitting it:

  • Prompted: the schema is pasted into the instructions as text. The model may follow it. The library parses the reply and validates it.
  • Tool-forced: the schema becomes the parameters of a tool (Pydantic AI's final_result, ADK's set_model_response, Claude Code's StructuredOutput), and the request says a tool call is required. Tool-calling models are trained to fill tool arguments.
  • Native: the schema goes in a separate request field, response_format on OpenAI-style servers or output_config.format on Anthropic's API, and the server constrains decoding: at every step it masks the tokens that would break the schema, so the reply is valid by construction. Anthropic's docs describe "constrained sampling with compiled grammar artifacts", with extra latency the first time a schema is used and grammars "cached for 24 hours from last use" (structured outputs, read 6 Oct 2026).

The catch in the native route is in its first word: it relies on the server. The local server used on these pages, mlx_lm.server 0.32.0, reads a fixed list of request fields (server.py, lines 1159 to 1194 and 1614) and response_format and tool_choice are not among them: both are silently ignored. Many self-hosted servers differ here (vLLM, SGLang and llama.cpp document grammar-constrained JSON), so this is a property of the server, not of local models.

3. Pydantic AI: types all the way through


The idea. Pydantic AI is built by the team behind Pydantic, the validation library that most Python LLM SDKs already use for their request types. Its bet is that an agent is a function with typed inputs and a typed result, so it makes the agent generic in two types: Agent[Deps, Output]. Deps (dependencies) is any object you want tools and validators to receive at run time (a database handle, an HTTP client, the case being worked on); Output is the type the run must return. A type checker then catches a tool that expects the wrong deps, or code that treats the result as the wrong type, before anything runs.


@dataclass
class Case:                       # the dependency: whatever tools and validators need
    code: str
    test_output: str

agent = Agent(model, deps_type=Case, output_type=Triage, retries=2)

@agent.output_validator
def check(ctx: RunContext[Case], out: Triage) -> Triage:
    names = {n.name for n in ast.walk(ast.parse(ctx.deps.code)) if isinstance(n, ast.FunctionDef)}
    if out.function not in names:
        raise ModelRetry(f"There is no function named {out.function!r} in mod.py; it defines {sorted(names)}.")
    ...                           # the line must parse, and must not be a line already in the file
    return out

result = agent.run_sync(prompt, deps=Case(code, test_output))   # result.output is a Triage


Excerpt of this page's validator run (full script in the page's source folder). Triage is the result type used throughout this page: the buggy function's name, a category from a fixed list of five, the failing test, a one-line fix, and a confidence from 1 to 5.


Validate, then retry


Three things can send a retry prompt back to the model instead of failing the run: arguments that do not fit a tool's types (checked by Pydantic before your function is called; probed with a scripted fake model, the model received an int_parsing error and the function never ran MEASURED), a tool that raises ModelRetry("..."), and an output that fails validation or an output validator that raises ModelRetry. Each retry message ends with the same sentence, "Fix the errors and try again." (messages.py, line 1854). The budget is small by default: one retry for tools and one for output (agent/__init__.py, line 432; retries=2 above raises both), then the run raises UnexpectedModelBehavior: Exceeded maximum output retries.


Measured. The validator above on the ten triage cases, local model, three passes:  MEASURED. A schema can only check shape; a validator with access to deps can check content against the world (the function exists, the line is new), which is where most real failures are.


Where the result comes from: the hidden final_result tool


By default the output type travels as an extra tool named final_result (_output.py, line 73), described by the output class's docstring when it has one (ours: "Triage of one failing test.") and otherwise as "The final response which ends this conversation" (line 74), and the request sets tool_choice to "required" so the model may not answer in plain text. The run ends when that tool is called with arguments that validate. Two consequences matter in practice. First, a model that ignores tool_choice, or a server that drops it (the local server used here does, section 2), can answer in prose; Pydantic AI then tries to parse the prose as JSON and sends back "Invalid JSON" plus "Fix the errors and try again", which does not say "call final_result". That is exactly how the parent's Same agent tab lost 3 of 4 Pydantic AI runs after the code was already fixed. Second, if the model calls final_result alongside other tools in one reply, the end strategy decides: 'graceful' (the default since 2.0) runs the function tools that came before it, 'early' stops at once, 'exhaustive' runs everything (_agent_graph.py, line 128). The other two output modes, native and prompted, are compared on real requests in section 2.


The run is a graph


Under run_sync is a small state machine from the companion package pydantic_graph: UserPromptNode builds the request, ModelRequestNode calls the model, CallToolsNode runs tools and decides whether the output is final, SetFinalResult ends it (_agent_graph.py, lines 600 to 2609). agent.iter(...) hands you those nodes one at a time, so you can log, stop or edit between steps without callbacks. pydantic_graph is also usable on its own for multi-step workflows with typed state, the same school as LangGraph (see LangChain and LangGraph).


What it does not do for you


    

  • Memory. There is no session store: a run returns its messages and you pass them back as message_history next time. That is explicit and easy to test; it also means persistence is your job.
    • 

  • Durable execution. Not built in, but the docs list five co-maintained integrations (Temporal, DBOS, Prefect, Restate, AWS Lambda) that checkpoint each model and tool call so a crashed run resumes (durable execution overview); the 2.54.0 wheel ships the Temporal, DBOS and Prefect modules.
    • 

  • Limits. UsageLimits defaults to 50 requests per run (usage.py, line 482); tokens are unlimited unless you set them.
    • 

  • Tracing. Off until you configure OpenTelemetry or Logfire (Pydantic's hosted tracing product). 2.x has no Agent(instrument=...) argument: turn it on with Agent.instrument_all() or capabilities=[Instrumentation()]; it then writes gen_ai.aggregated_usage.* on the agent span and captures prompt and reply content by default, as measured on LLM observability (section 3, instrumenting). On the first run in a terminal, 2.54.0 prints a banner advertising Logfire setup; it is shown once per process and suppressed by PYDANTIC_AI_NO_BANNER, in CI and under pytest (_display.py, line 212) MEASURED.

4. OpenAI Agents SDK: few primitives, everything is a tool


The idea. OpenAI calls the SDK "a production-ready upgrade of our previous experimentation for agents, Swarm" and lists its primitives as agents ("LLMs equipped with instructions and tools"), handoffs and agents as tools, and guardrails, plus sessions, tracing, realtime voice agents and, newest, sandbox agents that "run specialists inside real isolated workspaces" (SDK home, read 6 Oct 2026). It is still 0.x after 19 months on PyPI. Despite the name it is not tied to OpenAI's models: OpenAIChatCompletionsModel talks to any Chat Completions server (every run here used the local model), and a LiteLLM adapter covers other providers.


The loop and when it stops


Runner.run(agent, input) loops: call the model, run the tools it asked for, repeat. Without an output_type, the first reply with no tool call is the final output. With one, the SDK sends the type as a JSON-schema response format (a request field asking the provider to constrain the reply) and validates the reply text against it; if validation fails, the run raises ModelBehaviorError unless you registered an error handler for invalid_final_output: there is no automatic retry (run_internal/turn_resolution.py, lines 1010 to 1060). The cap is 10 turns (run_config.py, line 45), lower than Pydantic AI's 50; a coding task that reads a few files, edits and tests can need more. tool_use_behavior changes the stopping rule: "stop_on_first_tool" or StopAtTools([...]) end the run with a tool's output instead of asking the model again (agent.py, line 396).


Handoffs are tools named transfer_to_<agent>


A handoff passes the whole conversation to another agent, which then owns it. The SDK implements it with no new machinery: each agent in handoffs=[...] becomes a tool whose name is transfer_to_ plus the agent's name and whose description is "Handoff to the name agent to handle the request." plus its handoff_description (handoffs/__init__.py, line 214). When the model calls it, the tool's output is {"assistant": "fixer"}, and the next request goes out with the new agent's instructions and tools and, by default, "the entire previous conversation history" (handoffs docs). An input_filter can cut that history; the opt-in nest_handoff_history summarises it, and the source warns that "Nesting does not redact sensitive data" (run_config.py, line 378).


Recorded: a triage agent with two handoffs (a fixer with the four tools, an explainer with read-only tools) on the running example, local model:  MEASURED. The request-by-request view is on the Mechanisms, recorded tab. Two source details matter once a reply can hand off to more than one agent: if the model calls several handoff tools in one reply, only the first runs and the others get the tool output "Multiple handoffs detected, ignoring this one." (run_internal/turn_resolution.py); and nest_handoff_history defaults to off (RunConfig, "Opt-in beta"). Section 6 of Multi-agent patterns (handoffs against agents-as-tools) measures what that costs: with a two-problem message the second problem was never handled after a handoff, while agents-as-tools handled both. When several agents help and when they hurt is the subject of that page.


Guardrails run in parallel by default


A guardrail is a check on the input (before the agent) or the output (after it) that can trip a tripwire: an exception that ends the run. Input guardrails default to run_in_parallel=True (guardrail.py, line 100): the check and the agent's first model call start together, which saves latency, and the docs say plainly that "if the guardrail's tripwire is triggered, the agent may have already consumed tokens and executed tools before being cancelled"; with run_in_parallel=False "the agent never executes" (guardrails docs).


Recorded: the same off-topic request ("Write a short poem about the sea.") against the fixer agent guarded by a topic checker (itself a small agent told to answer YES or NO; our first version gave it a typed output, which failed on this server for the reason in section 2):  MEASURED. Parallel guardrails are a latency optimisation, not a safety boundary: anything with side effects belongs behind a blocking check or a tool guardrail, which runs before each tool call.


Sessions and tracing


A session stores a conversation's items so the next Runner.run with the same session sends them again. Recorded with SQLiteSession:  MEASURED. A session is history, not durable execution: a run that crashes between two tool calls is not resumed.


Tracing records each run as a trace of spans (model calls, tool calls, handoffs, guardrails) and is on by default, exporting to OpenAI's dashboard. By default the spans include "LLM inputs and outputs" and "function call inputs and outputs"; turn that off with trace_include_sensitive_data=False, or tracing itself with OPENAI_AGENTS_DISABLE_TRACING=1, set_tracing_disabled(True) or per run; it is unavailable under Zero Data Retention (tracing docs). Recorded with no OpenAI key, the default:  MEASURED. If you run a non-OpenAI model with an OpenAI key in the environment, your prompts and tool outputs go to OpenAI's trace store unless you switch it off: check this before using the SDK on private data.


Predict: you add a blocking input guardrail that calls a small model to classify every request. What does it cost on requests that pass?
One extra model call of latency before the agent starts, on every request, plus its tokens. A parallel guardrail hides the latency but pays the agent's first call on requests that fail. Choose by what a failed request may do before it is stopped: if the agent's first step can have side effects, block.







5. smolagents: the action is a program


The idea. The other three libraries let the model emit one JSON tool call per action. Hugging Face's smolagents makes its main agent, CodeAgent, emit Python instead: the tools are exposed as Python functions, the model writes a short program that calls them (with loops, variables and arithmetic), the library executes it, and the printed output comes back as the observation. The argument is from the CodeAct paper, which reports "up to 20% higher success rate" for code actions than for JSON or text actions across 17 models (Wang et al., 2024). A ToolCallingAgent with ordinary JSON tool calls exists too.

How the loop works, and where it stops the model


Each step the model writes a "Thought:" and a code block between <code> and </code> (the default tags). The request carries stop sequences "Observation:", "Calling tools:" and the closing tag (agents.py), so generation ends right after the code: the model cannot write its own "Observation:" and invent the result, which is the action-boundary failure the harness pages recorded (Other coding harnesses, section 1). The run ends when the code calls final_answer(value), or after max_steps=20. There is no output schema: final_answer takes any object, and final_answer_checks (a list of functions that may reject it) is the hook for validation.


The local executor is a rule set, not a sandbox


By default the code runs in LocalPythonExecutor, an interpreter written in Python that walks the program's syntax tree and refuses what its rules do not allow: imports outside an allow-list (eleven standard modules by default: collections, datetime, itertools, math, queue, random, re, stat, statistics, time, unicodedata; utils.py, line 49), builtins it does not expose, access to double-underscore attributes, and loops past a cap. Its own docstring says: "It is not a security sandbox: for isolated execution of untrusted code, use a remote executor" (local_python_executor.py, line 1688). Benign probes, no model involved MEASURED:




Two rows carry the lesson. import os is refused by default, but once you authorise it (people do, to let the agent read files) it works and the program has the host's operating system; the list of "dangerous" modules in the source is labelled "Non-exhaustive". And the runaway loop is stopped by an iteration count, not by isolation. For anything beyond your own trusted tasks, the docs offer remote executors (executor_type "docker", "e2b", "modal", "blaxel") and say that "no local python sandbox can ever be completely secure" (secure code execution). Version 1.26.0 removed the WebAssembly executor. What a real sandbox does is on Agent security and Containers and isolation.


What the parent's runs found


On the running example with the local 4B model, smolagents fixed 0 of 8 runs, with code actions and with JSON tool calls (Same agent, six ways). Two causes are in the source: the CodeAgent's own system prompt made its first request 2,231 tokens against 385 to 507 for the others, and past tool calls go back into the history as plain text, "Calling tools:\n" + str([...]) (memory.py, line 106), rather than as native tool-call messages, so a small model imitates the text and the parser rejects it. A strong model copes; a small local one does not. Option use_structured_outputs_internally=True asks the provider to constrain each step to a JSON object holding the thought and the code, which helps only where the server enforces response formats (section 2 shows the local server here does not).







6. Google ADK: a runtime with sessions, events and workflow agents


The idea. Google's Agent Development Kit describes itself as "the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale", available in Python, TypeScript, Go, Java and Kotlin, with adapters for "many other models and model providers, including locally running models" (adk.dev, read 6 Oct 2026). Where the other three hand you a function that runs a loop, ADK hands you a small runtime: an agent, a Runner that executes it, a SessionService that stores what happened, and a stream of events (one per model reply, tool call or tool result) that the runner yields as the run proceeds.


Other models go through LiteLLM. For a model that is not Gemini, google-adk 2.11.0 needs LiteLLM; every ADK run here used LiteLlm(model="openai/" + name, api_base=...) against the local server's Chat Completions endpoint. The provider prefix is not cosmetic: it decides the wire format. Section 8 of Gateways and routing (the translation layer) sent an Anthropic /v1/messages request through the LiteLLM proxy: an openai/ deployment forwarded it upstream as the OpenAI Responses API (/v1/responses, which the local server does not serve), while an lm_studio/ deployment sent /v1/chat/completions and worked.


Agents


    

  • LlmAgent (also exported as Agent): instruction, tools (plain functions become FunctionTools), optional output_schema and output_key, optional sub_agents. ADK appends a line to your instruction naming the agent: the recorded request ends with 'You are an agent. Your internal name is "fixer". The description about you is "Fixes failing tests by editing code."', and tool results go back wrapped as {"result": ...} MEASURED.
    • 

  • Workflow agents that call no model themselves: SequentialAgent, ParallelAgent and LoopAgent run their sub-agents in a fixed pattern; version 2 adds graph workflows (a workflow package of nodes and edges in the 2.11.0 wheel; the docs announce "ADK TypeScript 2.0 GA ... with graph workflows support"). These are the root's workflow patterns as classes (Topic: agentic-frameworks, Reading, section 1).
    • 

  • Transfer: an agent with sub_agents gets a transfer_to_agent(agent_name, transfer_reason) tool whose agent_name is an enum of the valid names, so the model cannot invent one (tools/transfer_to_agent_tool.py). Same idea as the Agents SDK's handoffs, one tool instead of one per target. Recorded:  MEASURED.
    • 



State as a ledger of events


A session holds the events and a state dictionary. State is never assigned directly in a well-behaved agent: a tool, callback or agent puts a change in an event's state_delta, and the session service applies it when the event is appended, so every change is logged next to what caused it (state docs). Key prefixes give scope: no prefix is this session, user: is shared across a user's sessions, app: across all users, temp: lives for one invocation and is "Not Persistent". output_key="triage" writes the agent's final reply into state["triage"], and another agent's instruction can read it with {triage} (or {triage?} when it may be absent): that is how a SequentialAgent passes data from one step to the next.


Typed output


output_schema is sent to the model as a response format; ADK validates the reply and stores the parsed object under output_key. When the agent also has tools and the model is not known to support both at once, ADK adds a set_model_response tool and an instruction beginning "IMPORTANT: You have access to other tools, but you must provide your final response using the set_model_response tool" (flows/llm_flows/prompt/_schema.py): the same trick as Pydantic AI's final_result. The measured behaviour on the local model is in section 2.


The seventh way: ADK on the running example


The parent's Same agent tab compared six ways to write one agent but not ADK. Same task, same four tool bodies, same system prompt, local model, a 15-call cap:  MEASURED. ADK's default cap is 500 model calls per run (agents/run_config.py, overridable with ADK_MAX_LLM_CALLS), the highest of the four: set your own.


A2A in one call, and deployment


to_a2a(agent) wraps any ADK agent as an A2A server (the agent-to-agent protocol, on the wire on Agent-to-agent and beyond), a Starlette web app whose agent card (the JSON document other agents fetch to learn what this one does) is built automatically. Fetched in-process with no model call MEASURED:  Two things to notice: the card lists every tool as a public "skill", names and descriptions included, so review it before exposing an agent; and ADK's A2A classes print "[EXPERIMENTAL] ... subject to breaking changes" warnings in 2.11.0, while "A2A protocol and SDK are themselves not experimental". Deployment targets in the docs are Google Cloud's Agent Runtime, Cloud Run and GKE, or any container (not run here).







7. The role-based contrast: CrewAI and Microsoft Agent Framework


The four libraries above ask you for functions and types. The role-based school asks for characters: CrewAI agents need a role, a goal and a backstory, tasks are assigned to them, and a sequential or hierarchical process runs the crew, with event-driven Flows for fixed pipelines (CrewAI docs; crewai 1.15.23 on PyPI, 28 Sep 2026). The library writes the prompts from those fields. Microsoft Agent Framework (agent-framework 1.20.0 on PyPI, 2 Oct 2026) is "the next generation of both Semantic Kernel and AutoGen", with agents, typed graph workflows and checkpointing (Microsoft Learn). The difference that matters for this page: in a role-based library the prompt is generated from a persona, so the typed parts (tools, outputs) are a smaller share of what decides behaviour. The parent root compares the schools (Topic: agentic-frameworks, Reading, section 2); neither was run here.







8. Choosing between them




Pydantic AI
When the result is data another program consumes and you want the type checker, validators and retries on your side. Model-agnostic, explicit history, the most control over output. Bring your own persistence.


OpenAI Agents SDK
When the shape is a few specialised agents that pass a conversation along, with guardrails, on OpenAI or any Chat Completions server. Decide about tracing first; it is on by default.


smolagents
When the work is computation over tool results (loops, arithmetic, many small calls) and the model is strong. Run the code in a remote executor. Avoid it with small local models.


Google ADK
When you want a runtime rather than a loop: sessions with scoped state, workflow agents, A2A and a deployment path, especially on Google Cloud or with Gemini. Set the call cap.




Or none of them. All four are thin over the same loop. With the same small model, the parent's plain loop fixed the running example in 3 of 4 runs, LangGraph in 4 of 4, Pydantic AI and smolagents in none cleanly, and section 2 shows the library choice mattered less than whether the server honoured the request's structured-output field. A library earns its place when you use what it adds: validation and retries, handoffs and guardrails, an executor, sessions and state. If you use none of that, the loop you can read is the better choice (the 12-factor argument on the root, "Own your control flow").







9. Common mistakes and interview questions


Trusting NativeOutput or output_type on a server you have not checked
The schema moves from the prompt into response_format. If the server drops that field (the local mlx-lm server here does, silently), the model never sees the schema. Section 2 measured it. Test once with a schema the model could not guess.


Validating shape and calling it done
A valid Triage can name a function that does not exist. Content checks with access to the real inputs (Pydantic AI's output validators with deps, smolagents' final_answer_checks) catch what a schema cannot.


Leaving retries at the default
Pydantic AI gives one output retry, the Agents SDK none. One retry is too few for a small model and silent retries hide drift: set the budget and count retries in your metrics.


Treating a parallel guardrail as a gate
The agent's first call runs while the check runs. Anything with side effects needs a blocking guardrail or a tool guardrail.


Shipping traces you did not mean to
The Agents SDK exports traces with inputs and outputs by default when an OpenAI key is present. Decide per deployment.


Authorising os in the smolagents local executor
That turns the rule set into the host. Use a remote executor for anything you would not run yourself.


Exposing an ADK agent over A2A without reading its card
The generated card lists every tool by name and description.


Interview questions


Name three ways to get structured output from a model and their guarantees.
Prompted (schema in the instructions, parse the text: no guarantee), tool-forced (the schema as a tool's parameters, the model must call it: trained behaviour, validate and retry), native constrained decoding (the server masks tokens that would break the schema: valid by construction, content still unchecked). Constrained decoding needs the server to support it.


How does a handoff differ from calling an agent as a tool?
A handoff transfers the conversation: the new agent replies to the user and owns the rest of the run. An agent as a tool runs a sub-agent on a sub-task and returns its result to the caller, which stays in charge. In the Agents SDK both are tools on the wire; the difference is what happens after the call.


Why does the OpenAI Agents SDK mark a parameter with a default as required?
Strict schemas need every property in required and additionalProperties: false; strictness lets the provider constrain the arguments. The default stays in Python and the model always sends a value.


Why are code actions risky and what do you do about it?
The model's program runs with your process's rights unless isolated. An interpreter with allow-lists reduces mistakes but is not a boundary; run the code in a container or a remote sandbox with no secrets and limited network.


Where does an ADK agent keep data that another agent in a SequentialAgent needs?
In session state, written by output_key (or a tool's state_delta) and read with {key} in the next agent's instruction; the change is recorded on an event.
