The page in one screen

A model forgets everything between calls. Inside one session the harness resends the conversation; when the session ends, so does the memory. A memory layer is a store outside the context window with two policies: a write policy (after a conversation, what to keep, and what to do with what it contradicts) and a read policy (before an answer, what to put back into the prompt). Three designs dominate, each sold as a product:

Facts (Mem0)

A model turns each conversation into short sentences ("User's tests run with pytest"); a search over those sentences picks the ones to show. Cheap to read, easy to inspect. Since April 2026 the open-source library only ever adds: a changed fact becomes a second sentence beside the old one.

Temporal graph (Zep, Graphiti)

A model turns each conversation into entities and dated relations between them; a newer relation that contradicts an older one closes the older one's validity window instead of deleting it. Built for "what changed, and when".

Paging (Letta, MemGPT)

The model itself manages its memory with tools: a small block that is always in the prompt, plus archives it writes to and searches, like an operating system moving pages between RAM and disk. Nothing is stored or found unless the model decides to.

All three were run here on the same twelve invented conversations between a user, Sam, and an assistant (the parent topic's four sessions, extended), then asked 25 questions of the kinds LongMemEval tests. Every memory, edge, tool call and answer below is MEASURED from those runs; the table fills from the recordings.

Three corrections to what the parent pages and the old notes say
(1) Mem0's update step as the parent root describes it (ADD, UPDATE, DELETE, NOOP; its Production stack tab implements exactly that) is the 2025 paper and Mem0 1.x; the open-source library since v2.0.0 (16 April 2026) is "single-pass, ADD-only" (release notes), measured below. (2) The Letta server that implements MemGPT's memory blocks, archival and recall memory was archived on 16 August 2026; the PyPI name letta now installs Letta Code, whose memory is a git-backed folder of Markdown files ("MemFS"). (3) Mem0 has no "layers (conversation, user, organisation) with promotion between layers", as the old Notion page said: it scopes memories by user_id, agent_id and run_id, and nothing is promoted (docs).

1. From zero: what a memory layer is for

The problem. The context window is everything the model sees in one call. Within a session, the harness keeps a conversation going by resending the whole history each turn (how, and what that costs, is the subject of Context engineering). A new session starts empty. Users expect an assistant to remember that they switched to pytest last week; a coding agent should not rediscover the test command every morning.

There are four ways to carry knowledge from one session to the next, in rising order of machinery:

1. Paste the full history

Works while it fits, and is the baseline every memory product has to beat. Costs input tokens on every call, and recall falls as the window fills (Context engineering, section 8, measures it). In this page's experiment the whole history is about tokens (characters divided by four), so it fits easily: that is deliberate, so the baseline is an honest upper bound.

2. Notes the agent keeps

Progress files, a CLAUDE.md, the Claude API's memory tool: the agent writes plain files and reads them next time. Owned by Context engineering, section 7 (notes outside the window); a resident assistant's version (always-loaded files plus searched daily notes) is in Personal agents, section 5.

3. Search the raw history

Keep every message, embed or index it, and retrieve the most similar ones before answering: retrieval-augmented generation over your own chat log (rag-and-retrieval, not yet migrated). Nothing is lost, but nothing is consolidated either: "the test command is now pytest" and "tests run with test_core.py" come back side by side.

4. A memory layer

A model derives a smaller store from the history (facts, a graph, a self-edited block) and decides what to do when new information contradicts old. This page. LangGraph's store is the bare key-value version of it (LangChain and LangGraph, section 10).

Two decisions define every memory layer. The write policy: what is extracted from a conversation, in what form, and what happens to an existing memory that the new one contradicts (overwrite it, keep both, or close it with a date). The read policy: who decides to look (the harness always searches, or the model searches when it chooses to), with what query, and how many results go into the prompt. A layer that writes well but reads badly fails as surely as one that never wrote the fact.

answer correct ⇒ fact written ∧ fact retrieved ∧ fact read correctly

Every failure in this page's experiment sits at one of those three links; section 5 separates them by checking whether the right evidence reached the prompt (no model needed) before asking whether the answer was right.

Vocabulary you will meet. LangMem's guide splits long-term memory into semantic (facts and knowledge: preferences, "knowledge triplets"), episodic (past experiences: summaries, few-shot examples) and procedural (how to behave: prompt rules), and memory formation into "in the hot path" (the agent saves while it talks, adding latency) and in the background (a reflection pass afterwards) (LangMem conceptual guide, read 6 Oct 2026). All three products here are semantic memory formed in the background (Mem0, Graphiti) or in the hot path (Letta). Two recent papers in this knowledge base question when to curate: Just-in-Time Memory curates at read time once the task is known, and Proactive Memory Agent runs a second model that injects reminders.

What a memory has to get right: LongMemEval's five abilities

LongMemEval (Wu et al., arXiv 2410.10813, ICLR 2025) is the benchmark built for this: 500 questions over chat histories of about 115K tokens (setting S), testing five abilities. This page's 25 questions use the same five, on Sam's history:

2. Fact memory: Mem0, the paper and the library

The idea. Store what was learnt, not what was said: a model reads the conversation and writes short, self-contained sentences ("Sam's tests run with python3 -m pytest -q"), each embedded as a vector. Before an answer, the question is embedded too and the closest sentences are pasted into the prompt. Reading is one search, a few milliseconds, and the prompt grows by a few hundred tokens instead of the whole history.

The hard part is change. When Sam says "we moved to pytest", the old sentence "tests run with test_core.py" is now wrong. Mem0's answer changed in 2026:

The paper (Apr 2025) and Mem0 1.x

Two phases (Chhikara et al., arXiv 2504.19413, section 2.1). Extraction: a model sees the new message pair, a running summary and the last m = 10 messages, and lists candidate facts. Update: for each candidate, the s = 10 most similar stored memories are retrieved and a model picks one operation by tool call: ADD, UPDATE ("augmentation of existing memories with complementary information"), DELETE ("removal of memories contradicted by new information") or NOOP. All with GPT-4o-mini. The store holds the current truth; the past is gone (a history table logs the edits).

The library since v2.0.0 (16 Apr 2026), run here at 2.2.1

"Single-pass, ADD-only": one call per add(), "No separate UPDATE/DELETE pass ... Hash-based deduplication prevents exact duplicates; ranking at retrieval time handles the rest" (v2.0.0 release). The call sees the 10 stored memories most similar to the new messages (their ids replaced by small integers, "anti-hallucination"), the last 10 messages of the scope, and an observation date (main.py, _add_to_vector_store). Old and new facts both stay; the docs: "Nothing is overwritten or deleted" (memory evaluation).

Reading in 2.2.1 is hybrid (_search_vector_store, score_and_rank): a vector search over-fetches max(4 × k, 60) candidates; a BM25 keyword search runs on spaCy-lemmatised text; named entities in the question boost memories linked to the same entity; candidates whose cosine similarity is under 0.1 are dropped, and the rest are ranked by

score = (cos + bm25̂ + entity boost) / (1 + 1bm25 + 0.5entity)
cos
cosine similarity of question and memory embeddings (here bge-small-en-v1.5, 384 dimensions)
bm25̂
BM25 score squashed into 0 to 1 by a sigmoid whose midpoint depends on query length
divisor
1 plus 1 if any BM25 hit, plus the entity weight (0.5) if any entity hit, so a memory found by all three signals can reach 1.0

Two things the open-source library cannot do that its paper and platform can
Dates. add() takes a timestamp argument documented as "Platform-only temporal parameter. Not supported in OSS." The extraction prompt's "Observation Date", the anchor for "yesterday" and "last week", is therefore the machine's current date. In live use that is right; when you import an old history it is wrong for every message. This run simulated live use by setting the prompt's date to each session's date (the patch is in src/code/run_mem0.py). Prompt size. The extraction system prompt alone is tokens (counted with the Qwen3 tokenizer), larger than the shared local model server's safe limit, so the library's writes here used Haiku; the local 4B model ran the paper loop instead.

3. Temporal graph: Zep and Graphiti

The idea. Facts are relations between things: Sam uses OpenRouter, Priya manages Sam. Store them as a graph whose nodes are entities (Sam, OpenRouter, Priya) and whose edges are facts, each carrying the time it became true and, once something contradicts it, the time it stopped. Nothing is deleted: "LiteLLM is the gateway" stays in the graph, closed on 15 September, so the graph can answer both "what now" and "what before".

Who is who. Zep (the company) published the design (Rasmussen et al., arXiv 2501.13956, 20 Jan 2025); its open-source engine is Graphiti (Apache-2.0, 31,489 GitHub stars on 6 Oct 2026). Zep stopped maintaining its self-hosted Community Edition on 2 April 2025 (announcement); Zep Cloud now runs on a proprietary engine. Graphiti 0.30.2 needs a graph database: Neo4j, FalkorDB, Amazon Neptune, or the embedded Kuzu, which is deprecated ("the upstream Kuzu project is no longer maintained") and here failed on the first episode ('KuzuDriver' object has no attribute '_database'); this run used FalkorDB 4.22 in Docker.

Four timestamps per fact

The paper's model is bi-temporal: "t'_created and t'_expired ... monitor when facts are created or invalidated in the system, while t_valid and t_invalid track the temporal range during which facts held true." In Graphiti's edge they are created_at, expired_at, valid_at and invalid_at. The first pair is the database's clock; the second is the world's. In this replay they differ visibly: every closed edge has expired_at 6 October 2026 (the day the run happened) but invalid_at in September (the session date that contradicted it), which is exactly the distinction the design exists for.

What one call to add_episode does

Each of Sam's sessions went in as one episode (the raw text, kept as "a non-lossy data store") with reference_time set to the session's date. The recorded calls show the pipeline, prompt by prompt (names as Graphiti logs them, counts from the Haiku run):

Invalidation is a model's judgement. For each new edge, Graphiti finds similar existing edges and asks a model, in one prompt, which are duplicates and which the new fact contradicts (prompts/dedupe_edges.py). Code then closes each contradicted edge by setting its invalid_at to the new edge's valid_at, provided the old edge started earlier (resolve_edge_contradictions). An edge with no valid_at (the model could not date it) is never closed by that rule.

Reading. Graphiti.search combines cosine similarity over edge embeddings with BM25 full-text search and merges the two lists by reciprocal rank fusion; the paper adds breadth-first graph search and rerankers (maximal marginal relevance, distance from a centre node, episode mentions, a cross-encoder). Only edges come back, so a detail that ended up in an entity's summary rather than on an edge is invisible to this search.

4. Paging: MemGPT and Letta

The idea. Treat the context window like RAM and give the model the job of an operating system's memory manager. MemGPT (Packer et al., arXiv 2310.08560, 12 Oct 2023) splits the prompt into system instructions, a working context the model edits with function calls, and a queue of recent messages; outside the prompt sit recall storage (every past message, searchable) and archival storage (anything the model chose to file away, searched by embedding). When the prompt passes a warning threshold ("e.g. 70% of the context window") the system tells the model so; at the flush threshold it evicts about half the queue into recall storage and replaces it with a recursive summary. The analogy is with paging in an operating system (Virtual memory): small fast memory, large slow memory, something deciding what moves.

The published evidence is MemGPT's own Deep Memory Retrieval test (five short sessions per conversation): GPT-4 alone with a fixed window and recursive summaries answered 32.1% correctly, GPT-4 inside MemGPT 92.5%; GPT-4 Turbo 35.3% against 93.4%. Zep later reported that the full conversation, pasted in, scores 94.4% on the same test with GPT-4 Turbo: the baseline MemGPT beat was a deliberately small window (Published numbers).

16 Aug 2026
The server repository is archived ("chore: archive the legacy server repository"); development moves to Letta Code. From 0.32.13 (17 Sep 2026) the PyPI name letta installs Letta Code, a terminal agent.
Now
Letta's memory is MemFS: "a git repository that belongs to the agent"; files at its root are in the system prompt every turn, other folders are read on demand, and there is no vector index by default. Background "dreaming" subagents consolidate memory (MemFS docs, read 6 Oct 2026). That is the memory-files design of Context engineering, section 7, run by the agent itself.

Running the archived server took three repairs, each a finding: pip install letta==0.16.8 today resolves to dependency versions that break its imports (installing with dependencies as of its release date fixed that); its database layer only speaks Postgres, though its settings still mention SQLite; and the wheel ships no migrations, so the tables were created from its ORM, and the message table's sequence default added by hand. The agent was Letta's default type (letta_v1_agent) with archival tools added, an 8,192-token window (the shared local model server's limit), temperature 0, and the local Qwen3-4B, which is the only model here that can drive Letta's tool loop over an OpenAI-compatible endpoint. Each session went in as one dated message; each question was asked in a fresh conversation of the same agent with its blocks copied, so questions could not see each other.

Every failure below happened in this page's runs; each card names the mechanism, shows the recorded evidence, and says what would have prevented it. They are the failures to test for before trusting any memory layer, including your own.

7. What memory costs

A memory layer moves cost from every answer (no long history in the prompt) to every conversation (model calls to write the memory), and adds a search before each answer. The table counts what the runs here spent; Claude figures are the CLI's API-price equivalent at Haiku 4.5 list prices (the subscription paid), local-model figures are tokens and seconds on a shared, busy M1 Pro and are only comparable with each other.

break-even sessions ≈ write cost per session / (history tokens saved per answer × answers per session × input price)

At this page's size (about 1,400 tokens of history) pasting everything is cheaper than any memory layer for a long time. The vendors' own numbers make the same point at their scale: Mem0's paper puts full context at 26,031 tokens per LOCOMO conversation against 1,764 for Mem0, and Zep's at about 115K against 1.6K on LongMemEval; the saving only appears once history is tens of thousands of tokens and is read many times.

The ownership split, in one paragraph
What the model sees in one call (budgets, caching, compaction, memory files, subagents) is context engineering and belongs to the harnesses topic. A memory layer is a separate store a framework plugs in, with its own write and read policy, and belongs here. Retrieval is the read path both reuse. The three meet in one design question: who curates, and when: the harness at write time (Mem0, Graphiti), the model in the hot path (Letta, the memory tool), or a curator at read time (Just-in-Time Memory).

Checking a memory layer before you trust it

  1. Write a question set like section 5's on your own data, with all five abilities, and keep the full-history baseline in it while history fits.
  2. Measure evidence before answers. Log what the memory put in the prompt; if the evidence is not there, no reader model will fix it.
  3. Read the store after every session for a while: duplicates, wrong dates and wrongly closed facts are visible long before they cause a wrong answer.
  4. Log write failures loudly. An extraction that fails to parse must be an alert, not an empty list.
  5. Swap the writer model and rerun: here the same library with a 4B writer lost episodes the Haiku writer did not.

Common mistakes

"Memory layer X scores 90% on LOCOMO, so it is the best."
Ask who ran it, with which answer model, at what retrieval budget, on which version, and against full context. On the Published numbers tab the same product spans 58.44% to 80.32% on the same benchmark.
"Mem0 updates and deletes outdated memories."
The 2025 paper and Mem0 1.x did. The open-source library since 2.0.0 is ADD-only; its docs: "Nothing is overwritten or deleted." Old and new versions are both stored and the retrieval ranking has to sort them out.
"A temporal graph knows when facts changed."
It knows when a model said they changed. Invalidation is an LLM judgement per new fact; here it closed a past measurement because a later one existed, and could never close facts it had failed to date.
"Give the agent a search tool and it will remember."
Only if it decides to search. The small model here mostly answered from what was already in its prompt; the sibling page Personal agents measured Haiku never searching until one sentence of instruction told it to.
"Replaying old chat logs into a memory layer recreates the memory."
Not with dates: the Mem0 open-source add() has no timestamp ("Platform-only"), so every replayed message is dated today and every "yesterday" resolves to the wrong day. Graphiti takes a reference_time per episode; Letta stamps messages when they arrive.
"Memory saves tokens."
Per answer, yes; per conversation, writing costs model calls (one per session for Mem0, several per episode for Graphiti). Below tens of thousands of tokens of history, pasting it all is cheaper and more accurate.

Interview questions

Design memory for a support assistant used by a million users.
Scope memories per user (and per account); write in the background after each conversation, not in the hot path; store short facts with source message ids and dates; read with hybrid search (embeddings plus BM25) and a small top-k; keep raw transcripts for audit and re-extraction; resolve conflicts explicitly (latest wins with history kept, or validity windows); evaluate with a LongMemEval-style set including abstention and knowledge updates; let users see and delete what is stored.
The user says "I moved from Austin to Seattle". What should each design store?
Paper-style fact memory: update "lives in Austin" to "lives in Seattle" (history lost unless logged). Mem0 2.x: add "moved to Seattle" beside "lives in Austin" and rely on ranking. Temporal graph: close the LIVES_IN Austin edge at the move date, open LIVES_IN Seattle. Self-managed: the model edits its core block if it notices. Only the graph answers "where did I live in March" directly.
How do you know whether a wrong answer is a memory failure or a model failure?
Check whether the evidence reached the prompt. If not, the write or read policy failed (never written, written wrongly, or not retrieved); if it did, the reader failed. This page's evidence column separates the two without any model.
Why can adding memory make an assistant worse?
Stale or duplicated facts outrank current ones, wrong dates get repeated with confidence, and retrieved snippets crowd out the instruction. Without a "say you don't know" rule, a memory layer also turns abstention questions into confident wrong answers built from near misses.
What is bi-temporal modelling, and why does an agent memory need it?
Two time axes per fact: when it was true in the world (valid_at, invalid_at) and when the system learnt or retired it (created_at, expired_at). An agent needs the first to answer "what was true then" and the second to audit and replay what it knew when it acted.

What the benchmarks test

LOCOMO

Paper: 50 conversations of about 300 turns and 9K tokens, up to 35 sessions. Public release: 10 conversations, 19 to 32 sessions and 369 to 689 turns each, 1,986 questions in five categories; 444 of the 446 adversarial questions have no reference answer, so every product evaluation drops that category (counted from locomo10.json, 6 Oct 2026). No knowledge-update questions.

LongMemEval

500 questions over five abilities: information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention (Wu et al., arXiv 2410.10813, ICLR 2025). The S setting has about 115K tokens of history per question, M about 500 sessions and 1.5M tokens. Counts in the released file: temporal 133, multi-session 133, knowledge update 78, single-session user 70, assistant 56, preference 30; 30 are abstention variants.

DMR (Deep Memory Retrieval)

Introduced by MemGPT: 500 conversations of 5 sessions with up to a dozen messages each. Zep's own paper says each conversation "easily" fits in a context window, and the full-conversation baseline scores 94.4% with gpt-4-turbo, beside MemGPT 93.4% and Zep 94.8% (arXiv 2501.13956).

MemoryAgentBench

Independent (UCSD, arXiv 2507.05257, v4 28 Jun 2026): feeds long inputs in chunks and tests accurate retrieval, test-time learning, long-range understanding and selective forgetting, all memory products on gpt-4o-mini. Mem0 21.1, Zep 24.0, MemGPT 28.3 overall, against plain BM25 41.5 and gpt-4o-mini with the whole input 42.2 (Table 3). The products ran as of 2025 and on document-style input, far from what they are tuned for; versions not stated.

How to read a memory benchmark claim
Ask five things: who ran it (vendor, rival, independent); does the whole history fit in the answer model's window (then full context is the baseline to beat, and it often wins); which answer and judge models (gpt-4o-mini in most rows above); how many memories were retrieved per question (Zep's own sweep went from 69.62% at 5 edges to 80.32% at 30); and which version of the product (Mem0's 2026 numbers are its managed platform, "which includes proprietary optimizations not available in the open-source SDK").
