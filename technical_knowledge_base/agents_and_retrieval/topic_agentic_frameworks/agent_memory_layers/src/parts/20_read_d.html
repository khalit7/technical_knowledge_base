4. Paging: MemGPT and Letta

The idea. Treat the context window like RAM and give the model the job of an operating system's memory manager. MemGPT (Packer et al., {{arXiv 2310.08560|https://arxiv.org/abs/2310.08560}}, 12 Oct 2023) splits the prompt into system instructions, a working context the model edits with function calls, and a queue of recent messages; outside the prompt sit recall storage (every past message, searchable) and archival storage (anything the model chose to file away, searched by embedding). When the prompt passes a warning threshold ("e.g. 70% of the context window") the system tells the model so; at the flush threshold it evicts about half the queue into recall storage and replaces it with a recursive summary. The analogy is with paging in an operating system ({{Virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}}): small fast memory, large slow memory, something deciding what moves.

The published evidence is MemGPT's own Deep Memory Retrieval test (five short sessions per conversation): GPT-4 alone with a fixed window and recursive summaries answered 32.1% correctly, GPT-4 inside MemGPT 92.5%; GPT-4 Turbo 35.3% against 93.4%. Zep later reported that the full conversation, pasted in, scores 94.4% on the same test with GPT-4 Turbo: the baseline MemGPT beat was a deliberately small window ({{Published numbers|#t-bench}}).

From MemGPT to Letta, and what is left of it

Sep 2024
MemGPT becomes Letta (the company and the framework); "MemGPT should refer to the original agent design pattern" ({{Letta blog, 23 Sep 2024|https://www.letta.com/blog/memgpt-and-letta/}}).
V1 server
Memory blocks (a label such as human or persona, a text value, a character limit) always in the prompt; tools to edit them (memory_insert, memory_replace); conversation_search over recall; archival_memory_insert and archival_memory_search ({{constants.py|lt:letta/constants.py}}); a REST server with Postgres and pgvector.
14 May 2026
Last PyPI release of that server, 0.16.8: the version run here.
16 Aug 2026
The server repository is archived ("chore: archive the legacy server repository"); development moves to Letta Code. From 0.32.13 (17 Sep 2026) the PyPI name letta installs Letta Code, a terminal agent.
Now
Letta's memory is MemFS: "a git repository that belongs to the agent"; files at its root are in the system prompt every turn, other folders are read on demand, and there is no vector index by default. Background "dreaming" subagents consolidate memory ({{MemFS docs|https://docs.letta.com/concepts/memfs/index.md}}, read 6 Oct 2026). That is the memory-files design of {{Context engineering, section 7|n:3f15c17b0d0d811292cee46514370431}}, run by the agent itself.

Running the archived server took three repairs, each a finding: pip install letta==0.16.8 today resolves to dependency versions that break its imports (installing with dependencies as of its release date fixed that); its database layer only speaks Postgres, though its settings still mention SQLite; and the wheel ships no migrations, so the tables were created from its ORM, and the message table's sequence default added by hand. The agent was Letta's default type (letta_v1_agent) with archival tools added, an 8,192-token window (the shared local model server's limit), temperature 0, and the local Qwen3-4B, which is the only model here that can drive Letta's tool loop over an OpenAI-compatible endpoint. Each session went in as one dated message; each question was asked in a fresh conversation of the same agent with its blocks copied, so questions could not see each other.
