1. From zero: what a memory layer is for

The problem. The context window is everything the model sees in one call. Within a session, the harness keeps a conversation going by resending the whole history each turn (how, and what that costs, is the subject of {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}). A new session starts empty. Users expect an assistant to remember that they switched to pytest last week; a coding agent should not rediscover the test command every morning.

There are four ways to carry knowledge from one session to the next, in rising order of machinery:

1. Paste the full history

Works while it fits, and is the baseline every memory product has to beat. Costs input tokens on every call, and recall falls as the window fills (Context engineering, section 8, measures it). In this page's experiment the whole history is about tokens (characters divided by four), so it fits easily: that is deliberate, so the baseline is an honest upper bound.

2. Notes the agent keeps

Progress files, a CLAUDE.md, the Claude API's memory tool: the agent writes plain files and reads them next time. Owned by {{Context engineering, section 7 (notes outside the window)|n:3f15c17b0d0d811292cee46514370431}}; a resident assistant's version (always-loaded files plus searched daily notes) is in {{Personal agents, section 5|n:3c75c17b0d0d81bf9462fbeb09593e1c}}.

3. Search the raw history

Keep every message, embed or index it, and retrieve the most similar ones before answering: retrieval-augmented generation over your own chat log ({{rag-and-retrieval|n:3c65c17b0d0d81b89145c37dfe8a3b0b}}, not yet migrated). Nothing is lost, but nothing is consolidated either: "the test command is now pytest" and "tests run with test_core.py" come back side by side.

4. A memory layer

A model derives a smaller store from the history (facts, a graph, a self-edited block) and decides what to do when new information contradicts old. This page. LangGraph's store is the bare key-value version of it ({{LangChain and LangGraph, section 10|n:3c65c17b0d0d81529358c996382224ac}}).

Two decisions define every memory layer. The write policy: what is extracted from a conversation, in what form, and what happens to an existing memory that the new one contradicts (overwrite it, keep both, or close it with a date). The read policy: who decides to look (the harness always searches, or the model searches when it chooses to), with what query, and how many results go into the prompt. A layer that writes well but reads badly fails as surely as one that never wrote the fact.

answer correct ⇒ fact written ∧ fact retrieved ∧ fact read correctly

Every failure in this page's experiment sits at one of those three links; section 5 separates them by checking whether the right evidence reached the prompt (no model needed) before asking whether the answer was right.

Vocabulary you will meet. LangMem's guide splits long-term memory into semantic (facts and knowledge: preferences, "knowledge triplets"), episodic (past experiences: summaries, few-shot examples) and procedural (how to behave: prompt rules), and memory formation into "in the hot path" (the agent saves while it talks, adding latency) and in the background (a reflection pass afterwards) ({{LangMem conceptual guide|https://langchain-ai.github.io/langmem/concepts/conceptual_guide/}}, read 6 Oct 2026). All three products here are semantic memory formed in the background (Mem0, Graphiti) or in the hot path (Letta). Two recent papers in this knowledge base question when to curate: {{Just-in-Time Memory|n:3e95c17b0d0d818f89b3f066f816727b}} curates at read time once the task is known, and {{Proactive Memory Agent|n:3e25c17b0d0d81ce85e0c6d82f6beb4c}} runs a second model that injects reminders.

What a memory has to get right: LongMemEval's five abilities

LongMemEval (Wu et al., {{arXiv 2410.10813|https://arxiv.org/abs/2410.10813}}, ICLR 2025) is the benchmark built for this: 500 questions over chat histories of about 115K tokens (setting S), testing five abilities. This page's 25 questions use the same five, on Sam's history:

AbilityWhat it testsExample hereQuestions
Information extractionOne fact said once, by the user or by the assistant"In the talk outline you drafted for me, what was the second point?" (an assistant-side fact)
Multi-session reasoningCombine facts from different sessions"How many times in total did the fallback kick in?" (37 in one session, 12 in another)
Knowledge updateThe latest value of a fact that changed"What gateway setup do we use right now?" (LiteLLM, then OpenRouter, then LiteLLM in front of OpenRouter)
Temporal reasoningDates, order, and past values"On what date did the agent delete the tests folder?" (said as "yesterday" on 17 September)
AbstentionSay "I don't know" when it was never said, or correct a false premise"When is the team offsite in Tokyo?" (it is in Lisbon)
Predict: with the whole twelve-session history pasted into the prompt (about 1,400 tokens), how many of the 25 questions does Claude Haiku 4.5 get right?
It got of 25. Even with everything in the window and a strong model, temporal questions failed: it dated the deletion to the day Sam reported it, not "yesterday", and put the OpenRouter outage on the wrong Saturday. A memory layer cannot beat this baseline on correctness here; its case is cost and scale, once history stops fitting.
