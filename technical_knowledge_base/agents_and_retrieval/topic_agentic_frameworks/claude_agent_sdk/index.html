The SDK in one screen

The Claude Agent SDK lets your own Python or TypeScript program run the agent that powers Claude Code: the same loop, tools, permission system, context management and sessions. It is not a reimplementation. When your code calls query(), the SDK starts the Claude Code program itself as a child process and talks to it in lines of JSON; your functions (permission checks, hooks, your own tools) are called back over that same pipe SOURCE MEASURED.

The agent loop (model call, tool call, tool result, repeat until the model stops) is taught from zero on Topic: agentic-harnesses (tab Loop lab), and Claude Code as a product, with its permission rule syntax, hook events, memory files and headless runs, is taken apart on Claude Code, taken apart. This page owns the library: what your code controls, what it costs, and how it differs from the frameworks compared on Topic: agentic-frameworks.

Three things to remember
  1. The SDK is a command-line builder plus a callback server. Everything Claude Code does still happens in the Claude Code process; read Claude Code, taken apart to know what that process does.
  2. Defaults are not safe defaults: with nothing set, the system prompt is empty, the tool list is Claude Code's full default set, every settings file on the machine is read, and in a subscription login the account's connected apps can join the tool list. Pass every option on purpose (section 3).
  3. "success" is not "done": our bare run ended with subtype: "success", six refused tool calls and both tests still failing (section 3).

1. What the SDK is: your program starting Claude Code

The problem it solves. Claude Code is a terminal program. If you want its agent inside your own service (a support bot, a code-review job, an internal research agent), you can either rebuild the loop, tools, permissions and context management yourself (the Loop lab on the harnesses root shows what that takes) or drive Claude Code from code. Anthropic first shipped the second option as the Claude Code SDK and renamed it the Claude Agent SDK on 29 September 2025, because "the agent harness that powers Claude Code ... can power many other types of agents, too" (Anthropic, Thariq Shihipar, 29 Sep 2025) DOCS. Packages: Python claude-agent-sdk (first release 0.1.0 on 28 September 2025 UTC, MIT licence for the Python wrapper per its PyPI classifier) and TypeScript @anthropic-ai/claude-agent-sdk (0.1.0 on 29 September 2025; its package says "All rights reserved", use under Anthropic's legal agreements) (PyPI, npm) DOCS.

How it works. The Python wheel carries a whole Claude Code binary (_bundled/claude, 225,167,728 bytes on macOS arm64 for 0.2.163, which pins Claude Code 2.1.286); the TypeScript package pulls a platform package with its own binary (233,211,568 bytes, Claude Code 2.1.291 for SDK 0.3.291: the TypeScript version 0.3.N ships Claude Code 2.1.N) MEASURED. The Python transport looks for the bundled binary first, then claude on the PATH, then a few fixed install locations; cli_path overrides all of that (_internal/transport/subprocess_cli.py, 0.2.163) SOURCE. It then starts the binary with --output-format stream-json --verbose --input-format stream-json plus one flag per option you set, sets CLAUDE_CODE_ENTRYPOINT=sdk-py and CLAUDE_AGENT_SDK_VERSION in its environment, and from then on both sides write one JSON object per line: your prompt and your answers go down the child's standard input, messages and questions come back on its standard output. The docs say the same: "When your code calls query(), the SDK spawns a separate claude CLI process and talks to it over stdio", and "One agent session maps to one subprocess" (Hosting the Agent SDK) DOCS.

Drawn from the recorded wire of run s1 (Haiku 4.5, our four tools, a hook and a permission callback): the counts are its real traffic. The Wire lab tab replays all 83 lines one by one, next to a run where nobody answers.

Two kinds of lines share the pipe. Messages are the conversation: the system/init record, assistant messages (thinking, text, tool calls), user messages (tool results) and the final result. Control messages are the side channel: a control_request with a request id and a control_response that echoes it. Your process sends initialize (with the ids of your hook callbacks and your subagent definitions), interrupt, set_permission_mode, set_model, rewind_files, get_context_usage and a few MCP management requests; the Claude Code process sends can_use_tool, hook_callback and mcp_message (a JSON-RPC message for an MCP server that lives inside your process) SOURCE. In run s1 the Claude Code process asked our process 28 questions in 15.8 seconds: 14 hook calls, 4 permission questions and 10 MCP messages (initialize, the initialized notification, the tool list, 7 tool calls) MEASURED.

What this means in practice

Your callbacks are in the critical path of every tool call: a slow can_use_tool or hook slows the agent, and an exception in one comes back to Claude Code as an error response. The model, the context window, compaction, the tool implementations of Read, Edit and Bash, and the session file all live in the child process; your process sees them only as messages. The answer to "how does the SDK do X" is almost always "Claude Code does X; the SDK passes a flag". An infrastructure analogy from the old version of this page still helps: Claude Code is a managed runtime in which hooks are middleware, subagents are worker processes with private memory, MCP is the driver interface, permissions are the security policy and skills are lazy-loaded configuration.

Predict: you run 50 agents at once with the SDK on one machine. How many Claude Code processes are running?
Fifty: one per session. (We did not check whether a subagent starts a further process; the session files show each subagent writing its own transcript inside the parent session's folder, section 6.) The hosting docs suggest planning "1 GiB RAM, 5 GiB disk, and 1 CPU per agent" as "a floor, not the ceiling" (hosting) DOCS. This is the main operational difference from a library such as Pydantic AI, where an agent is an object in your process.

2. Two ways in: query() and ClaudeSDKClient

query() starts one Claude Code process, sends the prompt and yields messages until the result. The prompt is either a string or an async iterator of user messages (streaming input). The docs call streaming input "the preferred way" and list what the string form lacks: image attachments, queued messages, interruption and natural multi-turn conversation (streaming vs single message) DOCS. All our runs that use a permission callback stream the prompt as a one-message iterator, as the docs' examples do.

The messages your loop receives, by Python class: SystemMessage (the init record with model, tools, permission mode and Claude Code version; also permission_denied and progress notices), AssistantMessage (one per content block: thinking, text or a tool call, all blocks of one model call sharing a message_id), UserMessage (tool results), Task*Message (subagent started, progress, finished), RateLimitEvent, and the final ResultMessage with subtype, num_turns, total_cost_usd, usage, model_usage, permission_denials and structured_output (types.py, 0.2.163) SOURCE. With include_partial_messages=True you also get the raw token stream.

query() is not stateless. Every call writes its conversation to ~/.claude/projects/<encoded working directory>/<session id>.jsonl (sessions) DOCS; our recordings left 15 session transcripts there (9 KB to 567 KB; the two largest came from the connector measurements of section 9), plus two subagent transcripts in a subfolder of run s5's session; we measured and deleted them MEASURED. TypeScript has persistSession: false; Python 0.2.163 has no such option (its extra_args can pass the command line's --no-session-persistence flag: not run here).

ClaudeSDKClient (Python only; TypeScript uses a streaming prompt and continue) keeps one Claude Code process open: client.query() sends the next turn, receive_response() reads until that turn's result, and between turns you can call get_context_usage(), interrupt(), set_permission_mode(), set_model() or rewind_files() SOURCE. Run s4 used it for two turns, then started two more processes from the saved session: one with resume, one with resume plus fork_session.

Run s4, Haiku 4.5, our four tools. "Reported" is the result message's total_cost_usd; "own" is the difference from the previous phase. Same session id after resume, a new one after the fork.

What the run shows MEASURED: (1) the second turn remembered the first without our code sending any history: the history lives in the Claude Code process; (2) total_cost_usd and model_usage are running totals, across turns of one client and across later processes that resume the session, while usage covers only the last turn; the docs say so: "A call that resumes a session also counts the session's earlier spend" (cost tracking) DOCS; (3) the fork answered from the full history ("Both failures have been fixed") under a new session id, so the original session can continue separately. The context report after turn 1 split 2,572 tokens into system prompt 56, MCP tools 258 (list_files 51, read_file 58, edit_file 96, run_tests 53) and messages 2,258, with autocompaction set for 167,000 of Haiku's 200,000.

Interrupting a running turn is recorded on Building a harness: the SDK's interrupt() made Claude Code write a refused tool result and end with error_during_execution.

The mapping is in _build_command(); the Options lab rebuilds it so you can see the exact command for any choice, checked against the commands our runs actually started. Four defaults deserve to be known by heart SOURCE DOCS:

  • System prompt: empty. system_prompt=None sends --system-prompt "". Since v0.1.0 "The SDK no longer uses Claude Code's system prompt by default"; ask for it with {"type": "preset", "preset": "claude_code"}, optionally with "append" (migration guide).
  • Tools: Claude Code's whole default set. tools=None adds no flag, so you get the default list; ours had 29 tools (Read, Edit, Write, Bash, WebFetch, WebSearch, Skill, the subagent tool and the task tools among them; Glob and Grep absent, as Claude Code, taken apart found on macOS) MEASURED. tools=[] removes them all.
  • Settings: everything on the machine. setting_sources=None reads user, project and local settings, "matching the CLI": your ~/.claude/settings.json, its hooks, CLAUDE.md files, skills and commands. A short-lived v0.1.0 change to load nothing "was briefly changed ... and then reverted" (same page). Pass [] to isolate (Python 0.1.59 and earlier treated [] as "not given").
  • Outside MCP servers: allowed. Without strict_mcp_config=True, servers from .mcp.json, settings and plugins load, and with a claude.ai login so do the account's connectors, which the docs list among things "read regardless of settingSources" (Claude Code features in the SDK). Section 9 shows what that did to one call.
Predict, then open: run s3 gives the textstats task to query() with only isolation added: Claude Code's default tools, the empty system prompt, permission mode default, no permission callback. Do the tests pass?
No. The run ended with subtype: "success" after 14 model calls, but 6 of its 16 tool calls were refused: 3 Bash calls ("This command requires approval", including the plain python3 tests/test_core.py) and all 3 edits ("Claude requested permissions to write to /work/textstats/core.py, but you haven't granted it yet."). Nobody was there to answer "ask", so ask became deny. Its final answer found both bugs and asked: "Please approve the file edits". Tests after: 2 failed. Cost: 247,863 input tokens processed, $0.0867 at list prices, against $0.0215 for run s1, which fixed both bugs MEASURED. Check permission_denials and your own test, never only subtype.

The fix is a decision about who answers "ask": a mode (acceptEdits approves file edits and simple file commands in the working directory; dontAsk turns every unresolved ask into a deny, which makes an allow-list exact), allow rules (allowed_tools=["Bash(python3 tests/test_core.py)"]), or your own can_use_tool. Section 5 shows the order in which these are consulted.

What happens on the wire (run s1) MEASURED: before the first model call the Claude Code process opened our server with an MCP initialize (protocol version 2025-11-25, client name claude-code), sent the initialized notification and asked for tools/list; the SDK had turned {"path": str} into the JSON schema {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}. Each tool call was then one tools/call round trip: 1 to 5 ms for the file tools, 26 and 36 ms for the two test runs (which start Python). The MCP protocol itself (initialize, capabilities, transports) is taught on MCP.

Details from the docs worth knowing (custom tools, MCP, tool search) DOCS: return is_error for a failure the model should see; annotations such as readOnlyHint let read-only tools run in parallel but "are metadata, not enforcement"; stdio and in-process servers may delay the first turn by up to MCP_TIMEOUT (30 s by default); tool search is on by default, because "50 tools can use 10-20K tokens" and selection "degrades with more than 30-50 tools loaded at once", and it is switched off when ANTHROPIC_BASE_URL points to a host that is not Anthropic's.

5. Permissions and hooks: your code in the decision

Every tool call passes a permission check run by the Claude Code process. The SDK docs give the order: (1) hooks, (2) deny rules ("even in bypassPermissions mode"), (3) ask rules (these go to your callback even in bypass mode), (4) the permission mode, (5) allow rules (including calls a tool approves on its own, such as reading a file in the working directory), (6) your can_use_tool callback; in dontAsk mode step 6 is skipped and the call is denied (configure permissions) DOCS. Two consequences: "Auto-approved tools never reach canUseTool", so a callback is not an audit log (use a PreToolUse hook for that); and a hook that returns allow still cannot override a deny rule. The SDK source adds that a PreToolUse hook returning allow "also skips" the callback, and setting can_use_tool makes the SDK pass --permission-prompt-tool stdio so the questions come down the pipe SOURCE.

One step per tool call, in the order the model made them, from the three recordings. The stage that settled each call is read from the recording (hook output, callback log, refusal text); stages before it were passed, stages after it never ran. s1 and s2 use our four tools with a hook that allows the two read-only tools; s3 uses Claude Code's built-in tools with no hook and no callback.

The callback. async def can_use_tool(tool_name, input, context) returns PermissionResultAllow(updated_input=..., updated_permissions=...) or PermissionResultDeny(message=..., interrupt=False); context carries the tool-use id, a suggested rule, the blocked path, a reason and a ready-made prompt sentence (title) for a human approval screen SOURCE. Run s2 asked for a fix and a new regression test in tests/, while our callback made tests/ read-only with the message "tests/ is read-only for this agent. Describe the test you would add in your final reply instead." The model received that sentence as an error tool result, did not try another route, and ended: "I was unable to edit the test file as it's read-only. However, I have successfully fixed the code." Tests passed and the test file was unchanged MEASURED. The callback can also wait as long as you like (for a human on Slack, say); for very long waits the docs suggest a hook that returns defer so the process can exit and the session resume later (user input) DOCS.

Hooks as callbacks. hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[fn])]} registers fn; the SDK gives each function an id (hook_0, hook_1) in the initialize request and the Claude Code process calls it back with hook_callback SOURCE MEASURED. A PreToolUse callback can answer permissionDecision allow, deny, ask or defer, rewrite the input (updatedInput) or add context; PostToolUse can replace the tool's output. Several matchers on one event run concurrently, so do not rely on their order (docstring of hooks, 0.2.163). Python supports 10 events (PreToolUse, PostToolUse, PostToolUseFailure, UserPromptSubmit, Stop, SubagentStart, SubagentStop, PreCompact, Notification, PermissionRequest); TypeScript supports 33, including SessionStart, SessionEnd, PostCompact and PermissionDenied; in Python, SessionStart and SessionEnd exist only as shell hooks in settings files (hooks) DOCS SOURCE. Shell hooks from settings files also run if setting_sources loads them. What each event means, and a hook that blocks, are on Claude Code, taken apart (section Hooks).

Callbacks are policy, not a sandbox

A permission callback sees the tool's arguments, not what a command will do: python3 -c "..." passes any rule written about file paths. Run the agent where it cannot hurt you (the sandbox option for Bash, a container, a VM); the hosting docs compare sandbox-runtime, Docker, gVisor and Firecracker VMs (secure deployment) DOCS. Gate and sandbox design are taught on Agent security and Containers and isolation.

6. Subagents defined in code

A subagent is a second agent loop with its own system prompt, tools, model and context window; the main agent starts one through the Agent tool (the init record still lists it as Task, an alias kept for compatibility) and receives only its final message (subagents) DOCS MEASURED. In the SDK you define them with agents={"test-runner": AgentDefinition(...)}: description (when to use it) and prompt are required; tools, disallowedTools, model, skills, memory, mcpServers, initialPrompt, maxTurns, background, effort and permissionMode are optional (Python keeps the camelCase spelling of the wire format) SOURCE. The docs add: subagents run in the background by default; the only thing the parent passes is the Agent tool's prompt string, not its history; defaults allow 3 levels of nesting and 20 concurrent subagents, with no spend limit unless you set max_budget_usd DOCS.

Run s5 (Sonnet 5.5 as the main agent, told to delegate every test run to a Haiku test-runner with only Bash, maxTurns=4, background=False; permission mode acceptEdits with the single allow rule Bash(python3 tests/test_core.py)) MEASURED:

  • The first delegation went wrong in an instructive way. The subagent ran the allowed command, got the failures, then asked for more detail three times with variants (-v 2>&1, python3 -m pytest ..., a redirect to a file); each was refused because an allow rule matches the command it names, not its relatives. It hit its 4-turn cap with no report, and Claude Code told the main agent: "this agent stopped at its 4-turn limit before finishing ... Send the agent a message (SendMessage)". The main agent tried; SendMessage was "disabled for this session". It then read the files itself with one read-only shell command, made both edits, and delegated again; the second subagent ran one command and reported "0 failed".
  • Cost split by model in model_usage: Haiku $0.0228, Sonnet $0.0625, total $0.0852. The result's usage counted 33,906 input tokens, model_usage 65,602: usage leaves the subagent out, as the docs' table says ("Excluded. Counts only the top-level agent loop").
  • The subagent messages arrive in your stream with parent_tool_use_id set to the Agent call's id, plus task_started, task_progress and task_notification system messages; text and thinking of subagents are forwarded only with forward_subagent_text=True SOURCE.

When several agents help and when they hurt is the subject of Multi-agent patterns; subagents as a context-isolation tool, with a measured window saving, are on Context engineering.

7. Sessions: resume, fork, and putting files back

A session is the saved conversation of one Claude Code process: a JSONL file under ~/.claude/projects/<encoded cwd>/ (or $CLAUDE_CONFIG_DIR/projects/). The SDK reaches it four ways (sessions) DOCS: keep the process open (ClaudeSDKClient); continue_conversation=True (the most recent session in that directory, no id needed); resume="<id>"; or resume plus fork_session=True (a copy under a new id), optionally cut at a message with resume_session_at. Helpers list, read, rename and tag sessions (list_sessions(), get_session_messages()), and a session_store mirrors every transcript line to storage you choose, so a fresh container can resume a session written by another (the "hybrid" hosting pattern, section 10). Run s4 in section 2 showed resume and fork; a long session still compacts as Claude Code does (taught on Context engineering).

File checkpointing is the undo button. With enable_file_checkpointing=True (and extra_args={"replay-user-messages": None} so user messages come back with their ids), Claude Code backs up each file before its built-in Write, Edit or NotebookEdit tools change it, and client.rewind_files(user_message_id) restores the files to that point. Bash changes and subagent edits are not tracked (file checkpointing) DOCS; by the same logic, edits made by your own in-process tools are not either (our reading of the docs, not run).

Run s9 MEASURED: tests before the agent "2 failed"; after the agent (Read, Edit and Bash, acceptEdits, one exact allow rule) "0 failed"; after rewind_files() to the prompt's checkpoint "2 failed" again, with one 457-byte backup written under ~/.claude/file-history/<session id>/. Rewinding restores files, not the conversation: the model still remembers its fix. (The same run shows Haiku making six refused attempts to test in other forms, python instead of python3 and inline scripts, while python3 tests/test_core.py 2>&1 || true was allowed: Claude Code checks each part of a compound command separately, as its refusals say ("contains multiple operations. The following part requires approval"). The run cost $0.0773 against $0.0215 for s1.)

8. Structured output: a schema, enforced by a tool

output_format={"type": "json_schema", "schema": {...}} asks for a final answer that matches a JSON schema; the result message carries it parsed in structured_output. The SDK passes the schema as --json-schema, and Claude Code adds a tool named StructuredOutput whose input is the answer SOURCE MEASURED. The docs: the SDK "validates the output against it, re-prompting on mismatch", gives up with subtype error_max_structured_output_retries, checks schemas as JSON Schema draft-07, and before Claude Code 2.1.205 silently ignored an invalid schema (structured outputs) DOCS.

9. Cost and usage: what the numbers mean


Every result message carries total_cost_usd and, per model, model_usage (input, output, cache read and cache write tokens, and a cost). The docs are blunt: these "are client-side estimates, not authoritative billing data", computed "from a price table bundled at build time"; "Do not bill end users or trigger financial decisions from these fields" (cost tracking) DOCS. On a subscription, as here, nothing is billed per token: the figure is what the same tokens would cost at API list prices.




total_cost_usd of each recorded run (s4: the last reported total, which includes all four phases). Every one reproduces exactly as model_usage tokens x list prices (Haiku 4.5 $1 input, $5 output, $0.10 cache read, $2 per million for 1-hour cache writes; Sonnet 5.5 $2, $10, $0.20, $4), with one twist: in s5 the subagent's cache writes match only at the 5-minute price ($1.25), the main thread's at the 1-hour price, as the Claude Code child also found.

The connector pitfall, counted


With a claude.ai login, an SDK run that leaves strict_mcp_config off can be given the account's connected apps as MCP tools. We measured it with a one-word task ("Reply OK.", Haiku 4.5, tools=[], setting_sources=[], one turn), keeping only counts: no tool or server name was stored anywhere MEASURED.




Input tokens of the single model call (fresh + cache write + cache read). Same machine, same account, 6 October 2026; batch 1 and batch 2 were minutes apart.


Two lessons. The cost: one "OK" cost $0.257 at list prices instead of $0.0008, because 128,296 tokens of tool definitions were written to the 1-hour cache. And the non-determinism: the identical non-strict call loaded nothing in batch 1, 165 tools in batch 2, and 122 tools (with our own server present) a minute later; connectors connect while the session starts, so how many arrive before the first call varies. 10. Deployment, authentication, and the alternatives


Authentication. The SDK reads an API key (ANTHROPIC_API_KEY) or a cloud provider switch: CLAUDE_CODE_USE_BEDROCK=1, CLAUDE_CODE_USE_VERTEX=1, CLAUDE_CODE_USE_FOUNDRY=1, CLAUDE_CODE_USE_ANTHROPIC_AWS=1 (Claude Platform on AWS) (overview) DOCS. Use the API key authentication methods described in the Quickstart instead." (same page) DOCS.

Sizing starts at "1 GiB RAM, 5 GiB disk, and 1 CPU per agent"; a small container costs "roughly $0.05 per hour, while a single long agent session can spend dollars in tokens"; pin a session to one container by hashing its id; the subprocess needs outbound HTTPS to the API and "does not listen on the network". For several customers on one host the docs ask for setting_sources=[], CLAUDE_CODE_DISABLE_AUTO_MEMORY=1, a separate CLAUDE_CONFIG_DIR and working directory per tenant, and per-tenant egress rules; "Do not rely on default query() options for multi-tenant isolation." Known gaps: no top-level session timeout, memory growth in long sessions, no per-subagent deadline DOCS.

11. The old page, claim by claim


The previous version of this page (Notion, last edited 22 Sep 2026) was checked against the docs, the 0.2.163 source and our runs. Every claim, with its fate:









Common mistakes


Trusting subtype: "success"
It means the loop ended normally, not that the task was done. Run s3 succeeded with six refused calls and failing tests. Check permission_denials and run your own verification.


Leaving setting_sources and strict_mcp_config at their defaults in a service
Defaults read every settings file, hook, CLAUDE.md and skill on the machine and, with a claude.ai login, the account's connectors (128,306 tokens in one measured call). Pass setting_sources=[], strict_mcp_config=True and an explicit tool list.


Expecting Claude Code's system prompt
The default system prompt is empty since v0.1.0. Ask for {"type": "preset", "preset": "claude_code"} if you want Claude Code's behaviour, and measure the context it adds (about 6,200 tokens on Haiku in the root's runs: 7,612 against 1,388).


Using can_use_tool as an audit log
Calls allowed by a mode, an allow rule or a hook never reach it. Log in a PreToolUse hook, which runs for every call.


Writing allow rules for the command you expect
Bash(python3 tests/test_core.py) refused python3 tests/test_core.py -v 2>&1 and two other variants in s5, and python tests/test_core.py plus four inline test scripts in s9; each refusal is a wasted model call. Prefer a tool of your own (run_tests) over a shell rule when the action is known.


Summing total_cost_usd over turns or resumed runs
It is already a running total (s4). Take differences, or use usage per turn, deduplicated by message_id; and never bill customers from it.


Treating query() as stateless
Each call writes a session transcript to the home directory. In a container that is lost on restart; on a shared host it is a data-retention question. Use session_store, a per-tenant CLAUDE_CONFIG_DIR, or turn persistence off.


Shipping a product on a subscription login
Not allowed without approval; products use API keys or a cloud provider.







Interview questions


How does the Claude Agent SDK call your Python tool if the agent runs in another process?
The SDK registers an MCP server of type sdk in the Claude Code process's MCP config; when the model calls the tool, Claude Code sends a control_request of subtype mcp_message carrying a JSON-RPC tools/call down stdout; the SDK runs your function and answers with a control_response on stdin. No socket, no extra process.


In what order is a tool call checked, and where does your callback sit?
Hooks, deny rules, ask rules, permission mode, allow rules, then can_use_tool. The callback only sees calls nothing earlier settled; in dontAsk mode it is skipped and the call denied.


An agent built with the SDK reports success but did nothing. What do you check?
permission_denials in the result, the init record's permissionMode and tool list, whether anything answers "ask" (a mode, allow rules or a callback), then the transcript.


How would you compute the cost of one turn of a long session?
Difference of consecutive total_cost_usd values, or price that turn's usage (deduplicated by message id) plus subagents from model_usage differences. Remember it is an estimate.


When would you pick the Agent SDK over LangGraph, and over Managed Agents?
Over LangGraph: when the work needs a computer and Claude Code's loop is good enough, and you do not need your own control flow or provider choice. Over Managed Agents: when the agent must run on your filesystem, network and audit trail, or you need hooks, plan mode and in-process tools.


How do you isolate tenants?
One process and working directory per session, setting_sources=[], strict_mcp_config=True, auto memory off, a per-tenant CLAUDE_CONFIG_DIR, a sandbox or container, egress rules, and credentials injected by a proxy rather than given to the agent.
