The topic in one screen

You have a model API and a job to automate. What do you build it from? The sibling topic, Topic: agentic-harnesses, takes a finished agent apart: the agent loop (call the model, run the tool it asks for, show it the result, repeat until it stops), tools, context, permissions. This topic is about the parts you assemble when you build your own: the libraries that run the loop or a fixed sequence of calls, the gateway in front of the model providers, the tracing that tells you what happened, and the memory that outlives one conversation.

The one idea to keep
A framework is worth its weight only when it gives you something you would otherwise build by hand and get wrong: saved state you can resume, a human pause, typed results, traces. 1. Workflows or agents: who picks the next step?

Anthropic's Building effective agents (Erik Schluntz and Barry Zhang, 19 Dec 2024) SOURCE draws the line every framework sits on. A workflow is a system where model calls and tools are "orchestrated through predefined code paths": your code decides what happens next. An agent is a system where models "dynamically direct their own processes and tool usage": the model decides what happens next, turn after turn, until it stops. The same post names five workflow patterns, which are the shapes most production "agents" really are:

  • Prompt chaining: a fixed sequence of calls, each reading the last one's output, with code checks (gates) in between.
  • Routing: one call classifies the input and sends it to a specialised prompt or model.
  • Parallelisation: independent calls at once, then code merges them (sectioning), or the same call several times and a vote.
  • Orchestrator-workers: a model writes the plan at run time, workers carry out the pieces, a model combines them.
  • Evaluator-optimizer: one call produces, another critiques, repeat until the critic is satisfied or a round limit hits.

When a workflow beats an agent. When the steps are known (triage, extraction, a fixed review), when cost and latency must be bounded, when an auditor will ask why each step ran, and when the model is weak at choosing (a small local model). When an agent earns its cost. When the number and kind of steps depend on what is found along the way: debugging, research, anything open-ended. Anthropic's advice is to find "the simplest solution possible, and only increasing complexity when needed". Most real systems are mixtures: a workflow whose steps are small agents, or an agent that calls a workflow as a tool.

2. The orchestration schools

Orchestration libraries differ less in what they can do (all of them can call tools in a loop) than in what they make you describe: a graph, a cast of roles, a typed function, or nothing at all. Four schools, one honest paragraph each, with what each costs you. Versions are those installed on 5 October 2026 by the Same agent tab MEASURED.

Graph and state machine: LangGraph, LlamaIndex Workflows

LangGraph (1.2.13) models an application as a StateGraph: a typed state object, nodes that are plain functions returning updates to it, and edges (fixed, or functions that route on the state). Its reason to exist is the checkpointer of section 3: state saved after every step, so resume, human interrupts and time travel come with it. LangChain 1.0 and LangGraph 1.0 shipped together on 22 October 2025, and LangChain's create_agent "uses LangGraph under the hood" with "middleware" hooks around each model call (LangChain blog) SOURCE; the older create_react_agent now prints a deprecation warning MEASURED. LlamaIndex Workflows is the event-driven version: "an event-driven, step-based way to control the execution flow" (docs), where steps react to typed events instead of declared edges. Costs you: ceremony (state schema, nodes, edges, compile) for what may be a 15-line loop, a large dependency, and a history of breaking changes before 1.0. Pays when: runs must survive crashes, pause for people, branch and merge. Super-steps, checkpointers, interrupts and the criticisms, each measured: LangChain and LangGraph.

Roles and crews: CrewAI, AutoGen, AG2, Microsoft Agent Framework

CrewAI describes a system as agents with a required role, goal and backstory, tasks assigned to them, and a sequential or hierarchical process; for fixed pipelines it adds event-driven Flows (docs) SOURCE. The prompts are generated from those fields, which makes a system quick to sketch and hard to control precisely. AutoGen made multi-agent work a conversation between agents; its repository now says "AutoGen is now in maintenance mode" and names the Microsoft Agent Framework as its successor, which Microsoft describes as "the next generation of both Semantic Kernel and AutoGen" (AutoGen, Microsoft Learn); its 1.0 releases for Python and .NET were tagged on 2 April 2026 SOURCE. AG2 continues the AutoGen line separately ("AG2 (formerly AutoGen)", repo). Costs you: prompts you did not write and many model calls spent on agents talking to each other. Pays when: the problem really is several roles, and you value speed of sketching over control.

Minimal typed loops: Pydantic AI, OpenAI Agents SDK, smolagents, Google ADK

The same small shape: an Agent object with instructions and tools, and a run function that loops. Pydantic AI (2.54.0) builds tool schemas from function signatures, validates results against an output_type, and sends a ModelRetry message back to the model as a retry prompt (docs). The OpenAI Agents SDK (0.23.1) is "a production-ready upgrade" of the Swarm experiment with agents, tools, handoffs, guardrails and sessions; tracing to OpenAI's dashboard "is enabled by default", and non-OpenAI models run through a LiteLLM adapter (docs). smolagents (1.26.0) changes the action language: its CodeAgent writes Python that is executed, so several tool calls and a loop fit in one step (the CodeAct paper reports "up to 20% higher success rate" than JSON actions, Wang et al., 2024); executing model-written code needs a sandbox, and its executors are local, Docker, E2B, Modal and Blaxel (the WebAssembly executor was removed in 1.26.0, release notes). Google ADK is "available in Python, TypeScript, Go, Java, and Kotlin", speaks A2A (the agent-to-agent protocol, now a Linux Foundation project) and deploys to Google Cloud (adk.dev) SOURCE. Costs you: prompt inflation and an abstraction between you and the request. Same task, same four tools, a local 4B model: the plain loop's first request was 397 tokens, LangGraph 385, the OpenAI Agents SDK 491, Pydantic AI 507 (it adds an output tool), smolagents 2,231 (its own code-action system prompt) MEASURED. Pays when: you would otherwise hand-roll and want typed tools and results for little code. All four read from their source and run, tool schemas and output modes compared: Typed agent libraries.

3. State, durability and humans in the loop

The state of a run is everything needed to carry on: the messages so far, intermediate results, which step comes next. In a plain script it lives in one process's memory. Kill the process (a deploy, an out-of-memory kill, a closed laptop) and the run is gone, including the model calls already paid for. Agents make this the normal case: runs last minutes to hours, and some must wait days for a person to approve something.

The fix is a checkpoint. After every step, write the whole state to a database under a thread id. To recover, load the newest checkpoint of that thread and continue from the next step. Two features fall out of the same mechanism: a human-in-the-loop interrupt (save, exit, and resume later with the person's answer) and time travel (load an older checkpoint, edit it, and run forward on a new branch).

The Orchestration lab did this for real with a LangGraph StateGraph and a SQLite checkpointer MEASURED: the diagnosis call finished ( s, ) and was checkpointed; the process was killed s into the next model call; the restarted process resumed at , not at the start, so the diagnosis was not paid for twice, while the call in flight was lost and made again.

The two details that bite
A node that resumes after an interrupt or a crash runs again from its first line (LangGraph's interrupt() docstring: "The graph resumes from the start of the node, re-executing all logic"), so anything with a side effect before the pause (an email, a payment, a file write) must be safe to repeat or sit in its own node. And nothing restarts a dead process for you: a job queue, a supervisor or a hosted platform has to notice and call resume with the same thread id.

Two families of durability. Checkpointing (LangGraph and most agent libraries) saves a snapshot of state after each step. Durable execution engines such as Temporal save an event history of every completed activity and, after a crash, re-run your workflow code from the top, replaying recorded results instead of calling again; in exchange, the workflow code must be deterministic. If your company already runs Temporal or a job system, putting each model call in an activity gives an agent durability without an agent framework.

Pending writes, and when the checkpoint is written. LangGraph runs a graph in super-steps: every node that is ready runs in parallel, then all their updates are applied together. A node that finishes inside a step has its update saved at once as a pending write, before the step's checkpoint exists, so a finished parallel task survives a crash: killed by SIGKILL in the middle of a parallel step, the graph resumed only the unfinished node and took the finished one's result from its pending write MEASURED (langgraph 1.2.14, SQLite, on the child page). When checkpoints are written is the durability mode: "sync" before the next step starts, "async" in the background while it runs, "exit" only when the run ends, which left nothing to resume after a kill. invoke defaults to "async" (the pregel/main.py docstring), the cheaper mode: 0.288 ms per super-step against 0.423 ms for sync on SQLite, measured on the same page.

Predict: your agent asks a manager to approve a refund, waits two days, and the server was redeployed in between. What must be true for the approval to work?
The state was checkpointed to a durable store (not memory) under a thread id the approval link carries; the resume path reloads it in a new process; and the step before the pause did not already send the refund, because the paused node will run again from its first line.

4. Structured output and typed tools

A model returns text. Code downstream needs fields: a function name, a list of bugs, an amount. Structured output is getting the model's answer as data that matches a schema (a description of the fields and their types, usually JSON Schema), and typed tools are the same idea for tool arguments. There are three ways, from weakest to strongest:

  1. Ask in the prompt and parse. "Reply with JSON only". Works most of the time; fails on fences, preambles, trailing commas, a missing field.
  2. Make the answer a tool call. Offer one tool whose input schema is your result type and require the model to call it. Tool-calling models are trained to emit arguments that fit a schema, and the harness can validate them. Pydantic AI does this (its first request adds a final_result output tool, measured on the Same agent tab), and so does the Claude Code CLI's --json-schema flag, as the run below shows.
  3. Constrain the decoding. The provider only lets the model produce tokens that keep the output valid for the schema (OpenAI's strict mode for function schemas, function calling guide, read 5 Oct 2026 SOURCE). Validity is then guaranteed by construction; whether the content is right is not. It also needs the server to support it: a library's native output mode often sends the schema only in response_format, and mlx_lm.server 0.32.0 reads neither response_format nor tool_choice, so a local model behind it never sees the schema and nothing forces a tool call MEASURED (on Typed agent libraries).

Same input, the first two ways, recorded on 6 October 2026 with Claude Haiku 4.5 and every built-in tool switched off MEASURED: the running example's code and failing test output, and the instruction "do not edit anything: report the bugs" as an object {"bugs": [...]} with function, failing_test, cause and fixed_line.

What it shows. Both answers were correct; only one was data. The prompt-only reply wrapped its JSON in a Markdown fence, so json.loads on the raw text failed at the first character. The usual repair is a parser that strips fences, then a validate-and-retry loop: check the parsed object against the schema and, on failure, send the validation error back to the model and ask again (Pydantic AI raises ModelRetry for this; cap it at two or three tries and count every retry, because a rising retry rate is an early sign that a prompt or model changed). The tool route cost more input tokens (the tool definition and its instructions) and one more turn, and returned a parsed object in result.structured_output.

5. Multi-agent: when it helps and when it hurts

A multi-agent system is several model loops cooperating, each with its own prompt, tools and context window. The patterns are few:

  • Orchestrator-workers (supervisor): a lead agent splits the task, spawns workers with short briefs, and combines their reports. Workers' contexts are isolated: they return a summary, not their transcript. Claude Code's subagents work this way.
  • Handoffs: control passes wholly from one agent to another (triage to billing); one specialist owns the conversation at a time. The OpenAI Agents SDK's native primitive.
  • Parallel fan-out: the parallelisation workflow of section 1; often most of the benefit, with none of the coordination.
  • Debate or a judge panel: several answers, a judge or a vote picks. At equal budget, majority voting over samples of one model explains most of the gain usually credited to debate (Debate or Vote, 24 Aug 2025; earlier Smit et al., Nov 2023) SOURCE. Measured on 30 nine-person knights-and-knaves puzzles with Claude Haiku 4.5, tools off, the same puzzles for every method: one sample solved 21, a vote of 5 samples 27, three samples plus a judge 29, debate (3 agents, 2 rounds) 29 MEASURED (Debate lab on Multi-agent patterns).
  • Shared state (blackboard): agents coordinate through a common store (files, a database, a graph of results) instead of messages. Anthropic's Fermat's Last Theorem formalisation had Claude agents work over a shared directed acyclic graph of theorem statements and reached a complete machine-checked proof in 11 days on about six billion output tokens (Anthropic, 4 Sep 2026) SOURCE; the Agora paper keeps the shared record in Git so every result can be checked out and rerun.

The two published positions, both June 2025. Anthropic's multi-agent research system (13 Jun): a lead with parallel subagents "outperformed single-agent Claude Opus 4 by 90.2%" on its internal research eval, agents use about 4 times the tokens of chat and multi-agent systems about 15 times, and token usage alone explained 80% of the variance on BrowseComp; it also says "most coding tasks involve fewer truly parallelizable tasks than research". Cognition's Don't Build Multi-Agents (Walden Yan, 12 Jun): "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results" SOURCE. They are not contradictory: parallel reading (search, research, review) splits well; parallel writing of one artifact does not, because each writer makes decisions the others cannot see (Philipp Schmid's read and write framing, 20 Jun 2025).

6. Gateways

Once more than one team or one provider is involved, every agent needs the same plumbing around each model call: credentials, a request format per provider, retries when a provider returns 429 (rate limited) or 5xx (server error), a fallback model when one is down, a timeout, a spend limit, and a log line. A gateway (an LLM proxy) does all of it in one place: your code calls one OpenAI-shaped endpoint, and model choice, keys and spend become configuration instead of code.

  • LiteLLM (self-hosted): one endpoint over "100+ LLM providers", virtual keys with budgets and rate limits per key, user and team, a router with retries, fallbacks and cooldowns, and logging callbacks to tracing tools such as Langfuse; MIT licence outside its enterprise/ folder (repo, reliability docs, read 6 Oct 2026) SOURCE. The old page notes Khalid runs it at work.
  • OpenRouter (managed): one key and one bill over "400+ AI models", passing through provider prices "without any markup" and charging 5.5% (minimum $0.80) on card credit purchases (FAQ). It announced on 19 Aug 2026 that it is "joining forces with Stripe", subject to closing conditions; no price was disclosed (announcement) SOURCE. The two compose: LiteLLM can use OpenRouter as one more upstream.
  • A learned orchestrator behind a gateway's interface. Sakana's Fugu is a "multi-agent system delivered as a single OpenAI-compatible API": you send a request to what looks like one model, and a trained orchestrator routes it across other models (Sakana; Fugu Max and Fugu Ultra v2 announced 11 Sep 2026) SOURCE. Same interface as LiteLLM and OpenRouter, opposite premise: it takes the orchestration from you.
A fallback you never evaluated is a silent quality cliff
The same prompt behaves differently on another provider's model. When the gateway falls back during an outage, the agent keeps answering, worse, and nothing errors. Run your evals against every model in the fallback chain, and tag each trace with the model that actually answered.

7. Observability and evals

You cannot debug an agent from log lines: you need to see which call saw what. Every tool converges on one data model. A trace is one run; it holds a tree of spans (timed units of work: a model call, a tool call, a subagent), each with attributes such as the model, token counts and cost. OpenTelemetry's GenAI semantic conventions standardise the names, for example gen_ai.operation.name (invoke_agent, chat, execute_tool), gen_ai.request.model, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens; they are still marked "Development" and now live in their own repository (semantic-conventions-genai, read 6 Oct 2026) SOURCE.

8. Memory

The context window is working memory: it empties when the session ends. Long-term memory is a store outside the window that the agent writes to and reads from, so that next week's session knows what this week's learned. The harness's own memory files (CLAUDE.md, AGENTS.md) and compaction are the sibling root's subject; the libraries here are separate stores you plug in. They differ in what they keep. Illustrative example on the running example: in March the user says "run the tests with pytest"; in October, "pytest is gone, use python3 tests/test_core.py" (the lab's multi-agent run did try pytest first).

The open-source library since v2.0.0 (16 April 2026) is "single-pass, ADD-only": a changed fact is stored beside the old one and retrieval has to sort them out.

Common mistakes

Adopting a framework before naming the capability it buys
Write down which of checkpointing, interrupts, typed outputs or tracing you need. If none, a loop and a gateway are the simpler system (section 10).
Building an agent where a workflow would do
Known steps, bounded cost and auditability favour a workflow; the lab's two-call chain matched the free agent's hidden-check score (section 1).
Parsing JSON out of free text
The recorded reply was correct and still failed json.loads because of a Markdown fence. Use a tool call or constrained decoding, then validate and retry with the error (section 4).
A side effect before an interrupt
The resumed node runs again from its first line. Make it idempotent or move it after the approval (section 3).
Splitting a write task across agents
Parallel writers make decisions the others cannot see; on the running example the split cost several times more for the same result (section 5).

Interview questions

Answer aloud first, then open.

Workflow or agent: define both and say when you pick each.
A workflow runs model calls along code paths you wrote; an agent lets the model choose each next step until it stops. Pick a workflow when steps are known and cost, latency and audit matter; an agent when the steps depend on what is found.
What does LangGraph give you that a while loop does not?
State saved after every step under a thread id: resume after a crash, human interrupts of any length, replay or fork from an old step, plus merge rules for parallel branches. Nothing else that a loop cannot do.
How do you get reliable structured output from a model?
Offer the schema as a tool or use constrained decoding, validate the result against the schema in code, and on failure send the validation error back for a bounded number of retries, counting them as a metric.
Your agent must wait two days for a manager's approval. Design it.
Checkpoint state to a durable store under a thread id; the approval request carries the id; exit; on approval, a worker reloads and resumes. Side effects after the approval only, or idempotent. A supervisor or queue restarts failed resumes.
When does multi-agent help?
Breadth-first reading that exceeds one context (research, search, review) with independent subtasks and a value that justifies several times the tokens. Not for one artifact many agents would write.
What does a gateway do and what can go wrong with fallbacks?
One endpoint, keys, budgets, rate limits, retries, fallbacks, logging. A fallback model that was never evaluated degrades quality silently; eval every model in the chain and tag traces with the model that answered.
What is in a trace of an agent run?
A root span for the run, child spans per model call (model, tokens, cost) and per tool call (name, arguments, result, error), nested subagent subtrees, all with timings, ideally with OpenTelemetry GenAI attribute names.
Fact memory or temporal graph?
Facts (Mem0 style) are compact and simple; a temporal graph (Zep style) keeps when each fact was true, so it can answer "what was true in March" and supersede instead of overwrite. Paging (Letta) lets the agent manage its own context.
Build, adopt a framework, or buy a hosted runtime?
Build when the loop is your product or must run in an unusual place; adopt a framework for durability or typing you would get wrong; buy when you do not want to operate sandboxes and sessions and accept the vendor's control flow, models and trace export.

1. Plain loop


Did for you
Nothing: you wrote the schema, the loop, the stop rule and the error handling. The openai client retries connection errors, 429 and 5xx responses twice by default (DEFAULT_MAX_RETRIES = 2 in openai 3.24.0's _constants.py).


Hid
Nothing. The request is exactly the dictionary you built.


Approval

    result = "denied by the user"   # the model sees the refusal
The pause blocks the process: fine for a CLI, not for a web service, where you must save messages and resume later yourself.


Retry
API: OpenAI(max_retries=5). Model mistakes: already there, the except turns a bad call into an observation.


2. LangGraph


Did for you
Tool schemas from signatures and docstrings; ToolNode runs every tool call and appends the results; the checkpointer saves the whole state after every step under a thread_id, so a run can be paused, inspected, resumed or replayed (persistence docs).


Hid
Little in the request (385 tokens, slightly fewer than ours: it omits empty required lists). The cost is concepts: state reducers, conditional edges, recursion_limit counting graph steps rather than model calls (15 model turns needed a limit of 31). create_react_agent, the one-line version, warns in 1.2.13 that it is deprecated in favour of LangChain's create_agent.


Approval

          interrupt_before=["tools"])
# run stops before tools; a human looks, then:
app.invoke(None, config)          # resume
or call interrupt(...) inside a node and resume with Command(resume=...) (interrupts docs). Works across processes because the state lives in the checkpointer.


Retry
g.add_node("agent", agent, retry_policy=RetryPolicy()): defaults 3 attempts, 0.5 s then doubling (langgraph/types.py). Tool argument errors go back to the model as a message by default; other tool exceptions are raised.


3. Pydantic AI


Did for you
Typed tools, a validated typed result (FixReport), usage limits, and ModelRetry: raise it in a tool and the message goes back to the model with "Fix the errors and try again." appended (tools docs).


Hid
The typed result is implemented as an extra tool, final_result, plus tool_choice: "required": the model may never answer in plain text (output docs). Tools get strict: true and additionalProperties: false. A model that ends with a sentence instead of calling final_result gets a validation error back, and after one retry (the default) the run raises UnexpectedModelBehavior. That is what happened here, and the server explains why: mlx_lm.server 0.32.0 ignores tool_choice, so "required" never reached the model and nothing forced the call (read from its source and measured on Typed agent libraries).

agent.run_sync(message_history=r.all_messages(),

(deferred tools docs)

Model mistakes: ModelRetry, and retries= on the agent or tool (default 1). API failures: configure the HTTP client of the provider.

Hid

5. smolagents (CodeAgent)


Did for you
The model writes Python instead of JSON tool calls, so one step can call several tools, loop and compute (the CodeAct idea, Wang et al. 2024). Python errors come back as the next observation.


Hid
The largest prompt by far: a long system prompt with worked examples of the Thought, code, Observation format and the tools rendered as Python signatures (2,231 tokens on the first call, no tools field at all), plus stop sequences. Interview questions


What does an agent framework actually give you over a while loop?
Schema generation from types, state persistence and resumption, retries, typed outputs, approval and interrupt primitives, tracing, multi-agent handoffs. The loop itself is the smallest part.


How would you add human approval to a tool call in a web service?
The run must stop, persist its state and resume later in another request: LangGraph's checkpointer with interrupt, Pydantic AI's deferred tool requests, the Agents SDK's RunState with approve/reject. A blocking input() works only in a CLI.


What is prompt inflation and how do you measure it?
Tokens a framework adds to every request (system prompt, examples, schema decorations, extra tools). Measure by capturing the first request with a proxy or the provider's usage field and comparing it with a hand-written request for the same tools.


Code actions versus JSON tool calls: trade-offs?
Code lets one step loop, compose and compute, and models write code well; it needs a sandbox, a longer prompt and a model that keeps the format, and tool return types matter. JSON calls are simpler, safer and supported natively by providers.


Your agent passes with framework A and fails with framework B on the same model. What do you check?
Diff the requests (prompt, tool schemas, tool_choice, max_tokens, stop sequences), then the error paths (how tool errors and format errors return to the model), then limits (turn counting).     Durable execution: kill it, resume it, rewind it
    

    The problem. A workflow lives in the memory of one process. If that process dies halfway (a deploy, an out-of-memory kill, a laptop lid), a plain script has lost everything: the model calls already paid for, the decisions already made. It starts again from zero and pays again. Long agent runs, and runs that wait hours for a human, make this the normal case rather than the rare one.
    

    The idea. After every step, write the whole state of the run to a database. Each saved snapshot is a checkpoint; all the checkpoints of one run share a thread id. To recover, load the newest checkpoint of that thread and carry on from the step after it. The same mechanism gives two more features for free: pausing for a human (save, exit, and resume days later with the human's answer) and time travel (load an older checkpoint, optionally edit it, and run forward again on a new branch).
    

    The recording. The prompt-chaining workflow above, rebuilt as a LangGraph StateGraph with five nodes and a SQLite checkpointer (langgraph , langgraph-checkpoint-sqlite ), run with durability="sync". A driver script started it, waited until the fix step's model call was in flight, and sent SIGKILL to the whole process group. Then it ran four more separate processes: resume, approve, rewind, approve. Every process is a fresh Python interpreter: the only thing that survives between them is the SQLite file.

      Three details that bite in production
      

        

      • When the checkpoint is written. LangGraph has three durability modes (from the pinned source, langgraph/types.py): "sync", "changes are persisted synchronously before the next step starts"; "async" (the default), "persisted asynchronously while the next step executes"; "exit", "persisted only when the graph exits". Under "exit" the kill above would have lost the diagnosis too. "async" is faster but a crash in the wrong millisecond can lose the last step.
        • 

      • A resumed node runs again from its first line. The interrupt() docstring says it plainly: "The graph resumes from the start of the node, re-executing all logic." The event log shows human_review starting twice. Anything with a side effect (sending an email, charging a card, writing a file) that sits before an interrupt, or inside a node that can crash, must be safe to run twice (idempotent) or must move into its own node. The same holds for the killed model call: it was paid for and its answer was lost, so the resumed process called the model again.
        • 

      • Nothing restarts the process for you. The checkpointer makes resuming possible; something else has to notice the crash and call invoke again with the same thread id (here, the driver script; in production a job queue, a supervisor, or a hosted platform).

        Interview questions
        

        What is the difference between a workflow and an agent?
        Who picks the next step. In a workflow your code fixes the sequence and the model fills in steps; in an agent the model chooses the next action each turn until it decides to stop. Workflows are cheaper to reason about, test and bound; agents handle problems whose steps cannot be listed in advance.
        

        Name the five workflow patterns and one use for each.
        Chaining (draft, then check, then polish), routing (send billing questions and technical questions to different prompts or models), parallelisation (sections at once, or several votes on one answer), orchestrator-workers (a planner that decides which files to change, workers per file), evaluator-optimizer (writer plus critic with clear criteria, such as tests or a rubric).
        

        Your 20-step workflow crashes at step 17. What do you need so it resumes at 17?
        State saved after every step to durable storage, keyed by a run id (a checkpointer and a thread id in LangGraph, an event history in Temporal); synchronous persistence or an accepted loss window; steps that are safe to run twice, because the crashed step will run again; and something that detects the crash and restarts the run.
        

        How do you add a human approval step to an agent?
        Pause before the risky action, persist the state, show the human the proposed action (here, a diff), and resume with their answer. In LangGraph: interrupt() inside a node with a checkpointer, then invoke(Command(resume=...)) on the same thread. Remember that the node re-runs from its start on resume.
        

        When would you use several agents rather than one?
        When the work splits into independent, mostly read-only pieces, or exceeds one context window, and the gain is worth several times the tokens (Anthropic reports about 15 times a chat). Not when the pieces must make consistent decisions about one shared artefact, where a single agent with good context management is usually better (Cognition). Measure both on your task.
        

        An evaluator-optimizer loop never converges. What do you check?
        Whether the evaluator's criteria are concrete and checkable (tests beat opinions), whether feedback actually reaches the generator, a maximum number of rounds, and cost per round: in this lab each review by a strict reviewer cost more than the generation it reviewed.

        Everything around the loop, once it runs
        

        The agent loop on your laptop calls one model with one key and prints what happened. A loop that serves real users needs four more things, and each one exists because something specific goes wrong without it: providers fail, so a gateway retries and falls back; nobody can see inside a run, so you record a trace; a prompt change quietly breaks things, so an eval gate checks every change; each conversation starts from nothing, so a memory layer carries facts forward. The last question is whether to run the loop at all, or rent one (a hosted runtime).
        

        

        

        Gateway
        A proxy between your code and the model providers. Your code speaks one API to it (usually OpenAI's chat format); it forwards each call to a provider and adds retries, fallbacks, timeouts, keys, budgets and a log of every call.
        

        Trace and span
        A span is one timed operation with a name and attributes (a model call, a tool call). A trace is the tree of spans for one request. OpenTelemetry (OTel) is the vendor-neutral standard for producing and shipping them.
        

        Eval in the loop
        A fixed set of tasks with automatic checks, run on every change to the agent (prompt, model, tools, harness version), with a gate that blocks the change if the checks get worse.
        

        Memory layer
        A store outside the context window plus two policies: what to write after a conversation and what to read back into the next one. Mem0, Zep and Letta are three different answers.

        Gateways: one front door for every provider
        

        The problem. A model provider is a remote service, and remote services fail in three ordinary ways: they refuse you because you sent too much (HTTP 429 Too Many Requests, often with a Retry-After header saying how many seconds to wait), they break (500, 503), or they stop answering (a hang, which only a timeout ends). An agent makes ten or fifty calls per task, so a 1% failure rate per call becomes a failed task surprisingly often. Every provider also has its own SDK, keys, prices and limits.
        

        How a gateway works. Your code sends every call to the gateway with a model name you chose (here primary). The gateway maps that name to one or more real deployments, sends the call, and when it fails decides what to do: wait and retry the same deployment, fall back to another model group, or give up. It also checks the caller's virtual key (a key the gateway issued, so the real provider keys never leave it), its budget and its rate limit, and logs the cost of every call. LiteLLM's proxy, OpenRouter and the cloud vendors' AI gateways all do some version of this.

        Tracing: seeing inside a run
        

        The problem. An agent run is dozens of model calls and tool calls deciding each other. When it fails, costs too much or takes too long, the final answer does not tell you which step did it. Logging every call to a file helps until two runs interleave or a call is retried inside a gateway.
        

        How tracing works. Each operation opens a span when it starts and closes it when it ends; a span records its name, start and end times, a parent span and attributes (key-value pairs such as the model name and token counts). The spans of one task share a trace id and form a tree. An exporter in your process ships finished spans, usually over OTLP (the OpenTelemetry protocol), to a collector or straight to a backend that stores and draws them. The OpenTelemetry GenAI semantic conventions agree on names: a model call is a span named chat {model} with gen_ai.operation.name = "chat", gen_ai.usage.input_tokens, gen_ai.usage.output_tokens; a tool call is execute_tool {tool}; one agent run is invoke_agent {agent}. Message content is opt-in (gen_ai.input.messages, gen_ai.output.messages), because prompts carry private data. Every one of these is still marked "Development" (not stable), and in 2026 the conventions moved out of the main OpenTelemetry repository into their own (semantic-conventions-genai, commit cb10b70 of 5 Oct 2026; agent spans).

        Evals in the loop: a gate on every change
        

        The problem. You change the system prompt, swap the model, add a tool or upgrade the harness. The demo still works. Did anything get worse? One run cannot tell you, because the same agent on the same task varies run to run in turns, cost and even in what it fixes.

        Memory layers: what to carry from one conversation to the next
        

        The problem. A model remembers nothing between calls; within a session the harness resends the history (see the sibling root's context management), but the next session starts empty. Pasting every past conversation back in works until it does not fit, costs input tokens on every call, and buries the one fact that matters. A memory layer is a store outside the context window with a write policy (what to keep after a conversation) and a read policy (what to put back in before the next answer).
        

        

        Facts (Mem0)
        After each exchange a model extracts short facts, then decides for each one against similar stored facts: ADD, UPDATE, DELETE or NOOP. Reads retrieve the most similar facts. The store holds the current text of each fact. (Chhikara et al., arXiv 2504.19413, 28 Apr 2025) That is the 2025 paper and Mem0 1.x, and what this tab implements; the open-source library since v2.0.0 (16 April 2026) only adds ("single-pass, ADD-only"), so a changed fact sits beside the old one. Mem0 scopes memories by user, agent and run ids; it has no layers with promotion between them.
        

        Temporal graph (Zep, Graphiti)
        Facts become edges between entities, each with the time it became true (t_valid) and, when a newer fact contradicts it, the time it stopped (t_invalid); nothing is deleted, and raw episodes are kept. (Rasmussen et al., arXiv 2501.13956, 20 Jan 2025)
        

        Paging (Letta, MemGPT)
        The model manages its own memory with tool calls, like an operating system paging between RAM and disk: a small always-visible core block it edits, plus archival and recall stores it searches when needed. The Letta server was archived on 16 August 2026; the PyPI name letta now installs Letta Code. (Packer et al., arXiv 2310.08560, 12 Oct 2023; the analogy is with virtual memory)

        Interview questions
        

        Your agent calls a provider that returns 429 with Retry-After: 2. What should the client do?
        Wait at least 2 seconds (plus a little random jitter so many clients do not retry together), then retry; give up or fall back after a few attempts. LiteLLM does exactly this when the header is between 0 and 60 seconds, and otherwise uses exponential backoff, 0.5 · 2k seconds capped at 8, plus up to 0.75 s of jitter.
        

        Why can retries make an outage worse?
        Each retry is another request against the same rate limit and the same struggling service, so a 2-retry policy can triple the load exactly when capacity is lowest (a retry storm). Backoff with jitter, a cap on retries, cooldowns that take a failing deployment out of rotation, and a fallback to a different provider all limit it. The simulator above shows the 429 count growing with retries during an outage.
        

        The gateway has an 8 s timeout, 2 retries and a fallback; the provider hangs for 20 s. How long does the user wait?
        Three timeouts (24 s) plus the backoff waits plus the fallback's own latency:  in the recording, against  with no gateway at all. Per-attempt timeouts must come from measured latency, and the whole call needs one deadline.
        

        What is a virtual key, and why can a budget be exceeded?
        A key issued by the gateway, mapped to the real provider keys it never reveals, with its own allowed models, spend cap and rate limits. The budget check runs before each call against spend recorded so far, so the call that crosses the cap still runs: in the recording a $0.0008 cap ended at three calls costing $0.00099. Parallel calls do not widen this by default on LiteLLM 1.104.0, because each call reserves its worst-case cost before it starts; with disable_budget_reservation 20 simultaneous calls all got through at 4 times the budget (Gateways and routing).
        

        Name the spans you would emit for one agent run, following the OpenTelemetry GenAI conventions.
        One invoke_agent {agent name} span as the parent; a chat {model} span (kind CLIENT) per model call with gen_ai.operation.name, gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens and output_tokens, finish reasons; an execute_tool {tool name} span (kind INTERNAL) per tool call with gen_ai.tool.name and gen_ai.tool.call.id. Message content only as opt-in attributes. Auto-instrumentation of the model client gives you the chat spans only.
        

        How do you attribute an agent run's cost to its steps?
        Put token counts on every model-call span, split by type (fresh input, cache write, cache read, output), multiply by the model's prices, and sum up the tree. On the recorded Claude Code run the span-level sum equals the run's reported total exactly; output and cache writes, not the reread history, were most of the cost.
        

        What belongs in an eval gate for a coding agent?
        Final-state checks (visible tests pass, hidden tests pass, tests not edited), trajectory checks (did it verify after its last edit, any permission denials, any dangerous commands), and budgets (cost, turns, time), each run several times per configuration and compared with a baseline distribution. Final-state checks alone pass an agent that got lucky without verifying.
        

        Fact memory, a temporal graph, or a self-editing core block: when would you pick each?
        Facts when you need cheap recall of current preferences and can tolerate losing history; a temporal graph when questions ask what changed and when, or facts expire (people leave, prices change); a self-edited core block when a few always-relevant facts should be in every prompt and the model can be trusted with tools. And none at all while the full history still fits in the context window.
