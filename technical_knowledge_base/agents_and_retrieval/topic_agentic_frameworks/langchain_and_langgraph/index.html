The idea in one picture

LangGraph runs your program as rounds of parallel steps over one shared state and saves a checkpoint of that state at the barrier after every round; surviving a crash, waiting days for a person and rewinding are all that checkpoint. LangChain 1.x is the thin layer above: one interface for models, tools and retrievers, and a ready agent loop that compiles to a LangGraph graph.

LangChain's create_agent builds a StateGraph; compile() turns any graph into a Pregel runtime that loops plan (which nodes are triggered), execute (all of them in parallel, each against the state as of the step start) and update (merge their writes through the reducers). Each finished task's output is saved as a pending write, and each update saves a checkpoint under the run's thread_id. Resume, whether after a SIGKILL or after a person answers an interrupt(), is just loading the last checkpoint and planning again. Fig. 1 is the page's running example, run for real with Claude Haiku 4.5 and killed halfway (section 5 has the timings and the run without checkpoints):

  1. One graph, one state, one checkpointer. The graph of section 2 compiled with a SqliteSaver: the nodes on the floor, the shared state behind them, the database on the right. Process 1 calls invoke({}) on a fresh thread; the input is saved as the first checkpoints.
  2. Super-step 1: read_and_test. One node runs and returns core and test_output; at the barrier the update is applied to the state and a checkpoint is written.
  3. Super-step 2: both diagnoses at once. The two nodes run in parallel, each a model call. diagnose_top_words returns after 6.6 s and its output is saved at once as a pending write, before the step ends.
  4. SIGKILL at 6.6 s. The driver kills the process while diagnose_word_count's call is in flight. Memory is gone and that call returns nothing; the database still holds the checkpoints and the pending write.
  5. Process 2: invoke(None) on the same thread. A fresh process loads the last checkpoint and its pending write and plans again: only diagnose_word_count runs (6.3 s). At the barrier the operator.add reducer joins both diagnoses into one list; a checkpoint is written.
  6. propose_fix, then interrupt(). propose_fix makes the third returned call (7.8 s); human_review calls interrupt(): the pause is saved, invoke returns the diff at 21.0 s and process 2 exits. Nothing runs while the person decides, for seconds or for days.
  7. Process 3: Command(resume="approve"). Another process loads the thread; human_review runs again from its first line, interrupt() now returns "approve", apply_and_test applies the patch and the tests pass. SQLite holds 7 checkpoints and 19 writes; 4 model calls started for 3 that returned ($0.0132 at list prices).

You need the agent loop itself, written by hand in Building a harness, and the root's workflows against agents (Topic: agentic-frameworks, Reading). Nothing else.

    1. LangChain 1.x: one interface for every building block

    Since 1.0 (October 2025) the langchain package is an agent library, create_agent plus middleware (section 9), built on the interfaces in langchain-core. The pre-1.0 chains, retrievers and indexes moved to langchain-classic; on 1.4.3, import langchain.chains raises ModuleNotFoundError and from langchain_classic.chains import RetrievalQA works MEASURED. LangGraph does not need LangChain at all: its README says it "can be used without LangChain", and every graph in sections 2 to 8 imports only langgraph.

    Everything is a Runnable. A prompt template, a chat model, an output parser, a retriever, a tool, and any chain built from them implement one interface, Runnable: invoke (one input), batch (a list, run concurrently), stream, the async ainvoke, and wrappers such as with_retry and with_fallbacks. LCEL, the LangChain Expression Language (August 2023, "a declarative way to truly compose chains", LangChain), is the | operator over Runnables: prompt | model | parser builds a RunnableSequence whose invoke feeds each step's output to the next.     2. A graph from zero
    

    The running example's tests fail because of two bugs. A sensible workflow: run the tests, diagnose each failure (independent, so in parallel), propose one fix from both diagnoses, show it to a person, apply it only if they approve. LangGraph asks for it as three kinds of object:
    

      

    • State: a typed dictionary (a TypedDict, Pydantic model or dataclass) that every step reads and updates: here the code, the test output, the diagnoses, the patch, the decision.
      • 

    • Nodes: plain functions that take the state and return a partial update, a dictionary with only the keys they change. A node never mutates the state it was given.
      • 

    • Edges: which node runs after which. A normal edge always fires; a conditional edge calls a function on the state and returns the next node's name (or several, or END).
      • 

    

    This is the graph that section 5 runs with real Claude Haiku 4.5 calls, trimmed to its shape (full script: src/code/e6_real.py):
    

    class S(TypedDict, total=False):
    core: str
    test_output: str
    diagnoses: Annotated[list, operator.add]   # a reducer: parallel writes are concatenated
    patch: str
    decision: str
    passed: bool

b = StateGraph(S)
b.add_node("read_and_test", read_and_test)            # returns {"core": ..., "test_output": ...}
b.add_node("diagnose_word_count", diag("test_word_count"))
b.add_node("diagnose_top_words", diag("test_top_words"))
b.add_node("propose_fix", propose_fix)                # one model call, returns {"patch": ...}
b.add_node("human_review", human_review)              # calls interrupt(), returns {"decision": ...}
b.add_node("apply_and_test", apply_and_test)
b.add_edge(START, "read_and_test")
b.add_edge("read_and_test", "diagnose_word_count")    # two edges out of one node:
b.add_edge("read_and_test", "diagnose_top_words")     # both run, in parallel
b.add_edge(["diagnose_word_count", "diagnose_top_words"], "propose_fix")   # wait for both
b.add_edge("propose_fix", "human_review")
b.add_edge("human_review", "apply_and_test")
b.add_edge("apply_and_test", END)
app = b.compile(checkpointer=SqliteSaver(conn))       # the checkpointer is what makes it durable
app.invoke({}, {"configurable": {"thread_id": "fix-1"}})
    

    compile() checks the wiring (an edge to an unknown node raises ValueError: Found edge ending at unknown node; a node that no edge reaches compiles without complaint MEASURED) and returns a Pregel object, the runtime of section 3, with invoke (run to the end or the next interrupt), stream, get_state and get_state_history (read checkpoints) and update_state (write one: edit or rewind). Every call carries a config whose thread_id names the run; with a checkpointer it is required ("you must specify a thread_id", docs).
    

    The functional API writes the same thing as ordinary Python: a function marked @entrypoint calls functions marked @task whose results are saved (section 9 measures one). "Compiling a StateGraph or creating an @entrypoint produces a Pregel instance" (docs): one runtime under both.
    

    

    The code on the left as LangGraph draws it: two edges out of read_and_test run both diagnoses in one super-step
    

    START is where the input enters; reaching END with nothing else scheduled ends the run. Dashed arrows (in later figures) are conditional edges.
    


    

    

    3. How a graph runs: super-steps
    

    LangGraph's README says it "is inspired by Pregel and Apache Beam". Pregel is Google's system for computing over huge graphs (Malewicz et al., SIGMOD 2010), in the bulk synchronous parallel style of Valiant (CACM 33(8), 1990): work proceeds in rounds, everything in a round runs in parallel, and results are exchanged only at the barrier. LangGraph's round is the super-step, "a single tick of the graph where all nodes scheduled for that step execute (potentially in parallel)" (docs). Its three phases, as pregel/_algo.py implements them:
    

      

    1. Plan. Every state key is a channel with a version number that rises on each write. Edges are channels too, with names you never typed: branch:to:propose_fix, or join:diagnose_word_count+diagnose_top_words:propose_fix for a wait-for-both edge. Each node records the version of each trigger channel it last saw (versions_seen) and runs in this step if one has a newer version.
      2. 

    2. Execute. All triggered nodes run in parallel, each reading the state as of the start of the step, so none sees another's output from the same step. What a node returns is not applied yet: it is held, and saved, as a pending write.
      3. 

    3. Update. At the barrier all pending writes are applied together, sorted by task path rather than finishing time, each through its channel's reducer; written channels get the next version; a checkpoint is saved. When no node is triggered, the run ends.
      4. 

    

    A key with no reducer is a LastValue channel: exactly one write per step. A key annotated with a reducer (Annotated[list, operator.add], or add_messages for chat messages) is a BinaryOperatorAggregate channel that folds in any number. Predict before you watch: on "Fan-out, reducer", check_top_words finishes before check_tokenize; which finding comes first in the merged list?

    The answer. With the reducer the findings are concatenated in task-path order: check_top_words finished first, yet its finding comes second. Without it the step fails with InvalidUpdateError: At key 'findings': Can receive only one value per step. Use an Annotated key to handle multiple values. And something the message does not say MEASURED: both writes were already saved as pending writes, so every later get_state() on that thread raised the same error. The thread stays stuck until you write past it: update_state(config, {"findings": [...]}, as_node="check_tokenize") saved a new checkpoint, after which invoke(None, config) finished. To bypass a reducer on purpose for one write (reset a list), return Overwrite(value) (langgraph 1.0.2 and later).
    

    Predict: branch A is two nodes long (search, then read the hits), branch B one (lint). Both have a plain edge into join. How many times does join run? (Then pick "Uneven, plain edges" for Fig. 2.)
    Twice MEASURED. In super-step 3, B's edge has fired while A is on its second node, so join runs alongside a_read_hits; in super-step 4 A's edge fires and join runs again. The recorded log is read, a_search, b_lint, a_read_hits, join, join. Written as add_edge(["a_read_hits", "b_lint"], "join") the edge becomes one join: channel that fires only when both have written ("Uneven, join"): plain edges mean "run when any arrives", the list form "wait for all".
    

    Loops and the recursion limit. A conditional edge may point backwards (fix, test, fix again: the "Loop" graph). Each pass is a super-step, and the run stops with GraphRecursionError past recursion_limit super-steps. The default was 25 up to langgraph 1.0.x, then 10,000 in 1.1.0 and 10,007 in 1.2.0 SOURCE (DEFAULT_RECURSION_LIMIT in _internal/_config.py of each wheel; override with LANGGRAPH_DEFAULT_RECURSION_LIMIT or per call). Tutorials that warn about hitting 25 describe the old default: a runaway loop now runs for a very long time unless you set a limit, or a model-call limit (section 9).
    

    Map-reduce with Send. When the number of parallel tasks is known only at run time (one review per file), a conditional edge returns a list of Send("review", {"file": f}); each becomes one task in the next super-step with its own input instead of the shared state. The "Send" graph: three files, three review tasks in one step, gathered by a reducer, then summarise.
    

    

    

    

    

    4. Checkpointers: what is saved, where, and how big it gets
    

    A checkpointer is what you pass to compile(checkpointer=...): it saves a checkpoint at every super-step boundary and the pending writes of every task in between. Without one the state lives only in the running process and interrupts cannot be resumed (section 6); with one, a thread's whole history is in a database, keyed by thread_id.
    

    What one checkpoint holds (the Checkpoint type, langgraph-checkpoint 4.2.0): id (unique and increasing, so it sorts by time), ts, channel_values (the state plus trigger channels), channel_versions, versions_seen per node and updated_channels; beside it, metadata: source (input, loop, update or fork), step (-1 for the input checkpoint, then 0, 1, 2 ...), the parent checkpoint and the run id. Pick a checkpoint of the recorded linear run:
    

    Where it goes (docs): InMemorySaver (core package, "for experimentation"), SqliteSaver (langgraph-checkpoint-sqlite, "ideal for experimentation and local workflows"), PostgresSaver (langgraph-checkpoint-postgres, "used in LangSmith. Ideal for using in production"), plus separately packaged MongoDB and Azure Cosmos DB savers. Redis appears in the docs only as a store (section 10), not a checkpointer; the old version of this page listed it as a checkpointer backend. SQLite keeps the whole serialized state in each checkpoint row; Postgres keeps one row per channel per version, so an unchanged channel is not stored again MEASURED. Checkpoints hold every prompt, tool result and secret your agent saw: encrypt them (EncryptedSerializer, AES key from LANGGRAPH_AES_KEY).
    

    The table schemas and the serializer, read from the databases after the runs
    

    SQLite (3.1.1): two tables. checkpoints (thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint BLOB, metadata BLOB) and writes (thread_id, checkpoint_ns, checkpoint_id, task_id, idx, channel, type, value BLOB).
    

    Postgres (3.1.2, Postgres 16 in Docker): four tables, created by setup() through 10 migrations. checkpoints (small JSONB rows), checkpoint_blobs (one row per channel per version), checkpoint_writes and checkpoint_migrations.
    

    Values are serialized with JsonPlusSerializer (msgpack; pickle fallback off by default; LANGGRAPH_STRICT_MSGPACK=true restricts which classes may be rebuilt); EncryptedSerializer wraps it (docs).
    

    

    A real checkpoint, as the saver stores it
    

    MEASURED straight from InMemorySaver.list() after the run (ids shortened to their last 8 characters, versions to their counter). Pending writes are stored against the checkpoint before the step that produced them, which is how a resumed run knows which tasks of that step are already done.
    


    

    

    Storage grows with the square of the run length
    

    An agent's state is mostly its message list, and the list changes every step. A checkpoint stores the whole list each time, so N steps that each add about the same amount store about N(N+1)/2 steps' worth. The test: an agent-shaped graph with no model, 40 super-steps, each adding a tool call and a 1,000-character tool result, stored bytes read back after every step MEASURED. LangGraph 1.2 added a beta channel type, DeltaChannel, that stores only each step's new writes and rebuilds the value by replaying them:
    

    So for long threads keep the message list short (trim or summarise with middleware, section 9, or a context policy), prune old checkpoints, or try DeltaChannel, whose docstring warns "The API and on-disk representation may change"; its price is on the read side, where reading the state replays writes.
    

    

    add_messages stores the whole list every step; DeltaChannel stores only the new part
    

    

    

    

    Stored bytes = checkpoint rows + blobs + writes, uncompressed (length() in SQLite, octet_length() in Postgres). Tool results are hex text, different every step, so compression would not hide the growth. get_state times are one call on the M1 Pro; Postgres times include the round trip into Docker. Script: src/code/e3_storage.py.
    


    

    Durability modes: when the checkpoint is written
    

    invoke(..., durability=...) takes three values (docs): "sync" persists "synchronously before the next step starts"; "async", the default in the source, persists "asynchronously while the next step executes", with a "small risk" of losing a checkpoint in a crash; "exit" persists "only when graph execution exits", so "you cannot recover from system failures (like process crashes) mid-execution". The cost of each, on a one-node loop of 200 super-steps (best of 3) MEASURED:
    

    

    Under half a millisecond per step on SQLite, against model calls of seconds: for agents sync is the safe choice and costs nothing that matters. exit is for short graphs where only the final state counts.
    

    


    

    

    5. What survives a crash
    

    A run can stop halfway because the process dies (a deploy, an out-of-memory kill), a node raises (a provider timeout), or a person has not answered yet (section 6). First without a model: run the tests, then two checks in parallel (0.5 s and 6 s), then merge; SIGKILL about 3 s into the parallel step, after the fast check returned and while the slow one runs; then a fresh process calls invoke(None, config) on the same thread. Every node logs when it runs MEASURED:
    

    

    With a checkpointer writing each step, the fast check's result survived as a pending write and the resumed process ran only the slow check and the merge, as the docs promise: "When you resume graph execution from that super-step you don't re-run the successful nodes." An exception instead of a kill behaved the same (the database held the fast node's write plus an __error__ write, and only the failed node re-ran). With exit nothing had been saved: invoke(None) failed with EmptyInputError: Received no input for __start__, and the only option was to start over.
    

    Now with real model calls. The graph of section 2, each diagnosis a Claude Haiku 4.5 call through claude -p with every tool off. A driver killed the whole process group the moment the first diagnosis returned, started a second process that called invoke(None) on the same thread (or a fresh invoke({}) when there was no checkpoint), and a third that approved at the interrupt with Command(resume="approve"). Predict: with exit, how many model calls does the whole run start, against 3 when nothing goes wrong? Then switch Fig. 3 to exit. It opens on the end of each run; step back or drag to replay it event by event (Fig. 1 plays the sync run step by step).
    

    The answer: 5 calls with exit against 4 with sync. Both lose the call that was in flight; only exit also pays again for the diagnosis that had already returned, because with no checkpoint the restart begins from the input.

    What a checkpointer does not do. It restarts nothing: a supervisor (a job queue, Kubernetes, the Agent Server of section 11) must notice the dead run and resume it with the same thread_id. It cannot save the call in flight, so the smaller your nodes, the less a crash costs. And it cannot make side effects safe: a node that sent an e-mail and died before its write was saved sends it again on resume. Per node, LangGraph adds RetryPolicy (defaults in 1.2.14: first wait 0.5 s, doubling, at most 128 s, 3 attempts in all, with jitter), TimeoutPolicy (1.2; run and idle timeouts, "Timeouts apply to async nodes only", 1.2.0a6 notes) and error_handler (1.2; runs after the retries are exhausted and may return a Command, for compensation steps). The parent's Orchestration lab tab, part "Durable execution", sets this checkpointer against Temporal-style event-history replay.

    6. Interrupts and Command: pausing for a person, routing from inside a node
    

    An agent about to apply a patch, pay a refund or send an e-mail should sometimes ask first, and the answer may come tomorrow. Holding a process open for a day is fragile, so LangGraph pauses through the checkpoint: inside a node, interrupt(payload) raises a special exception, the runtime saves the state, and invoke returns with the payload (with 1.1's version="v2", in result.interrupts). Later, from any process, invoke(Command(resume=answer), config) loads the thread and runs the node again, and this time interrupt() returns the answer instead of raising. "The thread_id you choose is effectively your persistent cursor" (docs).
    

    The trap is runs the node again, from its first line ("The graph resumes from the start of the node, re-executing all logic", interrupt's docstring).     Every rule in the docs follows from that one fact, and each was checked here MEASURED:
    

    

    Rules checked: two interrupts in one node are matched by order ("Matching is strictly index-based"); parallel interrupts are resumed together by interrupt id; a single plain value fails when several are pending; a bare try/except Exception swallows the interrupt and the node carries on; without a checkpointer the resume fails ("Cannot use Command(resume=...) without checkpointer"); response_schema (1.2.12) validates the resume value; interrupt_before is a breakpoint, not an approval.
    

    Command carries these instructions. Command(resume=...) answers interrupts; returned from a node, Command(update={...}, goto="node") updates the state and picks the next node in one move (the node declares its possible destinations, add_node("triage", f, destinations=("billing", "tech")), so the graph can be drawn); goto may also be a Send or a list; graph=Command.PARENT sends the jump to the enclosing graph, which is how one agent hands over to another (section 8).
    

    Static breakpoints, compile(interrupt_before=["apply"]), stop before a node with no code in it; resume with invoke(None, config). The docs keep them for debugging: "Static interrupts are not recommended for human-in-the-loop workflows." Time travel is the same machinery: get_state_history(config) lists every checkpoint; update_state(old_config, values, as_node=...) writes a new checkpoint whose parent is an old one (a fork); invoke(None, new_config) runs forward from it. The parent's Orchestration lab forks a recorded run with an edited diagnosis.

    8. Subgraphs and handoffs
    

    A compiled graph can be a node of another, in two ways that behave differently on resume. Recorded: a parent graph (triage, fix_bug, apply) whose fix_bug is a two-node subgraph (locate, then patch, which calls interrupt()) MEASURED:
    

    

    In both, the subgraph got its own checkpoints under a namespace (fix_bug:<task id>), so locate was not re-run on resume and get_state(config, subgraphs=True) showed the paused subgraph's state. The difference: called from inside a function, the parent's wrapper function ran twice, because the parent node is what resumes from its first line. Whether a subgraph keeps state between calls is set by compile(checkpointer=...) on it: None (default) inherits the parent's checkpointer for one call, True keeps state per thread, False keeps none (docs).
    

    Handoffs. A node inside a subgraph returned Command(goto="billing", graph=Command.PARENT, update={...}); the parent ran billing next and the final log was ["triage: refund question, handing off", "billing: handled"] MEASURED. That is the whole mechanism behind LangGraph's handoff pattern. The prebuilt langgraph-supervisor and langgraph-swarm packages still exist, but the supervisor README now says "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases" (langgraph-supervisor); LangChain's multi-agent docs point to subagents as tools and to Deep Agents. When several agents help at all is Multi-agent patterns's subject; its section 6 sets handoffs like this one against agents called as tools.
    

    

    

    

    9. create_agent and middleware: the agent loop as a graph
    

    Most people never write a StateGraph for a tool-calling agent: create_agent(model, tools, system_prompt=..., middleware=[...], checkpointer=...) builds the ReAct-style loop (call the model; if it asked for tools, run them and call it again; otherwise stop) and "uses LangGraph under the hood" (LangChain). It replaces LangGraph's create_react_agent, deprecated since 1.0 and due for removal in 2.0 (migration guide). The loop itself, written by hand, is Building a harness's subject.
    

    Middleware changes that loop without rewriting it. A middleware class implements some of six hooks (docs): before_agent and after_agent (once per invocation), before_model and after_model (around every model call, as graph nodes that may return a state update or jump), and wrap_model_call and wrap_tool_call (functions around each call, for retries, fallbacks, caching or rewriting the request). before_* hooks run first to last, after_* last to first, and wrap hooks nest like function calls. The hooks become nodes: the compiled graph of the same agent without and with two middlewares, read with get_graph() MEASURED:

    10. The store: memory across threads
    

    A checkpoint belongs to one thread: a new conversation starts empty. What should carry over (a user's preferences, facts about a project) goes in a store: "LangGraph stores provide cross-thread long-term memory, complementing per-thread checkpointer persistence" (docs). A store is a key-value database whose keys live in namespaces, tuples such as ("users", user_id, "prefs"); pass it to compile(store=...) and a node receives it as an argument. Three threads of one graph sharing an InMemoryStore MEASURED:
    

    

    Backends: InMemoryStore for tests; PostgresStore, MongoDBStore, RedisStore or UpstashStore for production; with an index configuration (an embedding function, its dimensions, the fields to embed) store.search(namespace, query=...) does semantic search (docs; not run here, it needs an embedding model). A store keeps exactly what your node writes. What to remember, what to do when a new fact contradicts an old one, and when to retrieve are a design problem of their own, which memory-layer libraries (Mem0, Zep's Graphiti, Letta) hand to a model; they are compared in Context engineering, section 8 (agent memory), which absorbed the old Agent memory layers page.
    

    


    

    11. Deployment: the Agent Server
    

    Everything above runs in your process with your database, and you own what a checkpointer does not do: a process per graph, a queue, something that notices a dead run and resumes it, an HTTP API. LangChain sells those as LangSmith Deployment (formerly LangGraph Platform). Its server, the Agent Server (formerly LangGraph Server), is "built on the concept of assistants" with "built-in persistence and a task queue", and with it "you do not need to implement or configure checkpointers or stores manually" (docs). LangSmith Studio (formerly LangGraph Studio) is a visual debugger over a running graph's threads, checkpoints and interrupts. Plans and prices are in the dated table below. Hosted agent runtimes in general (Claude Managed Agents, the OpenAI Agents API) are compared on the parent's Production stack tab.

    Mistakes, one line each (every one shown in a section above)
      

    • Two parallel nodes write a key with no reducer: InvalidUpdateError, and the saved pending writes keep the thread failing on every read until update_state repairs it (3).
      • 

    • Expecting a join from plain edges: with branches of different lengths the node runs twice; use add_edge(["a", "b"], "join") (3).
      • 

    • A side effect before interrupt(): the e-mail is sent twice; move it after the interrupt, into a later node, or make it idempotent with a key (6).
      • 

    • interrupt() inside try/except Exception: the except branch catches it and the node carries on without pausing (measured: it auto-approved); catch specific types (6).
      • 

    • No checkpointer, or InMemorySaver, in production: the interrupt returns but the resume fails; in-memory state dies with the process; use Postgres, or SQLite on one machine (4, 6).
      • 

    • Reusing a thread_id for a new conversation, or a new one for a resume: the id is the cursor; your approval link must carry the paused run's id (6).
      • 

    • Letting the message list grow forever: 1.3 MB for 40 small steps in SQLite; trim, summarise, prune, or try DeltaChannel (4).
      • 

    • Trusting the old recursion limit of 25: set recursion_limit or a model-call limit yourself (3).
      • 

    • Approving tool calls without reading them: an approve-everything reviewer let a 4B model write a new core.py in the wrong directory (9).
      • 

    • Assuming LangGraph restarts crashed runs: it saves state; a supervisor, a queue or the Agent Server must call resume (5).

    Interview rehearsal: nine questions with short answers
    

    What is a super-step, and why does LangGraph use them? One round: plan the triggered nodes (a trigger channel newer than the node last saw), run them in parallel against the state as of the step start, apply all writes together through the reducers and save a checkpoint. From Pregel and bulk synchronous parallel computing; it makes parallel branches deterministic (fixed write order) and gives a natural point to checkpoint.
    

    What does a reducer do, and what happens without one? It merges several writes to one key in a step (append, add, merge messages by id). Without one a key accepts one write per step; two parallel writes raise InvalidUpdateError.
    

    A run crashes while two parallel nodes run; one had finished. What re-runs? With a checkpointer in sync or async mode, only the unfinished one: the finished output was a pending write. With "exit", everything. The call in flight is lost and paid again either way.
    

    How does interrupt() work, and what is the trap? It raises; the runtime saves state and returns the payload. Command(resume=value) reloads the thread and re-runs the node from its first line, and interrupt() returns the value. Everything before it runs again. Several interrupts in a node match by order; parallel ones resume by id.
    

    Checkpointer against store? A checkpointer saves the full graph state per thread at every step (resume, time travel); a store holds application key-value data across threads in namespaces (user preferences), optionally with semantic search.
    

    Which durability mode for an agent? sync: written before the next step, so a crash never loses a finished step, at under half a millisecond per step on SQLite. async (the default) overlaps the write at a small risk; exit cannot recover from a crash.
    

    Design a multi-day human approval. Postgres checkpointer; the approval node calls interrupt() with the diff; store the thread_id in the approval request; the approve endpoint calls invoke(Command(resume="approve"), {"thread_id": ...}) from any worker; side effects after the interrupt; something retries if that worker dies.
    

    What is create_agent, and how does middleware change the graph? LangChain 1.x's tool-calling loop compiled to a LangGraph graph (a model node and a tools node). Each node-style hook becomes its own node; wrap hooks nest around the call; the human-in-the-loop middleware is an after_model node that calls interrupt() with the pending tool calls.
    

    When would you not use LangGraph? A short linear tool loop that needs no crash survival, no waiting for people, no parallel branches and no inspection of intermediate state: a plain loop is simpler and shows every prompt.
