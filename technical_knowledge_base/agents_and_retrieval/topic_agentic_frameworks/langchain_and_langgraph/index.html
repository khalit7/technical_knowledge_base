The page in one screen

LangChain is a Python (and TypeScript) library of building blocks for model applications: one interface for every provider's chat model, tools, and since version 1.0 a ready agent loop, create_agent, customised with middleware (code that runs before or after each model or tool call). LangGraph is the runtime underneath: you describe a program as a graph of steps (nodes) that read and update one shared state, and LangGraph runs it in rounds called super-steps, saving a checkpoint of the state after each one. The 1.0 announcement put the split in one line each: LangChain is "the fastest way to build an AI agent", LangGraph "a lower level framework and runtime, useful for highly custom and controllable agents" (LangChain, 22 Oct 2025).

The reason to use LangGraph rather than the thirty-line loop of the Topic: agentic-frameworks Reading tab is almost entirely the checkpoint: it is what lets a run survive a crash, wait days for a person, and be rewound. So this page spends most of its time on what a checkpoint holds and what it does and does not save you from, measured.

    1. LangChain: three eras, and what is still useful

    LangChain began as one package that wrapped everything: prompts, chains of calls, agents, retrievers, hundreds of integrations. It was then split into a small stable core plus integration packages, and in October 2025 cut down to an agent library on top of LangGraph.     2. A graph from zero

    Start from the problem. The running example's tests fail because of two bugs. A sensible workflow: run the tests, diagnose each failure (the two diagnoses are independent, so they can run at the same time), propose one fix from both diagnoses, show the fix to a person, and apply it only if they approve. In plain Python that is five function calls in a row. LangGraph asks you to write the same thing as three kinds of object:

    • State: a typed dictionary (a TypedDict, Pydantic model or dataclass) that every step reads and updates. Here: the code, the test output, a list of diagnoses, the patch, the decision.
    • Nodes: plain functions that take the state and return a partial update, a dictionary with only the keys they change. A node never mutates the state it was given.
    • Edges: which node runs after which. A normal edge always fires; a conditional edge calls a function on the state and returns the name of the next node (or several, or END).

    This is the graph that the Crash lab ran with real Claude Haiku 4.5 calls, trimmed to its shape (the full script is in this page's src/code/e6_real.py):

    class S(TypedDict, total=False):
    core: str
    test_output: str
    diagnoses: Annotated[list, operator.add]   # a reducer: parallel writes are concatenated
    patch: str
    decision: str
    passed: bool

b = StateGraph(S)
b.add_node("read_and_test", read_and_test)            # returns {"core": ..., "test_output": ...}
b.add_node("diagnose_word_count", diag("test_word_count"))
b.add_node("diagnose_top_words", diag("test_top_words"))
b.add_node("propose_fix", propose_fix)                # one model call, returns {"patch": ...}
b.add_node("human_review", human_review)              # calls interrupt(), returns {"decision": ...}
b.add_node("apply_and_test", apply_and_test)
b.add_edge(START, "read_and_test")
b.add_edge("read_and_test", "diagnose_word_count")    # two edges out of one node:
b.add_edge("read_and_test", "diagnose_top_words")     # both run, in parallel
b.add_edge(["diagnose_word_count", "diagnose_top_words"], "propose_fix")   # wait for both
b.add_edge("propose_fix", "human_review")
b.add_edge("human_review", "apply_and_test")
b.add_edge("apply_and_test", END)
app = b.compile(checkpointer=SqliteSaver(conn))       # the checkpointer is what makes it durable
app.invoke({}, {"configurable": {"thread_id": "fix-1"}})

    compile() checks the wiring (an edge to an unknown node raises ValueError: Found edge ending at unknown node; a node that no edge reaches compiles without complaint MEASURED) and returns a Pregel object, the runtime of section 3. It has invoke (run to the end or to the next interrupt), stream (the same, yielding events as it goes), get_state and get_state_history (read checkpoints) and update_state (write one, which is how you edit or rewind). Every call carries a config whose thread_id names the run; with a checkpointer it is required ("you must specify a thread_id", docs).

    Dashed arrows are conditional edges; solid ones always fire. START and END are not nodes you write: START is where the input enters, and reaching END with nothing else scheduled ends the run.

    A second way to write the same thing is the functional API (stable since langgraph 0.2.74, 19 Feb 2025, release notes): ordinary Python control flow inside a function marked @entrypoint, calling functions marked @task whose results are saved. Section 9 shows a measured example. Both compile to the same runtime: "Compiling a StateGraph or creating an @entrypoint produces a Pregel instance" (docs).

    3. How a graph runs: super-steps

    LangGraph's README says it "is inspired by Pregel and Apache Beam". Pregel is Google's system for computing over huge graphs (Malewicz et al., SIGMOD 2010); it runs in the bulk synchronous parallel style that Valiant described in 1990 (CACM 33(8)): work proceeds in rounds, everything in a round runs in parallel, and results are exchanged only at the barrier between rounds. LangGraph calls a round a super-step: "a single tick of the graph where all nodes scheduled for that step execute (potentially in parallel)" (docs). Each super-step has three phases, which you can read straight out of pregel/_algo.py:

    1. Plan. Every state key is a channel with a version number that goes up each time it is written. Edges are channels too, with names you never typed: branch:to:propose_fix, or join:diagnose_word_count+diagnose_top_words:propose_fix for a wait-for-both edge. Each node remembers the version of each trigger channel it last saw (versions_seen). A node runs in this step if one of its trigger channels has a newer version than it saw.
    2. Execute. All triggered nodes run in parallel. Each reads the state as it was at the start of the step, so no node sees another's output from the same step. What a node returns is not applied yet: it is held, and saved, as a pending write.
    3. Update. At the barrier, all pending writes are applied together, sorted by task path rather than by finishing time, each through its channel's reducer; written channels get the next version; and a checkpoint is saved. Then the next plan starts. When no node is triggered, the run ends.

    A key with no reducer is a LastValue channel: it accepts exactly one write per step. A key annotated with a reducer (Annotated[list, operator.add], or add_messages for chat messages) is a BinaryOperatorAggregate channel: any number of writes are folded in.     What the toggle shows. With the reducer, the two findings are concatenated in a fixed order: check_top_words finished first, yet its finding comes second, because writes are applied by task path. Without it, the step fails with InvalidUpdateError: At key 'findings': Can receive only one value per step. Use an Annotated key to handle multiple values. One more thing happened that the error message does not say MEASURED: both writes had already been saved as pending writes, so every later get_state() on that thread raised the same error. The thread is stuck until you write past it: update_state(config, {"findings": [...]}, as_node="check_tokenize") saved a new checkpoint, after which invoke(None, config) finished the run MEASURED; fix the schema before you run, not after. To bypass a reducer on purpose for one write (reset a list, say), return Overwrite(value) (since langgraph 1.0.2, 29 Oct 2025, release).

    Predict: branch A is two nodes long (search, then read the hits), branch B one node (lint). Both have a plain edge into join. How many times does join run?
    Twice MEASURED. In super-step 3, B's edge has fired and A is still on its second node, so join is triggered by B alone and runs alongside a_read_hits; in super-step 4 A's edge fires and join runs again. The recorded log is read, a_search, b_lint, a_read_hits, join, join. Written as add_edge(["a_read_hits", "b_lint"], "join") the edge becomes one join: channel that fires only when both have written, and join runs once. Plain edges mean "run when any arrives"; the list form means "wait for all". Both runs are in the Super-step lab.

    Loops and the recursion limit. A conditional edge may point backwards (fix, test, fix again). Each pass is a super-step, and the run stops with GraphRecursionError when it exceeds recursion_limit super-steps. The default was 25 up to langgraph 1.0.x, then 10,000 in 1.1.0 and 10,007 in 1.2.0 SOURCE (DEFAULT_RECURSION_LIMIT in _internal/_config.py of each wheel on PyPI; override with LANGGRAPH_DEFAULT_RECURSION_LIMIT or per call). Older tutorials that warn about hitting 25 describe the old default; a runaway agent loop now runs for a very long time unless you set a limit or a model-call limit (section 9) yourself.

    Map-reduce with Send. When the number of parallel tasks is known only at run time (one review per file), a conditional edge returns a list of Send("review", {"file": f}). Each Send becomes one task in the next super-step, with its own input rather than the shared state. Recorded: three files, three review tasks in one step, results gathered by a reducer, then summarise.

    4. Checkpointers: what is saved, where, and how big it gets

    A checkpointer is the object you pass to compile(checkpointer=...); it saves a checkpoint at every super-step boundary and the pending writes of every task in between. Without one, the state lives only in the running process, and interrupts cannot be resumed (section 6). With one, a thread's whole history is in a database, keyed by thread_id.

    What one checkpoint holds (the Checkpoint type in langgraph-checkpoint 4.2.0): id (unique and increasing, so it sorts by time), ts, channel_values (the state, plus trigger channels), channel_versions, versions_seen (per node) and updated_channels. Beside it sits metadata: source (input, loop, update or fork), step (-1 for the input checkpoint, then 0, 1, 2 ...), the parent checkpoint and the run id.     MEASURED straight from InMemorySaver.list() after the run (ids shortened to their last 8 characters, version strings to their counter). Pending writes are stored against the checkpoint before the step that produced them.
    

    Where it goes. The official list (docs): InMemorySaver (in the core package, "for experimentation"), SqliteSaver (langgraph-checkpoint-sqlite, "ideal for experimentation and local workflows"), PostgresSaver (langgraph-checkpoint-postgres, "used in LangSmith. Ideal for using in production"), and separately packaged MongoDB and Azure Cosmos DB savers. Redis appears in the docs only as a store (section 10), not a checkpointer: the old version of this page listed it as a checkpointer backend. The schemas, read from the two databases after the runs below MEASURED:
    

    SQLite (3.1.1): two tables. checkpoints (thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint BLOB, metadata BLOB) and writes (thread_id, checkpoint_ns, checkpoint_id, task_id, idx, channel, type, value BLOB). Each checkpoint row holds the whole serialized state.
    

    Postgres (3.1.2, Postgres 16 in Docker): four tables, created by setup() through 10 migrations. checkpoints (small JSONB rows), checkpoint_blobs (one row per channel per version, so an unchanged channel is not stored again), checkpoint_writes and checkpoint_migrations.
    

    Values are serialized with JsonPlusSerializer (msgpack; pickle fallback off by default; LANGGRAPH_STRICT_MSGPACK=true restricts which classes may be rebuilt). An EncryptedSerializer encrypts everything with an AES key from LANGGRAPH_AES_KEY (docs): checkpoints hold every prompt, tool result and secret your agent saw.
    

    Storage grows with the square of the run length
    

    An agent's state is mostly its message list, and the message list changes every step. A checkpoint stores the whole list each time, so a run of N steps that adds about the same amount per step stores about N(N+1)/2 copies' worth. The test: an agent-shaped graph with no model, 40 super-steps, each adding a tool call and a 1,000-character tool result, stored bytes read back after every step MEASURED. LangGraph 1.2 added a beta channel type, DeltaChannel, that stores only each step's new writes and rebuilds the value by replaying them:
    

    

    

    

    

    Stored bytes = checkpoint rows + blobs + writes, uncompressed (length() in SQLite, octet_length() in Postgres). Tool results are hex text, different every step, so compression would not hide the growth. get_state times are one call on the M1 Pro; Postgres times include the round trip into Docker. Script: src/code/e3_storage.py.
    

    So for long agent threads, either keep the message list short (summarise or trim with middleware, section 9, or a context policy), prune old checkpoints, or try DeltaChannel, whose docstring marks it beta: "The API and on-disk representation may change". Its price is on the read side: reading the state replays writes.
    

    Durability modes: when the checkpoint is written
    

    invoke(..., durability=...) takes one of three values (docs): "sync" persists "synchronously before the next step starts"; "async", the default in the source, persists "asynchronously while the next step executes", with a "small risk" of losing a checkpoint in a crash; "exit" persists "only when graph execution exits", so "you cannot recover from system failures (like process crashes) mid-execution". The cost of each, on a one-node loop of 200 super-steps (best of 3) MEASURED:
    

    

    A fraction of a millisecond per step against model calls of seconds: for agents the overhead does not matter, and sync is the safe choice. exit exists for short graphs where you only care about the final state.
    

    


    

    5. What survives a crash
    

    Three things can stop a run halfway: the process dies (a deploy, an out-of-memory kill, a laptop lid), a node raises (a provider timeout), or a person has not answered yet. The first two are tested here; the third is section 6.
    

    A kill in the middle of a parallel step, no model. Graph: run the tests, then two checks in parallel (one 0.5 s, one 6 s), then merge. The process is sent SIGKILL about 3 s into the parallel step, after the fast check has returned and while the slow one is still running; a fresh process then calls invoke(None, config) on the same thread. Every node appends to a log when it runs, so we can see what ran where MEASURED:
    

    

    With a checkpointer writing each step, the fast check's result survived as a pending write, and the resumed process ran only the slow check and the merge. The docs promise exactly this: "When a graph node fails mid-execution at a given super-step, LangGraph stores pending checkpoint writes from any other nodes that completed successfully at that super-step. When you resume graph execution from that super-step you don't re-run the successful nodes." The same happened when the slow node raised an exception instead of being killed: the database held the fast node's write plus an __error__ write, and the resume re-ran only the node that failed. With exit nothing had been saved, invoke(None) failed with EmptyInputError: Received no input for __start__, and the only option was to start over.
    

    The same experiment with real model calls. The graph of section 2, each diagnosis a Claude Haiku 4.5 call through claude -p with every tool off, killed the moment the first diagnosis returned, then resumed, then approved at the interrupt. Once with sync, once with exit:
    

    

    Bars are model calls to scale in seconds, one lane per process; the red line is the SIGKILL. A call cut by the kill (hatched) was in flight: its tokens may well have been billed, but no result came back and the recording has no usage for it. Call times overlap other agents' load on the same machine, so durations are indicative. Full transcripts and the replay: Crash lab.
    

    What a checkpointer does not do. It does not restart anything: some supervisor (a job queue, Kubernetes, the Agent Server of section 11) must notice the dead run and call resume with the same thread_id. It cannot save the call that was in flight; the smaller your nodes, the less a crash costs. And it cannot make side effects safe: a node that sent an e-mail and then died before its write was saved will send it again on resume. Per node, LangGraph adds three knobs: RetryPolicy (defaults in 1.2.14: first wait 0.5 s, doubling, at most 128 s, 3 attempts in all, with jitter), TimeoutPolicy (1.2; run and idle timeouts, "Timeouts apply to async nodes only", 1.2.0a6 notes), and error_handler (1.2; runs after the retries are exhausted and may return a Command, for compensation steps).
    

    Go deeper. The parent's Orchestration lab tab, part "Durable execution", kills, resumes, interrupts and forks a linear version of this graph and contrasts the checkpointer with Temporal-style event-history replay; this page's Crash lab replays both runs above call by call.
    

    

    

    6. Interrupts and Command: pausing for a person, and routing from inside a node
    

    An agent about to apply a patch, pay a refund or send an e-mail should sometimes ask first, and the answer may come tomorrow. Holding a process open for a day is fragile, so LangGraph does it with the checkpoint: inside a node, interrupt(payload) raises a special exception, the runtime saves the state, and invoke returns with the payload (in the 1.1+ version="v2" format, in result.interrupts). Later, from any process, invoke(Command(resume=answer), config) loads the thread and runs the node again, and this time interrupt() returns the answer instead of raising. "The thread_id you choose is effectively your persistent cursor" (docs).
    

    The key phrase is runs the node again: from its first line ("The graph resumes from the start of the node, re-executing all logic", interrupt's docstring).     Every rule in the docs follows from that one fact, and each was checked here MEASURED:
    

    

    Command is the object that carries these instructions. Command(resume=...) answers interrupts; returned from a node, Command(update={...}, goto="node") updates the state and picks the next node in one move (the node must declare its possible destinations, for example add_node("triage", f, destinations=("billing", "tech")), so the graph can be drawn); goto may also be a Send or a list; and graph=Command.PARENT sends the jump to the enclosing graph, which is how one agent hands a conversation to another (section 8).
    

    Static breakpoints, compile(interrupt_before=["apply"]), stop before a node without any code in it; resuming is invoke(None, config). The docs keep them for debugging: "Static interrupts are not recommended for human-in-the-loop workflows." Time travel uses the same machinery: get_state_history(config) lists every checkpoint; update_state(old_config, values, as_node=...) writes a new checkpoint whose parent is an old one (a fork), and invoke(None, new_config) runs forward from it. The parent's Orchestration lab forks a recorded run with an edited diagnosis; it is not repeated here.

    8. Subgraphs and handoffs
    

    A compiled graph can be a node of another graph. Two ways to do it, which behave differently on resume. Recorded: a parent graph (triage, fix_bug, apply) whose fix_bug is a two-node subgraph (locate, then patch, which calls interrupt()) MEASURED:
    

    

    In both, the subgraph got its own checkpoints under a namespace (fix_bug:<task id>), so locate was not re-run on resume and get_state(config, subgraphs=True) showed the paused subgraph's own state. The difference: called from inside a function, the parent's wrapper function ran twice, because the parent node is what resumes from its first line. Whether a subgraph keeps state between calls is set by compile(checkpointer=...) on the subgraph: None (default) inherits the parent's checkpointer for one call, True keeps state per thread, False keeps none (docs).
    

    Handoffs. A node inside a subgraph returned Command(goto="billing", graph=Command.PARENT, update={...}); the parent ran billing next, and the final log was ["triage: refund question, handing off", "billing: handled"] MEASURED. That is the whole mechanism behind LangGraph's handoff pattern. The prebuilt langgraph-supervisor and langgraph-swarm packages still exist, but the supervisor README now says "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases", and neither has had a release since December 2025 (langgraph-supervisor); LangChain's multi-agent docs point to subagents as tools and to Deep Agents. When several agents help at all is the subject of Multi-agent patterns.
    

    

    

    9. create_agent and middleware: the agent loop as a graph
    

    Most people never write a StateGraph for a tool-calling agent: LangChain 1.x gives you one. create_agent(model, tools, system_prompt=..., middleware=[...], checkpointer=...) builds the ReAct-style loop (call the model; if it asked for tools, run them and call it again; otherwise stop) and "uses LangGraph under the hood" (LangChain). It replaces LangGraph's create_react_agent, deprecated since 1.0 and due for removal in 2.0 (migration guide).
    

    Middleware is how you change that loop without rewriting it. A middleware class implements some of six hooks (docs): before_agent and after_agent (once per invocation), before_model and after_model (around every model call, as graph nodes that may return a state update or jump), and wrap_model_call and wrap_tool_call (functions wrapped around each call, for retries, fallbacks, caching or rewriting the request). before_* hooks run first to last, after_* last to first, and wrap hooks nest like function calls. Built in: HumanInTheLoopMiddleware, SummarizationMiddleware, ModelCallLimitMiddleware, ToolCallLimitMiddleware, ModelRetryMiddleware, ToolRetryMiddleware, ModelFallbackMiddleware, ToolErrorMiddleware, PIIMiddleware, TodoListMiddleware, LLMToolSelectorMiddleware, ProviderToolSearchMiddleware, ContextEditingMiddleware, ShellToolMiddleware, FilesystemFileSearchMiddleware and LLMToolEmulator (the exports of langchain.agents.middleware in 1.4.3; the docs page adds filesystem, subagent and rubric middleware from the deepagents package).

    10. The store: memory across threads
    

    A checkpoint belongs to one thread: a new conversation starts empty. What should carry over (a user's preferences, facts about a project) goes in a store: "LangGraph stores provide cross-thread long-term memory, complementing per-thread checkpointer persistence" (docs). A store is a key-value database whose keys live in namespaces, tuples such as ("users", user_id, "prefs"); you pass it to compile(store=...) and a node receives it as an argument.     11. Deployment: LangSmith Deployment and the Agent Server
    

    Everything above runs in your own process with your own database, and you own the parts a checkpointer does not do: a process to run each graph, a queue, something that notices a dead run and resumes it, and an HTTP API. LangChain sells those as a service. Names changed in October 2025: "LangGraph Platform is now LangSmith Deployment and LangGraph Studio is now LangSmith Studio" (LangSmith changelog, 13 to 17 Oct 2025); the server formerly called LangGraph Server is now the Agent Server, "built on the concept of assistants" with "built-in persistence and a task queue" (docs), and "you do not need to implement or configure checkpointers or stores manually" when using it. Studio is a visual debugger over a running graph's threads, checkpoints and interrupts. Prices change; on 6 October 2026 the pricing page listed a Plus plan at $39 per seat per month with one small deployment included, and usage-metered compute beyond it (pricing; read through a summarising fetch, so treat the figures as indicative).     12. The criticisms, checked, and when LangGraph earns its keep
    

    The criticism of LangChain is old, specific and mostly about the pre-1.0 package:
    

      

    • Abstraction tax. Max Woolf, 14 Jul 2023: "The problem with LangChain is that it makes simple things relatively complex" (minimaxir.com). Octomind (Fabian Both; the page is undated, the first archived copy is from 14 Jun 2024; the site is gone): "We used LangChain in production for over 12 months, starting in early 2023 then removing it in 2024", and "in hindsight, we would've been better off long-term without a framework" (archived copy). Both target prompt templates, output parsers and LCEL chains, which 1.0 moved to langchain-classic; neither discusses LangGraph.
      • 

    • Hidden prompts. Hamel Husain, 14 Feb 2024: the prompts a framework sends are "the fastest way to understand how they work" (hamel.dev). Anthropic, 19 Dec 2024: frameworks "often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug" (Building effective agents). The first version of that page named "LangGraph from LangChain" first among the frameworks it meant (archived 20 Dec 2024); the current one names others. The cure is unchanged: log the literal request, as section 9 does.
      • 

    • Graph ceremony. For a linear tool loop a schema, nodes, edges and compile() are overhead over a loop you can write in thirty lines; the parent's Same agent, six ways tab shows the same agent in both styles.
      • 

    • Churn. The 0.x years broke APIs often. Since October 2025 the promise is "no breaking changes until 2.0", and 1.0 is a long-term-support line until 2.0 ships (release policy); a year in, no 2.x exists, while defaults still move inside 1.x (the recursion limit went from 25 to 10,000 in 1.1.0, section 3).
      • 

    

    Two critiques this page adds from its own runs: the reducer error leaves a thread unreadable until repaired (section 3), and resuming re-executes the interrupted node and its wrapper (sections 6 and 8), which is correct but surprises everyone once.
    

    When LangGraph earns its keep
    

      

    • Runs long enough that a crash or deploy mid-run must not lose paid work (pending writes saved the finished diagnosis in section 5).
      • 

    • Approvals that wait hours or days: interrupt plus checkpoint, resumable from any process.
      • 

    • Real branching: parallel fan-out with merge rules, wait-for-all joins, loops with limits, map-reduce over a list known only at run time. If you have hand-built a DAG engine over model calls, this is that engine plus persistence, streaming and rewind.
      • 

    • You want inspection: every intermediate state is a row you can read, diff and fork.
      • 

    

    If none applies, a plain loop over provider calls behind a gateway such as LiteLLM, with tracing, is the simpler system; and if you only need a typed agent loop, the typed agent libraries are lighter.
    

    

    

    Common mistakes
    

    Two parallel nodes write the same key that has no reducer
    InvalidUpdateError at the end of the step, and the saved pending writes keep the thread failing on every read until update_state repairs it (section 3). Give every key that parallel nodes write a reducer.
    

    Expecting a join with plain edges
    Two plain edges into one node mean "run when either arrives": with branches of different lengths the node runs twice. Use add_edge(["a", "b"], "join") to wait for both (section 3).
    

    A side effect before interrupt()
    The node re-runs from its first line on resume, so the e-mail is sent twice (measured, section 6). Put side effects after the interrupt, in a later node, or make them idempotent with a key.
    

    Wrapping interrupt() in try/except Exception
    The interrupt is an exception; a bare except catches it and the node carries on without pausing (measured: the except branch auto-approved). Catch specific exception types only.
    

    No checkpointer in production, or InMemorySaver
    Without a checkpointer an interrupt still returns its payload, but Command(resume=...) fails with "Cannot use Command(resume=...) without checkpointer" (measured). InMemorySaver loses everything with the process. Use Postgres (or SQLite for one machine).
    

    Reusing a thread_id for a new conversation, or a new one for a resume
    The thread id is the cursor: the same id continues (and appends to) the old state; a different id starts from nothing. Resume with the id the paused run used, which your approval link must carry.
    

    Letting the message list grow forever
    Storage grows with the square of the run length (section 4: 1.3 MB for 40 small steps). Trim or summarise messages, prune checkpoints, or try DeltaChannel (beta).
    

    Trusting the old recursion limit
    Tutorials say a loop stops at 25 super-steps; since langgraph 1.1.0 the default is 10,000 (10,007 in 1.2). Set recursion_limit or a model-call limit yourself.
    

    Approving tool calls without reading them
    The approval gate only helps if the reviewer checks what it shows. In section 9, an approve-everything reviewer let a 4B model write a new core.py in the wrong directory.
    

    Assuming LangGraph restarts crashed runs
    It saves state; it does not watch processes. A supervisor, queue or the Agent Server has to call resume.
    


    Interview questions
    

    What is a super-step, and why does LangGraph use them?
    One round of the graph: plan which nodes are triggered (a trigger channel has a version newer than the node last saw), run them all in parallel against the state as of the step start, then apply all their writes together through the reducers and save a checkpoint. Taken from Pregel and bulk synchronous parallel computing. It makes parallel branches deterministic (writes applied in a fixed order) and gives a natural point to checkpoint.
    

    What does a reducer do, and what happens without one?
    It merges several writes to one key in a step (append, add, merge messages by id). Without one, a key accepts one write per step; two parallel writes raise InvalidUpdateError.
    

    A run crashes while two nodes are running in parallel; one had finished. What re-runs on resume?
    With a checkpointer in sync or async mode, only the unfinished one: the finished node's output was saved as a pending write against the step's checkpoint. With durability "exit", everything: nothing was saved. The call that was in flight is lost and paid again either way.
    

    How does interrupt() work, and what is the trap?
    It raises a special exception; the runtime saves state and returns the payload. Command(resume=value) reloads the thread and re-runs the node from its first line, and interrupt() then returns the value. Trap: everything before it runs again, so side effects there repeat. Multiple interrupts in a node are matched by order; parallel ones are resumed by interrupt id.
    

    Checkpointer versus store?
    A checkpointer saves the full graph state per thread, every step: short-term memory, resume, time travel. A store holds application key-value data across threads in namespaces: long-term memory such as user preferences, optionally with semantic search.
    

    Durability modes: which would you choose for an agent and why?
    sync: the checkpoint is written before the next step starts, so a crash never loses a finished step; the measured cost is under half a millisecond per step on SQLite, nothing next to a model call. async (the default) overlaps the write with the next step at a small risk; exit writes only at the end and cannot recover from a crash.
    

    How would you implement a multi-day human approval with LangGraph?
    Postgres checkpointer; the approval node calls interrupt() with the diff; the run returns; store the thread_id in the approval request; the approve endpoint calls invoke(Command(resume="approve"), {"thread_id": ...}) from any worker; keep side effects after the interrupt; something must retry if that worker dies.
    

    What is create_agent and how does middleware change the graph?
    LangChain 1.x's standard tool-calling loop, compiled to a LangGraph graph with a model node and a tools node. Each middleware hook (before_model, after_model and so on) becomes its own node on the path, and wrap hooks nest around the model or tool call; the human-in-the-loop middleware is an after_model node that calls interrupt() with the pending tool calls.
    

    When would you not use LangGraph?
    A short, linear tool loop with no need to survive crashes, wait for people, branch in parallel or inspect intermediate state: a plain loop is simpler and shows you every prompt.
