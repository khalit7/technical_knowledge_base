Mistakes, one line each (every one shown in a section above)
  • Two parallel nodes write a key with no reducer: InvalidUpdateError, and the saved pending writes keep the thread failing on every read until update_state repairs it (3).
  • Expecting a join from plain edges: with branches of different lengths the node runs twice; use add_edge(["a", "b"], "join") (3).
  • A side effect before interrupt(): the e-mail is sent twice; move it after the interrupt, into a later node, or make it idempotent with a key (6).
  • interrupt() inside try/except Exception: the except branch catches it and the node carries on without pausing (measured: it auto-approved); catch specific types (6).
  • No checkpointer, or InMemorySaver, in production: the interrupt returns but the resume fails; in-memory state dies with the process; use Postgres, or SQLite on one machine (4, 6).
  • Reusing a thread_id for a new conversation, or a new one for a resume: the id is the cursor; your approval link must carry the paused run's id (6).
  • Letting the message list grow forever: 1.3 MB for 40 small steps in SQLite; trim, summarise, prune, or try DeltaChannel (4).
  • Trusting the old recursion limit of 25: set recursion_limit or a model-call limit yourself (3).
  • Approving tool calls without reading them: an approve-everything reviewer let a 4B model write a new core.py in the wrong directory (9).
  • Assuming LangGraph restarts crashed runs: it saves state; a supervisor, a queue or the Agent Server must call resume (5).
Interview rehearsal: nine questions with short answers

What is a super-step, and why does LangGraph use them? One round: plan the triggered nodes (a trigger channel newer than the node last saw), run them in parallel against the state as of the step start, apply all writes together through the reducers and save a checkpoint. From Pregel and bulk synchronous parallel computing; it makes parallel branches deterministic (fixed write order) and gives a natural point to checkpoint.

What does a reducer do, and what happens without one? It merges several writes to one key in a step (append, add, merge messages by id). Without one a key accepts one write per step; two parallel writes raise InvalidUpdateError.

A run crashes while two parallel nodes run; one had finished. What re-runs? With a checkpointer in sync or async mode, only the unfinished one: the finished output was a pending write. With "exit", everything. The call in flight is lost and paid again either way.

How does interrupt() work, and what is the trap? It raises; the runtime saves state and returns the payload. Command(resume=value) reloads the thread and re-runs the node from its first line, and interrupt() returns the value. Everything before it runs again. Several interrupts in a node match by order; parallel ones resume by id.

Checkpointer against store? A checkpointer saves the full graph state per thread at every step (resume, time travel); a store holds application key-value data across threads in namespaces (user preferences), optionally with semantic search.

Which durability mode for an agent? sync: written before the next step, so a crash never loses a finished step, at under half a millisecond per step on SQLite. async (the default) overlaps the write at a small risk; exit cannot recover from a crash.

Design a multi-day human approval. Postgres checkpointer; the approval node calls interrupt() with the diff; store the thread_id in the approval request; the approve endpoint calls invoke(Command(resume="approve"), {"thread_id": ...}) from any worker; side effects after the interrupt; something retries if that worker dies.

What is create_agent, and how does middleware change the graph? LangChain 1.x's tool-calling loop compiled to a LangGraph graph (a model node and a tools node). Each node-style hook becomes its own node; wrap hooks nest around the call; the human-in-the-loop middleware is an after_model node that calls interrupt() with the pending tool calls.

When would you not use LangGraph? A short linear tool loop that needs no crash survival, no waiting for people, no parallel branches and no inspection of intermediate state: a plain loop is simpler and shows every prompt.
