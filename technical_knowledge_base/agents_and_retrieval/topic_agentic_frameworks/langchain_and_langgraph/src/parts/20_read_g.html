Common mistakes

Two parallel nodes write the same key that has no reducer
InvalidUpdateError at the end of the step, and the saved pending writes keep the thread failing on every read until update_state repairs it (section 3). Give every key that parallel nodes write a reducer.
Expecting a join with plain edges
Two plain edges into one node mean "run when either arrives": with branches of different lengths the node runs twice. Use add_edge(["a", "b"], "join") to wait for both (section 3).
A side effect before interrupt()
The node re-runs from its first line on resume, so the e-mail is sent twice (measured, section 6). Put side effects after the interrupt, in a later node, or make them idempotent with a key.
Wrapping interrupt() in try/except Exception
The interrupt is an exception; a bare except catches it and the node carries on without pausing (measured: the except branch auto-approved). Catch specific exception types only.
No checkpointer in production, or InMemorySaver
Without a checkpointer an interrupt still returns its payload, but Command(resume=...) fails with "Cannot use Command(resume=...) without checkpointer" (measured). InMemorySaver loses everything with the process. Use Postgres (or SQLite for one machine).
Reusing a thread_id for a new conversation, or a new one for a resume
The thread id is the cursor: the same id continues (and appends to) the old state; a different id starts from nothing. Resume with the id the paused run used, which your approval link must carry.
Letting the message list grow forever
Storage grows with the square of the run length (section 4: 1.3 MB for 40 small steps). Trim or summarise messages, prune checkpoints, or try DeltaChannel (beta).
Trusting the old recursion limit
Tutorials say a loop stops at 25 super-steps; since langgraph 1.1.0 the default is 10,000 (10,007 in 1.2). Set recursion_limit or a model-call limit yourself.
Approving tool calls without reading them
The approval gate only helps if the reviewer checks what it shows. In section 9, an approve-everything reviewer let a 4B model write a new core.py in the wrong directory.
Assuming LangGraph restarts crashed runs
It saves state; it does not watch processes. A supervisor, queue or the Agent Server has to call resume.

Interview questions

What is a super-step, and why does LangGraph use them?
One round of the graph: plan which nodes are triggered (a trigger channel has a version newer than the node last saw), run them all in parallel against the state as of the step start, then apply all their writes together through the reducers and save a checkpoint. Taken from Pregel and bulk synchronous parallel computing. It makes parallel branches deterministic (writes applied in a fixed order) and gives a natural point to checkpoint.
What does a reducer do, and what happens without one?
It merges several writes to one key in a step (append, add, merge messages by id). Without one, a key accepts one write per step; two parallel writes raise InvalidUpdateError.
A run crashes while two nodes are running in parallel; one had finished. What re-runs on resume?
With a checkpointer in sync or async mode, only the unfinished one: the finished node's output was saved as a pending write against the step's checkpoint. With durability "exit", everything: nothing was saved. The call that was in flight is lost and paid again either way.
How does interrupt() work, and what is the trap?
It raises a special exception; the runtime saves state and returns the payload. Command(resume=value) reloads the thread and re-runs the node from its first line, and interrupt() then returns the value. Trap: everything before it runs again, so side effects there repeat. Multiple interrupts in a node are matched by order; parallel ones are resumed by interrupt id.
Checkpointer versus store?
A checkpointer saves the full graph state per thread, every step: short-term memory, resume, time travel. A store holds application key-value data across threads in namespaces: long-term memory such as user preferences, optionally with semantic search.
Durability modes: which would you choose for an agent and why?
sync: the checkpoint is written before the next step starts, so a crash never loses a finished step; the measured cost is under half a millisecond per step on SQLite, nothing next to a model call. async (the default) overlaps the write with the next step at a small risk; exit writes only at the end and cannot recover from a crash.
How would you implement a multi-day human approval with LangGraph?
Postgres checkpointer; the approval node calls interrupt() with the diff; the run returns; store the thread_id in the approval request; the approve endpoint calls invoke(Command(resume="approve"), {"thread_id": ...}) from any worker; keep side effects after the interrupt; something must retry if that worker dies.
What is create_agent and how does middleware change the graph?
LangChain 1.x's standard tool-calling loop, compiled to a LangGraph graph with a model node and a tools node. Each middleware hook (before_model, after_model and so on) becomes its own node on the path, and wrap hooks nest around the model or tool call; the human-in-the-loop middleware is an after_model node that calls interrupt() with the pending tool calls.
When would you not use LangGraph?
A short, linear tool loop with no need to survive crashes, wait for people, branch in parallel or inspect intermediate state: a plain loop is simpler and shows you every prompt.
