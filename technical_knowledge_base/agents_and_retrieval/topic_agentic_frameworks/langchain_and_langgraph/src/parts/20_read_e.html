9. create_agent and middleware: the agent loop as a graph

Most people never write a StateGraph for a tool-calling agent: LangChain 1.x gives you one. create_agent(model, tools, system_prompt=..., middleware=[...], checkpointer=...) builds the {{ReAct|n:3c65c17b0d0d816b9a24c28de8f08ea8}}-style loop (call the model; if it asked for tools, run them and call it again; otherwise stop) and "uses LangGraph under the hood" ({{LangChain|https://www.langchain.com/blog/langchain-langgraph-1dot0}}). It replaces LangGraph's create_react_agent, deprecated since 1.0 and due for removal in 2.0 ({{migration guide|https://docs.langchain.com/oss/python/migrate/langgraph-v1}}).

Middleware is how you change that loop without rewriting it. A middleware class implements some of six hooks ({{docs|https://docs.langchain.com/oss/python/langchain/middleware}}): before_agent and after_agent (once per invocation), before_model and after_model (around every model call, as graph nodes that may return a state update or jump), and wrap_model_call and wrap_tool_call (functions wrapped around each call, for retries, fallbacks, caching or rewriting the request). before_* hooks run first to last, after_* last to first, and wrap hooks nest like function calls. Built in: HumanInTheLoopMiddleware, SummarizationMiddleware, ModelCallLimitMiddleware, ToolCallLimitMiddleware, ModelRetryMiddleware, ToolRetryMiddleware, ModelFallbackMiddleware, ToolErrorMiddleware, PIIMiddleware, TodoListMiddleware, LLMToolSelectorMiddleware, ProviderToolSearchMiddleware, ContextEditingMiddleware, ShellToolMiddleware, FilesystemFileSearchMiddleware and LLMToolEmulator (the exports of langchain.agents.middleware in 1.4.3; the docs page adds filesystem, subagent and rubric middleware from the deepagents package).

What it shows. First, the request: the first body sent to the server held our system prompt verbatim, the user message, and three tool schemas generated from the functions' signatures and docstrings, with nothing added by LangChain MEASURED (open "The first request" below), which answers the hidden-prompt criticism for this version. Second, the gate: the interrupt payload is a HITLRequest, a list of action_requests (tool name, arguments, description) plus the decisions allowed for each; the answer is {"decisions": [...]}, each approve, edit (replace the arguments), reject (with a message the model sees as the tool result) or respond (answer instead of running the tool). Third, the human matters: the model wrote a brand-new core.py at the repository root; the approve-all reviewer let it through and the bugs stayed; the checking reviewer's rejection message made the model read the real file and fix one of the two bugs, after which it declared success without running the tests. Gates are only as good as the reviewer, and an agent's final message is not evidence.
