6. Interrupts and Command: pausing for a person, routing from inside a node

An agent about to apply a patch, pay a refund or send an e-mail should sometimes ask first, and the answer may come tomorrow. Holding a process open for a day is fragile, so LangGraph pauses through the checkpoint: inside a node, interrupt(payload) raises a special exception, the runtime saves the state, and invoke returns with the payload (with 1.1's version="v2", in result.interrupts). Later, from any process, invoke(Command(resume=answer), config) loads the thread and runs the node again, and this time interrupt() returns the answer instead of raising. "The thread_id you choose is effectively your persistent cursor" ({{docs|https://docs.langchain.com/oss/python/langgraph/interrupts}}).

The trap is runs the node again, from its first line ("The graph resumes from the start of the node, re-executing all logic", interrupt's docstring). Every rule in the docs follows from that one fact, and each was checked here MEASURED:




Rules checked: two interrupts in one node are matched by order ("Matching is strictly index-based"); parallel interrupts are resumed together by interrupt id; a single plain value fails when several are pending; a bare try/except Exception swallows the interrupt and the node carries on; without a checkpointer the resume fails ("Cannot use Command(resume=...) without checkpointer"); response_schema (1.2.12) validates the resume value; interrupt_before is a breakpoint, not an approval.


Command carries these instructions. Command(resume=...) answers interrupts; returned from a node, Command(update={...}, goto="node") updates the state and picks the next node in one move (the node declares its possible destinations, add_node("triage", f, destinations=("billing", "tech")), so the graph can be drawn); goto may also be a Send or a list; graph=Command.PARENT sends the jump to the enclosing graph, which is how one agent hands over to another (section 8).


Static breakpoints, compile(interrupt_before=["apply"]), stop before a node with no code in it; resume with invoke(None, config). The docs keep them for debugging: "Static interrupts are not recommended for human-in-the-loop workflows." Time travel is the same machinery: get_state_history(config) lists every checkpoint; update_state(old_config, values, as_node=...) writes a new checkpoint whose parent is an old one (a fork); invoke(None, new_config) runs forward from it. messages, the mode for chat interfaces, yields each model token with the node and step that produced it; it needs a model, so it was measured on the create_agent run of section 9. Modes combine (stream_mode=["updates", "custom"] yields (mode, data) pairs), and subgraphs=True adds events from inside subgraphs with their namespace. Since 1.1, version="v2" makes every event a typed {"type", "ns", "data"} dictionary; since 1.2 the docs recommend event streaming (stream_events(..., version="v3"), beta) for new applications, one typed stream per model call ({{docs|https://docs.langchain.com/oss/python/langgraph/streaming}}; not run here).







8. Subgraphs and handoffs


A compiled graph can be a node of another, in two ways that behave differently on resume. Recorded: a parent graph (triage, fix_bug, apply) whose fix_bug is a two-node subgraph (locate, then patch, which calls interrupt()) MEASURED:




In both, the subgraph got its own checkpoints under a namespace (fix_bug:<task id>), so locate was not re-run on resume and get_state(config, subgraphs=True) showed the paused subgraph's state. The difference: called from inside a function, the parent's wrapper function ran twice, because the parent node is what resumes from its first line. Whether a subgraph keeps state between calls is set by compile(checkpointer=...) on it: None (default) inherits the parent's checkpointer for one call, True keeps state per thread, False keeps none ({{docs|https://docs.langchain.com/oss/python/langgraph/use-subgraphs}}).


Handoffs. A node inside a subgraph returned Command(goto="billing", graph=Command.PARENT, update={...}); the parent ran billing next and the final log was ["triage: refund question, handing off", "billing: handled"] MEASURED. That is the whole mechanism behind LangGraph's handoff pattern. The prebuilt langgraph-supervisor and langgraph-swarm packages still exist, but the supervisor README now says "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases" ({{langgraph-supervisor|https://github.com/langchain-ai/langgraph-supervisor-py}}); LangChain's multi-agent docs point to subagents as tools and to Deep Agents. When several agents help at all is {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}'s subject; its section 6 sets handoffs like this one against agents called as tools.
