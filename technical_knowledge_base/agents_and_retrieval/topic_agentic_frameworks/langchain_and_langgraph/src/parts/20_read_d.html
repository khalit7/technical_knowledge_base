6. Interrupts and Command: pausing for a person, and routing from inside a node

An agent about to apply a patch, pay a refund or send an e-mail should sometimes ask first, and the answer may come tomorrow. Holding a process open for a day is fragile, so LangGraph does it with the checkpoint: inside a node, interrupt(payload) raises a special exception, the runtime saves the state, and invoke returns with the payload (in the 1.1+ version="v2" format, in result.interrupts). Later, from any process, invoke(Command(resume=answer), config) loads the thread and runs the node again, and this time interrupt() returns the answer instead of raising. "The thread_id you choose is effectively your persistent cursor" ({{docs|https://docs.langchain.com/oss/python/langgraph/interrupts}}).

The key phrase is runs the node again: from its first line ("The graph resumes from the start of the node, re-executing all logic", interrupt's docstring). Command is the object that carries these instructions. Command(resume=...) answers interrupts; returned from a node, Command(update={...}, goto="node") updates the state and picks the next node in one move (the node must declare its possible destinations, for example add_node("triage", f, destinations=("billing", "tech")), so the graph can be drawn); goto may also be a Send or a list; and graph=Command.PARENT sends the jump to the enclosing graph, which is how one agent hands a conversation to another (section 8).


Static breakpoints, compile(interrupt_before=["apply"]), stop before a node without any code in it; resuming is invoke(None, config). The docs keep them for debugging: "Static interrupts are not recommended for human-in-the-loop workflows." Time travel uses the same machinery: get_state_history(config) lists every checkpoint; update_state(old_config, values, as_node=...) writes a new checkpoint whose parent is an old one (a fork), and invoke(None, new_config) runs forward from it. 8. Subgraphs and handoffs


A compiled graph can be a node of another graph. Two ways to do it, which behave differently on resume. Recorded: a parent graph (triage, fix_bug, apply) whose fix_bug is a two-node subgraph (locate, then patch, which calls interrupt()) MEASURED:




In both, the subgraph got its own checkpoints under a namespace (fix_bug:<task id>), so locate was not re-run on resume and get_state(config, subgraphs=True) showed the paused subgraph's own state. The difference: called from inside a function, the parent's wrapper function ran twice, because the parent node is what resumes from its first line. Whether a subgraph keeps state between calls is set by compile(checkpointer=...) on the subgraph: None (default) inherits the parent's checkpointer for one call, True keeps state per thread, False keeps none ({{docs|https://docs.langchain.com/oss/python/langgraph/use-subgraphs}}).


Handoffs. A node inside a subgraph returned Command(goto="billing", graph=Command.PARENT, update={...}); the parent ran billing next, and the final log was ["triage: refund question, handing off", "billing: handled"] MEASURED. That is the whole mechanism behind LangGraph's handoff pattern. The prebuilt langgraph-supervisor and langgraph-swarm packages still exist, but the supervisor README now says "We now recommend using the supervisor pattern directly via tools rather than this library for most use cases", and neither has had a release since December 2025 ({{langgraph-supervisor|https://github.com/langchain-ai/langgraph-supervisor-py}}); LangChain's multi-agent docs point to subagents as tools and to Deep Agents.
