4. Checkpointers: what is saved, where, and how big it gets

A checkpointer is what you pass to compile(checkpointer=...): it saves a checkpoint at every super-step boundary and the pending writes of every task in between. Without one the state lives only in the running process and interrupts cannot be resumed (section 6); with one, a thread's whole history is in a database, keyed by thread_id.

What one checkpoint holds (the Checkpoint type, langgraph-checkpoint 4.2.0): id (unique and increasing, so it sorts by time), ts, channel_values (the state plus trigger channels), channel_versions, versions_seen per node and updated_channels; beside it, metadata: source (input, loop, update or fork), step (-1 for the input checkpoint, then 0, 1, 2 ...), the parent checkpoint and the run id. Where it goes ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}): InMemorySaver (core package, "for experimentation"), SqliteSaver (langgraph-checkpoint-sqlite, "ideal for experimentation and local workflows"), PostgresSaver (langgraph-checkpoint-postgres, "used in LangSmith. Ideal for using in production"), plus separately packaged MongoDB and Azure Cosmos DB savers. Redis appears in the docs only as a store (section 10), not a checkpointer; the old version of this page listed it as a checkpointer backend. SQLite keeps the whole serialized state in each checkpoint row; Postgres keeps one row per channel per version, so an unchanged channel is not stored again MEASURED. Checkpoints hold every prompt, tool result and secret your agent saw: encrypt them (EncryptedSerializer, AES key from LANGGRAPH_AES_KEY).


The table schemas and the serializer, read from the databases after the runs


SQLite (3.1.1): two tables. checkpoints (thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint BLOB, metadata BLOB) and writes (thread_id, checkpoint_ns, checkpoint_id, task_id, idx, channel, type, value BLOB).


Postgres (3.1.2, Postgres 16 in Docker): four tables, created by setup() through 10 migrations. checkpoints (small JSONB rows), checkpoint_blobs (one row per channel per version), checkpoint_writes and checkpoint_migrations.


Values are serialized with JsonPlusSerializer (msgpack; pickle fallback off by default; LANGGRAPH_STRICT_MSGPACK=true restricts which classes may be rebuilt); EncryptedSerializer wraps it ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}).


Storage grows with the square of the run length


An agent's state is mostly its message list, and the list changes every step. A checkpoint stores the whole list each time, so N steps that each add about the same amount store about N(N+1)/2 steps' worth. The test: an agent-shaped graph with no model, 40 super-steps, each adding a tool call and a 1,000-character tool result, stored bytes read back after every step MEASURED. LangGraph 1.2 added a beta channel type, DeltaChannel, that stores only each step's new writes and rebuilds the value by replaying them:


add_messages stores the whole list every step; DeltaChannel stores only the new part








Stored bytes = checkpoint rows + blobs + writes, uncompressed (length() in SQLite, octet_length() in Postgres). Tool results are hex text, different every step, so compression would not hide the growth. get_state times are one call on the M1 Pro; Postgres times include the round trip into Docker. Script: src/code/e3_storage.py.


So for long threads keep the message list short (trim or summarise with middleware, section 9, or a {{context policy|n:3f15c17b0d0d811292cee46514370431}}), prune old checkpoints, or try DeltaChannel, whose docstring warns "The API and on-disk representation may change"; its price is on the read side, where reading the state replays writes.


Durability modes: when the checkpoint is written


invoke(..., durability=...) takes three values ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}): "sync" persists "synchronously before the next step starts"; "async", the default in the source, persists "asynchronously while the next step executes", with a "small risk" of losing a checkpoint in a crash; "exit" persists "only when graph execution exits", so "you cannot recover from system failures (like process crashes) mid-execution". The cost of each, on a one-node loop of 200 super-steps (best of 3) MEASURED:




Under half a millisecond per step on SQLite, against model calls of seconds: for agents sync is the safe choice and costs nothing that matters. exit is for short graphs where only the final state counts.







5. What survives a crash


A run can stop halfway because the process dies (a deploy, an out-of-memory kill), a node raises (a provider timeout), or a person has not answered yet (section 6). First without a model: run the tests, then two checks in parallel (0.5 s and 6 s), then merge; SIGKILL about 3 s into the parallel step, after the fast check returned and while the slow one runs; then a fresh process calls invoke(None, config) on the same thread. Every node logs when it runs MEASURED:




With a checkpointer writing each step, the fast check's result survived as a pending write and the resumed process ran only the slow check and the merge, as the docs promise: "When you resume graph execution from that super-step you don't re-run the successful nodes." An exception instead of a kill behaved the same (the database held the fast node's write plus an __error__ write, and only the failed node re-ran). With exit nothing had been saved: invoke(None) failed with EmptyInputError: Received no input for __start__, and the only option was to start over.

What a checkpointer does not do. It restarts nothing: a supervisor (a job queue, Kubernetes, the Agent Server of section 11) must notice the dead run and resume it with the same thread_id. It cannot save the call in flight, so the smaller your nodes, the less a crash costs. And it cannot make side effects safe: a node that sent an e-mail and died before its write was saved sends it again on resume. Per node, LangGraph adds RetryPolicy (defaults in 1.2.14: first wait 0.5 s, doubling, at most 128 s, 3 attempts in all, with jitter), TimeoutPolicy (1.2; run and idle timeouts, "Timeouts apply to async nodes only", {{1.2.0a6 notes|https://github.com/langchain-ai/langgraph/releases/tag/1.2.0a6}}) and error_handler (1.2; runs after the retries are exhausted and may return a Command, for compensation steps). The parent's {{Orchestration lab|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} tab, part "Durable execution", sets this checkpointer against Temporal-style event-history replay.
