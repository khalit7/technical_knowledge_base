4. Checkpointers: what is saved, where, and how big it gets

A checkpointer is the object you pass to compile(checkpointer=...); it saves a checkpoint at every super-step boundary and the pending writes of every task in between. Without one, the state lives only in the running process, and interrupts cannot be resumed (section 6). With one, a thread's whole history is in a database, keyed by thread_id.

What one checkpoint holds (the Checkpoint type in langgraph-checkpoint 4.2.0): id (unique and increasing, so it sorts by time), ts, channel_values (the state, plus trigger channels), channel_versions, versions_seen (per node) and updated_channels. Beside it sits metadata: source (input, loop, update or fork), step (-1 for the input checkpoint, then 0, 1, 2 ...), the parent checkpoint and the run id. Where it goes. The official list ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}): InMemorySaver (in the core package, "for experimentation"), SqliteSaver (langgraph-checkpoint-sqlite, "ideal for experimentation and local workflows"), PostgresSaver (langgraph-checkpoint-postgres, "used in LangSmith. Ideal for using in production"), and separately packaged MongoDB and Azure Cosmos DB savers. Redis appears in the docs only as a store (section 10), not a checkpointer: the old version of this page listed it as a checkpointer backend. The schemas, read from the two databases after the runs below MEASURED:


SQLite (3.1.1): two tables. checkpoints (thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint BLOB, metadata BLOB) and writes (thread_id, checkpoint_ns, checkpoint_id, task_id, idx, channel, type, value BLOB). Each checkpoint row holds the whole serialized state.


Postgres (3.1.2, Postgres 16 in Docker): four tables, created by setup() through 10 migrations. checkpoints (small JSONB rows), checkpoint_blobs (one row per channel per version, so an unchanged channel is not stored again), checkpoint_writes and checkpoint_migrations.


Values are serialized with JsonPlusSerializer (msgpack; pickle fallback off by default; LANGGRAPH_STRICT_MSGPACK=true restricts which classes may be rebuilt). An EncryptedSerializer encrypts everything with an AES key from LANGGRAPH_AES_KEY ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}): checkpoints hold every prompt, tool result and secret your agent saw.


Storage grows with the square of the run length


An agent's state is mostly its message list, and the message list changes every step. A checkpoint stores the whole list each time, so a run of N steps that adds about the same amount per step stores about N(N+1)/2 copies' worth. The test: an agent-shaped graph with no model, 40 super-steps, each adding a tool call and a 1,000-character tool result, stored bytes read back after every step MEASURED. LangGraph 1.2 added a beta channel type, DeltaChannel, that stores only each step's new writes and rebuilds the value by replaying them:










Stored bytes = checkpoint rows + blobs + writes, uncompressed (length() in SQLite, octet_length() in Postgres). Tool results are hex text, different every step, so compression would not hide the growth. get_state times are one call on the M1 Pro; Postgres times include the round trip into Docker. Script: src/code/e3_storage.py.


So for long agent threads, either keep the message list short (summarise or trim with middleware, section 9, or a {{context policy|n:3f15c17b0d0d811292cee46514370431}}), prune old checkpoints, or try DeltaChannel, whose docstring marks it beta: "The API and on-disk representation may change". Its price is on the read side: reading the state replays writes.


Durability modes: when the checkpoint is written


invoke(..., durability=...) takes one of three values ({{docs|https://docs.langchain.com/oss/python/langgraph/checkpointers}}): "sync" persists "synchronously before the next step starts"; "async", the default in the source, persists "asynchronously while the next step executes", with a "small risk" of losing a checkpoint in a crash; "exit" persists "only when graph execution exits", so "you cannot recover from system failures (like process crashes) mid-execution". A fraction of a millisecond per step against model calls of seconds: for agents the overhead does not matter, and sync is the safe choice. exit exists for short graphs where you only care about the final state.







5. What survives a crash


Three things can stop a run halfway: the process dies (a deploy, an out-of-memory kill, a laptop lid), a node raises (a provider timeout), or a person has not answered yet. The first two are tested here; the third is section 6.


A kill in the middle of a parallel step, no model. Graph: run the tests, then two checks in parallel (one 0.5 s, one 6 s), then merge. The process is sent SIGKILL about 3 s into the parallel step, after the fast check has returned and while the slow one is still running; a fresh process then calls invoke(None, config) on the same thread. Every node appends to a log when it runs, so we can see what ran where MEASURED:




With a checkpointer writing each step, the fast check's result survived as a pending write, and the resumed process ran only the slow check and the merge. The docs promise exactly this: "When a graph node fails mid-execution at a given super-step, LangGraph stores pending checkpoint writes from any other nodes that completed successfully at that super-step. When you resume graph execution from that super-step you don't re-run the successful nodes." The same happened when the slow node raised an exception instead of being killed: the database held the fast node's write plus an __error__ write, and the resume re-ran only the node that failed. With exit nothing had been saved, invoke(None) failed with EmptyInputError: Received no input for __start__, and the only option was to start over.


The same experiment with real model calls. The graph of section 2, each diagnosis a Claude Haiku 4.5 call through claude -p with every tool off, killed the moment the first diagnosis returned, then resumed, then approved at the interrupt. Once with sync, once with exit:




Bars are model calls to scale in seconds, one lane per process; the red line is the SIGKILL. A call cut by the kill (hatched) was in flight: its tokens may well have been billed, but no result came back and the recording has no usage for it. Call times overlap other agents' load on the same machine, so durations are indicative. Full transcripts and the replay: {{Crash lab|#t-crash}}.


What a checkpointer does not do. It does not restart anything: some supervisor (a job queue, Kubernetes, the Agent Server of section 11) must notice the dead run and call resume with the same thread_id. It cannot save the call that was in flight; the smaller your nodes, the less a crash costs. And it cannot make side effects safe: a node that sent an e-mail and then died before its write was saved will send it again on resume. Per node, LangGraph adds three knobs: RetryPolicy (defaults in 1.2.14: first wait 0.5 s, doubling, at most 128 s, 3 attempts in all, with jitter), TimeoutPolicy (1.2; run and idle timeouts, "Timeouts apply to async nodes only", {{1.2.0a6 notes|https://github.com/langchain-ai/langgraph/releases/tag/1.2.0a6}}), and error_handler (1.2; runs after the retries are exhausted and may return a Command, for compensation steps).
