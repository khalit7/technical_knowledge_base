The page in one screen

An agent run is a chain of model calls and tool calls that decide each other. When a run fails, costs too much or takes too long, its final answer does not say which step did it. Observability is the practice of recording enough about every step, while it runs, that you can answer questions you did not think to ask beforehand. For agents the record that works is a trace: one tree per run, with a timed node, a span, for every model call and every tool call.

Four questions keep coming back, and each needs something specific in the trace:

1. Traces and spans, from zero

The problem. The local agent run made model calls and 7 tool calls in a loop. Print a log line for each and you get a list. That list cannot tell you which model call asked for which tool, which calls belonged to which run when two runs interleave, or how long the run spent waiting on the model against running tools.

How a trace answers it. A span is one timed operation: it has a name, a start and end time, a parent span (or none, if it is the root), a status (unset, ok or error), attributes (key-value pairs such as the model name and token counts) and optional events (timestamped notes inside the span). All spans of one run share a 128-bit trace id, so they form one tree. The program creates spans through the OpenTelemetry API; an exporter ships finished spans over OTLP (the OpenTelemetry protocol) to a collector (a separate program that can filter, redact, sample and forward) or straight to a backend that stores and draws them (Langfuse, Jaeger, Datadog and many others).

Step through the same recorded run three ways. Logs is what you get from print statements. Auto spans is what a popular auto-instrumentation package gives you for free: one span per model call, each in a trace of its own. Agent trace is what you want: one root span for the run, a child for each model call and each tool call.

Timings are the real run's: each model call's bar is how long the shared local server took to answer it (other agents' load varied, so call 4 took 78 s). Tool calls took milliseconds and are drawn at a minimum width. Token counts are the server's.

Across processes. A trace does not stop at the edge of your program. W3C Trace Context defines a header, traceparent, that carries the trace id and the parent span id from one process to the next. Claude Code reads it from a TRACEPARENT environment variable in claude -p and Agent SDK sessions, and hands its own context to every Bash subprocess in the same variable (Claude Code monitoring docs). We used both: a small "application" opened a span for a ticket, started Claude Code under it, and a python3 wrapper on the PATH turned the inherited TRACEPARENT into a span for the test runner. The result, measured MEASURED:

One trace id, three services, spans: the ticket and the agent invocation from the application, Claude Code's interaction, model requests and tool spans, and two process tests/test_core.py spans from the test runner, each parented under the claude_code.tool.execution span of the Bash call that started it. Nobody had to share a database or a request id; the context travelled in an environment variable. How the header is built byte by byte, and what goes wrong when a hop drops it, is on Observability: logs, metrics, traces, alerting.

Predict, then open. The Claude Code run fixed both bugs and its result says success. Yet two of its spans have status ERROR. What were they?
A Read of a directory (EISDIR, at 10.6 s) and a test run that exited non-zero (ShellError, at 19.0 s). Both are normal in an agent: a failed test run is how the agent learns what is wrong. Span status describes one operation, not the run's outcome. Section 7 shows what this does to error-based sampling.

2. The OpenTelemetry GenAI conventions, attribute by attribute

The problem. A trace is only useful across tools if everyone names things the same way. If one library writes the model under model, another under llm.model_name and a third under gen_ai.request.model, a backend cannot compute cost or group by model without a mapping for each. OpenTelemetry's semantic conventions are the agreed names; the GenAI conventions are the part for model calls, agents and tools.

Where they live and how stable they are. In 2026 they moved out of the main conventions repository into their own, open-telemetry/semantic-conventions-genai. This page pins commit cb10b70 (5 Oct 2026) and reads the machine-readable model files (spans.yaml, registry.yaml, metrics.yaml), not the prose. Its manifest declares stability: development and schema gen-ai-dev/1.42.0-dev, built on the main conventions v1.44.0. "Development" means names can still change without a deprecation period; instrumentation packages that already follow the latest draft ask you to opt in with OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental (see the research notes in src/inputs/research.md) SOURCE.

Span types. The model defines span types and values of gen_ai.operation.name. Three of them carry an agent run:

The others cover the rest of an LLM application: create_agent, invoke_workflow (a multi-agent or multi-step workflow), plan, retrieval, embeddings, fetch_response (reading a stored response back), and memory operations (search_memory, create_memory and five more). Explore any of them:

Three rules that matter in practice.

  • Requirement levels. On an inference span only gen_ai.operation.name and gen_ai.provider.name are required; gen_ai.request.model is required "if available"; token counts are only recommended. A span can follow the conventions and still be useless for cost.
  • Sampling-relevant attributes (marked S) should be set when the span is created, not when it ends, because a head sampler (one that decides at span start, section 7) only sees what exists at that moment. For an inference span these are the operation, provider, model, server address and port.
  • Content is opt-in. The system instructions, input and output messages, tool definitions, and a tool call's arguments and result are all opt_in: by default the conventions record that a call happened, not what was said. Section 8 measures which libraries respect that.

Counting tokens. The registry says gen_ai.usage.input_tokens "SHOULD include all types of input tokens, including cached tokens", with gen_ai.usage.cache_read.input_tokens and gen_ai.usage.cache_write.input_tokens as subsets of it. Anthropic's API counts differently, so the Anthropic section adds: "Anthropic input_tokens excludes cached tokens. Compute: gen_ai.usage.input_tokens = input_tokens + cache_read_input_tokens + cache_write_input_tokens". On the first model call of our Claude Code run that is the difference between two very different numbers:

Other attributes worth knowing. gen_ai.conversation.id groups the calls of one multi-turn conversation (Langfuse turns it into a session, measured below); gen_ai.prompt.name and gen_ai.prompt.version record which version of a managed prompt produced a call (the link a prompt registry needs); gen_ai.conversation.compacted marks a call made after the history was compacted; gen_ai.request.reasoning.level carries an effort setting.

Metrics. The same commit defines histograms, among them gen_ai.client.operation.duration, gen_ai.invoke_agent.duration, gen_ai.invoke_agent.inference_calls and gen_ai.invoke_agent.tool_calls. The last two are the ones to alert on for agents: a jump in model calls per run is the earliest sign of an agent looping. Token usage metrics are in a separate token-metrics.yaml.

The names are still moving
The provider attribute used to be gen_ai.system; it is now gen_ai.provider.name, and gen_ai.system does not appear in this repository's registry at the pinned commit. In our runs, opentelemetry-instrumentation-openai-v2 2.4b0 still writes only gen_ai.system (so its spans miss a required attribute), Pydantic AI writes both, Claude Code 2.1.291 writes gen_ai.system plus its own token names (input_tokens, cache_read_tokens, cache_creation_tokens), and OpenInference uses a different convention altogether (llm.token_count.prompt, input.value) MEASURED. Check what your backend maps before trusting a dashboard; section 6 is what happens when you do not.

3. Instrumenting an agent: by hand, automatically, or by the framework

The three ways. Manual instrumentation is code you write: open a span, set attributes, close it. Auto-instrumentation is a package that patches a client library (here the openai Python client) so every call it makes produces a span, with no change to your code. Framework-native instrumentation is built into an agent framework, which knows where its own runs and tool calls begin and end.

We replayed the identical recorded run through the same loop eight ways: hand-written spans with and without content, OpenTelemetry's own opentelemetry-instrumentation-openai-v2 with and without its content switch, Traceloop's OpenLLMetry, Arize's OpenInference, Langfuse's drop-in OpenAI client, and the same agent rewritten in Pydantic AI with its built-in instrumentation. All sent their spans both to a local file and to the self-hosted Langfuse MEASURED:

"Model calls / tools / root": spans of each kind. "Traces": how many trace ids the one run was split into. "Fake PII": occurrences of the fake customer's e-mail and account id in span attributes (and, for openai-v2, in its log events). "KB": total attribute size, a proxy for storage cost. "Langfuse": the observation types Langfuse stored. Every span, attribute by attribute: tab Eight instrumentations.

What the table says.

  • Auto-instrumenting the model client does not give you an agent trace. All four client-level packages produced separate traces of one span each: no run, no tool calls, nothing linking call 3 to call 4. The agent structure only appears when something that knows about the loop opens the root and the tool spans: your code, or a framework (Pydantic AI produced the same 16-span tree as our hand-written version).
  • Content defaults differ, and the difference is the privacy policy. The GenAI conventions make content opt-in, and openai-v2 obeys: by default it records no message text. With its content switch on, the text went into log events, not span attributes. OpenLLMetry, OpenInference, Langfuse's client and Pydantic AI all record prompts and completions by default (OpenLLMetry documents TRACELOOP_TRACE_CONTENT=false to stop it; Pydantic AI's InstrumentationSettings(include_content=True) is the default).
  • Size follows content. The same run cost KB of attributes without content and KB with it by hand; OpenInference, which writes the messages twice (as one JSON blob in input.value and flattened into one attribute per message field), reached KB.
  • Cached tokens are hit and miss. The local server reported prompt-cache hits (cached_tokens). OpenLLMetry, OpenInference, Langfuse and Pydantic AI recorded them; openai-v2 and our first hand-written version did not, so a backend would price those tokens as fresh input.

Why you want content somewhere. A trace with the messages is how you check what a framework really sends. The sibling page LangChain and LangGraph recorded create_agent's first request and found it is exactly your system prompt, the user message and the tool schemas, with nothing added; the parent's Same agent, six ways tab found Pydantic AI's structured output arrives through an added final_result tool (details on Typed agent libraries) and smolagents sends a 2,231-token system prompt of its own. Those findings came from logging the requests; with content capture on, your tracing backend shows the same thing for every run.

What to do. Use auto-instrumentation for the model client (it captures parameters, tokens and errors you would forget) and add the agent skeleton yourself: one invoke_agent span around the run and one execute_tool span around each tool call, both with the conventions' names, so the client spans nest under them. If a framework already does it, as Pydantic AI does, use that. Decide content capture deliberately, per environment: on in evaluation runs, where graders need the arguments and results; off or redacted in production.

4. Langfuse, self-hosted, fed by every variant

What it is. Langfuse is an open-source platform for tracing, evaluating and managing prompts of LLM applications: MIT-licensed except its ee/ folders (LICENSE). ClickHouse announced it had acquired Langfuse on 16 January 2026, saying it "stays open source and self-hostable" (ClickHouse blog). Version 4 became generally available on 17 August 2026 (changelog); the latest release when we ran it was 4.53.0, published that morning (releases) SOURCE.

What it took to run. Langfuse's own Docker Compose file at tag v4.53.0, ports moved to localhost: six containers (web, worker, ClickHouse 25.12, Postgres 17, Redis 7, MinIO for S3-style blob storage), about GB of images, and GiB of memory at rest after ingesting this page's traces MEASURED. Postgres holds users, projects, prompts and datasets; ClickHouse holds the observations; Redis is the queue between web and worker; blob storage keeps raw events. That is the main cost of "self-hostable": you operate a column store.

The data model. A trace is one request or run; it contains observations, typed as span, generation (a model call), event, agent, tool, chain, retriever, evaluator, embedding or guardrail (observation types). Traces group into sessions and are attributed to users; scores attach to traces or observations. Version 4 rebuilt storage around one wide, mostly immutable ClickHouse table, in which "traces are represented as root spans within the same table instead of a separate entity", and replaced the old batch ingestion API with OpenTelemetry (v3 to v4 upgrade guide). We saw it directly: on the default events_only deployment, the old GET /api/public/traces, /observations and /scores endpoints answer 404 with "This endpoint is not available on deployments running in Langfuse v4 events_only mode", while /api/public/v2/observations and /api/public/v3/scores work MEASURED.

How OpenTelemetry spans become observations. Langfuse accepts OTLP at /api/public/otel with the project's public and secret key as HTTP Basic auth. Its mapping, from its docs: the observation type comes from langfuse.observation.type, then gen_ai.operation.name, then "model present means generation"; the model from gen_ai.request.model, llm.model_name or model; usage from gen_ai.usage.* or llm.token_count.* (OpenTelemetry integration). What it stored from our eight variants MEASURED:

Every variant's model calls became generations with the model and token counts, including OpenInference's llm.* names and Langfuse's own langfuse.observation.* attributes. Langfuse also split cached tokens out of the input into a separate input_cached_tokens bucket (its usage keys are non-overlapping: "each token must be counted in exactly one key", docs). Our hand-written gen_ai.conversation.id became the session id, and Pydantic AI's became a session too. No cost was computed for any of them: Langfuse has no price for a local model, which is correct. The Claude Code run in section 6 is where prices come in.

Telemetry loss is silent
On the first attempt, two of the eight variants (openai-v2 and Pydantic AI) lost every span: Langfuse, still warming up, answered their exports with HTTP 500 ("stream is not readable", 12 times in its log). The agents finished normally; the only trace of the failure was one exporter warning on standard error, "Failed to export spans batch due to timeout, max retries or shutdown". The reruns were ingested MEASURED. Watch the exporter's own metrics, or put a collector with a retry queue between your app and the backend.

Langfuse's other halves (from its docs, used only where marked): scores and datasets (section 9, measured); LLM-as-a-judge evaluators that run on observations as they arrive ("observation-level evaluators are the recommended target for live production data; trace-level evaluators are deprecated", docs); prompt management, where labels such as production and staging point at prompt versions and an unlabelled fetch serves production (docs); masking in the SDK before export (mask_otel_spans in the Python SDK v4); and sampling in the SDK (sample_rate, decided per trace).

With a gateway. If your model calls already go through LiteLLM, its langfuse_otel callback sends a GenAI span per request to the same endpoint with usage and cost, and LiteLLM now recommends it over the older langfuse callback (LiteLLM docs) SOURCE. Gateway spans see every request but not the agent around it; app spans see the agent. Run both and join them on the trace id. Gateways in depth: Gateways and routing.

6. Cost attribution: from spans to dollars, reconciled

The problem. The bill says what you spent; it does not say which agent, user, feature or step spent it. A trace can, if each model span carries the model and the token counts by kind, and the backend multiplies them by the right prices. Two things go wrong in practice: the counts arrive under names the backend does not read, and the prices the backend applies are not the ones you paid.

The experiment. The Claude Code run reported total_cost_usd = for turns (an API-price equivalent; the subscription paid). We sent its recorded trace to Langfuse three times through a collector, changing only how the token counts were labelled MEASURED:

Three independent totals agree. The run's own total_cost_usd, Langfuse's sum over generations once the counts carried their cache duration, and Claude Code's claude_code.cost.usage metric (delta temporality, summed over its exports) all give . The formula, with Haiku 4.5's list prices per million tokens (input $1, 1-hour cache write $2, cache read $0.10, output $5; Anthropic pricing):

cost = ( × 1 + × 2 + × 0.10 + × 5) / 106 = $

The 16% gap in the middle step is cache-write tokens priced at the 5-minute rate (1.25x) instead of the 1-hour rate (2x) that Claude Code used on these runs (ephemeral_1h_input_tokens in its usage, and in the shared facts for the agent pages). The GenAI conventions have one cache_write count and no field for the cache's lifetime, so a backend that follows them faithfully must guess; Langfuse's model table has separate input_cache_creation_5m and _1h prices, so passing the count under the explicit key fixed it. An open Langfuse issue reports the same mispricing from its LangChain integration (#17450).

Rolling cost up. Once each model span has a correct cost, attribution is a group-by over the trace: by the root's attributes for user, ticket and feature (our application set app.user, app.ticket, app.feature on its span), by gen_ai.conversation.id for a session, by span name for a step. Langfuse propagates user, session and tags to every observation when you set them with propagate_attributes() (its v4 SDK). Reconcile against a second source: the gateway's spend log, the provider's invoice, or, as here, the harness's own metric. Two sources that disagree by a fixed ratio usually mean a price or a token kind is wrong, as in step 2 above.

7. Sampling agent traces

The problem. Keeping every trace costs storage and money, and with content on a single run of our small task was 30 to 100 KB of attributes. Sampling keeps a subset. Head sampling decides when the root span starts (usually "keep 10% of trace ids") and is cheap, but cannot know whether the run will fail. Tail sampling decides after seeing the spans, so it can keep every failure; in OpenTelemetry it is the collector's tail_sampling processor, which holds a trace's spans in memory for decision_wait (30 s by default) after the first one arrives, evaluates its policies once, and then forwards or drops (processor README at v0.162.0). The general mechanics are on Observability: logs, metrics, traces, alerting; here is what is different about agents.

Agent traces break three assumptions. They are long (minutes, hours for some harnesses), so a fixed wait decides before the run ends. Their root span ends last, so the outcome arrives last. And their spans fail routinely: our successful Claude Code run already had two ERROR spans (section 1). We replayed that run's 49 spans into a real collector at their recorded end times (29 s from first to last), after marking its final tool execution and its root as failed, through four tail-sampling setups that all keep "any trace with an ERROR span" MEASURED:

With a 5-second wait the collector decided before the first error span arrived (6.35 s into the replay) and dropped the trace; every later span, the failures included, followed that decision. With a 60-second wait the whole trace was kept, but only emitted 61 s after it started, and every trace in flight sits in memory that long. The setting made for this case is decision_wait_after_root_received: wait as long as you like (300 s here), but decide shortly (2 s) after the root span arrives. It kept the trace and emitted it 33 s in, 4 s after the root.

And the policy must look at the run, not at any span. We replayed the same trace twice more, once marked failed and once exactly as recorded (a success with two recoverable errors), through two policies that both wait for the root MEASURED:

PolicyFailed runSuccessful run
status_code: [ERROR] on any span (kept, wrongly)
ottl_condition: IsRootSpan() and span.status.code == STATUS_CODE_ERROR

The application has to say whether the run failed, on the root span: an ERROR status or an attribute such as app.outcome. Our first attempt at the root condition, parent_span_id.string == "", matched nothing and raised no error (the policy's error_mode: ignore swallowed it); only the empty output file showed it. Test a sampling policy with a known failing trace before you trust it.

Soft failures need scores, not status. The worst agent failures end with status OK: the tests pass but the agent edited the tests, or the answer is wrong. No status-based rule keeps those. Keep a small random share of everything (so you can estimate rates), every run whose root says failed, and every run an online evaluator scored low (section 9); count runs with metrics, which are computed before sampling. Langfuse's SDK can also sample, per trace, with sample_rate (docs).

8. Personal data and secrets in traces

The problem. A trace with content holds every prompt, every tool argument and every tool result. In an agent that means customer messages, file contents, shell output and the paths of the machine it ran on, copied to a second system with its own access rules and retention. Prompts were opt-in in the conventions for exactly this reason.

What leaked in our runs MEASURED:

  • Libraries that capture content by default put the fake customer's e-mail and account id into every model span of the run (section 3's table): OpenLLMetry, OpenInference, Langfuse's client and Pydantic AI. openai-v2 and our hand-written spans did not until we turned content on.
  • Claude Code by default redacts the prompt (user_prompt = <REDACTED>), tool inputs and tool output, but puts the account identity on every span: user.email, user.account_uuid, user.id and organization.id were on all of its spans. The docs say user.email and organization.id are "always included when available"; the OTEL_METRICS_INCLUDE_* switches cover only session id, account uuid, version, entrypoint and repository (see src/inputs/research.md). If a trace leaves the developer's machine, that is personal data in every span.
  • With Claude Code's content switches on (OTEL_LOG_USER_PROMPTS=1, OTEL_LOG_TOOL_DETAILS=1, OTEL_LOG_TOOL_CONTENT=1), the prompt with the customer's e-mail appeared on the interaction span, file paths on tool spans, and tool.output span events held file contents, diffs and shell output. The operating-system login name appeared times outside the identity attributes: in absolute file paths (the working folder sits under the home folder) and in the output of an ls -la the agent ran, where the file-owner column is the login name. The content-on trace carried % more attribute bytes than the default run's (52 spans against 49).

Where to remove it, in order of preference. (1) Do not capture it: leave content off in production and turn it on per environment. (2) Mask in the SDK before export (Langfuse's mask_otel_spans, a custom span processor), which only covers that SDK's spans. (3) Redact in a collector you control, before data leaves your network, which covers every service at once. What the measurement says. Masking by pattern caught every e-mail, the account ids and every path, in span attributes and in span event attributes alike, and still missed the login name in ls -la output, because no pattern described it. A keyed hash (hmac-sha256) does the same job while keeping values joinable: the same e-mail always becomes the same digest, so you can still count one customer's runs. The allow-list of keys removed everything not on the list ( attributes on the Claude Code trace) and left nothing to leak, at the price of the content you wanted to debug with. A deny-list fails open on whatever you did not think of; an allow-list fails closed. In production, use the allow-list and keep full content only where access is controlled and retention is short. The attack side of the same problem (prompt injection, exfiltration through tools) is on Agent security.

9. Evals in the loop

The idea. Traces are the raw material for evaluation. Online evaluation scores a sample of production traces as they arrive, with code checks where they can decide and a model judge where they cannot, and writes the result back onto the trace as a score. Offline evaluation reruns a fixed dataset of tasks before every change; interesting production traces get promoted into that dataset. The same trace store serves debugging, monitoring and regression testing, which is the main argument for an integrated platform over plain OpenTelemetry.

What we ran. A 55-line scorer read each run's outcome and wrote four rule-based scores to Langfuse through its API (tests_pass, summary_complete, turns, and cost_usd for the Claude run), then read scores back from /api/public/v3/scores. We also created a dataset and promoted the local run's trace into it as an item with sourceTraceId set and an expected output MEASURED.

A rule that passed a summary it should have failed
The local model fixed both bugs but its final message describes only the tokenize change; it mentions the second one only as a test name ("including the apostrophes test, ties handling"). Our keyword rule looked for "tie" and scored the summary complete. Cheap checks drift from what they mean; check them against labelled cases (here: the diff contains two changes, the summary names one), and use a judge or a stricter structured check where a keyword cannot decide.

Making it a loop. Sample live traces for scoring (vendor docs suggest 1 to 10% for high volume, more for critical paths, and the judge bill is a budget line: figures on Production eval engineering); alert on score rates and on the agent metrics from section 2 (model calls and tool calls per run, cost per run, p95 duration); promote failures to the dataset; gate every prompt, model, tool or harness change on that dataset. The parent's Production stack tab runs a small gate over 18 recorded runs. How to grade a trajectory rather than a final answer: Agent and trajectory evaluation; judge design and biases: LLM-as-judge; alert design: Observability: logs, metrics, traces, alerting.

Common mistakes

Turning on client auto-instrumentation and calling it agent tracing
It gives one trace per model call (section 3). Add the invoke_agent and execute_tool spans yourself or use a framework that does.
Reading Anthropic's input_tokens as the input size
It excludes cache reads and writes. On our first Claude Code call it was tokens out of . The GenAI value is the sum (section 2).
Trusting a backend's cost without reconciling it
Our first two Langfuse totals were $0 and 16% short, both silently (section 6). Compare with a second source on every model you use.
Error-based tail sampling on agent traces
Successful runs have ERROR spans; long runs outlive decision_wait. Decide on the root's outcome after the root arrives (section 7).
Assuming content is off by default
The conventions say opt-in; four of the five instrumentation libraries we ran capture it by default, and Claude Code adds the account e-mail to every span regardless (section 8).
Redacting with a deny-list only
Patterns catch what you anticipated. The login name in ls -la output got through ours. Allow-list keys for anything leaving your network.
Not noticing lost telemetry
Exporters drop data on errors and print a warning; the application carries on (section 4). Monitor the exporter or the collector's own metrics.
Double-counting usage on parent spans
If the agent span carries the run's total tokens under the same names as the model spans, a backend that sums all spans counts them twice. Pydantic AI writes the totals on its agent span as gen_ai.aggregated_usage.* for this reason (its use_aggregated_usage_attribute_names setting, default on).

Interview questions

What is the difference between a trace, a span and an event?
A trace is one run (all spans sharing a trace id); a span is one timed operation in it with a parent, attributes and status; an event is a timestamped record inside a span (Claude Code puts tool output in a tool.output event).
How do you get one trace across your app, an agent subprocess and the tools it runs?
Propagate W3C trace context: inject traceparent into the child's environment or headers and extract it there. Claude Code reads TRACEPARENT in -p and SDK sessions and passes it to Bash subprocesses (section 1).
Which GenAI attributes are required on a model-call span, and which do you need for cost?
Required: gen_ai.operation.name and gen_ai.provider.name (model if available). For cost: the model and the token counts by kind (input including cache, cache read, cache write, output) plus the cache lifetime where prices differ.
Head or tail sampling for agents?
Tail, deciding on the root span's outcome shortly after the root arrives, plus a small random share; count with metrics computed before sampling.
How do you keep personal data out of traces?
Content off by default, on per environment; SDK masking; a collector with an allow-list of keys (or keyed hashing where you need joins) before data leaves your network; short retention and access control where full content is kept.
Your trace tool says a run cost $0.035 and the bill says $0.042. Where do you look?
Token kinds and prices: cache writes priced at the wrong lifetime (our case), cache reads counted as fresh, a model name that does not match a price entry, or missing spans (sampled or lost).
What does an online evaluator add over tracing?
Quality: a trace shows what happened; a score says whether it was good. Scores catch soft failures that end with status OK, drive sampling and alerts, and select traces to promote into the regression set.
Langfuse or LangSmith?
Langfuse if you need to self-host without an Enterprise contract or want MIT; LangSmith if LangGraph is your runtime and a hosted service is fine. Instrument with OpenTelemetry either way.

Where openai-v2 put content

Findings

  • Only the hand-written version and Pydantic AI produced one trace with an invoke_agent root and execute_tool children; Langfuse then typed them as agent, generation and tool observations.
  • openai-v2 2.4b0 misses the required gen_ai.provider.name (it writes the older gen_ai.system) and has no content by default; with its content switch on, the messages went to log events rather than span attributes, which a traces-only backend never receives.
  • OpenLLMetry wrote the newer GenAI names, including gen_ai.usage.cache_read.input_tokens, plus its own extras (gen_ai.openai.api_base, the server's system_fingerprint, which here named the server's OS version).
  • Pydantic AI put run totals on its agent span as gen_ai.aggregated_usage.*, so a backend summing gen_ai.usage.* over all spans does not double count, and records the full message history on the agent span (pydantic_ai.all_messages).

Late spans: in our runs the collector still held the trace's decision in memory, so spans arriving after a "drop" were dropped too, with or without the decision cache.
