The page in one screen

An agent run is a chain of model calls and tool calls that decide each other. When a run fails, costs too much or takes too long, its final answer does not say which step did it. Observability is the practice of recording enough about every step, while it runs, that you can answer questions you did not think to ask beforehand. For agents the record that works is a trace: one tree per run, with a timed node, a span, for every model call and every tool call.

Four questions keep coming back, and each needs something specific in the trace:

1. Traces and spans, from zero

The problem. The local agent run made model calls and 7 tool calls in a loop. Print a log line for each and you get a list. That list cannot tell you which model call asked for which tool, which calls belonged to which run when two runs interleave, or how long the run spent waiting on the model against running tools.

How a trace answers it. A span is one timed operation: it has a name, a start and end time, a parent span (or none, if it is the root), a status (unset, ok or error), attributes (key-value pairs such as the model name and token counts) and optional events (timestamped notes inside the span). All spans of one run share a 128-bit trace id, so they form one tree. The program creates spans through the OpenTelemetry API; an exporter ships finished spans over OTLP (the OpenTelemetry protocol) to a collector (a separate program that can filter, redact, sample and forward) or straight to a backend that stores and draws them (Langfuse, Jaeger, Datadog and many others).

Step through the same recorded run three ways. Logs is what you get from print statements. Auto spans is what a popular auto-instrumentation package gives you for free: one span per model call, each in a trace of its own. Agent trace is what you want: one root span for the run, a child for each model call and each tool call.

Timings are the real run's: each model call's bar is how long the shared local server took to answer it (other agents' load varied, so call 4 took 78 s). Tool calls took milliseconds and are drawn at a minimum width. Token counts are the server's.

Across processes. A trace does not stop at the edge of your program. W3C Trace Context defines a header, traceparent, that carries the trace id and the parent span id from one process to the next. Claude Code reads it from a TRACEPARENT environment variable in claude -p and Agent SDK sessions, and hands its own context to every Bash subprocess in the same variable ({{Claude Code monitoring docs|https://code.claude.com/docs/en/monitoring-usage}}). We used both: a small "application" opened a span for a ticket, started Claude Code under it, and a python3 wrapper on the PATH turned the inherited TRACEPARENT into a span for the test runner. The result, measured MEASURED:

One trace id, three services, spans: the ticket and the agent invocation from the application, Claude Code's interaction, model requests and tool spans, and two process tests/test_core.py spans from the test runner, each parented under the claude_code.tool.execution span of the Bash call that started it. Nobody had to share a database or a request id; the context travelled in an environment variable. How the header is built byte by byte, and what goes wrong when a hop drops it, is on {{Observability: logs, metrics, traces, alerting|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.

Predict, then open. The Claude Code run fixed both bugs and its result says success. Yet two of its spans have status ERROR. What were they?
A Read of a directory (EISDIR, at 10.6 s) and a test run that exited non-zero (ShellError, at 19.0 s). Both are normal in an agent: a failed test run is how the agent learns what is wrong. Span status describes one operation, not the run's outcome. Section 7 shows what this does to error-based sampling.
