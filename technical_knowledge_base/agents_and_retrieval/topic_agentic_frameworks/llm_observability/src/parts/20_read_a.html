The idea in one screen

Record every agent run as one trace: a tree of timed spans, one for the run, one for each model call and one for each tool call. Everything else on this page (cost, sampling, redaction, scores) reads the attributes on those spans, so what you put on them decides what you can answer later.

Why: a run's final answer does not say which step failed, cost too much or took too long. Observability means recording enough about every step, while it runs, to answer questions you did not think to ask beforehand.

span
one timed operation: name, start and end, parent, status, attributes, events
trace
all spans sharing one 128-bit trace id: one tree per run
GenAI conventions
OpenTelemetry's agreed attribute names for model calls, agents and tools (gen_ai.*)
collector
a separate OpenTelemetry process that receives spans over OTLP and can sample, redact, rename and forward them
generation, observation
Langfuse's names: an observation is any node of its trace; a generation is a model call
head, tail sampling
keep or drop a trace when it starts (cheap, blind), or after its spans arrive (can keep failures)
score
a number or label an evaluator (a rule, a model judge or a person) writes back onto a trace

1. Traces and spans

The problem. The local run made model calls and 7 tool calls in a loop. A log line per call gives a list that cannot say which model call asked for which tool, which calls belonged to which run when two runs interleave, or how long the run waited on the model against running tools.

How a trace answers it. Each span has a name, a start and end time, a parent span (none for the root), a status (unset, ok or error), attributes (key-value pairs such as the model name and token counts) and optional events (timestamped notes inside the span). The program creates spans through the OpenTelemetry API; an exporter ships finished spans over OTLP (the OpenTelemetry protocol) to a collector or straight to a backend that stores and draws them (Langfuse, Jaeger, Datadog and many others). Predict before stepping: what does a popular client auto-instrumentation give you for this run? Then step through the same recorded run three ways.

Logs: print statements. Auto spans: one span per model call, each in a trace of its own. Agent trace: one root span for the run, a child for each model call and each tool call. Timings are the real run's: each model call's bar is how long the shared local server took to answer it (other agents' load varied, so call 4 took 78 s). Tool calls took milliseconds and are drawn at a minimum width. Token counts are the server's.

Across processes. W3C Trace Context carries the trace id and the parent span id from one process to the next in a header, traceparent. Claude Code reads it from a TRACEPARENT environment variable in claude -p and Agent SDK sessions, and hands its own context to every Bash subprocess in the same variable ({{Claude Code monitoring docs|https://code.claude.com/docs/en/monitoring-usage}}). A small "application" opened a span for a ticket and started Claude Code under it; a python3 wrapper on the PATH turned the inherited TRACEPARENT into a span for the test runner MEASURED:

One trace id, three services, spans: the ticket and the agent invocation from the application, Claude Code's interaction, model requests and tool spans, and two process tests/test_core.py spans from the test runner, each under the claude_code.tool.execution span of the Bash call that started it. No shared database or request id; the context travelled in an environment variable. The header byte by byte, and what goes wrong when a hop drops it: {{Observability: logs, metrics, traces, alerting|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}.

Predict, then open. The Claude Code run fixed both bugs and its result says success. Yet two of its spans have status ERROR. What were they?
A Read of a directory (EISDIR, at 10.6 s) and a test run that exited non-zero (ShellError, at 19.0 s). Both are normal in an agent: a failed test run is how the agent learns what is wrong. Span status describes one operation, not the run's outcome. Section 7 shows what this does to error-based sampling. When everything fails, put a typed error on the root span, with the same trace id the user's request had, so the incident is one query away.
