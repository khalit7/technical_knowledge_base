7. Sampling agent traces

The problem. Keeping every trace costs storage and money, and with content on a single run of our small task was 30 to 100 KB of attributes. Sampling keeps a subset. Head sampling decides when the root span starts (usually "keep 10% of trace ids") and is cheap, but cannot know whether the run will fail. Tail sampling decides after seeing the spans, so it can keep every failure; in OpenTelemetry it is the collector's tail_sampling processor, which holds a trace's spans in memory for decision_wait (30 s by default) after the first one arrives, evaluates its policies once, and then forwards or drops ({{processor README at v0.162.0|https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.162.0/processor/tailsamplingprocessor}}). The general mechanics are on {{Observability: logs, metrics, traces, alerting|n:3ef5c17b0d0d811e8490c54dd42c2b9b}}; here is what is different about agents.

Agent traces break three assumptions. They are long (minutes, hours for some harnesses), so a fixed wait decides before the run ends. Their root span ends last, so the outcome arrives last. And their spans fail routinely: our successful Claude Code run already had two ERROR spans (section 1). We replayed that run's 49 spans into a real collector at their recorded end times (29 s from first to last), after marking its final tool execution and its root as failed, through four tail-sampling setups that all keep "any trace with an ERROR span" MEASURED:

With a 5-second wait the collector decided before the first error span arrived (6.35 s into the replay) and dropped the trace; every later span, the failures included, followed that decision. With a 60-second wait the whole trace was kept, but only emitted 61 s after it started, and every trace in flight sits in memory that long. The setting made for this case is decision_wait_after_root_received: wait as long as you like (300 s here), but decide shortly (2 s) after the root span arrives. It kept the trace and emitted it 33 s in, 4 s after the root.

And the policy must look at the run, not at any span. We replayed the same trace twice more, once marked failed and once exactly as recorded (a success with two recoverable errors), through two policies that both wait for the root MEASURED:

PolicyFailed runSuccessful run
status_code: [ERROR] on any span (kept, wrongly)

The application has to say whether the run failed, on the root span: an ERROR status or an attribute such as app.outcome. Our first attempt at the root condition, parent_span_id.string == "", matched nothing and raised no error (the policy's error_mode: ignore swallowed it); only the empty output file showed it. Test a sampling policy with a known failing trace before you trust it.

Soft failures need scores, not status. The worst agent failures end with status OK: the tests pass but the agent edited the tests, or the answer is wrong. No status-based rule keeps those. Keep a small random share of everything (so you can estimate rates), every run whose root says failed, and every run an online evaluator scored low (section 9); count runs with metrics, which are computed before sampling. Langfuse's SDK can also sample, per trace, with sample_rate ({{docs|https://langfuse.com/docs/observability/features/sampling}}).

8. Personal data and secrets in traces

The problem. A trace with content holds every prompt, every tool argument and every tool result. In an agent that means customer messages, file contents, shell output and the paths of the machine it ran on, copied to a second system with its own access rules and retention. Prompts were opt-in in the conventions for exactly this reason.

What leaked in our runs MEASURED:

  • Libraries that capture content by default put the fake customer's e-mail and account id into every model span of the run (section 3's table): OpenLLMetry, OpenInference, Langfuse's client and Pydantic AI. openai-v2 and our hand-written spans did not until we turned content on.
  • Claude Code by default redacts the prompt (user_prompt = <REDACTED>), tool inputs and tool output, but puts the account identity on every span: user.email, user.account_uuid, user.id and organization.id were on all of its spans. The docs say user.email and organization.id are "always included when available"; the OTEL_METRICS_INCLUDE_* switches cover only session id, account uuid, version, entrypoint and repository (see src/inputs/research.md). If a trace leaves the developer's machine, that is personal data in every span.
  • With Claude Code's content switches on (OTEL_LOG_USER_PROMPTS=1, OTEL_LOG_TOOL_DETAILS=1, OTEL_LOG_TOOL_CONTENT=1), the prompt with the customer's e-mail appeared on the interaction span, file paths on tool spans, and tool.output span events held file contents, diffs and shell output. The operating-system login name appeared times outside the identity attributes: in absolute file paths (the working folder sits under the home folder) and in the output of an ls -la the agent ran, where the file-owner column is the login name. The content-on trace carried % more attribute bytes than the default run's (52 spans against 49).

Where to remove it, in order of preference. (1) Do not capture it: leave content off in production and turn it on per environment. (2) Mask in the SDK before export (Langfuse's mask_otel_spans, a custom span processor), which only covers that SDK's spans. (3) Redact in a collector you control, before data leaves your network, which covers every service at once. We measured three collector policies with the redaction processor (beta for traces) on the content-on Claude Code trace and on the content-on hand-instrumented trace:

What the measurement says. Masking by pattern caught every e-mail, the account ids and every path, in span attributes and in span event attributes alike, and still missed the login name in ls -la output, because no pattern described it. A keyed hash (hmac-sha256) does the same job while keeping values joinable: the same e-mail always becomes the same digest, so you can still count one customer's runs. The allow-list of keys removed everything not on the list ( attributes on the Claude Code trace) and left nothing to leak, at the price of the content you wanted to debug with. A deny-list fails open on whatever you did not think of; an allow-list fails closed. In production, use the allow-list and keep full content only where access is controlled and retention is short. The attack side of the same problem (prompt injection, exfiltration through tools) is on {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}.

9. Evals in the loop


The idea. Traces are the raw material for evaluation. Online evaluation scores a sample of production traces as they arrive, with code checks where they can decide and a model judge where they cannot, and writes the result back onto the trace as a score. Offline evaluation reruns a fixed dataset of tasks before every change; interesting production traces get promoted into that dataset. The same trace store serves debugging, monitoring and regression testing, which is the main argument for an integrated platform over plain OpenTelemetry.


One trace store serves debugging, monitoring and the regression gate
Online: a sample of production traces is scored as it arrives and the score is written back onto the trace. Offline: failures are promoted into a dataset that every prompt, model, tool or harness change must pass before it ships, which produces new traces.
