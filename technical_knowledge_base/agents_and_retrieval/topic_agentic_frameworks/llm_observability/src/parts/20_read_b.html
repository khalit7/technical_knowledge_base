2. The OpenTelemetry GenAI conventions, attribute by attribute

The problem. A trace is only useful across tools if everyone names things the same way. If one library writes the model under model, another under llm.model_name and a third under gen_ai.request.model, a backend cannot compute cost or group by model without a mapping for each. OpenTelemetry's semantic conventions are the agreed names; the GenAI conventions are the part for model calls, agents and tools.

Where they live and how stable they are. In 2026 they moved out of the main conventions repository into their own, {{open-telemetry/semantic-conventions-genai|https://github.com/open-telemetry/semantic-conventions-genai}}. This page pins commit {{cb10b70 (5 Oct 2026)|https://github.com/open-telemetry/semantic-conventions-genai/tree/cb10b70c15c099ccab144e8316d934c9699da0fd/model/gen-ai}} and reads the machine-readable model files (spans.yaml, registry.yaml, metrics.yaml), not the prose. Its manifest declares stability: development and schema gen-ai-dev/1.42.0-dev, built on the main conventions v1.44.0. "Development" means names can still change without a deprecation period; instrumentation packages that already follow the latest draft ask you to opt in with OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental (see the research notes in src/inputs/research.md) SOURCE.

Three rules that matter in practice.

  • Requirement levels. On an inference span only gen_ai.operation.name and gen_ai.provider.name are required; gen_ai.request.model is required "if available"; token counts are only recommended. A span can follow the conventions and still be useless for cost.
  • Sampling-relevant attributes (marked S) should be set when the span is created, not when it ends, because a head sampler (one that decides at span start, section 7) only sees what exists at that moment. For an inference span these are the operation, provider, model, server address and port.
  • Content is opt-in. The system instructions, input and output messages, tool definitions, and a tool call's arguments and result are all opt_in: by default the conventions record that a call happened, not what was said. Section 8 measures which libraries respect that.

Counting tokens. The registry says gen_ai.usage.input_tokens "SHOULD include all types of input tokens, including cached tokens", with gen_ai.usage.cache_read.input_tokens and gen_ai.usage.cache_write.input_tokens as subsets of it. Anthropic's API counts differently, so the Anthropic section adds: "Anthropic input_tokens excludes cached tokens. Compute: gen_ai.usage.input_tokens = input_tokens + cache_read_input_tokens + cache_write_input_tokens". Other attributes worth knowing. gen_ai.conversation.id groups the calls of one multi-turn conversation (Langfuse turns it into a session, measured below); gen_ai.prompt.name and gen_ai.prompt.version record which version of a managed prompt produced a call (the link a prompt registry needs); gen_ai.conversation.compacted marks a call made after the history was compacted; gen_ai.request.reasoning.level carries an effort setting.

Metrics. The same commit defines histograms, among them gen_ai.client.operation.duration, gen_ai.invoke_agent.duration, gen_ai.invoke_agent.inference_calls and gen_ai.invoke_agent.tool_calls. The last two are the ones to alert on for agents: a jump in model calls per run is the earliest sign of an agent looping. Token usage metrics are in a separate token-metrics.yaml.

The names are still moving
The provider attribute used to be gen_ai.system; it is now gen_ai.provider.name, and gen_ai.system does not appear in this repository's registry at the pinned commit. In our runs, opentelemetry-instrumentation-openai-v2 2.4b0 still writes only gen_ai.system (so its spans miss a required attribute), Pydantic AI writes both, Claude Code 2.1.291 writes gen_ai.system plus its own token names (input_tokens, cache_read_tokens, cache_creation_tokens), and OpenInference uses a different convention altogether (llm.token_count.prompt, input.value) MEASURED. Check what your backend maps before trusting a dashboard; section 6 is what happens when you do not.

3. Instrumenting an agent: by hand, automatically, or by the framework

The three ways. Manual instrumentation is code you write: open a span, set attributes, close it. Auto-instrumentation is a package that patches a client library (here the openai Python client) so every call it makes produces a span, with no change to your code. Framework-native instrumentation is built into an agent framework, which knows where its own runs and tool calls begin and end.

We replayed the identical recorded run through the same loop eight ways: hand-written spans with and without content, OpenTelemetry's own opentelemetry-instrumentation-openai-v2 with and without its content switch, Traceloop's OpenLLMetry, Arize's OpenInference, Langfuse's drop-in OpenAI client, and the same agent rewritten in Pydantic AI with its built-in instrumentation. All sent their spans both to a local file and to the self-hosted Langfuse MEASURED:

"Model calls / tools / root": spans of each kind. "Traces": how many trace ids the one run was split into. "Fake PII": occurrences of the fake customer's e-mail and account id in span attributes (and, for openai-v2, in its log events). "KB": total attribute size, a proxy for storage cost. "Langfuse": the observation types Langfuse stored. Every span, attribute by attribute: tab {{Eight instrumentations|#t-inst}}.

What the table says.

  • Auto-instrumenting the model client does not give you an agent trace. All four client-level packages produced separate traces of one span each: no run, no tool calls, nothing linking call 3 to call 4. The agent structure only appears when something that knows about the loop opens the root and the tool spans: your code, or a framework (Pydantic AI produced the same 16-span tree as our hand-written version).
  • Content defaults differ, and the difference is the privacy policy. The GenAI conventions make content opt-in, and openai-v2 obeys: by default it records no message text. With its content switch on, the text went into log events, not span attributes. OpenLLMetry, OpenInference, Langfuse's client and Pydantic AI all record prompts and completions by default (OpenLLMetry documents TRACELOOP_TRACE_CONTENT=false to stop it; Pydantic AI's InstrumentationSettings(include_content=True) is the default).
  • Size follows content. The same run cost KB of attributes without content and KB with it by hand; OpenInference, which writes the messages twice (as one JSON blob in input.value and flattened into one attribute per message field), reached KB.
  • Cached tokens are hit and miss. The local server reported prompt-cache hits (cached_tokens). OpenLLMetry, OpenInference, Langfuse and Pydantic AI recorded them; openai-v2 and our first hand-written version did not, so a backend would price those tokens as fresh input.

Why you want content somewhere. A trace with the messages is how you check what a framework really sends. The sibling page {{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}} recorded create_agent's first request and found it is exactly your system prompt, the user message and the tool schemas, with nothing added; the parent's {{Same agent, six ways|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} tab found Pydantic AI's structured output arrives through an added final_result tool (details on {{Typed agent libraries|n:3f15c17b0d0d819fba89f9ec88feb859}}) and smolagents sends a 2,231-token system prompt of its own. Those findings came from logging the requests; with content capture on, your tracing backend shows the same thing for every run.

What to do. Use auto-instrumentation for the model client (it captures parameters, tokens and errors you would forget) and add the agent skeleton yourself: one invoke_agent span around the run and one execute_tool span around each tool call, both with the conventions' names, so the client spans nest under them. If a framework already does it, as Pydantic AI does, use that. Decide content capture deliberately, per environment: on in evaluation runs, where graders need the arguments and results; off or redacted in production.
