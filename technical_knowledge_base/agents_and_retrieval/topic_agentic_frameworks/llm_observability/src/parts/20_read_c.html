4. Langfuse, self-hosted, fed by every variant

What it is. Langfuse is an open-source platform for tracing, evaluating and managing prompts of LLM applications: MIT-licensed except its ee/ folders ({{LICENSE|https://github.com/langfuse/langfuse/blob/main/LICENSE}}). ClickHouse announced it had acquired Langfuse on 16 January 2026, saying it "stays open source and self-hostable" ({{ClickHouse blog|https://clickhouse.com/blog/clickhouse-acquires-langfuse-open-source-llm-observability}}). Version 4 became generally available on 17 August 2026 ({{changelog|https://langfuse.com/changelog/2026-08-17-langfuse-v4}}); the latest release when we ran it was 4.53.0, published that morning ({{releases|https://github.com/langfuse/langfuse/releases}}) SOURCE.

What it took to run. Langfuse's own Docker Compose file at tag v4.53.0, ports moved to localhost: six containers (web, worker, ClickHouse 25.12, Postgres 17, Redis 7, MinIO for S3-style blob storage), about GB of images, and GiB of memory at rest after ingesting this page's traces MEASURED. Postgres holds users, projects, prompts and datasets; ClickHouse holds the observations; Redis is the queue between web and worker; blob storage keeps raw events. That is the main cost of "self-hostable": you operate a column store.

The data model. A trace is one request or run; it contains observations, typed as span, generation (a model call), event, agent, tool, chain, retriever, evaluator, embedding or guardrail ({{observation types|https://langfuse.com/docs/observability/features/observation-types}}). Traces group into sessions and are attributed to users; scores attach to traces or observations. Version 4 rebuilt storage around one wide, mostly immutable ClickHouse table, in which "traces are represented as root spans within the same table instead of a separate entity", and replaced the old batch ingestion API with OpenTelemetry ({{v3 to v4 upgrade guide|https://langfuse.com/self-hosting/upgrade/upgrade-guides/upgrade-v3-to-v4}}). We saw it directly: on the default events_only deployment, the old GET /api/public/traces, /observations and /scores endpoints answer 404 with "This endpoint is not available on deployments running in Langfuse v4 events_only mode", while /api/public/v2/observations and /api/public/v3/scores work MEASURED.

How OpenTelemetry spans become observations. Langfuse accepts OTLP at /api/public/otel with the project's public and secret key as HTTP Basic auth. Its mapping, from its docs: the observation type comes from langfuse.observation.type, then gen_ai.operation.name, then "model present means generation"; the model from gen_ai.request.model, llm.model_name or model; usage from gen_ai.usage.* or llm.token_count.* ({{OpenTelemetry integration|https://langfuse.com/integrations/native/opentelemetry}}). What it stored from our eight variants MEASURED:

Every variant's model calls became generations with the model and token counts, including OpenInference's llm.* names and Langfuse's own langfuse.observation.* attributes. Langfuse also split cached tokens out of the input into a separate input_cached_tokens bucket (its usage keys are non-overlapping: "each token must be counted in exactly one key", {{docs|https://langfuse.com/docs/observability/features/token-and-cost-tracking}}). Our hand-written gen_ai.conversation.id became the session id, and Pydantic AI's became a session too. No cost was computed for any of them: Langfuse has no price for a local model, which is correct. The Claude Code run in section 6 is where prices come in.

Telemetry loss is silent
On the first attempt, two of the eight variants (openai-v2 and Pydantic AI) lost every span: Langfuse, still warming up, answered their exports with HTTP 500 ("stream is not readable", 12 times in its log). The agents finished normally; the only trace of the failure was one exporter warning on standard error, "Failed to export spans batch due to timeout, max retries or shutdown". The reruns were ingested MEASURED. Watch the exporter's own metrics, or put a collector with a retry queue between your app and the backend.

Langfuse's other halves (from its docs, used only where marked): scores and datasets (section 9, measured); LLM-as-a-judge evaluators that run on observations as they arrive ("observation-level evaluators are the recommended target for live production data; trace-level evaluators are deprecated", {{docs|https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge}}); prompt management, where labels such as production and staging point at prompt versions and an unlabelled fetch serves production ({{docs|https://langfuse.com/docs/prompt-management/features/prompt-version-control}}); masking in the SDK before export (mask_otel_spans in the Python SDK v4); and sampling in the SDK (sample_rate, decided per trace).

With a gateway. If your model calls already go through LiteLLM, its langfuse_otel callback sends a GenAI span per request to the same endpoint with usage and cost, and LiteLLM now recommends it over the older langfuse callback ({{LiteLLM docs|https://docs.litellm.ai/docs/observability/langfuse_integration}}) SOURCE. Gateway spans see every request but not the agent around it; app spans see the agent. Run both and join them on the trace id. Gateways in depth: {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}.

6. Cost attribution: from spans to dollars, reconciled

The problem. The bill says what you spent; it does not say which agent, user, feature or step spent it. A trace can, if each model span carries the model and the token counts by kind, and the backend multiplies them by the right prices. Two things go wrong in practice: the counts arrive under names the backend does not read, and the prices the backend applies are not the ones you paid.

The 16% gap in the middle step is cache-write tokens priced at the 5-minute rate (1.25x) instead of the 1-hour rate (2x) that Claude Code used on these runs (ephemeral_1h_input_tokens in its usage, and in the shared facts for the agent pages). The GenAI conventions have one cache_write count and no field for the cache's lifetime, so a backend that follows them faithfully must guess; Langfuse's model table has separate input_cache_creation_5m and _1h prices, so passing the count under the explicit key fixed it. An open Langfuse issue reports the same mispricing from its LangChain integration ({{#17450|https://github.com/langfuse/langfuse/issues/17450}}).

Rolling cost up. Once each model span has a correct cost, attribution is a group-by over the trace: by the root's attributes for user, ticket and feature (our application set app.user, app.ticket, app.feature on its span), by gen_ai.conversation.id for a session, by span name for a step. Langfuse propagates user, session and tags to every observation when you set them with propagate_attributes() (its v4 SDK). Reconcile against a second source: the gateway's spend log, the provider's invoice, or, as here, the harness's own metric. Two sources that disagree by a fixed ratio usually mean a price or a token kind is wrong, as in step 2 above.
