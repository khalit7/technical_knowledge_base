The idea in one screen

An agent framework is a library that writes part of the agent loop for you; every one sits somewhere on one line, how much of the loop you own, and is worth adopting only for a capability you would otherwise build by hand and get wrong: saved state you can resume, a human pause, typed results, traces.

The sibling topic, {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}, takes a finished agent apart: the agent loop (call the model, run the tool it asks for, show it the result, repeat until it stops), tools, context, permissions. This topic is the parts you assemble when you build your own. Fig. 1 adds them one at a time around one loop; each step names the page that owns the block.

  1. The loop every framework runs. Your app hands the agent loop a job. The loop sends the conversation and the tool list to a model provider; the model answers or asks for a tool; the loop runs it, appends the result and calls again until the model stops. Written by hand it is about 15 lines (the {{Same agent|#t-same}} tab's version 1). How the loop works: {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}.
  2. Orchestration: who picks the next step, and the run's state. A library takes over the loop. The schools differ in what they make you describe: a graph runtime (LangGraph, {{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}}), a typed loop (Pydantic AI, OpenAI Agents SDK, smolagents, Google ADK, {{Typed agent libraries|n:3f15c17b0d0d819fba89f9ec88feb859}}), a harness as a library (the {{Claude Agent SDK|n:3c65c17b0d0d813b960fd9857118fbd2}}), roles and crews (CrewAI, Microsoft Agent Framework, owned by this page). Workflows or agents, the schools and typed results: sections 1, 2 and 4.
  3. State: checkpoints within a run, memory across runs. After every step the run's whole state is saved under a thread id, so a crash or a human pause resumes instead of starting again (section 3, Fig. 3). Facts kept across sessions (facts, temporal graphs, paged context) are another store, owned by {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, section 8.
  4. Several loops cooperating. A lead hands pieces of the job to workers, each with its own prompt, tools and context, and reads back their reports: orchestrator-workers, handoffs, blackboard, debate (section 5, {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}).
  5. A gateway: one endpoint over many providers. Every model call goes to one proxy that holds the keys, budgets, retries, fallbacks and routing, and forwards it to Anthropic, OpenAI, Google or a model you serve (section 6, {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}).
  6. Observability: a trace of every step. Each model call and tool call becomes a span with its tokens and cost; one run is a tree of spans, and evals score them (section 7, {{LLM observability|n:3c65c17b0d0d81fe82c0c6e9360afec4}}).
  7. Or buy the whole loop. At the far end of the axis a hosted runtime runs the loop, the tools' sandbox and the session on the vendor's servers; your app sends a task and receives events (section 9).

Orchestration decides the next step; everything else wraps each model call. Drag the figure to turn it. The labs put the whole stack around one running agent.

The running example. Both agent topics use one job: a tiny Python library, textstats, with two planted bugs (the tokenizer splits don't into don and t; top_words does not break ties alphabetically) and a test file that catches both. The prompt, word for word: "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests." Three tabs run it for real: {{Same agent, six ways|#t-same}} (one agent in a plain loop and five frameworks), the {{Orchestration lab|#t-orch}} (five workflow patterns, a free agent, a crash and resume, one agent against several) and the {{Production stack|#t-ops}} (a gateway, traces, an eval gate and hosted runtimes around it).

New terms (each defined again where it is used):

Workflow
model calls along code paths you wrote; your code picks the next step.
Agent
the model picks the next step, turn after turn, until it stops.
Framework
any library that writes some of the loop, its state or its plumbing for you.
Checkpoint, thread id
the run's whole state saved after a step, under the id that names the run; resuming loads the newest one.
Structured output
the model's answer as data that matches a schema, not free text.
Gateway
a proxy between your code and the model providers: one API, keys, budgets, retries, fallbacks.
Trace, span
one run recorded as a tree of timed steps (model calls, tool calls) with tokens and cost.
Hosted runtime
the vendor runs the loop, the sandbox and the session; you send a task and receive events.

Who writes each piece, by position on the axis

Every library sits on one line, from You own the loop (plain API calls) to The vendor owns the loop (a hosted runtime, section 9). Fig. 2 takes the nine pieces of an agent along it, one position per step: blue, you write it; grey, the library provides it; purple, the vendor runs it. Moving right buys features with control.

Predict first: moving right from a plain loop, at which position does crash recovery stop being your job?

  1. Plain API calls (the provider SDK, a while loop or your own DAG engine). All nine pieces are yours: the loop in about 15 lines, hand-written JSON schemas, persisting messages, pausing, trimming, tools, sandbox, and your process runs it. Everything is visible and nothing is hidden: the request is exactly the dictionary you built. The {{Same agent|#t-same}} tab's version 1 is this position.
  2. Minimal loop library (Pydantic AI, OpenAI Agents SDK, smolagents, Google ADK). The loop (an Agent and run()), the tool schemas (from type hints or docstrings) and the order of steps (the model, plus handoffs or agents-as-tools) move to the library. Sessions keep history, but crash recovery, approval, compaction, tools and the sandbox stay yours. Prompt inflation starts here: the framework adds instructions or tools you did not write.
  3. Graph runtime (LangGraph, LlamaIndex Workflows). Saved state and the human pause move to the library: a checkpointer after every step, interrupt() and resume. The order of steps comes back to you as the graph you declare; the runtime runs it. Crash recovery, human pauses of any length and replay from an old step come with it (section 3).
  4. Harness as a library (Claude Agent SDK). Everything but where it runs moves to the library: Claude Code's loop, @tool served in-process, sessions you can resume, a permission callback you write, automatic compaction, Read, Edit, Bash and Grep, permission modes and an optional OS sandbox. You configure a finished agent instead of assembling one; the loop is only as open as its settings.
  5. Hosted runtime (OpenAI Agents API, Claude Managed Agents). The vendor runs eight of the nine pieces on its servers; you only declare your custom tools. What you give up is exactly control flow and visibility: what you trace is what the vendor exports (section 9).

The one idea to keep
For the running example, two plain model calls glued by 20 lines of script fixed the visible tests in 19.4 s for $0.013, and a free agent did it in 24.8 s for $0.030 MEASURED. Neither needed a framework. Start there, and add one when a section below names a need you have.
