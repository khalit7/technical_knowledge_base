3. State, durability and humans in the loop

The state of a run is everything needed to carry on: the messages so far, intermediate results, which step comes next. In a plain script it lives in one process's memory. Kill the process (a deploy, an out-of-memory kill, a closed laptop) and the run is gone, including the model calls already paid for. Agents make this the normal case: runs last minutes to hours, and some must wait days for a person to approve something.

The fix is a checkpoint. After every step, write the whole state to a database under a thread id. To recover, load the newest checkpoint of that thread and continue from the next step. Two features fall out of the same mechanism: a human-in-the-loop interrupt (save, exit, and resume later with the person's answer) and time travel (load an older checkpoint, edit it, and run forward on a new branch).

The Orchestration lab did this for real with a LangGraph StateGraph and a SQLite checkpointer MEASURED: the diagnosis call finished ( s, ) and was checkpointed; the process was killed s into the next model call; the restarted process resumed at , not at the start, so the diagnosis was not paid for twice, while the call in flight was lost and made again.

The two details that bite
A node that resumes after an interrupt or a crash runs again from its first line (LangGraph's interrupt() docstring: "The graph resumes from the start of the node, re-executing all logic"), so anything with a side effect before the pause (an email, a payment, a file write) must be safe to repeat or sit in its own node. And nothing restarts a dead process for you: a job queue, a supervisor or a hosted platform has to notice and call resume with the same thread id.

Two families of durability. Checkpointing (LangGraph and most agent libraries) saves a snapshot of state after each step. Durable execution engines such as Temporal save an event history of every completed activity and, after a crash, re-run your workflow code from the top, replaying recorded results instead of calling again; in exchange, the workflow code must be deterministic. If your company already runs Temporal or a job system, putting each model call in an activity gives an agent durability without an agent framework.

Pending writes, and when the checkpoint is written. LangGraph runs a graph in super-steps: every node that is ready runs in parallel, then all their updates are applied together. A node that finishes inside a step has its update saved at once as a pending write, before the step's checkpoint exists, so a finished parallel task survives a crash: killed by SIGKILL in the middle of a parallel step, the graph resumed only the unfinished node and took the finished one's result from its pending write MEASURED (langgraph 1.2.14, SQLite, on the child page). When checkpoints are written is the durability mode: "sync" before the next step starts, "async" in the background while it runs, "exit" only when the run ends, which left nothing to resume after a kill. invoke defaults to "async" (the pregel/main.py docstring), the cheaper mode: 0.288 ms per super-step against 0.423 ms for sync on SQLite, measured on the same page.

Predict: your agent asks a manager to approve a refund, waits two days, and the server was redeployed in between. What must be true for the approval to work?
The state was checkpointed to a durable store (not memory) under a thread id the approval link carries; the resume path reloads it in a new process; and the step before the pause did not already send the refund, because the paused node will run again from its first line.

4. Structured output and typed tools

A model returns text. Code downstream needs fields: a function name, a list of bugs, an amount. Structured output is getting the model's answer as data that matches a schema (a description of the fields and their types, usually JSON Schema), and typed tools are the same idea for tool arguments. There are three ways, from weakest to strongest:

  1. Ask in the prompt and parse. "Reply with JSON only". Works most of the time; fails on fences, preambles, trailing commas, a missing field.
  2. Make the answer a tool call. Offer one tool whose input schema is your result type and require the model to call it. Tool-calling models are trained to emit arguments that fit a schema, and the harness can validate them. Pydantic AI does this (its first request adds a final_result output tool, measured on the {{Same agent|#t-same}} tab), and so does the Claude Code CLI's --json-schema flag, as the run below shows.
  3. Constrain the decoding. The provider only lets the model produce tokens that keep the output valid for the schema (OpenAI's strict mode for function schemas, function calling guide, read 5 Oct 2026 SOURCE). Validity is then guaranteed by construction; whether the content is right is not. It also needs the server to support it: a library's native output mode often sends the schema only in response_format, and mlx_lm.server 0.32.0 reads neither response_format nor tool_choice, so a local model behind it never sees the schema and nothing forces a tool call MEASURED (on {{Typed agent libraries|n:3f15c17b0d0d819fba89f9ec88feb859}}).

Same input, the first two ways, recorded on 6 October 2026 with Claude Haiku 4.5 and every built-in tool switched off MEASURED: the running example's code and failing test output, and the instruction "do not edit anything: report the bugs" as an object {"bugs": [...]} with function, failing_test, cause and fixed_line.

What it shows. Both answers were correct; only one was data. The prompt-only reply wrapped its JSON in a Markdown fence, so json.loads on the raw text failed at the first character. The usual repair is a parser that strips fences, then a validate-and-retry loop: check the parsed object against the schema and, on failure, send the validation error back to the model and ask again (Pydantic AI raises ModelRetry for this; cap it at two or three tries and count every retry, because a rising retry rate is an early sign that a prompt or model changed). The tool route cost more input tokens (the tool definition and its instructions) and one more turn, and returned a parsed object in result.structured_output.

5. Multi-agent: when it helps and when it hurts

A multi-agent system is several model loops cooperating, each with its own prompt, tools and context window. The patterns are few:

  • Orchestrator-workers (supervisor): a lead agent splits the task, spawns workers with short briefs, and combines their reports. Workers' contexts are isolated: they return a summary, not their transcript. Claude Code's subagents work this way.
  • Handoffs: control passes wholly from one agent to another (triage to billing); one specialist owns the conversation at a time. The OpenAI Agents SDK's native primitive.
  • Parallel fan-out: the parallelisation workflow of section 1; often most of the benefit, with none of the coordination.
  • Debate or a judge panel: several answers, a judge or a vote picks. At equal budget, majority voting over samples of one model explains most of the gain usually credited to debate (Debate or Vote, 24 Aug 2025; earlier Smit et al., Nov 2023) SOURCE. Measured on 30 nine-person knights-and-knaves puzzles with Claude Haiku 4.5, tools off, the same puzzles for every method: one sample solved 21, a vote of 5 samples 27, three samples plus a judge 29, debate (3 agents, 2 rounds) 29 MEASURED (Debate lab on {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}).
  • Shared state (blackboard): agents coordinate through a common store (files, a database, a graph of results) instead of messages. Anthropic's Fermat's Last Theorem formalisation had Claude agents work over a shared directed acyclic graph of theorem statements and reached a complete machine-checked proof in 11 days on about six billion output tokens (Anthropic, 4 Sep 2026) SOURCE; the {{Agora|n:3e25c17b0d0d81399738c3e65f4bf900}} paper keeps the shared record in Git so every result can be checked out and rerun.

The two published positions, both June 2025. Anthropic's multi-agent research system (13 Jun): a lead with parallel subagents "outperformed single-agent Claude Opus 4 by 90.2%" on its internal research eval, agents use about 4 times the tokens of chat and multi-agent systems about 15 times, and token usage alone explained 80% of the variance on BrowseComp; it also says "most coding tasks involve fewer truly parallelizable tasks than research". Cognition's Don't Build Multi-Agents (Walden Yan, 12 Jun): "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results" SOURCE. They are not contradictory: parallel reading (search, research, review) splits well; parallel writing of one artifact does not, because each writer makes decisions the others cannot see (Philipp Schmid's read and write framing, 20 Jun 2025).

On the running example, a coding task with two independent bugs, the Orchestration lab ran the same model alone and as a lead with two investigating subagents MEASURED. Pick a measure:

Same fix, same hidden-check score, several times the tokens and time: the subagents re-read files the lead had already read, and the lead waited for them. That is Cognition's case on a task Anthropic's own post says is a poor fit. Larger evidence points the same way: across 260 configurations, Kim et al. (Dec 2025, revised Apr 2026) measured effects from "+80.8% on decomposable financial reasoning to -70.0% on sequential planning", and found that "tool-heavy tasks appear to incur multi-agent overhead" SOURCE. Failure analysis of real multi-agent traces (MAST, Cemri et al., 2025) sorts what goes wrong into "14 unique modes" in three groups: system design, inter-agent misalignment and task verification.

Before you go multi-agent, ask
Is the bottleneck context size or breadth of exploration? Are the subtasks independent, with no shared artifact being written? Is the result worth several times the tokens? Can you trace every agent? Would a fixed fan-out workflow do? Does the brief say exactly what counts as a result? Auditors sharing a blackboard filed 107 and 170 extra reports beyond the 16 planted violations, and same-model checkers kept 186 of 186 reports, whether shown the claim or not; a sharper brief gave 16 of 16 with no extras (Audit lab on {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}). A "no" to any of these is a reason to stay with one agent. Nous Research's 1,393-subagent refactor of the Hermes Agent repository (Nous Research, Sep 2026) SOURCE shows the last risk: reviewers found removed public names and changed exception handling at roughly 65 sites, "real regressions the existing tests had missed". A green test suite over a huge parallel diff is not evidence the diff is safe.
