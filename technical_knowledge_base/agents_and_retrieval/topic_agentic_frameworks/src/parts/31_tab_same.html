Same agent, six ways

An agent is a model in a loop: send the conversation and a list of tools, get back either an answer or a request to run a tool, run it, append the result, repeat. That loop fits in about fifteen lines. A framework is a library that writes that loop for you and adds things around it (tool schemas from type hints, saved state, retries, typed results, tracing, approval steps). This tab builds the same agent six times, runs every version for real, and shows what each framework did for you, what it sent to the model on your behalf, and where it got in the way.

The experiment

Task (the running example of both agent topics): a tiny Python library, textstats, with two planted bugs (the tokenizer drops apostrophes, so word_count("don't stop") is 3 instead of 2; top_words breaks ties by order of appearance, not alphabetically). Prompt, word for word: "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests." One task for all six: every framework here can call tools, so a coding task with a test runner as the judge works for all of them.

Tools, identical in all six (the same Python bodies are imported by every version, so only the framework differs): list_files(), read_file(path), edit_file(path, old, new) (exact-string replace, as real harnesses do) and run_tests(). Same short system prompt, same limit of 15 model calls.

Models. Versions 1 to 5 talk to an OpenAI-compatible endpoint served on this laptop: local model on Apple M1 Pro mlx-community/Qwen3-4B-Instruct-2507-4bit (a 4-billion-parameter open model, 4-bit weights) served by mlx_lm.server (mlx-lm 0.32.0), through a logging proxy that saved every request byte for byte. Version 6 cannot use that endpoint (the Claude Agent SDK drives Claude Code, which talks to Anthropic), so it runs Claude Haiku 4.5 and Sonnet through a Claude subscription. The two are never compared as if they were the same model: a 4B local model failing where Claude succeeds says nothing about the frameworks.

Pass means: the test file is unchanged and python3 tests/test_core.py passes afterwards, checked by the runner, not by the agent's own claim. All runs on 2026-10-05; package versions pinned below each code panel.

5. What each one did for you, what it hid, and how to add approval and a retry


Read from each library's installed source (versions above) and its docs on 2026-10-05. "Approval" is a human saying yes before edit_file runs; "retry" covers the two kinds every agent needs: a transient API failure (retry the same call) and a model mistake (tell the model what went wrong and let it try again).




1. Plain loop


Did for you
Nothing: you wrote the schema, the loop, the stop rule and the error handling. The openai client retries connection errors, 429 and 5xx responses twice by default (DEFAULT_MAX_RETRIES = 2 in openai 3.24.0's _constants.py).


Hid
Nothing. The request is exactly the dictionary you built.


Approval
if call.function.name == "edit_file" and input(f"Allow {args}? ") != "y":
    result = "denied by the user"   # the model sees the refusal
The pause blocks the process: fine for a CLI, not for a web service, where you must save messages and resume later yourself.


Retry
API: OpenAI(max_retries=5). Model mistakes: already there, the except turns a bad call into an observation.


2. LangGraph


Did for you
Tool schemas from signatures and docstrings; ToolNode runs every tool call and appends the results; the checkpointer saves the whole state after every step under a thread_id, so a run can be paused, inspected, resumed or replayed ({{persistence docs|https://docs.langchain.com/oss/python/langgraph/persistence}}).


Hid
Little in the request (385 tokens, slightly fewer than ours: it omits empty required lists). The cost is concepts: state reducers, conditional edges, recursion_limit counting graph steps rather than model calls (15 model turns needed a limit of 31). create_react_agent, the one-line version, warns in 1.2.13 that it is deprecated in favour of LangChain's create_agent.


Approval
g.compile(checkpointer=InMemorySaver(),
          interrupt_before=["tools"])
# run stops before tools; a human looks, then:
app.invoke(None, config)          # resume
or call interrupt(...) inside a node and resume with Command(resume=...) ({{interrupts docs|https://docs.langchain.com/oss/python/langgraph/interrupts}}). Works across processes because the state lives in the checkpointer.


Retry
g.add_node("agent", agent, retry_policy=RetryPolicy()): defaults 3 attempts, 0.5 s then doubling (langgraph/types.py). Tool argument errors go back to the model as a message by default; other tool exceptions are raised.


3. Pydantic AI


Did for you
Typed tools, a validated typed result (FixReport), usage limits, and ModelRetry: raise it in a tool and the message goes back to the model with "Fix the errors and try again." appended ({{tools docs|https://ai.pydantic.dev/tools/}}).


Hid
The typed result is implemented as an extra tool, final_result, plus tool_choice: "required": the model may never answer in plain text ({{output docs|https://ai.pydantic.dev/output/}}). Tools get strict: true and additionalProperties: false. A model that ends with a sentence instead of calling final_result gets a validation error back, and after one retry (the default) the run raises UnexpectedModelBehavior. That is what happened here.


Approval
@agent.tool_plain(requires_approval=True)
def edit_file(...): ...
agent = Agent(..., output_type=[FixReport, DeferredToolRequests])
# the run ends with DeferredToolRequests; ask the human, then:
agent.run_sync(message_history=r.all_messages(),
    deferred_tool_results=DeferredToolResults(approvals={call_id: True}))
({{deferred tools docs|https://ai.pydantic.dev/deferred-tools/}})


Retry
Model mistakes: ModelRetry, and retries= on the agent or tool (default 1). API failures: configure the HTTP client of the provider.


4. OpenAI Agents SDK


Did for you
Typed tools, the loop (Runner), turn limit, handoffs between agents, guardrails, sessions and tracing. By default a tool exception becomes an error message for the model.


Hid
Tracing is on by default and exports every span (prompts and tool results included) to OpenAI's trace dashboard, which needs an OpenAI API key; this version turns it off ({{tracing docs|https://openai.github.io/openai-agents-python/tracing/}}). The request carries strict: true, additionalProperties: false and a title on every schema and argument: 491 tokens against our 397. It sent no max_tokens, so the server default decided the output cap.


Approval
@function_tool(needs_approval=True)
def edit_file(...): ...
r = Runner.run_sync(agent, TASK)
state = r.to_state()
for item in r.interruptions: state.approve(item)  # or reject
r = Runner.run_sync(agent, state)
({{human-in-the-loop docs|https://openai.github.io/openai-agents-python/human_in_the_loop/}})


Retry
API: the underlying openai client's max_retries. Model mistakes: tool errors are returned as text by default.


5. smolagents (CodeAgent)


Did for you
The model writes Python instead of JSON tool calls, so one step can call several tools, loop and compute (the CodeAct idea, {{Wang et al. 2024|https://arxiv.org/abs/2402.01030}}). Python errors come back as the next observation.


Hid
The largest prompt by far: a long system prompt with worked examples of the Thought, code, Observation format and the tools rendered as Python signatures (2,231 tokens on the first call, no tools field at all), plus stop sequences. The code runs in the same process in LocalPythonExecutor, which its own docstring calls "not a security sandbox"; executor_type can be "docker", "e2b", "modal" or "blaxel" instead ({{secure execution docs|https://huggingface.co/docs/smolagents/tutorials/secure_code_execution}}). Past tool calls go back into the history as text, "Calling tools:\n" + str([...]) in memory.py (a Python repr, single quotes), with results as user messages starting "Observation:", not as native tool-call messages, even in its ToolCallingAgent.


Approval
No approval primitive in 1.26.0: ask inside the tool (edit_file calls input()), or inspect each step with step_callbacks. Approval must live in the tool because one code step can call it many times.


Retry
API: OpenAIServerModel retries rate-limit errors up to 3 attempts (RETRY_MAX_ATTEMPTS = 3). Model mistakes: errors in the code become the next observation.


6. Claude Agent SDK


Did for you
Everything Claude Code does: the loop, context handling, permissions, hooks, sessions, subagents, parallel tool calls, prompt caching. Custom tools are an in-process MCP server ({{custom tools docs|https://code.claude.com/docs/en/agent-sdk/custom-tools}}); the SDK starts the Claude Code CLI as a subprocess and talks to it over a stream.


Hid
The loop runs in another process, and the request to Anthropic cannot be captured from here: only the stream of messages and the token counts come back. Two defaults surprised us. Without strict_mcp_config=True, the first run also loaded the subscription account's connected apps as tools: over a hundred thousand tokens of tool definitions on every call, for a task that needed four tools (that run is discarded). And without tools=[] plus our own system_prompt, the first call carries Claude Code's prompt and built-in tools (section 3).


Approval
async def ask(name, args, ctx):
    ok = input(f"{name} {args}? ") == "y"
    return PermissionResultAllow() if ok else \
           PermissionResultDeny(message="denied")
options = ClaudeAgentOptions(..., can_use_tool=ask)
or a permission_mode, or a PreToolUse hook ({{permissions docs|https://code.claude.com/docs/en/agent-sdk/permissions}}). Here allowed_tools pre-approved all four tools, so no prompt appeared.


Retry
How Claude Code retries a failed API call is internal to the CLI and was not tested here; the SDK exposes max_turns and max_budget_usd as stops. Model mistakes: tool errors return as tool results.





Predict. In a Pydantic AI run the repository ended up fixed (tests pass) but the run raised an exception. What is the most likely reason?



Right answer: the typed result. With output_type=FixReport, Pydantic AI accepts only a call to its final_result tool. The local model wrote "I modified the tokenize function ..." as text; the validation error went back as a retry prompt, and the run either exhausted its one output retry or wandered into more edits until the 15-request limit. The repository was fine; the contract between framework and model was not. A stronger model, or output_type=str, removes the failure.


Predict. In one smolagents run the model said the repository's files were named "R", "E", "A", "D". Where did that come from?



The model's code did for f in list_files(): print(f). Our tool returns one newline-separated string (fine for a JSON tool call, where the model reads text), so Python iterated over its characters. With code actions, a tool's return type becomes part of its interface: return a list[str] to a code agent, text to a JSON-calling agent.



6. Choosing, after seeing all six


    

  • Write the plain loop first, once. At about 30 lines it shows you what every framework is doing, and for one agent with a few tools it is often all you need. Anthropic's advice is the same: start with direct API calls and add a framework only when it earns its place ({{Building effective agents|https://www.anthropic.com/engineering/building-effective-agents}}); see also {{12-factor agents|https://github.com/humanlayer/12-factor-agents}} ("own your control flow", "own your prompts").
    • 

  • Reach for LangGraph when the state must outlive a process: pauses for a human, resumable long runs, branching workflows. Its checkpointer is the feature; the loop is incidental.
    • 

  • Reach for Pydantic AI when the output feeds code that needs a validated type, and the model is strong enough to call an output tool reliably (the 4B model here was not).
    • 

  • Reach for the OpenAI Agents SDK for handoffs between agents and its tracing, mainly on OpenAI models; it works with any chat-completions endpoint, as here.
    • 

  • Reach for smolagents when actions are naturally code (data work, many small tool calls per step) and you can sandbox the executor; expect a much longer prompt and a model that must follow its code-block format.
    • 

  • Reach for the Claude Agent SDK when you want Claude Code's harness (context handling, permissions, hooks, subagents) inside your program and you are on Claude. Set strict_mcp_config, setting_sources, tools and system_prompt deliberately, or you inherit whatever the machine and account have configured.
    • 




Common mistakes


Blaming the framework for the model
With the 4B local model every version except LangGraph lost at least one run, the plain loop included: the model decided the apostrophe test was wrong, or stopped before running the tests. Run the plain loop on the same model as a baseline before judging a framework, then look at what differs in the requests.


Trusting the agent's "the tests pass"
Four runs ended with a confident "the tests should now pass" or a final answer claiming success while a test still failed. Verify outside the agent: here the runner re-ran the tests and compared the test file byte for byte.


Never looking at the request
The framework's prompt, schema decorations and hidden tools are billed on every call. A logging proxy (thirty lines here) or the framework's own tracing shows them; do it once per framework you adopt.


Letting the SDK inherit the machine's configuration
The Claude Agent SDK's first run here loaded tools from the account's connected apps. Pin every source of tools, settings and prompts explicitly in production code.


Comparing tokens across tokenizers
397 Qwen tokens and 1,388 Claude tokens for the same request are not "3.5 times more": the system prompts differ (Claude's included its own framing) and the tokenizers differ. Compare within one model only.



Interview questions


What does an agent framework actually give you over a while loop?
Schema generation from types, state persistence and resumption, retries, typed outputs, approval and interrupt primitives, tracing, multi-agent handoffs. The loop itself is the smallest part.


How would you add human approval to a tool call in a web service?
The run must stop, persist its state and resume later in another request: LangGraph's checkpointer with interrupt, Pydantic AI's deferred tool requests, the Agents SDK's RunState with approve/reject. A blocking input() works only in a CLI.


What is prompt inflation and how do you measure it?
Tokens a framework adds to every request (system prompt, examples, schema decorations, extra tools). Measure by capturing the first request with a proxy or the provider's usage field and comparing it with a hand-written request for the same tools.


Code actions versus JSON tool calls: trade-offs?
Code lets one step loop, compose and compute, and models write code well; it needs a sandbox, a longer prompt and a model that keeps the format, and tool return types matter. JSON calls are simpler, safer and supported natively by providers.


Your agent passes with framework A and fails with framework B on the same model. What do you check?
Diff the requests (prompt, tool schemas, tool_choice, max_tokens, stop sequences), then the error paths (how tool errors and format errors return to the model), then limits (turn counting). Here Pydantic AI's tool_choice "required" and smolagents' code format changed the model's behaviour, not its knowledge.
