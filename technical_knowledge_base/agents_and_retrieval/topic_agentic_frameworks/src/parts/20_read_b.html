3. State, durability and humans in the loop

The state of a run is everything needed to carry on: the messages so far, intermediate results, which step comes next. In a plain script it lives in one process's memory; kill the process (a deploy, an out-of-memory kill, a closed laptop) and the run is gone, including the model calls already paid for. Agents make this the normal case: runs last minutes to hours, and some must wait days for a person.

The fix is a checkpoint: after every step, write the whole state to a database under a thread id; to recover, load the newest checkpoint of that thread and continue from the next step. Two features fall out of the same mechanism: a human-in-the-loop interrupt (save, exit, resume later with the person's answer) and time travel (load an older checkpoint, edit it, run forward on a new branch). The Orchestration lab did this with a LangGraph StateGraph and a SQLite checkpointer MEASURED: the diagnosis call finished ( s, ) and was checkpointed; the process was killed s into the next model call; the restarted process resumed at , so the diagnosis was not paid for twice, while the call in flight was lost and made again.

Two families of durability, compared side by side in the lab. Checkpointing (LangGraph and most agent libraries) saves a snapshot of state after each step. Durable execution engines such as Temporal save an event history of every completed activity and, after a crash, re-run your workflow code from the top, replaying recorded results instead of calling again; in exchange, the workflow code must be deterministic. If your company already runs Temporal or a job system, one model call per activity gives an agent durability without an agent framework. Across the schools: the graph runtimes give crash recovery with no extra work; the minimal loops give sessions (history), which is not resuming a half-finished run; the Claude Agent SDK resumes and forks sessions; a hosted runtime keeps sessions on the vendor's side. Nothing restarts a dead process for you: a job queue, a supervisor or a hosted platform has to call resume with the same thread id.

4. Structured output and typed tools

Code downstream needs fields, not prose. Structured output is getting the model's answer as data that matches a schema (usually JSON Schema), and typed tools are the same idea for tool arguments. Three ways, from weakest to strongest:

  1. Ask in the prompt and parse. Works most of the time; fails on fences, preambles, trailing commas, a missing field.
  2. Make the answer a tool call. Offer one tool whose input schema is your result type and require the model to call it; tool-calling models are trained to emit arguments that fit, and the harness validates them (Pydantic AI's output tool, the Claude Code CLI's --json-schema).
  3. Constrain the decoding. The provider only lets the model produce tokens that keep the output valid (OpenAI's strict mode, function calling guide, read 5 Oct 2026 SOURCE). Validity is guaranteed; whether the content is right is not, and the server must support it.

This page recorded the first two once on the running example (Claude Haiku 4.5, every built-in tool off, 6 October 2026) MEASURED: both answers named the right bugs, but the prompt-only reply wrapped its JSON in a Markdown fence, so json.loads on the raw text failed at the first character; --json-schema returned a parsed object for one more turn and a larger first request. The usual repair is validate-and-retry: check the parsed object against the schema and, on failure, send the error back and ask again, a bounded number of times, counting every retry.

5. Multi-agent: when it helps and when it hurts

A multi-agent system is several model loops cooperating, each with its own prompt, tools and context window: a lead with workers, handoffs between specialists, a shared blackboard, a debate or a vote. The one distinction that decides most cases: parallel reading (search, research, review) splits well, because the pieces need not agree; parallel writing of one artefact does not, because each writer makes decisions the others cannot see. That reconciles the two published positions of June 2025, Anthropic's multi-agent research system (for, on breadth-first research) and Cognition's Don't Build Multi-Agents (against, on writing), in Philipp Schmid's read and write framing SOURCE.

On the running example, a small coding task, the Orchestration lab ran the same model alone and as a lead with two investigating subagents MEASURED: the same fix and the same hidden-check score (5 of 6), for 438,517 tokens against 120,530 and 68.4 s against 24.8 s. The subagents re-read files the lead had already read, and the lead waited for them. Most published evidence for multi-agent gains is vendor-run on internal evaluations; say who ran a number before quoting it.
