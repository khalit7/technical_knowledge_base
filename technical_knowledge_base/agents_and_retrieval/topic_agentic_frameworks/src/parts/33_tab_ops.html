Everything around the loop, once it runs

The agent loop on your laptop calls one model with one key and prints what happened. A loop that serves real users needs four more things, and each one exists because something specific goes wrong without it: providers fail, so a gateway retries and falls back; nobody can see inside a run, so you record a trace; a prompt change quietly breaks things, so an eval gate checks every change; each conversation starts from nothing, so a memory layer carries facts forward. The last question is whether to run the loop at all, or rent one (a hosted runtime).

Gateway

A proxy between your code and the model providers. Your code speaks one API to it (usually OpenAI's chat format); it forwards each call to a provider and adds retries, fallbacks, timeouts, keys, budgets and a log of every call.

Trace and span

A span is one timed operation with a name and attributes (a model call, a tool call). A trace is the tree of spans for one request. OpenTelemetry (OTel) is the vendor-neutral standard for producing and shipping them.

Eval in the loop

A fixed set of tasks with automatic checks, run on every change to the agent (prompt, model, tools, harness version), with a gate that blocks the change if the checks get worse.

Memory layer

A store outside the context window plus two policies: what to write after a conversation and what to read back into the next one. Mem0, Zep and Letta are three different answers.

Gateways: one front door for every provider

The problem. A model provider is a remote service, and remote services fail in three ordinary ways: they refuse you because you sent too much (HTTP 429 Too Many Requests, often with a Retry-After header saying how many seconds to wait), they break (500, 503), or they stop answering (a hang, which only a timeout ends). An agent makes ten or fifty calls per task, so a 1% failure rate per call becomes a failed task surprisingly often. Every provider also has its own SDK, keys, prices and limits.

How a gateway works. Your code sends every call to the gateway with a model name you chose (here primary). The gateway maps that name to one or more real deployments, sends the call, and when it fails decides what to do: wait and retry the same deployment, fall back to another model group, or give up. It also checks the caller's virtual key (a key the gateway issued, so the real provider keys never leave it), its budget and its rate limit, and logs the cost of every call. LiteLLM's proxy, OpenRouter and the cloud vendors' AI gateways all do some version of this.

Keys, budgets and rate limits

A virtual key is issued by the gateway and stored in its database (LiteLLM needs Postgres for this; it ran in Docker here). Each key can be limited to some model names, a spending cap in dollars and a number of requests per minute. The gateway prices every call with its own price table (here an illustrative $1 per million input tokens and $5 per million output tokens, set in the config because the local model has no price) and adds it to the key's spend.

OpenRouter: the same idea, hosted (from its docs, not run here)

OpenRouter is a gateway you do not run: one OpenAI-compatible endpoint and one bill for models from many providers. Two kinds of routing, read from its documentation on 5 October 2026:

  • Model fallbacks: send a models list in priority order; "If the first model returns an error, OpenRouter will automatically try the next model in the list", triggered by context-length errors, moderation flags, rate limiting and downtime, and "Requests are priced using the model that was ultimately used, which will be returned in the model attribute of the response body." ({{Model fallbacks|https://openrouter.ai/docs/guides/routing/model-fallbacks}})
  • Provider routing for one model served by several providers: by default it prefers providers without significant outages in the last 30 seconds and, among the cheapest, picks one "weighted by inverse square of the price"; allow_fallbacks defaults to true; order, sort (price, throughput, latency), data_collection, zdr and max_price override it. ({{Provider routing|https://openrouter.ai/docs/features/provider-routing}})
  • Fees: "We pass through the pricing of the underlying providers; there is no markup on inference pricing"; buying credits costs "5.5% ($0.80 minimum)"; with your own provider keys (BYOK), "Pay-as-you-go includes $25,000 per month with no BYOK fee" and usage above that pays 5%. ({{FAQ|https://openrouter.ai/docs/faq}})
When a gateway earns its place
More than one provider or model; more than one team or app sharing keys and budgets; a need to log every call in one place; or failures you cannot afford to surface. It costs a network hop (the recorded overhead of the local proxy is in the counters above), one more service to run and secure, and a translation layer: provider features the common API does not express (Anthropic's cache breakpoints, for example) depend on the gateway passing them through.

Tracing: seeing inside a run

The problem. An agent run is dozens of model calls and tool calls deciding each other. When it fails, costs too much or takes too long, the final answer does not tell you which step did it. Logging every call to a file helps until two runs interleave or a call is retried inside a gateway.

How tracing works. Each operation opens a span when it starts and closes it when it ends; a span records its name, start and end times, a parent span and attributes (key-value pairs such as the model name and token counts). The spans of one task share a trace id and form a tree. An exporter in your process ships finished spans, usually over OTLP (the OpenTelemetry protocol), to a collector or straight to a backend that stores and draws them. The OpenTelemetry GenAI semantic conventions agree on names: a model call is a span named chat {model} with gen_ai.operation.name = "chat", gen_ai.usage.input_tokens, gen_ai.usage.output_tokens; a tool call is execute_tool {tool}; one agent run is invoke_agent {agent}. Message content is opt-in (gen_ai.input.messages, gen_ai.output.messages), because prompts carry private data. Every one of these is still marked "Development" (not stable), and in 2026 the conventions moved out of the main OpenTelemetry repository into their own ({{semantic-conventions-genai, commit cb10b70 of 5 Oct 2026|https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-spans.md}}; {{agent spans|https://github.com/open-telemetry/semantic-conventions-genai/blob/cb10b70c15c099ccab144e8316d934c9699da0fd/docs/gen-ai/gen-ai-agent-spans.md}}).

Three real traces, all collected by an OpenTelemetry Collector (0.139.0, in Docker) writing OTLP JSON to a file. The first two are the same plain agent loop as the {{Same agent, six ways|#t-same}} tab, run on the running example through the gateway above (its primary provider scripted to fail, so every model call fell back to the local model): once with spans written by hand following the conventions, once with only the official opentelemetry-instrumentation-openai-v2 package switched on. Cost attribution: which step spent the money

Tracing turns a bill into a breakdown. Evals in the loop: a gate on every change

The problem. You change the system prompt, swap the model, add a tool or upgrade the harness. The demo still works. Did anything get worse? One run cannot tell you, because the same agent on the same task varies run to run in turns, cost and even in what it fixes.

How it works. Keep a fixed set of tasks. For each change, run the agent on them (several times each), keep the recordings, and score each recording with checks: deterministic code where possible (do the tests pass, were the tests edited, how much did it cost), a model judge only where code cannot decide. A gate compares the candidate with the baseline and blocks the change if it regresses. The suite below has no model in it: it scores recorded Claude Code runs of the running example from this page and the sibling root, rebuilding each run's final code from its recorded diff and rerunning the visible tests and the six hidden checks from the {{Orchestration lab|#t-orch}} (derived from the docstrings; no run saw them).

Memory layers: what to carry from one conversation to the next

The problem. A model remembers nothing between calls; within a session the harness resends the history (see the sibling root's context management), but the next session starts empty. Pasting every past conversation back in works until it does not fit, costs input tokens on every call, and buries the one fact that matters. A memory layer is a store outside the context window with a write policy (what to keep after a conversation) and a read policy (what to put back in before the next answer).

Facts (Mem0)

After each exchange a model extracts short facts, then decides for each one against similar stored facts: ADD, UPDATE, DELETE or NOOP. Reads retrieve the most similar facts. The store holds the current text of each fact. ({{Chhikara et al., arXiv 2504.19413, 28 Apr 2025|https://arxiv.org/abs/2504.19413}}) That is the 2025 paper and Mem0 1.x, and what this tab implements; the open-source library since v2.0.0 (16 April 2026) only adds ("single-pass, ADD-only"), so a changed fact sits beside the old one. Mem0 scopes memories by user, agent and run ids; it has no layers with promotion between them.

Temporal graph (Zep, Graphiti)

Facts become edges between entities, each with the time it became true (t_valid) and, when a newer fact contradicts it, the time it stopped (t_invalid); nothing is deleted, and raw episodes are kept. ({{Rasmussen et al., arXiv 2501.13956, 20 Jan 2025|https://arxiv.org/abs/2501.13956}})

Paging (Letta, MemGPT)

The model manages its own memory with tool calls, like an operating system paging between RAM and disk: a small always-visible core block it edits, plus archival and recall stores it searches when needed. The Letta server was archived on 16 August 2026; the PyPI name letta now installs Letta Code. ({{Packer et al., arXiv 2310.08560, 12 Oct 2023|https://arxiv.org/abs/2310.08560}}; the analogy is with {{virtual memory|n:3f05c17b0d0d81a48892cea154ce950b}})

The experiment. One invented user, Sam, talks to an assistant in four sessions a week apart; two facts change on the way (the test command and the gateway) and one person leaves. Each memory layer was implemented minimally from its paper (about 200 lines in src/ops/code/mem.py; not the vendors' libraries), driven by the local model on Apple M1 Pro, and asked five questions a week after the last session, beside two baselines: no memory, and the full history pasted in. Build, use a framework, or rent
Renting the loop removes the sandbox, the state store, compaction and recovery from your list, and binds you to one vendor's models, tools and data handling. A framework keeps the model choice and the code in your hands; your own loop keeps everything, including the work. Interview questions

Your agent calls a provider that returns 429 with Retry-After: 2. What should the client do?
Wait at least 2 seconds (plus a little random jitter so many clients do not retry together), then retry; give up or fall back after a few attempts. LiteLLM does exactly this when the header is between 0 and 60 seconds, and otherwise uses exponential backoff, 0.5 · 2k seconds capped at 8, plus up to 0.75 s of jitter.
Why can retries make an outage worse?
Each retry is another request against the same rate limit and the same struggling service, so a 2-retry policy can triple the load exactly when capacity is lowest (a retry storm). Backoff with jitter, a cap on retries, cooldowns that take a failing deployment out of rotation, and a fallback to a different provider all limit it. The simulator above shows the 429 count growing with retries during an outage.
The gateway has an 8 s timeout, 2 retries and a fallback; the provider hangs for 20 s. How long does the user wait?
Three timeouts (24 s) plus the backoff waits plus the fallback's own latency: in the recording, against with no gateway at all. Per-attempt timeouts must come from measured latency, and the whole call needs one deadline.
What is a virtual key, and why can a budget be exceeded?
A key issued by the gateway, mapped to the real provider keys it never reveals, with its own allowed models, spend cap and rate limits. The budget check runs before each call against spend recorded so far, so the call that crosses the cap still runs: in the recording a $0.0008 cap ended at three calls costing $0.00099. Parallel calls do not widen this by default on LiteLLM 1.104.0, because each call reserves its worst-case cost before it starts; with disable_budget_reservation 20 simultaneous calls all got through at 4 times the budget ({{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}).
Name the spans you would emit for one agent run, following the OpenTelemetry GenAI conventions.
One invoke_agent {agent name} span as the parent; a chat {model} span (kind CLIENT) per model call with gen_ai.operation.name, gen_ai.provider.name, gen_ai.request.model, gen_ai.usage.input_tokens and output_tokens, finish reasons; an execute_tool {tool name} span (kind INTERNAL) per tool call with gen_ai.tool.name and gen_ai.tool.call.id. Message content only as opt-in attributes. Auto-instrumentation of the model client gives you the chat spans only.
How do you attribute an agent run's cost to its steps?
Put token counts on every model-call span, split by type (fresh input, cache write, cache read, output), multiply by the model's prices, and sum up the tree. On the recorded Claude Code run the span-level sum equals the run's reported total exactly; output and cache writes, not the reread history, were most of the cost.
What belongs in an eval gate for a coding agent?
Final-state checks (visible tests pass, hidden tests pass, tests not edited), trajectory checks (did it verify after its last edit, any permission denials, any dangerous commands), and budgets (cost, turns, time), each run several times per configuration and compared with a baseline distribution. Final-state checks alone pass an agent that got lucky without verifying.
Fact memory, a temporal graph, or a self-editing core block: when would you pick each?
Facts when you need cheap recall of current preferences and can tolerate losing history; a temporal graph when questions ask what changed and when, or facts expire (people leave, prices change); a self-edited core block when a few always-relevant facts should be in every prompt and the model can be trusted with tools. And none at all while the full history still fits in the context window.
