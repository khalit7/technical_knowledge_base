Workflows versus agents, taught by running them

An agent framework is mostly a way of deciding who chooses the next step: your code or the model. This lab takes one small job, fixing the two bugs in the running example, and does it six ways, each recorded for real on . Then it kills a workflow halfway and brings it back, and finally splits the job across several agents.

Workflow

"Systems where LLMs and tools are orchestrated through predefined code paths." Your code decides the order of steps; the model fills in each step. ({{Anthropic, Building effective agents, 19 Dec 2024|https://www.anthropic.com/engineering/building-effective-agents}})

Agent

"Systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." The model decides the next step, every turn, until it stops. (same source)

Orchestration

The code (yours or a framework's) that decides which model call or tool runs next, passes outputs between them, and decides when the whole thing is finished.

The input, the same for all six. A tiny Python library, textstats, with two planted bugs that its own test file catches: tokenize splits don't into don and t, and top_words does not break ties alphabetically. The task prompt, word for word: "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests."

Passing the visible tests is a low bar, so every result is also run against six hidden checks derived only from the two docstrings ("Apostrophes inside words are kept", "ties broken alphabetically"). No model saw them. The unfixed code passes of them.

How the five workflows were run. The model is Claude Haiku 4.5 (claude-haiku-4-5-20251001) called through claude -p with every built-in tool switched off (--tools "") and its system prompt replaced, so it can only return text. A short Python script (in src/orch/code/) does everything else: reads the files, pastes them into prompts, parses the code the model returns, writes it, runs the tests. The free agent is the same model inside Claude Code (version ) with its own Read, Edit, Write, Bash, Grep and Glob tools, choosing every step itself. Same model everywhere, so the differences below come from the orchestration.

Read every number here as one recording, not a benchmark
Each pattern ran once. Model calls vary from run to run by several seconds and thousands of thinking tokens; one specialist call in the routing run took 35 s where a similar call took 8 s. What the recordings show

    The rule this lab supports
    Anthropic's advice is to find "the simplest solution possible, and only increasing complexity when needed". Here a two-call chain and a free agent cost cents and seconds and fixed what the tests check. The two designs that also got the hidden checks right did so because something in them carried more knowledge of what "correct" means: a specialist prompt (routing) or a reviewer that hunted for edge cases (evaluator-optimizer). Orchestration did not add correctness by itself; information and verification did.

    Durable execution: kill it, resume it, rewind it

    The problem. A workflow lives in the memory of one process. If that process dies halfway (a deploy, an out-of-memory kill, a laptop lid), a plain script has lost everything: the model calls already paid for, the decisions already made. It starts again from zero and pays again. Long agent runs, and runs that wait hours for a human, make this the normal case rather than the rare one.

    The idea. After every step, write the whole state of the run to a database. Each saved snapshot is a checkpoint; all the checkpoints of one run share a thread id. To recover, load the newest checkpoint of that thread and carry on from the step after it. The same mechanism gives two more features for free: pausing for a human (save, exit, and resume days later with the human's answer) and time travel (load an older checkpoint, optionally edit it, and run forward again on a new branch).

    The recording. The prompt-chaining workflow above, rebuilt as a {{LangGraph|https://github.com/langchain-ai/langgraph}} StateGraph with five nodes and a SQLite checkpointer (langgraph , langgraph-checkpoint-sqlite ), run with durability="sync". A driver script started it, waited until the fix step's model call was in flight, and sent SIGKILL to the whole process group. Then it ran four more separate processes: resume, approve, rewind, approve. Every process is a fresh Python interpreter: the only thing that survives between them is the SQLite file.

    What the recording proves, line by line from the event log

      Three details that bite in production

      • When the checkpoint is written. LangGraph has three durability modes (from the pinned source, langgraph/types.py): "sync", "changes are persisted synchronously before the next step starts"; "async" (the default), "persisted asynchronously while the next step executes"; "exit", "persisted only when the graph exits". Under "exit" the kill above would have lost the diagnosis too. "async" is faster but a crash in the wrong millisecond can lose the last step.
      • A resumed node runs again from its first line. The interrupt() docstring says it plainly: "The graph resumes from the start of the node, re-executing all logic." The event log shows human_review starting twice. Anything with a side effect (sending an email, charging a card, writing a file) that sits before an interrupt, or inside a node that can crash, must be safe to run twice (idempotent) or must move into its own node. The same holds for the killed model call: it was paid for and its answer was lost, so the resumed process called the model again.
      • Nothing restarts the process for you. The checkpointer makes resuming possible; something else has to notice the crash and call invoke again with the same thread id (here, the driver script; in production a job queue, a supervisor, or a hosted platform).

      One agent or several

      The question. A multi-agent system splits a job across several model loops. The usual shape is orchestrator-workers with agents in place of single calls: a lead agent hands pieces of the job to subagents, each running its own loop in its own fresh context window, and reads back only their final reports. That separation is called context isolation: whatever a subagent reads (files, search results, dead ends) never enters the lead's context.

      The recording. The free agent from above, against the same model told by an appended system prompt to run the tests, launch one subagent per failing test with Claude Code's subagent tool, wait for their reports, and apply the fixes itself.

        Two published arguments, and where each applies

        For: Anthropic, 13 June 2025

        {{How we built our multi-agent research system|https://www.anthropic.com/engineering/multi-agent-research-system}}: a lead Claude Opus 4 with Claude Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%" on Anthropic's internal research evaluation. By their measurements agents use about 4 times the tokens of a chat and multi-agent systems about 15 times; token usage alone explained 80% of the variance on BrowseComp. Good fit: "heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools". Poor fit: "most coding tasks involve fewer truly parallelizable tasks than research", and domains that need shared context or many dependencies between agents.

        Against: Cognition, 12 June 2025

        {{Don't Build Multi-Agents (Walden Yan)|https://cognition.com/blog/dont-build-multi-agents}}: two principles, "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Their example: two subagents building parts of a Flappy Bird clone each guess a different style, and the parts do not fit. Recommended instead: one single-threaded agent, plus a model that compresses history for very long tasks. Subagents are acceptable when they only answer narrow, read-only questions, as in Claude Code.

        Interview questions

        What is the difference between a workflow and an agent?
        Who picks the next step. In a workflow your code fixes the sequence and the model fills in steps; in an agent the model chooses the next action each turn until it decides to stop. Workflows are cheaper to reason about, test and bound; agents handle problems whose steps cannot be listed in advance.
        Name the five workflow patterns and one use for each.
        Chaining (draft, then check, then polish), routing (send billing questions and technical questions to different prompts or models), parallelisation (sections at once, or several votes on one answer), orchestrator-workers (a planner that decides which files to change, workers per file), evaluator-optimizer (writer plus critic with clear criteria, such as tests or a rubric).
        Your 20-step workflow crashes at step 17. What do you need so it resumes at 17?
        State saved after every step to durable storage, keyed by a run id (a checkpointer and a thread id in LangGraph, an event history in Temporal); synchronous persistence or an accepted loss window; steps that are safe to run twice, because the crashed step will run again; and something that detects the crash and restarts the run.
        How do you add a human approval step to an agent?
        Pause before the risky action, persist the state, show the human the proposed action (here, a diff), and resume with their answer. In LangGraph: interrupt() inside a node with a checkpointer, then invoke(Command(resume=...)) on the same thread. Remember that the node re-runs from its start on resume.
        When would you use several agents rather than one?
        When the work splits into independent, mostly read-only pieces, or exceeds one context window, and the gain is worth several times the tokens (Anthropic reports about 15 times a chat). Not when the pieces must make consistent decisions about one shared artefact, where a single agent with good context management is usually better (Cognition). Measure both on your task.
        An evaluator-optimizer loop never converges. What do you check?
        Whether the evaluator's criteria are concrete and checkable (tests beat opinions), whether feedback actually reaches the generator, a maximum number of rounds, and cost per round: in this lab each review by a strict reviewer cost more than the generation it reviewed.
