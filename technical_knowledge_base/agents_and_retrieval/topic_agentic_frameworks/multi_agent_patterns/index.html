Multi-agent patterns: orchestrator-workers, handoffs, debate, when several agents help or hurt

When one model loop becomes several: who decides the next step, who sees what, and what it costs. In one screen

An agent is a model in a loop: the model asks for a tool, the program around it (the harness) runs the tool and pastes the result back, and this repeats until the model answers. A multi-agent system runs several such loops on one job. Every multi-agent pattern is an answer to two questions: who decides what happens next (code you wrote, or a model), and who sees what (does each loop get the whole history, or only a short brief and its own work).

The parent page measured the case against: on a small bug fix, a lead agent with two subagents cost several times a single agent and scored the same (Topic: agentic-frameworks, tab Orchestration lab, part "One agent or several"). This page asks when the answer flips, and measures each pattern on a task built for it:

Split reading across agents when the material does not fit comfortably in one context window, and let code do the splitting if you know the split in advance. Say exactly what counts before you split: parallel workers drew the boundary of the task differently from run to run (from no extra reports to 170), a second opinion from the same model confirmed them all, and a sharper brief removed them for less than the check cost.

1. From one loop to several

Start from one agent loop. Each model call sends the whole conversation so far (system prompt, tool definitions, every message and tool result) and gets back either tool requests or a final answer. Everything the call sends is its context; the most a model accepts in one call is its context window (200,000 tokens for Claude Haiku 4.5, the model of every Claude run here). The loop itself is the subject of Topic: agentic-harnesses; what goes into the context is Context engineering.

Several loops need four new words. A lead (or orchestrator, or supervisor) is a loop that starts others. A worker (or subagent) is a loop started by a lead, given a brief (the text that starts its conversation) and returning a report (its final answer). Context isolation means a worker's reading and dead ends stay in its own context; the lead receives only the report. A handoff passes the conversation itself to another agent, which carries on in its place. Pick a pattern to see its shape:

a model loopcode you wroteshared storesolid arrow: control (who starts whom); dashed: what is passed

Two families hide in that list. In a workflow your code decides the steps: fan-out, voting and a fixed pipeline are workflows that happen to call a model several times. In an agentic pattern a model decides: the lead chooses how to split, the triage agent chooses whom to hand to. Anthropic drew this line in December 2024 (workflows are "orchestrated through predefined code paths", agents "dynamically direct their own processes and tool usage", in Building effective agents); the parent page's section 1 compares its five workflow patterns.

Why it lost is the whole subject in miniature. The task fitted easily in one context window, so isolation saved nothing. There was little to do in parallel: two short investigations, then edits to the same file. And every subagent paid for its own start-up context (Claude Code's system prompt and tool definitions, about 13,000 tokens before any work: Context engineering, section 1) and re-read files the lead could have read once. Anthropic's own write-up says the same about this kind of job: "most coding tasks involve fewer truly parallelizable tasks than research" (Anthropic, 13 June 2025).

So the fair test needs a task with the opposite properties: much more to read than one context holds comfortably, split into pieces that do not depend on each other, and an answer that can be scored.

3. A task too big for one window

The audit. A generated package, fleetops, has modules ( of Python) with public functions. Each function's docstring makes one checkable promise: a default ("The default timeout is 30 seconds."), a unit ("Returns the elapsed time in milliseconds."), an order, a bound, what happens for a missing key, a number of attempts, a scale, or case handling. In functions spread over 14 modules the code breaks its own promise (timeout=60 under "defaults to 30 seconds"; lo <= x < hi under "both bounds are inclusive"). The job: find all of them, reading only (tools Read, Grep, Glob), and answer with a JSON list. The answer key never sits in the agent's folder. The generator is in this page's src/code/gen_audit.py with a fixed seed.

Why it does not fit. The module text alone is about tokens for Claude Haiku 4.5 (measured: the six fan-out prompts of section 4 carry exactly the module text, minus a measured -token frame each). Claude Code's Read tool adds a line number to every line, and the session starts with about 13,000 tokens of its own. Reading everything in full would put a Haiku agent at or past its 200,000-token window. A Sonnet 5.5 session that did read everything in full peaked at tokens per call (a different tokenizer, which counts the same text as more tokens: Context engineering, section 1).

Four designs, same model, same task MEASURED, three runs each (two for the blackboard, which section 5 varies further): one agent; a lead with six auditor subagents (Claude Code's Agent tool, defined with --agents; the lead is told to split the modules into six groups of eight and start all six at once); a fan-out workflow (section 4); and a blackboard without a lead (section 5). What happened to the single agent. It did not run out of window and it did not crash. It cut corners to stay inside the window: in the first run it opened all 48 modules but read of them only in part (only the first 50 or 100 lines of a module of to lines), in the second it read modules and grepped for the rest, and it batched up to six reads into one model call ( calls for the whole audit). Its findings were all correct; it simply never looked at half the bugs. Nothing in its answer says so: it reported a "comprehensive audit of all 48 modules". That is the failure mode isolation fixes: no single loop has to choose what to skip.

What the workers did. Each auditor read its eight modules in full (about 26,000 tokens of module text), and the lead's context never held a module: its largest call was tokens. Every orchestrator run found all 16. The cost was about the single agent's, and it took longer, because the lead waits for its slowest worker and then merges.

The other fix: a bigger window. The same single-agent prompt on Sonnet 5.5, whose window is 1,000,000 tokens, read every module in full in model calls and found all 16 with no other reports, for in (one run). When the material fits a larger model's window, that can be simpler than coordinating six agents; isolation is what you reach for when it does not, or when the cheap model is the one you can afford to run many times.

Predict, then open: the orchestrator found all 16 in every run. Did it ever report anything else?
Yes. In one of three orchestrator runs (and one of three fan-out runs) a worker also reported functions that promise "a fraction between 0 and 1" and return hits / total without checking that hits does not exceed total. That is not one of the eight contract kinds in the brief, but it is a defensible reading of the docstring, and the lead passed it through. Recall was perfect; the share of reports that were planted bugs was not. Section 5 tries to fix that with a check, and finds a better fix.
Go deeper. The Audit lab replays every run lane by lane, lists the six briefs each lead wrote, shows which planted bug each run found or missed, and the claim order on the blackboard. A worker that runs out of turns returns nothing to merge: on the Claude Agent SDK page (section 6, run s5) a subagent with maxTurns 4 stopped without a report, and Claude Code told the parent to use SendMessage, which was "disabled for this session". Give workers enough turns for the job, and have the lead check that every brief came back with a report.

4. Workflow or agents?

The lead in section 3 spent its first calls deciding something that was known before the run started: 48 files, six groups. A fan-out workflow moves that decision into code. A script splits the modules into six groups, pastes each group's text into one claude -p call with every tool switched off (--tools "") and the auditor's instructions as the system prompt, runs the six calls at once, and concatenates their JSON lists. No lead, no tool calls, no exploration: each call is one model turn.

It found all 16 in all three runs, at about of the orchestrator's mean cost and of its wall time MEASURED. Part of that is the prompt cache: runs 2 and 3 sent exactly the same six prompts as run 1 within the hour, so most of their input was read from cache at a tenth of the price. Run 1 alone, with nothing cached, cost , still of the orchestrator's mean. Two things make it cheaper. Each call reads its 26,000-odd tokens once instead of resending them on every tool round, and there is no Claude Code start-up context per worker. What it gives up is everything a model decides at run time: it cannot follow an import into a module it was not given, cannot notice a group is too big, and cannot re-split. When the split is known, write it in code; when finding the split is part of the job (research, where the next query depends on the last answer), you need a lead.

5. Blackboard: no lead, a shared store, and the limits of checking

A blackboard is a shared store that every agent reads and writes; nobody assigns work, each agent takes what it can do next. The idea is older than language models: Hearsay-II, a speech-understanding system built at Carnegie Mellon from 1971 to 1976, had independent "knowledge sources" posting hypotheses to a shared blackboard (Erman, Hayes-Roth, Lesser and Reddy, Computing Surveys, June 1980). Today's versions: Claude Code agent teams share a task list in which "Task claiming uses file locking to prevent race conditions" (agent teams docs); Anthropic's Fermat's Last Theorem run coordinated through a graph of theorem statements; Agora keeps every result as a Git commit that others re-run.

Our board MEASURED. Six Haiku agents, no lead, a 29-line Python script as the store (in src/code/run_audit.py): python3 board.py claim w3 hands out the next unclaimed module using an exclusive file create (the operating system guarantees only one agent can create a given file, so two agents can never claim the same module), and post appends a finding. The agents may run only that script (--allowedTools "Bash(python3 board.py:*)"). Work balanced itself: faster agents claimed more modules (Audit lab lists who claimed what). Every board run found all 16 planted bugs.

But the board also collected other reports in its two plain runs. Read them and they fall into two kinds (classified by their stated reason): "returns hits / total with no check, so it can exceed 1 although the docstring promises a fraction" and "the docstring says it raises ValueError on malformed input, but nothing raises". Neither is one of the eight contract kinds the brief listed, and the first is only wrong for impossible inputs, but both are defensible readings of the docstrings; the second is a flaw in our generator, which adds that sentence without code to match. So they are not hallucinations: they are workers drawing the boundary of the task in different places. The single agent and most orchestrator and fan-out runs never reported them; one orchestrator run and one fan-out run did, and so did of the board runs with the original brief.

Does a check round fix it? We took the 186 findings one board run had posted and gave them to six fresh Haiku checkers, each claiming findings it had not posted, twice: once shown the auditor's reason, once blind (only the file and function, asked to decide for itself). Then, separately, we ran the board again with a sharper brief that names what does not count ("Do not report missing input validation, exceptions the code does not raise, thread safety, or results that are wrong only for impossible inputs").

planted bug keptother report keptother report rejected

Both check rounds kept every one of the findings, for each. Showing the claim was not the problem: the blind checkers, reading the same docstring, reached the same broad reading on their own. A second opinion from the same model shares the first one's interpretation, so it confirms rather than checks. The sharp brief removed the extra reports at the source: planted bugs found and other reports, at per run.

What actually checks
A verifier that does not share the workers' judgement: an answer key or test suite (our hidden checks), a proof checker (Lean, in the FLT run: "computer-checked"), re-execution by someone else (Agora's verifications by "an account other than the target's author"), or a person. A model checker helps against random slips, not against a shared reading of an ambiguous brief. Anthropic's advice for briefs is the cheaper fix: "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" (Anthropic, 13 June 2025).

Why did the board drift more than the orchestrator? Its agents posted each finding the moment they saw it, one shell command per line, with nobody assembling a final list; the orchestrator's workers each wrote one considered JSON answer. Our runs cannot separate that from chance (two or three runs per design), so treat it as a hypothesis.

6. Handoffs against agents-as-tools

A support desk is the textbook case for a handoff: a triage agent reads the customer's message and transfers the conversation to the right specialist, who then owns it. The OpenAI Agents SDK makes this its native primitive DOCUMENTED: "Handoffs are represented as tools to the LLM", named transfer_to_<agent>, and the receiving agent "gets to see the entire previous conversation history" (handoffs docs). The alternative is agents as tools: a manager calls each specialist like a function and keeps the conversation. The SDK's own docstring for Agent.as_tool states the two differences: "In handoffs, the new agent receives the conversation history. In this tool, the new agent receives generated input," and "In handoffs, the new agent takes over the conversation. In this tool, the new agent is called as a tool, and the conversation is continued by the original agent" (openai-agents 0.23.1, agents/agent.py).

The run LOCAL MODEL. One customer message with two problems: "I was charged twice for invoice 1042 and I want the duplicate refunded. Also your app has crashed every time I log in since this evening." Billing has lookup_invoice and refund_charge; tech has check_status; all three tools return fixed fake data. Three designs on openai-agents 0.23.1 with Qwen3-4B-Instruct-2507 served locally: a triage agent with handoffs to both; the same with the specialists also allowed to hand off to each other ("mesh"); and a manager with both specialists as tools. What the recordings show. The triage model asked for both transfers in one reply, which is the right reading of a two-problem message. A conversation can only have one owner, so the SDK took the first and answered the second with a tool result, "Multiple handoffs detected, ignoring this one." (in run_internal/turn_resolution.py, actual_handoff = run_handoffs[0]). The crash was never looked at, in every handoff run. Allowing the specialists to hand off to each other did not help: billing had the transfer tool and an instruction to use it, and did not. The manager design consulted both specialists in every run, at about the prompt tokens.

All designs share one failure that has nothing to do with the pattern: no run ever called refund_charge, yet of replies told the customer the refund was under way. A 4B model is weak at acting before it speaks; the lesson for any pattern is to check the actions in the trace, not the words in the reply.

When to use which
Use a handoff when routing is the job and the specialist should own the rest of the conversation (one topic per conversation, as in a phone menu). Use agents as tools when one request can need several specialists, or when the user must keep talking to one voice. The SDK docs say the same: agents as tools "when a specialist should help with a bounded subtask but should not take over the user-facing conversation" (orchestrating multiple agents). Handoff history can be trimmed with an input_filter, and nest_handoff_history (an opt-in beta, off by default in 0.23.1) compacts earlier turns into summaries.

7. When it hurts: two writers, one feature

Cognition's warning is about writing: "Actions carry implicit decisions, and conflicting decisions carry bad results." An implicit decision is a choice the spec did not make, such as what to call a field. Two agents writing halves of one feature in parallel each make those choices alone, and nobody notices until the halves meet.

The test MEASURED. Starting from textstats with its bugs fixed, two modules must fit together: one computes something from a text, the other formats it. Three designs, three runs each, all Claude Haiku 4.5 in Claude Code (tools Read, Write, Edit, Bash limited to python3, Glob, Grep): one agent writes both; two parallel writers, each in its own copy of the repository, told the other half exists but that they cannot see it; and contract first, where one tools-off call writes the shared data shape before the same two parallel writers start. A hidden check imports both halves from the merged tree and calls one on the other's output. We ran two specs:

  • Pinned: "build_report(text) returns the word count, the number of distinct words, and the top 3 words with their counts; render(report) makes a Markdown table." The wording nearly names the fields.
  • Open: "profile(text) describes a text's vocabulary: how long it is, how varied it is, and which words dominate it; card(p) formats it as a plain-text card, one line per item." Every name is left to the writer.
SpecDesignHalves fit (of 3)Mean costMean wall time

What happened. With the pinned spec the two writers chose the same field names every time: the same model reading the same sentence makes the same guess, so the "conflict" never arose. With the open spec the parallel halves fitted in of 3 runs. In the others nothing crashed: the formatter had been written defensively (if "length" in p:), so the card silently printed only the line whose name both writers happened to share, and the word count and variety vanished. A defensive guess turned a loud KeyError into quiet data loss. Run 3 was the mirror image of run 1: the names the formatter expected in run 1 were the ones the profile used in run 3, and the reverse. The same model, asked twice, decides differently, which is why "it worked when I tried it" means little here.

Writing the contract first fixed it in every run, for one extra short call and about of extra wall time on average (the writers also spent longer following it). The single agent never had the problem, because one context holds both decisions. This is the general rule: parallel writers need their implicit decisions made explicit before they start (an interface, a schema, a test that pins the shape), or a single writer.

Predict, then open: which would have caught the silent loss: the writers' own tests, or the hidden check?
Only a check across the seam. Each writer could test its half only against its own idea of the other half, so any test it wrote would pass. The hidden check called card(profile(...)) and looked for the word count in the output. Nous Research's 1,393-agent refactor met the same wall at scale: the repository's tests passed while reviewers found exception handling changed at about 65 sites (section 10).

8. Debate and voting

When the job is one hard answer rather than a lot of reading, the multi-agent move is to ask several times and combine. Voting (self-consistency) samples the same question independently several times and takes the most common answer. Debate lets solvers read each other's answers and reasoning and revise; Du et al. used "three agents with two rounds of debates" and reported arithmetic accuracy rising from 67.0% for one agent to 81.8% (Du et al., May 2023). A judge reads several answers and picks one. The catch the later papers found: compare against voting at equal cost, and most of debate's gain belongs to voting ("Majority Voting alone accounts for most of the performance gains typically attributed to MAD", Debate or Vote, Aug 2025; earlier Smit et al., Nov 2023 and Wang et al., Feb 2024).

Our test MEASURED. knights-and-knaves puzzles with nine islanders each (knights always tell the truth, knaves always lie; every puzzle has exactly one solution, checked by brute force), for example "Cleo says: 'If Ivo is a knight, then Fay is a knave.'" and "Fay says: 'Exactly 8 of us 9 are knights.'" Claude Haiku 4.5 with tools off. What happened. One sample solved puzzles. Voting over three samples solved , over five . Debate solved and the judge , the judge for about of the tokens of a five-sample vote. In the debate round wrong solver answers were corrected and right ones were talked out of it; after one round all three solvers agreed on of the 30 puzzles (before it, on ), of them unanimously wrong.

How to read it. Voting explains most of the improvement over one sample (from to ), as the Debate or Vote paper found. Reading other solvers' work added the last couple of puzzles here, and there is a reason it can on this task: a proposed assignment of knights and knaves can be checked statement by statement, so a solver shown a correct solution can verify it, which is easier than finding it. Where checking is no easier than solving (open questions, judgement calls), expect less. And 30 puzzles is a small sample: a two-puzzle gap is within noise. The judge result says something practical: when you already have several samples, one call that checks them can be cheaper than more samples.

The other side of agreement
Debate converges: after one round the solvers were unanimous on every puzzle. That is efficient when the majority is right and dangerous when it is not, because unanimity looks like confidence. Keep a verifier outside the debate when you can (here, the brute-force solver).

9. Token and quality accounting

Every comparison on this page reduces to a few sums, and knowing them lets you predict a design's bill before you run it.

tokens processed = ∑calls (context sent by that call)
context
start-up prompt + tool definitions + every message so far in that loop

In one loop the context grows with every step, so the sum grows roughly with the square of the number of steps: a loop of T calls that adds g tokens per call and starts at S processes about T·S + g·T2/2. Split the same reading across k isolated workers and the second term shrinks to about g·T2/(2k), while the first stays (every worker pays its own start-up) and the lead adds its own calls. That is the argument for isolation in one line, and also why it lost on the small bug fix: when T is small the square term is small, and only the extra start-ups remain.

Prompt caching changes which term costs money. A token re-sent from cache costs a tenth of a fresh one on Haiku 4.5, and Claude Code writes its cache with the one-hour lifetime at twice the input price (Context engineering, section 2). So the growing re-reads are cheap, and the bill is set by what is new: content written to the cache for the first time, and output, including the model's hidden thinking.

cost = pin·fresh + pwrite·written + pread·cached + pout·output
Haiku 4.5
$1 fresh, $2 written (1-hour cache; $1.25 for 5-minute), $0.10 cached, $5 output, per million tokens (list prices read 5 Oct 2026)

Reading the audit's bill. The single agent's tokens are mostly cache reads, the square-law term, and they are cheap. The orchestrator and the fan-out workflow write each worker's modules to the cache once (six fresh contexts instead of one growing one), and every worker thinks before answering: output is the largest single item in both (for the fan-out workflow partly because its repeated prompts were cache hits, section 4). The blackboard designs cost most: every agent makes several model calls per module (claim, read, post each findings line), each re-sending its growing history, and the check round starts six more loops. Quality has to be counted the same way: recall (planted bugs found out of 16) and precision against the key (planted bugs out of everything reported). A design that reports 186 items to find 16 has perfect recall and a precision under 10%; someone has to read the other 170 and decide which of them matter.

11. Choosing

Ask these in order; the first "no" is your answer.

  1. Does the material overflow one context, or is the work wide? If one agent can hold it and the steps depend on each other, stay single (section 2). If a bigger window fits it, try that before agents (section 3, Sonnet).
  2. Are the pieces independent, with nothing written in common? Parallel reading splits well; parallel writing of one artefact needs a contract first (section 7) or one writer.
  3. Do you know the split in advance? Then it is a workflow: split in code, fan out, merge in code (section 4). Use a lead only when finding the split is part of the job.
  4. Is the brief exact, and who checks the merged result? Name what does not count, and budget a verifier that does not share the workers' judgement (an answer key, tests, Lean, a person) before you add workers (section 5). Every parallel design here reported things outside the brief in some run, and same-model checks kept them all.
  5. Is the answer worth several times the tokens? On our audit the orchestrator cost about one agent; Anthropic reports about 15 times chat for its research system.
  6. Can you see every agent? Without per-agent traces you cannot tell which worker invented a finding. LLM observability covers how.

For routing a conversation (support desks, intake), choose between a handoff and agents-as-tools by one question: should the specialist own the rest of the conversation, or answer one bounded question? Section 6 shows what each passes along.

Common mistakes

Splitting a task that fits in one context
Each worker pays a full start-up context (about 13,000 tokens in Claude Code) and often re-reads what the lead read. The parent page's bug fix cost as much with subagents, for the same result.
Using a lead model to make a split you already know
If the pieces are files, rows or documents you can list, split them in code and fan out (section 4). A lead earns its cost only when finding the split is part of the job.
Trusting a merge that only concatenates
A lead that pastes worker reports together passes through whatever each worker decided to include. One orchestrator run here reported 43 items for 16 planted bugs, because one worker also flagged unchecked ratios.
Checking a model with the same model
Haiku checkers kept all 186 findings of one board run, whether shown the auditor's reasoning or not (section 5): they share its reading of the brief. Fix the brief, or use a verifier that does not share the judgement (tests, an answer key, Lean, a person).
Parallel writers without a contract
Two halves written apart fit only when the spec happens to name everything. A defensive reader (if key in p) turns the mismatch into silent data loss (section 7).
Expecting a handoff to handle two requests
A conversation has one owner at a time. The OpenAI Agents SDK keeps the first transfer and answers the rest with "Multiple handoffs detected, ignoring this one." Use agents as tools when one message can need two specialists (section 6).
Calling debate a win without a voting baseline
Compare against majority voting over the same number of independent samples, at equal tokens. Most published gains attributed to debate shrink against that baseline (section 8).
Reading the agent's own summary as coverage
The single agent reported a "comprehensive audit of all 48 modules" after reading half of them partially. Check coverage from the trace (which files were read, how much of each), not from the report.
Summing result.usage for cost
In Claude Code, result.usage leaves out subagent calls; result.modelUsage and total_cost_usd include them (Claude Code, taken apart, section 7).

Interview questions

When does a multi-agent system beat a single agent?
When the material exceeds what one context holds well and splits into independent pieces (wide reading: research, audits, review). The win is coverage and wall time, bought with several times the tokens. It loses when the task fits one context or the pieces must agree on decisions.
What is context isolation, and what does it cost?
Each worker reads in its own window and returns only a report, so no loop has to hold everything. It costs a start-up context per worker, duplicated reading, and lost detail at the report boundary.
Handoff or agent-as-tool?
Handoff when the specialist should own the rest of the conversation and sees the full history; agent-as-tool when the manager keeps the conversation and the specialist answers one bounded, self-contained question from a generated input.
Why can tokens processed grow with the square of the steps?
Each call resends the whole history, so call t sends about S + g·t tokens; summed over T calls that is T·S + g·T²/2. Isolation divides the square term by the number of workers. Caching makes the re-sent part cheap per token but not free.
How would you verify a multi-agent system's output?
Measure recall and precision against a labelled set; check across seams (call one part on another's output); re-derive findings blind or with a non-model verifier; inspect per-agent traces for coverage. Do not use an agent's own confidence or summary.
Debate or voting?
Start with voting: it is cheaper per round, needs no prompt growth, and at equal budget it accounts for most of the gains attributed to debate in published comparisons. Add debate only if it beats voting on your data.
How do agents coordinate without a lead?
Through a shared store with atomic operations: claim a task with a lock or an exclusive create, post results, read others'. Claude Code agent teams use file-locked task claims; Agora uses a Git graph with cross-verification.
Design a research assistant that reads 500 documents.
A fan-out workflow if the documents are known: code splits them, parallel calls extract per document, code merges, a check step verifies each extracted claim blind. Add a lead only if what to read next depends on what was found. Trace every agent; report recall and precision on a labelled sample; budget tokens per worker.

How the runs were made

  • Every run: claude -p <task> --output-format stream-json --verbose --no-session-persistence --setting-sources project --strict-mcp-config --model haiku in a fresh copy of the corpus; the answer key was never in the agent's folder. Claude Code 2.1.291 on 6 October 2026.
  • One agent: --tools "Read,Grep,Glob". Lead + 6 auditors: --tools "Read,Grep,Glob,Agent", an auditor subagent defined with --agents (tools Read, Grep, Glob; model haiku) and --forward-subagent-text so the subagents' messages are in the recording; the lead was told to split into six groups of eight and start all six in one message. Fan-out: six --tools "" calls started together by a Python script, each with eight modules pasted in. Blackboard: six agents with --tools "Read,Bash" and --allowedTools "Bash(python3 board.py:*)"; board.py claims a module with an exclusive file create (so two agents can never claim the same one) and appends findings to a shared file. The check round: six more agents claim findings to check, never their own.
  • Check only: the 186 findings posted by "Blackboard 2" copied onto a fresh board and checked by six new agents, shown the auditor's reason or blind (file and function only). Sharp brief: the blackboard with one extra sentence in the task and the agents' instructions: "Only these eight kinds count: a default value, a unit, an ordering, a bound (inclusive or exclusive), missing-key behaviour, a number of attempts, a scale (fraction or percentage), case handling. Do not report missing input validation, exceptions the code does not raise, thread safety, or results that are wrong only for impossible inputs (for example hits greater than total)."
  • The modules are about 528 KB; the repository copies of the recordings replace module text with a placeholder (size kept), because src/code/gen_audit.py regenerates it exactly. Everything the models wrote is kept.
  • Several of this page's experiments ran at the same time on one subscription, and other agents were using it too: wall times are real but include queueing. The extreme case is "Blackboard + blind check 1": four of its six agents waited about 16 minutes for their last model call after the board answered DONE; nothing in the recording explains the wait, so read that run's wall time as an outlier.
