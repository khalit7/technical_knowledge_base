5. Blackboard: no lead, a shared store, and the limits of checking

A blackboard is a shared store that every agent reads and writes; nobody assigns work, each agent takes what it can do next. The idea is older than language models: Hearsay-II, a speech-understanding system built at Carnegie Mellon from 1971 to 1976, had independent "knowledge sources" posting hypotheses to a shared blackboard ({{Erman, Hayes-Roth, Lesser and Reddy, Computing Surveys, June 1980|https://mas.cs.umass.edu/Documents/Erman_Hearsay80.pdf}}). Today's versions: Claude Code agent teams share a task list in which "Task claiming uses file locking to prevent race conditions" ({{agent teams docs|https://code.claude.com/docs/en/agent-teams}}); Anthropic's Fermat's Last Theorem run coordinated through a graph of theorem statements; {{Agora|n:3e25c17b0d0d81399738c3e65f4bf900}} keeps every result as a Git commit that others re-run.

Our board MEASURED. Six Haiku agents, no lead, a 29-line Python script as the store (in src/code/run_audit.py): python3 board.py claim w3 hands out the next unclaimed module using an exclusive file create (the operating system guarantees only one agent can create a given file, so two agents can never claim the same module), and post appends a finding. The agents may run only that script (--allowedTools "Bash(python3 board.py:*)"). Work balanced itself: faster agents claimed more modules ({{Audit lab|#t-audit}} lists who claimed what). Every board run found all 16 planted bugs.

But the board also collected other reports in its two plain runs. Read them and they fall into two kinds (classified by their stated reason): "returns hits / total with no check, so it can exceed 1 although the docstring promises a fraction" and "the docstring says it raises ValueError on malformed input, but nothing raises". Neither is one of the eight contract kinds the brief listed, and the first is only wrong for impossible inputs, but both are defensible readings of the docstrings; the second is a flaw in our generator, which adds that sentence without code to match. So they are not hallucinations: they are workers drawing the boundary of the task in different places. The single agent and most orchestrator and fan-out runs never reported them; one orchestrator run and one fan-out run did, and so did of the board runs with the original brief.

Does a check round fix it? We took the 186 findings one board run had posted and gave them to six fresh Haiku checkers, each claiming findings it had not posted, twice: once shown the auditor's reason, once blind (only the file and function, asked to decide for itself). Then, separately, we ran the board again with a sharper brief that names what does not count ("Do not report missing input validation, exceptions the code does not raise, thread safety, or results that are wrong only for impossible inputs").

Both check rounds kept every one of the findings, for each. Showing the claim was not the problem: the blind checkers, reading the same docstring, reached the same broad reading on their own. A second opinion from the same model shares the first one's interpretation, so it confirms rather than checks. The sharp brief removed the extra reports at the source: planted bugs found and other reports, at per run.

What actually checks
A verifier that does not share the workers' judgement: an answer key or test suite (our hidden checks), a proof checker (Lean, in the FLT run: "computer-checked"), re-execution by someone else (Agora's verifications by "an account other than the target's author"), or a person. A model checker helps against random slips, not against a shared reading of an ambiguous brief. Anthropic's advice for briefs is the cheaper fix: "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries" ({{Anthropic, 13 June 2025|https://www.anthropic.com/engineering/multi-agent-research-system}}).

Why did the board drift more than the orchestrator? Its agents posted each finding the moment they saw it, one shell command per line, with nobody assembling a final list; the orchestrator's workers each wrote one considered JSON answer. Our runs cannot separate that from chance (two or three runs per design), so treat it as a hypothesis.
