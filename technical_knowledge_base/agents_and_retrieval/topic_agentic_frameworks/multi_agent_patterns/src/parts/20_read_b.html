Why it lost is the whole subject in miniature. The task fitted easily in one context window, so isolation saved nothing. There was little to do in parallel: two short investigations, then edits to the same file. And every subagent paid for its own start-up context (Claude Code's system prompt and tool definitions, about 13,000 tokens before any work: {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, section 1) and re-read files the lead could have read once. Anthropic's own write-up says the same about this kind of job: "most coding tasks involve fewer truly parallelizable tasks than research" ({{Anthropic, 13 June 2025|https://www.anthropic.com/engineering/multi-agent-research-system}}).

So the fair test needs a task with the opposite properties: much more to read than one context holds comfortably, split into pieces that do not depend on each other, and an answer that can be scored.

3. A task too big for one window

The audit. A generated package, fleetops, has modules ( of Python) with public functions. Each function's docstring makes one checkable promise: a default ("The default timeout is 30 seconds."), a unit ("Returns the elapsed time in milliseconds."), an order, a bound, what happens for a missing key, a number of attempts, a scale, or case handling. In functions spread over 14 modules the code breaks its own promise (timeout=60 under "defaults to 30 seconds"; lo <= x < hi under "both bounds are inclusive"). The job: find all of them, reading only (tools Read, Grep, Glob), and answer with a JSON list. The answer key never sits in the agent's folder. The generator is in this page's src/code/gen_audit.py with a fixed seed.

Why it does not fit. The module text alone is about tokens for Claude Haiku 4.5 (measured: the six fan-out prompts of section 4 carry exactly the module text, minus a measured -token frame each). Claude Code's Read tool adds a line number to every line, and the session starts with about 13,000 tokens of its own. Reading everything in full would put a Haiku agent at or past its 200,000-token window. A Sonnet 5.5 session that did read everything in full peaked at tokens per call (a different tokenizer, which counts the same text as more tokens: {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, section 1).

Four designs, same model, same task MEASURED, three runs each (two for the blackboard, which section 5 varies further): one agent; a lead with six auditor subagents (Claude Code's Agent tool, defined with --agents; the lead is told to split the modules into six groups of eight and start all six at once); a fan-out workflow (section 4); and a blackboard without a lead (section 5). What happened to the single agent. It did not run out of window and it did not crash. It cut corners to stay inside the window: in the first run it opened all 48 modules but read of them only in part (only the first 50 or 100 lines of a module of to lines), in the second it read modules and grepped for the rest, and it batched up to six reads into one model call ( calls for the whole audit). Its findings were all correct; it simply never looked at half the bugs. Nothing in its answer says so: it reported a "comprehensive audit of all 48 modules". That is the failure mode isolation fixes: no single loop has to choose what to skip.

What the workers did. Each auditor read its eight modules in full (about 26,000 tokens of module text), and the lead's context never held a module: its largest call was tokens. Every orchestrator run found all 16. The cost was about the single agent's, and it took longer, because the lead waits for its slowest worker and then merges.

The other fix: a bigger window. The same single-agent prompt on Sonnet 5.5, whose window is 1,000,000 tokens, read every module in full in model calls and found all 16 with no other reports, for in (one run). When the material fits a larger model's window, that can be simpler than coordinating six agents; isolation is what you reach for when it does not, or when the cheap model is the one you can afford to run many times.

Predict, then open: the orchestrator found all 16 in every run. Did it ever report anything else?
Yes. In one of three orchestrator runs (and one of three fan-out runs) a worker also reported functions that promise "a fraction between 0 and 1" and return hits / total without checking that hits does not exceed total. That is not one of the eight contract kinds in the brief, but it is a defensible reading of the docstring, and the lead passed it through. Recall was perfect; the share of reports that were planted bugs was not. Section 5 tries to fix that with a check, and finds a better fix.

4. Workflow or agents?

The lead in section 3 spent its first calls deciding something that was known before the run started: 48 files, six groups. A fan-out workflow moves that decision into code. A script splits the modules into six groups, pastes each group's text into one claude -p call with every tool switched off (--tools "") and the auditor's instructions as the system prompt, runs the six calls at once, and concatenates their JSON lists. No lead, no tool calls, no exploration: each call is one model turn.

It found all 16 in all three runs, at about of the orchestrator's mean cost and of its wall time MEASURED. Part of that is the prompt cache: runs 2 and 3 sent exactly the same six prompts as run 1 within the hour, so most of their input was read from cache at a tenth of the price. Run 1 alone, with nothing cached, cost , still of the orchestrator's mean. Two things make it cheaper. Each call reads its 26,000-odd tokens once instead of resending them on every tool round, and there is no Claude Code start-up context per worker. What it gives up is everything a model decides at run time: it cannot follow an import into a module it was not given, cannot notice a group is too big, and cannot re-split. When the split is known, write it in code; when finding the split is part of the job (research, where the next query depends on the last answer), you need a lead.
