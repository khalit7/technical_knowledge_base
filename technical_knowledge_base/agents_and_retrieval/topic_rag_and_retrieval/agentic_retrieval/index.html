A retrieval pipeline searches once, with the user's words, and hands the top results to a language model. This page is about what happens when that is not enough and something has to decide what to read: the model itself, in a loop (agentic retrieval); a fixed program that splits the question; a cheap classifier in front (a router); or nobody, because the whole corpus goes into the window (long context). The same machinery, pointed at an agent's own past, is agent memory.

The parent page, Topic: rag-and-retrieval, introduces these ideas in its section 7 and its Agentic lab tab measures five strategies on 200 HotpotQA questions with Qwen3 models running on this laptop, with a replay of single trajectories. This page reuses those recorded runs (nothing is re-generated) and goes further: what the second search needs, the iterative methods one by one, retrieval evaluators and routers measured on the same questions, where along a trajectory the answer gets lost, deep-research systems read in their source code, the real cost of long context on this machine, and retrieval over an agent's own history. GraphRAG has its own child page, GraphRAG and structured retrieval; search quality itself (chunking, hybrid search, reranking) is on The retrieval pipeline and Rerankers and late interaction.

The running example, and how to read the numbers
The topic's multi-hop set: 200 questions from HotpotQA's distractor dev split (160 "bridge" questions, where the second paragraph can only be found once the first is read, and 40 "comparison" questions about two named things), each needing two gold paragraphs, searched over a corpus of 9,760 Wikipedia paragraphs (the gold and distractor paragraphs of 1,000 dev questions; the root's data README). The search tool is bge-small-en-v1.5 (a 33 M-parameter embedding model) with exact search; the generator is Qwen3-1.7B quantised to 4 bits (Q4_K_M) in llama.cpp's llama-server on the laptop's GPU, temperature 0. Answers are scored with HotpotQA's official exact match (EM) and token F1. Every measured number is labelled measured on Apple M1 Pro; small models answer worse than frontier ones, so read the absolute numbers as a small-model case and the gaps and costs as what the experiment shows. A number that needs a generator run this page has not made yet sits in a dashed pending box with the command that will fill it.

Four findings carry the page, all measured on the same 200 questions:

  1. The first hop is free; the second hop is a query-writing problem. The question finds one gold paragraph in its top 3 for 198 of 200 questions; for the 78 that still miss the second, searching again with the sentence a perfect reasoning step would have written finds it in the top 3 for 37, the question plus that sentence for 50, and the bridge entity's exact name for all 78. The 1.7B agent's own second queries found it for 18 of 55 (section 2).
  2. The loop helps this small model more by reading less at a time than by finding more. The agent saw both gold paragraphs for only 114 questions against 164 for a single top-10 search, but when both were in front of it, it answered right 59% of the time against 32% for the top 10 and 28% with the question's own 10 paragraphs in the window (section 6).
  3. On all-multi-hop traffic, routers and retrieval evaluators barely beat a coin. The best measured router reaches F1 0.346 against 0.339 for sending a random half to the agent, while a perfect chooser among the recorded strategies would reach 0.641 (sections 4 and 5).
  4. Long context is paid for in seconds here, and the attention term grows with the square of the window. A prefill model fitted to 3,813 recorded calls predicts 9.14 s for 7,611 tokens (the production child measured 9.34 s independently) and about 77 s for a full 32k window, two thirds of it attention (section 8).

1. Retrieval as a tool

The problem. A pipeline decides everything before it has seen a single result: one query, the user's words, a fixed k. If that search misses, nothing notices. Handing the search to the model lets it read a result and react to it.

How it works, from zero. A tool is an ordinary function (here: search a paragraph collection) that the harness (the program running the model) executes on the model's behalf. The model is shown a tool description (a name, a sentence saying what it does and returns, and its parameters, usually as a JSON schema). Instead of answering, the model may emit a tool call: structured text naming the tool and its arguments. The harness parses it, runs the search, and appends the result to the conversation as an observation. The model is called again with everything so far, and decides again: another call, or a final answer. The loop ends when the model answers or when the harness's step budget (a maximum number of calls) runs out. This is the reason-then-act loop of ReAct; Topic: agentic-harnesses covers harnesses in general, and Context engineering what to keep in the window.

The tool every agent on this page calls, runnable on its own (the page's src/scripts/demo_tool.py; real output, paragraphs cut to 160 characters for display):

def search(query, k=3, exclude=()):
    """bge-small exact search over the 9,760 paragraphs; already-seen paragraphs are skipped"""
    return A.ranking(query, exclude)[:k]

first = search(q["question"])
second = search("Russian Civil War end date", exclude=first)

Excluding already-seen paragraphs is a design choice of the root's tool: it forces every search to show something new.

Two consequences: the description is the main lever on query quality (say what the tool returns and how a good query looks: "a short query naming one entity or fact"), and every tool added to an agent is paid on every call.

Budgets and stopping

The root's agent may search at most 4 times. What it did with that freedom, over the 200 questions (measured, from the recorded trajectories):

  • It saw both gold paragraphs in 114 trajectories: after the first search in 32, the second in 72, the third or fourth in 10. It searched again after already having both 28 times.
  • It stopped too early (answered without ever seeing the second gold paragraph) in 75 trajectories, 52 of them wrong. Stopping is a judgment the model makes from its own reading, and a small model is overconfident.
  • It repeated a query in 28 trajectories and used the whole budget in 28 (the same trajectories, mostly: stuck loops that only the budget ended); 17 times it wrote no parseable action at all.

The root's table of F1 by number of calls makes the same point from the other side: questions the agent needed 4 or 5 calls for scored far worse than those it finished in 2 or 3. Long trajectories are mostly failing trajectories, so a tighter budget may cost little accuracy. Measured with budgets of 1, 2, 3 and 6: pending: run_pending.sh budgets.

How to check it on your system: log every call's prompt tokens and every search's query and results; plot calls per question, and count repeated queries, unparseable steps and budget hits. They are cheap to compute and they find most loop bugs.

2. The second hop: what the next query needs

The problem. A bridge question ("Where was the music festival Billy McFarland was charged with wire fraud for supposed to take place?") names the first thing (Billy McFarland) but not the second (the Fyre Festival). The question finds the first paragraph easily. The second paragraph is about something the question never names, so it ranks low: in the root's Agentic lab, both gold paragraphs are in a single search's top 3 for 122 of 200 questions, and at least one for nearly all. Here, one gold paragraph is in the top 3 for 198 of 200; the other paragraph's median rank is 3. For the 78 questions whose second paragraph is not in the first top 3, what should the second search say?

Predict: for those 78 questions, a second search with the same question (showing the next 3 paragraphs, since the first 3 are excluded) finds the missing gold paragraph for how many?
17 of 78. "Search more" with the same words buys little: the missing paragraph's median rank in that second search is 7. A better query is what helps, as the animation shows.

Reading the bars from the bottom: naming the bridge entity exactly finds the paragraph every time (its title is the entity), so the second hop is solved by knowing the name. The labelled supporting sentence of the first paragraph (what a perfect reasoning step would write after reading it) finds it for 37, and adding the question to it for 50. The real queries are far worse: the 1.7B ReAct agent's own second query, where it made one, found the paragraph for 18 of 55 (median rank 22), and only 12 of its 55 second queries contained the bridge entity's name; the decomposition program's second sub-question found it for 11 of 60. The gap between the oracle bars and the agent's bar is query writing, not retrieval: the same search tool returns the paragraph when given the right words.

What this means for design
Every iterative method below is a different way of getting the bridge entity into the next query: ReAct lets the model write the query; Self-Ask makes it ask an explicit follow-up question; IRCoT uses its last reasoning sentence verbatim; decomposition writes the sub-questions in advance (and so cannot know the entity yet unless it fills in the first answer). A larger model writes better queries; a small one benefits from structure that forces the entity into the query. Measuring "did the next query contain the entity I just read" is a cheap trajectory metric (section 6).

Caveats: the oracle sentence is HotpotQA's labelled supporting sentence, so it is an upper bound for what a reasoning step could write, not a method. This corpus is small (9,760 paragraphs); in the full 5.2-million-paragraph Wikipedia the first hop is harder too (the root's data README: BM25 recall@100 0.740 on BEIR's full HotpotQA against recall@10 0.868 here).

3. Loops and programs: ReAct, Self-Ask, IRCoT, FLARE, decomposition

Five published ways to interleave retrieval with generation. They differ in two things: where the next query comes from (the model writes it, the model's reasoning sentence is it, a planned sub-question is it) and who decides to stop (the model, a fixed number of steps, a marker string, a confidence threshold). All are measured or pending on the same 200 questions, same tool, same 1.7B generator; published results are the authors' own runs, on other models and corpora, and are not comparable to the numbers here.

ReAct: the model writes every query and decides when to stop

think→search(q1)→read→think→search(q2)→...finish[answer]

Yao et al. 2022 (the ReAct paper page): free-text "Thought", a tool "Action", an "Observation", repeated. Most flexible: any number of searches, any query. Cost: the quadratic token growth of section 1, and every failure mode of a model judging its own progress. Here: F1 0.411 at 2,458 tokens and 3.67 s per question measured (root's run); the best of the root's five strategies, ahead of the top-5 pipeline (0.249) on 68 questions and behind it on 22.

Self-Ask: explicit follow-up questions

Follow up: Who directed X?→search→Intermediate answer: Y→Follow up: Where is Y from?→search→So the final answer is: Z

Press et al. 2022 (arXiv 2210.03350) named the compositionality gap: the share of two-hop questions a model gets wrong although it answers both sub-questions right; it stayed at roughly 40% across GPT-3 sizes. The prompt makes the model ask follow-ups ("Are follow up questions needed here: Yes." / "Follow up:" / "Intermediate answer:" / "So the final answer is:"), each sent to a search engine. Published (Table 1, Davinci-002): Bamboogle chain of thought 46.4%, Self-Ask 57.6%, Self-Ask with search 60.0%; 2WikiMultiHopQA 29.8, 30.0, 40.1 published. Why it may suit a small model: a follow-up question is a well-formed query that usually names the entity (section 2). Here: pending: run_pending.sh core (selfask).

IRCoT: the last reasoning sentence is the next query

search(question)→sentence 1→search(sentence 1)→sentence 2→..."So the answer is: ..."

Trivedi et al. 2022 (arXiv 2212.10509): retrieve with the question, generate one chain-of-thought sentence from everything retrieved so far, search with that sentence, repeat until a sentence contains "answer is:" or 8 steps, keeping at most 15 paragraphs (BM25, K of 2 to 8 per step, tuned on dev). Published answer F1 (Table 4), one retrieval against IRCoT: HotpotQA 49.7 to 59.1 with Flan-T5-XXL and 53.6 to 60.7 with GPT-3 (code-davinci-002); 2WikiMultihopQA 54.8 to 68.0 with GPT-3 published. The oracle "sent" bar of section 2 is IRCoT's best case on this set: the sentence that states the fact read finds the second paragraph for 37 of 78. Here: pending: run_pending.sh core (ircot).

FLARE: retrieve only when the model is unsure

search(question)→draft answer, token probabilities→any token < θ?→ yes →search(question + confident part of draft)→answer again

Jiang et al. 2023 (arXiv 2305.06983): generate the next sentence; if any of its tokens has probability below a threshold θ, use the sentence (with tokens below a second threshold β masked out) as a query and regenerate. The decision to retrieve comes from the model's own confidence, which costs nothing extra to compute (the probabilities come with the tokens). Published (Table 1, text-davinci-003, 2WikiMultihopQA EM / F1): single retrieval 39.4 / 48.8, question decomposition 47.8 / 56.4, FLARE 51.0 / 59.7 (θ 0.8, β 0.4, Table 9) published. Here it needs token probabilities from llama-server (its OpenAI-compatible logprobs field, cached separately from the root's calls): pending: run_pending.sh core (flare).

Decomposition (plan, then execute): sub-questions written in advance

split into 1. and 2. (#1)→search(1.)→answer 1→search(2. with #1 filled)→answer

A fixed program: one call plans, the program executes, the model never decides to stop or search again. Cheaper to evaluate and to bound (always 4 calls here), and it cannot loop. Its weakness shows in section 2: a sub-question written before reading cannot name the bridge entity unless "#1" is filled correctly, and the 1.7B's second sub-question found the missing paragraph for 11 of 60. Here: F1 0.335 at 1,961 tokens measured (root's run). LangGraph's plan-and-execute template and most deep-research planners are this shape (section 7).

Training the loop: Search-R1 and RL-trained search agents

Everything above is prompting. Jin et al. 2025 (Search-R1, arXiv 2503.09516) train the loop with reinforcement learning: Qwen2.5-3B and 7B emit <search> queries inside their reasoning, a retriever (E5, top 3, 2018 Wikipedia) inserts results, and PPO (GRPO also tested) optimises only the final answer's exact match, with no format reward. One detail matters for anyone training this: the retrieved tokens are masked out of the loss, so the policy is not trained to predict text it did not write. Published: about 24% (7B) and 20% (3B) average improvement over RAG baselines across seven QA sets; average EM 0.304 for RAG against 0.431 for Search-R1 with Qwen2.5-7B base (Table 2) published. The policy learns when and what to search, which is exactly the query-writing gap section 2 measured. RL training itself is covered on the Topic: rl page; not run here (a training run of this kind needs GPU-days).

4. Should I search again? Self-RAG, CRAG and retrieval evaluators

The problem. A pipeline answers from whatever came back, even when it is useless. A loop searches again, but only when the model notices. A retrieval evaluator is a separate judgment of the results: good enough, useless, or in between. If it works, the system can spend extra searches only where they are needed.

Self-RAG: the model is trained to judge itself

Asai et al. 2023 (arXiv 2310.11511) teach the generator four kinds of special reflection tokens: Retrieve (yes, no, continue: should I search now?), ISREL (is this passage relevant?), ISSUP (is my sentence fully, partially or not supported by it?), ISUSE (how useful is the answer, 5 to 1). A critic model (Llama2-7B trained on 4k to 20k GPT-4 judgments per token type) labels about 150k training examples offline (145,619), and the generator (Llama2 7B or 13B) is fine-tuned on them; at inference the tokens drive retrieval and a beam search over segments. Published (Table 2): PopQA 54.9 / 55.8% for Self-RAG 7B / 13B against 51.8% for Llama2-chat-13B with retrieval; PubHealth 72.4 / 74.5 against 52.1 published. It needs training; the untrained imitation here asks the same 1.7B model one yes/no question ("do the paragraphs support this answer?") and falls back to the agent loop on "no": pending: run_pending.sh core (selfcheck).

CRAG: a small evaluator decides correct, incorrect or ambiguous

Yan et al. 2024, Corrective RAG (arXiv 2401.15884): a fine-tuned T5-large (0.77 B) scores each retrieved document from -1 to 1. If any score is above an upper threshold, the action is Correct (keep, refine); if all are below a lower threshold, Incorrect (discard, rewrite the query into keywords and search the web); otherwise Ambiguous (both). Kept documents are cut into strips, scored and filtered ("decompose then recompose"). Thresholds are set per dataset (for PopQA upper 0.59, lower -0.99). Published: on the Self-RAG 7B generator, PopQA 52.8 for plain RAG against 59.8 for CRAG, PubHealth 39.0 against 75.6 (Table 1); the evaluator's accuracy at telling relevant from irrelevant, 84.3% against 58.0% for ChatGPT prompted to judge (Table 4) published.

Measured here: can a cheap signal tell a good search from a bad one?

Before generating anything, the pipeline already has signals: bge-small's cosine score of the best paragraph, the gap to the third, the running example's 22 M cross-encoder (ms-marco MiniLM-L6, run on the CPU over the top 5, standing in for CRAG's T5 evaluator) and how many of the top 5 BM25 agrees with. For each signal, the AUROC: the probability that a randomly chosen question where the search succeeded gets a higher score than one where it failed (0.5 is a coin, 1.0 perfect). 5. Routers: deciding once, before anything runs

The problem. The agent loop costs 2,458 tokens per question against 753 for the pipeline (3.3 times), and most real traffic is easy. A router looks at the question once and sends it to the cheapest strategy likely to answer it. Adaptive-RAG (Jeong et al. 2024) trains a T5-Large classifier to predict a question's complexity and route to no retrieval, one search or the multi-step loop: with FLAN-T5-XL it reached 46.94 F1 against 48.85 for always multi-step, at 3.60 against 8.81 times the single-step time (Table 1), although the classifier was right only 54.52% of the time (Table 4); a perfect router would have reached 56.28 published. Their per-query times show why routing matters: 0.35 s with no retrieval, 3.08 s with one search, 27.18 s multi-step (Table 3) published.

6. Evaluating a trajectory: where the answer got lost

The problem. An agent's final answer is right or wrong, but the run that produced it is a sequence of decisions: which query, which results, when to stop. Scoring only the answer cannot tell a retrieval failure from a reading failure, and cannot tell a lucky guess from a grounded answer. The root page splits a pipeline's accuracy as A = rK × pk|K × g (retrieved, then placed in the prompt, then used by the generator); for a trajectory the same split applies to everything the model read along the way. Every question of every recorded strategy falls in one of four bins (measured; "right" = F1 at least 0.5):

rightboth gold read, answer wrong (reading failure)one gold read (retrieval failure, hop 2)no gold read

Read across the bars and the agent's advantage is not where one expects. The top-10 pipeline put both gold paragraphs in front of the model for 164 questions, the agent for only 114 (it often stopped early, section 1). But given both, the agent answered right 59% of the time, the top-10 pipeline 32%, and the long-context strategy, with both gold paragraphs always present among the question's own 10, 28% (and 24% in an 8k window). For this small model the bottleneck is reading, and the loop helps reading: each observation is 3 paragraphs, and its own thoughts restate what it found before the next step. Two cautions. The agent was also right 23 times without reading both gold paragraphs (comparison questions answered yes or no, or from memory; the closed-book model was right on 32): an answer metric alone would credit those. And whether the gain comes from the thoughts or from the smaller observations can be separated by answering from everything the agent read in one prompt, without its thoughts: pending: run_pending.sh core (memory, how=all).

7. Deep research systems: the same loop, for minutes, with parallel sub-agents

The problem. Some questions are reports, not facts: "compare the GPU export rules of three countries since 2022". They need dozens of searches across many sources, more text than fits in one window, and a cited write-up. Deep-research systems scale the agent loop with three additions: a planner that splits the task, parallel sub-agents that each research one part in their own context window, and compression of what each sub-agent found before it returns, so the lead agent's window holds summaries, not pages. Not run here: every one of them needs a web search API key, and this topic runs on the laptop without paid APIs. Three lessons that carry over to a retrieval system you build: the parallel sub-agent is a context-window device (each reads pages the lead never sees), so its value grows with how much must be read, and its cost is the 15 times tokens; the compression step is retrieval in reverse (decide what of a page to keep) and is where citations are most often lost (open_deep_research's citations are written by the model and never checked in code; GPT Researcher only tells the writer not to cite sources it was not given); and stopping is set by budgets in prompts and config, exactly as in section 1, only larger. Context engineering covers sub-agents and compaction as harness techniques; Topic: agentic-frameworks and LangChain and LangGraph cover the graph frameworks two of these are built on.

8. Long context against retrieval, in depth

The problem. Qwen3-1.7B and 4B read 32,768 tokens natively (their model cards; the GGUF files declare 40,960), frontier models a million or more. If the documents fit, why retrieve? The root's section 7 gives the per-query price formula and the published head-to-head results; this section measures what a long window costs on this laptop and what it does to accuracy.

What a long prompt costs: prefill, from zero

Before writing its first token, the model must run every prompt token through every layer: prefill. Each token's attention reads the keys and values of all tokens before it, so prefill has a part linear in the prompt length n (the weight matrices, once per token) and a part that grows with n2 (attention). The keys and values are kept for the rest of the request: the KV cache. Its size per token is fixed by the architecture: 2 (keys and values) × layers × KV heads × head dimension × bytes per number. A model fitted to the 3,813 generator calls the root recorded (llama-server's own timings, prompt cache on, 1.7B, up to 8,065 tokens), with nnew the tokens actually computed and nctx the whole prompt:

tprefill = a + b · nnew + c · nnew (nctx − nnew/2) / 1000
a
23.8 ms fixed per call
b
0.821 ms per token (the linear part: about 1,200 tokens per second)
c
0.099 ms per token per thousand tokens of context (attention)

Fitted on half the calls, it predicts the other half within 3.7% on average (0.3% on the 120 calls over 2,000 new tokens) measured on Apple M1 Pro (Metal). An independent check: the RAG in production child timed 9.34 s to the first token for a 7,611-token prompt under the bench lock; the model gives 9.14 s. Beyond the measured range it extrapolates to about 26 s at 16k tokens and 77 s for a full 32k window, of which 66% is attention (at 1,500 tokens attention is 8%): extrapolated; a measured point at 16k and 32k is pending: run_pending.sh lim (80 paragraphs, about 12k tokens). Decoding also slows as the cache grows: about 10.4 + 0.57 ms per output token per thousand tokens of context (fitted on 3,813 calls). KV cache at fp16 (from the configs): Qwen3-1.7B 114,688 bytes (112 KiB) per token, so 3.5 GiB for 32k tokens; Qwen3-4B 144 KiB, 4.5 GiB, on a 16 GB machine that also holds the weights.

What transfers: the shape (a linear term, an attention term that dominates past a few thousand tokens, a cache that grows with the window) holds on any GPU; datacenter GPUs and FlashAttention kernels change the constants by an order of magnitude or more (not run here). Hosted APIs hide prefill in the time to first token and bill it per token; a cached prefix is billed at a discount and skips the prefill. The Long-context calculator puts both sides together: tokens, dollars at dated list prices, seconds on this laptop, KV memory.

Advertised against effective context

A window size says what the model accepts, not what it uses. RULER (Hsieh et al. 2024, arXiv 2404.06654) defines a model's effective length as the longest length at which its average score over 13 synthetic tasks stays above 85.6% (Llama-2-7B's score at 4k). Published (Table 3, claimed / effective): GPT-4 128k / 64k; Llama-3.1-70B 128k / 64k; Qwen2-72B 128k / 32k published. The RULER leaderboard lists Qwen3 models from the Qwen3 report (authors' numbers), and two rows contradict the stated rule: Qwen3-8B (82.1 at 64k) and Qwen3-4B (77.8 at 64k) are marked 64k effective although both are below 85.6 (README read 2026-10-14). NoLiMa (Modarressi et al. 2025, arXiv 2502.05167) removes the word overlap between question and answer that makes needle-in-a-haystack easy: GPT-4o falls from 99.3% to 69.7% at 32k published. Long-context and multimodal benchmarks covers these benchmarks.

When each wins
Long context: a small, stable corpus read once or as a whole (summarise, find inconsistencies), repeated queries over the same documents with a cached prefix, and no per-user access rules. Retrieval: corpora beyond the window, per-query cost and latency budgets, per-user filtering, and small or mid-size models that read badly with distractors (measured above). They compose: retrieve generously (whole sections, 20 to 50 chunks) and let the window absorb chunking mistakes; on this model, keep the retrieved set small.

9. Memory: retrieval over the agent's own history

The problem. An agent working for hours, or across sessions, produces more history than fits in its window, and re-reading it all on every step is the quadratic cost of section 1. Agent memory stores that history outside the window and retrieves from it. Everything about retrieval carries over (chunk, embed, search, rerank, measure recall), with two differences: the corpus is written by the same process that will later search it, and it changes on every step, so what to write, when to curate, and when to recall matter as much as search.

Write-time against read-time curation. Write-time: when a step or task ends, distil it into a fact, a summary or a skill, and store only that; whatever the distillation dropped is gone for every later task. Read-time: keep the raw history and select or summarise from it once the current task is known. Just-in-Time Memory argues for read-time curation and gains 16.2 points on ALFWorld over the strongest baseline, mostly from training the curator (its page has the corrected reading); the Proactive Memory Agent adds the timing question, a second model deciding when to remind the worker. Extracted-fact stores: Mem0 (arXiv 2504.19413) extracts facts per turn and applies ADD, UPDATE, DELETE or NOOP against similar stored facts; on LOCOMO it reports 91% lower p95 latency (1.44 s against 17.12 s) and about 1.8k memory tokens against 26k for the full conversation, while full context stays more accurate (J score 72.90 against 66.88) published by the Mem0 authors. Zep's Graphiti (arXiv 2501.13956) stores facts in a temporal graph with validity windows; LongMemEval 71.2% against 60.2% for full context with gpt-4o published by the Zep authors. Fact stores, temporal graphs and paging are the subject of Agent memory layers.

How to check a memory system: plant facts in early turns, ask about them later, and measure recall of the planted memory (did retrieval return it) separately from the answer; add superseded facts (an old address, then a new one) and check the newer wins; log every write so a wrong answer can be traced to a write that never happened, a retrieval that missed, or a reading failure.

Common mistakes

"The agent is better, so route everything to it."
It costs 2,458 tokens per question against 753 here, grows quadratically with searches (section 1), and loses to the pipeline on some questions (22 of 200 here). In Ferrazzi et al.'s controlled comparison (arXiv 2601.07711) the agentic system used 3.3 times the input tokens and 1.5 times the time, and lost by 64.6 against 87.9 F1 on FEVER; note that the FEVER number there scores user-intent routing (is the question in scope), not fact verification as it is often quoted, including on the old version of this page published.
"The second search failed, so retrieval is the problem."
The same tool finds the second gold paragraph every time it is given the bridge entity's name (78 of 78), and the 1.7B agent's own queries for 18 of 55. Log the queries; most second-hop failures are query writing.
"More context is safer: put everything in the window."
Here the question's own 10 paragraphs, gold always included, scored 0.273, and an 8k window 0.230, below a top-10 search (0.261), at 12.48 s per question. Distractors cost a small model more than retrieval misses.
"A confident top hit means retrieval succeeded."
For multi-hop questions it predicted the opposite here (AUROC 0.43 for both gold in the top 5): the search locked onto the first hop. Evaluate the result set against everything the question needs.
"Our router works: accuracy went up and tokens went down."
Compare it with sending a random share of the same size to the expensive path. Here every router landed on the line between always-pipeline and always-agent, within the interval of a random split.
"Score the final answer only."
The agent was right 23 times without reading both gold paragraphs, and wrong 47 times with both in hand. Answer-only metrics cannot separate guessing from grounding or retrieval failures from reading failures.
"The window is 128k, so the model uses 128k."
RULER's effective length was half the claimed window for GPT-4 and a quarter for Qwen2-72B published; at 32k tokens prefill alone would take about 77 s on this laptop (extrapolated).
"Prompt caching makes long agent loops cheap."
It cuts the price of re-read tokens and skips their prefill (1,022 of 2,258 tokens computed here), but each step still generates its own output and the window still grows; budgets still matter.
"Memory: keep the last few turns."
A sliding window kept both gold paragraphs in 1 of 92 multi-hop trajectories; retrieval over the agent's own reads, queried with its current state, kept them in 85.

Interview questions, short answers

Why does an agent loop's token cost grow quadratically?
Every call re-reads everything before it: T = (n + 1)s + r n(n + 1)/2. Prompt caching discounts the re-read part; budgets bound n.
What is the compositionality gap?
Press et al.: the share of two-hop questions a model gets wrong although it answers both sub-questions correctly; about 40% for GPT-3 sizes. Self-Ask closes part of it by asking the sub-questions explicitly.
IRCoT, Self-Ask, FLARE: where does each next query come from?
IRCoT: the last chain-of-thought sentence. Self-Ask: an explicit "Follow up:" question. FLARE: the draft sentence with unsure tokens masked, and only when some token's probability is below a threshold.
How does CRAG decide to search again?
A T5-large evaluator scores each document; any above the upper threshold means Correct, all below the lower threshold means Incorrect (rewrite the query, search the web), otherwise Ambiguous (both). Thresholds are tuned per dataset.
Why mask retrieved tokens in Search-R1's loss?
The policy did not generate them; training it to predict retrieved text would teach it to imitate documents instead of deciding what to search.
When is long context better than RAG?
Small stable corpora read whole or repeatedly with a cached prefix, no per-user access rules, and a model that reads well with distractors. Otherwise retrieve, and retrieve generously only for strong readers.
How do you know a router is worth it?
Plot it on the cost-accuracy plane against always-cheap, always-expensive, a random split of the same share and the oracle; it must beat the random split, on your own traffic mix.
What would you log to debug an agentic RAG system?
Every call's prompt tokens and latency, every query and its results, gold or judged relevance of each observation, stop reason, repeats and parse failures; then bin each failure as retrieval, reading, stopping or format.
System design: a research assistant over 2 million internal documents, answers with citations in under a minute, per-user permissions.
Hybrid index (BM25 plus dense) with ACL filters applied at retrieval, a reranker; a router sending lookups to a single-shot pipeline (seconds) and analytical questions to a planner with 3 to 5 parallel sub-agents, each with a tool budget and a compression step that keeps document ids; citations checked in code against the retrieved chunks before the answer is shown; prompt caching for the shared system and tool prefix; budgets per request (tool calls, tokens, wall time) with a partial answer on timeout; trajectory logs and a labelled set of 200 to 500 questions with gold documents to track retrieval recall, stop reasons and answer quality per route. Freshness and deletes as on RAG in production.
Write-time or read-time memory curation?
Documents: write-time (an index), because they cannot know the future question. An agent's own history: keep it raw and curate at read time with the current task as the query, when storage is cheap; distil at write time only what must survive the raw log's deletion.
