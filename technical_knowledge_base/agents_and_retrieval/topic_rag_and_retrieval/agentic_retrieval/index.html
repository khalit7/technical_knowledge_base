Agentic retrieval in one picture

Agentic retrieval moves the decision of what to read next from the engineer to the model (or to a router, or to nobody, with the whole corpus in the window). It pays only when the next query can name what the last search found, and every extra call re-reads everything before it.

Fig. 1 follows one recorded question through three deciders, the running example's Qwen3-1.7B answering each time; each slab is one model call, its length the prompt tokens, to scale.

  1. One question, one corpus. "Where was the music festival Billy McFarland was charged with wire fraud for supposed to take place?" (answer Great Exuma). Its two gold paragraphs are Billy McFarland (entrepreneur), which the question names, and Fyre Festival, which it does not. The tiles stand for the 9,760 paragraphs; where a tile sits is layout only.
  2. The engineer decides: one search, top 5. The question finds hop 1; Fyre Festival is not among the five. One call of 753 prompt tokens answers "New Orleans": wrong.
  3. The model decides: it writes a query. The agent searches "Billy McFarland" and reads three paragraphs, hop 1 among them. Its second call (580 tokens) re-reads the first call and its output (grey, 231 tokens) and adds the thought and the result (349).
  4. The next query names what it just read. "Fyre Festival" finds hop 2. The third call is 1,061 tokens, 629 of them re-read, and answers "Great Exuma": right, after 1,812 prompt tokens over three calls.
  5. Nobody decides: everything in the window. The question's own 10 paragraphs (both gold among them, eight near-misses) go into one call of 1,933 tokens: "Bahamian island of Great Exuma" (F1 0.57: the right island, extra words).
  6. Over all 200 questions, the three land close. Mean tokens billed and F1: top 5 735 and 0.402; ReAct 2,458 and 0.411; long context 1,455 and 0.456. 1. Retrieval as a tool, and what each step costs

A pipeline commits to one query and one k before it has seen a result; if that search misses, nothing notices. Handing the search to the model lets it read a result and react. The search is a tool: a function the harness runs for the model. The model sees a tool description, may answer with a tool call (structured text naming the tool and its arguments), the harness runs the search and appends the result as an observation, and the model is called again with everything so far, until it answers or the step budget runs out. That is the reason-then-act loop of ReAct; how a harness renders the tool schema into the chat template and parses the call is on Building a harness. What matters here is what the loop reads and what it pays.

  1. Call 1: s tokens. Instructions, the tool description and the question: s = 172 tokens on average for the root's agent.
  2. Search 1: the first prompt is read again. The model's thought, its action and the observation add r = 474 tokens; call 2 re-reads all of call 1 (grey) and bills s + r.
  3. Search 2: everything again. Call 3 bills s + 2r. Every call re-reads every call before it, so the bill grows with the square of n.
  4. Searches 3 and 4: the last call alone is the largest. Predict first: how much does the fourth search add, against the first? Call 5 bills s + 4r = 2,069 tokens, (s + 4r) / (s + r), about 3.2 times call 2. The five calls bill 5s + 10r = 5,601 with the mean s and r; the 28 recorded trajectories with four searches billed 6,067 (the formula with their own s and r: 6,205).
  5. The prompt cache: computed once, billed again. llama-server keeps the earlier calls' keys and values (glass), so only the coloured parts are computed: s + 4r with the means, 2,186 recorded for those 28 questions.

Over the 200 recorded trajectories the formula, with s and r measured per question, predicts the billed tokens within 2.5% on average (worst 15%, from r varying between steps) measured; with one search it is exact by construction. On average 1,022 of the 2,258 billed tokens were actually computed. An API with prompt caching bills the re-read part at a discount (the Long-context calculator has dated prices); it does not make each step's generation faster.

What goes into s and r: tool descriptions and result formats

The tool description is text in the system turn, paid on every call. Counted with Qwen3's own chat template (tokenizer only, measured): the question alone is 37 tokens; with the root's text protocol (Thought:, Action: search[...], finish[...], a budget rule) 174; with an OpenAI-style JSON function schema passed as tools=[...] 207; with that schema plus a two-line budget prompt 232. The description is also the main lever on query quality: say what the tool returns and what a good query looks like ("a short query naming one entity or fact"). Every tool added to an agent is paid on every call.

Results per search, same agent measured: 1 paragraph F1 0.452 (1,540 tokens), 3 (the root's run) 0.411 (2,458), 5 0.424 (3,569). One per search scored highest and cost less than three, within noise (one against three: +0.041 (paired 95% interval -0.019 to +0.102)): smaller observations do not hurt this model, because it searches again.

Titles cost a fifteenth of full paragraphs

The same 3 results formatted four ways, mean Qwen3 tokens over the 406 searches the root's 1.7B agent made measured. The first sentence carries more than expected: 287 of the 486 labelled supporting sentences of these 200 questions (59%) are a paragraph's first sentence. That is the case for the two-tool design many agents use: search returns titles and a snippet, read returns one document in full, so full text is paid only when chosen. JSON wrapping costs about 12% more than the same text as a plain list, for no gain.

Budgets and stopping

What the agent did with a budget of 4 (recorded trajectories): it saw both gold paragraphs in 114 of 200, after the first search in 32, the second in 72, the third or fourth in 10, and searched again after already having both 28 times. It stopped too early (answered without ever seeing the second gold paragraph) in 75 trajectories, 52 of them wrong: stopping is a judgment from its own reading, and a small model is overconfident. It repeated a query in 28 trajectories and used the whole budget in 28 (mostly the same ones: stuck loops only the budget ended); 17 times it wrote no parseable action. Long trajectories are mostly failing trajectories, so a tight budget costs little. How to check yours: log every call's prompt tokens and every query with its results; count calls per question, repeated queries, unparseable steps and budget hits. They are cheap and find most loop bugs.

Beyond two searches, the budget buys tokens, not accuracy

The same ReAct agent with a search budget of 1, 2, 3, 4 (the root's run) and 6, 200 questions measured: F1 0.278, 0.400, 0.407, 0.411, 0.407 at 938, 1,702, 2,095, 2,458 and 3,270 tokens. Budget 6 against 4: -0.004 (paired 95% interval -0.043 to +0.036). A budget of 1 forces an answer from 3 paragraphs and falls well below the top-5 pipeline (-0.134 (paired 95% interval -0.196 to -0.071) against the root's budget-4 run).

2. The second hop: what the next query needs

A bridge question ("Where was the music festival Billy McFarland was charged with wire fraud for supposed to take place?") names the first thing (Billy McFarland) but not the second (the Fyre Festival). The question finds the first paragraph easily: one gold paragraph is in the top 3 for 198 of 200 questions. The second paragraph is about something the question never names, so it ranks low (median rank 3); for 78 questions it is not in the first top 3. What should the second search say?

Predict: for those 78 questions, a second search with the same question (showing the next 3 paragraphs, since the first 3 are excluded) finds the missing gold paragraph for how many?
17 of 78. "Search more" with the same words buys little: the missing paragraph's median rank in that second search is 7. A better query is what helps, as the stepper shows.

  5. The sentence hop 1 states, as the query (oracle). What IRCoT would search with: it names the bridge entity, and hop 2 lands in or near the disc (median rank 4). The search tool was never the problem; the query was.

So every iterative method in section 3 is a different way of getting the bridge entity into the next query. ReAct lets the model write the query; Self-Ask makes it ask an explicit follow-up question; IRCoT uses its last reasoning sentence verbatim; decomposition writes the sub-questions in advance, so it cannot know the entity unless it fills in the first answer. A larger model writes better queries; a small one benefits from structure that forces the entity in. "Did the next query contain the entity just read" is a cheap trajectory metric (section 6).

Caveats: an oracle upper bound, and a small corpus
The oracle sentence is HotpotQA's labelled supporting sentence, an upper bound for what a reasoning step could write, not a method. This corpus is small (9,760 paragraphs); in the full 5.2-million-paragraph Wikipedia the first hop is harder too (the root's data README: BM25 recall@100 0.740 on BEIR's full HotpotQA against recall@10 0.868 here). In the root's agent runs both gold paragraphs are in a single search's top 3 for 122 of 200 questions.

Naming the bridge entity solves the second hop; the agent rarely names it

Of the 78 questions whose second paragraph is not in the first top 3, how many each second query finds in the top 3 (bge-small, first search's results skipped) measured. The exact entity name finds it every time (its title is the entity). HotpotQA's labelled supporting sentence of hop 1, what a perfect reasoning step would write after reading it, finds it for 37; the question plus that sentence for 50. The 1.7B ReAct agent made a second query for 55 of these questions; where its own first query had not already found hop 2 (50), the second found it in the top 3 for 18 (median rank 22), and only 12 of its 55 second queries contained the entity's name; the decomposition program's second sub-question found it for 11 of 60. The gap between the oracle bars and the agent's is query writing, not retrieval.

3. Loops and programs: ReAct, Self-Ask, IRCoT, FLARE, decomposition

Five published ways to interleave retrieval with generation differ in two things: where the next query comes from and who decides to stop. All are run here on the same 200 questions, tool and generators; the papers' own results are on other models and corpora and sit in the closed blocks.

ReAct: the model writes every query and decides when to stop

think→search(q1)→read→think→search(q2)→...finish[answer]

Most flexible, and it pays the quadratic tokens of section 1 and every failure of a model judging its own progress. Here F1 0.411 at 2,458 tokens and 3.67 s per question (root's run), level with the top 5 (paired difference +0.009, 95% interval -0.060 to +0.081): better on 48 questions, worse on 53. With Qwen3-4B, 0.574 against 0.490 for the top 5: the larger model gets more out of the loop.

Self-Ask: explicit follow-up questions

Follow up: Who directed X?→search→Intermediate answer: Y→So the final answer is: Z

Press et al. 2022 named the compositionality gap: the share of two-hop questions a model gets wrong although it answers both sub-questions right, roughly 40% across GPT-3 sizes. A follow-up question is a well-formed query that usually names the entity. Here F1 0.286 (95% interval 0.231 to 0.345) at 4,112 tokens: the 1.7B rarely decided it was done, ending by itself in 34 of 200 runs and using all 4 follow-ups in 144, often repeating the first one word for word. The 4B ended by itself in 194 of 200.

IRCoT: the last reasoning sentence is the next query

search(question)→sentence 1→search(sentence 1)→..."So the answer is: ..."

Trivedi et al. 2022: retrieve with the question, write one chain-of-thought sentence, search with that sentence, repeat until a sentence contains "answer is:". The oracle "sentence" bar of section 2 is IRCoT's best case here (37 of 78). Here, with a separate reader over everything collected, F1 0.442 (95% interval 0.384 to 0.504) at 1,015 tokens, the best iterative method; but it barely iterated: the 1.7B wrote "So the answer is" in its first sentence for 196 of 200, so the gain comes from a reasoning sentence plus a reader, not from a second retrieval. Given both gold paragraphs it was right 62% of the time, the highest of any strategy. The 4B comes within a few points of its ReAct loop at less than half the tokens.

FLARE: retrieve only when the model is unsure

search(question)→draft, token probabilities→any token < θ?→ yes →search(question + confident part)

Jiang et al. 2023: if any token of the draft sentence has probability below θ, search with the sentence (tokens below β masked) and regenerate; the decision costs nothing extra, since the probabilities come with the tokens. Here (θ 0.8, β 0.4, the paper's 2WikiMultihopQA setting) F1 0.400 (95% interval 0.342 to 0.461) at 811 tokens, level with the top 5 at about its cost. The draft was confident enough to skip the second search for 119 of 200, and a confident draft is not a right one: confidence in a short answer says little about whether the second hop was found.

Decomposition: sub-questions written in advance

split into 1. and 2. (#1)→search(1.)→answer 1→search(2. with #1 filled)→answer

A fixed program: one call plans, the program executes, the model never decides to stop or search again. Easy to bound (always 4 calls here), and it cannot loop; but a sub-question written before reading cannot name the bridge entity unless "#1" is filled correctly (11 of 60 second sub-questions found it). Here F1 0.335 at 1,961 tokens (root's run). LangGraph's plan-and-execute template and most deep-research planners have this shape (section 7).

Search-R1: training the loop instead of prompting it

Jin et al. 2025 train Qwen2.5-3B and 7B with reinforcement learning (PPO; GRPO also tested) to emit <search> queries inside their reasoning; a retriever inserts the results, and only the final answer's exact match is rewarded. The retrieved tokens are masked out of the loss, so the policy is not trained to predict text it did not write. The policy learns when and what to search, which is the query-writing gap of section 2. Not run here (GPU-days); RL itself is on Topic: rl.

4. Should I search again? Retrieval evaluators

A pipeline answers from whatever came back; a loop searches again only when the model notices. A retrieval evaluator judges the results separately (good enough, useless, in between), so extra searches are spent only where needed. Two published designs: Self-RAG (Asai et al. 2023) trains the generator itself to emit reflection tokens (Retrieve: search now?; ISREL: is this passage relevant?; ISSUP: is my sentence supported by it?; ISUSE: how useful is the answer); CRAG (Yan et al. 2024) puts a small fine-tuned T5-large in front that scores each document and picks Correct (keep and refine), Incorrect (discard, rewrite the query, search the web) or Ambiguous (both).

The best paragraph's cross-encoder score scores AUROC 0.43 for "both gold in the top 5", below a coin: a very relevant top paragraph usually means the search locked onto the first hop, and the rest are near-copies of it. The second-best score is the useful one (0.64), and agreement between BM25 and dense search is the best single signal (0.69). For multi-hop questions an evaluator must judge the set against everything the question needs, not each result against the question; CRAG's per-document scores were designed for single-hop sets (PopQA, PubHealth, ARC, biographies). No signal predicts the 1.7B's answer well: the best is the second-best cross-encoder score (0.60), and a cross-validated logistic regression on all 8 signals reaches 0.57.

Three evaluator policies, measured. Escalate when the evaluator's best score is below its median (use the agent loop's recorded answer, else the top 5): F1 0.390 (against always-pipeline -0.012, 95% interval -0.055 to +0.034), the same as escalating a random half (0.406). Correct, as CRAG does: thresholds at the 33rd and 67th percentiles split the questions into 66 correct, 68 ambiguous and 66 incorrect; on incorrect the model rewrites the question into keywords and the new top 5 replaces the old, on ambiguous it is added. F1 0.332 (95% interval 0.274 to 0.391) at 1,050 tokens, below the plain top 5 (0.402): throwing away results that found the first hop, because the set "looks wrong", removes half of what a two-hop question needs. Self-check, as an untrained Self-RAG: the same 1.7B asked whether the paragraphs support its top-5 answer said "supported" for 187 of 200 answers, only 77 of them right; falling back to the agent loop on "no" scored 0.420 at 1,632 tokens. An untrained small model is not a critic of its own answers, which is why Self-RAG trains one.

A confident best hit predicts that the second hop is missing

For each signal the pipeline has before generating, the AUROC: the probability that a question where the search succeeded scores higher than one where it failed (0.5 is a coin). Targets: both gold paragraphs in the top 5 (137 of 200) and the pipeline's answer right (F1 at least 0.5, 80 of 200). 5. Routers: deciding once, before anything runs

The agent loop costs 2,458 tokens per question against 735 for the pipeline, and most real traffic is easy. A router looks at the question once and sends it to the cheapest strategy likely to answer it. Adaptive-RAG (Jeong et al. 2024) trains a T5-Large classifier on question complexity to choose no retrieval, one search or the multi-step loop, and gets close to always-multi-step accuracy at well under half its time, although its classifier is right only about half the time (details below). Here every router chooses between two recorded strategies per question, so each policy is exact and costs no new generation (the router's own cost is not counted: the signals come from the search the pipeline makes anyway; the cross-encoder adds 58 ms for 10 pairs on this laptop, root pipeline runs).

Most routers land on the grey line between always-pipeline and always-agent: the learned router barely sends anything to the agent, and the evaluator-based one does no better than a random split. One beats the line: the rule that sends questions containing a comparison word (or, both, first, older, ...) to the agent, F1 0.444 at 1,143 tokens, +0.042 over always-pipeline (paired 95% interval +0.003 to +0.081). On the 49 questions with such a word (33 of them HotpotQA comparison questions) the agent scores 0.602 against 0.43 for the pipeline: two named things are two searches, and the loop makes them. The learned router's cross-validated AUROC for "the agent beats the pipeline on this question" is 0.48; the agent won on 48 questions, lost on 53 and tied on 99, and beyond the comparison cue which ones is mostly how a 1.7B model happened to read. The oracle over all 8 recorded strategies would reach 0.731 at 927 tokens, headroom nothing measured here can predict.

A router cannot help when the expensive path is not better. On the mixed set of the root's agent runs (Topic: rag-and-retrieval) (199 questions, about half constructed one-hop), always-pipeline scored 0.512 at 766 tokens, always-agent 0.451, its learned router 0.500 and its LLM router 0.520 (which sent almost nothing to the agent). An Adaptive-RAG-style three-way router prompted to the 1.7B on the 200 two-hop questions labelled 0 none, 0 one and 200 many: right every time, so routing reduced to always-agent (F1 0.411 at 2,458 tokens). How to check a router: put it on the cost-accuracy plane against always-cheap, always-expensive, a random split of the same share and the oracle; it must beat the random split, on your own traffic mix.

7. Deep research: the same loop, for minutes, with parallel sub-agents

Some questions are reports, not facts ("compare the GPU export rules of three countries since 2022"): dozens of searches, more text than one window holds, and a cited write-up. Deep-research systems scale the agent loop with three additions: a planner that splits the task, parallel sub-agents that each research one part in their own context window, and compression of what each found before it returns, so the lead's window holds summaries, not pages. Not run here: each needs a web search API key, and this topic runs without paid APIs; the shapes are read from the open projects' source at pinned commits and the vendors' documentation.

Fig. 4 is the shape of open_deep_research (LangChain, read at commit 1b7d2e8) with its default budgets (the counts are its defaults, the sizes illustrative); Anthropic's Research system has the same orchestrator-worker shape (a lead "spins up 3-5 subagents in parallel", each using "3+ tools in parallel").

  1. A brief, then a lead. The question is clarified and rewritten as a research brief; a supervisor, the lead, plans in its own window.
  2. Researchers in parallel, each with its own window. The lead calls ConductResearch; up to 5 researcher sub-graphs run at once (extra calls are rejected).
  3. Each reads pages the lead never sees. Up to 10 tool calls per researcher; every web page is summarised to about a quarter of its length by a small model before it enters the researcher's window.
  4. Compressed findings return. Each researcher compresses what it found, with inline citations, before returning; the lead sees only the compressed research. The compression step is retrieval in reverse (what of a page to keep) and is where citations are most often lost.
  5. Rounds, then a report. Up to 6 supervisor rounds, then one report with citations, written by the model and never checked in code.

What it costs and buys (vendor claims, on vendor-run evaluations): Anthropic reports that agents "typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more", that on BrowseComp "token usage by itself explains 80% of the variance", and that the multi-agent system "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" (Anthropic engineering, 13 June 2025) vendor. OpenAI's BrowseComp (arXiv 2504.12516, 1,266 hard-to-find questions) scores GPT-4o 0.6%, GPT-4o with browsing 1.9%, o1 9.9% and Deep Research 51.5% (Table 3; Deep Research was trained on similar data); human trainers solved 29.2% published by OpenAI. Three lessons carry over to a retrieval system you build: the sub-agent's value grows with how much must be read, and its cost is the 15 times tokens; check citations in code (open_deep_research's citations are written by the model and never checked; GPT Researcher only tells the writer not to cite sources it was not given); and stopping is set by budgets in prompts and config, as in section 1, only larger. Context engineering covers sub-agents and compaction as harness techniques; LangChain and LangGraph the graph framework two of these are built on.

What a long prompt costs: prefill

Before its first token the model runs every prompt token through every layer (prefill): a part linear in the prompt length (the weight matrices, once per token) and a part that grows with its square (each token's attention reads all earlier keys and values). A model fitted to the 5,497 generator calls the root recorded (llama-server's own timings, prompt cache on, 1.7B, up to 8,065 tokens), with nnew the tokens computed and nctx the whole prompt:

tprefill = a + b · nnew + c · nnew (nctx − nnew/2) / 1000
a
22.5 ms fixed per call
b
0.830 ms per token (the linear part: about 1,200 tokens per second)

0.104 ms per token per thousand tokens of context (attention)

Extrapolated, the model gives about 27 s at 16k tokens and 80 s for a full 32k window, 67% of it attention (at 1,500 tokens attention is 8%); 32k remains an extrapolation. Decoding also slows as the cache grows: about 10.4 + 0.67 ms per output token per thousand tokens of context (fitted on 5,497 calls). The shape (a linear term, an attention term that dominates past a few thousand tokens, a cache that grows with the window) holds on any GPU; datacenter GPUs and FlashAttention kernels change the constants by an order of magnitude or more (not run here). Hosted APIs hide prefill in the time to first token and bill it per token; a cached prefix is billed at a discount and skips the prefill. When each wins
Long context: a small, stable corpus read once or as a whole (summarise, find inconsistencies), repeated queries over the same documents with a cached prefix, and no per-user access rules. Retrieval: corpora beyond the window, per-query cost and latency budgets, per-user filtering, and small or mid-size models that read badly with distractors (measured above). They compose: strong readers can take generous retrieval (whole sections, 20 to 50 chunks) and let the window absorb chunking mistakes; on this model, keep the retrieved set small.

Published head-to-heads say the same. More retrieved passages is not monotone: for many long-context models quality "initially improves" and then declines as the count grows, mostly because of hard negatives (passages that look relevant and are not); reordering the retrieved passages, without training, recovers part of it (Jin et al., arXiv 2410.05983, Oct 2024). And there is no single winner: LaRA's 2,326 test cases over 11 models (seven open, four proprietary) found that "the optimal choice between RAG and LC depends on a complex interplay of factors": model size, long-text ability, context length, task type and the retrieved chunks (LaRA, arXiv 2502.09977, Mar 2025). So evaluate recall@k and end-to-end accuracy together across k, on your own questions.

9. Memory: retrieval over the agent's own history

An agent working for hours, or across sessions, produces more history than fits in its window, and re-reading it all on every step is the quadratic cost of section 1. Agent memory stores that history outside the window and retrieves from it: everything about retrieval carries over, except that the corpus is written by the process that will search it and changes on every step. What to write, when to curate, fact stores (Mem0), temporal graphs (Graphiti) and memory files are owned by Context engineering, which measured all three in a twelve-session experiment. The retrieval question this page measures: once the task is known, which of the agent's own reads should the final step keep? Write-time curation (distil each step into a fact) loses whatever the distillation dropped; read-time curation keeps the raw history and selects with the current task as the query (Just-in-Time Memory argues for it and gains 16.2 points on ALFWorld, mostly from training the curator). The plainest read-time design is also the baseline every memory system must beat: Bao et al. 2026 (arXiv 2610.30755) run "Raw-RAG", dense retrieval plus a reranker over the raw conversation history, against agentic memory systems on LoCoMo, LongMemEval, MEME and MemoryAgentBench, and it "ranks first among the compared memory systems in six of seven benchmark-model settings", by 0.13 to 5.53 points over the strongest one published. Their reading: raw history covers more of the needed evidence, which outweighs the reader using it less efficiently, and even full access to a transformed memory store leaves an accuracy gap, because the transformation already lost information.

Re-answering from the curated memory in one prompt (no thoughts), on the 131 trajectories with at least two searches (the agent's own answers: F1 0.407) measured: everything read 0.412 at 1,131 tokens, the last observation 0.296 at 481, the top 3 by question plus last thought 0.378 at 442. How to check a memory system: plant facts in early turns and ask about them later, measuring recall of the planted memory (did retrieval return it) apart from the answer; add superseded facts (an old address, then a new one) and check the newer wins; log every write, so a wrong answer can be traced to a write that never happened, a retrieval that missed, or a reading failure.

IRCoT, Self-Ask, FLARE: where does each next query come from, and who stops?
IRCoT: the last chain-of-thought sentence; it stops on "answer is:". Self-Ask: an explicit "Follow up:" question; it stops on "So the final answer is". Why mask retrieved tokens in Search-R1's loss?
The policy did not generate them; training it to predict retrieved text would teach it to imitate documents instead of deciding what to search.
What would you log to debug an agentic RAG system?
Every call's prompt tokens and latency, every query and its results, gold or judged relevance of each observation, stop reason, repeats and parse failures; then bin each failure as retrieval, reading, stopping or format (sections 1 and 6).

Write-time or read-time memory curation?
Documents: write-time (an index), because they cannot know the future question. An agent's own history: keep it raw and curate at read time with the current task as the query, when storage is cheap; distil at write time only what must survive the raw log's deletion (section 9).

  • Five ways to answer, with Qwen3-4B. The loop pays for its +0.084 with 2,456 tokens per question against 754 (3.3 times) and 6.15 s against 1.98 s. Without retrieval the 4B scores 0.193, so most of what it answers comes from what it reads. The agent saw fewer gold paragraphs than the top 5 did (81% against 84%) and still answered better: it reads 3 paragraphs at a time, chosen for the piece it is missing, instead of 5 chosen for the whole question. Long context came in two sizes: the question's own 10 paragraphs (HotpotQA's "distractor" setting, about 1.4k tokens) and about 8k tokens (the own 10 plus the corpus paragraphs nearest the question). The own 10 (about 1,470 prompt tokens) score 0.576, level with the loop at 60% of its tokens and 3.95 s against 6.15 s; widened to about 8,000 tokens F1 falls to 0.475, below the five-paragraph pipeline, at 7,963 tokens and 28.8 s per question. The corpus is 1.34 million Qwen3 tokens, so a window of 8,000 holds 0.6% of it, and prefill grows faster than linearly (about 0.26 s for a 270-token prompt, about 9.3 s for 7,600 tokens). The 1.7B uses about the same tokens per strategy and roughly half the seconds.
  • Tokens per step, with Qwen3-4B. The prompt carried into the loop's calls grows from 172 tokens at the first call to 613, 1,077, 1,565 and 2,047 at the fifth, while the prompt cache keeps the tokens actually computed near 450 to 530 per call; a cache stores the attention keys and values of a prefix already processed, lowers the price of the re-read prefix (providers bill cached tokens at a discount, not for free) but not the time to generate each step. A question that ends in two calls bills 820 input tokens; one that uses all five bills 5,370, 6.5 times as much. The long trajectories are the failures: the 29 questions that used all four searches score F1 0.18, against 0.673 for the 112 that stopped after two, so a step cap does more than bound cost (past two or three searches the small model was mostly lost). Repeating a query (36 questions) or losing the format (3 questions; 17 for the 1.7B) is how a small model wastes its budget; a loop can also search for the wrong entity or stop early with a plausible guess. The old page's worked example, with illustrative s = 1,500 and r = 2,000 tokens against a pipeline reading 4,000 retrieved tokens once: at 3 searches the agent reads 18,000 tokens (3.3 times the pipeline), at 6 searches 52,500 (9.5 times).
  • Lost in the middle on 20 paragraphs. The same 20 paragraphs per question (the two gold paragraphs kept together as one block, plus the 18 corpus paragraphs bge-small ranks highest among the rest, so the distractors are on topic), with only the position of the gold block changing. Qwen3-4B (100 questions): F1 0.682 first, 0.540 at positions 5 to 6, 0.554 at 10 to 11, 0.599 at 15 to 16 and 0.592 last; first against the middle +0.128: Liu et al.'s shape at a smaller scale, a strong advantage at the very start, a drop of 0.13 to 0.14 in the early middle and only part of it recovered at the end, though the middle slots overlap in their intervals. Qwen3-1.7B (200 questions) shows the U more clearly: 0.496 first, 0.405 and 0.381 in the middle, 0.381 at 15 to 16 and 0.468 last; first against the middle +0.116 (95% interval +0.063 to +0.168), last against the middle +0.087 (+0.045 to +0.130). The practical rule: when stuffing a window, put the best evidence first (or last), and measure on your own model before trusting a long prompt to be read evenly.
  • A router on a mixed set. HotpotQA has no one-hop questions, so Qwen3-4B read one corpus paragraph (never a gold paragraph of the 200) and wrote a question answerable from it alone, with a short answer copied from it; questions whose answer was not in the paragraph, was longer than six words or appeared in the question were dropped. Of 240 paragraphs drawn, 198 questions survived (62,375 tokens, 259 s), split 99 for training and 99 for the test; the mixed test set is 100 two-hop questions plus that one-hop test half. Two routers were trained or prompted without touching the test set: a logistic regression on the question's bge-small vector (free, since the search tool computes it), trained on 400 held-out HotpotQA questions and the one-hop training half, and Qwen3-1.7B asked, with four examples, whether the question needs ONE fact or TWO. Because the 1.7B loop is no better than the pipeline on the two-hop half (0.389 against 0.426) and worse on one-hop questions (0.515 against 0.599), always-pipeline is the best simple policy: 0.512 for 766 tokens and 0.92 s, against 0.451 for 2,652 tokens and 3.39 s for always-agent. The logistic router is right about the question type 74.9% of the time and sends 122 of 199 questions to the loop, which costs accuracy (0.500) and tokens (1,942); even a perfect router (0.493 for 1,841 tokens) is below always-pipeline. With the 4B, whose loop is better on two-hop questions, the same router would pay; that run was not made. Caveat: the constructed one-hop questions are easier to tell apart than real traffic.
  • Published, for comparison. ReAct (Yao et al. 2022; PaLM-540B, HotpotQA, question only, Wikipedia search API, exact match, prompting only): standard 28.7, chain of thought 29.4, act only 25.7, ReAct 27.4, ReAct then CoT-SC 35.1; supervised state of the art 67.5. ReAct's failures: 47% reasoning errors (including loops), 23% search results without the needed information, and 29% of failures were label ambiguity. Self-Route (arXiv 2407.16833 v2, Table 1; LongBench and InfiniteBench subsets): Gemini-1.5-Pro long context 49.70, RAG 37.33, Self-Route 46.41 with 38.4% of long context's tokens; GPT-4o 48.67, 32.60, 48.89 with 61.4% (the paper's prose quotes different values; the table is used here). Li et al. (arXiv 2501.01880) found long context generally ahead on question answering (most on Wikipedia questions) and retrieval ahead on dialogue and general questions.
  • Memory. Everything about retrieval carries over to an agent's own history (chunk it into turns or facts, embed, search with the current goal as the query, rerank, measure whether the needed memory was retrieved), with two differences: the store changes on every step, so writing and forgetting policies matter as much as search, and time matters (a newer fact can overrule an older one).
  • What transfers. A loop costs several generator calls and a growing prompt per question; a router saves most of that on one-hop traffic; long context pays for every token it reads; a fixed decomposition is cheaper and more predictable than a free loop; an entity graph costs one generator call per chunk before the first question. Small models fail more at the "agent" part (choosing a good query, knowing when to stop) than at reading; larger models were trained for exactly this and gain more from a loop.
  • Mistakes and a design, from the old page. Compare an agent with a pipeline at matched reading budgets too: an agent that searches four times reads up to 12 paragraphs, a pipeline given the top 3 reads 3, and part of any gain is just more text (compare at matched paragraphs or tokens, and report the cost next to the accuracy). Do not evaluate with an embedder trained on the benchmark. Exact match alone counts "October 1922" against "1922", or "Yes" against "yes, both are American", as wrong: report F1 too, and read a sample of failures. Use a loop when the question needs information you can only know to look for after reading something (multi-hop, comparisons, research tasks), when the first search often fails and needs reformulation, or when the tools vary (search, SQL, an API). To cut its cost, retrieve better per step (hybrid search, a reranker) so fewer steps are needed, and use a smaller model for planning queries and a larger one only to answer. A design for mixed traffic: ingestion parses, chunks on structure, embeds, builds a BM25 index and stores metadata and access lists per chunk; a router (a small classifier on the query) sends lookups to hybrid search, a reranker and the top 5 with citations, and multi-step questions to a loop with search as a tool (bounded steps, each search filtered by the user's access, observations summarised, a prompt cache for the fixed prefix); evaluation keeps a golden set of both kinds and tracks answer quality, evidence recall, cost and p95 latency per route; operations re-index on change, cache frequent queries and log trajectories for failure review.
