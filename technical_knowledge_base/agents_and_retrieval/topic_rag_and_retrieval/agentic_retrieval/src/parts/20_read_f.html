6. Evaluating a trajectory: where the answer got lost

A final answer is right or wrong, but the run behind it is a sequence of decisions: which query, which results, when to stop. Scoring only the answer cannot tell a retrieval failure from a reading failure, or a lucky guess from a grounded answer. The root splits a pipeline's accuracy as A = rK × pk|K × g (retrieved, placed in the prompt, used); for a trajectory the same split applies to everything the model read along the way, which puts every question of every strategy in one of four bins ("right" = F1 at least 0.5) measured:

The top-10 pipeline put both gold paragraphs in front of the model for @@t_single_k10_both_seen@@ questions, the agent for only @@t_react_both_seen@@ (it often stopped early, section 1), long context for all 200. Given both, reading success is similar for every retrieval strategy: agent @@t_react_rgb@@, top 10 @@t_single_k10_rgb@@, top 5 @@t_single_k5_rgb@@, top 2 @@t_single_k2_rgb@@, the question's own 10 paragraphs @@t_longctx_rgb@@, falling to @@t_longctx_tokens8000_rgb@@ in an 8k window. The biggest single loss is the second hop never read (@@t_react_half@@ questions for the agent, @@t_single_k5_half@@ for the top 5). Re-answering each multi-search trajectory from everything it read, in one prompt without the thoughts, gives F1 @@pd_mem_all_f1@@ against the agent's own @@pd_mem_react_same_f1@@ on the same @@pd_mem_all_n@@ questions: what the loop adds is evidence, not better reading.

Two cautions. The agent was right @@t_react_right_without_both@@ times without reading both gold paragraphs (comparison questions answered yes or no, or from memory; closed book was right on @@t_closed_right@@): an answer metric credits those. And reading can fail for reasons unrelated to retrieval: the first 1.7B runs used an answer prompt that made the model answer "yes" or "no" to open questions (63 of 200 single-shot answers, found by the root), and the same top 5 scored @@s2_k5_f1@@ instead of @@f1_single_k5@@, a larger gap than between any two architectures here. Counting answers of the wrong type is a one-line check.

7. Deep research: the same loop, for minutes, with parallel sub-agents

Some questions are reports, not facts ("compare the GPU export rules of three countries since 2022"): dozens of searches, more text than one window holds, and a cited write-up. Deep-research systems scale the agent loop with three additions: a planner that splits the task, parallel sub-agents that each research one part in their own context window, and compression of what each found before it returns, so the lead's window holds summaries, not pages. Not run here: each needs a web search API key, and this topic runs without paid APIs; the shapes are read from the open projects' source at pinned commits and the vendors' documentation.

Sub-agents are a context-window device: each reads pages the lead never sees

The shape of open_deep_research (LangChain, read at commit 1b7d2e8) with its default budgets; Anthropic's Research system has the same orchestrator-worker shape (a lead "spins up 3-5 subagents in parallel", each using "3+ tools in parallel"). The compression step is retrieval in reverse (what of a page to keep) and is where citations are most often lost.

What it costs and buys (vendor claims, on vendor-run evaluations): Anthropic reports that agents "typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more", that on BrowseComp "token usage by itself explains 80% of the variance", and that the multi-agent system "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval" ({{Anthropic engineering, 13 June 2025|https://www.anthropic.com/engineering/multi-agent-research-system}}) vendor. OpenAI's BrowseComp ({{arXiv 2504.12516|https://arxiv.org/abs/2504.12516}}, 1,266 hard-to-find questions) scores GPT-4o 0.6%, GPT-4o with browsing 1.9%, o1 9.9% and Deep Research 51.5% (Table 3; Deep Research was trained on similar data); human trainers solved 29.2% published by OpenAI. Three lessons carry over to a retrieval system you build: the sub-agent's value grows with how much must be read, and its cost is the 15 times tokens; check citations in code (open_deep_research's citations are written by the model and never checked; GPT Researcher only tells the writer not to cite sources it was not given); and stopping is set by budgets in prompts and config, as in section 1, only larger. {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} covers sub-agents and compaction as harness techniques; {{LangChain and LangGraph|n:3c65c17b0d0d81529358c996382224ac}} the graph framework two of these are built on.
