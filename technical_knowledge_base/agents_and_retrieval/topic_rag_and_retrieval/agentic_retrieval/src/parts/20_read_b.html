1. Retrieval as a tool, and what each step costs

A pipeline commits to one query and one k before it has seen a result; if that search misses, nothing notices. Handing the search to the model lets it read a result and react. The search is a tool: a function the harness runs for the model. The model sees a tool description, may answer with a tool call (structured text naming the tool and its arguments), the harness runs the search and appends the result as an observation, and the model is called again with everything so far, until it answers or the step budget runs out. That is the reason-then-act loop of {{ReAct|n:3c65c17b0d0d816b9a24c28de8f08ea8}}; how a harness renders the tool schema into the chat template and parses the call is on {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}. What matters here is what the loop reads and what it pays.

What goes into s and r: tool descriptions and result formats

The tool description is text in the system turn, paid on every call. Counted with Qwen3's own chat template (tokenizer only, measured): the question alone is @@sch_bare@@ tokens; with the root's text protocol (Thought:, Action: search[...], finish[...], a budget rule) @@sch_text@@; with an OpenAI-style JSON function schema passed as tools=[...] @@sch_json@@; with that schema plus a two-line budget prompt @@sch_json_plus_rules@@. The description is also the main lever on query quality: say what the tool returns and what a good query looks like ("a short query naming one entity or fact"). Every tool added to an agent is paid on every call.

Titles cost a fifteenth of full paragraphs

The same 3 results formatted four ways, mean Qwen3 tokens over the @@n_searches@@ searches the root's 1.7B agent made measured. The first sentence carries more than expected: @@first_sent@@ of the @@n_sf@@ labelled supporting sentences of these 200 questions (@@first_sent_pct@@) are a paragraph's first sentence. That is the case for the two-tool design many agents use: search returns titles and a snippet, read returns one document in full, so full text is paid only when chosen. JSON wrapping costs about 12% more than the same text as a plain list, for no gain.

Budgets and stopping

Beyond two searches, the budget buys tokens, not accuracy

The same ReAct agent with a search budget of 1, 2, 3, 4 (the root's run) and 6, 200 questions measured: F1 @@pd_react_budget1_f1@@, @@pd_react_budget2_f1@@, @@pd_react_budget3_f1@@, @@f1_react@@, @@pd_react_budget6_f1@@ at @@pd_react_budget1_tok@@, @@pd_react_budget2_tok@@, @@pd_react_budget3_tok@@, @@tok_react@@ and @@pd_react_budget6_tok@@ tokens. Budget 6 against 4: @@pd_rvr_budget6@@. A budget of 1 forces an answer from 3 paragraphs and falls well below the top-5 pipeline (@@pd_rvr_budget1@@ against the root's budget-4 run).

What the agent did with a budget of 4 (recorded trajectories): it saw both gold paragraphs in @@b_until_both_n@@ of 200, after the first search in @@b_found1@@, the second in @@b_found2@@, the third or fourth in @@b_found34@@, and searched again after already having both @@b_wasted_after_both@@ times. It stopped too early (answered without ever seeing the second gold paragraph) in @@b_stopped_missing@@ trajectories, @@b_stopped_missing_wrong@@ of them wrong: stopping is a judgment from its own reading, and a small model is overconfident. It repeated a query in @@b_repeat@@ trajectories and used the whole budget in @@b_budget_hit@@ (mostly the same ones: stuck loops only the budget ended); @@b_noaction@@ times it wrote no parseable action. Long trajectories are mostly failing trajectories, so a tight budget costs little. How to check yours: log every call's prompt tokens and every query with its results; count calls per question, repeated queries, unparseable steps and budget hits. They are cheap and find most loop bugs.

The tool, runnable, with its real output; the budget and results-per-search runs with intervals

The tool every agent on this page calls (src/scripts/demo_tool.py; real output, paragraphs cut to 160 characters):

def search(query, k=3, exclude=()):
    """bge-small exact search over the 9,760 paragraphs; already-seen paragraphs are skipped"""
    return A.ranking(query, exclude)[:k]

first = search(q["question"])
second = search("Russian Civil War end date", exclude=first)

The answer (October 1922) is in the first result; the second gold paragraph (the Socialist Revolutionary Party, which links Kerensky to the war) is never found, and a second search for the war's end date only returns more war. Excluding already-seen paragraphs is a design choice of the root's tool: every search must show something new.

Qwen3's chat template renders a JSON tool as a <tools> block in the system turn and asks for calls inside <tool_call> tags: "native tool calling" is a prompt convention the model was trained on, and the call is text the harness parses ({{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}} shows the full rendering).
