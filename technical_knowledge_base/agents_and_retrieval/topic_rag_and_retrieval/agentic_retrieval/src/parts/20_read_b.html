1. Retrieval as a tool

The problem. A pipeline decides everything before it has seen a single result: one query, the user's words, a fixed k. If that search misses, nothing notices. Handing the search to the model lets it read a result and react to it.

How it works, from zero. A tool is an ordinary function (here: search a paragraph collection) that the harness (the program running the model) executes on the model's behalf. The model is shown a tool description (a name, a sentence saying what it does and returns, and its parameters, usually as a JSON schema). Instead of answering, the model may emit a tool call: structured text naming the tool and its arguments. The harness parses it, runs the search, and appends the result to the conversation as an observation. The model is called again with everything so far, and decides again: another call, or a final answer. The loop ends when the model answers or when the harness's step budget (a maximum number of calls) runs out. This is the reason-then-act loop of {{ReAct|n:3c65c17b0d0d816b9a24c28de8f08ea8}}; {{Topic: agentic-harnesses|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} covers harnesses in general, and {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} what to keep in the window.

The tool every agent on this page calls, runnable on its own (the page's src/scripts/demo_tool.py; real output, paragraphs cut to 160 characters for display):

def search(query, k=3, exclude=()):
    """bge-small exact search over the 9,760 paragraphs; already-seen paragraphs are skipped"""
    return A.ranking(query, exclude)[:k]

The answer (October 1922) is already in the first result; the second gold paragraph (the Socialist Revolutionary Party, which links Kerensky to the war) is never found, and a second search for the war's end date only returns more war. Excluding already-seen paragraphs is a design choice of the root's tool: it forces every search to show something new.

So "native tool calling" is a prompt convention the model was trained on, rendered by the template: the schema is text in the system turn, and the call is text the harness parses. Two consequences: the description is the main lever on query quality (say what the tool returns and how a good query looks: "a short query naming one entity or fact"), and every tool added to an agent is paid on every call.

Why loops get expensive: the formula, checked against the recordings

Each call re-reads everything before it. With s the tokens of the first call (instructions, tool description, question) and r the tokens each step adds (the model's own thought and action plus the observation), the prompt tokens over n searches and a final answer are

With one search the formula is exact by construction (two calls, r is their difference). The last column is the point of prompt caching: llama-server keeps the previous call's attention state (the KV cache) and only computes the new tokens, so on average @@prefilled_mean@@ of the @@billed_mean@@ billed tokens were computed. An API with prompt caching bills the cached part at a discount (the {{Long-context calculator|#t-arlong}} has the prices); it does not make each step's generation faster.

Budgets and stopping

The root's agent may search at most 4 times. What it did with that freedom, over the 200 questions (measured, from the recorded trajectories):

  • It saw both gold paragraphs in @@b_until_both_n@@ trajectories: after the first search in @@b_found1@@, the second in @@b_found2@@, the third or fourth in @@b_found34@@. It searched again after already having both @@b_wasted_after_both@@ times.
  • It stopped too early (answered without ever seeing the second gold paragraph) in @@b_stopped_missing@@ trajectories, @@b_stopped_missing_wrong@@ of them wrong. Stopping is a judgment the model makes from its own reading, and a small model is overconfident.
  • It repeated a query in @@b_repeat@@ trajectories and used the whole budget in @@b_budget_hit@@ (the same trajectories, mostly: stuck loops that only the budget ended); @@b_noaction@@ times it wrote no parseable action at all.

The root's table of F1 by number of calls makes the same point from the other side: questions the agent needed 4 or 5 calls for scored far worse than those it finished in 2 or 3. Long trajectories are mostly failing trajectories, so a tighter budget may cost little accuracy. Measured, the same agent with a search budget of 1: F1 @@pd_react_budget1_f1@@ (@@pd_react_budget1_tok@@ tokens); 2: @@pd_react_budget2_f1@@ (@@pd_react_budget2_tok@@); 3: @@pd_react_budget3_f1@@ (@@pd_react_budget3_tok@@); 4, the root's run: @@f1_react@@ (@@tok_react@@); 6: @@pd_react_budget6_f1@@ (@@pd_react_budget6_tok@@). Beyond two searches the budget buys tokens, not accuracy (budget 6 against 4: @@pd_rvr_budget6@@): a budget of 1 forces an answer from 3 paragraphs and falls well below the top-5 pipeline.

How to check it on your system: log every call's prompt tokens and every search's query and results; plot calls per question, and count repeated queries, unparseable steps and budget hits. They are cheap to compute and they find most loop bugs.
