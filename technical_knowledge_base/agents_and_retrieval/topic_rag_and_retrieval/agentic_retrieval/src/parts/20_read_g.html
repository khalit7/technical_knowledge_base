8. Long context against retrieval, in depth

The problem. Qwen3-1.7B and 4B read 32,768 tokens natively (their model cards; the GGUF files declare 40,960), frontier models a million or more. If the documents fit, why retrieve? The root's section 7 gives the per-query price formula and the published head-to-head results; this section measures what a long window costs on this laptop and what it does to accuracy.

What a long prompt costs: prefill, from zero

Before writing its first token, the model must run every prompt token through every layer: prefill. Each token's attention reads the keys and values of all tokens before it, so prefill has a part linear in the prompt length n (the weight matrices, once per token) and a part that grows with n2 (attention). The keys and values are kept for the rest of the request: the KV cache. Its size per token is fixed by the architecture: 2 (keys and values) × layers × KV heads × head dimension × bytes per number. KV cache at fp16 (from the configs): Qwen3-1.7B @@kv17@@ bytes (@@kv17_kib@@ KiB) per token, so @@kv17_32k@@ GiB for 32k tokens; Qwen3-4B @@kv4_kib@@ KiB, @@kv4_32k@@ GiB, on a 16 GB machine that also holds the weights.

What transfers: the shape (a linear term, an attention term that dominates past a few thousand tokens, a cache that grows with the window) holds on any GPU; datacenter GPUs and FlashAttention kernels change the constants by an order of magnitude or more (not run here). Hosted APIs hide prefill in the time to first token and bill it per token; a cached prefix is billed at a discount and skips the prefill. Advertised against effective context

A window size says what the model accepts, not what it uses. RULER (Hsieh et al. 2024, {{arXiv 2404.06654|https://arxiv.org/abs/2404.06654}}) defines a model's effective length as the longest length at which its average score over 13 synthetic tasks stays above 85.6% (Llama-2-7B's score at 4k). Published (Table 3, claimed / effective): GPT-4 128k / 64k; Llama-3.1-70B 128k / 64k; Qwen2-72B 128k / 32k published. The RULER leaderboard lists Qwen3 models from the Qwen3 report (authors' numbers), and two rows contradict the stated rule: Qwen3-8B (82.1 at 64k) and Qwen3-4B (77.8 at 64k) are marked 64k effective although both are below 85.6 (README read 2026-10-14). NoLiMa (Modarressi et al. 2025, {{arXiv 2502.05167|https://arxiv.org/abs/2502.05167}}) removes the word overlap between question and answer that makes needle-in-a-haystack easy: GPT-4o falls from 99.3% to 69.7% at 32k published. {{Long-context and multimodal benchmarks|n:3ef5c17b0d0d810bb4dfc98919c9be8a}} covers these benchmarks.

When each wins
Long context: a small, stable corpus read once or as a whole (summarise, find inconsistencies), repeated queries over the same documents with a cached prefix, and no per-user access rules. Retrieval: corpora beyond the window, per-query cost and latency budgets, per-user filtering, and small or mid-size models that read badly with distractors (measured above). They compose: retrieve generously (whole sections, 20 to 50 chunks) and let the window absorb chunking mistakes; on this model, keep the retrieved set small.

9. Memory: retrieval over the agent's own history

The problem. An agent working for hours, or across sessions, produces more history than fits in its window, and re-reading it all on every step is the quadratic cost of section 1. Agent memory stores that history outside the window and retrieves from it. Everything about retrieval carries over (chunk, embed, search, rerank, measure recall), with two differences: the corpus is written by the same process that will later search it, and it changes on every step, so what to write, when to curate, and when to recall matter as much as search.

Write-time against read-time curation. Write-time: when a step or task ends, distil it into a fact, a summary or a skill, and store only that; whatever the distillation dropped is gone for every later task. Read-time: keep the raw history and select or summarise from it once the current task is known. {{Just-in-Time Memory|n:3e95c17b0d0d818f89b3f066f816727b}} argues for read-time curation and gains 16.2 points on ALFWorld over the strongest baseline, mostly from training the curator (its page has the corrected reading); the {{Proactive Memory Agent|n:3e25c17b0d0d81ce85e0c6d82f6beb4c}} adds the timing question, a second model deciding when to remind the worker. Extracted-fact stores: Mem0 ({{arXiv 2504.19413|https://arxiv.org/abs/2504.19413}}) extracts facts per turn and applies ADD, UPDATE, DELETE or NOOP against similar stored facts; on LOCOMO it reports 91% lower p95 latency (1.44 s against 17.12 s) and about 1.8k memory tokens against 26k for the full conversation, while full context stays more accurate (J score 72.90 against 66.88) published by the Mem0 authors. Zep's Graphiti ({{arXiv 2501.13956|https://arxiv.org/abs/2501.13956}}) stores facts in a temporal graph with validity windows; LongMemEval 71.2% against 60.2% for full context with gpt-4o published by the Zep authors. Fact stores, temporal graphs and paging are the subject of {{Agent memory layers|n:3f15c17b0d0d8170a200ce4476385ff5}}.

How to check a memory system: plant facts in early turns, ask about them later, and measure recall of the planted memory (did retrieval return it) separately from the answer; add superseded facts (an old address, then a new one) and check the newer wins; log every write so a wrong answer can be traced to a write that never happened, a retrieval that missed, or a reading failure.
