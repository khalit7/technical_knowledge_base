Qwen3-1.7B and 4B read 32,768 tokens natively (their model cards; the GGUF files declare 40,960), frontier models a million or more. If the documents fit, why retrieve? When each wins
Long context: a small, stable corpus read once or as a whole (summarise, find inconsistencies), repeated queries over the same documents with a cached prefix, and no per-user access rules. Retrieval: corpora beyond the window, per-query cost and latency budgets, per-user filtering, and small or mid-size models that read badly with distractors (measured above). They compose: strong readers can take generous retrieval (whole sections, 20 to 50 chunks) and let the window absorb chunking mistakes; on this model, keep the retrieved set small.

9. Memory: retrieval over the agent's own history

An agent working for hours, or across sessions, produces more history than fits in its window, and re-reading it all on every step is the quadratic cost of section 1. Agent memory stores that history outside the window and retrieves from it: everything about retrieval carries over, except that the corpus is written by the process that will search it and changes on every step. What to write, when to curate, fact stores (Mem0), temporal graphs (Graphiti) and memory files are owned by {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, which measured all three in a twelve-session experiment. The retrieval question this page measures: once the task is known, which of the agent's own reads should the final step keep? Write-time curation (distil each step into a fact) loses whatever the distillation dropped; read-time curation keeps the raw history and selects with the current task as the query ({{Just-in-Time Memory|n:3e95c17b0d0d818f89b3f066f816727b}} argues for it and gains 16.2 points on ALFWorld, mostly from training the curator). The plainest read-time design is also the baseline every memory system must beat: Bao et al. 2026 ({{arXiv 2610.30755|https://arxiv.org/abs/2610.30755}}) run "Raw-RAG", dense retrieval plus a reranker over the raw conversation history, against agentic memory systems on LoCoMo, LongMemEval, MEME and MemoryAgentBench, and it "ranks first among the compared memory systems in six of seven benchmark-model settings", by 0.13 to 5.53 points over the strongest one published. Their reading: raw history covers more of the needed evidence, which outweighs the reader using it less efficiently, and even full access to a transformed memory store leaves an accuracy gap, because the transformation already lost information.

How to check a memory system: plant facts in early turns and ask about them later, measuring recall of the planted memory (did retrieval return it) apart from the answer; add superseded facts (an old address, then a new one) and check the newer wins; log every write, so a wrong answer can be traced to a write that never happened, a retrieval that missed, or a reading failure.

Published memory systems: the numbers context engineering does not carry

Mem0 ({{arXiv 2504.19413|https://arxiv.org/abs/2504.19413}}) extracts facts per turn and applies ADD, UPDATE, DELETE or NOOP against similar stored facts; on LOCOMO it reports 91% lower p95 latency (1.44 s against 17.12 s) and about 1.8k memory tokens against 26k for the full conversation, while full context stays more accurate (J score 72.90 against 66.88) published by the Mem0 authors. Zep's Graphiti ({{arXiv 2501.13956|https://arxiv.org/abs/2501.13956}}) stores facts in a temporal graph with validity windows; LongMemEval 71.2% against 60.2% for full context with gpt-4o published by the Zep authors. The {{Proactive Memory Agent|n:3e25c17b0d0d81ce85e0c6d82f6beb4c}} adds the timing question: a second model deciding when to remind the worker.
