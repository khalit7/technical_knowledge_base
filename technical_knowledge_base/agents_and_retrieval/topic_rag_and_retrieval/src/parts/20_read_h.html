8. Production: latency, freshness, tenants, cost, caching

Latency: time the whole request, not the stages. Measured one at a time, the stages of a SciFact request look cheap except the generator. Measured as one request in one process on the same laptop, the embedding and reranking stages are several times slower, because the embedding model, the reranker and the generator share one GPU.

One request, measured two ways

Median milliseconds per query, batch 1, Apple M1 Pro (MPS for the encoders, Metal llama.cpp for Qwen3-1.7B), bench lock held measured. Stages: Qwen3-Embedding query embedding, exact search over 5,183 vectors, ms-marco MiniLM cross-encoder on the top 30, generator time to first token. "On its own": the Pipeline lab's stage timings (40 claims × 3) and the production child's time to first token at about 1,720 prompt tokens. "One process": the production child's end-to-end run (40 claims × 3, 1,644 prompt tokens with the top 5).

The ratios transfer to a server (the reranker and generator dominate, vector search over thousands of documents is negligible); the milliseconds do not (a datacenter GPU is much faster and batches many users). The lesson that transfers exactly: a latency budget is checked on the whole request path, under the real sharing of hardware.

Freshness and re-indexing. New documents must be parsed, chunked, embedded and written to both indexes; deletions must really delete. A model change re-embeds the whole corpus, and the vectors of two models cannot share an index even at the same dimension: halfway through a backfill from MiniLM to bge-small in one index, nDCG@10 falls to 0.374 to 0.379 from 0.645 and 0.713; a bge-small query against an all-MiniLM index scores 0.137 measured, production child. Build the new index beside the old one, then switch. How documents are chunked decides how much a revision costs: on ten revised arXiv papers whose revisions changed 15.0% of the words, fixed 200-word windows re-embedded 75.8% of the words and structure-aware chunks 49.2%, because one inserted word shifts every later fixed window (the {{Document ingestion|n:3f85c17b0d0d81279079f614f382f2e7}} child) measured.

Tenants and access control. Filter at retrieval, by tenant and permission, inside the search (sections 1 and 4). Even then, check the engine: in pgvector with row-level security no forbidden row ever came back, but with psycopg's default prepared statements PostgreSQL reused one generic HNSW plan across users, so a user allowed 2.1% of the corpus got 0.96 rows of 10 on average and nothing at all for 123 of 300 claims measured, production child.

Cost per query. The production child's worked example with list prices read on 2026-10-14 (1 million queries a month, a hosted embedder, a hosted reranker on 30 candidates, a small hosted generator reading 5 chunks): $0.0012 per query, of which generation 62% and reranking 36%; the hosted reranker costs more than half as much as the generator because it reads 30 passages where the generator reads 5 derived from vendor prices. The vector store's own bill (read units, replicas, minimums) sits mostly outside that formula. Its {{Cost calculator|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}} has every knob.

Caching. Three caches, three different risks. A prompt (prefix) cache keeps the model's state for a repeated prompt prefix: for a 3,606-token prefix the 1.7 B model's first call took 4,149 ms and later calls 73 ms measured; safe and large. A result cache keyed on the query vector returns a previous query's retrieved list for a near-identical query: at a cosine threshold of 0.90 SciFact's nDCG@10 moved from 0.700 to 0.702, harmless. A semantic answer cache returns a previous query's answer, and near-duplicates with opposite meanings break it: SciFact contains 303 pairs of claims about the same abstract with opposite verdicts, whose median cosine (0.947, Qwen3-Embedding) is higher than that of same-verdict pairs (0.781); replayed at a threshold of 0.95, 144 of the 254 cache hits (57%) would have returned the answer to the opposite claim measured, production child.

Go deeper: {{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}} (latency waterfall, cost calculator, access lab, cache lab, monitoring); prefix caching and serving the generator on {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}.

9. The tools

A retrieval system is a stack of separate choices: a parser, a framework or your own code to chunk and wire the steps, an embedding model, an ANN index inside a vector store (or a library such as FAISS), a keyword engine, a reranker, and an evaluation tool. The {{Tool map|#t-map}} is a dated atlas of each layer (owner, licence, latest release, status, the algorithm it actually runs, when to choose it), a "which store" chooser and a timeline. Its measured lesson: the defaults differ more than the algorithms. Given the same SciFact bge-small vectors and nothing changed, hnswlib (ef 10) returns 0.876 of the exact top 10, FAISS IVF (nprobe 1) 0.420, LanceDB's default IVF_PQ index about 0.59, Chroma 0.996 to 0.998, and Qdrant's local mode and Milvus Lite 1.000 because they never build an index; one knob each recovers nearly everything measured, Tool map. Framework defaults bite the same way: LlamaIndex returns 2 chunks unless told otherwise, LangChain's text splitter cuts 4,000 characters (MiniLM reads only its first 256 tokens, a third of such a chunk).

Which to use, in one line each (status and evidence on the Tool map): pgvector when the data already lives in PostgreSQL and fits one server; Qdrant, Weaviate or Milvus as dedicated engines with in-graph filtering and built-in hybrid search; Elasticsearch or OpenSearch when BM25 is already there; FAISS as a library for experiments and exact baselines; a managed service when nobody can operate a database. For models, shortlist open ones you can measure locally (Qwen3-Embedding, bge, gte) against hosted ones (OpenAI, Gemini, Voyage, Cohere) on your own golden set. For evaluation, ranx or pytrec_eval for retrieval metrics; RAGAS, DeepEval or TruLens for judged ones, by way of the {{RAG and retrieval evaluation|n:3ef5c17b0d0d8194a914d1843ee26f13}} page.
