Interview questions, short answers

Explain RAG in two minutes, and why not just fine-tune?
Retrieve the passages that bear on a question from an external corpus, put them in the prompt, have the model answer from them and cite them. Fine-tuning changes how a model behaves but is a poor way to add facts: it cannot be updated per document, cannot cite, cannot give two users different views, and still hallucinates on what it saw once. RAG updates by re-indexing, cites by construction and enforces access at retrieval. They combine: fine-tune for format and domain style, retrieve for facts.
BM25 or embeddings?
Both, usually. BM25 wins on exact identifiers, rare names and domain terms and costs no model; embeddings win on paraphrase. Fuse them with RRF, then check on your data: fusion helped every model close to BM25 on SciFact and hurt the two that clearly beat it. If one dominates, weight it, with the weight chosen on held-out queries.
How is an embedding model trained?
Contrastively, on (query, relevant passage) pairs: InfoNCE asks each query to pick its passage out of a line-up of the batch's other passages (in-batch negatives, free) and mined hard negatives (passages that look relevant but are not). Large batches and hard negatives make the line-up harder; false negatives (unlabelled relevant passages) must be filtered. Often followed by Matryoshka training, instruction prefixes and distillation from a cross-encoder.
HNSW, IVF or exact search?
Exact below about a million vectors if the scan fits the latency budget (one core scans about 37 GB/s here: 112 ms per million 1,024-dim vectors), and always as the ground truth. HNSW for low latency at high recall in memory (knobs M, efSearch). IVF or IVF-PQ when memory or build time dominate (knobs nprobe, m, rescoring). DiskANN when the vectors outgrow RAM. Report ANN recall at the setting, never speed alone.
Our vector search has 0.98 recall but answers are bad. Where do you look?
0.98 is ANN recall against exact search: the index is fine. Measure retrieval recall@K and nDCG on labelled queries with exact search: if low, the embedding model, chunking or query (prefix, domain) is the problem. Then check whether the evidence reaches the prompt (ranking) and whether the model uses it (generation).
Users say the answers are wrong. How do you find the broken stage?
Build a golden set (a few hundred real questions with labelled passages). Log the first stage's top K, the reranked top k and the answer for each. Count the three buckets: evidence not in top K (retrieval), in K not in k (ranking), in the prompt but wrong (generation). Run an oracle prompt with only the gold passages for the ceiling of g. Fix the biggest bucket; on SciFact with a 1.7 B model that was generation, 82 of 92.
How deep should the reranker read?
Sweep K on the golden set against latency. The first stage's recall@K is the ceiling; past the point where it flattens, more K costs linearly more time and gives a reranker more chances to promote a wrong passage. On SciFact the strong rerankers peaked at K 20; the weak one got worse with every extra candidate.
When would you use an agent loop instead of a pipeline? GraphRAG? Long context?
A loop for multi-hop and exploratory questions, whose second search depends on what the first found, with a step budget, since input tokens grow with n(n + 1)/2; a router in front sends lookups to the pipeline. GraphRAG for corpus-global questions ("main themes across everything") when the corpus is stable and the indexing budget is there. Long context when a small corpus fits the window and is read once or holistically; retrieval for scale, cost per query, latency and per-user access.
How do you enforce multi-tenant access control?
Metadata on every chunk at index time (tenant, groups); the filter applied inside each search (BM25 query and ANN traversal), never on the result list and never as a prompt instruction (17 of 18 answers leaked that way here). Then test it: restrictive filters with graph indexes, the engine's planner, prepared-statement plans, and deletion that really deletes.
Design a RAG system: question answering over 5 million internal documents (PDFs, wiki pages, tickets) for 20,000 employees, permission-aware, p95 under 3 s. Walk through it end to end.

1. Clarify and measure first. Question types (lookups, multi-hop, "summarise everything about X"), freshness needs, languages, the permission model, query volume (say 50,000 a day), budget. Build a golden set of 300 to 500 real questions with labelled passages from search logs and tickets, split into tuning and test.

2. Ingestion. A layout-aware parser for PDFs (tables and headings kept), connectors for the wiki and tickets; chunk by structure (sections, then paragraphs, capped near 256 to 512 tokens), title and section path prepended; metadata on every chunk: source, date, owner, access groups, document id and version. Content hashes per chunk so a revision re-embeds only what changed.

3. Indexes. About 5 M documents may be 50 to 100 M chunks: at 1,024 dims float32 that is 200 to 400 GB of vectors, so a Matryoshka model cut to 512 dims with int8 storage (about 26 to 51 GB) plus float originals on disk for rescoring, in an HNSW index sharded across a few nodes; or IVF-PQ if memory is tight. BM25 index on the same chunks. Choose the embedding model by nDCG@10 on the tuning split (open models measured locally against one or two hosted ones).

4. Query path. Conversational rewrite in chat; BM25 and dense search in parallel with the user's access groups as a filter inside each search (top 100 each); RRF, or a weighted fusion tuned on the tuning split; a cross-encoder on the top 20 to 50 (measure K); the top 5 to 8 chunks with ids into the prompt; the generator answers with citations or says it cannot find it.

5. Latency budget (an illustrative split of p95 3 s to first token, to be checked by measurement): rewrite 300 ms (skip when the question stands alone), embed 30 ms on a GPU, search 50 ms, rerank 200 to 400 ms on a GPU at K 30, generator time to first token about 1 s; stream the answer. Time it as one request on the real hardware.

6. Hard parts. Permissions change: sync groups into chunk metadata and filter at query time, never cache answers across users. Freshness: incremental re-index on change events, deletes propagated. Model upgrade: build a new index beside the old, switch when complete. Cost: estimate per query (reranker plus generator dominate) and cache prefixes, not answers.

7. Evaluate and monitor. Offline: recall@K at the rerank depth, nDCG@10, r, p and g, faithfulness by a calibrated judge. Online: citation clicks, "no answer" rate, sampled human review, alerts when retrieval scores drift. Add an agent loop and a router later, only if the golden set shows multi-hop failures the pipeline cannot fix.
