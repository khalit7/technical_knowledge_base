4. Indexes: finding the nearest vectors fast

Exact search first. Exact (flat, brute-force) search compares the query with every stored vector and keeps the best k. It is always right and needs no index. On one core of this laptop it streams about 37 GB of vectors per second: 0.5 ms for SciFact's 5,183 vectors of 1,024 numbers, 22 ms for 522,931 Quora questions of 384 numbers, about 112 ms for a million of 1,024 measured, Vector indexes child. Below roughly a million vectors, exact search is often fast enough, and it is always the honest baseline that every approximate index is measured against.

The memory bill, and what an exact scan costs

Vector bytes = vectors × dimensions × bytes per number derived. Graph: hnswlib's layer 0 keeps up to 2M neighbour ids of 4 bytes plus a 4-byte count per vector (upper layers hold about 1 in M vectors and are left out) derived from the layout read in hnswlib 0.8.0 by the Vector indexes child. Scan time = vector bytes / 37 GB/s, the one-core rate measured for float32 on this M1 Pro; at the defaults it gives 111 ms against the child's measured 112 ms (by construction, since the rate came from that run). Real engines add metadata, text and allocator overhead.

Approximate nearest neighbour (ANN) indexes look at a small part of the data and accept that they will sometimes miss a true neighbour. Three ideas cover almost every index in use, each shown here with one measured number on SciFact's Qwen3-Embedding vectors (share of the exact top 10 returned, called ANN recall@10) measured:

  • IVF (inverted file): k-means splits the vectors into cells; a query scans only the nprobe cells nearest to it. With 72 cells, scanning 1 cell returns 0.482 of the true top 10, 8 cells 0.901, 32 cells 0.992. It misses neighbours just across a cell border.
  • PQ (product quantization): cut each vector into m pieces and replace each piece by the id of its nearest learned centroid, so 4,096 bytes become m bytes, and distances are estimated from the codes. At 16 bytes per vector: 0.450 alone, 0.914 after rescoring the top 100 with the full vectors. IVF-PQ combines both, the classic billion-scale design.
  • HNSW (hierarchical navigable small world, {{Malkov and Yashunin|https://arxiv.org/abs/1603.09320}}): link each vector to a few near neighbours, in layers from sparse to dense; a query walks greedily toward closer vectors keeping a frontier of efSearch candidates. FAISS HNSW (M 32): efSearch 16 returns 0.980, efSearch 64 0.999. It is the graph index of pgvector, Qdrant, Weaviate, Milvus and Lucene, and costs memory for the graph.
  • DiskANN (Vamana graph): one flat graph kept on SSD with compressed vectors in memory, for collections larger than RAM ({{Subramanya et al., NeurIPS 2019|https://papers.nips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html}} published). Not runnable on this Mac (diskannpy ships Linux and Windows wheels only); the Vector indexes child built Vamana from the paper's algorithms instead.

Smaller vectors. Two knobs, independent: fewer bits per number, or fewer numbers. Storing Qwen3-Embedding's vectors as int8 (1 byte each) and searching with a float query returns 0.996 of the exact top 10; binary codes (1 bit each, 32 times smaller) return only 0.674, and 0.990 after rescoring the top 100 with the float vectors. Matryoshka training ({{Kusupati et al. 2022|https://arxiv.org/abs/2205.13147}}) packs the most useful information into the first dimensions so vectors can be cut: Qwen3-Embedding, trained that way, keeps 98% of its nDCG at half its dimensions and 95% at a quarter; bge-small, not trained that way, keeps 94% and 81% measured, Vector search lab. Binary needs rescoring; int8 with a float query is close to free; truncation works for models trained for it.

Predict: an HNSW setting returns 95.9% of the exact top 10 (efSearch 8). Exact search finds a labelled relevant abstract in the top 10 for 84.5% of claims. With this index, about how often?
82.7%. These are two different recalls. ANN recall asks how much of the exact top 10 the index returned: it needs no labels and measures only the index. Retrieval recall asks how many labelled relevant documents are in the top 10: it measures the embedding model first and the index second. The index loses relevant abstracts at about the rate it loses any neighbour (IVF with 8 cells: ANN 0.901, retrieval 0.779 against 0.761 expected from 0.901 × 0.845) measured. A perfect index cannot lift retrieval above the model's 0.845.

Filters. Real queries carry conditions (tenant, date, permissions). Applying the filter after the index (a post-filter) is easy and silently returns fewer results: when a user may see 10% of SciFact, fetching 10 and filtering leaves 1.73 on average and nothing at all for 14 of 300 claims measured, Pipeline lab. Filtering inside the search is the fix, and with a graph index it has its own failure: a restrictive filter cuts the paths the walk needs. Engines add iterative scans (pgvector since 0.8.0), filter-aware traversal (ACORN, Weaviate's default since v1.34) or a switch to exact search when few rows pass. The {{Vector indexes|n:3f85c17b0d0d81f29707c130b2ebcfb1}} child measures all of these, and {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}} shows them inside PostgreSQL.

Stores, and the index you did not get. A vector store wraps an index with storage, metadata and filtering. Small test collections can hide the index entirely: the Qdrant 1.19.2 server builds no HNSW graph for a collection under its 10,000 KB indexing threshold, and even with the graph built its planner scans exactly below a second 10,000 KB threshold, so SciFact (about 8 MB of bge-small vectors) was always searched exactly; Milvus Lite scans flat even after you ask for HNSW measured, Tool map. Benchmark the server and the size you will run. The atlas of stores, with what index each actually runs, is the {{Tool map|#t-map}}; the {{Vector search lab|#t-vec}} shows exact against HNSW against IVF-PQ on one query.
