This is the index's recall, not the retrieval's: it asks whether the tool found the true nearest vectors, whatever their relevance. Relevance is the second number, nDCG@10 against SciFact's human labels (a ranking score from 0 to 1 that rewards relevant abstracts near the top; the {{Pipeline lab|#t-pipe}} teaches it).

What it shows. Besides the reference (FAISS Flat), three tools are exact at their defaults: Qdrant's Python client in local mode and Milvus Lite never build an index (they scan), and LanceDB scans until you call create_index(). The graph indexes (Chroma, USearch, FAISS HNSW, hnswlib) are close but not exact, and the gap is the search-breadth knob: hnswlib ships ef = 10 and FAISS efSearch = 16, Chroma ef_search = 100. The cluster indexes lose most: FAISS IVF (72 clusters here, the common square-root-of-N choice; FAISS has no default for it) searches only the nearest cluster by default (nprobe 1), and LanceDB's default IVF_PQ compresses each vector, so the ranking inside the shortlist is approximate too. One knob each recovers nearly everything, which is why "we tried X and recall was bad" usually means "we did not set the knob".

Common mistake: benchmarking a local mode
Qdrant's QdrantClient(":memory:") and Milvus Lite are for development. Both scan every vector, so their recall is perfect and their speed says nothing about the server's index. Milvus Lite even reports HNSW from describe_index after you ask for it, while returning flat-scan results (measured above in the atlas card). Benchmark the server you will run.
