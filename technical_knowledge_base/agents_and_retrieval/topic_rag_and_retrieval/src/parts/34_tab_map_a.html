Tool map

A retrieval system is a stack of separate choices: something that splits documents and wires the steps together (a framework), a model that turns text into vectors (an embedding model), a structure that finds the nearest vectors fast (an ANN index, approximate nearest neighbour), usually wrapped in a vector store that also keeps the text and metadata, a keyword engine (BM25), a second model that re-scores the shortlist (a reranker), and tools that evaluate the result. This tab is a dated atlas of the tools at each layer as of 13 October 2026: who owns each one, its licence, its latest release, whether it is alive, what algorithm it actually runs (read in source or docs, not from marketing pages), and when to choose it.

The stack, one layer per choice

Read from the top: a question arrives, a framework (or your own code) splits and wires; the embedding model and BM25 turn the question into something searchable; the index finds candidates; a reranker or late-interaction model orders them; an evaluation tool tells you whether any of it worked. Click a layer to filter the atlas below to it.

The one idea to keep
Most of the difference between two vector stores is not the algorithm (nearly all of them run HNSW, the graph index, or a cluster-based IVF index) but the defaults they ship, how they filter, whether hybrid search is built in, and who operates them. The measured section below shows how far the defaults alone move the result on the same vectors.
