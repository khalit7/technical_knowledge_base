5. The pipeline: chunk, rewrite, fuse, filter, rerank, assemble

A production retrieval pipeline runs in two halves. At index time, before any question: parse documents, cut them into chunks, attach metadata, write a keyword index and a vector index. At query time: rewrite the question if it needs it, search both indexes with the filters inside each search, fuse the two lists, rerank the top of the fused list, and put the best few chunks, with their ids, into the prompt. Each stage below has the problem it solves, what it costs, and one measured lesson. The {{Pipeline lab|#t-pipe}} measures every stage on the running example; the {{retrieval pipeline|n:3c65c17b0d0d819899fde889e1e8b782}} and {{rerankers|n:3f85c17b0d0d813fba53fc883f8a2c8f}} children go deeper.

Chunking: cut where the author did, compare at equal tokens

A paper is thousands of tokens; an embedding model reads a few hundred, and the prompt holds a few passages. So documents are cut into chunks, each indexed on its own. If a cut falls through the paragraph that answers the question, no chunk holds the whole answer. On QASPER's 892 questions with annotated evidence paragraphs, fixed 256-token windows keep an evidence paragraph whole for 607 (68.0%); splitting on blank lines first (the "recursive" rule) keeps 838 (93.9%) measured. Overlap between windows is a patch: 32 tokens of it move fixed windows from 546 to 607 and cost 14% more tokens to index.

The trap is in how chunkers are compared. At a fixed number of chunks (the top 3), 512-token fixed chunks beat paragraph-aware chunks of at most 256 tokens with BM25 (61.4% of questions found against 45.3%), because three 512-token chunks are three times the text. At an equal budget of 1,024 tokens the order flips: 45.9% against 64.5% measured. Compare chunkers at an equal token budget. Before chunking comes parsing PDFs into text: of 107 evidence paragraphs in QASPER papers' PDFs, MinerU (flash) kept 94 intact and pdfplumber 1 ({{Document ingestion|n:3f85c17b0d0d81279079f614f382f2e7}} child) measured.

Contextual retrieval ({{Anthropic, September 2024|https://www.anthropic.com/news/contextual-retrieval}}) has a language model write one or two sentences situating each chunk in its document, prepended before indexing; Anthropic reports top-20 retrieval failures falling from 5.7% to 3.7% with contextual embeddings, 2.9% adding contextual BM25 and 1.9% adding a reranker, at $1.02 per million document tokens with prompt caching vendor. Run here with Qwen3-1.7B writing the context on 71 QASPER papers, it gave no clear gain (bge-small at a 1,024-token budget 57.7% to 55.2%, within noise) measured: the writer's quality matters, and the setting differs (here retrieval runs inside one paper).

Query transformation

The words a user types are not always the documents' words. HyDE ({{Gao et al. 2022|https://arxiv.org/abs/2212.10496}}) asks the model to write a fake answer passage and embeds that; multi-query retrieves with several rewordings and fuses; conversational rewrite turns "does it help?" into a standalone question using the chat history. On SciFact, HyDE lifts Qwen3-Embedding from 0.700 to 0.718, multi-query does nothing (0.699), and each costs a generator call before retrieval can start (about 2.2 s and 0.8 s per claim with the 1.7 B model here, more than the whole retrieval stage) measured. On eight constructed two-turn chats, the rewrite put the evidence in the top 3 for 6 to 7 of 8, against 3 to 5 for the follow-up alone. Rewrite in chat always; gate the rest on query difficulty.

Hybrid search and reciprocal rank fusion

BM25 and embeddings make different mistakes, so production systems run both and merge the lists. The scores live on different scales (a BM25 score of 9 against a cosine of 0.7), so the standard merge ignores scores and uses ranks: reciprocal rank fusion (RRF; {{Cormack, Clarke and Büttcher, SIGIR 2009|https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf}}) gives each document Σlists 1 / (k + rank), with k = 60. A document both lists rank moderately beats one list's favourite.

Hybrid helps some models and hurts others; a reranker helps only if it is stronger

SciFact, 300 test claims, nDCG@10, deterministic measured, Pipeline lab (src/pipe/out/fusion.json and rerank.json). Fused list: BM25 + Qwen3-Embedding-0.6B with RRF k 60. Rerankers read the fused top K and the rest of the list keeps its order.

Equal-weight RRF helps a dense model that is about as good as BM25 and disagrees with it (MiniLM 0.645 to 0.713, Qwen3-Embedding 0.700 to 0.724) and hurts the two that clearly beat BM25 (gte-modernbert 0.767 to 0.763, ColBERT-small 0.743 to 0.731): equal weight gives the weaker list the same say. A weighted fusion with the weight chosen on SciFact's training claims (z-score fusion, α 0.6) reaches 0.739 for Qwen3; picking α on the test claims would claim 0.744, a leak. Hybrid is not always better; measure it, and tune any weight on held-out queries.

Filtering

Metadata filters go inside each first-stage search, never on a list already cut to a top-k (section 4 has the measured loss). Access control is a filter, and the only place it works is here (section 1).

Reranking, and late interaction

A cross-encoder reranker puts the query and one candidate through a single transformer together and outputs one relevance score. It sees every interaction between their words, so it is far more accurate than comparing two precomputed vectors, and far too slow for the whole corpus, so it reads only the first stage's top K. Qwen3-Reranker-0.6B lifts the fused list from 0.724 to 0.782 at K 20; bge-reranker-v2-m3 reaches 0.757; the small ms-marco MiniLM cross-encoder, trained on web search, makes it worse the deeper it reads (0.702 at K 30, 0.689 at K 100). It reproduces the BEIR paper's BM25+CE score (0.688) only because BM25 alone is weaker than it. A reranker helps only when it is stronger than the first stage. The price is time and grows linearly with K: at K 30, 155 ms for MiniLM, 2.18 s for bge-reranker-v2-m3 and 6.62 s for Qwen3-Reranker on this laptop's GPU, batch 1 measured.

Late interaction ({{ColBERT|https://arxiv.org/abs/2004.12832}}) sits between the two: keep one small vector per token of every document, and score a query by summing, for each query token, its best match among the document's tokens (MaxSim). answerai-colbert-small scores 0.743 on SciFact searching exhaustively, at 29 times the storage of one bge-small vector per abstract measured, rerankers child. The {{rerankers|n:3f85c17b0d0d813fba53fc883f8a2c8f}} child covers cross-encoders in code, depth, calibration, LLM rerankers, ColBERT and PLAID.

Prompt assembly and citations

The top k chunks go into the prompt with stable ids, and the instruction asks the model to answer from them and cite the id it used, which makes the answer checkable. Two measured lessons. The prompt is a knob, tuned on held-out data like any other: the Pipeline lab's first SciFact prompt made Qwen3-1.7B answer "NOT ENOUGH INFO" almost always (23 of 188 right even with the gold abstracts); three prompts were compared on training claims, and the chosen one gets 112 with gold abstracts. More context is not free for a small model: with the reranker on, g falls from 0.626 with one abstract to 0.539 with three and 0.530 with five measured. Where in a long prompt the evidence sits matters too (section 7).
