The idea in one screen

An answer can use only the evidence that survives every stage: cut into a chunk that holds it whole, found by words or vectors under the user's filters, kept through fusion and reranking into the few chunks the prompt holds, then read and cited. So the pipeline is built for recall first, and judged by where, on your own labelled questions, the evidence is lost.

1. Chunking: cut where the author did

An embedder reads a few hundred tokens and returns one vector; a prompt holds a few thousand tokens. So a 6,000-token paper is cut into chunks, each indexed alone, and only some reach the model. A cut can lose the answer in two ways: the evidence paragraph is split, so no chunk holds it whole, or the chunk that holds it has lost the context that would make it match ("the model" without saying which). The root's shared runs measured the headline on QASPER: fixed 256-token windows keep an evidence paragraph whole for 607 of 892 questions, splitting on paragraphs first keeps 832 to 838, and at an equal budget of 1,024 tokens the share of questions whose evidence is handed over rises from 56.8% to 70.0% (bge-small) root runs. What the recursive splitter does (LangChain's default, read in langchain-text-splitters 1.1.3): it holds separators from coarse to fine, ["\n\n", "\n", " ", ""]; splits on the first one present; keeps pieces already under the target; merges consecutive short pieces up to the target, carrying a tail of up to overlap into the next chunk; and recurses with the next separator on any piece still too long. The default list has no sentence separator: after the newline comes the space, so a long paragraph is cut between two words wherever the size runs out (add ". ", as the root's rule does). The source, and the check that the real library reproduces the root's numbers, are in the closed block below.

Structure first, then small to big

When a document carries its own structure, cut along it. QASPER has Markdown headings, so LangChain's MarkdownHeaderTextSplitter splits at each heading, records the heading path as metadata (for filters and citations), and a size cap applies inside each section: 832 intact and 0.652 found with BM25 at 1,024 tokens, level with the root's paragraphs-within-sections rule (832; 0.645) measured.

Small chunks match precisely (a sentence is about one thing); big chunks carry the context the model needs. Small to big (or parent-child) retrieval does both: index small units, and when one matches, hand over the larger unit that contains it. LlamaIndex's SentenceWindowNodeParser is one form (it embeds single sentences and returns three on each side, DEFAULT_WINDOW_SIZE = 3, llama-index-core 0.14.25). Measured on QASPER within each question's paper (bge-small, parents handed over in the order their children rank until 1,024 tokens are used, each parent once):

Giving a chunk its document's context

Two methods attack the second failure, a chunk that lost its context. Late chunking (Günther et al., Jina AI, arXiv 2409.04701) runs the whole document through a long-context, mean-pooling embedder once, then averages the token vectors inside each chunk's span, so a chunk that says "the model" carries which model; published gains are large for weak embedders and small for strong ones (NFCorpus nDCG@10 23.5 → 30.0 with jina-embeddings-v2-small, none with nomic-embed) published, authors' runs. Run here with modernbert-embed-base it hurt: hurt here: paragraph-aware chunks found within 1,024 tokens 0.733 → 0.684, fixed windows 0.556 → 0.536 (modernbert-embed-base) measured; every chunk competing within one paper shares the same context, which makes them more alike, not easier to tell apart. Contextual retrieval (Anthropic, post of 2024-09-19) has a model write 50 to 100 tokens situating each chunk and prepends them before indexing; the vendor's top-20 retrieval failure rate fell from 5.7% to 3.7%, and to 1.9% with contextual BM25 and a reranker published, vendor, while the root's run with Qwen3-1.7B on 71 papers was within noise (at 1,024 tokens 57.7% → 55.2%) root runs. Late chunking costs one extra forward pass per document; contextual prefixes cost a generator call per chunk.

Fixed windows of c tokens overlapping by o start a new chunk every c − o tokens (the stride). A 10,000-token document at c = 512, o = 64 gives a stride of 448, ⌈9,936 / 448⌉ = 23 chunks and 10,000 + 22 × 64 = 11,408 tokens stored, 14% more than the text:

n = ⌈(L − o) / (c − o)⌉,    T = L + (n − 1) · o

Late chunking, published and run. It needs an embedder that pools by averaging and a context long enough for the document; longer documents go through in overlapping windows ("long late chunking", the paper's Algorithm 2). The paper's Table 2 (nDCG@10 on BEIR, 256-token chunks): jina-embeddings-v2-small NFCorpus 23.5 → 30.0 and SciFact 64.2 → 66.1 (Jina's blog of 2024-08-22 prints 23.46 and 29.98); jina-embeddings-v3 35.6 → 36.7 and 71.8 → 73.2; nomic-embed-text-v1 35.3 → 35.3 on NFCorpus; an average relative gain of about 3.5% for fixed-size chunks published, authors' runs. Merola and Singh (arXiv 2504.19754, April 2025) found contextual retrieval "preserves semantic coherence more effectively" while late chunking "offers higher efficiency but tends to sacrifice relevance and completeness". Run here with nomic-ai/modernbert-embed-base (ModernBERT, 149 M parameters, 8,192 tokens, mean pooling, Apache 2.0): it did not help. Within each question's own paper, at a 1,024-token budget, paragraph-aware chunks found 0.733 of questions embedded one by one and 0.684 with late chunking; fixed 256-token windows 0.556 against 0.536; the top-1 chunk is right for 0.318 against 0.243 (paragraph-aware) measured. The setting explains it: every chunk competing here comes from the same paper, so the document-wide context late chunking adds is shared by all of them and makes them more alike, not easier to tell apart. The published gains come from search across many documents (BEIR), where knowing which document a chunk belongs to is exactly what separates it. Cost: one pass over each whole paper (19 of 281 papers were longer than 8,192 tokens and went through in overlapping windows) took 376 s against 168 s for embedding the chunks one by one on MPS, because attention over long sequences costs more than over many short ones. The root lab's contextual prefixes showed the same within-paper pattern.

Contextual retrieval in detail. The vendor's failure rate was 2.9% with contextual embeddings plus contextual BM25, before the reranker. With prompt caching (the document is read once per document, not once per chunk) the vendor put the one-off cost at $1.02 per million document tokens, assuming 800-token chunks, 8,000-token documents and 100 tokens of context per chunk published, vendor. In the root's run, llama.cpp's prompt cache cut the prompt tokens from 11.1 M to 0.87 M, and bge-small top 3 moved 46.9% → 49.4% root runs.

2. BM25: the tokenizer matters more than k1 and b

A dense retriever finds paraphrases but can rank a vaguely related abstract above the one that names the exact gene; a word-matching retriever finds the exact word every time. BM25 ("Best Match 25", Robertson and colleagues, 1990s) is the standard word-matching score, computed over an inverted index (for every word, the documents containing it and how often). The formula from zero, with a calculator, and how the index is stored inside a database are on Search and vector databases (its section 4, "Ranking with BM25"). In one line: score(D, Q) = Σt in Q idf(t) · tf / (tf + k1 · (1 − b + b · |D| / avgdl)), where k1 sets how fast repeats stop counting and b how much document length matters. The tokenizer. BM25 only sees the terms its tokenizer produces. bm25s's default lowercases, keeps runs of two or more word characters (token_pattern=r"(?u)\b\w\w+\b", tokenization.py line 572), drops Lucene's 33 English stopwords (which include "no" and "not": "X causes Y" and "X does not cause Y" become the same query), and optionally stems ("decreases" and "decreased" both become "decreas"). Stemming is worth 1.7 points of nDCG@10 on SciFact and 1.3 on NFCorpus; stopwords change nothing here. The two-character pattern silently drops single characters: "Type 1 Diabetes" loses the "1", "IL-6" becomes just "il", "H2A.Z" loses its "Z"; 109 of the 300 SciFact claims contain such a token, and keeping them is worth 0.7 points measured. The one-line formula is the "Lucene" variant as bm25s computes it (bm25s/scoring.py lines 115 to 130 and 190 to 195, tag 0.3.13); the textbook version multiplies the fraction by (k1 + 1), a constant that changes no ranking. A 60-line NumPy version written for this page (src/exp/bm25lab.py) reproduces the setup's recorded bm25s run: identical top-10 scores for 281 of 300 SciFact claims and 310 of 323 NFCorpus questions (the rest differ only in how zero-score documents pad the list) measured.

Defaults differ: bm25s uses k1 1.5 and b 0.75 (bm25s/__init__.py lines 146 and 147); Lucene and Elasticsearch use 1.2 and 0.75, as does the running example.

Variants. The Robertson, ATIRE, BM25L and BM25+ formulas (bm25s implements all five, following Kamphuis et al., ECIR 2020) differ in the idf floor and in a small boost for long documents; on SciFact they span 0.679 to 0.686 and on NFCorpus 0.318 to 0.322. Pick one and move on.

Fields: BM25F. A title is short and on topic; a body is long. BM25F (Robertson, Zaragoza and Taylor, CIKM 2004) normalises each field by its own average length, weights it, and adds the fields before saturation, so a word in both title and body is not counted as two independent pieces of evidence:

tf̃ = Σf wf · tff / (1 − bf + bf · |Df| / avgdlf),   score = Σt idf(t) · tf̃ / (k1 + tf̃)

With the title weight chosen on the tuning split (titles average 10 terms against 147 for SciFact abstracts): SciFact 0.679 → 0.689 (title weight 2), NFCorpus 0.318 → 0.321 measured. Elasticsearch's combined_fields query "takes a principled approach to scoring based on the simple BM25F formula" (Elasticsearch docs, read 2026-10-14); multi_match with best_fields scores each field on its own and keeps the best, which is a different thing.

3. Learned sparse retrieval

Keep BM25's machinery (an inverted index, a score summed over shared terms) but let a model choose the terms and their weights. SPLADE (Formal, Piwowarski and Clinchant, SIGIR 2021) runs a BERT masked-language-model head over the text: for every position it predicts a weight for each of the 30,522 vocabulary entries, takes the maximum over positions after log(1 + ReLU), and keeps the non-zero entries. The vector is sparse but holds expansion terms, words the text lacks but a reader would expect (a statin abstract gets weight on "cholesterol" even if it only says "LDL"). An inference-free variant runs the model on documents only and gives each query word a fixed weight from a table, so a query costs a tokenizer call, like BM25.

Run here: opensearch-neural-sparse-encoding-doc-v3-distill (67 M parameters, Apache 2.0) through sentence-transformers' SparseEncoder, documents encoded on MPS (42 and 38 documents per second, load average about 11 to 18 from other jobs). nDCG@10: SciFact 0.708 against 0.679 for BM25 and 0.700 for Qwen3-Embedding; NFCorpus 0.345 against 0.318 and 0.363 measured. Fused with Qwen3-Embedding by RRF it scores 0.724 (SciFact) and 0.364 (NFCorpus), level with BM25 + Qwen3 (0.724, 0.361). A document keeps 239 non-zero terms on average and a query 20 (SciFact) or 5 (NFCorpus), so the index stays an inverted index. Caveat: the model card lists SciFact and NFCorpus among its training sets, so these scores are in-domain and flatter it against BM25 and the dense models, which never saw these sets.

Published for this model: average nDCG@10 0.517 on 13 BEIR sets against 0.524 for the larger query-and-document v1 model published, vendor (OpenSearch model card). BGE-M3 (BAAI) gives dense, sparse and multi-vector outputs from one model; not run here (2.3 GB, and its sparse head is one more variant of the same idea).

4. Fusion: merging two ranked lists

Hybrid search runs BM25 and a dense retriever on the same query and gets two ranked lists whose scores live on unrelated scales: a BM25 score of 8.96 and a cosine of 0.71. The root's shared runs measured the two common answers (RRF lifts Qwen3-Embedding on SciFact from 0.700 to 0.724; z-score fusion with a weight tuned on training claims reaches 0.739) root runs. This section is why each works and what each throws away.

Why raw scores cannot simply be added. BM25 is unbounded above (a SciFact claim's top-1 score ranges from 6.9 to 28.5, 5th to 95th percentile); Qwen3-Embedding's top-1 cosines range from 0.56 to 0.83 measured. Add them with equal weight and BM25 decides almost alone: 0.5 · BM25 + 0.5 · cosine scores 0.685, close to BM25 alone (0.679). The trap is the equal weight, not the addition: give the cosine 0.99 of the weight (chosen on training claims) and the raw sum scores 0.734, as good as any normalised method. The weight absorbs the scale difference, so it must be learned on labelled queries for each pair of retrievers, and again whenever either changes.

5. Understanding and rewriting the query

The text a user types may need a different retriever (an error code wants BM25), contain a condition that should be a filter ("papers from 2019"), lean on earlier turns of a chat ("does it help?"), be phrased unlike the documents, or ask two things at once. Query understanding is everything done to the query before the search (routing, extracting filters, rewriting); each costs time before retrieval starts, so each has to earn its place on measured queries.

Routing: the ceiling is high, the router is not

On SciFact, BM25 beats Qwen3-Embedding on 56 claims, loses on 81 and ties on 163, so a perfect router choosing per claim among BM25, dense and hybrid would score 0.798 against 0.724 for always-hybrid. A logistic-regression router on nine query-time features separates "BM25 wins" from "dense wins" only weakly (ROC AUC 0.67) and scores 0.721, slightly below always-hybrid. Even "identifiers go to BM25" fails: the 172 claims with a digit or an inner capital (gene and protein names) score 0.707 dense and 0.666 with BM25 measured. So fuse by default, and route only between query types that really differ (part-number lookups against natural questions) after checking on labelled queries that the router beats fusion. Routing between whole sources or tools is on Agentic retrieval, long context and memory.

Self-query: words in the question become a filter

"In the CoVoST paper, how many languages..." mixes a metadata condition into the question; embedded, the title words only nudge the vector, while as a filter they restrict the search to the right document. Self-query retrieval asks a language model to split the request into a cleaned query and a structured filter over known fields (LangChain's SelfQueryRetriever pattern). Measured with the local generator (Qwen3-1.7B, greedy) on 300 constructed requests: real QASPER questions with a reference to their paper added by template, a third by title, a third by month and year of the arXiv posting, a third by year only; search over all 6,463 default chunks of 281 papers with bge-small; found = the root's rule within 1,024 tokens.

Titles were resolved well, but the generator invented values: the generator added a month to all 100 year-only requests, so its filter dropped the right paper for 93 of them; checking each extracted value against the request fixed that (found within 1,024 tokens, year-only requests: 22 with no filter, 17 raw filter, 25 checked) measured. So an extracted filter is checked against the request and the schema before use (keep a value only if the request states it; fall back to no filter when it matches nothing): a wrong year silently removes the right document, which is worse than no filter. The filter itself runs inside the search (section 6).

6. Metadata filters: inside the search, never after it

Real queries carry conditions: this customer's documents, what this user may read, papers after 2020, the current version. A condition on metadata (structured fields stored next to each chunk) is a filter. The root's shared runs measured the central fact: applied after the search (a post-filter: fetch the top 10, drop what is not allowed), a filter that lets a user see 10% of SciFact returns 1.73 results of 10 on average and none at all for 14 of 300 claims; applied inside the search (a pre-filter: only allowed documents compete) it always returns 10 root runs.

What to store on every chunk

  • Identity and provenance: document id, chunk index, character span or page, section path (the Markdown splitter's heading metadata, §1), source URL. Needed for citations (§8) and for deleting or replacing a document's chunks.
  • Version and time: document version or content hash, published and indexed dates. Needed for "current only" and for re-indexing (the ingestion page, section 9).
  • Access: tenant, owner, groups allowed. Needed for access control, which must be a filter inside the search, never an instruction in the prompt; measured with PostgreSQL row-level security on RAG in production.
  • Facets users filter on: language, document type, product, year. Store as typed fields (integer year, date), not inside the text, so the engine can index them.

Every chunk inherits its document's fields at index time; a metadata change (a permission revoked) must update every chunk of the document, in both the BM25 and the vector index.

The arithmetic of post-filtering

If an index returns its top K and then a filter keeps a share s of documents (the filter's selectivity), the expected number of survivors is about K · s, assuming the allowed documents are spread evenly through the ranking. The pgvector README gives the same arithmetic for its HNSW index: "If a condition matches 10% of rows, with HNSW and the default hnsw.ef_search of 40, only 4 rows will match on average" (README line 450 at tag v0.8.7, verified). Correlated access, and how engines filter inside the search (depth)

Correlation cuts both ways: a user's own documents are often exactly what they search for; a tenant's documents may all sit far from a generic query. pgvector from 0.8.0 rescans more of the index until enough rows pass (SET hnsw.iterative_scan = strict_order or relaxed_order, stopping at hnsw.max_scan_tuples, 20,000 by default; README lines 480 and 527); Qdrant and Weaviate filter during graph traversal and switch to an exact scan when few points match.

Filters in hybrid search

BM25 filters cheaply: the engine intersects the query terms' posting lists with the set of allowed documents (a bitmap), so a selective filter makes BM25 faster. A vector index pays for a selective filter instead, because its graph or clusters were built over every document. So the two halves of a hybrid search behave differently under the same filter, and both must receive it before fusion. The filters a user never typed (tenant, permissions) come from the session; the ones they typed come from query understanding (§5).

7. Duplicates and diversity

Ten retrieved chunks that say the same thing waste nine slots of the prompt. Duplicates come from the corpus (the same abstract under two ids, a page crawled twice, mirrored documentation), from overlapping chunks (neighbours share their overlap), and from near-identical versions. Two remedies: remove duplicates, or penalise similarity among the chosen results.

NFCorpus has 41 pairs above cosine 0.995 with bge-small, and they are true duplicates: for example "Alkylphenols in human milk and their relations to dietary habits in central Taiwan." appears as MED-118 and MED-2651 with identical text measured. Exact duplicates are best removed at ingestion with a content hash, before they reach any index (the ingestion page covers content hashing). How much near-duplication each set has:

Overlapping chunks: merge, do not drop

With overlapping fixed windows, a chunk and its neighbour often both rank high, because both hold part of the same paragraph. Treating the neighbour as a duplicate and dropping it is wrong: on QASPER (bge-small, within the paper) dropping any chunk that overlaps one already chosen cuts the questions found within 1,024 tokens from 0.568 to 0.455, because the neighbour is what completes a paragraph the window boundary cut. Merging overlapping or touching chunks into one span and paying for the shared tokens once gives 0.571; MMR at λ 0.7 gives 0.512 measured.

8. Assembling the prompt, and citing

Retrieval ends with a ranked list; the generator needs one prompt. Between them sit decisions that change the answer: how many chunks (the context budget), in what order, and with what labels so the answer can cite them. Measured with the root's end-to-end task: Qwen3-1.7B (llama.cpp, greedy, thinking off) reads a SciFact claim and k abstracts and answers SUPPORT, CONTRADICT or NOT ENOUGH INFO with the number of the abstract it relied on; an answer is strictly right when the label matches the annotators' and the cited abstract is annotated evidence. 188 test claims with evidence; candidates from hybrid RRF, then Qwen3-Reranker-0.6B on the top 30; the root's answer prompt (answers identical to the root's runs were reused from its cache, so shared cells agree by construction).

How many chunks

Strictly right answers barely move with k: 97 of 188 with only the top abstract, 96 at k 3, 96 at k 5 and 101 at k 10, while the prompt grows from 504 to 3,644 tokens on average. The reranked top 3 already holds the evidence for 178 of the 188 claims (root lab), so more abstracts add little to find; this 1.7 B model's limit is reading, not finding (it never answered CONTRADICT in any of these runs, the same failure the root lab found). More context is not free even when the window allows it: prefill time grows with the prompt (about 1,040 prompt tokens per second for this model here, root's latency table), and a small model is distracted by more near-miss abstracts.

Order: put the best chunk first

Published: Liu et al., "Lost in the Middle" (arXiv 2307.03172, 2023) moved the one relevant document through 10, 20 and 30 retrieved documents and found a U shape for several models: accuracy highest with the document first or last, lowest in the middle published, authors' runs. Citation formats, and checking a citation

A citation is a pointer from the answer to a chunk; it is only useful if it can be resolved and checked. Three formats on the same top 5:

A template that holds up

  • Label each chunk with a short id the model can repeat exactly ([1], [2]...) and keep the mapping to document, section and span outside the prompt; here numbers and corpus ids both resolved for every answer.
  • Put each chunk's title and date in its header line: the model cannot weigh a 2019 document against a 2025 one if it never sees the dates.
  • Merge chunks that overlap or touch into one span (§7); drop exact duplicates; never truncate a chunk mid-sentence to fit the budget, drop the lowest-ranked chunk instead.
  • Keep instructions and the question outside the retrieved text, and treat retrieved text as data: a document that says "ignore previous instructions" is an injection (indirect prompt injection is owned by Agent security; its RAG specifics are on RAG in production).
  • Ask for the label or answer first and the citation in a fixed format, then parse it; count unparseable answers as wrong. If you ask for quotes, verify them: here most were not verbatim (§8).

9. Measuring the pipeline on your own set, and where an answer is lost

The golden set. Every number on this page needs one: real questions, each with the passages a human marked as answering it (and, to judge answers, a reference answer). A few hundred real, labelled questions separate systems that differ by a few points; synthetic questions written from a chunk are easy by construction, because they reuse the chunk's words. Version the set, re-label when the corpus is re-chunked, choose every knob (fusion weight, rerank depth, prompt) on a tuning split, and report the test split once: SciFact here has 809 training claims for tuning and 300 test claims for reporting.

Retrieval metrics, per question then averaged (computed with pytrec_eval, the TREC tool BEIR uses; definitions and their edge cases are owned by Evaluation metrics): recall@K, the share of a question's relevant passages in the top K (with one relevant passage, as for 277 of 300 SciFact claims, simply found or not); precision@k, the share of the top k that is relevant (irrelevant chunks in the prompt distract the generator); MRR, 1 / rank of the first relevant passage; nDCG@10, each relevant passage in the top 10 earns its grade divided by log2(rank + 1), normalised by the best possible order, so it rewards putting the right passage first. Measure the first stage's recall at the depth the reranker reads (K), not only at the k that reaches the prompt: a reranker cannot rescue what it was never given, and the two depths separate a retrieval miss from a ranking miss.

Common mistakes, one line each (checklist)
  • Sizing chunks in characters for a model that counts tokens: with LangChain's default and all-MiniLM-L6-v2 only 33.3% of the text reaches the vector, silently (§1).
  • Believing the default separators cut at sentences: they are blank line, newline, space, nothing; add ". " or split on structure (§1).
  • Dropping overlapping neighbours as duplicates: QASPER fell from 0.568 to 0.455 found; merging overlapping spans gave 0.571 (§7).
  • Tuning k1, b, the fusion weight or k on the test queries: the best BM25 pair on SciFact test claims claims 0.688; chosen on training claims it scores 0.678 (§2).
  • Adding BM25 and cosine scores with equal weight: BM25's scale wins (0.685, near BM25's 0.679); normalise, learn the weight, or use ranks (§4).
  • Tuning the fusion weight when a reranker follows: after it, RRF and tuned z-score fusion land within a point; spend the effort on rerank depth (§4).
  • Ignoring what the BM25 tokenizer does to identifiers and negations: one-character tokens dropped, "not" a stopword (§2).
  • Filtering after the search or after fusion: about K · s results come back, often none (§6).
  • Turning on MMR because diversity sounds good: it hurt on every set here, including the multi-hop one (§7).
  • Trusting an extracted filter without checking it: the generator added December to every year-only request (§5).
  • Accepting citations without resolving and checking them: an unresolvable citation is a wrong answer (§8).
  • Debugging a bad answer by swapping the model first: measure r, p and g; the largest bucket names the stage (§9).
Interview questions, short answers (optional rehearsal)

How would you choose a chunking strategy for a new corpus? Get a few hundred questions with located evidence. Split on the documents' own structure first (headings, paragraphs), cap the size in the embedder's tokens, and compare candidates on "evidence intact" and on retrieval at an equal token budget, never at an equal number of chunks. Try small-to-big (index sentences or paragraphs, return the paragraph) before tuning sizes.

Why does RRF work without calibration, and when would you not use it? It uses ranks, so the two score scales never meet, and it rewards agreement, which is a strong signal (documents in both top 10s were relevant 13 to 28 times as often as single-list ones on SciFact). It discards score margins; with no reranker and labelled queries to learn a weight, normalised score fusion did about 1 to 1.6 points better here. With a strong reranker after it, RRF is enough.

BM25 or dense for queries with product codes? Run both and fuse. Check the BM25 tokenizer keeps the codes intact (a two-character pattern drops "X1" pieces; hyphens split). A router is only worth it if it beats fusion on labelled queries; here a learned router did not.

Design a multi-tenant RAG search for 10,000 customers. Where do permissions go? Tenant id and ACL groups as typed metadata on every chunk, enforced as a filter inside both the BM25 and the vector search (or row-level security in the database), never in the prompt. Choose shared index plus filter or index per tenant by tenant size: tiny tenants make post-filtering useless and filtered ANN slow, so check the engine's filtered-search strategy (iterative scans, ACORN-style traversal, exact scan below a threshold) and measure recall for the smallest tenant. Re-index a document's chunks when its permissions change.

Your RAG answers cite the wrong document. How do you debug it? Split the failure: was the right chunk retrieved (recall at the rerank depth), did it reach the prompt (rank after reranking against the budget), and did the model use it (an oracle run with only the right chunk)? Then check the citation plumbing.

When is query rewriting worth its latency? Always for chat follow-ups (they are not queries without the history). Otherwise measure: HyDE helped one embedder and hurt another here; multi-query did nothing and step-back and decomposition hurt; a rewrite costs a generator call (0.3 to 2.2 s per query here, depending on how much it writes), more than the whole retrieval.

What is late chunking and what does it need? Embed the whole document with a long-context, mean-pooling embedder, then average token vectors per chunk span, so each chunk vector sees the document. It needs mean pooling and a long context; published gains are large for weak embedders and small for strong ones, and within a single document (where every chunk shares the same context) it hurt here.

Measured on the topic's shared runs: details the root page used to show (moved here when the root's Pipeline lab was retired, 2026-10-24; 3 min)

All recorded in the root page's src/pipe on the running example (load average during the runs 1.2 to 3.9).

  • BM25 by hand. Document frequency is the length of a term's postings list: in SciFact, "statin" appears in 23 of 5,183 abstracts, "decreas" in 573. BM25's first and third results for claim 1099 of the SciFact test set score 8.963 and 7.366 (k1 1.2, b 0.75), recomputed exactly from the bm25s index's term counts and lengths; the relevant abstract is the third.
  • Chunking, more cuts. Two fair ways to hand text over: the top k chunks, or a token budget filled in rank order. The 0.6 B Qwen3-Embedding shows the same gap between fixed windows and paragraph-aware chunks as bge-small (59.4% against 70.3%): a bigger embedder does not repair a bad cut. Semantic chunking cut at the 80th percentile gives small chunks that split the evidence (547 intact). A title and section prefix (no model) helps paragraph-aware chunks (bge-small at 1,024 tokens: 70.0% to 72.0%) and not fixed windows (56.8% to 54.9%), whose section label can be wrong for half the window. One caution: QASPER's evidence unit is the paragraph, so "one paragraph per chunk" (median 89 tokens, 888 of 892 intact, 77.5% at 1,024 tokens with bge-small) is favoured by construction; on documents whose answers span paragraphs, packing paragraphs up to a size is the safer default.
  • Contextual retrieval, run on the laptop. Qwen3-1.7B wrote the context with Anthropic's prompt verbatim on 71 papers (every fourth; 1,664 default chunks, 239 questions): 2,560 s of generation, 0.87 M new prompt tokens because llama.cpp kept each paper in its cache (11.1 M without that cache). Without and with the context: bge-small top 3 46.9% to 49.4%, but at a 1,024-token budget 57.7% to 55.2%; BM25 top 3 38.5% to 40.2%, budget 49.0% to 48.1%. With 239 questions a difference of 2 to 3 points is within noise: a 1.7 B writer gives no clear gain on this task, and some of its "contexts" just repeat the chunk's first lines. The setting differs from Anthropic's: here retrieval runs inside one paper, where every chunk shares the same document context.
  • Late chunking on the root's models was not run: their long-context embedders pool differently (gte-modernbert uses the CLS token, Qwen3-Embedding the last token of a causal model), so a late-chunking run would measure a pooling the models were never trained for (section 1 runs it with modernbert-embed-base instead).
  • Fusion tuning. BM25 and dense runs for the training and dev splits use the same settings as the recorded test runs (BM25 reproduces the recorded test top 10 for every query).
  • Rewrites. HyDE used the authors' SciFact prompt from their code (texttron/hyde, promptor.py): "Please write a scientific paper passage to support/refute the claim." Multi-query asks for three rewordings, retrieves with each and the original, and fuses the four lists with RRF. For BM25, appending the HyDE passage to the claim adds words the abstracts use: recall@100 rises from 0.913 to 0.943. Longer chats, where pasting everything dilutes the query, were not tested.
  • Post-filter, in numbers. When a user may see 10% of SciFact, the evidence reaches the post-filtered results for 255 claims, against 284 when the filter runs inside the search. Over-fetching repairs it only partly: with the top 100 fetched, the evidence is found as often as with the pre-filter (284), but 96 claims still get fewer than 10 results; at 1% visibility even 1,000 fetched leaves 112 claims short. The evidence count even rises as the filter narrows (284 at 10%, 299 at 1%, against 256 unfiltered), but that is the construction: the evidence is always allowed and fewer abstracts compete with it.
  • End to end, by label. The decomposition uses the 188 test claims that have evidence (124 SUPPORT, 64 CONTRADICT). None of the 64 CONTRADICT claims was answered correctly, and almost all of them reached the prompt, so they are lost at generation; on SUPPORT claims the model is right 96 times of 124. The reranker still pays: without it (first stage only, k 3) the evidence reaches the prompt for 171 claims instead of 178, and 90 claims are answered correctly instead of 96. A 4 B or frontier model would move g, not r or p.
  • How the answer prompt was chosen. Three prompts were compared on SciFact training claims, each with its gold abstracts (120 claims with evidence, 60 without), as right with evidence, right without, balanced: p1 "SUPPORT, CONTRADICT, or NOT ENOUGH INFO?" 17 / 120, 60 / 60, 0.571; p2 "SUPPORT or CONTRADICT? NOT ENOUGH INFO only if no abstract addresses the claim" (chosen) 78 / 120, 41 / 60, 0.667; p3 (a role and definitions of each label) 86 / 120, 11 / 60, 0.450. p2 was then run once on the test claims. Qwen3's thinking mode was started and stopped: about 8 s per answer, about 5 hours for the 2,300 answers of the end-to-end runs.
