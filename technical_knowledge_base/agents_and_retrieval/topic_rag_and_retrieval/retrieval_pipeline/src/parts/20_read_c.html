2. BM25 in depth

The problem. A dense retriever finds paraphrases but can rank a vaguely related abstract above the one that names the exact gene; a word-matching retriever finds the exact word every time. BM25 ("Best Match 25", Robertson and colleagues, 1990s) is the standard word-matching score. It lives on an inverted index: for every word, the list of documents containing it and how often, so a query only touches the lists of its own words. How that index is stored, compressed and updated inside a database is on {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}; this section is about the score and its knobs.

2.1 The formula, on a real claim

score(D, Q) = Σt in Q idf(t) · tf / (tf + k1 · (1 − b + b · |D| / avgdl))
tf
how many times term t occurs in document D
idf(t)
ln(1 + (N − df + 0.5) / (df + 0.5)): large for rare terms, near 0 for terms in most documents (N documents, df containing t)
k1
saturation: how fast repeats stop counting (0 = only presence counts)
b
length normalisation: 0 = ignore length, 1 = divide fully by relative length
|D|, avgdl
the document's length in terms and the corpus average

This is the "Lucene" variant as bm25s computes it (bm25s/scoring.py lines 115 to 130 and 190 to 195, tag 0.3.13); the textbook version multiplies the fraction by (k1 + 1), a constant that changes no ranking. A 60-line NumPy version written for this page (src/exp/bm25lab.py) reproduces the setup's recorded bm25s run: identical top-10 scores for @@bm_check_sf@@ of 300 SciFact claims and @@bm_check_nf@@ of 323 NFCorpus questions (the rest differ only in how zero-score documents pad the list) measured. 2.3 Tokenisation, stemming, stopwords

BM25 only sees the terms its tokenizer produces, and that matters more than k1. bm25s's default tokenizer lowercases, keeps runs of two or more word characters (token_pattern=r"(?u)\b\w\w+\b", tokenization.py line 572), drops Lucene's 33 English stopwords (which include "no" and "not": the claims "X causes Y" and "X does not cause Y" become the same query), and optionally stems ("decreases" and "decreased" both become "decreas").

2.4 Fields: BM25F

A document often has fields of different value: a title is short and on topic, a body is long. Concatenating them treats a title word like any body word. BM25F ({{Robertson, Zaragoza and Taylor, CIKM 2004|https://doi.org/10.1145/1031171.1031181}}) normalises each field by its own average length, weights it, and adds the fields before saturation, so a word that appears in the title and the body is not counted as two independent pieces of evidence:

tf̃ = Σf wf · tff / (1 − bf + bf · |Df| / avgdlf),   score = Σt idf(t) · tf̃ / (k1 + tf̃)

With the title weight chosen on the tuning split (titles average @@title_len_sf@@ terms against @@body_len_sf@@ for SciFact abstracts): SciFact @@bm_sf_def@@ → @@bm25f_sf@@ (title weight @@bm25f_sf_w@@), NFCorpus @@bm_nf_def@@ → @@bm25f_nf@@ measured. Elasticsearch's combined_fields query "takes a principled approach to scoring based on the simple BM25F formula" ({{Elasticsearch docs|https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-combined-fields-query.html}}, read 2026-10-14); multi_match with best_fields is field-centric (each field scored on its own, the best field's score used), which is a different thing.

3. Learned sparse retrieval

The idea. Keep BM25's machinery (an inverted index, a score that is a sum over shared terms) but let a model choose the terms and their weights. SPLADE ({{Formal, Piwowarski and Clinchant, SIGIR 2021|https://arxiv.org/abs/2107.05720}}) runs a BERT masked-language-model head over the text: for every position it predicts a weight for each of the 30,522 vocabulary entries, takes the maximum over positions after log(1 + ReLU), and keeps the non-zero entries. The vector is sparse but contains expansion terms: words the text does not contain but that a reader would expect (a statin abstract gets weight on "cholesterol" even if it only says "LDL"). An inference-free variant runs the model on documents only and gives each query word a fixed weight from a table, so a query costs a tokenizer call, like BM25.
