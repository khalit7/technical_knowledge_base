5. Understanding and rewriting the query

The text a user types may need a different retriever (an error code wants BM25), contain a condition that should be a filter ("papers from 2019"), lean on earlier turns of a chat ("does it help?"), be phrased unlike the documents, or ask two things at once. Query understanding is everything done to the query before the search (routing, extracting filters, rewriting); each costs time before retrieval starts, so each has to earn its place on measured queries.

Routing: the ceiling is high, the router is not

On SciFact, BM25 beats Qwen3-Embedding on @@rt_sf_bm_better@@ claims, loses on @@rt_sf_de_better@@ and ties on @@rt_sf_tie@@, so a perfect router choosing per claim among BM25, dense and hybrid would score @@rt_sf_oracle3@@ against @@rt_sf_hybrid@@ for always-hybrid. A logistic-regression router on nine query-time features separates "BM25 wins" from "dense wins" only weakly (ROC AUC @@rt_sf_auc@@) and scores @@rt_sf_router@@, slightly below always-hybrid. Even "identifiers go to BM25" fails: the @@rt_sf_ident_n@@ claims with a digit or an inner capital (gene and protein names) score @@rt_sf_ident_de@@ dense and @@rt_sf_ident_bm@@ with BM25 measured. So fuse by default, and route only between query types that really differ (part-number lookups against natural questions) after checking on labelled queries that the router beats fusion. Routing between whole sources or tools is on {{Agentic retrieval, long context and memory|n:3c65c17b0d0d8105a68cfb504ed4b0e8}}.

Self-query: words in the question become a filter

"In the CoVoST paper, how many languages..." mixes a metadata condition into the question; embedded, the title words only nudge the vector, while as a filter they restrict the search to the right document. Self-query retrieval asks a language model to split the request into a cleaned query and a structured filter over known fields (LangChain's SelfQueryRetriever pattern). Measured with the local generator (Qwen3-1.7B, greedy) on @@sq_n@@ constructed requests: real QASPER questions with a reference to their paper added by template, a third by title, a third by month and year of the arXiv posting, a third by year only; search over all 6,463 default chunks of 281 papers with bge-small; found = the root's rule within 1,024 tokens.

Titles were resolved well, but the generator invented values: @@sq_summary@@ measured. So an extracted filter is checked against the request and the schema before use (keep a value only if the request states it; fall back to no filter when it matches nothing): a wrong year silently removes the right document, which is worse than no filter. The filter itself runs inside the search (section 6).

Rewriting: helps chat follow-ups, rarely anything else

The root's shared runs measured three rewrites on SciFact with the same generator root runs: HyDE (write a hypothetical answer passage and search with it; {{Gao et al., arXiv 2212.10496|https://arxiv.org/abs/2212.10496}}) lifts Qwen3-Embedding from 0.700 to 0.718 when the passage replaces the claim, and helps bge-small only when the passage vector is averaged with the claim's (0.713 → 0.733; the passage alone gives 0.692); multi-query (three rewordings fused with RRF) buys nothing on these already specific claims (0.699 for Qwen3); a conversational rewrite turns a follow-up that is meaningless alone into a standalone question and repairs most of eight constructed chats (the relevant abstract at rank 1 for 6 of 8 with bge-small, against 2 of 8 for the follow-up alone; one chat got worse). The old version of this page said HyDE is "largely superseded by instruction-aware embedders": here it still helped the instruction-aware Qwen3-Embedding by 1.8 points, so that claim is dropped.

What the generator wrote:

Step-back ({{Zheng et al., arXiv 2310.06117|https://arxiv.org/abs/2310.06117}}: ask for the more general question behind the query and retrieve for both) and decomposition (split a multi-part question into sub-questions, retrieve for each, fuse) both hurt here: the general question retrieves general abstracts when a claim needs one specific study, and the 1.7 B generator rarely split HotpotQA's two-hop questions; where it did, fusing the lists lost gold paragraphs. A decomposition written before any retrieval cannot resolve a bridge question ("the director of the film that..."), because the second sub-question needs the first answer; that needs retrieval in a loop ({{Agentic retrieval, long context and memory|n:3c65c17b0d0d8105a68cfb504ed4b0e8}}). Tables in the closed block.

What it costs. Every rewrite is a generator call before the search: the root measured about 2.2 s per claim for HyDE and 0.8 s for three rewordings with the 1.7 B model on this laptop; here step-back took @@sb_sec_per@@ s per claim and a decomposition @@dec_sec_per@@ s per question measured. That is more than the whole retrieval stage (BM25 0.25 ms, query embedding 49 ms, exact search 0.5 ms in the root's latency table). Rewrite always for chat follow-ups; otherwise only for query types where it measurably helps.
