1. Chunking: cut where the author did

An embedder reads a few hundred tokens and returns one vector; a prompt holds a few thousand tokens. So a 6,000-token paper is cut into chunks, each indexed alone, and only some reach the model. A cut can lose the answer in two ways: the evidence paragraph is split, so no chunk holds it whole, or the chunk that holds it has lost the context that would make it match ("the model" without saying which). The root's shared runs measured the headline on QASPER: fixed 256-token windows keep an evidence paragraph whole for 607 of 892 questions, splitting on paragraphs first keeps 832 to 838, and at an equal budget of 1,024 tokens the share of questions whose evidence is handed over rises from 56.8% to 70.0% (bge-small) root runs. The animation shows why, on one real section.

One section of the CoVoST paper (QASPER, arXiv 2002.01320), cut by fixed 128-token windows, then by the recursive splitter at the same size. Red bars are cuts; green underline is evidence an annotator used. Predict before you step: how many evidence paragraphs survive whole under each?

What the recursive splitter does (LangChain's default, read in langchain-text-splitters 1.1.3): it holds separators from coarse to fine, ["\n\n", "\n", " ", ""]; splits on the first one present; keeps pieces already under the target; merges consecutive short pieces up to the target, carrying a tail of up to overlap into the next chunk; and recurses with the next separator on any piece still too long. The default list has no sentence separator: after the newline comes the space, so a long paragraph is cut between two words wherever the size runs out (add ". ", as the root's rule does). The source, and the check that the real library reproduces the root's numbers, are in the closed block below.

Size is counted in the embedder's tokens

A token is the unit a model reads, as cut by its tokenizer. Structure first, then small to big

When a document carries its own structure, cut along it. QASPER has Markdown headings, so LangChain's MarkdownHeaderTextSplitter splits at each heading, records the heading path as metadata (for filters and citations), and a size cap applies inside each section: @@lc_md_intact@@ intact and @@lc_md_bm1024@@ found with BM25 at 1,024 tokens, level with the root's paragraphs-within-sections rule (832; 0.645) measured.

Small chunks match precisely (a sentence is about one thing); big chunks carry the context the model needs. Small to big (or parent-child) retrieval does both: index small units, and when one matches, hand over the larger unit that contains it. LlamaIndex's SentenceWindowNodeParser is one form (it embeds single sentences and returns three on each side, DEFAULT_WINDOW_SIZE = 3, llama-index-core 0.14.25). Measured on QASPER within each question's paper (bge-small, parents handed over in the order their children rank until 1,024 tokens are used, each parent once):

Semantic chunking (embed each sentence, cut where neighbours are least similar) lost here: the root ran LangChain's SemanticChunker defaults (cut above the 95th percentile of distances) and got chunks of median 342 and up to 4,967 tokens, last at an equal 1,024-token budget (38.6% with BM25) root runs. It costs an embedding call per sentence and has no size cap; where real paragraphs exist, the author's breaks are the better boundaries.

Giving a chunk its document's context

Two methods attack the second failure, a chunk that lost its context. Late chunking ({{Günther et al., Jina AI, arXiv 2409.04701|https://arxiv.org/abs/2409.04701}}) runs the whole document through a long-context, mean-pooling embedder once, then averages the token vectors inside each chunk's span, so a chunk that says "the model" carries which model; published gains are large for weak embedders and small for strong ones (NFCorpus nDCG@10 23.5 → 30.0 with jina-embeddings-v2-small, none with nomic-embed) published, authors' runs. Run here with modernbert-embed-base it hurt: @@late_summary@@ measured; every chunk competing within one paper shares the same context, which makes them more alike, not easier to tell apart. Contextual retrieval (Anthropic, {{post of 2024-09-19|https://www.anthropic.com/news/contextual-retrieval}}) has a model write 50 to 100 tokens situating each chunk and prepends them before indexing; the vendor's top-20 retrieval failure rate fell from 5.7% to 3.7%, and to 1.9% with contextual BM25 and a reranker published, vendor, while the root's run with Qwen3-1.7B on 71 papers was within noise (at 1,024 tokens 57.7% → 55.2%) root runs. Late chunking costs one extra forward pass per document; contextual prefixes cost a generator call per chunk.

How many chunks, how many tokens stored.

Fixed windows of c tokens overlapping by o start a new chunk every c − o tokens (the stride). A 10,000-token document at c = 512, o = 64 gives a stride of 448, ⌈9,936 / 448⌉ = 23 chunks and 10,000 + 22 × 64 = 11,408 tokens stored, 14% more than the text:

n = ⌈(L − o) / (c − o)⌉,    T = L + (n − 1) · o
n
chunks for a document of L tokens (one when L ≤ c)
T
tokens stored and embedded: every overlap is stored twice

    def __init__(self, separators=None, keep_separator=True, is_separator_regex=False, **kwargs):
        super().__init__(keep_separator=keep_separator, **kwargs)
        self._separators = separators or ["\n\n", "\n", " ", ""]

    def _split_text(self, text, separators):
        separator = separators[-1]; new_separators = []
        for i, s_ in enumerate(separators):              # first separator present in this text wins
            if not s_: separator = s_; break
            if re.search(re.escape(s_), text): separator = s_; new_separators = separators[i + 1:]; break
        splits = _split_text_with_regex(text, re.escape(separator), keep_separator=self._keep_separator)
        good_splits = []
        for s in splits:
            if self._length_function(s) < self._chunk_size: good_splits.append(s)   # short enough: keep for merging
            else:
                if good_splits: final_chunks.extend(self._merge_splits(good_splits, separator_)); good_splits = []
                if not new_separators: final_chunks.append(s)                    # nothing finer: an oversize chunk
                else: final_chunks.extend(self._split_text(s, new_separators))   # recurse with the next separator
        if good_splits: final_chunks.extend(self._merge_splits(good_splits, separator_))
        return final_chunks

The merge step (base.py lines 167 to 210) drops pieces from the front of the running chunk while the running total is above the overlap, which is how the overlap is made: the last few pieces of one chunk start the next.

Running the real library on all 281 papers with sizes in Qwen3 tokens (from_huggingface_tokenizer, 256 tokens, 32 overlap) gives the same result: @@lc_tok_intact@@ of 892 questions with evidence intact (root: 838) and @@lc_tok_bm1024@@ found with BM25 at 1,024 tokens (root: 0.613) measured. The Markdown splitter's quirk (markdown.py lines 250 to 257 and 107): it strips every line, drops blank lines and re-joins a section's lines with two spaces and a newline, so paragraph breaks ("\n\n") no longer exist when the size cap runs; the cap falls back to single newlines. Harmless on QASPER, where each paragraph is one line; costly on text whose paragraphs wrap across lines. The library also has HTMLHeaderTextSplitter and per-language separators for code (for Python "\nclass ", then "\ndef ", then "\n\tdef " before blank lines, character.py lines 366 to 374), so functions stay whole when they fit. Not run here: the running example has no HTML or code corpus.

Sentences. A regex such as the root's (cut after . ! ? followed by a capital, digit or bracket) breaks on abbreviations. On 94 QASPER papers the regex makes @@sent_regex_n@@ sentences of which @@sent_regex_bad@@ end on an abbreviation such as "et al.", "Fig." or "No."; pySBD 0.3.4 makes @@sent_pysbd_n@@ with @@sent_pysbd_bad@@ such ends measured. Under 2% either way, and sentence packing is a poor chunker here anyway (593 intact, below fixed windows with overlap) because it ignores paragraph and section breaks root runs.

Late chunking, published and run. It needs an embedder that pools by averaging and a context long enough for the document; longer documents go through in overlapping windows ("long late chunking", the paper's Algorithm 2). The paper's Table 2 (nDCG@10 on BEIR, 256-token chunks): jina-embeddings-v2-small NFCorpus 23.5 → 30.0 and SciFact 64.2 → 66.1 ({{Jina's blog of 2024-08-22|https://jina.ai/news/late-chunking-in-long-context-embedding-models/}} prints 23.46 and 29.98); jina-embeddings-v3 35.6 → 36.7 and 71.8 → 73.2; nomic-embed-text-v1 35.3 → 35.3 on NFCorpus; an average relative gain of about 3.5% for fixed-size chunks published, authors' runs. {{Merola and Singh (arXiv 2504.19754, April 2025)|https://arxiv.org/abs/2504.19754}} found contextual retrieval "preserves semantic coherence more effectively" while late chunking "offers higher efficiency but tends to sacrifice relevance and completeness". Run here with nomic-ai/modernbert-embed-base (ModernBERT, 149 M parameters, 8,192 tokens, mean pooling, Apache 2.0): @@late_detail@@

Contextual retrieval in detail. The vendor's failure rate was 2.9% with contextual embeddings plus contextual BM25, before the reranker. With prompt caching (the document is read once per document, not once per chunk) the vendor put the one-off cost at $1.02 per million document tokens, assuming 800-token chunks, 8,000-token documents and 100 tokens of context per chunk published, vendor. In the root's run, llama.cpp's prompt cache cut the prompt tokens from 11.1 M to 0.87 M, and bge-small top 3 moved 46.9% → 49.4% root runs.

Mixing chunking strategies in one index. The old version of this page said mixing strategies across ingestion runs "can cost about 8 points of recall". No source was found, so it was tested: one index over all 281 papers, half chunked in 128-token windows and half in 512-token windows, searched globally with bge-small:

indexfound within 1,024 tokens, all 892questions about the 512-token halfquestions about the 128-token halflong chunks: share of index / of top 10s

The mixed index lands between the two uniform ones. The papers re-chunked to 512 do worse than in an all-512 index (@@mx_b_mixed@@ against @@mx_b_u512@@), because they compete with small chunks for the same budget; so mixing moves recall by about five points for the affected half, and the old "8 points" is dropped. What holds: a chunker change should re-index the whole corpus, in both the BM25 and the vector index; how chunk boundaries move when one document is revised is measured in section 9 of {{Document ingestion and multimodal retrieval|n:3f85c17b0d0d81279079f614f382f2e7}}.
