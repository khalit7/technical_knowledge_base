1. Chunking in depth

The problem. An embedding model reads a few hundred tokens at a time and turns them into one vector; a prompt can hold a few thousand tokens. A 6,000-token paper therefore has to be cut into pieces, each indexed on its own, and only some pieces reach the model. Two things can go wrong at a cut: the paragraph that answers the question is split, so no single chunk contains the answer; or the chunk that does contain it has lost the context that would make it match the question ("the model" without saying which). The root's Pipeline lab measured the headline: on QASPER, fixed 256-token windows keep an evidence paragraph whole for 607 of 892 questions, splitting on paragraphs first keeps 832 to 838, and at an equal budget of 1,024 tokens the share of questions whose evidence is handed over rises from 56.8% to 70.0% (bge-small) root lab. This section opens the box: what a splitter does line by line, what "size" means, and the variants the root does not run.

1.1 Size is measured in tokens, and in the embedder's tokens

A token is the unit a model reads: a word, a piece of a word, or a punctuation mark, as cut by that model's tokenizer. Every model limit is in tokens (bge-small reads 512, all-MiniLM-L6-v2 reads 256 by default; anything longer is silently cut off), but the most used splitter measures size in characters by default: LangChain's TextSplitter takes chunk_size=4000, chunk_overlap=200 and length_function=len (langchain-text-splitters 1.1.3, base.py lines 64 to 66). from transformers import AutoTokenizer
from langchain_text_splitters import RecursiveCharacterTextSplitter

tok = AutoTokenizer.from_pretrained("sentence-transformers/all-MiniLM-L6-v2")   # reads at most 256 tokens
n = lambda s: len(tok(s)["input_ids"])                                           # counts [CLS] and [SEP] too
for name, sp in [("library default, 4,000 characters", RecursiveCharacterTextSplitter()),
                 ("tutorial setting, 1,000 characters", RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)),
                 ("256 MiniLM tokens", RecursiveCharacterTextSplitter.from_huggingface_tokenizer(tok, chunk_size=254, chunk_overlap=32))]:
    sizes = [n(c) for c in sp.split_text(paper_text)]    # paper_text: QASPER's CoVoST paper (arXiv 2002.01320)
    seen = sum(min(s, 256) for s in sizes) / sum(sizes)
    print(f"{name:36s} {len(sizes):3d} chunks, largest {max(sizes):4d} tokens, MiniLM reads {seen:.0%} of the text")

1.2 The recursive splitter, read in the source

"Recursive character splitting" is the default almost everywhere, and it is simpler than its name. It holds an ordered list of separators, from the coarsest to the finest. It splits the text on the first separator that occurs in it, keeps every piece already shorter than the target, merges consecutive short pieces back together up to the target size (carrying a tail of up to overlap tokens into the next chunk), and calls itself on any piece still too long with the next, finer separator. The source, at langchain-text-splitters 1.1.3:

langchain_text_splitters/character.py, lines 98 to 107 (defaults) and 110 to 149 (_split_text; abridged and reflowed onto fewer lines, highlighted lines verbatim)

    def __init__(self, separators=None, keep_separator=True, is_separator_regex=False, **kwargs):
        super().__init__(keep_separator=keep_separator, **kwargs)
        self._separators = separators or ["\n\n", "\n", " ", ""]

    def _split_text(self, text, separators):
        separator = separators[-1]; new_separators = []
        for i, s_ in enumerate(separators):              # first separator present in this text wins
            if not s_: separator = s_; break
            if re.search(re.escape(s_), text): separator = s_; new_separators = separators[i + 1:]; break
        splits = _split_text_with_regex(text, re.escape(separator), keep_separator=self._keep_separator)
        good_splits = []
        for s in splits:
            if self._length_function(s) < self._chunk_size: good_splits.append(s)   # short enough: keep for merging
            else:
                if good_splits: final_chunks.extend(self._merge_splits(good_splits, separator_)); good_splits = []
                if not new_separators: final_chunks.append(s)                    # nothing finer: an oversize chunk
                else: final_chunks.extend(self._split_text(s, new_separators))   # recurse with the next separator
        if good_splits: final_chunks.extend(self._merge_splits(good_splits, separator_))
        return final_chunks

Two details people miss. The default list has no sentence separator: after the blank line and the newline comes the space, so a paragraph longer than the target is cut between two words, wherever the size runs out (add ". " to the list to cut at sentence ends; the root lab's rule does). And the merge step (base.py lines 167 to 210) drops pieces from the front of the running chunk while the running total is above the overlap, which is how the overlap is made: the last few pieces of one chunk start the next.

Checked against the root. The root lab reimplemented this rule in its own code. Running the real library on all 281 papers with sizes in Qwen3 tokens (from_huggingface_tokenizer, 256 tokens, 32 overlap) gives the same result: @@lc_tok_intact@@ of 892 questions with evidence intact (root: 838) and @@lc_tok_bm1024@@ found with BM25 at 1,024 tokens (root: 0.613) measured. The 1,000-character tutorial setting keeps @@lc_c1000_intact@@ intact (smaller chunks, more cuts); the 4,000-character default keeps all @@lc_c4000_intact@@ intact (its chunks are huge) but then fits almost nothing into a 1,024-token budget (@@lc_c4000_bm1024@@).

1.3 How many chunks, how many tokens stored

With fixed windows of c tokens overlapping by o, each new chunk starts c − o tokens (the stride) after the previous one, so a document of L tokens gives

n = ⌈(L − o) / (c − o)⌉,    T = L + (n − 1) · o
n
chunks (one when L ≤ c); the last chunk may be shorter
T
tokens stored and embedded: every overlap is stored twice (exactly, when the last chunk ends at the document end)

Worked example (the old version of this page): L = 10,000, c = 512, o = 64 gives a stride of 448, n = ⌈9,936 / 448⌉ = 23 and T = 10,000 + 22 × 64 = 11,408 tokens, 14% more than the text. Checked on the real chunk files: the formula gives the exact chunk count for all 281 papers at each of 128/16, 256/32 and 512/64, and the stored overhead is @@ovh_128@@, @@ovh_256@@ and @@ovh_512@@ measured. Overlap is not free, and the root lab showed what it buys: 32 tokens of overlap move fixed 256-token windows from 546 to 607 intact questions, still far below the 832 of cutting at paragraphs.

1.4 Structure-aware splitting: Markdown, HTML, code, sentences

When a document carries its own structure, cut along it first. QASPER's text has Markdown section headings, so LangChain's MarkdownHeaderTextSplitter applies: it splits at each heading and records the heading path as metadata (useful for filters and for citations), then the recursive splitter caps the size inside each section. One behaviour to know, read in markdown.py (lines 250 to 257 and 107): it strips every line, drops blank lines, and re-joins the remaining lines of a section with two spaces and a newline, so paragraph breaks ("\n\n") no longer exist when the size cap runs; the cap falls back to single newlines. On QASPER that costs nothing, because each paragraph is one line: @@lc_md_intact@@ intact and @@lc_md_bm1024@@ found with BM25 at 1,024 tokens, level with the root's paragraphs-within-sections rule (832; 0.645) measured. On text where paragraphs wrap across several lines it would.

The same library has HTMLHeaderTextSplitter for web pages and per-language separators for code: for Python it tries "\nclass ", then "\ndef ", then "\n\tdef " before blank lines (character.py lines 366 to 374), so functions stay whole when they fit. Not run here: the running example has no HTML or code corpus.

Sentences. Packing whole sentences needs a sentence splitter, and a regex such as the root's (cut after . ! ? followed by a capital, digit or bracket) breaks on abbreviations. On a third of the QASPER papers (94), the regex makes @@sent_regex_n@@ sentences of which @@sent_regex_bad@@ end on an abbreviation such as "et al.", "Fig." or "No." (a false cut); pySBD 0.3.4, a rule-based segmenter, makes @@sent_pysbd_n@@ with @@sent_pysbd_bad@@ such ends measured. Under 2% of cuts either way, and the root measured that sentence packing itself is a poor chunker here (593 intact, below fixed windows with overlap) because it ignores paragraph and section breaks.

1.5 Small to big: retrieve a sentence, return its paragraph

Small chunks match precisely (a sentence is about one thing, so its vector is not an average of several topics); big chunks carry the context the model needs to answer. Parent-child or small-to-big retrieval does both: index small units (the children), and when one matches, hand over the larger unit that contains it (its parent). LlamaIndex's SentenceWindowNodeParser is one form: it embeds single sentences and stores the three sentences on each side as the window to return (DEFAULT_WINDOW_SIZE = 3, llama-index-core 0.14.25, node_parser/text/sentence_window.py line 16).

Measured on QASPER inside each question's paper, with the vectors the root lab already computed (bge-small; sentence vectors are three-sentence windows), handing over parents in the order their children rank until 1,024 tokens are used, a parent counted once:

evidence paragraph covered (root's rule)an extractive answer string handed over (@@pc_n_ext@@ questions)

The best unit to hand over here is the paragraph, and the best way to find it is through its sentences: sentence → parent paragraph reaches @@pc_sent_par_1024@@ against @@pc_par_1024@@ for ranking whole paragraphs and @@pc_struct_1024@@ for paragraph-aware 256-token chunks. Returning bare sentence windows looks bad under the paragraph rule (@@pc_win_1024@@) but holds up better when the test is only whether the answer string arrived (@@pc_win_ans_1024@@ against @@pc_par_ans_1024@@): a sentence often carries the answer without its paragraph. Going bigger than the paragraph loses: whole sections as parents fall to @@pc_sec_1024@@, because one section can eat the budget.

1.6 Semantic chunking

Semantic chunking embeds each sentence (with its neighbours) and cuts where consecutive vectors are least similar. The root lab ran LangChain's SemanticChunker defaults (cut above the 95th percentile of distances): chunks of median 342 and up to 4,967 tokens, best at a fixed top 3 only because the chunks are big, and last at an equal 1,024-token budget (38.6% with BM25) root lab. It costs an embedding call per sentence at index time and has no size cap; on documents with real paragraphs, the author's breaks are the better boundaries.

1.7 Late chunking

The idea ({{Günther et al., Jina AI, arXiv 2409.04701|https://arxiv.org/abs/2409.04701}}): instead of cutting first and embedding each piece alone, run the whole document through a long-context embedding model once, so every token's vector has attended to the whole document; then, for each chunk, average the token vectors inside its span. A chunk that says "the model" now carries which model. It needs an embedder that pools by averaging token vectors (so a span's average is a sensible vector) and a context long enough for the document; documents longer than the context are processed in overlapping windows ("long late chunking", the paper's Algorithm 2).

Published (the paper's Table 2, nDCG@10 on BEIR, documents cut into 256-token chunks): with jina-embeddings-v2-small, NFCorpus rises from 23.5 to 30.0 and SciFact from 64.2 to 66.1 ({{Jina's blog of 2024-08-22|https://jina.ai/news/late-chunking-in-long-context-embedding-models/}} prints 23.46 and 29.98); with the stronger jina-embeddings-v3 the gains shrink to 35.6 → 36.7 and 71.8 → 73.2, and with nomic-embed-text-v1 to nothing on NFCorpus (35.3 → 35.3) published, authors' runs. The paper reports an average relative gain of about 3.5% for fixed-size chunks. A comparison by {{Merola and Singh (arXiv 2504.19754, April 2025)|https://arxiv.org/abs/2504.19754}} found contextual retrieval (next section) "preserves semantic coherence more effectively" while late chunking "offers higher efficiency but tends to sacrifice relevance and completeness".

1.8 Contextual prefixes written by a model

Anthropic's contextual retrieval ({{post of 2024-09-19|https://www.anthropic.com/news/contextual-retrieval}}) asks a model, given the whole document and one chunk, for a short context (usually 50 to 100 tokens) situating the chunk, and prepends it before embedding and BM25 indexing. Their reported top-20 retrieval failure rate fell from 5.7% to 3.7% with contextual embeddings, 2.9% adding contextual BM25, and 1.9% adding a reranker; with prompt caching (the document is read once per document, not once per chunk) they put the one-off cost at $1.02 per million document tokens, assuming 800-token chunks, 8,000-token documents and 100 tokens of context per chunk published, vendor. The root lab ran it with Qwen3-1.7B on 71 papers: llama.cpp's prompt cache cut the prompt tokens from 11.1 M to 0.87 M, and the gain was within noise for this small writer (bge-small top 3 46.9% → 49.4%, but at 1,024 tokens 57.7% → 55.2%) root lab; see its Pipeline lab for the details. Late chunking gets document context for one extra forward pass per document and no generator; contextual prefixes cost a generator call per chunk.

1.9 Mixing chunking strategies in one index

The old version of this page said that mixing chunking strategies across ingestion runs "can cost about 8 points of recall". No source for that number was found, so it was tested. One index over all 281 papers, half chunked in 128-token windows and half in 512-token windows (as if a re-ingestion changed the chunker for half the corpus), searched globally (any paper) with bge-small:

indexfound within 1,024 tokens, all 892questions about the 512-token halfquestions about the 128-token halflong chunks: share of index / of top 10s

The mixed index lands between the two uniform ones. The papers re-chunked to 512 tokens do worse than they would in an all-512 index (@@mx_b_mixed@@ against @@mx_b_u512@@), because they now compete with small chunks for the same budget; the 128-token papers gain a little. So mixing does move recall, by about five points for the affected half here, but the old "8 points" is not reproduced and is dropped. What does hold: a chunker change should re-index the whole corpus, in both the BM25 and the vector index; how chunk boundaries move when a single document is revised (and how much has to be re-embedded) is measured in the ingestion page's {{Re-indexing lab|n:3f85c17b0d0d81279079f614f382f2e7}}.
