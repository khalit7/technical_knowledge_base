0. In one screen

A vector index is a data structure that answers one question: which of the stored vectors are closest to this query vector? Answering it exactly means comparing the query with every stored vector. An index answers it approximately, by looking at a small part of the collection, and every index on this page is a different answer to "which part?": a few k-means cells (IVF), a walk through a graph (HNSW, Vamana), or everything, but in compressed form (PQ, scalar and binary codes). Each trades four things against one another: recall (how many of the true nearest it returns), latency (or queries per second), memory, and build and update cost.

text→embedding model→vector (1,024 numbers)→index: which stored vectors are nearest?→top k ids→reranker, LLM

Six ideas that carry the page

1. Exact search is a memory scan

Comparing one query with N vectors of d numbers reads N × d × 4 bytes. Measured here, one thread scans at about 37 GB/s, so the 522,931 Quora vectors take 22 ms per query. Below roughly 105 vectors that is fine (section 2).

2. Recall is not relevance

ANN recall counts how many of the exact nearest neighbours an index returns. On SciFact, index settings that return about 90% of the exact top 10 keep nDCG@10 between 0.650 and 0.698 against 0.700 for exact search: the last points of recall barely move answer quality, but below about 0.8 it falls fast (section 1).

3. Every index has a boundary problem

IVF loses neighbours that sit in a cell it did not probe (48% of SciFact's true top-10 neighbours are in the query's nearest cell); graphs lose them when the walk stops early. More probes or a larger ef buy recall with time (sections 3, 6).

4. Compression needs rescoring

16-byte PQ codes are 256 times smaller than 4,096-byte float32 vectors and find 0.450 of the true top 10 alone; re-scoring the best 100 with the full vectors brings it to 0.914 (section 4).

5. Filters change everything

With a filter that keeps 0.4% of chunks, an HNSW search plus post-filtering finds 0.43 of the right answers; hnswlib's in-graph filter finds all of them but computes 6,513 distances, while pre-filtering and exact search computes 23 (section 9).

6. The "H" in HNSW matters less than its pruning

On the topic's 25,039 mixed vectors, a single-layer graph matched HNSW (recall 0.953 vs 0.949 at ef 40), while replacing the neighbour-selection heuristic with "keep the M closest" cost 4 points (section 6).

1. The job, and the scorecard

k-nearest-neighbour search (kNN): given a query vector q and N stored vectors, return the k with the highest similarity to q (or the smallest distance). With unit-length vectors, cosine similarity, inner product and Euclidean distance rank in the same order (|a − b|2 = 2 − 2 a·b), which is why every index here uses inner product. Approximate nearest neighbour search (ANN) accepts returning some vectors that are not in the true top k, in exchange for doing far less work.

The score of an index is ANN recall@k: of the true top k (found by exact search on the same vectors), the share the index returned in its top k, averaged over queries. It is not the retrieval recall of the parent page (did we find the documents a human labelled relevant); it measures only how faithfully the index imitates exact search. Always quote it with a cost: any index is fast at low recall. The cost this page counts first is distance computations per query, deterministic and machine-independent; time and memory come later.

Predict: an index that returns 90% of the exact top 10 on SciFact. How much of exact search's nDCG@10 (answer quality against human labels) does it keep?
Measured on SciFact with Qwen3-Embedding: exact search scores nDCG@10 0.700. Across every HNSW and IVF setting tried, settings with ANN recall@10 between 0.88 and 0.92 score between 0.650 and 0.698, that is 93 to 100% of exact. The neighbours an index misses are usually the borderline ones (ranks 8 to 10), which are rarely the labelled answer. Below about 0.8, quality falls fast. The chart shows every setting.

Two consequences. First, chasing ANN recall from 0.99 to 0.999 is usually wasted latency for retrieval-augmented generation, where a reranker and a language model sit downstream; measure relevance on your own labelled queries before buying the last points. Second, the reverse is dangerous: a recall of 0.6 does hurt, and the defaults of some libraries land there (the parent's Tool map measured LanceDB's default IVF-PQ at 0.59 and FAISS IVF at its default nprobe 1 at 0.42 on SciFact with bge-small).

Measuring recall yourself: keep a few hundred real queries; compute their exact top k once with a flat scan (it is the ground truth); compare every index setting against it. That is all this page does.

2. Exact search, and why it stops scaling

Exact search (also flat or brute-force search) computes the similarity of the query with every stored vector and keeps the k best in a small heap. Its cost is easy to write down:

work = N · d multiply-adds    bytes read = N · d · b
N
stored vectors
d
dimensions (1,024 for Qwen3-Embedding, 384 for MiniLM)
b
bytes per number: 4 for float32, 2 for float16, 1 for int8

One query against the 5,183 SciFact vectors is 5.3 million multiply-adds over 21 MB. A CPU core can do the multiplications far faster than memory can deliver the numbers, so for one query at a time exact search is memory-bound: its speed is the speed of reading the vectors. Measured here with FAISS's IndexFlatIP on one thread, the scan ran at 37 GB/s once the collection no longer fitted in the chip's caches measured here, timed.

Predict: one query, one CPU core, 1 million vectors of 1,024 float32 numbers (4.1 GB). How long does exact search take on this laptop?
About 112 ms: 4.1 GB at the measured 37 GB/s. The 522,931 Quora vectors (384 numbers, 803 MB) took 22 ms per query measured. Fine for a nightly job or a few queries a second; too slow for a search box at hundreds of queries per second. Apple quotes up to 200 GB/s of memory bandwidth for the whole M1 Pro (vendor claim, 2021); one core reaches a fraction of it, and all cores together share it.

Batching changes the bottleneck. With many queries at once, each vector read from memory is reused for every query in the batch, which turns the scan into a matrix multiplication (GEMM) that keeps the arithmetic units busy. FAISS switches to BLAS when the batch is large enough:

faiss/utils/distances.cpp at v1.15.1, lines 572 to 577 and 607
if (res.sel || ny == 0 || nx * d < static_cast<size_t>(distance_compute_blas_threshold)) { exhaustive_inner_product_seq(x, y, d, nx, ny, res); // one query at a time } else { exhaustive_inner_product_blas(x, y, d, nx, ny, res); // a matrix multiplication } ... int distance_compute_blas_threshold = 128000; // nx * d: for d = 1,024, batches of 125+ queries

Measured on the four corpora stacked (25,039 × 1,024): one query at a time 2.53 ms each; a batch of 200, 0.22 ms per query, about 12 times less measured here, timed. The threshold matters: on Quora (384 dimensions) a batch of 200 is 200 × 384 = 76,800, under 128,000, so FAISS stayed on the one-at-a-time path and the batch saved nothing (21 ms per query against 22 ms). That is why offline jobs (evaluating a golden set, deduplicating a corpus, building a kNN graph) often need no index at all, and why GPUs, which are built for matrix multiplication, do exact search well (Johnson, Douze and Jégou built a k-NN graph over 1 billion vectors in under 12 hours on 4 GPUs, arXiv 1702.08734, published, authors' runs, 2017).

When exact search is the right answer

  • Small collections. FAISS's own decision tree says Flat below 10,000 vectors (The Faiss library, Fig. 10), and ScaNN's documentation "fewer than 20k points, use brute-force" (algorithms.md), both vendor docs. At 25,039 vectors of 1,024 dimensions it costs 2.53 ms here: often still fine.
  • After a selective filter. If a condition leaves 300 rows, scanning them exactly is cheaper than any index walk (section 9).
  • Ground truth. Every recall on this page is measured against it.
  • "Local" or "lite" modes of databases often are exact search. The parent's Tool map found that Qdrant's Python client in local mode and Milvus Lite both scan every vector (Milvus Lite even after reporting an HNSW index), so their recall is 1.0 and their speed is not that of the server.

3. IVF: k-means cells, nlist and nprobe

The first idea for doing less work: group similar vectors, and look only in the groups nearest the query. An inverted file index (IVF; the name comes from text search's inverted index, a list of documents per word, here a list of vectors per cell) runs k-means clustering once: it picks nlist centroids so that each vector is close to its centroid, then files every vector in the list of its nearest centroid. Each list is a cell of the space (a Voronoi cell: the region nearer to that centroid than to any other). A query is compared with the nlist centroids, and only the nprobe nearest cells are scanned.

distances per query ≈ nlist + nprobe · N / nlist
nlist
number of cells (FAISS: nlist; pgvector: lists; Milvus: nlist)
nprobe
cells scanned per query (pgvector: ivfflat.probes)

For a fixed share of cells probed, this is smallest when nlist is about √N, the usual rule (The Faiss library, Eq. 18: the number of distances "K + P × N/K" is minimised at K = √(P N), published); the parent's Tool map used nlist = 72 ≈ √5,183 for SciFact. Here is FAISS's search at the top level, two steps exactly as described:

The boundary problem, measured

A true neighbour can sit just across a cell wall. Where do SciFact's true top-10 neighbours live, counted by the rank of their cell among the query's nearest cells (nlist 72)? measured here

Only 48% sit in the nearest cell, so nprobe 1 finds 0.482 of the true top 10; nprobe 8 (11% of the cells) reaches 0.901 and nprobe 32 0.992. In 1,024 dimensions, "near the query" spreads over many cells. More cells (larger nlist) make each cell smaller, so more probes are needed for the same recall, but each probe is cheaper:

Training: how many points, and which

k-means is trained on a sample. FAISS subsamples to 256 points per centroid and warns below 39 (faiss/Clustering.h lines 44 and 46: min_points_per_centroid = 39, max_points_per_centroid = 256; the warning is printed at Clustering.cpp lines 113 to 120). On SciFact with nlist 72, training on 5% of the corpus (259 points, 3.6 per centroid) instead of all of it changed recall at nprobe 8 from 0.913 to 0.889, but made the lists much more uneven (coefficient of variation of list sizes 0.85 against 0.44): uneven lists mean some probes scan many more vectors than others, so latency varies by query. Two k-means runs on the same vectors fed in a different order (so k-means starts from different points) gave nprobe-1 recall of 0.482 and 0.498: report IVF numbers with the seed. measured here

Drift: when the collection changes after training

The centroids describe the data they were trained on. Train them on SciFact only, then add NFCorpus, HotpotQA and QASPER (the collection grows into new topics, 25,039 vectors, nlist 158): the biggest list grows to 3,480 vectors against 399 after retraining, and at nprobe 16 recall is 0.886 against 0.914 while scanning far more vectors per query (6,477 against 2,837 distances) measured here. pgvector's IVFFlat has the same property; the Search and vector databases page covers rebuilding it in PostgreSQL.

IVF in one line
Solves exact search's linear cost with a cheap build and little extra memory (the centroids: nlist × d floats). Costs the boundary problem, a training step, and drift. Tune nprobe on your own queries; start with nlist ≈ √N (FAISS's decision tree goes further at scale: 16k cells below 1M vectors, 64k below 10M, 1M cells below 1B, with an HNSW index over the centroids) and expect to probe 5 to 15% of the cells for recall near 0.9 on embedding data like this.

4. Quantization: storing each vector in fewer bytes

IVF reduces how many vectors a query touches; quantization reduces how many bytes each one takes, so more of them fit in memory and each comparison reads less. A 1,024-dimension float32 vector is 4,096 bytes; at 100 million vectors that is 410 GB before any index. Six ways to store fewer bytes, from gentle to aggressive:

Product quantization, step by step

Product quantization (Jégou, Douze and Schmid, TPAMI 2011) cuts each vector into m sub-vectors of d/m numbers. For each of the m positions it learns, with k-means, a codebook of 256 centroids (8 bits). A vector is stored as m bytes: for each sub-vector, the id of its nearest centroid. The codebooks (256 × d floats in total, 1 MB for d = 1,024) are shared by the whole collection.

At query time the query is not quantized. For each position m the query's sub-vector is compared with all 256 centroids once, giving an m × 256 distance table; the approximate score of any stored vector is then the sum of m table entries picked by its code. The paper calls this asymmetric distance computation (ADC) and shows it beats quantizing the query too ("SDC"): "For m=8 we obtain the same accuracy for ADC and k*=64 as for SDC and k*=256" (Section V, published, authors' runs). FAISS's table construction is one loop over positions:

faiss/impl/ProductQuantizer.cpp at v1.15.1, lines 443 to 456 (L2 version; compute_inner_prod_table at line 472 is the same with dot products)
void ProductQuantizer::compute_distance_table(const float* x, float* dis_table) const { ... for (size_t m = 0; m < M; m++) { fvec_L2sqr_ny<SL>( dis_table + m * ksub, // row m of the table: ksub = 256 entries x + m * dsub, // the query's m-th sub-vector get_centroids(m, 0), // the 256 centroids of position m dsub, ksub); }

So per candidate the work drops from d multiply-adds over 4d bytes to m additions over m bytes. The IVF-PQ lab animates this on a real index: the table as a heat map, one candidate's 16 bytes, its score against the exact one.

Measured: what each byte budget keeps

SciFact with Qwen3-Embedding (and the four corpora stacked) measured here; "rescore" means: take the index's best 10 × r by approximate score, re-rank them with the float32 vectors, keep 10.

  • int8 is almost free: recall 0.995 at a quarter of the bytes; int4 0.946.
  • PQ alone is lossy, PQ with rescoring is not. 16-byte codes (m = 16) alone find 0.450 of the true top 10; rescoring the best 100 finds 0.914, the best 400, 0.988. The reconstruction error falls from 0.452 (m = 8) to 0.055 (m = 256), in squared distance on unit vectors.
  • OPQ helps PQ at equal bytes. Optimized product quantization (Ge et al., CVPR 2013) first learns a rotation so that each sub-vector carries a balanced share of the information; here it lifts m = 16 from 0.450 to 0.579 and m = 64 from 0.688 to 0.797, for the cost of one d × d matrix multiply per query.
  • Binary needs rescoring; RaBitQ needs less of it. Sign bits alone: 0.674; with 100 candidates rescored: 0.990. RaBitQ (Gao and Long, SIGMOD 2024; in FAISS by 1.11.0, 2025-04-24, per its CHANGELOG) stores about the same 136 bytes but estimates distances better: 0.814 alone, 1.000 with 100 candidates rescored. Its paper proves an error bound of O(1/√d) and reports beating PQ "by a clear margin" (published, authors' runs).
Rescoring is not free
It needs the full vectors somewhere: in RAM (then compression saved nothing on memory, only on scan bandwidth), or on SSD, read for the shortlist only (DiskANN's design, section 7), or in object storage. Count it in the memory budget (section 11).

Published on larger models: Hugging Face's measurements kept about 96% of retrieval quality with binary codes plus rescoring (32 times less memory) and about 99% with int8 (blog, 2024-03-22) published; the share kept depends strongly on the model, as the 384-dimension Quora run on the Search and vector databases page shows (pgvector's halfvec and binary_quantize measured there). Which model tolerates quantization, and Matryoshka truncation of dimensions, belong to Embedding models.

5. IVF-PQ, residuals and rescoring

The classic billion-scale recipe combines both ideas: IVF picks the cells, PQ compresses what is inside them (Jégou et al. call it IVFADC). One refinement: PQ encodes the residual, the vector minus its cell's centroid, which is smaller and so quantizes with less error. For inner product the score splits into a coarse term and a table term, and FAISS's comment spells out the bookkeeping (for L2 it adds a third term it can precompute):

faiss/IndexIVFPQ.cpp at v1.15.1, lines 379 to 390 (comment above the precomputed tables); by_residual = true by default (line 64)
* During IVFPQ search with by_residual, we compute * * d = || x - y_C - y_R ||^2 * * where x is the query vector, y_C the coarse centroid, y_R the * refined PQ centroid. The expression can be decomposed as: * * d = || x - y_C ||^2 + || y_R ||^2 + 2 * (y_C|y_R) - 2 * (x|y_R) * --------------- --------------------------- ------- * term 1 term 2 term 3

Measured on SciFact, IVF72 with 32-byte PQ codes: recall alone stops rising at about 0.57 however many cells are probed (the PQ error, not the cell boundary, is the limit); with rescoring of the best 100 it climbs to 0.916 at nprobe 32 measured here. That is the same story the parent's Tool map found in LanceDB, whose default index is IVF-PQ: 0.59 at defaults, 0.97 with refine_factor 10 (rescoring) on SciFact with bge-small.

The general shape: candidates cheap, final ranking exact
Every compressed index ends the same way: a cheap, approximate stage generates candidates, and an exact stage re-ranks a short list. ScaNN calls it "reorder", LanceDB "refine_factor", FAISS "IndexRefine", Qdrant "rescore", DiskANN reads the full vector from SSD during the walk. It is the same pattern as a cross-encoder reranker after a retriever, one level down (Rerankers and late interaction).

6. HNSW: a graph you walk, read in the code

The second idea: connect each vector to a few of its neighbours, and find the query's neighbours by walking. In a proximity graph every stored vector is a node with links to some nearby nodes. A greedy search starts at some node, looks at its neighbours, moves to the one closest to the query, and repeats until no neighbour is closer. If the graph has the right mix of short links (for precision) and long links (to cross the collection quickly), the walk reaches the query's region in few steps. A navigable small world (NSW) graph is one built so that this works; HNSW (hierarchical NSW; Malkov and Yashunin, arXiv 1603.09320, IEEE TPAMI) adds two things: layers and a neighbour-selection heuristic. Watch both in the HNSW lab.

Layers from a coin that keeps landing tails

Every node is on layer 0. A node also appears on layers 1, 2, ... up to its level, drawn at insertion as floor(−ln U · mL) with U uniform in (0, 1). The paper recommends mL = 1/ln M, which makes each layer about M times smaller than the one below ("this corresponds to the skip list parameter p=1/M", Section 4.1). The code is exactly that:

hnswlib/hnswalg.h at v0.8.0, line 142 and lines 207 to 211
mult_ = 1 / log(1.0 * M_); ... int getRandomLevel(double reverse_size) { std::uniform_real_distribution<double> distribution(0.0, 1.0); double r = -log(distribution(level_generator_)) * reverse_size; return (int) r; }

So a node reaches level l or higher with probability M−l. FAISS computes the same distribution as a table (impl/HNSW.cpp lines 80 to 93, exp(-level / levelMult) * (1 - exp(-1 / levelMult)) with levelMult = 1/ln M, line 63). Measured on SciFact measured here:

Search: greedy on top, best-first at the bottom

A query enters at the single entry point (the node with the highest level), walks greedily on each upper layer until no neighbour is closer, drops a layer, and repeats. On layer 0 it switches to a best-first search that keeps the ef best nodes seen (ef = "exploration factor"; efSearch in FAISS, hnsw.ef_search in pgvector): repeatedly expand the closest unexpanded candidate, compute distances to its unvisited neighbours, keep those that beat the worst of the ef results. It stops when the closest open candidate is worse than the worst result:

hnswlib/hnswalg.h at v0.8.0, searchBaseLayerST, lines 342 to 348 and 395 (comments added)
while (!candidate_set.empty()) { std::pair<dist_t, tableint> current_node_pair = candidate_set.top(); // closest open candidate dist_t candidate_dist = -current_node_pair.first; bool flag_stop_search; if (bare_bone_search) { flag_stop_search = candidate_dist > lowerBound; // lowerBound = worst of the ef kept ... // then, for each unvisited neighbour of that candidate: flag_consider_candidate = top_candidates.size() < ef || lowerBound > dist;

FAISS's version stops differently: after more than efSearch expansions, or when efSearch closer candidates are already queued (impl/HNSW.cpp lines 1164 and 1224). Same idea, different counters, which is one reason "ef 64" does not mean the same recall in two libraries. In both, ef is the runtime dial: recall up, latency up, no rebuild.

Build: every insert is a search, then a careful choice of links

Inserting a node runs the same search with a wider list, efConstruction (ef_construction), on every layer from its level down, then picks which candidates to link to. The heuristic (the paper's Algorithm 4) takes candidates nearest first and keeps one only if it is closer to the new node than to every neighbour already kept:

hnswlib/hnswalg.h at v0.8.0, getNeighborsByHeuristic2, lines 457 to 478 (abridged)
while (queue_closest.size()) { if (return_list.size() >= M) break; std::pair<dist_t, tableint> curent_pair = queue_closest.top(); dist_t dist_to_query = -curent_pair.first; // candidate to new node queue_closest.pop(); bool good = true; for (std::pair<dist_t, tableint> second_pair : return_list) { dist_t curdist = fstdistfunc_(getDataByInternalId(second_pair.second), getDataByInternalId(curent_pair.second), ...); // candidate to a kept neighbour if (curdist < dist_to_query) { good = false; break; } } if (good) return_list.push_back(curent_pair); }

A rejected candidate is reachable through the neighbour that blocked it, so the link budget goes to other directions; in clustered data this is what keeps a link to the next cluster (the paper's Fig. 2). Three details that the paper's prose does not make obvious and the code does:

  • The new node keeps at most M links, even on layer 0 (line 513: getNeighborsByHeuristic2(top_candidates, M_)); layer 0 lists can hold 2M (line 113: maxM0_ = M_ * 2, the paper's recommendation "2*M is a good choice for Mmax0") and fill up through reverse links from later nodes.
  • Reverse links are pruned again: when a neighbour's list is already full, adding the new node re-runs the heuristic over the old list plus the new node, and something is dropped (lines 586 to 610). Links are not symmetric.
  • The next layer down starts from the closest node found (line 524).

To check that this reading is right, this page ships a line-by-line Python port of hnswlib's insert and search (src/scripts/pyhnsw.py) and compares it with hnswlib on all 5,183 SciFact vectors, M 16, efConstruction 200, with hnswlib's own levels: 5,530 of 5,539 neighbour lists come out identical in content and order (the rest differ by floating-point ties), and all 300 test claims get the same top 10 at ef 10, 40 and 100 measured here. The port is what draws the HNSW lab, and what counts distance computations where hnswlib's Python API does not.

What each half of HNSW buys

Remove one idea at a time, with the port, on the same vectors, order and levels measured here:

On the four corpora stacked, plain "keep the M closest" links cost recall at every ef (0.906 against 0.949 at ef 40): the data is clustered by source, which is exactly the case the heuristic was designed for. A single layer with the heuristic matched full HNSW (0.953). On SciFact alone, one topic, neither change mattered much. This agrees with Munyampirwa, Lakshman and Coleman ("Down with the Hierarchy: The 'H' in HNSW Stands for 'Hubs'", arXiv 2412.01940 v3, ICML 2025 workshop, published, authors' runs): a flat graph had "latency and recall performance essentially identical to the original algorithm but with less memory overhead" on data from 96 to 960 dimensions at up to 100M vectors, the hierarchy helping only below about 32 dimensions; they explain it with "hubs", a few well-connected nodes that every search passes through early. The hierarchy costs little memory (about 1/(M−1) extra lists), so libraries keep it.

HNSW in one line
Solves high recall at low latency with no training step; inserts work any time. Costs memory (the full vectors plus 2M links per node, in RAM), slow builds (each insert is a search), and deletes that leave tombstones (section 10). Tune M once (16 to 32), efConstruction once (100 to 200), and ef per query on your own data.

7. DiskANN and Vamana: the graph on SSD

HNSW wants the full vectors and the links in RAM. At a billion 128-dimension vectors that is hundreds of gigabytes. DiskANN (Subramanya et al., NeurIPS 2019) keeps only small PQ codes in RAM to steer the walk, and puts the graph and the full vectors on SSD: "for each point i, we store its full precision vector x_i followed by the identities of its ≤ R neighbors" (Section 3.2), padded so a node's position on disk is computed, not looked up. Each step of the walk is then one random SSD read of one node, and the full vector that arrives with it re-scores the candidate for free. Its headline: a billion SIFT vectors on one workstation with 64 GB of RAM, "> 5000 queries a second with < 3ms mean latency and 95%+ 1-recall@1" on 16 cores (published, authors' runs, 2019).

The graph is Vamana, a single layer (no hierarchy) built in two passes over the data from a random start graph, with one new knob, α, in its pruning rule RobustPrune: repeatedly keep the closest remaining candidate p*, then drop every candidate p′ with α · d(p*, p′) ≤ d(p, p′) (Algorithm 2). With α = 1 this is the same rule as HNSW's heuristic ("both HNSW and NSG have no tunable parameter alpha and implicitly use alpha = 1", Section 2.4); α > 1 prunes less, so a node keeps edges that make "the distance to the query decrease by a multiplicative factor of α" at each hop, giving fewer hops, which is what matters when each hop is an SSD read. The search keeps a list of L candidates and expands them until all are expanded (Algorithm 1); on SSD it fetches the W best at once (beam width W of 2 to 8 in the paper).

Not run here: the official DiskANN. Its Python package diskannpy 0.7.0 ships only Linux x86_64 and Windows wheels, and the current Rust code (DiskANN v0.60.0, 2026-10-05, per the parent's FACTS) would need a Rust toolchain this machine does not have. Instead this page implements Vamana from the paper's three algorithms in Python (src/scripts/vamana.py, about 120 lines; not the authors' code) and measures it against HNSW on the same SciFact vectors measured here:

  • Hops track L. Vamana expands about L nodes per query: at L = 40, 44 hops for recall 0.989; HNSW at ef 40 walks 45 for 0.992. At 5,183 vectors the two graphs are equally good; the paper's claim of "2 - 3 times fewer hops ... compared to HNSW and NSG" is for large datasets (Section 4.2) and is not tested here.
  • α in 1,024 dimensions behaves differently from the paper's 128. With α = 1 the pruning keeps on average 16.0 of the allowed 32 edges; with α = 1.2 every node fills all 32. And the extra edges are short ones: the median rank of an edge's target among the node's neighbours falls from 24 to 20, and the share of edges to nodes outside the 50 nearest from 29% to 1%. The reason is distance concentration: in high dimensions a point's 10th neighbour (median distance 0.92) is nearly as far as its typical graph neighbour (0.96), so the α margin rarely triggers a prune. The α = 1 graph had half the edges for the same recall: on data like this, half the memory for links.
  • Sector arithmetic. A node on disk is d × 4 + R × 4 bytes: 128 × 4 + 64 × 4 = 768 bytes for SIFT with R = 64 (several nodes per 4 KB sector; the paper's Section 3.5 notes a degree-128 neighbourhood plus a 128-d vector fits one sector), but 1,024 × 4 + 32 × 4 = 4,224 bytes for Qwen3-Embedding, just over one 4,096-byte sector: two reads per hop unless the vector is stored in float16 or the degree lowered. Dimension matters for disk indexes in a way it does not in RAM.

In products: Milvus's DISKANN index (defaults MaxDegree 56, SearchListSize 100, PQCodeBudgetGBRatio 0.125, BeamWidthRatio 4; Milvus 3.0 docs, vendor docs), Azure's pg_diskann and Cosmos DB, SQL Server 2025, Timescale's pgvectorscale (StreamingDiskANN), and Redis 8.2's SVS-VAMANA (dates and links on the Search and vector databases page and the parent's Tool map). FreshDiskANN handles deletes lazily: deleted points stay in the graph for navigation, are filtered from results, and are consolidated in batches once "1-10% of the index size" is deleted (arXiv 2105.09613, published, authors' runs); section 10 measures the same trade-off with hnswlib's tombstones.

8. ScaNN: quantize for ranking, not for reconstruction

PQ learns codebooks that reconstruct each vector as faithfully as possible. But for inner-product search only one part of the error matters much: the part along the vector's own direction, which moves its score for every query that is similar to it. Anisotropic vector quantization (Guo et al., ICML 2020), the core of Google's ScaNN library, weights the residual parallel to the data point by a factor η more than the orthogonal residual; with a threshold T = 0.2 the paper uses η = 4.125 and reports better recall than reconstruction loss at the same bit rate on Glove-1.2M, and the fastest high-recall results on ann-benchmarks.com at the time (published, authors' runs). ScaNN's own rules of thumb: brute force below 20,000 points; "score with AH, then rescore" below 100,000; "partition, score with AH, then rescore" above, with about √N leaves and dimensions_per_block 2 (algorithms.md, vendor docs).

Run here, in a container. ScaNN 1.4.2 publishes Linux wheels only. Its aarch64 wheels tagged for Python 3.12 and 3.13 refuse to import ("module was compiled for Python 3.9"), so it ran in a python:3.9-slim Linux container on this Mac, recall only (no timing: a container on a shared laptop) measured here:

AH = asymmetric hashing, ScaNN's PQ-like scoring with 16 centres per block (4 bits); dims_per_block 2 gives d/4 bytes per vector. "Tree" partitions into √N leaves like IVF. Reorder 100 = rescore the best 100 exactly.

On these unit-length vectors the anisotropic loss did not beat plain reconstruction at equal code size (0.867 against 0.885 at 256 bytes, 0.654 against 0.668 at 64 bytes, SciFact, no reordering), and with reordering both reached the same recall. That does not contradict the paper, which measures a different dataset (Glove-1.2M, 100 dimensions) and recall regime; it is a reminder to measure a published trick on your own vectors before paying for it. The partitioned configuration behaved like IVF with rescoring: 0.937 when searching 16 of 72 leaves.

In Postgres, Google's AlloyDB offers ScaNN as alloydb_scann; Vertex AI Vector Search is built on it (see the Search and vector databases page).

9. Filtered search: where indexes break

Real queries come with conditions: "chunks of this paper", "documents this user may read", "published this year". A filtered (or hybrid) vector search must return the k nearest vectors among those that pass the filter. Two properties of the filter decide which strategy works:

  • Selectivity: the share of rows that pass. "Own paper" in QASPER keeps 0.35% of the 6,463 chunks (about 23).
  • Correlation with the query: whether the rows that pass are the ones near the query anyway. A question's own paper is correlated (its best chunks are near the question); a randomly chosen other paper of the same size is not; a filter on a different collection than the query came from is anti-correlated.

Four strategies

StrategyHowFails when
Pre-filterfind the passing rows with an ordinary index (B-tree, bitmap), then exact search over themthe filter keeps many rows (then it is a big exact scan)
Post-filterANN search for k′ > k results, drop those that failthe filter is selective or anti-correlated: few of the k′ pass
In-graph filterwalk the graph as usual, but only passing nodes enter the resultsselective filters: the walk must visit most of the graph to collect k passing nodes
Predicate-aware graphwalk only (or mostly) through passing nodes, with extra links so they stay connected: ACORN, Qdrant's payload links, Filtered-DiskANNbuild cost and memory for the extra links

  • Post-filtering a selective filter fails, and anti-correlation makes it worse. With "own paper", 100 unfiltered neighbours contain on average 4.3 chunks of the right paper, so recall is 0.43; with an uncorrelated paper of the same size, 0.03, and 756 of 892 questions got nothing back at all.
  • hnswlib's in-graph filter is always right and sometimes absurdly expensive. For "own paper" it found every true neighbour but computed 6,513 distances, the whole collection and more, where pre-filtering computes 23.
  • Pre-filtering wins below a crossover. On the 25,039 stacked vectors with a random attribute, pre-filter work equals the rows kept (251 at 1%, 2,588 at 10%); the in-graph filter needs 22,021 distances at 1% and 6,156 at 10%, and is cheaper than pre-filtering only from about 10 to 25% selectivity. Every production planner encodes this crossover.
  • ACORN-1 fixes the middle. Written here from Patel et al. (SIGMOD 2024, section 5.3: build HNSW without neighbour pruning, then search through one-hop and two-hop neighbours that pass the filter): at 1% selectivity recall 0.918 for 143 distances; at 10%, 0.953 for 621. Its weak spots are very selective filters (0.093 at 0.1%) and, in this implementation, no filter at all (0.873 at ef 100: truncating the two-hop list to M drops good neighbours), which the paper handles with the denser ACORN-γ build; a two-hop search on the ordinary pruned graph (no unpruned build) did worse (0.866 at 1%, 0.486 on QASPER's own-paper filter, where ACORN-1 reached 0.566). The paper reports "2-1000x higher queries per second ... at 0.9 recall compared to prior methods" (published, authors' runs).
  • Qdrant got all of them right, and its telemetry says how. What production systems do
pgvector 0.8 added iterative index scans (keep walking until enough rows pass), measured on the Search and vector databases page. Qdrant plans per segment from a cardinality estimate and uses payload links. Weaviate added ACORN as a filter strategy in v1.27 and made it the default in v1.34 (docs). The NeurIPS'23 Big-ANN filtered track (YFCC 10M CLIP vectors, queries with one or two tags) was won by ParlayANN at 37,902 queries per second at recall@10 ≥ 0.9, more than 11 times the FAISS baseline, using per-tag indexes for common tags and plain lists for rare ones (arXiv 2409.17424, independent benchmark). Multi-tenancy (one index with a tenant filter, or one index per tenant) is this problem with a very selective, perfectly correlated filter; RAG in production covers it as an access-control question.

10. Updates and deletes

Collections change. Each family takes changes differently:

  • Flat: trivial; append or remove rows.
  • IVF: new vectors go into the nearest existing cell, so inserts are cheap, but the centroids slowly stop describing the data (section 3 measured the drift). Deletes just remove entries from a list. Periodic retraining is the fix.
  • HNSW: an insert is a search plus link updates (the same work as building, per vector). A delete cannot simply remove a node: other nodes route through it. hnswlib, like pgvector and FreshDiskANN, marks it as deleted (a tombstone; hnswlib sets a flag bit in the node's link-list header, *ll_cur |= DELETE_MARK, line 877): searches still walk through it but never return it, exactly the in-graph filter of section 9.

Measured with hnswlib's tombstones on SciFact (M 16, efC 200), recall against the exact top 10 of the rows still alive, and the work per query, against a graph rebuilt on the live rows only measured here:

Recall does not suffer: the dead nodes still route. The cost is work: with half the rows deleted, a query at ef 40 computes 977 distances against 544 in a rebuilt graph, and the dead vectors still occupy memory. hnswlib can reuse the slot of a deleted element for a new vector (allow_replace_deleted); replacing 30% of SciFact with NFCorpus abstracts that way gave recall 0.848 at ef 10 against 0.900 for a graph built fresh on the same final vectors (0.982 and 0.991 at ef 40): replacement keeps the old links around a new vector that may belong elsewhere. FreshDiskANN's answer is batch consolidation: after "1-10% of the index size" is deleted, reconnect the neighbours of each deleted node to its out-neighbours and re-prune (arXiv 2105.09613, published, authors' runs); pgvector does the equivalent in VACUUM (measured on the Search and vector databases page). In every system the honest long-term fix is the same: rebuild periodically, or rebuild per segment, as Lucene does when it merges segments.

Changing the embedding model is not an update
Vectors from two models are not comparable: a new model means re-embedding everything and building a new index, usually side by side with the old one until the switch. The Search and vector databases page gives the column-by-column recipe; RAG in production the dual-index operations.

12. Scaling to 100 million vectors and beyond

How work per query grows with N, measured on prefixes of Quora (10,000 to 522,931 vectors) at a fixed recall target, in distance computations measured here:

From 10,000 to 522,931 vectors (52 times more), exact search grows 52 times; IVF at recall 0.95 grows from 2,580 to 13,188 distances, roughly like √N; HNSW barely moves (437 to 297). On these vectors the graph's work is close to flat in N; the paper's claim is O(log N). The higher the recall target, the faster the work grows (IVF at 0.99: 4,957 to 73,111), as the Faiss library paper found on BigANN-1B, where IVF search time grew as N0.29 at recall 0.5 and N0.45 at 0.99 (published). Past one machine's memory, four techniques combine:

  • Compress in RAM (PQ, int8, binary, RaBitQ) and rescore from somewhere cheaper. With 64 GB of RAM for a billion vectors, the NeurIPS'21 Big-ANN in-memory track reached recall@10 of roughly 0.63 to 0.76 at 10,000 queries per second (arXiv 2205.03763, Table 2, independent benchmark).
  • Put the graph on SSD (DiskANN) or the lists on SSD (SPANN). The same competition's SSD track, with the DiskANN baseline on 8 vCPUs and 64 GB, reached roughly 0.90 to 0.95 at 1,500 queries per second (Table 3); SPANN reports 90% recall@10 "in just around one millisecond with only 32GB memory cost" on billion-scale sets, about twice as fast as DiskANN at equal memory (NeurIPS 2021, published, authors' runs).
  • Shard: split the collection over machines, search every shard for its top k, merge. Recall of the merged result is about the per-shard recall; latency is the slowest shard's. Sharding by a key the queries filter on (a tenant, a date) lets most queries touch one shard. Replicate each shard for queries per second and availability.
  • Use GPUs for builds and for batched search: FAISS on 4 GPUs built a kNN graph over a billion vectors in under 12 hours (2017, section 2).

Memory at 100M with HNSW is large: Munyampirwa et al. measured hnswlib's peak build memory at 183 GB for 100M BigANN vectors (128-d), 113 GB for their flat graph (Table 6, published, authors' runs). ANN-Benchmarks, the standard independent comparison of libraries, tests at most about 10 million vectors on a single CPU (README, "as of April 2025"), so it says little directly about 100M to 1B behaviour.

14. Common mistakes

Quoting latency or QPS without recall
Any index is fast at low recall. FAISS IVF at its default nprobe 1 answers SciFact in 0.017 ms with recall 0.482 (Frontier).
Leaving the query-time knob at its default
hnswlib's ef defaults to 10 (recall 0.876 on SciFact with bge-small), FAISS IVF's nprobe to 1 (0.42); LanceDB's default IVF-PQ without refinement gave 0.59 (parent's Tool map). Set ef or nprobe from a measured curve.
Benchmarking a "lite" or local mode
Qdrant's Python local mode and Milvus Lite scan every vector: recall 1.0, server speed unknown. A Qdrant server below indexing_threshold also has no graph (Tool map). Read back what index is actually being used.
Post-filtering a selective filter
With a 0.4% filter, 100 ANN results contained 4.3 matching rows on average (section 9). Pre-filter, or use a filter-aware search.
Training IVF or PQ on too little, or old, data
Lists become uneven and recall drifts as the collection grows into new topics (section 3). FAISS warns below 39 training points per centroid.
Using PQ or binary codes without rescoring
16-byte PQ alone: 0.450; with the best 100 rescored: 0.914 (section 4). Keep the full vectors somewhere and rescore a short list.
M too small
At M = 4, 134 of 5,183 nodes were unreachable: those documents can never be returned (section 6).
Mixing metrics or forgetting to normalise
Inner product on unnormalised vectors favours long vectors; build the index with the metric the model was trained for, and normalise if you use inner product as cosine.
Deleting heavily from an HNSW index and never rebuilding
Recall holds, cost grows: 977 against 544 distances per query with half the rows deleted (section 10).
Trusting a published trick without measuring it on your vectors
ScaNN's anisotropic loss gave no gain on these unit-length 1,024-d vectors (section 8); Vamana's α behaved differently in 1,024 dimensions than in 128 (section 7).

15. Interview questions

Why does exact search not scale, and when is it still right?
It reads N × d × 4 bytes per query and is memory-bound (about 37 GB/s per core here). Right for small sets, batched offline jobs (it becomes a matrix multiply), filtered subsets, and ground truth.
Explain IVF's nlist and nprobe and how you would set them.
nlist cells from k-means (about √N to start); nprobe nearest cells scanned per query. Distances ≈ nlist + nprobe · N/nlist. Sweep nprobe on real queries against exact search; pick the smallest that meets the recall target.
How does PQ compute a distance without decompressing?
The query builds an m × 256 table of sub-vector distances to each codebook centroid once; each candidate's score is the sum of m table entries chosen by its m code bytes (ADC).
What do M, efConstruction and ef control in HNSW?
M: links per node (2M on layer 0), graph quality and memory. efConstruction: candidate list while inserting, build quality and time. ef: candidate list at query time, the recall and latency dial.
Why does HNSW use a neighbour-selection heuristic?
Keeping only the M closest bunches links inside dense regions; the heuristic skips a candidate already reachable through a kept neighbour, preserving links between clusters. Measured: on the clustered four-corpus set, closest-M lost 4 points of recall at ef 40.
What makes DiskANN work on SSD?
PQ codes in RAM steer the walk; each node's full vector and neighbour list sit together on disk, so one hop is one read, and the full vector re-scores for free; α > 1 keeps edges that cut the number of hops; beam search reads several nodes at once.
A filter keeps 0.5% of documents. What do you do?
Pre-filter with an ordinary index and search those rows exactly (here about 141 distances), or use a filter-aware graph. Do not post-filter. If the filter is a tenant id, consider partitioning by tenant.
System design: semantic search over 200 million passages, 1,024-d embeddings, 500 queries per second, p99 under 100 ms, per-customer filters, daily updates.
Raw vectors: 200M × 4 KB = 819 GB, too much RAM for one node. Options: (1) int8 or RaBitQ codes in RAM (205 GB or about 27 GB) with HNSW or IVF, full vectors on SSD for rescoring the top 100; (2) DiskANN-style SSD graph with PQ codes in RAM. Shard by customer where customers are large (filter becomes routing), by hash otherwise, 4 to 8 shards plus replicas for QPS; scatter-gather and merge top k. Filters: pre-filter for small customers, filter-aware graph for large ones. Updates: write to a small fresh in-memory index, merge into the main one nightly, tombstones for deletes, periodic rebuild. Measure recall against exact search on a sample daily, and answer quality on a labelled set after every change.
Your RAG answers got worse after switching to a faster index. How do you check whether the index is to blame?
Run the same queries through exact search and compare top-k overlap (ANN recall) and the downstream metric; if ANN recall dropped below about 0.9 the index (or its default knob) is the cause; if not, look at chunking, the model, or filters.

Frontier: recall, speed and memory for every index measured

Every index family on this page, each swept over its query-time knob, timed on the same machine the same way: one CPU thread, one query at a time, three passes over the query set (median of each pass, median of the three). Up and right is better. The outlined points form the Pareto frontier: no other setting is both faster and more accurate. Lower the memory budget and watch which families survive.

Every setting

What transfers, and what does not
Measured on an Apple M1 Pro on one thread, from Python (each call adds roughly 10 to 30 microseconds, which dominates the fastest settings), on a shared machine: the load average during each run is in the table. Transfers: the order of the families, the shape of each curve, the recall numbers (deterministic), the bytes. Does not transfer: absolute milliseconds (a server core, many threads, batching and SIMD width all change them), and the libraries' relative speed in their own servers (Qdrant, pgvector and others add their own overheads; the Search and vector databases page times pgvector inside PostgreSQL). Memory here counts what the index needs at query time; "+ rescore" rows include the float32 vectors kept for rescoring. hnswlib 0.8.0 has hand-written SIMD distance code only for x86 (SSE, AVX, AVX-512; hnswlib.h lines 11 to 20); on this ARM chip it falls back to a plain loop, which is why it ran 4 to 7 times slower than FAISS at the same recall here. A batched call took the same time per query, so it is not Python overhead: the gap is a platform effect, not a property of the algorithm (on x86 hnswlib uses its SIMD code; not measured here).
