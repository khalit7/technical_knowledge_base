6. HNSW: a graph you walk

Second way to read less: link each vector to a few neighbours, and find the query's neighbours by walking. In a proximity graph every stored vector is a node with links to some nearby nodes. A greedy search starts at some node, moves to whichever neighbour is closest to the query, and repeats until no neighbour is closer. With the right mix of short links (precision) and long links (crossing the collection fast), the walk reaches the query's region in few steps. HNSW (hierarchical navigable small world; Malkov and Yashunin, arXiv 1603.09320, IEEE TPAMI) adds two things to such a graph: layers and a neighbour-selection heuristic. What to look for. Build, HNSW: most inserts stay on layer 0; about one in M reaches layer 1. Build, Closest-M: the M closest are kept whatever their direction, so links bunch up inside a dense corner and a cluster can end up reachable only through one or two nodes. At 240 points the layers save little: the lab shows the mechanism, the charts below what each half buys at 5,183 and 25,039 vectors.

Layers. Every node is on layer 0 and on layers up to its level, drawn as floor(−ln U · mL) with U uniform in (0, 1) and mL = 1/ln M: a node reaches level l with probability M−l, so each layer is about M times smaller ("the skip list parameter p=1/M", Section 4.1).

Search. From the single entry point (the highest node), walk greedily on each upper layer, then on layer 0 run a best-first search keeping the ef best seen: expand the closest unexpanded candidate, keep neighbours that beat the worst of the ef, stop when the closest open candidate is worse than the worst kept. ef is the runtime dial: recall up, latency up, no rebuild. FAISS's stop rule differs (impl/HNSW.cpp lines 1164 and 1224), so "ef 64" is not the same recall in two libraries.

Build. An insert runs the same search with a wider list, efConstruction, on every layer from its level down, then the heuristic (Algorithm 4) takes candidates nearest first and keeps one only if it is closer to the new node than to every neighbour already kept. A rejected candidate is reachable through the neighbour that blocked it, so the link budget goes to other directions: in clustered data, a link to the next cluster (the paper's Fig. 2; red dashed in the lab).

Three details that the paper's prose does not make obvious and the code does:

  • The new node keeps at most M links, even on layer 0 (line 513: getNeighborsByHeuristic2(top_candidates, M_)); layer 0 lists can hold 2M (line 113: maxM0_ = M_ * 2, the paper's recommendation "2*M is a good choice for Mmax0") and fill up through reverse links from later nodes.
  • Reverse links are pruned again: when a neighbour's list is already full, adding the new node re-runs the heuristic over the old list plus the new node, and something is dropped (lines 586 to 610). Links are not symmetric.
  • The next layer down starts from the closest node found (line 524).

Munyampirwa, Lakshman and Coleman found the same at up to 100M vectors in 96 to 960 dimensions: the hierarchy helps only below about 32 dimensions, because a few well-connected "hubs" do its job (arXiv 2412.01940, published, authors' runs). It costs little memory (about 1/(M−1) extra lists), so libraries keep it.

"Down with the Hierarchy" in its own words (provenance)

"Down with the Hierarchy: The 'H' in HNSW Stands for 'Hubs'", v3, ICML 2025 workshop: a flat graph had "latency and recall performance essentially identical to the original algorithm but with less memory overhead"; hubs are nodes that every search passes through early.

HNSW in one line
Solves high recall at low latency with no training step; inserts work any time. Costs memory (the full vectors plus 2M links per node, in RAM), slow builds (each insert is a search), and deletes that leave tombstones (section 10). Tune M once (16 to 32), efConstruction once (100 to 200), and ef per query on your own data.
