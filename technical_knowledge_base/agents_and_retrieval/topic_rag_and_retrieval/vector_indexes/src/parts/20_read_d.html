6. HNSW: a graph you walk, read in the code

The second idea: connect each vector to a few of its neighbours, and find the query's neighbours by walking. In a proximity graph every stored vector is a node with links to some nearby nodes. A greedy search starts at some node, looks at its neighbours, moves to the one closest to the query, and repeats until no neighbour is closer. If the graph has the right mix of short links (for precision) and long links (to cross the collection quickly), the walk reaches the query's region in few steps. A navigable small world (NSW) graph is one built so that this works; HNSW (hierarchical NSW; Malkov and Yashunin, arXiv 1603.09320, IEEE TPAMI) adds two things: layers and a neighbour-selection heuristic. Watch both in the {{HNSW lab|#t-vixhnsw}}.

Layers from a coin that keeps landing tails

Every node is on layer 0. A node also appears on layers 1, 2, ... up to its level, drawn at insertion as floor(−ln U · mL) with U uniform in (0, 1). The paper recommends mL = 1/ln M, which makes each layer about M times smaller than the one below ("this corresponds to the skip list parameter p=1/M", Section 4.1). The code is exactly that:

Search: greedy on top, best-first at the bottom

A query enters at the single entry point (the node with the highest level), walks greedily on each upper layer until no neighbour is closer, drops a layer, and repeats. On layer 0 it switches to a best-first search that keeps the ef best nodes seen (ef = "exploration factor"; efSearch in FAISS, hnsw.ef_search in pgvector): repeatedly expand the closest unexpanded candidate, compute distances to its unvisited neighbours, keep those that beat the worst of the ef results. It stops when the closest open candidate is worse than the worst result:

hnswlib/hnswalg.h at v0.8.0, searchBaseLayerST, lines 342 to 348 and 395 (comments added)

FAISS's version stops differently: after more than efSearch expansions, or when efSearch closer candidates are already queued (impl/HNSW.cpp lines 1164 and 1224). Same idea, different counters, which is one reason "ef 64" does not mean the same recall in two libraries. In both, ef is the runtime dial: recall up, latency up, no rebuild.

Build: every insert is a search, then a careful choice of links

Inserting a node runs the same search with a wider list, efConstruction (ef_construction), on every layer from its level down, then picks which candidates to link to. The heuristic (the paper's Algorithm 4) takes candidates nearest first and keeps one only if it is closer to the new node than to every neighbour already kept:

hnswlib/hnswalg.h at v0.8.0, getNeighborsByHeuristic2, lines 457 to 478 (abridged)
while (queue_closest.size()) { if (return_list.size() >= M) break; std::pair<dist_t, tableint> curent_pair = queue_closest.top(); dist_t dist_to_query = -curent_pair.first; // candidate to new node queue_closest.pop(); bool good = true; for (std::pair<dist_t, tableint> second_pair : return_list) { dist_t curdist = fstdistfunc_(getDataByInternalId(second_pair.second), getDataByInternalId(curent_pair.second), ...); // candidate to a kept neighbour if (curdist < dist_to_query) { good = false; break; } } if (good) return_list.push_back(curent_pair); }

A rejected candidate is reachable through the neighbour that blocked it, so the link budget goes to other directions; in clustered data this is what keeps a link to the next cluster (the paper's Fig. 2). Three details that the paper's prose does not make obvious and the code does:

  • The new node keeps at most M links, even on layer 0 (line 513: getNeighborsByHeuristic2(top_candidates, M_)); layer 0 lists can hold 2M (line 113: maxM0_ = M_ * 2, the paper's recommendation "2*M is a good choice for Mmax0") and fill up through reverse links from later nodes.
  • Reverse links are pruned again: when a neighbour's list is already full, adding the new node re-runs the heuristic over the old list plus the new node, and something is dropped (lines 586 to 610). Links are not symmetric.
  • The next layer down starts from the closest node found (line 524).

What each half of HNSW buys

Remove one idea at a time, with the port, on the same vectors, order and levels measured here:

On the four corpora stacked, plain "keep the M closest" links cost recall at every ef (@@var_simple_40@@ against @@var_hnsw_40@@ at ef 40): the data is clustered by source, which is exactly the case the heuristic was designed for. A single layer with the heuristic matched full HNSW (@@var_flat_40@@). On SciFact alone, one topic, neither change mattered much. This agrees with Munyampirwa, Lakshman and Coleman ("Down with the Hierarchy: The 'H' in HNSW Stands for 'Hubs'", arXiv 2412.01940 v3, ICML 2025 workshop, published, authors' runs): a flat graph had "latency and recall performance essentially identical to the original algorithm but with less memory overhead" on data from 96 to 960 dimensions at up to 100M vectors, the hierarchy helping only below about 32 dimensions; they explain it with "hubs", a few well-connected nodes that every search passes through early. The hierarchy costs little memory (about 1/(M−1) extra lists), so libraries keep it.

HNSW in one line
Solves high recall at low latency with no training step; inserts work any time. Costs memory (the full vectors plus 2M links per node, in RAM), slow builds (each insert is a search), and deletes that leave tombstones (section 10). Tune M once (16 to 32), efConstruction once (100 to 200), and ef per query on your own data.
