9. Filtered search: where indexes break

Real queries come with conditions: "chunks of this paper", "documents this user may read", "published this year". A filtered vector search must return the k nearest vectors among those that pass. Two properties of the filter decide which strategy works: selectivity, the share of rows that pass ("own paper" in QASPER keeps @@filt_q_share@@% of the 6,463 chunks, about 23), and correlation with the query, whether the rows that pass are near the query anyway (a question's own paper is correlated; a random other paper of the same size is not; a filter on a different collection than the query came from is anti-correlated).

StrategyHowFails when
Pre-filterfind the passing rows with an ordinary index (B-tree, bitmap), then exact search over themthe filter keeps many rows (then it is a big exact scan)
Post-filterANN search for k′ > k results, drop those that failthe filter is selective or anti-correlated: few of the k′ pass
In-graph filterwalk the graph as usual, but only passing nodes enter the resultsselective filters: the walk must visit most of the graph to collect k passing nodes
Predicate-aware graphwalk only (or mostly) through passing nodes, with extra links so they stay connected: ACORN, Qdrant's payload links, Filtered-DiskANNbuild cost and memory for the extra links

Why selective filters break graph walks, on Fig. 3's real graph: a walk that may only step on passing nodes finds them scattered into pieces with no links between them.

  1. The graph. Layer 0 of Fig. 3's HNSW graph: 240 passages and every link between them.
  2. A filter keeps a few. Passing nodes stay lit; failing ones fade, and with them every link that touches one. A random attribute is uncorrelated with the links, so the survivors fall apart into many small pieces: a walk that may only step on passing nodes cannot get from one to another. A filter on one collection is correlated with the links (similar passages are linked) and stays almost in one piece.
  3. In-graph filter: walk through the failures. hnswlib keeps every link and lets the walk pass through failing nodes, never returning them (the orange path joins two pieces through white failing nodes). Always connected, but most of the distances go to nodes it may not return.
  4. Two-hop links. ACORN's repair: from a passing node, also step to passing nodes two links away (green dashed). The pieces join up without visiting failing nodes; ACORN-1 builds the graph without neighbour pruning so that more such links exist.

hnswlib's in-graph filter is the same code path as deleted nodes: a node that fails is still expanded (its neighbours are explored) but never added to the results, and the stop rule waits for ef passing results. FAISS's HNSW with an IDSelector filters the same way but keeps its own stop rule (at most efSearch expansions), so it gives up earlier and returns fewer, sometimes wrong, results.

      What production systems do
      pgvector 0.8 keeps walking until enough rows pass (iterative index scans, measured on {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}, section 10); Qdrant plans per segment and uses payload links; Weaviate and Qdrant ship ACORN (versions in section 13). Multi-tenancy is this problem with a very selective, perfectly correlated filter: pre-filter small tenants, partition large ones (the filter becomes routing); {{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}} covers it as access control.
      The NeurIPS'23 filtered track (published)

      The NeurIPS'23 Big-ANN filtered track (YFCC 10M CLIP vectors, queries with one or two tags) was won by ParlayANN at 37,902 queries per second at recall@10 ≥ 0.9, more than 11 times the FAISS baseline, using per-tag indexes for common tags and plain lists for rare ones (arXiv 2409.17424, independent benchmark).
