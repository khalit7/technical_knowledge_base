Frontier: recall, speed and memory for every index measured

Every index family on this page, each swept over its query-time knob, timed on the same machine the same way: one CPU thread, one query at a time, three passes over the query set (median of each pass, median of the three). Up and right is better. The outlined points form the Pareto frontier: no other setting is both faster and more accurate. Lower the memory budget and watch which families survive.

What transfers, and what does not
Measured on an Apple M1 Pro on one thread, from Python (each call adds roughly 10 to 30 microseconds, which dominates the fastest settings), on a shared machine: the load average during each run is in the table. Transfers: the order of the families, the shape of each curve, the recall numbers (deterministic), the bytes. Does not transfer: absolute milliseconds (a server core, many threads, batching and SIMD width all change them), and the libraries' relative speed in their own servers (Qdrant, pgvector and others add their own overheads; the Search and vector databases page times pgvector inside PostgreSQL). Memory here counts what the index needs at query time; "+ rescore" rows include the float32 vectors kept for rescoring. hnswlib 0.8.0 has hand-written SIMD distance code only for x86 (SSE, AVX, AVX-512; hnswlib.h lines 11 to 20); on this ARM chip it falls back to a plain loop, which is why it ran 4 to 7 times slower than FAISS at the same recall here. A batched call took the same time per query, so it is not Python overhead: the gap is a platform effect, not a property of the algorithm (on x86 hnswlib uses its SIMD code; not measured here).
