13. Choosing an index

Start from the hard constraint, almost always memory, then from how the data changes, then tune on your own queries. The {{Frontier|#t-vixfront}} tab puts every measured setting on one recall, speed and memory chart.

Corrected from the old "Embeddings and vector search" page
  • "HNSW is the default in pgvector, Qdrant, Weaviate and Milvus": pgvector has no default index (you create HNSW or IVFFlat yourself; the Search and vector databases page), and Qdrant only builds its graph once a segment passes indexing_threshold (parent's Tool map).
  • "Below about 1M vectors, nothing matters much": exact search over 522,931 vectors of 384 dimensions took @@exact_quora_ms@@ ms per query on one core here, and an untuned index loses recall at any size (FAISS IVF at nprobe 1: @@ivf72_np1@@ on 5,183 vectors).
  • "The HNSW graph costs roughly M × 8 to M × 10 bytes per vector": from hnswlib's code it is 8M + 12 bytes per vector on layer 0 plus about (4M + 4)/(M − 1) for the upper layers, about 145 bytes at M = 16, checked against the file size in section 11. Consistent, now with its terms.
  • "ScaNN handled roughly twice the queries per second of the next-fastest of eleven libraries" (Google Research blog, July 2020): a vendor claim not re-checked here; this page's container run of ScaNN measured recall only (section 8).

Interview rehearsal: two design questions (optional)

Semantic search over 200 million passages, 1,024-d embeddings, 500 queries per second, p99 under 100 ms, per-customer filters, daily updates. Raw vectors: 200M × 4 KB = 819 GB, too much RAM for one node. Options: (1) int8 or RaBitQ codes in RAM (205 GB or about 27 GB) with HNSW or IVF, full vectors on SSD for rescoring the top 100; (2) a DiskANN-style SSD graph with PQ codes in RAM. Shard by customer where customers are large (the filter becomes routing), by hash otherwise, 4 to 8 shards plus replicas for QPS; scatter-gather and merge top k. Filters: pre-filter for small customers, a filter-aware graph for large ones. Updates: write to a small fresh in-memory index, merge into the main one nightly, tombstones for deletes, periodic rebuild. Measure recall against exact search on a sample daily, and answer quality on a labelled set after every change.

Your RAG answers got worse after switching to a faster index. How do you check whether the index is to blame? Run the same queries through exact search and compare top-k overlap (ANN recall) and the downstream metric; if ANN recall dropped below about 0.9 the index (or its default knob) is the cause; if not, look at chunking, the model, or filters.
