14. Common mistakes

Quoting latency or QPS without recall
Any index is fast at low recall. FAISS IVF at its default nprobe 1 answers SciFact in @@ivf_np1_ms@@ ms with recall @@ivf72_np1@@ (Frontier).
Leaving the query-time knob at its default
hnswlib's ef defaults to 10 (recall 0.876 on SciFact with bge-small), FAISS IVF's nprobe to 1 (0.42); LanceDB's default IVF-PQ without refinement gave 0.59 (parent's Tool map). Set ef or nprobe from a measured curve.
Benchmarking a "lite" or local mode
Qdrant's Python local mode and Milvus Lite scan every vector: recall 1.0, server speed unknown. A Qdrant server below indexing_threshold also has no graph (Tool map). Read back what index is actually being used.
Post-filtering a selective filter
With a 0.4% filter, 100 ANN results contained @@post_own_ret@@ matching rows on average (section 9). Pre-filter, or use a filter-aware search.
Training IVF or PQ on too little, or old, data
Lists become uneven and recall drifts as the collection grows into new topics (section 3). FAISS warns below 39 training points per centroid.
Using PQ or binary codes without rescoring
16-byte PQ alone: @@pq16_rec@@; with the best 100 rescored: @@pq16_rs_rec@@ (section 4). Keep the full vectors somewhere and rescore a short list.
M too small
At M = 4, @@m4_unreach@@ of 5,183 nodes were unreachable: those documents can never be returned (section 6).
Mixing metrics or forgetting to normalise
Inner product on unnormalised vectors favours long vectors; build the index with the metric the model was trained for, and normalise if you use inner product as cosine.
Deleting heavily from an HNSW index and never rebuilding
Recall holds, cost grows: @@del50_tomb_nd@@ against @@del50_reb_nd@@ distances per query with half the rows deleted (section 10).
Trusting a published trick without measuring it on your vectors
ScaNN's anisotropic loss gave no gain on these unit-length 1,024-d vectors (section 8); Vamana's α behaved differently in 1,024 dimensions than in 128 (section 7).

15. Interview questions

Why does exact search not scale, and when is it still right?
It reads N × d × 4 bytes per query and is memory-bound (about @@exact_gbps@@ GB/s per core here). Right for small sets, batched offline jobs (it becomes a matrix multiply), filtered subsets, and ground truth.
Explain IVF's nlist and nprobe and how you would set them.
nlist cells from k-means (about √N to start); nprobe nearest cells scanned per query. Distances ≈ nlist + nprobe · N/nlist. Sweep nprobe on real queries against exact search; pick the smallest that meets the recall target.
How does PQ compute a distance without decompressing?
The query builds an m × 256 table of sub-vector distances to each codebook centroid once; each candidate's score is the sum of m table entries chosen by its m code bytes (ADC).
What do M, efConstruction and ef control in HNSW?
M: links per node (2M on layer 0), graph quality and memory. efConstruction: candidate list while inserting, build quality and time. ef: candidate list at query time, the recall and latency dial.
Why does HNSW use a neighbour-selection heuristic?
Keeping only the M closest bunches links inside dense regions; the heuristic skips a candidate already reachable through a kept neighbour, preserving links between clusters. Measured: on the clustered four-corpus set, closest-M lost @@var_simple_gap@@ points of recall at ef 40.
What makes DiskANN work on SSD?
PQ codes in RAM steer the walk; each node's full vector and neighbour list sit together on disk, so one hop is one read, and the full vector re-scores for free; α > 1 keeps edges that cut the number of hops; beam search reads several nodes at once.
A filter keeps 0.5% of documents. What do you do?
Pre-filter with an ordinary index and search those rows exactly (here about @@pre_s005@@ distances), or use a filter-aware graph. Do not post-filter. If the filter is a tenant id, consider partitioning by tenant.
System design: semantic search over 200 million passages, 1,024-d embeddings, 500 queries per second, p99 under 100 ms, per-customer filters, daily updates.
Raw vectors: 200M × 4 KB = 819 GB, too much RAM for one node. Options: (1) int8 or RaBitQ codes in RAM (205 GB or about 27 GB) with HNSW or IVF, full vectors on SSD for rescoring the top 100; (2) DiskANN-style SSD graph with PQ codes in RAM. Shard by customer where customers are large (filter becomes routing), by hash otherwise, 4 to 8 shards plus replicas for QPS; scatter-gather and merge top k. Filters: pre-filter for small customers, filter-aware graph for large ones. Updates: write to a small fresh in-memory index, merge into the main one nightly, tombstones for deletes, periodic rebuild. Measure recall against exact search on a sample daily, and answer quality on a labelled set after every change.
Your RAG answers got worse after switching to a faster index. How do you check whether the index is to blame?
Run the same queries through exact search and compare top-k overlap (ANN recall) and the downstream metric; if ANN recall dropped below about 0.9 the index (or its default knob) is the cause; if not, look at chunking, the model, or filters.
