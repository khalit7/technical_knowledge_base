Embedding models: training, choosing and fine-tuning

How a text becomes one vector (a transformer, a pooling step and a normalisation, read in the sentence-transformers code), how contrastive training shapes the space (in-batch negatives, temperature, hard and false negatives, batch size), what instructions, prefixes and truncation do, why the MTEB rank does not carry over to your data, and a protocol to choose and fine-tune a model on a few hundred labelled queries with confidence intervals. 0. In one screen

An embedding model turns a piece of text into one fixed-length list of numbers (a vector, here 384 to 1,024 numbers), trained so that a question and the passage that answers it end up pointing in nearly the same direction. Retrieval then becomes geometry: embed every passage once, embed the question at search time, return the passages whose vectors are closest. This page is about the model that makes those vectors: what is inside it, how it is trained, how to choose one and how to fine-tune one, all measured on the topic's running example (SciFact: 5,183 scientific abstracts and 300 test claims; NFCorpus: 3,633 medical documents and 323 test queries).

text→tokens→transformer: one vector per token→pooling: one vector→normalise to length 1→compare by cosine

Seven ideas that carry the page

1. A transformer plus two small steps

Every model here is a transformer whose per-token outputs are pooled (the first token, the mean, or the last token) and normalised. Rebuilt by hand from the sentence-transformers 6.1.0 code, the vectors match encode() exactly (largest difference 0.0) for all five models (section 1).

2. Training is "pick your positive out of a line-up"

The InfoNCE loss is a softmax over cosines divided by a temperature (0.05 by default). This page's training code gives the same loss as sentence-transformers' MultipleNegativesRankingLoss to 2e-07 (section 4).

3. The hardest negatives are often not negatives

For 33.8% of SciFact's training pairs, both bge-small and Qwen3-Embedding rank some unlabelled abstract above the labelled one; the 95%-of-positive filter discards 42.1% of the top-10 mined candidates (section 5).

4. A tiny fine-tune, with its noise floor

pending run Fine-tuning bge-small on SciFact's train pairs with four kinds of negatives, three batch sizes and three seeds each: script written and tested at toy size on CPU, GPU run waiting for a slot (section 6, Training lab tab).

5. An instruction matters; its wording much less

Qwen3-Embedding without any instruction loses 6.6 nDCG@10 points on NFCorpus and 2.1 on SciFact; swapping the task wording for a generic one moves less than a point. bge-small's documented prefix helps on one set and hurts on the other, both within noise (section 7).

6. The leaderboard average does not pick your model

Over 149 models in the MTEB results repository, the 10 best by the MTEB(eng, v2) average and the 10 best on SciFact share 2 models; Qwen3-Embedding-0.6B is 13th by the average and 73th on SciFact (section 11).

7. A few hundred labelled queries decide it, with paired statistics

On SciFact, 99.95% of random 100-query subsets pick the same winner as all 300; per-model 95% intervals are about ±0.05 wide, but the paired difference between two models is far tighter (section 12, Model chooser tab).

1. What an embedding model is: a transformer, a pooling step, a normalisation

The problem. A transformer (the same architecture as a language model) reads a text and returns one vector per token: a 12-token claim gives 12 vectors. A vector database wants one vector per text, of the same length for every text, so that any two texts can be compared with one dot product. Two small steps after the transformer do that.

  • Tokenise: the text becomes token ids (WordPiece pieces such as cc ##l ##19 for BERT-style models; byte-level pieces for Qwen3). The model's tokenizer also adds special tokens: [CLS] at the start and [SEP] at the end for BERT, an end-of-text token for Qwen3. See Tokenizers.
  • Transformer: every layer lets each token's vector look at the others (attention). After the last layer, each token's vector describes that token in context. An encoder (BERT, MiniLM, ModernBERT) lets every token see every other; a decoder (Qwen3) lets a token see only the tokens before it.
  • Pooling: collapse the per-token vectors into one. Three choices are in use: CLS (keep the first token's vector; bge-small, gte-modernbert), mean (average the real tokens, ignoring padding; all-MiniLM-L6, e5-small-v2), last token (keep the final token's vector; Qwen3-Embedding, because in a decoder only the last token has seen the whole text).
  • Normalise: divide the vector by its length, so it has length 1. Then the dot product of two vectors is their cosine, and every vector index can use the fast inner product. gte-modernbert ships without this step (section 3).

Which pooling a model uses is not a choice you make at search time: it is fixed by how it was trained, and written in its 1_Pooling/config.json and modules.json. Read them before you write your own inference code.

2. Bi-encoder or cross-encoder: where the query meets the document


The problem. Relevance is a property of a pair (query, document), but a corpus has millions of documents and a query arrives in real time. Two designs answer differently.




Bi-encoder (this page)
Query and document are encoded separately by the same model. Every document vector is computed once, at indexing time; a query costs one model pass plus a vector search. The price: the two texts never see each other, so all the meaning must squeeze into one vector each.


Cross-encoder (a reranker)
Query and document are concatenated and read together: every query token attends to every document token, and the model outputs one score. More accurate, but nothing can be precomputed: one model pass per (query, document) pair. Owned by Rerankers and late interaction.

3. Similarity and normalisation


Three ways to compare two vectors q and d: the dot product Σ qidi (larger is closer, grows with both lengths), the cosine, the dot product divided by both lengths (only the angle counts, from −1 to 1), and the L2 distance |q − d| (smaller is closer). For vectors of length 1 they rank documents identically, because |q − d|2 = 2 − 2 cos(q, d). The parent's Vector search lab shows this on real vectors: gte-modernbert has no Normalize step, and ranking its raw vectors by dot product drops SciFact nDCG@10 from 0.767 to 0.740, while L2 and cosine agree. measured here (parent page)


Worked example (from the old page, arithmetic re-checked)
Query q = (0.6, 0.8), length 1. Documents d1 = (1, 0), d2 = (0, 1), d3 = (2, 0), which points the same way as d1 but is twice as long. Dot products 0.6, 0.8, 1.2: d3 first. Cosines 0.6, 0.8, 0.6: d2 first, d1 and d3 tied. L2 distances 0.894, 0.632, 1.612: d2 first. Check: 2 − 2 × 0.8 = 0.4 = 0.6322. The dot product put the longest vector first although it points further from the query than d2.


Rule. Use the similarity the model was trained with. For a model trained with cosine (all five here), normalise once at indexing time and use the inner product; never mix normalised documents with an unnormalised query. Hosted APIs usually return normalised vectors: OpenAI's embeddings are "normalized to length 1" (its embeddings guide, read 2026-10-14) published, vendor.







4. How the space is trained: the contrastive loss


The problem. A pretrained transformer's hidden states are not a retrieval space: next-token or masked-token training never asked a claim and its evidence to point the same way. The geometry has to be taught, with pairs.


The data: pairs. (query, positive) pairs: a question and its answer passage, a title and its body, a claim and its evidence, a search and the page clicked. SciFact's train split gives 919 such pairs from 809 claims. Production models use hundreds of millions: Qwen3-Embedding reports about 150 million synthetic pairs for a weakly supervised first stage, then about 12 million selected synthetic pairs plus labelled data for supervised fine-tuning, then model merging (Qwen3 Embedding report, arXiv 2506.05176, sections 3.2 and 3.3) published, vendor.


Li = − log   exp(si,i / τ) / Σj exp(si,j / τ)


si,j
cosine between query i and candidate document j; candidate i is query i's positive


j
runs over the line-up: every positive in the batch (the other queries' positives are in-batch negatives) and every mined hard negative in the batch


τ
the temperature; sentence-transformers writes it as a scale 1/τ = 20, so τ = 0.05 by default


This is InfoNCE (van den Oord et al. 2018, arXiv 1807.03748): a cross-entropy whose "classes" are the candidates (its reading as a bound on mutual information is on Information theory for ML; CLIP uses the same loss on image-text pairs, see the CLIP paper page). It raises the positive's cosine and lowers every negative's, each in proportion to its softmax weight. In-batch negatives are free because the batch's documents are embedded anyway (Karpukhin et al. 2020, DPR, arXiv 2004.04906). The temperature sets how sharp that weighting is: at τ = 0.05 a cosine gap of 0.05 is a factor e ≈ 2.7 in weight, so nearly all the push lands on the one or two closest negatives.

5. Hard negatives and false negatives


Hard negatives teach fine distinctions: a random abstract about cardiology is trivially wrong for a claim about a chemokine; an abstract about the same chemokine that does not support the claim is what the model must learn to rank second. They are mined by running a retriever over the corpus and taking high-ranked documents that are not labelled relevant. Two miners here, on the 919 SciFact train pairs (scripts/e_mine.py): BM25 (word overlap) and bge-small (the model being trained). Their top-10 pools overlap by only 33% on average: they find different negatives. measured here


False negatives are the catch: "not labelled relevant" is not "irrelevant". SciFact's annotators labelled the abstracts cited for each claim, not every abstract that bears on it. How often does a retriever rank an unlabelled abstract above the labelled one?

Per claim with its first labelled abstract (the parent's way of counting), the same check gives 38.8% for bge-small and 38.4% for Qwen3-Embedding, equal to the parent's 38.8% and 38.4%. measured here


Two different models agreeing that an unlabelled abstract beats the labelled one is a strong hint that the label is missing. The pairs where both models put the same unlabelled abstract first (154 of them) read like this:




Filtering them out. NV-Retriever (Moreira et al. 2024, arXiv 2407.15831) proposed "positive-aware" mining: use the positive's own score as an anchor and drop candidates scoring above 95% of it ("TopK-PercPos"), which they found best among their settings published. sentence-transformers' mine_hard_negatives(relative_margin=0.05) is the same rule. Qwen3-Embedding's loss instead masks any negative scoring more than 0.1 above the positive (report, section 3.1). On SciFact train with bge-small scores the 95% filter removes 42.1% of the top-10 dense candidates; after filtering, the first surviving candidate sits at rank 3 (median) of the dense list, and 65 pairs have no candidate left in the top 200, so they fall back to a random abstract. measured here


A sibling already met this
On Rerankers and late interaction, fine-tuning the MS MARCO cross-encoder on the same 809 train claims, random negatives beat BM25-mined hard negatives (rerank nDCG@10 0.734 against 0.726 on the BM25 list, 2 seeds each), and the page named sparse-label false negatives as the likely cause without testing it. Section 6 tests the same question on a bi-encoder, with a false-negative filter as a third arm.

7. Instructions and prefixes: asymmetric queries


The problem. Queries are short and phrased as questions or claims; documents are long and phrased as statements. Many models are trained with a marker that tells them which side they are encoding, and some with a task description:


    

  • E5-style prefixes: "query: " before queries and "passage: " before documents. The e5-small-v2 card: "Yes, this is how the model is trained, otherwise you will see a performance degradation" (FAQ, card at revision ffb93f3b, read 2026-10-14) published, vendor.
    • 

  • bge: a query-side instruction "Represent this sentence for searching relevant passages: ", nothing on documents.
    • 

  • Qwen3-Embedding: "Instruct: <task>\nQuery:" before the query, nothing on documents; the card says instructions "typically" improve results by 1% to 5% published, vendor.
    • 

  • all-MiniLM-L6 and gte-modernbert: no prompts.
    •

What it says. bge-small: without its prefix SciFact moves from 0.713 to 0.720 (paired interval of the difference -0.006 to +0.021) and NFCorpus from 0.343 to 0.337 (-0.013 to +0.002): opposite directions, both inside their intervals, so on these sets the prefix is a coin toss, not the rule its card implies. Qwen3-Embedding: dropping the instruction costs 2.1 points on SciFact and 6.6 on NFCorpus, clear of the noise; but the wording barely matters: the card's generic web-search instruction scores 0.702 against the task instruction's 0.700 on SciFact (-0.011 to +0.014) and 0.356 against 0.363 on NFCorpus (-0.013 to -0.000), and the other set's instruction scores 0.368 on NFCorpus (-0.001 to +0.011). A decoder embedder trained with instructions needs to be told "this is a query"; which task description it gets matters much less here. pending run e5-small-v2 with "query: " and "passage: " on both, either or neither side needs its corpus re-embedded twice per set (e_prefix.py e5).


The rule
Use the model's documented prompt as the default, then measure without it and with one or two task wordings on your own labelled queries: it costs one re-encoding of the queries, not of the corpus. The document side is different: a document prefix changes every stored vector, so changing it means re-embedding the corpus, and a query encoded with a mismatched setting silently loses quality.







8. Smaller vectors: Matryoshka training and quantization


Two knobs shrink a stored vector: keep fewer numbers, or fewer bits per number. The parent's Vector search lab measures both on Qwen3-Embedding over SciFact, with an explorer (dimensions × float32, int8, binary × rescoring); this page does not rebuild it. The training side, which is this page's subject:


LMRL = Σm ∈ M cm  L(v1:m)


M
the nested sizes, for example {32, 64, 128, 256, 512, 1024}
v1:m
the first m numbers of the embedding, re-normalised
L
the contrastive loss of section 4, applied to the truncated vector

Matryoshka Representation Learning (Kusupati et al. 2022, arXiv 2205.13147) adds the loss on every prefix, so the front of the vector carries the most. sentence-transformers wraps any loss this way (MatryoshkaLoss). The parent's measurements show what it buys measured here (parent page): Qwen3-Embedding (trained with it) keeps 98% of its nDCG@10 at half its dimensions and 95% at a quarter; bge-small (trained without) keeps 94% and 81%; gte-modernbert cut to 384 dimensions (0.726) still beats Qwen3-Embedding at 1,024 (0.700). Binary codes of all 1,024 dimensions with the top 100 rescored in float32 keep all of it (0.700). Index-side compression (product quantization, RaBitQ) is on Vector indexes from the inside.


The old page's figure "up to 14x smaller embeddings at the same ImageNet accuracy" is the MRL paper's ImageNet-1K classification result; it says nothing about retrieval on your corpus. A truncation and quantization explorer was considered for this page and rejected: it would repeat the parent's, on the same vectors.







9. Long inputs and truncation


The problem. Every model reads at most a fixed number of tokens (its maximum sequence length) and silently drops the rest: all-MiniLM-L6 reads 256 tokens by default, bge-small and e5-small-v2 512 (the e5 card: "Long texts will be truncated to at most 512 tokens"), gte-modernbert 8,192 (run here at 1,024), Qwen3-Embedding 32K (run here at 1,024). Nothing warns you: the vector of a truncated text is still a vector.

Right: for every SciFact evidence sentence of a train or dev claim (from the original release, which marks evidence sentences), the BERT-token position where it ends. measured here






The point the right panel makes: in a scientific abstract the evidence is late (conclusions come last). 52.8% of evidence sentences end after BERT token 256, and for 38.7% of (claim, abstract) pairs even the first evidence sentence ends after token 256, so all-MiniLM-L6 at its default limit never reads the sentence that makes the abstract relevant. It still retrieves many of them, from the topic words in the title and opening. At 512 tokens, 12.1% of evidence sentences are cut.

The same problem in chunked pipelines is measured by The retrieval pipeline on QASPER papers: LangChain's default 4,000-character chunks are 782 BERT tokens at the median, so all-MiniLM-L6 reads 33.3% of their tokens and bge-small 65.1%; even 256-Qwen3-token chunks exceed MiniLM's 256 BERT tokens 16.9% of the time, because the two tokenizers count differently. measured here (sibling page) The fix is to size chunks in the embedding model's tokens, not in characters or in the generator's tokens.


Long-context embedders (gte-modernbert, Qwen3-Embedding, modernbert-embed at 8K to 32K) can embed a whole paper, but one vector for 8,000 tokens averages many topics; the usual design still chunks, and late chunking (embed the long text once, pool per chunk) is measured on the pipeline page.






10. Domain shift: the same models on different data


The problem. A model's quality is a property of (model, data), not of the model. The running example has three labelled sets in different domains: SciFact (scientific claims against abstracts), NFCorpus (consumer health questions against medical documents, many relevant documents per query) and the multi-hop set (200 HotpotQA questions against Wikipedia paragraphs).

A shift inside one dataset

11. MTEB: what it measures, and why its rank does not transfer


MTEB (the Massive Text Embedding Benchmark) scores a model on many tasks with one fixed protocol, and its leaderboard ranks models by the mean. The current English benchmark, MTEB(eng, v2) (introduced with MMTEB, Enevoldsen et al. 2025, arXiv 2502.13595), has 41 tasks: 10 retrieval, 9 semantic similarity (STS), 8 classification, 8 clustering, 3 pair classification, 2 reranking, 1 summarization. Each task type has its own score (retrieval and reranking: nDCG@10 or MAP; classification: accuracy of a logistic regression on the vectors; clustering: V-measure; semantic similarity: Spearman correlation of cosines with human scores; pair classification: average precision). Its description in mteb 2.24.13: "prioritizing tasks not commonly used for fine-tuning to give a more realistic estimate of generalization performance". SciFact and NFCorpus are not among its 10 retrieval tasks.

12. Choosing a model on your own data: the protocol


    

  1. Shortlist 3 to 6 models: licence, languages, maximum length against your chunk size, vector size against your memory, a hosted or local budget, and the MTEB retrieval tasks nearest your domain. The current open and hosted models (OpenAI text-embedding-3, Gemini embedding, Voyage 4, Cohere embed v5, Jina v5, Qwen3-Embedding, bge, gte, e5, MiniLM), with their status, licences and context lengths as read in October 2026, are listed on the parent's Tool map tab; this page does not repeat them.
    2. 

  2. Label a few hundred real queries (from logs if you have them) with their relevant chunks; keep 20 to 30% aside as a confirmation set. Same chunking for every model.
    3. 

  3. Run each model with its documented prompt and without; exact search (no index, so the index does not blur the comparison); BM25 and a hybrid as references.
    4. 

  4. Compare paired: per-query nDCG@10 (or recall@k at your k), differences between models on the same queries, bootstrap interval of the difference. Treat models within the interval as tied and break ties on cost (bytes per vector, query latency, indexing time, licence).
    5. 

  5. Confirm the winner on the held-out queries, then on a sample of production traffic after launch.
    6.

13. Fine-tuning for real: when it pays and how


When. Fine-tune after the protocol above says the best off-the-shelf model is not good enough, and when you have a domain the general models have not seen (internal jargon, product codes, a query style such as error messages), at least a few thousand (query, positive) pairs or a way to make them (a language model writing questions for your passages is the common route; Qwen3-Embedding's report describes synthetic pairs at scale), and a labelled evaluation set that is not used for training.


How, with sentence-transformers 6.1.0 (the tools this page's run mirrors): mine_hard_negatives(..., relative_margin=0.05) for positive-aware mining; MultipleNegativesRankingLoss (or CachedMultipleNegativesRankingLoss for large batches on a small GPU); GISTEmbedLoss, which uses a second "guide" model to mask in-batch negatives the guide scores above the positive; MatryoshkaLoss around any of them if you will truncate; a no-duplicates batch sampler; evaluate on held-out queries every epoch. The core of this page's loop, which equals the library's loss (section 4):




The costs people forget. A new model means re-embedding the whole corpus (bge-small: 36 s for SciFact here; Qwen3-Embedding-0.6B: 816 s), and vectors from the old and new model cannot share an index; a running system needs a second index and a switch-over (RAG in production measures what mixing them does: nDCG@10 0.379 at 50% re-embedded against 0.713 clean). Watch the other domains too: fine-tuning can forget (the NFCorpus panel of section 6).







14. Common mistakes


Writing your own inference with the wrong pooling
A mean-pooled model read with CLS still returns a vector; only the quality drops. Read 1_Pooling/config.json, or load through sentence-transformers. Section 1.


Mixing normalised and unnormalised vectors, or the wrong metric
gte-modernbert's raw dot product loses 0.027 nDCG@10 on SciFact. Normalise once, at indexing, and use the inner product. Section 3.


Forgetting the query prompt, or adding a document prefix the model was not trained with
Qwen3-Embedding without its instruction loses 6.6 points on NFCorpus. But do not assume the documented prompt is best: measure both. Section 7.


Chunking in characters for a 256-token model
The model reads the first 256 tokens and drops the rest silently. Size chunks in the embedding model's tokens. Section 9.


Treating every unlabelled document as a negative
On SciFact train, a third of pairs have an unlabelled abstract that two different models rank above the labelled one. Filter mined negatives against the positive's score, or use a guide model. Section 5.


Letting a shared positive into a batch twice
Two claims with the same abstract in one batch make that abstract a negative for one of them. Mask labelled columns or sample without duplicates. Section 4.


Picking the model by leaderboard rank
Near the top the order is noise for your set. Shortlist from MTEB, decide on your queries with paired intervals. Sections 11 and 12.


Reporting one fine-tuning run
Seeds move results by about as much as many of the effects people report. Run three seeds and show the spread. Section 6.


Truncating a vector the model was not trained to truncate
bge-small keeps 81% of its quality at a quarter of its dimensions; Qwen3-Embedding (Matryoshka-trained) 95%. Re-normalise after cutting. Section 8.







15. Interview questions


Why is a bi-encoder used for first-stage retrieval and a cross-encoder for reranking?
A bi-encoder's document vectors are precomputed, so a query costs one encode plus a vector search over millions; a cross-encoder must run once per (query, document) pair, 21.9 s for 5,183 abstracts with a small one here. So: bi-encoder to get tens of candidates, cross-encoder to order them.


What does the temperature in InfoNCE do?
It scales cosines before the softmax. Low τ (0.05) concentrates the gradient on the closest negatives (hard-negative focus, but also on false negatives); high τ spreads it evenly. Too low makes training unstable; it is sometimes learned.


Why do contrastive embedders want large batches, and how do you get them on one GPU?
More in-batch negatives, so the line-up is harder and the gradient informative. Gradient caching computes the loss on all embeddings without storing activations, then re-encodes in chunks; the result equals the large-batch loss at the memory of a chunk.


What is a false negative in hard-negative mining, and how do you reduce it?
A mined "negative" that is actually relevant but unlabelled. Reduce it with positive-aware filtering (drop candidates above 95% of the positive's score), skipping the very top ranks, a stronger guide model (GISTEmbed), or denoising with a cross-encoder.


Your team picked the MTEB number-one model and retrieval got worse. Why could that happen?
The mean mixes non-retrieval tasks; your domain differs; near the top the order is noise (a coin flip for models within one point here); the model may have trained on the benchmark's data; or it was run without its query instruction or with a different maximum length.


How would you decide between two embedding models with 300 labelled queries?
Per-query metric for both on the same queries, paired bootstrap of the difference; if the interval covers 0, they are tied and cost decides. Check the decision on held-out queries.


System design: a company wants to switch its 50-million-chunk index to a better embedding model without downtime. Plan it.
Evaluate offline on a labelled set first (paired, with intervals). Then build a second index: re-embed all chunks with the new model in a batch job (throughput-bound; cost = tokens × price or GPU-hours), while new and updated documents are written to both indexes. Shadow-query the new index and compare results and latency; switch reads with a flag per tenant or a percentage; keep the old index until the new one has been stable; then delete. Never mix vectors of two models in one index: a query vector from one model is meaningless against the other's documents (the RAG in production page measures the damage). Budget memory for two indexes during the switch, or use Matryoshka truncation or quantization to fit.


System design: retrieval over a company's internal documents is poor on product codes and jargon. What do you try, in what order?
Measure first (golden set from search logs). Add BM25 and hybrid fusion (exact terms are BM25's strength); check chunking and the query prompt; try two or three stronger off-the-shelf models with the protocol of section 12; add a reranker; only then fine-tune on mined pairs from logs or LLM-generated questions, with positive-aware hard negatives, several seeds, and a held-out set, and check general-domain queries for forgetting.
