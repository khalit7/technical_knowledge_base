5. OCR: route only the pages that need it

Scans, photos and some exports have no usable text layer (none, an old invisible OCR layer, or glyphs without a Unicode mapping). Optical character recognition (OCR) reads characters from pixels; it replaces exact text with a guess and costs seconds per page, so it is routed per page, never run on everything.

Check the text layer first; OCR only what fails the check

The check: characters per page area, share of replacement or private-use characters, share of dictionary words, a single full-page image. Times on this CPU: Tesseract at 300 dpi took 2.18 s per page on the QASPER papers and 3.15 s on the olmOCR sample; VLM OCR was not run here.

Classic engines. Tesseract (5.4.1, Apache 2.0) binarises the page, finds lines with its page-layout analysis (--psm 3, the default, assumes a full page of any layout) and since version 4 reads each line with an LSTM trained per language (documentation); it knows nothing of tables or reading order beyond its block finder. Layout-aware parsers OCR only image-text regions or broken pages: Docling through whichever engine its OcrAutoOptions finds (pipeline_options.py line 312; here RapidOCR, PP-OCRv6 small), Unstructured hi_res through Tesseract, MinerU and Marker through their own models.

VLM OCR. Since 2025 the strongest systems on olmOCR-bench are vision-language models that read a page image and write Markdown, tables as HTML and maths as LaTeX: olmOCR 2 (7B), PaddleOCR-VL, Chandra, dots.ocr, DeepSeek-OCR. They handle reading order, tables and handwriting jointly, need a GPU and a few seconds per page, and can hallucinate text that is not on the page or repeat a line forever (olmOCR-bench's baseline test checks for runaway repetition). None ran here (reference pipelines target NVIDIA GPUs with vLLM; published scores in section 4). How to check any OCR: character error rate against a hand transcription of a sample.

6. Tables: structure is the content

A number means nothing until you know its row and column. A text extractor emits cells as a stream (by row, by column, headers scattered), and retrieval fails twice: the chunk has no words matching the question, and if retrieved the generator cannot tell which number answers it.

How much it matters. In QASPER validation (281 papers, 1,005 questions), a table or figure is evidence for 164 (17.4%) of the 945 answerable questions, and for 35 of them a table or figure is the only evidence (30 tables, 5 figures; src/scripts/qasper_stats.py, FLOAT SELECTED entries). The root's set keeps only questions with text evidence, so these never reach its recall numbers: an ingestion choice hidden by an evaluation choice.

Extraction in four steps: detect the region (a Table box, or ruling lines); recognise structure, rows, columns, spanning and header cells (pdfplumber, Camelot and pymupdf4llm use ruling lines or whitespace; Docling's TableFormer predicts structure from the image, Nassar et al., 2022, then matches cells to the PDF's own text, do_cell_matching=True by default in docling 2.138.0); fill cells from the text layer or OCR; serialise as HTML (keeps spans) or Markdown (cannot express a spanning cell, so merged headers repeat or vanish).

Numbers kept under the right headers, every parser

Table 1 of arXiv 1909.00175 v1 (Zou and Lu, 2019), page 4: 15 rows, 13 columns, three header rows with spanning cells; ground truth from the paper's LaTeX source. Pick a parser, then switch views. Apple M1 Pro (CPU), default settings (Marker without OCR), 2026-10-14; one table shows kinds of failure, not a ranking.

  • Plain-text extractors kept the numbers, lost the table: pypdf one line per row with the headers as loose words; pdftotext each row cut in halves; PyMuPDF one cell per line; pdfminer.six and Unstructured fast column by column. Nothing says that 92.19 is homographic detection F1.
  • Docling kept every number under the right headers (100%, answer cells in place), merging the three header rows into one ("Homographic - Detection - F1"), already a row serialisation.
  • Other table tools: body right, headers wrong. MinerU (basic and flash) and pymupdf4llm put every number in the right cell (adjacency F1 0.93 to 0.99) but split header words ("Detectio" / "nF 1"), so only 0 to 18% of numbers sit under all three headers. Marker split names across columns ("Pramanick | and | Das"); Unstructured hi_res OCRed the image: "F1" became "Fi", "89.19" became "89,19", a header row lost.
How the table was scored

Adjacency F1: pairs of horizontally or vertically adjacent non-empty cells where at least one is a number, compared as text with the ground truth (the relation idea of the ICDAR 2013 table competition, restricted to the body so that merging the three header rows into one, as Docling does, is not penalised). Header association: the share of the table's numbers found in the right row whose column header text contains all three ground-truth header words; it was added after the first scoring, because plain adjacency F1 ranked MinerU above Docling although MinerU's headers were split mid-word. A parser that emits no table has no grid, so neither score applies; "cells whose text appears" still counts a number found anywhere. Ground truth: the tabular in the paper's pun.tex (lines 244 to 277 of the arXiv source, kept in src/inputs/). Script: src/scripts/table_score.py.

Making a table retrievable: keep it whole with its caption, or split by rows with the header repeated (a chunker that cuts a Markdown table mid-way leaves rows without headers); row serialisation ("Model: BERT-base; Dataset: SQuAD; F1: 88.5", values illustrative) gives each value its headers in words BM25 and an embedder can match; or embed a model-written summary and pass the full table to the generator. How to check: TEDS (tree-edit distance between HTML trees, Zhong et al., 2020), the adjacency F1 of the ICDAR 2013 competition, or olmOCR-bench's single facts ("a cell reads 4.5% and the cell above it reads 2.4%", its README's example).
