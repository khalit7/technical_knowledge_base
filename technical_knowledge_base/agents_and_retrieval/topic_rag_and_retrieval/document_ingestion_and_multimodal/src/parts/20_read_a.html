Ingestion in one picture

The idea in one sentenceA PDF stores glyphs at coordinates, not paragraphs, so every parser reconstructs reading order, tables and structure (by rules, by a layout model, by OCR, or not at all when the page image itself is embedded), and retrieval can only find what that reconstruction kept.

1. What a PDF page actually contains

A PDF is a page description: drawing instructions that put glyphs at coordinates so the page looks right (ISO 32000-2:2020, PDF 2.0; overview). Paragraphs, columns, tables and captions are not stored; every parser's output is rebuilt from those instructions, or from pixels. Four facts cause most ingestion bugs:

  • Text is positioned, not flowing. In each page's content stream, Tm and Td move a text cursor and Tj or TJ draw glyphs there (section 9.4); nothing marks a line continuing or a second column, and spaces are often only a gap the parser must notice.
  • Stream order is the producer's order: a typesetter may draw the left column, the right, then the header and footnotes, or a table cell by cell; a Word export draws text boxes in creation order. An extractor that follows the stream inherits it.
  • Glyphs are font codes, not letters: they become Unicode only through the font's encoding or a ToUnicode map (section 9.10), and a subset font without one decodes to garbage although the page looks perfect. Ligatures (one glyph for "fi", U+FB01) and line-end hyphens add damage.
  • A scan is a picture with no text, unless an earlier OCR run added an invisible layer (text render mode 3) of whatever quality that OCR had.

A structure tree (Tagged PDF, section 14.8, required by accessibility rules such as PDF/UA, ISO 14289) does record paragraphs, headings, tables and reading order; use it when present and correct. None of the 38 arXiv PDF files downloaded for this page (24 papers, every version) has one (no StructTreeRoot, checked with PyMuPDF).

  1. The text layer. The 90 text lines PyMuPDF 1.28.2 reads on page 1 of arXiv 1909.00175 (3,701 characters in 5 fonts, 4 ligature glyphs) lift off the page image, each at its own coordinates.
  2. Content-stream order. The order the producer (here pdfTeX) drew the lines. On this LaTeX page it is close to reading order, except the rotated arXiv stamp in the left margin, drawn last.
  3. pdfplumber. extract_text() clusters characters into lines by vertical position across the whole page width, so a line of the left column and the line beside it in the right column become one: it merges 34 of its 60 lines across the gutter. Its default 3-point x tolerance also drops many spaces on this page.
  4. Docling. A layout model found the two columns, so the left column is read top to bottom, then the right; the arXiv stamp is classified as page furniture and dropped.

2. Rule-based extractors: geometry and thresholds

A rule-based extractor rebuilds words, lines and blocks from glyph coordinates with no learned model. The steps are the same everywhere; only the thresholds and the final sort differ.

The tools differ mainly in the last step: pypdf (6.20.1) keeps content-stream order; PyMuPDF (1.28.2) too, unless sort=True sorts blocks by top then left (recipes); pdfplumber (0.11.10) clusters characters into lines (x_tolerance 3 points) and reads them across the full width; pdftotext (poppler 26.02) detects columns; pymupdf4llm (1.28.2) adds headings by font size, tables by ruling lines, Markdown, and here called RapidOCR on pages it judged to be images. Milliseconds per page and no model: the right first stage for clean single-column files; columns, headers, footnotes, tables and scans break the rules.

class LAParams:
    line_overlap = 0.5  # overlap, relative to the smaller char height, to share a line
    char_margin  = 2.0  # chars closer than 2 char widths join the same line
    line_margin  = 0.5  # lines closer than 0.5 line heights join the same box
    word_margin  = 0.1  # a gap over 0.1 char widths inserts a space
    boxes_flow   = 0.5  # -1: order boxes by x only ... +1: by y only; None: no grouping
