1. What a PDF page actually contains

The problem. A retrieval system needs text in reading order, split into paragraphs, with headings, tables and captions marked. A PDF stores none of that. It is a page description: a list of drawing instructions that put glyphs (the shapes of characters) at coordinates, so that the page looks right on screen and on paper (ISO 32000-2:2020, the PDF 2.0 standard; overview; section numbers below are the standard's). Everything a parser returns is a guess reconstructed from those instructions, or from pixels.

Four facts that cause most ingestion bugs

  • Text is positioned, not flowing. Each page has a content stream: operators such as Tm and Td move a text cursor and Tj or TJ draw a run of glyphs there (ISO 32000 section 9.4). Nothing says "this run continues the previous line" or "this is the second column". Spaces between words are often not characters at all, only a gap the parser must notice.
  • The stream order is the producer's order, not the reader's. A typesetter may draw the left column, then the right, then the running header, then the footnotes, or draw a table cell by cell; a Word export may draw text boxes in the order they were created. An extractor that follows the stream inherits that order.
  • Glyphs are codes in a font, not letters. A glyph becomes Unicode only through the font's encoding or a ToUnicode map (ISO 32000 section 9.10). If a producer embeds a subset font without one, the text layer decodes to garbage even though the page looks perfect. Typesetters also draw ligatures, one glyph for "fi" (U+FB01), and break words at line ends with a hyphen.
  • A scan is a picture. A scanned page is one image per page with no text at all, unless an earlier OCR run added an invisible text layer (text render mode 3) of whatever quality that OCR had.

Some PDFs carry a structure tree (Tagged PDF, ISO 32000 section 14.8) that does record paragraphs, headings, tables and reading order, because accessibility rules such as PDF/UA (ISO 14289) require it. When it is present and correct, use it. None of the 38 arXiv PDF files downloaded for this page (24 papers, every version) has one (no StructTreeRoot in the catalogue, checked with PyMuPDF), and a plain scan has none to give, which is why the rest of this page exists.

Try: predict first: which of the three readers will produce lines that run across both columns? Then play each. Watch the gutter-crossing counter and where the arXiv stamp in the left margin ends up.
