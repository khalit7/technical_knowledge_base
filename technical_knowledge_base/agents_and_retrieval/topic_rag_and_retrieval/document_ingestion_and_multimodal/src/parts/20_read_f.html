5. Tables: structure is the content

The problem. A table's meaning is in its grid: "0.84" means nothing until you know it sits in the row "BERT-base" and the column "F1 (test)" (an illustration; the real table below makes the same point). A text extractor emits the cells as a stream of numbers, usually row by row but sometimes column by column or with merged header cells scattered, so the link between a value and its headers is lost. Retrieval then fails twice: the chunk holding the numbers has no words that match the question, and if it is retrieved anyway the generator cannot tell which number answers it.

How much it matters on the running example. In QASPER validation (the topic's long-document set: 281 NLP papers, 1,005 questions), annotators marked a table or figure as evidence for 164 (17.4%) of the 945 answerable questions, and for 35 of them a table or figure is the only evidence (30 tables, 5 figures; counted by src/scripts/qasper_stats.py from the FLOAT SELECTED evidence entries). The root's long-document set keeps only questions with text evidence, so these questions never appear in its recall numbers: an ingestion choice hidden by an evaluation choice.

How table extraction works

  1. Detection: find the table's region on the page (a layout model's "Table" class, or ruling lines).
  2. Structure recognition: recover rows, columns, spanning cells and header cells. Rule-based tools (pdfplumber, Camelot, pymupdf4llm) use ruling lines or whitespace alignment; model-based ones predict the structure from the image: Docling's TableFormer predicts the logical row and column structure and header cells from the table image (Nassar et al., 2022), then matches the predicted cells to the PDF's own text so the cell contents are exact (do_cell_matching=True by default in docling 2.138.0).
  3. Cell content: from the text layer for born-digital PDFs, from OCR for scans.
  4. Serialisation: write the grid out as HTML (keeps row and column spans) or Markdown (cannot express a spanning cell, so merged headers are repeated or lost).

Making a table retrievable

  • Keep the table whole in one chunk with its caption, or split it by rows and repeat the header row in every piece. A chunker that cuts a Markdown table in the middle produces rows with no headers.
  • Row serialisation (format only, values illustrative: "Model: BERT-base; Dataset: SQuAD; F1: 88.5") gives each value its headers in plain words, which both BM25 and an embedding model can match.
  • A summary written by a model ("Table 3 compares five models on SQuAD; BERT-base has the highest F1") is embedded for retrieval while the full table goes to the generator. The {{GraphRAG and structured retrieval page|n:3f85c17b0d0d81e2bb4cdbb749e48a5a}} covers querying tables with SQL instead.

How to check it. Structure metrics compare the predicted grid with a true one: TEDS (tree-edit distance between the two HTML trees, Zhong et al., 2020) and the adjacency-relation F1 of the ICDAR 2013 table competition; olmOCR-bench (section 3) instead checks single facts such as "a cell reads 4.5% and the cell above it reads 2.4%" (the benchmark README's own example). The {{Table lab|#t-ingtab}} shows one real table from the running example before and after, scored against the grid in the paper's LaTeX source.

Measured on one table of the running example

Table 1 of arXiv 1909.00175 (15 rows, 13 columns, three header rows with spanning cells) is the only evidence for the QASPER question "What state-of-the-art results are achieved?" Against its LaTeX source:

  • Every plain-text extractor kept the numbers and lost the table. pypdf emits each row as one line, "Ours – BPA-p 91.25 93.28 92.19 82.06 76.54 79.20 86.67 ...", with the three header rows above as loose words; pdftotext cuts each row into its homographic and heterographic halves; PyMuPDF writes one cell per line in row order; pdfminer.six and Unstructured fast (which uses pdfminer for this strategy) emit it column by column: "78.32 72.51 79.93 68.38 90.24 - - 87.21 89.19 89.24 91.25 -" is the first column of numbers. Either way nothing says that 92.19 is homographic detection F1.
  • Docling kept every number under the right headers (100%, and the three answer cells in the right row and column). It merges the three header rows into one, "Homographic - Detection - F1", which is already a row serialisation.
  • The other table-aware tools got the body right and the headers wrong. MinerU (basic and flash) and pymupdf4llm put every number in the right row and column (adjacency F1 0.93 to 0.99) but split header words ("Detectio" / "nF 1", "Homog" / "raphic"), so only 0 to 18% of numbers sit under all three of their headers. Marker split system names across columns ("Pramanick | and | Das"), which shifts rows that have fewer cells. Unstructured hi_res read the table from the image with Tesseract: "F1" became "Fi" and "Fy", "89.19" became "89,19", and the Homographic and Heterographic header row was lost.

Measured on Apple M1 Pro (CPU), default settings of each tool (Marker without OCR), 2026-10-14; one table, so this shows kinds of failure, not a ranking. Details, raw outputs and rebuilt grids in the {{Table lab|#t-ingtab}}.
