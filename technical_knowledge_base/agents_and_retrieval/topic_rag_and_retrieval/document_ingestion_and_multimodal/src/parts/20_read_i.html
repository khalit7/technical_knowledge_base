8. Incremental updates: re-embed only what changed

The problem. Documents change: a contract gets an amendment, a wiki page an edit, an arXiv paper a v2. Re-parsing and re-embedding the whole corpus on every change costs compute and, worse, time during which the index is stale. The goal is to touch only the chunks whose text changed, and to delete the chunks of text that no longer exists.

How it works. Three levels of hashing, each a content hash (a fingerprint such as SHA-256 that changes whenever the bytes change and is identical when they do not):

  1. File level: hash the raw file. Same hash, skip it entirely. This catches the common case, an unchanged file re-synced, without parsing.
  2. Chunk level: parse and chunk the changed file, hash each chunk's normalised text, and compare with the hashes stored for that document. Embed only new hashes; delete stored chunks whose hash disappeared; keep the rest with their vectors.
  3. Embedding level: key the vector cache by (chunk hash, embedding model, model version), so a model upgrade is a deliberate full re-embed and never a silent mix of two vector spaces.

The trap: chunk boundaries move. Chunk-level hashing only saves work if an edit leaves the other chunks' text identical. With fixed-size windows (every 200 words), inserting one sentence near the top shifts every later boundary by a few words, so every later chunk gets a new hash and the whole tail is re-embedded. Boundaries tied to the content survive edits: paragraph and heading boundaries (structure-aware chunking), or content-defined chunking, which cuts wherever a rolling hash of the last few words hits a chosen value, the technique the LBFS network file system used, with Rabin fingerprints over a sliding window (Muthitacharoen et al., SOSP 2001), so a boundary moves only if the words around it change.

Predict: arXiv 1801.02073 v2 differs from v1 by one word: an author's middle initial, "Jinho Choi" became "Jinho D. Choi", in the author line at the top. With 200-word fixed windows, how many of the paper's 17 chunks must be embedded again?
All 17. The inserted word shifts every later window by one word, so every window's text, and hash, changes. Structure-aware chunks of the same two versions: 1 of 26 re-embedded; content-defined chunks: 1 of 40.

Measured on the running example. Ten papers of the QASPER sample have a revised arXiv version (parsed by Docling, last two versions compared; full table in the {{Re-indexing lab|#t-ingcd}}). Across them the revisions changed 15.0% of the words. Fixed 200-word windows re-embedded 75.8% of the words, and 76.4% with 50 words of overlap; structure-aware chunks 49.2%; content-defined chunks 44.2%. Where a revision rewrites a third of a paper (1910.14599, 39.5% changed) every strategy re-embeds most of it; where it touches a word or a sentence, the boundaries decide whether the cost is one chunk or the whole document.

Deletes are the half people forget. When text disappears, its chunks must leave the index, or retrieval keeps citing a clause that was removed. In HNSW-based stores a delete is usually a tombstone until compaction; purging, freshness targets and the right to be forgotten belong to {{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}}. How to check it: after a sync, the set of chunk hashes in the index for a document must equal the set computed from its current version, no more and no fewer.
