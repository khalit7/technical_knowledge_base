1. What a PDF page actually contains

A PDF is a page description: drawing instructions that put glyphs at coordinates so the page looks right (ISO 32000-2:2020, PDF 2.0; overview). Paragraphs, columns, tables and captions are not stored; every parser's output is rebuilt from those instructions, or from pixels. Four facts cause most ingestion bugs:

  • Text is positioned, not flowing. In each page's content stream, Tm and Td move a text cursor and Tj or TJ draw glyphs there (section 9.4); nothing marks a line continuing or a second column, and spaces are often only a gap the parser must notice.
  • Stream order is the producer's order: a typesetter may draw the left column, the right, then the header and footnotes, or a table cell by cell; a Word export draws text boxes in creation order. An extractor that follows the stream inherits it.
  • Glyphs are font codes, not letters: they become Unicode only through the font's encoding or a ToUnicode map (section 9.10), and a subset font without one decodes to garbage although the page looks perfect. Ligatures (one glyph for "fi", U+FB01) and line-end hyphens add damage.
  • A scan is a picture with no text, unless an earlier OCR run added an invisible layer (text render mode 3) of whatever quality that OCR had.

A structure tree (Tagged PDF, section 14.8, required by accessibility rules such as PDF/UA, ISO 14289) does record paragraphs, headings, tables and reading order; use it when present and correct. None of the 38 arXiv PDF files downloaded for this page (24 papers, every version) has one (no StructTreeRoot, checked with PyMuPDF).

2. Rule-based extractors: geometry and thresholds

A rule-based extractor rebuilds words, lines and blocks from glyph coordinates with no learned model. The steps are the same everywhere; only the thresholds and the final sort differ.

Three thresholds and a sort: where two columns go wrong

Glyphs to words and lines, lines to boxes, boxes to an order, with pdfminer.six's LAParams defaults on illustrative glyphs: word_margin 0.1, char_margin 2.0, line_overlap 0.5, line_margin 0.5. The final sort decides columns: top to bottom over the full width interleaves them.

The tools differ mainly in the last step: pypdf (6.20.1) keeps content-stream order; PyMuPDF (1.28.2) too, unless sort=True sorts blocks by top then left (recipes); pdfplumber (0.11.10) clusters characters into lines (x_tolerance 3 points) and reads them across the full width; pdftotext (poppler 26.02) detects columns; pymupdf4llm (1.28.2) adds headings by font size, tables by ruling lines, Markdown, and here called RapidOCR on pages it judged to be images. Milliseconds per page and no model: the right first stage for clean single-column files; columns, headers, footnotes, tables and scans break the rules.

3. Layout-aware parsers: let a model look at the page

A person finds columns, headers and tables by looking. A layout-aware parser renders the page and runs a layout detection model, an object detector trained on labelled pages (the eleven classes of IBM's DocLayNet: Text, Title, Section-header, Table, Picture, Caption, Formula, List-item, Page-header, Page-footer, Footnote); it fills each box from the text layer where it is good and OCR where not, orders the boxes, sends tables to a table-structure model, and drops headers and footers by class, not by guessing.

Four open layout-aware parsers ran here on the CPU: Docling, Marker (fast mode, OCR off, so it reads scans like a text extractor), MinerU and Unstructured. Licences differ: Docling MIT, Unstructured Apache 2.0, MinerU its own licence with extra conditions, and Marker's model weights a modified OpenRAIL-M, free below $5M revenue.

Retrieval barely notices the middle group. 5. OCR: route only the pages that need it

Scans, photos and some exports have no usable text layer (none, an old invisible OCR layer, or glyphs without a Unicode mapping). Optical character recognition (OCR) reads characters from pixels; it replaces exact text with a guess and costs seconds per page, so it is routed per page, never run on everything.

Check the text layer first; OCR only what fails the check

The check: characters per page area, share of replacement or private-use characters, share of dictionary words, a single full-page image. Times on this CPU: Tesseract at 300 dpi took 2.18 s per page on the QASPER papers and 3.15 s on the olmOCR sample; VLM OCR was not run here.

Classic engines. Tesseract (5.4.1, Apache 2.0) binarises the page, finds lines with its page-layout analysis (--psm 3, the default, assumes a full page of any layout) and since version 4 reads each line with an LSTM trained per language (documentation); it knows nothing of tables or reading order beyond its block finder. Layout-aware parsers OCR only image-text regions or broken pages: Docling through whichever engine its OcrAutoOptions finds (pipeline_options.py line 312; here RapidOCR, PP-OCRv6 small), Unstructured hi_res through Tesseract, MinerU and Marker through their own models.

VLM OCR. Since 2025 the strongest systems on olmOCR-bench are vision-language models that read a page image and write Markdown, tables as HTML and maths as LaTeX: olmOCR 2 (7B), PaddleOCR-VL, Chandra, dots.ocr, DeepSeek-OCR. They handle reading order, tables and handwriting jointly, need a GPU and a few seconds per page, and can hallucinate text that is not on the page or repeat a line forever (olmOCR-bench's baseline test checks for runaway repetition). None ran here (reference pipelines target NVIDIA GPUs with vLLM; published scores in section 4). How to check any OCR: character error rate against a hand transcription of a sample.

6. Tables: structure is the content

A number means nothing until you know its row and column. A text extractor emits cells as a stream (by row, by column, headers scattered), and retrieval fails twice: the chunk has no words matching the question, and if retrieved the generator cannot tell which number answers it.

How much it matters. In QASPER validation (281 papers, 1,005 questions), a table or figure is evidence for 164 (17.4%) of the 945 answerable questions, and for 35 of them a table or figure is the only evidence (30 tables, 5 figures; src/scripts/qasper_stats.py, FLOAT SELECTED entries). The root's set keeps only questions with text evidence, so these never reach its recall numbers: an ingestion choice hidden by an evaluation choice.

Extraction in four steps: detect the region (a Table box, or ruling lines); recognise structure, rows, columns, spanning and header cells (pdfplumber, Camelot and pymupdf4llm use ruling lines or whitespace; Docling's TableFormer predicts structure from the image, Nassar et al., 2022, then matches cells to the PDF's own text, do_cell_matching=True by default in docling 2.138.0); fill cells from the text layer or OCR; serialise as HTML (keeps spans) or Markdown (cannot express a spanning cell, so merged headers repeat or vanish).

How the table was scored

Adjacency F1: pairs of horizontally or vertically adjacent non-empty cells where at least one is a number, compared as text with the ground truth (the relation idea of the ICDAR 2013 table competition, restricted to the body so that merging the three header rows into one, as Docling does, is not penalised). Header association: the share of the table's numbers found in the right row whose column header text contains all three ground-truth header words; it was added after the first scoring, because plain adjacency F1 ranked MinerU above Docling although MinerU's headers were split mid-word. A parser that emits no table has no grid, so neither score applies; "cells whose text appears" still counts a number found anywhere. Ground truth: the tabular in the paper's pun.tex (lines 244 to 277 of the arXiv source, kept in src/inputs/). Script: src/scripts/table_score.py.

Making a table retrievable: keep it whole with its caption, or split by rows with the header repeated (a chunker that cuts a Markdown table mid-way leaves rows without headers); row serialisation ("Model: BERT-base; Dataset: SQuAD; F1: 88.5", values illustrative) gives each value its headers in words BM25 and an embedder can match; or embed a model-written summary and pass the full table to the generator. SQL over tables is on GraphRAG and structured retrieval. How to check: TEDS (tree-edit distance between HTML trees, Zhong et al., 2020), the adjacency F1 of the ICDAR 2013 competition, or olmOCR-bench's single facts ("a cell reads 4.5% and the cell above it reads 2.4%", its README's example).

7. Figures, images and other formats

A chart, diagram or photo carries information no text extractor sees. Three things can be recovered, at rising cost:

  1. The caption, which layout parsers label as its own element (caption in Docling, Caption in Marker, FigureCaption in Unstructured): keep it attached to its figure and make it its own chunk, since "Figure 3: accuracy against context length for four models" is often exactly what a question matches. A rule-based extractor emits it as an ordinary line, often inside the paragraph that flows around the figure.
  2. Text inside the figure: axis labels and legends are real text in vector figures (a scatter of short lines) and need OCR in raster ones.
  3. What the figure shows, which only a VLM can describe. Captioning for retrieval: crop each figure, ask a VLM for its quantities, axes and main finding, index that beside the caption, labelled as generated. One VLM call per figure; the risk is a confident wrong description. In the ColPali paper's Table 2, Claude 3 Sonnet captions raised BM25 on ArxivQA (figure questions) from 31.6 to 40.1 nDCG@5 over OCR text alone (the authors' runs).

Images as items. For standalone images (product photos, diagrams) a single-vector image-text embedding of the CLIP or SigLIP kind puts pictures and queries in one space (Vision encoders). A page full of small text is too much for one vector; when answers live in charts, infographics or slides, section 10 keeps one vector per patch instead of translating figures into words.

8. Metadata: what every chunk must carry

Once a chunk leaves its file, three jobs need facts only the parser had: a citation the user can check ("page 4 of the 2020 annual report, section 3.2"), a filter inside the search ("contracts signed after 2024", "documents this user may read"), and an update (replace every chunk of a changed file). Store each chunk as a record, not a string.

9. Incremental updates: re-embed only what changed


A contract gets an amendment, an arXiv paper a v2. Re-embedding the whole corpus on every change costs compute and stale time; the goal is to touch only chunks whose text changed and delete chunks of text that is gone, with three levels of content hash:


    

  1. File: same hash, skip it without parsing (an unchanged file re-synced).
    2. 

  2. Chunk: hash each chunk's normalised text and compare with the document's stored hashes: embed only new hashes, delete vanished ones, keep the rest with their vectors.
    3. 

  3. Embedding: key vectors by (chunk hash, embedding model, model version), so a model upgrade is a deliberate full re-embed, never a silent mix of two vector spaces.
    4. 



The trap: chunk boundaries move. With fixed 200-word windows, one sentence inserted near the top shifts every later boundary and every later hash. Boundaries tied to content survive edits: paragraph and heading boundaries from the parser (structure-aware), or content-defined chunking, which cuts where a rolling hash of the last few words hits a chosen value, as the LBFS file system did with Rabin fingerprints (Muthitacharoen et al., SOSP 2001). Which chunking retrieves best is The retrieval pipeline's question; this is what each costs when documents change.

10. Skip the parser: retrieve the page image


Parsing loses what text cannot hold: a chart's shape, an infographic's layout, a diagram's arrows. A vision-language model reads a page as a picture cut into patches (small squares, each a vector); page-image retrieval embeds each page's screenshot and searches it with the text query, with no parsing at all.


ColPali (Faysse et al., 2024) takes PaliGemma-3B and keeps one 128-dimension vector per image patch: 1,024 patch vectors plus 6 for the text prompt, 1,030 per page (paper section 4.1 and footnote 10); a query keeps one vector per token. The score is late interaction as in ColBERT: each query token takes its best dot product with any patch and the maxima are summed (MaxSim), so "revenue" can match a bar label's patches and "2019" an axis tick's. MaxSim, ColBERT and PLAID-style indexing are owned by Rerankers and late interaction; this section is what changes when the document tokens are image patches.


score(q, page) = ∑i ∈ query tokens maxj ∈ patches qi · pj

The paper's token pooling (mean-pooling similar patch vectors, pool factor 3) cuts the vectors by 66.7% and keeps 97.8% of the retrieval quality (paper section 5.2, the authors' runs).


Published results. ViDoRe (Visual Document Retrieval benchmark, same paper) pairs text queries with page images, scored by nDCG@5 (normalised discounted cumulative gain over the top five pages). In its Table 2 ColPali averages 81.3 against 65.5 for Unstructured + OCR + BM25 and 67.0 for the best text pipeline (Unstructured + captions written by Claude 3 Sonnet + BGE-M3); the gap is largest on figures (ArxivQA 79.1 against 31.6) and smallest on text-heavy reports (Energy 91.0 against 85.9). The authors' runs; section 11 reruns it with a small open model.






11. Measured: page images against OCR text


Rerun here with laptop-sized models on 100-query, 200-page subsets of three ViDoRe v1 sets, InfoVQA (infographics), ArxivQA (figures from papers) and Energy (text-heavy reports): Tesseract OCR then BM25; the same OCR text embedded by bge-small-en-v1.5 (the root's small embedder); and the page image embedded by colSmol-256M (vidore/colSmol-256M: the ColPali recipe on SmolVLM-256M, MIT licence, 128 dimensions per vector).


Predict: on the Energy set (text-heavy industrial reports), does the 256M page-image model beat plain BM25 over Tesseract OCR?




No clear winner: colSmol 97.7 against 95.0 for BM25, with intervals of about ±2.5 and ±3.8, so the two tie on text-heavy pages. The image model's lead appears where the text is not the content: ArxivQA (figures) 74.2 against 37.9, InfoVQA (infographics) 87.6 against 72.6.


The page image wins where the text is not the content, and ties on text




nDCG@5, solid bars measured here with ± half the 95% interval; lighter bar: BM25 on the full set, for scale; dashed bars: the ColPali paper's Table 2 (the authors' runs on the full sets), not a reproduction.


On figures OCR text barely helps (the words in a plot are not what the question asks), so BM25 and the dense embedder both land near 38 and the 256M image model doubles that. On infographics the image model leads by 15 points, beyond both intervals. On text-heavy reports the methods tie, and plain BM25 beats the dense text embedder (95.0 against 88.2): rare domain terms favour exact matching. The shape matches the paper's, at smaller scale.


Cost here: colSmol produced 699 to 1,103 vectors of 128 numbers per page (mean per set), about 175 to 280 KB per page in float16, against one vector for bge-small. Encoding took 4.3 to 5.9 s per page on this CPU in float32, against 0.3 to 1.6 s for Tesseract (the paper's 3B ColPali: 0.39 s on a GPU). What transfers: the ranking by document type and the storage arithmetic; not the absolute times or nDCG, since 200-page subsets are easier than full sets (BM25 on the full InfoVQA set: 67.5 against 72.6 on the subset).

How the ViDoRe comparison was run
Measured on Apple M1 Pro, 2026-10-14, on seeded subsets (seed 0) of three ViDoRe v1 test sets at pinned revisions: 100 queries and 200 pages each (the queries' relevant pages plus random others), so every retriever ranks the same 200 pages. Your documentsStart withWhy (evidence on this page)



Born-digital, single column, mostly prose (reports, contracts, editor exports)A fast text-layer extractor (PyMuPDF, pdftotext), with de-hyphenation and ligature normalisationMilliseconds per page; on LaTeX papers stream order was already close to reading order; hyphens and ligatures were the main damage (section 4)


Born-digital with columns, tables, captions, running headers (papers, filings, manuals)A layout-aware parser (Docling, Marker, MinerU), tables kept as HTML or Markdown with headersHighest evidence survival and the only correct table grid here; about a second per page on CPU (sections 4 and 6)


Scans and photosOCR routed per page (Tesseract or a parser's OCR), or VLM OCR on a GPU for hard layoutsText-layer tools return nothing on scans; published VLM OCR scores lead the full benchmark (sections 4 and 5)


Charts, infographics, slides, figure-heavy pagesPage-image retrieval (ColPali family), alone or fused with text retrievalSection 11 and the ColPali paper's Table 2


A corpus that changesStructure-aware or content-defined chunk boundaries, chunk hashes, vectors keyed by model versionSection 9: 49% or 44% of words re-embedded against 76% for fixed windows, with a 15% floor




Interview rehearsal: ingest 5 million mixed documents for an enterprise assistant with citations and per-user permissions
    

  1. Intake: a queue of (document id, version, ACL) events from each source; a file hash skips unchanged files.
    2. 

  2. Triage per page: text-layer quality check; born-digital pages to a fast layout-aware parser on CPU workers, broken or scanned pages to an OCR or VLM-OCR pool on GPUs; spreadsheets read natively, not as images.
    3. 

  3. Elements, not strings: keep type, page, bounding box and heading path; tables as HTML with a row serialisation; figures with captions, and VLM descriptions for figure-heavy collections.
    4. 

  4. Chunk by structure; hash chunks; embed only new hashes, keyed by model version; write vectors and metadata (ACL, tenant, dates) to a store that filters inside the search; delete chunks whose hashes vanished in the same transaction.
    5. 

  5. Optional visual index for slide decks and reports with charts: page-image embeddings (ColPali family) fused with text results, if you can afford about 30 times the vector storage and a multi-vector index.
    6. 

  6. Evaluate on a golden set built from the original files, per document type; track parse failures, OCR share and pages per second as production metrics; re-parse by parser version when a parser improves.
    7.
