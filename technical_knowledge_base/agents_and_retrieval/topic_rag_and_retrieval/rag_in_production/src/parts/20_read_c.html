4. Deletes and the right to be forgotten

A document is withdrawn, or a person asks for their data to be erased: under the EU's GDPR, Article 17 gives a right to erasure "without undue delay", and Article 12(3) requires a response within one month (Regulation (EU) 2016/679; not legal advice). Graph indexes cannot simply remove a node, because other nodes route through it: hnswlib, pgvector and FreshDiskANN mark it deleted (a tombstone) and skip it. The sibling page measured that recall holds while work grows (with half of SciFact deleted, @@vix_del_tomb@@ distances per query against @@vix_del_reb@@ in a rebuilt graph; {{Vector indexes, section 10|n:3f85c17b0d0d81f29707c130b2ebcfb1}}). A tombstone stops retrieval; it erases nothing.

What does erase? One constructed row (a fake HR note with a unique marker string) was added to a pgvector table of 2,000 SciFact abstracts with an HNSW index (PostgreSQL @@pg_ver@@, pgvector @@pgv_ver@@, Docker); after each step the files were flushed with CHECKPOINT and searched for the marker's bytes and the row's vector bytes measured here:

DELETE hides the row; only VACUUM FULL removes it from the files, and the WAL keeps the text

PostgreSQL keeps old row versions for concurrent transactions, and VACUUM marks the space reusable without overwriting it, so the text and vector stay in the table and index files until the page is reused. VACUUM FULL rewrites the table and its indexes into new files (locking the table while it runs). The write-ahead log (WAL, the record of every change that makes crash recovery and replication possible) kept its copies at every step; segments are recycled later, but any WAL archive or backup keeps them as long as it is retained, and the filesystem and SSD may keep freed blocks.

A design that works: every chunk, cache entry and log line carries the source document id; a deletion writes to a deletion ledger that each store consumes; logs keep passage ids rather than passage text where they can; backups expire on a schedule shorter than the erasure deadline, or each subject's data is encrypted with its own key that is destroyed on erasure (crypto-shredding). Check it: search with the deleted chunk's own vector (its nearest neighbour must not be itself), search the BM25 index for a distinctive phrase, look the id up in every cache, and keep the ledger as the audit trail.

5. Access control: enforce it at retrieval

An access control list (ACL) records which users or groups may read each document. If the assistant searches one shared index, two places can enforce it. In the prompt: retrieve as usual and tell the model "the user is in group X; do not use documents from other groups"; every forbidden passage retrieved is now inside the model's input, and the model is the only thing between it and the user. At retrieval: copy each document's ACL into the index as metadata at ingestion and make the search return only rows the user may read; forbidden passages never reach the prompt, so no wording, injection or model mistake can reveal them.

A real retrieval-time filter: PostgreSQL row-level security. Row-level security (RLS) attaches a policy to a table and PostgreSQL adds it to every query, so application code cannot forget it. The policy here reads the user's groups from a session setting:

acl_pg.py, the policy (PostgreSQL @@pg_ver@@, pgvector @@pgv_ver@@)
ALTER TABLE docs ENABLE ROW LEVEL SECURITY; CREATE POLICY read_own_groups ON docs FOR SELECT USING (grp = ANY (string_to_array(current_setting('app.groups', true), ','))); -- per request, from the authenticated identity, then the ordinary vector query: SELECT set_config('app.groups', 'public', false); SELECT id FROM docs ORDER BY emb <#> $1 LIMIT 10;

Across all five users and every RLS configuration, @@rls_leaks@@ forbidden rows came back. Three things still went wrong, each measured:

  1. Correct but incomplete. With a fresh plan per query, the planner saw that the hr filter is selective, used the ordinary index on the group column and sorted the @@g_hr_n@@ hr abstracts exactly (recall @@plan_rec_hr@@). On one long-lived connection with the driver's default prepared statements (psycopg prepares a statement after 5 executions), the plan made for the first user (an HNSW index scan) was reused for everyone. HNSW returns its best 40 candidates (ef_search) and the policy then removes the forbidden ones, so the hr user got @@prep_rows_hr@@ rows on average and nothing at all for @@prep_empty_hr@@ of 300 claims (recall @@prep_rec_hr@@); the legal user @@prep_rows_legal@@ rows. pgvector 0.8's iterative scans (keep walking the graph until enough rows pass) fix it: @@relax_rec_hr@@ with relaxed_order, @@strict_rec_hr@@ with strict_order. Secure, and silently empty: check result counts.
  2. Owners bypass policies. Connected as the table's owner, the policy did not apply: the contractor got @@owner_leak_contr@@ forbidden rows over 300 claims, exactly the unfiltered count. After ALTER TABLE ... FORCE ROW LEVEL SECURITY: @@forced_leaks@@. Serve queries from a role that owns nothing; superusers always bypass RLS.
  3. The setting is trusted. Any session can call set_config: a client that can run SQL set its groups to 'hr' and read @@setgroups_rows@@ hr rows. Set the value in the server from the authenticated identity (in the same transaction as the query, inside a function, or in a pooler), never from anything the user controls.
