7. Latency: where the time of one request goes

The problem. A user waits for the whole read path. Retrieval papers report quality; a product is judged by time to first token (TTFT: from sending the question to seeing the first word of the answer stream in) and by the slowest few percent of requests.

The budget, stage by stage. One request path on the running example, assembled from timings recorded on this laptop (measured here, Apple M1 Pro, MPS and Metal; each with its own run and load average, listed under the chart): Qwen3-Embedding-0.6B encodes the claim (p50 51.3 ms), exact search scans the 5,183 vectors (about @@exact_sci_ms@@ ms at the measured scan rate of @@scan_gbps@@ GB/s per core), the MiniLM cross-encoder reranks 30 candidates (about 0.13 s at its measured pair rate), and Qwen3-1.7B (4-bit, llama.cpp) reads the top 5 abstracts, about @@tt_k5_n@@ prompt tokens, before its first token: about @@tt_k5@@ ms at the prefill rate the root's Pipeline lab recorded over @@pip_answers@@ answers (median @@pip_prefill@@ tokens per second, decoding at @@pip_decode@@; load average @@pip_load@@). Generation is most of the wait. Timed end to end in one process (40 claims, 3 passes, one request at a time, bench lock held, load average @@e2e_load@@), the whole request reached its first token in @@e2e_wall_to_first_token_p50@@ ms at p50 and @@e2e_wall_to_first_token_p90@@ ms at p90, of which the generator's own time to first token was @@e2e_ttft_p50@@ ms (p90 @@e2e_ttft_p90@@) for a median prompt of @@e2e_prompt_n@@ tokens; embedding @@e2e_embed_p50@@ ms, search @@e2e_search_p50@@ ms, reranking @@e2e_rerank_p50@@ ms; 64 output tokens finished @@e2e_gen_total_p50@@ ms after the generator started. Measuring the path, not the parts, mattered: the embedding and reranking stages took several times longer here than in their isolated runs (51.3 ms and about 130 ms), because the embedder, the cross-encoder and the generator share one GPU and its memory; the load average stayed low, so other agents were not the cause. On a server, put the model stages on separate devices or services and measure under load.

Three things decide the budget, and the {{Latency waterfall|#t-prdlat}} lets you change each one:

  • Prefill grows with context. Before the first token, the model must read the whole prompt (prefill). At the recorded rate, one abstract in the prompt costs about @@tt_k1@@ ms to the first token, five about @@tt_k5@@ ms and ten (@@tt_k10_n@@ tokens) about @@tt_k10@@ ms (derived: prompt tokens ÷ the recorded prefill rate for that prompt length). Measured directly with streamed requests (load @@tt_load@@), Qwen3-1.7B took @@tt17_256@@ ms to the first token at about 256 prompt tokens and @@tt17_8192@@ ms at @@tt17_8192_n@@; Qwen3-4B @@tt4_256@@ and @@tt4_8192@@ ms (@@tt4_8192_n@@ tokens), decoding at about @@dec17@@ and @@dec4@@ tokens per second. Every extra retrieved chunk costs prefill on every request, which is one reason to rerank and pass 5 good chunks rather than 20 mediocre ones.
  • Reranker cost is per pair. A cross-encoder reads each (query, passage) pair, so its cost is K times one pair: the setup measured 228 to 237 pairs per second for the 22 M MiniLM cross-encoder, 14.5 for bge-reranker-v2-m3 and 5.0 for Qwen3-Reranker-0.6B on MPS, so reranking 30 candidates costs about 0.13 s, 2.1 s and 6 s respectively (rates from the root's running example; the latencies are derived as 30 ÷ rate). On a server GPU all three are far faster (not run here); the ratios hold.
  • The tail, not the median. When a request fans out to many shards or services and waits for all of them, a rare slow response becomes a common slow request: Dean and Barroso's example is a server with 1 request in 100 taking a second, where a request touching 100 such servers is slow 63% of the time (The Tail at Scale, CACM 2013, published). Their remedies (hedged requests, sending a second copy after the 95th-percentile wait; tied requests; micro-partitions) apply to sharded vector search unchanged.

Prefix caching. A model server can keep the computed attention keys and values (the KV cache) of a prompt's beginning and reuse them for the next request that starts with the same tokens. In RAG the retrieved passages differ per question, so the reusable prefix is what comes before them: system prompt, tool definitions, few-shot examples. Put stable text first and per-request text last. Measured here with llama-server's prompt cache, a prompt of about @@pre_n@@ tokens (a block of abstracts) followed by five different questions: the first call took @@pre17_first@@ ms to the first token, the next four @@pre17_hit@@ ms at the median (Qwen3-1.7B); @@pre4_first@@ and @@pre4_hit@@ ms for Qwen3-4B. Hosted APIs price the same effect: Claude Haiku 5.5 bills cache hits at $0.01 per million input tokens against $0.10 for uncached input (published, read 2026-10-14). How servers do it belongs to {{Topic: inference-and-serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}}.

What transfers. The shape does: generation dominates, prefill grows linearly with retrieved tokens, reranking scales with K times the reranker's per-pair cost, and the embedding and search stages are tens of milliseconds or less for collections of this size. The milliseconds do not: a datacenter GPU serves the same models many times faster, and a server batches concurrent requests, which raises throughput and changes per-request latency (not run here).

8. Caching, and the wrong answers a semantic cache serves

Caches can sit at every stage of the read path, and they differ in one property that matters most: can a hit be wrong?

CacheKeySavesCan a hit be wrong?
Query embeddingmodel + exact query textthe embed stage (5.9 to 51 ms per query here)no
Retrieval resultquery (or its vector) + filters + user's groups + index versionsearch and rerankingonly if stale, or if the key misses the user's groups
Answerthe same, plus the model and prompt versioneverythingyes when stale; yes if shared across users with different access
Semantic (answer or result)the nearest earlier query above a similarity thresholdeverything, on paraphrasesyes, by design: it guesses that two different questions deserve the same answer
Prefix (KV) at the model serverexact token prefixprefill of the shared beginningno

Invalidation. Put the index version into every result and answer key, so a re-index or model switch invalidates everything at once; tag entries with the source document ids, so a change or deletion (section 4) can evict exactly the entries built from it; and add a time-to-live so nothing outlives the freshness target. Put the user's access groups (or tenant) into the key: an answer built from HR documents and served to a contractor is a leak through the cache.

Semantic caching on a RAG workload. SciFact is a hard, realistic test: its annotators wrote many claims in pairs from one cited abstract, one the abstract supports and one it contradicts, often by changing a single word. Among the @@c_n@@ labelled claims there are @@c_opp_pairs@@ such opposite-verdict pairs and @@c_same_pairs@@ same-verdict pairs. Replaying the claims in order through a semantic cache keyed on Qwen3-Embedding vectors measured here:

  • Opposites are the most similar pairs. Median cosine @@c_opp_med@@ for opposite-verdict pairs, @@c_same_med@@ for same-verdict pairs: "positively correlated" and "negatively correlated" differ by one word, two claims with the same verdict usually differ by many. No threshold separates them.
  • Most hits are wrong. At a threshold of 0.95, @@c_hits_95@@ of @@c_n@@ claims were served from the cache; @@c_opp_95@@ of those hits (@@c_oppshare_95@@%) would have returned the opposite verdict and only @@c_same_95@@ the same verdict on the same abstract (the rest cite the same abstract without a verdict, or a different one). At 0.90 the opposite share was @@c_oppshare_90@@% with Qwen3-Embedding, @@c_oppshare_90_mini@@% with MiniLM, @@c_oppshare_90_bge@@% with bge-small, @@c_oppshare_90_gte@@% with gte-modernbert.
  • A semantic result cache is far safer than a semantic answer cache. 9. Cost per query

A request pays for each stage it uses; the corpus pays once to be embedded, then again for what changes, and for storage every month. Spread the monthly costs over the month's queries and the cost per query is a sum:

cost = embed + rerank + generate + (re-embedding + storage) ÷ queries
embed
query tokens × embedding price
rerank
(query tokens × K + K × chunk tokens) × price, Voyage's counting rule (the query is billed once per candidate), or a price per request
generate
uncached input tokens × input price + cached prefix tokens × cached price + output tokens × output price

A worked example with published list prices read on 2026-10-14 (published; the {{Cost calculator|#t-prdcost}} has the sources and every knob): 1 million queries a month over 10 million chunks of 256 tokens; text-embedding-3-small ($0.02 per million tokens, 1,536 dimensions); Voyage rerank-3 on K = 30 candidates ($0.05 per million tokens: @@rerank_tok@@ tokens per query); gpt-5-mini reading k = 5 chunks plus a cached 300-token system prompt (@@gen_in_tok@@ input tokens, 200 output; $0.25, $0.025 cached, $2.00 per million); vectors at Pinecone's $0.33 per GB-month (@@co_gb@@ GB of float32 vectors). The total is @@co_total@@ per query, @@co_month@@ a month: generation @@co_gen@@ (@@co_gen_share@@%), reranking @@co_rerank@@ (@@co_rerank_share@@%), storage @@co_storage_month@@ a month, the first full embedding @@co_init@@ once. Two things surprise people: the hosted reranker costs more than half as much as the model, because it reads 30 passages where the model reads 5; and the vector database's bill is mostly not in this formula (read units, replicas and minimums are billed separately, and depend on the store).

Self-host or API. A self-hosted component costs its machines whether or not they are busy; an API costs per call. The break-even is the monthly machine cost divided by the API cost per query. One AWS g6.xlarge (one NVIDIA L4 GPU) at @@l4_hour@@ an hour on demand is @@l4_month@@ a month (Vantage listing, read 2026-10-14); at @@co_rerank@@ per query for the hosted reranker, self-hosting a reranker pays off above about @@be_rerank@@ queries a month, if one L4 can carry the peak load at the latency target (measure it; not run here) and before counting the engineers who run it. For generation the same arithmetic usually favours an API at low volume and a self-hosted open model at high, steady volume; a cheaper hosted model changes the balance too (Claude Haiku 5.5 makes the example's generation @@co_gen_haiku@@).
