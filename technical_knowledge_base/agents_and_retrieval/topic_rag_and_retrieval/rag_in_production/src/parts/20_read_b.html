2. Freshness: how long until a change is searchable

A policy page is edited at 09:00; at 09:20 the assistant still quotes the old text, with a citation, and a stale answer looks exactly like a correct one. Two designs move changes into the index. Batch: a job runs every hour or night, lists the source, finds what changed by modification time or a content hash (a fingerprint such as SHA-256 that changes whenever the bytes do), and re-processes only that; simple to rerun, with a lag of up to a full interval. Streaming: the source pushes each change (a webhook from a wiki, or change data capture, CDC, reading a database's own log of committed changes as Debezium does for PostgreSQL and MySQL) into a queue that indexing workers drain; seconds of lag, at the price of a queue, retries and ordering to operate. Either way the lag is a sum, and the slowest term is usually not the one people tune:

lag ≈ detect + queue + parse + embed + write + visible
detect
half the polling interval on average for batch; near zero for webhooks and CDC
queue
the backlog ahead of this change divided by the workers' throughput: a bulk import of 10,000 documents delays the edit behind it
embed
chunks ÷ embedding throughput (measured here on MPS: Qwen3-Embedding-0.6B 6.3 SciFact abstracts per second, bge-small 143, MiniLM 465)
visible
the store's own delay: PostgreSQL makes a row visible at commit; Elasticsearch at the next refresh, which defaults to 1 s (5 s on Serverless), and an idle shard is not refreshed until it is searched (index settings docs, read 2026-10-14); Qdrant applies writes in two asynchronous steps (write-ahead log first, then the segment) ("Any point modification operation is asynchronous and takes place in 2 steps", points docs); Pinecone's serverless indexes are eventually consistent (see the {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}} page)

Re-embed only what changed. Hash every chunk, compare with the stored hashes, embed only new ones and delete the ones that disappeared. The trap is that chunk boundaries move: on the ingestion page's ten revised QASPER papers, revisions changed 15.0% of the words but fixed 200-word windows re-embedded 75.8% of them, structure-aware chunks 49.2% (measured there, in its {{section 9|n:3f85c17b0d0d81279079f614f382f2e7}}, which owns the hashing). Check it the way users feel it: a freshness probe writes a sentinel document carrying the current time to the source every few minutes and searches for it through the production read path; the difference is the end-to-end lag, graphed and alerted like latency. A reconciliation job compares, per document, the chunk hashes in the index with those computed from the source: anything extra is a stale chunk, anything missing an unindexed one. Permission changes travel the same path, so ACLs (section 5) have a freshness lag too.

Every step of an in-place backfill serves worse results than either end

3. Changing the embedding model: dual indexes and the backfill trap

A vector from one embedding model means nothing to another (each position is learned separately), so a model upgrade means re-embedding the whole corpus, a backfill, and the question is what the index serves meanwhile. If both models output the same number of dimensions, nothing stops you overwriting vectors in place: all-MiniLM-L6-v2 and bge-small-en-v1.5 both output 384.   1. Build beside. The old index keeps serving MiniLM queries (@@bf_old@@) while the new one fills; nobody queries the new one except the evaluation.
  2. Halfway. Users still get @@bf_old@@. The price is twice the storage while the backfill runs.
  3. Evaluate, then switch. The new index is complete and evaluated; one atomic switch moves traffic to it (@@bf_new@@). The old one stays for rollback.

Why it fails so badly. Not because the new vectors are worse: the two models use different similarity scales. bge-small's cosine between a claim and a random abstract has a median of @@bf_scale_bge@@, MiniLM's @@bf_scale_mini@@. A bge-small query against a mixed index scores every re-embedded abstract above every old one, so its top 10 comes only from the re-embedded share; with 10% done its nDCG@10 is @@bf_10_new@@, because it is searching a tenth of the corpus. The ends show the same: a bge-small query against an all-MiniLM index scores @@bf_cross_no@@, a MiniLM query against an all-bge index @@bf_cross_on@@. Different dimensions would at least raise an error; equal dimensions fail silently.

The dual-index pattern. Build the new index beside the old one (a new column, table or collection), backfill it while the old index keeps serving with old-model query vectors, evaluate it on the golden set (section 10) and a shadow copy of live traffic, then switch in one atomic step (an alias in Elasticsearch or OpenSearch, a view or a configuration flag), keep the old index for rollback and drop it later. It costs twice the storage during the backfill and a second query embedding while shadowing. Store the model name and version with every vector so a query can never be compared with another model's vectors.

What a backfill takes. Embedding time scales with tokens: Qwen3-Embedding-0.6B embedded SciFact's 1.70 million tokens in 816 s on MPS (about 2,100 tokens per second; the root's running example), so a 1-billion-token corpus would take about 5.5 days on this laptop. A hosted API at $0.02 per million tokens (OpenAI text-embedding-3-small, published 2026-10-14) charges $20 for the same billion tokens; the binding limits then are rate limits and the time to write and index the vectors.
