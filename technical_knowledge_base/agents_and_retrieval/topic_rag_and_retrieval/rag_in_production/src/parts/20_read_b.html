2. Freshness: how long until a change is searchable

The problem. A policy page is edited at 09:00; at 09:20 the assistant still quotes the old text, with a citation, to a user who then acts on it. Stale answers look exactly like correct ones. Freshness lag is the time from a change at the source to the moment the new text can be retrieved (and the old text cannot).

How it works. Two designs move changes into the index:

  • Batch: a job runs every hour or night, lists the source, finds what changed (by modification time or a content hash, a fingerprint such as SHA-256 that changes whenever the bytes do), and re-processes only that. Simple, easy to rerun, and the lag is up to a full interval.
  • Streaming: the source pushes each change as it happens: a webhook from a wiki, or change data capture (CDC: reading a database's own log of committed changes, as Debezium does for PostgreSQL and MySQL) into a queue that indexing workers drain. Lag is seconds, at the price of a queue, retries and ordering to operate.

Whichever design, the lag is a sum of stages, and the slowest one usually is not the one people tune:

lag ≈ detect + queue + parse + embed + write + visible
detect
half the polling interval on average for batch; near zero for webhooks and CDC
queue
the backlog ahead of this change divided by the workers' throughput: a bulk import of 10,000 documents delays the edit behind it
embed
chunks ÷ embedding throughput (measured here on MPS: Qwen3-Embedding-0.6B 6.3 SciFact abstracts per second, bge-small 143, MiniLM 465)
visible
the store's own delay: PostgreSQL makes a row visible at commit; Elasticsearch at the next refresh, which defaults to 1 s (5 s on Serverless), and an idle shard is not refreshed until it is searched (index settings docs, read 2026-10-14); Qdrant applies writes in two asynchronous steps (write-ahead log first, then the segment) ("Any point modification operation is asynchronous and takes place in 2 steps", points docs); Pinecone's serverless indexes are eventually consistent (see the Search and vector databases page)

Expected lag for one edited SciFact-sized document arriving behind the queue, one embedding worker on this laptop. Parse time is left out (it depends on the format; the ingestion page measures parsers). Detection is half the interval; 0 means webhooks or CDC.

What it costs. Re-embedding is the dominant cost of a change. The cure is to re-embed only chunks whose text changed: hash every chunk, compare with the stored hashes, embed only new ones and delete the ones that disappeared. The trap is that chunk boundaries move: on the ingestion page's ten revised QASPER papers, revisions changed 15.0% of the words but fixed 200-word windows re-embedded 75.8% of them, structure-aware chunks 49.2% (measured there, in its {{Re-indexing lab|n:3f85c17b0d0d81279079f614f382f2e7}}). That page owns the hashing; this one owns the lag and the deletes.

How to check it. Measure freshness the way users experience it: a freshness probe writes a sentinel document carrying the current time to the source every few minutes, then searches for it through the production read path; the difference is the end-to-end lag, graphed and alerted like latency. A reconciliation job compares, per document, the set of chunk hashes in the index with the set computed from the source: anything extra is a stale chunk, anything missing is an unindexed one.

3. Changing the embedding model: dual indexes and the backfill trap

The problem. A better embedding model comes out. Every stored vector was made by the old one, and a vector from one model means nothing to another: the numbers in each position are learned separately. So a model upgrade means re-embedding the whole corpus (a backfill), and the question is what the index serves while that runs.

The trap. If the two models output the same number of dimensions, nothing stops you from overwriting vectors in place. all-MiniLM-L6-v2 and bge-small-en-v1.5 both output 384 numbers; the animation replays a backfill from the first to the second on SciFact, 10% of the abstracts at a time, querying with either model, against the dual-index pattern. Every nDCG is measured here (exact search on the setup's precomputed vectors, 300 test claims).

Why the in-place backfill fails so badly. Not because the new vectors are worse: because the two models use different similarity scales. bge-small's cosine between a claim and a random abstract has a median of @@bf_scale_bge@@, MiniLM's @@bf_scale_mini@@. A bge-small query compared with a mixed index gives every re-embedded abstract a higher score than any old one, so its top 10 comes only from the re-embedded share; a MiniLM query does the opposite. With 10% re-embedded, the new model's nDCG@10 is @@bf_10_new@@: it is searching a tenth of the corpus. The cross-model numbers show the same thing at the ends: a bge-small query against an all-MiniLM index scores @@bf_cross_no@@, a MiniLM query against an all-bge index @@bf_cross_on@@ (both models score @@bf_old@@ and @@bf_new@@ in their own space). Different dimensions would at least raise an error; equal dimensions fail silently.

The dual-index pattern. Build the new index beside the old one (a new column, table or collection), backfill it while the old index keeps serving with old-model query vectors, evaluate the new one on the golden set (section 10) and on a shadow copy of live traffic, then switch with one atomic step (an alias in Elasticsearch or OpenSearch, a view or a configuration flag elsewhere), keep the old index for rollback, and drop it later. It costs twice the storage during the backfill and a second query embedding while you shadow-evaluate.

What a backfill takes. Embedding time scales with tokens: here, Qwen3-Embedding-0.6B embedded SciFact's 1.70 million tokens in 816 s on MPS (about 2,100 tokens per second; root's running example), so a 1-billion-token corpus would take about 5.5 days on this laptop. A hosted embedding API at $0.02 per million tokens (OpenAI text-embedding-3-small, published 2026-10-14) charges $20 for the same billion tokens; the binding limits then are rate limits and the time to write and index the vectors. Store the model name and version with every vector, so that a query can never be compared with vectors of another model.
