Two design questions for rehearsal (optional)

You add a tenant filter to an HNSW query and some tenants get empty answers. Why, and what are the fixes? The index returns its best ef_search candidates by distance only; the filter removes other tenants' rows afterwards, so a small tenant keeps few or none. Fixes: iterative scans or a filter-aware graph (ACORN, Qdrant payload links), pre-filtering with exact search for small tenants, partitions or separate indexes for large ones.

System design: a company assistant over its wiki, drive and ticket system for 20,000 employees with per-document permissions. Connectors with webhooks or change logs feed a queue; workers parse, chunk, hash and embed, writing chunks with source id, hash, ACL groups, model version and timestamp into a store that filters inside the search (pgvector with RLS and iterative scans, or Qdrant with payload indexes); permission changes flow through the same queue. The read path resolves the user's groups from the identity provider server-side, runs hybrid retrieval with the ACL filter, reranks, and generates with stable instructions first and passages as delimited data, with citations. Caches are keyed by groups and index version. A deletion ledger handles removals. Monitoring: per-stage p50/p95/p99, a freshness probe, canary queries, a best-match-similarity drift monitor, a golden set in CI, an "ask as the wrong user" leak test. Model upgrades through a second index and an atomic switch. Cost per query from the formula in section 9, revisited when K, k or prices change.
