Queries cost too: 10.7 s per question for GraphRAG and 13.3 s for LightRAG against 0.3 s for dense retrieval in the same table published.

When a graph pays. When (a) the questions are global or relational, not lookups; (b) the corpus is stable, so the index is built once and read many times (updates re-extract and re-cluster; LightRAG and graphrag's incremental methods reduce, not remove, this); (c) entities are what the corpus is about (people, companies, products, cases), so extraction finds real relations; and (d) someone owns entity resolution. When any of these fails, the cheaper rungs win: hybrid search with a reranker for lookups, the agent loop for occasional multi-hop questions (the root's agent runs), an NLP-indexed graph with query-time LLM work (the LazyGraphRAG shape) for occasional global questions, and SQL for anything that is already a table.

10. Structured retrieval: text-to-SQL

When the data is already a table, retrieval should be a query. Text-to-SQL asks a language model to translate the question into SQL; the database computes the answer exactly, over every row, with joins and aggregates. The model needs the schema (tables, columns, keys), and schema linking is where most errors start ("stations" in a question about the stadium table; two databases both with a singer table).

How it is scored. Execution accuracy runs the predicted and the gold query and compares results; exact match compares the SQL's parsed structure and rejects correct queries written differently. Execution accuracy has the opposite flaw, false positives: a wrong query can return the right rows on a small database by luck. Zhong et al. measured single-database execution accuracy accepting wrong queries 6.5% of the time on average across Spider submissions, up to 9.0%, and proposed test suites of extra databases ({{arXiv 2010.02840, Table 2|https://arxiv.org/abs/2010.02840}}) published.

The same method on bigger, messier databases: 86.6% falls to 5.68%

DAIL-SQL with GPT-4o, execution accuracy, as re-run by Spider 2.0's authors ({{arXiv 2411.07763 v2, Tables 4 and 5|https://arxiv.org/abs/2411.07763}}) published. The drop is mostly schema size and dialect, which is a retrieval problem.

The benchmarks, dated (Spider 1.0, BIRD, Spider 2.0, leaderboards)
  • Spider 1.0 (Yu et al. 2018): 10,181 questions, 5,693 SQL queries over 200 databases in 138 domains; the dev split (used here) is 1,034 questions over 20 databases ({{arXiv 1809.08887 v5|https://arxiv.org/abs/1809.08887}}). The best model at publication reached 12.4% exact match; prompted GPT-4o reaches 85.3 to 86.6% execution accuracy with DIN-SQL or DAIL-SQL in Spider 2.0's re-runs published. Its databases are small and clean, which is why newer benchmarks moved on.
  • BIRD (Li et al. 2023): 12,751 questions over 95 databases totalling 33.4 GB, with dirty values and "external knowledge evidence" (a hint such as which column means what). GPT-4 reached 34.88% test execution accuracy without the evidence and 54.89% with it; humans 92.96% ({{arXiv 2305.03111 v3, Table 2|https://arxiv.org/abs/2305.03111}}) published. The leaderboard's best test score read on 2026-10-14 is 82.95 (GrainSQL, dated 2026-09-26; {{bird-bench.github.io|https://bird-bench.github.io/}}) leaderboard.
  • Spider 2.0 (Lei et al. 2024): 632 enterprise tasks over BigQuery, Snowflake and local databases with hundreds of columns and dialect details. An o1-preview agent solved 21.36%; DAIL-SQL with GPT-4o, 86.6% on Spider 1.0 and 57.4% on BIRD, solved 5.68% of Spider 2.0-lite published. The leaderboard's best on Spider 2.0-lite read on 2026-10-14 is 76.23 (dated 2026-07-28; {{spider2-sql.github.io|https://spider2-sql.github.io/}}) leaderboard.

The model writes code that will run against production data: connect with a read-only role, set a statement timeout and a row limit, reject anything but SELECT (parse it; do not regex it), and enforce access with the database's own row-level security rather than with instructions in the prompt ({{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}} measures prompt-level access control leaking).
