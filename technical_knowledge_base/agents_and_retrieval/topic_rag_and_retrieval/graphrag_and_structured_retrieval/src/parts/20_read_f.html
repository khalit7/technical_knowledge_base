10. Structured retrieval: text-to-SQL

When the data is already a table, retrieval should be a query. Text-to-SQL asks a language model to translate the question into SQL; the database computes the answer exactly, over every row, with joins and aggregates. The model needs to know the schema (tables, columns, keys); matching the question's words to the right tables and columns is called schema linking, and it is where most errors start ("stations" in a question about the stadium table; two databases both with a singer table).

How it is scored. Execution accuracy runs the predicted and the gold query and compares results; exact match compares the SQL's parsed structure and rejects correct queries written differently. Execution accuracy has the opposite flaw, false positives: a wrong query can return the right rows on a small database by luck. Zhong et al. measured single-database execution accuracy accepting wrong queries 6.5% of the time on average across Spider submissions, up to 9.0%, and proposed test suites of extra databases ({{arXiv 2010.02840, Table 2|https://arxiv.org/abs/2010.02840}}) published.

The benchmarks, dated.

  • Spider 1.0 (Yu et al. 2018): 10,181 questions, 5,693 SQL queries over 200 databases in 138 domains; the dev split (used here) is 1,034 questions over 20 databases ({{arXiv 1809.08887 v5|https://arxiv.org/abs/1809.08887}}). The best model at publication reached 12.4% exact match; prompted GPT-4o reaches 85.3 to 86.6% execution accuracy with DIN-SQL or DAIL-SQL in Spider 2.0's re-runs (below) published. Its databases are small and clean, which is why newer benchmarks moved on.
  • BIRD (Li et al. 2023): 12,751 questions over 95 databases totalling 33.4 GB, with dirty values and "external knowledge evidence" (a hint such as which column means what). GPT-4 reached 34.88% test execution accuracy without the evidence and 54.89% with it; humans 92.96% ({{arXiv 2305.03111 v3, Table 2|https://arxiv.org/abs/2305.03111}}) published. The leaderboard's best test score read on 2026-10-14 is 82.95 (GrainSQL, dated 2026-09-26; {{bird-bench.github.io|https://bird-bench.github.io/}}) leaderboard.
  • Spider 2.0 (Lei et al. 2024): 632 enterprise tasks over BigQuery, Snowflake and local databases with hundreds of columns and dialect details. An o1-preview agent solved 21.36%; DAIL-SQL with GPT-4o, 86.6% on Spider 1.0 and 57.4% on BIRD, solved 5.68% of Spider 2.0-lite ({{arXiv 2411.07763 v2, Tables 4 and 5|https://arxiv.org/abs/2411.07763}}) published. The leaderboard's best on Spider 2.0-lite read on 2026-10-14 is 76.23 (dated 2026-07-28; {{spider2-sql.github.io|https://spider2-sql.github.io/}}) leaderboard. The jump from Spider to Spider 2.0 is mostly schema size and messiness, which is the retrieval problem below.

Running generated SQL safely. The model writes code that will run against production data: connect with a read-only role, set a statement timeout and a row limit, reject anything but SELECT (parse it; do not regex it), and enforce access with the database's own row-level security rather than with instructions in the prompt ({{RAG in production|n:3f85c17b0d0d81aa9ba9c0ceac9e28c1}} measures prompt-level access control leaking).

11. Tables as text, SQL plus vectors, and graph query languages

Retrieving rows as text

The alternative to writing queries is to serialise each row into text ("singer: name Rose White; country France; age 41"), or each small table into Markdown, embed it and retrieve it like a passage. That works for lookups of descriptive records (a product's specification, one customer's ticket) and fails for anything that counts, sums, ranks or joins, for the reason in section 1: the answer depends on rows that are not in the top k. Measured on the 100 Spider questions, @@sql_agg10@@ of the @@sql_agg@@ aggregates read more than 10 rows measured. A useful hybrid keeps both: rows retrievable as text for "find the record about X", the table queryable for "how many X".

SQL and vectors in one query

Where structured filters and semantic similarity meet ("cheap hotels near the sea with good reviews about quiet rooms"), put both in one engine: a vector column in the table and a query that filters with SQL and orders by distance. In PostgreSQL with pgvector: SELECT name FROM hotels WHERE price < 120 AND city = 'Nice' ORDER BY review_embedding <=> $1 LIMIT 5. The filter and the index interact (an HNSW scan can return too few rows after filtering; pgvector 0.8's iterative scans fix that), which {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}} and {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}} measure; the language model's job shrinks to extracting the filter values from the question ("self-query", on {{The retrieval pipeline|n:3c65c17b0d0d819899fde889e1e8b782}}).

Cypher and SPARQL

The same rows can live in a graph database. Spider's concert_singer database loaded into Kùzu @@kz_ver@@ (an embedded graph database that speaks Cypher, in process like SQLite; 0.11.3 is its last release: its {{repository|https://github.com/kuzudb/kuzu}} was archived in October 2025, last push 2025-10-10, read 2026-10-14, so it serves here as a teaching engine, not a recommendation) becomes @@kz_st@@ stadiums, @@kz_si@@ singers and @@kz_co@@ concerts as nodes, with @@kz_held@@ HELD_AT edges (concert to stadium) and @@kz_perf@@ PERFORMED_IN edges (singer to concert) (s_kuzu.py). The join that SQL spells out becomes a path pattern:

"List singer names and number of concerts for each singer." Spider gold SQL, then hand-written Cypher; same rows on both engines, @@kz_ok@@ example questions measured
SELECT T2.name, count(*) FROM singer_in_concert AS T1 JOIN singer AS T2 ON T1.singer_id = T2.singer_id GROUP BY T2.singer_id MATCH (s:Singer)-[:PERFORMED_IN]->(c:Concert) RETURN s.name, count(c)

Graph query languages pay off when the question is a path of unknown length ("who is connected to this account within three transfers"), which SQL expresses only with recursive common table expressions. For language models, Cypher is the harder target: on CypherBench (11 Wikidata property graphs, over 10,000 questions) the best zero-shot execution accuracy reported was 61.58% (Claude 3.5 Sonnet) and 60.18% (GPT-4o) ({{arXiv 2412.18702 v2, Table 3|https://arxiv.org/abs/2412.18702}}); Neo4j's Text2Cypher dataset has 44,387 question and query pairs for fine-tuning ({{arXiv 2412.10064|https://arxiv.org/abs/2412.10064}}) published. SPARQL over curated graphs such as Wikidata is the older form of the same idea, knowledge-graph question answering; it needs the graph's identifiers, which is why open-extraction graphs rarely use it. Temporal graphs for an agent's own memory (Graphiti and Zep) are on {{Agent memory layers|n:3f15c17b0d0d8170a200ce4476385ff5}}; how relational engines plan joins on {{Topic: databases|n:3cd5c17b0d0d815d8841ec845f5f3324}}.
