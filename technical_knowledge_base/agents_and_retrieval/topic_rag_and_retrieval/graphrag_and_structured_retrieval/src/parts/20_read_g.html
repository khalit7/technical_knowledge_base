11. Tables as text, SQL plus vectors, and graph query languages

Retrieving rows as text. The alternative to writing queries is to serialise each row into text ("singer: name Rose White; country France; age 41"), or each small table into Markdown, embed it and retrieve it like a passage. That works for lookups of descriptive records (a product's specification, one customer's ticket) and fails for anything that counts, sums, ranks or joins, for the reason in section 1: @@sql_agg10@@ of the @@sql_agg@@ Spider aggregates here read more than 10 rows measured. A useful hybrid keeps both: rows retrievable as text for "find the record about X", the table queryable for "how many X".

SQL and vectors in one query. Where structured filters and semantic similarity meet ("cheap hotels near the sea with good reviews about quiet rooms"), put both in one engine: a vector column in the table and a query that filters with SQL and orders by distance. In PostgreSQL with pgvector: SELECT name FROM hotels WHERE price < 120 AND city = 'Nice' ORDER BY review_embedding <=> $1 LIMIT 5. The language model only extracts the filter values ("self-query", on {{The retrieval pipeline|n:3c65c17b0d0d819899fde889e1e8b782}}); how the filter and an HNSW index interact (too few rows after filtering; pgvector 0.8's iterative scans) is on {{Vector indexes from the inside|n:3f85c17b0d0d81f29707c130b2ebcfb1}} and {{Search and vector databases|n:3ef5c17b0d0d815eb4caef9b4cd4d732}}.

Graph query languages pay off when the question is a path of unknown length ("who is connected to this account within three transfers"), which SQL expresses only with recursive common table expressions; for fixed short paths a relational database is often enough (on {{NoSQL in practice|n:3ef5c17b0d0d81ec8456c41e4e8f5f6b}}, section 8, Postgres was fastest up to three hops against the graph engines). For language models, Cypher is the harder target: on CypherBench (11 Wikidata property graphs, over 10,000 questions) the best zero-shot execution accuracy reported was 61.58% (Claude 3.5 Sonnet) and 60.18% (GPT-4o) ({{arXiv 2412.18702 v2, Table 3|https://arxiv.org/abs/2412.18702}}); Neo4j's Text2Cypher dataset has 44,387 question and query pairs for fine-tuning ({{arXiv 2412.10064|https://arxiv.org/abs/2412.10064}}) published. Measured here on all 45 concert_singer dev questions, same rows on both engines: Qwen3-1.7B wrote correct SQL for @@cy17b_sql@@ and correct Cypher for @@cy17b_cy@@, and only @@cy17b_cyruns@@ of the 45 Cypher queries even parse and run; Qwen3-4B, SQL @@cy4b_sql@@ against Cypher @@cy4b_cy@@ measured. Most failures are SQL habits carried into Cypher (a GROUP BY clause, a WHERE in the wrong place, two statements in one answer): a small model has seen far more SQL than Cypher, the practical argument for keeping relational data relational.

13. Depth: mistakes worth a check, and interview rehearsal

Mistakes the core does not already show (4)
  • Measuring entity resolution by eye. The graph you draw in a demo is not connected the way you think: measure link recall on a labelled sample (title and bridge pairs give it for free on HotpotQA) before trusting traversal.
  • Quoting indexing cost per chunk without the prompt. Count prompt tokens with the real prompt (s_prompt_tokens.py); the instructions, not the text, are most of the bill for small chunks.
  • Paying for gleaning without checking it. Count distinct (name, type) pairs with and without the second call on a sample before paying for it.
  • Scoring text-to-SQL by execution on one small database. Use test suites or several database states for a real evaluation.
Interview rehearsal (three design questions)

System design: an assistant over a company's contracts, CRM and support tickets that answers "which enterprise customers with renewals next quarter have open P1 tickets mentioning data loss?" Route by question type. The structured part (customers, renewals, ticket priority) is SQL over the CRM and ticketing databases: schema retrieval over table descriptions, generated SELECT on a read-only replica with row-level security per user, timeouts. The unstructured part ("mentioning data loss") is hybrid search over ticket text, filtered by the customer and ticket ids the SQL returned (or pgvector in the same query). Contract terms that matter (renewal dates, parties) are extracted at ingestion into columns, not left for retrieval. No GraphRAG unless users ask relational questions across accounts often; then an entity graph keyed on CRM ids, which solves entity resolution with the company's own identifiers. Evaluate each path separately (execution accuracy on a labelled SQL set, recall@k on tickets), log every query and its SQL, cache nothing that crosses permissions.

When would you not build a graph even though the questions are multi-hop? When they are rare (an agent loop pays per question, no index), when the corpus changes daily (re-extraction cost), or when there are no stable entities to resolve. Measure the agent first; the root's lab gives its token bill.

Text-to-SQL accuracy is 85% on Spider; why does that not predict production? Spider databases are small and clean, the schema fits the prompt and execution accuracy has false positives. Production has thousands of tables, dirty values and dialects: Spider 2.0 dropped the same methods to about 6%.

The root page's first small graph, as it was measured (moved here when the root's Agentic lab was retired, 2026-10-24; 2 min)

Recorded in the root page's src/agent (its graphrag.json, which this page's build also reads). Microsoft's graphrag package sizes its extraction prompts and thousands of calls for large hosted models; a LightRAG-style extraction with one call per paragraph gives the indexing-cost shape at a scale the laptop can run.

  • Build. The own paragraphs of the first 40 test questions were indexed LightRAG-style (Qwen3-1.7B lists entities and relations, one call per paragraph; the paragraph's title is always an entity; entities merged by normalised name), with Louvain communities (networkx; Leiden is the same idea with a guarantee of connected communities) and a summary per community of 8 or more entities. Indexing 394 paragraphs that hold 53,062 tokens of text cost 161,797 generator tokens (81,368 in, 80,429 out: about 3 tokens of work per token indexed) and 15.9 minutes of generation, plus 36,720 tokens and 99 s to summarise 92 of the 131 communities. At this rate the whole 9,760-paragraph corpus would take about 6.5 hours of extraction on the laptop; the published GraphRAG indexed about 1 million tokens of podcasts in 281 minutes with a hosted model.
  • Names. The graph has 3,160 entities, only 284 of which appear in more than one paragraph: a small model's names rarely match across paragraphs, which is why real systems add entity resolution (section 4).
  • Local use, one graph hop. Seeds are the dense top 2 paragraphs for the question; the graph adds every paragraph that mentions an entity of the seeds or of the question, ranked by their dense score. With one graph hop both gold paragraphs are in the top 3 for 29 of the 40 questions against 26 for dense search alone; at the top 2 and the top 5 the two tie (19 and 34). The gain is the bridge case: the second paragraph is reached because it mentions an entity of the first ("Viglen" through "Bordan Tkachuk").
  • Global use. No gold answers exist for a question about the whole subset, so the map-reduce answer and the top-10 answer were compared side by side, not scored; the small model makes visible mistakes in both (one global answer puts the Cleveland Browns in the NBA). This is the GraphRAG trade in miniature: a large indexing bill and a larger per-question bill for global questions, in exchange for answers that cover the corpus instead of ten passages.
