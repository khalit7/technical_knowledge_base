13. Common mistakes

Building GraphRAG for a lookup workload
The paper evaluates global sensemaking questions only. For lookups, measure hybrid plus reranker first; on the running example a noun-phrase graph lowered multi-hop recall (@@ppr_ppr_phrase_5@@ against @@ppr_dense_5@@ at 5).
Ignoring entity resolution
Exact upper-cased names (graphrag's merge) joined @@ent_full_exact_link@@ of @@ent_full_bq@@ bridge pairs in the NLP graph; the graph you draw in a demo is not connected the way you think. Measure link recall on a labelled sample before trusting traversal.
Merging too loosely to fix it
Token-subset matching joined the most pairs and was right for only @@lab_subset@@ hand-checked extra merges; every wrong merge is an edge PageRank and Leiden will use.
Quoting indexing cost per chunk without the prompt
The instructions dominate small chunks: @@ex_ratio@@ times the text for 125-token paragraphs with graphrag's prompt, before gleaning doubles the calls. Count prompt tokens with the real prompt (s_prompt_tokens.py).
Paying for gleaning without checking it
graphrag's default second "you missed entities" call doubled the extraction calls and moved distinct entities per paragraph from @@x17_d1@@ to @@x17_dall@@ with Qwen3-1.7B (the model repeated its first list). Count distinct (name, type) pairs with and without it on a sample before paying for it.
Comparing graph methods across papers
Each paper runs its rivals with its own model, prompts and judge: LightRAG beats GraphRAG narrowly in its own paper and scores F1 2.4 on HotpotQA in HippoRAG 2's re-run. Compare on your data, with the same generator.
Trusting LLM-judge win rates as accuracy
GraphRAG's 72 to 83% are pairwise preferences of an LLM judge on comprehensiveness and diversity, which reward longer, broader answers; they are not correctness. Judges and their biases are on {{LLM-as-judge|n:3c65c17b0d0d810ba2a2ecc08c4c233b}}.
Retrieving rows to answer a count
@@sql_agg10@@ of the @@sql_agg@@ aggregate Spider questions here need more than 10 rows. Query the table.
Dumping every schema into the prompt
@@sql_all_tok@@ tokens for 20 small databases; real warehouses do not fit. Retrieve tables (@@sr_bgesmall_all5@@ of 100 complete at k = 5, @@sr_bgesmall_tok5@@ tokens).
Scoring text-to-SQL by execution on one small database
Wrong queries can return right rows: 6.5% average false positives in Zhong et al.'s analysis. Use test suites or several database states for a real evaluation.
Executing generated SQL with a privileged connection
Read-only role, statement timeout, row limit, SELECT-only after parsing, and row-level security in the database, not in the prompt.

14. Interview questions

Why can't vector RAG answer "what are the main themes of this corpus"?
The answer is a property of the whole collection; top-k retrieves the k chunks most similar to the question, a sample of fragments. You need a structure built over everything (community summaries) and a map-reduce over it, or a long-context pass.
Walk through GraphRAG's indexing pipeline and say where the cost is.
Chunk (1,200 tokens), extract entities and relations per chunk with an LLM plus a gleaning call, merge by name and type, summarise multi-chunk descriptions, cluster with hierarchical Leiden, write one report per community, embed. Cost is LLM calls per chunk (prompt overhead included) plus one per community; HippoRAG 2's re-run measured about 9,900 input tokens per passage.
Leiden versus Louvain?
Both maximise modularity by local moves and aggregation; Leiden adds a refinement step that re-splits communities from singletons, guaranteeing connected communities. Louvain can leave disconnected ones (up to 16% in the Leiden paper's tests).
How does global search differ from local search and DRIFT?
Global maps the question over all community reports at one level (0 to 100 scores), keeps the scored points and reduces. Local starts from entities nearest the question and assembles their relationships, text units and reports. DRIFT primes with the most similar reports, then answers generated follow-up questions with local searches for a few rounds.
What is personalised PageRank, and why does HippoRAG use it?
A random walk that restarts at the question's entities with probability 1 - d; the stationary probabilities rank nodes by how reachable they are from the question. It ranks a passage two hops away above one that only shares words, in one step, without an LLM loop at query time.
How would you evaluate entity resolution?
Precision of merges on a labelled sample, and the recall that matters downstream: are the entity pairs your questions need connected? On HotpotQA titles and bridge pairs give both for free.
Text-to-SQL accuracy is 85% on Spider; why does that not predict production?
Spider databases are small and clean, the schema fits the prompt and execution accuracy has false positives. Production has thousands of tables, dirty values and dialects: Spider 2.0 dropped the same methods to about 6%.
System design: an assistant over a company's contracts, CRM and support tickets that answers "which enterprise customers with renewals next quarter have open P1 tickets mentioning data loss?"
Route by question type. The structured part (customers, renewals, ticket priority) is SQL over the CRM and ticketing databases: schema retrieval over table descriptions, generated SELECT on a read-only replica with row-level security per user, timeouts. The unstructured part ("mentioning data loss") is hybrid search over ticket text, filtered by the customer and ticket ids the SQL returned (or pgvector in the same query). Contract terms that matter (renewal dates, parties) are extracted at ingestion into columns, not left for retrieval. No GraphRAG unless users ask relational questions across accounts often; then an entity graph keyed on CRM ids, which solves entity resolution with the company's own identifiers. Evaluate each path separately (execution accuracy on a labelled SQL set, recall@k on tickets), log every query and its SQL, cache nothing that crosses permissions.
When would you not build a graph even though the questions are multi-hop?
When they are rare (an agent loop pays per question, no index), when the corpus changes daily (re-extraction cost), or when there are no stable entities to resolve. Measure the agent first; the root's lab gives its token bill.
