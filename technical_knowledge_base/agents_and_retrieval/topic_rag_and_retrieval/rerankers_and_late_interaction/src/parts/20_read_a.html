0. In one screen

A reranker is a second, slower and more accurate model that re-orders the short list a first retriever returns. The first stage (BM25 or a vector search, often both) looks at the whole corpus and keeps the top K candidates, say 30 out of 5,183 abstracts; the reranker reads each candidate together with the query and gives it a new score; the top few go to the language model. The idea is old (search engines have used two-stage ranking for decades) and the reason is cost: a model that reads query and document together cannot precompute anything, so it can afford to look at only a few candidates per query.

corpus (5,183 abstracts)→first stage: BM25, vectors, hybrid→top K (10 to 100)→reranker: score each (query, candidate)→top k (3 to 10)→LLM

Six ideas that carry the page

1. Cost per pair, not per query

A vector search pays one model pass per query; a reranker pays one per candidate. A reranker cannot surface what the first stage did not return: recall@K of the hybrid list is @@hy_rec10@@ at K = 10 and @@hy_rec30@@ at K = 30. Past about K = 20 to 30 quality stops rising here while cost keeps rising linearly (section 4, Depth chooser tab).

4. Scores are not probabilities

The three rerankers here return three different things (a raw logit, a sigmoid, a yes-minus-no log-odds). Thresholds do not transfer between models or domains, but a reranker's top score is a better "nothing relevant here" signal than the retriever's: AUROC @@abst_qw@@ against @@abst_cos@@ for the cosine (section 5).

Quality numbers (nDCG@10, recall) are deterministic and transfer to any machine running the same model; milliseconds and pairs per second are this laptop's, and only their ratios transfer. The running example is SciFact (BEIR): 5,183 abstracts, 300 test claims, binary labels; most claims have exactly one relevant abstract, so nDCG@10 (normalised discounted cumulative gain over the top 10: 1.0 when the relevant abstract is first, about 0.63 when it is second, 0 when it is missing) mostly measures "how high is the right abstract".

1. Why a second stage

The problem. A first-stage retriever must look at every document for every query, so it can only afford a cheap comparison. A bi-encoder (the usual "embedding model") encodes the query and each document separately into one vector each; documents are encoded once, offline, and a query costs one model pass plus N dot products. Encoding separately is also its weakness: the document vector was fixed before the query existed, so it has to summarise everything the document might be asked about in about a thousand numbers. BM25 is cheaper still and only counts shared words.

How a reranker fixes it. A cross-encoder puts the query and one document into the same transformer input, so every query token can attend to every document token in every layer, and the model outputs one relevance score for that pair. It sees "MDA5" in the claim next to "RIG-I, MDA5, and LGP2" in the abstract, rather than two summaries of them. Nothing can be precomputed, so it is run only on the first stage's top K.

One real pair: claim 1180 of the SciFact test set and its relevant abstract (PubMed 31272411).
