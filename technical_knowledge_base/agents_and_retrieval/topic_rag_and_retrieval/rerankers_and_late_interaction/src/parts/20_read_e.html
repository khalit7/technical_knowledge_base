8. Late interaction: ColBERT and MaxSim

The idea. A bi-encoder squeezes a document into one vector; a cross-encoder reads query and document together and precomputes nothing. Late interaction keeps the document side precomputable but much richer: the encoder outputs one small vector per token, stored offline, and the query and document only "interact" at the end, through a cheap score. ColBERT (Khattab and Zaharia, 2020) defines that score as MaxSim: for each query token, take its highest dot product with any document token, then add those maxima up.

score(q, d) = ∑i ∈ query tokens maxj ∈ document tokens qi · dj

Each query token looks for its own best match: "md ##a ##5" in claim 1180 finds the same three word pieces in the abstract (similarities @@ms_md@@), "sensor" finds "sensing" (@@ms_sensor@@), "rna", "virus" and "infection" find themselves. Watch it token by token, against the single-vector cosine on the same pair, in the {{MaxSim lab|#t-rrmax}} tab.

pylate 1.6.0, scores/colbert.py, lines 189-200 (the plain torch path)

scores = torch.einsum("ash,bth->abst", queries_embeddings, documents_embeddings) # every query token x every doc token if queries_mask is not None: scores = scores * queries_mask.unsqueeze(1).unsqueeze(3) if documents_mask is not None: scores = scores * documents_mask.unsqueeze(0).unsqueeze(2) scores = scores.max(axis=-1).values.sum(axis=-1) # max over doc tokens, sum over query tokens

Three details that matter, all from the paper and visible in pylate's models/colbert.py:

  • Markers. A query starts [CLS] [Q], a document [CLS] [D] (here the unused vocabulary slots [unused0] and [unused1]), so one encoder can embed both differently.
  • Query augmentation. Queries are padded with [MASK] tokens to a fixed 32 (pylate sets the pad token to the mask token, lines 411-412, and pads queries to max_length, lines 1173-1178). The [MASK] vectors are kept and scored like real tokens: a learned soft query expansion. SciFact claims have @@q_real@@ real tokens on average, so about @@q_mask_pct@@% of each query is [MASK]. Measured here: dropping them at search time moves nDCG@10 from @@cb_all@@ to @@cb_real@@, and they contribute @@mask_share@@% of the top abstract's score. Most of that share is nearly the same for every abstract (they all match the document's [CLS] at about 0.97), which is why MaxSim totals sit close together (30.25 to 30.91 for claim 1180's top 10) and the ranking is decided by the real tokens.
  • Punctuation. Document vectors for punctuation are dropped (the skiplist mask, lines 750-757), so an abstract stores fewer vectors than it has tokens.

9. PLAID: compressing and searching token vectors

The problem. One vector per token multiplies storage by the number of tokens (@@cb_tok_mean_r@@ here), and exhaustive MaxSim reads all of them. ColBERTv2 compresses each token vector as the id of its nearest k-means centroid plus the residual (vector minus centroid) quantised to 1 or 2 bits per dimension: "this total of 20 or 36 bytes per vector" at 128 dimensions against 256 bytes in float16, a 6 to 10 times smaller index. PLAID then searches without decompressing everything: (1) each query token picks its nearest centroids and the documents with tokens in them become candidates; (2) and (3) candidates are scored with centroid interaction, MaxSim with every token replaced by its centroid, pruning centroids that score low for every query token; (4) only the survivors are decompressed and scored exactly. PLAID's Table 3 reports 39.8 MRR@10 on MS MARCO at k = 100 in 222 ms on one CPU core and 20 ms on a GPU, against 4,569 ms on 8 cores for vanilla ColBERTv2 (published, academic, 2022).

Measured here with fast-plaid 1.4.6 (the PLAID engine pylate uses) on the stored SciFact vectors, CPU, seed 42 (e_plaid.py):

What it shows. The quality cost of compression is small: nDCG@10 @@pl2_best@@ at 2 bits and @@pl4_best@@ at 4 bits against @@cb_all@@ exhaustive, though only @@pl2_ov@@% (2 bits) and @@pl4_ov@@% (4 bits) of the exact top 10 are reproduced exactly. Of the two search knobs, the number of candidates fully scored is the one that matters here: with @@pl_full_lo@@, nDCG@10 drops to @@pl2_lo@@ and only @@pl2_lo_ov@@% of the exact top 10 survive; from @@pl_full_hi@@ on it is back. The number of centroids probed barely matters on 5,183 abstracts, because even one centroid per query token, times 32 query tokens, already reaches most of the relevant candidates; on millions of passages it does. Storage per token falls from 192 bytes to @@pl2_tok@@ bytes of residual codes plus a centroid id (fast-plaid stores the id as an 8-byte integer; ColBERTv2's paper counts 4 bytes): @@pl2_mb@@ MB for the corpus with centroids and inverted lists, @@pl2_x@@ times less than float16. fast-plaid also keeps a merged second copy of codes and residuals for search, so its folder is @@pl2_disk_mb@@ MB. On 5,183 abstracts none of this is needed (exhaustive MaxSim is already fast); PLAID is for millions of passages.
