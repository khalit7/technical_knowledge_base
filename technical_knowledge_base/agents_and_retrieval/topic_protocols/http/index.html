HTTP is the language your code and an LLM API speak: a request ("do this to that thing") and a response ("here is the result, and here is what you may do with it"). The meaning of that language has been stable for decades. What changed, three times, is how the words are cut into bytes on the wire, and every change was made to stop one slow or lost thing from holding up everything behind it.

The running example. A chat app sends "What colour is the sky?" as one streaming request, POST /v1/messages with a 117-byte JSON body, and the answer comes back as five tokens, one every 50 ms after a 120 ms wait that stands in for the model reading the prompt. The server is the root page's stand-in (its On the wire tab built it), run here with a few extra knobs: a longer think time, keep-alive pings, injected errors. No model runs and no real API is called, except one read-only request to three public LLM hosts in section 10.

Five things to remember
  1. Meaning (RFC 9110) and wire format (RFC 9112, 9113, 9114) are specified separately: your code sees the meaning, your latency and your proxies see the wire.
  2. Every version fixed one kind of head-of-line blocking: HTTP/1.1 requests queue behind each other on a connection, HTTP/2 streams queue behind a lost TCP packet, HTTP/3 removes that.
  3. A proxy is a full HTTP participant: it re-parses, rewrites, re-frames and times out. Two parsers that disagree about where a message ends are a security hole (request smuggling).
  4. Know every timeout on the path and whether it counts silence or total time.
  5. Retries are a protocol question first: did the server start the work? If you cannot know, you need an idempotency key.

1. A message, piece by piece

The problem. Two programs that have never met need to agree on what is being asked, about which thing, with what extra conditions, and where the request ends. HTTP's answer is a message: a start line, a list of header fields (name, colon, value), a blank line, and an optional body. The program that sends requests is the client; the one that answers is the server, and the server that actually owns the resource (here, the model API) is the origin. Everything in between that receives a message and sends it on is an intermediary; each leg between two of them is a hop.

The URL, split. https://api.llm.test/v1/messages has a scheme (https: HTTP over TLS, default port 443), an authority (api.llm.test, the host and an optional port) and a path (/v1/messages), optionally followed by a query (?limit=20). HTTP/1.1 puts the path in the start line and the authority in the Host field; HTTP/2 and HTTP/3 carry all of them as pseudo-headers (:method, :scheme, :authority, :path), fields whose names start with a colon. One server can host many names, which is why Host is mandatory: an HTTP/1.1 request without it gets 400 (RFC 9112 section 3.2; measured both nginx and hypercorn answered 400, section 7).

Where does the body end? A connection is a byte stream with no built-in boundaries, so every HTTP version must say where a body stops. HTTP/1.1 has three ways: a Content-Length (the request above: 117), chunked transfer coding (the response above: each piece prefixed by its size in hexadecimal, ending with a zero-size chunk), or closing the connection. HTTP/2 and HTTP/3 instead put the body in DATA frames and mark the last one with an end-of-stream flag. Getting this boundary wrong is the root of the worst HTTP bugs (request smuggling).

2. Meaning: methods, status codes, header fields

The problem. A client must be able to talk to a server it has never seen, through intermediaries that know nothing about the application, and everyone must agree on what a request asks for and what an answer means. RFC 9110 (HTTP Semantics, June 2022) defines that shared meaning once, for every version. It is the one HTTP document worth reading end to end.

Methods, and the two promises that decide retries

A method names the kind of operation. Two properties matter more than the names. A method is safe if the client asks for no change on the server (reading). It is idempotent if sending it twice has the same intended effect as sending it once: "PUT, DELETE, and safe request methods are idempotent" (RFC 9110 section 9.2.2). Idempotent requests can be repeated after a network error without asking whether the first one ran; that is the whole reason the property exists.

The consequence for LLM APIs
Generation is a POST, so it is neither safe nor idempotent. If the connection breaks after the request left, the client cannot know whether the model is already generating (and billing). Section 9 shows what the official SDKs do about it (they retry anyway) and what the protocol offers to make it safe.

Status codes: the first thing a client reads

A status code is three digits whose first digit is its class: 1xx informational (more is coming), 2xx success, 3xx go elsewhere, 4xx the request is wrong, 5xx the server or something in front of it failed. Clients must treat an unknown code as the x00 of its class, which is why APIs can invent codes such as 529 and still be understood as "server error" (RFC 9110 section 15). Predict, then reveal

A streamed request returns HTTP/2 200, three tokens arrive, then the stream carries an overloaded_error event and ends. What status code did the request "have"?

200. The status line goes out with the response head, before any of the body, so a failure later in a stream can only be reported inside the body (an SSE error event) or by cutting the connection. Logs and dashboards that count status codes record this request as a success: count stream-level errors separately. (HTTP does allow trailer fields after a body, but status is not one of them, and SSE clients do not read trailers.)

Header fields: everything else

Header fields carry the rest, and they fall into a few families. Representation: content-type (what the body is: application/json, text/event-stream), content-length, content-encoding (gzip, br, zstd). Negotiation: accept, accept-encoding (what the client can take; the server picks and says so). Credentials: authorization, or an API's own such as x-api-key. Caching and conditions: cache-control, etag, if-none-match. Limits and hints: retry-after, rate-limit headers. Connection management: connection, keep-alive, transfer-encoding, upgrade, which apply to one hop only and which proxies must strip (section 7). Field names are case-insensitive; HTTP/2 and HTTP/3 require them in lower case on the wire, which is why the same request shows Content-Type on one hop and content-type on the next.

Content negotiation in LLM APIs. One endpoint can answer in two shapes: with "stream": true in the body, the Claude and OpenAI APIs answer text/event-stream; without it, one application/json body at the end. MCP's Streamable HTTP transport uses the Accept header for the same choice on one endpoint (MCP). Compression is negotiated the same way, and it has a streaming trap: a proxy that gzips an event stream may hold tokens until it has enough bytes to compress (the root page's Failure lab reproduces this as "A buffering proxy delays tokens").

3. Caching and conditional requests

The problem. Fetching the same unchanged thing again wastes time and bandwidth: a model list, a 2 GB weights file, a tokenizer. HTTP lets any client or intermediary keep a copy (a cache) and says, in the response itself, how long the copy may be used and how to check it cheaply afterwards (RFC 9111, HTTP Caching).

How it works. Two mechanisms, used together. Freshness: Cache-Control: max-age=60 says the copy may be reused without asking for 60 s (s-maxage applies to shared caches such as CDNs only; private forbids shared caches; no-store forbids keeping it at all). Validation: once stale, the client asks "has it changed?" by sending back a validator the server gave it, an ETag (an opaque version tag) in If-None-Match, or a date in If-Modified-Since; the server answers 304 Not Modified with no body if not. no-cache, despite its name, means "store it, but validate before every use". Vary: Accept-Encoding tells caches to keep a separate copy per value of that request header.

measured The lab server's GET /v1/models, then the same request with the ETag it returned (curl -v; lines with > were sent, < received):



The second answer carries no body: on a 2 GB file that is the difference between a round trip and a download. Download tools for model weights rely on exactly this (they compare an ETag or a hash before fetching again).


What it costs, and when not to use it. A cache serves what was true when it was stored: a stale model list after a deployment, or worse, one user's response served to another if a private answer is cached by a shared proxy. Generation responses are unique per request and are sent with no-store or no-cache (the root's recording shows cache-control: no-cache on the stream). Provider prompt caching is a different mechanism entirely (the model server reuses computed state for a repeated prefix) and has nothing to do with these headers.

4. HTTP/1.1: text on a connection, one request at a time


The problem it solved. HTTP/1.0 (1996) opened a new TCP connection per request, paying a handshake each time. HTTP/1.1 (1997; today RFC 9112) made connections persistent by default (keep-alive): after one response ends, the next request can go on the same connection. That is why the body boundary (section 1) is so important: the receiver must know exactly where one message ends to read the next.


How it works. Messages are lines of text ending in CR LF. A response body is delimited by Content-Length, by chunked coding (needed whenever the length is unknown when the headers go out, as for a stream of tokens), or by closing the connection. Chunks can be followed by trailer fields, headers sent after the body (gRPC relies on the HTTP/2 equivalent to send its status). Expect: 100-continue lets a client ask "will you take this big body?" before sending it. Upgrade switches the connection to another protocol (that is how a WebSocket starts; Streaming and real-time).


What it costs: head-of-line blocking at the HTTP layer. On one connection, responses must come back in the order the requests were sent. A client may send the next request before the previous answer arrives (pipelining), but a slow first answer then holds up every answer behind it. Browsers never enabled pipelining by default, and opened about six connections per host instead; HTTP client libraries keep a connection pool for the same reason. When HTTP/1.1 is the right choice. Very often still: one request at a time per connection is fine for a service that makes a few long calls (most LLM generations), every tool understands it, and you can read it with nc. Python's requests speaks only HTTP/1.1, and httpx needs http2=True (and the h2 package) for HTTP/2; measured the official Anthropic (1.11.0) and OpenAI (3.24.0) Python SDKs, built on an httpx fork, spoke HTTP/1.1 to the lab server over TLS even though it offered HTTP/2, and HTTP/2 only when given a client with http2=True (raw/sdk_version.json). For a handful of long generations that costs nothing; for an agent firing dozens of parallel calls it means dozens of connections.


How it fails
Symptom: a keep-alive connection the client reuses is closed by the server at the same moment, and the next request fails with "connection reset" or "server disconnected". Cause: the server's idle keep-alive timeout is shorter than the client pool's. See it: the error appears only after idle periods, on the first request. Fix: client keep-alive shorter than the server's; retry idempotent requests on a fresh connection. Reproduced in the root's Failure lab ("Reused keep-alive connection closed by the server"); AWS documents the same race producing 502s behind its load balancer (section 8).







5. HTTP/2: binary frames, many streams, compressed headers


The problem it solved. HTTP/1.1 needs one connection per request in flight and repeats hundreds of bytes of identical headers on every request. HTTP/2 (2015, from Google's SPDY; today RFC 9113, June 2022) keeps the same meaning and changes only the wire: one connection carries many requests at once, and headers are compressed against what both sides already sent.


How it works: frames on streams


Everything on an HTTP/2 connection is a frame: a 9-byte header (length 24 bits, type 8, flags 8, one reserved bit, a 31-bit stream identifier) followed by up to 16,384 bytes of payload unless the peer allows more. A stream is one request and its response; the client numbers its streams 1, 3, 5 (odd), so frames of different streams can interleave and the receiver sorts them by number. Stream 0 is the connection itself. A connection over TLS is chosen by ALPN (the client offers h2 in the TLS handshake; TLS and certificates); the client then sends a fixed 24-byte connection preface (PRI * HTTP/2.0 ...), and both sides send SETTINGS.

HPACK: why the second request's headers cost 7 bytes


The problem. Requests to one API repeat the same header fields: the same host, path, content type, API key, user agent. HPACK (RFC 7541, May 2015) compresses them with three tools: a static table of 61 common fields both sides know by heart (index 2 is :method: GET, 3 is :method: POST), a dynamic table (4,096 bytes by default) to which each side adds fields as it sends them, so a repeat becomes a one-byte index, and a fixed Huffman code that shrinks literal text (by 26% on the SDK header values below: 164 bytes of values became 121). Security: secrets in a compression table
Compression leaks information when an attacker can mix guesses with a secret and watch the size (the CRIME and BREACH attacks on TLS and HTTP compression). HPACK was designed against this: literal fields can be marked never indexed, so they are sent in full every time and no intermediary may add them to a table (RFC 7541 section 7.1.3). measured The h2 library marks authorization never-indexed automatically (the "Bearer" set above costs 32 bytes on every request instead of 7), but not x-api-key, which it added to the dynamic table on the first request. HPACK's per-connection table and fixed Huffman code make the attack far harder than with gzip, so this is defence in depth, not an open hole; but a library's list of "sensitive" headers is worth knowing when your API key travels in a custom header.


Flow control: a window, and credit returned by WINDOW_UPDATE


The problem. Many streams share one connection, so a receiver needs a way to say "slow down on this one" without stopping the others (TCP's own flow control can only throttle the whole connection). HTTP/2 gives each stream, and the connection as a whole, a window: the number of DATA bytes the sender may send before it must wait. The receiver adds credit back with WINDOW_UPDATE frames as it consumes data. The cost: a stream can never move more than one window per round trip, so throughput is at most window divided by round-trip time, whatever the link's bandwidth.














measured A 200,000-byte GET /big from the lab server over HTTP/2 (src/lab/flow_h2.py, raw/flow_h2.json): every DATA frame and every WINDOW_UPDATE with its time. simulated Loopback has almost no round trip, so the client holds each WINDOW_UPDATE for 50 ms, standing in for one; the server's behaviour is real. derived Expected time is about ceil(200,000 / window) × 50 ms when the window is the limit.




The default 65,535-byte window is small for a fast long path: at 100 ms round trip it caps one stream at about 0.65 MB/s. Servers that move large bodies raise it (SETTINGS_INITIAL_WINDOW_SIZE for streams, a WINDOW_UPDATE on stream 0 for the connection, which always starts at 65,535). The root page's Failure lab measures the same cap on a real path ("One stream's throughput is capped at window / round trip"); for token streams of a few KB it never matters.

  • Priorities. RFC 7540 let clients build a dependency tree of streams with weights.   • Server push. The server could send responses the client had not asked for yet.   • Upgrading a cleartext connection to h2c. The Upgrade: h2c dance from HTTP/1.1 is deprecated in RFC 9113 (section 3.1). Cleartext HTTP/2 itself is alive inside clusters, started with "prior knowledge" (the client just sends the preface): that is how much gRPC traffic runs.

Ending streams and connections, safely


RST_STREAM cancels one stream (a user pressed stop; a client gave up). GOAWAY starts a graceful shutdown: it carries the highest stream number the server may have processed. This is HTTP/2's gift to retries: requests on higher-numbered streams "are therefore guaranteed to be safe to retry", and so is any request reset with the REFUSED_STREAM code, "even those with non-idempotent methods" (RFC 9113 section 8.7). A server being deployed should send GOAWAY and let in-flight streams finish; a client should retry what GOAWAY says was never started (section 9).


How it fails, and how it was attacked


    

  • One lost TCP packet stalls every stream. All streams share one TCP byte stream, which must be delivered in order; the root page's On the wire tab measured one lost packet delaying all three concurrent streams by 43 to 68 ms. This is what HTTP/3 fixes.
    • 

  • Streams queue on a connection. When a client opens more than SETTINGS_MAX_CONCURRENT_STREAMS (100 here), the rest wait for a free slot; the root's Failure lab shows calls queuing ("Max concurrent streams").
    • 

  • One connection, one backend. A long-lived HTTP/2 connection through a connection-level (L4) load balancer pins every request to one backend (Service APIs; Failure lab "gRPC behind an L4 load balancer").
    • 

  • Rapid Reset (CVE-2023-44487). An attacker opens a stream and immediately cancels it with RST_STREAM, again and again: cancelled streams do not count against the concurrency limit, but the server has already started work on each. Cloudflare saw a peak just above 201 million requests per second from about 20,000 machines; Google saw 398 million (Cloudflare, 10 Oct 2023; Google Cloud). Fix: servers now count resets and close abusive connections.
    • 

  • CONTINUATION flood (April 2024). HEADERS followed by endless CONTINUATION frames without END_HEADERS makes a server buffer headers forever; one connection could crash many implementations, and because no request ever completes, nothing appears in access logs (Nowotarski, 3 Apr 2024).
    •

6. HTTP/3: the same streams on QUIC


The problem it solved. HTTP/2 removed the queue between requests but kept one underneath: TCP delivers one ordered byte stream, so a single lost packet holds every stream until it is resent. HTTP/3 (RFC 9114, June 2022) moves HTTP/2's idea onto QUIC, a transport over UDP with TLS 1.3 built in and many independently ordered streams (RFC 9000; the transport itself is on Networking foundations). A lost packet now stalls only the stream it belonged to, and connection setup takes one round trip instead of two.


How it works. Each request is one client-opened bidirectional QUIC stream (numbers 0, 4, 8, ...), carrying HTTP/3 HEADERS and DATA frames. Frame types and lengths are QUIC variable-length integers rather than HTTP/2's fixed 9-byte header, and stream ids live in QUIC, not in the frame. Settings and other connection-level business move to unidirectional streams that each side opens once. measured In the recorded connection the client opened its control stream (id 2, carrying SETTINGS), a QPACK encoder stream (6) and a QPACK decoder stream (10); the server opened the same three as 3, 7 and 11 (raw/h3_frames.json).


QPACK, and why HPACK could not be reused. HPACK assumes both sides see header blocks in exactly the order they were sent; QUIC streams arrive in any order, so a block could refer to a table entry the decoder has not received yet. QPACK (RFC 9204) moves table insertions onto the dedicated encoder stream and lets the encoder choose, per request, between referring only to entries the decoder has acknowledged (never blocks) or to newer ones (smaller, but the request waits if the insertion has not arrived: a blocked stream, limited by QPACK_BLOCKED_STREAMS). measured aioquic's encoder sent request 1 with the static table only (59 bytes, plus 3 bytes on the encoder stream to set the table size), then inserted the fields on the encoder stream (53 bytes) and sent request 2's headers in 9 bytes that referred to those not-yet-acknowledged entries. Toggle QPACK in the header animation above to compare.


How a client finds HTTP/3. It cannot know a server speaks QUIC on UDP before trying, so servers advertise it: an Alt-Svc: h3=":443"; ma=86400 response header ("HTTP/3 is available on UDP 443; remember for a day", RFC 7838) or an HTTPS record in DNS (RFC 9460; DNS). Browsers then race QUIC against TCP and keep the winner. measured on 5 October 2026: api.openai.com and generativelanguage.googleapis.com advertised h3 in Alt-Svc; api.anthropic.com did not; curl negotiated HTTP/2 with all three (section 10).


0-RTT and 425. A client that has talked to a server before can send its first request inside the very first packet (TLS early data, 0-RTT). An attacker who copies that packet can replay it, so the request must be safe to repeat; a server that will not take the risk answers 425 Too Early and the client resends after the handshake (RFC 8470). Never let a POST that starts a generation be accepted as early data.


What it costs, and when not to use it. QUIC runs in user space and encrypts nearly every header, so it costs more CPU per byte than kernel TCP, and the usual packet tools see little. UDP 443 is blocked or throttled on some corporate networks, which forces a fallback to TCP after a delay. Between your own services in a data centre, where loss is rare, HTTP/2 over TCP is simpler and as fast; HTTP/3 pays off on lossy, mobile and long-distance client links.

Four things to notice. The version changed: the client spoke HTTP/2, the backend got HTTP/1.1, because the proxy terminates one connection and opens another. Host was rewritten to the upstream's address unless configured (nginx's proxy_set_header Host $host; note that $host drops the port). The client's address is gone: the backend sees the proxy's, unless the proxy adds X-Forwarded-For (or the standard Forwarded, RFC 7239); trust those headers only from your own proxies, since any client can send them. Header order and case changed, which is harmless but breaks anything that signs raw header bytes.


Hop-by-hop headers. Some fields describe one connection, not the request: Connection and every field it names, Keep-Alive, Transfer-Encoding, TE, Upgrade, Proxy-Authorization. A proxy must not forward them (RFC 9110 section 7.6.1), and HTTP/2 and HTTP/3 forbid them outright: measured nginx 1.31.6 answered 400 to an HTTP/2 request carrying transfer-encoding, a rule added in nginx 1.31.0 (13 May 2026).


Docs disagree with the software: nginx's upstream defaults changed in 2026
nginx's proxy module page still lists proxy_set_header Connection close as a default, and older guides say nginx talks HTTP/1.0 to the backend. Since nginx 1.29.7 (24 March 2026) "the default value for proxy_http_version is 1.1; the Connection proxy header is not sent by default anymore", and upstream keep-alive is on by default (nginx CHANGES, kept in src/inputs/nginx_changes_excerpt.txt). measured The capture above, with nothing but proxy_pass configured, shows HTTP/1.1 and no Connection header. Configurations copied from older guides that add proxy_set_header Connection "" are now harmless but redundant.


Buffering. By default nginx reads the upstream's response into buffers before sending it on (proxy_buffering on), which for a token stream means the user sees nothing, then everything. Turn it off for streaming locations, or let the app send X-Accel-Buffering: no (nginx proxy module); the ingress-nginx controller defaults to proxy-buffering: off (ConfigMap docs). The root's Failure lab measures the delay ("A buffering proxy delays tokens").


Request smuggling: two parsers, two answers


The attack. A front proxy and a backend share one keep-alive connection for many users' requests. If they disagree about where a request ends, an attacker can send one request that the proxy sees as one message and the backend as two: the hidden second request is then glued to the front of the next user's request on that connection. It bypasses the proxy's checks and can capture another user's request. The classic disagreement is a message with both Content-Length and Transfer-Encoding: chunked.






illustrative drawing of the bytes of the first probe below: a parser that trusts Content-Length (4) reads 4 bytes of body and leaves the rest on the connection; one that follows chunked coding reads the empty chunk 0 and sees a second request, GET /smuggled.




The rules are strict: a server receiving both "MAY reject" the request or use Transfer-Encoding alone, and "Regardless, the server MUST close the connection after responding" (RFC 9112 section 6.3). measured Eight ambiguous HTTP/1.1 messages and three HTTP/2 ones, sent raw to nginx 1.31.6 (in front of the recording backend) and to hypercorn 0.18.0 (the lab server, parser h11 0.16.0):




A finding, not a vulnerability report
nginx refused every ambiguous message with 400 or 501 and forwarded nothing. hypercorn followed Transfer-Encoding, answered 400 to the (empty) POST, and then answered the hidden GET /smuggled as a second request on the same connection, where RFC 9112 section 6.3 says it MUST close the connection. Behind nginx this cannot be exploited, because nginx rejects such messages first; behind a front proxy that trusted Content-Length it would be the textbook desync. The lesson is general: run a strict proxy in front, keep the same parser behaviour on every hop, and prefer HTTP/2 end to end where you can. AWS's ALB ships a "desync mitigation mode" for exactly this, defensive by default (ALB attributes).


HTTP/2 at the front does not remove the problem when the back hop is HTTP/1.1: a header value containing CR LF, or a content-length that disagrees with the DATA frames, can become two requests after the downgrade (James Kettle, "HTTP/2: The Sequel is Always Worse", PortSwigger, 5 Aug 2021). measured nginx rejected all three HTTP/2 probes with 400 and passed nothing on.

The trap in that table
Two hops count total time: Google Cloud's 30 s backend service timeout and API Gateway's 29 s. Behind either, a generation longer than 30 s fails even when it streams perfectly, and no amount of pings helps; raise the limit, or switch to the async shape (submit, get a job ID, poll or receive a webhook). Envoy's 15 s route timeout is total too, and is usually the first thing to bite a streaming service behind Istio.


Keep-alive timeouts in the wrong order. AWS spells out the classic one: if the application closes idle connections sooner than the load balancer does, the balancer "might send a request to the application before it receives the packet indicating that the connection is closed", and the client gets a 502; keep the application's idle timeout larger than the balancer's (ALB docs). The rule generalises: each hop's keep-alive idle timeout should be longer than that of the hop in front of it.


Predict, then reveal


A model thinks for 45 s before its first token, then streams for 3 minutes. The path is: Anthropic SDK (defaults), then an AWS ALB (defaults), then nginx (defaults), then the model server. The server sends the 200 head immediately and nothing else until the first token. What happens?




Works, but only just. The longest silence is the 45 s think; nginx (60 s idle), the ALB (60 s idle) and the SDK (600 s idle) all reset on every token, so the 3-minute stream is fine. Push the think to 70 s and the first hop to hit 60 s of silence (nginx behind the ALB here, both at 60) closes the connection: the client sees a cut stream under a 200. Fixes, in order of preference: send an SSE keep-alive comment every 15 to 30 s while thinking (what the Claude API's ping events do), or raise every idle timeout on the path above the longest expected silence. 9. Retries and idempotency, at the protocol level


The problem. A request failed. Should the client send it again? If the server never started, yes. If it finished but the answer was lost, a retry does the work twice: two generations billed, two tool calls executed, two orders placed. What the official SDKs actually do (measured)


The Anthropic (1.11.0) and OpenAI (3.24.0) Python SDKs share one generated base client. Its source, read in the installed packages, retries on connection errors, timeouts, 408, 409, 429 and every 5xx, twice by default; waits 0.5 s, then 1 s, up to 8 s, each multiplied by a random factor between 0.75 and 1 ("jitter"); and obeys retry-after-ms, Retry-After and a non-standard x-should-retry: true|false header from the server. measured Pointed at the lab server with errors injected, every attempt the server received:

What this means
On a read timeout (1 s client timeout, a server that takes 2.5 s) and on a connection dropped after the request was sent, both SDKs sent the same POST three times, and no attempt carried an idempotency key: the base client has an idempotency header slot, but neither SDK sets it. Against a real API each of those attempts may run a full generation. That is a deliberate trade (a dropped request is retried rather than failed), and the Claude API's docs describe the retry behaviour; but it means a client timeout shorter than the model's real latency multiplies load and cost by up to three. Set the SDK timeout above the longest expected generation, or stream. Note also the server's role: api.anthropic.com answered our credential-free request with x-should-retry: false on its 401 (section 10), telling the SDK not to bother.


Making a POST safe to retry. The client sends a unique idempotency key header with the POST; the server stores the key with the result and, on a retry with the same key, returns the stored result instead of doing the work again (Stripe's design). The IETF draft that would standardise an Idempotency-Key header reached revision 07 and expired without becoming an RFC (Datatracker), so each API defines its own. The server side, including the hard case of work outside your database, is on Building a backend API; retry budgets, backoff and the retry storms they prevent are on Reliability engineering.


Predict, then reveal


A deployment sends GOAWAY with last stream id 41 on an HTTP/2 connection where your client had streams 39, 41 and 43 in flight, all POSTs. Which may it retry automatically?




Only 43. GOAWAY carries "the highest stream number that might have been processed", so 39 and 41 might have run and are unknown; 43 is guaranteed untouched and "can be safely retried", POST or not (RFC 9113 section 8.7). This is why graceful HTTP/2 shutdown loses nothing: the server finishes 39 and 41, the client moves 43 to a new connection.

A checklist for calling a model over HTTP


    

  • Stream long generations. It keeps idle timeouts happy, gives a first token early, and is what the Claude docs recommend for requests that could exceed 10 minutes; for anything that can wait, use the batch API (the 202-and-poll shape).
    • 

  • Handle errors in the stream, not only the status code (section 2).
    • 

  • Set your client timeout above the slowest real generation, and know that the SDK will retry a timeout twice (section 9).
    • 

  • Read the rate-limit headers. On a 429, wait retry-after seconds; the Claude API also sends anthropic-ratelimit-requests-remaining, -tokens-remaining and their reset times on every response (rate limits), which lets a client slow down before it is refused. A 429 from a spend cap carries no retry-after and will not clear by retrying.
    • 

  • Log the request id (request-id on the Claude API) with every failure; it is what support will ask for.
    • 

  • Reuse connections. One client object per process, not per call: a new connection costs the TCP and TLS round trips again (the root measured 108 ms against 54 ms to the first byte on a 50 ms path). In serverless functions, create the client outside the handler.
    • 

  • Behind your own proxy: buffering off for streams, idle timeouts above the longest think, keep-alive timeouts ordered, no total timeout shorter than the longest generation.
    • 

  • Serving a model yourself (vLLM and Ollama, for example, expose OpenAI-style HTTP APIs): send the response head and periodic SSE comments early, so every proxy in front sees bytes; return 429 or 503 with Retry-After when the queue is full instead of letting requests time out.

Common mistakes


Treating 200 as success for a stream
The status goes out before the first token. Count in-stream error events as failures.


Setting a short client timeout "to fail fast" on generations
The SDK retries it twice, so the server may run the same request three times (measured in section 9). Fail fast on connect, not on read.


Streaming behind a total timeout and expecting it to help
Google Cloud's backend service timeout, API Gateway's integration timeout, Envoy's route timeout and curl --max-time count the whole response.


Trusting X-Forwarded-For from anyone
Any client can send it. Take the address appended by your own outermost proxy, and only from proxies you run.


Retrying on 301 or 302 with a POST
Clients may turn the POST into a GET and drop the body; APIs that move use 307 or 308.


One HTTP client per request
Every call pays a new TCP and TLS handshake and leaves sockets in TIME_WAIT. Create one client and reuse it.


Assuming HTTP/2 because the server supports it
The Python SDKs and requests speak HTTP/1.1 unless told otherwise (measured in section 4).







12. Interview questions, with model answers


What happens, at the HTTP level, when I call an LLM API with stream=true?
The SDK opens (or reuses) a TLS connection, ALPN picks HTTP/1.1 or HTTP/2, and it sends POST /v1/messages with a JSON body and credentials in a header. The server answers 200 with content-type: text/event-stream right away, then writes SSE events as tokens are produced: as chunked coding on HTTP/1.1, as DATA frames on HTTP/2. The status is fixed before the first token, so later failures arrive as error events. Every proxy on the path must forward bytes as they come (no buffering) and must not hit its idle timeout between events.


HTTP/1.1 vs HTTP/2 vs HTTP/3: what does each fix, and what does each still cost?
Same semantics (RFC 9110), different framing. HTTP/1.1: text, one outstanding response per connection, so clients open several connections; headers repeated in full. HTTP/2: binary frames, many streams on one TCP connection, HPACK header compression, per-stream flow control; still stalls every stream on one lost TCP packet, and one long connection can pin a backend behind an L4 balancer. HTTP/3: the same over QUIC, so a loss stalls only its own stream and setup is one round trip; costs more CPU, UDP may be blocked, fewer tools. Inside a data centre HTTP/2 is the usual answer; HTTP/3 pays on lossy client links.


Our streaming endpoint works locally but users see the whole answer at once in production. Why?
Something on the path buffers the response: nginx's default proxy_buffering on, a compression filter that waits for enough bytes, a serverless platform that does not stream, or a CDN rule. Check hop by hop with curl -N and timestamps; fix with proxy_buffering off or X-Accel-Buffering: no on that location, no gzip on text/event-stream, and send an early byte.


Long generations fail after exactly 60 seconds. Walk me through it.
A round number means a configured timeout. 60 s is nginx's proxy_read_timeout, ingress-nginx's default and the AWS ALB idle timeout. If the failure depends on silence (a long think before the first token) it is an idle timeout: send SSE keep-alive comments and raise it. If it depends on total length even while tokens flow, it is a total timeout (Envoy route 15 s, Google Cloud backend 30 s, API Gateway 29 s): raise it or go asynchronous. A cut stream under a 200 means the head had passed; a 504 means it had not.


When is it safe to retry a failed POST?
When the server provably did not process it: connection refused, TLS failure, REFUSED_STREAM, a stream above GOAWAY's last stream id, 425 Too Early, 429 or 503 with Retry-After. A reset or timeout after the request was sent is ambiguous, so retry only with an idempotency key the server honours. Use capped exponential backoff with jitter and honour Retry-After; budget retries so layers do not multiply them.


What is HTTP request smuggling and how do you prevent it?
A front proxy and a backend that disagree about where a request ends (Content-Length against Transfer-Encoding, duplicate lengths, malformed chunking, CR LF injected through an HTTP/2 to HTTP/1.1 downgrade) let an attacker hide a second request that is then prefixed to another user's. Prevent it by rejecting ambiguous messages at the edge (nginx does, measured here), closing connections after any ambiguity as RFC 9112 requires, using the same strict parser on every hop, and HTTP/2 end to end where possible.


Why does HTTP/3 need QPACK instead of HPACK?
HPACK assumes header blocks are decoded in the order they were sent, which TCP guarantees. QUIC streams arrive independently, so a block could reference a dynamic table entry the decoder has not seen. QPACK sends table insertions on a separate encoder stream and lets the encoder choose between references the decoder has acknowledged (never blocks) and newer ones (smaller, may block, capped by QPACK_BLOCKED_STREAMS).


What is the difference between 502, 503 and 504?
All three are usually written by a proxy about the hop behind it. 502 Bad Gateway: the upstream answered with something invalid or closed the connection (often a keep-alive race or a crashed backend). 503 Service Unavailable: no healthy upstream, or the server is shedding load, ideally with Retry-After. 504 Gateway Timeout: the upstream did not answer within the proxy's timeout. Each points at a different fix, so find which hop wrote it.

Does the model match reality?


The same model, run on the cases measured for the Reading (nginx 1.31.6 with a 2 s idle timeout, curl and httpx against the lab server), predicts each outcome independently; the measurement is not an input.




model Assumptions, stated: the server sends the response head the moment it accepts a streamed request (the lab server does; most streaming APIs do) and nothing else until the first token, unless pings are on; an idle timer starts when the request is sent and restarts on every byte; a first-byte timer stops when the head arrives; a total timer never restarts. Real hops add detail this leaves out: connect and TLS timeouts, keep-alive races, proxies that buffer and so delay bytes to the next hop, and retries by intermediaries. Python check: src/recompute.py runs the same model on the same cases.
