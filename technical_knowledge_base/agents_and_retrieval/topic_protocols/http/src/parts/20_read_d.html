5. HTTP/2: binary frames, many streams, compressed headers

The problem it solved. HTTP/1.1 needs one connection per request in flight and repeats hundreds of bytes of identical headers on every request. HTTP/2 (2015, from Google's SPDY; today {{RFC 9113, June 2022|https://www.rfc-editor.org/rfc/rfc9113}}) keeps the same meaning and changes only the wire: one connection carries many requests at once, and headers are compressed against what both sides already sent.

How it works: frames on streams

Everything on an HTTP/2 connection is a frame: a 9-byte header (length 24 bits, type 8, flags 8, one reserved bit, a 31-bit stream identifier) followed by up to 16,384 bytes of payload unless the peer allows more. A stream is one request and its response; the client numbers its streams 1, 3, 5 (odd), so frames of different streams can interleave and the receiver sorts them by number. Stream 0 is the connection itself. A connection over TLS is chosen by ALPN (the client offers h2 in the TLS handshake; {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}); the client then sends a fixed 24-byte connection preface (PRI * HTTP/2.0 ...), and both sides send SETTINGS.

HPACK: why the second request's headers cost 7 bytes

The problem. Requests to one API repeat the same header fields: the same host, path, content type, API key, user agent. HPACK ({{RFC 7541, May 2015|https://www.rfc-editor.org/rfc/rfc7541}}) compresses them with three tools: a static table of 61 common fields both sides know by heart (index 2 is :method: GET, 3 is :method: POST), a dynamic table (4,096 bytes by default) to which each side adds fields as it sends them, so a repeat becomes a one-byte index, and a fixed Huffman code that shrinks literal text (by 26% on the SDK header values below: 164 bytes of values became 121). Press play: the running request's headers, sent twice on one connection, as HTTP/1.1 text and as the bytes HPACK actually produced.

Security: secrets in a compression table
Compression leaks information when an attacker can mix guesses with a secret and watch the size (the CRIME and BREACH attacks on TLS and HTTP compression). HPACK was designed against this: literal fields can be marked never indexed, so they are sent in full every time and no intermediary may add them to a table ({{RFC 7541 section 7.1.3|https://www.rfc-editor.org/rfc/rfc7541#section-7.1.3}}). measured The h2 library marks authorization never-indexed automatically (the "Bearer" set above costs 32 bytes on every request instead of 7), but not x-api-key, which it added to the dynamic table on the first request. HPACK's per-connection table and fixed Huffman code make the attack far harder than with gzip, so this is defence in depth, not an open hole; but a library's list of "sensitive" headers is worth knowing when your API key travels in a custom header.

Flow control: a window, and credit returned by WINDOW_UPDATE

The problem. Many streams share one connection, so a receiver needs a way to say "slow down on this one" without stopping the others (TCP's own flow control can only throttle the whole connection). HTTP/2 gives each stream, and the connection as a whole, a window: the number of DATA bytes the sender may send before it must wait. The receiver adds credit back with WINDOW_UPDATE frames as it consumes data. The cost: a stream can never move more than one window per round trip, so throughput is at most window divided by round-trip time, whatever the link's bandwidth.

measured A 200,000-byte GET /big from the lab server over HTTP/2 (src/lab/flow_h2.py, raw/flow_h2.json): every DATA frame and every WINDOW_UPDATE with its time. simulated Loopback has almost no round trip, so the client holds each WINDOW_UPDATE for 50 ms, standing in for one; the server's behaviour is real. derived Expected time is about ceil(200,000 / window) × 50 ms when the window is the limit.

The default 65,535-byte window is small for a fast long path: at 100 ms round trip it caps one stream at about 0.65 MB/s. Servers that move large bodies raise it (SETTINGS_INITIAL_WINDOW_SIZE for streams, a WINDOW_UPDATE on stream 0 for the connection, which always starts at 65,535). The root page's Failure lab measures the same cap on a real path ("One stream's throughput is capped at window / round trip"); for token streams of a few KB it never matters.

What was tried and retired

  • Priorities. RFC 7540 let clients build a dependency tree of streams with weights. Few servers implemented it well, and RFC 9113 "deprecates the priority signaling defined in RFC 7540" (section 5.3.2). Its replacement is a simple Priority header (urgency 0 to 7, incremental or not) shared with HTTP/3 ({{RFC 9218, June 2022|https://www.rfc-editor.org/rfc/rfc9218}}).
  • Server push. The server could send responses the client had not asked for yet. Chrome turned it off by default in Chrome 106, after measuring that only 1.25%, later 0.7%, of HTTP/2 sites used it; 103 Early Hints (a hint, not the bytes) replaced it ({{Chrome, 18 Aug 2022|https://developer.chrome.com/blog/removing-push}}). The server recorded here sends ENABLE_PUSH 0.
  • Upgrading a cleartext connection to h2c. The Upgrade: h2c dance from HTTP/1.1 is deprecated in RFC 9113 (section 3.1). Cleartext HTTP/2 itself is alive inside clusters, started with "prior knowledge" (the client just sends the preface): that is how much gRPC traffic runs.

Ending streams and connections, safely

RST_STREAM cancels one stream (a user pressed stop; a client gave up). GOAWAY starts a graceful shutdown: it carries the highest stream number the server may have processed. This is HTTP/2's gift to retries: requests on higher-numbered streams "are therefore guaranteed to be safe to retry", and so is any request reset with the REFUSED_STREAM code, "even those with non-idempotent methods" ({{RFC 9113 section 8.7|https://www.rfc-editor.org/rfc/rfc9113#section-8.7}}). A server being deployed should send GOAWAY and let in-flight streams finish; a client should retry what GOAWAY says was never started (section 9).

How it fails, and how it was attacked

  • One lost TCP packet stalls every stream. All streams share one TCP byte stream, which must be delivered in order; the root page's {{On the wire|n:3c65c17b0d0d81ec9355f4eecd6eed02}} tab measured one lost packet delaying all three concurrent streams by 43 to 68 ms. This is what HTTP/3 fixes.
  • Streams queue on a connection. When a client opens more than SETTINGS_MAX_CONCURRENT_STREAMS (100 here), the rest wait for a free slot; the root's Failure lab shows calls queuing ("Max concurrent streams").
  • One connection, one backend. A long-lived HTTP/2 connection through a connection-level (L4) load balancer pins every request to one backend ({{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}; Failure lab "gRPC behind an L4 load balancer").
  • Rapid Reset (CVE-2023-44487). An attacker opens a stream and immediately cancels it with RST_STREAM, again and again: cancelled streams do not count against the concurrency limit, but the server has already started work on each. Cloudflare saw a peak just above 201 million requests per second from about 20,000 machines; Google saw 398 million ({{Cloudflare, 10 Oct 2023|https://blog.cloudflare.com/technical-breakdown-http2-rapid-reset-ddos-attack/}}; {{Google Cloud|https://cloud.google.com/blog/products/identity-security/how-it-works-the-novel-http2-rapid-reset-ddos-attack}}). Fix: servers now count resets and close abusive connections.
  • CONTINUATION flood (April 2024). HEADERS followed by endless CONTINUATION frames without END_HEADERS makes a server buffer headers forever; one connection could crash many implementations, and because no request ever completes, nothing appears in access logs ({{Nowotarski, 3 Apr 2024|https://nowotarski.info/http2-continuation-flood-technical-details/}}).
