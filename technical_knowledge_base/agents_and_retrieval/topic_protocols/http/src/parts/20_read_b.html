2. Meaning: methods, status codes, header fields

The problem. A client must be able to talk to a server it has never seen, through intermediaries that know nothing about the application, and everyone must agree on what a request asks for and what an answer means. {{RFC 9110 (HTTP Semantics, June 2022)|https://www.rfc-editor.org/rfc/rfc9110}} defines that shared meaning once, for every version. It is the one HTTP document worth reading end to end.

Methods, and the two promises that decide retries

A method names the kind of operation. Two properties matter more than the names. A method is safe if the client asks for no change on the server (reading). It is idempotent if sending it twice has the same intended effect as sending it once: "PUT, DELETE, and safe request methods are idempotent" ({{RFC 9110 section 9.2.2|https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2}}). Idempotent requests can be repeated after a network error without asking whether the first one ran; that is the whole reason the property exists.

The consequence for LLM APIs
Generation is a POST, so it is neither safe nor idempotent. If the connection breaks after the request left, the client cannot know whether the model is already generating (and billing). Section 9 shows what the official SDKs do about it (they retry anyway) and what the protocol offers to make it safe.

Status codes: the first thing a client reads

A status code is three digits whose first digit is its class: 1xx informational (more is coming), 2xx success, 3xx go elsewhere, 4xx the request is wrong, 5xx the server or something in front of it failed. Clients must treat an unknown code as the x00 of its class, which is why APIs can invent codes such as 529 and still be understood as "server error" ({{RFC 9110 section 15|https://www.rfc-editor.org/rfc/rfc9110#section-15}}). Predict, then reveal

A streamed request returns HTTP/2 200, three tokens arrive, then the stream carries an overloaded_error event and ends. What status code did the request "have"?

200. The status line goes out with the response head, before any of the body, so a failure later in a stream can only be reported inside the body (an SSE error event) or by cutting the connection. Logs and dashboards that count status codes record this request as a success: count stream-level errors separately. (HTTP does allow trailer fields after a body, but status is not one of them, and SSE clients do not read trailers.)

Header fields: everything else

Header fields carry the rest, and they fall into a few families. Representation: content-type (what the body is: application/json, text/event-stream), content-length, content-encoding (gzip, br, zstd). Negotiation: accept, accept-encoding (what the client can take; the server picks and says so). Credentials: authorization, or an API's own such as x-api-key. Caching and conditions: cache-control, etag, if-none-match. Limits and hints: retry-after, rate-limit headers. Connection management: connection, keep-alive, transfer-encoding, upgrade, which apply to one hop only and which proxies must strip (section 7). Field names are case-insensitive; HTTP/2 and HTTP/3 require them in lower case on the wire, which is why the same request shows Content-Type on one hop and content-type on the next.

Content negotiation in LLM APIs. One endpoint can answer in two shapes: with "stream": true in the body, the Claude and OpenAI APIs answer text/event-stream; without it, one application/json body at the end. MCP's Streamable HTTP transport uses the Accept header for the same choice on one endpoint ({{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}). Compression is negotiated the same way, and it has a streaming trap: a proxy that gzips an event stream may hold tokens until it has enough bytes to compress (the root page's Failure lab reproduces this as "A buffering proxy delays tokens").
