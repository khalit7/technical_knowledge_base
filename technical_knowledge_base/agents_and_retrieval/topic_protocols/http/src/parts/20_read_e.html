8. Proxies: everything between you and the model

Real requests rarely go straight to the origin: something adds TLS, balances load, caches, enforces limits, logs, or controls what leaves a company network. An intermediary receives a full HTTP message, may change it, and sends a new message on the next hop.

The version changed (HTTP/2 in, HTTP/1.1 out), because the proxy terminates one connection and opens another. Host was rewritten to the upstream's address unless configured (proxy_set_header Host $host; $host drops the port). The client's address is gone unless the proxy adds X-Forwarded-For (or the standard Forwarded, {{RFC 7239|https://www.rfc-editor.org/rfc/rfc7239}}); any client can send those, so take the address appended by your own outermost proxy and trust the header only from proxies you run. Header order and case changed, harmless except to anything that signs raw header bytes.


Hop-by-hop headers. Connection and every field it names, Keep-Alive, Transfer-Encoding, TE, Upgrade and Proxy-Authorization describe one connection; a proxy must not forward them ({{RFC 9110 section 7.6.1|https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1}}), and HTTP/2 and 3 forbid them outright: measured nginx 1.31.6 answered 400 to an HTTP/2 request carrying transfer-encoding, a rule added in nginx 1.31.0 (13 May 2026).


Docs disagree with the software: nginx's upstream defaults changed in 2026
nginx's proxy module page still lists proxy_set_header Connection close as a default, and older guides say nginx talks HTTP/1.0 to the backend. Since nginx 1.29.7 (24 March 2026) "the default value for proxy_http_version is 1.1; the Connection proxy header is not sent by default anymore", and upstream keep-alive is on by default (nginx CHANGES, kept in src/inputs/nginx_changes_excerpt.txt). measured The capture above shows HTTP/1.1 and no Connection header; configurations that add proxy_set_header Connection "" are now harmless but redundant.


Buffering. By default nginx reads the upstream's response into buffers before sending it on (proxy_buffering on): for a token stream the user sees nothing, then everything. Turn it off for streaming locations, or let the app send X-Accel-Buffering: no ({{nginx proxy module|https://nginx.org/en/docs/http/ngx_http_proxy_module.html}}); ingress-nginx defaults to proxy-buffering: off ({{ConfigMap docs|https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/}}). The root's Failure lab measures the delay ("A buffering proxy delays tokens") and reproduces 502 and 504 with real error text.


Request smuggling: two parsers, two answers


A front proxy and a backend share one keep-alive connection for many users' requests. If they disagree about where a request ends, an attacker can send bytes the proxy sees as one message and the backend as two; the hidden second request is glued to the front of the next user's request on that connection, bypassing the proxy's checks and possibly capturing that user's request. The classic disagreement is a message with both Content-Length and Transfer-Encoding: chunked.




The same bytes are one request to a Content-Length parser and two to a chunked parser




illustrative drawing of the first probe below: a parser that trusts Content-Length (4) reads 4 bytes of body and leaves the rest on the connection; one that follows chunked coding reads the empty chunk 0 and sees a second request, GET /smuggled.




The rule: a server receiving both "MAY reject" the request or use Transfer-Encoding alone, and "Regardless, the server MUST close the connection after responding" ({{RFC 9112 section 6.3|https://www.rfc-editor.org/rfc/rfc9112#section-6.3}}). measured Eight ambiguous HTTP/1.1 messages and three HTTP/2 ones, sent raw to nginx 1.31.6 and to hypercorn 0.18.0 (parser h11 0.16.0): nginx refused every one with 400 or 501 and forwarded nothing. hypercorn followed Transfer-Encoding, answered 400 to the empty POST, and then answered the hidden GET /smuggled as a second request on the same connection, where RFC 9112 section 6.3 says it MUST close it.


A finding, not a vulnerability report
Behind nginx this cannot be exploited, because nginx rejects such messages first; behind a front proxy that trusted Content-Length it would be the textbook desync. Run a strict proxy in front, keep the same parser behaviour on every hop, and prefer HTTP/2 end to end where you can. AWS's ALB ships a "desync mitigation mode" for exactly this, defensive by default ({{ALB attributes|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html}}).


HTTP/2 at the front does not remove the problem when the back hop is HTTP/1.1: a header value containing CR LF, or a content-length that disagrees with the DATA frames, can become two requests after the downgrade ({{James Kettle, "HTTP/2: The Sequel is Always Worse", PortSwigger, 5 Aug 2021|https://portswigger.net/research/http2}}). measured nginx rejected all three HTTP/2 probes with 400 and passed nothing on.
