6. HTTP/3: the same streams on QUIC

The problem it solved. HTTP/2 removed the queue between requests but kept one underneath: TCP delivers one ordered byte stream, so a single lost packet holds every stream until it is resent. HTTP/3 ({{RFC 9114, June 2022|https://www.rfc-editor.org/rfc/rfc9114}}) moves HTTP/2's idea onto QUIC, a transport over UDP with TLS 1.3 built in and many independently ordered streams ({{RFC 9000|https://www.rfc-editor.org/rfc/rfc9000}}; the transport itself is on {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}). A lost packet now stalls only the stream it belonged to, and connection setup takes one round trip instead of two.

How it works. Each request is one client-opened bidirectional QUIC stream (numbers 0, 4, 8, ...), carrying HTTP/3 HEADERS and DATA frames. Frame types and lengths are QUIC variable-length integers rather than HTTP/2's fixed 9-byte header, and stream ids live in QUIC, not in the frame. Settings and other connection-level business move to unidirectional streams that each side opens once. measured In the recorded connection the client opened its control stream (id 2, carrying SETTINGS), a QPACK encoder stream (6) and a QPACK decoder stream (10); the server opened the same three as 3, 7 and 11 (raw/h3_frames.json).

QPACK, and why HPACK could not be reused. HPACK assumes both sides see header blocks in exactly the order they were sent; QUIC streams arrive in any order, so a block could refer to a table entry the decoder has not received yet. QPACK ({{RFC 9204|https://www.rfc-editor.org/rfc/rfc9204}}) moves table insertions onto the dedicated encoder stream and lets the encoder choose, per request, between referring only to entries the decoder has acknowledged (never blocks) or to newer ones (smaller, but the request waits if the insertion has not arrived: a blocked stream, limited by QPACK_BLOCKED_STREAMS). measured aioquic's encoder sent request 1 with the static table only (59 bytes, plus 3 bytes on the encoder stream to set the table size), then inserted the fields on the encoder stream (53 bytes) and sent request 2's headers in 9 bytes that referred to those not-yet-acknowledged entries. Toggle QPACK in the header animation above to compare.

How a client finds HTTP/3. It cannot know a server speaks QUIC on UDP before trying, so servers advertise it: an Alt-Svc: h3=":443"; ma=86400 response header ("HTTP/3 is available on UDP 443; remember for a day", {{RFC 7838|https://www.rfc-editor.org/rfc/rfc7838}}) or an HTTPS record in DNS ({{RFC 9460|https://www.rfc-editor.org/rfc/rfc9460}}; {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}}). Browsers then race QUIC against TCP and keep the winner. measured on 5 October 2026: api.openai.com and generativelanguage.googleapis.com advertised h3 in Alt-Svc; api.anthropic.com did not; curl negotiated HTTP/2 with all three (section 10).

0-RTT and 425. A client that has talked to a server before can send its first request inside the very first packet (TLS early data, 0-RTT). An attacker who copies that packet can replay it, so the request must be safe to repeat; a server that will not take the risk answers 425 Too Early and the client resends after the handshake ({{RFC 8470|https://www.rfc-editor.org/rfc/rfc8470}}). Never let a POST that starts a generation be accepted as early data.

What it costs, and when not to use it. QUIC runs in user space and encrypts nearly every header, so it costs more CPU per byte than kernel TCP, and the usual packet tools see little. UDP 443 is blocked or throttled on some corporate networks, which forces a fallback to TCP after a delay. Between your own services in a data centre, where loss is rare, HTTP/2 over TCP is simpler and as fast; HTTP/3 pays off on lossy, mobile and long-distance client links.

7. Proxies: everything between you and the model

The problem. Real requests rarely go straight from your code to the origin. Something in the middle adds TLS, balances load, caches, enforces limits, logs, or controls what leaves a company network. HTTP was designed for this: an intermediary receives a full HTTP message, may change it, and sends a new message on the next hop.

Four things to notice. The version changed: the client spoke HTTP/2, the backend got HTTP/1.1, because the proxy terminates one connection and opens another. Host was rewritten to the upstream's address unless configured (nginx's proxy_set_header Host $host; note that $host drops the port). The client's address is gone: the backend sees the proxy's, unless the proxy adds X-Forwarded-For (or the standard Forwarded, {{RFC 7239|https://www.rfc-editor.org/rfc/rfc7239}}); trust those headers only from your own proxies, since any client can send them. Header order and case changed, which is harmless but breaks anything that signs raw header bytes.


Hop-by-hop headers. Some fields describe one connection, not the request: Connection and every field it names, Keep-Alive, Transfer-Encoding, TE, Upgrade, Proxy-Authorization. A proxy must not forward them ({{RFC 9110 section 7.6.1|https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1}}), and HTTP/2 and HTTP/3 forbid them outright: measured nginx 1.31.6 answered 400 to an HTTP/2 request carrying transfer-encoding, a rule added in nginx 1.31.0 (13 May 2026).


Docs disagree with the software: nginx's upstream defaults changed in 2026
nginx's proxy module page still lists proxy_set_header Connection close as a default, and older guides say nginx talks HTTP/1.0 to the backend. Since nginx 1.29.7 (24 March 2026) "the default value for proxy_http_version is 1.1; the Connection proxy header is not sent by default anymore", and upstream keep-alive is on by default (nginx CHANGES, kept in src/inputs/nginx_changes_excerpt.txt). measured The capture above, with nothing but proxy_pass configured, shows HTTP/1.1 and no Connection header. Configurations copied from older guides that add proxy_set_header Connection "" are now harmless but redundant.


Buffering. By default nginx reads the upstream's response into buffers before sending it on (proxy_buffering on), which for a token stream means the user sees nothing, then everything. Turn it off for streaming locations, or let the app send X-Accel-Buffering: no ({{nginx proxy module|https://nginx.org/en/docs/http/ngx_http_proxy_module.html}}); the ingress-nginx controller defaults to proxy-buffering: off ({{ConfigMap docs|https://kubernetes.github.io/ingress-nginx/user-guide/nginx-configuration/configmap/}}). The root's Failure lab measures the delay ("A buffering proxy delays tokens").


Request smuggling: two parsers, two answers


The attack. A front proxy and a backend share one keep-alive connection for many users' requests. If they disagree about where a request ends, an attacker can send one request that the proxy sees as one message and the backend as two: the hidden second request is then glued to the front of the next user's request on that connection. It bypasses the proxy's checks and can capture another user's request. The classic disagreement is a message with both Content-Length and Transfer-Encoding: chunked.






illustrative drawing of the bytes of the first probe below: a parser that trusts Content-Length (4) reads 4 bytes of body and leaves the rest on the connection; one that follows chunked coding reads the empty chunk 0 and sees a second request, GET /smuggled.




The rules are strict: a server receiving both "MAY reject" the request or use Transfer-Encoding alone, and "Regardless, the server MUST close the connection after responding" ({{RFC 9112 section 6.3|https://www.rfc-editor.org/rfc/rfc9112#section-6.3}}). measured Eight ambiguous HTTP/1.1 messages and three HTTP/2 ones, sent raw to nginx 1.31.6 (in front of the recording backend) and to hypercorn 0.18.0 (the lab server, parser h11 0.16.0):




A finding, not a vulnerability report
nginx refused every ambiguous message with 400 or 501 and forwarded nothing. hypercorn followed Transfer-Encoding, answered 400 to the (empty) POST, and then answered the hidden GET /smuggled as a second request on the same connection, where RFC 9112 section 6.3 says it MUST close the connection. Behind nginx this cannot be exploited, because nginx rejects such messages first; behind a front proxy that trusted Content-Length it would be the textbook desync. The lesson is general: run a strict proxy in front, keep the same parser behaviour on every hop, and prefer HTTP/2 end to end where you can. AWS's ALB ships a "desync mitigation mode" for exactly this, defensive by default ({{ALB attributes|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html}}).


HTTP/2 at the front does not remove the problem when the back hop is HTTP/1.1: a header value containing CR LF, or a content-length that disagrees with the DATA frames, can become two requests after the downgrade ({{James Kettle, "HTTP/2: The Sequel is Always Worse", PortSwigger, 5 Aug 2021|https://portswigger.net/research/http2}}). measured nginx rejected all three HTTP/2 probes with 400 and passed nothing on.
