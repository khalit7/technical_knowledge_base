9. Timeouts: the smallest one on the path wins

A program waiting on the network must eventually give up, or one dead server ties up threads, connections and memory forever, so every client, proxy and server has timeouts. An LLM generation is unusual traffic: it can think for a minute before the first token and stream for ten more, which is what most timeouts were tuned to kill.

Does the model match reality? (8 measured runs, and its assumptions)

Assumptions: the server sends the response head the moment it accepts a streamed request (the lab server does; most streaming APIs do) and nothing else until the first token, unless pings are on; an idle timer starts when the request is sent and restarts on every byte; a first-byte timer stops when the head arrives; a total timer never restarts. Real hops add what this leaves out: connect and TLS timeouts, keep-alive races, proxies that buffer and so delay bytes to the next hop, and retries by intermediaries. Python check: src/recompute.py runs the same model on the same cases.

The trap: two hops count total time
Google Cloud's 30 s backend service timeout and API Gateway's 29 s count the whole response. Behind either, a generation longer than 30 s fails even when it streams perfectly, and no amount of pings helps: raise the limit, or switch to the async shape (submit, get a job id, poll or receive a webhook). Envoy's 15 s route timeout is total too, and is usually the first thing to bite a streaming service behind Istio.

Keep-alive timeouts in the wrong order. If the application closes idle connections sooner than the load balancer does, the balancer "might send a request to the application before it receives the packet indicating that the connection is closed", and the client gets a 502; keep the application's idle timeout larger than the balancer's ({{ALB docs|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html}}). In general each hop's keep-alive idle timeout should be longer than that of the hop in front of it. 10. Retries and idempotency, at the protocol level

A request failed. If the server never started, send it again; if it finished but the answer was lost, a retry does the work twice: two generations billed, two tool calls executed. The protocol question is always: can the client prove the server did not start?

Where the failure happened decides whether a POST may be retried

Static diagram of one POST's life. Safe: the request never reached HTTP, or the server guarantees it did not act (RFC 9113 section 8.7 for REFUSED_STREAM and GOAWAY; RFC 8470 for 425; 429 and 503 with Retry-After refuse before the work by contract). Unknown: anything after the request bytes left, unless it carries an idempotency key the server honours. 500 and 529 probably failed, not guaranteed; the Claude docs say to retry 500 with backoff. An error event mid-stream: the partial output is not resumable, start a new request.

What the official SDKs actually do (measured)

The Anthropic (1.11.0) and OpenAI (3.24.0) Python SDKs share one generated base client. Its source retries on connection errors, timeouts, 408, 409, 429 and every 5xx, twice by default; waits 0.5 s, then 1 s, up to 8 s, each multiplied by a random factor between 0.75 and 1 ("jitter"); and obeys retry-after-ms, Retry-After and a non-standard x-should-retry: true|false header from the server. A read timeout or a dropped connection: the same POST arrives three times, with no idempotency key

What this means
On a read timeout (1 s client timeout, a server that takes 2.5 s) and on a connection dropped after the request was sent, both SDKs sent the same POST three times, and no attempt carried an idempotency key: the base client has an idempotency header slot, but neither SDK sets it. Against a real API each attempt may run a full generation, so a client timeout shorter than the model's real latency multiplies load and cost by up to three: fail fast on connect, not on read; set the read timeout above the longest generation, or stream. The server has a say too: api.anthropic.com answered our credential-free request with x-should-retry: false on its 401 (section 11).

Making a POST safe to retry. The client sends a unique idempotency key header; the server stores the key with the result and, on a retry with the same key, returns the stored result instead of working again (Stripe's design). The IETF draft that would standardise an Idempotency-Key header reached revision 07 and expired without becoming an RFC ({{Datatracker|https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/}}), so each API defines its own. The server side, including work outside your database, is on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}; retry budgets, backoff and the retry storms they prevent are on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}.

Predict, then reveal

A deployment sends GOAWAY with last stream id 41 on an HTTP/2 connection where your client had streams 39, 41 and 43 in flight, all POSTs. Which may it retry automatically?

Only 43. GOAWAY carries "the highest stream number that might have been processed", so 39 and 41 might have run and are unknown; 43 is guaranteed untouched and "can be safely retried", POST or not (RFC 9113 section 8.7). This is why graceful HTTP/2 shutdown loses nothing: the server finishes 39 and 41, the client moves 43 to a new connection.
