8. Timeouts: the smallest one on the path wins

The problem. A program waiting for a network answer must eventually give up, or one dead server ties up threads, connections and memory forever. So every client, proxy and server has timeouts. An LLM generation is unusual traffic: it can think for a minute before the first token and stream for ten more, which is exactly what most timeouts were tuned to kill.

The trap in that table
Two hops count total time: Google Cloud's 30 s backend service timeout and API Gateway's 29 s. Behind either, a generation longer than 30 s fails even when it streams perfectly, and no amount of pings helps; raise the limit, or switch to the async shape (submit, get a job ID, poll or receive a webhook). Envoy's 15 s route timeout is total too, and is usually the first thing to bite a streaming service behind Istio.

Keep-alive timeouts in the wrong order. AWS spells out the classic one: if the application closes idle connections sooner than the load balancer does, the balancer "might send a request to the application before it receives the packet indicating that the connection is closed", and the client gets a 502; keep the application's idle timeout larger than the balancer's ({{ALB docs|https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html}}). The rule generalises: each hop's keep-alive idle timeout should be longer than that of the hop in front of it.

Predict, then reveal

A model thinks for 45 s before its first token, then streams for 3 minutes. The path is: Anthropic SDK (defaults), then an AWS ALB (defaults), then nginx (defaults), then the model server. The server sends the 200 head immediately and nothing else until the first token. What happens?

Works, but only just. The longest silence is the 45 s think; nginx (60 s idle), the ALB (60 s idle) and the SDK (600 s idle) all reset on every token, so the 3-minute stream is fine. Push the think to 70 s and the first hop to hit 60 s of silence (nginx behind the ALB here, both at 60) closes the connection: the client sees a cut stream under a 200. Fixes, in order of preference: send an SSE keep-alive comment every 15 to 30 s while thinking (what the Claude API's ping events do), or raise every idle timeout on the path above the longest expected silence. 9. Retries and idempotency, at the protocol level

The problem. A request failed. Should the client send it again? If the server never started, yes. If it finished but the answer was lost, a retry does the work twice: two generations billed, two tool calls executed, two orders placed. The protocol question is always the same: can the client prove the server did not start?

What the official SDKs actually do (measured)

The Anthropic (1.11.0) and OpenAI (3.24.0) Python SDKs share one generated base client. Its source, read in the installed packages, retries on connection errors, timeouts, 408, 409, 429 and every 5xx, twice by default; waits 0.5 s, then 1 s, up to 8 s, each multiplied by a random factor between 0.75 and 1 ("jitter"); and obeys retry-after-ms, Retry-After and a non-standard x-should-retry: true|false header from the server. measured Pointed at the lab server with errors injected, every attempt the server received:

measured src/lab/sdk_retries.py, raw/sdk_retries.json. Each dot is one request the server received, at its time after the first; gaps include the SDK's random jitter, so they vary run to run. No real API was called.

What this means
On a read timeout (1 s client timeout, a server that takes 2.5 s) and on a connection dropped after the request was sent, both SDKs sent the same POST three times, and no attempt carried an idempotency key: the base client has an idempotency header slot, but neither SDK sets it. Against a real API each of those attempts may run a full generation. That is a deliberate trade (a dropped request is retried rather than failed), and the Claude API's docs describe the retry behaviour; but it means a client timeout shorter than the model's real latency multiplies load and cost by up to three. Set the SDK timeout above the longest expected generation, or stream. Note also the server's role: api.anthropic.com answered our credential-free request with x-should-retry: false on its 401 (section 10), telling the SDK not to bother.

Making a POST safe to retry. The client sends a unique idempotency key header with the POST; the server stores the key with the result and, on a retry with the same key, returns the stored result instead of doing the work again (Stripe's design). The IETF draft that would standardise an Idempotency-Key header reached revision 07 and expired without becoming an RFC ({{Datatracker|https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/}}), so each API defines its own. The server side, including the hard case of work outside your database, is on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}; retry budgets, backoff and the retry storms they prevent are on {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}.

Predict, then reveal

A deployment sends GOAWAY with last stream id 41 on an HTTP/2 connection where your client had streams 39, 41 and 43 in flight, all POSTs. Which may it retry automatically?

Only 43. GOAWAY carries "the highest stream number that might have been processed", so 39 and 41 might have run and are unknown; 43 is guaranteed untouched and "can be safely retried", POST or not (RFC 9113 section 8.7). This is why graceful HTTP/2 shutdown loses nothing: the server finishes 39 and 41, the client moves 43 to a new connection.
