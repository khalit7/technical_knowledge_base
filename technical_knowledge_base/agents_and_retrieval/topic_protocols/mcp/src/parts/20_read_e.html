6. Versions, compatibility and extensions

A revision is named by the date it was frozen. Five have been released (checked 5 October 2026 against each revision's changelog in the {{specification repository|https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification}}); the direction is consistent, from a chatty, stateful conversation between two processes toward self-describing requests that ordinary web infrastructure can route, cache and secure.

Eras, and the compatibility matrix run for real

The specification calls versions with a handshake legacy and versions with per-request metadata modern; a dual-era implementation speaks both. A dual-era client probes: on stdio it sends server/discover first and falls back to initialize on any error that is not a recognised modern error; on HTTP it tries a modern request and inspects a 400's body before falling back ({{versioning|https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning}}). All 9 pairings were run over stdio. Predict each cell, then click it.

The instructive failure is the modern-only client against the legacy server: the old SDK answered the unfamiliar request with -32602 Invalid request parameters, an error that names no version and gives a user nothing to act on. That is why the specification recommends that even modern-only clients probe with server/discover first, and why a modern-only server should name its versions when it rejects initialize (the hand-written one here says "this server speaks MCP 2026-07-28 only").

Deprecation and extensions

  • Lifecycle. A feature goes Active, then Deprecated (still works; new code should not adopt it), then Removed, with at least twelve months between the release that deprecates it and its removal; the window can be shortened for an active security risk ({{feature lifecycle|https://modelcontextprotocol.io/community/feature-lifecycle}}).
  • Extensions are optional additions negotiated in the extensions field of capabilities, named like _meta keys: io.modelcontextprotocol/... for official ones, your reversed domain (com.example/...) for your own. If one side lacks an extension, the other must fall back to core behaviour or refuse ({{extensions|https://modelcontextprotocol.io/docs/extensions/overview}}). Official ones: Tasks (io.modelcontextprotocol/tasks: a durable handle for long work, polled with tasks/get, input via tasks/update); MCP Apps (io.modelcontextprotocol/ui: a server returns interactive HTML that renders inside the conversation); OAuth client credentials for machine-to-machine access and Enterprise-Managed Authorization, where an organisation's identity provider grants access to servers centrally; and Skills over MCP.
Governance

Changes go through Specification Enhancement Proposals (SEPs, numbered by pull request) with working and interest groups; the project sits in the Agentic AI Foundation under the Linux Foundation (section 1).
