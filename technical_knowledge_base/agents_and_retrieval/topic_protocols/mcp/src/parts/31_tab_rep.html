One confirm-then-delete tool call, recorded through a round-robin balancer in front of two ckpt-tools replicas, four ways. Watch which replica each HTTP request reaches, what each replica remembers, and where the call breaks.

Try: play the 2025-11-25 session with round robin, then the same call with session affinity; then the 2026-07-28 call with per-process keys and with a shared key. The first two differ only in the balancer; the last two only in one key.

measured 5 October 2026, src/lab/replicas.py: two ckpt_server.py processes (SDK 2.3.0) on ports 30711 (A) and 30712 (B), lb_proxy.py on 30710 sending each HTTP request to the next replica in turn (or, with affinity, to the replica that minted the session), and an SDK client whose "user" answers yes by script. The animation replays the first of 20 runs of each setup; the counts under it are all 20.

What to take from it

  • Old protocol, round robin: initialize creates a session in one replica; the very next request goes to the other, which answers 404 "Session not found". Nothing about the tool matters; the session itself cannot cross replicas.
  • Old protocol, affinity: works, at the price of a balancer that understands MCP sessions, uneven load, and lost sessions whenever a replica restarts. The confirmation travels as a server request on the open stream and the answer as a separate POST.
  • New protocol, per-process keys: no session, but the first answer carries sealed requestState; the retry reaches the other replica, which cannot open it. Fails 20 of 20.
  • New protocol, shared key: two independent POSTs, either replica can answer either one. 20 of 20, with no affinity and nothing held in memory between them.
