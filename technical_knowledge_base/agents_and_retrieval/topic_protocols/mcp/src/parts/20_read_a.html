MCP in one screen

MCP is a small, standard way for an AI application to reach tools and data. A host (Claude Code, an IDE, your own agent) runs one client per server; the server offers tools the model may call, resources the application may read and prompts the user may pick. The messages are JSON-RPC 2.0, carried either over a child process's standard input and output (stdio) or as one HTTP POST per message (Streamable HTTP). Remote servers are OAuth resource servers. The current revision, 2026-07-28, made every request self-contained: no handshake, no session.

1. What MCP is, and what it is not

The problem. A language model only produces text. To list your checkpoints, read a file or open a pull request, the application around it must call real code. Before MCP every application wired every integration itself: N applications and M tools meant N × M adapters. MCP makes it N + M: write a server once, and every MCP host can use it. Anthropic released it on {{25 November 2024|https://www.anthropic.com/news/model-context-protocol}} and donated it on 9 December 2025 to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with Block and OpenAI ({{Anthropic|https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation}}).

Three roles

Host
The application the user runs. It owns the conversation with the model, decides which servers to start, which tools the model may see, and asks the user for consent. The specification puts security policy here: "Enforces security policies and consent requirements" ({{architecture|https://modelcontextprotocol.io/specification/2026-07-28/architecture}}).
Client
A component inside the host that speaks MCP to exactly one server. A host with five servers runs five clients.
Server
A program that offers capabilities: ckpt-tools, a GitHub server, a database server. It sees only the requests sent to it, never the whole conversation and never other servers.

Where MCP sits in an agent loop

The most common confusion: the model does not speak MCP. Model APIs have their own tool-calling format (a list of tool definitions in the request; tool_use blocks in the answer). The host is a translator between the two:

  1. The client asks each server for its tools (tools/list). The host copies each tool's name, description and inputSchema into the model request's tool list.
  2. The model answers with a tool call, for example list_checkpoints({"run": "llama-7b-sft"}).
  3. The host checks its policy (is this tool allowed? does the user need to confirm?), then its client sends tools/call to the right server.
  4. The server runs the function and returns a result. The host puts the result's text into the next model request as a tool result. The model reads it and continues.

So everything a server returns ends up in the model's context, and everything in a tool's description shapes what the model does. Both facts drive section 8. The root page records this loop byte for byte ({{Topic: protocols, section 9|n:3c65c17b0d0d81ec9355f4eecd6eed02}}).

What MCP costs, and when not to use it
It adds a process or a network hop, a JSON layer and a dependency on host support. If one application calls one internal API, ordinary function calling with the model API's own tool format is simpler and has fewer moving parts. MCP pays off when several hosts (an IDE, a CLI agent, a chat app) must reach the same tools, when a team wants to publish tools once, or when tools must run with credentials or isolation the host should not hold. For one agent delegating a whole task to another agent, use A2A ({{Agent-to-agent and beyond|n:3f05c17b0d0d81199373d4d0b18706d8}}).
