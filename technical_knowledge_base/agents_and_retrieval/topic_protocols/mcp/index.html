MCP in one screen

MCP is a small, standard way for an AI application to reach tools and data. A host (Claude Code, an IDE, your own agent) runs one client per server; the server offers tools the model may call, resources the application may read and prompts the user may pick. The messages are JSON-RPC 2.0, carried either over a child process's standard input and output (stdio) or as one HTTP POST per message (Streamable HTTP). Remote servers are OAuth resource servers. The current revision, 2026-07-28, made every request self-contained: no handshake, no session.

1. What MCP is, and what it is not

The problem. A language model only produces text. To list your checkpoints, read a file or open a pull request, the application around it must call real code. Before MCP every application wired every integration itself: N applications and M tools meant N × M adapters. MCP makes it N + M: write a server once, and every MCP host can use it. Anthropic released it on 25 November 2024 and donated it on 9 December 2025 to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with Block and OpenAI (Anthropic).

Three roles

Host
The application the user runs. It owns the conversation with the model, decides which servers to start, which tools the model may see, and asks the user for consent. The specification puts security policy here: "Enforces security policies and consent requirements" (architecture).
Client
A component inside the host that speaks MCP to exactly one server. A host with five servers runs five clients.
Server
A program that offers capabilities: ckpt-tools, a GitHub server, a database server. It sees only the requests sent to it, never the whole conversation and never other servers.

Where MCP sits in an agent loop

The most common confusion: the model does not speak MCP. Model APIs have their own tool-calling format (a list of tool definitions in the request; tool_use blocks in the answer). The host is a translator between the two:

  1. The client asks each server for its tools (tools/list). The host copies each tool's name, description and inputSchema into the model request's tool list.
  2. The model answers with a tool call, for example list_checkpoints({"run": "llama-7b-sft"}).
  3. The host checks its policy (is this tool allowed? does the user need to confirm?), then its client sends tools/call to the right server.
  4. The server runs the function and returns a result. The host puts the result's text into the next model request as a tool result. The model reads it and continues.

So everything a server returns ends up in the model's context, and everything in a tool's description shapes what the model does. Both facts drive section 8. The root page records this loop byte for byte (Topic: protocols, section 9).

What MCP costs, and when not to use it
It adds a process or a network hop, a JSON layer and a dependency on host support. If one application calls one internal API, ordinary function calling with the model API's own tool format is simpler and has fewer moving parts. MCP pays off when several hosts (an IDE, a CLI agent, a chat app) must reach the same tools, when a team wants to publish tools once, or when tools must run with credentials or isolation the host should not hold. For one agent delegating a whole task to another agent, use A2A (Agent-to-agent and beyond).

2. The messages: JSON-RPC 2.0 with an MCP envelope

JSON-RPC 2.0 is a ten-year-old convention for remote procedure calls in JSON (specification). MCP uses three of its message kinds (MCP basic protocol):

  • A request has an id, a method and params. MCP forbids a null id and reusing an id that is still waiting for its answer.
  • A response carries the same id and either a result or an error (code, message, optional data). The id is how a client matches answers to questions when several are in flight on one pipe.
  • A notification has a method and no id, and gets no answer: progress updates, change notices, cancellation on stdio.

Since 2026-07-28 only the client sends requests. When a server needs something from the client (a confirmation, a model completion), it says so inside its result and the client asks again (section 5). Four MCP additions to plain JSON-RPC are visible:


    

  • _meta on every request. io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities are required; clientInfo is recommended. A request missing a required field is rejected with -32602 (on HTTP, status 400). Names under the io.modelcontextprotocol/ prefix (and any prefix whose second label is modelcontextprotocol or mcp) are reserved for the protocol.
    • 

  • resultType on every result: "complete", or "input_required" when the server needs more input. A client must treat a missing resultType (an older server) as complete.
    • 

  • serverInfo in the result's _meta, so a client can tell who answered without remembering a handshake. Both clientInfo and serverInfo are self-reported: the specification says not to base security decisions on them.
    • 

  • Trace context: traceparent, tracestate and baggage may ride in _meta (W3C formats), so one trace can follow a request from the model call through the host into the server.
    • 



What the envelope costs
The same tools/call line is 304 bytes under 2026-07-28 and 121 bytes under 2025-11-25 (measured, stdio, newline included): 183 bytes of _meta that every request now repeats instead of saying once at the start of a session. The result grows by 111 bytes (819 against 708) for resultType and serverInfo. On a local pipe this is noise; across millions of calls through a gateway it is the price of letting any replica answer any request.

3. What a server offers, and what the client offers back


The three server primitives differ by who decides to use them, which is the single most useful way to remember them (server features):

Tools in depth


A tool definition has a name, an optional display title, a description written for the model, an inputSchema (JSON Schema, 2020-12 by default) and optionally an outputSchema and annotations. In the Python SDK you write none of the schemas by hand: the type hints are the schema. def list_checkpoints(run: str) -> list[Checkpoint] produced this input schema and a matching output schema with the four Checkpoint fields:


{"type":"object","properties":{"run":{"title":"Run","type":"string"}},"required":["run"],"title":"list_checkpointsArguments"}


Two copies of every structured result. With an output schema, the result carries structuredContent (JSON a program can use) and, for backward compatibility, the same data as text in content, which is what most hosts show the model. For three checkpoints the SDK sent three pretty-printed text blocks plus the structured copy: 818 bytes of result body for about 200 bytes of facts (measured). Every byte of content becomes model input tokens, so return short, task-shaped results and paginate.


Annotations are claims, not guarantees. readOnlyHint, destructiveHint, idempotentHint and openWorldHint (talks to the outside world) tell a host how careful to be: ckpt-tools marks delete_checkpoint destructive and idempotent. The specification is blunt: "clients MUST consider tool annotations to be untrusted unless they come from trusted servers" (tools). A malicious server can mark a destructive tool read-only.


Names collide across servers. Tool names are only unique within one server (SHOULD be 1 to 128 characters of letters, digits, _ - .). Two servers that both offer search must be told apart by the host, for example by prefixing a server identifier; serverInfo.name is not unique and should not be used for this.


State without sessions. A shopping cart, an open browser or a database transaction spans several calls. With no session, the server returns an explicit handle (basket_id: "bsk_a1b2c3") and takes it back as an ordinary argument; the model carries it forward. The specification's advice: a handle is a name, not a password, so check on every call that it belongs to the caller; make it random; state its lifetime in the tool description; return a clear tool error when it has expired so the model can start again (stateful tools).


Order matters for cost. Servers SHOULD return tools/list in a deterministic order, because hosts paste the list into the model request, and a reordered list breaks the model provider's prompt cache.

4. The two transports


A transport (the specification also says binding) defines how messages are framed and delivered, how cancellation is signalled, and where request metadata lives. It never changes what the messages mean (transports).


stdio: a child process and two pipes


The host starts the server as a subprocess. The client writes one JSON-RPC message per line to the server's standard input; the server writes one per line to standard output. Messages must not contain raw newlines (JSON escapes them as \n). There is no network, no port and no authentication: the server runs as the user, with the environment the host gives it, which is also where its credentials come from (the authorization framework explicitly does not apply to stdio, stdio).


    

  • stdout is the protocol channel. The server "MUST NOT write anything to its stdout that is not a valid MCP message". Logs go to stderr, which the client may show or ignore. One stray print() corrupts the stream: the root page's Failure lab case "MCP over stdio: stdout pollution" shows a hand-written server whose debug print glued itself to a response, which the client then dropped and timed out on.
    • 

  • Shutdown: the client closes the server's stdin, waits, then sends SIGTERM and finally SIGKILL. A server should exit when stdin reaches end of file.
    • 

  • Crash: the client restarts the process. Because the protocol is stateless, in-flight requests are simply lost and can be retried.
    • 

  • The same newline-delimited framing is recommended for custom transports over Unix sockets or TCP.
    • 



Streamable HTTP: one POST per message


The server exposes one URL, the MCP endpoint (for example https://mcp.example.com/mcp). Every client message is its own HTTP POST with Accept: application/json, text/event-stream. The server answers each request either with one JSON object or with a server-sent events (SSE) stream scoped to that request, carrying progress notifications and then the final response (Streamable HTTP; SSE itself is taught on Streaming and real-time).

Headers that mirror the body. Every POST carries MCP-Protocol-Version, Mcp-Method and, for tools/call, resources/read and prompts/get, Mcp-Name. They exist so an ordinary load balancer, gateway or firewall can route, rate-limit or block by tool without parsing JSON. A tool may also ask for an argument to be copied into a header with x-mcp-header (for example a region, so a gateway can route to the right cluster); sensitive values must not be marked this way, since intermediaries see headers. Because two components could disagree about which copy is true (a gateway allows by header, the server executes by body), servers MUST reject a mismatch with 400 and -32020 HeaderMismatch.

Three of these deserve a word. The Origin check stops a web page you happen to visit from calling a server on your laptop: browsers attach Origin to cross-site requests, and the specification requires a 403 for an invalid one. The Host check (421 Misdirected Request) stops DNS rebinding, where an attacker's domain is made to resolve to 127.0.0.1 after the page loads (DNS explains the trick); the specification also says local servers should bind to 127.0.0.1, not 0.0.0.0. And a header that names an older protocol version was not treated as a header mismatch: this dual-era server took it as a legacy request and asked for a session ID. Intermediaries that route on headers should therefore reject versions older than 2026-07-28, as the specification advises, rather than trust unvalidated headers.


Behind a proxy. Servers SHOULD send X-Accel-Buffering: no on event streams so nginx-style proxies pass events immediately (the legacy recording shows the header). Long-lived streams (subscriptions/listen) should send a comment line : now and then so idle timeouts do not cut them. Streams are not resumable any more: Last-Event-ID was removed, and a broken stream loses its request, which the client re-sends with a new id.


Measured: the same call over each transport




Cold: from opening the client to the first result, median of 7 (stdio includes starting a Python process that imports the SDK, which is most of the 360 to 380 ms). Warm: median and 90th percentile of 300 calls on an open client. Bytes: one warm call, request and response on the wire including HTTP headers (TCP tap) or the pipe lines (tee). Loopback on one laptop shared with other jobs: two runs of identical settings differed by up to 0.5 ms, so read only differences larger than that.


What the numbers say: on one machine every transport answers in one to three milliseconds, far below a model call's hundreds of milliseconds, so transport choice is about deployment, not speed. stdio's cost is the process start (and a process per user per server); HTTP's is the network, TLS and authorization you must add to leave the laptop. The legacy session mode pays an extra round trip at the start (initialize, then the initialized notice, then the GET stream) and SSE framing on every reply.


Choosing
stdio when the server works on the user's own files and accounts (a code editor's tools, a local database) and should run with exactly the user's rights. Streamable HTTP when many users or agents share one server, when the data lives in a service, or when credentials must stay off the user's machine. The deprecated 2024-11-05 HTTP+SSE transport (two endpoints: a GET stream and a POST URL) should not be used for anything new.






5. The stateless revision (2026-07-28)


Before. From 2024-11-05 to 2025-11-25 an MCP connection began with a handshake: the client sent initialize with its version and capabilities, the server answered with its own, the client sent notifications/initialized, and only then could work start. Over HTTP the server minted an Mcp-Session-Id that the client sent on every later request, opened a GET stream for messages the server wanted to push, and ended the session with DELETE. A server could also send its own requests to the client (asking for a confirmation, or for a model completion) on an open stream, and wait for the answer.


The problem this caused. A session is memory inside one server process. Put two replicas behind an ordinary round-robin load balancer and the second request of a session lands, half the time, on a replica that never saw the first. You then need sticky routing (the balancer pins each session to a replica) or a shared session store, and a server that pauses mid-call waiting for the client holds that memory open even longer. That is the opposite of how the rest of the web scales.


After. The 2026-07-28 revision (changelog) removed the handshake, the session, the GET stream, ping, logging/setLevel and server-initiated requests. Every request says everything about itself in _meta. A client that wants to know a server up front may call server/discover (servers MUST implement it), which returns supported versions, capabilities and identity, and is cacheable.


Multi round-trip requests: asking the user without holding a session


The replacement for server-initiated requests is MRTR (multi round-trip requests). The server answers the original request with resultType: "input_required", a map of inputRequests (an elicitation, a sampling request, a roots request) and an opaque requestState. The client gathers the answers and sends the same request again, with a new id, plus inputResponses and the echoed requestState. Any replica can finish it, because everything it needs is in the retry. Only tools/call, resources/read and prompts/get may do this.


ckpt_server.py: the same confirmation written for both eras (SDK 2.3.0)


if ctx.protocol_version and ctx.protocol_version >= "2026-07-28":
    answer = (ctx.input_responses or {}).get("confirm")
    if answer is None:   # round 1: ask, keep nothing in server memory
        return InputRequiredResult(
            input_requests={"confirm": ElicitRequest(params=ElicitRequestFormParams(
                message=f"Delete checkpoint {name}? This cannot be undone.",
                requested_schema={...}))},
            request_state=f"delete:{name}")   # sealed by the SDK before it leaves
    ok = answer.action == "accept" and answer.content["confirm"]
else:   # 2025-11-25: a request back to the client over the session's open stream
    r = await ctx.elicit(f"Delete checkpoint {name}? ...", Confirm)
    ok = r.action == "accept" and r.data.confirm


Calling ctx.elicit() on a 2026-07-28 request fails with NoBackChannelError: Cannot send 'elicitation/create': this transport context has no back-channel for server-initiated requests (measured): the old style simply has no channel any more.


requestState is attacker-controlled. It travels through the client, so the specification requires the server to protect its integrity (an HMAC or authenticated encryption) whenever it affects authorization or business logic, and recommends binding it to the authenticated user, a short expiry and the original request. The Python SDK does this for you: it seals every requestState with AES-GCM (the 25-character plaintext delete:llama-7b-step-2000 went out as a 281-character string starting v1., carrying the sealed payload plus the expiry, request binding and audience the SDK adds), and a forged value came back as -32602 Invalid or expired requestState (measured).

No, for a different reason: 0 of 20. The first round went to replica B, which sealed requestState with a key generated when that process started; the retry went to A, which could not open it: -32602 Invalid or expired requestState. The SDK's documentation says it plainly: "Multi-instance deployments must share a key via keys=[...]". With one key shared by both replicas (RequestStateSecurity(keys=[...]), here from an environment variable), 20 of 20. Stateless protocol does not mean stateless deployment: something must still be shared, but it is a key in your secret store rather than live session memory in one process.

What statelessness costs
183 more bytes on every request (section 2); a retry round trip where the old protocol kept a stream open; state handles the model must carry (section 3); and a sealing key to distribute and rotate (the SDK takes a ring of keys: the first seals, all of them open). What it buys: any replica answers any request, gateways can route on headers, list results can be cached, and a crashed server loses only in-flight requests.


Not confirmed, so not repeated
The old page said "MCP was declared dead" became a recurring headline in August 2026, citing InfoQ; the article could not be retrieved and the root page dropped it. The argument behind it is worth knowing anyway: with no handshake and no session, MCP over HTTP is close to a plain JSON API with conventions for discovery, tool schemas, consent and authorization. Whether those conventions justify a protocol is a fair interview question; the answer is that the value is in the shared conventions (any host, any server), not in the transport.






6. Versions, compatibility and extensions


A protocol revision is named by the date it was frozen. Five have been released; each row is checked against that revision's changelog in the specification repository:




RevisionWhat changed



2024-11-05First release: JSON-RPC 2.0; tools, resources, prompts; sampling and roots; stdio and HTTP with SSE (two endpoints).


2025-03-26OAuth 2.1 authorization framework; Streamable HTTP replaces HTTP with SSE; JSON-RPC batching; tool annotations (read-only, destructive); audio content; argument completion (changelog).


2025-06-18Batching removed; structured tool output (outputSchema, structuredContent); servers become OAuth resource servers with protected resource metadata; clients must send RFC 8707 resource indicators; security best practices page; elicitation; resource links in results; MCP-Protocol-Version header required (changelog).


2025-11-25OpenID Connect discovery for authorization servers; icons; incremental scope consent; tool-name guidance; URL-mode elicitation; tool calling inside sampling; Client ID Metadata Documents as the recommended registration; experimental tasks; JSON Schema 2020-12 as default; SDK tiers and governance (changelog).


2026-07-28Stateless core: no handshake, no sessions, server/discover, _meta on every request, MRTR, subscriptions/listen, header mirroring, ttlMs/cacheScope, no stream resumability; tasks move to an extension; RFC 9207 iss validation; credentials bound to their issuer; error-code ranges; roots, sampling, logging and Dynamic Client Registration deprecated; a feature lifecycle policy with a twelve-month minimum deprecation window (changelog).




The direction is consistent: from a chatty, stateful conversation between two processes toward self-describing requests that ordinary web infrastructure can route, cache and secure.


Eras, and the compatibility matrix run for real


The specification calls versions with a handshake legacy (2025-11-25 and earlier) and versions with per-request metadata modern (2026-07-28 on). A dual-era implementation speaks both. A dual-era client probes: on stdio it sends server/discover first and falls back to initialize on any error that is not a recognised modern error; on HTTP it tries a modern request and inspects a 400's body before falling back (versioning). Deprecation, extensions and governance


    

  • Lifecycle. A feature goes Active, then Deprecated (still works; new code should not adopt it), then Removed, with at least twelve months between the release that deprecates it and its removal; the window can be shortened for an active security risk (feature lifecycle).
    • 

  • Extensions are optional additions negotiated in the extensions field of capabilities, named like _meta keys: io.modelcontextprotocol/... for official ones, your reversed domain (com.example/...) for your own. If one side lacks an extension, the other must fall back to core behaviour or refuse (extensions). Official ones today: Tasks (io.modelcontextprotocol/tasks: a durable handle for long work, polled with tasks/get, input via tasks/update); MCP Apps (io.modelcontextprotocol/ui: a server returns interactive HTML that renders inside the conversation); OAuth client credentials for machine-to-machine access and Enterprise-Managed Authorization, where an organisation's identity provider grants access to servers centrally; and Skills over MCP.
    • 

  • Governance. Changes go through Specification Enhancement Proposals (SEPs, numbered by pull request) with working and interest groups; the project sits in the Agentic AI Foundation under the Linux Foundation (section 1).
    • 







7. Authorization: how a remote server knows who is calling


A stdio server inherits the user's environment, so it needs no protocol for credentials (the specification says stdio servers SHOULD NOT use this framework and should read credentials from the environment). A remote server must decide, on every request, whether this caller may do this. MCP does not invent a scheme: it profiles OAuth 2.1 (still an IETF draft, revision 16 of 3 September 2026; the MCP text cites revision 13). What OAuth is and how authorization code, PKCE and JWTs work is taught on Auth; this section is how MCP uses them (authorization).


Roles. The MCP server is an OAuth resource server: it accepts tokens and serves requests. The MCP client is an OAuth client acting for a user. An authorization server (your company's identity provider, or one built into the service) talks to the user and issues tokens. The design goal is that a client which has never heard of a server can still connect to it securely, with no manual setup.


The flow, as recorded


ckpt-tools ran behind the SDK's resource-server support; a small authorization server stood in for an identity provider, with the user's consent scripted (it approves every valid request); the SDK 2.3.0 client used its OAuthClientProvider. All on loopback (measured; every byte in the Wire lab):


    

  1. Try without a token. POST /mcp returned 401 with WWW-Authenticate: Bearer ..., resource_metadata=".../.well-known/oauth-protected-resource/mcp".
    2. 

  2. Read the server's metadata (RFC 9728 protected resource metadata): it names the resource (http://127.0.0.1:30752/mcp) and its authorization_servers. If the header is missing, clients try the well-known URLs themselves.
    3. 

  3. Read the authorization server's metadata (RFC 8414, or OpenID Connect discovery): endpoints, code_challenge_methods_supported: ["S256"], client_id_metadata_document_supported: true, authorization_response_iss_parameter_supported: true. The client must check that the document's issuer equals the address it fetched it from.
    4. 

  4. Identify the client without registering. With a Client ID Metadata Document, the client_id is an HTTPS URL that serves a JSON description of the client (name, redirect URIs); the authorization server fetches it and checks it describes itself. Here: https://localhost:30744/oauth/client.json. This replaces Dynamic Client Registration (RFC 7591), now deprecated, under which every server's authorization server had to accept registrations from anyone.
    5. 

  5. Authorization request in the user's browser: response_type=code, a PKCE code_challenge (S256), state, scope=ckpt:read and resource=http://127.0.0.1:30752/mcp. That last parameter (RFC 8707) is the MCP-specific must: it says which server the token is for.
    6. 

  6. Redirect back with code, state and iss. The client compares iss with the issuer it recorded before redirecting (RFC 9207, required of clients since 2026-07-28).
    7. 

  7. Token request with the code and the PKCE verifier; the token comes back with aud set to the resource.
    8. 

  8. Retry POST /mcp with Authorization: Bearer ... on every request (never in the URL): 200, three checkpoints.
    9. 



The failures, recorded




Two findings. First, the server answered a request with no credentials with error="invalid_token", although RFC 6750 section 3.1 says a request that "lacks any authentication information" SHOULD get a challenge with no error code (RFC 6750); harmless, but clients should not treat the error code as meaning "your token is bad". Second, the challenge carried no scope, which the MCP text says servers SHOULD include so clients request the least privilege; without it a client falls back to everything in scopes_supported.


Step-up. The 403 with error="insufficient_scope", scope="ckpt:write" tells the client to re-authorize with the union of its old scopes and the new ones, retry a few times at most, then give up. Servers should name every scope an operation needs in one challenge, not one per retry.

The rules that matter most


    

  • Audience binding. Servers MUST accept only tokens issued for them. A token for another API is useless here, as the 401 above shows, so a token stolen from one server cannot be replayed at another.
    • 

  • No token passthrough. A server that needs to call an upstream API (GitHub, your data warehouse) must get its own token for that API, never forward the one it received. Forwarding breaks audience binding, hides the real caller from the upstream's logs and rate limits, and turns the server into a proxy for stolen tokens (security best practices). Token exchange (RFC 8693) is the standard way to get a downstream token; see Auth.
    • 

  • Credentials belong to one issuer. Clients key stored client credentials and tokens by the authorization server's issuer and never reuse them with another; a CIMD client ID, being a URL, works with any authorization server.
    • 

  • Machines and enterprises. An agent with no user (a nightly job) uses the OAuth client credentials extension; organisations that want central control use Enterprise-Managed Authorization, where the identity provider decides which servers each employee's client may reach (section 6).
    •

8. Security: where trust breaks, and what holds it


MCP connects a system that follows instructions written in text (the model) to systems that act (tools). Most of its security problems follow from two facts in section 1: whatever a tool returns becomes part of the model's context, and whatever a server says about its tools shapes what the model does. The protocol can carry the right signals (consent, audiences, annotations), but the decisions are the host's. The clearest way to organise the risks is by who the attacker is.




AttackerRiskWhat holds



Whoever wrote content a tool reads (a web page, an issue, an email, a file)Indirect prompt injection: instructions hidden in data reach the model as if they were part of the task. Becomes data theft when one agent has private data, untrusted content and a way to send data out: Simon Willison's "lethal trifecta" (16 June 2025). The root page records the bytes of such a tool result (Topic: protocols, section 9).Remove a leg of the trifecta for each task: scope the tools a session can see, keep secrets out of reach, restrict where data can be sent. Confirm consequential actions with the user, showing the exact arguments. No filter reliably detects injected text; design as if it gets through.


The server itself (malicious, compromised or updated)Tool poisoning: instructions hidden in a tool's description, which the model reads but users rarely do (named by Invariant Labs, 1 April 2025). Rug pull: a definition that changes after the user approved it. False annotations: a destructive tool marked read-only. And a local server is a program running with your rights.Install servers like any dependency: from known publishers, pinned versions. Show users full tool descriptions; record a hash of each approved definition and ask again when it changes (listChanged notices and ttlMs tell a host when to re-check). Treat annotations from untrusted servers as untrusted (the specification's MUST). Run local servers in a sandbox or container with only the files and network they need.


A web page in the user's browserReaching a server on localhost: by cross-site requests or DNS rebinding. The real case: MCP Inspector, the official debugging tool, let unauthenticated requests to its local proxy launch commands over stdio; CVE-2025-49596, fixed in 0.14.1 (NVD, CVSS 4.0 score 9.4).Validate Origin and Host (the SDK does by default: 403 and 421 in section 4), bind to 127.0.0.1, require a token even on localhost, or use stdio, which has no listening socket at all.


A malicious remote server, against the clientHostile metadata: OAuth URLs and endpoints come from the server, so a client that opens or fetches them carelessly can be led to internal addresses (server-side request forgery, for example a cloud metadata endpoint) or, with unsafe URL handling, to running commands. The real case: mcp-remote, a widely used bridge, was open to OS command injection from a crafted authorization_endpoint; CVE-2025-6514 (NVD, CVSS 3.1 score 9.6).Accept only https: URLs for OAuth endpoints (loopback excepted in development); open authorization URLs only through the system browser, never a shell; for clients running on servers, block private and link-local addresses when fetching metadata; validate the issuer of every metadata document (section 7).


A malicious client or a network intermediaryConfused deputy: an MCP server that proxies a third-party API with one shared OAuth client can be tricked into using a user's earlier consent for an attacker's client. Token passthrough. Forged state: a tampered requestState or a guessed state handle. Header and body disagreeing so a gateway allows one thing and the server does another.Per-client consent recorded by the proxy server, exact redirect URI matching; audience-bound tokens, no passthrough; integrity-protected requestState (the SDK's default; a forgery was rejected in section 5) and handles bound to the authenticated user; reject header mismatches (-32020, measured in section 4).




The specification's security best practices page treats the protocol-level items in depth: confused deputy, token passthrough, SSRF, state handle hijacking (the 2026-07-28 replacement for the old "session hijacking"), local server compromise, OAuth URL validation, stdio in proxy setups, mix-up attacks, localhost redirect impersonation, CIMD trust and scope minimisation.


A defensive checklist for a host


    

  • Show which servers and tools are active, and show tool inputs before sensitive calls; the specification asks for a human able to deny any tool call.
    • 

  • Expose per task only the tools the task needs; do not combine tools that read private data with tools that read untrusted content and tools that send data out, unless a human approves each outbound action.
    • 

  • Give each server its own credentials with the least scope, from the environment or OAuth, never the user's master tokens; prefer short-lived tokens.
    • 

  • Run local servers with restricted file system and network access; show the exact command before adding a server from a one-click link.
    • 

  • Pin and diff tool definitions; prefix tool names by server to avoid collisions.
    • 

  • Log every tool call with its arguments and result size, so an incident can be reconstructed; set time limits on tool calls.
    • 

  • Treat irreversible actions (deleting, paying, sending, moving hardware) as a different class: confirmation outside the conversation, so text in the context cannot approve them. The root page's note on agents driving instruments makes the same point.
    •

9. Building a server in Python


The official Python SDK (mcp on PyPI, 2.3.0 here; documentation) turns typed functions into tools. The whole ckpt-tools server is about 90 lines (src/lab/ckpt_server.py); its skeleton:


from mcp.server import MCPServer
from mcp.server.caching import CacheHint
from mcp_types import ToolAnnotations

mcp = MCPServer("ckpt-tools", version="1.0.0",
                instructions="Inspect and prune training checkpoints. Deleting asks the user first.",
                cache_hints={"tools/list": CacheHint(ttl_ms=300_000, scope="public")})

class Checkpoint(BaseModel):
    name: str; step: int; val_loss: float; size_gb: float

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True, openWorldHint=False))
def list_checkpoints(run: str) -> list[Checkpoint]:
    """List the saved checkpoints of a training run, oldest first, with validation loss."""
    return RUNS.get(run, [])

@mcp.resource("ckpt://{run}/config")
def run_config(run: str) -> str: ...

@mcp.prompt()
def pick_best(run: str) -> str: ...

if __name__ == "__main__":
    mcp.run("stdio")          # or mcp.run("streamable-http", host="127.0.0.1", port=8000)


The docstring becomes the description, the type hints become both schemas, a Pydantic model becomes a structured result, a parameter typed Context gives access to progress, input responses and the protocol version. The same server object answers 2025-11-25 and 2026-07-28 clients.


Design tools for a model, not as an API mirror


    

  • Few, task-shaped tools. A model choosing among 40 thin REST wrappers picks worse and pays for 40 definitions in every request (ckpt-tools' list of three tools was 1,818 bytes of JSON). Prefer "list checkpoints of a run with their eval loss" over "GET /runs/{id}/artifacts?type=ckpt".
    • 

  • Write descriptions as documentation for a capable newcomer: what it does, when to use it, units, limits, what an error means. This text is the model's only manual.
    • 

  • Return little. Summaries, identifiers and a cursor beat full dumps; every byte of content is input tokens (section 3).
    • 

  • Errors the model can act on: "checkpoint llama-7b-step-9000 not found; existing: ..." as isError: true, not a stack trace.
    • 

  • Mark side effects honestly (annotations), make destructive tools idempotent where possible (deleting twice is a no-op), and ask for confirmation through elicitation for irreversible ones, as delete_checkpoint does.
    • 

  • No state in the process for an HTTP server: handles in arguments, a shared requestState key, external stores; then any replica can serve any request (section 5).
    • 

  • stdout is sacred on stdio: log to stderr; check that libraries you import do not print.
    • 



Testing


    

  • In process, no transport. The SDK's Client accepts the server object itself: async with Client(mcp) as c: r = await c.call_tool("list_checkpoints", {"run": "llama-7b-sft"}). Fast unit tests of every tool, both eras (mode="legacy" forces the handshake).
    • 

  • Over the real transport: the same calls through stdio and through HTTP, to catch stdout pollution, serialisation and header problems.
    • 

  • Contract tests on the wire: send the hostile requests of section 4 (wrong headers, bad versions, foreign Origin) and assert the status codes; keep them in CI so an SDK upgrade cannot silently change them.
    • 

  • Interactive: MCP Inspector (uv run mcp dev server.py) lists and calls tools by hand. Use 0.14.1 or later (CVE-2025-49596, section 8), and do not leave it running.
    • 

  • With a model: record real agent transcripts and score whether the model picks the right tool with the right arguments, before and after you change a description. A description change is a behaviour change.
    • 



Deploying across an organisation


    

  • Local servers are distributed like packages (PyPI, npm, container images) and configured per host. Pin versions; review the launch command.
    • 

  • Remote servers are ordinary web services: behind TLS and a load balancer, several stateless replicas sharing the requestState key, OAuth with your identity provider, rate limits per client, logs with the caller's identity. Header mirroring lets a gateway enforce per-tool policy and route by Mcp-Name without reading bodies.
    • 

  • Central configuration. Hosts let administrators decide which servers people may use. In Claude Code, for example, a managed-mcp.json file or the managedMcpServers managed setting provides servers to every user, and allowedMcpServers and deniedMcpServers restrict the rest (Claude Code MCP docs; the setting needs Claude Code 2.1.259 or later). On the authorization side, the Enterprise-Managed Authorization extension lets the identity provider grant access centrally.
    • 

  • Finding servers. The official registry (registry.modelcontextprotocol.io) launched in preview on 8 September 2025: an open catalogue and API with namespaced server names. A listing is metadata, not a security review.
    • 

  • Observability. Put traceparent in _meta so traces join across host and server; the Python SDK wraps handling in OpenTelemetry spans.
    •

10. Building a client and a host


Most engineers write servers; anyone building an agent writes a host. The client side of the SDK in a few lines:


from mcp import Client, StdioServerParameters

async with Client(StdioServerParameters(command="python", args=["ckpt_server.py", "stdio"]),
                  elicitation_callback=ask_user) as c:      # or Client("https://.../mcp")
    tools = (await c.list_tools()).tools                   # cached for ttlMs
    r = await c.call_tool("delete_checkpoint", {"name": "llama-7b-step-1000"})
    # an input_required result is handled inside call_tool: ask_user runs, the call is retried


mode="auto" (the default) probes server/discover and falls back to the handshake for legacy servers; mode="2026-07-28" skips the probe; mode="legacy" forces the handshake. The host's job around this:


    

  1. Start and supervise servers: launch stdio processes, restart crashed ones, set call timeouts.
    2. 

  2. Build the model's tool list from every server's tools/list, prefixing names by server so search from two servers stays distinct; keep the order stable for the prompt cache; drop tools the current task does not need.
    3. 

  3. Run the loop: send the model request; for each tool call apply policy (allowed? needs confirmation? show the arguments), route to the right client, return content as the tool result (including isError results, so the model can correct itself), repeat.
    4. 

  4. Handle input requests: render elicitation forms to the user, and say who is asking; on decline, return the decline rather than inventing an answer.
    5. 

  5. Watch for change: re-list when ttlMs expires or a list_changed notice arrives on subscriptions/listen; diff definitions against what the user approved.
    6. 

  6. Authorize remote servers with OAuth (section 7), storing tokens per authorization server, never in logs.
    7.

Interview questions, with model answers


Does the model call MCP servers?
No. The host lists the servers' tools, translates them into the model API's tool definitions, receives the model's tool calls, applies its own policy, and sends tools/call through the client for that server. MCP is between host and server; the model sees only tool definitions and tool results. That is also why the host, not the protocol, is where consent and scoping live.


Tools, resources and prompts: what is the difference?
Who decides to use them. Tools are model-controlled (the model calls them), resources are application-controlled (the app attaches data to context), prompts are user-controlled (the user picks a template). They differ in risk too: a tool can act, a resource only informs.


Why did MCP remove sessions in 2026-07-28, and what did it cost?
Sessions lived in one server process, so every request of a session had to reach that process: sticky load balancing or a shared session store, and servers holding streams open while waiting for clients. Now every request carries version and capabilities in _meta, server-to-client questions become input-required results that the client answers by retrying (MRTR), and any replica can serve any request. Costs: about 180 bytes of metadata per request, an extra round trip for confirmations, state handles the model must carry, and a key that all replicas must share to seal requestState. In a two-replica test, old sessions failed 20 of 20 calls through round robin; new requests failed 20 of 20 until the replicas shared the key, then succeeded 20 of 20.


A tool fails because of bad input. Error response or result?
A result with isError: true and an explanation, so the model can retry with corrected arguments (clarified in 2025-11-25). JSON-RPC errors are for problems the model cannot fix: malformed requests, unknown methods, protocol versions, header mismatches.


How does a client that has never seen a server get a token for it?
The server's 401 points to its protected resource metadata (RFC 9728), which names its authorization server; the client reads that server's metadata (RFC 8414 or OIDC discovery), identifies itself with a Client ID Metadata Document URL (or falls back to dynamic registration), runs authorization code with PKCE including resource= the server's URL (RFC 8707), checks the iss in the response (RFC 9207), and sends the bearer token on every request. The server accepts only tokens whose audience is itself, and never forwards them upstream.


What is token passthrough and why is it banned?
A server accepting a token that was not issued for it and forwarding it to an upstream API. It breaks audience binding (a token for one service works at another), hides the real caller from the upstream's controls and logs, and makes the server a proxy for stolen tokens. The fix is for the server to hold or exchange for its own upstream credentials.


Your agent reads web pages and can send email. What do you worry about, and what do you do?
Indirect prompt injection: page text reaching the model as if it were instructions. With private data in reach, that is the lethal trifecta. Break a leg per task: do not give a browsing task access to private data, or require a human to approve every outbound message with its full content, or restrict destinations. Detection helps but is not a control; design for the injection getting through.


stdio or Streamable HTTP for a new server?
stdio when it acts on the user's own machine and accounts with the user's rights: no network surface, credentials from the environment, one process per user. Streamable HTTP when it is shared, holds data or credentials that should not be on laptops, or must scale: then it is a web service with TLS, OAuth, stateless replicas and a shared state key. Speed is not the deciding factor: both answered in one to three milliseconds on loopback.

What to take from it


    

  • Old protocol, round robin: initialize creates a session in one replica; the very next request goes to the other, which answers 404 "Session not found". Nothing about the tool matters; the session itself cannot cross replicas.
    • 

  • Old protocol, affinity: works, at the price of a balancer that understands MCP sessions, uneven load, and lost sessions whenever a replica restarts. The confirmation travels as a server request on the open stream and the answer as a separate POST.
    • 

  • New protocol, per-process keys: no session, but the first answer carries sealed requestState; the retry reaches the other replica, which cannot open it. Fails 20 of 20.
    • 

  • New protocol, shared key: two independent POSTs, either replica can answer either one. 20 of 20, with no affinity and nothing held in memory between them.
    •
