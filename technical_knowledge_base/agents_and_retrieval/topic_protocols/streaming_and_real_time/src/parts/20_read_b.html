2. Polling and long polling: asking again and again

Polling is the obvious first answer and still the right one more often than people admit. The client sends GET /jobs/123 every few seconds and the server answers at once with the current state. Every piece of HTTP works unchanged: caching, retries, load balancers, authentication, logs. A status endpoint that sends an ETag lets the client ask "has it changed since version 7?" with If-None-Match, and the answer to most polls becomes an empty 304 Not Modified (conditional requests are taught on the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page, section 3). Its costs are the two numbers in section 1: latency set by the timer, and a request per tick whether or not anything happened.

Long polling removes the empty answers. The client sends the same request, but the server does not answer until it has something new or a hold timeout passes (then it answers "nothing yet", and the client asks again). It was the standard trick for chat in browsers before WebSockets (the "Comet" era); the IETF wrote down its known problems in {{RFC 6202|https://www.rfc-editor.org/rfc/rfc6202}} (Informational, April 2011).

How it works, step by step.

  1. The client asks for everything after a cursor: GET /events?after=3. The cursor is what makes it safe: events that happen while no request is waiting are not lost, they are returned to the next request.
  2. The server holds the request (an asynchronous server holds thousands cheaply; a thread-per-request server runs out of threads).
  3. When news exists, or after the hold timeout, it answers with the events and the new cursor.
  4. The client immediately asks again with the new cursor.

What it costs, and how it fails.

  • One request per batch of events, each with full headers and, for an authenticated API, a credential check. measured 6 requests for 7 events on the running answer.
  • An extra round trip whenever events come faster than requests (section 1's 100 ms run).
  • The hold timeout must be shorter than every idle timeout on the path, or a proxy answers for the server: a 504 or a cut connection (nginx's proxy_read_timeout defaults to 60 s; the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page's Timeout chain tab has the others). 20 to 30 s is the usual choice.
  • Each waiting request occupies a connection. In a browser on HTTP/1.1 that is one of only six per host (measured in section 4).
  • Thundering herd: when the server restarts, every held request fails at once and every client re-asks at once. Add random jitter to the client's retry.

Where you still meet both. Asynchronous jobs: a batch inference or fine-tuning API answers 202 Accepted with a job id, and the client polls a status URL (or registers a webhook, section 10). A2A, the agent-to-agent protocol, lets a client poll a task's state as well as stream it or receive push notifications ({{Agent-to-agent|n:3f05c17b0d0d81199373d4d0b18706d8}}). And long polling is the fallback that libraries such as Socket.IO use when a network blocks WebSockets.

Predict, then reveal

Your long-polling endpoint holds requests for 90 s. Behind an nginx with default settings, what do clients see when nothing happens for two minutes?

A 504 after 60 s. nginx's default proxy_read_timeout is 60 s ({{nginx docs|https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout}}): it waits that long for the upstream to send something, then gives up and answers 504 Gateway Timeout itself. The root page's Failure lab reproduces exactly this as "Read timeout: connected, then nothing". Hold for less than the shortest timeout on the path, and treat a 504 from a long-poll endpoint as "ask again".

3. Server-Sent Events: the format, byte by byte

The idea. Instead of answering and closing, the server answers once and keeps the response open, writing a new chunk of text whenever it has news. The client reads the body as it arrives rather than waiting for its end. That is all SSE is: an agreed text format for a response that does not end, defined in the HTML standard ({{WHATWG HTML, section 9.2|https://html.spec.whatwg.org/multipage/server-sent-events.html}}, a living standard, last updated 5 October 2026), plus a small browser API, EventSource, that reads it.

The response head. Three header fields matter:

  • Content-Type: text/event-stream: the only thing that makes it SSE. A browser's EventSource refuses any other type, and refuses any status other than 200.
  • Cache-Control: no-cache: an event stream is not a document to cache.
  • X-Accel-Buffering: no: not part of the standard; it tells nginx-style proxies not to buffer this response (the root's Failure lab case "A buffering proxy delays tokens" shows what buffering does). The standard way to say the same thing is now the Incremental header field ({{RFC 10036|https://www.rfc-editor.org/rfc/rfc10036}}, August 2026).

There is no Content-Length, because nobody knows how long the answer will be. On HTTP/1.1 the body therefore travels in chunked encoding (each chunk preceded by its size in hex); on HTTP/2 and HTTP/3, in DATA frames. Neither is visible to the SSE parser, which sees only the text.

The body. A sequence of events. Each event is one or more lines of the form field: value, and a blank line ends it. Here is one token event of the running answer, exactly as sent:

event: content_block_delta␊ data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"The"}}␊ ␊
Click a line. measured This event is 118 bytes: 27 for the event line, 90 for the data line (6 for data: , 83 of JSON, 1 newline), 1 for the blank line. The token itself is 3 of them.

The four fields, and comments.

LineWhat the parser doesUsed for
data: ...Appends the value to the event's data, plus a newline. Several data lines in one event are joined with newlines; the final newline is removed when the event is delivered.The payload. LLM APIs put one JSON object here.
event: nameSets the event's type. Without it the type is message.Typed events (message_start, content_block_delta). In a browser, onmessage sees only untyped events; typed ones need addEventListener('name', ...), a classic "my handler never fires" bug.
id: 42Sets the last event id, which the browser sends back as Last-Event-ID when it reconnects. An id containing a NUL character is ignored.Resuming after a cut (section 6).
retry: 500Sets the reconnection delay in milliseconds, if the value is all digits; otherwise ignored.Telling clients how fast to come back.

(blank line)Dispatches the event, if its data is not empty, then starts a new one.The end of every event. Forget it and nothing is ever delivered.

The parsing rules that bite. Lines may end in LF, CR LF, or a lone CR. Exactly one space after the colon is removed, so data:  a carries " a". A line with no colon is a field name with an empty value. A field name the parser does not know is ignored, including data  with a space before the colon. An event that the stream ends before its blank line is thrown away. One UTF-8 byte order mark at the very start is stripped. The stream is UTF-8, and a network read can end in the middle of a character or a line, so a parser must buffer bytes, not decode each read on its own.

Measured: eight real parsers against these rules

measured The {{Parser test|#t-parse}} tab sends 18 byte streams, each testing one rule, to 8 parsers and shows what each delivered. Chrome's EventSource and Node's eventsource package followed the standard on all of them. The four Python parsers tried (the parsers inside the official OpenAI and Anthropic SDKs, httpx-sse, sseclient-py) each lost the first event after a byte order mark, and the first three delivered an event that had no data line, which the standard says to skip. sseclient-py also delivered an event cut off by the end of the stream and kept an id containing NUL. None of this hurts with today's LLM APIs, which never send these shapes; it matters when you write the server or a proxy that re-frames events.

Predict, then reveal

A server sends data:{"text":"hi"} with no space after the colon, then a blank line. What does the client's event contain?

The whole JSON. The space after the colon is optional; if it is there, exactly one space is removed. All eight parsers measured agree on this case (the nospace row of the Parser test tab).
