1. One answer, four ways: polling, long polling, SSE, WebSocket

In HTTP the client always speaks first, and gets one response. Server push bends that in four ways: polling asks again on a timer; long polling asks and the server holds the request until it has news; SSE asks once and the response never quite ends; a WebSocket asks once to switch protocols and then either side sends at any time. (The fifth, a webhook, reverses the roles: section 9.) Predict before you press play: on a 50 ms round trip, how much later than SSE does polling every 100 ms deliver the last token?

SSE and WebSocket track the earliest possible arrival; long polling falls behind when tokens outpace round trips; polling delivers in clumps

What the run shows. On the 50 ms path the last token reached the client at 376 ms by SSE, 379 ms by WebSocket, 401 ms by long polling (6 requests for 7 events) and 528 ms by polling (4 requests). Once a stream is open, each token costs one one-way trip. Long polling needs the next request to be waiting at the server: at a 100 ms round trip, tokens 50 ms apart bunch two per response (4 requests for 7 events) and the last token lands at 446 ms against SSE's 428 ms. Polling's latency is set by its timer, not by the model.

Polling is still often right: all of HTTP works unchanged (caching, retries, load balancers, auth, logs), and with an ETag most polls become an empty 304 Not Modified via If-None-Match ({{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}, section 3). A batch or fine-tuning API answers 202 Accepted with a job id and the client polls a status URL (or registers a webhook); A2A lets a client poll a task as well as stream it ({{Agent-to-agent|n:3f05c17b0d0d81199373d4d0b18706d8}}).

Long polling, done safely. The client asks for everything after a cursor (GET /events?after=3), so events that happen while no request waits go to the next one, never lost. The server holds the request (cheap when asynchronous, fatal for thread-per-request) and answers with the events and the new cursor. Costs: one request per batch with full headers and a credential check; a connection held per waiting client (one of a browser's six per host on HTTP/1.1, section 3); a thundering herd when the server restarts and every held request retries at once (add jitter). Its problems are written down in {{RFC 6202|https://www.rfc-editor.org/rfc/rfc6202}} (Informational, April 2011, the "Comet" era), and it remains Socket.IO's fallback when a network blocks WebSockets.

Predict, then reveal

Your long-polling endpoint holds requests for 90 s. Behind an nginx with default settings, what do clients see when nothing happens for two minutes?

A 504 after 60 s. nginx's default proxy_read_timeout is 60 s ({{nginx docs|https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout}}): it waits that long for the upstream to send something, then answers 504 Gateway Timeout itself (the parent topic's Failure lab reproduces this as "Read timeout: connected, then nothing"; the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page's Timeout chain tab has the other hops). Hold for less than the shortest timeout on the path (20 to 30 s is usual) and treat a 504 from a long-poll endpoint as "ask again".
Bytes: over an hour of waiting, per mechanism on the running answer, and why tokens can also bunch over TCP

Bytes grow with idle time, not with the answer. Waiting one hour for a job, polling every second is 3,600 requests (3,600 s ÷ 1 s), long polling held 25 s per request is 144 (3,600 ÷ 25), and SSE is one request plus a comment line every 15 s (the HTML standard's keep-alive advice), 240 lines of 8 bytes (: ping plus two newlines).
