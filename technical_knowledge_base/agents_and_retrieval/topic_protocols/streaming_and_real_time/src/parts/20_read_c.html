4. SSE clients: EventSource, fetch, and the six-connection trap

EventSource, the browser's built-in client. new EventSource('/events') opens the stream, parses it, delivers each event to your handlers, and reconnects on its own when the connection drops. It is deliberately small, and three of its limits decide when you can use it:

  • GET only, no body. An LLM request carries a JSON body with the conversation, so it cannot be an EventSource request.
  • No custom headers. You cannot send Authorization or x-api-key; only cookies (with withCredentials for another origin, which then needs CORS). That is one more reason browser apps never send an LLM API key directly (the {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} page explains why keys stay on the server).
  • Status and type are strict. Any status other than 200, or a content type other than text/event-stream, "fails the connection" and it does not retry. A network error, or the stream simply ending, makes it reconnect.

So LLM apps use fetch() (or an SDK built on it) with a POST, read response.body as a stream, and run an SSE parser over the bytes; that gives full control of method, headers and body, and you write reconnection yourself if you want it. The {{JavaScript and TypeScript|n:3cd5c17b0d0d81dbac7be3b8686be023}} page (Part 1) builds exactly this client. On the server side of your own app, the same pattern applies in Python: httpx streaming plus httpx-sse, or the official SDKs, which wrap their own parser.

The six-connection trap. On HTTP/1.1 a browser opens at most six connections to one host, and an open SSE stream holds one for as long as it lives. measured In Chrome 148 against this page's HTTP/1.1 lab server, a page opened eight EventSource streams to one host: 6 opened within 10 ms and the other two never opened in the 3.5 s observed; a plain fetch() to the same host, started 0.3 s in, had not finished either. Every request to that host queues behind the streams. MDN notes the limit is per browser and host, across tabs, and that Chrome and Firefox marked the bug "Won't fix" ({{MDN: EventSource|https://developer.mozilla.org/en-US/docs/Web/API/EventSource}}). The fix is HTTP/2 or HTTP/3, where each stream is one of many on a single connection; the server's SETTINGS_MAX_CONCURRENT_STREAMS sets how many, with no limit until it says otherwise and a recommendation of at least 100 ({{RFC 9113 section 6.5.2|https://www.rfc-editor.org/rfc/rfc9113#section-6.5.2}}).

Correction to a common reading of MDN

MDN says the HTTP/2 limit "defaults to 100". The protocol has no default: until the server's SETTINGS arrive the number of streams is unlimited, and RFC 9113 only recommends that servers not set it below 100. Most servers do announce 100 or more, so in practice the advice holds.

A real public stream. measured Wikimedia publishes every edit to its wikis as an SSE stream. Four seconds of curl -N https://stream.wikimedia.org/v2/stream/recentchange on 5 October 2026: HTTP/2, content-type: text/event-stream; charset=utf-8, a first line :ok (a comment, sent at once so every proxy sees bytes), then 150 events and 228,771 bytes. Each event's id is a JSON array naming Kafka topics, partitions and timestamps or offsets: send it back as Last-Event-ID and the service resumes from that point in its log. Its documentation also says the connection is cut after 15 minutes regardless, and that "a good SSE / EventSource client should be able to automatically reconnect and begin consuming at the right location" ({{EventStreams docs|https://wikitech.wikimedia.org/wiki/Event_Platform/EventStreams_HTTP_Service}}). That is the whole design of a resumable stream in one service: ids that name a position in a durable log.








5. LLM token streams: what the APIs actually send


The shape. A streaming LLM call is an ordinary POST with "stream": true in the JSON body. The server answers 200 with text/event-stream at once, then writes one event per piece of the answer. Because the status line went out first, an error that happens later (the model overloaded halfway) cannot change it: it arrives as an event inside the stream (the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page, section 2, has a drill on this).


Anthropic's Messages API ({{streaming docs|https://platform.claude.com/docs/en/build-with-claude/streaming}}, read 5 October 2026) sends named events in a fixed order:


    

  1. message_start: a Message object with empty content.
    2. 

  2. For each content block: content_block_start, one or more content_block_delta, content_block_stop. Deltas are text_delta for text, input_json_delta for a tool call's arguments (partial JSON strings: accumulate them and parse at content_block_stop), thinking_delta for extended thinking, and one signature_delta just before a thinking block closes.
    3. 

  3. One or more message_delta (stop reason; cumulative token usage).
    4. 

  4. message_stop.
    5. 



Two more can appear anywhere: ping events (the server's own keep-alive), and error, for example {"type": "error", "error": {"type": "overloaded_error", ...}}, which would have been an HTTP 529 had the response not started. The docs also say new event types may be added and clients should ignore types they do not know. The running example on this page sends a trimmed version of this sequence.


The OpenAI-compatible style uses unnamed events (data lines only) and ends with a sentinel event whose data is [DONE]. To SSE that is ordinary data; the client must recognise it. The official Python SDK does, with if sse.data.startswith("[DONE]"): break ({{openai-python _streaming.py|https://github.com/openai/openai-python/blob/main/src/openai/_streaming.py}}), and vLLM's OpenAI-compatible server ends chat and completion streams with yield "data: [DONE]\n\n" ({{vLLM chat_completion/serving.py|https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/openai/chat_completion/serving.py}}, read at commit b0eb87fe49, 4 October 2026). A client that forgets the sentinel tries to parse [DONE] as JSON and throws on the last event of every answer.


What the server must do so the stream really streams (you own this if you serve a model or proxy one):


    

  • Send the response head and a first byte immediately (an SSE comment works), so every hop sees activity before the model's first token.
    • 

  • Flush after every event; never compress text/event-stream (gzip holds bytes until it has enough to compress).
    • 

  • Mark the response unbuffered: X-Accel-Buffering: no for nginx, the Incremental header for intermediaries that support RFC 10036.
    • 

  • Send a heartbeat (a : ping comment or a ping event) more often than the shortest idle timeout on the path. The {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page measured a 3 s think surviving a short idle timeout because of a comment every second; it also owns the list of proxy and load balancer timeouts and which ones streaming cannot help (total-duration timeouts).
    • 

  • Write each event with one write call. Small writes can also be held by TCP itself (Nagle's algorithm), which bunches tokens on a real network: {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}, section 7.
    • 

  • When proxying a stream, forward complete events; never cut and re-join the bytes in a way that splits a line or a UTF-8 character.
    • 



The same format in agent protocols. MCP's Streamable HTTP transport answers each request with plain JSON, or with an SSE stream when it has progress notifications to send before the result; since the 2026-07-28 revision those streams are no longer resumable (Last-Event-ID was removed) and servers should send X-Accel-Buffering: no (the {{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}} page measured both). A2A streams task updates over SSE and also offers polling and push notifications, which are webhooks ({{Agent-to-agent|n:3f05c17b0d0d81199373d4d0b18706d8}}).


Predict, then reveal


Your app streams from the Claude API. Halfway through, the stream delivers event: error with an overloaded_error, then ends. Your logs record the HTTP status of each call. What do they record for this one?




200. The status was sent before the first token and cannot change; the failure lives only in the body. Count stream-level errors (and streams that end without message_stop) as their own metric, or your error rate will read zero during an overload.
