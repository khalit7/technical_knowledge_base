10. Beyond text: voice and WebRTC, gRPC streams, WebTransport

Realtime voice: why audio does not ride on SSE

A voice agent streams audio both ways at once and must stop when the user speaks over it (barge-in), which rules out SSE and makes loss matter far more than for text. The realtime LLM APIs use a WebSocket from servers and WebRTC from browsers and phones: OpenAI's Realtime API connects over WebRTC "in the browser or WebSocket on the server" ({{Realtime guide|https://developers.openai.com/api/docs/guides/realtime}}, read 5 October 2026), and Google's Gemini Live API is a "stateful WebSocket connection (WSS)" with WebRTC through partners ({{Gemini Live API|https://ai.google.dev/gemini-api/docs/live}}). Over a WebSocket the audio is raw PCM, base64 inside JSON events, and that sets the bit rate:

WebRTC's codec: "from low bitrate narrowband speech at 6 kbit/s to very high quality stereo music at 510 kbit/s" ({{RFC 6716|https://www.rfc-editor.org/rfc/rfc6716}})

What WebRTC is for. A WebSocket rides on TCP, which delivers bytes in order: one lost packet on a phone's radio holds back every later byte until it is resent (head-of-line blocking, measured on HTTP/1.1, 2 and 3 in the parent topic's On the wire tab), so speech stalls, then bursts. WebRTC is the browser's real-time media stack: media over UDP with jitter buffers that skip a lost packet instead of waiting, a compressed codec instead of raw PCM, and the browser's echo cancellation. Hence the pattern OpenAI's docs recommend: WebRTC from the user's device, WebSocket between your server and the provider, where the network is clean and you already have raw audio.

Audio formats and endpoints of the OpenAI and Gemini realtime APIs

OpenAI's Realtime API also documents telephony (SIP) integrations ({{WebSocket guide|https://developers.openai.com/api/docs/guides/realtime-websocket}}, read 5 October 2026). Over WebSocket, audio goes up inside JSON events (input_audio_buffer.append) as base64 of raw PCM: 16-bit mono at 24 kHz (default) or 16 kHz, or G.711 at 8 kHz; the same guide points to a separate full-duplex model, gpt-live-1, with its own WebSocket endpoint (wss://api.openai.com/v1/live/sessions). Gemini Live: input 16-bit PCM at 16 kHz, output 16-bit PCM at 24 kHz.

gRPC streaming, on the wire

A gRPC call is one HTTP/2 stream: headers, length-prefixed messages, and the status in trailers

From gRPC's {{PROTOCOL-HTTP2.md|https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md}} (read 24 October 2026). Each message is a 1-byte compressed flag, a 4-byte big-endian length, then the bytes (usually protobuf).

gRPC's four call types (unary, server streaming, client streaming, bidirectional) are one shape on the wire: a single HTTP/2 stream on which either side writes length-prefixed messages in DATA frames, so a streaming call costs no new connection and HTTP/2 flow control gives each stream its backpressure. Like SSE, the response starts with :status 200; the outcome travels last, in trailers ("Status must be sent in Trailers even if the status code is OK"), so a stream that fails halfway still had HTTP 200, and your metrics must read grpc-status. A client cancels with RST_STREAM CANCEL, mapped to call cancellation; a deadline travels as the grpc-timeout header ("If Timeout is omitted a server should assume an infinite timeout"). Browsers cannot read HTTP/2 trailers, so they speak gRPC-Web, which carries the status as the last message of the body ("Due to browser limitation, the Web client library implements a different protocol", {{PROTOCOL-WEB.md|https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-WEB.md}}), normally through a translating proxy. gRPC as an API style (protobuf contracts, when to choose it over REST, load balancing long-lived HTTP/2 connections) is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}'s.

WebTransport: streams and datagrams over HTTP/3

WebTransport gives a web page what WebSockets cannot: several independent streams on one connection (a loss on one does not stall the others), unreliable datagrams for data useless if late (game state, live media), and QUIC's faster setup. It runs over HTTP/3 ({{draft-ietf-webtrans-http3|https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/}}, revision 16 of 6 July 2026, still a draft), using HTTP datagrams ({{RFC 9297|https://www.rfc-editor.org/rfc/rfc9297}}) and QUIC datagrams ({{RFC 9221|https://www.rfc-editor.org/rfc/rfc9221}}). MDN marks the browser API "Baseline 2026, newly available" since March 2026: Chrome 97, Firefox 114, Safari 26.4 ({{MDN: WebTransport API|https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API}}, compatibility data checked 5 October 2026). Networks that block UDP need a WebSocket fallback, server and proxy support is thinner than for HTTP/1.1 and 2, and for an LLM text stream it adds nothing over SSE.

Sync engines: subscribe to a query, receive diffs

A different use of a WebSocket: the client subscribes to a query and the server keeps a local copy of the results up to date. Meteor's Distributed Data Protocol (DDP, about 2012) is the early, documented example ({{DDP specification|https://github.com/meteor/meteor/blob/devel/packages/ddp/DDP.md}}): over WebSockets or SockJS, the client sends sub, and the server sends added, changed and removed messages for documents, then ready; the same connection carries method calls with their result and updated messages. Two ideas outlived it: the server tracks what each client has and sends differences, not snapshots; and the client applies a method's effect immediately and reconciles when the answer arrives (latency compensation). Live-query features in Firebase, Supabase Realtime and Phoenix LiveView are the same shape. (In ML, "DDP" means PyTorch's DistributedDataParallel, unrelated: {{Distributed training|n:3c65c17b0d0d8103a916c4824abbd82e}}.)
