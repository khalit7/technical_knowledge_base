7. WebSockets: an HTTP request that becomes a two-way pipe

The problem it solves. SSE only flows one way. A voice agent must hear the user while it speaks (so the user can interrupt), a shared document must send each keystroke while receiving everyone else's, a game must send moves while receiving the world. Doing that with HTTP means a POST per client message next to a stream for server messages: two channels, two sets of ordering and failure, a request's headers on every keystroke. A WebSocket gives one connection on which either side can send a message at any moment, with 2 to 14 bytes of framing instead of hundreds of bytes of headers. It is defined in {{RFC 6455|https://www.rfc-editor.org/rfc/rfc6455}} (December 2011, a Proposed Standard, updated by RFC 7936, 8307 and 8441), and the browser API in the {{WHATWG WebSockets standard|https://websockets.spec.whatwg.org/}}.

Two negotiations people confuse. Sec-WebSocket-Protocol names the application protocol carried inside (the client offers a list, the server picks one): graphql-transport-ws, MQTT, your own chat.v2. Version your messages this way rather than with a field you add later. Sec-WebSocket-Extensions changes the framing; in practice there is one extension, permessage-deflate (section 8).


Authentication is awkward, by design of the browser API. The handshake is the only moment HTTP headers exist, and the browser's new WebSocket(url) cannot set any (no Authorization). The options: a cookie (then you must check Origin, section 9); a short-lived single-use ticket fetched over normal HTTPS and passed in the URL (keep URLs out of logs, expire in seconds); or an authentication message as the first frame, refusing everything else until it arrives. Realtime LLM APIs use tickets: OpenAI's browser clients get an ephemeral client secret from your server, which created it with POST /v1/realtime/client_secrets ({{OpenAI Realtime guide|https://developers.openai.com/api/docs/guides/realtime}}), and Google recommends ephemeral tokens for client-side Gemini Live connections ({{Gemini Live API|https://ai.google.dev/gemini-api/docs/live}}). Server-side clients send the API key in the handshake header as usual. The {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} page covers token audience and lifetime.







8. Frames: what travels after the 101


After the handshake, everything is a frame: a header of 2 to 14 bytes, then the payload. The {{WebSocket bytes|#t-ws}} tab decodes every frame of the recorded exchange bit by bit; here is the layout.




FieldSizeMeaning



FIN1 bit1 on the last frame of a message. A message may be split into fragments: the first frame carries the type, the rest are "continuation" frames, and only the last has FIN = 1.


RSV1 to RSV33 bits0 unless an extension says otherwise; permessage-deflate sets RSV1 on compressed messages.


Opcode4 bits0 continuation, 1 text (UTF-8), 2 binary, 8 close, 9 ping, 10 pong; the rest unassigned ({{IANA registry|https://www.iana.org/assignments/websocket/websocket.xhtml}}).


MASK1 bit1 on every frame from client to server, 0 on every frame from server to client. A wrong value must fail the connection.


Payload length7, 7+16 or 7+64 bits0 to 125 fits in the 7 bits; 126 means "the next 2 bytes are the length"; 127, "the next 8 bytes are".


Masking key0 or 4 bytesPresent only when MASK = 1: four random bytes, and the payload is XORed with them, repeating.




measured The server's token "The" went out as 81 53 followed by 83 bytes of JSON: 81 is FIN = 1 plus opcode 1 (text), 53 is MASK = 0 and length 83. The client's message "Stop" went out as 10 bytes: 81 84 (FIN, text; MASK = 1, length 4), four bytes of masking key, and the four XORed bytes. Seven messages of the running answer: 539 bytes of JSON plus 14 bytes of headers (2 per message).


Why clients mask. Not for secrecy: the key travels in clear next to the data. In 2011, researchers showed that some proxies, seeing an upgraded connection they did not understand, could be fed attacker-chosen bytes that looked like a second HTTP request and would cache the "response", poisoning the cache for everyone behind it. Masking with a fresh random key per frame means a script in a browser cannot choose the bytes that appear on the wire (RFC 6455 section 10.3). It costs one XOR pass over every byte a client sends; servers do not mask, and must reject unmasked client frames.


Control frames. Ping, pong and close carry at most 125 bytes and are never fragmented, so they can be slipped between the fragments of a long message. A ping must be answered by a pong with the same bytes: that is the protocol's built-in heartbeat (measured: the client's ping "hb" came back as 8a 02 68 62). Browsers answer pings automatically, but JavaScript can neither send a ping nor see one, so browser apps that want to detect a dead peer send their own heartbeat messages.


Closing. Either side sends a close frame with an optional 2-byte status code and a reason; the other answers with a close frame; then the TCP connection closes (measured: 1000 "bye", echoed). The codes you will see in logs:

Compression: permessage-deflate ({{RFC 7692|https://www.rfc-editor.org/rfc/rfc7692}}, December 2015) compresses each message's payload with DEFLATE and sets RSV1. By default the compressor's state carries from one message to the next (context takeover), so a message can refer back to earlier ones: ideal for a stream of near-identical JSON. measured With the websockets library's own encoder, the running answer's 7 messages took 553 bytes uncompressed and 198 compressed with context takeover; a longer answer (the 357 words of RFC 6455 section 1.1 sent one word per message, same JSON shape) took 31,759 bytes uncompressed, 3,937 with zlib's defaults, 4,250 with the library's smaller defaults, and 25,278 with no context takeover (each message compressed alone, losing most of the gain). The price is memory per connection: the library's documentation measures about 14 KiB without compression, 64 KiB with its defaults (window 212, memLevel 5) and 316 KiB with zlib's (window 215, memLevel 8) ({{websockets: compression|https://websockets.readthedocs.io/en/stable/topics/compression.html}}), from zlib's formula of 2windowBits+2 + 2memLevel+9 bytes to compress and 2windowBits to decompress. At 100,000 connections that is about 6 GiB against 30 GiB (derived: 100,000 × 64 KiB and × 316 KiB). Compressing a secret next to attacker-controlled text in one context also re-opens CRIME-style attacks, where the compressed size leaks the secret; and compressing audio or images wastes CPU.


WebSockets over HTTP/2 and HTTP/3. The upgrade above only exists in HTTP/1.1. {{RFC 8441|https://www.rfc-editor.org/rfc/rfc8441}} (September 2018) carries a WebSocket as one stream of an HTTP/2 connection through an "extended CONNECT" request with :protocol: websocket, and {{RFC 9220|https://www.rfc-editor.org/rfc/rfc9220}} (June 2022) does the same for HTTP/3. Both are Proposed Standards; which browsers, proxies and servers implement them was not checked for this page, so plain HTTP/1.1 upgrade remains the safe assumption, and a load balancer may speak HTTP/2 to the client and HTTP/1.1 upgrade to your server.
