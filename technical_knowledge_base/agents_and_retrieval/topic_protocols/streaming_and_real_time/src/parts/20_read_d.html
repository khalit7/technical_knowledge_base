6. Stop, cut, resume: when a stream ends early

A stream can end early in three ways, and each needs a different answer: the network cuts it (a proxy timeout, a deploy draining a server, a phone moving from Wi-Fi to cellular), the user cuts it (the Stop button), or the server fails partway (the overloaded error above).

The network cuts it: reconnect, and resume if you can

A browser's EventSource reconnects by itself. What the user then sees depends entirely on whether the server numbered its events. Below, the running answer is cut after three events on every connection, and Chrome reconnects; the three runs are the same server with three settings.

Each step is one thing the page's handlers saw, with its time; the server's log adds the Last-Event-ID each reconnect carried. Text shown is what a chat UI would render by appending every token it receives; highlighted tokens are repeats.

What the three runs show. Without ids, Chrome reconnected after 3.007 s and the server, knowing nothing, started the answer again: the user saw "The sky" twice, then three times, forever. With ids, the reconnect carried Last-Event-ID: 2, the server resumed at event 3, and the answer completed; but when the stream then ended normally, Chrome reconnected again (to EventSource, an ended stream is a dropped one) and would keep doing so every 3 s. With retry: 500 the reconnects came after 0.504 s, and answering the final reconnect with 204 No Content (a status other than 200, so the connection "fails") stopped it cleanly. The standard leaves the default delay to the browser, "probably in the region of a few seconds"; 3 s is Chrome's.

Making a stream resumable is a server design, not a header. The server must be able to answer "everything after event 2", which means the events must outlive the connection. The common shape: generation runs as a job that appends events to a log (a Redis stream, a Kafka topic, a database table) keyed by response id; the HTTP handler only tails that log from the client's last id. Then a dropped connection neither stops the work nor duplicates it, and any server behind the load balancer can serve the reconnect. Wikimedia's stream (section 4) is this shape over Kafka. design pattern No LLM API resumes a generation stream today: a cut stream is a failed request, retried from the start (with an idempotency key where the API supports one, per the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page, section 9), and MCP removed SSE resumability in its 2026-07-28 revision.

The rule for clients

A stream that ends without its final event (message_stop, [DONE]) is a failure, even when no exception was raised: some proxies close a cut stream cleanly. Check for the terminator before you show or store the answer.

The user cuts it: the server must notice

When the user presses Stop, the client closes the connection (on HTTP/2, it resets only that stream, with RST_STREAM and the error code CANCEL, {{RFC 9113 section 7|https://www.rfc-editor.org/rfc/rfc9113#section-7}}). The client is gone; whether the GPU stops working is up to the server. A server usually learns about a closed connection only when it next tries to write, and during the think before the first token it writes nothing.

measured src/lab/cancel.py against lab_server.py (aiohttp 3.14.3): 200 tokens 20 ms apart; the client closes the connection 0.5 s after sending the request. "Careful" checks every 20 ms whether the connection is closing. "Think" stands for prefill or queueing: a stretch with nothing to write.

The naive handler burned 3.0 s of "GPU time" for a user who had left after 0.5 s, against 0.51 s for the careful one. Once tokens flow, both stop within one token, because the next write fails. Real servers do the careful version: vLLM wraps its OpenAI-compatible endpoints in a with_cancellation decorator that runs the handler and a listener for the ASGI http.disconnect message side by side and cancels the handler when the disconnect arrives ({{vllm/entrypoints/serve/utils/api_utils.py|https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/serve/utils/api_utils.py}}, read at commit 8c1557a79c). Note what that cannot see: a proxy between the user and the server that keeps its upstream connection open after the client left (some do, to reuse it) hides the disconnect entirely.

Predict, then reveal

An EventSource stream without ids is cut after the first two tokens. What does a chat UI that appends every token show after the reconnect?

The beginning twice. The browser does reconnect, but without an id it sends no Last-Event-ID, so the server cannot know where to resume and starts over. Either number the events and resume, or have the client clear the partial answer on open.
