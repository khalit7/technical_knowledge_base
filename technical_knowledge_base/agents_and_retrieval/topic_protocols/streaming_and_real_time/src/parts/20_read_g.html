10. Webhooks: the provider calls you

The problem. A fine-tuning job runs for four hours. Holding a stream open that long is fragile (Wikimedia cuts its streams at 15 minutes), and polling is wasteful. A webhook turns the direction around: you register a URL with the provider, and when something happens it sends an HTTP POST with a JSON description of the event to that URL. It is not a protocol, it is a convention on top of HTTP, and correctness lives entirely in a few rules that both sides must follow. A community specification, Standard Webhooks, writes them down ({{spec|https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md}}, v1.0.0 December 2025; the root's Protocol atlas checked its versions).

Rule 1: verify the signature, over the raw bytes

Your endpoint is a public URL; anyone can POST to it. So the provider signs each delivery with a secret it shared with you, using an HMAC (a hash keyed by the secret, here HMAC-SHA256): only someone holding the secret can produce the right value. The three common formats:

measured GitHub publishes a test vector (secret "It's a Secret to Everybody", payload "Hello, World!"); this page's three-line HMAC reproduced its signature exactly. With the standardwebhooks Python library and a made-up secret, the raw body verified; the same JSON after json.loads and json.dumps (which adds spaces after colons and commas) failed with "No matching signature found"; and a correctly signed message 10 minutes old failed with "Message timestamp too old" (the library's tolerance is 5 minutes). The lesson: read the raw request body before any framework parses it, compare signatures with a constant-time function (hmac.compare_digest), and reject stale timestamps so a captured request cannot be replayed later.



Rules 2 and 3: duplicates and disorder are normal


A provider retries any delivery that did not get a 2xx answer in time, with backoff over hours or days: Standard Webhooks' example schedule is immediately, then 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 14 h, 20 h, 24 h (about 75 hours in all), and Stripe retries "for up to three days" in live mode. So the same event can arrive several times (a slow handler that finished after the sender gave up), and events can arrive in any order (a retried early event lands after a later one). Stripe states both plainly: it does not guarantee order, and endpoints "might occasionally receive the same event more than once".

      What the replay shows. The naive receiver did the work before answering, so every delivery outlived the sender's 1 s timeout; the sender saw only failures, retried each event to the end of its schedule, and the work ran 7 times. Worse, the stored status flipped back from "succeeded" to "running" whenever a late copy of job.running finished. The careful receiver answered 200 within milliseconds, ignored duplicates by webhook-id, did the work from a queue, and wrote the job's status as re-read from the source of truth rather than from the payload: 2 runs of the work, and the right final status even though job.running arrived last.
      

      The receiver checklist
      

        

      1. Verify the signature over the raw body; reject stale timestamps; compare in constant time.
        2. 

      2. Store the event id before working; if it is already there, answer 200 and stop.
        3. 

      3. Answer 2xx quickly (Stripe: "before any complex logic that could cause a timeout"; Standard Webhooks suggests senders allow 15 to 30 s), then work from a queue.
        4. 

      4. Do not trust order: treat an event as "something changed about job X" and fetch X's current state from the API (a thin payload design, which also keeps less data in transit).
        5. 

      5. Answer 410 Gone to tell a sender to stop sending to this URL; 429, 502 and 504 ask it to slow down.

      The sender's side. If you send webhooks (an agent platform notifying customers, A2A push notifications), you are making HTTP requests to URLs your users chose, from inside your network. Standard Webhooks tells senders to route them through a proxy that refuses internal addresses, or an attacker registers http://169.254.169.254/ and reads your cloud metadata (server-side request forgery, SSRF; the {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}} page covers the DNS rebinding variant). Sign every delivery, keep payloads small (the spec suggests under 20 KB), retry with jitter, and disable endpoints that fail for days, telling their owner through another channel. The outbox pattern that makes "update the database and send the webhook" reliable is on {{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}; webhook API design is on {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}}.
      

      Where an ML engineer meets them. Completion of long jobs: fine-tuning, batch inference, evaluations, training runs on a managed platform. Inside your own infrastructure the same need is usually met by a queue or event bus (SNS, EventBridge, Pub/Sub, Kafka), with exactly the same at-least-once discipline: a function triggered by a queue also sees duplicates.
