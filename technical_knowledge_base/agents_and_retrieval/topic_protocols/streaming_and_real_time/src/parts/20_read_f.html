6. WebSockets: an HTTP request that becomes a two-way pipe

SSE flows one way. A voice agent must hear the user while it speaks (barge-in), a shared document sends each keystroke while receiving everyone else's, a game sends moves while receiving the world. With HTTP that means a POST per client message beside a stream: two channels, two sets of ordering and failure, a request's headers on every keystroke. A WebSocket gives one connection on which either side sends a message at any moment, with 2 to 14 bytes of framing. It is {{RFC 6455|https://www.rfc-editor.org/rfc/rfc6455}} (December 2011, a Proposed Standard, updated by RFC 7936, 8307 and 8441), with the browser API in the {{WHATWG WebSockets standard|https://websockets.spec.whatwg.org/}}.

Two negotiations people confuse. Sec-WebSocket-Protocol names the application protocol inside (subprotocol; the client offers a list, the server picks one): graphql-transport-ws, MQTT, your own chat.v2; version your messages this way. Sec-WebSocket-Extensions changes the framing; in practice the one extension is permessage-deflate (section 7).


Authentication is awkward by design. The handshake is the only moment HTTP headers exist, and the browser's new WebSocket(url) cannot set any. The options: a cookie (then check Origin); a short-lived single-use ticket fetched over HTTPS and passed in the URL (keep URLs out of logs, expire in seconds); or an authentication message as the first frame. Realtime LLM APIs use tickets: OpenAI's browser clients get an ephemeral client secret from your server, which created it with POST /v1/realtime/client_secrets ({{OpenAI Realtime guide|https://developers.openai.com/api/docs/guides/realtime}}), and Google recommends ephemeral tokens for client-side Gemini Live connections ({{Gemini Live API|https://ai.google.dev/gemini-api/docs/live}}). Server-side clients send the API key in the handshake header as usual ({{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} covers token audience and lifetime).






7. Frames: what travels after the 101




Every frame starts with two bytes; length and mask decide how many more




measured The bits are the server's token "The": 81 53 then 83 bytes of JSON. Opcodes: 0 continuation, 1 text (UTF-8), 2 binary, 8 close, 9 ping, 10 pong; the rest unassigned ({{IANA registry|https://www.iana.org/assignments/websocket/websocket.xhtml}}). Length 0 to 125 fits in the 7 bits; 126 means the next 2 bytes hold it, 127 the next 8. RSV1 is set by permessage-deflate on compressed messages. A message may be split into fragments: the first carries the type, the rest are continuations, and only the last has FIN = 1.




measured The client's message "Stop" went out as 10 bytes: 81 84 (FIN, text; MASK = 1, length 4), four bytes of masking key, and four XORed bytes. Seven messages of the running answer: 539 bytes of JSON plus 14 bytes of headers (2 per message). Pick any frame of the recorded session below.

The slider moves through 0, 1, 3, 83, 125, 126, 1,000, 65,535, 65,536 and 1,048,576 bytes; lengths up to 125 fit in 7 bits, up to 65,535 take 2 more bytes, larger ones 8 more (RFC 6455 section 5.2).




Why clients mask. Not for secrecy: the key travels in clear beside the data. In 2011, researchers showed that some proxies, seeing an upgraded connection they did not understand, could be fed attacker-chosen bytes that looked like a second HTTP request and would cache the "response", poisoning the cache for everyone behind them. A fresh random key per frame means a script in a browser cannot choose the bytes on the wire (RFC 6455 section 10.3). It costs one XOR pass over every byte a client sends; servers never mask, every client frame must be masked, and a wrong MASK bit must fail the connection.


Control frames. Ping, pong and close carry at most 125 bytes and are never fragmented, so they slip between the fragments of a long message. A ping is answered by a pong with the same bytes, the built-in heartbeat (measured: the client's ping "hb" came back as 8a 02 68 62). Browsers answer pings automatically, but JavaScript can neither send nor see one, so browser apps send their own heartbeat messages.


Closing. Each side sends a close frame with an optional 2-byte code and reason, the other echoes it, then TCP closes (measured: 1000 "bye", echoed). The code to know is 1006 Abnormal Closure: never sent, only reported locally when the connection died without a close frame: idle timeouts, crashes, network loss and, in browsers, every failed handshake whatever the reason. 1000 is the intended end, 1001 Going Away a server shutting down or a page left, 1008 and 1011 "not allowed" and "we broke", and 4000 to 4999 are yours.




permessage-deflate shrinks a token stream about eight times, but only if the compressor remembers earlier messages




measured The websockets library's own encoder on a long answer: the 357 words of RFC 6455 section 1.1 sent one word per message in the running answer's JSON shape. Memory per connection is the library's documented measurement ({{websockets: compression|https://websockets.readthedocs.io/en/stable/topics/compression.html}}).




Compression ({{RFC 7692|https://www.rfc-editor.org/rfc/rfc7692}}, December 2015) deflates each payload and sets RSV1. By default the compressor's state carries from message to message (context takeover), ideal for near-identical JSON (the figure: about eight times smaller). The price is memory per connection, 64 KiB to 316 KiB, so about 6 GiB against 30 GiB at 100,000 connections; and compressing a secret beside attacker-controlled text re-opens CRIME-style attacks, where the compressed size leaks the secret. Do not compress audio or images.

Compression, the numbers. measured the short running answer took 553 bytes uncompressed and 198 compressed; the long one 31,759, 3,937 with zlib's defaults, 4,250 with the library's smaller defaults and 25,278 with no context takeover. The price is memory per connection: about 14 KiB without compression, 64 KiB with the library's defaults (window 212, memLevel 5), 316 KiB with zlib's (window 215, memLevel 8), from zlib's formula of 2windowBits+2 + 2memLevel+9 bytes to compress and 2windowBits to decompress. At 100,000 connections that is about 6 GiB against 30 GiB (derived: 100,000 × 64 KiB and × 316 KiB). Compressing a secret beside attacker-controlled text in one context re-opens CRIME-style attacks, where the compressed size leaks the secret; and compressing audio or images wastes CPU.

WebSockets over HTTP/2 and HTTP/3. The upgrade above exists only in HTTP/1.1. {{RFC 8441|https://www.rfc-editor.org/rfc/rfc8441}} (September 2018) carries a WebSocket as one stream of an HTTP/2 connection through an "extended CONNECT" request with :protocol: websocket, and {{RFC 9220|https://www.rfc-editor.org/rfc/rfc9220}} (June 2022) does the same for HTTP/3. Both are Proposed Standards; which browsers, proxies and servers implement them was not checked for this page, so the HTTP/1.1 upgrade remains the safe assumption, and a load balancer may speak HTTP/2 to the client and HTTP/1.1 upgrade to your server.
