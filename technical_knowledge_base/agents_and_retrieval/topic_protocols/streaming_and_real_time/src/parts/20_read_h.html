11. Voice agents, WebTransport, and sync engines

Realtime voice: why audio does not ride on SSE

A voice agent streams audio both ways at once: the user's microphone up, the model's speech down, and the user must be able to interrupt (barge-in). That rules out SSE (one direction) and makes the network's behaviour on loss matter far more than for text.

  • OpenAI's Realtime API connects over WebRTC "in the browser or WebSocket on the server", and documents telephony (SIP) integrations ({{Realtime guide|https://developers.openai.com/api/docs/guides/realtime}}, {{WebSocket guide|https://developers.openai.com/api/docs/guides/realtime-websocket}}, read 5 October 2026). Over WebSocket, audio goes up inside JSON events (input_audio_buffer.append) as base64 of raw PCM: 16-bit mono at 24 kHz (default) or 16 kHz, or G.711 at 8 kHz. The same guide points to a separate full-duplex model, gpt-live-1, with its own WebSocket endpoint (wss://api.openai.com/v1/live/sessions).
  • Google's Gemini Live API is a "stateful WebSocket connection (WSS)"; input audio is 16-bit PCM at 16 kHz, output 16-bit PCM at 24 kHz; WebRTC is available through partner integrations ({{Gemini Live API|https://ai.google.dev/gemini-api/docs/live}}).

Why WebRTC for the last mile. A WebSocket rides on TCP, which delivers bytes in order: one lost packet on a phone's radio holds back every later byte until it is resent (head-of-line blocking, measured on HTTP/1.1, 2 and 3 in the root's On the wire tab), so speech stalls, then bursts. WebRTC carries media over UDP with jitter buffers that skip a lost packet rather than wait for it, a compressed codec instead of raw PCM, and the browser's echo cancellation. Hence the pattern the OpenAI docs recommend: WebRTC from the user's device, WebSocket between your server and the model provider, where the network is clean and you already have raw audio.

WebTransport: streams and datagrams over HTTP/3

WebTransport gives a web page what WebSockets cannot: several independent streams on one connection (a loss on one does not stall the others), unreliable datagrams for data that is useless if late (game state, live media), and QUIC's faster setup. It runs over HTTP/3 ({{draft-ietf-webtrans-http3|https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/}}, revision 16 of 6 July 2026, still a draft), using HTTP datagrams ({{RFC 9297|https://www.rfc-editor.org/rfc/rfc9297}}) and QUIC datagrams ({{RFC 9221|https://www.rfc-editor.org/rfc/rfc9221}}). The browser API is now in every major engine: MDN marks it "Baseline 2026, newly available" since March 2026, with support from Chrome 97, Firefox 114 and Safari 26.4 ({{MDN: WebTransport API|https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API}}; MDN's compatibility data, checked 5 October 2026). Two costs remain: networks that block UDP (some corporate ones) need a WebSocket fallback, and server and proxy support is thinner than for HTTP/1.1 and 2. For an LLM text stream it adds nothing over SSE.

Sync engines: subscribe to data, receive diffs

A different use of a WebSocket: instead of messages, the client subscribes to a query and the server keeps a local copy of the results up to date. Meteor's Distributed Data Protocol (DDP, about 2012) is the early, documented example ({{DDP specification|https://github.com/meteor/meteor/blob/devel/packages/ddp/DDP.md}}): over WebSockets or SockJS, the client sends sub, and the server sends added, changed and removed messages for documents, then ready; the same connection carries method calls with their result and updated messages. Two ideas outlived it: the server tracks what each client has and sends differences, not snapshots; and the client applies a method's effect immediately and reconciles when the server's answer arrives (latency compensation). Live-query features in Firebase, Supabase Realtime and Phoenix LiveView are the same shape. (In ML, "DDP" means PyTorch's DistributedDataParallel, which has nothing to do with this: see {{Distributed training|n:3c65c17b0d0d8103a916c4824abbd82e}}.)
