HTTP was built for "ask, then get an answer". Real-time is everything that does not fit that shape: the server has news before the client knows to ask. There are only a handful of ways to do it, and they differ in who opens the connection, how long it stays open, which direction bytes can flow, and what happens when it breaks.

The running example. The root page's chat app asks "What colour is the sky?" with one 117-byte POST /v1/messages, and the answer is five tokens: The,  sky,  is,  blue, .. The stand-in model (no real model runs) waits 120 ms before the first token, standing in for the model reading the prompt, then produces one every 50 ms, framed by a message_start and a message_stop event: seven events in all, in the shapes of Anthropic's Messages API. This page delivers that same answer by polling, long polling, Server-Sent Events and a WebSocket, cuts it, resumes it, cancels it, and sends a webhook when a job ends.

Five things to remember
  1. If only the server talks, use SSE: it is plain HTTP, so everything you know about HTTP still works. Reach for a WebSocket only when the client must talk on the same channel.
  2. Every long-lived connection dies eventually (idle timeouts, deploys, phones changing networks). Design the reconnect first: event ids, resume, backoff with jitter.
  3. A quiet stream is a dead stream to some proxy on the path: send a heartbeat (an SSE comment, a WebSocket ping) more often than the shortest idle timeout.
  4. When the user presses Stop, the server should stop computing. Detecting a closed connection is your job, and a server that only notices on its next write wastes the whole think time.
  5. Webhooks are at least once and unordered: verify the signature over the raw bytes, deduplicate on the event id, answer 2xx fast, and treat the payload as a hint to re-read the truth.

1. Push: getting news to a client that did not ask

The problem. In HTTP the client always speaks first: it sends a request, the server sends one response, done (the HTTP page teaches requests and responses from zero). That is perfect for "give me this page". It does not fit "tell me each token as the model produces it", "tell me when someone else edits this document", or "tell me when my fine-tuning job finishes in four hours". In each, the server has news at a moment the client cannot predict. Getting it to the client is called server push, and every mechanism on this page is a way to do it.

There are only four basic shapes, and the picture below runs the running answer through all four on the same clock:

  • Polling (short polling): the client asks "anything new?" on a timer, say every 100 ms, and the server answers at once, often with "no".
  • Long polling: the client asks, and the server holds the request open until it has news (or a timeout passes), answers, and the client immediately asks again.
  • Server-Sent Events (SSE): the client asks once, and the server's answer never quite ends: it keeps writing small text events into the same response.
  • WebSocket: the client asks once to switch protocols; after that the connection is a two-way pipe and either side can send a message at any time.

The fifth, webhooks, turns the direction around: the provider becomes the client and calls a URL on your server when the news exists (section 10).

2. Polling and long polling: asking again and again

Polling is the obvious first answer and still the right one more often than people admit. The client sends GET /jobs/123 every few seconds and the server answers at once with the current state. Every piece of HTTP works unchanged: caching, retries, load balancers, authentication, logs. A status endpoint that sends an ETag lets the client ask "has it changed since version 7?" with If-None-Match, and the answer to most polls becomes an empty 304 Not Modified (conditional requests are taught on the HTTP page, section 3). Its costs are the two numbers in section 1: latency set by the timer, and a request per tick whether or not anything happened.

Long polling removes the empty answers. The client sends the same request, but the server does not answer until it has something new or a hold timeout passes (then it answers "nothing yet", and the client asks again). It was the standard trick for chat in browsers before WebSockets (the "Comet" era); the IETF wrote down its known problems in RFC 6202 (Informational, April 2011).

How it works, step by step.

  1. The client asks for everything after a cursor: GET /events?after=3. The cursor is what makes it safe: events that happen while no request is waiting are not lost, they are returned to the next request.
  2. The server holds the request (an asynchronous server holds thousands cheaply; a thread-per-request server runs out of threads).
  3. When news exists, or after the hold timeout, it answers with the events and the new cursor.
  4. The client immediately asks again with the new cursor.

What it costs, and how it fails.

  • One request per batch of events, each with full headers and, for an authenticated API, a credential check. measured 6 requests for 7 events on the running answer.
  • An extra round trip whenever events come faster than requests (section 1's 100 ms run).
  • The hold timeout must be shorter than every idle timeout on the path, or a proxy answers for the server: a 504 or a cut connection (nginx's proxy_read_timeout defaults to 60 s; the HTTP page's Timeout chain tab has the others). 20 to 30 s is the usual choice.
  • Each waiting request occupies a connection. In a browser on HTTP/1.1 that is one of only six per host (measured in section 4).
  • Thundering herd: when the server restarts, every held request fails at once and every client re-asks at once. Add random jitter to the client's retry.

Where you still meet both. Asynchronous jobs: a batch inference or fine-tuning API answers 202 Accepted with a job id, and the client polls a status URL (or registers a webhook, section 10). A2A, the agent-to-agent protocol, lets a client poll a task's state as well as stream it or receive push notifications (Agent-to-agent). And long polling is the fallback that libraries such as Socket.IO use when a network blocks WebSockets.

Predict, then reveal

Your long-polling endpoint holds requests for 90 s. Behind an nginx with default settings, what do clients see when nothing happens for two minutes?

A 504 after 60 s. nginx's default proxy_read_timeout is 60 s (nginx docs): it waits that long for the upstream to send something, then gives up and answers 504 Gateway Timeout itself. The root page's Failure lab reproduces exactly this as "Read timeout: connected, then nothing". Hold for less than the shortest timeout on the path, and treat a 504 from a long-poll endpoint as "ask again".

3. Server-Sent Events: the format, byte by byte

The idea. Instead of answering and closing, the server answers once and keeps the response open, writing a new chunk of text whenever it has news. The client reads the body as it arrives rather than waiting for its end. That is all SSE is: an agreed text format for a response that does not end, defined in the HTML standard (WHATWG HTML, section 9.2, a living standard, last updated 5 October 2026), plus a small browser API, EventSource, that reads it.

The response head. Three header fields matter:

  • Content-Type: text/event-stream: the only thing that makes it SSE. A browser's EventSource refuses any other type, and refuses any status other than 200.
  • Cache-Control: no-cache: an event stream is not a document to cache.
  • X-Accel-Buffering: no: not part of the standard; it tells nginx-style proxies not to buffer this response (the root's Failure lab case "A buffering proxy delays tokens" shows what buffering does). The standard way to say the same thing is now the Incremental header field (RFC 10036, August 2026).

There is no Content-Length, because nobody knows how long the answer will be. On HTTP/1.1 the body therefore travels in chunked encoding (each chunk preceded by its size in hex); on HTTP/2 and HTTP/3, in DATA frames. Neither is visible to the SSE parser, which sees only the text.

The body. A sequence of events. Each event is one or more lines of the form field: value, and a blank line ends it. Here is one token event of the running answer, exactly as sent:

event: content_block_delta␊ data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"The"}}␊ ␊
Click a line. measured This event is 118 bytes: 27 for the event line, 90 for the data line (6 for data: , 83 of JSON, 1 newline), 1 for the blank line. The token itself is 3 of them.

The parsing rules that bite. Lines may end in LF, CR LF, or a lone CR. Exactly one space after the colon is removed, so data:  a carries " a". A line with no colon is a field name with an empty value. A field name the parser does not know is ignored, including data  with a space before the colon. An event that the stream ends before its blank line is thrown away. One UTF-8 byte order mark at the very start is stripped. The stream is UTF-8, and a network read can end in the middle of a character or a line, so a parser must buffer bytes, not decode each read on its own.

4. SSE clients: EventSource, fetch, and the six-connection trap

EventSource, the browser's built-in client. new EventSource('/events') opens the stream, parses it, delivers each event to your handlers, and reconnects on its own when the connection drops. It is deliberately small, and three of its limits decide when you can use it:

  • GET only, no body. An LLM request carries a JSON body with the conversation, so it cannot be an EventSource request.
  • No custom headers. You cannot send Authorization or x-api-key; only cookies (with withCredentials for another origin, which then needs CORS). That is one more reason browser apps never send an LLM API key directly (the Auth page explains why keys stay on the server).
  • Status and type are strict. Any status other than 200, or a content type other than text/event-stream, "fails the connection" and it does not retry. A network error, or the stream simply ending, makes it reconnect.

So LLM apps use fetch() (or an SDK built on it) with a POST, read response.body as a stream, and run an SSE parser over the bytes; that gives full control of method, headers and body, and you write reconnection yourself if you want it. The JavaScript and TypeScript page (Part 1) builds exactly this client. On the server side of your own app, the same pattern applies in Python: httpx streaming plus httpx-sse, or the official SDKs, which wrap their own parser.

The six-connection trap. On HTTP/1.1 a browser opens at most six connections to one host, and an open SSE stream holds one for as long as it lives. measured In Chrome 148 against this page's HTTP/1.1 lab server, a page opened eight EventSource streams to one host: 6 opened within 10 ms and the other two never opened in the 3.5 s observed; a plain fetch() to the same host, started 0.3 s in, had not finished either. Every request to that host queues behind the streams. MDN notes the limit is per browser and host, across tabs, and that Chrome and Firefox marked the bug "Won't fix" (MDN: EventSource). The fix is HTTP/2 or HTTP/3, where each stream is one of many on a single connection; the server's SETTINGS_MAX_CONCURRENT_STREAMS sets how many, with no limit until it says otherwise and a recommendation of at least 100 (RFC 9113 section 6.5.2).

Correction to a common reading of MDN

MDN says the HTTP/2 limit "defaults to 100". The protocol has no default: until the server's SETTINGS arrive the number of streams is unlimited, and RFC 9113 only recommends that servers not set it below 100. Most servers do announce 100 or more, so in practice the advice holds.

A real public stream. measured Wikimedia publishes every edit to its wikis as an SSE stream. Four seconds of curl -N https://stream.wikimedia.org/v2/stream/recentchange on 5 October 2026: HTTP/2, content-type: text/event-stream; charset=utf-8, a first line :ok (a comment, sent at once so every proxy sees bytes), then 150 events and 228,771 bytes. Each event's id is a JSON array naming Kafka topics, partitions and timestamps or offsets: send it back as Last-Event-ID and the service resumes from that point in its log. Its documentation also says the connection is cut after 15 minutes regardless, and that "a good SSE / EventSource client should be able to automatically reconnect and begin consuming at the right location" (EventStreams docs). That is the whole design of a resumable stream in one service: ids that name a position in a durable log.








5. LLM token streams: what the APIs actually send


The shape. A streaming LLM call is an ordinary POST with "stream": true in the JSON body. The server answers 200 with text/event-stream at once, then writes one event per piece of the answer. 6. Stop, cut, resume: when a stream ends early


A stream can end early in three ways, and each needs a different answer: the network cuts it (a proxy timeout, a deploy draining a server, a phone moving from Wi-Fi to cellular), the user cuts it (the Stop button), or the server fails partway (the overloaded error above).


The network cuts it: reconnect, and resume if you can


A browser's EventSource reconnects by itself. What the user then sees depends entirely on whether the server numbered its events. Below, the running answer is cut after three events on every connection, and Chrome reconnects; the three runs are the same server with three settings.

What the three runs show. Without ids, Chrome reconnected after 3.007 s and the server, knowing nothing, started the answer again: the user saw "The sky" twice, then three times, forever. With ids, the reconnect carried Last-Event-ID: 2, the server resumed at event 3, and the answer completed; but when the stream then ended normally, Chrome reconnected again (to EventSource, an ended stream is a dropped one) and would keep doing so every 3 s. With retry: 500 the reconnects came after 0.504 s, and answering the final reconnect with 204 No Content (a status other than 200, so the connection "fails") stopped it cleanly. The standard leaves the default delay to the browser, "probably in the region of a few seconds"; 3 s is Chrome's.


Making a stream resumable is a server design, not a header. The server must be able to answer "everything after event 2", which means the events must outlive the connection. The common shape: generation runs as a job that appends events to a log (a Redis stream, a Kafka topic, a database table) keyed by response id; the HTTP handler only tails that log from the client's last id. Then a dropped connection neither stops the work nor duplicates it, and any server behind the load balancer can serve the reconnect. Wikimedia's stream (section 4) is this shape over Kafka. design pattern No LLM API resumes a generation stream today: a cut stream is a failed request, retried from the start (with an idempotency key where the API supports one, per the HTTP page, section 9), and MCP removed SSE resumability in its 2026-07-28 revision.


The rule for clients
A stream that ends without its final event (message_stop, [DONE]) is a failure, even when no exception was raised: some proxies close a cut stream cleanly. Check for the terminator before you show or store the answer.



The user cuts it: the server must notice


When the user presses Stop, the client closes the connection (on HTTP/2, it resets only that stream, with RST_STREAM and the error code CANCEL, RFC 9113 section 7). The client is gone; whether the GPU stops working is up to the server. A server usually learns about a closed connection only when it next tries to write, and during the think before the first token it writes nothing.

7. WebSockets: an HTTP request that becomes a two-way pipe


The problem it solves. SSE only flows one way. A voice agent must hear the user while it speaks (so the user can interrupt), a shared document must send each keystroke while receiving everyone else's, a game must send moves while receiving the world. Doing that with HTTP means a POST per client message next to a stream for server messages: two channels, two sets of ordering and failure, a request's headers on every keystroke. A WebSocket gives one connection on which either side can send a message at any moment, with 2 to 14 bytes of framing instead of hundreds of bytes of headers. It is defined in RFC 6455 (December 2011, a Proposed Standard, updated by RFC 7936, 8307 and 8441), and the browser API in the WHATWG WebSockets standard.

Two negotiations people confuse. Sec-WebSocket-Protocol names the application protocol carried inside (the client offers a list, the server picks one): graphql-transport-ws, MQTT, your own chat.v2. Authentication is awkward, by design of the browser API. The handshake is the only moment HTTP headers exist, and the browser's new WebSocket(url) cannot set any (no Authorization). The options: a cookie (then you must check Origin, section 9); a short-lived single-use ticket fetched over normal HTTPS and passed in the URL (keep URLs out of logs, expire in seconds); or an authentication message as the first frame, refusing everything else until it arrives. Server-side clients send the API key in the handshake header as usual. The Auth page covers token audience and lifetime.







8. Frames: what travels after the 101


After the handshake, everything is a frame: a header of 2 to 14 bytes, then the payload. The WebSocket bytes tab decodes every frame of the recorded exchange bit by bit; here is the layout.

FIN1 bit1 on the last frame of a message. A message may be split into fragments: the first frame carries the type, the rest are "continuation" frames, and only the last has FIN = 1.


RSV1 to RSV33 bits0 unless an extension says otherwise; permessage-deflate sets RSV1 on compressed messages.

Why clients mask. Not for secrecy: the key travels in clear next to the data. In 2011, researchers showed that some proxies, seeing an upgraded connection they did not understand, could be fed attacker-chosen bytes that looked like a second HTTP request and would cache the "response", poisoning the cache for everyone behind it. Masking with a fresh random key per frame means a script in a browser cannot choose the bytes that appear on the wire (RFC 6455 section 10.3). It costs one XOR pass over every byte a client sends; servers do not mask, and must reject unmasked client frames.


Control frames. Ping, pong and close carry at most 125 bytes and are never fragmented, so they can be slipped between the fragments of a long message. A ping must be answered by a pong with the same bytes: that is the protocol's built-in heartbeat (measured: the client's ping "hb" came back as 8a 02 68 62). Browsers answer pings automatically, but JavaScript can neither send a ping nor see one, so browser apps that want to detect a dead peer send their own heartbeat messages.


Closing. Either side sends a close frame with an optional 2-byte status code and a reason; the other answers with a close frame; then the TCP connection closes (measured: 1000 "bye", echoed). The codes you will see in logs:

Compression: permessage-deflate (RFC 7692, December 2015) compresses each message's payload with DEFLATE and sets RSV1. The price is memory per connection: the library's documentation measures about 14 KiB without compression, 64 KiB with its defaults (window 212, memLevel 5) and 316 KiB with zlib's (window 215, memLevel 8) (websockets: compression), from zlib's formula of 2windowBits+2 + 2memLevel+9 bytes to compress and 2windowBits to decompress. At 100,000 connections that is about 6 GiB against 30 GiB (derived: 100,000 × 64 KiB and × 316 KiB). Compressing a secret next to attacker-controlled text in one context also re-opens CRIME-style attacks, where the compressed size leaks the secret; and compressing audio or images wastes CPU.


WebSockets over HTTP/2 and HTTP/3. The upgrade above only exists in HTTP/1.1. Both are Proposed Standards; which browsers, proxies and servers implement them was not checked for this page, so plain HTTP/1.1 upgrade remains the safe assumption, and a load balancer may speak HTTP/2 to the client and HTTP/1.1 upgrade to your server.

A WebSocket is a long-lived, stateful connection, and most of the work of running one is fighting the infrastructure built for short HTTP requests. measured Three things broke on purpose here, each through nginx 1.31.6 in front of the lab's websockets server, each seen by three clients.

1. A proxy that drops the upgrade. Even with proxy_http_version 1.1 (the default since nginx 1.29.7), nginx does not pass Upgrade and Connection on, because they are hop-by-hop headers, unless told to. The server then sees a plain GET and refuses it (426 Upgrade Required here). The fix is three lines in the location: proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade"; (nginx: WebSocket proxying). Note the browser column: JavaScript never sees the 426, only an error and close code 1006. To debug a failed browser handshake, look at the network panel or replay the request with curl:




2. An idle timeout. A proxy treats a WebSocket like any request: if no bytes arrive from the upstream for proxy_read_timeout (60 s by default; 2 s here to make it quick), it closes both sides. No close frame is sent, so every client reports 1006. nginx logged it only at the info level, which the default error level hides:




The fix is a heartbeat more frequent than the shortest idle timeout on the path: with the client sending a ping every second (the pong comes back from the server, so the proxy sees upstream bytes), the same quiet 6 s survived and all seven messages arrived. The websockets library pings every 20 s by default; cloud load balancers and NAT gateways have their own idle limits (AWS's NAT gateway drops a connection idle for 350 s, per Networking foundations, section 9). Raise the proxy timeout for WebSocket routes as well, but never rely on that alone.


3. Cross-site WebSocket hijacking (CSWSH). Browsers do not apply the same-origin policy or CORS to WebSockets: a page on any site can open a socket to your server, and the browser attaches your cookies. If the server authenticates by cookie and does not check Origin, an attacker's page talks to your API as the logged-in user and reads the replies. measured The lab server without an origin list accepted Origin: https://evil.example and sent all seven messages; with origins=["https://chat.example"] it answered 403. Check Origin against a list during the handshake (it protects browser users; non-browser clients can send any Origin they like), prefer tickets to cookies, and remember that the handshake authenticates once: a socket can outlive a logout or a revoked permission, so re-check authorisation periodically and close with 1008 when it lapses.


Scale and lifecycle


    

  • Backpressure. WebSocket.send() in a browser never blocks: it queues, and bufferedAmount tells you how much is waiting. A producer that ignores it fills memory when the network is slow. WebSocketStream gives streams with automatic backpressure, but it is non-standard and, per MDN's compatibility data, shipped only in Chrome (since 124), not Firefox or Safari (MDN: WebSocketStream). Server libraries have their own limits (the websockets library queues at most 16 incoming messages by default, then stops reading).
    • 

  • Reconnection is yours. No browser reconnects a WebSocket. Write exponential backoff with random jitter and a cap, give messages sequence numbers, keep a short replay buffer on the server, and resume from the last number the client saw. Most of what Socket.IO, Phoenix Channels and hosted realtime services sell is this.
    • 

  • Reconnect storms. When a server with 50,000 sockets dies, 50,000 clients reconnect within seconds; without jitter they arrive together. During deploys, close connections in batches with 1001 or 1012 rather than all at once.
    • 

  • Load balancing. A socket is pinned to one server for its whole life, so round-robin balancing only applies to new connections, and adding servers does not move existing load. Keep servers stateless where possible: per-user state in a store, and a publish/subscribe backplane (Redis, NATS, Kafka) so a message for user X reaches whichever server holds X's socket.
    • 

  • Cost per connection is a file descriptor, kernel buffers and whatever state you keep, including compression contexts (section 8). Raise ulimit -n, cap message size, message rate and connections per IP: the protocol itself has no limits, so an unlimited reader is a denial-of-service.
    • 

  • Serverless. Request-scoped functions cannot hold a socket. Platforms offer a managed connection layer that calls your function per message (AWS API Gateway WebSocket APIs) or long-lived objects per room (Cloudflare Durable Objects); both change the cost model, so check per-message prices and limits before choosing them.
    • 

  • Observability. Count open connections per server, messages and bytes per second, close codes (a jump in 1006 is infrastructure, not your code), reconnect rate, and send-queue high-water marks.
    •

10. Webhooks: the provider calls you


The problem. A fine-tuning job runs for four hours. Holding a stream open that long is fragile (Wikimedia cuts its streams at 15 minutes), and polling is wasteful. A webhook turns the direction around: you register a URL with the provider, and when something happens it sends an HTTP POST with a JSON description of the event to that URL. It is not a protocol, it is a convention on top of HTTP, and correctness lives entirely in a few rules that both sides must follow. A community specification, Standard Webhooks, writes them down (spec, v1.0.0 December 2025; the root's Protocol atlas checked its versions).


Rule 1: verify the signature, over the raw bytes


Your endpoint is a public URL; anyone can POST to it. So the provider signs each delivery with a secret it shared with you, using an HMAC (a hash keyed by the secret, here HMAC-SHA256): only someone holding the secret can produce the right value. The three common formats:

Rules 2 and 3: duplicates and disorder are normal


A provider retries any delivery that did not get a 2xx answer in time, with backoff over hours or days: Standard Webhooks' example schedule is immediately, then 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 14 h, 20 h, 24 h (about 75 hours in all), and Stripe retries "for up to three days" in live mode. So the same event can arrive several times (a slow handler that finished after the sender gave up), and events can arrive in any order (a retried early event lands after a later one). Stripe states both plainly: it does not guarantee order, and endpoints "might occasionally receive the same event more than once".

      Realtime voice: why audio does not ride on SSE
      

      A voice agent streams audio both ways at once: the user's microphone up, the model's speech down, and the user must be able to interrupt (barge-in). That rules out SSE (one direction) and makes the network's behaviour on loss matter far more than for text.

      Why WebRTC for the last mile. A WebSocket rides on TCP, which delivers bytes in order: one lost packet on a phone's radio holds back every later byte until it is resent (head-of-line blocking, measured on HTTP/1.1, 2 and 3 in the root's On the wire tab), so speech stalls, then bursts. Hence the pattern the OpenAI docs recommend: WebRTC from the user's device, WebSocket between your server and the model provider, where the network is clean and you already have raw audio.
      

      WebTransport: streams and datagrams over HTTP/3
      

      WebTransport gives a web page what WebSockets cannot: several independent streams on one connection (a loss on one does not stall the others), unreliable datagrams for data that is useless if late (game state, live media), and QUIC's faster setup. It runs over HTTP/3 (draft-ietf-webtrans-http3, revision 16 of 6 July 2026, still a draft), using HTTP datagrams (RFC 9297) and QUIC datagrams (RFC 9221). The browser API is now in every major engine: MDN marks it "Baseline 2026, newly available" since March 2026, with support from Chrome 97, Firefox 114 and Safari 26.4 (MDN: WebTransport API; MDN's compatibility data, checked 5 October 2026). Two costs remain: networks that block UDP (some corporate ones) need a WebSocket fallback, and server and proxy support is thinner than for HTTP/1.1 and 2. For an LLM text stream it adds nothing over SSE.
      

      Sync engines: subscribe to data, receive diffs
      

      A different use of a WebSocket: instead of messages, the client subscribes to a query and the server keeps a local copy of the results up to date. Meteor's Distributed Data Protocol (DDP, about 2012) is the early, documented example (DDP specification): over WebSockets or SockJS, the client sends sub, and the server sends added, changed and removed messages for documents, then ready; the same connection carries method calls with their result and updated messages. Two ideas outlived it: the server tracks what each client has and sends differences, not snapshots; and the client applies a method's effect immediately and reconciles when the server's answer arrives (latency compensation). Live-query features in Firebase, Supabase Realtime and Phoenix LiveView are the same shape. (In ML, "DDP" means PyTorch's DistributedDataParallel, which has nothing to do with this: see Distributed training.)

      14. Interview questions, with model answers
      

      Compare polling, long polling, SSE and WebSockets.
      All four solve server push. Polling asks on a timer: simplest, cacheable, but latency is the interval and most requests return nothing. Long polling holds each request until there is news: low latency for sparse events, but one request per batch, an extra round trip when events are frequent, and the hold must stay under every proxy timeout. SSE is one HTTP response that keeps sending text events: one direction, but it is plain HTTP (auth headers, status codes, proxies, HTTP/2 multiplexing), and EventSource adds reconnection with Last-Event-ID. WebSockets turn the connection into a two-way message channel with 2 to 14 bytes of framing: needed when the client sends while receiving (voice, collaboration), at the cost of losing HTTP semantics per message and owning heartbeats, reconnection and resume yourself. LLM text streaming uses SSE; realtime voice uses WebSockets or WebRTC.
      

      Walk me through what an SSE parser does with the bytes.
      Decode the stream as UTF-8 (incrementally: a read may end mid-character), strip one leading byte order mark, split into lines on LF, CR LF or CR, buffering any partial line. For each line: empty means dispatch (if the data buffer is non-empty, deliver an event with the type, the data minus its final newline, and the last event id; then reset data and type); a leading colon means comment; otherwise split at the first colon into field and value, remove one leading space from the value, and handle data (append plus newline), event (set type), id (set last id unless it contains NUL), retry (set delay if all digits); ignore other fields. At end of stream, discard an undispatched event.
      

      How would you make a token stream resumable after a disconnect?
      Decouple generation from the connection: run generation as a job that appends events, each with a monotonically increasing id, to a durable log keyed by response id (Redis stream, Kafka, a table) with a retention window. The HTTP handler tails the log from the id in Last-Event-ID (or a query parameter for fetch clients) and sends events with id: lines. Then any server instance can serve a reconnect, the work is neither repeated nor lost, and a final event plus a 204 on later reconnects ends it cleanly. Cost: storage, and a cancellation path, since a disconnect no longer stops the job by itself.
      

      The user presses Stop. What should happen on the server, and what usually goes wrong?
      The client closes the connection (HTTP/1.1) or resets the stream with RST_STREAM CANCEL (HTTP/2). The server must notice and abort the generation to free the GPU slot. What goes wrong: servers often learn of a closed socket only when a write fails, so during queueing or prefill they keep working (measured here: 3.0 s of work for a client gone at 0.5 s). Listen for the disconnect concurrently with the work, as vLLM's with_cancellation does with ASGI http.disconnect, and make sure proxies propagate the close.
      

      What is Sec-WebSocket-Accept for, and why do clients mask frames?
      Accept is base64(SHA-1(client key + a fixed GUID)): proof that the server understood the WebSocket upgrade, so a non-WebSocket server or cache cannot appear to accept. It is not authentication. Masking XORs every client frame with a fresh random key so that a script in a browser cannot control the exact bytes on the wire; that prevents a class of attacks in which confused intermediaries interpreted attacker-chosen bytes as HTTP and poisoned caches. Servers do not mask; a client frame without the mask bit is a protocol error.
      

      Your WebSocket connections drop every 60 seconds with code 1006. Debug it.
      1006 means no close frame: the connection vanished, typically a middlebox. A fixed interval points at an idle timeout: nginx proxy_read_timeout defaults to 60 s, many load balancers default to similar values. Confirm by sending traffic (pings) and seeing whether the drops stop, and by checking the proxy's log at info level. Fix with application or protocol pings well under the shortest idle timeout, raise the timeout for the WebSocket route, and make clients reconnect with backoff and jitter.
      

      What is cross-site WebSocket hijacking and how do you prevent it?
      Browsers do not apply the same-origin policy or CORS to WebSocket handshakes and attach cookies, so a malicious page can open a socket to your service as the logged-in user and read the replies. Prevent it by validating the Origin header against an allow-list in the handshake, preferring short-lived tickets over cookies, setting SameSite on cookies, and re-authorising long-lived sockets.
      

      Design a webhook receiver for fine-tuning completion events.
      Public HTTPS endpoint; read the raw body; verify the HMAC signature in constant time and reject timestamps outside a tolerance (5 minutes is common); insert the event id into a table with a unique constraint and stop if it already exists; enqueue and answer 2xx within a second or two; a worker fetches the job's current state from the provider's API (the payload is a hint, order is not guaranteed) and updates your records idempotently. Monitor delivery failures, support secret rotation (several signatures in the header), and alert on a growing queue.
      

      Why do LLM APIs stream over SSE rather than WebSockets?
      The stream is one direction, so a WebSocket buys nothing and costs a lot: a stateful connection to balance and keep alive, no HTTP status, caching or standard retry semantics per message, auth awkwardness in browsers, and trouble with proxies that do not pass upgrades. SSE keeps the request a normal POST with headers and a JSON body, works through ordinary HTTP infrastructure, and multiplexes over HTTP/2. Voice and other bidirectional realtime APIs are where WebSockets (and WebRTC) win.

      Glossary
      

      

      At least once: a delivery promise that allows duplicates but not loss; the receiver must deduplicate.
      

      Backpressure: a slow consumer making a fast producer wait, instead of an unbounded queue growing.
      

      Barge-in: the user speaking over a voice agent, which must stop and listen.
      

      Close code: the 2-byte reason in a WebSocket close frame; 1006 is never sent, only reported locally.
      

      Comment line: an SSE line starting with a colon; ignored by parsers, used as a keep-alive.
      

      Context takeover: permessage-deflate keeping its compression state across messages.
      

      CSWSH: cross-site WebSocket hijacking; another site's page using the user's cookies on your socket.
      

      Cursor: a position the client sends back ("after event 3") so no event is missed between requests.
      

      Datagram: a message sent once, with no retransmission or ordering.
      

      Event (SSE): lines of field: value ended by a blank line.
      

      EventSource: the browser's built-in SSE client; GET only, no custom headers, reconnects by itself.
      

      Frame: the unit a WebSocket sends: a 2 to 14 byte header and a payload.
      

      Heartbeat: traffic sent only to prove a connection is alive and keep middleboxes from closing it.
      

      HMAC: a hash keyed by a shared secret; proves who sent a message and that it was not changed.
      

      Idle timeout: a middlebox closing a connection that carried no bytes for some time.
      

      Last-Event-ID: the header a reconnecting EventSource sends with the last id it saw.
      

      Long polling: a request the server holds until it has news.
      

      Masking: XOR of each client frame with a random 4-byte key, against cache poisoning.
      

      Opcode: the 4-bit frame type: text, binary, continuation, close, ping, pong.
      

      permessage-deflate: the WebSocket compression extension (RFC 7692).
      

      Ping and pong: WebSocket control frames for heartbeats; a pong echoes the ping's bytes.
      

      Polling: asking for news on a timer.
      

      RST_STREAM: the HTTP/2 frame that cancels one stream without closing the connection.
      

      Server push: getting data from server to client when the server has it, not when the client asks.
      

      Server-Sent Events (SSE): a text/event-stream HTTP response that stays open and carries events.
      

      SSRF: server-side request forgery; making a server fetch an internal URL for you.
      

      Subprotocol: the application format inside a WebSocket, agreed by Sec-WebSocket-Protocol.
      

      Sync engine: a client subscribing to a query and receiving diffs that keep a local copy current.
      

      Thin payload: a webhook that says "X changed" and lets the receiver fetch X's current state.
      

      Webhook: an HTTP POST a provider sends to your URL when an event happens.
      

      WebRTC: the browser's real-time media stack, over UDP with jitter buffers and codecs such as Opus.
      

      WebSocket: an HTTP/1.1 request upgraded (101) into a two-way message channel.
      

      WebTransport: streams and datagrams for web pages over HTTP/3.
