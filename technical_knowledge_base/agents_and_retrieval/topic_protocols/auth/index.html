In one screen

Every request that reaches an API has to answer two questions before it does anything: who is calling (authentication) and may they do this (authorization). The answer travels with the request as a credential: a secret string, a signed token, a certificate or a signature. This page follows the credentials an ML engineer meets, from the API key on an LLM request to the tokens an agent carries to an MCP server, and shows each one on the wire.

The parent page, Topic: protocols (Reading, section 8), gives the overview in five minutes. This page owns the depth. Everything marked "recorded" below was produced on 5 October 2026 by a small lab built for this page: an OAuth 2.1 authorization server, an MCP server and client from the official Python SDK (mcp 2.3.0), and two upstream APIs, all on one laptop, with a recording proxy in front of each so every byte that crossed the wire was saved (scripts and raw output in this page's src/lab/).

Three ideas carry the whole page:

  1. Bearer versus bound. A bearer credential works for anyone who holds it, like cash; a bound one also needs a private key or a TLS connection the thief does not have. Most leaks are bearer leaks.
  2. Narrow it. A credential should say which service it is for (its audience), what it allows (its scopes) and until when (its expiry). Each narrowing turns a leak from a catastrophe into an incident.
  3. Never forward what you received. A service that gets a token for itself and needs to call another service obtains a new token for that service. Agents made this rule urgent: the MCP specification makes it a MUST NOT (section 9).
What changed recently (checked 5 October 2026)
  • OAuth 2.1 is still an Internet-Draft: revision 16, 3 September 2026 (datatracker). It removes the implicit and password grants, requires PKCE (with one narrow exception), drops the PKCE "plain" method and requires exact redirect URI matching.
  • The security rules it consolidates are already an RFC: the OAuth 2.0 Security Best Current Practice, RFC 9700 (January 2025). Browser apps got their own BCP in August 2026: RFC 10017, which strongly recommends a backend-for-frontend for business and sensitive apps.
  • MCP's 2026-07-28 revision makes Client ID Metadata Documents the preferred way for a client to identify itself and deprecates dynamic client registration (MCP authorization, 2026-07-28).
  • GitHub Actions OIDC tokens for repositories created after 15 July 2026 carry an immutable subject with owner and repository IDs (GitHub docs): cloud trust policies written against the old format do not match them.

1. The words, from zero

A principal is whoever a request acts for: a person ("alice"), a service ("batch-job") or an agent acting for a person. A credential is the evidence the request carries. The server authenticates the credential (is it genuine, unexpired, meant for me?) and then authorizes the action (may this principal read this file?). The two fail differently, and HTTP gives them different status codes:

401 Unauthorized

Despite its name, this means unauthenticated: no credential, or one the server cannot accept (bad signature, expired, wrong audience). The server MUST say how to authenticate in a WWW-Authenticate header (RFC 9110 s15.5.2). Retrying with a fresh credential can fix it.

403 Forbidden

The server knows who you are and the answer is no (RFC 9110 s15.5.4). A new token with the same rights will not help; more rights (a scope, a role) might. OAuth signals the scope case with error="insufficient_scope" (RFC 6750 s3.1).

Here is a real 401 from this page's lab: a token minted for the mail API, presented to the MCP server (recorded). The server names the problem class and, in the MCP style, points to the document that says where to get a proper token.



One detail worth noticing: for a request with no credential, RFC 6750 says the server "SHOULD NOT include an error code" (s3.1); the MCP SDK 2.3.0 server sends error="invalid_token" in that case too (see the first response in the MCP auth flow tab). Harmless, but it means a client cannot tell "no token" from "bad token" by the error code alone.

Bearer versus bound, the distinction that matters most


A bearer credential is accepted from anyone who presents it (RFC 6750 s1.2 defines the term exactly that way). API keys, session cookies and ordinary OAuth access tokens are bearer credentials: a copy in a log file, a crash dump, a notebook or a model's context window is as good as the original. A sender-constrained (bound) credential also requires proof that the presenter holds a private key: a DPoP proof signed per request, or the TLS client certificate the token was issued to. Section 7 shows a stolen bound token failing three ways.


Predict, then reveal


An agent's token has scope files:read. It calls write_file on an MCP server that checks scopes. Which status, and which header tells the client what to ask for?


Reveal
403 Forbidden with WWW-Authenticate: Bearer error="insufficient_scope", scope="files:write", resource_metadata="...". The token is genuine (so not 401); the right fix is a step-up authorization that requests the union of the old and the new scopes, which the MCP specification spells out (Scope Challenge Handling). The parent page's Failure lab reproduces this case as "Missing scope: authenticated but not allowed".






2. API keys: the simplest credential, done properly


The problem. Your backend calls an LLM provider thousands of times a day. There is no user to ask, no browser to redirect; the provider just needs to know which account to bill and limit. The parent page's running request carries the answer in one header: x-api-key: sk-wirelab-not-a-real-key (a fake). An API key is a long random string the provider generated, showed you once, and remembers. Whoever presents it is the account.


Anatomy of a good key


GitHub's 2021 token redesign is the clearest public write-up of what a key should look like (GitHub blog, 5 April 2021): a short prefix that says what it is, a random body, and a checksum. The lab made one in the same shape (recorded):




    

  • Prefix (lab_): secret scanners (GitHub's, your CI's, your log pipeline's) can match it with almost no false positives, and an underscore keeps double-click selection whole.
    • 

  • Body: 30 characters from 62 symbols carry 30 × log2(62) =  bits; GitHub quotes 178. Guessing is hopeless, so the server can store a plain SHA-256 of the key (shown above) rather than the slow, salted hash a human-chosen password needs: there is nothing to brute-force.
    • 

  • Checksum: the last six characters are a CRC32 of the body in base 62. A scanner or the server can reject a mistyped or made-up key without a database lookup. Try it: change one character.
    • 





Living with keys


    

  • One key per service and environment. When staging's key leaks you revoke staging, not production, and the provider's per-key usage tells you who spent what. Providers apply rate limits per key or per organisation, so one runaway job with a shared key throttles everyone (429 with retry-after; the Failure lab case "429 Too Many Requests with Retry-After" shows the headers).
    • 

  • Store it in a secrets manager and inject it at run time. Not in git, not in a notebook (outputs and cell history get shared), not in a Docker image layer, not in a browser or mobile app (anyone can read it out).
    • 

  • Rotate with overlap. Create key 2, deploy it everywhere, watch key 1's usage fall to zero, then revoke key 1. Rotating by revoking first is an outage.
    • 

  • Show only a hint () in dashboards and logs, so people can tell keys apart without exposing them.
    • 



What a key cannot do. It carries no user (every call is "the account"), no consent, no expiry unless you add one, and no narrower audience than the whole provider. That is fine for your backend calling your provider. It is wrong as soon as a third party (an app, an agent) acts for one of your users: then you want OAuth (section 4).


Predict, then reveal


A notebook that worked yesterday now gets 401 from the LLM provider on every call; your colleague's identical notebook works. The key in your environment variable has the right prefix. What do you check first?


Reveal
Which key the process actually sees, and whether it is still active: print its hint (prefix and last four characters), not the key, and compare with the provider's dashboard. The usual causes are a key revoked in a rotation, a staging key against the production endpoint, or a stale value cached by the kernel or a .env file loaded before the change. A 401 says "this key is not accepted"; a 403 would say "this key is fine but may not use this model or workspace".






3. Sessions and cookies: how browsers stay logged in


The problem. HTTP forgets everything between requests. After you type your password once, the site needs every later request to say "still me". The classic answer is a session: the server creates a record (user, login time, expiry) under a long random ID and gives the browser that ID in a cookie with Set-Cookie; the browser sends it back automatically on every request to that site.


Set-Cookie: __Host-sid=Wq3v8kH0t2nX...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800


Illustrative header (not recorded). Attribute meanings from the cookie specification, RFC 6265, and its revision draft rfc6265bis (revision 22, August 2026, not yet an RFC), which defines SameSite and the __Host- prefix.




Secureonly sent over HTTPS, so a coffee-shop network cannot read it.


HttpOnlyinvisible to JavaScript, so an injected script cannot read and exfiltrate it (it can still make requests that carry it).


SameSite=Laxnot attached to requests that other sites trigger in the background (form posts, images, fetches); attached when you follow a link. This is the main defence against CSRF (cross-site request forgery: a malicious page making your browser send a request to your bank, cookie included).


__Host- prefixthe browser refuses the cookie unless it is Secure, has Path=/ and no Domain, so a sibling subdomain cannot plant or overwrite it.




Sessions versus tokens. A session ID is a pointer: the truth lives in the server's store, so logging out or "sign out everywhere" deletes the record and every copy of the cookie dies at once. A self-contained token such as a JWT is the truth itself: the server checks a signature and trusts the contents, so it cannot be killed early (section 6 records exactly that). For a website's own users, server-side sessions remain the simpler and safer default; tokens earn their place when a third party, a mobile app or another service is involved.


Browser apps and OAuth. A single-page app that holds OAuth tokens in JavaScript exposes them to any injected script. The August 2026 BCP for browser apps, RFC 10017, describes three architectures and "strongly recommends" the backend for frontend (BFF) for business apps, sensitive apps and apps handling personal data (s6.1): a small server-side component does the OAuth flow, keeps the tokens, and gives the browser only an HttpOnly session cookie. The pattern where the browser holds the tokens itself (s6.3) is "not recommended" for those apps.


Predict, then reveal


Your internal labelling tool stores a JWT in localStorage and sends it as a Bearer header. Someone proposes moving it to a cookie "for security". What do you gain, and what new risk appears?


Reveal
Gain: with HttpOnly, an injected script can no longer read the token and send it away (it can still act within the page while it runs). New risk: the browser now attaches the credential automatically, which opens CSRF; you need SameSite=Lax or Strict (and for state-changing requests, a CSRF token or a custom header check). RFC 10017's BFF pattern is this move done fully: tokens stay on a server, the browser holds only a session cookie.






4. OAuth 2.1: letting an app act for a user


The problem. You want a CLI agent to read your files on a cloud drive. You could paste your drive password into the agent: then it can do everything you can, forever, and the drive cannot tell it from you. OAuth replaces the password with a delegation: the drive's login server asks you, once, whether this particular app may do these particular things, and if you agree it gives the app a short-lived, limited token. The app never sees your password.


Four roles, named in every spec (OAuth 2.1 draft-16 s1.1):




Resource owner
You, alice: the person whose data it is.


Client
The app or agent that wants access (a CLI, a web app, an MCP client). Public clients (CLIs, desktop and mobile apps, browser code) cannot keep a secret; confidential clients (servers) can.


Authorization server (AS)
Logs you in, asks for consent, issues tokens. Google's accounts.google.com, Microsoft Entra, Okta, Auth0, Keycloak, or your own.


Resource server (RS)
The API that holds the data and accepts the tokens: the drive API, an MCP server.




The authorization code flow with PKCE, step by step


This is the flow for anything a person logs into: web apps, mobile apps, CLIs, desktop agents, MCP clients. What each piece does (the parameters are in every authorization URL you will ever debug; the recorded one is in the MCP auth flow tab, step 4):


    

  • response_type=code: ask for a one-time authorization code, not a token. The code comes back through the browser, which is the leaky part; the tokens come back on a direct, TLS-protected back-channel call from the client to the AS's token endpoint.
    • 

  • code_challenge and code_challenge_method=S256 (PKCE, RFC 7636): the client invents a random code_verifier, sends only its SHA-256 (base64url) in the authorization request, and must present the verifier itself to redeem the code. Whoever steals the code from the redirect does not have the verifier. The RFC's own example (verifier dBjftJeZ...EjXk gives challenge ) is recomputed live by this page's SHA-256: .
    • 

  • state: a random value the client checks when the browser comes back, so an attacker cannot feed the client a response to a request it never made (CSRF on the callback).
    • 

  • redirect_uri: where the AS sends the browser back. It must exactly match a registered value (RFC 9700 s4.1.3); pattern matching let attackers register lookalike paths and receive codes. One relaxation: for native apps listening on a loopback address, the port may vary (RFC 8252 s7.3), which is how claude, gh and gcloud logins catch the redirect on http://127.0.0.1:<random port>/callback. The Failure lab's "OAuth redirect URI mismatch" case shows the error a near-miss gets.
    • 

  • iss in the response (RFC 9207): the AS names itself, so a client talking to several authorization servers can refuse a response that came from the wrong one (a "mix-up" attack). MCP clients must check it (section 9); the SDK did, in the recording.
    • 

  • scope and resource: what the token may do, and for which API (RFC 8707). Together they decide how bad a leak is.
    •

Correction to the old page
The old page said PKCE is "mandatory even for confidential clients". OAuth 2.1 draft-16 is one notch softer: PKCE is required unless the client is confidential and the AS has reasonable assurance it implements the OpenID Connect nonce correctly; even then PKCE stays recommended, because only PKCE lets the AS refuse an injected code before issuing any token (draft-16 s7.5.1.1). The draft also removed the PKCE plain method and the redirect_uri parameter in the token request (s10, s10.2). The MCP SDK 2.3.0 client still sends redirect_uri at the token endpoint (visible in the recording); servers ignore it.



Refresh tokens: staying signed in without long-lived access tokens


Access tokens are kept short (the lab's live 300 s) so a stolen one expires soon. To avoid sending the user through the browser every few minutes, the AS also issues a refresh token, which the client trades for a new access token at the token endpoint. A refresh token is long-lived and therefore precious, so OAuth 2.1 requires, for public clients, that refresh tokens be either sender-constrained (DPoP or mTLS) or rotated: every refresh returns a new refresh token and invalidates the old one, and if an old one is ever presented again, someone has a copy, so the AS revokes the whole grant (draft-16 s4.3.1). Client credentials: a service acting as itself


When there is no user (a nightly batch job calling an internal API), the client authenticates as itself at the token endpoint and receives a token whose subject is the client. How it authenticates matters more than the grant: a shared secret in a Basic header (simple, but a secret to store and rotate), or better a private_key_jwt: the client signs a short JWT assertion with its own private key and the AS checks it with the registered public key (RFC 7523 s2.2), so no shared secret exists at all. The device grant: logging in a box with no browser


A GPU node over SSH, a TV, a CLI in a container: none can open a browser. The device asks the AS for a device code (kept secret) and a short user code (shown to you), you type the user code on your phone, and the device polls the token endpoint until you approve (RFC 8628). Polling has rules: wait interval seconds (5 if unspecified); on slow_down, add 5 seconds for good (s3.5). Recorded, with the lab's interval set to 1 s to keep it short:




The user code is short on purpose. RFC 8628's own example, 8 characters from a 20-letter alphabet, carries 8 × log2(20) =  bits, enough only because of rate limiting and expiry (s6.1). The flow has a real weakness: the user approves a code someone else started. In the Storm-2372 campaign, attackers sent victims device codes disguised as meeting invitations, and the victims' approvals gave the attackers tokens; Microsoft's advice is to block the device flow wherever it is not needed (Microsoft Threat Intelligence, 13 February 2025).



What OAuth 2.1 removed, and what real providers still offer


The draft's list of changes from 2.0 (s10): PKCE by default; exact redirect URI matching; no implicit grant (tokens in the redirect could not be sender-constrained and leaked through history and referrers); no resource owner password grant (the app saw the password); no bearer tokens in query strings; refresh tokens for public clients sender-constrained or one-time; no redirect_uri in the token request; client credentials accepted in the request body; no PKCE plain. A draft is not a switch, though. Google's discovery document, fetched for this page, still advertises what 2.1 removed, for old clients:




So "OAuth 2.1" in practice means: your client uses only the 2.1 subset, whatever the provider still allows. Two further pieces you will meet: pushed authorization requests (RFC 9126), where the client posts the authorization parameters to the AS first and the browser carries only a reference, so nothing in the URL can be tampered with or leaked; and authorization server metadata (RFC 8414), the /.well-known/oauth-authorization-server document every client above read first.


Predict, then reveal


A mobile app uses the code flow with PKCE. A malicious app on the same phone registered the same custom URL scheme and receives the redirect, code included. What can it do with the code?


Reveal
Nothing useful: redeeming the code needs the code_verifier, which never left the real app's memory; the token endpoint answers invalid_grant (the recording above). Depending on the AS, its attempt may burn the code, so the user has to log in again: a denial, not a theft. Without PKCE the same interception yields tokens, which is why RFC 8252 s6 required PKCE for native apps in 2017 and OAuth 2.1 extends it to everyone.






5. OpenID Connect: who logged in


The problem. OAuth answers "may this app call this API?" but deliberately says nothing about who the user is: an access token is addressed to the API, and the client is not even supposed to read it. Apps that just want "Sign in with Google" were abusing access tokens as proof of identity, which is unsafe (a token issued to a different app could be replayed to yours). OpenID Connect (OIDC) adds the missing piece on top of the same code flow (OIDC Core 1.0):


    

  • Request scope openid, and the token response also contains an ID token: a signed JWT about the login, addressed to your app (aud = your client_id), with iss, sub (a stable user ID, unique per issuer), exp, iat, auth_time and the nonce your app put in the authorization request (s2, s3.1.3.7).
    • 

  • A UserInfo endpoint returns profile claims (email, name) for an access token with the right scopes.
    • 

  • Discovery (OIDC Discovery 1.0): the provider describes itself at /.well-known/openid-configuration, including where its signing keys are (jwks_uri).
    • 



The one rule people break: the ID token is for the app to learn who logged in. Never send it to an API as a credential, and never accept one as an access token. They look alike (both JWTs, often from the same issuer and key), which is exactly why the JWT best practices ask for explicit typing (RFC 8725 s3.11) and why access tokens carry typ: at+jwt (RFC 9068 s2.1). The JWT lab has the case "An ID token, not an access token": same issuer, valid signature, matching audience, and only the typ check stops it.


Real discovery documents, fetched today


Three providers you will meet, fetched read-only on . Each one is a contract a client can check before it sends anyone a password.




Three things to read off them. Google signs ID tokens with RS256 and publishes  keys at once, with cache-control: : two keys so it can rotate (sign with the new one while tokens signed with the old one are still valid), and a cache lifetime of hours so verifiers do not fetch keys on every request. The verifier's rule follows: cache the JWKS, and when a token arrives with a kid you do not know, refetch once (rate-limited), never per request. Second, GitHub Actions is an OIDC issuer with no users at all: it mints ID tokens about workflow runs, with claims such as repository, ref and environment, which clouds trade for credentials (section 7). Third, Microsoft's common endpoint does not list code_challenge_methods_supported; Entra supports PKCE, but an MCP client following the 2026-07-28 rules literally must refuse to proceed when that field is absent (MCP authorization security, "Authorization Code Protection"). A real interoperability snag, visible only by reading the document.


Predict, then reveal


Your app validates the ID token's signature against Google's JWKS and checks exp. It does not check aud. What can an attacker who runs another site with "Sign in with Google" do?


Reveal
Log in to your app as any user who ever signed in to their site: they hold genuine Google ID tokens for those users, signed with the same keys, but with aud = their client_id. Without the audience check, your app accepts them. OIDC Core requires the client to verify that aud contains its own client_id (s3.1.3.7, rule 3), and the nonce check ties the token to your own login request.






6. JWTs: tokens a server can check alone


The problem. If every API call required the API to ask the authorization server "is this token good?", the AS would carry the whole system's traffic and its latency. A JSON Web Token lets the AS put the answer inside the token and sign it, so any API holding the AS's public key can verify it offline in microseconds (RFC 7519). The family of specs, all May 2015: JWS (signed, RFC 7515), JWE (encrypted, RFC 7516), JWK (keys as JSON, RFC 7517), JWA (algorithm names, RFC 7518) and JWT itself (the claims). "JWT" in conversation almost always means a JWS-signed JWT.


Anatomy


Three base64url pieces separated by dots: a header (algorithm and key ID), a payload (the claims), a signature over the ASCII bytes base64url(header) + "." + base64url(payload). A real token from this page's lab (an RS256 access token, decoded by this page's JavaScript):






Anyone can decode the first two parts: base64url is an encoding, not encryption. Never put secrets or more personal data than needed in claims; use JWE or an opaque token if the contents must stay private.


The algorithms, measured


The same claims signed five ways with PyJWT 2.15.1 on this laptop (Apple M1 Pro, one core; median of 7 runs of 200; recorded):




    

  • HS256 is a MAC with a shared secret: the smallest and fastest, but every service that can verify can also mint tokens. Fine inside one service; wrong for an issuer with many verifiers.
    • 

  • RS256 (RSA) is the most widely deployed (Google, Microsoft and GitHub Actions all list only RS256 in the discovery documents in section 5). Verification is cheap and signing is about ten times slower, which suits one issuer and many verifiers; the cost is a 256-byte signature, so RS256 tokens are roughly twice the size of the others.
    • 

  • ES256 (P-256) and EdDSA (Ed25519) give 64-byte signatures. ECDSA needs care in implementations: Java 17.0.2 and 18 accepted a signature of all zeros as valid for any message and any key (CVE-2022-21449; Neil Madden, "Psychic signatures in Java", 19 April 2022): the verifier skipped the check that r and s are at least 1.
    • 



Validating a JWT, in order


    

  1. Choose the algorithm yourself. Accept only the algorithm(s) you expect for this issuer; never use the token's alg header to decide how to verify (RFC 8725 s3.1). In PyJWT that is the algorithms=["RS256"] argument, required since 2.0.0 (changelog); applications that passed "every algorithm" there were still open to key confusion until 2.4.0 (CVE-2022-29217).
    2. 

  2. Choose the key yourself. Look the kid up in the issuer's JWKS, fetched from the jwks_uri in its discovery document and cached. Never fetch keys from a URL inside the token (jku, x5u) and never treat kid as a file path or a database query.
    3. 

  3. Verify the signature.
    4. 

  4. Check the type (typ: at+jwt for access tokens) so an ID token or another JWT from the same issuer is not accepted as an access token (RFC 8725 s3.11).
    5. 

  5. Check iss equals the issuer you trust and aud contains your own identifier (s3.8, s3.9).
    6. 

  6. Check time: exp in the future, nbf/iat not in the future, with a small leeway (seconds to a couple of minutes) for clock skew.
    7. 

  7. Only now authorize: scopes, roles, tenant, the specific object.

The price of offline checking: no revocation


A self-contained token stays valid until exp, whatever happens at the AS. Recorded in the lab: a client-credentials token was revoked at the AS (RFC 7009); the AS's introspection endpoint (RFC 7662) then reported it inactive, and the MCP server, which validates JWTs offline, still accepted it:




The remedies, in order of cost: short lifetimes (minutes), so a revoked token dies soon anyway; a denylist of revoked jti values pushed to verifiers; introspection on every call for high-value operations, which brings the round trip back. This is also why JWTs make poor browser sessions (section 3): "log out" cannot reach a token already issued.






7. Beyond bearer: bound tokens, signed requests, cloud IAM and mTLS


Every credential so far is a bearer credential: steal it and you are the owner. This section is about the designs where a stolen copy is not enough.


DPoP: a token that only works with its key


How it works (RFC 9449, September 2023). The client generates a key pair and keeps the private key. With every request (to the token endpoint and to the API) it sends a DPoP header: a small JWT, signed with that key, whose header carries the public key and whose claims name the HTTP method (htm), the URL (htu), the time (iat), a unique ID (jti) and, at the API, the hash of the access token (ath). The AS puts the key's thumbprint (RFC 7638) into the token as cnf.jkt; the API checks that the proof was signed by that same key, for this request, just now. Recorded in the lab, a token bound to the client's key and then stolen:




What it costs: one ES256 signature per request on the client (about  µs here, from the table in section 6) and one verification plus a replay cache of recent jti values on the server. What it does not stop: malware running inside the client can ask the client to sign proofs (RFC 9449 s11.4 discusses this); the server-provided nonce (s8, s9) limits proofs made in advance. When to use it: public clients holding valuable refresh tokens (OAuth 2.1 accepts it in place of rotation), and APIs where a leaked token in a log would be serious. The older alternative binds the token to a TLS client certificate instead (RFC 8705), natural where mTLS already exists.



SigV4: AWS signs every request instead of sending a token


AWS chose a different shape long ago. You hold an access key ID (public) and a secret access key (never sent). For each request the SDK builds a canonical request (method, path, sorted query, lowercased sorted headers, the list of signed headers, the SHA-256 of the body), hashes it into a string to sign with the timestamp and a credential scope (date, region, service), derives a signing key by chaining HMACs of the secret over date, region, service and the literal aws4_request, and sends the final HMAC as the signature (AWS: create a signed request). The calculator below does all of it in this page's JavaScript. Its defaults are the get-vanilla vector of the SigV4 test suite as shipped in botocore (example credentials AKIDEXAMPLE), and they reproduce the suite's expected signature .




















Try: change one character of the path or the body and watch the signature change completely: the signature covers the request, so a proxy cannot alter it. Change the date by one day: the signing key changes too, which is why a leaked derived key is only good for one day, one region, one service.




What this buys. The secret never crosses the wire, so a logged request leaks no reusable credential; the body hash means nobody in the middle can change the request; the timestamp means a captured request is refused after a few minutes ("in most cases, a request must reach AWS within five minutes of the time stamp", AWS SigV4 overview). What it costs: every client needs an SDK (or this page's dozen steps done exactly right: header case, whitespace and URI encoding rules cause most SignatureDoesNotMatch errors), and clock skew of more than a few minutes breaks every call.



Cloud IAM and workload identity: no long-lived secrets at all


The best secret is one you never store. On AWS, code on an EC2 instance, a Lambda or a pod gets temporary credentials for its role from the platform (access key, secret and a session token sent as X-Amz-Security-Token), the SDK refreshes them before they expire, and IAM policies on the role decide what it may do. Calling Bedrock, SageMaker or S3 from your own AWS code needs no key at all.


Across clouds and from CI, the same idea uses OIDC: the platform gives the job an ID token about itself, and the cloud's security token service trades it for temporary credentials if a trust policy matches its claims (on AWS, AssumeRoleWithWebIdentity). GitHub Actions is the common case: a workflow with permissions: id-token: write gets a token from the issuer whose discovery document is in section 5. The trust policy is the whole security boundary, so read the subject claim it matches (GitHub docs):

Two traps follow. A trust condition with a wildcard such as repo:octo-org/* lets every workflow on every branch of every repository in the organisation assume the role, so anyone who can push a branch anywhere in the organisation holds the role's permissions; match the exact repository and a protected branch or environment. And a policy written for the old format silently stops matching new repositories, whose subject now includes the numeric IDs; GitHub added the IDs because a deleted organisation or repository name could be re-registered by someone else and inherit the old subject.



mTLS: identity in the connection


With mutual TLS both sides present certificates during the TLS handshake, so a service's identity is proven before any HTTP byte flows, and there is no header to leak. Service meshes automate the hard part (issuing and rotating short-lived certificates per workload); SPIFFE standardises the identity as a URI such as spiffe://prod.example/ns/serving/sa/vllm inside the certificate (SPIFFE ID spec). Authorization then works on that name ("the gateway may call vLLM; the notebook may not"). The handshake, the certificate chain and the failure modes belong to the sibling page TLS and certificates; the parent's Failure lab has "mTLS: client certificate missing".


Corrected from the old page
The old page said public certificate authorities stop issuing client-authentication certificates in "February 2027", and the old TLS page gave a different date. The TLS and certificates page (its section 7) has since checked the Chrome Root Program policy (version 1.8, 5 February 2026): subordinate CAs disclosed from 15 June 2026 must be serverAuth-only, and leaf certificates issued from 15 March 2027 must carry only serverAuth. The practical advice is the same: use a private CA (or a mesh) for mTLS between your own services.

8. Token exchange: calling onward without forwarding


The problem. Service A received alice's token, addressed to A. To do its job, A must call service B for alice. Forwarding alice's token is wrong (B is not its audience, and if B accepts it anyway, every token for A becomes a token for B). Using A's own all-powerful service credential is also wrong (B can no longer tell which user is behind the call, and A can be tricked into acting for the wrong user). The standard answer is token exchange (RFC 8693, January 2020): A authenticates to the AS as itself, hands over the token it received as the subject_token, names the target with resource or audience, and receives a new token for B, usually with narrower scopes.


Recorded: the lab's MCP server performing exchange inside a tool call. It authenticates with private_key_jwt (a JWT it signed with its own key, so there is no shared secret anywhere), and the AS's policy allows only this one mapping (tokens for the MCP server, exchanged by the MCP server, for the mail API, scope narrowed to mail:read):




The new token's claims carry the distinction RFC 8693 names (s1.1). Delegation: the token says "alice, acted for by the MCP server" with an act claim (s4.1), so the mail API can log both and apply policy to both. Impersonation: the token simply says "alice", and the API cannot tell an intermediary was involved. Prefer delegation whenever an agent or service acts for a person; the audit trail is the point.


Where you meet it. Microsoft Entra's equivalent is the on-behalf-of flow. In MCP, the enterprise-managed authorization extension (status: stable) chains the two standard grants: the client exchanges the user's single-sign-on ID token at the company's identity provider for an ID-JAG (identity assertion JWT authorization grant), then presents it to the MCP server's authorization server as a JWT bearer grant (RFC 7523), so employees never click through a consent screen per server and administrators decide centrally which servers are allowed (MCP ext-auth; the underlying IETF draft is at revision 04, May 2026).


Predict, then reveal


In the recording, which three checks did the AS make before issuing the exchanged token, and which single one stops a compromised other service from using the MCP server's identity?


Reveal
It authenticated the caller (the private_key_jwt signature, issuer and audience, plus a one-time jti), validated the subject token (signature, issuer, and that its audience is the MCP server), and applied policy (only this client, only toward the mail API, scope narrowed). Client authentication is what stops another service: without the MCP server's private key it cannot produce the assertion, whatever tokens it has collected.






9. Agent-era auth: MCP authorization, audience binding, no token passthrough


Why agents change the threat model. An agent is a program that holds credentials and decides what to do with them based on text it reads, and some of that text was written by strangers: a web page, an email, a tool result. The parent page's section 9 and its Failure lab case "A tool result that carries an injected instruction" show the mechanism; Simon Willison's "lethal trifecta" names when it becomes theft: private data, untrusted content and a way to send data out, in one agent (16 June 2025). Auth cannot stop an agent from being talked into misusing a credential it legitimately holds. What auth can do is decide how much each credential is worth when that happens, and keep credentials from travelling further than intended. The rules below all serve that.


The protocol details of MCP (messages, transports, the stateless 2026-07-28 revision) live on the sibling page MCP: building servers and clients, transports, auth and security. This section is the authorization part, quoted from MCP 2026-07-28, Authorization and its sub-pages, and checked against the official Python SDK.



The MCP authorization flow in eight steps


Authorization is optional in MCP and applies to the HTTP transport. A local server started over stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". For a remote server, the spec composes the OAuth pieces from sections 4 to 6. Every step below happened in the recording; the MCP auth flow tab replays each one byte for byte.


    

  1. Unauthenticated call, 401. The client POSTs an MCP request with no token. The server answers 401 with WWW-Authenticate: Bearer resource_metadata="...", optionally with a scope the operation needs.
    2. 

  2. Protected resource metadata (RFC 9728, April 2025). The client fetches the URL from the header (or, without one, tries /.well-known/oauth-protected-resource/<path> then the root). The document names the server's canonical resource URI and its authorization_servers. Servers MUST publish it; clients MUST use it.
    3. 

  3. Authorization server metadata. The client fetches RFC 8414 metadata (or OIDC discovery, trying the documented well-known paths in order) and MUST reject it if the issuer inside differs from the issuer it used to build the URL.
    4. 

  4. Client identity. In priority order: credentials pre-registered for this AS; otherwise a Client ID Metadata Document, if the AS advertises client_id_metadata_document_supported: the client's ID is an HTTPS URL, and the AS fetches that URL to read the client's name and allowed redirect URIs; otherwise dynamic client registration (RFC 7591), now deprecated; otherwise ask the user. CIMD solves MCP's peculiar situation: thousands of clients meeting thousands of servers with no prior relationship, without every AS accepting unlimited anonymous registrations.

  5. Authorization request. PKCE with S256 (the client MUST refuse to proceed if the metadata lacks code_challenge_methods_supported), the resource parameter set to the server's canonical URI in both the authorization and the token request, and the scopes from the 401 challenge (else from scopes_supported).

  6. Issuer check on the way back. The client records the expected issuer before redirecting and compares the iss in the response by exact string match before sending the code anywhere (RFC 9207). In the recording, the SDK refused a response carrying another issuer: .

    8.

Audience binding: the server must check the token is for it


The spec is blunt: "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" and "MUST only accept tokens that are valid for use with their own resources." The client's half is the resource parameter, which asks the AS to put the server's URI in aud. The recording's step W shows the server half: a token minted for the mail API was refused by the MCP server with a 401.


A default worth knowing (MCP Python SDK 2.3.0)
The SDK's resource-server mode has a setting AuthSettings.validate_token_resource. In 2.3.0 it is not on by default: with resource_server_url set and the setting left unset, the SDK warns that bearer tokens "are not checked against resource_server_url" and says the default becomes True in 3.0 (read from the installed package's mcp/server/auth/settings.py). Audience checking is then entirely up to your token verifier. The lab's server turns the setting on and passes the expected audience to PyJWT; do both.



No token passthrough


The rule: "MCP servers MUST NOT accept or transit any other tokens", and when a server calls an upstream API, "the access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received" (security considerations). Here is what passthrough looks like, recorded with three tool calls on the same connection:




Read the middle row twice. A careless upstream that checks only the signature accepts the forwarded token and believes alice's MCP client called it directly: the MCP server, the actual caller, is invisible in its logs and to any per-client limits it applies. That is the accountability failure the spec's best-practices page lists, and the same mechanics let anyone holding a token for the MCP server reach the mail API through it. The careful upstream refuses (first row), and token exchange (last row, section 8) gives it a token that names both alice and the MCP server. The confused deputy, MCP's version


An MCP server that fronts a third-party API with one static OAuth client ID is a deputy acting for many users. The spec's best-practices page walks through the attack (Confused Deputy Problem): alice once approved the proxy at the third-party AS, which set a consent cookie; an attacker registers a new client with the proxy (dynamic registration) using their own redirect URI and sends alice a link; the third-party AS sees the cookie, skips consent, and the code lands at the attacker. Required fixes on the proxy: per-client consent stored server-side before forwarding to the third party, a consent page that names the client, its scopes and its redirect URI, exact redirect matching, a state stored only after consent, and consent cookies with the __Host- prefix, Secure, HttpOnly, SameSite=Lax and bound to the specific client_id.



Credential isolation and least privilege for agents


    

  • Keep credentials out of the model's context. Anything in the prompt or in a tool result can be repeated into a tool call by an injected instruction. Tokens belong in the client and server processes, attached by code to HTTP requests, never pasted into messages, tool arguments or tool results.
    • 

  • Per user, per server. A server that needs upstream access keeps upstream tokens per verified user (keyed by the token's sub, never by something the client sends). The spec's rule for state handles in the stateless 2026-07-28 protocol is the same idea: possession of a handle is not authentication; key stored state by <user_id>:<handle> with the user ID taken from the verified token ("State Handle Hijacking" in the best-practices page).
    • 

  • Local servers get only their own secrets. A stdio server inherits environment variables from the host that starts it; give each server only the variables it needs, not your whole shell environment.
    • 

  • Scopes small, then step up. Start with read-only scopes and let the server challenge for more with 403 insufficient_scope when a write is first attempted; the spec lists publishing every scope in scopes_supported, wildcard scopes and bundling unrelated privileges as common mistakes ("Scope Minimization").
    • 

  • Irreversible actions need a human, out of band. A confirmation dialog shown by the host, outside the conversation, cannot be forged by text arriving through a tool. Separate destructive scopes make that enforceable at the server too.
    • 

  • Clients: treat server-supplied URLs as hostile. An authorization URL from a malicious server can be javascript: or carry shell metacharacters; clients MUST allow only http(s) (http only for loopback), and MUST NOT open URLs through a shell ("OAuth Authorization URL Validation").
    • 



Two dated details. The spec cites the CIMD Internet-Draft at revision 00; the draft has since reached revision 02 (6 July 2026, datatracker). The spec cites OAuth 2.1 draft 13; the current draft is 16 (section 4).

Common mistakes


Using an ID token to call an API
The ID token is addressed to your app. APIs need access tokens; check typ so they cannot be confused (section 5).


Letting the token choose its algorithm or key
Pin algorithms per issuer; look keys up by kid in the issuer's JWKS only; ignore jku and x5u (section 6, JWT lab).


Skipping the audience check "because it is our own issuer"
The same issuer mints tokens for every API you own. Without aud, a token for the least important one opens all of them.


Long-lived access tokens to avoid refresh logic
A leaked hour-long or day-long bearer token is an incident you cannot stop (JWTs cannot be revoked early). Keep minutes, add refresh.


Logging Authorization headers
Access logs, proxy debug logs and tracing spans are where bearer tokens most often leak. Redact the header at the logger, and prefer bound tokens where logs are widely readable.


Forwarding the token you received
Token passthrough (section 9). Exchange it instead (section 8).






11. Interview questions, with model answers


What is the difference between authentication and authorization, and how does HTTP show it?
Authentication establishes who the caller is; authorization decides whether that caller may perform this action. A failed or missing credential is 401 with a WWW-Authenticate challenge; a valid credential without permission is 403 (with OAuth, error="insufficient_scope").


Walk me through the authorization code flow with PKCE. What does PKCE protect against?
Client creates a random verifier and sends its S256 hash in the authorization request with state, redirect URI, scope and resource; the user authenticates and consents; the AS redirects back with a one-time code (and iss); the client checks state and iss, then redeems the code with the verifier at the token endpoint over a direct TLS call. PKCE stops an intercepted or injected code from being redeemed by anyone who does not hold the verifier, which matters most for public clients that have no secret.


Why did OAuth 2.1 remove the implicit grant?
It returned the access token in the redirect URL, where it leaks through history, referrers, extensions and logs, cannot be sender-constrained, and can be injected. The code flow with PKCE gives browser apps the same result with the token delivered on a back channel.


How would you validate a JWT access token?
Pin the expected algorithm; pick the key by kid from the issuer's cached JWKS (never from jku/x5u or a kid path); verify the signature; check typ (at+jwt), iss, aud (contains me), exp/nbf with small leeway; then authorize on scopes and the resource. Refetch JWKS on unknown kid, rate-limited.


JWT or opaque token with introspection? Trade-offs.
JWT: offline verification in microseconds, no AS on the hot path, but no early revocation and contents visible to anyone. Opaque with introspection: revocable immediately and private, but every call (or cache window) hits the AS. Common answer: short-lived JWTs plus refresh, with introspection or a denylist for high-value operations.


What is refresh token rotation and what does reuse detection buy you?
Each refresh returns a new refresh token and invalidates the old one. If an invalidated one is presented, two parties hold copies, so the AS revokes the whole grant: a stolen refresh token becomes detectable and short-lived, at the cost of logging the real user out too.


How do bearer tokens differ from DPoP or mTLS-bound tokens?
Bearer tokens work for whoever holds them. Bound tokens carry a confirmation (cnf) of a key; each request must prove possession (a signed DPoP proof covering method, URL, time and the token hash, or the TLS client certificate). A token stolen from a log is useless without the key.


Your service received a user's token and needs to call another service for them. What do you do?
Not forward it. Use token exchange (RFC 8693): authenticate as the service, present the received token as subject_token, request the downstream audience and narrower scopes, and prefer a delegation token with an act claim so the downstream sees both the user and the service.


How does a remote MCP server authorize clients, and what must the server check?
It is an OAuth resource server: 401 with resource_metadata, protected resource metadata naming its AS, the client discovers the AS, identifies itself (pre-registered, CIMD, or deprecated DCR), runs code + PKCE S256 with the resource parameter, checks iss, and sends Bearer tokens on every request. The server must validate each token including that its audience is this server, must not accept tokens for other resources, and must not pass tokens through to upstream APIs.


How do you give a CI job cloud access without storing a cloud secret?
Workload identity federation: the CI platform issues an OIDC token for the job; the cloud's token service exchanges it for short-lived credentials if a trust policy matches iss, aud and an exact sub (repository plus protected branch or environment). Watch for wildcards and for subject format changes.


Why is an API key acceptable for calling an LLM provider but not for a third-party integration?
Server to server under one owner, the key's lack of user context and consent does not matter, and secrets management plus rotation handle its risks. A third party acting for your users needs per-user consent, limited scopes, expiry and revocation per grant: OAuth.
