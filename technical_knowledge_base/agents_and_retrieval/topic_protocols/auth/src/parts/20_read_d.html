3. Sessions and cookies: how browsers stay logged in

The problem. HTTP forgets everything between requests. After you type your password once, the site needs every later request to say "still me". The classic answer is a session: the server creates a record (user, login time, expiry) under a long random ID and gives the browser that ID in a cookie with Set-Cookie; the browser sends it back automatically on every request to that site.

Set-Cookie: __Host-sid=Wq3v8kH0t2nX...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800

Illustrative header (not recorded). Attribute meanings from the cookie specification, {{RFC 6265|https://www.rfc-editor.org/rfc/rfc6265}}, and its revision draft {{rfc6265bis|https://datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis/}} (revision 22, August 2026, not yet an RFC), which defines SameSite and the __Host- prefix.

Secureonly sent over HTTPS, so a coffee-shop network cannot read it.
HttpOnlyinvisible to JavaScript, so an injected script cannot read and exfiltrate it (it can still make requests that carry it).
SameSite=Laxnot attached to requests that other sites trigger in the background (form posts, images, fetches); attached when you follow a link. This is the main defence against CSRF (cross-site request forgery: a malicious page making your browser send a request to your bank, cookie included).
__Host- prefixthe browser refuses the cookie unless it is Secure, has Path=/ and no Domain, so a sibling subdomain cannot plant or overwrite it.

Sessions versus tokens. A session ID is a pointer: the truth lives in the server's store, so logging out or "sign out everywhere" deletes the record and every copy of the cookie dies at once. A self-contained token such as a JWT is the truth itself: the server checks a signature and trusts the contents, so it cannot be killed early (section 6 records exactly that). For a website's own users, server-side sessions remain the simpler and safer default; tokens earn their place when a third party, a mobile app or another service is involved.

Browser apps and OAuth. A single-page app that holds OAuth tokens in JavaScript exposes them to any injected script. The August 2026 BCP for browser apps, {{RFC 10017|https://www.rfc-editor.org/rfc/rfc10017}}, describes three architectures and "strongly recommends" the backend for frontend (BFF) for business apps, sensitive apps and apps handling personal data (s6.1): a small server-side component does the OAuth flow, keeps the tokens, and gives the browser only an HttpOnly session cookie. The pattern where the browser holds the tokens itself (s6.3) is "not recommended" for those apps.

Predict, then reveal

Your internal labelling tool stores a JWT in localStorage and sends it as a Bearer header. Someone proposes moving it to a cookie "for security". What do you gain, and what new risk appears?

Reveal
Gain: with HttpOnly, an injected script can no longer read the token and send it away (it can still act within the page while it runs). New risk: the browser now attaches the credential automatically, which opens CSRF; you need SameSite=Lax or Strict (and for state-changing requests, a CSRF token or a custom header check). RFC 10017's BFF pattern is this move done fully: tokens stay on a server, the browser holds only a session cookie.
