Debugging habits: always print the status and the WWW-Authenticate header (curl -sS -D - -o /dev/null ...); the server usually names the check that failed. Decode tokens to read them, but trust nothing they say about themselves until a signature check has run. Print key and token hints (first characters, last four, jti), never the values.

Interview rehearsal (eleven questions, model answers)
What is the difference between authentication and authorization, and how does HTTP show it?
Authentication establishes who the caller is; authorization decides whether that caller may perform this action. A failed or missing credential is 401 with a WWW-Authenticate challenge; a valid credential without permission is 403 (with OAuth, error="insufficient_scope").
Walk me through the authorization code flow with PKCE. What does PKCE protect against?
Client creates a random verifier and sends its S256 hash in the authorization request with state, redirect URI, scope and resource; the user authenticates and consents; the AS redirects back with a one-time code (and iss); the client checks state and iss, then redeems the code with the verifier at the token endpoint over a direct TLS call. PKCE stops an intercepted or injected code from being redeemed by anyone who does not hold the verifier, which matters most for public clients that have no secret.
Why did OAuth 2.1 remove the implicit grant?
It returned the access token in the redirect URL, where it leaks through history, referrers, extensions and logs, cannot be sender-constrained, and can be injected. The code flow with PKCE gives browser apps the same result with the token delivered on a back channel.
How would you validate a JWT access token?
Pin the expected algorithm; pick the key by kid from the issuer's cached JWKS (never from jku/x5u or a kid path); verify the signature; check typ (at+jwt), iss, aud (contains me), exp/nbf with small leeway; then authorize on scopes and the resource. Refetch JWKS on unknown kid, rate-limited.
JWT or opaque token with introspection? Trade-offs.
JWT: offline verification in microseconds, no AS on the hot path, but no early revocation and contents visible to anyone. Opaque with introspection: revocable immediately and private, but every call (or cache window) hits the AS. Common answer: short-lived JWTs plus refresh, with introspection or a denylist for high-value operations.
What is refresh token rotation and what does reuse detection buy you?
Each refresh returns a new refresh token and invalidates the old one. If an invalidated one is presented, two parties hold copies, so the AS revokes the whole grant: a stolen refresh token becomes detectable and short-lived, at the cost of logging the real user out too.
How do bearer tokens differ from DPoP or mTLS-bound tokens?
Bearer tokens work for whoever holds them. Bound tokens carry a confirmation (cnf) of a key; each request must prove possession (a signed DPoP proof covering method, URL, time and the token hash, or the TLS client certificate). A token stolen from a log is useless without the key.
Your service received a user's token and needs to call another service for them. What do you do?
Not forward it. Use token exchange (RFC 8693): authenticate as the service, present the received token as subject_token, request the downstream audience and narrower scopes, and prefer a delegation token with an act claim so the downstream sees both the user and the service.
How does a remote MCP server authorize clients, and what must the server check?
It is an OAuth resource server: 401 with resource_metadata, protected resource metadata naming its AS, the client discovers the AS, identifies itself (pre-registered, CIMD, or deprecated DCR), runs code + PKCE S256 with the resource parameter, checks iss, and sends Bearer tokens on every request. The server must validate each token including that its audience is this server, must not accept tokens for other resources, and must not pass tokens through to upstream APIs.
How do you give a CI job cloud access without storing a cloud secret?
Workload identity federation: the CI platform issues an OIDC token for the job; the cloud's token service exchanges it for short-lived credentials if a trust policy matches iss, aud and an exact sub (repository plus protected branch or environment). Watch for wildcards and for subject format changes.
Why is an API key acceptable for calling an LLM provider but not for a third-party integration?
Server to server under one owner, the key's lack of user context and consent does not matter, and secrets management plus rotation handle its risks. A third party acting for your users needs per-user consent, limited scopes, expiry and revocation per grant: OAuth.
