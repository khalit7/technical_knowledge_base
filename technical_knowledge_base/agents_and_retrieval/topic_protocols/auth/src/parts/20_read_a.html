In one screen

Every request that reaches an API has to answer two questions before it does anything: who is calling (authentication) and may they do this (authorization). The answer travels with the request as a credential: a secret string, a signed token, a certificate or a signature. This page follows the credentials an ML engineer meets, from the API key on an LLM request to the tokens an agent carries to an MCP server, and shows each one on the wire.

The parent page, {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}} (Reading, section 8), gives the overview in five minutes. This page owns the depth. Everything marked "recorded" below was produced on 5 October 2026 by a small lab built for this page: an OAuth 2.1 authorization server, an MCP server and client from the official Python SDK (mcp 2.3.0), and two upstream APIs, all on one laptop, with a recording proxy in front of each so every byte that crossed the wire was saved (scripts and raw output in this page's src/lab/).

Three ideas carry the whole page:

  1. Bearer versus bound. A bearer credential works for anyone who holds it, like cash; a bound one also needs a private key or a TLS connection the thief does not have. Most leaks are bearer leaks.
  2. Narrow it. A credential should say which service it is for (its audience), what it allows (its scopes) and until when (its expiry). Each narrowing turns a leak from a catastrophe into an incident.
  3. Never forward what you received. A service that gets a token for itself and needs to call another service obtains a new token for that service. Agents made this rule urgent: the MCP specification makes it a MUST NOT (section 9).
What changed recently (checked 5 October 2026)
  • OAuth 2.1 is still an Internet-Draft: revision 16, 3 September 2026 ({{datatracker|https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/}}). It removes the implicit and password grants, requires PKCE (with one narrow exception), drops the PKCE "plain" method and requires exact redirect URI matching.
  • The security rules it consolidates are already an RFC: the OAuth 2.0 Security Best Current Practice, {{RFC 9700|https://www.rfc-editor.org/rfc/rfc9700}} (January 2025). Browser apps got their own BCP in August 2026: {{RFC 10017|https://www.rfc-editor.org/rfc/rfc10017}}, which strongly recommends a backend-for-frontend for business and sensitive apps.
  • MCP's 2026-07-28 revision makes Client ID Metadata Documents the preferred way for a client to identify itself and deprecates dynamic client registration ({{MCP authorization, 2026-07-28|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization}}).
  • GitHub Actions OIDC tokens for repositories created after 15 July 2026 carry an immutable subject with owner and repository IDs ({{GitHub docs|https://docs.github.com/en/actions/reference/security/oidc}}): cloud trust policies written against the old format do not match them.
