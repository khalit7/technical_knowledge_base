7. Beyond bearer: bound tokens, signed requests, cloud IAM and mTLS

Every credential so far is a bearer credential: steal it and you are the owner. This section is about the designs where a stolen copy is not enough.

DPoP: a token that only works with its key

How it works ({{RFC 9449|https://www.rfc-editor.org/rfc/rfc9449}}, September 2023). The client generates a key pair and keeps the private key. With every request (to the token endpoint and to the API) it sends a DPoP header: a small JWT, signed with that key, whose header carries the public key and whose claims name the HTTP method (htm), the URL (htu), the time (iat), a unique ID (jti) and, at the API, the hash of the access token (ath). The AS puts the key's thumbprint ({{RFC 7638|https://www.rfc-editor.org/rfc/rfc7638}}) into the token as cnf.jkt; the API checks that the proof was signed by that same key, for this request, just now. What it costs: one ES256 signature per request on the client (about µs here, from the table in section 6) and one verification plus a replay cache of recent jti values on the server. What it does not stop: malware running inside the client can ask the client to sign proofs (RFC 9449 s11.4 discusses this); the server-provided nonce (s8, s9) limits proofs made in advance. When to use it: public clients holding valuable refresh tokens (OAuth 2.1 accepts it in place of rotation), and APIs where a leaked token in a log would be serious. The older alternative binds the token to a TLS client certificate instead ({{RFC 8705|https://www.rfc-editor.org/rfc/rfc8705}}), natural where mTLS already exists.

SigV4: AWS signs every request instead of sending a token

AWS chose a different shape long ago. You hold an access key ID (public) and a secret access key (never sent). For each request the SDK builds a canonical request (method, path, sorted query, lowercased sorted headers, the list of signed headers, the SHA-256 of the body), hashes it into a string to sign with the timestamp and a credential scope (date, region, service), derives a signing key by chaining HMACs of the secret over date, region, service and the literal aws4_request, and sends the final HMAC as the signature ({{AWS: create a signed request|https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html}}). The calculator below does all of it in this page's JavaScript. Its defaults are the get-vanilla vector of the SigV4 test suite as shipped in botocore (example credentials AKIDEXAMPLE), and they reproduce the suite's expected signature .



Try: change one character of the path or the body and watch the signature change completely: the signature covers the request, so a proxy cannot alter it. Change the date by one day: the signing key changes too, which is why a leaked derived key is only good for one day, one region, one service.




What this buys. The secret never crosses the wire, so a logged request leaks no reusable credential; the body hash means nobody in the middle can change the request; the timestamp means a captured request is refused after a few minutes ("in most cases, a request must reach AWS within five minutes of the time stamp", {{AWS SigV4 overview|https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html}}). What it costs: every client needs an SDK (or this page's dozen steps done exactly right: header case, whitespace and URI encoding rules cause most SignatureDoesNotMatch errors), and clock skew of more than a few minutes breaks every call.



Cloud IAM and workload identity: no long-lived secrets at all


The best secret is one you never store. On AWS, code on an EC2 instance, a Lambda or a pod gets temporary credentials for its role from the platform (access key, secret and a session token sent as X-Amz-Security-Token), the SDK refreshes them before they expire, and IAM policies on the role decide what it may do. Calling Bedrock, SageMaker or S3 from your own AWS code needs no key at all.


Across clouds and from CI, the same idea uses OIDC: the platform gives the job an ID token about itself, and the cloud's security token service trades it for temporary credentials if a trust policy matches its claims (on AWS, AssumeRoleWithWebIdentity). GitHub Actions is the common case: a workflow with permissions: id-token: write gets a token from the issuer whose discovery document is in section 5. The trust policy is the whole security boundary, so read the subject claim it matches ({{GitHub docs|https://docs.github.com/en/actions/reference/security/oidc}}):

Two traps follow. A trust condition with a wildcard such as repo:octo-org/* lets every workflow on every branch of every repository in the organisation assume the role, so anyone who can push a branch anywhere in the organisation holds the role's permissions; match the exact repository and a protected branch or environment. And a policy written for the old format silently stops matching new repositories, whose subject now includes the numeric IDs; GitHub added the IDs because a deleted organisation or repository name could be re-registered by someone else and inherit the old subject.



mTLS: identity in the connection


With mutual TLS both sides present certificates during the TLS handshake, so a service's identity is proven before any HTTP byte flows, and there is no header to leak. Service meshes automate the hard part (issuing and rotating short-lived certificates per workload); SPIFFE standardises the identity as a URI such as spiffe://prod.example/ns/serving/sa/vllm inside the certificate ({{SPIFFE ID spec|https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md}}). Authorization then works on that name ("the gateway may call vLLM; the notebook may not"). The handshake, the certificate chain and the failure modes belong to the sibling page {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}; the parent's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} has "mTLS: client certificate missing".

Predict, then reveal


A CI job's AWS calls work on GitHub-hosted runners but fail on one self-hosted runner with an error about the signature or the request time. Same code, same role. What do you check first?


Reveal
The runner's clock (date -u against a trusted time source). The timestamp is part of the string to sign and AWS refuses requests that arrive more than a few minutes away from it. After that, look for a proxy on that runner's network that rewrites a signed header (Host, Content-Type) or re-encodes the path, which changes the canonical request.
