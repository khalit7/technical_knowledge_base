1. The words, from zero

A principal is whoever a request acts for: a person ("alice"), a service ("batch-job") or an agent acting for a person. A credential is the evidence the request carries. The server authenticates the credential (is it genuine, unexpired, meant for me?) and then authorizes the action (may this principal read this file?). The two fail differently, and HTTP gives them different status codes:

401 Unauthorized

Despite its name, this means unauthenticated: no credential, or one the server cannot accept (bad signature, expired, wrong audience). The server MUST say how to authenticate in a WWW-Authenticate header ({{RFC 9110 s15.5.2|https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2}}). Retrying with a fresh credential can fix it.

403 Forbidden

The server knows who you are and the answer is no ({{RFC 9110 s15.5.4|https://www.rfc-editor.org/rfc/rfc9110#section-15.5.4}}). A new token with the same rights will not help; more rights (a scope, a role) might. OAuth signals the scope case with error="insufficient_scope" ({{RFC 6750 s3.1|https://www.rfc-editor.org/rfc/rfc6750#section-3.1}}).

Here is a real 401 from this page's lab: a token minted for the mail API, presented to the MCP server (recorded). The server names the problem class and, in the MCP style, points to the document that says where to get a proper token.



One detail worth noticing: for a request with no credential, RFC 6750 says the server "SHOULD NOT include an error code" ({{s3.1|https://www.rfc-editor.org/rfc/rfc6750#section-3.1}}); the MCP SDK 2.3.0 server sends error="invalid_token" in that case too (see the first response in the {{MCP auth flow|#t-mcpflow}} tab). Harmless, but it means a client cannot tell "no token" from "bad token" by the error code alone.

Bearer versus bound, the distinction that matters most


A bearer credential is accepted from anyone who presents it ({{RFC 6750 s1.2|https://www.rfc-editor.org/rfc/rfc6750#section-1.2}} defines the term exactly that way). API keys, session cookies and ordinary OAuth access tokens are bearer credentials: a copy in a log file, a crash dump, a notebook or a model's context window is as good as the original. A sender-constrained (bound) credential also requires proof that the presenter holds a private key: a DPoP proof signed per request, or the TLS client certificate the token was issued to. Section 7 shows a stolen bound token failing three ways.


Predict, then reveal


An agent's token has scope files:read. It calls write_file on an MCP server that checks scopes. Which status, and which header tells the client what to ask for?


Reveal
403 Forbidden with WWW-Authenticate: Bearer error="insufficient_scope", scope="files:write", resource_metadata="...". The token is genuine (so not 401); the right fix is a step-up authorization that requests the union of the old and the new scopes, which the MCP specification spells out ({{Scope Challenge Handling|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#scope-challenge-handling}}).
