4. OAuth 2.1: letting an app act for a user

The problem. You want a CLI agent to read your files on a cloud drive. You could paste your drive password into the agent: then it can do everything you can, forever, and the drive cannot tell it from you. OAuth replaces the password with a delegation: the drive's login server asks you, once, whether this particular app may do these particular things, and if you agree it gives the app a short-lived, limited token. The app never sees your password.

Four roles, named in every spec ({{OAuth 2.1 draft-16 s1.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-1.1}}):

Resource owner

You, alice: the person whose data it is.

Client

The app or agent that wants access (a CLI, a web app, an MCP client). Public clients (CLIs, desktop and mobile apps, browser code) cannot keep a secret; confidential clients (servers) can.

Authorization server (AS)

Logs you in, asks for consent, issues tokens. Google's accounts.google.com, Microsoft Entra, Okta, Auth0, Keycloak, or your own.

Resource server (RS)

The API that holds the data and accepts the tokens: the drive API, an MCP server.

The authorization code flow with PKCE, step by step

This is the flow for anything a person logs into: web apps, mobile apps, CLIs, desktop agents, MCP clients. The animation runs one login three ways: the implicit flow OAuth 2.0 used for browser apps (now removed), the code flow without PKCE, and the code flow with PKCE, each with an attacker who can read the redirect (a malicious app that registered the same custom URL scheme on a phone, a browser extension, or a log that records full URLs: the attacks {{RFC 9700 s4.1 to s4.5|https://www.rfc-editor.org/rfc/rfc9700#section-4.1}} describe).

Try: play each mode to its last step and compare what the attacker ends up holding. Then compare the step counts: PKCE costs the client one hash and two extra parameters, and no extra round trip.

What each piece does (the parameters are in every authorization URL you will ever debug; the recorded one is in the {{MCP auth flow|#t-mcpflow}} tab, step 4):

  • response_type=code: ask for a one-time authorization code, not a token. The code comes back through the browser, which is the leaky part; the tokens come back on a direct, TLS-protected back-channel call from the client to the AS's token endpoint.
  • code_challenge and code_challenge_method=S256 (PKCE, {{RFC 7636|https://www.rfc-editor.org/rfc/rfc7636}}): the client invents a random code_verifier, sends only its SHA-256 (base64url) in the authorization request, and must present the verifier itself to redeem the code. Whoever steals the code from the redirect does not have the verifier. The RFC's own example (verifier dBjftJeZ...EjXk gives challenge ) is recomputed live by this page's SHA-256: .
  • state: a random value the client checks when the browser comes back, so an attacker cannot feed the client a response to a request it never made (CSRF on the callback).
  • redirect_uri: where the AS sends the browser back. It must exactly match a registered value ({{RFC 9700 s4.1.3|https://www.rfc-editor.org/rfc/rfc9700#section-4.1.3}}); pattern matching let attackers register lookalike paths and receive codes. One relaxation: for native apps listening on a loopback address, the port may vary ({{RFC 8252 s7.3|https://www.rfc-editor.org/rfc/rfc8252#section-7.3}}), which is how claude, gh and gcloud logins catch the redirect on http://127.0.0.1:<random port>/callback. The {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}}'s "OAuth redirect URI mismatch" case shows the error a near-miss gets.
  • iss in the response ({{RFC 9207|https://www.rfc-editor.org/rfc/rfc9207}}): the AS names itself, so a client talking to several authorization servers can refuse a response that came from the wrong one (a "mix-up" attack). MCP clients must check it (section 9); the SDK did, in the recording.
  • scope and resource: what the token may do, and for which API ({{RFC 8707|https://www.rfc-editor.org/rfc/rfc8707}}). Together they decide how bad a leak is.

Correction to the old page
The old page said PKCE is "mandatory even for confidential clients". OAuth 2.1 draft-16 is one notch softer: PKCE is required unless the client is confidential and the AS has reasonable assurance it implements the OpenID Connect nonce correctly; even then PKCE stays recommended, because only PKCE lets the AS refuse an injected code before issuing any token ({{draft-16 s7.5.1.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-7.5.1.1}}). The draft also removed the PKCE plain method and the redirect_uri parameter in the token request (s10, s10.2). The MCP SDK 2.3.0 client still sends redirect_uri at the token endpoint (visible in the recording); servers ignore it.



Refresh tokens: staying signed in without long-lived access tokens


Access tokens are kept short (the lab's live 300 s) so a stolen one expires soon. To avoid sending the user through the browser every few minutes, the AS also issues a refresh token, which the client trades for a new access token at the token endpoint. A refresh token is long-lived and therefore precious, so OAuth 2.1 requires, for public clients, that refresh tokens be either sender-constrained (DPoP or mTLS) or rotated: every refresh returns a new refresh token and invalidates the old one, and if an old one is ever presented again, someone has a copy, so the AS revokes the whole grant ({{draft-16 s4.3.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-4.3.1}}). Client credentials: a service acting as itself


When there is no user (a nightly batch job calling an internal API), the client authenticates as itself at the token endpoint and receives a token whose subject is the client. How it authenticates matters more than the grant: a shared secret in a Basic header (simple, but a secret to store and rotate), or better a private_key_jwt: the client signs a short JWT assertion with its own private key and the AS checks it with the registered public key ({{RFC 7523 s2.2|https://www.rfc-editor.org/rfc/rfc7523#section-2.2}}), so no shared secret exists at all. The device grant: logging in a box with no browser


A GPU node over SSH, a TV, a CLI in a container: none can open a browser. The device asks the AS for a device code (kept secret) and a short user code (shown to you), you type the user code on your phone, and the device polls the token endpoint until you approve ({{RFC 8628|https://www.rfc-editor.org/rfc/rfc8628}}). Polling has rules: wait interval seconds (5 if unspecified); on slow_down, add 5 seconds for good (s3.5). Recorded, with the lab's interval set to 1 s to keep it short:




The user code is short on purpose. RFC 8628's own example, 8 characters from a 20-letter alphabet, carries 8 × log2(20) =  bits, enough only because of rate limiting and expiry (s6.1). The flow has a real weakness: the user approves a code someone else started. In the Storm-2372 campaign, attackers sent victims device codes disguised as meeting invitations, and the victims' approvals gave the attackers tokens; Microsoft's advice is to block the device flow wherever it is not needed ({{Microsoft Threat Intelligence, 13 February 2025|https://www.microsoft.com/en-us/security/blog/2025/02/13/storm-2372-conducts-device-code-phishing-campaign/}}).



What OAuth 2.1 removed, and what real providers still offer


The draft's list of changes from 2.0 ({{s10|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-10}}): PKCE by default; exact redirect URI matching; no implicit grant (tokens in the redirect could not be sender-constrained and leaked through history and referrers); no resource owner password grant (the app saw the password); no bearer tokens in query strings; refresh tokens for public clients sender-constrained or one-time; no redirect_uri in the token request; client credentials accepted in the request body; no PKCE plain. A draft is not a switch, though. Google's discovery document, fetched for this page, still advertises what 2.1 removed, for old clients:




So "OAuth 2.1" in practice means: your client uses only the 2.1 subset, whatever the provider still allows. Two further pieces you will meet: pushed authorization requests ({{RFC 9126|https://www.rfc-editor.org/rfc/rfc9126}}), where the client posts the authorization parameters to the AS first and the browser carries only a reference, so nothing in the URL can be tampered with or leaked; and authorization server metadata ({{RFC 8414|https://www.rfc-editor.org/rfc/rfc8414}}), the /.well-known/oauth-authorization-server document every client above read first.

Reveal
Nothing useful: redeeming the code needs the code_verifier, which never left the real app's memory; the token endpoint answers invalid_grant (the recording above). Depending on the AS, its attempt may burn the code, so the user has to log in again: a denial, not a theft. Without PKCE the same interception yields tokens, which is why {{RFC 8252 s6|https://www.rfc-editor.org/rfc/rfc8252#section-6}} required PKCE for native apps in 2017 and OAuth 2.1 extends it to everyone.
