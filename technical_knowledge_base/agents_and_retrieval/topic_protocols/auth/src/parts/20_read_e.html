4. OAuth 2.1: letting an app act for a user

alice wants a CLI agent to read her files on a cloud drive. Pasting her drive password into the agent would let it do everything she can, forever, indistinguishable from her. OAuth replaces the password with a delegation: the drive's login server asks alice once whether this app may do these things, and if she agrees gives the app a short-lived, limited token. The app never sees her password. Four roles, named in every spec ({{OAuth 2.1 draft-16 s1.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-1.1}}):

Resource owner

alice, whose data it is.

Client

The app or agent (a CLI, a web app, an MCP client). Public clients (CLIs, desktop and mobile apps, browser code) cannot keep a secret; confidential clients (servers) can.

Authorization server (AS)

Logs alice in, asks for consent, issues tokens: accounts.google.com, Microsoft Entra, Okta, Auth0, Keycloak, or your own.

Resource server (RS)

The API that holds the data and accepts the tokens: the drive API, an MCP server.

The authorization code flow with PKCE

The flow for anything a person logs into: web and mobile apps, CLIs, desktop agents, MCP clients. Predict first: an attacker can read the browser redirect (a malicious app that registered the same custom URL scheme on a phone, a browser extension, a log that records full URLs: the attacks of {{RFC 9700 s4.1 to s4.5|https://www.rfc-editor.org/rfc/rfc9700#section-4.1}}). What does it end up holding in each mode? Then step through.

The same login three ways: only PKCE leaves the attacker with nothing it can redeem

Compare the step counts too: PKCE costs the client one hash and two extra parameters, and no extra round trip.

The parameters you will debug in every authorization URL (the recorded one is step 4 of the MCP flow in section 9):

  • response_type=code: ask for a one-time authorization code, not a token. The code comes back through the browser, the leaky part; the tokens come back on a direct, TLS-protected call from the client to the AS's token endpoint.
  • code_challenge, code_challenge_method=S256 (PKCE, {{RFC 7636|https://www.rfc-editor.org/rfc/rfc7636}}): the client invents a random code_verifier, sends only its SHA-256 (base64url), and must present the verifier to redeem the code. The RFC's own example (verifier dBjftJeZ...EjXk gives challenge ) is recomputed live by this page's SHA-256: .
  • state: a random value the client checks on return, so an attacker cannot feed it a response to a request it never made (CSRF on the callback).
  • redirect_uri: must exactly match a registered value ({{RFC 9700 s4.1.3|https://www.rfc-editor.org/rfc/rfc9700#section-4.1.3}}); pattern matching let attackers register lookalike paths and receive codes. For native apps on a loopback address the port may vary ({{RFC 8252 s7.3|https://www.rfc-editor.org/rfc/rfc8252#section-7.3}}), which is how claude, gh and gcloud logins catch the redirect on http://127.0.0.1:<random port>/callback (the {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}}'s "OAuth redirect URI mismatch" shows a near-miss).
  • iss in the response ({{RFC 9207|https://www.rfc-editor.org/rfc/rfc9207}}): the AS names itself, so a client talking to several authorization servers can refuse a response from the wrong one (a "mix-up" attack). MCP clients must check it; the SDK did, in the recording (section 9).
  • scope and resource: what the token may do, and for which API ({{RFC 8707|https://www.rfc-editor.org/rfc/rfc8707}}). Together they decide how bad a leak is.

Correction to the old page
The old page said PKCE is "mandatory even for confidential clients". OAuth 2.1 draft-16 is one notch softer: PKCE is required unless the client is confidential and the AS has reasonable assurance it implements the OpenID Connect nonce correctly; even then PKCE stays recommended, because only PKCE lets the AS refuse an injected code before issuing any token ({{draft-16 s7.5.1.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-7.5.1.1}}). The draft also removed the redirect_uri parameter from the token request (s10.2); the MCP SDK 2.3.0 client still sends it (visible in the recording), and servers ignore it.



Refresh tokens: rotation catches a copy


Access tokens stay short (the lab's live 300 s) so a stolen one expires soon; a refresh token lets the client get new ones without sending alice through the browser again. Being long-lived, it is precious, so OAuth 2.1 requires that a public client's refresh tokens be sender-constrained (DPoP or mTLS) or rotated: each refresh returns a new refresh token and invalidates the old one, and if an old one is ever presented again someone has a copy, so the AS revokes the whole grant ({{draft-16 s4.3.1|https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-16#section-4.3.1}}).




The thief's replay of a spent refresh token revokes the grant, logging out the real client too




recorded Statuses and error texts from the lab AS: "refresh token reuse detected; grant revoked", then "refresh token invalid or revoked". The AS cannot tell which of the two presenters was the thief, so both lose: one forced re-login against a silent, long-lived compromise. The same mechanism bites honest code: two processes sharing one refresh token look exactly like this (section 10).





Client credentials: a service acting as itself


With no user (a nightly batch job calling an internal API), the client authenticates as itself at the token endpoint and receives a token whose subject is the client. How it authenticates matters more than the grant: a shared secret in a Basic header (a secret to store and rotate), or better private_key_jwt, a short JWT assertion the client signs with its own private key and the AS checks with the registered public key ({{RFC 7523 s2.2|https://www.rfc-editor.org/rfc/rfc7523#section-2.2}}), so no shared secret exists at all (the lab's MCP server authenticates this way in section 8). recorded with a secret:





The device grant: logging in a box with no browser


A GPU node over SSH, a TV, a CLI in a container cannot open a browser. The device asks the AS for a secret device code and a short user code, alice types the user code on her phone, and the device polls the token endpoint until she approves ({{RFC 8628|https://www.rfc-editor.org/rfc/rfc8628}}). Polling rules: wait interval seconds (5 if unspecified); on slow_down, add 5 seconds for good (s3.5).




The device polls; polling too fast earns slow_down; tokens arrive on the first poll after approval




recorded with the lab's interval set to 1 s to keep it short; after slow_down the AS answered "polling too fast; interval is now 6 s".




The user code is short on purpose: RFC 8628's own example, 8 characters from a 20-letter alphabet, carries 8 × log2(20) =  bits, enough only because of rate limiting and expiry (s6.1). The flow's real weakness: the user approves a code someone else started. In the Storm-2372 campaign, attackers sent victims device codes disguised as meeting invitations, and the victims' approvals gave the attackers tokens; Microsoft's advice is to block the device flow wherever it is not needed ({{Microsoft Threat Intelligence, 13 February 2025|https://www.microsoft.com/en-us/security/blog/2025/02/13/storm-2372-conducts-device-code-phishing-campaign/}}).

Predict, then reveal


A mobile app uses the code flow with PKCE. A malicious app on the same phone registered the same custom URL scheme and receives the redirect, code included. What can it do with the code?


Reveal
Nothing useful: redeeming the code needs the code_verifier, which never left the real app's memory; the token endpoint answers invalid_grant (the recording above). Depending on the AS, its attempt may burn the code, so the user logs in again: a denial, not a theft. Without PKCE the same interception yields tokens, which is why {{RFC 8252 s6|https://www.rfc-editor.org/rfc/rfc8252#section-6}} required PKCE for native apps in 2017 and OAuth 2.1 extends it to everyone.
