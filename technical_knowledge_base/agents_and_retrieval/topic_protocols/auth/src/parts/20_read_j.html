9. Agent-era auth: MCP authorization, audience binding, no token passthrough

Why agents change the threat model. An agent is a program that holds credentials and decides what to do with them based on text it reads, and some of that text was written by strangers: a web page, an email, a tool result. The parent page's section 9 and its {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "A tool result that carries an injected instruction" show the mechanism; Simon Willison's "lethal trifecta" names when it becomes theft: private data, untrusted content and a way to send data out, in one agent ({{16 June 2025|https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/}}). Auth cannot stop an agent from being talked into misusing a credential it legitimately holds. What auth can do is decide how much each credential is worth when that happens, and keep credentials from travelling further than intended. The rules below all serve that.

The protocol details of MCP (messages, transports, the stateless 2026-07-28 revision) live on the sibling page {{MCP: building servers and clients, transports, auth and security|n:3c65c17b0d0d813f9695dc4175c44cbb}}. This section is the authorization part, quoted from {{MCP 2026-07-28, Authorization|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization}} and its sub-pages, and checked against the official Python SDK.

The MCP authorization flow in eight steps

Authorization is optional in MCP and applies to the HTTP transport. A local server started over stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment". For a remote server, the spec composes the OAuth pieces from sections 4 to 6. Every step below happened in the recording; the {{MCP auth flow|#t-mcpflow}} tab replays each one byte for byte.

  1. Unauthenticated call, 401. The client POSTs an MCP request with no token. The server answers 401 with WWW-Authenticate: Bearer resource_metadata="...", optionally with a scope the operation needs.
  2. Protected resource metadata ({{RFC 9728|https://www.rfc-editor.org/rfc/rfc9728}}, April 2025). The client fetches the URL from the header (or, without one, tries /.well-known/oauth-protected-resource/<path> then the root). The document names the server's canonical resource URI and its authorization_servers. Servers MUST publish it; clients MUST use it.
  3. Authorization server metadata. The client fetches RFC 8414 metadata (or OIDC discovery, trying the documented well-known paths in order) and MUST reject it if the issuer inside differs from the issuer it used to build the URL.
  4. Client identity. In priority order: credentials pre-registered for this AS; otherwise a Client ID Metadata Document, if the AS advertises client_id_metadata_document_supported: the client's ID is an HTTPS URL, and the AS fetches that URL to read the client's name and allowed redirect URIs; otherwise dynamic client registration ({{RFC 7591|https://www.rfc-editor.org/rfc/rfc7591}}), now deprecated; otherwise ask the user. CIMD solves MCP's peculiar situation: thousands of clients meeting thousands of servers with no prior relationship, without every AS accepting unlimited anonymous registrations.
  5. Authorization request. PKCE with S256 (the client MUST refuse to proceed if the metadata lacks code_challenge_methods_supported), the resource parameter set to the server's canonical URI in both the authorization and the token request, and the scopes from the 401 challenge (else from scopes_supported).
  6. Issuer check on the way back. The client records the expected issuer before redirecting and compares the iss in the response by exact string match before sending the code anywhere (RFC 9207). In the recording, the SDK refused a response carrying another issuer: .
  7. Token request with the code, the verifier and the resource; for public clients, the AS MUST rotate refresh tokens.
  8. Every MCP request carries Authorization: Bearer ... (never the query string), and the server validates each token, including that it was issued for this server.

Audience binding: the server must check the token is for it

The spec is blunt: "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" and "MUST only accept tokens that are valid for use with their own resources." The client's half is the resource parameter, which asks the AS to put the server's URI in aud. The recording's step W shows the server half: a token minted for the mail API was refused by the MCP server with a 401.

A default worth knowing (MCP Python SDK 2.3.0)
The SDK's resource-server mode has a setting AuthSettings.validate_token_resource. In 2.3.0 it is not on by default: with resource_server_url set and the setting left unset, the SDK warns that bearer tokens "are not checked against resource_server_url" and says the default becomes True in 3.0 (read from the installed package's mcp/server/auth/settings.py). Audience checking is then entirely up to your token verifier. The lab's server turns the setting on and passes the expected audience to PyJWT; do both.

No token passthrough

The rule: "MCP servers MUST NOT accept or transit any other tokens", and when a server calls an upstream API, "the access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received" ({{security considerations|https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations}}). A careless upstream that checks only the signature accepts the forwarded token and believes alice's MCP client called it directly: the MCP server, the actual caller, is invisible in its logs and to any per-client limits it applies. That is the accountability failure the spec's best-practices page lists, and the same mechanics let anyone holding a token for the MCP server reach the mail API through it. The careful upstream refuses (first row), and token exchange (last row, section 8) gives it a token that names both alice and the MCP server. The confused deputy, MCP's version

An MCP server that fronts a third-party API with one static OAuth client ID is a deputy acting for many users. The spec's best-practices page walks through the attack ({{Confused Deputy Problem|https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices}}): alice once approved the proxy at the third-party AS, which set a consent cookie; an attacker registers a new client with the proxy (dynamic registration) using their own redirect URI and sends alice a link; the third-party AS sees the cookie, skips consent, and the code lands at the attacker. Required fixes on the proxy: per-client consent stored server-side before forwarding to the third party, a consent page that names the client, its scopes and its redirect URI, exact redirect matching, a state stored only after consent, and consent cookies with the __Host- prefix, Secure, HttpOnly, SameSite=Lax and bound to the specific client_id.

Credential isolation and least privilege for agents

  • Keep credentials out of the model's context. Anything in the prompt or in a tool result can be repeated into a tool call by an injected instruction. Tokens belong in the client and server processes, attached by code to HTTP requests, never pasted into messages, tool arguments or tool results.
  • Per user, per server. A server that needs upstream access keeps upstream tokens per verified user (keyed by the token's sub, never by something the client sends). The spec's rule for state handles in the stateless 2026-07-28 protocol is the same idea: possession of a handle is not authentication; key stored state by <user_id>:<handle> with the user ID taken from the verified token ("State Handle Hijacking" in the best-practices page).
  • Local servers get only their own secrets. A stdio server inherits environment variables from the host that starts it; give each server only the variables it needs, not your whole shell environment.
  • Scopes small, then step up. Start with read-only scopes and let the server challenge for more with 403 insufficient_scope when a write is first attempted; the spec lists publishing every scope in scopes_supported, wildcard scopes and bundling unrelated privileges as common mistakes ("Scope Minimization").
  • Irreversible actions need a human, out of band. A confirmation dialog shown by the host, outside the conversation, cannot be forged by text arriving through a tool. Separate destructive scopes make that enforceable at the server too.
  • Clients: treat server-supplied URLs as hostile. An authorization URL from a malicious server can be javascript: or carry shell metacharacters; clients MUST allow only http(s) (http only for loopback), and MUST NOT open URLs through a shell ("OAuth Authorization URL Validation").

Two dated details. The spec cites the CIMD Internet-Draft at revision 00; the draft has since reached revision 02 (6 July 2026, {{datatracker|https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/}}). The spec cites OAuth 2.1 draft 13; the current draft is 16 (section 4).

Predict, then reveal

Your company runs one MCP server in front of the internal ticketing API. A teammate suggests: "the client already has the user's SSO token for ticketing, just let the MCP server forward it". List two things that break.

Reveal
(1) Audience binding: the MCP server would have to accept a token not issued for it, so any ticketing token (from any app) would work at the MCP server, and the MCP server would be a convenient proxy for stolen ones. (2) Accountability and control: the ticketing API sees the user's original client, not the MCP server, so it cannot rate-limit, scope or audit what the agent does separately. Correct design: the MCP server is a resource server with its own audience, and it obtains its own ticketing token by token exchange (or the enterprise-managed authorization extension), narrowed to what its tools need.
