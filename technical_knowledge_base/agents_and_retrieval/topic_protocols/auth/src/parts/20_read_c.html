2. API keys: the simplest credential, done properly

The problem. Your backend calls an LLM provider thousands of times a day. There is no user to ask, no browser to redirect; the provider just needs to know which account to bill and limit. The parent page's running request carries the answer in one header: x-api-key: sk-wirelab-not-a-real-key (a fake). An API key is a long random string the provider generated, showed you once, and remembers. Whoever presents it is the account.

Anatomy of a good key

GitHub's 2021 token redesign is the clearest public write-up of what a key should look like ({{GitHub blog, 5 April 2021|https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/}}): a short prefix that says what it is, a random body, and a checksum. The lab made one in the same shape (recorded):



    

  • Prefix (lab_): secret scanners (GitHub's, your CI's, your log pipeline's) can match it with almost no false positives, and an underscore keeps double-click selection whole.
    • 

  • Body: 30 characters from 62 symbols carry 30 × log2(62) =  bits; GitHub quotes 178. Guessing is hopeless, so the server can store a plain SHA-256 of the key (shown above) rather than the slow, salted hash a human-chosen password needs: there is nothing to brute-force.
    • 

  • Checksum: the last six characters are a CRC32 of the body in base 62. A scanner or the server can reject a mistyped or made-up key without a database lookup. Try it: change one character.
    • 





Living with keys


    

  • One key per service and environment. When staging's key leaks you revoke staging, not production, and the provider's per-key usage tells you who spent what. Providers apply rate limits per key or per organisation, so one runaway job with a shared key throttles everyone (429 with retry-after; the {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "429 Too Many Requests with Retry-After" shows the headers).
    • 

  • Store it in a secrets manager and inject it at run time. Not in git, not in a notebook (outputs and cell history get shared), not in a Docker image layer, not in a browser or mobile app (anyone can read it out).
    • 

  • Rotate with overlap. Create key 2, deploy it everywhere, watch key 1's usage fall to zero, then revoke key 1. Rotating by revoking first is an outage.
    • 

  • Show only a hint () in dashboards and logs, so people can tell keys apart without exposing them.
    • 



What a key cannot do. It carries no user (every call is "the account"), no consent, no expiry unless you add one, and no narrower audience than the whole provider. That is fine for your backend calling your provider. It is wrong as soon as a third party (an app, an agent) acts for one of your users: then you want OAuth (section 4).


Predict, then reveal


A notebook that worked yesterday now gets 401 from the LLM provider on every call; your colleague's identical notebook works. The key in your environment variable has the right prefix. What do you check first?


Reveal
Which key the process actually sees, and whether it is still active: print its hint (prefix and last four characters), not the key, and compare with the provider's dashboard. The usual causes are a key revoked in a rotation, a staging key against the production endpoint, or a stale value cached by the kernel or a .env file loaded before the change. A 401 says "this key is not accepted"; a 403 would say "this key is fine but may not use this model or workspace".
