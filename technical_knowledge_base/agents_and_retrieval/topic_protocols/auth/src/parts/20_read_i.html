8. Token exchange: calling onward without forwarding

The problem. Service A received alice's token, addressed to A. To do its job, A must call service B for alice. Forwarding alice's token is wrong (B is not its audience, and if B accepts it anyway, every token for A becomes a token for B). Using A's own all-powerful service credential is also wrong (B can no longer tell which user is behind the call, and A can be tricked into acting for the wrong user). The standard answer is token exchange ({{RFC 8693|https://www.rfc-editor.org/rfc/rfc8693}}, January 2020): A authenticates to the AS as itself, hands over the token it received as the subject_token, names the target with resource or audience, and receives a new token for B, usually with narrower scopes.

Recorded: the lab's MCP server performing exchange inside a tool call. It authenticates with private_key_jwt (a JWT it signed with its own key, so there is no shared secret anywhere), and the AS's policy allows only this one mapping (tokens for the MCP server, exchanged by the MCP server, for the mail API, scope narrowed to mail:read):

The new token's claims carry the distinction RFC 8693 names (s1.1). Delegation: the token says "alice, acted for by the MCP server" with an act claim (s4.1), so the mail API can log both and apply policy to both. Impersonation: the token simply says "alice", and the API cannot tell an intermediary was involved. Prefer delegation whenever an agent or service acts for a person; the audit trail is the point.

Where you meet it. Microsoft Entra's equivalent is the {{on-behalf-of flow|https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow}}. In MCP, the enterprise-managed authorization extension (status: stable) chains the two standard grants: the client exchanges the user's single-sign-on ID token at the company's identity provider for an ID-JAG (identity assertion JWT authorization grant), then presents it to the MCP server's authorization server as a JWT bearer grant ({{RFC 7523|https://www.rfc-editor.org/rfc/rfc7523}}), so employees never click through a consent screen per server and administrators decide centrally which servers are allowed ({{MCP ext-auth|https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/stable/enterprise-managed-authorization.mdx}}; the underlying {{IETF draft|https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/}} is at revision 04, May 2026).

Predict, then reveal

In the recording, which three checks did the AS make before issuing the exchanged token, and which single one stops a compromised other service from using the MCP server's identity?

Reveal
It authenticated the caller (the private_key_jwt signature, issuer and audience, plus a one-time jti), validated the subject token (signature, issuer, and that its audience is the MCP server), and applied policy (only this client, only toward the mail API, scope narrowed). Client authentication is what stops another service: without the MCP server's private key it cannot produce the assertion, whatever tokens it has collected.
