6. JWTs: tokens a server can check alone

The problem. If every API call required the API to ask the authorization server "is this token good?", the AS would carry the whole system's traffic and its latency. A JSON Web Token lets the AS put the answer inside the token and sign it, so any API holding the AS's public key can verify it offline in microseconds ({{RFC 7519|https://www.rfc-editor.org/rfc/rfc7519}}). The family of specs, all May 2015: JWS (signed, {{RFC 7515|https://www.rfc-editor.org/rfc/rfc7515}}), JWE (encrypted, RFC 7516), JWK (keys as JSON, {{RFC 7517|https://www.rfc-editor.org/rfc/rfc7517}}), JWA (algorithm names, {{RFC 7518|https://www.rfc-editor.org/rfc/rfc7518}}) and JWT itself (the claims). "JWT" in conversation almost always means a JWS-signed JWT.

Anatomy

Three base64url pieces separated by dots: a header (algorithm and key ID), a payload (the claims), a signature over the ASCII bytes base64url(header) + "." + base64url(payload). A real token from this page's lab (an RS256 access token, decoded by this page's JavaScript):

Anyone can decode the first two parts: base64url is an encoding, not encryption. Never put secrets or more personal data than needed in claims; use JWE or an opaque token if the contents must stay private.

The algorithms, measured

The same claims signed five ways with PyJWT 2.15.1 on this laptop (Apple M1 Pro, one core; median of 7 runs of 200; recorded):

  • HS256 is a MAC with a shared secret: the smallest and fastest, but every service that can verify can also mint tokens. Fine inside one service; wrong for an issuer with many verifiers.
  • RS256 (RSA) is the most widely deployed (Google, Microsoft and GitHub Actions all list only RS256 in the discovery documents in section 5). Verification is cheap and signing is about ten times slower, which suits one issuer and many verifiers; the cost is a 256-byte signature, so RS256 tokens are roughly twice the size of the others.
  • ES256 (P-256) and EdDSA (Ed25519) give 64-byte signatures. ECDSA needs care in implementations: Java 17.0.2 and 18 accepted a signature of all zeros as valid for any message and any key ({{CVE-2022-21449|https://www.cve.org/CVERecord?id=CVE-2022-21449}}; {{Neil Madden, "Psychic signatures in Java", 19 April 2022|https://neilmadden.blog/2022/04/19/psychic-signatures-in-java/}}): the verifier skipped the check that r and s are at least 1.

Validating a JWT, in order

  1. Choose the algorithm yourself. Accept only the algorithm(s) you expect for this issuer; never use the token's alg header to decide how to verify ({{RFC 8725 s3.1|https://www.rfc-editor.org/rfc/rfc8725#section-3.1}}). In PyJWT that is the algorithms=["RS256"] argument, required since 2.0.0 ({{changelog|https://github.com/jpadilla/pyjwt/blob/master/CHANGELOG.rst}}); applications that passed "every algorithm" there were still open to key confusion until 2.4.0 ({{CVE-2022-29217|https://www.cve.org/CVERecord?id=CVE-2022-29217}}).
  2. Choose the key yourself. Look the kid up in the issuer's JWKS, fetched from the jwks_uri in its discovery document and cached. Never fetch keys from a URL inside the token (jku, x5u) and never treat kid as a file path or a database query.
  3. Verify the signature.
  4. Check the type (typ: at+jwt for access tokens) so an ID token or another JWT from the same issuer is not accepted as an access token ({{RFC 8725 s3.11|https://www.rfc-editor.org/rfc/rfc8725#section-3.11}}).
  5. Check iss equals the issuer you trust and aud contains your own identifier ({{s3.8, s3.9|https://www.rfc-editor.org/rfc/rfc8725#section-3.9}}).
  6. Check time: exp in the future, nbf/iat not in the future, with a small leeway (seconds to a couple of minutes) for clock skew.
  7. Only now authorize: scopes, roles, tenant, the specific object.

The {{JWT lab|#t-jwt}} runs twelve real tokens (expired, wrong audience, skewed clock, ID token, edited payload, alg: none, HS256 signed with the RSA public key, kid path traversal, jku pointing at the attacker, weak HMAC secret and more) through two verifiers that both ran in Python: one that follows these rules and one that trusts the header. Switch each check off and watch which forgeries get through. The parent page's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} shows five of them as the 401 and 403 responses a real gateway returns ("Expired JWT", "Wrong audience", "Clock skew: token not yet valid", "Algorithm confusion rejected", "Missing scope: authenticated but not allowed").

Weak HMAC secrets fall offline

One captured HS256 token lets an attacker test candidate secrets on their own machine, as fast as they can compute HMACs, with no rate limit. Measured here: plain Python on one core tried candidates in s ( per second) and found secret123. At that rate, every 6-character secret of lowercase letters and digits takes 366 / rate = ; dedicated GPU crackers are faster still (not measured here). {{RFC 8725 s3.5|https://www.rfc-editor.org/rfc/rfc8725#section-3.5}} asks for keys with real entropy: use 32 random bytes, never a word.

The price of offline checking: no revocation

A self-contained token stays valid until exp, whatever happens at the AS. Recorded in the lab: a client-credentials token was revoked at the AS ({{RFC 7009|https://www.rfc-editor.org/rfc/rfc7009}}); the AS's introspection endpoint ({{RFC 7662|https://www.rfc-editor.org/rfc/rfc7662}}) then reported it inactive, and the MCP server, which validates JWTs offline, still accepted it:

The remedies, in order of cost: short lifetimes (minutes), so a revoked token dies soon anyway; a denylist of revoked jti values pushed to verifiers; introspection on every call for high-value operations, which brings the round trip back. This is also why JWTs make poor browser sessions (section 3): "log out" cannot reach a token already issued.
