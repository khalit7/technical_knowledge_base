MCP auth flow: every byte, recorded

An MCP client built with the official Python SDK (mcp 2.3.0, its OAuthClientProvider) connects to an MCP server built with the same SDK in resource-server mode, which trusts an OAuth 2.1 authorization server written for this page. A recording proxy sat in front of each server, so the bytes below are exactly what crossed the wire (plain HTTP on loopback; access tokens shortened to their first characters and length). Recorded 5 October 2026. Simulated, and said again where it matters: the browser and the user (a script fetched the authorization URL and the lab AS approved as if alice clicked "Allow"), and the client metadata host's certificate (a throwaway local CA). 2. Before and after: token passthrough against token exchange


The same connection then called three tools. Each one needs the user's mail from an upstream mail API. Pick a path and play it: the chips are tokens, labelled with their audience.















Try: play "Passthrough, careless upstream" and read the last counter: the mail API thinks alice's MCP client called it directly. Then play "Token exchange": one more round trip (to the AS), and the mail API sees both alice and the MCP server.





3. A mix-up attempt, refused by the SDK


A second client run had its callback report a different issuer (http://127.0.0.1:30666) than the one it discovered, the shape of a mix-up attack where a malicious AS tries to receive a code issued by an honest one (RFC 9207 s1). The SDK compared iss before sending the code anywhere and stopped. The recorded traffic ends at the redirect: no token request was made.




Reproduce it. WORK=<scratch dir> sh src/run_all.sh in this page's folder starts the four servers and three recording proxies on ports 30601 to 30614, runs the SDK client (src/lab/run_sdk_flow.py) and the scripted flows (src/lab/run_flows.py), and rebuilds this page from the recordings.
