8. Load balancing gRPC: L4, L7 and the client

The problem. You run three replicas of the inference service so that each takes a third of the calls. Something must choose a replica for every call. Where that choice is made, and how often, decides whether you get a third each or one hot replica and two idle ones. With HTTP/1.1 and short connections the answer barely mattered; with gRPC's long-lived multiplexed connections it is the number-one production surprise.

L4 balancer

Works at the transport layer (layer 4): it sees TCP connections, picks a backend once per connection, then copies bytes without reading them. Examples: AWS NLB, Linux IPVS, Kubernetes' kube-proxy, nginx stream.

L7 balancer

Terminates HTTP/2 (layer 7), reads each call's HEADERS, and picks a backend per call; it can also route on :path, retry, and count calls in flight. Examples: Envoy, nginx grpc_pass, a service-mesh sidecar, AWS ALB (gRPC since 29 October 2020, {{AWS announcement|https://aws.amazon.com/about-aws/whats-new/2020/10/application-load-balancers-enable-grpc-workloads-end-to-end-http-2-support/}}).

Client-side

No balancer in the path: the client's channel learns every backend address (from DNS or a control plane) and picks per call itself, with a policy. gRPC ships pick_first (the default) and round_robin, plus xDS policies ({{gRPC load balancing doc|https://github.com/grpc/grpc/blob/master/doc/load-balancing.md}}).

Two rows surprise people. The L4 balancer did its job perfectly: it balanced connections, and there was one. And a client that was given all three addresses still sent everything to backend-1, because the default policy, pick_first, "attempts to connect to those addresses one at a time, in order, until it finds one that is reachable" and then sends all calls there (gRPC load balancing doc). Client-side balancing needs round_robin (or an xDS policy) asked for explicitly, in code or in the service config.

What to do, in order of preference

  1. An L7 proxy that speaks HTTP/2 in front of the replicas (Envoy, nginx grpc_pass, a mesh such as Istio or Linkerd, a cloud L7 balancer with HTTP/2 to the targets). Costs: one more hop and its latency, and the proxy itself must be run and scaled.
  2. Client-side round_robin over every replica address: in Kubernetes a headless Service (clusterIP: None) makes DNS return one A or AAAA record per Pod instead of a virtual IP ({{Kubernetes Services|https://kubernetes.io/docs/concepts/services-networking/service/}}), and the channel target dns:///name resolves them all. Costs: every client holds a connection to every replica, and new Pods are seen only when the client resolves again. The fixed-list run above is the extreme case: it never saw backend-3.
  3. Proxyless xDS: the client gets endpoints, weights and policies from a control plane (as Envoy does), without a proxy in the data path. Most capable, most moving parts.
  4. An L4 balancer plus MAX_CONNECTION_AGE when nothing else is possible: crude, but it bounds how long imbalance lasts. Costs: periodic reconnects (a TCP and maybe TLS handshake each), so do not set it to seconds in production; minutes is typical.

Kubernetes' default (a ClusterIP Service) is L4: in iptables mode kube-proxy picks a backend Pod "at random" for each new connection ({{Kubernetes virtual IPs|https://kubernetes.io/docs/reference/networking/virtual-ips/}}). So a gRPC client of a plain Service behaves like the L4 rows above.

Balancing LLM calls is different

For ordinary services, spreading calls evenly is the goal. LLM calls differ in cost by orders of magnitude (a 50-token chat turn against a 100,000-token document), and a replica that already holds a conversation's prefix in its KV cache can skip most of the prefill. So the router wants to read the request and know each replica's state: queue depth, KV-cache contents, loaded LoRA adapters. That is L7 by definition, and it is where Kubernetes is heading:

  • Gateway API Inference Extension (an official Kubernetes project, v1.6.2 on 17 September 2026): turns any gateway that supports Envoy's external processing into an "inference gateway". An Endpoint Picker chooses the replica for each request from model-server metrics such as prefix-cache status and LoRA adapter availability ({{project README|https://github.com/kubernetes-sigs/gateway-api-inference-extension}}). The picker's main implementation has moved to the llm-d project's router.
  • The side channel is gRPC. Envoy asks the picker over ExternalProcessor.Process, a bidirectional gRPC stream (rpc Process(stream ProcessingRequest) returns (stream ProcessingResponse) in Envoy's {{ext_proc API|https://github.com/envoyproxy/envoy/blob/v1.39.2/api/envoy/service/ext_proc/v3/external_processor.proto}}).
  • llm-d (v0.10.0, 29 September 2026) packages prefix-cache-aware and load-aware routing with vLLM, and reports "3x higher output throughput and 2x faster TTFT" against round robin on Llama 3.1 70B with 4 AMD MI300X ({{llm-d README|https://github.com/llm-d/llm-d}}; a project-reported figure, not reproduced here).

Sometimes you want the pinning. NVIDIA Triton recommends unary inference calls, but notes that a bidirectional gRPC stream "will hold a single connection throughout the lifetime and hence ensure the requests are delivered to the same Triton instance" behind a load balancer, which sequence models need ({{Triton inference protocols|https://github.com/triton-inference-server/server/blob/main/docs/customization_guide/inference_protocols.md}}).
