5. Rate limits and quotas at the API

A rate limit caps what one caller may use per unit of time, so one runaway script cannot take capacity from everyone; for LLM APIs it is counted in tokens as well as requests, because a 100,000-token prompt and a 50-token one are not the same load. How the server counts (token bucket, sliding window) is {{Reliability engineering|n:3ef5c17b0d0d8152b8dececf34196174}}'s; budgets across many providers at a gateway are {{Gateways and routing|n:3f15c17b0d0d81e4a964c129a3e520ae}}'s. What this page owns is the contract with the client: what the API says before, at and after the limit.

Header names from the {{Claude API rate limits|https://platform.claude.com/docs/en/api/rate-limits}} page and the IETF {{RateLimit header fields draft|https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/}} (draft-11, 2026-05-23, an active draft, not an RFC: quota 5 per 5-second window, 4 remaining, resets in 0 s); values illustrative. OpenAI sends the same information as x-ratelimit-remaining-requests, x-ratelimit-remaining-tokens and their reset times.

  • At the wall: 429 Too Many Requests (RFC 6585) with Retry-After in seconds or as an HTTP date (RFC 9110). A well-behaved client waits that long; the official SDKs honour it automatically. In gRPC the same signal is RESOURCE_EXHAUSTED, with the wait in a RetryInfo detail or the grpc-retry-pushback-ms trailer (section 11).
  • Before the wall: remaining-budget headers on every response let a client slow down before it is refused, which is cheaper for both sides than a 429 and a retry.
  • A quota is not a rate limit. "1,000 messages a month" or a spend cap will not clear by waiting a second, so say so in the error type and omit retry-after: Anthropic's spend-cap 429 has the same error type as a rate limit but no retry-after, and tells itself apart with error.details.error_code enforced_spend_limit_reached; "Retrying, including the SDK's automatic retries, fails until access resumes" (rate-limits page, read 2026-10-24).
  • Limit before expensive work, and before the idempotency layer. Stripe notes that "rate limiters run before the API's idempotency layer" ({{Stripe, advanced error handling|https://docs.stripe.com/error-low-level}}), so a 429 is not stored against the key and the retry gets a fresh chance.
  • Limit per key, per model, per dimension. Anthropic publishes separate limits for requests, input tokens and output tokens per minute, per model (same rate-limits page); a client that only counts requests will be surprised by the token limit. What counts is a design decision with consequences: on most Claude models only uncached input tokens count toward input tokens per minute, and max_tokens "does not factor into OTPM rate limit calculations", so prompt caching raises effective throughput and a large max_tokens costs nothing against the limit. The server counts with a token bucket, so capacity refills continuously rather than at fixed intervals.

6. Webhooks: your API, called in reverse

Some events happen later: a batch finishes, a payment clears, a moderation review completes. Clients could poll; a webhook turns it around: the client registers a URL and your server POSTs to it when the event happens. Now you are the client, calling code you do not control, over a network that fails, so everything from sections 2 to 5 applies with the roles swapped. Step through one delivery that goes wrong in the usual way:

At-least-once delivery: sign, retry with backoff, and let the receiver dedupe on the event id

Header names and the signed string follow the {{Standard Webhooks spec|https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md}}; retry timings follow its suggested schedule; ids and times illustrative.

  • Sign every delivery with an HMAC-SHA256 over the id, a timestamp and the exact body, using a secret shared with that receiver: Standard Webhooks signs msg_id.timestamp.payload and sends webhook-id, webhook-timestamp and webhook-signature: v1,<base64>; Stripe signs timestamp.payload into Stripe-Signature: t=...,v1=... ({{Stripe webhooks|https://docs.stripe.com/webhooks}}). Receivers verify against the raw bytes before parsing (re-serialised JSON changes spacing and key order), compare in constant time, and reject old timestamps to stop replays: Stripe's libraries default to "a default tolerance of 5 minutes".
  • Retry with backoff, for days. Stripe retries "for up to three days with an exponential back off in live mode"; Standard Webhooks suggests immediately, 5 seconds, 5 minutes, 30 minutes, and on up to 24 hours. Then mark the endpoint failing and let the user redeliver.
  • Expect duplicates and disorder. Delivery is at-least-once, so "Use the webhook-id header as an idempotency key"; Stripe "doesn't guarantee the delivery of events in the order that they're generated", so receivers fetch current state rather than trust event order.
  • Receivers answer 2xx fast and work later: put the event on a queue ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}). Thin events carry only the type and ids, and the receiver fetches the object, so it always gets current data and no personal data travels in the webhook; Stripe now offers both "thin" and "snapshot" events.

How webhooks compare with SSE, WebSockets and polling as ways to push news to a client is {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}'s; this section owns the API design of one.
