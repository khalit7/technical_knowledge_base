3. Protobuf: the bytes inside every gRPC call

The problem. JSON spells out every field name in every message ("max_tokens":16 is 15 bytes to say "16"), stores numbers as text that must be parsed digit by digit, and has no schema, so a typo in a field name is silently ignored. Between your own services, sending millions of messages a second, that costs CPU and bandwidth and hides bugs. Protocol Buffers (protobuf) fix all three: a schema both sides compile, and a binary encoding that sends field numbers and compact values.

The schema. This is the lab's llm.proto, the running request as a message (the full file is in the page's src/lab/):

message GenerateRequest {
  string model = 1;
  repeated Message messages = 2;
  uint32 max_tokens = 3;
  bool stream = 4;
}
service Inference {
  rpc Generate(GenerateRequest) returns (stream Token);  // server streaming
}

The numbers after = are the field numbers. They, not the names, are the contract: names never travel on the wire. protoc turns this file into classes and stubs for each language.

How a message becomes bytes

Every field is written as a tag then a value. The tag is one number, (field_number << 3) | wire_type, where the wire type says how to find the value's end: 0 VARINT (integers, booleans, enums), 2 LEN (a length then that many bytes: strings, bytes, nested messages, packed lists), 1 and 5 for fixed 8- and 4-byte values ({{protobuf encoding guide|https://protobuf.dev/programming-guides/encoding/}}). Numbers are varints: 7 bits per byte, low group first, the top bit set on every byte except the last. So 150 is 96 01: 150 is 1 0010110 in binary; the low 7 bits 0010110 go first with the "more" bit set (0x96), then the remaining 1 (0x01). Try any number:

The savings are the names ("max_tokens": becomes the single tag byte 18), the quotes and braces, and the number 16 as one byte instead of two characters. Strings cost the same in both: "What colour is the sky?" is 23 bytes either way, which is why protobuf's win on chat text is modest and its win on numbers (token ids, logits, embeddings) is large. Each streamed token is a 5-to-9-byte message (" sky" at index 1 is 0a 04 20 73 6b 79 10 01).

Three encoding details that bite

  • Negative numbers. An int32 of -1 is sign-extended to 64 bits and costs 10 bytes; the sint32 type uses zigzag (-1 becomes 1, 1 becomes 2) and costs 1. Measured: against . Use sint32/sint64 for fields that are often negative.
  • Packed lists. In proto3, repeated numbers are packed by default: one tag and a length for the whole list. Five token ids took bytes packed against one tag per element.
  • Field numbers 1 to 15 cost one tag byte, 16 to 2047 two; give them to the fields you send most. Valid numbers run from 1 to 536,870,911, with 19,000 to 19,999 reserved ({{proto3 guide|https://protobuf.dev/programming-guides/proto3/}}).

Schema evolution: why the numbers are sacred

Services are deployed one at a time, so for a while a new writer talks to an old reader. Protobuf's rule is that a reader keeps fields it does not know as unknown fields and carries on. The lab tested three changes against the old GenerateRequest reader (measured):

The failure is silent

Reusing a number does not raise an error. With the same wire type the old reader reads your new priority = 9 as max_tokens = 9 and generates nine tokens; with a different wire type it quietly drops the field and max_tokens falls back to its default, 0. The fix is a habit: when you delete a field, write reserved 3; reserved "max_tokens"; so the compiler refuses to reuse it ({{protobuf best practices|https://protobuf.dev/best-practices/dos-donts/}}: "Never re-use a tag number").

Against a JSON list of numbers, protobuf wins by about five times in size and far more in time. Against base64 inside JSON the size gap is only 4/3 (base64's fixed overhead: against bytes); the bigger win is skipping the text decode. Triton accepts raw binary tensors over plain HTTP for the same reason (its "binary tensor data extension", section 12). Decode times for protobuf are parse-only; turning the values into Python objects costs extra in every format.
