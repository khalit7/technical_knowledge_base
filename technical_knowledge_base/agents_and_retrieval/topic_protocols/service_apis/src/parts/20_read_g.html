6. Status codes, errors and retries

The problem. When a call fails, the caller must decide in microseconds: give up, retry here, retry elsewhere, or tell the user something specific. HTTP's status codes were designed for documents; gRPC defines 17 codes designed for that decision ({{gRPC status codes|https://grpc.io/docs/guides/status-codes/}}). The number travels in the grpc-status trailer; the HTTP status stays 200.

And UNAVAILABLE to a closed port came back in about 1 ms: by default a call fails fast when the channel cannot connect, unless you ask for wait_for_ready=True ({{wait-for-ready guide|https://grpc.io/docs/guides/wait-for-ready/}}).

Retries: off by default, on by configuration

gRPC retries in two ways ({{gRPC retry design A6|https://github.com/grpc/proposal/blob/master/A6-client-retries.md}}):

  • Transparent retries, always on: when the call never left the client, or reached the server but never reached your handler, the library retries by itself, because nothing can have happened twice.
  • A retry policy, only if the service config (a JSON document given to the channel, or published by the name resolver) has one: which status codes to retry, up to how many attempts (values above 5 are treated as 5), with exponential backoff and plus or minus 20% jitter. The deadline covers all attempts. Each retry carries grpc-previous-rpc-attempts so the server can see it.
{"methodConfig": [{"name": [{"service": "llm.v1.Inference", "method": "Who"}],
  "retryPolicy": {"maxAttempts": 4, "initialBackoff": "0.1s", "maxBackoff": "1s",
                  "backoffMultiplier": 2, "retryableStatusCodes": ["UNAVAILABLE"]}}]}

Measured against a replica that answers UNAVAILABLE twice while "warming up": without the policy the call failed at once; with it, the server log shows three attempts , and the caller saw only success. Two safety valves stop retries from becoming a storm: retry throttling (a per-server token bucket; with "maxTokens": 10, "tokenRatio": 0.1 each failure costs a token, each success returns 0.1, and retries stop while the count is at or below half) and server pushback (the server's grpc-retry-pushback-ms trailer says when to retry, or a negative value says never). Hedging is the aggressive cousin: send a second copy after a delay without waiting for the first to fail, for idempotent calls with long tails; Go and C-core did not implement hedging when the design was last updated (2024-08-23).

Correction to the old page
The old page said "only UNAVAILABLE-class errors are safely retryable by default". By default no application-level retry happens at all; only the transparent retries above. Which codes are safe depends on whether the method is idempotent, and gRPC's own docs say there is "no fixed list of status codes on which it is appropriate to retry in all applications". UNAVAILABLE is the usual choice because it normally means the request was not processed; DEADLINE_EXCEEDED is the dangerous one, since it "may be returned even if the operation has completed successfully".

Richer errors. A code and a string are often not enough ("which field?", "retry after how long?"). The spec reserves the trailer grpc-status-details-bin for a serialised google.rpc.Status carrying typed details such as BadRequest or RetryInfo ({{Google's error model, AIP-193|https://google.aip.dev/193}}).
