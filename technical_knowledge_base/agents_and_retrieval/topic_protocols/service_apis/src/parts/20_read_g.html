9. gRPC on the wire

Protobuf gives bytes; a call also needs a method name, a deadline, credentials, streams both ways and an outcome, over connections that stay open for hours. gRPC (open-sourced by Google in 2015 from its internal Stubby) maps every call onto one HTTP/2 stream ({{gRPC over HTTP/2 spec|https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md}}); HTTP/2 frames and HPACK themselves are {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}}'s. The lab ran the running request through a logging proxy that decodes every HTTP/2 frame (no packet capture: the proxy sits on the socket between grpcio client and server), asking for 5 tokens with a 2-second deadline. measured 5 October 2026 by src/lab/frame_proxy.py: times are milliseconds since the TCP connection opened, as the proxy saw them (the two directions are read by two threads, so frames crossing within a fraction of a millisecond may print slightly out of order); bytes are exact; protobuf inside DATA frames is decoded with llm.proto.

Four things in that stream are gRPC's own:

  1. The method is the path: :path /llm.v1.Inference/Generate is /package.Service/Method, always a POST, so proxies can route on it like any URL.
  2. te: trailers and content-type: application/grpc: the first tells proxies the client understands trailers; the spec uses it "to detect incompatible proxies". A server sent a non-gRPC content type should answer 415.
  3. A 5-byte prefix on every message: the request DATA frame is 00 00 00 00 31 then the 49 bytes of section 8 (one byte "compressed?", four bytes of length, 0x31 = 49). Each token arrives the same way, 10 to 14 bytes in all. Frame boundaries need not match message boundaries, so readers parse by prefixes, never by frames.
  4. The outcome comes last: HTTP status is 200 even for failures; the real result is the trailer grpc-status (0 = OK) with grpc-message. A call that fails before any message gets one trailers-only HEADERS frame: the call to a missing method came back as :status 200, grpc-status 12, grpc-message Method not found! in a single frame.

The rest is HTTP/2 housekeeping: SETTINGS (both sides advertised 4 MB windows and frame size), WINDOW_UPDATE, and PINGs that gRPC sends to estimate the bandwidth-delay product and grow its windows (BDP probing). Against the root page's REST and SSE recording of the same request:

Four call shapes, one stream each: unary (most calls), server streaming (the token stream above), client streaming (audio chunks in, one transcript out) and bidirectional (realtime voice, Triton's sequence models, Envoy talking to an external processor). The shape only changes how many prefixed messages each side sends before closing its half; HTTP/1.1 cannot carry both bodies at once or trailers every client honours, hence HTTP/2.

Channels. Client code makes a channel to a target and a stub on it; the channel resolves the name, opens one connection per backend address (a subchannel), keeps them alive, reconnects with backoff, and multiplexes every call as a new stream. A channel is expensive (TCP, maybe TLS, SETTINGS) and a call cheap: one channel per target, shared, never one per call ({{performance guide|https://grpc.io/docs/guides/performance/}}); its hours-long connection is what confuses load balancers (section 13). Credentials, logging and tracing go in interceptors, gRPC's middleware.

10. Deadlines and cancellation: giving up together

The user closes the tab after the ninth token. The front door notices; behind it, the router and the inference server do not, and the GPU keeps decoding an answer nobody will read, while abandoned work queues ahead of live work. Every hop needs two facts: how long the caller will wait, and whether it is still there. In gRPC the caller sets a deadline; it travels as a relative timeout in grpc-timeout (at most 8 digits plus a unit, H M S m u n), and each hop subtracts the time already spent before passing it on, so no clocks need to agree ({{deadlines guide|https://grpc.io/docs/guides/deadlines/}}). When it passes, both ends end the call with DEADLINE_EXCEEDED and the client sends RST_STREAM with code CANCEL (8); cancellation for any other reason uses the same frame.

The default is "wait forever"

"By default, gRPC does not set a deadline which means it is possible for a client to end up waiting for a response effectively forever." Propagation "is supported by some gRPC implementations": on by default in Java and Go when you pass the incoming context on, opt-in in C++, and in Python you do it yourself (timeout=ctx.time_remaining()). Stopping the work is the server's job: "The server application is responsible for stopping any activity it has spawned to service the RPC."

The lab chained client, gateway and inference service (three processes, real gRPC, a frame log on the second hop). The inference service emits up to 40 tokens, the first after 0.12 s then one every 0.05 s, so a full answer takes about 2.1 s; in every run the client stops after 0.6 s. Depth: why run B was rescued by accident

No grpc-timeout reached the inference service in run B, yet it stopped early: when the client left, gRPC Python closed the gateway's generator, CPython freed the abandoned downstream call object at once, and freeing it cancelled the stream (the frame log shows the gateway's RST_STREAM CANCEL). Change the code shape, as run D does with a worker thread, and the rescue disappears.

Choosing the number. Start from what the caller will tolerate (a chat UI with a 60-second spinner sets about 60 s at the front door) and let each hop inherit what is left; gRPC suggests an educated guess "validated by some load testing". A deadline covers queueing as well as work (the root's Failure lab case "Max concurrent streams: calls queue on the connection" shows calls failing at 2.5 s that the server never saw fail); retries share it (section 11); and a streamed generation needs a deadline sized for the whole stream, or an idle timer instead (HTTP's Timeout chain tab plays that out for HTTP hops). With HTTP there is no deadline header: each hop sets its own timeout, cancellation is the connection closing, and the server must notice (details below).
