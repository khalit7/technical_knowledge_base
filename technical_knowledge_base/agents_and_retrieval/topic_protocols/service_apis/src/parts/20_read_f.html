8. Protobuf: the bytes inside every gRPC call

JSON spells out every field name in every message ("max_tokens":16 is 15 bytes to say "16"), stores numbers as text, and has no schema, so a typo in a field name is silently ignored. Between your own services, millions of times a second, that costs CPU and bandwidth and hides bugs. Protocol Buffers fix all three: a schema both sides compile, and a binary encoding that sends field numbers and compact values. The running request as the lab's llm.proto (in src/lab/):

message GenerateRequest {
  string model = 1;
  repeated Message messages = 2;
  uint32 max_tokens = 3;
  bool stream = 4;
}
service Inference {
  rpc Generate(GenerateRequest) returns (stream Token);  // server streaming
}

The numbers after = are the contract; protoc turns the file into classes and stubs for each language. On the wire every field is a tag, (field_number << 3) | wire_type, then a value; the wire type says how to find the value's end: 0 VARINT (integers, booleans, enums), 2 LEN (a length, then bytes: strings, nested messages, packed lists), 1 and 5 for fixed 8- and 4-byte values ({{encoding guide|https://protobuf.dev/programming-guides/encoding/}}). A varint is 7 bits per byte, low group first, the top bit set on every byte but the last: 150 is 1 0010110 in binary, so 0x96 (low 7 bits plus "more") then 0x01, written 96 01. Type a number:

The saving is names ("max_tokens": becomes the one tag byte 18), quotes and braces; strings cost the same in both ("What colour is the sky?" is 23 bytes either way), which is why protobuf's win on chat text is modest and its win on numbers (token ids, logits, embeddings) large. Schema evolution: why the numbers are sacred

Services deploy one at a time, so for a while a new writer talks to an old reader. A reader keeps fields it does not know as unknown fields and carries on. The lab tried three changes against the old reader (measured):

The failure is silent

Reusing a number raises no error. With the same wire type the old reader reads your new priority = 9 as max_tokens = 9 and generates nine tokens; with a different wire type it drops the field and max_tokens falls back to its default, 0. The fix is a habit: when you delete a field, write reserved 3; reserved "max_tokens"; so the compiler refuses to reuse it ({{protobuf best practices|https://protobuf.dev/best-practices/dos-donts/}}: "Never re-use a tag number"), and run a breaking-change check such as buf breaking in CI (section 3).

Depth: zigzag, packed lists, field-number ranges, ProtoJSON, and tensors in four formats
  • Negative numbers. An int32 of -1 is sign-extended to 64 bits and costs 10 bytes; sint32 uses zigzag (-1 becomes 1, 1 becomes 2) and costs 1. Measured: against . Use sint32/sint64 for fields that are often negative.
  • Packed lists. In proto3, repeated numbers are packed by default: one tag and a length for the whole list. Five token ids took bytes packed against with one tag per element.
  • Field numbers 1 to 15 cost one tag byte, 16 to 2047 two; give them to the fields you send most. Valid numbers run from 1 to 536,870,911, with 19,000 to 19,999 reserved ({{proto3 guide|https://protobuf.dev/programming-guides/proto3/}}).
  • ProtoJSON, the canonical JSON form gateways and logs use, turns the running request into : field names become lowerCamelCase (maxTokens; {{ProtoJSON format|https://protobuf.dev/programming-guides/json/}}), a frequent surprise when a REST gateway fronts a gRPC service.

Correction to the old page
Against a JSON list of numbers, protobuf wins by about five times in size and far more in time. Against base64 inside JSON the size gap is only 4/3 (base64's fixed overhead: against bytes); the bigger win is skipping the text decode. Triton accepts raw binary tensors over plain HTTP for the same reason (its binary tensor data extension, section 17). Protobuf decode times are parse-only; turning values into Python objects costs extra in every format.
