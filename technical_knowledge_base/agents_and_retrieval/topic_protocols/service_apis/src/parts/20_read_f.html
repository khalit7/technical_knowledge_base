5. Deadlines and cancellation: giving up together

The problem. The user closes the chat tab after the ninth token. The front door notices (its connection closed), but behind it the router and the inference server do not, and the GPU keeps decoding an answer nobody will read. At GPU prices this is real money, and under load it is worse: abandoned work queues ahead of live work. Every hop needs to know two things: how long the caller will wait, and whether the caller is still there.

How gRPC does it. The caller sets a deadline, a point in time after which it no longer wants the answer. On the wire it travels as a relative timeout in the grpc-timeout header, an integer of at most 8 digits plus a unit (H M S m u n: hours down to nanoseconds); each hop subtracts the time already spent before passing it on, which avoids trusting other machines' clocks ({{deadlines guide|https://grpc.io/docs/guides/deadlines/}}). When the deadline passes, both ends end the call with DEADLINE_EXCEEDED and the client sends an HTTP/2 RST_STREAM with code CANCEL (8). Cancellation, the second signal, uses the same RST_STREAM when the client gives up for any other reason.

The default is "wait forever"

"By default, gRPC does not set a deadline which means it is possible for a client to end up waiting for a response effectively forever" (gRPC deadlines guide). Propagation to downstream calls "is supported by some gRPC implementations": enabled by default in Java and Go when you pass the incoming context on, opt-in in C++, and in Python you do it yourself (timeout=ctx.time_remaining()). And stopping the work is the server's job: "The server application is responsible for stopping any activity it has spawned to service the RPC."

Choosing the number

Start from what the caller will tolerate, not from what the server needs: a chat UI that shows a spinner for 60 seconds sets about 60 s at the front door, and each hop inherits what is left. gRPC's guide suggests an educated guess "validated by some load testing". Three rules: a deadline covers queueing as well as work (the root's Failure lab case "Max concurrent streams: calls queue on the connection" shows calls failing at 2.5 s that the server never saw fail); retries do not get a fresh deadline (the deadline "applies across all attempts", {{gRPC retry design A6|https://github.com/grpc/proposal/blob/master/A6-client-retries.md}}); and streaming generations need a deadline sized for the whole stream, or an idle timer instead (the {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} page's Timeout chain tab plays that out for HTTP hops).

With HTTP instead of gRPC there is no deadline header: each hop has its own timeouts, and cancellation is the connection or stream closing. The equivalent discipline is a timeout on every outgoing call and a server that stops work when its incoming request is gone. vLLM's OpenAI-compatible server shows how in Python: its with_cancellation decorator races the handler against the ASGI http.disconnect message and cancels the handler when the client leaves; its comment notes that the simpler request.is_disconnected "does not work with middleware" ({{vLLM v0.31.0, api_utils.py|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/serve/utils/api_utils.py}}).
