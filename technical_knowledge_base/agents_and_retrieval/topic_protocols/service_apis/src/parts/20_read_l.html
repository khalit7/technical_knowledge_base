11. JSON-RPC 2.0: the smallest call format

The problem it solves. Sometimes you need named method calls over a channel that is not HTTP at all: a pipe to a child process (an MCP server on stdio, a language server in your editor), a WebSocket, or a single HTTP endpoint. JSON-RPC 2.0 is the whole answer in a few pages: "a stateless, light-weight remote procedure call (RPC) protocol", "transport agnostic" ({{JSON-RPC 2.0 specification|https://www.jsonrpc.org/specification}}, 2010, updated 2013).

Request
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"city": "Paris"}}}
Response (same id)
{"jsonrpc": "2.0", "id": 1, "result": {...}}
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32601, "message": "Method not found"}}
  • The id pairs answers with requests, so many calls can be in flight on one channel and answers may come back in any order.
  • A notification is a request with no id: the receiver must not answer. Use it for events ("progress 40%") where a reply would be noise.
  • Batches: an array of requests, answered by an array of responses (none for notifications).
  • Reserved error codes: -32700 parse error, -32600 invalid request, -32601 method not found, -32602 invalid params, -32603 internal error, -32000 to -32099 for the server implementation; everything else is yours.

What it leaves out is the point: no schema, no streaming, no deadlines, no transport rules, no auth. A protocol that adopts JSON-RPC must add those, and that is most of what the MCP and A2A specifications are. MCP defines its methods (tools/call, resources/read), its transports (stdio, Streamable HTTP) and its auth on top; it allowed JSON-RPC batches in its 2025-03-26 revision and removed them in 2025-06-18 ({{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}} page, section on revisions).

Correction carried from the root
The old page said agent protocols "chose JSON-RPC over HTTP (+SSE) rather than gRPC". True of MCP. A2A v1.0 separates the protocol from three bindings: JSON-RPC 2.0, gRPC and HTTP+JSON/REST (root {{Protocol atlas|n:3c65c17b0d0d81ec9355f4eecd6eed02}}, corrections list, item 3; {{A2A v1.0.1 specification|https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md}}).

Choosing between JSON-RPC and gRPC for a new internal protocol: JSON-RPC when the other end is a model or an editor plugin, messages are few, humans read the logs, and the channel may be stdio; gRPC when calls are many, typed, streaming, and cross-language teams need generated clients.
