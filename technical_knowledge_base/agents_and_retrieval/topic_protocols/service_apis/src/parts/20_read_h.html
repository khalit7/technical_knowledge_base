7. Connections: keepalive, limits, health and reflection

The problem. A gRPC channel keeps its connections for hours. In that time a NAT box or cloud load balancer may silently drop an idle connection, a server may be draining for a deploy, a slow call may hold a stream, and a big message may exceed a limit. These settings decide which of those you notice, and how.

Keepalive pings, and the GOAWAY that answers too many

A keepalive is an HTTP/2 PING sent on a quiet connection; if no ACK comes back within a timeout (20 s by default) the connection is declared dead and calls fail with UNAVAILABLE instead of hanging. Client keepalive is off by default in gRPC core. Servers defend themselves against ping floods: by default they expect at least 5 minutes between pings on a connection that carries no data, and after 2 "strikes" they send GOAWAY with error ENHANCE_YOUR_CALM and close it ({{gRPC core keepalive guide|https://github.com/grpc/grpc/blob/master/doc/keepalive.md}}).

The lab reproduced it: a client set grpc.keepalive_time_ms=1000 and made a call whose first token takes 8 s, so the connection carried no data for 8 s. On the first try nothing happened: the client's own brake (max_pings_without_data, default 2) stopped it after two pings. With that brake removed the server cut the connection mid-call:

The client saw UNAVAILABLE: Too many pings and the in-flight call was lost. This is not a lab curiosity. vLLM's gRPC server (v0.31.0) carries exactly this fix, with the comment that client keepalive and BDP-probe pings arriving while a non-streaming Generate is decoding "are strikes and eventually earn a GOAWAY(ENHANCE_YOUR_CALM, "too_many_pings") that fails every in-flight RPC", so it sets grpc.http2.max_ping_strikes to 0 ({{vLLM v0.31.0, grpc_server.py|https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/launchers/grpc_server.py}}). The rule: client keepalive must be slower than the server's minimum ping interval, or the server must be told to accept faster pings.

Misspelt options are ignored silently

The same vLLM file records a second trap: an option name that "expands to a string with no "recv"" was misspelt, "and gRPC Core silently ignores unknown keys, so the misspelt form left the 300s default in force". Channel arguments are plain strings; check them against the {{core channel argument list|https://grpc.github.io/grpc/core/group__grpc__arg__keys.html}} and test that the behaviour actually changed.

GOAWAY, connection age and draining

GOAWAY is HTTP/2's "no new streams on this connection": it names the last stream the server accepted, so the client knows which calls are safe to resend elsewhere, and finishes the rest. Servers send it when shutting down, and on a timer if configured: gRPC's server-side connection management adds MAX_CONNECTION_IDLE, MAX_CONNECTION_AGE (with plus or minus 10% jitter so clients do not all reconnect at once) and MAX_CONNECTION_AGE_GRACE, all infinite by default ({{gRPC proposal A9|https://github.com/grpc/proposal/blob/master/A9-server-side-conn-mgt.md}}). Its stated purpose includes making L4 load balancers work: "This option can force the client to periodically reconnect to a L4 LB which allows spreading load more quickly." Section 8 measures that.

Limits that shape latency

  • Message size: 4 MiB received by default (measured in section 6); sending is unlimited by default in gRPC core.
  • Concurrent streams: a server can cap streams per connection with HTTP/2's SETTINGS_MAX_CONCURRENT_STREAMS; calls beyond it queue on the client. The root's Failure lab reproduced it ("Max concurrent streams: calls queue on the connection": six 1-second calls finishing at 1, 2 and 3 s in pairs with a limit of 2). Fix with more connections (a channel pool) or more replicas.
  • Flow-control windows: the recorded SETTINGS show 4 MB windows, grown further by BDP probing; on long links one stream's throughput is window divided by round-trip time ({{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}).

Health checking and reflection

gRPC standardises two services every server should offer. Health (grpc.health.v1.Health/Check, answering SERVING or NOT_SERVING, optionally per service) is what balancers and Kubernetes probe; Kubernetes has had native gRPC liveness probes since v1.27, stable ({{Kubernetes probes docs|https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/}}). The recorded check answered the two bytes 08 01: field 1 = 1, SERVING.
