10. GraphQL: the client chooses the shape

The problem it solves. A model-catalogue page on the web shows each model's name and provider; the mobile app also shows eval scores; an internal tool wants licences. With REST you either make one call per object (the page above would need one request for the list and one per provider) or build a bloated endpoint for each screen. GraphQL (created at Facebook, now a Linux Foundation specification; current edition September 2025, per the root's atlas) gives one endpoint and a typed schema, and lets each client send a query naming exactly the fields it wants:

{ models(first: 20) { name provider { name } } }

The server runs a resolver function per field and returns JSON of exactly that shape. On the toy catalogue in this lab (20 made-up models, 12 fields each) a REST list returning every field is bytes; asking GraphQL for names only is .

Cost 1: one query, many backend calls (N+1)

Resolvers run per object, so a list of 20 models whose provider resolver queries the database makes 1 query for the list plus 20 for providers: the N+1 problem. The fix is a DataLoader: resolvers ask a loader for a key, the loader waits one tick of the event loop, then fetches every requested key in one batched call. Cost 2: one query can ask for the world

Nesting multiplies. A query for 3 models, each with 3 similar models, nested deeper, grows by 3 per level; with first: 20 and first: 10 five levels deep, the lab's static estimate (multiply each list's first down the tree, before running anything) came to fields:

Public GraphQL APIs therefore price queries before running them. GitHub's API (the best-known public one) caps a call at 500,000 nodes, requires first or last between 1 and 100 on every connection, charges a computed number of points against 5,000 points per hour per user, allows no more than 2,000 points per minute, and stops any request after 10 seconds ({{GitHub GraphQL limits|https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api}}). Other defences: depth limits, and persisted queries (the server accepts only queries registered in advance, referenced by hash).

Cost 3: HTTP stops helping

  • Caching. Queries usually travel as POST, which HTTP caches ignore. The GraphQL-over-HTTP draft allows GET for queries (never mutations: the server "MUST respond with an appropriate 4xx", 405 recommended) and RFC 10008's QUERY method now offers a cacheable request with a body.
  • Status codes. A field can fail while the rest succeeds. In the lab one resolver failed and the result carried data with null in that field plus an errors array naming its path:


Classic servers answer 200 with that body, so monitoring that counts HTTP 5xx sees nothing. The GraphQL-over-HTTP working draft fixes this for clients that send Accept: application/graphql-response+json: 400 for a document that does not parse, 422 for one that fails validation ({{GraphQL over HTTP draft|https://graphql.github.io/graphql-over-http/draft/}}, read 5 October 2026). Alert on the errors array, not only on status codes.


Where it fits in ML work. You will mostly consume GraphQL (GitHub's API from tooling and agents) rather than serve it; it is rarely right for model serving, where the request shape is fixed and the cost is in the GPU, not in fetching fields.
