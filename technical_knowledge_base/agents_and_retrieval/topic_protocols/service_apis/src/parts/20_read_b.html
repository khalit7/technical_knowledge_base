1. What an API style decides

The problem. Two programs, often written by different teams in different languages, must agree on five things before one can call the other: what the request and answer contain, how those are turned into bytes, how the bytes travel, what happens when something fails, and who is allowed to call. An "API style" is a bundle of answers to those questions. Name the five and every style on this page becomes a comparison along them.

RPC (remote procedure call) is the idea that calling a function on another machine should look like calling a local one: stub.Generate(request). The stub (or client) is generated code that turns that call into bytes on the network; the server side has a matching servicer you fill in. The idea is decades old and so is its trap: a network call can be slow, half-done or lost in ways a local call never is, so every RPC system adds timeouts, error codes and retries. REST takes the other road: instead of named functions it exposes named things (resources) and a fixed set of verbs, and lets HTTP's existing meaning (safe, idempotent, cacheable) do the work.

Two more words used throughout. A call is idempotent when doing it twice has the same effect as once (reading a model's metadata, setting a field to a value); generating text and charging for it is not. And a replica is one copy of a service; spreading calls over replicas is load balancing (section 8).
