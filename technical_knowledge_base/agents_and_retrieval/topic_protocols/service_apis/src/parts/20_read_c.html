2. REST: the front door's style

The problem it solves. A public LLM API is called by curl, by Python and TypeScript SDKs, by browsers, by no-code tools, through corporate proxies you have never seen. The only thing they all share is HTTP. REST says: use HTTP's own vocabulary and nothing else, and every one of those clients already knows how to call you.

What REST actually is. Not a protocol and not a spec: an architectural style Roy Fielding described in chapter 5 of his 2000 dissertation to explain why the web scaled ({{Fielding, chapter 5|https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm}}). Its constraints, each with the property it buys:

  • Resources, not functions. Anything nameable gets a URL (/v1/models/claude-x); you transfer representations of it (JSON) rather than calling a procedure.
  • A uniform interface. A small fixed set of verbs with universal meaning: GET is safe and cacheable, PUT and DELETE are idempotent, POST is neither. This, not JSON, is the deepest difference from RPC: every intermediary knows what a GET may do.
  • Statelessness. Each request carries everything needed (the API key, the full conversation); the server keeps no session between requests, which is what lets any replica answer any request.
  • Cacheable and layered. Because meaning is visible in the method and headers, proxies and caches can sit in between without understanding your app.
  • Hypermedia (HATEOAS: responses carry links to the next actions). The least followed constraint; the human web of HTML links and forms is its one mass deployment.

REST as practised is resource-shaped HTTP with JSON, not Fielding-complete REST; "HTTP API" is the honest name. Martin Fowler's write-up of Leonard Richardson's maturity levels is the usual yardstick ({{Fowler, 2010|https://martinfowler.com/articles/richardsonMaturityModel.html}}): level 0 is one endpoint taking POSTs (RPC in JSON), level 1 adds resources with their own URLs, level 2 uses the HTTP verbs and status codes properly, level 3 adds hypermedia links. Level 2 is where almost every good API stops. The running request is level 2 with one twist: POST /v1/messages creates nothing you can GET later; it is really a function call wearing a resource's URL, which is fine. For actions that are not create, read, update or delete, Google's API rules use a :verb suffix on the resource, such as POST /v1/{name=publishers/*/books/*}:archive ({{AIP-136|https://google.aip.dev/136}}).

Long-running work

When a call takes minutes, answer at once with a handle to poll: Google returns an Operation resource ({{AIP-151|https://google.aip.dev/151}}); plain HTTP says 202 Accepted (accepted, not done). Anthropic's Message Batches API is this pattern: a batch starts in_progress, you poll until ended, results stay for 29 days ({{Claude docs, batch processing|https://docs.claude.com/en/docs/build-with-claude/batch-processing}}).

Describing it: OpenAPI

A machine-readable list of paths, parameters, schemas and auth schemes, from which docs, SDKs and tests are generated. Current version 3.2.1 (10 September 2026; the root's {{Protocol atlas|n:3c65c17b0d0d81ec9355f4eecd6eed02}} entry). FastAPI writes one for you; the {{Building a backend API|n:3c65c17b0d0d8190ade6c34e8f653e79}} page walks through it.

Errors and the QUERY method

RFC 9457 problem details is the standard JSON error shape. RFC 10008 (June 2026) adds QUERY: a safe, idempotent request that carries a body, so a search or a GraphQL query no longer has to choose between a huge URL and a non-cacheable POST (atlas entry, checked against the RFC).

What REST does not give you, and the rest of this page supplies for internal calls: a required contract (clients and servers drift apart silently), compact encoding (section 3 measures JSON at 2.4 times protobuf for the running request), a deadline that travels with the call (section 5), and streaming in both directions (the LLM APIs add SSE for one direction; {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}} owns that).
