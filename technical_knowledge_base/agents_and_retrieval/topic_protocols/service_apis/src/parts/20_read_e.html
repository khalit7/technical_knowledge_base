4. gRPC on the wire

The problem. Protobuf gives you bytes; you still need a way to name the method, carry a deadline and credentials, stream messages both ways, and report how the call ended, all over connections that stay open for hours. gRPC (open-sourced by Google in 2015 from its internal Stubby; the root's atlas entry) answers by mapping every call onto one HTTP/2 stream ({{gRPC over HTTP/2 spec|https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md}}). If HTTP/2 streams, frames and HPACK are new, read {{HTTP|n:3c65c17b0d0d811bb035fa3f158b0889}} section 5 first; here is what gRPC adds on top.

Four things in that list are gRPC's own:

  1. The method is the path. :path /llm.v1.Inference/Generate is /package.Service/Method; every call is a POST. Proxies can route on it like any URL.
  2. te: trailers and content-type: application/grpc. The first tells any proxy in between that the client understands trailers (header fields sent after the body); the spec uses it "to detect incompatible proxies". A server that gets a non-gRPC content type should answer 415.
  3. A 5-byte prefix on every message. The request DATA frame is 00 00 00 00 31 then 49 bytes of protobuf: one byte "compressed?" (0 = no), four bytes of length (0x31 = 49), then the message from section 3. Each token arrives the same way, 10 to 14 bytes in all. DATA frame boundaries need not match message boundaries, so a reader must parse by these prefixes, never by frames.
  4. The outcome comes last. HTTP status is 200 even for failures; the real result is the trailer grpc-status (0 = OK) with grpc-message. When the call fails before any message, the server sends a single trailers-only HEADERS frame: the recorded call to a method the server does not have came back as :status 200, grpc-status 12, grpc-message Method not found!, all in one frame.

The other frames are HTTP/2 housekeeping: SETTINGS (both sides advertised a 4 MB window and frame size), WINDOW_UPDATE (flow control), and PINGs that gRPC sends to estimate the bandwidth-delay product and grow its windows (BDP probing; the root's Failure lab case "One stream's throughput is capped at window / round trip" shows why that matters on long links). The {{One gRPC call|#t-call}} tab steps through all three recorded connections frame by frame with every byte decoded.

Four shapes of call

Unary

One request, one response: rpc Who(WhoRequest) returns (WhoReply). Most calls.

Server streaming

One request, many responses: the token stream above. The LLM case.

Client streaming

Many requests, one response: upload audio chunks, get one transcript.

Bidirectional

Both sides send whenever they like on one stream: realtime voice, Triton's sequence models, Envoy talking to an external processor (section 12).

All four are one HTTP/2 stream; the shape only changes how many length-prefixed messages each side sends before closing its half. That is why gRPC needs HTTP/2: HTTP/1.1 cannot carry a request body and a response body at the same time on one connection, and has no trailers that every client honours.

Channels, stubs and the connection underneath

In client code you create a channel to a target (grpc.insecure_channel("127.0.0.1:30500")) and a stub on it. The channel resolves the name, opens a connection per backend address (a subchannel), keeps them alive, reconnects with backoff, and multiplexes every call as a new stream. Creating a channel is expensive (TCP, maybe TLS, SETTINGS); a call is cheap. So: one channel per target, shared and reused, never one per call. gRPC's {{performance guide|https://grpc.io/docs/guides/performance/}} says the same. The flip side of reuse is that a channel's connection lives a long time, which is exactly what confuses load balancers (section 8). Cross-cutting work (attaching credentials, logging, metrics, tracing) goes in interceptors, gRPC's middleware that wraps every call on a channel or server; credentials themselves (per-call tokens, TLS and mTLS on the channel) are on the {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} page.
