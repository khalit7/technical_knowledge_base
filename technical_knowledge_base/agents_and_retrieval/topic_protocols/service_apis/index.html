The idea in one screen

A service API is a contract for a call that can fail halfway. REST, gRPC and GraphQL write that contract down and put it on the wire differently, but every good API answers the same questions: what may be sent, how long the caller waits, what each failure means, whether a retry is safe, and which copy of the service answers.

One LLM request crosses three API styles before a token comes back

The running example is the root page's request, POST /v1/messages with "What colour is the sky?". Outside the front door it is REST with SSE, because anyone with curl must be able to call it; inside it is gRPC, because both ends are yours and the calls are many, typed and streaming. Each label names the section that teaches it.

You need: HTTP methods, status codes and HTTP/2 streams (HTTP, sections 2 and 6), and what an SSE stream is (Streaming and real-time). Credentials on these calls are Auth's; MCP's own use of JSON-RPC is MCP's.

New terms

Idempotent: doing it twice has the same effect as once.
Idempotency key: a client-chosen id that makes one POST safe to retry.
Cursor: an opaque token meaning "the rows after the last one you saw".
Schema or IDL: a machine-readable description of messages and operations (OpenAPI, .proto, GraphQL SDL).
Webhook: your server POSTs to a URL the client registered when an event happens.
Field number: the integer that names a protobuf field on the wire; names never travel.
Deadline: the moment after which the caller no longer wants the answer; gRPC passes what is left to each hop.
Trailers: header fields sent after the body; gRPC puts its result there.
Channel: a gRPC client's long-lived handle on a target: names, connections, calls.
L4 / L7 balancer: chooses a replica once per TCP connection / once per call.
Resolver: the GraphQL function that produces one field's value.
Replica: one running copy of a service.

1. What an API style decides

Two programs written by different teams must agree on what a request contains, how it becomes bytes, how the bytes travel, what shape a call has, and how it fails. An API style is a bundle of answers. Put the four styles you will meet side by side on those questions:

RPC (remote procedure call) makes a call on another machine look like a local one, stub.Generate(request): a generated stub turns it into bytes, a server-side servicer you fill in answers it. Its old trap is that a network call can be slow, half-done or lost in ways a local call never is, which is why sections 4, 10 and 11 exist. REST takes the other road: named things (resources) and a fixed set of verbs whose meaning (safe, idempotent, cacheable) every proxy already knows.

2. REST done properly: resources, errors, pages, versions

A public LLM API is called by curl, SDKs, browsers and proxies you have never seen; the one thing they share is HTTP. "REST" in practice means resource-shaped HTTP with JSON (Fielding's full style, below, is rarely followed), and what separates a good one is a handful of decisions client code depends on.

Resources and methods

Model the API as nouns with URLs (/v1/chats/{id}/messages), plural collections, one level of nesting for real ownership, and opaque prefixed string ids (chat_ae8136d1b896 rather than 17, which leaks volume and invites guessing). Let the method be the verb: GET is safe, PUT and DELETE are idempotent, POST is neither (HTTP section 2 owns those semantics). Return the created object with 201 and Location. Two shapes cover what CRUD does not:

  • Custom methods. An action that is not create, read, update or delete gets a :verb suffix on the resource, POST /v1/{name=publishers/*/books/*}:archive in Google's rules (AIP-136). Never a GET with side effects: crawlers, link previews and caches send GETs freely.
  • Long-running work. When a call takes minutes, answer at once with a handle to poll: Google returns an Operation resource (AIP-151); plain HTTP says 202 Accepted. Anthropic's Message Batches API is this pattern: a batch starts in_progress, you poll until ended, results stay for 29 days (Claude docs, batch processing); a webhook (section 6) is the push alternative to polling.

The running request is a function call wearing a resource's URL (POST /v1/messages creates nothing you GET later), which is fine: the expensive call hangs off an ordinary resource that can be stored, billed, listed and made idempotent. For searches with large bodies, RFC 10008 (June 2026) adds QUERY: a safe, idempotent request that carries a body, so a search or GraphQL query no longer has to choose between a huge URL and an uncacheable POST.

Errors: three layers

Client code must decide, for every failure, whether to show a message, retry, give up or re-authenticate. It can only do that if errors have three layers: the status code (whose fault, retry or not), a stable error type that code switches on and that is append-only (never renamed or reused), and human text that no code parses. Add a request id in a header and in the body (Anthropic: request-id; OpenAI: x-request-id). The standard shape is RFC 9457 problem details, application/problem+json with type, status, title, detail, instance (RFC 9457, July 2023, obsoletes RFC 7807). LLM providers predate it and keep their own envelopes with the same layers (Anthropic's types run from invalid_request_error, 400, to overloaded_error, a non-standard 529, and "the type values will grow over time"). Two rules people break: one shape for every error, including a proxy's HTML 502 page; and once a stream has started the status is already 200, so later errors arrive as an event inside the stream.

Pagination: offset shifts under writes, a cursor does not

A list endpoint returns a page and a way to ask for the next. Offset (?limit=20&offset=40) is easy and lets a UI jump to page 7, but the database still reads every skipped row, and rows added while the user pages shift everything. A cursor encodes the sort key of the last row seen, WHERE (created_at, id) > (:t, :id), so an index seeks straight to it. Offset keeps a place in small admin tables.

Versioning: never break a client you cannot see

A breaking change is any change after which a correct existing client stops working or starts doing something different: removing or renaming a field, changing its type, making an optional field required, changing a default ("Changing the default value is considered breaking", AIP-180), or changing behaviour under the same shape. Adding endpoints, optional fields, response fields and enum values is safe only if clients are tolerant readers that ignore what they do not know; Anthropic's contract reserves the right, within a version, to "add new variants to enum-like output values (for example, streaming event types)" (Claude API versioning).

Depth: what Fielding's REST actually is, the Richardson levels, retiring endpoints

REST is an architectural style Roy Fielding described in chapter 5 of his 2000 dissertation to explain why the web scaled (Fielding, chapter 5). Its constraints, each with what it buys: resources, not functions (you transfer representations of a named thing); a uniform interface (a small fixed set of verbs with universal meaning: this, not JSON, is the deepest difference from RPC, since every intermediary knows what a GET may do); statelessness (each request carries everything needed, the API key and the full conversation, which is what lets any replica answer any request); cacheable and layered (proxies and caches can sit in between without understanding your app); and hypermedia (HATEOAS: responses carry links to the next actions; the least followed constraint, whose one mass deployment is the human web of HTML links and forms).

Martin Fowler's write-up of Leonard Richardson's maturity levels is the usual yardstick (Fowler, 2010): level 0 is one endpoint taking POSTs (RPC in JSON), level 1 adds resources with their own URLs, level 2 uses the HTTP verbs and status codes properly, level 3 adds hypermedia links. Level 2 is where almost every good API stops, and the running request is level 2; "HTTP API" is the honest name.

Retire anything with a date, a warning while it still works (the Deprecation header, RFC 9745, and Sunset, RFC 8594), and logs that show nobody still calls it. A fourth versioning school uses no URL versions at all and evolves compatibly, new media types if forced (Zalando's guidelines: "MUST not use URL versioning"). Stripe's post reports close to 100 backwards-incompatible upgrades over six years handled by its transform modules without breaking integrations; most teams should start with /v1/ plus strictly additive changes and add a version header when the first unavoidable break arrives.

3. OpenAPI and schema-first design: the contract as data

Without a written contract, clients and servers drift apart silently: a renamed field is found by a customer, not a compiler. A schema turns the contract into data that tools check. For REST that is an OpenAPI document (paths, methods, parameters, request and response schemas, auth schemes); for gRPC it is the .proto file (section 8); for GraphQL its SDL. The fan-out is the same for an OpenAPI document and a .proto file; only the tools differ (OpenAPI Generator and commercial generators, oasdiff; protoc, buf breaking).

Code-first writes the server and exports the spec (FastAPI serves one at /openapi.json); schema-first writes the spec, reviews it like code, and generates server stubs and clients from it. Larger organisations with many teams tend to the second, because the review happens before anyone depends on the shape, and a CI job that diffs the new spec against the published one fails the build when a field disappears. Several API companies, LLM providers among them, generate their official SDKs from an OpenAPI spec with commercial generators. OpenAPI 3.1 aligned its schemas with JSON Schema; 3.2.0 (19 September 2025) added sequential and streaming media types such as text/event-stream, so SSE endpoints can finally be described; the current release is 3.2.1 (10 September 2026, the root's Protocol atlas entry).

4. Idempotency keys and retries across services

The user presses Send; after 30 seconds nothing has come back. Either the request never arrived, or it arrived, the model answered, the credits were charged and the reply was lost. The client sees the same timeout in both cases: retrying risks paying twice, not retrying risks losing the message. GET, PUT and DELETE may be retried because they are idempotent; generation is a POST. An idempotency key makes one POST idempotent: the client generates a unique value per logical action, sends it on every retry of that action, and the server answers repeats from what it stored the first time. Same input, with and without the key:

The retry is harmless only when the server remembers the key

The mechanism follows Stripe's design (Stripe, idempotent requests; Brandur Leach, 2017); credits, ids and timings are illustrative.

The server side, in three steps. (1) Claim the key atomically: insert (user, key, request fingerprint, status started) under a unique constraint, so exactly one of two simultaneous attempts wins; never "select, and if absent insert", which races. (2) If it exists, compare and replay: a different fingerprint means the client reused a key for a different action (422); started means the first attempt is still running (409, retry later); done means return the stored status and body (Stripe marks it Idempotent-Replayed: true). (3) Do the work and store the result in one transaction, so the message, the charge and the stored response commit together. Then release the claim on every exit that did not store a response, and give claims an expiry, or a crash between steps 1 and 3 leaves the key stuck at started and every retry gets 409 forever (Code design found and measured exactly that bug in the Building a backend API demo).

Across services: one retry layer, one deadline, one key

Behind the front door the same request crosses a router and an inference service, and each hop has a client that could retry. Three rules keep that safe:

  • Retry at one layer. If three layers each make 3 attempts, one failing call becomes 3 × 3 × 3 = 27 attempts at the bottom, arriving exactly when the bottom is already failing (attempts multiply: aL for a attempts at each of L layers). Retry at the edge, or in the client closest to the failure, and let the others fail fast. Retry budgets and circuit breakers that cap this system-wide are Reliability engineering's.
  • Every attempt shares the original deadline. gRPC's deadline "applies across all attempts" (section 11); a retry that resets the clock outlives the user who asked.
  • Pass the key down. A retried front-door request must not become a second charge two hops down, so the service that owns the side effect (the billing call, the outbox row) receives a key derived from the caller's, and dedupes on it. When the side effect leaves your database (a payment provider, a message queue), store the intent and the key first and send later: the outbox pattern on Queues, streams and async work.

The official Anthropic and OpenAI Python SDKs retry connection errors, 408, 409, 429 and 5xx themselves, with no idempotency key; HTTP section 10 measures their attempts, and is the owner of retry safety at the protocol level.

5. Rate limits and quotas at the API

A rate limit caps what one caller may use per unit of time, so one runaway script cannot take capacity from everyone; for LLM APIs it is counted in tokens as well as requests, because a 100,000-token prompt and a 50-token one are not the same load. How the server counts (token bucket, sliding window) is Reliability engineering's; budgets across many providers at a gateway are Gateways and routing's.   • At the wall: 429 Too Many Requests (RFC 6585) with Retry-After in seconds or as an HTTP date (RFC 9110). A well-behaved client waits that long; the official SDKs honour it automatically. In gRPC the same signal is RESOURCE_EXHAUSTED, with the wait in a RetryInfo detail or the grpc-retry-pushback-ms trailer (section 11).
  • Before the wall: remaining-budget headers on every response let a client slow down before it is refused, which is cheaper for both sides than a 429 and a retry.
  • A quota is not a rate limit. "1,000 messages a month" or a spend cap will not clear by waiting a second, so say so in the error type and omit retry-after: Anthropic's spend-cap 429 has the same error type as a rate limit but no retry-after, and tells itself apart with error.details.error_code enforced_spend_limit_reached; "Retrying, including the SDK's automatic retries, fails until access resumes" (rate-limits page, read 2026-10-24).
  • Limit before expensive work, and before the idempotency layer. Stripe notes that "rate limiters run before the API's idempotency layer" (Stripe, advanced error handling), so a 429 is not stored against the key and the retry gets a fresh chance.
  • Limit per key, per model, per dimension. Anthropic publishes separate limits for requests, input tokens and output tokens per minute, per model (same rate-limits page); a client that only counts requests will be surprised by the token limit. What counts is a design decision with consequences: on most Claude models only uncached input tokens count toward input tokens per minute, and max_tokens "does not factor into OTPM rate limit calculations", so prompt caching raises effective throughput and a large max_tokens costs nothing against the limit. The server counts with a token bucket, so capacity refills continuously rather than at fixed intervals.

6. Webhooks: your API, called in reverse

Some events happen later: a batch finishes, a payment clears, a moderation review completes. Clients could poll; a webhook turns it around: the client registers a URL and your server POSTs to it when the event happens. Now you are the client, calling code you do not control, over a network that fails, so everything from sections 2 to 5 applies with the roles swapped. Step through one delivery that goes wrong in the usual way:

At-least-once delivery: sign, retry with backoff, and let the receiver dedupe on the event id

Header names and the signed string follow the Standard Webhooks spec; retry timings follow its suggested schedule; ids and times illustrative.

  • Sign every delivery with an HMAC-SHA256 over the id, a timestamp and the exact body, using a secret shared with that receiver: Standard Webhooks signs msg_id.timestamp.payload and sends webhook-id, webhook-timestamp and webhook-signature: v1,<base64>; Stripe signs timestamp.payload into Stripe-Signature: t=...,v1=... (Stripe webhooks). Receivers verify against the raw bytes before parsing (re-serialised JSON changes spacing and key order), compare in constant time, and reject old timestamps to stop replays: Stripe's libraries default to "a default tolerance of 5 minutes".
  • Retry with backoff, for days. Stripe retries "for up to three days with an exponential back off in live mode"; Standard Webhooks suggests immediately, 5 seconds, 5 minutes, 30 minutes, and on up to 24 hours. Then mark the endpoint failing and let the user redeliver.
  • Expect duplicates and disorder. Delivery is at-least-once, so "Use the webhook-id header as an idempotency key"; Stripe "doesn't guarantee the delivery of events in the order that they're generated", so receivers fetch current state rather than trust event order.
  • Receivers answer 2xx fast and work later: put the event on a queue (Queues, streams and async work). Thin events carry only the type and ids, and the receiver fetches the object, so it always gets current data and no personal data travels in the webhook; Stripe now offers both "thin" and "snapshot" events.

How webhooks compare with SSE, WebSockets and polling as ways to push news to a client is Streaming and real-time's; this section owns the API design of one.

7. LLM provider APIs: one design problem, three answers

Every LLM provider faces the same design problem: a conversation that grows each turn, model output that is sometimes text and sometimes a request to run a tool, and a result that has to come back paired with the call that asked for it. OpenAI's Chat Completions, OpenAI's Responses API, which replaced it as the recommended API ("While Chat Completions remains supported, Responses is recommended for all new projects"), and Anthropic's Messages API answer it differently. 8. Protobuf: the bytes inside every gRPC call

JSON spells out every field name in every message ("max_tokens":16 is 15 bytes to say "16"), stores numbers as text, and has no schema, so a typo in a field name is silently ignored. Between your own services, millions of times a second, that costs CPU and bandwidth and hides bugs. Protocol Buffers fix all three: a schema both sides compile, and a binary encoding that sends field numbers and compact values. The running request as the lab's llm.proto (in src/lab/):

message GenerateRequest {
  string model = 1;
  repeated Message messages = 2;
  uint32 max_tokens = 3;
  bool stream = 4;
}
service Inference {
  rpc Generate(GenerateRequest) returns (stream Token);  // server streaming
}

The numbers after = are the contract; protoc turns the file into classes and stubs for each language. On the wire every field is a tag, (field_number << 3) | wire_type, then a value; the wire type says how to find the value's end: 0 VARINT (integers, booleans, enums), 2 LEN (a length, then bytes: strings, nested messages, packed lists), 1 and 5 for fixed 8- and 4-byte values (encoding guide). 9. gRPC on the wire

Protobuf gives bytes; a call also needs a method name, a deadline, credentials, streams both ways and an outcome, over connections that stay open for hours. gRPC (open-sourced by Google in 2015 from its internal Stubby) maps every call onto one HTTP/2 stream (gRPC over HTTP/2 spec); HTTP/2 frames and HPACK themselves are HTTP's. The lab ran the running request through a logging proxy that decodes every HTTP/2 frame (no packet capture: the proxy sits on the socket between grpcio client and server), asking for 5 tokens with a 2-second deadline. Four things in that stream are gRPC's own:

  1. The method is the path: :path /llm.v1.Inference/Generate is /package.Service/Method, always a POST, so proxies can route on it like any URL.
  2. te: trailers and content-type: application/grpc: the first tells proxies the client understands trailers; the spec uses it "to detect incompatible proxies". A server sent a non-gRPC content type should answer 415.
  3. A 5-byte prefix on every message: the request DATA frame is 00 00 00 00 31 then the 49 bytes of section 8 (one byte "compressed?", four bytes of length, 0x31 = 49). Each token arrives the same way, 10 to 14 bytes in all. Frame boundaries need not match message boundaries, so readers parse by prefixes, never by frames.
  4. The outcome comes last: HTTP status is 200 even for failures; the real result is the trailer grpc-status (0 = OK) with grpc-message. A call that fails before any message gets one trailers-only HEADERS frame: the call to a missing method came back as :status 200, grpc-status 12, grpc-message Method not found! in a single frame.

The rest is HTTP/2 housekeeping: SETTINGS (both sides advertised 4 MB windows and frame size), WINDOW_UPDATE, and PINGs that gRPC sends to estimate the bandwidth-delay product and grow its windows (BDP probing). Against the root page's REST and SSE recording of the same request:

Four call shapes, one stream each: unary (most calls), server streaming (the token stream above), client streaming (audio chunks in, one transcript out) and bidirectional (realtime voice, Triton's sequence models, Envoy talking to an external processor). Channels. Client code makes a channel to a target and a stub on it; the channel resolves the name, opens one connection per backend address (a subchannel), keeps them alive, reconnects with backoff, and multiplexes every call as a new stream. A channel is expensive (TCP, maybe TLS, SETTINGS) and a call cheap: one channel per target, shared, never one per call (performance guide); its hours-long connection is what confuses load balancers (section 13). Credentials, logging and tracing go in interceptors, gRPC's middleware.

10. Deadlines and cancellation: giving up together

The user closes the tab after the ninth token. The front door notices; behind it, the router and the inference server do not, and the GPU keeps decoding an answer nobody will read, while abandoned work queues ahead of live work. Every hop needs two facts: how long the caller will wait, and whether it is still there. In gRPC the caller sets a deadline; it travels as a relative timeout in grpc-timeout (at most 8 digits plus a unit, H M S m u n), and each hop subtracts the time already spent before passing it on, so no clocks need to agree (deadlines guide). When it passes, both ends end the call with DEADLINE_EXCEEDED and the client sends RST_STREAM with code CANCEL (8); cancellation for any other reason uses the same frame.

The default is "wait forever"

"By default, gRPC does not set a deadline which means it is possible for a client to end up waiting for a response effectively forever." Propagation "is supported by some gRPC implementations": on by default in Java and Go when you pass the incoming context on, opt-in in C++, and in Python you do it yourself (timeout=ctx.time_remaining()). Stopping the work is the server's job: "The server application is responsible for stopping any activity it has spawned to service the RPC."

The lab chained client, gateway and inference service (three processes, real gRPC, a frame log on the second hop). The inference service emits up to 40 tokens, the first after 0.12 s then one every 0.05 s, so a full answer takes about 2.1 s; in every run the client stops after 0.6 s. Choosing the number. Retries: off by default, on by configuration

gRPC retries two ways (retry design A6). Transparent retries are always on: when the call never left the client, or reached the server but not your handler, the library retries, because nothing can have happened twice. A retry policy exists only if the service config (JSON given to the channel, or published by the name resolver) has one: which codes, up to how many attempts (values above 5 are treated as 5), exponential backoff with plus or minus 20% jitter, and the deadline "applies across all attempts". Each retry carries grpc-previous-rpc-attempts.

Hedging sends a second copy after a delay without waiting for the first to fail, for idempotent calls with long tails; Go and C-core had not implemented it when the design was last updated (2024-08-23).

12. Connections: keepalive, limits, health and reflection

A channel keeps its connections for hours. Meanwhile a NAT box may silently drop an idle connection, a server may drain for a deploy, and a big message may exceed a limit. A keepalive is an HTTP/2 PING on a quiet connection; no ACK within 20 s (the default timeout) and the connection is declared dead, so calls fail with UNAVAILABLE instead of hanging. Client keepalive is off by default in gRPC core, and servers defend themselves against ping floods: by default they expect at least 5 minutes between pings on a connection carrying no data, and after 2 "strikes" they send GOAWAY with ENHANCE_YOUR_CALM (keepalive guide). The lab reproduced it: a client with grpc.keepalive_time_ms=1000 made a call whose first token takes 8 s. At first nothing happened (the client's own brake, max_pings_without_data, default 2, stopped it after two pings); with that brake removed the server cut the connection mid-call:

The client saw UNAVAILABLE: Too many pings and lost the in-flight call. vLLM's gRPC server (v0.31.0) carries exactly this fix, noting that keepalive and BDP-probe pings during a non-streaming Generate "are strikes and eventually earn a GOAWAY(ENHANCE_YOUR_CALM, "too_many_pings") that fails every in-flight RPC", so it sets grpc.http2.max_ping_strikes to 0 (grpc_server.py). Rule: client keepalive slower than the server's minimum interval, or tell the server to accept faster pings. The same file records a second trap: a misspelt option "and gRPC Core silently ignores unknown keys, so the misspelt form left the 300s default in force"; check channel arguments against the core list and test that behaviour changed.

GOAWAY and connection age. GOAWAY is "no new streams on this connection": it names the last stream accepted, so the client knows which calls to resend elsewhere. Servers send it when shutting down, and on a timer if configured: MAX_CONNECTION_IDLE, MAX_CONNECTION_AGE (plus or minus 10% jitter so clients do not reconnect together) and MAX_CONNECTION_AGE_GRACE, all infinite by default (proposal A9), whose stated purpose includes L4 balancers: "This option can force the client to periodically reconnect to a L4 LB which allows spreading load more quickly." 13. Load balancing gRPC: L4, L7 and the client

Three replicas should take a third of the calls each. Where and how often a replica is chosen decides whether they do, or one is hot and two idle; with gRPC's long-lived multiplexed connections this is the number-one production surprise.

An L4 balancer chooses once per connection; an L7 balancer or the client chooses once per call

L4 (AWS NLB, Linux IPVS, kube-proxy, nginx stream) sees TCP and copies bytes without reading them. L7 (Envoy, nginx grpc_pass, a mesh sidecar, AWS ALB, which has supported gRPC since 29 October 2020, AWS) terminates HTTP/2, reads each call's HEADERS and can route on :path, retry and count calls in flight. Client-side: the channel learns every address (DNS or a control plane) and picks per call with a policy: pick_first (the default), round_robin, or xDS policies (gRPC load balancing).

What to do, in order of preference

  1. An L7 proxy that speaks HTTP/2 (Envoy, nginx grpc_pass, Istio or Linkerd, a cloud L7 balancer). Cost: one more hop to run and scale.
  2. Predict, then reveal (protobuf)


The running request with max_tokens = 300 instead of 16. How many bytes is the protobuf message now (it was 49)?




50. 16 fits in 7 bits (one byte, 10); 300 needs 9 bits, so two varint bytes, ac 02 (the varint box in section 8 shows exactly these bytes). The tag 18 (field 3, wire type 0) does not change. Try it in the varint box in section 8.

Team A deletes uint32 max_tokens = 3 and later adds uint32 priority = 3. An old inference server receives priority = 9. What does it do?




It generates 9 tokens. The wire carries only "field 3, varint, 9"; the old schema calls field 3 max_tokens, so that is what it reads (measured in section 8). Answer b is what happens when the reused number has a different wire type. Prevention: reserved 3; when deleting.


Predict, then reveal (status)


A gRPC call to a server that is down returns in 1 ms. What code, and what would make it wait instead?




UNAVAILABLE ("failed to connect to all addresses", measured in about 1 ms). Without wait-for-ready a call on a channel in TRANSIENT_FAILURE fails at once; with it, the call waits for a connection until its deadline. Use wait-for-ready during start-up races, not to hide a dead dependency.

Client deadline 600 ms. The gateway spends a few milliseconds and calls the inference service, propagating the deadline. What grpc-timeout does the inference service receive?

A Kubernetes Deployment of 3 gRPC Pods sits behind a normal ClusterIP Service. One client process sends 3,000 calls per second on one channel. How are the calls spread?

51: one for the list and one provider lookup per model (N+1). With a DataLoader, 2. The lab's 20-model version measured 21 and 2.



Why does gRPC need HTTP/2, and what breaks if a proxy in the path speaks HTTP/1.1 upstream?
gRPC maps each call to one HTTP/2 stream, sends request and response bodies concurrently for streaming calls, and puts the outcome in trailers after the body. HTTP/1.1 has no multiplexing and no trailers that clients reliably honour, so a proxy that downgrades upstream either fails or loses the status. The te: trailers header exists to detect such proxies; the client then synthesises a status from the HTTP response, which is how the lab saw "Received http2 header with status: 502". gRPC-Web and Connect exist for paths that cannot be HTTP/2 end to end.


Explain deadline propagation and what happens without it in an LLM serving stack.
The caller sets a deadline; each hop passes on the remaining time in grpc-timeout and cancels downstream calls when its caller cancels. Without it, a user who leaves does not stop the generation: in the lab's run D the inference service produced  tokens over  s for a client that had stopped after . On GPUs that is wasted capacity and longer queues for live users. Also: gRPC sets no deadline by default, retries share the original deadline, and stopping work is the server's job.


Your gRPC service is behind an AWS NLB and one instance is hot. Explain and fix.
An NLB is L4: it balances connections, and gRPC clients hold few long-lived connections, so load follows connections, not calls. Options: an ALB (gRPC since 2020) or Envoy for per-call L7 balancing; client-side round_robin with service discovery; or server MAX_CONNECTION_AGE (minutes) so clients reconnect and spread over time. The lab measured 30/0/0 through L4, 10/10/10 through L7, and a new replica reached only after reconnects.


How do you evolve a protobuf schema safely?
Add fields with new numbers (old readers keep them as unknown fields and re-serialise them unchanged, measured); never change a field's number or type; when deleting, reserved both the number and the name; prefer optional or wrapper semantics when "unset" must differ from zero; remember ProtoJSON renames fields to lowerCamelCase, so JSON clients see a second contract. Run a breaking-change checker in CI (buf breaking is one).


When would you choose GraphQL over REST, and what would you put in place on day one?
When many clients need different shapes of the same graph of data and round trips are expensive (mobile, aggregating many backends). Day one: DataLoader batching on every resolver that fetches, a cost or depth limit evaluated before execution, pagination arguments with a maximum (GitHub's 1 to 100), persisted queries for first-party clients, monitoring on the errors array, and per-field authorisation.


Which gRPC status codes would you retry, and how do you stop retries from making an outage worse?
UNAVAILABLE for any method (normally means not processed); others only for idempotent methods. Never blindly retry DEADLINE_EXCEEDED on non-idempotent calls, since the work may have happened. Bound it: maxAttempts (capped at 5), exponential backoff with jitter, retry throttling (token bucket per server), server pushback, the overall deadline, and a retry budget across the system.
