Service APIs in one screen

When you send the root page's request, POST /v1/messages with "What colour is the sky?", one program does not answer it. The front door checks your key, a router picks a GPU replica, an inference server generates tokens, and telemetry goes to a collector. Each arrow between those programs is an API call: an agreed way for one program to ask another to do something over the network. This page is about the arrows: what goes on the wire, how a call gives up, what its errors mean, and how calls get spread over many copies of a service.

The running example, behind the front door

Outside: REST and SSE, because anyone with curl must be able to call it. Inside: gRPC, because both ends are yours and the calls are many, typed and streaming. The labels are the ports and protocols real systems use (sources in section 12); the lab on this page builds the middle two hops and records every byte.

The ten things to remember
  1. gRPC is HTTP/2 underneath: every call is a POST /package.Service/Method stream, each message has a 5-byte prefix, and the result arrives in trailers (grpc-status) after the body. Section 4 shows the recorded frames.
  2. Protobuf sends field numbers, not names: the running request is 49 bytes against 117 in JSON (measured). Never reuse a field number: an old reader silently misreads it (section 3, measured).
  3. gRPC sets no deadline by default. Set one on every call and pass the remaining time on; without that, a GPU kept generating tokens for a user who left after (section 5, measured).
  4. Status codes say who failed and whether a retry is safe. Retries are off unless a service config turns them on, and the deadline covers every attempt (section 6).
  5. One gRPC channel keeps one long-lived connection. An L4 balancer chooses once per connection, so all 30 calls went to one replica; an L7 balancer chose per call, 10/10/10 (section 8, measured).
  6. The default client policy, pick_first, also sends everything to one address even when it knows three. Ask for round_robin or use a proxy (section 8, measured).
  7. New replicas stay idle behind an L4 balancer until clients reconnect; MAX_CONNECTION_AGE forces that (section 8 and the Balancer lab).
  8. Browsers cannot speak gRPC's trailers: gRPC-Web, Connect and HTTP/JSON transcoding exist for that (section 9).
  9. GraphQL turns one query into many backend calls: 141 database calls for one innocent query, 4 with batching (section 10, measured).
  10. ML serving speaks all of these: OpenAI-compatible REST at the edge, gRPC into Triton, vLLM's new gRPC mode, OTLP telemetry, and a gRPC side channel that lets a gateway route by KV cache (section 12).

Neighbours own the rest: HTTP (HTTP/2 frames, flow control, proxies, timeouts and idempotency keys), Networking foundations (TCP underneath; gRPC sets TCP_NODELAY), Auth (credentials on these calls, mTLS), MCP (JSON-RPC as MCP uses it). API design (pagination, versioning, error envelopes) is on Building a backend API; balancing algorithms and queueing on Capacity planning and performance.

1. What an API style decides

The problem. Two programs, often written by different teams in different languages, must agree on five things before one can call the other: what the request and answer contain, how those are turned into bytes, how the bytes travel, what happens when something fails, and who is allowed to call. An "API style" is a bundle of answers to those questions. Name the five and every style on this page becomes a comparison along them.

QuestionTermREST answergRPC answer

RPC (remote procedure call) is the idea that calling a function on another machine should look like calling a local one: stub.Generate(request). The stub (or client) is generated code that turns that call into bytes on the network; the server side has a matching servicer you fill in. The idea is decades old and so is its trap: a network call can be slow, half-done or lost in ways a local call never is, so every RPC system adds timeouts, error codes and retries. REST takes the other road: instead of named functions it exposes named things (resources) and a fixed set of verbs, and lets HTTP's existing meaning (safe, idempotent, cacheable) do the work.

Two more words used throughout. A call is idempotent when doing it twice has the same effect as once (reading a model's metadata, setting a field to a value); generating text and charging for it is not. And a replica is one copy of a service; spreading calls over replicas is load balancing (section 8).

2. REST: the front door's style

The problem it solves. A public LLM API is called by curl, by Python and TypeScript SDKs, by browsers, by no-code tools, through corporate proxies you have never seen. The only thing they all share is HTTP. REST says: use HTTP's own vocabulary and nothing else, and every one of those clients already knows how to call you.

What REST actually is. Not a protocol and not a spec: an architectural style Roy Fielding described in chapter 5 of his 2000 dissertation to explain why the web scaled (Fielding, chapter 5). Its constraints, each with the property it buys:

  • Resources, not functions. Anything nameable gets a URL (/v1/models/claude-x); you transfer representations of it (JSON) rather than calling a procedure.
  • A uniform interface. A small fixed set of verbs with universal meaning: GET is safe and cacheable, PUT and DELETE are idempotent, POST is neither. This, not JSON, is the deepest difference from RPC: every intermediary knows what a GET may do.
  • Statelessness. Each request carries everything needed (the API key, the full conversation); the server keeps no session between requests, which is what lets any replica answer any request.
  • Cacheable and layered. Because meaning is visible in the method and headers, proxies and caches can sit in between without understanding your app.
  • Hypermedia (HATEOAS: responses carry links to the next actions). The least followed constraint; the human web of HTML links and forms is its one mass deployment.

REST as practised is resource-shaped HTTP with JSON, not Fielding-complete REST; "HTTP API" is the honest name. Martin Fowler's write-up of Leonard Richardson's maturity levels is the usual yardstick (Fowler, 2010): level 0 is one endpoint taking POSTs (RPC in JSON), level 1 adds resources with their own URLs, level 2 uses the HTTP verbs and status codes properly, level 3 adds hypermedia links. Level 2 is where almost every good API stops. The running request is level 2 with one twist: POST /v1/messages creates nothing you can GET later; it is really a function call wearing a resource's URL, which is fine. For actions that are not create, read, update or delete, Google's API rules use a :verb suffix on the resource, such as POST /v1/{name=publishers/*/books/*}:archive (AIP-136).

Long-running work

When a call takes minutes, answer at once with a handle to poll: Google returns an Operation resource (AIP-151); plain HTTP says 202 Accepted (accepted, not done). Anthropic's Message Batches API is this pattern: a batch starts in_progress, you poll until ended, results stay for 29 days (Claude docs, batch processing).

Describing it: OpenAPI

A machine-readable list of paths, parameters, schemas and auth schemes, from which docs, SDKs and tests are generated. Current version 3.2.1 (10 September 2026; the root's Protocol atlas entry). FastAPI writes one for you; the Building a backend API page walks through it.

Errors and the QUERY method

RFC 9457 problem details is the standard JSON error shape. RFC 10008 (June 2026) adds QUERY: a safe, idempotent request that carries a body, so a search or a GraphQL query no longer has to choose between a huge URL and a non-cacheable POST (atlas entry, checked against the RFC).

What REST does not give you, and the rest of this page supplies for internal calls: a required contract (clients and servers drift apart silently), compact encoding (section 3 measures JSON at 2.4 times protobuf for the running request), a deadline that travels with the call (section 5), and streaming in both directions (the LLM APIs add SSE for one direction; Streaming and real-time owns that).

Go deeper (optional). Designing a REST API well (resource names, pagination, filtering, versioning, idempotency keys, rate-limit headers) is the whole of Building a backend API; Stripe's API reference is the best example to copy. Status codes, caching and retries at the protocol level: HTTP.

3. Protobuf: the bytes inside every gRPC call

The problem. JSON spells out every field name in every message ("max_tokens":16 is 15 bytes to say "16"), stores numbers as text that must be parsed digit by digit, and has no schema, so a typo in a field name is silently ignored. Between your own services, sending millions of messages a second, that costs CPU and bandwidth and hides bugs. Protocol Buffers (protobuf) fix all three: a schema both sides compile, and a binary encoding that sends field numbers and compact values.

The schema. This is the lab's llm.proto, the running request as a message (the full file is in the page's src/lab/):

message GenerateRequest {
  string model = 1;
  repeated Message messages = 2;
  uint32 max_tokens = 3;
  bool stream = 4;
}
service Inference {
  rpc Generate(GenerateRequest) returns (stream Token);  // server streaming
}

The numbers after = are the field numbers. They, not the names, are the contract: names never travel on the wire. protoc turns this file into classes and stubs for each language.

How a message becomes bytes

Every field is written as a tag then a value. The tag is one number, (field_number << 3) | wire_type, where the wire type says how to find the value's end: 0 VARINT (integers, booleans, enums), 2 LEN (a length then that many bytes: strings, bytes, nested messages, packed lists), 1 and 5 for fixed 8- and 4-byte values (protobuf encoding guide). Numbers are varints: 7 bits per byte, low group first, the top bit set on every byte except the last. So 150 is 96 01: 150 is 1 0010110 in binary; the low 7 bits 0010110 go first with the "more" bit set (0x96), then the remaining 1 (0x01). Try any number:

The savings are the names ("max_tokens": becomes the single tag byte 18), the quotes and braces, and the number 16 as one byte instead of two characters. Three encoding details that bite

  • Negative numbers. An int32 of -1 is sign-extended to 64 bits and costs 10 bytes; the sint32 type uses zigzag (-1 becomes 1, 1 becomes 2) and costs 1. Measured: against . Use sint32/sint64 for fields that are often negative.
  • Packed lists. In proto3, repeated numbers are packed by default: one tag and a length for the whole list. Five token ids took bytes packed against one tag per element.
  • Field numbers 1 to 15 cost one tag byte, 16 to 2047 two; give them to the fields you send most. Valid numbers run from 1 to 536,870,911, with 19,000 to 19,999 reserved (proto3 guide).

Schema evolution: why the numbers are sacred

Services are deployed one at a time, so for a while a new writer talks to an old reader. Protobuf's rule is that a reader keeps fields it does not know as unknown fields and carries on. The lab tested three changes against the old GenerateRequest reader (measured):

4. gRPC on the wire

The problem. Protobuf gives you bytes; you still need a way to name the method, carry a deadline and credentials, stream messages both ways, and report how the call ended, all over connections that stay open for hours. gRPC (open-sourced by Google in 2015 from its internal Stubby; the root's atlas entry) answers by mapping every call onto one HTTP/2 stream (gRPC over HTTP/2 spec). If HTTP/2 streams, frames and HPACK are new, read HTTP section 5 first; here is what gRPC adds on top.

One server-streaming call, as recorded

The lab ran the running request as a gRPC call through a logging proxy that decodes every HTTP/2 frame (no packet capture needed: the proxy sits between client and server on the socket). The client asked for 5 tokens with a 2-second deadline. What crossed the wire, in order:

Four things in that list are gRPC's own:

  1. The method is the path. :path /llm.v1.Inference/Generate is /package.Service/Method; every call is a POST. Proxies can route on it like any URL.
  2. te: trailers and content-type: application/grpc. The first tells any proxy in between that the client understands trailers (header fields sent after the body); the spec uses it "to detect incompatible proxies". A server that gets a non-gRPC content type should answer 415.
  3. A 5-byte prefix on every message. The request DATA frame is 00 00 00 00 31 then 49 bytes of protobuf: one byte "compressed?" (0 = no), four bytes of length (0x31 = 49), then the message from section 3. Each token arrives the same way, 10 to 14 bytes in all. DATA frame boundaries need not match message boundaries, so a reader must parse by these prefixes, never by frames.
  4. The outcome comes last. HTTP status is 200 even for failures; the real result is the trailer grpc-status (0 = OK) with grpc-message. When the call fails before any message, the server sends a single trailers-only HEADERS frame: the recorded call to a method the server does not have came back as :status 200, grpc-status 12, grpc-message Method not found!, all in one frame.

The other frames are HTTP/2 housekeeping: SETTINGS (both sides advertised a 4 MB window and frame size), WINDOW_UPDATE (flow control), and PINGs that gRPC sends to estimate the bandwidth-delay product and grow its windows (BDP probing; the root's Failure lab case "One stream's throughput is capped at window / round trip" shows why that matters on long links). Four shapes of call

Unary

One request, one response: rpc Who(WhoRequest) returns (WhoReply). Most calls.

Server streaming

One request, many responses: the token stream above. The LLM case.

Client streaming

Many requests, one response: upload audio chunks, get one transcript.

Bidirectional

Both sides send whenever they like on one stream: realtime voice, Triton's sequence models, Envoy talking to an external processor (section 12).

All four are one HTTP/2 stream; the shape only changes how many length-prefixed messages each side sends before closing its half. That is why gRPC needs HTTP/2: HTTP/1.1 cannot carry a request body and a response body at the same time on one connection, and has no trailers that every client honours.

Channels, stubs and the connection underneath

In client code you create a channel to a target (grpc.insecure_channel("127.0.0.1:30500")) and a stub on it. The channel resolves the name, opens a connection per backend address (a subchannel), keeps them alive, reconnects with backoff, and multiplexes every call as a new stream. Creating a channel is expensive (TCP, maybe TLS, SETTINGS); a call is cheap. So: one channel per target, shared and reused, never one per call. gRPC's performance guide says the same. The flip side of reuse is that a channel's connection lives a long time, which is exactly what confuses load balancers (section 8). Cross-cutting work (attaching credentials, logging, metrics, tracing) goes in interceptors, gRPC's middleware that wraps every call on a channel or server; credentials themselves (per-call tokens, TLS and mTLS on the channel) are on the Auth page.

5. Deadlines and cancellation: giving up together

The problem. The user closes the chat tab after the ninth token. The front door notices (its connection closed), but behind it the router and the inference server do not, and the GPU keeps decoding an answer nobody will read. At GPU prices this is real money, and under load it is worse: abandoned work queues ahead of live work. Every hop needs to know two things: how long the caller will wait, and whether the caller is still there.

How gRPC does it. The caller sets a deadline, a point in time after which it no longer wants the answer. On the wire it travels as a relative timeout in the grpc-timeout header, an integer of at most 8 digits plus a unit (H M S m u n: hours down to nanoseconds); each hop subtracts the time already spent before passing it on, which avoids trusting other machines' clocks (deadlines guide). When the deadline passes, both ends end the call with DEADLINE_EXCEEDED and the client sends an HTTP/2 RST_STREAM with code CANCEL (8). Cancellation, the second signal, uses the same RST_STREAM when the client gives up for any other reason.

The default is "wait forever"

"By default, gRPC does not set a deadline which means it is possible for a client to end up waiting for a response effectively forever" (gRPC deadlines guide). Propagation to downstream calls "is supported by some gRPC implementations": enabled by default in Java and Go when you pass the incoming context on, opt-in in C++, and in Python you do it yourself (timeout=ctx.time_remaining()). And stopping the work is the server's job: "The server application is responsible for stopping any activity it has spawned to service the RPC."

Choosing the number

Start from what the caller will tolerate, not from what the server needs: a chat UI that shows a spinner for 60 seconds sets about 60 s at the front door, and each hop inherits what is left. gRPC's guide suggests an educated guess "validated by some load testing". Three rules: a deadline covers queueing as well as work (the root's Failure lab case "Max concurrent streams: calls queue on the connection" shows calls failing at 2.5 s that the server never saw fail); retries do not get a fresh deadline (the deadline "applies across all attempts", gRPC retry design A6); and streaming generations need a deadline sized for the whole stream, or an idle timer instead (the HTTP page's Timeout chain tab plays that out for HTTP hops).

With HTTP instead of gRPC there is no deadline header: each hop has its own timeouts, and cancellation is the connection or stream closing. The equivalent discipline is a timeout on every outgoing call and a server that stops work when its incoming request is gone. vLLM's OpenAI-compatible server shows how in Python: its with_cancellation decorator races the handler against the ASGI http.disconnect message and cancels the handler when the client leaves; its comment notes that the simpler request.is_disconnected "does not work with middleware" (vLLM v0.31.0, api_utils.py).

6. Status codes, errors and retries

The problem. When a call fails, the caller must decide in microseconds: give up, retry here, retry elsewhere, or tell the user something specific. Retries: off by default, on by configuration

gRPC retries in two ways (gRPC retry design A6):

  • Transparent retries, always on: when the call never left the client, or reached the server but never reached your handler, the library retries by itself, because nothing can have happened twice.
  • A retry policy, only if the service config (a JSON document given to the channel, or published by the name resolver) has one: which status codes to retry, up to how many attempts (values above 5 are treated as 5), with exponential backoff and plus or minus 20% jitter. The deadline covers all attempts. Each retry carries grpc-previous-rpc-attempts so the server can see it.
{"methodConfig": [{"name": [{"service": "llm.v1.Inference", "method": "Who"}],
  "retryPolicy": {"maxAttempts": 4, "initialBackoff": "0.1s", "maxBackoff": "1s",
                  "backoffMultiplier": 2, "retryableStatusCodes": ["UNAVAILABLE"]}}]}

Measured against a replica that answers UNAVAILABLE twice while "warming up": without the policy the call failed at once; with it, the server log shows three attempts , and the caller saw only success. Two safety valves stop retries from becoming a storm: retry throttling (a per-server token bucket; with "maxTokens": 10, "tokenRatio": 0.1 each failure costs a token, each success returns 0.1, and retries stop while the count is at or below half) and server pushback (the server's grpc-retry-pushback-ms trailer says when to retry, or a negative value says never). Hedging is the aggressive cousin: send a second copy after a delay without waiting for the first to fail, for idempotent calls with long tails; Go and C-core did not implement hedging when the design was last updated (2024-08-23).

Correction to the old page
The old page said "only UNAVAILABLE-class errors are safely retryable by default". By default no application-level retry happens at all; only the transparent retries above. Which codes are safe depends on whether the method is idempotent, and gRPC's own docs say there is "no fixed list of status codes on which it is appropriate to retry in all applications". UNAVAILABLE is the usual choice because it normally means the request was not processed; DEADLINE_EXCEEDED is the dangerous one, since it "may be returned even if the operation has completed successfully".

Richer errors. A code and a string are often not enough ("which field?", "retry after how long?"). The spec reserves the trailer grpc-status-details-bin for a serialised google.rpc.Status carrying typed details such as BadRequest or RetryInfo (Google's error model, AIP-193).

7. Connections: keepalive, limits, health and reflection

The problem. A gRPC channel keeps its connections for hours. In that time a NAT box or cloud load balancer may silently drop an idle connection, a server may be draining for a deploy, a slow call may hold a stream, and a big message may exceed a limit. These settings decide which of those you notice, and how.

Keepalive pings, and the GOAWAY that answers too many

A keepalive is an HTTP/2 PING sent on a quiet connection; if no ACK comes back within a timeout (20 s by default) the connection is declared dead and calls fail with UNAVAILABLE instead of hanging. Client keepalive is off by default in gRPC core. Servers defend themselves against ping floods: by default they expect at least 5 minutes between pings on a connection that carries no data, and after 2 "strikes" they send GOAWAY with error ENHANCE_YOUR_CALM and close it (gRPC core keepalive guide).

The lab reproduced it: a client set grpc.keepalive_time_ms=1000 and made a call whose first token takes 8 s, so the connection carried no data for 8 s. On the first try nothing happened: the client's own brake (max_pings_without_data, default 2) stopped it after two pings. With that brake removed the server cut the connection mid-call:

The client saw UNAVAILABLE: Too many pings and the in-flight call was lost. This is not a lab curiosity. vLLM's gRPC server (v0.31.0) carries exactly this fix, with the comment that client keepalive and BDP-probe pings arriving while a non-streaming Generate is decoding "are strikes and eventually earn a GOAWAY(ENHANCE_YOUR_CALM, "too_many_pings") that fails every in-flight RPC", so it sets grpc.http2.max_ping_strikes to 0 (vLLM v0.31.0, grpc_server.py). The rule: client keepalive must be slower than the server's minimum ping interval, or the server must be told to accept faster pings.

Misspelt options are ignored silently

The same vLLM file records a second trap: an option name that "expands to a string with no "recv"" was misspelt, "and gRPC Core silently ignores unknown keys, so the misspelt form left the 300s default in force". Channel arguments are plain strings; check them against the core channel argument list and test that the behaviour actually changed.

GOAWAY, connection age and draining

GOAWAY is HTTP/2's "no new streams on this connection": it names the last stream the server accepted, so the client knows which calls are safe to resend elsewhere, and finishes the rest. Servers send it when shutting down, and on a timer if configured: gRPC's server-side connection management adds MAX_CONNECTION_IDLE, MAX_CONNECTION_AGE (with plus or minus 10% jitter so clients do not all reconnect at once) and MAX_CONNECTION_AGE_GRACE, all infinite by default (gRPC proposal A9). Its stated purpose includes making L4 load balancers work: "This option can force the client to periodically reconnect to a L4 LB which allows spreading load more quickly." Section 8 measures that.

Limits that shape latency

  • Message size: 4 MiB received by default (measured in section 6); sending is unlimited by default in gRPC core.
  • Concurrent streams: a server can cap streams per connection with HTTP/2's SETTINGS_MAX_CONCURRENT_STREAMS; calls beyond it queue on the client. The root's Failure lab reproduced it ("Max concurrent streams: calls queue on the connection": six 1-second calls finishing at 1, 2 and 3 s in pairs with a limit of 2). Fix with more connections (a channel pool) or more replicas.
  • Flow-control windows: the recorded SETTINGS show 4 MB windows, grown further by BDP probing; on long links one stream's throughput is window divided by round-trip time (Networking foundations).

Health checking and reflection

gRPC standardises two services every server should offer. Health (grpc.health.v1.Health/Check, answering SERVING or NOT_SERVING, optionally per service) is what balancers and Kubernetes probe; Kubernetes has had native gRPC liveness probes since v1.27, stable (Kubernetes probes docs). The recorded check answered the two bytes 08 01: field 1 = 1, SERVING. Reflection lets a tool ask the server for its schema, which is what makes grpcurl list work without the .proto file; the lab's server listed . Turn reflection off on anything internet-facing: it hands an attacker your whole API surface.

8. Load balancing gRPC: L4, L7 and the client

The problem. You run three replicas of the inference service so that each takes a third of the calls. Something must choose a replica for every call. Where that choice is made, and how often, decides whether you get a third each or one hot replica and two idle ones. With HTTP/1.1 and short connections the answer barely mattered; with gRPC's long-lived multiplexed connections it is the number-one production surprise.

L4 balancer

Works at the transport layer (layer 4): it sees TCP connections, picks a backend once per connection, then copies bytes without reading them. Examples: AWS NLB, Linux IPVS, Kubernetes' kube-proxy, nginx stream.

L7 balancer

Terminates HTTP/2 (layer 7), reads each call's HEADERS, and picks a backend per call; it can also route on :path, retry, and count calls in flight. Examples: Envoy, nginx grpc_pass, a service-mesh sidecar, AWS ALB (gRPC since 29 October 2020, AWS announcement).

Client-side

No balancer in the path: the client's channel learns every backend address (from DNS or a control plane) and picks per call itself, with a policy. gRPC ships pick_first (the default) and round_robin, plus xDS policies (gRPC load balancing doc).

Two rows surprise people. The L4 balancer did its job perfectly: it balanced connections, and there was one. And a client that was given all three addresses still sent everything to backend-1, because the default policy, pick_first, "attempts to connect to those addresses one at a time, in order, until it finds one that is reachable" and then sends all calls there (gRPC load balancing doc). Client-side balancing needs round_robin (or an xDS policy) asked for explicitly, in code or in the service config.

What to do, in order of preference

  1. An L7 proxy that speaks HTTP/2 in front of the replicas (Envoy, nginx grpc_pass, a mesh such as Istio or Linkerd, a cloud L7 balancer with HTTP/2 to the targets). Costs: one more hop and its latency, and the proxy itself must be run and scaled.
  2. Client-side round_robin over every replica address: in Kubernetes a headless Service (clusterIP: None) makes DNS return one A or AAAA record per Pod instead of a virtual IP (Kubernetes Services), and the channel target dns:///name resolves them all. Costs: every client holds a connection to every replica, and new Pods are seen only when the client resolves again. The fixed-list run above is the extreme case: it never saw backend-3.
  3. Proxyless xDS: the client gets endpoints, weights and policies from a control plane (as Envoy does), without a proxy in the data path. Most capable, most moving parts.
  4. An L4 balancer plus MAX_CONNECTION_AGE when nothing else is possible: crude, but it bounds how long imbalance lasts. Costs: periodic reconnects (a TCP and maybe TLS handshake each), so do not set it to seconds in production; minutes is typical.

Kubernetes' default (a ClusterIP Service) is L4: in iptables mode kube-proxy picks a backend Pod "at random" for each new connection (Kubernetes virtual IPs). So a gRPC client of a plain Service behaves like the L4 rows above.

Balancing LLM calls is different

For ordinary services, spreading calls evenly is the goal. LLM calls differ in cost by orders of magnitude (a 50-token chat turn against a 100,000-token document), and a replica that already holds a conversation's prefix in its KV cache can skip most of the prefill. So the router wants to read the request and know each replica's state: queue depth, KV-cache contents, loaded LoRA adapters. That is L7 by definition, and it is where Kubernetes is heading:

  • Gateway API Inference Extension (an official Kubernetes project, v1.6.2 on 17 September 2026): turns any gateway that supports Envoy's external processing into an "inference gateway". An Endpoint Picker chooses the replica for each request from model-server metrics such as prefix-cache status and LoRA adapter availability (project README). The picker's main implementation has moved to the llm-d project's router.
  • The side channel is gRPC. Envoy asks the picker over ExternalProcessor.Process, a bidirectional gRPC stream (rpc Process(stream ProcessingRequest) returns (stream ProcessingResponse) in Envoy's ext_proc API).
  • llm-d (v0.10.0, 29 September 2026) packages prefix-cache-aware and load-aware routing with vLLM, and reports "3x higher output throughput and 2x faster TTFT" against round robin on Llama 3.1 70B with 4 AMD MI300X (llm-d README; a project-reported figure, not reproduced here).

Sometimes you want the pinning. NVIDIA Triton recommends unary inference calls, but notes that a bidirectional gRPC stream "will hold a single connection throughout the lifetime and hence ensure the requests are delivered to the same Triton instance" behind a load balancer, which sequence models need (Triton inference protocols).

9. Browsers, gateways and the gRPC family

The problem. A browser's fetch cannot read HTTP trailers and cannot control HTTP/2 framing, so it cannot speak gRPC as section 4 recorded it. Neither can many HTTP/1.1-only proxies, serverless platforms or third-party developers with only curl. Four answers exist; you will meet all of them.

gRPC-Web

The same messages with the trailers moved into the body: a final length-prefixed frame whose flag byte has its top bit set (0x80) carries grpc-status as text. Works over HTTP/1.1; unary and server streaming only; a proxy (Envoy's grpc_web filter) translates to real gRPC (PROTOCOL-WEB.md).

Connect

A protocol and libraries (a CNCF sandbox project, per connectrpc.com): same .proto files, but a unary call is a plain POST /package.Service/Method with application/json or application/proto, a Connect-Protocol-Version: 1 header and Connect-Timeout-Ms for the deadline; errors use ordinary HTTP status codes with a JSON body. Unary and server streaming work over HTTP/1.1; bidirectional streaming needs HTTP/2 (Connect protocol). curl-able, which is the point.

HTTP/JSON transcoding

Annotate each RPC with the REST shape it should also have, and a gateway (Envoy's JSON transcoder, grpc-gateway) serves both: option (google.api.http) = { post: "/v1/{parent=publishers/*}/books" body: "book" }. Google's rule is that APIs "must" provide this for every RPC except bidirectional streaming (AIP-127). The open-source grpc-gateway does the same from the annotations.

tRPC (not related)

Despite the name, tRPC shares nothing with gRPC: no protobuf, no HTTP/2 requirement, no code generation. It is a TypeScript library where the client imports the server router's type, giving "fully typesafe APIs without schemas or code generation"; on the wire it is ordinary HTTP with JSON, with request batching and subscriptions (tRPC README, v11.19.0 on 16 September 2026).

10. GraphQL: the client chooses the shape

The problem it solves. A model-catalogue page on the web shows each model's name and provider; the mobile app also shows eval scores; an internal tool wants licences. With REST you either make one call per object (the page above would need one request for the list and one per provider) or build a bloated endpoint for each screen. GraphQL (created at Facebook, now a Linux Foundation specification; current edition September 2025, per the root's atlas) gives one endpoint and a typed schema, and lets each client send a query naming exactly the fields it wants:

{ models(first: 20) { name provider { name } } }

The server runs a resolver function per field and returns JSON of exactly that shape. On the toy catalogue in this lab (20 made-up models, 12 fields each) a REST list returning every field is bytes; asking GraphQL for names only is .

Cost 1: one query, many backend calls (N+1)

Resolvers run per object, so a list of 20 models whose provider resolver queries the database makes 1 query for the list plus 20 for providers: the N+1 problem. The fix is a DataLoader: resolvers ask a loader for a key, the loader waits one tick of the event loop, then fetches every requested key in one batched call. Measured with graphql-core against a counting fake database:

Database calls are measured; the fake database sleeps 2 ms per call. Wall times were close because these resolvers run concurrently on one event loop: the price of N+1 here is load on the database (141 queries for one page view), which is what falls over in production.

Cost 2: one query can ask for the world

Nesting multiplies. A query for 3 models, each with 3 similar models, nested deeper, grows by 3 per level; with first: 20 and first: 10 five levels deep, the lab's static estimate (multiply each list's first down the tree, before running anything) came to fields:

Nesting depthEstimated fieldsResolver and database calls (measured)

Public GraphQL APIs therefore price queries before running them. GitHub's API (the best-known public one) caps a call at 500,000 nodes, requires first or last between 1 and 100 on every connection, charges a computed number of points against 5,000 points per hour per user, allows no more than 2,000 points per minute, and stops any request after 10 seconds (GitHub GraphQL limits). Other defences: depth limits, and persisted queries (the server accepts only queries registered in advance, referenced by hash).

Cost 3: HTTP stops helping

  • Caching. Queries usually travel as POST, which HTTP caches ignore. The GraphQL-over-HTTP draft allows GET for queries (never mutations: the server "MUST respond with an appropriate 4xx", 405 recommended) and RFC 10008's QUERY method now offers a cacheable request with a body.
  • Status codes. A field can fail while the rest succeeds. In the lab one resolver failed and the result carried data with null in that field plus an errors array naming its path:


Classic servers answer 200 with that body, so monitoring that counts HTTP 5xx sees nothing. The GraphQL-over-HTTP working draft fixes this for clients that send Accept: application/graphql-response+json: 400 for a document that does not parse, 422 for one that fails validation (GraphQL over HTTP draft, read 5 October 2026). Alert on the errors array, not only on status codes.


Where it fits in ML work. You will mostly consume GraphQL (GitHub's API from tooling and agents) rather than serve it; it is rarely right for model serving, where the request shape is fixed and the cost is in the GPU, not in fetching fields.

11. JSON-RPC 2.0: the smallest call format


The problem it solves. Sometimes you need named method calls over a channel that is not HTTP at all: a pipe to a child process (an MCP server on stdio, a language server in your editor), a WebSocket, or a single HTTP endpoint. JSON-RPC 2.0 is the whole answer in a few pages: "a stateless, light-weight remote procedure call (RPC) protocol", "transport agnostic" (JSON-RPC 2.0 specification, 2010, updated 2013).




Request
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",

    • 

  • A notification is a request with no id: the receiver must not answer. Use it for events ("progress 40%") where a reply would be noise.
    • 

  • Batches: an array of requests, answered by an array of responses (none for notifications).
    • 

  • Reserved error codes: -32700 parse error, -32600 invalid request, -32601 method not found, -32602 invalid params, -32603 internal error, -32000 to -32099 for the server implementation; everything else is yours.

What it leaves out is the point: no schema, no streaming, no deadlines, no transport rules, no auth. A protocol that adopts JSON-RPC must add those, and that is most of what the MCP and A2A specifications are. MCP defines its methods (tools/call, resources/read), its transports (stdio, Streamable HTTP) and its auth on top; it allowed JSON-RPC batches in its 2025-03-26 revision and removed them in 2025-06-18 (MCP page, section on revisions).


Correction carried from the root
The old page said agent protocols "chose JSON-RPC over HTTP (+SSE) rather than gRPC". True of MCP. A2A v1.0 separates the protocol from three bindings: JSON-RPC 2.0, gRPC and HTTP+JSON/REST (root Protocol atlas, corrections list, item 3; A2A v1.0.1 specification).


Choosing between JSON-RPC and gRPC for a new internal protocol: JSON-RPC when the other end is a model or an editor plugin, messages are few, humans read the logs, and the channel may be stdio; gRPC when calls are many, typed, streaming, and cross-language teams need generated clients.

Predict, then reveal (protobuf)


The running request with max_tokens = 300 instead of 16. How many bytes is the protobuf message now (it was 49)?




50. 16 fits in 7 bits (one byte, 10); 300 needs 9 bits, so two varint bytes, ac 02 (the recorded varint table above shows exactly these bytes). The tag 18 (field 3, wire type 0) does not change. Try it in the varint box in section 3.


Predict, then reveal (schema evolution)


Team A deletes uint32 max_tokens = 3 and later adds uint32 priority = 3. An old inference server receives priority = 9. What does it do?




It generates 9 tokens. The wire carries only "field 3, varint, 9"; the old schema calls field 3 max_tokens, so that is what it reads (measured in section 3). Answer b is what happens when the reused number has a different wire type. Prevention: reserved 3; when deleting.


Predict, then reveal (status)


A gRPC call to a server that is down returns in 1 ms. What code, and what would make it wait instead?




UNAVAILABLE ("failed to connect to all addresses", measured in about 1 ms). Without wait-for-ready a call on a channel in TRANSIENT_FAILURE fails at once; with it, the call waits for a connection until its deadline. Use wait-for-ready during start-up races, not to hide a dead dependency.


Predict, then reveal (deadlines)


Client deadline 600 ms. The gateway spends a few milliseconds and calls the inference service, propagating the deadline. What grpc-timeout does the inference service receive?




A little under 600 ms: the lab's frame log recorded grpc-timeout:  on the second hop in run A. The header carries a relative timeout recomputed at each hop, so elapsed time is subtracted and no clocks need to agree.


Predict, then reveal (load balancing)


A Kubernetes Deployment of 3 gRPC Pods sits behind a normal ClusterIP Service. One client process sends 3,000 calls per second on one channel. How are the calls spread?




All on one Pod. kube-proxy chooses a Pod per new connection ("at random" in iptables mode) and the channel has one connection. Measured equivalent: 30 calls through the L4 balancer, 30/0/0. Fix with an L7 proxy or client-side round_robin over a headless Service.

Interview questions


Why does gRPC need HTTP/2, and what breaks if a proxy in the path speaks HTTP/1.1 upstream?
gRPC maps each call to one HTTP/2 stream, sends request and response bodies concurrently for streaming calls, and puts the outcome in trailers after the body. HTTP/1.1 has no multiplexing and no trailers that clients reliably honour, so a proxy that downgrades upstream either fails or loses the status. The te: trailers header exists to detect such proxies; the client then synthesises a status from the HTTP response, which is how the lab saw "Received http2 header with status: 502". gRPC-Web and Connect exist for paths that cannot be HTTP/2 end to end.


Explain deadline propagation and what happens without it in an LLM serving stack.
The caller sets a deadline; each hop passes on the remaining time in grpc-timeout and cancels downstream calls when its caller cancels. Without it, a user who leaves does not stop the generation: in the lab's run D the inference service produced  tokens over  s for a client that had stopped after . On GPUs that is wasted capacity and longer queues for live users. Also: gRPC sets no deadline by default, retries share the original deadline, and stopping work is the server's job.


Your gRPC service is behind an AWS NLB and one instance is hot. Explain and fix.
An NLB is L4: it balances connections, and gRPC clients hold few long-lived connections, so load follows connections, not calls. Options: an ALB (gRPC since 2020) or Envoy for per-call L7 balancing; client-side round_robin with service discovery; or server MAX_CONNECTION_AGE (minutes) so clients reconnect and spread over time. The lab measured 30/0/0 through L4, 10/10/10 through L7, and a new replica reached only after reconnects.


How do you evolve a protobuf schema safely?
Add fields with new numbers (old readers keep them as unknown fields and re-serialise them unchanged, measured); never change a field's number or type; when deleting, reserved both the number and the name; prefer optional or wrapper semantics when "unset" must differ from zero; remember ProtoJSON renames fields to lowerCamelCase, so JSON clients see a second contract. Run a breaking-change checker in CI (buf breaking is one).


When would you choose GraphQL over REST, and what would you put in place on day one?
When many clients need different shapes of the same graph of data and round trips are expensive (mobile, aggregating many backends). Day one: DataLoader batching on every resolver that fetches, a cost or depth limit evaluated before execution, pagination arguments with a maximum (GitHub's 1 to 100), persisted queries for first-party clients, monitoring on the errors array, and per-field authorisation.


Which gRPC status codes would you retry, and how do you stop retries from making an outage worse?
UNAVAILABLE for any method (normally means not processed); others only for idempotent methods. Never blindly retry DEADLINE_EXCEEDED on non-idempotent calls, since the work may have happened. Bound it: maxAttempts (capped at 5), exponential backoff with jitter, retry throttling (token bucket per server), server pushback, the overall deadline, and a retry budget across the system.

Balancer lab: the same calls, four ways to balance them


One client, one channel, one unary call every 50 ms for 7 seconds. The fleet starts with two replicas; backend-3 joins at 1.5 s (the hatched part of its track is before it existed). Each tick is one real call, placed at the time it was sent and on the replica that answered. Press play and watch where the calls go before and after the new replica arrives.








measured on 5 October 2026: nginx 1.31.6 (stream module for L4, grpc_pass for L7, round robin, reloaded with the longer backend list at 1.5 s), three Python gRPC servers (grpcio ), a Python client with one channel per run. The client's round_robin run was given backend-1 and backend-2 only. Script: src/lab/lb_run.py.


Counts: 30 calls on one channel, all three replicas up

What each run teaches, and the Reading section that explains it:


    

  • L4: one connection, one choice, forever. Adding replicas does nothing for existing clients (Reading, section 8).
    • 

  • L4 + MAX_CONNECTION_AGE: the servers close each connection with GOAWAY after about a second, so the client reconnects and the balancer chooses again; the load drifts onto backend-3 within a few reconnects and no call fails. In production use minutes, not a second (section 7).
    • 

  • L7: nginx reads every call and picks per call; the new replica starts taking calls right after the reload.
    • 

  • Client round_robin with a fixed list: perfectly even over what it knows, and blind to what it does not: backend-3 never gets a call. Real deployments refresh the list from DNS (a headless Service) or a control plane (xDS).
    •
