6. Revocation: un-trusting a certificate before it expires

The problem. A private key leaks, or a CA mis-issues. The certificate is still within its dates, so every client would keep trusting it. Revocation is how a CA says "stop", and it has never worked well, which is the deepest reason lifetimes are being cut.

What your code does. Python's ssl, Go's crypto/tls, curl and Node do not check revocation at all by default. For an API client that is usually acceptable because lifetimes are short; for mTLS inside your own systems (section 7) the practical revocation tool is the same: very short-lived certificates (an hour), so that removing a workload's ability to renew is the revocation.

7. Mutual TLS and workload identity

The problem. Inside a cluster, the vLLM server must know that the caller is the gateway and not a notebook someone left running. API keys in headers (see {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}) are bearer secrets: anyone who copies one is the gateway. Mutual TLS (mTLS) makes the caller prove possession of a private key during the handshake, so there is nothing reusable to copy from a log.

How it works, recorded. Same handshake as section 2 with three additions, all inside the encrypted part (the {{Handshake, decrypted|#t-hs}} tab has the full mTLS recording):

  1. The server adds a CertificateRequest ( bytes) to its flight, listing the signature algorithms (and optionally the CAs) it accepts.
  2. The client answers with its own Certificate ( bytes): here a one-day certificate whose only identity is the URI SAN spiffe://lab.test/ns/serving/sa/gateway, with EKU clientAuth.
  3. The client sends a CertificateVerify signing the transcript with its private key, then Finished. The server verifies the chain against its own trust bundle (here the lab's private root), then the signature.

The client's certificate travels encrypted in TLS 1.3 (it was plaintext in TLS 1.2), so an observer cannot learn which workload is calling. Total cost in the recording: the client's flight grew from 1,913 to bytes over the whole connection, one extra signature on the client and one extra verification on the server.

Authentication is not authorization. A valid certificate from your internal CA proves "this is some workload in our trust domain". Your server must still decide whether this identity may call this endpoint: match on the SPIFFE ID or SAN ("only .../sa/gateway may call /v1/messages"), never on "it was signed by our CA", or every workload in the cluster can call everything.

Workload identity: SPIFFE, SPIRE and service meshes

SPIFFE standardises the identity: a URI spiffe://trust-domain/path placed in an X.509 certificate called an SVID ({{SPIFFE ID spec|https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md}}). SPIRE is the reference implementation: an agent on each node attests the workload (which Kubernetes service account, which container image) and hands it short-lived SVIDs over a local Unix socket; by default an X.509 SVID lives 1 hour and a JWT SVID 5 minutes ({{SPIRE server docs|https://github.com/spiffe/spire/blob/main/doc/spire_server.md}}). Istio issues each workload a 24-hour certificate and rotates it at half-life ({{pilot-agent reference|https://istio.io/latest/docs/reference/commands/pilot-agent/}}); in ambient mode a per-node proxy, ztunnel, does mTLS for the pods instead of a sidecar in each ({{Istio ambient|https://istio.io/latest/docs/ambient/overview/}}). Linkerd turns mTLS on by default for all TCP between meshed pods, with 24-hour proxy certificates; its trust anchor and issuer default to one year and must be rotated by you ({{Linkerd|https://linkerd.io/2-edge/features/automatic-mtls/}}). Outside Kubernetes, AWS IAM Roles Anywhere exchanges a certificate from your private CA for temporary AWS credentials lasting 15 minutes to 12 hours ({{AWS docs|https://docs.aws.amazon.com/rolesanywhere/latest/userguide/authentication-create-session.html}}).

Rotation: the real cost of mTLS

Hour-long certificates mean the application must load new ones without restarting. Two measured facts about Python (src/lab/rotate.py, Python 3.13.16, OpenSSL 3.5.9):

Correction to the old page
The old page said Python "needs a whole new SSLContext because you cannot mutate one in place". Measured: calling load_cert_chain() again on the server's existing SSLContext took ms and every connection opened afterwards got the new certificate. A fresh context also works and is cleaner when several settings change at once.

The second fact is the one that bites: a connection keeps the identity it was established with. Connection 1 still carried data under the old certificate after the rotation. gRPC and HTTP/2 connections can live for days, so rotation, revocation and trust-bundle changes never reach them; set a maximum connection age (gRPC's max_connection_age, an idle timeout at the proxy) shorter than your certificate lifetime.

Clock skew is fatal at short lifetimes: 5 minutes of skew is 5/60 = 8% of a one-hour SVID, and a fresh certificate arrives "not yet valid" if the receiver's clock is behind. Run time sync everywhere (on EC2, the Amazon Time Sync Service at 169.254.169.123). Trust-bundle rotation (a new CA) is the hard part: distribute the new root to every verifier first, then start issuing from it, and remove the old root only after every certificate it signed has expired. An overlap, never a cutover.

Where TLS actually terminates

"We have mTLS" usually means the sidecars do. A request can cross a cloud load balancer, an ingress and a sidecar, and each hop that terminates TLS sees plaintext and starts a new connection. An AWS Network Load Balancer in TCP mode passes TLS through untouched; an Application Load Balancer terminates it, and a backend behind it cannot see the original client certificate unless the terminator forwards it in a header (Envoy's x-forwarded-client-cert, nginx's $ssl_client_escaped_cert). If you do that, strip the header from every untrusted source, or anyone can send a forged one: an authentication bypass you built yourself.

Public certificates for client authentication are ending

Browsers want public CA hierarchies used only for server authentication. The {{Chrome Root Program policy|https://googlechrome.github.io/chromerootprogram/crp/policy/}} (version 1.8, 5 February 2026, section 1.3.2) requires subordinate CAs disclosed from 15 June 2026 to assert serverAuth only, and leaf certificates issued from 15 March 2027 to carry only serverAuth. CAs are moving ahead of it: Let's Encrypt dropped clientAuth from its default profile on 11 February 2026 and ended its opt-in client profile on 8 July 2026 ({{Let's Encrypt|https://letsencrypt.org/2025/05/14/ending-tls-client-authentication/}}); DigiCert stopped adding it by default on 1 October 2025 and removes it entirely on 1 March 2027 ({{DigiCert|https://knowledge.digicert.com/alerts/sunsetting-client-authentication-eku-from-digicert-public-tls-certificates}}). The survey shows the transition: 11 of 12 public leaves are serverAuth only; the twelfth (pypi.org, issued December 2025) still has both.

What to do
If any service-to-service mTLS uses publicly trusted certificates on the client side, move it to a private CA (AWS Private CA, SPIRE, Vault, cert-manager with a private issuer) before your CA stops issuing them. This answers the date question the {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}} page left open: the old pages' "February 2027" and "March 2027" were each half right (Sectigo's date could not be confirmed here; Chrome's leaf deadline is 15 March 2027).
Predict, then reveal: after rotating a service's mTLS certificate, its dashboards show some callers still presenting the old certificate two days later, though every pod restarted. Where are they coming from?
Long-lived connections that were established before the rotation, typically through a proxy or a client-side connection pool that did not restart (an L4 load balancer keeps the TCP connection; HTTP/2 multiplexes on it for days). They will keep the old identity until they close. Set a maximum connection age on the server and on the proxies.
