1. The four building blocks, from zero

The problem in one picture. Picture three attackers on the path. A passive one records everything (a coffee-shop Wi-Fi, a tap at an internet exchange, or someone storing traffic to decrypt in ten years). An active one also changes bytes in flight. An impostor answers in the server's place (a poisoned DNS answer or a hostile proxy sends you to their machine). TLS defeats all three with four tools. You never implement them, but every TLS error message is about one of them, so it pays to know what each does.

Tool 1: symmetric authenticated encryption (AEAD)

One secret key, shared by both ends, encrypts and decrypts. Modern TLS uses an AEAD (Authenticated Encryption with Associated Data) cipher: AES-GCM or ChaCha20-Poly1305. Each encrypted record carries a 16-byte tag, a cryptographic checksum that only a holder of the key can compute; change one bit and decryption fails. That gives confidentiality and integrity together. It is fast: AES-128-GCM ran at on one core of this laptop, ChaCha20-Poly1305 at (OpenSSL 3.6 speed, 16 KB blocks), so encrypting a token stream costs nothing you will notice. ChaCha20 exists for CPUs without AES instructions (older phones); servers with AES hardware prefer AES-GCM.

Checked on the recording: the running request is 277 bytes of HTTP; on the wire it became one encrypted record of 294 bytes: 277 + 1 byte of hidden content type + 16 bytes of tag = 294 ({{RFC 9846 section 5.2|https://www.rfc-editor.org/rfc/rfc9846#section-5.2}}). Each streamed token record grows the same 17 bytes.

Tool 2: key exchange (how two strangers agree on that key in public)

The shared key cannot be sent, since the passive attacker would read it. Diffie-Hellman (DH) solves this: each side keeps a random private number and sends a public value derived from it; each combines its own private number with the other's public value and both arrive at the same secret, while someone who saw both public values cannot compute it. TLS uses an elliptic-curve version (X25519: 32-byte public values) and, since 2024 to 2026, a hybrid with ML-KEM that resists quantum computers (section 8). Below, the same idea with toy numbers you can follow by hand: real ones are 255-bit, and the attacker's job (recover a from A) is then infeasible.

Illustrative: toy-sized numbers with generator g = 5. Real TLS uses X25519 or X25519MLKEM768 (section 2).

Forward secrecy follows: the private numbers are fresh per connection and thrown away, so a server key stolen next year cannot decrypt today's recording. TLS 1.2 also allowed "RSA key transport" (the client encrypted the secret to the server's certificate key), which had no forward secrecy; TLS 1.3 removed it.

A KEM (key encapsulation mechanism) is the same job in a different shape: the client sends a public key, the server uses it to encapsulate a fresh random secret and sends back the ciphertext; only the client can open it. ML-KEM is a KEM. TLS 1.3's key_share carries either kind.

Tool 3: hash functions and key derivation

A hash (SHA-256, SHA-384) turns any input into a fixed-size fingerprint; changing the input changes the fingerprint unpredictably. TLS hashes the whole conversation so far (the transcript) and feeds it, with the DH secret, into HKDF, a key-derivation function that stretches one secret into many independent keys: one per direction, one for the handshake, one for application data, one for resumption ({{RFC 9846 section 7.1|https://www.rfc-editor.org/rfc/rfc9846#section-7.1}}). Because every key depends on the transcript, an attacker who changes any handshake byte makes the two sides derive different keys, and the Finished check fails.

Tool 4: signatures and certificates (who is on the other end)

Key exchange alone would happily agree a key with an impostor. A signature scheme fixes that: a private key signs, the matching public key verifies, and nobody without the private key can forge one (ECDSA P-256 here: a 65-byte public key and signatures of about 70 bytes, 70 in the recording; RSA-2048; and the post-quantum ML-DSA). The server signs the handshake transcript with its private key. But how does the client know which public key is the real API's? A certificate answers: a document saying "the public key K belongs to the name api.anthropic.com", signed by a certificate authority (CA). The CA's own certificate is signed by another, up to a root certificate that ships in your operating system or language runtime: the trust store. Sections 4 to 6 are about this chain of trust and where it breaks.

The whole handshake in one sentence
Agree a fresh secret in public (tool 2), prove who you are by signing the transcript with the key a CA vouched for (tool 4), confirm the transcript matches on both sides (tool 3), then encrypt everything with keys derived from that secret (tool 1).
Predict, then reveal: what does the passive attacker still learn?
Encryption hides content, not shape.
