8. Post-quantum TLS: key exchange is done, signatures are not

The threat. A large enough quantum computer running Shor's algorithm would break the elliptic-curve and RSA mathematics behind both key exchange and signatures. Nobody has one. But the two halves of TLS are exposed differently:

Key exchange: urgent

An attacker can record today and decrypt later ("harvest now, decrypt later"). Anything that must stay secret for years (prompts with personal data, model weights in transit, credentials) is already at risk if recorded. The fix has to be deployed before the computer exists, and it has been.

Signatures: not urgent yet

Forging a signature only helps an attacker during a handshake, in real time. A quantum computer that arrives in 2035 cannot retroactively impersonate a server in 2026. So authentication can migrate later, and the size cost (below) makes everyone wait for a better design.

Key exchange: hybrid ML-KEM, on by default

NIST published the first post-quantum standards on 13 August 2024: {{FIPS 203|https://csrc.nist.gov/pubs/fips/203/final}} (ML-KEM, a lattice-based key encapsulation), {{FIPS 204|https://csrc.nist.gov/pubs/fips/204/final}} (ML-DSA signatures) and FIPS 205 (SLH-DSA, hash-based signatures). TLS deploys ML-KEM as a hybrid: the X25519 exchange and ML-KEM-768 run side by side and both outputs feed the key schedule, so the connection is safe if either one holds (a hedge against a flaw in the new mathematics). {{RFC 10024|https://www.rfc-editor.org/rfc/rfc10024}} (August 2026) fixed the code points and sizes:

GroupCode pointClient shareServer shareOrder inside
X25519MLKEM7680x11EC1,216 B1,120 BML-KEM first, then X25519
SecP256r1MLKEM7680x11EB1,249 B1,153 BECDH first, then ML-KEM
SecP384r1MLKEM10240x11ED1,665 B1,665 BECDH first, then ML-KEM

The client share is ML-KEM-768's 1,184-byte encapsulation key plus 32 bytes of X25519; the server share is the 1,088-byte ciphertext plus 32. The reversed order of X25519MLKEM768 is deliberate and a real interoperability trap for anyone implementing it by hand. The 2024 experimental X25519Kyber768Draft00 code point is obsolete and does not interoperate.

Where deployment is. OpenSSL 3.5.0 (8 April 2025) prefers the hybrid and sends X25519MLKEM768 and X25519 shares by default ({{release notes|https://openssl-library.org/news/openssl-3.5-notes/}}); Go 1.24 enables it by default ({{Go 1.24 notes|https://go.dev/doc/go1.24#cryptotlspkgcryptotls}}); Apple's iOS 26 and macOS 26 advertise it on all TLS 1.3 connections ({{Apple|https://support.apple.com/en-us/122756}}). Cloudflare saw post-quantum key agreement on over 60% of client requests in February 2026, while only about 10% of origin servers supported it ({{Cloudflare, 27 February 2026|https://blog.cloudflare.com/radar-origin-pq-key-transparency-aspa/}}). ML-KEM-768 is faster than X25519 per operation; the hybrid costs a few tens of microseconds per handshake. What it adds is about 1.2 KB in each direction: the ClientHello grew from 236 to 1,458 bytes in the HelloRetryRequest runs of section 2. That spills over one 1,500-byte packet once extensions are added, and network devices that inspect TLS (firewalls, TLS-inspecting proxies) must handle a ClientHello split across packets and a group they may not know; Apple's guidance to network administrators for iOS 26 is about exactly this ({{Apple|https://support.apple.com/en-us/122756}}). Not reproduced here. The symptom after upgrading a TLS library or base image: handshakes fail or hang through one particular network only. Test against your own proxies before rolling out; the workaround while the box is fixed is to configure that client's groups to X25519 only.

Signatures: why post-quantum certificates are not here yet

ML-DSA works, but it is large: an ML-DSA-44 public key is 1,312 bytes and a signature 2,420 bytes, against 65 and about 70 for ECDSA P-256 (FIPS 204 table 2). A handshake carries several signatures: the CertificateVerify, the signature on each certificate in the chain, and the CT timestamps inside the leaf. The line that matters is the initial congestion window: a new TCP connection may send only 10 segments (about 14,600 bytes with 1,460-byte segments) before waiting one round trip for acknowledgements ({{RFC 6928|https://www.rfc-editor.org/rfc/rfc6928}}; see {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}} for congestion control). The ECDSA flight is about 2.4 KB. ML-DSA-65 crosses the window on its own, before CT timestamps (in a real public certificate, two more ML-DSA-44 signatures would add about 2 × 2,420 = 4,840 bytes, computed, not measured): a whole extra round trip on every new connection.

The way out: Merkle Tree Certificates. Instead of signing each certificate, the CA adds certificates to a batch, builds a Merkle tree and signs only the tree's root; browsers fetch the signed roots ahead of time, so a handshake carries one signature plus a short inclusion proof, smaller even than today's classical chain. The design is an IETF draft ({{draft-ietf-plants-merkle-tree-certs-06|https://datatracker.ietf.org/doc/draft-ietf-plants-merkle-tree-certs/}}, 21 September 2026). Cloudflare and Chrome began an experiment on 28 October 2025 ({{Cloudflare|https://blog.cloudflare.com/bootstrap-mtc/}}); Chrome plans to bootstrap public MTCs in the first quarter of 2027 and a quantum-resistant root store accepting only MTCs in the third quarter of 2027, with no immediate plan to admit post-quantum X.509 certificates ({{Google Security Blog, 27 February 2026|https://security.googleblog.com/2026/02/cultivating-robust-and-efficient.html}}). Let's Encrypt plans MTC staging in late 2026 and production in 2027 ({{Let's Encrypt, 3 June 2026|https://letsencrypt.org/2026/06/03/pq-certs}}).

Deadlines. Google set 2029 for its own migration ({{Google, 25 March 2026|https://blog.google/innovation-and-ai/technology/safety-security/cryptography-migration-timeline/}}). The NSA's CNSA 2.0 asks US national-security systems to support and prefer post-quantum algorithms in web browsers, servers and cloud services now and to use them exclusively by 2033, with all systems quantum-resistant by 2035 (the NSA's PDF could not be fetched for this page; dates as widely reported, not re-checked). NIST also chose HQC on 11 March 2025 as a backup KEM built on different mathematics, with a final standard expected in 2027 ({{NIST|https://www.nist.gov/news-events/news/2025/03/nist-selects-hqc-fifth-algorithm-post-quantum-encryption}}).

What to do now
Make sure your own servers and internal hops negotiate X25519MLKEM768: upgrading to OpenSSL 3.5 or later, Go 1.24 or later, or a current managed load balancer is usually all it takes, and the client half of the internet already offers it. Check with openssl s_client -connect host:443 -groups X25519MLKEM768 -brief (OpenSSL 3.5+): the output names the negotiated group. Leave certificates alone until MTCs arrive.
Predict, then reveal: two of the twelve surveyed endpoints negotiated plain X25519. Is traffic to them at risk today?
Its confidentiality is at risk later: anyone recording it now could decrypt it once a large quantum computer exists. Authentication is not at risk today. The client offered the hybrid; the servers (or their load balancers) did not support it, so the fix is on their side.
