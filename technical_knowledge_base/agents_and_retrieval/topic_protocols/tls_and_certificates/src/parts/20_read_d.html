3. Resumption and 0-RTT: cheaper reconnects, and a replay trap

The problem. A full handshake costs a round trip plus asymmetric cryptography (a key exchange and a signature on the server, a verification and certificate checks on the client). Clients reconnect to the same server all the time.

How resumption works. After the handshake the server sends a NewSessionTicket (the 249-byte message in the recording): an opaque blob, usually the session's resumption secret encrypted under a key only the server fleet knows (a session ticket key), plus a lifetime. Next time the client puts that ticket in its ClientHello as a pre-shared key (PSK). If the server can decrypt it, both sides skip the certificate and its signature. With the psk_dhe_ke mode they still do a fresh key exchange, so forward secrecy holds; the alternative psk_ke skips it and loses forward secrecy for that connection ({{RFC 9846 section 4.2.9|https://www.rfc-editor.org/rfc/rfc9846#section-4.2.9}}). The client in the recording offers only psk_dhe_ke.

On a real network add one TCP round trip and one TLS round trip to each new connection (resumed or not); the parent page's {{On the wire|n:3c65c17b0d0d81ec9355f4eecd6eed02}} tab measured cold against resumed on an emulated 50 ms path. The lesson for clients is unchanged: one long-lived connection pool per process. A new httpx.Client or requests.Session per call pays all of this per call.

How resumption fails silently. Behind a load balancer, each terminator that creates tickets with its own random key cannot decrypt the others' tickets; resumption then "works" only when you happen to land on the same machine, and nothing logs an error. Fleets share and rotate ticket keys (nginx ssl_session_ticket_key, files rotated by your own tooling), which is the setup used below. A stolen ticket key decrypts every ticket made with it, so rotate it often (daily is common) and keep it out of disks and backups.

0-RTT early data: sending the request before the handshake finishes

With a ticket, the client can derive an early traffic key from the PSK alone and send application data in its very first flight, alongside the ClientHello: zero round trips before the request leaves. The catch is in {{RFC 9846 section 8|https://www.rfc-editor.org/rfc/rfc9846#section-8}}: early data is not protected against replay. The server has not contributed any fresh randomness yet, so an attacker who recorded the first flight can send the same bytes again and the server will decrypt the same request again. Server-side defences (single-use tickets, a cache of recent ClientHellos, freshness windows) are all partial, especially across many servers.

Recorded here (src/lab/zero_rtt.py, nginx 1.31.6 with OpenSSL 3.6.5, ssl_early_data on): two nginx instances standing for two front ends of one fleet share a ticket key; behind them a stand-in backend counts "generations" (each POST is one billed generation). An openssl s_client makes a full handshake and keeps the ticket, then resumes and sends the running request as early data through a recording proxy. The attacker then resends the recorded first flight, byte for byte, without knowing any key:

The replays did not even need to complete a handshake: the backend had already run the request. Three replays, three extra billed generations; in an agent loop each could be a repeated side-effecting tool call. nginx's documentation warns about exactly this and suggests forwarding $ssl_early_data to the backend ({{ssl_early_data|https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_early_data}}); OpenSSL's own replay protection (on by default in s_server, per {{its manual|https://docs.openssl.org/master/man1/openssl-s_server/}}) depends on a server-side session cache, which a fleet of stateless-ticket terminators does not have.

The standard fix is {{RFC 8470|https://www.rfc-editor.org/rfc/rfc8470}}: the terminator marks requests that arrived as early data with Early-Data: 1; a backend that cannot tolerate replay answers 425 Too Early, and a conforming client retries after the handshake completes. The second run above does that: the early request and its replay both got 425 and no generation ran.

Rule
Never accept non-idempotent requests as 0-RTT: no generations, no tool calls, no payments, no writes. If early data is on at your edge (some CDNs offer it as a toggle), make sure the origin sees Early-Data: 1 and refuses with 425. The saving (one round trip on resumed connections) is rarely worth it for an API that then thinks for seconds; a kept-alive connection saves more.
Predict, then reveal: does QUIC (HTTP/3) avoid the replay problem?
No. QUIC uses the TLS 1.3 handshake (RFC 9001) and has the same 0-RTT with the same replay property; HTTP/3 clients must follow the same rules. The parent page's On the wire tab recorded an HTTP/3 0-RTT attempt.
Predict, then reveal: in step 2 the client got "Early data was accepted" but also 425. What should a correct client do?
Resend the request after the handshake has completed (RFC 8470 section 5.2). openssl s_client does not, so the run stops at 425. Browsers and HTTP libraries that implement early data retry automatically; check yours before enabling it.
