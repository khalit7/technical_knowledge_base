9. Trust stores, TLS inspection and the classic failures

Every client has its own trust store, and they are not the same file. macOS and Windows keep one in the operating system (Keychain, the Windows certificate store); browsers use the OS store or their own (Firefox); Linux distributions ship /etc/ssl/certs; Python's requests uses the certifi package (Mozilla's list frozen when the package was built); Node ships its own copy of Mozilla's list. So "I installed our corporate root" may have fixed one client and not the others.

Measured: which variable does each client read? A local server presented a certificate from the lab's private root; each client ran with no variable, then with exactly one variable pointing at that root (src/lab/trust_matrix.py; Python 3.13, requests 2.34, httpx 0.28, certifi , Node , macOS curl 8.7.1):

Readings: SSL_CERT_FILE is read by OpenSSL-based tools and by Python's default context and httpx, but not by requests, which uses certifi unless REQUESTS_CA_BUNDLE or CURL_CA_BUNDLE is set. NODE_EXTRA_CA_CERTS is read only by Node, and it adds to the built-in list. truststore read none of them: it asks the operating system (Keychain on this Mac), where the lab root was not installed. And setting SSL_CERT_FILE replaces the default list rather than adding to it: The safe pattern is a bundle file containing the public roots plus yours.

TLS-inspecting proxies

Many companies route traffic through a proxy that terminates TLS, inspects it and re-encrypts it with certificates signed on the fly by a company root pushed to managed laptops' OS stores. Browsers trust it (they use the OS store); Python with certifi, Node, and anything in a Docker container do not, so pip install, huggingface_hub downloads and docker pull fail with unable to get local issuer certificate while the browser works. Look at the issuer in openssl s_client output: if it names your company or a security vendor instead of a public CA, that is the cause. The laptop this page was built on shows a variant: a DNS filter answers some names with a block page whose certificate fails verification, so the symptom is a certificate error and the cause is DNS (the parent's Failure lab case "A TLS error caused by DNS: the name was answered by a filter").

Fixes, best first. Use the OS store from Python: pip has done so by default since version 24.2 through truststore ({{pip docs|https://pip.pypa.io/en/stable/topics/https-certificates/}}), and your own code can call truststore.inject_into_ssl(). Otherwise build one bundle (certifi's file plus the company root) and point SSL_CERT_FILE and REQUESTS_CA_BUNDLE at it; in containers, add the root to the image's system store (update-ca-certificates). Pin a recent certifi: an old one in a Docker image lacks newer roots and keeps distrusted ones.

Turning verification off is never the fix

verify=False, curl -k, Go's InsecureSkipVerify: true, Node's NODE_TLS_REJECT_UNAUTHORIZED=0, ssl._create_unverified_context(): each keeps encryption and drops authentication, which means encrypting to whoever answers, attacker included. Two subtler variants: ssl.CERT_NONE also turns off hostname checking, and turning off check_hostname while keeping CERT_REQUIRED accepts any valid certificate for any name, which looks secure and is not. A CI rule that greps for these strings is cheap.

Debugging toolkit

# what does the server send, and does it verify against THIS store?
openssl s_client -connect host:443 -servername host -showcerts -CAfile bundle.pem </dev/null
# version, cipher and key-exchange group only (OpenSSL 3.5+ prints the group)
openssl s_client -connect host:443 -servername host -brief </dev/null
# what does curl negotiate and which issuer does it see?
curl -v https://host/ -o /dev/null 2>&1 | grep -E 'SSL connection|issuer|subject|ALPN'
# expiry of a local file, and of a remote host
openssl x509 -in cert.pem -noout -enddate
echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -enddate
# decrypt your own traffic in Wireshark: Python, curl (OpenSSL builds), Firefox and Chrome honour this
SSLKEYLOGFILE=/tmp/keys.log python client.py      # then Wireshark: TLS, (Pre)-Master-Secret log filename

The key-log mechanism is how this page decrypted its own recordings. The file holds session secrets that decrypt the recorded traffic: treat it like a password and never enable it in production.

Monitoring. Alert on days remaining on the certificate actually served (probe it, as above), not on "the renewal job succeeded": the job can succeed while the server keeps serving the old file because nothing reloaded it. With 47-day certificates, alert when less than a third of the lifetime remains.
