2. The TLS 1.3 handshake, message by message

Everything below comes from one recording: the running request sent by a Python 3.13 client (OpenSSL 3.5.9) to a local TLS server, every byte that crossed the socket logged, and the client's session secrets written to a key log (the SSLKEYLOGFILE mechanism Wireshark uses) so this page could decrypt every record (src/lab/hs_record.py).

Flight 1, client: ClientHello (1,529 bytes, readable by anyone)

The client cannot wait to learn what the server supports, so it guesses and sends everything needed to finish in one round trip: the server name (SNI) and wanted protocol (ALPN) in clear, the cipher suites, and key shares for its best guesses, X25519MLKEM768 (1,216 bytes) and x25519 (32). The hybrid share is why this ClientHello is 1,529 bytes; without it OpenSSL's is about 240.

Every ClientHello field, and why it is there
  • random (32 bytes) and cipher_suites: in TLS 1.3 a suite names only the AEAD and the hash (TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256); key exchange and signature are negotiated separately. This client also lists TLS 1.2 suites in case the server is old.
  • server_name (SNI): api.llm.test, in clear, so one IP address can host many sites and pick the right certificate. alpn: http/1.1 here (a browser sends h2 too); there is no other way to reach HTTP/2 over TLS.
  • supported_versions: TLS 1.3, TLS 1.2. The legacy version field still says 1.2, a fossil kept because middleboxes broke on new values.
  • key_share: public values for its best guesses, X25519MLKEM768 (1,216 bytes, post-quantum hybrid) and x25519 (32 bytes). The hybrid share is why this ClientHello is 1,529 bytes; without it OpenSSL's is about 240 (section 8).
  • signature_algorithms it can verify (this OpenSSL lists ML-DSA first, then ECDSA, Ed25519, RSA-PSS) and psk_key_exchange_modes psk_dhe_ke: "if we resume, still do a fresh key exchange" (section 3).

Flight 2, server: ServerHello, then everything else encrypted

ServerHello (1,210 bytes, readable): the chosen suite TLS_AES_256_GCM_SHA384, the version, and the server's key_share for X25519MLKEM768: 1,120 bytes (the ML-KEM ciphertext of 1,088 plus a 32-byte X25519 value, the sizes in {{RFC 10024 section 4|https://www.rfc-editor.org/rfc/rfc10024#section-4}}). Both sides can now compute the shared secret, and the server switches to handshake keys. Everything after this is encrypted, the big privacy change from TLS 1.2:

  • EncryptedExtensions (21 bytes inside a 38-byte record): the chosen ALPN, http/1.1.
  • Certificate (917 bytes): the server's certificate (478 bytes) and the intermediate CA's (421 bytes). Not the root: the client already has it.
  • CertificateVerify (78 bytes): an ECDSA P-256 signature (70 bytes) over the transcript hash, proving the server holds the certificate's private key ({{RFC 9846 section 4.4.3|https://www.rfc-editor.org/rfc/rfc9846#section-4.4.3}}).
  • Finished (52 bytes): an HMAC over the transcript under a key derived from the handshake secret.

On the wire an observer sees five records all labelled application_data, plus one meaningless one-byte change_cipher_spec sent only so that old middleboxes believe they are watching TLS 1.2 ({{RFC 9846 appendix D.4|https://www.rfc-editor.org/rfc/rfc9846#appendix-D.4}}).

Flight 3, client: Finished, then the request in the same burst

The client verifies the chain and the signature, checks the server's Finished, sends its own Finished (69-byte record) and, without waiting, the request (294-byte record): one round trip after TCP's. The server then sends a NewSessionTicket (249 bytes) for later resumption, and the answer streams in records of 396, then 139 to 143 bytes per token.

In TLS 1.2 the certificate is readable on the wire; in mTLS the client's own certificate and its SPIFFE ID travel encrypted. How the page decrypts the records
The key log gives CLIENT_HANDSHAKE_TRAFFIC_SECRET, SERVER_HANDSHAKE_TRAFFIC_SECRET and the two application traffic secrets. For each, key = HKDF-Expand-Label(secret, "key", "", 32) and iv = HKDF-Expand-Label(secret, "iv", "", 12) ({{RFC 9846 section 7.3|https://www.rfc-editor.org/rfc/rfc9846#section-7.3}}); record n of a direction uses nonce = iv XOR n, and the 5-byte record header is the associated data; every TLS 1.3 record is decrypted with AES-256-GCM. The inner plaintext ends with the real content type and optional zero padding (none was used here). The TLS 1.2 recording is shown as observed only: decrypting it needs the TLS 1.2 PRF, which this page does not implement, and nothing hidden in it is not also shown by the TLS 1.3 recordings. What else TLS 1.3 removed, and what RFC 9846 changed
From {{RFC 9846 section 1.2|https://www.rfc-editor.org/rfc/rfc9846#section-1.2}} and the original RFC 8446 list: static RSA and static DH key exchange (no forward secrecy), custom DH groups, compression (the CRIME attack), renegotiation (replaced by KeyUpdate and post-handshake authentication), CBC-mode and RC4 ciphers, SHA-1 and MD5 signatures. RFC 9846 itself changed less: it makes updating keys before the key-usage limits a MUST ({{section 5.5|https://www.rfc-editor.org/rfc/rfc9846#section-5.5}}), limits how often KeyUpdate may be sent, forbids reusing a key share across connections and adds a generic_error alert. Two companions published the same month: {{RFC 9851|https://www.rfc-editor.org/rfc/rfc9851}} freezes TLS 1.2 (security fixes only; "PQC for TLS 1.2 will not be specified at any time") and {{RFC 9852|https://www.rfc-editor.org/rfc/rfc9852}} says new protocols must require TLS 1.3.

When the guess is wrong: HelloRetryRequest

If the server accepts none of the client's key shares, it replies with a HelloRetryRequest (a ServerHello with a fixed magic random value) naming the group it wants, and the client starts over: one extra round trip ({{RFC 9846 section 4.1.4|https://www.rfc-editor.org/rfc/rfc9846#section-4.1.4}}). So a client that offers only a hybrid share to a server that only does classical X25519, or the reverse, pays a full round trip on every new connection. OpenSSL 3.5 and later send both shares by default for exactly this reason ({{OpenSSL 3.5 release notes|https://openssl-library.org/news/openssl-3.5-notes/}}); a hand-tuned groups list can undo it.

Encrypted Client Hello: hiding the last plaintext

After TLS 1.3 the only content an observer still reads is the ClientHello, and its SNI says exactly which site you visit. Encrypted Client Hello (ECH, {{RFC 9849|https://www.rfc-editor.org/rfc/rfc9849}}, March 2026) splits it: an outer ClientHello naming a shared front end (a CDN's public name) and an inner one, with the real SNI and ALPN, encrypted to a public key the front end publishes in its DNS HTTPS record ({{RFC 9848|https://www.rfc-editor.org/rfc/rfc9848}}). It only hides something if many sites share the front end, so in practice it is a CDN feature; it is pointless over plaintext DNS, which leaks the name anyway (see {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}}); and networks that filter by SNI lose that signal, so an ECH client behind such a filter fails in ways that look like network errors rather than policy blocks.

Predict, then reveal: a corporate firewall blocks a site by SNI. Over TLS 1.3 without ECH, can it still see the server's certificate?
No. In TLS 1.3 the Certificate message is encrypted (record 5 in the recording is 934 bytes of ciphertext). In TLS 1.2 it was readable, which is why older filters inspected certificates. A TLS 1.3 filter can only see SNI, ALPN and the IP address, unless it breaks TLS by acting as a proxy with its own CA (section 9).
