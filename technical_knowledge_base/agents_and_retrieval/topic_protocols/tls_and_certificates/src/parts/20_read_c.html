2. The TLS 1.3 handshake, message by message

Everything below comes from one recording: the running request sent by a Python 3.13 client (OpenSSL 3.5.9) to a local TLS server on 127.0.0.1, every byte that crossed the socket logged, and the client's session secrets written to a key log (the SSLKEYLOGFILE mechanism Wireshark uses) so this page could decrypt every record. The {{Handshake, decrypted|#t-hs}} tab steps through it record by record, with the mTLS and TLS 1.2 versions. Script: src/lab/hs_record.py.

Flight 1, client to server: ClientHello (1,529 bytes, readable by anyone)

The client cannot wait to learn what the server supports, so it guesses and sends everything needed to finish in one round trip:

  • random (32 bytes) and cipher_suites: the AEAD plus hash pairs it accepts. In TLS 1.3 a suite names only those two (TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256); key exchange and signature are negotiated separately. This client also lists TLS 1.2 suites in case the server is old.
  • server_name (SNI): api.llm.test, in clear, so one IP address can host many sites and pick the right certificate.
  • alpn: the application protocols it can speak after TLS (http/1.1 here; a browser sends h2 and http/1.1). This is how HTTP/2 is chosen; there is no other way to reach HTTP/2 over TLS.
  • supported_versions: TLS 1.3, TLS 1.2. The legacy version field still says 1.2, a fossil kept because middleboxes broke on new values.
  • supported_groups and key_share: the key-exchange methods it accepts, and actual public values for its best guesses. Here two shares: X25519MLKEM768 (1,216 bytes, post-quantum hybrid) and x25519 (32 bytes). The hybrid share is why this ClientHello is 1,529 bytes; without it, OpenSSL's ClientHello is about 240 bytes (measured in section 8).
  • signature_algorithms: which signatures it can verify (this OpenSSL lists ML-DSA first, then ECDSA, Ed25519, RSA-PSS); psk_key_exchange_modes: psk_dhe_ke, meaning "if we resume, still do a fresh key exchange" (section 3).

Flight 2, server to client: ServerHello, then everything else encrypted

ServerHello (1,210 bytes, readable): the chosen suite TLS_AES_256_GCM_SHA384, the chosen version (in the supported_versions extension) and the server's key_share for X25519MLKEM768: 1,120 bytes (the ML-KEM ciphertext of 1,088 plus a 32-byte X25519 value, exactly the sizes in {{RFC 10024 section 4|https://www.rfc-editor.org/rfc/rfc10024#section-4}}). From this moment both sides can compute the shared secret, and the server switches to handshake keys derived from it. Everything after this is encrypted, which is the big privacy change from TLS 1.2:

  • EncryptedExtensions (21 bytes inside a 38-byte record): the chosen ALPN, http/1.1.
  • Certificate (917 bytes): the server's certificate (478 bytes) and the intermediate CA's (421 bytes). Not the root: the client already has it.
  • CertificateVerify (78 bytes): an ECDSA P-256 signature (70 bytes) over the transcript hash, proving the server holds the private key of the certificate it just sent ({{RFC 9846 section 4.4.3|https://www.rfc-editor.org/rfc/rfc9846#section-4.4.3}}).
  • Finished (52 bytes): an HMAC over the transcript under a key derived from the handshake secret. If an attacker had altered any earlier byte, this check would fail.

On the wire an observer sees five records all labelled application_data, plus one meaningless one-byte change_cipher_spec sent only so that old middleboxes believe they are watching TLS 1.2 ({{RFC 9846 appendix D.4|https://www.rfc-editor.org/rfc/rfc9846#appendix-D.4}}). The real type is hidden inside the encryption.

Flight 3, client: Finished, then the request in the same packet burst

The client verifies the chain and the signature, checks the server's Finished, sends its own Finished (69-byte record) and, without waiting, the request (294-byte record). One round trip after TCP's, the request is on its way. The server then sends a NewSessionTicket (249 bytes) for later resumption, and the answer streams in records of 396, then 139 to 143 bytes per token.

Checked on this page, not just asserted
From the key log and the decrypted bytes, hs_record.py recomputes the server's and the client's Finished values with HKDF and HMAC and verifies the server's CertificateVerify signature with the public key from the decrypted certificate: . src/recompute.py redoes it from raw/.

Before and after: what a passive observer sees, TLS 1.2 against TLS 1.3

The same request, the same server and certificate, recorded twice: once with the server limited to TLS 1.2. Each arrow is one network trip. Watch the counters: how many round trips before the request can leave, and how much an observer on the path can read.

What TLS 1.3 removed besides the extra round trip ({{RFC 9846 section 1.2|https://www.rfc-editor.org/rfc/rfc9846#section-1.2}} and the original RFC 8446 list): static RSA and static DH key exchange (no forward secrecy), custom DH groups, compression (the CRIME attack), renegotiation (replaced by KeyUpdate and post-handshake authentication), CBC-mode and RC4 ciphers, SHA-1 and MD5 signatures. RFC 9846 itself changed less: it makes updating keys before the key-usage limits a MUST ({{section 5.5|https://www.rfc-editor.org/rfc/rfc9846#section-5.5}}), limits how often KeyUpdate may be sent, forbids reusing a key share across connections and adds a generic_error alert. Two companions published the same month: {{RFC 9851|https://www.rfc-editor.org/rfc/rfc9851}} freezes TLS 1.2 (security fixes only; "PQC for TLS 1.2 will not be specified at any time") and {{RFC 9852|https://www.rfc-editor.org/rfc/rfc9852}} says new protocols must require TLS 1.3.

When the guess is wrong: HelloRetryRequest

The client sent key shares for its best guesses. If the server accepts none of them, it replies with a HelloRetryRequest (a ServerHello with a fixed magic random value) naming the group it wants, and the client starts over with a second ClientHello: one extra round trip ({{RFC 9846 section 4.1.4|https://www.rfc-editor.org/rfc/rfc9846#section-4.1.4}}). So a client that offers only a hybrid share to a server that only does classical X25519, or the reverse, pays a full round trip on every new connection. OpenSSL 3.5 and later send both shares by default for exactly this reason ({{OpenSSL 3.5 release notes|https://openssl-library.org/news/openssl-3.5-notes/}}); a hand-tuned groups list can undo it.

Encrypted Client Hello: hiding the last plaintext

After TLS 1.3 the only content an observer still reads is the ClientHello, and its SNI says exactly which site you visit. Encrypted Client Hello (ECH, {{RFC 9849|https://www.rfc-editor.org/rfc/rfc9849}}, March 2026) splits it in two: an outer ClientHello naming a shared front end (for example a CDN's public name) and an inner one, with the real SNI and ALPN, encrypted to a public key the front end publishes in its DNS HTTPS record ({{RFC 9848|https://www.rfc-editor.org/rfc/rfc9848}}). Consequences: it only hides something if many sites share the front end, so in practice it is a CDN feature; it is pointless over plaintext DNS, which leaks the name anyway (see {{DNS|n:3c65c17b0d0d812387d8f92b546f07af}}); and networks that filter by SNI lose that signal, so an ECH client behind such a filter fails in ways that look like network errors rather than policy blocks.

Predict, then reveal: a corporate firewall blocks a site by SNI. Over TLS 1.3 without ECH, can it still see the server's certificate?
No. In TLS 1.3 the Certificate message is encrypted (record 5 in the recording is 934 bytes of ciphertext). In TLS 1.2 it was readable, which is why older filters inspected certificates. A TLS 1.3 filter can only see SNI, ALPN and the IP address, unless it breaks TLS by acting as a proxy with its own CA (section 9).
