The idea in one screen

TLS agrees a fresh secret with a stranger in public, proves the stranger is the named server by a signature that chains up to a root your client already trusts, and then encrypts every byte with keys derived from that secret and the whole conversation.

Your code sends POST /v1/messages with an API key and a user's words. Between your laptop and the API sit a Wi-Fi router, an internet provider, maybe a corporate proxy and several cloud hops. Any of them could read those bytes, change them, or pretend to be the API. TLS (Transport Layer Security) stops all three: it gives confidentiality, integrity and authentication. It runs on top of TCP (or inside QUIC for HTTP/3), under HTTP, and it is the "S" in HTTPS. The current version is TLS 1.3, re-published in July 2026 as {{RFC 9846|https://www.rfc-editor.org/rfc/rfc9846}}, which replaced RFC 8446 (and TLS 1.2's RFC 5246).

New terms on this page (open when one is unfamiliar)
AEAD
Authenticated encryption with associated data: a cipher that encrypts and adds a tag detecting any change (AES-GCM, ChaCha20-Poly1305).
Key share, KEM
A public value for key exchange; a key encapsulation mechanism sends a secret wrapped to the other side's public key (ML-KEM).
SNI, ALPN
Server Name Indication: the host name in the ClientHello, in clear unless ECH is used. Application-Layer Protocol Negotiation: the ClientHello extension that picks http/1.1, h2 or h3 inside the handshake.
CA, root, intermediate
Certificate authority; a root is a self-signed CA certificate in a trust store; an intermediate is a CA certificate signed by a root that issues leaves.
Trust store
The set of root certificates a client trusts; differs per OS, browser and runtime.
SAN
Subject Alternative Name: the names (DNS, IP, URI) a certificate is valid for; the only place hostnames are checked.
PSK, session ticket
Pre-shared key from an earlier session, carried in an opaque ticket, used for resumption.
0-RTT, early data
Application data sent in the first flight of a resumed connection; replayable.
mTLS
Mutual TLS: the client also presents a certificate and signs the transcript.
Hybrid key exchange
A classical and a post-quantum exchange run together, both mixed into the secret (X25519MLKEM768).

The full glossary is in the Reference section at the end.

What to remember

  1. Two handshakes before the first byte. A new HTTPS connection costs TCP's round trip plus one for TLS 1.3 (two for TLS 1.2). Reuse connections: on this machine a request on a kept-alive connection took 0.05 ms against 1.4 ms with a fresh handshake, even with no network delay at all (section 3).
  2. A certificate binds a name to a public key, signed by a certificate authority (CA) your trust store already trusts. Most TLS outages are certificate operations: expiry, a missing intermediate, a trust store that lacks a root, a wrong clock. Public certificates now last at most 200 days, falling to 47 by March 2029, so renewal must be automatic (ACME, section 5).
  3. 0-RTT early data can be replayed. Recorded here: one captured request replayed to nginx produced three more billed generations (section 3). Never accept a generation or a tool call as early data.
  4. Post-quantum key exchange is already on: 10 of the 12 public endpoints probed here (Anthropic, OpenAI, Google, Hugging Face and others) negotiated the hybrid X25519MLKEM768. Post-quantum certificates are years away because their signatures are large (section 8).
  5. Never "fix" a certificate error by disabling verification. Serve the full chain, or add the right CA to the right trust store; which variable each client reads is measured in section 9.
