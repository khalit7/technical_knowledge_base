DNS (the Domain Name System) turns a name such as api.anthropic.com into the records a program needs, mostly IP addresses. It is a tree of servers that each know one part of the answer, and almost every answer is cached for a number of seconds the owner chose. Nearly every DNS problem you will debug is one of four things: the answer is cached somewhere you did not expect, one name was turned into many queries, one lost packet cost a fixed timeout, or the wrong server was asked.

The running example. The root page follows one streaming request to an LLM API. Before the first byte of that request leaves your machine, the client must turn the API's name into an address. Here the API is api.llm.test on a private DNS tree built for this page (a root zone, the top-level domain test., and the zone llm.test., each served by a real DNS server in a container, with a real recursive resolver in front), because the laptop this page was recorded on answers every ordinary public DNS packet with a local filter, so public walks cannot be observed from it (the root's Failure lab tab shows the filter as its "A TLS error caused by DNS" case). The real api.anthropic.com appears wherever a public lookup tells the story better; those were sent over encrypted DNS to a public resolver, with its certificate checked, which the filter does not touch.

1. Names, zones and delegation

The problem. Packets are delivered to IP addresses, but people and configuration files use names, and the machines behind a name change all the time: load balancers are replaced, a region fails over, a CDN answers from the nearest city. One central table of every name could never keep up (the Internet tried: until the 1980s every host downloaded one file, HOSTS.TXT; RFC 1034 s2.1). DNS splits the job by ownership: whoever owns a name runs, or rents, the servers that answer for it, and everyone else finds those servers by asking down a tree (RFC 1034 and RFC 1035, November 1987, still the core of the protocol).

Names are read right to left. api.anthropic.com. is three labels under the root, which is the empty label written as the final dot. Each label is at most 63 bytes and a whole name at most 255 (RFC 1035 s2.3.4). A name ending in a dot is a fully qualified domain name (FQDN): absolute, never extended. Without the dot, your resolver library may try to complete it with local suffixes first, which is the whole story of section 7.

Zones and delegation. A zone is the part of the tree one set of servers answers for. The root zone answers for . but hands com. to other servers; com. hands anthropic.com. to the servers the company chose. That hand-over is a delegation: the parent zone holds NS records (name server) naming the child's servers, plus glue, the addresses of those servers when they live inside the child zone itself, without which nobody could reach them. The servers that hold a zone's records are its authoritative servers.

Why exactly 13 root servers. There are 13 root server identities, a to m.root-servers.net, run by 12 organisations; on 5 October 2026 they were served by 2,045 machines in many cities, each identity answering from many places on one address through anycast (the same IP address announced from many sites, routing sends you to the nearest) (root-servers.org). The number 13 is a fossil: in the early 1990s the list of root servers had to fit in one 512-byte UDP answer, and renaming them all under root-servers.net let compression squeeze 13 into it (RSSAC023 s2.6).

Costs and limits of the design. Delegation makes DNS scale, and it is also why changes are slow and failures are wide. A delegation in the parent is cached for as long as the parent says: 172,800 seconds (48 hours) for com. in the root zone file, and the same for the delegations inside .com, so moving a domain to new name servers can take two days to reach every cache. And every name under a zone depends on that zone's servers and the chain above them: when one record or one signature at a high level breaks, everything below it breaks at once (section 11 has the outages).

2. Resolution, step by step

Two kinds of question. Your program asks its resolver a recursive question: "give me the final answer, do whatever it takes" (the RD, recursion desired, flag is set). The resolver then asks iterative questions down the tree: each authoritative server answers with what it knows, either the record or a referral ("I do not have that; these servers do"), and never asks anyone on your behalf (RFC 1034 s4.3.1 and s5.3.3). A resolver starts with nothing but a list of root server addresses (the root hints); its first act is to ask a root server for the current list (priming, the NS . query in the recording below).

The recording. A fresh Unbound with an empty cache was asked for api.llm.test once, then again. Each authoritative server's own query log shows exactly what it was asked. The animation replays those logs; the toggle switches between three runs of the same question.

Every message is from the servers' own logs (measured, CoreDNS log plugin and dig, 5 October 2026); arrows are not drawn to time scale because each lab hop takes about a millisecond. On the internet the same walk costs real round trips: the root page measured 212 to 451 ms for an uncached public name and 2.4 ms once cached on the laptop.

What a cold lookup costs. One round trip from your process to the resolver, plus, on a cache miss, one round trip from the resolver to each level it does not already know. In practice the root and the top-level domains are almost always cached (their records live for days), so a cold lookup on the internet usually costs the round trip to the domain's own servers, often tens to hundreds of milliseconds. That is why the second lookup is cheap, and why a cache that is restarted or flushed causes a burst of slow lookups and a burst of load on the authoritative servers.

QNAME minimisation: tell each server only what it needs. Classic resolvers sent the full name to every server, so the root learned every name anyone looked up. With QNAME minimisation (RFC 9156) the resolver asks the root only about test., the test. servers only about llm.test., and only the zone's own servers see api.llm.test.. The recording shows both: with it on, the root's log holds A test.; with it off, A api.llm.test.. Unbound has done this by default since version 1.7.2 (June 2018; Unbound manual); BIND does a "relaxed" version by default that falls back to the full name when a server answers oddly (BIND 9.20 reference). It costs nothing in the common case and can cost extra queries for names many labels deep. Notice also that Unbound sets the CD (checking disabled) flag on its own upstream questions: it validates signatures itself (section 9) and wants the raw data.

Why you cannot see this walk with dig +trace on every network

dig +trace name normally does the walk itself, from the root down, and is the best way to separate "the zone is broken" from "my resolver cached something wrong". It only works if your packets reach the root servers. On the laptop this page was recorded on, a filter answers every plain DNS packet itself, even one addressed to a root server and even from inside a container: asked example.com without recursion, a.root-servers.net's address replied with a final answer and the RA flag set, which a real root server never does (it would refer you to the .com servers). Corporate device management, VPNs and security software often do this. That is why the walk on this page is recorded on a private tree, and why the public lookups were sent over DNS over TLS (section 10).

3. The message on the wire

One format for everything. A question and its answer use the same message layout (RFC 1035 s4.1): a 12-byte header, then four sections. The question holds the name, the record type and the class (always IN, Internet). The answer holds the records asked for; the authority section holds NS records for a referral, or the zone's SOA record with a "no"; the additional section holds glue addresses and the EDNS pseudo-record. Each record carries its owner name, type, class, a 32-bit TTL in seconds, and its data.

The header, field by field. A 16-bit ID that the answer must echo (with the source port, it is all that ties an answer to its question over UDP: section 10). Flags: QR (this is a response), AA (authoritative answer, from the zone's own server), TC (truncated: the answer did not fit), RD and RA (recursion desired and available), AD (authentic data: the resolver validated the DNSSEC signatures) and CD (checking disabled). A 4-bit response code: NOERROR; NXDOMAIN (the name does not exist at all); SERVFAIL (the resolver tried and failed: says nothing about whether the name exists); REFUSED (this server will not answer you). Finally four 16-bit counts, one per section. One special case has no code of its own: NODATA is NOERROR with an empty answer, meaning the name exists but has no record of that type (asking api.llm.test for TXT in the lab returns exactly that, with the SOA in the authority section).

Names are compressed. A name is written as length-prefixed labels (03 api 03 llm 04 test 00), and to save space any later occurrence can be replaced by a two-byte pointer: two high bits set, then a 14-bit offset back into the message, which is why a pointer can only reach the first 16,383 bytes (RFC 1035 s4.1.4). In the CNAME answer above, www.llm.test in the answer is the two bytes c0 0c ("see byte 12", where the question's name starts).

Size: 512 bytes, EDNS, and falling back to TCP

DNS runs on UDP port 53 because one question and one answer usually fit in one datagram each, with no connection to set up. The original rule was that a UDP message is at most 512 bytes (RFC 1035 s2.3.4). EDNS(0) (RFC 6891) lets a client add an OPT pseudo-record that says how large an answer it can take, plus a DNSSEC OK bit and room for options (cookies, client subnet, padding). The DNS operators' Flag Day 2020 settled the default advertised size at 1,232 bytes, small enough that an answer never needs IP fragmentation on any normal path (dnsflagday.net/2020). Fragments are lost more often and can be forged more easily (section 10), so bigger is not better.

When an answer does not fit, the server sends what fits with TC set, and the client must ask again over TCP. Support for TCP is required of every DNS implementation, stubs included (RFC 7766 s5). The lab's pool.llm.test has 40 addresses:



measured. Without EDNS (+noedns, which is how glibc and musl ask unless told otherwise: their queries in section 7's capture are 30 bytes, header plus question, with no OPT record) the 671-byte answer does not fit in 512, so the first reply is an empty truncated message and dig repeats the question over TCP. With EDNS at 1,232 it arrives in one UDP datagram (682 bytes). The Pod resolver lab has the same name looked up by glibc and musl: both got a truncated UDP answer, opened a TCP connection and received all 40 addresses; glibc went through the whole UDP-then-TCP exchange twice within one call.


How it fails
    

  • TCP 53 blocked by a firewall or security group: small answers work, big ones (many addresses, long TXT records, DNSSEC) fail or time out. Check with dig +tcp name and dig +bufsize=512 name.

  • Fragmented UDP answers dropped on a path with a smaller MTU: a resolver advertising 4,096 gets nothing back for large answers. Advertise 1,232.
    • 

  • A client that never retries over TCP: older musl versions (before 1.2.4, 2023) had no TCP fallback, so very large answers failed on Alpine images (see section 6).

The apex problem: why you cannot CNAME example.com


A CNAME says "this name is an alias; ask about that other name instead", and a name that has a CNAME may have no other data (RFC 1034 s3.6.2, RFC 2181 s10.1). The zone apex (the bare domain, llm.test. itself) must hold SOA and NS records, so it can never be a CNAME. That bites when a cloud load balancer or CDN gives you a hostname rather than fixed addresses. Three ways out:


    

  1. Provider-side flattening (called ALIAS, ANAME or CNAME flattening): the authoritative server resolves the target itself and answers with plain A and AAAA records. Every implementation is proprietary; the IETF draft to standardise it (draft-ietf-dnsop-aname) expired.
    2. 

  2. Route 53 alias records: allowed at the apex, they point at an AWS resource and Route 53 answers with its current addresses; queries to alias records that point at AWS resources are not charged (Route 53 docs).
    3. 

  3. The HTTPS record in AliasMode (RFC 9460, November 2023), the standard answer: example.com. HTTPS 0 lb.provider.net. is legal at the apex. Its ServiceMode form (priority 1 or more) also tells a browser, before it connects, which HTTP versions the server speaks (alpn), its addresses, and the key for Encrypted Client Hello (ech). On 5 October 2026 cloudflare.com advertised alpn="h3,h2" and api.anthropic.com advertised alpn="h2" with IPv4 and IPv6 hints (measured), which is how a browser can start with HTTP/3 without a first HTTP/2 visit (see HTTP).
    4. 



Mistakes these records invite
    

  • A long TXT value in one string. One TXT string is at most 255 bytes (RFC 1035 s3.3); a 2048-bit DKIM key is about 410 characters, so it must be split into several quoted strings that the receiver joins. The lab's record above is a real 2048-bit key split exactly that way. Pasting it as one string either fails to load or is silently cut by some control panels.

  • MX or NS pointing at a CNAME. Not allowed (RFC 2181 s10.3); some mail servers refuse delivery. A domain that sends no mail can say so with a null MX, MX 0 . (RFC 7505).
    • 

  • Forgetting CAA. Since September 2017 every public certificate authority must check CAA before issuing (CA/Browser Forum ballot 187); a CAA record that names only one CA makes another CA's issuance fail. Details on the TLS and certificates page.

5. Caching: TTLs, negative answers and stale answers


The rule. Every record carries a TTL (time to live), chosen by the zone owner: the number of seconds a cache may keep it. A resolver that fetches a record with TTL 300 serves it for up to 300 seconds, counting down, then asks again. There is no way to push a change into caches or to invalidate them from outside. So "DNS propagation" is a myth: the authoritative server has the new data the moment you save it, and you are waiting for every cache that holds the old answer to expire.


Recorded. The lab resolver fetched weights.llm.test (TTL 30); a few seconds later the address was changed at the authoritative server. Both were then asked every two seconds:


resolver's answer: old addressresolver's answer: new addressauthoritative server


The resolver kept serving the old address, its TTL falling 30, 27, 25 ... 1, until its copy expired, about 30 seconds after it was fetched, whatever the authoritative server said. With a TTL of a day the same picture lasts a day. Two public readings make the same point: api.anthropic.com came back with 292 seconds left and, five seconds later from the same resolver address, 212 seconds left, 80 seconds lower instead of 5 (measured over DoT): one address hides many caches filled at different times, so a TTL is a per-cache countdown, not a global clock.


Planning a change (the Cache timeline tab simulates this)
Lower the TTL (to 60 to 300 s) at least one old TTL before the change, because caches that fetched just before you lowered it keep the old TTL. Make the change. Keep the old address serving until the old TTL has passed since the change, then raise the TTL again. For a move between DNS providers (changing NS records) count the parent's TTL, 48 hours for .com. The Cache timeline tab lets you set these numbers and watch what share of clients is still on the old address.


Negative caching: "no" is cached too


A resolver also caches NXDOMAIN and NODATA, so that a typo hammered in a loop does not reach the authoritative servers every time. How long is set by the zone's SOA record, which the "no" carries in its authority section: the minimum of the SOA record's own TTL and its last field, MINIMUM (RFC 2308 s5; MINIMUM once meant something else and was repurposed for exactly this). In the lab, llm.test's SOA has TTL 300 and MINIMUM 30, so a "no" lives min(300, 30) = 30 seconds:




The name was looked up before it existed, created at the authoritative server a few seconds later, and stayed "does not exist" at the resolver until 30 seconds after the first lookup (measured). For anthropic.com both numbers are 1,800 (SOA ... 604800 1800, measured), so a name looked up a moment before it is created stays missing for up to half an hour for everyone behind that cache; a zone with MINIMUM 86400 would make it a day. Keep MINIMUM between about 300 and 900 seconds on zones that change, and do not let deploy scripts or health checks look up names before they exist. The Failure lab's "NXDOMAIN" case shows what each client library prints.


Failures are cached as well: a resolver that gets no usable answer must remember that for at least 1 second and at most 5 minutes, and back off rather than retry hard (RFC 9520 s3, December 2023), which is why a broken zone can stay broken for a few minutes after it is fixed.


Serving stale answers when the source is down


When an authoritative server is unreachable and a cached record has expired, a resolver normally has nothing to give: SERVFAIL, or, as recorded below, no answer at all before the client gives up. Serve-stale (RFC 8767) lets it return the expired record instead, marked with a short TTL (30 s recommended), after trying the servers for a moment (1.8 s recommended). Recorded: two Unbound resolvers, one with serve-expired: yes, both cached weights.llm.test; then the zone's server was stopped and the TTL allowed to run out:




It trades correctness for availability: a client may get an address that has changed. That is usually the right trade for internal names during an outage of the DNS provider, and it softened the .de outage (section 9). corrected The old page said serve-stale is on by default in Unbound and BIND; it is off by default in both (Unbound serve-expired: no, manual; BIND 9.20 stale-answer-enable no, reference). 6. The resolver inside your process: glibc and musl


Who actually asks. When Python's requests or httpx, curl, Node's default dns.lookup or a gRPC channel opens a connection to a name, it calls getaddrinfo(), and the C library's stub resolver does the DNS work: it reads /etc/resolv.conf (the nameserver lines, the search list, the options), sends the questions, waits, retries, and returns addresses or an error. On Debian, Ubuntu and most images that is glibc; on Alpine it is musl, and they behave differently in ways that matter. For ML containers the safer default is a glibc-based image (Debian, Ubuntu, the CUDA images): the musl differences below are where Alpine images surprise people. Go is the exception: on Linux it normally uses its own resolver written in Go, which reads the same file (Go net package).


The knobs in /etc/resolv.conf (resolv.conf(5)): up to three nameserver lines; search, the suffixes tried for names with few dots; options ndots:n (default 1), the dot count below which the search list is tried first; timeout:n (default 5 seconds) and attempts:n (default 2); and glibc-only switches such as single-request, single-request-reopen, use-vc (always TCP), edns0, trust-ad and no-aaaa. musl documents its differences from glibc in one place (musl wiki).

A dead name server, and a server that fails


Caseglibcmusl


glibc asks the listed servers in order, moving to the next only after a timeout, so a dead first server costs every lookup 5 seconds; musl asks all of them in parallel and takes the first answer, so the same dead server cost it almost nothing. Two consequences: put your most reliable server first for glibc, and do not list servers that disagree (an internal and a public one) for musl, which will take whichever answers first. A server that answers SERVFAIL is final for glibc, which reports it at once; musl treats SERVFAIL as a reason to keep asking until its timeout runs out.


What the application sees


The error text tells you which failure you have. In Python both libraries raise socket.gaierror; the codes are the C library's EAI_* values:

"Name or service not known" (EAI_NONAME, -2) means a real "no": check the spelling and which resolver you asked (the Failure lab's "NXDOMAIN" and "Wrong resolver" cases). 7. Kubernetes: search lists, ndots and the cluster DNS


What a pod gets. With the default dnsPolicy: ClusterFirst, kubelet writes every pod a resolv.conf that points at the cluster DNS service (CoreDNS) and adds a search list and ndots:5 (Kubernetes docs):


search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5


This is what lets code in namespace default say http://llm-proxy and reach llm-proxy.default.svc.cluster.local. CoreDNS answers cluster.local names from the Kubernetes API and forwards everything else upstream. Note that the policy named Default is not the default: it copies the node's resolver settings instead.


The rule that costs. A name with fewer dots than ndots is tried with every search suffix before it is tried as written. api.llm.test has two dots, fewer than five, so the stub first asks for api.llm.test.default.svc.cluster.local, then api.llm.test.svc.cluster.local, then api.llm.test.cluster.local, each for both A and AAAA, and only then for api.llm.test. External API names (api.anthropic.com, s3.us-east-1.amazonaws.com: two and three dots) all pay this. The fixes, in order of preference.


    

  1. Write external names with a trailing dot (api.anthropic.com.): absolute, one A and one AAAA, nothing else. Most HTTP clients accept it; a few TLS stacks dislike the dot in the server name, so test it.
    2. 

  2. Lower ndots for the pod with dnsConfig: {options: [{name: ndots, value: "1"}]} (or 2). External names are then tried as written first. The 5-second stall: conntrack races


Pods reach the CoreDNS service address through kube-proxy's iptables rules, which rewrite the destination (DNAT) and record each flow in the kernel's connection tracking table (conntrack). glibc and musl send A and AAAA together from one socket, and UDP has no handshake, so the two packets can race through conntrack on different CPUs. Martynas Pumputis found three races in 2018; in each, one of the two packets is dropped and the pod waits out its 5-second timeout (Weave blog, archived). The fixes landed over three kernel releases: clashing identical entries are resolved (Linux 4.19, ed07d9a), same-origin NAT clashes skipped (5.0, 4e35c1c), and clashing UDP entries allowed to coexist briefly, which covers the third race where the two packets were sent to different CoreDNS pods (5.6, 6a757c0). corrected The old page said the first two were fixed in 4.17 and the third "never"; on nodes older than 5.6 it still bites.


The symptom is the fingerprint: lookups that take 5.0x seconds (or 2.5 on Alpine), the stub's timeout, never "slow" in general. The lab's dropped-packet runs in section 6 show exactly that number. Workarounds for old kernels: options single-request-reopen (glibc only), timeout:1, or NodeLocal DNSCache.

A ClusterIP service gives one virtual address that forwards each connection to one random pod, which is useless when every rank must reach every other rank. 8. Cloud resolvers and managed DNS (AWS as the example)


The VPC resolver. Every AWS VPC has a built-in recursive resolver (Route 53 Resolver, newer pages call it the VPC Resolver) at the VPC's base address plus two (10.0.0.2 for 10.0.0.0/16) and at 169.254.169.253 (AWS VPC DNS). It answers private hosted zones, public names and the VPC's own instance names; the VPC needs enableDnsSupport (and enableDnsHostnames for instance names).


    

  • A hard packet limit. Each instance may send at most 1,024 packets per second to link-local services in total, DNS, the metadata service and time sync together, and the limit cannot be raised (same page). Excess packets are dropped, so the symptom is the stub's timeout, not an error. A dense Kubernetes node whose pods all talk to the VPC resolver, each external lookup multiplied by eight (section 7), reaches it; NodeLocal DNSCache and fewer search-list misses are the remedies. corrected The old page said "per ENI"; the documentation states the quota for link-local traffic in aggregate.
    • 

  • Split horizon. A private hosted zone answers only inside the VPCs associated with it, so the same name can mean different things inside and outside (the Failure lab's "Wrong resolver" case is this shape). Resolver endpoints forward queries between a VPC and on-premises DNS in both directions and are billed per endpoint and per query, a common surprise on the bill.
    • 

  • Query logs are off until you turn them on: Resolver query logging needs a logging configuration associated with the VPC, and cached answers are not logged (AWS). It is the native way to spot exfiltration (section 10) and runaway lookups.
    • 



Route 53 as an authoritative service. Health checks probe every 30 seconds by default, or every 10 with fast checks, and mark an endpoint unhealthy after 3 failures by default (HealthCheckConfig). Health checkers live on the internet, so they cannot probe private addresses; for a private resource, health-check a CloudWatch alarm instead (AWS). Routing policies choose which answer a client gets: weighted, latency-based, failover, geolocation, and multivalue (up to eight healthy records per answer; AWS). All of them act only when a resolver asks again, so a failover is as fast as the record's TTL plus the health check's detection time, never faster: with 30-second checks, 3 failures and a 60-second TTL, clients can keep the dead address for about 90 + 60 = 150 seconds (derived).







9. DNSSEC: signed answers, and the root key roll


The problem. Classic DNS has no authentication: a resolver accepts the first answer that matches its question's ID and port, so anyone who can answer first, or who controls a hop, can send you to the wrong address (section 10 has the attacks). DNSSEC (RFC 4033 to 4035) lets a resolver prove that an answer is exactly what the zone's owner published, and that a "no such name" is genuine.


How it works. Each zone signs every RRset; the signature is an RRSIG record with an inception and an expiry date. The zone publishes its public keys as DNSKEY records, usually two roles: a key-signing key (KSK) that signs only the key set, and a zone-signing key (ZSK) that signs everything else. The parent vouches for the child's KSK by publishing a hash of it, a DS record, which the parent signs in turn. Following DS to DNSKEY to DS up the tree ends at the root's KSK, which the resolver must already trust: that copy is the trust anchor. A name that does not exist is proven by an NSEC (or hashed NSEC3) record, a signed statement "nothing exists between these two names". Each key and signature is identified by a 16-bit key tag, a checksum of the key.


The chain, recorded. The lab's three zones were signed (ECDSA P-256, algorithm 13) and the lab resolver given the lab root's KSK as its anchor. Step through the chain for api.llm.test, then switch to the two ways it breaks:

What it does not do. DNSSEC proves origin and integrity, not secrecy: the question and answer still cross the network in the clear. It protects the resolver, not the hop from your laptop to the resolver, unless your own stub validates or trusts the AD flag over a secure channel (glibc only honours AD with options trust-ad, since glibc 2.31; resolv.conf(5)). It says nothing about the server you then connect to (that is TLS's job). And signed answers are larger, which makes DNS a better amplifier for denial-of-service floods.


Adoption, dated. On 3 October 2026, 39.65% of users worldwide sat behind resolvers that fully validate, and another 9.41% behind a mix of validating and non-validating ones (APNIC Labs). Signing is far rarer: 8,362,748 .com domains had a DS record (Verisign scoreboard, 3 October 2026) out of 167,164,684 names in the zone, about 5.0% (8,362,748 / 167,164,684; Verisign zone counts). corrected The old page said "about 36 percent of users and about 7 percent of zones" with no date or scope.


How it fails: one bad signature takes everything below it down


A validating resolver that finds a broken signature must return SERVFAIL, not the unvalidated answer, so a signing mistake looks exactly like an outage. The test is the CD flag: dig +cd name asks the resolver to skip validation. If that returns an answer while the normal query fails, the problem is DNSSEC. A public example, deliberately broken by its owner: dnssec-failed.org returned SERVFAIL through 1.1.1.1, with the Extended DNS Error "9 (DNSKEY Missing): no SEP matching the DS found", and an address with +cd (measured; Extended DNS Errors are RFC 8914).


The .de outage, 5 May 2026. During a routine key roll, DENIC's new signer generated three different key pairs (one per hardware security module) under the same key tag, 33834, but published only one public key, so about two thirds of the signatures could not be validated. Validating resolvers returned SERVFAIL for much of .de for about three hours from roughly 19:30 UTC (DENIC analysis). Resolver operators mitigated with negative trust anchors (RFC 7646), an operator's instruction to treat one zone as unsigned for a while; Cloudflare's took effect at 22:17 UTC, and serving stale cached answers (section 5) softened the impact as records expired (Cloudflare).


Dated: the root key changes on 11 October 2026


The root zone's KSK is being replaced. The new key, KSK-2024 (key tag 38696), was generated in April 2024 and published in the root zone on 11 January 2025; on 11 October 2026 it becomes the only key signing the root's key set, and the old KSK-2017 (20326) is to be revoked in the first quarter of 2027 (IANA, ICANN). On 5 October 2026 the real root served both KSKs and two ZSKs (measured over DNS over TLS, with the AD flag), and the key set was still signed by KSK-2017 (the RRSIG's key tag 20326). The risk is a trust anchor frozen in a file: a container image, appliance or VM that runs its own validating resolver with an anchor baked in before 2025 and never updated. 10. Privacy and attacks


Encrypted DNS: DoT, DoH, DoQ


Plain DNS is readable and rewritable by every network it crosses: your Wi-Fi, your ISP, a filter on your laptop. Three standards encrypt the hop from your machine to the resolver: DNS over TLS (DoT), TCP port 853 (RFC 7858, 2016); DNS over HTTPS (DoH), ordinary HTTPS requests on port 443 (RFC 8484, 2018); and DNS over QUIC (DoQ), UDP port 853 (RFC 9250, 2022). DoT is easy for a network to recognise and block by port, which enterprises like and censors exploit; DoH looks like any other web traffic, which is why enterprises dislike it; DoQ avoids TCP's head-of-line blocking and sets up faster. In one academic measurement DoQ loaded simple pages up to 10% faster than DoH and was only about 2% slower than plain DNS on complex pages (Kosek et al., IMC 2022). corrected The old page's "88 ms against 883 ms, 2026 measurements" could not be found in any source and is not repeated.


Seen from this laptop. Every public lookup on this page went over DoT to 1.1.1.1 with the certificate checked against one.one.one.one, and a test query for the resolver's identity returned a Cloudflare data-centre code, so the answers really came from the public resolver. The same identity query over plain UDP was answered by the laptop's filter instead. Each encrypted answer arrived padded to 468 bytes: the resolver pads responses to a multiple of 468 so the size does not reveal the name (RFC 8467; measured: all ten replies whose size was recorded were exactly 468 bytes, whatever the name). Encryption made the interception visible rather than silent, which is also how the root's Failure lab caught it.


Cache poisoning: forging an answer


Over UDP a resolver accepts the first reply whose 16-bit ID and port match its question. In 2008 Dan Kaminsky showed that an attacker who triggers many lookups of random names in one zone can race the real server with forged replies carrying a forged delegation, and with a fixed source port only the ID (on average 32,768 guesses) stood in the way (CERT VU#800113). The fix was source-port randomisation, adding up to another 16 bits (RFC 5452); later layers are DNS cookies (RFC 7873) and randomising the letter case of the question ("0x20", an expired draft). In 2020 SAD DNS recovered the random port through a side channel in the kernel's global ICMP rate limit, fixed in Linux by randomising that limit (saddns.net, CVE-2020-25705 fix). Fragmented answers are another way around the port check, one more reason for the 1,232-byte limit. DNSSEC is the only complete fix.


DNS rebinding: the attack that matters most for ML engineers


Browsers decide what a page may read by its origin: scheme, host name and port (HTML standard), not the IP address behind the name. An attacker's name first resolves to the attacker's server, which serves JavaScript; with a TTL of 0 the next lookup of the same name returns 127.0.0.1, a LAN address or the cloud metadata address 169.254.169.254, and the script, still "same origin", reads whatever is there. Every notebook, Ray dashboard, MLflow, TensorBoard or model server bound to 0.0.0.0 without authentication is reachable this way from a browser on the same network. Chrome now asks the user before a public site may reach local addresses (Local Network Access, from Chrome 142, late October 2025; Chrome blog); servers should still check the Host header, as the MCP page shows for MCP servers.


The same trick against an agent's fetch tool. A tool that fetches URLs for a model usually checks the URL first ("refuse internal addresses") and then fetches it. If the check resolves the name and the HTTP library resolves it again, the two lookups can get different answers. The lab reproduces it: rebind.attacker.test answers alternately with the attacker's server and with 10.53.0.99, a stand-in for the metadata address, always with TTL 0; a 30-line fetch tool is run twice, written two ways:














measured: the attacker's DNS server log and the tool's own output; the "credential" is a fake string served by a container. The real metadata service also needs the fix below.


The fix
Resolve once, validate the address (not the name), connect to that literal address and send the name in the Host header (and as TLS SNI); refuse redirects or re-validate them the same way. On AWS, require IMDSv2, whose session token must be fetched with a PUT, so a plain GET from a rebinding page or a naive proxy fails; a response hop limit of 1 also keeps the token from reaching containers behind a bridge (AWS notes that containers then need a limit of 2 if they genuinely need the service; AWS IMDS docs). The MCP specification lists this among the checks a client must make before fetching a URL a server gave it (MCP security best practices).


Exfiltration: data out through your own resolver


Any machine that can resolve names can send data out: encode it in the labels of a name under a domain the attacker controls (c2VjcmV0.x.attacker.example), and your own resolver carries it to the attacker's authoritative server, past egress firewalls that only watch HTTP. It is slow but enough for keys. The SolarWinds SUNBURST backdoor (disclosed December 2020) used DNS for its first stage: it encoded the victim's domain name into subdomains of avsvmcloud[.]com and read its instructions from the answers, then moved to HTTPS for the rest (Mandiant). Detection watches, per parent domain, the number of unique subdomains, the randomness of labels and the share of NXDOMAIN answers. On AWS this needs Route 53 Resolver query logging, which you must configure; it is not on until you create a logging configuration (AWS).

13. Predict, then check: drills and interview questions


Pick an answer before reading the explanation; each one uses this page's recordings.




Interview questions, with model answers


What happens, step by step, when your service calls an API by name for the first time?
getaddrinfo reads /etc/hosts and /etc/resolv.conf, expands the name with the search list if it has fewer than ndots dots, and sends A and AAAA questions over UDP to the configured resolver. On a cache miss the resolver asks a root server (usually cached), the TLD's servers (usually cached) and the zone's servers, following referrals, validating DNSSEC if configured, caching every answer for its TTL. The stub returns the addresses; the client then opens TCP or QUIC to one of them and starts TLS with the name as SNI. Costs: one round trip to the resolver plus up to one per uncached level; failure modes: timeouts, NXDOMAIN, SERVFAIL, stale caches.


You changed a record ten minutes ago; half your users still reach the old server. Why, and what would you have done differently?
Resolvers cached the old answer for its TTL, which was probably long, and some clients cache beyond the TTL (JVM settings, long-lived connections). Nothing propagates; caches expire. Plan: lower the TTL to about 60 s at least one old TTL before the change, make the change, keep the old server running until the old TTL has passed, then raise the TTL. For name-server changes allow 48 hours, the TLD's delegation TTL.


Pods see occasional 5-second delays on outbound calls. How do you diagnose it?
Exactly 5 s (2.5 s on musl) is the stub's retry timeout, so a DNS packet was lost. Measure lookup time separately (curl -w %{time_namelookup}), check the kernel version for the conntrack races (fixed by 5.6), the CoreDNS and node drop counters, the VPC resolver's packet limit, and the query volume from ndots:5. Fixes: NodeLocal DNSCache, trailing dots or lower ndots, single-request-reopen on old kernels, connection reuse to cut lookups.


What does DNSSEC protect against, and what does it not?
It proves an RRset (or a non-existence) is what the zone owner signed, defeating cache poisoning and on-path forgery between resolver and authoritative servers. It does not encrypt, does not protect the stub-to-resolver hop unless the stub validates, does not authenticate the server you connect to, and adds a failure mode: a signing error makes validating resolvers return SERVFAIL (.de, May 2026). Privacy comes from DoT, DoH or DoQ; server identity from TLS.


An agent tool fetches URLs a model chooses. How can DNS be used to make it read cloud credentials, and how do you stop it?
DNS rebinding: the tool checks the URL's host resolves to a public address, then its HTTP library resolves again and gets 169.254.169.254 (TTL 0 defeats caches). Fix: resolve once, validate the IP against a denylist of private, loopback and link-local ranges, connect to that IP with the Host header and SNI set, re-validate on redirects, and require IMDSv2 so a plain GET to the metadata service fails. The lab reproduction on this page shows both versions.


Why is DNS mostly UDP, and when does it use TCP?
A question and an answer usually fit in one datagram, so UDP avoids a handshake. Answers larger than the client's advertised size (512 bytes without EDNS, typically 1,232 with it) come back truncated with TC set and the client retries over TCP; zone transfers use TCP; DoT uses TLS over TCP. TCP support is mandatory (RFC 7766), and blocking TCP 53 breaks large answers.







Glossary




Trust anchor: the public key (or its DS hash) a validating resolver trusts without proof; for the real DNS, the root KSK.


Anycast: one IP address announced from many sites; routing delivers to the nearest.


Apex: the top name of a zone (example.com.), which must hold SOA and NS and so cannot be a CNAME.


Authoritative server: a server that holds a zone's records and answers from them, never asking others.


conntrack: the Linux kernel's table of tracked flows, used for NAT; the source of the 5-second DNS races.


Delegation: NS records in a parent zone handing a child zone to other servers.


DNSSEC: signatures on DNS data (RRSIG, DNSKEY, DS, NSEC) so a resolver can verify it.


EDNS(0): an OPT pseudo-record that advertises a larger UDP size and carries flags and options.


FQDN: a fully qualified name, ending in a dot; never extended with a search list.


Glue: addresses of a child's name servers kept in the parent when those servers live inside the child.


Header: the 12 bytes at the start of every message: ID, flags, response code, four counts.


Headless service: a Kubernetes Service with clusterIP: None whose name returns every ready pod's address.


Root hints: the built-in list of root server addresses a resolver starts from.


Iterative query: a question a resolver asks an authoritative server, which answers or refers.


Key tag: a 16-bit checksum that names a DNSSEC key (38696 is KSK-2024).


KSK and ZSK: key-signing key (signs the key set; hashed into the parent's DS) and zone-signing key (signs the rest).


Label: one dot-separated part of a name, at most 63 bytes.


NODATA: NOERROR with no answer: the name exists without that type.


Negative trust anchor: an operator's temporary instruction to treat a zone as unsigned.


Priming: a resolver's first question, the current list of root servers.


Compression pointer: two bytes (c0 0c) standing for a name already written earlier in the message.


QNAME minimisation: sending each server only the labels it needs (RFC 9156).


Response code: NOERROR, NXDOMAIN, SERVFAIL, REFUSED and others, in the header.


Recursive query: a question asking the resolver for the final answer (RD flag set).


Referral: an answer naming the servers one level down instead of the record.


Resource record: one name, TTL, class, type and data.


RRset: all records of one name and type, cached and signed as one.


Serve-stale: answering from an expired cache entry when the source is unreachable (RFC 8767).


TTL: seconds a cache may keep a record; for a "no", min(SOA TTL, SOA MINIMUM).


Zone: the part of the name tree one set of authoritative servers answers for.

illustrative model: every resolver cache is assumed to be kept warm by steady traffic, with fetch times spread evenly over one TTL; a real cache that sees little traffic refetches later and flips sooner. The rule it encodes is exact: a cache flips when the entry it held at the moment of the change expires, and an entry keeps the TTL it was fetched with.
