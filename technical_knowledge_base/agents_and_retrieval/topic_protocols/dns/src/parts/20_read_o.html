Interview questions, with model answers

What happens, step by step, when your service calls an API by name for the first time?
getaddrinfo reads /etc/hosts and /etc/resolv.conf, expands the name with the search list if it has fewer than ndots dots, and sends A and AAAA questions over UDP to the configured resolver. On a cache miss the resolver asks a root server (usually cached), the TLD's servers (usually cached) and the zone's servers, following referrals, validating DNSSEC if configured, caching every answer for its TTL. The stub returns the addresses; the client then opens TCP or QUIC to one of them and starts TLS with the name as SNI. Costs: one round trip to the resolver plus up to one per uncached level; failure modes: timeouts, NXDOMAIN, SERVFAIL, stale caches.

You changed a record ten minutes ago; half your users still reach the old server. Why, and what would you have done differently?
Resolvers cached the old answer for its TTL, which was probably long, and some clients cache beyond the TTL (JVM settings, long-lived connections). Nothing propagates; caches expire. Plan: lower the TTL to about 60 s at least one old TTL before the change, make the change, keep the old server running until the old TTL has passed, then raise the TTL. For name-server changes allow 48 hours, the TLD's delegation TTL.

Pods see occasional 5-second delays on outbound calls. How do you diagnose it?
Exactly 5 s (2.5 s on musl) is the stub's retry timeout, so a DNS packet was lost. Measure lookup time separately (curl -w %{time_namelookup}), check the kernel version for the conntrack races (fixed by 5.6), the CoreDNS and node drop counters, the VPC resolver's packet limit, and the query volume from ndots:5. Fixes: NodeLocal DNSCache, trailing dots or lower ndots, single-request-reopen on old kernels, connection reuse to cut lookups.

What does DNSSEC protect against, and what does it not?
It proves an RRset (or a non-existence) is what the zone owner signed, defeating cache poisoning and on-path forgery between resolver and authoritative servers. It does not encrypt, does not protect the stub-to-resolver hop unless the stub validates, does not authenticate the server you connect to, and adds a failure mode: a signing error makes validating resolvers return SERVFAIL (.de, May 2026). Privacy comes from DoT, DoH or DoQ; server identity from TLS.

An agent tool fetches URLs a model chooses. How can DNS be used to make it read cloud credentials, and how do you stop it?
DNS rebinding: the tool checks the URL's host resolves to a public address, then its HTTP library resolves again and gets 169.254.169.254 (TTL 0 defeats caches). Fix: resolve once, validate the IP against a denylist of private, loopback and link-local ranges, connect to that IP with the Host header and SNI set, re-validate on redirects, and require IMDSv2 so a plain GET to the metadata service fails. The lab reproduction on this page shows both versions.

Why is DNS mostly UDP, and when does it use TCP?
A question and an answer usually fit in one datagram, so UDP avoids a handshake. Answers larger than the client's advertised size (512 bytes without EDNS, typically 1,232 with it) come back truncated with TC set and the client retries over TCP; zone transfers use TCP; DoT uses TLS over TCP. TCP support is mandatory (RFC 7766), and blocking TCP 53 breaks large answers.
