9. DNSSEC: signed answers, and the root key roll

The problem. Classic DNS has no authentication: a resolver accepts the first answer that matches its question's ID and port, so anyone who can answer first, or who controls a hop, can send you to the wrong address (section 10 has the attacks). DNSSEC ({{RFC 4033|https://www.rfc-editor.org/rfc/rfc4033}} to 4035) lets a resolver prove that an answer is exactly what the zone's owner published, and that a "no such name" is genuine.

How it works. Each zone signs every RRset; the signature is an RRSIG record with an inception and an expiry date. The zone publishes its public keys as DNSKEY records, usually two roles: a key-signing key (KSK) that signs only the key set, and a zone-signing key (ZSK) that signs everything else. The parent vouches for the child's KSK by publishing a hash of it, a DS record, which the parent signs in turn. Following DS to DNSKEY to DS up the tree ends at the root's KSK, which the resolver must already trust: that copy is the trust anchor. A name that does not exist is proven by an NSEC (or hashed NSEC3) record, a signed statement "nothing exists between these two names". Each key and signature is identified by a 16-bit key tag, a checksum of the key.

What it does not do. DNSSEC proves origin and integrity, not secrecy: the question and answer still cross the network in the clear. It protects the resolver, not the hop from your laptop to the resolver, unless your own stub validates or trusts the AD flag over a secure channel (glibc only honours AD with options trust-ad, since glibc 2.31; {{resolv.conf(5)|https://man7.org/linux/man-pages/man5/resolv.conf.5.html}}). It says nothing about the server you then connect to (that is TLS's job). And signed answers are larger, which makes DNS a better amplifier for denial-of-service floods.


Adoption, dated. On 3 October 2026, 39.65% of users worldwide sat behind resolvers that fully validate, and another 9.41% behind a mix of validating and non-validating ones ({{APNIC Labs|https://stats.labs.apnic.net/dnssec/XA}}). Signing is far rarer: 8,362,748 .com domains had a DS record (Verisign scoreboard, 3 October 2026) out of 167,164,684 names in the zone, about 5.0% (8,362,748 / 167,164,684; {{Verisign zone counts|https://www.verisign.com/zone-domain-counts/zone_counts.json}}). corrected The old page said "about 36 percent of users and about 7 percent of zones" with no date or scope.


How it fails: one bad signature takes everything below it down


A validating resolver that finds a broken signature must return SERVFAIL, not the unvalidated answer, so a signing mistake looks exactly like an outage. The test is the CD flag: dig +cd name asks the resolver to skip validation. If that returns an answer while the normal query fails, the problem is DNSSEC. A public example, deliberately broken by its owner: dnssec-failed.org returned SERVFAIL through 1.1.1.1, with the Extended DNS Error "9 (DNSKEY Missing): no SEP matching the DS found", and an address with +cd (measured; Extended DNS Errors are {{RFC 8914|https://www.rfc-editor.org/rfc/rfc8914}}).


The .de outage, 5 May 2026. During a routine key roll, DENIC's new signer generated three different key pairs (one per hardware security module) under the same key tag, 33834, but published only one public key, so about two thirds of the signatures could not be validated. Validating resolvers returned SERVFAIL for much of .de for about three hours from roughly 19:30 UTC ({{DENIC analysis|https://blog.denic.de/en/analysis-of-the-dns-outage-on-5-may-2026/}}). Resolver operators mitigated with negative trust anchors ({{RFC 7646|https://www.rfc-editor.org/rfc/rfc7646}}), an operator's instruction to treat one zone as unsigned for a while; Cloudflare's took effect at 22:17 UTC, and serving stale cached answers (section 5) softened the impact as records expired ({{Cloudflare|https://blog.cloudflare.com/de-tld-outage-dnssec/}}).


Dated: the root key changes on 11 October 2026


The root zone's KSK is being replaced. The new key, KSK-2024 (key tag 38696), was generated in April 2024 and published in the root zone on 11 January 2025; on 11 October 2026 it becomes the only key signing the root's key set, and the old KSK-2017 (20326) is to be revoked in the first quarter of 2027 ({{IANA|https://www.iana.org/dnssec/files}}, {{ICANN|https://www.icann.org/resources/pages/ksk-rollover-en}}). On 5 October 2026 the real root served both KSKs and two ZSKs (measured over DNS over TLS, with the AD flag), and the key set was still signed by KSK-2017 (the RRSIG's key tag 20326). Resolvers that follow automated trust-anchor updates ({{RFC 5011|https://www.rfc-editor.org/rfc/rfc5011}}) have trusted KSK-2024 since February 2025. The risk is a trust anchor frozen in a file: a container image, appliance or VM that runs its own validating resolver with an anchor baked in before 2025 and never updated. The third mode of the chain above reproduces exactly that on the lab's tree: after the root rolls, the resolver with the old anchor returns SERVFAIL for every name, signed or not, while one with the new anchor validates. Check: find the anchor file your resolver is configured with (trust-anchor-file or auto-trust-anchor-file in Unbound, trust-anchors in BIND) and look for key tag 38696 or its DS digest 683D2D0A...; if it is missing, update the package or image that ships it.
