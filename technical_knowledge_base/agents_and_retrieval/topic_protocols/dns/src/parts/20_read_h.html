6. The resolver inside your process: glibc and musl

Who actually asks. When Python's requests or httpx, curl, Node's default dns.lookup or a gRPC channel opens a connection to a name, it calls getaddrinfo(), and the C library's stub resolver does the DNS work: it reads /etc/resolv.conf (the nameserver lines, the search list, the options), sends the questions, waits, retries, and returns addresses or an error. On Debian, Ubuntu and most images that is glibc; on Alpine it is musl, and they behave differently in ways that matter. For ML containers the safer default is a glibc-based image (Debian, Ubuntu, the CUDA images): the musl differences below are where Alpine images surprise people. Go is the exception: on Linux it normally uses its own resolver written in Go, which reads the same file ({{Go net package|https://pkg.go.dev/net#hdr-Name_Resolution}}).

The knobs in /etc/resolv.conf ({{resolv.conf(5)|https://man7.org/linux/man-pages/man5/resolv.conf.5.html}}): up to three nameserver lines; search, the suffixes tried for names with few dots; options ndots:n (default 1), the dot count below which the search list is tried first; timeout:n (default 5 seconds) and attempts:n (default 2); and glibc-only switches such as single-request, single-request-reopen, use-vc (always TCP), edns0, trust-ad and no-aaaa. musl documents its differences from glibc in one place ({{musl wiki|https://wiki.musl-libc.org/functional-differences-from-glibc.html#Name-Resolver/DNS}}).

A dead name server, and a server that fails

Caseglibcmusl

glibc asks the listed servers in order, moving to the next only after a timeout, so a dead first server costs every lookup 5 seconds; musl asks all of them in parallel and takes the first answer, so the same dead server cost it almost nothing. Two consequences: put your most reliable server first for glibc, and do not list servers that disagree (an internal and a public one) for musl, which will take whichever answers first. A server that answers SERVFAIL is final for glibc, which reports it at once; musl treats SERVFAIL as a reason to keep asking until its timeout runs out.

What the application sees

The error text tells you which failure you have. In Python both libraries raise socket.gaierror; the codes are the C library's EAI_* values:

DNS outcomeglibc (Debian)musl (Alpine)

"Name or service not known" (EAI_NONAME, -2) means a real "no": check the spelling and which resolver you asked (the Failure lab's "NXDOMAIN" and "Wrong resolver" cases). "Temporary failure in name resolution" (EAI_AGAIN, -3) means no usable answer arrived: a SERVFAIL, a timeout, or no reachable server; it is worth one retry with backoff, and if it took 5 or 10 seconds, packets were lost. curl reports both as curl: (6) Could not resolve host, so ask Python or getent ahosts name for the distinction.

Clients that ignore TTLs, in both directions

  • No cache at all: Python, Node, glibc and musl. socket.getaddrinfo wraps the C function and adds nothing ({{Python docs|https://docs.python.org/3/library/socket.html#socket.getaddrinfo}}); neither requests nor urllib3 caches names. Node's dns.lookup is a blocking getaddrinfo on libuv's thread pool of 4 threads by default, so slow DNS can stall unrelated file and crypto work ({{Node docs|https://nodejs.org/api/dns.html#implementation-considerations}}). What saves you is connection reuse: a pooled connection resolves once. Recorded in the lab pod (with Kubernetes settings, section 7):

measured: 8 queries per lookup because of the pod's search list (section 7). The middle row is the surprise of this recording: a "pooled" client gains nothing when the server closes the connection after each response, because every request then opens a new connection and resolves again.

  • A training loop that builds a new client per batch to fetch shards from object storage does the left-hand row thousands of times a second, which is how cluster DNS servers get overloaded. Reuse one session; on a node where you cannot, run a local cache (NodeLocal DNSCache in Kubernetes, section 7; systemd-resolved or nscd on a VM).
  • Caching longer than the TTL: the JVM. Java caches successful lookups for 30 seconds by default and failures for 10 (networkaddress.cache.ttl, networkaddress.cache.negative.ttl); up to JDK 23, installing a security manager made the positive cache last forever ({{JDK java.security|https://github.com/openjdk/jdk17u/blob/master/src/java.base/share/conf/security/java.security}}). Long-lived JVM services that set it to forever keep calling a load balancer's old address after it moves.
  • Long-lived connections never re-resolve at all, whatever the TTL: a gRPC channel or a keep-alive HTTP/2 connection stays on the old address until it breaks or is recycled. Cap connection age (gRPC's max_connection_age on the server) when backends move.
