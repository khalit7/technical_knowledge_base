12. Debugging DNS: commands and a symptom table

Rule one: ask the way your program asks. dig talks DNS directly to one server and ignores the search list, /etc/hosts and every cache in your C library; your program goes through getaddrinfo. When they disagree, both are telling the truth. Use getent ahosts name on Linux (it goes through the same path as your program) and dscacheutil -q host -a name name or scutil --dns on macOS, where apps and dig can use different resolvers.

CommandWhat it tells you
dig nameThe status (NOERROR, NXDOMAIN, SERVFAIL), flags, answer and the remaining TTL from your resolver
dig name twice, a few seconds apartTTL falling: served from a cache; TTL back at its maximum: the resolver just fetched it. Different numbers each time: several caches behind one address (seen in section 5: 292, then 212 five seconds later, for api.anthropic.com from one public resolver)
dig @ns1.zone.example name +norecurseWhat the zone's own server says, with no cache in between (look for the aa flag)
dig +trace nameThe walk from the root, done by dig itself: separates "the zone is wrong" from "my resolver cached something wrong". Fails behind interception (section 2)
dig zone SOAThe SOA's TTL and last field: how long a "no" will be cached
dig name +dnssec and dig name +cdThe ad flag means validated; a SERVFAIL that turns into an answer with +cd is a DNSSEC failure
delv nameValidates the chain itself and says which link failed
dig +tcp name, dig +bufsize=512 nameWhether TCP 53 works; whether big answers truncate
dig +tls @1.1.1.1 name, dig +https @1.1.1.1 nameEncrypted DNS (dig 9.18 and later); add +tls-ca to check the certificate. kdig (Knot) and doggo do the same and DoQ
dig @1.1.1.1 id.server CH TXTWhich instance of a public resolver answered, or whether something else did
dig name +nsidAsks the server to say which instance answered (the NSID option, {{RFC 5001|https://www.rfc-editor.org/rfc/rfc5001}}), useful behind anycast
dig -x 10.53.0.80Reverse lookup (PTR under in-addr.arpa)
curl -w '%{time_namelookup}\n' -o /dev/null -s URLHow long the lookup took inside a real client: about 5.0 s means a lost packet

Compare three answers: the zone's own server, your resolver and a public resolver. If the zone's server is wrong, fix the zone; if only your resolver is wrong, it is a cache or split horizon; if only the public one is wrong, it is still caching the old answer. nslookup works but uses its own resolution path and hides details; ISC once deprecated it and then reversed that ({{BIND changes, entry 1700|https://ftp.isc.org/isc/bind9/9.9.0/CHANGES}}), so prefer dig and getent.
