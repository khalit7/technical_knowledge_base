3. The message on the wire

One format for everything. A question and its answer use the same message layout ({{RFC 1035 s4.1|https://www.rfc-editor.org/rfc/rfc1035#section-4.1}}): a 12-byte header, then four sections. The question holds the name, the record type and the class (always IN, Internet). The answer holds the records asked for; the authority section holds NS records for a referral, or the zone's SOA record with a "no"; the additional section holds glue addresses and the EDNS pseudo-record. Each record carries its owner name, type, class, a 32-bit TTL in seconds, and its data.

The header, field by field. A 16-bit ID that the answer must echo (with the source port, it is all that ties an answer to its question over UDP: section 10). Flags: QR (this is a response), AA (authoritative answer, from the zone's own server), TC (truncated: the answer did not fit), RD and RA (recursion desired and available), AD (authentic data: the resolver validated the DNSSEC signatures) and CD (checking disabled). A 4-bit response code: NOERROR; NXDOMAIN (the name does not exist at all); SERVFAIL (the resolver tried and failed: says nothing about whether the name exists); REFUSED (this server will not answer you). Finally four 16-bit counts, one per section. One special case has no code of its own: NODATA is NOERROR with an empty answer, meaning the name exists but has no record of that type (asking api.llm.test for TXT in the lab returns exactly that, with the SOA in the authority section).

Names are compressed. A name is written as length-prefixed labels (03 api 03 llm 04 test 00), and to save space any later occurrence can be replaced by a two-byte pointer: two high bits set, then a 14-bit offset back into the message, which is why a pointer can only reach the first 16,383 bytes ({{RFC 1035 s4.1.4|https://www.rfc-editor.org/rfc/rfc1035#section-4.1.4}}). In the CNAME answer above, www.llm.test in the answer is the two bytes c0 0c ("see byte 12", where the question's name starts).

Size: 512 bytes, EDNS, and falling back to TCP

DNS runs on UDP port 53 because one question and one answer usually fit in one datagram each, with no connection to set up. The original rule was that a UDP message is at most 512 bytes ({{RFC 1035 s2.3.4|https://www.rfc-editor.org/rfc/rfc1035#section-2.3.4}}). EDNS(0) ({{RFC 6891|https://www.rfc-editor.org/rfc/rfc6891}}) lets a client add an OPT pseudo-record that says how large an answer it can take, plus a DNSSEC OK bit and room for options (cookies, client subnet, padding). The DNS operators' Flag Day 2020 settled the default advertised size at 1,232 bytes, small enough that an answer never needs IP fragmentation on any normal path ({{dnsflagday.net/2020|https://www.dnsflagday.net/2020/}}). Fragments are lost more often and can be forged more easily (section 10), so bigger is not better.

When an answer does not fit, the server sends what fits with TC set, and the client must ask again over TCP. Support for TCP is required of every DNS implementation, stubs included ({{RFC 7766 s5|https://www.rfc-editor.org/rfc/rfc7766#section-5}}). The lab's pool.llm.test has 40 addresses:

Without EDNS (+noedns, which is how glibc and musl ask unless told otherwise: their queries in section 7's capture are 30 bytes, header plus question, with no OPT record) the 671-byte answer does not fit in 512, so the first reply is an empty truncated message and dig repeats the question over TCP. With EDNS at 1,232 it arrives in one UDP datagram (682 bytes). How it fails
    

  • TCP 53 blocked by a firewall or security group: small answers work, big ones (many addresses, long TXT records, DNSSEC) fail or time out. Check with dig +tcp name and dig +bufsize=512 name.
    • 

  • Fragmented UDP answers dropped on a path with a smaller MTU: a resolver advertising 4,096 gets nothing back for large answers. Advertise 1,232.
    • 

  • A client that never retries over TCP: older musl versions (before 1.2.4, 2023) had no TCP fallback, so very large answers failed on Alpine images (see section 6).
