2. Resolution, step by step

Two kinds of question. Your program asks its resolver a recursive question: "give me the final answer, do whatever it takes" (the RD, recursion desired, flag is set). The resolver then asks iterative questions down the tree: each authoritative server answers with what it knows, either the record or a referral ("I do not have that; these servers do"), and never asks anyone on your behalf ({{RFC 1034 s4.3.1 and s5.3.3|https://www.rfc-editor.org/rfc/rfc1034#section-5.3.3}}). A resolver starts with nothing but a list of root server addresses (the root hints); its first act is to ask a root server for the current list (priming, the NS . query in the recording below).

The recording. A fresh Unbound with an empty cache was asked for api.llm.test once, then again. Each authoritative server's own query log shows exactly what it was asked. The animation replays those logs; the toggle switches between three runs of the same question.

Every message is from the servers' own logs (measured, CoreDNS log plugin and dig, 5 October 2026); arrows are not drawn to time scale because each lab hop takes about a millisecond. On the internet the same walk costs real round trips: the root page measured 212 to 451 ms for an uncached public name and 2.4 ms once cached on the laptop.

What a cold lookup costs. One round trip from your process to the resolver, plus, on a cache miss, one round trip from the resolver to each level it does not already know. In practice the root and the top-level domains are almost always cached (their records live for days), so a cold lookup on the internet usually costs the round trip to the domain's own servers, often tens to hundreds of milliseconds. That is why the second lookup is cheap, and why a cache that is restarted or flushed causes a burst of slow lookups and a burst of load on the authoritative servers.

QNAME minimisation: tell each server only what it needs. Classic resolvers sent the full name to every server, so the root learned every name anyone looked up. With QNAME minimisation ({{RFC 9156|https://www.rfc-editor.org/rfc/rfc9156}}) the resolver asks the root only about test., the test. servers only about llm.test., and only the zone's own servers see api.llm.test.. The recording shows both: with it on, the root's log holds A test.; with it off, A api.llm.test.. Unbound has done this by default since version 1.7.2 (June 2018; {{Unbound manual|https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html#unbound-conf-qname-minimisation}}); BIND does a "relaxed" version by default that falls back to the full name when a server answers oddly ({{BIND 9.20 reference|https://bind9.readthedocs.io/en/v9.20.0/reference.html#namedconf-statement-qname-minimization}}). It costs nothing in the common case and can cost extra queries for names many labels deep. Notice also that Unbound sets the CD (checking disabled) flag on its own upstream questions: it validates signatures itself (section 9) and wants the raw data.

Why you cannot see this walk with dig +trace on every network

dig +trace name normally does the walk itself, from the root down, and is the best way to separate "the zone is broken" from "my resolver cached something wrong". It only works if your packets reach the root servers. On the laptop this page was recorded on, a filter answers every plain DNS packet itself, even one addressed to a root server and even from inside a container: asked example.com without recursion, a.root-servers.net's address replied with a final answer and the RA flag set, which a real root server never does (it would refer you to the .com servers). Corporate device management, VPNs and security software often do this. That is why the walk on this page is recorded on a private tree, and why the public lookups were sent over DNS over TLS (section 10).
