7. Kubernetes: search lists, ndots and the cluster DNS

What a pod gets. With the default dnsPolicy: ClusterFirst, kubelet writes every pod a resolv.conf that points at the cluster DNS service (CoreDNS) and adds a search list and ndots:5 ({{Kubernetes docs|https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/#pod-s-dns-policy}}):

search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

This is what lets code in namespace default say http://llm-proxy and reach llm-proxy.default.svc.cluster.local. CoreDNS answers cluster.local names from the Kubernetes API and forwards everything else upstream. Note that the policy named Default is not the default: it copies the node's resolver settings instead.

The rule that costs. A name with fewer dots than ndots is tried with every search suffix before it is tried as written. api.llm.test has two dots, fewer than five, so the stub first asks for api.llm.test.default.svc.cluster.local, then api.llm.test.svc.cluster.local, then api.llm.test.cluster.local, each for both A and AAAA, and only then for api.llm.test. External API names (api.anthropic.com, s3.us-east-1.amazonaws.com: two and three dots) all pay this. The fixes, in order of preference.

  1. Write external names with a trailing dot (api.anthropic.com.): absolute, one A and one AAAA, nothing else. Most HTTP clients accept it; a few TLS stacks dislike the dot in the server name, so test it.
  2. Lower ndots for the pod with dnsConfig: {options: [{name: ndots, value: "1"}]} (or 2). External names are then tried as written first. The catch, recorded above: short in-cluster names with a dot, such as kubernetes.default or svc.namespace, are tried as absolute names first, fail, and glibc then falls back to the search list, but musl does not: it never retries a name with at least ndots dots against the search list ({{musl wiki|https://wiki.musl-libc.org/functional-differences-from-glibc.html#Name-Resolver/DNS}}), so on Alpine kubernetes.default stopped resolving at all. Use full names (llm-proxy.default.svc.cluster.local.) in configuration if you lower ndots. corrected The old page said lowering ndots breaks bare short names like myservice; recorded, a name with no dot (myjob-headless) still resolved on both libraries, because zero dots is below any ndots. The names that break are the ones with a dot, and only on musl.
  3. Cache on the node: NodeLocal DNSCache (stable since Kubernetes 1.18) runs a DNS cache on every node as a DaemonSet; pods talk to it on a link-local address (the add-on's default is 169.254.20.10), which skips the iptables DNAT and connection tracking described below, and it can use TCP towards CoreDNS ({{Kubernetes docs|https://kubernetes.io/docs/tasks/administer-cluster/nodelocaldns/}}, {{add-on README|https://github.com/kubernetes/kubernetes/blob/master/cluster/addons/dns/nodelocaldns/README.md}}). It cuts the load but not the number of queries.
  4. CoreDNS autopath does the search-list walk on the server: the first query returns the final answer, so the pod sends one question instead of eight ({{CoreDNS autopath|https://coredns.io/plugins/autopath/}}). It needs CoreDNS to know every pod, which costs memory on big clusters.

The 5-second stall: conntrack races

Pods reach the CoreDNS service address through kube-proxy's iptables rules, which rewrite the destination (DNAT) and record each flow in the kernel's connection tracking table (conntrack). glibc and musl send A and AAAA together from one socket, and UDP has no handshake, so the two packets can race through conntrack on different CPUs. Martynas Pumputis found three races in 2018; in each, one of the two packets is dropped and the pod waits out its 5-second timeout ({{Weave blog, archived|https://web.archive.org/web/20210127131121/https://www.weave.works/blog/racy-conntrack-and-dns-lookup-timeouts}}). The fixes landed over three kernel releases: clashing identical entries are resolved (Linux 4.19, {{ed07d9a|https://github.com/torvalds/linux/commit/ed07d9a021df6da53456663a76999189badc432a}}), same-origin NAT clashes skipped (5.0, {{4e35c1c|https://github.com/torvalds/linux/commit/4e35c1cb9460240e983a01745b5f29fe3a4d8e39}}), and clashing UDP entries allowed to coexist briefly, which covers the third race where the two packets were sent to different CoreDNS pods (5.6, {{6a757c0|https://github.com/torvalds/linux/commit/6a757c07e51f80ac34325fcd558490d2d1439e1b}}). corrected The old page said the first two were fixed in 4.17 and the third "never"; on nodes older than 5.6 it still bites.

The symptom is the fingerprint: lookups that take 5.0x seconds (or 2.5 on Alpine), the stub's timeout, never "slow" in general. The lab's dropped-packet runs in section 6 show exactly that number. Workarounds for old kernels: options single-request-reopen (glibc only), timeout:1, or NodeLocal DNSCache.

  • Forwarding loops crash it on purpose. Distributed training: finding the other ranks


A ClusterIP service gives one virtual address that forwards each connection to one random pod, which is useless when every rank must reach every other rank. A headless service (clusterIP: None) instead returns one A record per ready pod, and pods of a StatefulSet get stable names, myjob-0.myjob-headless.default.svc.cluster.local and so on ({{StatefulSet docs|https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#stable-network-id}}); the lab's myjob-headless answered with all four pod addresses. The trap: pods get records only once they are ready, and a training pod often cannot become ready until rendezvous succeeds, which needs the records. publishNotReadyAddresses: true on the service publishes them early; the API reference names StatefulSet peer discovery as its main use ({{Service API|https://kubernetes.io/docs/reference/kubernetes-api/service-resources/service-v1/#ServiceSpec}}). A torchrun job that hangs at start-up waiting for its master address is worth checking for this. Training jobs also suffer most from the 5-second stall, since every rank resolves at once. Placement, collectives and fabrics are on {{Distributed Training|n:3c65c17b0d0d8103a916c4824abbd82e}} and {{Training Infrastructure|n:3c65c17b0d0d81c9b2cac997583bf572}}.


For serving, DNS round-robin across model replicas is a poor load balancer: clients cache one address, and DNS knows nothing about queue depth or cached prompts. Put a real router in front, or let the client balance: the {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} page (its section 8) records gRPC pinned to one replica behind an L4 balancer, and the fix this section's headless Service enables, client-side round_robin over every Pod address from dns:///name.
