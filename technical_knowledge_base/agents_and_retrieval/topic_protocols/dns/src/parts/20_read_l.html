10. Privacy and attacks

Encrypted DNS: DoT, DoH, DoQ

Plain DNS is readable and rewritable by every network it crosses: your Wi-Fi, your ISP, a filter on your laptop. Three standards encrypt the hop from your machine to the resolver: DNS over TLS (DoT), TCP port 853 ({{RFC 7858|https://www.rfc-editor.org/rfc/rfc7858}}, 2016); DNS over HTTPS (DoH), ordinary HTTPS requests on port 443 ({{RFC 8484|https://www.rfc-editor.org/rfc/rfc8484}}, 2018); and DNS over QUIC (DoQ), UDP port 853 ({{RFC 9250|https://www.rfc-editor.org/rfc/rfc9250}}, 2022). DoT is easy for a network to recognise and block by port, which enterprises like and censors exploit; DoH looks like any other web traffic, which is why enterprises dislike it; DoQ avoids TCP's head-of-line blocking and sets up faster. In one academic measurement DoQ loaded simple pages up to 10% faster than DoH and was only about 2% slower than plain DNS on complex pages (Kosek et al., {{IMC 2022|https://arxiv.org/abs/2305.00790}}). corrected The old page's "88 ms against 883 ms, 2026 measurements" could not be found in any source and is not repeated.

Seen from this laptop. Every public lookup on this page went over DoT to 1.1.1.1 with the certificate checked against one.one.one.one, and a test query for the resolver's identity returned a Cloudflare data-centre code, so the answers really came from the public resolver. The same identity query over plain UDP was answered by the laptop's filter instead. Each encrypted answer arrived padded to 468 bytes: the resolver pads responses to a multiple of 468 so the size does not reveal the name ({{RFC 8467|https://www.rfc-editor.org/rfc/rfc8467}}; measured: all ten replies whose size was recorded were exactly 468 bytes, whatever the name). Encryption made the interception visible rather than silent, which is also how the root's Failure lab caught it.

Cache poisoning: forging an answer

Over UDP a resolver accepts the first reply whose 16-bit ID and port match its question. In 2008 Dan Kaminsky showed that an attacker who triggers many lookups of random names in one zone can race the real server with forged replies carrying a forged delegation, and with a fixed source port only the ID (on average 32,768 guesses) stood in the way ({{CERT VU#800113|https://www.kb.cert.org/vuls/id/800113}}). The fix was source-port randomisation, adding up to another 16 bits ({{RFC 5452|https://www.rfc-editor.org/rfc/rfc5452#section-9.2}}); later layers are DNS cookies ({{RFC 7873|https://www.rfc-editor.org/rfc/rfc7873}}) and randomising the letter case of the question ("0x20", an expired {{draft|https://datatracker.ietf.org/doc/draft-vixie-dnsext-dns0x20/}}). In 2020 SAD DNS recovered the random port through a side channel in the kernel's global ICMP rate limit, fixed in Linux by randomising that limit ({{saddns.net|https://www.saddns.net/}}, {{CVE-2020-25705 fix|https://github.com/torvalds/linux/commit/b38e7819cae946e2edf869e604af1e65a5d241c5}}). Fragmented answers are another way around the port check, one more reason for the 1,232-byte limit. DNSSEC is the only complete fix.

DNS rebinding: the attack that matters most for ML engineers

Browsers decide what a page may read by its origin: scheme, host name and port ({{HTML standard|https://html.spec.whatwg.org/multipage/browsers.html#same-origin}}), not the IP address behind the name. An attacker's name first resolves to the attacker's server, which serves JavaScript; with a TTL of 0 the next lookup of the same name returns 127.0.0.1, a LAN address or the cloud metadata address 169.254.169.254, and the script, still "same origin", reads whatever is there. Every notebook, Ray dashboard, MLflow, TensorBoard or model server bound to 0.0.0.0 without authentication is reachable this way from a browser on the same network. Chrome now asks the user before a public site may reach local addresses (Local Network Access, from Chrome 142, late October 2025; {{Chrome blog|https://developer.chrome.com/blog/local-network-access}}); servers should still check the Host header, as the {{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}} page shows for MCP servers.

The same trick against an agent's fetch tool. A tool that fetches URLs for a model usually checks the URL first ("refuse internal addresses") and then fetches it. If the check resolves the name and the HTTP library resolves it again, the two lookups can get different answers. The lab reproduces it: rebind.attacker.test answers alternately with the attacker's server and with 10.53.0.99, a stand-in for the metadata address, always with TTL 0; a 30-line fetch tool is run twice, written two ways:

measured: the attacker's DNS server log and the tool's own output; the "credential" is a fake string served by a container. The real metadata service also needs the fix below.

The fix

Resolve once, validate the address (not the name), connect to that literal address and send the name in the Host header (and as TLS SNI); refuse redirects or re-validate them the same way. On AWS, require IMDSv2, whose session token must be fetched with a PUT, so a plain GET from a rebinding page or a naive proxy fails; a response hop limit of 1 also keeps the token from reaching containers behind a bridge (AWS notes that containers then need a limit of 2 if they genuinely need the service; {{AWS IMDS docs|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-IMDS-existing-instances.html}}). The MCP specification lists this among the checks a client must make before fetching a URL a server gave it ({{MCP security best practices|https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices}}).

Exfiltration: data out through your own resolver

Any machine that can resolve names can send data out: encode it in the labels of a name under a domain the attacker controls (c2VjcmV0.x.attacker.example), and your own resolver carries it to the attacker's authoritative server, past egress firewalls that only watch HTTP. It is slow but enough for keys. The SolarWinds SUNBURST backdoor (disclosed December 2020) used DNS for its first stage: it encoded the victim's domain name into subdomains of avsvmcloud[.]com and read its instructions from the answers, then moved to HTTPS for the rest ({{Mandiant|https://cloud.google.com/blog/topics/threat-intelligence/evasive-attacker-leverages-solarwinds-supply-chain-compromises-with-sunburst-backdoor}}). Detection watches, per parent domain, the number of unique subdomains, the randomness of labels and the share of NXDOMAIN answers. On AWS this needs Route 53 Resolver query logging, which you must configure; it is not on until you create a logging configuration ({{AWS|https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver-query-logs.html}}).
