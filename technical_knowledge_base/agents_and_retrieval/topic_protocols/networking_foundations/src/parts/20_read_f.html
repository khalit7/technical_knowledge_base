5. Windows: why one connection is capped at window over round trip

The problem. A fast sender can overrun a slow reader. TCP's flow control stops it: every ACK carries the receiver's receive window, the free space left in its buffer, and the sender never has more unacknowledged bytes in flight than that. The congestion window (section 6) is a second, separate cap that protects the network. The sender may have at most min(receive window, congestion window) bytes unacknowledged.

The rule that explains most slow transfers follows directly. The sender can put one window's worth of bytes in flight, then must wait for acknowledgements, which take one round trip to come back. So at most one window arrives per round trip, however fast the link:

throughput ≤ window / RTT    and to fill a link: window ≥ bandwidth × RTT (the bandwidth-delay product, BDP)
window
bytes allowed in flight without acknowledgement
RTT
round-trip time; under load it includes queueing (section 6)
BDP
10 Gbit/s × 100 ms = 125 MB; 25 Gbit/s × 1 ms = 3.1 MB; 100 Gbit/s × 50 µs = 625 KB (derived)

Window scaling. The window field in the TCP header is 16 bits, so the largest window it can state is 65,535 bytes; over a 100 ms path that caps one connection at 65,535 × 8 / 0.1 = 5.2 Mbit/s whatever the link (derived). The window-scale option ({{RFC 7323 s2|https://www.rfc-editor.org/rfc/rfc7323#section-2}}) multiplies the field by 2shift, with the shift (at most 14, so windows up to 1 GiB) agreed once, in the SYN. A middlebox that strips it, or a socket whose buffer was small when it connected, is stuck with a small window for the life of the connection.

Measured: the buffer you set is the speed you get

Twelve downloads from Cloudflare's speed-test endpoint over one TCP connection each, the receive buffer fixed with SO_RCVBUF before connect() or left to the kernel, goodput measured over the second half of each transfer. The prediction is the measured window over the measured smoothed RTT; the link itself tops out near 46 Mbit/s.

Defaults reproduce the window-over-RTT rule independently: for the two window-limited buffers the measured goodput is within about 10 percent of window / RTT (the RTT is reported in whole milliseconds, so the prediction itself is only that precise); at 256 KB and with autotuning the prediction exceeds the link, and the link wins. The kernel advertised 28,728 to 29,776 bytes for a 16 KB request: macOS sizes the buffer above what you ask for, so read the window the kernel reports (tcpi_rcv_wnd), not the number you passed. Raw runs: src/meas/out/tcp_path.json.

Autotuning. Modern kernels grow the receive buffer as the connection proves it needs one. In the autotuned runs the advertised window grew from 128 KB to about 0.9 to 1.4 MB within a few hundred milliseconds (measured, first run below), with a window-scale shift of 6 against 3 when the buffer was fixed small: the kernel picks the shift at connect() from the buffer size at that moment.

The trap: setting a buffer can make you slower
Linux documents that calling setsockopt(SO_RCVBUF) disables receive autotuning for that socket ({{tcp_rmem in ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}). A client "tuned" with a 256 KB buffer is capped at 256 KB / RTT: on a 100 ms cross-region path that is 21 Mbit/s (derived), far below an untuned client whose window grows to tcp_rmem's maximum (default between 128 KB and 32 MB depending on memory). Two separate knobs: net.ipv4.tcp_rmem's third value caps autotuning; net.core.rmem_max caps only explicit setsockopt calls, and its default rose from 212,992 bytes to 4 MB in Linux 6.18 ({{commit a6d4f25888b8|https://github.com/torvalds/linux/commit/a6d4f25888b8}}, so guides that quote "208 KB" describe older kernels). For a 10 Gbit/s, 100 ms path the third value of tcp_rmem and tcp_wmem must be at least the 125 MB BDP.
How it shows up. A transfer far below the link speed with no retransmissions, and a throughput that changes with distance rather than with load. ss -ti on Linux shows rcv_space, snd_wnd and cwnd; iperf3 -c host -P 1 against -P 8 demonstrates the per-connection cap to anyone who doubts it.
