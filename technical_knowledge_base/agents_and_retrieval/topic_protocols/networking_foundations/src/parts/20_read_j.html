9. Idle connections, NAT tables and dead peers

NAT in one paragraph. A machine with a private address (section 1) reaching the internet goes through network address translation: a NAT device (a home router, a cloud NAT gateway, a Kubernetes node doing SNAT for its pods) rewrites the source address and port of each outgoing packet to its own public address and a port it allocates, and remembers the mapping in a table so it can rewrite the replies back. The table entry is the connection, as far as the NAT is concerned. Two limits follow: the table has a size, and entries for connections that look idle are thrown away.

Idle timeouts are shorter than you think. The IETF's NAT requirements ask that an established TCP mapping survive at least 2 hours 4 minutes of idleness ({{RFC 5382 REQ-5|https://www.rfc-editor.org/rfc/rfc5382#section-5}}) and a UDP mapping at least 2 minutes ({{RFC 4787 REQ-5|https://www.rfc-editor.org/rfc/rfc4787#section-4.3}}), but real devices choose their own: an AWS NAT gateway times out a connection idle for 350 seconds and answers later packets with a reset, not a FIN ({{AWS NAT troubleshooting|https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-troubleshooting.html}}). Load balancers do the same with their own idle timers. Neither end is told. The next write fails with "connection reset by peer", or, if the middlebox drops silently, hangs until a retransmission timer gives up.

TCP keepalive is not a heartbeat by default. With SO_KEEPALIVE on, Linux waits 7,200 s of idleness, then probes 9 times 75 s apart: 2 hours 11 minutes before it declares a silent peer dead (TCP_KEEPALIVE_TIME (120*60*HZ), TCP_KEEPALIVE_PROBES 9, TCP_KEEPALIVE_INTVL (75*HZ) in {{tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}; derived 7,200 + 9 × 75 = 7,875 s). This Mac uses 7,200 s, 75 s and 8 probes (measured sysctl). Both are far longer than a 350 s NAT timeout, so to keep a pooled connection alive through NAT set the per-socket options (TCP_KEEPIDLE, TCP_KEEPINTVL, TCP_KEEPCNT on Linux; TCP_KEEPALIVE on macOS) below the shortest idle timer on the path, as AWS's own fix says, or have the pool discard connections idle longer than that.

Keepalive cannot see a wedged peer. A process that is alive but stuck (a training rank deadlocked in a collective, a server stuck in garbage collection) still has a kernel that answers keepalive probes. For data you have sent, TCP_USER_TIMEOUT bounds how long it may stay unacknowledged before the connection is dropped (Linux 2.6.37 and later, {{man 7 tcp|https://man7.org/linux/man-pages/man7/tcp.7.html}}; standardised as an option in {{RFC 5482|https://www.rfc-editor.org/rfc/rfc5482}}). For everything else you need an application-level heartbeat and a deadline: NCCL's watchdog timeout in PyTorch, gRPC deadlines, an SSE stream's ping events. The Failure lab's "Reused keep-alive connection closed by the server" and "Read timeout: connected, then nothing" cases show both shapes with real client errors.

NAT tables fill up

Every connection through a NAT uses one of its source ports. An AWS NAT gateway supports up to 55,000 simultaneous connections per public IPv4 address to each unique destination (destination address, port and protocol), 5 Gbit/s scaling to 100 Gbit/s, and 1 to 10 million packets per second; beyond the connection limit its ErrorPortAllocation metric counts the connections it could not open ({{NAT gateway basics|https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html}}, {{CloudWatch metrics|https://docs.aws.amazon.com/vpc/latest/userguide/metrics-dimensions-nat-gateway.html}}). A fleet of dataloader workers opening fresh connections to the same storage endpoint can reach it. Fixes in order: reuse connections; add addresses to the NAT gateway; and for S3 or DynamoDB, take NAT out of the path with a gateway VPC endpoint, which has no additional charge and needs no NAT device ({{gateway endpoints|https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html}}).

Symptoms and commands. Failures only after idle periods, at a suspiciously round interval (350 s, 600 s, 3,600 s): a middlebox idle timer; compare the timestamps of failures with the time each connection was last used. New connections failing while old ones work: a full NAT table (check the gateway's port-allocation metric; on a Linux NAT, conntrack -S). ss -to (Linux) shows each socket's keepalive timer. SSH sessions to a cluster hit exactly these idle timers; the {{SSH|n:3c65c17b0d0d81f88f50e478c94ebdcd}} page (its section 9) records ServerAliveInterval detecting a dead path in seconds where TCP keepalive would take two hours.
