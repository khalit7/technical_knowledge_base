8. The server side: accept queues, ports shared by workers, file descriptors

The accept queue. The kernel completes the handshake on its own; accept() only hands your program a connection that is already established. Finished connections wait in an accept queue whose length is the backlog you passed to listen(), capped by somaxconn: 4,096 on Linux since 5.4 and 128 before ({{ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}; many tuning guides predate the change), and 128 on this Mac (measured kern.ipc.somaxconn). A server that accepts more slowly than clients arrive (a single-threaded process busy loading a model, a rendezvous rank before it calls accept) fills it.

What happens when it is full differs by kernel. Linux drops new SYNs while the queue is full (tcp_conn_request in {{tcp_input.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_input.c}} counts a ListenOverflow and drops), so the client retransmits its SYN after its 1 s initial timeout, then 2 s later: connects that take 1 s or 3 s instead of a millisecond. A handshake that completes while the queue is full has its final ACK ignored, unless tcp_abort_on_overflow is on, in which case the client gets a reset ({{tcp_minisocks.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_minisocks.c}}; off by default). measured on this Mac with listen(2) and a server that does not call accept() until all eight clients have tried:

Seven of eight connect() calls succeeded in under a millisecond, yet only the first two clients were ever served; the others learned they had been dropped only when they wrote (broken pipe) or read (reset). A successful connect is not a server that will answer. That is why a client needs a read timeout as well as a connect timeout, and why a health check should send a request, not just open a socket.

See it on Linux. ss -lnt: for a listening socket, Recv-Q is the current accept-queue length and Send-Q its limit (idiag_rqueue = sk_ack_backlog, idiag_wqueue = sk_max_ack_backlog in {{tcp_diag.c|https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_diag.c}}). nstat -az TcpExtListenOverflows TcpExtListenDrops counts the drops. Fix: accept faster (more workers, an event loop), raise the backlog in the code and somaxconn, and have clients retry with jitter.

Many workers, one port

SO_REUSEPORT lets several sockets, typically one per worker process, bind the same address and port; the kernel spreads incoming connections across them, so N workers accept in parallel without fighting over one queue (see SO_REUSEPORT in {{man 7 socket|https://man7.org/linux/man-pages/man7/socket.7.html}}). SO_REUSEADDR is a different, older option: it lets a restarted server bind its port while old connections on it are still in TIME_WAIT, which is why almost every server sets it.

Every connection is a file descriptor

Each socket uses one file descriptor, and processes have a limit (ulimit -n). A server with thousands of streaming clients, or a dataloader with many workers each holding connections, hits it with EMFILE ("Too many open files"); compare ls /proc/PID/fd | wc -l with the limit. On Slurm clusters the job inherits the soft limits of the shell it was submitted from, unless the administrator configured otherwise (PropagateResourceLimits, whose default is to propagate all limits, {{slurm.conf|https://slurm.schedmd.com/slurm.conf.html}}); check inside the job with srun bash -c 'ulimit -n' rather than trusting the login node.

Correction to the old page
The old page said that on Slurm "limits are inherited from slurmd's environment rather than your login shell, so ulimit -n in your .bashrc will not help a job". The current slurm.conf documentation says the opposite by default: slurmd reads the soft limits from the user's environment on the submit node and applies them to the job, unless PropagateResourceLimits or PropagateResourceLimitsExcept is configured. What is true: a cluster can be configured not to propagate, and a job cannot raise a limit above what the node allows.
