13. Moving big things: checkpoints, datasets, weights

The arithmetic first. A 70-billion-parameter model in bf16 (2 bytes per parameter) is 140 GB of weights. A full training checkpoint with Adam in mixed precision usually also holds an fp32 master copy and two fp32 moments, 4 + 4 + 4 more bytes per parameter: 14 bytes per parameter, 980 GB (derived; layouts vary by framework). Over one connection capped at 5 Gbit/s that is 140 × 8 / 5 = 224 s for the weights and 980 × 8 / 5 = 1,568 s, 26 minutes, for the full state (derived), per checkpoint, during which the GPUs may be waiting.

Four separate ceilings on one connection, and the lowest one wins:

  1. Window over RTT (section 5): a 16 MB window over a 100 ms cross-region path is 1.3 Gbit/s (derived).
  2. Loss: for loss-based congestion control the long-run rate is about (MSS / RTT) × 1.22 / √p ({{Mathis et al., 1997|https://dl.acm.org/doi/10.1145/263932.264023}}): 1,460-byte segments, 100 ms, one loss in 100,000 packets gives 45 Mbit/s (derived), whatever the link. (The old page said 37 Mbit/s: it left out the constant √(3/2) = 1.22.)
  3. Per-flow policy: AWS limits one flow (one 5-tuple) to 5 Gbit/s between instances outside a cluster placement group, up to 10 Gbit/s inside one, and up to 25 Gbit/s between instances in one Availability Zone with ENA Express ({{EC2 instance network bandwidth|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-network-bandwidth.html}}).
  4. The NIC and the instance's own bandwidth, shared by all flows.

The fix is always parallel streams. Each of the first three ceilings applies per connection, so N connections get up to N times as much until the NIC is full. That is what S3 multipart upload is for (an object split into up to 10,000 parts of 5 MiB to 5 GiB, uploaded concurrently, {{S3 multipart limits|https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html}}); what PyTorch's Distributed Checkpoint does by having every rank write its own shard ("saving models from multiple ranks in parallel", {{DCP docs|https://docs.pytorch.org/docs/stable/distributed.checkpoint.html}}); what tools such as s5cmd and rclone do with many concurrent transfers; and why NCCL opens several sockets per peer (section 14). AWS's own documentation lists Multipath TCP and ENA Express as ways past the single-flow cap. The {{Throughput lab|#t-thru}} tab works out, for a checkpoint size and a path you choose, which ceiling binds and how many streams it takes.

Request rates, not bytes, bound small objects. S3 supports at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix ({{S3 performance|https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html}}). Ten million small image files are a request-rate and latency problem (each GET pays at least a round trip, plus a handshake if the connection is not reused), not a bandwidth one. Pack them into large sequential shards (WebDataset tar files, Parquet, MosaicML's MDS) so each request moves megabytes, spread keys across prefixes, keep connections alive, and prefetch with several workers, which is the parallel-streams trick again.

A checklist for a slow transfer
  1. Is it one connection? Count with ss -tn dst HOST (Linux) or lsof -nP -iTCP.
  2. Divide the observed rate into window / RTT: if they match, the window binds; raise buffers (and do not set SO_RCVBUF by hand) or add streams.
  3. Retransmissions growing (nstat, ss -ti)? Loss binds: find it (mtr, NIC counters with ethtool -S) or use more streams.
  4. Does it stop at a round number (5, 10, 25 Gbit/s)? A per-flow policy cap.
  5. Is it going through a NAT gateway or out of the region? Use a gateway endpoint for S3, and keep data in the region where it is used.
Recent kernel work worth a line. Linux 6.15 added io_uring zero-copy receive (the {{iou-zcrx documentation|https://docs.kernel.org/networking/iou-zcrx.html}} was merged then), and {{devmem TCP|https://docs.kernel.org/networking/devmem.html}} lets a NIC place received payloads directly in device memory such as a GPU's. Both cut the CPU cost of receiving at high rates; they matter for ingest and serving rather than for NCCL, which already bypasses the kernel when it uses RDMA.
