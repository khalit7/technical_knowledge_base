10. MTU: the largest packet, and the hang it causes

The problem. Every link has a maximum transmission unit (MTU), the largest IP packet it carries: 1,500 bytes on standard Ethernet, less on links that wrap packets in extra headers. A packet that is too big for the next link must be split (fragmented) or dropped. Fragmentation is costly and fragile (lose one fragment and the whole packet is lost), so TCP avoids it: each side announces an MSS in its SYN, the MTU minus the IP and TCP headers (1,500 − 20 − 20 = 1,460 for IPv4; 1,440 for IPv6), and the timestamp option then takes 12 bytes of every segment.

Path MTU discovery. The sender's own link may be 1,500 while a link further on is smaller. So TCP sends with the Don't Fragment bit set, and a router that cannot forward a packet drops it and returns an ICMP message, "fragmentation needed" with the next link's MTU (IPv4, {{RFC 1191|https://www.rfc-editor.org/rfc/rfc1191}}) or "packet too big" (IPv6, {{RFC 8201|https://www.rfc-editor.org/rfc/rfc8201}}); the sender lowers its packet size for that destination. measured from this laptop (interface MTU 1,500) with don't-fragment pings to Cloudflare's resolver: the home router answered the oversized probes with exactly that message, naming an MTU of 1,492, and a binary search found the largest ping payload that gets through, 1,464 bytes (+ 28 bytes of IP and ICMP headers = 1,492).



1,492 is the classic signature of PPPoE, which carries IP over a DSL or fibre line inside an 8-byte header ({{RFC 2516|https://www.rfc-editor.org/rfc/rfc2516}}: "the PPP MTU MUST NOT be greater than 1492"). On this path the TCP connections to Cloudflare used a segment size of 1,388 bytes (tcpi_maxseg), below the 1,492 − 40 − 12 = 1,440 this link allows (derived), so the smaller limit came from the server's side of the negotiation, which cannot be seen without a packet capture. IPv6 could not be probed the same way: ping6 -D needs root on macOS ("IPV6_DONTFRAG: Operation not permitted").


The black hole


Path MTU discovery depends on that ICMP message coming back. A firewall or security group that drops all ICMP breaks it, and the failure has a signature worth memorising: the handshake and small requests work, then the first full-size packet vanishes and the transfer hangs. A TLS handshake whose certificate chain needs a full-size packet, a large POST, a big model download, or an allreduce over a VPN all stall while curl to a health endpoint passes. The fixes: allow ICMP "fragmentation needed" / "packet too big" through; clamp the MSS on the tunnel or router; or let TCP find the size by probing (packetization-layer PMTUD, {{RFC 4821|https://www.rfc-editor.org/rfc/rfc4821}}; Linux net.ipv4.tcp_mtu_probing=1 turns it on when a black hole is detected, 2 always, default 0, {{ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}). QUIC and other datagram protocols probe the same way ({{RFC 8899|https://www.rfc-editor.org/rfc/rfc8899}}).


Jumbo frames in the cloud and the mixed-MTU trap


Inside an AWS VPC every current-generation instance supports 9,001-byte jumbo frames, about six times fewer packets per byte than 1,500 (derived: 8,949 / 1,448 payload bytes per segment with timestamps). Traffic through an internet gateway, over a VPN, or between regions (unless through a transit gateway) is limited to 1,500, and inter-region VPC peering to 8,500 ({{EC2 network MTU|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/network_mtu.html}}). Within one cluster placement group AWS recommends jumbo frames. Two failure modes follow. Traffic leaving the VPC at 9,001 depends entirely on path MTU discovery working. And nodes in one job with different MTUs (one image sets 9,001, another 1,500) pass every small message and hang on the first large one: a training job whose small collectives succeed and whose first large allreduce never completes. Check every node: ip link show (the mtu field), then ping -M do -s 8973 peer (Linux; 8,973 + 28 = 9,001) between each pair.


Correction to the old page
The old page said NAT gateways cap at 8,500 bytes. The current EC2 MTU documentation (fetched 5 October 2026) lists 8,500 only for inter-region VPC peering, and 1,500 for internet gateways, VPN and inter-region traffic; it gives no NAT gateway figure, so this page does not repeat one.


Commands. macOS: ping -D -s 1472 host (1,472 + 28 = 1,500); Linux: ping -M do -s 1472 host, and tracepath host, which reports the path MTU hop by hop without root. A reply of "frag needed and DF set (MTU n)" tells you the limit; silence at one size and success just below it, with no ICMP message, is a black hole.
