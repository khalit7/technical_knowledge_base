2. Ports, sockets and the 5-tuple

An address picks a machine; a port (16 bits, 0 to 65,535) picks the program. A socket is the operating system's handle for one end of a conversation: your code reads and writes it, the kernel runs the protocol. Servers listen on a well-known port (443 for HTTPS, 22 for SSH, 29500 by convention for torch.distributed's rendezvous); the client's kernel picks a temporary ephemeral port for its end. A TCP connection is named by its 5-tuple, and the kernel at each end uses it to find the socket for every arriving packet.

Only the client's port varies, so one client address has a few tens of thousands of connections to one server port

Three connections from one client to one HTTPS server: the protocol, both addresses and the server's port are the same, and the ephemeral source port is the only thing that tells them apart. The ephemeral range is 32,768 to 60,999 on Linux, 28,232 ports ({{ip-sysctl docs|https://docs.kernel.org/networking/ip-sysctl.html}}), and 49,152 to 65,535 on this Mac, 16,384 ports (measured sysctl net.inet.ip.portrange, the IANA dynamic range of {{RFC 6335|https://www.rfc-editor.org/rfc/rfc6335}}).

Three consequences follow from the picture. Section 3 shows how TIME_WAIT turns the port count into a rate limit. Anything that rewrites addresses or ports (NAT, section 9; a load balancer) must keep a table keyed on the 5-tuple, and that table fills and forgets. And changing any element ends a TCP connection: a laptop moving from Wi-Fi to a phone hotspot gets a new address and every TCP connection on it dies, while QUIC survives the move (section 12 records it).

Server

socket() → bind(addr, port) → listen(backlog) → loop: accept() returns a new socket per client → recv/send → close()

Client

socket() → connect(addr, port) (the kernel picks the ephemeral port and runs the handshake) → send/recv → close()

Which address the server binds matters. 127.0.0.1 (loopback) accepts only from the same machine; 0.0.0.0 (or ::) accepts on every interface. A model server bound to 127.0.0.1 inside a container is unreachable from outside even with the port published, and the client sees "connection refused" (the root's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "Connection refused" shows the exact error text of curl, requests, httpx and Node). The reverse mistake, a notebook on 0.0.0.0 on a machine with a public address, exposes it to the internet. How one process serves thousands of sockets at once (epoll, kqueue, the event loop) is the {{Concurrency|n:3f05c17b0d0d8112ad1af99308fa913f}} page's.

A TCP socket is a stream, not a list of messages

TCP promises the bytes and their order, not where your writes started and ended; UDP keeps each datagram whole. measured on loopback, three writes of token-000n, reader started after the writes:



So every protocol on TCP has framing: HTTP/1.1 uses Content-Length or chunk sizes, Server-Sent Events use blank lines, gRPC and HTTP/2 put a length in front of each frame. Code that assumes "one recv equals one message" passes every test on loopback and fails under load or on a real network, where segments split and merge differently.


See it yourself (commands)
lsof -nP -iTCP -sTCP:ESTABLISHED (macOS and Linux) or ss -tnp (Linux) lists each connection's 5-tuple and owning process; lsof -nP -iTCP:8000 -sTCP:LISTEN shows who listens on a port and on which address.
