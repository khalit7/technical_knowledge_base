2. Ports, sockets and the 5-tuple

The problem. An address picks a machine, but a machine runs many programs. A port (a 16-bit number, 0 to 65,535) picks the program. A socket is the operating system's handle for one end of a conversation: your code reads and writes the socket, the kernel does the protocol. Servers listen on a well-known port (443 for HTTPS, 22 for SSH, 29500 by convention for torch.distributed's rendezvous); the client's kernel picks a temporary ephemeral port for its end.

A TCP connection is named by its 5-tuple: protocol, source address, source port, destination address, destination port. Every packet of the connection carries the four addresses and ports, and the kernel at each end uses them to find the socket. Three consequences you will meet:

  • One client address can only have so many connections to one server address and port, because only the source port varies. The ephemeral range is 32,768 to 60,999 on Linux, 28,232 ports ({{ip-sysctl docs|https://docs.kernel.org/networking/ip-sysctl.html}}), and 49,152 to 65,535 on this Mac, 16,384 ports (measured: sysctl net.inet.ip.portrange, the IANA dynamic range of {{RFC 6335|https://www.rfc-editor.org/rfc/rfc6335}}). Section 3 shows how TIME_WAIT turns that into a rate limit.
  • Anything that rewrites addresses or ports (NAT, section 9; a load balancer) must keep a table keyed on the 5-tuple, and the table is a resource that fills and forgets.
  • Changing any element ends a TCP connection. A laptop moving from Wi-Fi to a phone hotspot gets a new address, so every TCP connection on it dies. QUIC names connections differently and survives this; section 12 records it happening.

The calls behind every server and client

Server

socket() → bind(addr, port) → listen(backlog) → loop: accept() returns a new socket per client → recv/send → close()

Client

socket() → connect(addr, port) (the kernel picks the ephemeral port and runs the handshake) → send/recv → close()

Which address the server binds matters. 127.0.0.1 (loopback) accepts connections only from the same machine; 0.0.0.0 (or ::) accepts on every interface. A model server started on 127.0.0.1 inside a container is unreachable from outside the container even with the port published, and the client sees "connection refused" (the root's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "Connection refused" shows the exact error text of curl, requests, httpx and Node). The reverse mistake, a notebook or debug server on 0.0.0.0 on a machine with a public address, exposes it to the internet.

A TCP socket is a stream, not a list of messages

TCP promises the bytes and their order, not where your writes started and ended. Three writes of 10 bytes can arrive as one read of 30, or as reads of 7 and 23; UDP keeps each datagram whole. measured on loopback, three writes of token-000n each, reader started after the writes:



This is why every protocol on TCP has framing: HTTP/1.1 uses Content-Length or chunk sizes, Server-Sent Events use blank lines, gRPC and HTTP/2 put a length in front of each frame. Code that assumes "one recv equals one message" passes every test on loopback and fails under load or on a real network, where segments split and merge differently.


See it yourself. lsof -nP -iTCP -sTCP:ESTABLISHED (macOS and Linux) or ss -tnp (Linux) lists each connection's 5-tuple and owning process; lsof -nP -iTCP:8000 -sTCP:LISTEN shows who listens on a port and on which address.
