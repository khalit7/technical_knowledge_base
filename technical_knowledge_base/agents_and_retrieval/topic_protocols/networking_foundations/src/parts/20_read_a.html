The idea in one screen

Every byte you send rides in an IP packet that may be lost, and TCP turns those packets into a reliable stream by numbering bytes, waiting for acknowledgements and never having more than one window unacknowledged, so one connection moves at most one window per round trip. Almost every slow transfer, stalled token stream or hung training job traces back to that sentence, or to one of the boxes that rewrite or drop packets on the way.

Each layer adds one header and one promise; a streamed token pays 52 bytes of header for 124 of data

Drawn to scale in bytes. Top: one full-size segment of a checkpoint download on standard Ethernet (MTU 1,500). Bottom: one token of the running request (124 bytes on the wire as a Server-Sent Event, recorded by the root page). IP's 20 bytes carry the two addresses and the hop counter (section 1); TCP's 20, usually 32 with the timestamp option, carry the two ports, the byte numbers, the acknowledgement and the window (sections 2 to 7); UDP would carry only ports, length and checksum in 8 (section 11). The link below IP only sets the size limit, the MTU (section 10).

You need nothing beyond what an engineer who has called an HTTP API knows. The overview of one LLM request through every layer is section 3 of {{Topic: protocols|n:3c65c17b0d0d81ec9355f4eecd6eed02}}; this page is the depth under it. The running example is that root's streaming request: 277 bytes up, then Server-Sent Events, one small write per token about 50 ms apart. Later sections scale it up to the transfer that hurts most in ML work, a checkpoint of hundreds of gigabytes across a long path.
