7. Small writes: Nagle, delayed ACKs and streamed tokens

The problem, 1984 edition. A terminal user typing one character at a time sent one 41-byte packet per keystroke (40 bytes of headers, 1 of data), which flooded slow links. Nagle's algorithm ({{RFC 896|https://www.rfc-editor.org/rfc/rfc896}}, January 1984; {{RFC 9293 s3.7.4|https://www.rfc-editor.org/rfc/rfc9293#section-3.7.4}}) fixed it: while any sent data is still unacknowledged, hold new small writes and send them together when the ACK arrives or a full segment's worth has accumulated.

The other half. A receiver may wait before acknowledging, hoping to piggyback the ACK on a reply: a delayed ACK, which must be under 0.5 s, with an ACK for at least every second full-sized segment ({{RFC 1122 s4.2.3.2|https://www.rfc-editor.org/rfc/rfc1122#section-4.2.3.2}}). Linux delays between 40 ms and 200 ms (TCP_DELACK_MIN (HZ/25), TCP_DELACK_MAX (HZ/5) in {{tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}).

Together they deadlock for a while. A client writes a request in two pieces (headers, then body): the first piece goes out; Nagle holds the second until the first is acknowledged; the server, which has only half a request, has nothing to reply with, so its delayed ACK waits its 40 ms or more. Every request pays that stall. The same rule bites a token stream: the server writes token 1, then token 2 while token 1 is still unacknowledged, so Nagle holds token 2 until the ACK for token 1 returns, a full round trip later (plus any delayed-ACK wait). On a 100 ms path tokens that left the model 50 ms apart arrive in clumps, one clump per round trip. The {{TCP timeline|#t-tcp}} tab plays the running request both ways.

The fix is one socket option. TCP_NODELAY turns Nagle off: every write goes out at once. Latency-sensitive stacks set it by default: gRPC's C core calls grpc_set_socket_low_latency(fd, 1) on its client and server sockets ({{tcp_client_posix.cc|https://github.com/grpc/grpc/blob/master/src/core/lib/iomgr/tcp_client_posix.cc}}), and Go's TCP connections start with no delay ({{SetNoDelay: "The default is true"|https://pkg.go.dev/net#TCPConn.SetNoDelay}}). TCP_CORK (Linux) is the deliberate opposite, for when you want to assemble a response from several writes and release it as full segments.

Measured: who sets TCP_NODELAY for you

Python's asyncio sets TCP_NODELAY on every TCP transport, but only when the socket reports its protocol as TCP (sock.proto == IPPROTO_TCP in asyncio/base_events.py, read in the 3.13.5 source). On this Mac a socket returned by accept() reports protocol 0, so the server side of an asyncio connection was left with Nagle on while the client side had it off. Whether your server framework sets the option explicitly is worth one getsockopt call; do not assume. The root's Failure lab tried to reproduce the Nagle and delayed-ACK stall on this Mac's loopback and could not (case "Nagle plus delayed ACK (not reproduced on macOS loopback)"): on loopback the ACK returns in microseconds, so there is nothing to wait for. The stall needs a real round trip.

How it shows up. Latency per request of almost exactly 40 ms (or 200 ms) more than the work takes, independent of payload size; streamed tokens that arrive in bursts rather than evenly. Check with getsockopt(IPPROTO_TCP, TCP_NODELAY) on both ends, or a packet capture (tcpdump, needs root) showing small segments waiting for ACKs. Fix: set TCP_NODELAY on both ends, and write each logical message in one call.
