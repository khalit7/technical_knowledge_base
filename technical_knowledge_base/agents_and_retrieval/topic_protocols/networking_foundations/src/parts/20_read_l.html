11. UDP: a thin wrapper, and everything else is your problem

UDP adds an 8-byte header to IP: source port, destination port, length, checksum ({{RFC 768|https://www.rfc-editor.org/rfc/rfc768}}). No connection, handshake, acknowledgement, retransmission, ordering, flow or congestion control; what it keeps is message boundaries: each sendto is one datagram, delivered whole or not at all (section 2's recording shows three sends arriving as three reads). Use it when a late packet is worthless (voice, video, game state), when a question and its answer each fit in one packet (DNS), or to build your own transport in user space (QUIC). The price includes congestion control: an application that blasts UDP at a fixed rate harms everyone on the link, which is why the {{UDP usage guidelines|https://www.rfc-editor.org/rfc/rfc8085}} ask UDP applications to control their rate.

No window to push back: a busy reader with a 64 KB buffer kept 53 of 5,000 datagrams

measured on loopback: 5,000 datagrams of 1,200 bytes sent in one burst at a socket that reads only after the burst. TCP's buffer grows and its window slows the sender; a UDP socket has a fixed buffer, and datagrams that arrive while it is full are discarded with only a counter to record it.

A QUIC implementation treats those drops as network loss and slows down, so an undersized UDP buffer silently caps HTTP/3 throughput. quic-go's documentation recommends raising the Linux limits to about 7.5 MB (net.core.rmem_max and wmem_max = 7,500,000, {{quic-go wiki|https://github.com/quic-go/quic-go/wiki/UDP-Buffer-Sizes}}); Linux's default limit was 212,992 bytes until 6.18 raised it to 4 MB (section 5). HTTP/3 is not niche: W3Techs counted it on 40.8 percent of websites on 5 October 2026 ({{W3Techs|https://w3techs.com/technologies/details/ce-http3}}).

12. QUIC: TCP's job, rebuilt on UDP

TCP plus TLS has three costs that could not be fixed inside TCP: a round trip for TCP and another for TLS 1.3 before the request leaves (section 3); one ordered byte stream under all of HTTP/2's streams, so one loss stalls them all (section 4); and ossification: firewalls, NATs and load balancers parse TCP's headers and drop what they do not recognise, and TCP lives in kernels that update slowly, so new TCP features take a decade to deploy, if ever. QUIC ({{RFC 9000|https://www.rfc-editor.org/rfc/rfc9000}}, May 2021, started at Google) moves the transport into a library on UDP and encrypts almost everything so middleboxes cannot ossify it again.

  • One handshake for transport and encryption. TLS 1.3 runs inside QUIC's packets ({{RFC 9001|https://www.rfc-editor.org/rfc/rfc9001}}), so the connection is ready after one round trip. A returning client can send its request in the first flight (0-RTT), but that data can be replayed by an attacker who records it ({{RFC 9001 s9.2|https://www.rfc-editor.org/rfc/rfc9001#section-9.2}}): use it only for requests safe to repeat.
  • Streams, each with its own order and flow control. A lost packet holds up only the streams whose data it carried.
  • Packet numbers are never reused. A retransmission goes in a new packet with a new number, so an ACK is never ambiguous about which copy arrived and RTT samples are clean ({{RFC 9002 s4.2|https://www.rfc-editor.org/rfc/rfc9002#section-4.2}}). ACK frames list ranges, like SACK without a size limit. A packet is lost when three later packets are acknowledged or after 9/8 of an RTT ({{RFC 9002 s6.1|https://www.rfc-editor.org/rfc/rfc9002#section-6.1}}); the congestion controller the RFC describes is close to TCP's NewReno ({{RFC 9002 s7|https://www.rfc-editor.org/rfc/rfc9002#section-7}}), and implementations may plug in others.
  • Connections are named by connection IDs, not addresses, so they survive a change of address or port (connection migration, {{RFC 9000 s9|https://www.rfc-editor.org/rfc/rfc9000#section-9}}); the peer checks the new path with PATH_CHALLENGE and PATH_RESPONSE before trusting it.
  • No amplification. Until it has validated the client's address, a server may send at most three times the bytes it received ({{RFC 9000 s8.1|https://www.rfc-editor.org/rfc/rfc9000#section-8.1}}), one reason the client pads its first datagram to 1,200 bytes: it buys the server room for its certificate.

The client's port changes mid-connection: TCP's 5-tuple matches no socket, QUIC's connection ID still matches

The QUIC run is real: aioquic 1.3.0 on loopback, a client and a small echo server, every UDP datagram logged with its size and source port, and both endpoints' qlog (QUIC's standard event log) recording the packet types and frames inside (src/meas/quic_migrate.py). Midway the client moves to a new UDP socket, which is what a NAT rebinding or a switch from Wi-Fi to mobile looks like to the server. The TCP side is drawn from the specification, not recorded.

Costs. QUIC runs in user space, encrypting and acknowledging every packet itself, so it spends more CPU per byte than kernel TCP with its offloads. Some networks block or throttle UDP 443, so every client keeps a TCP fallback: it learns a server speaks HTTP/3 from an alt-svc header or a DNS HTTPS record, then races or falls back. Inside a data centre on a clean network, kernel TCP is usually cheaper and simpler; between your own services gRPC and most inference servers still use HTTP/2 over TCP.

Visibility, versions, datagrams, debugging QUIC (depth)

QUIC hides its headers from network operators who used to read TCP's to debug ({{RFC 9312|https://www.rfc-editor.org/rfc/rfc9312}} discusses what remains visible). QUIC v2 ({{RFC 9369|https://www.rfc-editor.org/rfc/rfc9369}}, 2023) changes nothing functional; it exists so that middleboxes do not hard-code version 1. {{RFC 9221|https://www.rfc-editor.org/rfc/rfc9221}} adds unreliable datagrams inside a QUIC connection, for media and tunnels. Packet captures show only encrypted payloads; use the endpoints' qlog files (aioquic, quic-go, Chrome's chrome://net-export) or SSLKEYLOGFILE to decrypt a capture in Wireshark. "HTTP/3 fast at home, slow or falling back in the office": UDP 443 blocked.
