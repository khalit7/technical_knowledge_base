14. Why GPU clusters avoid TCP for the heavy traffic

The problem. An allreduce moves gigabytes between GPUs every training step, and every microsecond of latency and every CPU copy shows up as idle accelerators. Kernel TCP copies each byte from the NIC into kernel memory and then into the application, takes CPU interrupts, and backs off on any loss. At hundreds of gigabits per second per node, that is too slow and too expensive.

RDMA (remote direct memory access) lets one machine's network card read and write another machine's memory directly, with no kernel stack copying on either side; with GPUDirect RDMA, straight into GPU memory. It runs on three kinds of fabric in practice:

  • InfiniBand: a separate network built for RDMA, with its own adapters and switches ({{InfiniBand Trade Association|https://www.infinibandta.org/}}).
  • RoCEv2 (RDMA over Converged Ethernet): the same RDMA operations carried in UDP datagrams to port 4791 over ordinary routed Ethernet and IP (IANA registered 4791/udp to the InfiniBand Trade Association in 2014, {{IANA port registry|https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml?search=4791}}). This is where UDP meets your training job; the UDP header is only an envelope, and the reliability lives in the RDMA transport and the fabric's configuration.
  • AWS EFA: an OS-bypass interface whose transport is AWS's Scalable Reliable Datagram (SRD) protocol, with built-in congestion control, reached through the Libfabric API; ML applications use it through NCCL and NIXL ({{EFA documentation|https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html}}).

NCCL, the library behind PyTorch's GPU collectives, picks the fastest path it finds: NVLink and shared memory inside a server, the IB/RoCE transport across servers, and plain TCP sockets when nothing better exists (NCCL_IB_DISABLE=1 forces that fallback, {{NCCL environment variables|https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html}}). Even on an InfiniBand cluster, NCCL sets up its connections over TCP sockets first (the same page describes the "InfiniBand connection bootstrap sockets"), and PyTorch's rendezvous is a TCP store on MASTER_PORT (29500 unless set, {{torchrun source|https://github.com/pytorch/pytorch/blob/main/torch/distributed/run.py}}). So the interface NCCL chooses for its sockets decides whether a job starts at all. When NCCL does fall back to sockets, it uses several per peer precisely because one TCP connection cannot fill a fast NIC (sections 5 and 13): NCCL_SOCKET_NTHREADS helper threads with NCCL_NSOCKS_PERTHREAD sockets each, defaulting on AWS to 2 and 8, so 16 TCP connections for each network connection between two ranks, with the product capped at 64 (same page).

When a distributed job hangs at start-up or on its first big collective
  1. Wrong interface. NCCL picked docker0, a loopback or a management NIC. NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET prints the choice; set NCCL_SOCKET_IFNAME, and GLOO_SOCKET_IFNAME for Gloo, which is a separate variable ({{PyTorch distributed docs|https://docs.pytorch.org/docs/stable/distributed.html}}).
  2. Firewall or security group. Only MASTER_PORT has a fixed number; NCCL's environment-variable reference names no fixed port range for its own sockets, so rules that open one port between nodes are not enough. A silent hang in init_process_group is usually a dropped SYN (section 3).
  3. MTU mismatch between nodes: small messages pass, the first large one hangs (section 10).
  4. Accept queue or file descriptors at the rendezvous rank with thousands of ranks (section 8).
  5. Not the network at all. One straggler rank (a slow GPU, a data-loading stall) makes every other rank wait inside the collective, which looks exactly like a network hang. Compare per-rank progress and GPU utilisation before blaming the fabric.
