3. A TCP connection's life: open, talk, close, wait

Opening: the three-way handshake. TCP numbers every byte. Each side picks a random starting number (the initial sequence number; random so that an attacker off the path cannot guess it and inject data, {{RFC 9293 s3.4.1|https://www.rfc-editor.org/rfc/rfc9293#section-3.4.1}}), and the handshake exchanges them: the client sends SYN ("my bytes start at x"), the server answers SYN-ACK ("mine start at y; I expect your x+1"), the client sends ACK. Data may ride on the third segment, so a new connection costs exactly one round trip before the request leaves. measured: connect() to Cloudflare's speed-test host took 14.1 to 19.4 ms over twelve connections, against a ping round trip of 14.0 to 18.4 ms to Cloudflare's resolver: one round trip, as predicted.

The SYN also negotiates options that can never be added later ({{RFC 9293 s3.2|https://www.rfc-editor.org/rfc/rfc9293#section-3.2}}, {{RFC 7323|https://www.rfc-editor.org/rfc/rfc7323}}, {{RFC 2018|https://www.rfc-editor.org/rfc/rfc2018}}): the MSS (maximum segment size, the largest payload each side will accept in one segment), window scaling (section 5), SACK permitted (section 4) and timestamps. On every one of this page's connections to Cloudflare the kernel reported all four plus ECN (explicit congestion notification, section 6) as agreed (TCP_CONNECTION_INFO options = 15). A middlebox that strips an option from the SYN removes that feature for the life of the connection, silently.

Closing. Each direction closes separately: a side that has finished sending sends FIN, and the other acknowledges; the connection is gone when both have. That allows a half-close (a client sends its whole request, shuts its sending side, and keeps reading the answer). RST (reset) is the abrupt alternative: "this connection does not exist for me, stop". A kernel sends RST for a segment that matches no socket (a refused connection, or a NAT that forgot the mapping), and an application can force one by closing with unread data.

The states, on one connection. Step through the eleven states the two kernels pass through for the running request: ss -tan (Linux) or netstat -an -p tcp (macOS) prints these names. Two of them cause most production tickets: CLOSE_WAIT piling up means your program received the peer's FIN but never called close() (a leak in your code, not the network), and TIME_WAIT piling up means you open and close connections faster than you should.

TIME_WAIT, and why closing fast runs out of ports

The side that closes first does not forget the connection at once: it holds it in TIME_WAIT for twice the maximum segment lifetime (2 MSL), so that a delayed duplicate of an old segment cannot be mistaken for data in a new connection that reuses the same 5-tuple, and so that it can resend the final ACK if that was lost ({{RFC 9293 s3.6|https://www.rfc-editor.org/rfc/rfc9293#section-3.6}}). Linux fixes TIME_WAIT at 60 seconds (TCP_TIMEWAIT_LEN (60*HZ) in {{include/net/tcp.h|https://github.com/torvalds/linux/blob/master/include/net/tcp.h}}; it is not a sysctl). This Mac uses an MSL of 15 s, so 30 s (measured net.inet.tcp.msl: 15000); its netstat did not list a single TIME_WAIT entry after twenty closed loopback connections, so the state itself could not be seen here and the numbers below are Linux's.

A client that opens a fresh connection per request (an HTTP client without a connection pool, a script calling an embedding API in a tight loop, a health checker) hits that wall and gets EADDRNOTAVAIL ("Cannot assign requested address"). The fix is reuse: a connection pool and keep-alive, which also saves the handshake round trip and, over TLS, a second one. The kernel knobs are a last resort: tcp_tw_reuse lets outgoing connections reuse a TIME_WAIT port when timestamps prove it is safe (default 2, loopback only, {{ip-sysctl|https://docs.kernel.org/networking/ip-sysctl.html}}), and tcp_tw_recycle, still recommended by old blog posts, was removed in Linux 4.12 because it broke clients behind NAT ({{commit 4396e46187ca|https://github.com/torvalds/linux/commit/4396e46187ca5070219b81773c4e65088dac50cc}}). Which side holds TIME_WAIT is whichever closed first, so a server that closes idle client connections collects them too.

When the handshake gets no answer

If the SYN is dropped (a firewall, a security group, a host that is down), the client retries it with exponential backoff. Linux's default of 6 retries gives up after about 131 seconds ({{tcp_syn_retries|https://docs.kernel.org/networking/ip-sysctl.html}}). So a connect with no timeout of its own can hang for two minutes, which is why every client needs an explicit connect timeout, separate from (and much shorter than) its read timeout. The Failure lab's "Connect timeout" case records the error text of five clients against an address that never answers, and "Connection refused" the contrast: an RST comes back in under a millisecond.
