8. Who is calling: keys, tokens, and delegation

The problem. TLS proved the server's identity to the client. The API now needs the reverse: who is this caller, and may they do this? Two different questions, often confused: authentication (who are you?) and authorization (what may you do?). A 401 status means the first failed, a 403 the second.

API keys: the simplest answer

The running request carries x-api-key: sk-wirelab-not-a-real-key (a fake). An API key is a long random secret: whoever holds it is the account. It is a bearer credential, like cash: the server checks the value, not who presents it. That makes keys simple and right for one backend calling a provider, and dangerous everywhere else: no expiry by default, no user behind it, no consent, and a leaked key works for anyone until revoked. Rules: one key per service and environment, stored in a secrets manager, never in a browser, a mobile app, a notebook or a git repository, rotated, and prefixed so scanners can find leaks.

OAuth 2.1: letting an app act for a user without their password

When a third-party app (or an agent) needs to act for a user, giving it the user's password or a master key is wrong. OAuth instead has an authorization server issue the app a short-lived, limited access token for a specific resource server, after the user approves. OAuth 2.1 consolidates OAuth 2.0 and a decade of security lessons; it is still an IETF draft (revision 16, 3 September 2026, {{datatracker|https://datatracker.ietf.org/doc/draft-ietf-oauth-v2-1/}}) but is what new systems implement. Three flows remain:

  • Authorization code with PKCE, for anything a user logs into (web apps, mobile apps, CLIs). The app sends the user's browser to the authorization server; the user logs in and approves; the browser comes back with a one-time code; the app trades the code for tokens. PKCE (proof key for code exchange) makes a stolen code useless: the app first sends the hash of a random secret, and must show the secret itself when it redeems the code. The RFC's own example, computed by this page's script: verifier dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk hashes to challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM, the value in {{RFC 7636, appendix B|https://www.rfc-editor.org/rfc/rfc7636#appendix-B}} (measured).
  • Client credentials, for machine to machine: a service authenticates as itself and gets a token for itself, no user involved.
  • Device authorization ({{RFC 8628|https://www.rfc-editor.org/rfc/rfc8628}}), for machines without a browser: the box shows a short code, you approve it on your phone, the box polls until the token arrives.

Two parameters make tokens safe to hand around. Scopes limit what a token may do (messages:write, not "everything"). Audience limits where it is valid: a token minted for the billing service must be refused by the messages service ({{RFC 8707|https://www.rfc-editor.org/rfc/rfc8707}} lets the client ask for a token bound to one resource). OpenID Connect (OIDC) adds identity on top of OAuth: an ID token saying who logged in, which is what "Sign in with Google" returns. ID tokens are for the app to learn who the user is, never to call APIs with.

JWTs: tokens a server can check without asking anyone

Access tokens are often JSON Web Tokens ({{RFC 7519|https://www.rfc-editor.org/rfc/rfc7519}}): three base64url parts, header.payload.signature. Anyone can decode the first two; the signature lets a server verify, offline, that the issuer signed exactly these claims. What the output shows: the claims (iss issuer, sub user, aud audience, scope, iat and exp times) are readable by anyone, so never put secrets in them. The same token presented to another service was rejected because its audience did not match, which only happens if that service checks aud. A forged token whose header says "alg": "none" was rejected because the verifier pinned the algorithm it accepts, instead of trusting the token's own header, the classic JWT mistake ({{RFC 8725, section 2.1|https://www.rfc-editor.org/rfc/rfc8725#section-2.1}}). The cost of checking offline: a JWT cannot be revoked before it expires, so lifetimes are kept to minutes and paired with refresh tokens.


Service to service, and the cloud


Inside one organisation, two stronger options avoid long-lived secrets. mTLS (section 4) gives every workload a short-lived certificate as its identity. Cloud IAM signs each request instead of sending a bearer token: AWS Signature Version 4 computes an HMAC over the request with temporary credentials from the machine's role ({{AWS docs|https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html}}), so nothing reusable crosses the wire. A CI job or another cloud can obtain those temporary credentials by presenting an OIDC token from its own platform, with no stored secret at all.


The agent-era twist


An agent is a program that holds credentials and decides what to do with them based on text it reads, and some of that text was written by strangers (section 9). Three rules follow. Least privilege: give an agent read-only scopes unless it must write, and separate tokens for destructive actions. Audience binding: a token issued for one tool server must not work anywhere else. No token passthrough: a server that receives a token must not forward it to another API; it obtains its own (the MCP specification makes this a MUST NOT, section 9). For actions that cannot be undone, a human approval outside the conversation, which text arriving through a tool cannot fake.
