4. Security: TLS 1.3, certificates, and the chain of trust

The problem. Between the chat app and the API sit a Wi-Fi router, an internet provider, perhaps a corporate proxy and several cloud hops. Any of them can read the bytes, change them, or pretend to be the server. The request carries an API key and a user's words. TLS (Transport Layer Security; version 1.3 is now specified by {{RFC 9846|https://www.rfc-editor.org/rfc/rfc9846}}, July 2026, which replaced RFC 8446) gives three guarantees on top of TCP: confidentiality (nobody in between can read), integrity (any changed byte is detected) and authentication (the client knows it reached the real server). It is the "S" in HTTPS.

How the handshake works, in intuition first

  1. Agree on a secret in public. Each side picks a random private number and sends a public "share" derived from it. Combining your own private number with the other side's share gives both sides the same secret, while someone who saw both shares cannot compute it: that is Diffie-Hellman key exchange. Fresh private numbers per connection mean that stealing the server's long-term key later does not unlock recorded traffic (forward secrecy, mandatory in TLS 1.3).
  2. Prove who you are. A shared secret is useless if you share it with an impostor. The server sends its certificate, a document binding its name to a public key and signed by a certificate authority, and then signs the whole handshake so far with the matching private key ({{RFC 9846, section 4.5.2|https://www.rfc-editor.org/rfc/rfc9846#section-4.5.2}}). Only the real server holds that key.
  3. Check nobody meddled. Both sides send a Finished message, a keyed checksum of everything exchanged ({{section 4.5.3|https://www.rfc-editor.org/rfc/rfc9846#section-4.5.3}}). Then application data flows, encrypted and authenticated record by record.

All of this takes one round trip after TCP's (TLS 1.2 needed two; on an emulated 50 ms path the {{On the wire|#t-wire}} tab measured 53 ms for a TLS 1.3 handshake against 107 ms for TLS 1.2, and TLS 1.2 is now in feature freeze, {{RFC 9851|https://www.rfc-editor.org/rfc/rfc9851}}): the client sends its key shares in its first message, guessing which method the server will accept ({{RFC 9846, Figure 1 in section 2|https://www.rfc-editor.org/rfc/rfc9846#section-2}}). What the recording teaches. Three things an eavesdropper still sees under TLS: the server name (SNI) and the protocol wanted (ALPN) in the ClientHello, the sizes of all records, and their timing. In the streamed answer that means one record per token, 146 to 148 bytes each, about 51 ms apart: the rhythm of generation is visible even though the text is not. Researchers turned exactly this into an attack on AI assistants that streamed one token per packet, reconstructing 29% of responses from token lengths alone ({{Weiss et al., 2024|https://arxiv.org/abs/2403.09751}}); the defence is padding records or grouping tokens. The server name stops leaking with Encrypted Client Hello ({{RFC 9849|https://www.rfc-editor.org/rfc/rfc9849}}, March 2026), which encrypts the inner ClientHello under a key the server publishes in DNS.

Post-quantum key exchange is already on by default

The client in the recording offered two key shares: X25519MLKEM768, 1,216 bytes, and plain x25519, 32 bytes, and the server chose the first, answering with 1,120 bytes. That is a hybrid share: a classical elliptic-curve exchange and ML-KEM, a lattice-based method believed to resist quantum computers, run together and both mixed into the secret, so the connection is safe if either holds. The sizes are exactly those of {{RFC 10024, sections 4.1 and 4.2|https://www.rfc-editor.org/rfc/rfc10024#section-4.1}} (August 2026). The reason to deploy it before quantum computers exist is "record now, decrypt later": traffic captured today could be decrypted once one does. The cost is bytes, not CPU: this ClientHello message is 1,482 bytes, against 314 bytes for the ClientHello of curl's TLS library (LibreSSL 3.3.6) on the same machine, which does not offer it (measured, curl -v in section 1). Cloudflare measured post-quantum key agreement on over 60% of the requests it received in February 2026, up from under 3% at the start of 2024, while only about 10% of origin servers supported it ({{Cloudflare, 27 February 2026|https://blog.cloudflare.com/radar-origin-pq-key-transparency-aspa/}}): clients upgraded, servers lag. Upgrading a server's TLS library (OpenSSL 3.5 or later, as here) is usually all it takes.

Certificates and the chain of trust

A certificate is signed by a certificate authority (CA); that CA's own certificate may be signed by another, up to a root certificate that ships inside your operating system or browser (the trust store). The server sends its own certificate and the intermediates, never the root; the client builds the chain up to a root it already trusts and checks each signature, the dates, and that the name it dialled appears in the certificate's subject alternative names. The recording's chain is two links: CN=api.llm.test, issued by the throwaway Wire Lab Root CA that the client was told to trust (the depth=1 and depth=0 lines of the openssl output in section 1). Public certificates are getting shorter-lived on a fixed schedule: at most 200 days since 15 March 2026, 100 days from 15 March 2027, and 47 days from 15 March 2029, when proof of domain control may be reused for only 10 days ({{CA/Browser Forum ballot SC-081v3|https://cabforum.org/2025/04/11/ballot-sc081v3-introduce-schedule-of-reducing-validity-and-data-reuse-periods/}}, summary by {{DigiCert|https://www.digicert.com/blog/tls-certificate-lifetimes-will-officially-reduce-to-47-days}}). Manual renewal stops being possible; automated issuance (ACME, {{RFC 8555|https://www.rfc-editor.org/rfc/rfc8555}}) becomes mandatory in practice.

mTLS (mutual TLS) runs the same proof in the other direction: the server asks for a certificate and the client signs the handshake too. It is the strongest way for one service to prove its identity to another, and the thing service meshes (Istio, Linkerd) and SPIFFE automate, because the hard part is issuing and rotating short-lived certificates for every workload. Section 8 places it among the other ways to prove who is calling.

Costs, and when not to use it

One extra round trip per new connection, a few kilobytes of handshake, and certificate operations; the symmetric encryption of the data itself is nearly free on modern CPUs. That is why connection reuse matters: a client that opens a fresh connection per request pays TCP and TLS round trips every time. TLS 1.3 can send data in the very first message when resuming an earlier session (0-RTT), but that early data can be replayed by an attacker ({{RFC 9846, section 8|https://www.rfc-editor.org/rfc/rfc9846#section-8}}), so it is only safe for requests that may run twice; a generation request or an agent's tool call is not one of them. There is no good reason to skip TLS on any network you do not fully control, including inside a cloud network; GPU-to-GPU traffic over NCCL is the usual exception, isolated at the network level instead.

Never "fix" a certificate error by turning verification off

verify=False, curl -k and InsecureSkipVerify keep the encryption and drop the authentication, which means encrypting to whoever answers, attacker included. The correct fixes are serving the full chain on the server, or adding the right CA to the client's trust store (for Python, the truststore package makes it use the operating system's store).

SSH, briefly. SSH, the protocol you use to reach a GPU box, solves the same problem with the same ideas: a Diffie-Hellman exchange (hybrid post-quantum mlkem768x25519-sha256 by default since OpenSSH 10.0, April 2025, standardised as {{RFC 10042|https://www.rfc-editor.org/rfc/rfc10042}} in August 2026, and a warning for non-post-quantum exchanges since 10.1, October 2025: {{OpenSSH release notes|https://www.openssh.org/releasenotes.html}}), a server host key as the server's identity, and user keys for the client. The difference is trust: instead of a CA, SSH trusts the host key it saw the first time (the known_hosts prompt), which is why "host key changed" warnings must never be clicked through.
