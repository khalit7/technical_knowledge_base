1. The map: layers, names, and how to see each one

Why layers exist. Getting a JSON body from your laptop to a GPU server involves at least five separate problems: moving bits over one physical link, finding a path across many networks, delivering bytes to the right program reliably, keeping them private, and agreeing on what the bytes mean. Each protocol solves one of them and assumes the others are solved. The result is a stack: on the way out, every layer wraps the message it was handed in its own small header (a few bytes of addressing and control information placed in front of the payload, the data being carried) and passes it down; on arrival, every layer strips its own header and passes the rest up. No layer reads the others' headers. That separation is why your Python code never thinks about Wi-Fi, and also why a problem in one layer often surfaces as a confusing symptom in another.

The four-layer internet model is the one the protocols were built on ({{RFC 1122, section 1.1.3|https://www.rfc-editor.org/rfc/rfc1122#section-1.1.3}}). Interviews and load-balancer docs use the numbers of the older seven-layer OSI model instead: "L4" means the transport layer (TCP, UDP) and "L7" the application layer (HTTP), so an "L4 load balancer" forwards connections without reading HTTP and an "L7" one reads every request. TLS has no clean place in either model; it sits between transport and application.

Names you will meet

Socket: the operating system's handle for one end of a connection, identified by IP address plus port. Your code reads and writes a socket; the kernel does the rest.
Connection: two sockets that have agreed to talk (TCP). Identified by five numbers, the 5-tuple: protocol, source IP, source port, destination IP, destination port.
Round trip (RTT): the time for a message to reach the other side and a reply to come back. About 0.1 ms on one machine, 1 ms in a data centre, 80 to 150 ms across an ocean. Light in fibre covers about 200 km per millisecond, so distance sets a floor no protocol can beat ({{High Performance Browser Networking, chapter 1|https://hpbn.co/primer-on-latency-and-bandwidth/}}).
Handshake: messages exchanged before useful data can flow, to agree on parameters. Each costs at least one round trip.
Latency and bandwidth: how long the first byte takes, against how many bytes per second flow once going. A satellite link has high bandwidth and terrible latency; most LLM API calls are latency-bound.
Stream: an ordered sequence of bytes or messages inside a connection. HTTP/2 and QUIC carry many streams in one connection.

The same request, wrapped and unwrapped

Below, the running request travels down the stack on the laptop, crosses one Ethernet link, and climbs back up on the server. Every bar is drawn to scale in bytes. Switch to one streamed token to see the same layers wrap the answer's first token, the three letters The.

Sizes: JSON, HTTP and TLS bytes measured on this page's run (the TLS record of the request is 299 bytes on the wire against 277 bytes of HTTP inside it: a 5-byte record header, 1 byte of inner content type and a 16-byte authentication tag, {{RFC 9846, section 5.2|https://www.rfc-editor.org/rfc/rfc9846#section-5.2}}). TCP, IP and Ethernet sizes come from their specifications, because capturing packets needs administrator rights this build did not have: a TCP header is 20 bytes plus options ({{RFC 9293, section 3.1|https://www.rfc-editor.org/rfc/rfc9293#section-3.1}}), here 12 bytes of the timestamps option that Linux and macOS send by default ({{RFC 7323, section 3|https://www.rfc-editor.org/rfc/rfc7323#section-3}}); an IPv4 header is 20 bytes ({{RFC 791, section 3.1|https://www.rfc-editor.org/rfc/rfc791#section-3.1}}; IPv6 is 40); Ethernet adds a 14-byte header and a 4-byte checksum (IEEE 802.3).

What the picture teaches. For the request, wrapping is two thirds of the bytes on the cable (252 of 369, mostly HTTP headers); for a streamed token, 213 of the 216 bytes are wrapping. Token streaming is cheap in bandwidth anyway, because a few hundred bytes per token is nothing for any link; what it costs is a connection held open for the whole generation (section 6). The other lesson is the order of unwrapping: a problem is visible only to the layer that owns it. A bad certificate is invisible to TCP, and a TCP stall is invisible to your JSON parser, which just sees a read that never returns.

See each layer yourself: the toolbox

Each tool below shows one layer, and all of them were run against the local server for this page. Learn which question each answers; that is most of network debugging.

Is the port reachable? (TCP)

nc -vz host port opens a TCP connection and closes it. Success means routing, firewalls and a listening program are all fine.



Is TLS healthy? (security)
openssl s_client -connect host:443 -servername host shows the certificate chain, the TLS version, the cipher and whether verification passed.


Where did the time go? (all layers)
curl -w prints a timer per phase: name lookup, TCP connect, TLS done, first byte, total, in seconds since the start.


Which connections are open? (sockets)
lsof -nP -iTCP on macOS, ss -tnp on Linux. Here one streaming request is in flight: the server's listening socket and the two ends of one connection.




curl -v narrates every layer in order, and is the first thing to run on any HTTP problem. Read it top to bottom: name resolution, TCP connect, the TLS handshake message by message, the certificate check, ALPN choosing HTTP/1.1, then the request (> lines) and the response headers (< lines).


The recorded curl -v output for the running request (HTTP/1.1)


Three more belong in the toolbox and appear in their sections: dig for names (section 2), traceroute or mtr for the path of routers and where packets are lost (section 3), and tcpdump or Wireshark for the packets themselves, which need administrator rights. On Linux, ss -ti adds each connection's round-trip time, window and retransmission count, the single most useful view of a slow transfer.
