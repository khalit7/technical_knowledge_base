1. The map: layers, and how to see each one

Each protocol solves one problem and assumes the others are solved. On the way out every layer wraps the message it was handed in its own header and passes it down; on arrival every layer strips its own header and passes the rest up.

Layer (internet model)JobIn our requestUnit and address
ApplicationWhat the bytes meanHTTP carrying JSON and Server-Sent Eventsa message; named by a URL
Security (between the two)Privacy, integrity, identityTLS 1.3a TLS record
TransportRight program, complete, in order, not too fastTCP (or QUIC over UDP for HTTP/3)a segment (TCP) or datagram (UDP); a port number picks the program
InternetGet across many networks to the right machineIPv4 or IPv6a packet; an IP address picks the machine
LinkMove bits over one cable or radio hopEthernet, Wi-Fia frame; a MAC address picks the next device

The four-layer internet model is the one the protocols were built on ({{RFC 1122, section 1.1.3|https://www.rfc-editor.org/rfc/rfc1122#section-1.1.3}}). Interviews and load-balancer docs use the numbers of the older seven-layer OSI model instead: "L4" means the transport layer (TCP, UDP) and "L7" the application layer (HTTP), so an "L4 load balancer" forwards connections without reading HTTP and an "L7" one reads every request. TLS has no clean place in either model; it sits between transport and application.

Wrapping is two thirds of the request's bytes, and nearly all of a streamed token's

For the request, wrapping is 252 of the 369 bytes on the cable (mostly HTTP headers); for a streamed token, 213 of 216. A few hundred bytes per token is nothing for any link; what streaming costs is a connection held open for the whole generation.

Where each size comes from

JSON, HTTP and TLS bytes measured on this page's run (the TLS record of the request is 299 bytes on the wire against 277 bytes of HTTP inside it: a 5-byte record header, 1 byte of inner content type and a 16-byte authentication tag, {{RFC 9846, section 5.2|https://www.rfc-editor.org/rfc/rfc9846#section-5.2}}). TCP, IP and Ethernet sizes come from their specifications, because capturing packets needs administrator rights this build did not have: a TCP header is 20 bytes plus options ({{RFC 9293, section 3.1|https://www.rfc-editor.org/rfc/rfc9293#section-3.1}}), here 12 bytes of the timestamps option that Linux and macOS send by default ({{RFC 7323, section 3|https://www.rfc-editor.org/rfc/rfc7323#section-3}}); an IPv4 header is 20 bytes ({{RFC 791, section 3.1|https://www.rfc-editor.org/rfc/rfc791#section-3.1}}; IPv6 is 40); Ethernet adds a 14-byte header and a 4-byte checksum (IEEE 802.3).
