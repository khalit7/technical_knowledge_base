The one idea that makes debugging fast
A request crosses layers in order: the name is looked up (DNS), a connection is opened (TCP), it is secured (TLS), the request is sent (HTTP), and only then do authentication and the application run. An error belongs to the first layer that failed, and its wording tells you which: "could not resolve" is DNS, "connection refused" or "timed out connecting" is TCP, "certificate" is TLS, a status code like 502 or 429 means TCP and TLS worked and an HTTP server (often a proxy, not your app) answered. Check the lowest failing layer first. The {{Reading tab|#t-read}} explains each layer.

How these were recorded, and what is simulated

Every command was run through sh -c exactly as printed, and its output (standard output and standard error together) is shown unedited except that the scratch directory reads $WORK. The variables: $PY is the lab's Python 3.13, $CL its client scripts, $CA the lab root CA from the On the wire tab, $OPENSSL OpenSSL 3.6, $PKI the lab's certificates. Python clients print the exception exactly as the last line of its traceback reads; Node prints the error and its cause.

All servers ran on 127.0.0.1: the On the wire tab's LLM stand-in (hypercorn), a real nginx 1.31.6 as the proxy and TLS terminator, small socket servers that misbehave in one way each, local DNS servers (dnspython), gRPC backends (grpcio), a JWT-checking gateway and OAuth endpoint (PyJWT), and MCP servers (the official Python SDK). A few lookups touched the public network, read-only: a reserved TEST-NET address (connect timeout), an .invalid name (NXDOMAIN), api.anthropic.com's TTL (twice), and cloudflare-dns.com and 1.1.1.1 (the DNS interception case). The machine's local network addresses and its filtering software's name are redacted. Where part of a setup is simulated, the card says so in a red-edged box.
