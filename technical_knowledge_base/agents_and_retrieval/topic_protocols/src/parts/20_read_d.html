3. Names: DNS turns a name into an address

The Domain Name System (DNS) is a worldwide, distributed, cached lookup from names to records ({{RFC 1034|https://www.rfc-editor.org/rfc/rfc1034}}, 1987). Your process asks a stub resolver (getaddrinfo in the C library), the stub asks one recursive resolver, and on a cache miss the resolver walks down from a root server through the .com servers to the zone's own authoritative servers. Each answer carries a TTL (time to live), the seconds a cache may keep it.

The one thing that crosses every other layer: caching is DNS's whole failure surface. There is no way to push a change or invalidate a cache; "propagation" is every cache's TTL running out. A "does not exist" answer is cached too, so a record created a minute after a failed lookup can stay invisible for as long as the zone says (30 minutes for anthropic.com, measured). DNS failures surface as connection errors in other layers: a 5-second stall on every new connection (a lost query and the C library's default retry timer), a pod flooding the cluster DNS (Kubernetes' ndots:5), a certificate error from a filter that answers DNS itself (section 5).

Where DNS meets agents. In DNS rebinding a name first resolves to the attacker's server, then to an internal address such as 127.0.0.1 or the cloud metadata address 169.254.169.254, so a check made on the first answer is bypassed by the second. Any service run on 0.0.0.0 without authentication (a notebook, a model server) is reachable this way from a browser on the same network, and the MCP specification names it among the attacks a client must guard against when it fetches URLs a server gave it.

4. Transport: IP, TCP, UDP and QUIC

IP gives every machine an address (32 bits for IPv4, 128 for IPv6) and forwards a packet one hop at a time, best effort: packets may be lost, duplicated, delayed or reordered, and IP will not tell you ({{RFC 791, section 1.2|https://www.rfc-editor.org/rfc/rfc791#section-1.2}}). A port picks the program; protocol, source and destination address and port, the 5-tuple, name one connection. Every guarantee is added above IP, and the three transports add different ones:

Two transport facts other layers keep running into. Head-of-line blocking is the thread through the HTTP versions (section 6). And a connection can die without either end knowing: a NAT or load balancer forgets a connection that was idle too long (350 seconds on an AWS NAT gateway), and TCP alone never notices a silent peer, so long-lived connections (streams, SSH sessions, connection pools, a training job's rendezvous) need keepalives or heartbeats shorter than the shortest idle timeout on the path.

Where the GPUs talk. Training traffic avoids this path for its data: GPU clusters use RDMA (the network card writes straight into the other machine's memory, no operating system in the path) over InfiniBand, RoCE or AWS's EFA, and NCCL picks NVLink, then RDMA, then plain TCP sockets. NCCL still bootstraps over ordinary TCP sockets, which is why a wrong network interface can hang a job at start-up even on an InfiniBand cluster.
