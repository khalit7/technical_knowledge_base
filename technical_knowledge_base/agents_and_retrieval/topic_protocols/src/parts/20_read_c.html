2. Naming: DNS turns a name into an address

The problem. Packets are delivered to IP addresses, but code and humans use names, and the machine behind a name changes: load balancers are replaced, regions fail over, a CDN answers from the nearest city. The Domain Name System (DNS) is a worldwide, distributed, cached lookup from names to records, designed in 1987 ({{RFC 1034|https://www.rfc-editor.org/rfc/rfc1034}}, {{RFC 1035|https://www.rfc-editor.org/rfc/rfc1035}}) and still the first step of almost every connection.

The running request uses the name api.llm.test, which deliberately exists in no DNS: .test is reserved for testing ({{RFC 6761, section 6.2|https://www.rfc-editor.org/rfc/rfc6761#section-6.2}}), so the local client pins it to 127.0.0.1. DNS is shown here against the real name of a public LLM API, api.anthropic.com, with a dozen read-only queries.

How a name is resolved

Three kinds of program are involved. Your process calls the stub resolver (getaddrinfo in the C library, which Python's socket, curl and every HTTP client call). The stub asks one recursive resolver (your router, your company's, the cloud provider's, or a public one such as 1.1.1.1), which does the work and keeps a cache. On a cache miss the resolver walks down the tree of authoritative servers, each of which knows one zone and answers with either the record or a referral to the servers one level down ({{RFC 1034, section 5.3.3|https://www.rfc-editor.org/rfc/rfc1034#section-5.3.3}}):

  1. A root server (13 named identities, a to m.root-servers.net, each many machines behind one address): "I do not know api.anthropic.com; ask the .com servers."
  2. A .com server (13 named a to m.gtld-servers.net): "Ask anthropic.com's servers: isla.ns.cloudflare.com and randy.ns.cloudflare.com."
  3. anthropic.com's authoritative server: "api.anthropic.com is 160.79.104.10; you may cache this for N seconds."

The server names above are the real NS (name server) records, read through this machine's resolver on 5 October 2026 (measured; full output below). Each answer carries a TTL (time to live), the number of seconds a cache may keep it. The .com delegation had 52,811 seconds left, anthropic.com's 898: high levels change rarely and are cached for hours, the final answer for minutes.

What the recorded run shows

The answer and its TTL, twice, 5 s apart

The first query said 115 seconds left, the second 79: 36 seconds gone in 5. The resolver address hides a pool of caches that were filled at different times, so a TTL is a per-cache countdown, not a global clock.

Resolver against operating-system cache

The first query to the resolver took 440 ms, later ones 104 to 122 ms, while getaddrinfo returned in 3.0 ms: macOS keeps its own cache. The {{On the wire|#t-wire}} tab measured the same gap inside curl: 212 to 451 ms for an uncached name, 2.4 ms cached. Python itself caches nothing, and a slim Linux container usually has no local cache, so every new connection pays the round trip.

A name that does not exist

The answer is NXDOMAIN plus the zone's SOA record. A resolver caches the "no" for the smaller of the SOA's own TTL and its last field ({{RFC 2308, section 5|https://www.rfc-editor.org/rfc/rfc2308#section-5}}): both are 1,800 seconds for anthropic.com (the recorded SOA shows 1,484 because the resolver had already held it for a while). Create the missing record a minute later and clients still get "does not exist" for up to 30 minutes.

This run also caught an intercepting DNS filter
The script asked a.root-servers.net directly, without requesting recursion. Root servers are authoritative servers for the root zone only ({{RFC 7720, section 2|https://www.rfc-editor.org/rfc/rfc7720#section-2}}): a real one answers with a referral to the .com servers and does not offer recursion, so its reply has no "recursion available" (RA) flag. The reply came back in 104 ms with RA set and the final address of api.anthropic.com: a DNS filter on the laptop this page was built on answers every DNS packet itself. Corporate device management, VPNs and security software do this. It explains odd results from dig +trace (it shows no delegation), and it is the reason this page shows NS lookups instead of a trace. The check takes one line: dig @198.41.0.4 example.com +norecurse should return a referral, not an answer.


What it costs, and when caching bites


A cache miss costs one round trip to the resolver, plus the resolver's own walk when it misses too. Caching is what makes DNS cheap, and it is also its whole failure surface: there is no way to push a change or invalidate a cache. "DNS propagation" is a myth; nothing propagates, and you are waiting for every cache's TTL to run out. The working rule for a planned change: lower the TTL at least one old-TTL ahead of time, make the change, then raise it again.

Dated: the DNS root key changes on 11 October 2026
Resolvers that validate DNSSEC signatures (a chain of signatures from the root down, proving answers were not forged) trust one root key. The root zone moves to a new key, KSK-2024 with key tag 38696, on 11 October 2026 ({{ICANN|https://www.icann.org/resources/pages/ksk-rollover-en}}). A validating resolver whose trust anchor was baked in before the new key existed and never updated will fail every lookup after that date. Most laptops and cloud resolvers update automatically; old container images and appliances running their own validating resolver are the ones to check.


Security in one paragraph. Classic DNS is unauthenticated and unencrypted: anyone on the path can read which names you look up and, in principle, answer first. DNSSEC adds signatures (authenticity, not privacy); DNS over TLS, HTTPS or QUIC ({{RFC 7858|https://www.rfc-editor.org/rfc/rfc7858}}, {{RFC 8484|https://www.rfc-editor.org/rfc/rfc8484}}, {{RFC 9250|https://www.rfc-editor.org/rfc/rfc9250}}) adds privacy on the hop to the resolver. The attack that matters most for ML engineers is DNS rebinding: a name first resolves to the attacker's server, then to an internal address such as 127.0.0.1 or the cloud metadata address 169.254.169.254, so a check made on the first answer is bypassed by the second. The MCP specification names it among the attacks a client must guard against when it fetches URLs a server gave it ({{MCP security best practices|https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices}}). Any service you run on 0.0.0.0 without authentication (a notebook, a Ray dashboard, a model server) is reachable this way from a browser on the same network.
