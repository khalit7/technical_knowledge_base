6. Streaming and events: tokens as they are generated

The problem. A model generates tokens one at a time over seconds or minutes. Waiting for the whole answer makes the app feel dead, and a long silence invites every proxy on the path to cut the connection. The answer must flow back as it is produced, over plain HTTP so that it passes through every proxy, load balancer and CDN.

Server-Sent Events: one response that does not end

Server-Sent Events (SSE) are defined in the HTML standard ({{WHATWG HTML, section 9.2|https://html.spec.whatwg.org/multipage/server-sent-events.html}}). The server answers with content-type: text/event-stream and keeps the response open, writing UTF-8 text events. Each event is a few field: value lines (event names the type, data carries the payload, id numbers it, retry suggests a reconnect delay) and ends with a blank line, which is what tells the parser to deliver it; a line starting with a colon is a comment and is ignored. That is the whole format. Here is the running request's complete answer as it arrived over plain HTTP/1.1, every byte, with each CR LF shown as ↵:

The hex numbers 81, 76, 77 before each event are HTTP/1.1 chunk sizes (0x76 = 118 bytes), not part of SSE; a final 0 chunk ends the body ({{RFC 9112, section 7.1|https://www.rfc-editor.org/rfc/rfc9112#section-7.1}}). Over HTTP/2 or HTTP/3 the same events travel in DATA frames instead. The events follow Anthropic's Messages API format, trimmed: the real API also sends content_block_start, content_block_stop, message_delta and ping events ({{streaming docs|https://platform.claude.com/docs/en/build-with-claude/streaming}}).


The client's job is to split the byte stream on blank lines, parse each event, and append each text_delta to the screen. The catch is that network reads do not respect event boundaries: one read may hold half an event, or three; a multi-byte UTF-8 character can be split across two reads. A correct parser buffers until it sees a blank line. The {{JavaScript and TypeScript page|n:3cd5c17b0d0d81dbac7be3b8686be023}} (Part 1) builds such a parser and feeds it real reads that split events mid-line.

SSE has a built-in resume mechanism: a browser's EventSource reconnects on its own and sends the last id it saw as a Last-Event-ID header, so a server that numbers events can continue where it left off. LLM APIs mostly do not offer this for generation, because the server would have to keep every in-flight answer; a dropped stream is a failed request.

WebSockets in one paragraph. A WebSocket starts as an HTTP/1.1 GET with Upgrade: websocket and a random Sec-WebSocket-Key; the server answers 101 Switching Protocols with Sec-WebSocket-Accept, the base64 SHA-1 of the key joined to a fixed GUID, which proves it understood the upgrade (the computation is not security). For the RFC's example key dGhlIHNhbXBsZSBub25jZQ== this page's script computes s3pPLMBiTxaQ9kYGzzhZRbK+xOo=, exactly the value in {{RFC 6455, section 1.3|https://www.rfc-editor.org/rfc/rfc6455#section-1.3}} (measured). After that the TCP connection carries small framed messages in both directions, with 2 to 14 bytes of framing each. One security trap: browsers do not apply the same-origin policy to WebSockets, so a server must check the Origin header of the upgrade request itself.


Webhooks in one paragraph. Inverted control: you give a provider a URL and it POSTs to you when something happens. Because anyone can POST to a public URL, providers sign each delivery, typically an HMAC-SHA256 over a timestamp and the raw body with a secret you share; verify it over the raw bytes (parsing and re-serialising the JSON changes them), and reject old timestamps to stop replays. Providers retry until you answer 2xx, so the same event can arrive more than once and out of order: store event IDs and make processing idempotent. Answer fast and do the work from a queue ({{Queues, streams and async work|n:3ef5c17b0d0d81aebf91df927f215b6e}}).
