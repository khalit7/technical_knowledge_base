6. HTTP: one meaning, three wire formats

HTTP is the shared vocabulary for requests and answers, and the key to its versions is that the meaning and the wire format are specified separately. Methods, status codes and headers are defined once in {{RFC 9110 (HTTP Semantics)|https://www.rfc-editor.org/rfc/rfc9110}} and mean the same in every version; HTTP/1.1, HTTP/2 and HTTP/3 only change how those messages are cut into bytes. Your code almost never notices the version; your latency and your proxies do. Each version exists to remove a form of head-of-line blocking:

HTTP/1.1 (1997, {{RFC 9112|https://www.rfc-editor.org/rfc/rfc9112}})HTTP/2 (2015, {{RFC 9113|https://www.rfc-editor.org/rfc/rfc9113}})HTTP/3 (2022, {{RFC 9114|https://www.rfc-editor.org/rfc/rfc9114}})
FormatText linesBinary frames, compressed headers (HPACK)Binary frames, compressed headers (QPACK)
Requests per connection at onceOne; clients open several connections (browsers about 6 per host)Many, as independent streamsMany, as independent QUIC streams
Head-of-line blockingA slow response blocks the connectionFixed between requests, but one lost TCP packet still stalls every streamGone: a loss stalls only its own stream
Handshakes before the requestTCP + TLS: 2 round tripsTCP + TLS: 2 round tripsQUIC with TLS inside: 1 round trip
Where you meet itMany APIs and most server-to-server codegRPC; browsers to CDNs and APIsBrowsers and mobile apps to CDNs

For one long streaming request on a clean network all three behave alike. They differ when packets are lost: measured on the running request, one dropped TCP packet delayed all three concurrent HTTP/2 streams (by 68, 56 and 43 ms), while over HTTP/3 only the stream that lost a packet was delayed (by 66 ms). The {{On the wire|#t-wire}} tab, section 4, replays it.

Three HTTP facts that decide what other layers must do.

  • LLM generation is a POST, and POST is not idempotent. A safe method (GET, HEAD) only reads; an idempotent one (GET, PUT, DELETE) has the same effect run once or twice, so a client may retry it after a network error ({{RFC 9110, section 9.2|https://www.rfc-editor.org/rfc/rfc9110#section-9.2}}). If the connection drops after a POST left, the client cannot know whether the server is already generating (and billing); APIs answer with an idempotency key, a design owned by {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}} (section 4).
  • The status code is sent before the first token. A stream that begins with 200 cannot report a later failure in its status, so errors after that point arrive as events inside the stream (Anthropic's API may send overloaded_error that way, {{streaming docs|https://platform.claude.com/docs/en/build-with-claude/streaming}}). 401 against 403 is auth's distinction (section 9); 502, 503 and 504 come from a proxy or gateway reporting on the hop behind it.
  • The effective timeout is the smallest one on the path. Between the app and the model server sit a client library, perhaps a corporate proxy, a CDN, a load balancer, an ingress and the API server, each with its own idle timeout (nginx gives up on a silent upstream after 60 s, {{nginx docs|https://nginx.org/en/docs/http/ngx_http_proxy_module.html}}) and sometimes a total one. Streaming defeats only idle timeouts; a total timeout counts the whole response even while tokens flow (Envoy's route default 15 s, API Gateway 29 s).

7. Streaming: tokens as they are generated

A model generates tokens over seconds or minutes; waiting for the whole answer makes the app feel dead, and a long silence invites every proxy on the path to cut the connection. Server-Sent Events (SSE) answer with content-type: text/event-stream and keep one HTTP response open, writing small text events (event: and data: lines ending in a blank line, {{WHATWG HTML, section 9.2|https://html.spec.whatwg.org/multipage/server-sent-events.html}}). Because it is plain HTTP it passes every proxy, which is why every major LLM API and MCP's HTTP transport use it. The choice among the four ways to deliver a result depends on direction and on how long the work takes:

MechanismDirectionUse it forWhat it costs
SSEServer to client, inside one HTTP responseToken streams, progress updates; MCP's HTTP transportOne direction only; text only; buffering proxies break it
WebSockets ({{RFC 6455|https://www.rfc-editor.org/rfc/rfc6455}})Both ways at any time, after an HTTP upgradeVoice agents and realtime APIs where the user can interruptNot HTTP after the first exchange: you write heartbeats, reconnection and resume yourself; long-lived connections complicate load balancing; browsers do not apply the same-origin policy, so the server checks Origin
WebhooksProvider to your server, later, as a separate signed POST"Your batch job finished": fine-tunes, batch inference, evaluationsA public endpoint, so verify signatures; delivery is at least once, so handle duplicates
Long pollingClient asks, server holds the request until there is newsA fallback where nothing else gets throughA full request per batch of events; awkward timeouts

Where streaming breaks, and which layer owns the fix. Tokens arriving in one burst at the end mean a proxy buffered the response (HTTP's proxies). A stream that dies after exactly 60 s while the model is thinking is an idle timeout on one hop; heartbeat comments every 15 s or so are the HTML standard's own advice. A stream that ends without its final event (message_stop) failed, even with no error: retry it with an idempotency key.

8. Service APIs: REST, gRPC, GraphQL behind the front door

Behind POST /v1/messages the API calls its own services thousands of times a second, between programs written by different teams in different languages. The style decides who writes the schema, how calls are encoded, and how they fail:

StyleShapeRight forCost
REST (JSON over HTTP)Resources with URLs, standard methods and status codes, stateless server (Fielding, 2000)Public APIs, including every major LLM API's external face; anyone with curl can call itLoose contracts unless you publish a schema (OpenAPI)
gRPCServices in a .proto file, generated clients, binary protobuf over HTTP/2, four call modesInternal calls where you own both ends; high call rates, streaming, deadlinesCode generation; long-lived HTTP/2 connections that L4 balancers handle badly
GraphQLOne endpoint and a typed schema; the client names the fields it wantsMany front ends reading overlapping dataHard to cache; one query can fan out into many backend calls
JSON-RPC 2.0A JSON object with method, params and id, answered by result or errorThe smallest call format; MCP and A2A use itNo schema or transport of its own

Two ideas that only show across services. A deadline is the time after which the caller no longer wants an answer, passed on by every hop, so that when the user closes the tab the router and the inference server stop too; by default gRPC sets none, so a client can wait effectively forever ({{gRPC docs|https://grpc.io/docs/guides/deadlines/}}). And L4 against L7 balancing: an L4 balancer picks a backend per connection, an L7 one per request. A gRPC client keeps one long-lived HTTP/2 connection, so behind an L4 balancer all its calls land on one replica while the others idle ({{gRPC blog|https://grpc.io/blog/grpc-load-balancing/}}); LLM serving adds routers that send a conversation back to the replica holding its KV cache, which only an L7 router can do.
