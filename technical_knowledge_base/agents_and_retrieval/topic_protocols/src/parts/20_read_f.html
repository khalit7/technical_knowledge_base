5. HTTP: one meaning, three wire formats

The problem. Once there is a private byte stream, client and server still need a shared vocabulary: what is being asked for, how big the answer is, whether it worked, whether it may be cached or retried. HTTP is that vocabulary. The key idea for understanding its versions: the meaning and the wire format are specified separately. Methods, status codes and headers are defined once in {{RFC 9110 (HTTP Semantics)|https://www.rfc-editor.org/rfc/rfc9110}} and mean the same in every version; HTTP/1.1 ({{RFC 9112|https://www.rfc-editor.org/rfc/rfc9112}}), HTTP/2 ({{RFC 9113|https://www.rfc-editor.org/rfc/rfc9113}}) and HTTP/3 ({{RFC 9114|https://www.rfc-editor.org/rfc/rfc9114}}) only change how those messages are cut into bytes. Your code almost never notices the version; your latency and your proxies do.

Meaning: methods, status codes, headers


Methods say what kind of operation this is, and two properties drive retries ({{RFC 9110, section 9.2|https://www.rfc-editor.org/rfc/rfc9110#section-9.2}}). A safe method (GET, HEAD) only reads. An idempotent one (GET, PUT, DELETE) has the same effect whether it runs once or twice, so a client may retry it after a network error. POST is neither, and LLM generation is a POST: if the connection drops after the request left, the client cannot know whether the server is already generating (and billing). APIs solve this with an idempotency key, a unique ID the client sends with the POST so the server can recognise a retry and return the first result instead of doing the work again ({{Stripe's description|https://stripe.com/blog/idempotency}}; an {{IETF draft|https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/}} standardises the header).

Headers carry everything else: content-type (what the body is), content-length or transfer-encoding: chunked (how the receiver knows where the body ends), credentials (x-api-key, authorization), caching (cache-control), and limits (retry-after). Wire format: three versions, one problem each


Each version exists to remove a form of head-of-line blocking: one slow or lost item holding up everything queued behind it.




HTTP/1.1 (1997, RFC 9112)HTTP/2 (2015, RFC 9113)HTTP/3 (2022, RFC 9114)



FormatText linesBinary frames, compressed headers (HPACK)Binary frames, compressed headers (QPACK)


Requests per connection at onceOne; clients open several connections (browsers about 6 per host)Many, as independent streamsMany, as independent QUIC streams


Head-of-line blockingA slow response blocks the connectionFixed between requests, but one lost TCP packet still stalls every streamGone: a loss stalls only its own stream


Handshakes before the requestTCP + TLS: 2 round tripsTCP + TLS: 2 round tripsQUIC with TLS inside: 1 round trip


Where you meet itMany APIs and most server-to-server codegRPC; browsers to CDNs and APIsBrowsers and mobile apps to CDNs




HTTP/2's multiplexing matters when many requests share a connection (a browser loading 80 resources, a gRPC client making thousands of calls). For one long streaming request, all three versions behave alike on a clean network. They differ when packets are lost: on HTTP/2 every stream on the connection waits for the retransmission, on HTTP/3 only the stream that lost the packet. The {{On the wire|#t-wire}} tab measured exactly this on the running request: one dropped TCP packet delayed all three concurrent HTTP/2 streams (by 68, 56 and 43 ms), while over HTTP/3 only the stream that lost a packet was delayed (by 66 ms).


Proxies and timeouts: the effective timeout is the smallest one


Between the app and the model server there are usually several HTTP hops: the client library, a corporate proxy, a CDN, a cloud load balancer, an ingress controller, the API server. Each has its own idle timeout (how long it tolerates silence) and sometimes a total timeout, and the request dies at the smallest. Defaults are short: nginx gives up on a silent upstream after 60 s (proxy_read_timeout, {{nginx docs|https://nginx.org/en/docs/http/ngx_http_proxy_module.html}}). A long generation that thinks for 90 s before its first token is cut at 60 s by a proxy nobody remembered. Streaming helps, because every token resets idle timers, and keepalive comments help further (section 6). Connection reuse (HTTP keep-alive, connection pools) is the other half: reusing one connection skips the TCP and TLS round trips on every later request; on an emulated 50 ms path the On the wire tab measured 108 ms to the first byte on a new connection against 54 ms on a reused one.
