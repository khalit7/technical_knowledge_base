The running example

Team A trains a model. Team B owns the evaluation stack. Team A's orchestrator agent asks Team B's eval agent to "evaluate checkpoint step-4000". Team A never sees Team B's tools or prompts; it sees a task, its states and its results. Both agents are scripted and labelled so on this page; every message is real SDK output.

The five things to remember

1. A2A is for delegating to an opaque agent; MCP is for using tools you can see. 2. The task, not the connection, is the unit: streams drop, tasks keep going. 3. Interrupted states (input-required, auth-required) are the protocol asking a human or client for something. 4. The other agent's output is untrusted input to yours. 5. Irreversible actions need a state where a person, not text, says yes.

1. Why agents need a protocol to talk to each other

Words first. An agent is a program that uses a model to decide its next step and then acts (calls a tool, writes a file, sends a message), in a loop, until a goal is met. Two agents are opaque to each other when neither can see the other's prompts, tools, memory or model: like two companies, they see only what the other says. Delegation is one agent giving another a goal ("evaluate this checkpoint") rather than a function call ("run shard 2 of suite gsm-mini on handle h-7").

The problem. Team A's training orchestrator wants Team B's evaluation results. Without a shared protocol, Team B writes a bespoke API, Team A writes a bespoke client, and every new pair of agents repeats the work: N agents calling M agents means up to N × M integrations. Worse, a job like an evaluation is not one request: it takes minutes, it may need to ask a question ("which suite?"), it may need permission ("I need read access to your bucket"), and the caller's connection may drop in the middle.

What A2A gives. The Agent2Agent protocol (A2A) is a shared contract for exactly that (A2A specification v1.0.1, section 1):

  • Discovery: every A2A server publishes an Agent Card, a JSON document saying who it is, what it can do (its skills), where and how to reach it, and how to authenticate (section 2).
  • A unit of work with a life: a message starts a task, which has an id, a state from a fixed list of eight, a history, and output artifacts (sections 3 and 4).
  • Three ways to hear back: wait for the answer, stream updates over Server-Sent Events, or have the agent POST updates to your webhook (section 5).
  • One meaning, three wire formats: JSON-RPC 2.0, gRPC, or plain HTTP+JSON, chosen from the card (section 6).
  • Opacity on purpose: agents "collaborate based on declared capabilities and exchanged information, without needing to share their internal thoughts, plans, or tool implementations" (spec section 1.2).

Where it came from. Google announced A2A on 9 April 2025 (Google Developers Blog); it became a Linux Foundation project on 23 June 2025, launched with "more than 100 leading technology companies" (Linux Foundation). Version 0.3.0 followed on 30 July 2025, 1.0.0 on 12 March 2026 and 1.0.1 on 28 May 2026 (GitHub releases). On 27 August 2026 A2A "has officially been accepted as a Growth Stage project at the Agentic AI Foundation (AAIF)" (A2A blog), the same Linux Foundation fund that holds MCP since December 2025.

What it costs, and when not to use it. Every A2A hop is another trust boundary (section 9), another credential to manage (section 8), and another service to run with a task store. If you own both sides and one side is really a set of functions, use MCP or a plain API: a protocol for opaque peers adds nothing between two pieces of your own code. If the "agent" answers instantly and never asks anything, a plain HTTP API is simpler. A2A pays off when the other side is someone else's agent, the work is long or conversational, or you want any compliant client to reach your agent without a custom integration.

Predict: Team B's eval agent is down for ten minutes while Team A's orchestrator is streaming a task's updates. Which survives?
The task lives on the server, in whatever task store Team B configured. The recording on this page uses the SDK's in-memory store, so a restart would lose it; the SDK also ships a database task store (DatabaseTaskStore, a2a-sdk[sql]). The client's job is only to find the task again by id (section 5), which works only if the server kept it.

2. Discovery: the Agent Card

The problem. Before Team A can delegate, it must learn that Team B's agent exists, what it can do, which wire format to use, and how to prove who it is. How it works: the agent serves a JSON document at a well-known path, https://{domain}/.well-known/agent-card.json (spec section 8.2; registered as a well-known URI in section 14.3). Clients may also find cards in registries or have them configured. Here is the card Team B's agent served, recorded on the wire:

measured 5 October 2026, src/lab/run_a2a.py scenario discovery: a GET without credentials, then the same GET with If-None-Match.

  • supportedInterfaces lists every binding in preference order; a client "MUST" pick the first one it supports and use that entry's URL (section 8.3.2). Here: JSON-RPC first, HTTP+JSON second.
  • capabilities says what optional features exist. If streaming is absent or false, streaming calls must fail with UnsupportedOperationError; same for pushNotifications (section 3.3.4). Check the card before you rely on either.
  • securitySchemes and securityRequirements say how to authenticate (bearer, API key, OAuth 2.0 flows, OpenID Connect, mutual TLS); the credential itself is obtained out of band (section 8).
  • skills are what a calling model reads to decide whether this agent fits the job: id, name, description, tags, examples. They are claims, not proof.

Caching. Cards change rarely, so servers "SHOULD" send Cache-Control and an ETag and clients "SHOULD" revalidate with If-None-Match (section 8.6). The SDK sends a weak ETag by default and leaves max-age to you (there is no default because only the deployment knows how often its card changes); the second request above came back 304 Not Modified with no body. Caching rules are the HTTP ones: HTTP page, section 3.

Signing. TLS proves you reached the right host (section 7.2 says clients "SHOULD" verify the server's certificate; see TLS and certificates). It does not prove a card copied into a registry or a cache is the one the provider published. For that a card may carry JSON Web Signatures: the card minus its signatures field is put into one canonical byte form with the JSON Canonicalization Scheme (RFC 8785), and that is signed as a JWS (RFC 7515), with the key found by kid and jku (section 8.4). The lab signed Team B's card with an ES256 key, verified it, then appended three words to a skill description:

measured run_a2a.py scenario signing, SDK create_agent_card_signer and create_signature_verifier (verifier pinned to ["ES256"], which blocks algorithm confusion; see Auth, JWTs). The private key stays in the scratch directory; the signature is truncated here.

Extended cards. A public card can hide skills from strangers: if capabilities.extendedAgentCard is true, an authenticated client may call GetExtendedAgentCard and gets a fuller card, which it should use instead of the public one for its session (sections 3.1.11 and 13.3). Do not put internal URLs or secrets in either.

How it fails. Symptom: the client picks a binding the server does not really serve, or a URL that points at a development host. Command: curl -s https://agent.example/.well-known/agent-card.json | jq '.supportedInterfaces'. Fix: the card is configuration; generate it from the deployment, not by hand, and test that every listed interface answers.

3. Messages, tasks, parts and artifacts

Intuition. Think of a ticket in another team's tracker. You write a note (a message); they open a ticket (a task) with a number and a status; they may comment back asking a question (another message, attached to the task); when done they attach the deliverable (an artifact). Related tickets share a thread (a context).

Message
One turn: role (ROLE_USER from the client, ROLE_AGENT from the server), a list of parts, a client-made messageId, and optionally contextId, taskId, referenceTaskIds.
Part
The smallest piece of content, exactly one of: text, raw (bytes), url (a file by reference), data (any JSON value), with optional mediaType and filename (a2a.proto, message Part).
Task
The unit of work: server-made id, contextId, status (a state, an optional message, a timestamp), artifacts, history.
Artifact
An output: artifactId, name, parts. It can be streamed in pieces: later pieces carry append: true, the final one lastChunk: true.
Context
An id grouping tasks and messages into one conversation; the server may keep model context per contextId.

The rules that bite (spec sections 3.4 and 3.7):

  • Task ids are made by the server; a client cannot create a task with its own id. A taskId the server does not know is TaskNotFoundError.
  • A message carrying a taskId and a different contextId must be rejected. Recorded: -32602 Context another-context does not match context ... (section 7).
  • A contextId without a taskId starts a new task in the same conversation.
  • Messages are for talking, artifacts for results: "Messages SHOULD NOT be used to deliver task outputs", and status messages are not guaranteed to reach a client that reconnects, so never put the only copy of a result in a message.
  • SendMessage may answer with a plain Message instead of a Task, for something quick that needs no tracking. A client must handle both.

A gotcha visible in the artifact
The agent wrote "shards": 3; the wire says "shards": 3.0. A data part is a protobuf google.protobuf.Value, whose numbers are doubles, so integers come back as floats in the official SDK. Parse numbers defensively, or send exact values as strings.


Naming on the wire. Version 1.0 serialises the protobuf model as JSON with camelCase field names and enum values as their full names (TASK_STATE_INPUT_REQUIRED, ROLE_USER), and it removed the kind field that 0.3 used to say what an object was (spec sections 5.5 and A.2.1). An object's type is now the key that wraps it: {"task": ...}, {"statusUpdate": ...}, {"artifactUpdate": ...}.






4. The task lifecycle: eight states


Every task is in exactly one state (a2a.proto, enum TaskState; spec section 4.1.3). Click a state to see what it means, who moves a task out of it, and the event that announced it in the recordings.




measured events from scenarios main, in_task_auth, rejected and canceled. failed was not recorded: the scripted agent never fails on its own.


    

  • Active: submitted (accepted, not started) and working.
    • 

  • Interrupted: input-required (the agent needs something from the client) and auth-required (it needs an authorization, section 8). The task waits; nothing is lost.
    • 

  • Terminal: completed, failed, canceled, rejected. A terminal task accepts no more messages (UnsupportedOperationError, recorded as -32004) and cannot be canceled (TaskNotCancelableError, -32002). To continue the conversation, send a new message in the same context: that makes a new task.
    • 



rejected is not failed. Rejected means the agent decided not to do it (in the recording, a request to delete a checkpoint: "this agent only evaluates checkpoints"); failed means it tried and could not. Retrying a rejected task unchanged is pointless; retrying a failed one may work.


What "blocking" means. A plain SendMessage waits until the task is terminal or interrupted, then answers (spec section 3.2.2). So a blocking call can return with the task in input-required: the caller must read the state, not assume a finished result. With returnImmediately: true it answers at once and you follow the task another way (section 5).


Predict: the task is in input-required. Team A answers with a message that carries the right contextId but forgets the taskId. What happens?




"Clients MAY use contextId without taskId to start a new task within an existing conversation context" (section 3.4.3). The original task stays in input-required until someone answers it with its taskId, or it expires under the server's policy. In the recording, Team A's second turn carries both ids.

Streaming, as recorded. Each update is one SSE event, data: {"result": {...}}, inside one HTTP response of type text/event-stream (the format is taught on Streaming and real-time). The stream starts with the Task, then status and artifact updates, and the server closes it when the task is terminal. When the stream drops: the task does not care


The most common A2A bug is treating the stream as the task. The lab started a six-shard job, read four events, then closed the connection, waited, and came back:

  • While nobody was listening, the task kept working (a GetTask in between said so) and produced two more shards.
    • 

  • SubscribeToTask "MUST return a Task object as the first event", the current state with every artifact so far (spec section 3.1.6). The snapshot held all four shards finished by then, so nothing was lost; live events continued from there.
    • 

  • Status messages sent while you were away may be gone: only the latest status is in the snapshot. That is why results belong in artifacts.
    • 



The failure, named. Symptom: after a client restart, tasks "hang in working forever" in your dashboard. Cause: the client relied on one stream and never resubscribed. Fix: persist task ids; on reconnect call SubscribeToTask (or poll GetTask), and treat the stream as a view of the task, never the task itself.


Push notifications


For a job that runs for hours, keeping a stream open is wasteful. Team A registered a webhook with the task (taskPushNotificationConfig inside the send configuration) and asked for an immediate return; the agent then POSTed every update to Team A's URL. As received:

  • The payload is the same StreamResponse object as a stream event (spec section 4.3.3). The SDK sent it as application/json; the specification's example shows application/a2a+json, so accept both.
    • 

  • Authentication of the agent to your webhook: the SDK sent the per-task token you registered as X-A2A-Notification-Token and the credentials you registered as Authorization: Bearer .... Check them on every POST, check the task id is one you created, answer 2xx, and deduplicate: delivery is "at least once" (section 4.3.3). The SDK ships validate_push_notification_url but its default is no screening; the lab's first agent accepted a loopback webhook, and a second agent with the validator turned on refused the same registration with InvalidParamsError: Invalid push notification URL (recorded). Turn it on, or put the sender behind an egress proxy.

Versions


    

  • Clients "MUST" send A2A-Version: 1.0 (major.minor only) on every request; a server that does not support it answers VersionNotSupportedError (section 3.6). Recorded: 9.9 gave -32009 A2A version '9.9' is not supported by this handler. Expected version '1.0'.
    • 

  • An empty or missing header means 0.3. Recorded: an empty header was read as '0.3' and refused the same way. Old clients that never send the header will be treated as 0.3 clients.
    • 

  • 0.3 and 1.0 differ on the wire: 0.3 method names like message/send, a kind field naming each part and streamed event (section A.2.1), lower-case roles such as "user". Sending a 0.3 request to a 1.0-only endpoint gave -32601 Method not found (recorded). The SDK can serve both on one endpoint (enable_v0_3_compat=True).
    • 



Version skew in the wild
UCP's own A2A binding page, in the 2026-08-25 release, still shows 0.3-style requests ("method": "message/send", "kind": "message", an X-A2A-Extensions header) (UCP checkout, A2A binding), while A2A 1.0 names the header A2A-Extensions (spec section 3.2.6). A 1.0-only agent rejects those requests. Check both the version header and the method names when two "A2A" systems cannot talk.

8. Authentication and authorization


Where identity lives. A2A does not put credentials inside its messages: "Identity information is handled at the protocol layer, not within A2A semantics" (section 7). The card declares the schemes; the client gets a credential out of band (an OAuth flow, an API key from a portal, a client certificate); then it sends that credential on every HTTP request, and the server authenticates every request (sections 7.3 and 7.4). The schemes are the ones taught on Auth: API keys, HTTP bearer, OAuth 2.0 flows (authorization code, client credentials, device code), OpenID Connect, and mutual TLS (TLS and certificates, section 7).


Recorded: the SDK client without a token got HTTP 401 Unauthorized with WWW-Authenticate: Bearer realm="eval-agent", and the SDK raised A2AClientError: HTTP Error 401. The discovery request carried no credential, on purpose: the card is public, and a token sent to every URL you fetch is a token you may leak.


The SDK does not authenticate anyone for you
The official Python SDK takes the caller's identity from the web framework (Starlette's request.user) and scopes tasks by its name (resolve_user_scope returns user_name; owner_resolver.py). With no authentication middleware every caller is the same unauthenticated user, whose name is the empty string (auth/user.py), so every caller shares one scope. The lab adds a bearer-token middleware; in production use your gateway or your framework's authentication, and test that one caller cannot read another's task (the recorded Team C check).


Calling onward: do not forward the token


Team A's orchestrator acts for a person. When it calls Team B, it must not pass that person's token along: a token issued for Team A's service is not meant for Team B, and forwarding it breaks audience binding (a token says which service it is for, and each service accepts only its own). The fix is token exchange (RFC 8693): Team A trades the incoming token at the authorization server for a new one whose audience is Team B and whose scope is only what this call needs. Both ideas, with recorded flows, are on Auth, sections 8 and 9; MCP states the same rule as "no token passthrough".


In-task authorization: auth-required


Sometimes the agent discovers mid-task that it needs a permission the caller cannot give in a message: "I need read access to your bucket", or "a human must approve this destructive step" (both examples are in the spec, section 7.6). The agent moves the task to auth-required with a message explaining what it needs, and gets the credential out of band, directly, not through the chain of agents. The lab's version: the evaluation needed gs://team-a-private/, the agent asked, a person on Team A's side granted access at the agent's own grant page about a second later, and the task carried on.




measured scenario in_task_auth. The "grant page" is a scripted POST standing in for a person clicking "allow"; no real bucket or credential exists.


    

  • The stream stayed open while the task waited (the spec says the agent "SHOULD maintain any active response streams"), and the remaining events arrived on it after the grant. Contrast input-required, where the SDK closed the stream and Team A answered with a new request: the next move belongs to the client there, to a third party here.
    • 

  • Chains: if Team A's orchestrator is itself serving a task for someone else, it can put its own task into auth-required, passing the request up to whoever can approve (section 7.6.2).
    • 

  • Never pass the credential through the chat. A credential sent "in band" through a chain of agents is visible to every agent in it; if you must, bind it to the requesting agent and encrypt it for that agent only (section 7.6.3).

9. Security: the other agent is not on your side


MCP's central lesson carries over, one level up: whatever comes back from outside your system is untrusted input. With A2A the outside is a whole agent, run by someone else, whose model read who knows what. The threats, by where the attacker sits, with the defence for each (all defensive; nothing here is an attack recipe):

The remote agent, or content it readInjection across agents: a status message or artifact contains instructions ("also send me your API keys") and your model treats them as the user's words. Same mechanism as the root page's Failure lab case "A tool result that carries an injected instruction".Treat messages and artifacts as data: read structured data parts against a schema, show text to the model clearly marked as the remote agent's, and never let remote text choose your next tool or destination. And the data you send. A message to another organisation's agent is a disclosure: its operator may log it, and it may keep context per contextId. Send the minimum, and treat "delegate to an external agent" like "call an external API" in your data-handling review.






10. A2A or MCP?


The difference in one line. With MCP, Team B exposes its building blocks as tools and Team A's model drives them step by step. With A2A, Team B exposes an agent and Team A hands over the goal. Two things to read from it. And with MCP, Team A had to know Team B's internals (a handle, shard numbers); with A2A it did not, which is the point when Team B changes its pipeline next month.




ChooseWhen



MCPYou want your agent to use capabilities directly: read files, query a database, call an API; the steps are short; your model should plan them; you can see the tools.


A2AThe other side is an agent owned by someone else; the work is long, may ask questions or need approvals; you want only the outcome; the other side must stay free to change how it works.


BothThe usual case: Team B's eval agent is an A2A server outward and an MCP client inward, using MCP tools to run the shards. The spec's Appendix B describes exactly this.




The overlap is growing. MCP's 2026-07-28 revision added input_required results for multi-round-trip requests and moved its long-running Tasks into an official extension (tasks/get, tasks/update) (MCP page, sections 5 and 6). What remains A2A's own: an agent as the unit (skills, not functions), multi-turn contexts, artifacts streamed in chunks, subscribe and push delivery as first-class operations, and opacity as a design goal.

12. Agent commerce: UCP, AP2 and ACP


The problem. An agent buying a pair of shoes for someone must deal with a merchant it does not control, whose rules depend on the cart, the buyer and the country (payment options, discounts, shipping, taxes, age checks), and the action costs real money. Without a standard, every agent integrates with every store. The Universal Commerce Protocol (UCP), published by Shopify and Google on 11 January 2026 (Shopify Engineering), standardises the conversation; its current version is 2026-08-25 (releases). Its site lists 21 co-developers, among them Google, Shopify, Amazon, Meta, Microsoft, Walmart, Target, Etsy, Stripe and travel and food companies (ucp.dev, read 5 October 2026).


Roles and discovery


UCP names roles by the direction capabilities flow (core concepts): the platform consumes them (a shopping agent, an app, a procurement system), the business exposes them and stays the merchant of record, a credential provider holds payment instruments and personal data (a wallet), and a payment service provider moves the money. A business publishes a profile at /.well-known/ucp; a platform sends the URL of its own profile on every request in a UCP-Agent header. A real store's profile, fetched once, read-only:




measured curl -s https://www.allbirds.com/.well-known/ucp, 5 October 2026 (src/inputs/ucp_allbirds_profile.json); the response carried cache-control: public, max-age=60.


Negotiation is an intersection


The business computes what the interaction may use ("server-selects"): (1) keep only capabilities both profiles name, (2) for each, keep the latest version both list, dropping the capability if there is none, (3) drop extensions none of whose parents survived, and repeat until nothing changes. The business returns the active set in every response. A business implements what it supports and an agent degrades predictably instead of failing; HTTP's content negotiation is the same idea. Try it against the real profile above in the Commerce lab.


    

  • Names carry authority. Capabilities and extensions use reverse-domain names: dev.ucp.shopping.checkout is governed by UCP's tech council, dev.shopify.catalog by Shopify, com.example.payments.installments by example.com, with no central registry. A platform "MUST" check that an entity's schema URL is on its namespace's domain; that proves provenance, not trustworthiness.
    • 

  • Versions are dates and match exactly. A release D is one compatible snapshot; an older date works only if the business lists it in supported_versions.
    • 

  • One service, several transports: REST (OpenAPI), MCP (OpenRPC), A2A (an Agent Card), and Embedded (OpenRPC). The store above offers shopping over MCP and embedded only.
    • 



Corrected from the old overview
The old page said core, capabilities and extensions are "each versioned independently so a core revision does not break a niche capability". In 2026-08-25 the UCP-authored dev.ucp.* capabilities and extensions are versioned in lockstep with the release; only third-party extensions and payment handlers version on their own (core concepts, Versioning). The "Embedded Checkout Protocol" of the January post is now the general Embedded Protocol (EP), with checkout methods under ec.*.


The checkout and its explicit "a person must finish this" state


This is UCP's most reusable idea. A checkout session moves through six statuses (checkout capability):




Each problem the business reports carries a severity that tells the agent what to do: recoverable (fix the input and update, such as a badly formatted phone number), requires_buyer_input (information the API cannot collect, such as a delivery window), requires_buyer_review (the order is complete but policy needs the buyer's own approval, such as an order over a limit), unrecoverable (start again or hand off). The two requires_* severities produce the requires_escalation status, and then the business "MUST" provide a continue_url: the agent hands the buyer to the merchant's own page to finish. The spec's overview sentence is the design in one line: "The checkout has to be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported."


Why this matters beyond shopping. An MCP tool call succeeds or fails, and a failure reaches the model as text. UCP makes "an agent cannot finish this, and a person must" a first-class state with a handoff attached. A2A's auth-required is the same move for authorization. Section 14 generalises it.


The handoff channel. When escalation happens inside the agent's app, the Embedded Protocol renders the merchant's checkout in an iframe or webview and exchanges JSON-RPC 2.0 messages with it over postMessage (methods such as ec.start, ec.complete), so the host can supply its native payment sheet and saved addresses while the merchant keeps control of the order (Embedded Protocol).


Paying: handlers, the trust triangle, and AP2


    

  • Payment handlers are specifications, not companies (com.google.pay, dev.shopify.shop_pay): the business lists the handlers it accepts; the platform runs the handler's flow to get a token from the credential provider; the business charges it through its own processor. Raw card numbers never touch the agent, and credentials flow platform to business only: businesses "MUST NOT" echo them back.
    • 

  • Authentication without prior registration: requests can be signed with HTTP Message Signatures (RFC 9421), the verifying keys published in the signer's profile; OAuth 2.0, API keys and mTLS are there for pre-arranged partners. Acting for a logged-in buyer uses OAuth account linking (dev.ucp.common.identity_linking).
    • 

  • AP2 answers "how does the merchant know the user approved this, if an agent clicked buy?" (AP2 specification v0.2). The user approves on a Trusted Surface, which "MUST be non-agentic" (deterministic code, no model in the loop), and signs mandates: a Checkout Mandate bound by hash to the merchant-signed checkout, and a Payment Mandate bound to the same checkout for the payment side. With the human present, the user signs the exact checkout. With the human not present, the user signs "open" mandates with constraints (allowed merchants, allowed line items, an amount range, a budget; checkout mandate, payment mandate), and the agent signs the final "closed" ones within them. Mandates are SD-JWTs, so a verifier sees only the constraints relevant to it. Verification "MUST happen in deterministic code", and the signed receipts become evidence in a dispute. Its stated threat model: "when either role is agentic, then the Agent itself is a potential attacker."
    • 



ACP, the other commerce protocol


OpenAI and Stripe's Agentic Commerce Protocol solves the same problem with a merchant REST API that the agent platform (its RFC names ChatGPT) calls: create, update, complete and cancel a checkout session, a required API-Version header, idempotency keys, request signing, and statuses not_ready_for_payment, ready_for_payment, in_progress, completed, canceled, plus authentication_required for 3-D Secure; an agent that cannot perform an intervention the merchant requires gets an intervention_required message (ACP agentic checkout RFC, version 2026-01-16, status Draft). The shape is close to UCP's checkout; the difference is scope (UCP adds discovery, negotiation, several transports and verticals beyond shopping) and who is behind each. A merchant on Shopify gets UCP through its platform; which one a given agent supports is the practical question.


Two adoption stories in the old overview (a consumer agent buying over UCP, and a retailer blocking it) have no primary source and are left out; see src/unconfirmed.md.






13. Agents driving devices: the Model Hardware Standard


The problem. Lab and factory instruments (liquid handlers, plate readers, robotic arms, microscopes, lasers) each come with their own driver and vendor software, and wiring several together for automation takes an engineer weeks. An agent can write the glue code, but it needs to know what each device can do and what it must never do.


What was announced. On 27 August 2026 Anthropic opened a research preview of the Model Hardware Standard (MHS), "a shared specification for AI agents to safely operate physical devices" (Anthropic). Verified from the announcement:


    

  • A standard driver with a small set of primitives, "read" (get temperature) and "write" (set temperature), and a standard format that makes each device discoverable. Users describe a device in natural-language tags (a robot arm's weight, say), and the driver generates a reference file with what the device can measure, what can be adjusted, and "what safety limits will be enforced".
    • 

  • Three ways for an agent to control it: MCP, a command line interface, and code (APIs). It works with any device that has a programmable interface, is model-agnostic, and "any agent harness can access it using standard protocols, such as the" Model Context Protocol. So MHS is a device layer above MCP, not a competing transport.
    • 

  • Status: shared with partners "ahead of making the standard open source"; access by waitlist; Anthropic plans to release safety findings with the open-source version.
    • 



Reported results (the partners' own measurements, as written in the post): Genentech had Claude tune liquid-handler flow rates (about 140 µL/s for water, 10 µL/s for a viscous protein solution); Carnegie Mellon ran dose-response experiments "roughly three times faster" with integration taking "eight hours, versus the several weeks" of vendor setups; HHMI Janelia unified seven vendor programs and cut adding a device from a "multi-day project" to "only a few minutes". At QuEra, an agent loop running overnight improved a laser-lock recovery script from 58% success at about 150 seconds per attempt to 96% at about six seconds; the finished script, then tested with no agent involved, recovered the lock in 695 of 700 trials (99.3%).


Corrected from the old overview
The old page said QuEra's result went "from 58% to 99.3%" and that Janelia went "from weeks to a day". The 58% and 99.3% are two different measurements (the starting script, and the finished script's blind test; the overnight development run itself reached 96%), and Janelia's figure is per-device integration time, "multi-day project" to "a few minutes".


The lessons that generalise, all from the same post:


    

  • Limits live in the device layer, not the prompt. "MHS enforces device-level safety limits", so a Janelia researcher did not need to worry about the agent using too much laser power. A rule the model is asked to follow can be talked out of; a limit enforced below the model cannot.
    • 

  • Ship the artefact, not the agent. QuEra's end product "was a deterministic, fully inspectable script capable of running in production without an AI agent controlling it." The agent did the search; a reviewed program does the irreversible work.
    • 

  • Physical failures look like software errors to a model. Bubbles from mixing caused runtime errors and Claude's "default instinct was simply to retry", which made more bubbles; Genentech had to teach it that foaming was a physical failure. Retrying is safe for idempotent API calls (HTTP page, section 9); it is not safe for a robot.
    • 

  • Caution has a cost and is still preferred. Claude "often stopped to wait for human confirmation before performing an action it deemed even slightly risky", so experiments sometimes paused overnight; the post's verdict: "an overly cautious agent is preferable to one that is not cautious enough."
    • 



One device item in the old overview could not be confirmed from a primary source and is left out; it is listed in src/unconfirmed.md.






14. The trust boundary for irreversible actions


Every protocol on this page meets the same moment: an action that cannot be taken back (spending money, deleting data, moving a robot arm, granting access). Text that arrives over a protocol, from a tool, a remote agent or a web page, can be written by an attacker, so it must never be enough to authorise such an action. What each protocol provides at that moment:




ProtocolThe "stop here" mechanismWho decidesWhat carries the decision



MCPelicitation; tool annotations such as destructiveHint (hints, not enforcement)the user, through the hostthe host's UI


A2Aauth-required (and input-required)whoever can grant: the client, or a person up a chaina credential delivered out of band, directly to the agent


UCPrequires_escalation with continue_url; requires_buyer_reviewthe buyerthe merchant's own checkout page


AP2mandates signed on a trusted surfacethe user, in advance or per purchasea signature verified in deterministic code


MHSdevice-level safety limits; the agent pausing for confirmationthe device configuration; the operatorthe driver, below the model




The pattern, as a checklist for anything you build:


    

  1. Name the irreversible actions and give each a protocol state, not a sentence in a tool result. A state can be logged, timed out, audited and tested.
    2. 

  2. Put the approval outside the model's channel. A dialog, a merchant page, a signed mandate, an out-of-band grant: something text in the context window cannot fake.
    3. 

  3. Show the person what they approve, rendered by deterministic code (AP2's non-agentic trusted surface), never a model's summary of it.
    4. 

  4. Enforce limits below the model (MHS's device limits, AP2's budget constraints, a payment amount range, an API scope).
    5. 

  5. Bind credentials to one audience and one agent (token exchange, AP2's hash binding, A2A's out-of-band credentials).
    6. 

  6. Prefer producing a reviewable artefact (a script, a closed checkout, a plan) over acting directly, when the action can wait.
    7. 

  7. Never retry an irreversible action blindly; use idempotency keys where the protocol has them (UCP and ACP checkout completion, A2A messageId) and read the state before trying again.
    8.

16. Interview questions, with model answers


When would you use A2A instead of MCP?
When the other side is an agent I do not control and I want to delegate a goal rather than drive tools: long-running work, questions back to me, approvals, and the other team free to change its internals. MCP is for my agent using tools and data directly. Often both: an agent is an A2A server outward and an MCP client inward.


What is an Agent Card and what must a client check in it?
A JSON document at /.well-known/agent-card.json with identity, skills, interfaces in preference order, capabilities and security schemes. Check that the binding you choose is listed (and pick the first you support), that streaming or push are declared before using them, which auth scheme to use, and, if present, the JWS signature over the RFC 8785 canonical form. Treat skills as claims.


Name the task states and which ones end a task.
Submitted, working, input-required, auth-required, completed, failed, canceled, rejected. The last four are terminal; input-required and auth-required are interrupted (waiting for someone). A blocking send returns at either kind.


A client's SSE stream drops mid-task. What should it do?
Nothing is lost on the server: reconnect with SubscribeToTask, whose first event is the full current task, or poll GetTask. Persist task ids so a restarted client can do this. Do not rely on status messages for results; results are artifacts.


How would you secure push notifications?
On the agent: screen webhook URLs against private and link-local ranges (SSRF), time out, retry with backoff, and authenticate to the webhook as configured. On the receiver: verify the token or credentials, accept only known task ids, return 2xx fast, process idempotently, and re-read the task before acting on a terminal state.


Your orchestrator calls a third-party agent for a user. How do credentials flow?
The user's token is for my service only. I exchange it (RFC 8693) for a token whose audience is the third-party agent and whose scope is just this call, and send that. If the agent later needs more (say, the user's bucket), it moves the task to auth-required and obtains the credential out of band, directly, never through my messages.


What is UCP's requires_escalation, and why does it matter beyond commerce?
The checkout status meaning "the agent cannot finish this; the buyer must", set when an error has severity requires_buyer_input or requires_buyer_review; the business must supply a continue_url to hand the buyer to its own page. It turns "a human must do this" into a protocol state with a channel attached, instead of an error string in a model's context, which is what any irreversible action needs.


How does UCP negotiate capabilities?
The business intersects its profile with the platform's: keep capabilities both name, choose the latest common version (drop if none), prune extensions whose parents were dropped, repeat until stable. Names are reverse-domain so anyone can define extensions without a registry; versions are dates matched exactly.


What does AP2 add to a checkout protocol?
Proof of user intent that survives an agent in the middle: mandates signed on a non-agentic trusted surface, bound by hash to the merchant-signed checkout and the payment, verified in deterministic code, with open mandates carrying constraints (merchants, items, amount range, budget) for purchases made while the user is away.


What did the Model Hardware Standard pilots teach about agents and physical actions?
Enforce safety limits in the device layer, below the model; models treat physical failures as software errors and retry, which can make things worse; the best output may be a reviewed deterministic script rather than an agent in the loop (QuEra's 99.3% blind test ran with no agent); and an agent that pauses for confirmation costs time but is the safer default.
