13. Agents driving devices: the Model Hardware Standard

The problem. Lab and factory instruments (liquid handlers, plate readers, robotic arms, microscopes, lasers) each come with their own driver and vendor software, and wiring several together for automation takes an engineer weeks. An agent can write the glue code, but it needs to know what each device can do and what it must never do.

What was announced. On 27 August 2026 Anthropic opened a research preview of the Model Hardware Standard (MHS), "a shared specification for AI agents to safely operate physical devices" ({{Anthropic|https://www.anthropic.com/news/model-hardware-standard-research-preview}}). Verified from the announcement:

  • A standard driver with a small set of primitives, "read" (get temperature) and "write" (set temperature), and a standard format that makes each device discoverable. Users describe a device in natural-language tags (a robot arm's weight, say), and the driver generates a reference file with what the device can measure, what can be adjusted, and "what safety limits will be enforced".
  • Three ways for an agent to control it: MCP, a command line interface, and code (APIs). It works with any device that has a programmable interface, is model-agnostic, and "any agent harness can access it using standard protocols, such as the" Model Context Protocol. So MHS is a device layer above MCP, not a competing transport.
  • Status: shared with partners "ahead of making the standard open source"; access by waitlist; Anthropic plans to release safety findings with the open-source version.

Reported results (the partners' own measurements, as written in the post): Genentech had Claude tune liquid-handler flow rates (about 140 µL/s for water, 10 µL/s for a viscous protein solution); Carnegie Mellon ran dose-response experiments "roughly three times faster" with integration taking "eight hours, versus the several weeks" of vendor setups; HHMI Janelia unified seven vendor programs and cut adding a device from a "multi-day project" to "only a few minutes". At QuEra, an agent loop running overnight improved a laser-lock recovery script from 58% success at about 150 seconds per attempt to 96% at about six seconds; the finished script, then tested with no agent involved, recovered the lock in 695 of 700 trials (99.3%).

Corrected from the old overview
The old page said QuEra's result went "from 58% to 99.3%" and that Janelia went "from weeks to a day". The 58% and 99.3% are two different measurements (the starting script, and the finished script's blind test; the overnight development run itself reached 96%), and Janelia's figure is per-device integration time, "multi-day project" to "a few minutes".

The lessons that generalise, all from the same post:

  • Limits live in the device layer, not the prompt. "MHS enforces device-level safety limits", so a Janelia researcher did not need to worry about the agent using too much laser power. A rule the model is asked to follow can be talked out of; a limit enforced below the model cannot.
  • Ship the artefact, not the agent. QuEra's end product "was a deterministic, fully inspectable script capable of running in production without an AI agent controlling it." The agent did the search; a reviewed program does the irreversible work.
  • Physical failures look like software errors to a model. Bubbles from mixing caused runtime errors and Claude's "default instinct was simply to retry", which made more bubbles; Genentech had to teach it that foaming was a physical failure. Retrying is safe for idempotent API calls ({{HTTP page, section 9|n:3c65c17b0d0d811bb035fa3f158b0889}}); it is not safe for a robot.
  • Caution has a cost and is still preferred. Claude "often stopped to wait for human confirmation before performing an action it deemed even slightly risky", so experiments sometimes paused overnight; the post's verdict: "an overly cautious agent is preferable to one that is not cautious enough."

One device item in the old overview could not be confirmed from a primary source and is left out; it is listed in src/unconfirmed.md.

14. The trust boundary for irreversible actions

Every protocol on this page meets the same moment: an action that cannot be taken back (spending money, deleting data, moving a robot arm, granting access). Text that arrives over a protocol, from a tool, a remote agent or a web page, can be written by an attacker, so it must never be enough to authorise such an action. What each protocol provides at that moment:

ProtocolThe "stop here" mechanismWho decidesWhat carries the decision

A2Aauth-required (and input-required)whoever can grant: the client, or a person up a chaina credential delivered out of band, directly to the agent
UCPrequires_escalation with continue_url; requires_buyer_reviewthe buyerthe merchant's own checkout page
AP2mandates signed on a trusted surfacethe user, in advance or per purchasea signature verified in deterministic code

The pattern, as a checklist for anything you build:

  1. Name the irreversible actions and give each a protocol state, not a sentence in a tool result. A state can be logged, timed out, audited and tested.
  2. Put the approval outside the model's channel. A dialog, a merchant page, a signed mandate, an out-of-band grant: something text in the context window cannot fake.
  3. Show the person what they approve, rendered by deterministic code (AP2's non-agentic trusted surface), never a model's summary of it.
  4. Enforce limits below the model (MHS's device limits, AP2's budget constraints, a payment amount range, an API scope).
  5. Bind credentials to one audience and one agent (token exchange, AP2's hash binding, A2A's out-of-band credentials).
  6. Prefer producing a reviewable artefact (a script, a closed checkout, a plan) over acting directly, when the action can wait.
  7. Never retry an irreversible action blindly; use idempotency keys where the protocol has them (UCP and ACP checkout completion, A2A messageId) and read the state before trying again.
