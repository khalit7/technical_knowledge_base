12. Agent commerce: UCP and ACP

An agent buying shoes deals with a merchant it does not control, whose rules depend on the cart, the buyer and the country, and the action costs real money. The Universal Commerce Protocol (UCP), published by Shopify and Google ({{Shopify Engineering|https://shopify.engineering/UCP}}), standardises that conversation. Its roles are named by the direction capabilities flow ({{core concepts|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/documentation/core-concepts.md}}): the platform consumes them (a shopping agent, an app, a procurement system); the business exposes them and stays the merchant of record; a credential provider holds payment instruments and personal data (a wallet); a payment service provider moves the money.

Discovery and negotiation by intersection

A business publishes a profile at /.well-known/ucp; a platform sends the URL of its own profile on every request in a UCP-Agent header. The business then computes what the interaction may use ("server-selects"): (1) keep only capabilities both profiles name; (2) for each, keep the latest version both list, dropping it if there is none; (3) drop extensions none of whose parents survived, and repeat until nothing changes. It returns the active set in every response, so an agent degrades predictably instead of failing (HTTP's content negotiation is the same idea).   • Names carry authority. Reverse-domain names: dev.ucp.shopping.checkout is governed by UCP's tech council, dev.shopify.catalog by Shopify, com.example.payments.installments by example.com, with no central registry. The checkout and its explicit "a person must finish this" state


Six checkout statuses; requires_escalation (orange) is the protocol saying the buyer, not the agent, must finish. Click a status


From the {{checkout capability|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/specification/shopping/checkout/index.md}}, 2026-08-25. canceled is reachable from any status. complete_in_progress means the business is placing the order: no new Update or Complete, poll Get Checkout.


Each problem the business reports carries a severity: recoverable (fix the input and update), requires_buyer_input (information the API cannot collect), requires_buyer_review (policy needs the buyer's own approval), unrecoverable (start again or hand off). Either requires_* produces requires_escalation, and the business "MUST" then provide a continue_url to its own page: "The checkout has to be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported." Why this matters beyond shopping. An MCP tool call succeeds or fails, and a failure reaches the model as text. UCP makes "an agent cannot finish this, and a person must" a first-class state with a handoff attached; A2A's auth-required is the same move for authorization (section 15 generalises it).


The handoff channel, payment handlers and request signing in UCP


Embedded Protocol. When escalation happens inside the agent's app, the Embedded Protocol renders the merchant's checkout in an iframe or webview and exchanges JSON-RPC 2.0 messages with it over postMessage (ec.start, ec.complete), so the host supplies its native payment sheet and saved addresses while the merchant keeps control of the order ({{Embedded Protocol|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/specification/embedded-protocol.md}}).


Payment handlers are specifications, not companies (com.google.pay, dev.shopify.shop_pay): the business lists the handlers it accepts, the platform runs the handler's flow to get a token from the credential provider, and the business charges it through its own processor. Raw card numbers never touch the agent, and credentials flow platform to business only: businesses "MUST NOT" echo them back. Requests can be signed with HTTP Message Signatures ({{RFC 9421|https://www.rfc-editor.org/rfc/rfc9421}}) with the verifying keys published in the signer's profile, so no prior registration is needed; OAuth 2.0, API keys and mTLS serve pre-arranged partners, and acting for a logged-in buyer uses OAuth account linking (dev.ucp.common.identity_linking).




ACP, the other commerce protocol


OpenAI and Stripe's Agentic Commerce Protocol solves the same problem with a merchant REST API that the agent platform calls (create, update, complete and cancel a checkout session); an agent that cannot perform an intervention the merchant requires gets an intervention_required message, ACP's version of the handoff. UCP adds discovery, negotiation, several transports and verticals beyond shopping; a merchant on Shopify gets UCP through its platform, so which one a given agent supports is the practical question.


ACP's checkout in detail
The RFC names ChatGPT as the agent platform; every request carries a required API-Version header, idempotency keys and request signing ({{ACP agentic checkout RFC|https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/main/rfcs/rfc.agentic_checkout.md}}, version 2026-01-16, status Draft). Statuses: not_ready_for_payment, ready_for_payment, in_progress, completed, canceled, plus authentication_required for 3-D Secure. The shape is close to UCP's checkout.
