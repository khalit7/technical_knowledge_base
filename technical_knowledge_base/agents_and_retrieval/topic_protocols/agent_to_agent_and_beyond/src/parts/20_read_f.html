9. Security: the other agent is not on your side

MCP's central lesson carries over, one level up: whatever comes back from outside your system is untrusted input. With A2A the outside is a whole agent, run by someone else, whose model read who knows what. The threats, by where the attacker sits, with the defence for each (all defensive; nothing here is an attack recipe):

AttackerWhat goes wrongDefence
The remote agent, or content it readInjection across agents: a status message or artifact contains instructions ("also send me your API keys") and your model treats them as the user's words. Same mechanism as the root page's {{Failure lab|n:3c65c17b0d0d81ec9355f4eecd6eed02}} case "A tool result that carries an injected instruction".Treat messages and artifacts as data: read structured data parts against a schema, show text to the model clearly marked as the remote agent's, and never let remote text choose your next tool or destination. Break a leg of the lethal trifecta ({{MCP page, section 8|n:3c65c17b0d0d813f9695dc4175c44cbb}}).
Someone pretending to be the agentA look-alike domain or a poisoned registry entry serves a card pointing at the attacker's endpoint.Allowlist agent domains; verify TLS; verify card signatures against keys you already trust (section 2); alert when a card's interfaces or keys change.
The agent's own claimsOver-claimed skills: the card says "evaluates checkpoints"; the skill is a claim, not a capability.Evaluate an agent before you route real work to it; keep a per-skill allowlist; watch rejected and failed rates.
A client registering a webhookSSRF: the agent POSTs to an internal address chosen by a stranger.Screen push URLs (off by default in the SDK, section 5), use an egress proxy, never follow redirects to private ranges.
Anyone who can reach your webhookForged "task completed" notifications.Check the per-task token and the agent's credentials on each POST; accept only task ids you created; re-read the task with GetTask before acting on a terminal state.
Another tenant of the same agentReading or listing someone else's tasks.Authentication on every request and per-caller scoping (section 8; Team C's recorded -32001).
A middle agent in a chainConfused deputy / token passthrough: it forwards a user's token to a third agent, or uses its own wide privileges for a caller who should have narrow ones.Token exchange with audience and scope per hop; authorize each request against the original caller (section 8).
A flood of requestsExhausting the agent (every task may cost model calls).Rate limits per caller, size limits on messages and files (spec section 13.4), quotas on concurrent tasks.

And the data you send. A message to another organisation's agent is a disclosure: its operator may log it, and it may keep context per contextId. Send the minimum, and treat "delegate to an external agent" like "call an external API" in your data-handling review.

10. A2A or MCP?

The difference in one line. With MCP, Team B exposes its building blocks as tools and Team A's model drives them step by step. With A2A, Team B exposes an agent and Team A hands over the goal. The {{One job, recorded|#t-run}} tab replays the same evaluation both ways; the counts (recorded on the same laptop, both servers built with the official SDKs, both clients scripted):

HTTP requestsBytes on the wire (up / down)Characters Team A's model must readWho plans the steps
MCP: tools/list, list_suites, load_checkpoint, three run_shard calls63,654 / 3,4481,424Team A's model, 5 tool calls; it must learn Team B's handles and shards
A2A: card, the job, the answer to "which suite?", a final GetTask41,795 / 8,144624Team B's agent; Team A sends 2 messages

measured src/lab/mcp_same_job.py (MCP SDK 2.3.0, Streamable HTTP, protocol 2026-07-28) and run_a2a.py scenario main. "Characters Team A's model must read": MCP, the tools/list schemas plus every tool result; A2A, the card's skills plus every status message and artifact. Ids and envelopes are not counted.

Two things to read from it. A2A moved more bytes here (every streamed event repeats the task and context ids), yet put less than half as much text in front of Team A's model, and that text does not grow with the number of shards: in the MCP version each extra shard is another round trip and another result in Team A's context. And with MCP, Team A had to know Team B's internals (a handle, shard numbers); with A2A it did not, which is the point when Team B changes its pipeline next month.

ChooseWhen
MCPYou want your agent to use capabilities directly: read files, query a database, call an API; the steps are short; your model should plan them; you can see the tools.
A2AThe other side is an agent owned by someone else; the work is long, may ask questions or need approvals; you want only the outcome; the other side must stay free to change how it works.
BothThe usual case: Team B's eval agent is an A2A server outward and an MCP client inward, using MCP tools to run the shards. The spec's Appendix B describes exactly this.

The overlap is growing. MCP's 2026-07-28 revision added input_required results for multi-round-trip requests and moved its long-running Tasks into an official extension (tasks/get, tasks/update) ({{MCP page, sections 5 and 6|n:3c65c17b0d0d813f9695dc4175c44cbb}}). What remains A2A's own: an agent as the unit (skills, not functions), multi-turn contexts, artifacts streamed in chunks, subscribe and push delivery as first-class operations, and opacity as a design goal.
