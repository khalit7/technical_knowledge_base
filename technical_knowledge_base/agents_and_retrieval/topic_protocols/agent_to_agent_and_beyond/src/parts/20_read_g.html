12. Agent commerce: UCP, AP2 and ACP

The problem. An agent buying a pair of shoes for someone must deal with a merchant it does not control, whose rules depend on the cart, the buyer and the country (payment options, discounts, shipping, taxes, age checks), and the action costs real money. Without a standard, every agent integrates with every store. The Universal Commerce Protocol (UCP), published by Shopify and Google on 11 January 2026 ({{Shopify Engineering|https://shopify.engineering/UCP}}), standardises the conversation; its current version is 2026-08-25 ({{releases|https://github.com/Universal-Commerce-Protocol/ucp/releases}}). Its site lists 21 co-developers, among them Google, Shopify, Amazon, Meta, Microsoft, Walmart, Target, Etsy, Stripe and travel and food companies ({{ucp.dev|https://ucp.dev/}}, read 5 October 2026).

Roles and discovery

UCP names roles by the direction capabilities flow ({{core concepts|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/documentation/core-concepts.md}}): the platform consumes them (a shopping agent, an app, a procurement system), the business exposes them and stays the merchant of record, a credential provider holds payment instruments and personal data (a wallet), and a payment service provider moves the money. A business publishes a profile at /.well-known/ucp; a platform sends the URL of its own profile on every request in a UCP-Agent header. A real store's profile, fetched once, read-only:

Negotiation is an intersection


The business computes what the interaction may use ("server-selects"): (1) keep only capabilities both profiles name, (2) for each, keep the latest version both list, dropping the capability if there is none, (3) drop extensions none of whose parents survived, and repeat until nothing changes. The business returns the active set in every response. A business implements what it supports and an agent degrades predictably instead of failing; HTTP's content negotiation is the same idea. Try it against the real profile above in the {{Commerce lab|#t-ucp}}.


    

  • Names carry authority. Capabilities and extensions use reverse-domain names: dev.ucp.shopping.checkout is governed by UCP's tech council, dev.shopify.catalog by Shopify, com.example.payments.installments by example.com, with no central registry. A platform "MUST" check that an entity's schema URL is on its namespace's domain; that proves provenance, not trustworthiness.
    • 

  • Versions are dates and match exactly. A release D is one compatible snapshot; an older date works only if the business lists it in supported_versions.
    • 

  • One service, several transports: REST (OpenAPI), MCP (OpenRPC), A2A (an Agent Card), and Embedded (OpenRPC). The store above offers shopping over MCP and embedded only.

The checkout and its explicit "a person must finish this" state


This is UCP's most reusable idea. A checkout session moves through six statuses ({{checkout capability|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/specification/shopping/checkout/index.md}}):




Each problem the business reports carries a severity that tells the agent what to do: recoverable (fix the input and update, such as a badly formatted phone number), requires_buyer_input (information the API cannot collect, such as a delivery window), requires_buyer_review (the order is complete but policy needs the buyer's own approval, such as an order over a limit), unrecoverable (start again or hand off). The two requires_* severities produce the requires_escalation status, and then the business "MUST" provide a continue_url: the agent hands the buyer to the merchant's own page to finish. The spec's overview sentence is the design in one line: "The checkout has to be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported."


Why this matters beyond shopping. An MCP tool call succeeds or fails, and a failure reaches the model as text. UCP makes "an agent cannot finish this, and a person must" a first-class state with a handoff attached. A2A's auth-required is the same move for authorization. Section 14 generalises it.


The handoff channel. When escalation happens inside the agent's app, the Embedded Protocol renders the merchant's checkout in an iframe or webview and exchanges JSON-RPC 2.0 messages with it over postMessage (methods such as ec.start, ec.complete), so the host can supply its native payment sheet and saved addresses while the merchant keeps control of the order ({{Embedded Protocol|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/specification/embedded-protocol.md}}).


Paying: handlers, the trust triangle, and AP2


    

  • Payment handlers are specifications, not companies (com.google.pay, dev.shopify.shop_pay): the business lists the handlers it accepts; the platform runs the handler's flow to get a token from the credential provider; the business charges it through its own processor. Raw card numbers never touch the agent, and credentials flow platform to business only: businesses "MUST NOT" echo them back.
    • 

  • Authentication without prior registration: requests can be signed with HTTP Message Signatures ({{RFC 9421|https://www.rfc-editor.org/rfc/rfc9421}}), the verifying keys published in the signer's profile; OAuth 2.0, API keys and mTLS are there for pre-arranged partners. Acting for a logged-in buyer uses OAuth account linking (dev.ucp.common.identity_linking).
    • 

  • AP2 answers "how does the merchant know the user approved this, if an agent clicked buy?" ({{AP2 specification v0.2|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md}}). The user approves on a Trusted Surface, which "MUST be non-agentic" (deterministic code, no model in the loop), and signs mandates: a Checkout Mandate bound by hash to the merchant-signed checkout, and a Payment Mandate bound to the same checkout for the payment side. With the human present, the user signs the exact checkout. With the human not present, the user signs "open" mandates with constraints (allowed merchants, allowed line items, an amount range, a budget; {{checkout mandate|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/checkout_mandate.md}}, {{payment mandate|https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/payment_mandate.md}}), and the agent signs the final "closed" ones within them. Mandates are SD-JWTs, so a verifier sees only the constraints relevant to it. Verification "MUST happen in deterministic code", and the signed receipts become evidence in a dispute. Its stated threat model: "when either role is agentic, then the Agent itself is a potential attacker."
    • 



ACP, the other commerce protocol


OpenAI and Stripe's Agentic Commerce Protocol solves the same problem with a merchant REST API that the agent platform (its RFC names ChatGPT) calls: create, update, complete and cancel a checkout session, a required API-Version header, idempotency keys, request signing, and statuses not_ready_for_payment, ready_for_payment, in_progress, completed, canceled, plus authentication_required for 3-D Secure; an agent that cannot perform an intervention the merchant requires gets an intervention_required message ({{ACP agentic checkout RFC|https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/main/rfcs/rfc.agentic_checkout.md}}, version 2026-01-16, status Draft). The shape is close to UCP's checkout; the difference is scope (UCP adds discovery, negotiation, several transports and verticals beyond shopping) and who is behind each. A merchant on Shopify gets UCP through its platform; which one a given agent supports is the practical question.
