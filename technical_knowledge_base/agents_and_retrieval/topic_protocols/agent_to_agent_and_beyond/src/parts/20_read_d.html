5. Hearing back: wait, poll, stream, or be called

The problem. An evaluation takes minutes; an HTTP request that hangs for minutes dies at the first proxy timeout ({{HTTP page, section 8|n:3c65c17b0d0d811bb035fa3f158b0889}}). A2A separates starting work from following it, and gives four ways to follow (spec section 3.5):

WayHowGood forCosts, and how it fails
WaitSendMessage (blocking default) returns at a terminal or interrupted stateshort tasksthe request is held open; long tasks hit proxy and client timeouts

Pushregister a webhook; the agent POSTs each update to itserver-to-server, hours-long tasksyou must run a reachable, authenticated endpoint; at-least-once delivery, so duplicates

Streaming, as recorded. Each update is one SSE event, data: {"result": {...}}, inside one HTTP response of type text/event-stream (the format is taught on {{Streaming and real-time|n:3c65c17b0d0d812daa9fdb38719fc82b}}). The stream starts with the Task, then status and artifact updates, and the server closes it when the task is terminal. In the running example the first stream closed right after input-required; Team A's answer opened a second stream. Replay it step by step in {{One job, recorded|#t-run}}.

When the stream drops: the task does not care

The most common A2A bug is treating the stream as the task. The lab started a six-shard job, read four events, then closed the connection, waited, and came back:

measured scenario resubscribe: raw httpx streams through the tap (the SDK server as recorded). Times are from the first request.

  • While nobody was listening, the task kept working (a GetTask in between said so) and produced two more shards.
  • SubscribeToTask "MUST return a Task object as the first event", the current state with every artifact so far (spec section 3.1.6). The snapshot held all four shards finished by then, so nothing was lost; live events continued from there.
  • Status messages sent while you were away may be gone: only the latest status is in the snapshot. That is why results belong in artifacts.

The failure, named. Symptom: after a client restart, tasks "hang in working forever" in your dashboard. Cause: the client relied on one stream and never resubscribed. Fix: persist task ids; on reconnect call SubscribeToTask (or poll GetTask), and treat the stream as a view of the task, never the task itself.

Push notifications

For a job that runs for hours, keeping a stream open is wasteful. Team A registered a webhook with the task (taskPushNotificationConfig inside the send configuration) and asked for an immediate return; the agent then POSTed every update to Team A's URL. As received:

  • The payload is the same StreamResponse object as a stream event (spec section 4.3.3). The SDK sent it as application/json; the specification's example shows application/a2a+json, so accept both.
    • 

  • Authentication of the agent to your webhook: the SDK sent the per-task token you registered as X-A2A-Notification-Token and the credentials you registered as Authorization: Bearer .... Check them on every POST, check the task id is one you created, answer 2xx, and deduplicate: delivery is "at least once" (section 4.3.3). This is the webhook discipline of {{Streaming and real-time, section 10|n:3c65c17b0d0d812daa9fdb38719fc82b}}.
    • 

  • The server-side risk: a webhook URL is a URL your agent will fetch for a stranger, the classic server-side request forgery (SSRF) setup: an attacker registers http://169.254.169.254/... (a cloud metadata service) or an internal host. The spec says agents "SHOULD" reject private, loopback and link-local addresses (section 13.2). The SDK ships validate_push_notification_url but its default is no screening; the lab's first agent accepted a loopback webhook, and a second agent with the validator turned on refused the same registration with InvalidParamsError: Invalid push notification URL (recorded). Turn it on, or put the sender behind an egress proxy.

6. One meaning, three wire formats, and versions


Version 1.0 defines the operations once and maps them onto three bindings (spec sections 5, 9, 10, 11): JSON-RPC 2.0 over HTTP with SSE for streams, gRPC (protobuf over HTTP/2, see {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b}}), and HTTP+JSON, a REST style whose URLs come from the same protobuf service definition. The byte counts differ by a few percent; the real difference is operational. JSON-RPC answers every A2A error with HTTP 200 and an error object; HTTP+JSON uses HTTP status codes (a missing task is a real 404, recorded in section 7). A dashboard that counts HTTP 5xx and 4xx sees JSON-RPC failures as successes. Pick the binding your load balancers, caches and monitors understand, and alert on the error object, not the status line.


Versions


    

  • Clients "MUST" send A2A-Version: 1.0 (major.minor only) on every request; a server that does not support it answers VersionNotSupportedError (section 3.6). Recorded: 9.9 gave -32009 A2A version '9.9' is not supported by this handler. Expected version '1.0'.
    • 

  • An empty or missing header means 0.3. Recorded: an empty header was read as '0.3' and refused the same way. Old clients that never send the header will be treated as 0.3 clients.
    • 

  • 0.3 and 1.0 differ on the wire: 0.3 method names like message/send, a kind field naming each part and streamed event (section A.2.1), lower-case roles such as "user". Sending a 0.3 request to a 1.0-only endpoint gave -32601 Method not found (recorded). The SDK can serve both on one endpoint (enable_v0_3_compat=True).
    • 



Version skew in the wild
UCP's own A2A binding page, in the 2026-08-25 release, still shows 0.3-style requests ("method": "message/send", "kind": "message", an X-A2A-Extensions header) ({{UCP checkout, A2A binding|https://github.com/Universal-Commerce-Protocol/ucp/blob/v2026-08-25/docs/specification/shopping/checkout/a2a.md}}), while A2A 1.0 names the header A2A-Extensions (spec section 3.2.6). A 1.0-only agent rejects those requests. Check both the version header and the method names when two "A2A" systems cannot talk.
