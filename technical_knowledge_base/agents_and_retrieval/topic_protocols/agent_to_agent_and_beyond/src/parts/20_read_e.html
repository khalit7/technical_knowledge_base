8. Authentication and authorization


Where identity lives. A2A does not put credentials inside its messages: "Identity information is handled at the protocol layer, not within A2A semantics" (section 7). The card declares the schemes; the client gets a credential out of band (an OAuth flow, an API key from a portal, a client certificate); then it sends that credential on every HTTP request, and the server authenticates every request (sections 7.3 and 7.4). The schemes are the ones taught on {{Auth|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}: API keys, HTTP bearer, OAuth 2.0 flows (authorization code, client credentials, device code), OpenID Connect, and mutual TLS ({{TLS and certificates, section 7|n:3c65c17b0d0d8105a37ff2d2f602a421}}).


Recorded: the SDK client without a token got HTTP 401 Unauthorized with WWW-Authenticate: Bearer realm="eval-agent", and the SDK raised A2AClientError: HTTP Error 401. The discovery request carried no credential, on purpose: the card is public, and a token sent to every URL you fetch is a token you may leak.


The SDK does not authenticate anyone for you
The official Python SDK takes the caller's identity from the web framework (Starlette's request.user) and scopes tasks by its name (resolve_user_scope returns user_name; {{owner_resolver.py|https://github.com/a2aproject/a2a-python/blob/v1.2.2/src/a2a/server/owner_resolver.py}}). With no authentication middleware every caller is the same unauthenticated user, whose name is the empty string ({{auth/user.py|https://github.com/a2aproject/a2a-python/blob/v1.2.2/src/a2a/auth/user.py}}), so every caller shares one scope. The lab adds a bearer-token middleware; in production use your gateway or your framework's authentication, and test that one caller cannot read another's task (the recorded Team C check).


Calling onward: do not forward the token


Team A's orchestrator acts for a person. When it calls Team B, it must not pass that person's token along: a token issued for Team A's service is not meant for Team B, and forwarding it breaks audience binding (a token says which service it is for, and each service accepts only its own). The fix is token exchange ({{RFC 8693|https://www.rfc-editor.org/rfc/rfc8693}}): Team A trades the incoming token at the authorization server for a new one whose audience is Team B and whose scope is only what this call needs. Both ideas, with recorded flows, are on {{Auth, sections 8 and 9|n:3c65c17b0d0d817692dcc8ebd59b5c2b}}; MCP states the same rule as "no token passthrough".


In-task authorization: auth-required


Sometimes the agent discovers mid-task that it needs a permission the caller cannot give in a message: "I need read access to your bucket", or "a human must approve this destructive step" (both examples are in the spec, section 7.6). The agent moves the task to auth-required with a message explaining what it needs, and gets the credential out of band, directly, not through the chain of agents. The lab's version: the evaluation needed gs://team-a-private/, the agent asked, a person on Team A's side granted access at the agent's own grant page about a second later, and the task carried on.




measured scenario in_task_auth. The "grant page" is a scripted POST standing in for a person clicking "allow"; no real bucket or credential exists.


    

  • The stream stayed open while the task waited (the spec says the agent "SHOULD maintain any active response streams"), and the remaining events arrived on it after the grant. Contrast input-required, where the SDK closed the stream and Team A answered with a new request: the next move belongs to the client there, to a third party here.
    • 

  • Chains: if Team A's orchestrator is itself serving a task for someone else, it can put its own task into auth-required, passing the request up to whoever can approve (section 7.6.2).
    • 

  • Never pass the credential through the chat. A credential sent "in band" through a chain of agents is visible to every agent in it; if you must, bind it to the requesting agent and encrypt it for that agent only (section 7.6.3).
