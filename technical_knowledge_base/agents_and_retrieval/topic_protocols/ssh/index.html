SSH: keys, certificates, jump hosts and tunnels for cluster work

How SSH turns one TCP connection into an encrypted, authenticated pipe that carries shells, file copies and port forwards; how keys, agents, host keys and certificates decide who trusts whom; and the jump-host, multiplexing and tunnel patterns that make a GPU cluster behind a bastion pleasant to use. Taught from zero, with every behaviour recorded on 5 October 2026 in a small container cluster (a bastion, two compute nodes, a notebook server) driven from a laptop with ssh -vvv. SSH in one screen

You want to run a training script on a GPU node. The node sits on a private network with no route from the internet; the only door is a bastion (also called a jump host: a hardened machine whose one job is to let authenticated people through). Between your laptop and the bastion are Wi-Fi, an internet provider, maybe a VPN. SSH (Secure Shell, protocol version 2) is what makes that path safe and usable: it encrypts everything, proves to you that you reached the real machine, proves to the machine that you are you, and then carries as many independent streams as you like (a shell, a file copy, a tunnel to a notebook) inside one connection. It runs on TCP, by default on port 22, and the implementation almost everyone uses is OpenSSH (client ssh, server sshd); the current release is 10.5, of 11 August 2026 (OpenSSH release notes).

Everything on this page was recorded in this small cluster, built with containers on one laptop. The laptop can reach only the bastion (published on 127.0.0.1:30922); the two compute nodes live on an internal network the laptop cannot route to, exactly like a real cluster. gpu-node-01 runs a stand-in for a Jupyter server (a token-protected Python web server, since installing Jupyter adds nothing to the protocol story); gpu-node-02 plays an old login node.

Three layers

Transport: agree keys, encrypt, prove the server's identity with its host key. User authentication: you prove who you are, usually with a key pair. Connection: many channels (shell, command, port forward, file transfer) share the one encrypted pipe (section 1).

Two kinds of key

The server's host key answers "is this really the bastion?"; your user key answers "is this really Khalid?". Each side trusts a public key it already knows, or a certificate signed by a key it trusts (sections 2 to 4).

Cluster patterns

ProxyJump reaches the node through the bastion without trusting it (5, 6); ControlMaster reuses one login for every later command (7); port forwarding brings the node's notebook to your browser (8).

What to remember

  1. The host key is SSH's only defence against a man in the middle (an attacker who sits on the path and pretends to be the server). SSH has no certificate authority by default: it trusts the key it saw the first time and stores it in known_hosts. Never click through "REMOTE HOST IDENTIFICATION HAS CHANGED"; when nodes are rebuilt often, use host certificates so there is nothing to click (section 3, recorded).
  2. Use ProxyJump, not agent forwarding. With ssh -A anyone who is root on the bastion can use your keys while you are logged in: recorded here, root on the bastion logged in to both compute nodes as Khalid. With -J bastion the bastion only relays encrypted bytes (section 6).
  3. Turn on ControlMaster. Through a bastion 40 ms away, a fresh ssh gpu-node-01 true took 850 ms (median of 10); riding an existing master connection it took 114 ms, 7.5 times faster, and on a cluster with two-factor login it also means one prompt instead of one per command (section 7).
  4. A notebook bound to 127.0.0.1 is still open to every other user on that node. Loopback is shared by all users of a machine; it only keeps other machines out. Keep the token, or serve on a Unix socket in a private directory and forward to it (section 8, recorded).
  5. Short-lived certificates beat authorized_keys at scale: the node trusts one CA key, a certificate expires by itself in hours, and the server log names the certificate. The client only ever says "Permission denied"; the reason is in the server log (section 4).
  6. Post-quantum key exchange is already the default (mlkem768x25519-sha256 since OpenSSH 10.0; RFC 10042, August 2026). It made the key-exchange messages 2512 bytes instead of 240 and cost no measurable time here; since 10.1 the client warns when a server cannot do it (section 11).
  7. Patch, and do not expose port 22 to the internet if you can avoid it. regreSSHion (2024) was remote code execution as root before any authentication, so keys did not help (section 12).

1. One connection on the wire

The problem. Before SSH (1995) people logged in to remote machines with telnet and rlogin, which sent everything, passwords included, as readable text, and copied files with rcp and ftp. SSH replaced all of them with one protocol that encrypts and authenticates. Version 2, the only one in use, is four RFCs from January 2006: the architecture (RFC 4251), user authentication (RFC 4252), the transport layer (RFC 4253) and the connection protocol (RFC 4254), plus many later extensions.

The three layers

Transport (RFC 4253). After TCP connects, each side sends one text line, its identification string (here SSH-2.0-OpenSSH_10.3 and SSH-2.0-OpenSSH_10.5: anyone on the path sees your software version). Then both send KEXINIT, a list of what they support in ten categories (key exchange, host key type, cipher and MAC each way, compression, languages); for each category the winner is the first entry on the client's list that the server also supports (RFC 4253 section 7.1). Then a key exchange (a Diffie-Hellman style agreement: each side sends a fresh public value, both compute the same secret, an eavesdropper cannot), in which the server also signs a hash of everything exchanged so far with its host key. That hash, H, becomes the session identifier. Both send NEWKEYS and switch on encryption.

User authentication (RFC 4252) runs inside the encrypted pipe. With a key, the client signs a message that includes the session identifier, so the signature is useless on any other connection: a malicious server cannot replay it elsewhere. OpenSSH goes further with publickey-hostbound-v00@openssh.com, which also binds the server's host key into the signature (seen in the log below).

Connection (RFC 4254) multiplexes channels over the one pipe: session (a shell, a command, or a subsystem such as SFTP), direct-tcpip (you asked to reach a host and port through the server: -L, -D, and ProxyJump), forwarded-tcpip (the server forwards a connection back to you: -R), and channels for X11 and the agent. Each channel has its own flow-control window. This is why one login can carry a shell, an rsync and three tunnels at once, and also why one dead TCP connection kills all of them together.

Watch one login, packet by packet

The relay below sat between the laptop and the bastion and decoded every SSH packet until encryption started; after NEWKEYS it could see only sizes. The command was ssh bastion true (log in, run nothing, leave). Pick a key exchange: the classic one, or the post-quantum hybrid that is now the default. Bars are drawn to scale by bytes on the wire.

Recorded 5 October 2026, laptop OpenSSH 10.3p1 to bastion OpenSSH 10.5p1, one connection per key exchange (forced with -o KexAlgorithms=). Sizes are whole SSH packets (length field, padding included). Time is the median of 15 fresh logins with no added delay; most of it is the container port proxy, not cryptography.

Reading the sizes. In the hybrid, the client's KEX_HYBRID_INIT carries an X25519 public key (32 bytes) and an ML-KEM-768 encapsulation key (1,184 bytes), the server's reply carries an X25519 key and a 1,088-byte ML-KEM ciphertext, plus the host key and signature (sizes from FIPS 203; message layout in RFC 10042 section 2.1). Payload arithmetic for the recorded init: 1 (message type) + 4 (length) + 32 + 1,184 = 1,221 bytes, exactly what the relay saw. The two secrets are combined as K = HASH(KPQ || KCL) (RFC 10042 section 2.4), so the result is safe if either half holds. The rest of the login (authentication, one channel, exit status) was 888 encrypted bytes up and 2040 down, the same for every key exchange.

Predict, then reveal: what can the relay (or anyone on the Wi-Fi) learn from this login?
Both software versions (the identification strings), every algorithm each side supports and which ones were chosen (KEXINIT is plaintext), the server's host key (it is in the reply, so a passive observer can fingerprint the server), and then the sizes and timing of every encrypted packet. Not visible: the user name, which key was used, the command, its output. Keystroke timing in interactive shells is partly hidden since OpenSSH 9.5's ObscureKeystrokeTiming (on by default; OpenSSH 9.5 release notes).

How many round trips a login costs

With 40 ms added between laptop and bastion, the same login was replayed through the relay. Every arrow is a real packet group at its real time; the labels after NEWKEYS are inferred from order, size and the client's -vvv log, because the content is encrypted.

The server's banner arrived at 123 ms (TCP setup plus the first round trip, plus the container proxy), keys were in place at 176 ms, and the command finished at 480 ms: about eight round trips for one ssh host command, before any work is done. Through a jump host you pay that twice, the second set inside the first (section 5). This is the cost that connection reuse removes (section 7).

2. Keys, agents and authentication


The problem. Passwords sent to a server can be guessed, phished, reused and brute-forced, and they are the whole input of the internet's SSH-guessing botnets. A key pair fixes that: a private key that never leaves your machine and a public key you can hand to anyone. To log in, the client proves it holds the private key by signing a message the server chooses (including the session identifier from section 1); the server checks the signature with the public key listed in ~/.ssh/authorized_keys.


Making and protecting a key


ssh-keygen -t ed25519 -C "khalid@laptop"      # Ed25519 is the default type since OpenSSH 9.5
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519      # add or change the passphrase, with more KDF rounds


    

  • Ed25519 (RFC 8709): 32-byte public keys, fast, no parameters to get wrong and no random number needed per signature. RSA still works (signed with rsa-sha2-512); DSA was removed entirely in OpenSSH 10.0 (9 April 2025), "completing the deprecation process that began in 2015" (10.0 release notes).
    • 

  • The passphrase encrypts the private key file on disk, stretched with bcrypt_pbkdf; -a sets the rounds (the 10.3 manual gives a default of 16; the current OpenBSD manual says 32). It protects a stolen file, nothing else: once the key is loaded in an agent, anything that can talk to the agent can use it.
    • 

  • Hardware keys (FIDO tokens, OpenSSH 8.2, February 2020): ssh-keygen -t ed25519-sk keeps the private key inside the token and needs a touch per login; -O resident stores it on the token so you can load it on another machine, -O verify-required adds a PIN. The server must run OpenSSH 8.2 or newer to accept them.
    • 

  • On the server, each authorized_keys line can carry options that limit the key: restrict (no forwarding, no pty), from="10.0.0.0/8", command="..." (this key may only run one command, useful for backup or CI keys). See sshd(8) AUTHORIZED_KEYS FILE FORMAT.
    • 



The agent


ssh-agent holds your decrypted keys in memory and signs on request; programs reach it through a Unix socket named by SSH_AUTH_SOCK. You type the passphrase once, and ssh, git and rsync use the key without seeing it. The agent protocol was standardised as RFC 9987 (Standards Track, May 2026); since OpenSSH 10.3 the IANA-assigned names are used when the server offers them, which is why the recorded server advertises an agent-forward extension in its EXT_INFO. Useful flags: ssh-add -t 8h (forget the key after 8 hours), ssh-add -c (ask for confirmation at every use), ssh-add -l (list). Since 10.1 agent sockets live under ~/.ssh/agent/ instead of /tmp, so a sandboxed process that can read /tmp no longer reaches your keys; the forwarded socket on the bastion in section 6 is at /home/khalid/.ssh/agent/s.…. Scripts that hard-coded /tmp/ssh-XXXX break.


Which key gets offered, and "Too many authentication failures"


The client offers keys one at a time; each refusal counts against the server's MaxAuthTries, 6 by default (recorded with sshd -T below). An agent full of keys can exhaust it before the right key is tried. Recorded: an agent holding seven unrelated keys, the right key named in IdentityFile:




The fix is IdentitiesOnly yes, which offers only the keys your config names. To see the order without connecting, OpenSSH 10.5 added ssh -Z host; recorded with the bastion's 10.5 client (the laptop's 10.3 lacks it). It lists the default identity names, including the new id_mldsa44_ed25519 (section 11):




A trap found while recording: IdentityFile lines add up
For almost every keyword the first value obtained wins, which is why Host * goes last. IdentityFile is the exception: "Multiple IdentityFile directives will add to the list of identities tried" (ssh_config(5)). The first certificate tests on this page all "succeeded", even the expired certificate, because the Host * block's ordinary key was also offered and accepted. If a test of one key must fail, give it a config where no other IdentityFile applies, and check ssh -G host | grep identityfile.


Predict, then reveal: a malicious server you log in to receives your signature. Can it use it to log in to the bastion as you?
No. The signed data includes the session identifier of that connection (RFC 4252 section 7), and OpenSSH's hostbound variant also includes the host key. The bastion's session has a different identifier, so the signature fails there. What a malicious server can do is ask a forwarded agent for fresh signatures while you are connected (section 6).

3. Host keys, known_hosts and churn


The problem. Encryption is worthless if you are encrypting to the attacker. In the key exchange the server signs the exchange hash with its host key; the client must decide whether that key really belongs to gpu-node-01. TLS answers with certificate authorities; plain SSH answers with trust on first use (TOFU): the first time, it shows you the key's fingerprint and asks; after that it remembers the key in ~/.ssh/known_hosts and insists on the same one. The first connection is the weak moment; every later one is protected.

The real risk of churn is habituation
A team whose nodes change keys weekly learns to run ssh-keygen -R without looking, and the one day it is a real man in the middle it gets the same treatment. Three ways out, best first: host certificates (section 4: nothing changes on the client when a node is rebuilt); a separate, throwaway known_hosts with accept-new scoped to the ephemeral nodes only (Host gpu-node-*, never Host *, never the bastion); or distributing the keys (a managed /etc/ssh/ssh_known_hosts, or SSHFP below).


Other knobs


    

  • HashKnownHosts yes stores names as hashes so a stolen known_hosts does not list every machine you use (default no upstream; some distributions turn it on). Lookups still work; ssh-keygen -F host finds an entry.
    • 

  • UpdateHostKeys: after login the server can send all its host keys (signed), so the client learns the others before a key rotation (the "hostkeys" extension in PROTOCOL).
    • 

  • SSHFP DNS records publish host key fingerprints; VerifyHostKeyDNS yes makes the client trust them. Only meaningful if the answer is DNSSEC-validated (see DNS), and it had a real bug: CVE-2025-26465, an on-path attacker could impersonate any server when VerifyHostKeyDNS was on, OpenSSH 6.8p1 to 9.9p1, fixed in 9.9p2 (18 February 2025, found by Qualys; release notes). Since 10.1 the release notes warn that SHA-1 SSHFP records will be ignored in a future release; publish SHA-256 ones (ssh-keygen -r host).
    • 



Predict, then reveal: the bastion's key changed and you are sure nobody rebuilt it. What do you do?
Stop. Do not remove the entry. Read the fingerprint the warning printed, get the real one through another channel (console, admin, a colleague on a different network), and compare. If they differ, someone is on the path or the server was compromised; if they match, the key really changed and you can update known_hosts. On a cluster with host certificates this situation becomes rare and therefore alarming, which is the point.






4. SSH certificates: user and host


The problem. With plain keys, trust is a list on every machine: N users' public keys in authorized_keys on M nodes, and M host keys in every user's known_hosts. Adding a person, removing a leaver, rebuilding a node all mean editing lists everywhere. SSH certificates replace the lists with one trusted certificate authority (CA) key: the CA signs a statement "this public key belongs to khalid, may log in as khalid, until 01:15 tomorrow", and every node trusts anything the CA signed. Not X.509 (the web's format from TLS and certificates): OpenSSH's own simpler format, since OpenSSH 5.4 in 2010 (PROTOCOL.certkeys), with no chains: one CA signs, and the CA key is configured directly.


A user certificate, made and used


ssh-keygen -s user_ca -I khalid@2026-10-05 -n khalid -V +8h -z 42 id_cert_only.pub   # writes id_cert_only-cert.pub
# on every node, once:   TrustedUserCAKeys /etc/ssh/user_ca.pub      (sshd_config)


-I is the key ID that appears in the server's log, -n the principals (the account names it may log in as), -V the validity window, -z a serial number for revocation. Recorded: the certificate, the client's view, and the node's log, which names the certificate, its serial and the CA:

The lesson for debugging: "Permission denied (publickey)" is all the client learns, deliberately, so an attacker learns nothing either. Since OpenSSH 10.1 the server logs "enough information to identify the certificate in addition to the reason" (10.1 release notes): that is the Refusing certificate ID ... Certificate invalid: expired line. Ask whoever can read /var/log/auth.log or journalctl -u sshd.


    

  • Revocation uses a KRL (key revocation list), a compact file of revoked serials or keys: ssh-keygen -k -f revoked.krl -s user_ca.pub spec, pushed to nodes and named by RevokedKeys; ssh-keygen -Q -f revoked.krl cert checks a certificate against it (recorded in the "revoked" case). Since 10.3 RevokedKeys accepts several files.
    • 

  • Short lifetimes are the real revocation. An 8-hour certificate stolen today is useless tomorrow, and nobody has to remember to revoke it. Since 10.1, ssh-add drops a certificate from the agent five minutes after it expires (-N disables this).
    • 

  • Empty principals. ssh-keygen warns ("certificate will contain no principals"), and the node refused it (recorded). Before 10.3 a certificate with no principals matched any user when trusted through an authorized_keys line with cert-authority,principals=""; 10.3 made it match none. CAs trusted through TrustedUserCAKeys, as here, never had that behaviour (10.3 release notes).
    • 

  • Restrictions travel in the certificate: -O no-port-forwarding, -O force-command=..., -O source-address=10.0.0.0/8. The recorded certificate carries the default extensions (permit-pty, permit-port-forwarding and so on).
    • 



Correction to the old page
It said 10.3 "changed empty-principal certificates from matching any principal to matching none, which broke sloppy CA tooling in April 2026". The change is real but narrower: it applied only to CAs trusted via authorized_keys principals="", not via TrustedUserCAKeys. That it "broke CA tooling" could not be confirmed from any primary source and is dropped.


Host certificates: the cure for churn


The same idea in the other direction. Provisioning signs each node's host key with a host CA (ssh-keygen -s host_ca -h -I gpu-node-01-host -n gpu-node-01 -V +52w ssh_host_ed25519_key.pub), the node presents it (HostCertificate in sshd_config), and clients carry one line instead of one per node:


@cert-authority gpu-node-* ssh-ed25519 AAAAC3Nza...   # in known_hosts


Recorded: the client accepts the node with no prompt; then the node is rebuilt (new key, re-signed at boot, as an image or a cloud-init step would do) and the client still connects with nothing to edit; and a certificate issued for the wrong name is refused:






Who runs the CA


Signing by hand is fine for a lab; in practice a service signs after a single sign-on login: HashiCorp Vault's SSH secrets engine, Teleport (CA, short-lived certificates, session recording), Smallstep, or cloud equivalents; Netflix published BLESS, a Lambda-based CA. The CA private key becomes the most valuable secret you have: keep it offline or in an HSM or KMS, and ssh-keygen -s can sign with a CA key held in an agent (-U; 10.2 fixed a bug in exactly that path).


Predict, then reveal: a laptop with a valid 8-hour certificate is stolen at 09:00. What can the thief do, and what do you do?
Until the certificate expires (and only if the private key is not passphrase-protected or the agent is unlocked), log in wherever its principals allow. Revoke its serial in the KRL and push it to the nodes for the remaining hours, and the stolen key cannot get a new certificate because the CA requires your single sign-on. Compare with a stolen plain key: valid until someone finds and deletes it from every authorized_keys.






5. Jump hosts and ProxyJump


The problem. Compute nodes are not routable from your laptop; only the bastion is. You could log in to the bastion and run ssh again from there, but then the second login uses keys on (or forwarded to) the bastion, and every tool (rsync, git, VS Code) would have to do the same dance. ProxyJump (OpenSSH 7.3, August 2016) does it properly: your laptop asks the bastion for a raw TCP stream to gpu-node-01:22 and then runs a second, complete SSH session from the laptop to the node through that stream.


ssh -J bastion gpu-node-01                # one hop
ssh -J bastion,login gpu-node-07          # two hops, in order
# or in ~/.ssh/config, so every tool gets it:
Host gpu-node-*
    ProxyJump bastion


Recorded with -vvv: the client turns ProxyJump into a helper ssh -W '[gpu-node-01]:22' bastion (a "stdio forward": its standard input and output become the TCP stream), and the bastion's server log shows only a direct-tcpip channel to port 22 of the node:






What the bastion sees. The node's session is encrypted end to end between laptop and node; the bastion relays ciphertext. The relay on the laptop's path, during a ProxyJump session that pulled about 27 KB of output, decoded the bastion's handshake and nothing else: the node's banner, its key exchange and everything after travelled inside the outer encryption, 5116 bytes up and 6732 down, unreadable to the observer and to the bastion alike.


What it costs. Two full logins, the second inside the first. Without added delay, ssh bastion true took 57 ms and ssh gpu-node-01 true through it 112 ms (medians of 10); with 40 ms between laptop and bastion, 429 ms against 850 ms. Section 7 removes most of that.


    

  • History. Before 7.3 the same thing was written ProxyCommand ssh -W %h:%p bastion, and before 5.4, ProxyCommand ssh bastion nc %h %p. ProxyCommand still matters for non-SSH transports: AWS Session Manager, for example, provides one so that plain ssh, -J and rsync work over it (AWS docs).
    • 

  • Untrusted input in command lines. CVE-2025-61984 (fixed in 10.1, 6 October 2025): control characters in a user name from the command line or a %-expansion could lead to code execution when a ProxyCommand using %r was configured (CVE record); the scenario is a crafted ssh:// or git URL. 10.3 added validation of user and host names given to -J on the command line (not in config files). OpenSSH's own advice: never build ssh command lines from untrusted input.
    • 

  • Each hop's options come from its own Host block, so the bastion can use a hardware key and long multiplexing while nodes use a throwaway known_hosts. ProxyJump none disables an inherited jump.
    • 








6. Agent forwarding against ProxyJump


Agent forwarding (ssh -A, ForwardAgent yes) solves the same problem the old way: you log in to the bastion, and the bastion's sshd creates a socket there that relays signing requests back to the agent on your laptop, so ssh gpu-node-01 typed on the bastion can authenticate as you. The cost: anyone who can open that socket while you are connected can authenticate as you, to any server that trusts your key. That is the bastion's root, or any process running as your user there. Your private key never leaves the laptop, but it does not need to.


Recorded, three ways to reach the nodes. In each, while the session was open, the lab played a malicious root on the bastion: look for agent sockets, list the keys, and try to log in to both nodes as Khalid.














The three results, from src/raw/agent_*.txt: with plain forwarding root found /home/khalid/.ssh/agent/s.…, listed the laptop's key, and logged in to both nodes as Khalid. With a destination-constrained key (ssh-add -h bastion -h 'bastion>gpu-node-01', OpenSSH 8.9 and later) root could still use it, but only for the hop you allowed: gpu-node-01 worked, gpu-node-02 was refused, because the agent checks each request against the host keys bound into the session (session-bind@openssh.com). With ProxyJump there was no socket to find.




    

  • Rules. Use ProxyJump. If a workflow truly needs a key on a remote machine (pushing to GitHub from a login node), prefer a separate deploy key there (section 13) over forwarding; if you must forward, forward a constrained key, add ssh-add -c so every use asks you, and never put ForwardAgent yes under Host *.
    • 

  • Agent locking. ssh-add -x locks the agent with a password. 10.5 fixed a bug where a locked agent refused the session-bind messages that identify forwarded use, so operations meant to be local-only (adding PKCS#11 tokens, using destination-restricted keys) could be done remotely (10.5 release notes).
    • 

  • Server side. AllowAgentForwarding no on a bastion is reasonable when everyone uses ProxyJump; it was enabled here to record the attack. 10.0 fixed DisableForwarding, which had failed to disable agent and X11 forwarding.
    • 



Predict, then reveal: with ProxyJump, can a malicious bastion do anything at all?
It cannot read or alter the node session (encrypted end to end, and the node's host key is checked by your laptop), cannot use your keys, and cannot replay your signature (bound to the node session). It can refuse to relay, delay traffic, see when and how much you send, and see which node you asked for. If your laptop accepts the node's host key blindly (StrictHostKeyChecking no), the bastion could itself pretend to be the node, which is why host key checking still matters behind a bastion.






7. Multiplexing: one login, many commands


The problem. Every ssh, scp, rsync -e ssh, git pull and every VS Code helper starts from zero: TCP, key exchange, authentication, through the bastion and then again to the node, plus a two-factor prompt if the cluster has one. Connection multiplexing keeps the first connection (the master) open and lets later clients ask it, over a local Unix socket, for a new channel on the already-authenticated connection.


Host gpu-node-* bastion
    ControlMaster auto            # use a master if one exists, otherwise become one
    ControlPath ~/.ssh/cm/%C      # where the socket lives; %C hashes local host, host, port, user and jump host
    ControlPersist 4h             # keep the master in the background after the first session ends














Recorded: ten ssh gpu-node-01 true in a row through the bastion, 40 ms added between laptop and bastion; each bar is one real run, drawn to scale. The first multiplexed run creates the master (821 ms), the next nine ride it.




Ten commands: 8.4 s fresh against 1.9 s multiplexed. A reused channel needs one round trip to the bastion and back for the channel open and request (the node hop is inside the cluster), against roughly eight per hop for a login (section 1). Recorded -vvv of a reuse, and the control commands:






ssh -O check host says whether a master is running; -O exit stops it; -O conninfo and -O channels are new in 10.3 (above: the negotiated algorithms and traffic, and the open channels).


What it costs and how it fails


    

  • One master, one fate. When the master dies, every session on it dies at once. Recorded: a session running sleep 20 on the master ended with exit status 255 within milliseconds of -O exit. A laptop that sleeps and wakes on another network often leaves a master that looks alive but is not: -O check, then -O exit, or a short ServerAliveInterval (section 9) so it notices.
    • 

  • The socket is a key. Anyone who can open the control socket can open sessions as you without authenticating. Keep ControlPath in a directory only you can read (mkdir -m 700 ~/.ssh/cm); never in /tmp on a shared machine.
    • 

  • Socket path length. A Unix socket path is limited (108 bytes on Linux, unix(7); 104 on macOS, sun_path[104] in its sys/un.h). %C is a fixed 40-character hash, which is why it is preferred to the older %r@%h:%p pattern. The lab hit the limit: its working directory alone was 120 characters, so it used the relative path ControlPath cm/%C.
    • 

  • Bandwidth is shared. One TCP connection carries everything: a large rsync on the master slows your interactive shell, and one connection's congestion window caps total throughput. For bulk copies, a separate connection (-o ControlMaster=no -o ControlPath=none) can be faster.
    • 

  • Since 10.0, scp and sftp pass ControlMaster no: they use an existing master but no longer silently create one (10.0 release notes). 10.2 fixed a 10.1 bug that made sessions unusable with ControlPersist active, so avoid 10.1 with multiplexing.
    • 

  • Authentication happens once, so a revoked key or an expired certificate does not end a master already running; ControlPersist bounds how long that lasts.
    • 



Predict, then reveal: you changed User in your config for a host, but ssh host whoami still prints the old name. Why?
A master from before the change is still running and serving the request: the new client never authenticated. ssh -O exit host and try again. The same trap catches changed forwarding options and agent forwarding: options of the original master apply.

Correction to the old page: loopback is not private to you
The old page said to bind to 127.0.0.1 "or any other user on that node reaches your kernel". Two lessons in three lines. The other direction: -R




The forwarded port opened on the bastion's loopback only, because the server's GatewayPorts defaults to no. Setting it to yes would expose your laptop's service to the whole network behind the bastion.


When forwarding fails silently




By default a forward that cannot listen is a warning and the session carries on, so a script believes its tunnel is up. With ExitOnForwardFailure yes it exits 255. One subtlety recorded here: -L 30985:... with no bind address listens on localhost in both IPv4 and IPv6; when only 127.0.0.1:30985 was taken, the IPv6 listener on [::1]:30985 still succeeded, so even ExitOnForwardFailure was satisfied, and http://127.0.0.1:30985 reached the other program.     • 

  • Kubernetes. kubectl port-forward pod/nb 8888:8888 is the same idea through the API server (Kubernetes docs).

Predict, then reveal: you run ssh -L 8888:localhost:8888 gpu-node-01 and the browser shows a different notebook from the one you started. How?

9. Keeping sessions alive, and noticing when they are dead


The problem. A VPN, a NAT gateway or a firewall between you and the cluster forgets idle connections after a few minutes (AWS's NAT gateway after 350 seconds, as recorded on Networking foundations); a laptop sleeps; a server freezes. TCP alone will not tell you: with nothing to send, a dead connection looks exactly like a quiet one, and your terminal just hangs.


Recorded: a session to gpu-node-01; three seconds in, the bastion was frozen (docker pause), so packets vanished without any refusal, as with a dead VPN.




    

  • ServerAliveInterval 30 with ServerAliveCountMax 3 (client): after 30 s of silence ssh sends a request inside the encrypted connection and expects an answer; after 3 unanswered it disconnects (about 90 s). The probes also keep NAT and firewall state alive. Recorded with 2 and 2: exit after 5.0 s. Without it (the default is 0, off): still hanging after 30 s.
    • 

  • TCPKeepAlive (on by default) asks the kernel for TCP keepalives, which on Linux start only after 2 hours idle (derived on Networking foundations: 7,200 s, then 9 probes 75 s apart). It is spoofable, does not go through the SSH layer, and is far too slow for a VPN that drops flows in minutes; ssh_config(5) itself points to ServerAliveInterval as the more robust mechanism.
    • 

  • ClientAliveInterval is the server's mirror image (default 0, recorded in sshd -T): it reaps sessions whose client vanished. ChannelTimeout and UnusedConnectionTimeout (both none by default) close idle channels or connections without channels.
    • 

  • Keepalives do not keep a job alive. When the connection dies, the shell and whatever runs in its foreground get a hangup. Run long work as a batch job (sbatch), and keep your interactive orchestration in tmux on the login node (section 13).
    • 








10. Moving files: scp, sftp, rsync, tar


All of these run over an SSH session channel; they differ in how many round trips each file costs and whether they can resume. Recorded through the bastion with 40 ms added (the same link as section 7), copying to gpu-node-01:




    

  • Many small files: scp -r took 193.3 s for 1,000 files of 4 KiB (one run), rsync -a 1.6 s, and tar -cf - small | ssh node 'tar -xf -' 1.3 s (medians of 3). Since OpenSSH 9.0, scp speaks the SFTP protocol underneath (9.0 release notes), which pays several request round trips per file; rsync and tar stream.
    • 

  • One large file (64 MiB): scp 4.5 s, rsync -a 4.1 s: similar, both bounded by one encrypted TCP stream.
    • 

  • Resuming: an rsync --partial of the 64 MiB file was interrupted after 1.5 s, leaving 10,321,920 bytes on the node; rerunning it matched 10,320,136 of them and sent only the rest, in 4.4 s against 4.1 s for a full copy. On this fast link resuming saved bytes, not time (rsync still reads and checksums both sides); it pays off on slow, metered or flaky links, which is exactly when checkpoints get interrupted. Use rsync -avhP --partial (-P is --partial --progress). The laptop's rsync was macOS's openrsync (protocol 29); the node ran rsync 3.5.1.
    • 

  • Legacy scp (scp -O) asks the remote shell to expand file names, which has produced a series of bugs; 10.3 fixed one where legacy-mode downloads as root kept setuid bits, and 10.4 fixed two cases where a malicious server could make sftp or a remote-to-remote scp write outside the intended directory (release notes).
    • 

  • sshfs mounts a remote directory over SFTP: handy for editing, slow for anything with many small reads (each is a round trip), so never point a data loader at it. The project is maintained for fixes but has "no active, regular contributors" (sshfs README; latest release 3.7.6, May 2026). For editing remote code, VS Code Remote-SSH runs the editor's server on the node instead (section 13).

11. Post-quantum SSH


The problem. A large enough quantum computer would break the elliptic-curve Diffie-Hellman behind every key exchange in section 1. None exists yet; OpenSSH's own estimate quotes "5-20 years, with many observers expecting them to arrive in the mid-2030s" (OpenSSH, Post-Quantum Cryptography). The danger is already real because of store now, decrypt later: someone who records your session today can decrypt it once they have such a machine. Signatures are different: a forged signature needs the quantum computer at the moment of the login, so there is no urgency for host and user keys yet.




WhenWhat


OpenSSH 9.0, 8 April 2022Hybrid sntrup761x25519-sha512@openssh.com (Streamlined NTRU Prime plus X25519) becomes the default: SSH was one of the first mainstream protocols with post-quantum key exchange on by default.


OpenSSH 9.9, 19 September 2024Adds mlkem768x25519-sha256: ML-KEM-768 (NIST FIPS 203) plus X25519.


OpenSSH 10.0, 9 April 2025mlkem768x25519-sha256 becomes the default, "considerably faster than the previous default".


OpenSSH 10.1, 6 October 2025The client warns when a connection uses a non-post-quantum key exchange; WarnWeakCrypto controls it, on by default.


April 2026RFC 9941 documents sntrup761x25519-sha512 (Informational).


OpenSSH 10.4, 6 July 2026Experimental composite signature mldsa44-ed25519 (ML-DSA-44 plus Ed25519), off by default; keys with ssh-keygen -t mldsa44-ed25519.


August 2026RFC 10042 specifies mlkem768x25519-sha256, mlkem768nistp256-sha256 and mlkem1024nistp384-sha384 (Informational).




Dates from the OpenSSH release notes and the RFC Editor.


What it cost here. The hybrid's key-exchange messages were 2512 bytes against 240 for classic X25519 (section 1), and the median login took 61 ms against 56 ms: no difference worth measuring on a link where a round trip costs more than the arithmetic. (sntrup761 took 67 ms, consistent with OpenSSH calling ML-KEM faster.) Unlike TLS, where large post-quantum certificates threaten handshake size (TLS and certificates, section 8), SSH sends one host key and one signature, so even future post-quantum signatures add little.


The warning, recorded against gpu-node-02, an OpenSSH 9.7p1 server configured to offer only classic key exchange, as an old login node would:




The fix is to upgrade the server or re-enable its post-quantum algorithms (9.0 and later support sntrup761, 9.9 and later ML-KEM). If you cannot, silence it for that host only, as the OpenSSH page recommends: Match host gpu-node-02 then WarnWeakCrypto no-pq-kex. Do not hand-write KexAlgorithms or Ciphers lists copied from old hardening guides: frozen lists are how servers end up without the post-quantum default, exactly as this node was configured.

"The IETF hybrid key exchange draft is in the RFC Editor queue rather than published": it was published as RFC 10042 in August 2026. The sntrup761 method is RFC 9941 (April 2026).






12. Security: the bugs worth understanding, and a baseline


regreSSHion (CVE-2024-6387): keys do not protect you from a pre-authentication bug


Disclosed by Qualys on 1 July 2024 (advisory). If a client has not authenticated within LoginGraceTime (120 s by default), sshd gets a SIGALRM whose handler logs a message; on glibc-based Linux, syslog() calls malloc() and free(), which are not safe inside a signal handler, so an alarm arriving in the middle of an allocation leaves the heap inconsistent, and a patient attacker turns that into code execution as root, before authentication. It is a regression of CVE-2006-5051, reintroduced in October 2020 (OpenSSH 8.5p1). Affected: portable OpenSSH below 4.4p1 (unless patched) and 8.5p1 up to but not including 9.8p1; fixed in 9.8 (1 July 2024). OpenBSD was not vulnerable (its handler uses syslog_r()).


How hard: Qualys needed about 10,000 tries on average to win the race; on 32-bit Linux with ASLR that took about 6 to 8 hours on average (9.8 release notes); 64-bit exploitation was "believed to be possible" but not demonstrated at disclosure. The stop-gap if you could not upgrade was LoginGraceTime 0, trading the exploit for a denial of service. The lesson stands: an internet-facing sshd is attack surface no matter how good your keys are.


Correction to the old page
It said "roughly one attempt in ten thousand ... glibc-Linux only". The advisory's figure is about 10,000 tries on average to win the race (6 to 8 hours on 32-bit glibc with ASLR); exploitation was shown on glibc Linux, other C libraries were not examined rather than ruled out, and OpenBSD is not vulnerable.


Terrapin (CVE-2023-48795): an attack on the protocol itself


Disclosed 18 December 2023 (terrapin-attack.com). An attacker on the path inserts an ignorable message during the plaintext handshake and deletes one right after encryption starts; sequence numbers still line up, so the integrity check passes. It works against chacha20-poly1305@openssh.com and against CBC ciphers with encrypt-then-MAC MACs; AES-GCM is not affected. Against OpenSSH the practical impact was small: deleting the EXT_INFO message, which disabled some keystroke-timing protections (OpenSSH 9.6 notes); some other implementations were hurt more. The fix, strict key exchange in OpenSSH 9.6, aborts on any unexpected handshake message and resets sequence numbers after each key exchange, and only works when both sides support it. You can see it in the recorded handshake: the client lists kex-strict-c-v00@openssh.com in its KEXINIT, and the log says will use strict KEX ordering and resetting send seqnr 3. The researchers found at least 77% of internet SSH servers supported an exploitable mode at disclosure.

PerSourcePenalties: rate limiting built in


Since OpenSSH 9.8, sshd penalises source addresses that fail authentication, connect without authenticating, or crash it, and refuses them for a while, with no log-parsing daemon such as fail2ban. Recorded on gpu-node-01 with the default policy: six failed logins one second apart, all arriving from the bastion's address.




After four failures the address was refused for 16.563 s, and attempts 5 and 6 were dropped before authentication. Note who got blocked: the bastion. Every user behind it shares that source address, so one broken script locks out the whole team. On nodes reached through a bastion or a NAT gateway, list those addresses in PerSourcePenaltyExemptList (and rate-limit on the bastion instead), or the protection becomes a self-inflicted outage.


A hardening baseline for a cluster


    

  • PasswordAuthentication no and KbdInteractiveAuthentication no (unless your two-factor login uses keyboard-interactive), PermitRootLogin no, AllowGroups for who may log in at all.
    • 

  • Keep the defaults for algorithms (recorded sshd -T in section 2): post-quantum first, ChaCha20-Poly1305 then AES-GCM; no CBC, no DSA, no finite-field Diffie-Hellman in sshd's defaults since 10.0. (The old page said non-EtM MACs are off by default: the recorded 10.5 default list still contains them, after the encrypt-then-MAC ones; with ChaCha20-Poly1305 or AES-GCM no separate MAC is used anyway.)
    • 

  • MaxAuthTries (6), MaxStartups (10:30:100: start refusing 30% of unauthenticated connections at 10, all at 100), LoginGraceTime (120 s), PerSourcePenalties (on): defaults recorded above; tighten LoginGraceTime and MaxAuthTries on the internet-facing host.
    • 

  • Forwarding off by default and enabled per Match Group; AllowAgentForwarding no on the bastion if people use ProxyJump.
    • 

  • User certificates with short lifetimes and host certificates (section 4); a KRL for emergencies.
    • 

  • Moving sshd to port 2222 reduces log noise from scanners; it is not a security control (reasoning, not a measured claim).
    • 



Not exposing port 22 at all


The strongest move is to have no internet-facing sshd: AWS Session Manager (no inbound port, IAM-authorised, audited; a ProxyCommand keeps ssh, -J and rsync working: AWS docs), a WireGuard or Tailscale overlay network (devices authenticate before any SSH packet flows), or Teleport (a certificate-issuing proxy with single sign-on and session recording). On a university cluster you rarely choose; ProxyJump plus ControlMaster is what makes a VPN plus two-factor login bearable.

15. Interview questions


Walk me through what happens when you type ssh gpu-node-01 through a bastion.
The client reads its config, finds ProxyJump bastion, and starts a helper ssh -W gpu-node-01:22 bastion. That helper opens TCP to the bastion, exchanges version strings and KEXINIT lists, runs the key exchange (by default the hybrid ML-KEM-768 plus X25519), verifies the bastion's host key signature against known_hosts or a host CA, switches on encryption, authenticates with a key or certificate whose signature covers the session identifier, and opens a direct-tcpip channel to the node's port 22. Through that channel the main client runs a second, independent handshake and authentication with the node, opens a session channel and requests a shell. The bastion only relays ciphertext. About eight round trips per login, doubled by the hop, which is why ControlMaster matters.


Why is agent forwarding dangerous, and what do you use instead?
The remote sshd exposes a socket that forwards signing requests to your local agent. Anyone with root on that machine, or running as your user, can use it while you are connected to authenticate as you anywhere your key is accepted; your private key never leaves your laptop but it does not need to. Use ProxyJump, which relays an encrypted stream and never gives the bastion signing ability. If forwarding is unavoidable, use destination-constrained keys (ssh-add -h) and confirmation (ssh-add -c).


How does SSH prevent a man in the middle, and where is it weak?
The server signs the key exchange hash with its host key, and the client checks that key against what it knows. The weak points are the first connection (trust on first use: the user must verify the fingerprint) and habituation to "host key changed" warnings on rebuilt machines. Host certificates fix both: the client trusts a CA key, and any properly signed host key for that name is accepted without a prompt. SSHFP records with DNSSEC are an alternative.


What are SSH certificates and why would a company use them?
A CA signs a user's public key together with a key ID, principals, a validity window, a serial and options. Servers trust the CA key instead of per-user authorized_keys. Onboarding and offboarding become CA policy, certificates expire on their own (hours), logs name the certificate, and a KRL handles emergencies. Host certificates do the same for server identity. The CA key becomes the crown jewel, usually behind single sign-on (Vault, Teleport).


Your notebook tunnel works but a colleague says they can reach your notebook too. How?
They are on the same node: loopback is shared by all local users, so binding to 127.0.0.1 does not isolate you from them, only from other machines. Or the notebook was bound to 0.0.0.0. Keep a token, and preferably serve on a Unix socket in a mode-700 directory and forward to it with -L port:/path/socket.


What does post-quantum key exchange protect against in SSH today, and what does it not?
It protects recorded sessions against future decryption (store now, decrypt later), which is why OpenSSH made a hybrid the default in 2022 and ML-KEM in 2025. It does not protect authentication against a future quantum attacker, but that attack would have to happen live, so there is time; experimental ML-DSA composite signatures arrived in 10.4. The hybrid construction means it is no weaker than X25519 even if ML-KEM were broken.


Explain regreSSHion in two minutes.
An async-signal-safety bug in sshd's login-grace-time alarm handler, which called syslog (and through it malloc) from a signal handler on glibc Linux. Interrupting an allocation at the right moment corrupts the heap; winning the race about one time in 10,000 led to root code execution before authentication. A 2006 bug reintroduced in 8.5p1 (2020), fixed in 9.8 (July 2024). Mitigation without patching: LoginGraceTime 0. Lesson: pre-auth bugs bypass key-only authentication, so limit exposure of sshd.

Glossary




bastion, jump host
The one machine reachable from outside, through which you reach the private network.


host key
The server's long-term key pair; proves the server's identity in every key exchange.


known_hosts
The client's list of host keys it trusts (trust on first use), or @cert-authority lines.


TOFU
Trust on first use: accept a key the first time, insist on it afterwards.


authorized_keys
The server-side list of user public keys allowed to log in to an account.


agent
ssh-agent: holds decrypted private keys and signs on request over a Unix socket.


certificate (SSH)
A public key plus key ID, principals, validity and options, signed by a CA key; not X.509.


principal
A name a certificate is valid for: a user account (user certificates) or a host name (host certificates).


KRL
Key revocation list: a compact file of revoked keys and certificate serials.


channel
One independent stream inside an SSH connection: session, direct-tcpip, forwarded-tcpip, agent, X11.


ProxyJump
Reach a host through another by tunnelling a second, end-to-end SSH session through a direct-tcpip channel.


ControlMaster
Connection multiplexing: later clients reuse one authenticated connection through a control socket.


session identifier
The hash of the first key exchange; signatures in user authentication cover it, binding them to one connection.


strict KEX
OpenSSH 9.6's fix for Terrapin: no unexpected handshake messages, sequence numbers reset at each key exchange.


hybrid key exchange
A classic and a post-quantum exchange run together, the secret derived from both, so it is at least as strong as either.
