2. Keys, agents and authentication

The problem. Passwords sent to a server can be guessed, phished, reused and brute-forced, and they are the whole input of the internet's SSH-guessing botnets. A key pair fixes that: a private key that never leaves your machine and a public key you can hand to anyone. To log in, the client proves it holds the private key by signing a message the server chooses (including the session identifier from section 1); the server checks the signature with the public key listed in ~/.ssh/authorized_keys.

Making and protecting a key

ssh-keygen -t ed25519 -C "khalid@laptop"      # Ed25519 is the default type since OpenSSH 9.5
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519      # add or change the passphrase, with more KDF rounds
  • Ed25519 ({{RFC 8709|https://www.rfc-editor.org/rfc/rfc8709}}): 32-byte public keys, fast, no parameters to get wrong and no random number needed per signature. RSA still works (signed with rsa-sha2-512); DSA was removed entirely in OpenSSH 10.0 (9 April 2025), "completing the deprecation process that began in 2015" ({{10.0 release notes|https://www.openssh.com/releasenotes.html}}).
  • The passphrase encrypts the private key file on disk, stretched with bcrypt_pbkdf; -a sets the rounds (the 10.3 manual gives a default of 16; the current {{OpenBSD manual|https://man.openbsd.org/ssh-keygen.1}} says 32). It protects a stolen file, nothing else: once the key is loaded in an agent, anything that can talk to the agent can use it.
  • Hardware keys (FIDO tokens, OpenSSH 8.2, February 2020): ssh-keygen -t ed25519-sk keeps the private key inside the token and needs a touch per login; -O resident stores it on the token so you can load it on another machine, -O verify-required adds a PIN. The server must run OpenSSH 8.2 or newer to accept them.
  • On the server, each authorized_keys line can carry options that limit the key: restrict (no forwarding, no pty), from="10.0.0.0/8", command="..." (this key may only run one command, useful for backup or CI keys). See {{sshd(8) AUTHORIZED_KEYS FILE FORMAT|https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT}}.

The agent

ssh-agent holds your decrypted keys in memory and signs on request; programs reach it through a Unix socket named by SSH_AUTH_SOCK. You type the passphrase once, and ssh, git and rsync use the key without seeing it. The agent protocol was standardised as {{RFC 9987|https://www.rfc-editor.org/rfc/rfc9987}} (Standards Track, May 2026); since OpenSSH 10.3 the IANA-assigned names are used when the server offers them, which is why the recorded server advertises an agent-forward extension in its EXT_INFO. Useful flags: ssh-add -t 8h (forget the key after 8 hours), ssh-add -c (ask for confirmation at every use), ssh-add -l (list). Since 10.1 agent sockets live under ~/.ssh/agent/ instead of /tmp, so a sandboxed process that can read /tmp no longer reaches your keys; the forwarded socket on the bastion in section 6 is at /home/khalid/.ssh/agent/s.…. Scripts that hard-coded /tmp/ssh-XXXX break.

Which key gets offered, and "Too many authentication failures"

The client offers keys one at a time; each refusal counts against the server's MaxAuthTries, 6 by default (recorded with sshd -T below). An agent full of keys can exhaust it before the right key is tried. Recorded: an agent holding seven unrelated keys, the right key named in IdentityFile:



The fix is IdentitiesOnly yes, which offers only the keys your config names. To see the order without connecting, OpenSSH 10.5 added ssh -Z host; recorded with the bastion's 10.5 client (the laptop's 10.3 lacks it). A trap found while recording: IdentityFile lines add up
For almost every keyword the first value obtained wins, which is why Host * goes last. IdentityFile is the exception: "Multiple IdentityFile directives will add to the list of identities tried" ({{ssh_config(5)|https://man.openbsd.org/ssh_config.5}}). The first certificate tests on this page all "succeeded", even the expired certificate, because the Host * block's ordinary key was also offered and accepted. If a test of one key must fail, give it a config where no other IdentityFile applies, and check ssh -G host | grep identityfile.


Predict, then reveal: a malicious server you log in to receives your signature. Can it use it to log in to the bastion as you?
No. The signed data includes the session identifier of that connection (RFC 4252 section 7), and OpenSSH's hostbound variant also includes the host key. The bastion's session has a different identifier, so the signature fails there. What a malicious server can do is ask a forwarded agent for fresh signatures while you are connected (section 6).
