4. SSH certificates: user and host

With plain keys, trust is a list on every machine: N users' public keys in authorized_keys on M nodes, and M host keys in every user's known_hosts. Adding a person, removing a leaver, rebuilding a node all mean editing lists everywhere. SSH certificates replace the lists with one trusted certificate authority (CA) key: the CA signs a statement "this public key belongs to dev, may log in as dev, until 01:15 tomorrow", and every node trusts anything the CA signed. Not X.509 (the web's format, on {{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}): OpenSSH's own simpler format, since OpenSSH 5.4 in 2010 ({{PROTOCOL.certkeys|https://cvsweb.openbsd.org/src/usr.bin/ssh/PROTOCOL.certkeys}}), with no chains: one CA signs, and the CA key is configured directly.

Before: every node lists every user's key. After: every node trusts one CA line, and nothing changes when people come and go.

Illustrative fleet of 20 users and 50 nodes: plain keys need 20 × 50 = 1,000 authorized_keys entries and 50 host keys in every user's known_hosts; certificates need one TrustedUserCAKeys line per node and one @cert-authority line per user.

A user certificate, made and used

ssh-keygen -s user_ca -I dev@2026-10-05 -n dev -V +8h -z 42 id_cert_only.pub   # writes id_cert_only-cert.pub
# on every node, once:   TrustedUserCAKeys /etc/ssh/user_ca.pub      (sshd_config)

-I is the key ID that appears in the server's log, -n the principals (the account names it may log in as), -V the validity window, -z a serial number for revocation. The client only ever says "Permission denied"; the reason is in the server log.

"Permission denied (publickey)" is all the client learns, deliberately, so an attacker learns nothing either. Since OpenSSH 10.1 the server logs "enough information to identify the certificate in addition to the reason" ({{10.1 release notes|https://www.openssh.com/releasenotes.html}}): that is the Refusing certificate ID ... Certificate invalid: expired line. Ask whoever can read /var/log/auth.log or journalctl -u sshd. On the accepted login the node's log names the certificate, its serial and the CA.

  • Short lifetimes are the real revocation. An 8-hour certificate stolen today is useless tomorrow, and nobody has to remember to revoke it. Since 10.1, ssh-add drops a certificate from the agent five minutes after it expires (-N disables this).
  • Revocation for the hours in between uses a KRL (key revocation list), a compact file of revoked serials or keys: ssh-keygen -k -f revoked.krl -s user_ca.pub spec, pushed to nodes and named by RevokedKeys; ssh-keygen -Q -f revoked.krl cert checks a certificate against it (recorded in the "revoked" case). Since 10.3 RevokedKeys accepts several files.
  • Restrictions travel in the certificate: -O no-port-forwarding, -O force-command=..., -O source-address=198.51.100.0/24. The recorded certificate carries the default extensions (permit-pty, permit-port-forwarding and so on).

Host certificates: the cure for churn

The same idea in the other direction. Provisioning signs each node's host key with a host CA (ssh-keygen -s host_ca -h -I gpu-node-01-host -n gpu-node-01 -V +52w ssh_host_ed25519_key.pub), the node presents it (HostCertificate in sshd_config), and clients carry one line instead of one per node: @cert-authority gpu-node-* ssh-ed25519 AAAAC3Nza... in known_hosts.

With a host CA, a rebuilt node is accepted with nothing to edit, and a certificate for the wrong name is refused.

CA services, signing with an agent-held key, and empty principals (with a correction)
Signing by hand is fine for a lab; in practice: {{HashiCorp Vault's SSH secrets engine|https://developer.hashicorp.com/vault/docs/secrets/ssh/signed-ssh-certificates}}, {{Teleport|https://goteleport.com/docs/}} (CA, short-lived certificates, session recording), Smallstep, or cloud equivalents; Netflix published {{BLESS|https://github.com/Netflix/bless}}, a Lambda-based CA. ssh-keygen -s can sign with a CA key held in an agent (-U; 10.2 fixed a bug in exactly that path).
  • Empty principals. ssh-keygen warns ("certificate will contain no principals"), and the node refused it (recorded). Before 10.3 a certificate with no principals matched any user when trusted through an authorized_keys line with cert-authority,principals=""; 10.3 made it match none. CAs trusted through TrustedUserCAKeys, as here, never had that behaviour ({{10.3 release notes|https://www.openssh.com/releasenotes.html}}).
Correction to the old page
It said 10.3 "changed empty-principal certificates from matching any principal to matching none, which broke sloppy CA tooling in April 2026". The change is real but narrower: it applied only to CAs trusted via authorized_keys principals="", not via TrustedUserCAKeys. That it "broke CA tooling" could not be confirmed from any primary source and is dropped.

Predict, then reveal: a laptop with a valid 8-hour certificate is stolen at 09:00. What can the thief do, and what do you do?
Until the certificate expires (and only if the private key is not passphrase-protected or the agent is unlocked), log in wherever its principals allow. Revoke its serial in the KRL and push it to the nodes for the remaining hours, and the stolen key cannot get a new certificate because the CA requires your single sign-on. Compare with a stolen plain key: valid until someone finds and deletes it from every authorized_keys.
