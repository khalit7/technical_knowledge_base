11. Post-quantum SSH

The problem. A large enough quantum computer would break the elliptic-curve Diffie-Hellman behind every key exchange in section 1. None exists yet; OpenSSH's own estimate quotes "5-20 years, with many observers expecting them to arrive in the mid-2030s" ({{OpenSSH, Post-Quantum Cryptography|https://www.openssh.com/pq.html}}). The danger is already real because of store now, decrypt later: someone who records your session today can decrypt it once they have such a machine. Signatures are different: a forged signature needs the quantum computer at the moment of the login, so there is no urgency for host and user keys yet.

WhenWhat
OpenSSH 9.0, 8 April 2022Hybrid sntrup761x25519-sha512@openssh.com (Streamlined NTRU Prime plus X25519) becomes the default: SSH was one of the first mainstream protocols with post-quantum key exchange on by default.
OpenSSH 9.9, 19 September 2024Adds mlkem768x25519-sha256: ML-KEM-768 (NIST {{FIPS 203|https://csrc.nist.gov/pubs/fips/203/final}}) plus X25519.
OpenSSH 10.0, 9 April 2025mlkem768x25519-sha256 becomes the default, "considerably faster than the previous default".
OpenSSH 10.1, 6 October 2025The client warns when a connection uses a non-post-quantum key exchange; WarnWeakCrypto controls it, on by default.
April 2026{{RFC 9941|https://www.rfc-editor.org/rfc/rfc9941}} documents sntrup761x25519-sha512 (Informational).
OpenSSH 10.4, 6 July 2026Experimental composite signature mldsa44-ed25519 (ML-DSA-44 plus Ed25519), off by default; keys with ssh-keygen -t mldsa44-ed25519.
August 2026{{RFC 10042|https://www.rfc-editor.org/rfc/rfc10042}} specifies mlkem768x25519-sha256, mlkem768nistp256-sha256 and mlkem1024nistp384-sha384 (Informational).

Dates from the {{OpenSSH release notes|https://www.openssh.com/releasenotes.html}} and the RFC Editor.

What it cost here. The hybrid's key-exchange messages were [[kex_ml_kexbytes]] bytes against [[kex_cv_kexbytes]] for classic X25519 (section 1), and the median login took [[kex_ml_ms]] ms against [[kex_cv_ms]] ms: no difference worth measuring on a link where a round trip costs more than the arithmetic. (sntrup761 took [[kex_sn_ms]] ms, consistent with OpenSSH calling ML-KEM faster.) Unlike TLS, where large post-quantum certificates threaten handshake size ({{TLS and certificates|n:3c65c17b0d0d8105a37ff2d2f602a421}}, section 8), SSH sends one host key and one signature, so even future post-quantum signatures add little.

The warning, recorded against gpu-node-02, an OpenSSH 9.7p1 server configured to offer only classic key exchange, as an old login node would:



The fix is to upgrade the server or re-enable its post-quantum algorithms (9.0 and later support sntrup761, 9.9 and later ML-KEM). If you cannot, silence it for that host only, as the OpenSSH page recommends: Match host gpu-node-02 then WarnWeakCrypto no-pq-kex. Do not hand-write KexAlgorithms or Ciphers lists copied from old hardening guides: frozen lists are how servers end up without the post-quantum default, exactly as this node was configured.
