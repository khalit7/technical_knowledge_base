1. One connection on the wire

The problem. Before SSH (1995) people logged in to remote machines with telnet and rlogin, which sent everything, passwords included, as readable text, and copied files with rcp and ftp. SSH replaced all of them with one protocol that encrypts and authenticates. Version 2, the only one in use, is four RFCs from January 2006: the architecture ({{RFC 4251|https://www.rfc-editor.org/rfc/rfc4251}}), user authentication ({{RFC 4252|https://www.rfc-editor.org/rfc/rfc4252}}), the transport layer ({{RFC 4253|https://www.rfc-editor.org/rfc/rfc4253}}) and the connection protocol ({{RFC 4254|https://www.rfc-editor.org/rfc/rfc4254}}), plus many later extensions.

The three layers

Transport ({{RFC 4253|https://www.rfc-editor.org/rfc/rfc4253}}). After TCP connects, each side sends one text line, its identification string (here SSH-2.0-OpenSSH_10.3 and SSH-2.0-OpenSSH_10.5: anyone on the path sees your software version). Then both send KEXINIT, a list of what they support in ten categories (key exchange, host key type, cipher and MAC each way, compression, languages); for each category the winner is the first entry on the client's list that the server also supports (RFC 4253 section 7.1). Then a key exchange (a Diffie-Hellman style agreement: each side sends a fresh public value, both compute the same secret, an eavesdropper cannot), in which the server also signs a hash of everything exchanged so far with its host key. That hash, H, becomes the session identifier. Both send NEWKEYS and switch on encryption.

User authentication ({{RFC 4252|https://www.rfc-editor.org/rfc/rfc4252}}) runs inside the encrypted pipe. With a key, the client signs a message that includes the session identifier, so the signature is useless on any other connection: a malicious server cannot replay it elsewhere. OpenSSH goes further with publickey-hostbound-v00@openssh.com, which also binds the server's host key into the signature (seen in the log below).

Connection ({{RFC 4254|https://www.rfc-editor.org/rfc/rfc4254}}) multiplexes channels over the one pipe: session (a shell, a command, or a subsystem such as SFTP), direct-tcpip (you asked to reach a host and port through the server: -L, -D, and ProxyJump), forwarded-tcpip (the server forwards a connection back to you: -R), and channels for X11 and the agent. Each channel has its own flow-control window. This is why one login can carry a shell, an rsync and three tunnels at once, and also why one dead TCP connection kills all of them together.

Watch one login, packet by packet

The relay below sat between the laptop and the bastion and decoded every SSH packet until encryption started; after NEWKEYS it could see only sizes. The command was ssh bastion true (log in, run nothing, leave). Pick a key exchange: the classic one, or the post-quantum hybrid that is now the default. Bars are drawn to scale by bytes on the wire.

Recorded 5 October 2026, laptop OpenSSH 10.3p1 to bastion OpenSSH 10.5p1, one connection per key exchange (forced with -o KexAlgorithms=). Sizes are whole SSH packets (length field, padding included). Time is the median of 15 fresh logins with no added delay; most of it is the container port proxy, not cryptography.

Reading the sizes. In the hybrid, the client's KEX_HYBRID_INIT carries an X25519 public key (32 bytes) and an ML-KEM-768 encapsulation key (1,184 bytes), the server's reply carries an X25519 key and a 1,088-byte ML-KEM ciphertext, plus the host key and signature (sizes from {{FIPS 203|https://csrc.nist.gov/pubs/fips/203/final}}; message layout in {{RFC 10042|https://www.rfc-editor.org/rfc/rfc10042}} section 2.1). Payload arithmetic for the recorded init: 1 (message type) + 4 (length) + 32 + 1,184 = 1,221 bytes, exactly what the relay saw. The two secrets are combined as K = HASH(KPQ || KCL) (RFC 10042 section 2.4), so the result is safe if either half holds. The rest of the login (authentication, one channel, exit status) was [[enc_c2s]] encrypted bytes up and [[enc_s2c]] down, the same for every key exchange.

Predict, then reveal: what can the relay (or anyone on the Wi-Fi) learn from this login?
Both software versions (the identification strings), every algorithm each side supports and which ones were chosen (KEXINIT is plaintext), the server's host key (it is in the reply, so a passive observer can fingerprint the server), and then the sizes and timing of every encrypted packet. Not visible: the user name, which key was used, the command, its output. Keystroke timing in interactive shells is partly hidden since OpenSSH 9.5's ObscureKeystrokeTiming (on by default; {{OpenSSH 9.5 release notes|https://www.openssh.com/releasenotes.html}}).

How many round trips a login costs

With 40 ms added between laptop and bastion, the same login was replayed through the relay. Every arrow is a real packet group at its real time; the labels after NEWKEYS are inferred from order, size and the client's -vvv log, because the content is encrypted.

The server's banner arrived at [[d40_banner]] ms (TCP setup plus the first round trip, plus the container proxy), keys were in place at [[d40_newkeys]] ms, and the command finished at [[d40_done]] ms: about eight round trips for one ssh host command, before any work is done. Through a jump host you pay that twice, the second set inside the first (section 5). This is the cost that connection reuse removes (section 7).

Rekeying. A long connection agrees new keys from time to time. RFC 4253 section 9 recommends after each gigabyte or each hour; the log shows OpenSSH's default for ChaCha20-Poly1305, rekey out after 134217728 blocks (227 blocks), and RekeyLimit sets it. Since OpenSSH 10.4 a peer that sends non-key-exchange messages during a post-authentication rekey is disconnected ({{10.4 release notes|https://www.openssh.com/releasenotes.html}}).
