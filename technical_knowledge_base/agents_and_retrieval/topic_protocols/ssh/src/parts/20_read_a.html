SSH in one screen

You want to run a training script on a GPU node. The node sits on a private network with no route from the internet; the only door is a bastion (also called a jump host: a hardened machine whose one job is to let authenticated people through). Between your laptop and the bastion are Wi-Fi, an internet provider, maybe a VPN. SSH (Secure Shell, protocol version 2) is what makes that path safe and usable: it encrypts everything, proves to you that you reached the real machine, proves to the machine that you are you, and then carries as many independent streams as you like (a shell, a file copy, a tunnel to a notebook) inside one connection. It runs on TCP, by default on port 22, and the implementation almost everyone uses is OpenSSH (client ssh, server sshd); the current release is 10.5, of 11 August 2026 ({{OpenSSH release notes|https://www.openssh.com/releasenotes.html}}).

Everything on this page was recorded in this small cluster, built with containers on one laptop. The laptop can reach only the bastion (published on 127.0.0.1:30922); the two compute nodes live on an internal network the laptop cannot route to, exactly like a real cluster. gpu-node-01 runs a stand-in for a Jupyter server (a token-protected Python web server, since installing Jupyter adds nothing to the protocol story); gpu-node-02 plays an old login node.

Three layers

Transport: agree keys, encrypt, prove the server's identity with its host key. User authentication: you prove who you are, usually with a key pair. Connection: many channels (shell, command, port forward, file transfer) share the one encrypted pipe (section 1).

Two kinds of key

The server's host key answers "is this really the bastion?"; your user key answers "is this really Khalid?". Each side trusts a public key it already knows, or a certificate signed by a key it trusts (sections 2 to 4).

Cluster patterns

ProxyJump reaches the node through the bastion without trusting it (5, 6); ControlMaster reuses one login for every later command (7); port forwarding brings the node's notebook to your browser (8).

What to remember

  1. The host key is SSH's only defence against a man in the middle (an attacker who sits on the path and pretends to be the server). SSH has no certificate authority by default: it trusts the key it saw the first time and stores it in known_hosts. Never click through "REMOTE HOST IDENTIFICATION HAS CHANGED"; when nodes are rebuilt often, use host certificates so there is nothing to click (section 3, recorded).
  2. Use ProxyJump, not agent forwarding. With ssh -A anyone who is root on the bastion can use your keys while you are logged in: recorded here, root on the bastion logged in to both compute nodes as Khalid. With -J bastion the bastion only relays encrypted bytes (section 6).
  3. Turn on ControlMaster. Through a bastion 40 ms away, a fresh ssh gpu-node-01 true took [[mux_n]] ms (median of 10); riding an existing master connection it took [[mux_reuse]] ms, [[mux_x]] times faster, and on a cluster with two-factor login it also means one prompt instead of one per command (section 7).
  4. A notebook bound to 127.0.0.1 is still open to every other user on that node. Loopback is shared by all users of a machine; it only keeps other machines out. Keep the token, or serve on a Unix socket in a private directory and forward to it (section 8, recorded).
  5. Short-lived certificates beat authorized_keys at scale: the node trusts one CA key, a certificate expires by itself in hours, and the server log names the certificate. The client only ever says "Permission denied"; the reason is in the server log (section 4).
  6. Post-quantum key exchange is already the default (mlkem768x25519-sha256 since OpenSSH 10.0; RFC 10042, August 2026). It made the key-exchange messages [[kex_ml_kexbytes]] bytes instead of [[kex_cv_kexbytes]] and cost no measurable time here; since 10.1 the client warns when a server cannot do it (section 11).
  7. Patch, and do not expose port 22 to the internet if you can avoid it. regreSSHion (2024) was remote code execution as root before any authentication, so keys did not help (section 12).
How this page was recorded
The laptop client is OpenSSH 10.3p1 (macOS); the bastion and gpu-node-01 run OpenSSH 10.5p1 (Alpine edge), gpu-node-02 runs Alpine 3.20's patched 9.7p1, configured with no post-quantum key exchange to play an old node. Every ssh call used -F with the lab's own config, so no personal key or known_hosts was touched; private keys never left the lab directory. An observer was simulated with a small relay on the laptop that decodes the SSH packets until encryption starts (no packet capture tool was used, so nothing below the TCP payload is shown). Where a delay is stated, 40 ms was added to the bastion's outward link with tc netem. Scripts and raw outputs: src/lab/, src/raw/; rerun with src/run_all.sh.
