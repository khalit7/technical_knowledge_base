8. Port forwarding, tunnels and notebooks

The problem. The notebook, TensorBoard or MLflow you want runs on a node your browser cannot reach. SSH can carry TCP connections through its encrypted pipe as channels, in three directions:

Correction to the old page: loopback is not private to you
The old page said to bind to 127.0.0.1 "or any other user on that node reaches your kernel". Binding to 127.0.0.1 keeps other machines out (the second node was refused), but every user on the same node shares its loopback: alice reached the loopback-bound notebook and, with the token, would have run code as Khalid. What protects you on a shared login or compute node is the token (Jupyter's default; never disable it) or, better, a Unix socket in a directory only you can enter: alice got Permission denied. Jupyter Server can listen on a Unix socket (--ServerApp.sock, created with mode 0600 by default, {{Jupyter Server config|https://jupyter-server.readthedocs.io/en/latest/other/full-config.html}}), and ssh -L port:/path/to/socket forwards straight to it (recorded: fwd_L_unix).


One proxy for everything: -D




Two lessons in three lines. Name resolution must happen on the far side: --socks5-hostname (or the URL scheme socks5h://, as in ALL_PROXY=socks5h://127.0.0.1:30989) sends the name to the bastion, which knows gpu-node-01; plain --socks5 resolves on the laptop and fails. And the proxy connects from the bastion, so a service bound to the node's loopback is unreachable through it; use -L to the node for that one.


The other direction: -R




The forwarded port opened on the bastion's loopback only, because the server's GatewayPorts defaults to no. Setting it to yes would expose your laptop's service to the whole network behind the bastion.


When forwarding fails silently




By default a forward that cannot listen is a warning and the session carries on, so a script believes its tunnel is up. With ExitOnForwardFailure yes it exits 255. One subtlety recorded here: -L 30985:... with no bind address listens on localhost in both IPv4 and IPv6; when only 127.0.0.1:30985 was taken, the IPv6 listener on [::1]:30985 still succeeded, so even ExitOnForwardFailure was satisfied, and http://127.0.0.1:30985 reached the other program. Bind explicitly (-L 127.0.0.1:30985:...) and pick ports nobody else uses: deriving the port from your user id (PORT=$((10000 + $(id -u) % 10000))) avoids collisions on shared nodes.

Predict, then reveal: you run ssh -L 8888:localhost:8888 gpu-node-01 and the browser shows a different notebook from the one you started. How?
Something else on your laptop was already listening on 8888 (another tunnel, a local Jupyter), so ssh's listener failed with only a warning and the browser reached the other program; or the address family trap above. Check with lsof -nP -iTCP:8888 -sTCP:LISTEN, use a unique port, bind 127.0.0.1 explicitly, and set ExitOnForwardFailure yes.
