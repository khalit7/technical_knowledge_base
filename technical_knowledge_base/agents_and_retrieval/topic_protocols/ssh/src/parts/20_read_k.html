12. Security: the bugs worth understanding, and a baseline

regreSSHion (CVE-2024-6387): keys do not protect you from a pre-authentication bug

Disclosed by Qualys on 1 July 2024 ({{advisory|https://www.qualys.com/2024/07/01/cve-2024-6387/regresshion.txt}}). If a client has not authenticated within LoginGraceTime (120 s by default), sshd gets a SIGALRM whose handler logs a message; on glibc-based Linux, syslog() calls malloc() and free(), which are not safe inside a signal handler, so an alarm arriving in the middle of an allocation leaves the heap inconsistent, and a patient attacker turns that into code execution as root, before authentication. It is a regression of CVE-2006-5051, reintroduced in October 2020 (OpenSSH 8.5p1). Affected: portable OpenSSH below 4.4p1 (unless patched) and 8.5p1 up to but not including 9.8p1; fixed in 9.8 (1 July 2024). OpenBSD was not vulnerable (its handler uses syslog_r()).

How hard: Qualys needed about 10,000 tries on average to win the race; on 32-bit Linux with ASLR that took about 6 to 8 hours on average ({{9.8 release notes|https://www.openssh.com/releasenotes.html}}); 64-bit exploitation was "believed to be possible" but not demonstrated at disclosure. The stop-gap if you could not upgrade was LoginGraceTime 0, trading the exploit for a denial of service. The lesson stands: an internet-facing sshd is attack surface no matter how good your keys are.

Terrapin (CVE-2023-48795): an attack on the protocol itself

Disclosed 18 December 2023 ({{terrapin-attack.com|https://terrapin-attack.com/}}). An attacker on the path inserts an ignorable message during the plaintext handshake and deletes one right after encryption starts; sequence numbers still line up, so the integrity check passes. It works against chacha20-poly1305@openssh.com and against CBC ciphers with encrypt-then-MAC MACs; AES-GCM is not affected. Against OpenSSH the practical impact was small: deleting the EXT_INFO message, which disabled some keystroke-timing protections (OpenSSH 9.6 notes); some other implementations were hurt more. The fix, strict key exchange in OpenSSH 9.6, aborts on any unexpected handshake message and resets sequence numbers after each key exchange, and only works when both sides support it. You can see it in the recorded handshake: the client lists kex-strict-c-v00@openssh.com in its KEXINIT, and the log says will use strict KEX ordering and resetting send seqnr 3. The researchers found at least 77% of internet SSH servers supported an exploitable mode at disclosure.

PerSourcePenalties: rate limiting built in


Since OpenSSH 9.8, sshd penalises source addresses that fail authentication, connect without authenticating, or crash it, and refuses them for a while, with no log-parsing daemon such as fail2ban. Recorded on gpu-node-01 with the default policy: six failed logins one second apart, all arriving from the bastion's address.




After four failures the address was refused for [[pen_s]] s, and attempts 5 and 6 were dropped before authentication. Note who got blocked: the bastion. Every user behind it shares that source address, so one broken script locks out the whole team. On nodes reached through a bastion or a NAT gateway, list those addresses in PerSourcePenaltyExemptList (and rate-limit on the bastion instead), or the protection becomes a self-inflicted outage.


A hardening baseline for a cluster


    

  • PasswordAuthentication no and KbdInteractiveAuthentication no (unless your two-factor login uses keyboard-interactive), PermitRootLogin no, AllowGroups for who may log in at all.
    • 

  • Keep the defaults for algorithms (recorded sshd -T in section 2): post-quantum first, ChaCha20-Poly1305 then AES-GCM; no CBC, no DSA, no finite-field Diffie-Hellman in sshd's defaults since 10.0. (The old page said non-EtM MACs are off by default: the recorded 10.5 default list still contains them, after the encrypt-then-MAC ones; with ChaCha20-Poly1305 or AES-GCM no separate MAC is used anyway.)
    • 

  • MaxAuthTries (6), MaxStartups (10:30:100: start refusing 30% of unauthenticated connections at 10, all at 100), LoginGraceTime (120 s), PerSourcePenalties (on): defaults recorded above; tighten LoginGraceTime and MaxAuthTries on the internet-facing host.
    • 

  • Forwarding off by default and enabled per Match Group; AllowAgentForwarding no on the bastion if people use ProxyJump.
    • 

  • User certificates with short lifetimes and host certificates (section 4); a KRL for emergencies.
    • 

  • Moving sshd to port 2222 reduces log noise from scanners; it is not a security control (reasoning, not a measured claim).
    • 



Not exposing port 22 at all


The strongest move is to have no internet-facing sshd: AWS Session Manager (no inbound port, IAM-authorised, audited; a ProxyCommand keeps ssh, -J and rsync working: {{AWS docs|https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager-getting-started-enable-ssh-connections.html}}), a WireGuard or Tailscale overlay network (devices authenticate before any SSH packet flows), or Teleport (a certificate-issuing proxy with single sign-on and session recording). On a university cluster you rarely choose; ProxyJump plus ControlMaster is what makes a VPN plus two-factor login bearable.
