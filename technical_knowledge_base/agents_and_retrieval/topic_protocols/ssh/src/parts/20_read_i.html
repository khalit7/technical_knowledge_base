9. Keeping sessions alive, and noticing when they are dead

The problem. A VPN, a NAT gateway or a firewall between you and the cluster forgets idle connections after a few minutes (AWS's NAT gateway after 350 seconds, as recorded on {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}); a laptop sleeps; a server freezes. TCP alone will not tell you: with nothing to send, a dead connection looks exactly like a quiet one, and your terminal just hangs.

Recorded: a session to gpu-node-01; three seconds in, the bastion was frozen (docker pause), so packets vanished without any refusal, as with a dead VPN.



    

  • ServerAliveInterval 30 with ServerAliveCountMax 3 (client): after 30 s of silence ssh sends a request inside the encrypted connection and expects an answer; after 3 unanswered it disconnects (about 90 s). The probes also keep NAT and firewall state alive. Recorded with 2 and 2: exit after [[keep_sa]] s. Without it (the default is 0, off): still hanging after [[keep_none]] s.
    • 

  • TCPKeepAlive (on by default) asks the kernel for TCP keepalives, which on Linux start only after 2 hours idle (derived on {{Networking foundations|n:3c65c17b0d0d8117b21dcb9041879564}}: 7,200 s, then 9 probes 75 s apart). It is spoofable, does not go through the SSH layer, and is far too slow for a VPN that drops flows in minutes; {{ssh_config(5)|https://man.openbsd.org/ssh_config.5}} itself points to ServerAliveInterval as the more robust mechanism.
    • 

  • ClientAliveInterval is the server's mirror image (default 0, recorded in sshd -T): it reaps sessions whose client vanished. ChannelTimeout and UnusedConnectionTimeout (both none by default) close idle channels or connections without channels.
    • 

  • Keepalives do not keep a job alive. When the connection dies, the shell and whatever runs in its foreground get a hangup. Run long work as a batch job (sbatch), and keep your interactive orchestration in tmux on the login node (section 13).
    • 








10. Moving files: scp, sftp, rsync, tar


All of these run over an SSH session channel; they differ in how many round trips each file costs and whether they can resume. Recorded through the bastion with 40 ms added (the same link as section 7), copying to gpu-node-01:




    

  • Many small files: scp -r took [[x_scp_small]] s for 1,000 files of 4 KiB (one run), rsync -a [[x_rsync_small]] s, and tar -cf - small | ssh node 'tar -xf -' [[x_tar_small]] s (medians of 3). Since OpenSSH 9.0, scp speaks the SFTP protocol underneath ({{9.0 release notes|https://www.openssh.com/releasenotes.html}}), which pays several request round trips per file; rsync and tar stream.
    • 

  • One large file (64 MiB): scp [[x_scp_big]] s, rsync -a [[x_rsync_big]] s: similar, both bounded by one encrypted TCP stream.
    • 

  • Resuming: an rsync --partial of the 64 MiB file was interrupted after 1.5 s, leaving [[x_partial]] bytes on the node; rerunning it matched [[x_resume_matched]] of them and sent only the rest, in [[x_resume_s]] s against [[x_rsync_big]] s for a full copy. On this fast link resuming saved bytes, not time (rsync still reads and checksums both sides); it pays off on slow, metered or flaky links, which is exactly when checkpoints get interrupted. Use rsync -avhP --partial (-P is --partial --progress). The laptop's rsync was macOS's openrsync (protocol 29); the node ran rsync 3.5.1.
    • 

  • Legacy scp (scp -O) asks the remote shell to expand file names, which has produced a series of bugs; 10.3 fixed one where legacy-mode downloads as root kept setuid bits, and 10.4 fixed two cases where a malicious server could make sftp or a remote-to-remote scp write outside the intended directory ({{release notes|https://www.openssh.com/releasenotes.html}}).
    • 

  • sshfs mounts a remote directory over SFTP: handy for editing, slow for anything with many small reads (each is a round trip), so never point a data loader at it. The project is maintained for fixes but has "no active, regular contributors" ({{sshfs README|https://github.com/libfuse/sshfs}}; latest release 3.7.6, May 2026). For editing remote code, VS Code Remote-SSH runs the editor's server on the node instead (section 13).
    •
