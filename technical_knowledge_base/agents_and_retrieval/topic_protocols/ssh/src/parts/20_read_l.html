A notebook on a Slurm compute node

# inside the batch job (sbatch), on the compute node
PORT=$((10000 + $(id -u) % 10000))
mkdir -m 700 -p ~/.nb
jupyter lab --no-browser --ServerApp.sock=$HOME/.nb/nb-$SLURM_JOB_ID.sock &
echo "on your laptop: ssh -N -L 127.0.0.1:$PORT:$HOME/.nb/nb-$SLURM_JOB_ID.sock $(hostname)"
# on the laptop (ProxyJump in the config does the hops)
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8888:/home/you/.nb/nb-123.sock gpu-node-07

The pieces: a Unix socket in a private directory so other users on the node cannot reach the kernel (section 8), a port derived from your user id so you do not collide with colleagues, the exact command printed into the job's log so you can paste it, ExitOnForwardFailure so a taken port is an error. If the site does not allow SSH to compute nodes at all, use the scheduler's own route (Open OnDemand, or srun with a port forward through the login node).

Getting onto a node where your job runs

  • srun --overlap --jobid=ID --pty bash starts a shell as a new step inside your running job; --overlap lets it share the job's resources with the steps already running ({{srun|https://slurm.schedmd.com/srun.html}}).
  • Plain ssh to the node works where the site runs pam_slurm_adopt: it refuses SSH to nodes where you have no running job and "adopts" your connection into the job's external step, so its processes are accounted and cleaned up with the job ({{pam_slurm_adopt|https://slurm.schedmd.com/pam_slurm_adopt.html}}).
  • Keep work in batch jobs. An interactive srun --pty dies with your connection. Run tmux on the login node for the shell you orchestrate from, so a closed laptop or dropped VPN loses nothing; avoid leaving it on compute nodes, where job cleanup kills stray processes.

Editors, Git and containers

  • VS Code Remote-SSH installs a server on the remote and runs extensions there. It needs glibc 2.28 or later and libstdc++ 3.4.25 on the remote ({{VS Code docs|https://code.visualstudio.com/docs/remote/linux}}), which excludes CentOS 7 era login nodes. It opens several channels, so pair it with ControlMaster and a long ControlPersist to avoid repeated two-factor prompts.
  • GitHub from a cluster. Use a per-repository deploy key (read-only by default) on the cluster rather than your personal key or a forwarded agent: a compromised login node then exposes one repository ({{GitHub deploy keys|https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys}}). If outbound port 22 is blocked: Host github.com, Hostname ssh.github.com, Port 443, User git ({{GitHub docs|https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port}}).
  • Signing commits with SSH keys: git config gpg.format ssh and user.signingkey; GitHub has verified SSH signatures since 23 August 2022 ({{GitHub changelog|https://github.blog/changelog/2022-08-23-ssh-commit-verification-now-supported/}}). An -sk key makes every signature need a touch.
  • Containers: do not run sshd inside a container to get a shell; use docker exec, kubectl exec or apptainer shell, and kubectl port-forward instead of -L. (This page's lab runs sshd in containers only because SSH is the subject.)
