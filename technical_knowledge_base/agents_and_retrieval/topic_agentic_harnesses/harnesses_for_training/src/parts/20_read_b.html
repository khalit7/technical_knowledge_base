1. The score belongs to the pair: a controlled experiment

An agent benchmark does not score a model. It scores a system: the model, the harness around it (tools, prompts, how outputs are shown, when to stop), the settings (reasoning effort, turn and token caps), the tasks, and luck. Evaluation papers call the harness the scaffold, and scaffold sensitivity is how much the score moves when only the scaffold changes.

The published evidence is collected in the parent's {{Harness atlas|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} ("The harness changes the score"): on Terminal-Bench 2.0's public board one model ranges over about 18 points across nine agents; Arena's HarnessTax study found success moving by about 2 points on SWE-bench Lite and 5 on Terminal-Bench 2.0 across Claude Code, Codex CLI and Pi, while cost moved by about 2 times. Those are other people's runs. Here is a small one where every variable is ours.

The experiment
Ten tasks (section 2), four harnesses, two models. Within each model only the harness changes: same prompts, same verifier, same cap of 16 model calls, same sampling. bash only gives the model one tool, a shell in the container. file tools gives four: list files, read a file (shown with line numbers), replace an exact piece of text, run the tests. file tools, no line numbers is identical except that read_file returns plain text, the one detail that differs. Claude Code is the product itself with its own prompt and six tools (Haiku only). Four rollouts per task and harness for the local model, three for Haiku. Every rollout is in the {{Scaffold experiment|#t-scaf}} tab.

Green: share of rollouts that passed the hidden verifier; amber: passed the tests the agent could see but not the hidden checks (the bracketed figure is the visible-test pass rate). Blue: input tokens the model read per rollout, summed over calls. Local model: Qwen3-4B-Instruct-2507, 4-bit, on Apple M1 Pro; Haiku: Claude Haiku 4.5 on a subscription. The two models are on different scales and are not compared with each other.

What moved, for the small model. With bash only, Qwen3-4B solved of its rollouts; with the file tools, ( without line numbers). Paired by task, the file tools beat bash by points (95% bootstrap interval over tasks ), large enough for ten tasks to see. Reading its rollouts shows why: Removing the line numbers moved success by points (interval ): no difference this task set can detect, even though it was the change we expected to matter most The line numbers did cost something, just not success: the local model's exact-text edits failed times with line numbers (it copied their padding into the text to replace) against without, and it recovered by re-reading the file.

A harness bug that looks like a model failure. mlx_lm.server drops a tool call whose JSON does not parse and returns the reply with no tool call (found in mlx-lm's source by the sibling page {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}; our server log shows the "Failed to parse tool call" warnings). Our loop, like most, ends the episode when a reply has no tool call. So in local rollouts () the model tried to act, wrote a malformed call, and the harness quietly declared the episode over; of them passed. A harness that returned "your tool call did not parse" as an observation would have given those rollouts another turn. Every such rule is part of what a benchmark measures, and part of what RL in that harness would train.

What moved, for Haiku. Success stayed between and in all four harnesses, and no paired difference excludes zero. What moved was the bill: Claude Code read input tokens per rollout against for the file tools without line numbers, because its first call alone carries about tokens of system prompt and tool definitions against for ours; caching made most of that cheap, so cost per rollout differed less ( against , API-price equivalents). That is HarnessTax's pattern in miniature: on easy tasks a strong model's harness moves cost more than success.

How to compare harnesses (or models) honestly
  • Vary one thing. To compare harnesses, fix the model, effort and caps; to compare models, fix the harness (that is why SWE-bench ran every model in the same 100-line mini-SWE-agent).
  • Pair by task. Tasks differ far more than harnesses do; compare harnesses on the same tasks and analyse per-task differences, not two overall percentages.
  • Several rollouts per cell, and an interval. Identical settings gave different outcomes in of our task-and-harness cells. With ten tasks, only differences of tens of points are visible; {{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}} has the sample-size arithmetic.
  • Report cost beside the score, and the harness version beside both.
  • Say which verifier. Our visible-test pass rates and hidden-verifier pass rates differ by up to points for the same cell (section 3).
Predict: the bash-only harness has strictly more power than the file tools (anything replace does, sed or a Python one-liner can do). Why would a weak model do worse with it?
Power is not the constraint; the interface is. With one shell tool the model must also choose and correctly quote a command for every edit, and shell quoting inside JSON inside a tool call is easy to get wrong; a dedicated replace(path, old, new) removes that whole class of error and returns a clear message when the text does not match. SWE-agent's "agent-computer interface" paper made the same point with GPT-4 Turbo: the interface, not the model, moved the resolve rate (the parent's {{Harness atlas|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} has its numbers).
