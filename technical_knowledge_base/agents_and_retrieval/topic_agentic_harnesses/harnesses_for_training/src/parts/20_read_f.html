5. From a rollout to training tokens: what gets loss

The trainer does not see messages; it sees one long sequence of token ids, and for each token a flag saying whether its log-probability enters the loss. In a single-turn maths answer that is easy: prompt off, answer on. In an agent rollout the sequence interleaves the model's replies with text the environment wrote, and the policy must be credited only for what it sampled. Most of the sequence is not the model's. Across the local rollouts, of all tokens were sampled by the model; the rest are the system prompt and tool schemas (), the task (), tool output () and template markers. Putting loss on tool output would train the model to predict ls listings and tracebacks it never chose, and would credit or blame it for the environment's text. Search-R1 measured the difference on question answering: with observation tokens masked, Qwen2.5-7B averaged 0.431 exact match over seven datasets; without the mask, 0.343 ({{arXiv 2503.09516|https://arxiv.org/abs/2503.09516}}). Masking in multi-turn RL in general is on {{RL for LLMs|n:3c65c17b0d0d818c9bcff7177325fe56}}, section 11.

Re-rendering is not the same as recording. mlx_lm.server reported token counts while the rollout ran, so the render can be checked. Every rendered prompt has exactly the length the server counted ( calls), and assistant turns have exactly as many tokens as the server generated. The other replies differ by one or two tokens (the template re-serialises tool-call JSON and whitespace, which tokenises differently from what was sampled), and by dozens (replies whose malformed tool call the server dropped, section 1, so the recorded message is missing tokens the model did sample). And in the last assistant turn the template inserts an empty <think>\n\n</think>\n\n block, 4 tokens: the template, shared with Qwen3's reasoning models, writes a reasoning block into a final assistant turn that follows the last user message, and this instruct model has no reasoning to put in it (chat_template.jinja, the loop.last branch). A trainer that renders the finished trajectory and puts loss on every assistant token trains on 4 tokens per rollout the policy did not sample, at log-probabilities it never had. Small here; with tool-call JSON re-serialised, whitespace normalised or thinking stripped from earlier turns, the mismatch grows.

Token-in, token-out is the fix: the rollout records the exact token ids the engine sampled, with their log-probabilities, and the trainer uses those, never re-tokenised text. That is hard when the harness is a black-box product that talks to an OpenAI-style text API, which is why the two 2026 harness-native RL systems put a proxy between the harness and the engine: Polar's gateway stores every completion with "prompt token IDs, sampled response token IDs, finish reason, and log probabilities" ({{arXiv 2605.24220|https://arxiv.org/abs/2605.24220}}); LEGO-RL captures raw generation streams in-process and recomputes log-probabilities trainer-side "even under harness-side compaction or re-serialization" ({{arXiv 2608.17393|https://arxiv.org/abs/2608.17393}}).

Why compaction makes this harder
A harness that compacts its context ({{Context engineering|n:3f15c17b0d0d811292cee46514370431}} section 4 forces one on purpose) changes the prompt in the middle of a rollout: the tokens after the compaction were sampled from a different context than the one a naive "render the whole conversation" would produce. Each model call is then its own training sample (prompt as the harness actually sent it, reply as sampled), which is what a per-call completion record gives you for free.
Depth: the frameworks say so in their own docs
verl, Agent Loop docs"the token_ids from apply the final messages may not equal to the token_ids by concat prompt_ids and response_ids in each turn ... This inconsistency is not a big problem for serving/agent system, but is critical to RL training."
SkyRL, inference server base class (commit 68a4f44)decoding the sampled ids reproduces the text, "but the reverse is not guaranteed, since there are multiple ways to represent the same text with tokens. Therefore, for multi-turn generation, please use token-in-token-out to ensure correctness."
Polar (arXiv 2605.24220)the gateway "stores a completion record containing the request messages, response messages, prompt token IDs, sampled response token IDs, finish reason, and log probabilities", and the loss mask is "one on tokens copied from sampled responses and zero on tokens copied from canonical interstitials".
