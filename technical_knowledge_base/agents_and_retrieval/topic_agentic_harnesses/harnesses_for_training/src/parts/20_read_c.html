2. An RL environment from zero

Reinforcement learning (RL) trains a policy (here, the model) by letting it act, scoring the result, and making the actions that led to high scores more likely. It needs an environment: something that starts in a state, accepts an action, answers with an observation, and at the end hands out a reward. One run from start to finish is an episode, in LLM work a rollout ({{Topic: rl|n:3c65c17b0d0d8195a6c6c11ad093c16e}} teaches these from the beginning). For a coding agent, almost every part of that environment is something the harness already does:

Fail-to-pass and pass-to-pass. SWE-bench's two test lists are worth copying exactly. Run every check against the buggy repository first: the checks that fail there are the FAIL_TO_PASS set (the fix must flip them), the ones that pass are PASS_TO_PASS (the fix must not break them). Compute them by running, not by deciding which tests "belong" to the bug: the off-by-one bug in top_words (task T04) also breaks the tie-ordering and command-line checks, so its fail-to-pass list has six checks, not two. Every task's list is in the {{Environment lab|#t-env}}.

Why the verifier runs outside the workspace. The tests the agent sees live in its workspace, which the agent can edit; a verifier that ran them would reward a rollout that weakened a test. So the verifier copies only the textstats/ package out, ignores the workspace's tests/, and runs its own checks in a container the agent never touched. Depth: the verifier command, and how published environments get their tasks
docker run --rm --network none --memory 256m \
  -v <workspace>:/work:ro -v <hidden checks>:/hidden:ro \
  python:3.13-slim python3 -B /hidden/hidden_tests.py /work      # prints {"check name": true/false, ...}

Two design choices sit under every published environment; the table at the end of this block (SWE-Gym, SWE-smith, R2E-Gym, SWE-rebench and others) shows where each landed. Where tasks come from: real issues and their fixing commits (SWE-Gym's 2,438 instances took about 200 annotation hours), bugs injected into a repository until tests fail (SWE-smith, and this page), or commits back-translated into issue text (R2E-Gym). How isolation is paid for: an image per task, an image per repository, or no container at all.

How the published SWE environments are built

Common recipe across these: (1) task = repo snapshot at the pre-fix commit plus a task statement (real issue, or back-translated / synthesized from a commit or injected bug); (2) environment = container image per task (SWE-Gym, R2E-Gym), per repo (SWE-smith), or container-free sandbox (SWE-MiniSandbox); (3) verifier = fail-to-pass tests that must flip plus pass-to-pass tests that must stay green; (4) reward = binary 1/0 on the test run with a time limit (DeepSWE: 5 min), or patch similarity without execution (SWE-RL), or a model judge (Dockerless); (5) rollout harness = the scaffold the policy acts in (OpenHands, SWE-agent, R2E tools, or, in 2026, the production harnesses themselves via LLM-call proxying: Polar, LEGO-RL, Composer 2).

Predict: the bash harness's container has no network. Which of these still works inside it: python3 tests/test_core.py, pip install pytest, sed -i?
The tests and sed -i work (Python and GNU sed are in the image); pip install fails, because it needs the network. That is why the tests here need nothing beyond the standard library, and why real environments bake every dependency into the image before the rollout starts (SWE-Gym's images total about 6 TB).
