2. An RL environment from zero

Reinforcement learning (RL) trains a policy (here, the model) by letting it act, scoring the result, and making the actions that led to high scores more likely. It needs an environment: something that starts in a state, accepts an action, answers with an observation, and at the end hands out a reward. One run from start to finish is an episode, or in LLM work a rollout. ({{Topic: rl|n:3c65c17b0d0d8195a6c6c11ad093c16e}} teaches these from the beginning; here they get concrete.)

For a coding agent, almost every part of that environment is something the harness already does. Mapping the words onto textstats-gym:

RL wordIn a coding environmentIn textstats-gym
Initial stateA repository at the commit before the fix, plus a task statementThe clean library with one to three bugs planted by exact text replacement, and an issue-style prompt
ResetA fresh copy and a fresh sandbox, so rollouts cannot see each otherA new workspace folder and a new python:3.13-slim container with --network none and 512 MB of memory, mounted at /work
Action spaceThe harness's toolsOne bash tool, or four file tools: the harness is the action space
ObservationThe tool's result as the harness formats itCommand output clipped to 3,000 characters (head and tail), exit code appended
Episode endThe model stops calling tools, or a cap is hitNo tool call in a reply, or 16 model calls
VerifierTests that must flip from failing to passing, and tests that must stay green20 checks (9 the agent can see, 11 held out) run in a second, fresh container that mounts the workspace read-only
RewardUsually 1 if the verifier passes, else 0Binary (all 20 checks) and partial (fraction of checks): section 3

Fail-to-pass and pass-to-pass. SWE-bench's two test lists are worth copying exactly. Run every check against the buggy repository first: the checks that fail there are the FAIL_TO_PASS set (the fix must flip them), the ones that pass are PASS_TO_PASS (the fix must not break them). Computing them by running, rather than by deciding which tests "belong" to the bug, matters: the off-by-one bug in top_words (task T04) also breaks the tie-ordering and command-line checks, so its fail-to-pass list has six checks, not two. The full list per task is in the {{Environment lab|#t-env}}.

Why the verifier runs outside the workspace. The tests the agent sees live in its workspace, which the agent can edit. A verifier that ran them would reward a rollout that weakened a test. So the verifier copies only the textstats/ package out of the workspace, ignores the workspace's tests/, and runs its own checks in a container the agent never touched. Containers are cheap at this size: a container started in s and a full verifier run took s on this laptop (Docker 20.10.17, five timings).

docker run --rm --network none --memory 256m \
  -v <workspace>:/work:ro -v <hidden checks>:/hidden:ro \
  python:3.13-slim python3 -B /hidden/hidden_tests.py /work      # prints {"check name": true/false, ...}

Two design choices sit under every published environment, and the atlas tab's table of them ({{Harness atlas|n:3c65c17b0d0d81d881a8fe98b4cff7bb}}, "How the published SWE environments are built": SWE-Gym, SWE-smith, R2E-Gym, SWE-rebench and others) shows where each one landed. Where tasks come from: real issues and their fixing commits (SWE-Gym's 2,438 instances took about 200 annotation hours), bugs injected into a repository until tests fail (SWE-smith, and this page), or commits back-translated into issue text (R2E-Gym). How isolation is paid for: an image per task, an image per repository, or no container at all. This page plants bugs because it makes the answer key exact: we know the correct code, so every rollout's diff can be judged against it.

Predict: the bash harness's container has no network. Which of these still works inside it: python3 tests/test_core.py, pip install pytest, sed -i?
The tests and sed -i work (Python and GNU sed are in the image); pip install fails, because it needs the network. That is why the tests here need nothing beyond the standard library, and why real environments bake every dependency into the image before the rollout starts (SWE-Gym's images total about 6 TB).
