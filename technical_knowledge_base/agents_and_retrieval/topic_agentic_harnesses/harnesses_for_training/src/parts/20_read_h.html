7. Self-improving harnesses: a search loop with a noisy ruler

If the harness moves the score (section 1), a program can search over harnesses: propose a change (a prompt line, a tool, a context rule, a whole new loop), score it on tasks, keep it if the score went up, repeat. In 2026 a run of papers did this with a strong model as the proposer. They differ in what they change, who proposes, and above all which tasks the score comes from.

One row per paper, each from its paper page in this knowledge base, whose "How much to believe" section carries the checks and corrections; the {{Self-improvement|#t-self}} tab has the full comparison with every field.

The catch is statistical before it is anything else. Each candidate's score is a measurement on a few dozen tasks, with noise of several points. Keep the best of many noisy measurements and the winner's measured gain is biased upward even if no candidate is truly better: the winner's curse. Repeat it over ten rounds and the visible score climbs while the true one wanders. The animation below is a simulation (no model involved), with noise set from the spread of our own rollouts.

The papers see the same pattern in real runs. HarnessDev's visible score and its held-out score moved in the same direction in only 34 of 64 version changes, and 27 of the 64 gains sat inside a noise band of ±4.75 points ({{HarnessDev|n:3d45c17b0d0d81cd9883f783840e013f}}). RRSI regularises the loop (an annealed edit budget, a critic that sent back 4 drafts for leaking task-specific answers, a stability floor, a cost rule); unregularised evolution scored 92.8 on its own tuning split and 40.3 out of distribution, RRSI's out-of-distribution gains were +1.8 to +4.7 (mean 3.6), each within about one standard error ({{RRSI|n:3e95c17b0d0d81dbb1a5e660ed019c8a}}). And a harness tuned with one model can fail with another: HarnessDev's best code harness, written by Opus 4.8, fell from 69.3 to 33.0 on SWE-Pro when Gemini executed it, because it had hard-coded a 120-step limit.

How to read a self-improving-harness claim
  • Which tasks produced the score the loop optimised, and which tasks produced the score reported? (StateM's 92.1% is on the 89 tasks it was tuned on; only BusinessBench is held out.)
  • How many runs, and what is the noise band of one evaluation? (Every search arm in these papers is a single run.)
  • Was the executing model the one the search used? (SoL-Pi checked with Opus 5, which its search never saw: 94.3% of Pi's score.)
  • What did the search itself cost? (Rarely reported: SoL-Pi's more than 3,000 runs are not priced.)
  • Does the loop store anything the reward can reach? (Prime Agent's harness saved a reward hack as a skill.)
Go deeper: each paper page has its own live toy: HarnessDev's "Replay the evolution runs", RRSI's "Replay the released runs" and its keep-the-best toy, SoL-Pi's "Replay a session", JIT-Agent's "Score a group of harnesses". {{Eval statistics|n:3ef5c17b0d0d8187a7b4e5b4ec4a546d}} for how many tasks a difference needs.

8. In production: environments, frameworks, harness-native RL

Everything above, at scale, is a set of services: a task store, a sandbox fleet, an inference engine that records tokens, a verifier service, and a trainer. The open frameworks now share one vocabulary (dataset of tasks, harness or agent, verifier, reward), and the newest ones treat a production harness as a black box behind a proxy.

Versions and licences from each project's GitHub releases and PyPI on 6 October 2026; definitions quoted from the README or docs linked.

Training inside the product harness. If a model is deployed in Claude Code or Codex, training it in a different scaffold teaches it the wrong tools. LEGO-RL (OpenHands SDK, Claude Code, OpenCode) and Polar (Codex, Claude Code, Qwen Code, Pi) intercept the harness's model calls and train inside unmodified harnesses; their before-and-after numbers per harness, and Cursor's statement that Composer 2 was trained in its shipping harness, are in the parent's {{Harness atlas|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} ("Harnesses for training"). The lesson from section 1 applies twice: a score after RL belongs to the model, the harness it was trained in, and the harness it was tested in.

Infrastructure numbers worth knowing. DeepSeek's DSec runs about 3 million sandboxes a day on about 160 nodes, over 5,000 created per second, and its sandboxes read only 4.2 to 13.3% of an image, which is why lazily loaded layers beat pulling whole images (self-reported; {{DSec|n:3e95c17b0d0d81bd927be047bb0d7b0b}}). DeepSWE trained Qwen3-32B with RL alone on 4,500 R2E-Gym problems, 64 H100s for 6 days, reaching 42.2% Pass@1 on SWE-bench Verified ({{blog|https://www.together.ai/blog/deepswe}}).
