7. Self-improving harnesses: a search loop with a noisy ruler

If the harness moves the score (section 1), a program can search over harnesses: propose a change (a prompt line, a tool, a context rule, a whole new loop), score it on tasks, keep it if the score went up, repeat. In 2026 a run of papers did this with a strong model as the proposer. They differ in what they change, who proposes, and above all which tasks the score comes from.

One row per paper, each from its paper page in this knowledge base, whose "How much to believe" section carries the checks and corrections; every field is in the closed comparison below.

The catch is statistical before it is anything else. Each candidate's score is a measurement on a few dozen tasks, with noise of several points. Keep the best of many noisy measurements and the winner's measured gain is biased upward even if no candidate is truly better: the winner's curse. Repeat it over ten rounds and the visible score climbs while the true one wanders. Predict how far apart the two lines end after ten rounds, then step; the simulation involves no model, and its starting rate is the local model's overall rate here.

Keeping the best noisy score inflates the gain; a held-out guard keeps the two lines together
Rig the search yourself: candidates, tasks, effect spread, rounds

Each round proposes several candidate harnesses whose true success rate differs from the current one by a small random amount; each is scored on a fixed set of pass/fail tasks; the loop keeps the best candidate if its score beats the current measured score. The guarded rule also re-scores the winner on a fresh held-out set and keeps it only if that gain exceeds two standard errors. Lines are averages over 300 simulated searches; the shaded band is the middle 80%.

The papers see the same pattern in real runs. HarnessDev's visible score and its held-out score moved in the same direction in only 34 of 64 version changes, and 27 of the 64 gains sat inside a noise band of ±4.75 points ({{HarnessDev|n:3d45c17b0d0d81cd9883f783840e013f}}). RRSI regularises the loop (an annealed edit budget, a critic that sent back 4 drafts for leaking task-specific answers, a stability floor, a cost rule); unregularised evolution scored 92.8 on its own tuning split and 40.3 out of distribution, while RRSI's out-of-distribution gains were +1.8 to +4.7 (mean 3.6), each within about one standard error ({{RRSI|n:3e95c17b0d0d81dbb1a5e660ed019c8a}}). And a harness tuned with one model can fail with another: HarnessDev's best code harness, written by Opus 4.8, fell from 69.3 to 33.0 on SWE-Pro when Gemini executed it, because it had hard-coded a 120-step limit.

How to read a self-improving-harness claim
  • Which tasks produced the score the loop optimised, and which produced the score reported? (StateM's 92.1% is on the 89 tasks it was tuned on; only BusinessBench is held out.)
  • How many runs, and what is the noise band of one evaluation? (Every search arm in these papers is a single run.)
  • Was the executing model the one the search used? (SoL-Pi checked with Opus 5, which its search never saw: 94.3% of Pi's score.)
  • What did the search itself cost? (Rarely reported: SoL-Pi's more than 3,000 runs are not priced.)
  • Does the loop store anything the reward can reach? (Prime Agent's harness saved a reward hack as a skill.)

Environments built or reshaped for agent training

Each paper in one line (moved from the parent page's Harness atlas)

  • {{HarnessDev|n:3d45c17b0d0d81cd9883f783840e013f}} (ByteDance Seed and others, 1 Sep 2026): can a model build its own harness, then improve it? Six creator models, four domains. The best generated harness averages 67.8 against 86.2 for mature human-built references; evolution feedback agreed with held-out results in only 34 of 64 changes; a code harness written by Opus 4.8 fell from 69.3 to 33.0 on SWE-Pro when another model executed it.
  • {{JIT-Agent|n:3cd5c17b0d0d81148227fbd67dc4b3ee}} (NUS, EverMind and others, 26 Aug 2026): trains a 27B model to write, repair and evolve a harness per task at inference time. GLM-5.2 goes from 74.1 to 81.8 averaged over nine agent benchmarks (+7.7; DeepSeek-V4-Flash +8.8) with a harness written for it instead of its default one, at 14.9 to 54.1% lower cost than the cheapest fixed harness on three benchmarks.
  • {{RRSI|n:3e95c17b0d0d81dbb1a5e660ed019c8a}} (Google Cloud AI Research, 21 Sep 2026): regularises recursive harness evolution (an annealed edit budget, a critic, a pruner). +14.1 points on the split the search was scored on; out of distribution, gains of 1.8 to 4.7 points on five benchmarks (mean 3.6), each within about one standard error, against +0.6 for unregularised evolution. Its own Table 2 gives 36% fewer tokens, not the 30% often quoted.
  • {{SoL-Pi|n:3e25c17b0d0d81a0bb77f16cbc898bb5}} (NVIDIA, NTU, MIT, 17 Sep 2026): auto-research loops over the Pi harness find four efficiency techniques (action execution, context compaction, observation handling, delegated reading) that cut recorded token traffic 44.7 to 49.0% at 93.7 to 94.3% of Pi's score. Single runs, no error bars.
  • {{Prime Agent|n:3cd5c17b0d0d81579a02f0431f24c6cb}} (Prime Intellect, 24 Aug 2026): an open harness that versions its own prompts, memories, skills and subagent specs across trajectories. 95.5% on ARC-AGI-3 with Opus 5 (best of three runs), against the 30% Opus 5 scored in the official ARC harness, which the paper did not run itself. Its authors report that "many harness capabilities remain underused because current models were not trained to operate them".
  • {{StateM|n:3c65c17b0d0d81899098d8153e100691}} (independent authors, 15 Aug 2026): a state-machine runbook with checked transitions around a fixed CLI agent lifts GPT-5.5 from 83.1% to 92.1% on Terminal-Bench 2.1, same weights. The runbook was developed on the same 89 tasks it is scored on: a harness-tuned upper bound.
  • {{NeoHorse-1|n:3db5c17b0d0d81e3b105e033a359ad24}} (TokenRhythm and others, 8 Sep 2026): makes the serving harness the source of the training curriculum: a router's signals order the post-training data. Qwen3.5-4B goes from 58.94 to 64.87 averaged over ten benchmarks; the evaluate, select and update loop ran once.
