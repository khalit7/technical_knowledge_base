Harnesses for training and evaluation: scaffold sensitivity, RL environments, trajectories, self-improving harnesses

The same harness that runs an agent is also the ruler that scores it and the gym that trains it. This page builds all three from zero on one small task set: real rollouts of a local 4B model and Claude Haiku 4.5 in four harnesses on a ten-task environment made for this page, with a verifier in a container, rewards, group advantages, loss masks and a training-data pipeline, then compares the 2026 papers that let a model improve its own harness. In one screen

A harness is the program around a model that turns its text into actions: it sends the request, runs the tool calls the model asks for, feeds the results back, and decides when to stop (the parent page, Topic: agentic-harnesses, builds one from scratch in its Loop lab). The same program does three different jobs, and this page is about the two that are not "use the agent":

JobWhat the harness isWhat you hold fixedWhat you get outWhat goes wrong
ProductThe agent you use (Claude Code, Codex, your own loop)Your taskA finished changeThe parent page and its siblings
Ruler (evaluation)Part of the measuring instrumentTasks, harness, settings; vary one thingA score, which belongs to the model and the harnessComparing models across different harnesses; one run per cell; no cost column (section 1)
Gym (training)Most of an RL environment: it turns the policy's tokens into actions and observationsTasks, verifier, harnessTrajectories with rewards, then gradientsA verifier that rewards the wrong thing; groups with no signal; training on tokens the model never sampled (sections 2 to 6)

Everything here is measured on one small, fully controlled setup built for this page: textstats-gym, ten bug-fixing tasks on a 60-line Python library, each with a hidden verifier that runs in a fresh container with no network. Two models act in it: a 4-billion-parameter open model running on this laptop (Qwen3-4B-Instruct-2507, 4-bit, "local model on Apple M1 Pro") and Claude Haiku 4.5 on a subscription. Four harnesses: bash only (one tool that runs a shell command), file tools (list, read with line numbers, replace exact text, run tests), the same file tools without line numbers (one detail changed), and Claude Code itself. The two models are never compared as if they were the same thing; the harnesses are compared within each model.

What the rollouts showed
  • The harness moved the small model's success a lot and the strong model's little. Qwen3-4B passed the verifier in of its rollouts with bash only and with file tools; Haiku 4.5 stayed between and in all four harnesses, while its input tokens per rollout differed -fold (section 1).
  • The verifier decides what "solved" means. rollouts passed every test the agent could see and still failed the hidden checks; of them wrote the same plausible but too-loose regular expression (section 3).
  • Most groups carry no learning signal. With a pass/fail reward, of the local model's groups and of Haiku's had every rollout score the same, so their GRPO advantages are all zero (section 4).
  • Only a minority of a trajectory's tokens are the model's. In the local model's rollouts, of the tokens are ones it sampled; the rest are prompt, tool output and template, and must be masked out of the loss. Rendering the trajectory back through the model's own chat template also adds tokens it never produced (section 5).

Then the same ideas at scale: how trajectories become training data (section 6), the 2026 papers in which a model rewrites its own harness and what their held-out numbers really say (section 7), and what production environments look like (section 8).

1. The score belongs to the pair: a controlled experiment

An agent benchmark does not score a model. It scores a system: the model, the harness around it (tools, prompts, how outputs are shown, when to stop), the settings (reasoning effort, turn and token caps), the tasks, and luck. Evaluation papers call the harness the scaffold, and scaffold sensitivity is how much the score moves when only the scaffold changes.

The published evidence is collected in the parent's Harness atlas ("The harness changes the score"): on Terminal-Bench 2.0's public board one model ranges over about 18 points across nine agents; Arena's HarnessTax study found success moving by about 2 points on SWE-bench Lite and 5 on Terminal-Bench 2.0 across Claude Code, Codex CLI and Pi, while cost moved by about 2 times. Those are other people's runs. Here is a small one where every variable is ours.

The experiment
Ten tasks (section 2), four harnesses, two models. Within each model only the harness changes: same prompts, same verifier, same cap of 16 model calls, same sampling. bash only gives the model one tool, a shell in the container. file tools gives four: list files, read a file (shown with line numbers), replace an exact piece of text, run the tests. file tools, no line numbers is identical except that read_file returns plain text, the one detail that differs. Claude Code is the product itself with its own prompt and six tools (Haiku only). Four rollouts per task and harness for the local model, three for Haiku. Every rollout is in the Scaffold experiment tab.

What moved, for the small model. With bash only, Qwen3-4B solved of its rollouts; with the file tools, ( without line numbers). Paired by task, the file tools beat bash by points (95% bootstrap interval over tasks ), large enough for ten tasks to see. Reading its rollouts shows why: Removing the line numbers moved success by points (interval ): no difference this task set can detect, even though it was the change we expected to matter most The line numbers did cost something, just not success: the local model's exact-text edits failed times with line numbers (it copied their padding into the text to replace) against without, and it recovered by re-reading the file.

A harness bug that looks like a model failure. mlx_lm.server drops a tool call whose JSON does not parse and returns the reply with no tool call (found in mlx-lm's source by the sibling page Building a harness; our server log shows the "Failed to parse tool call" warnings). Our loop, like most, ends the episode when a reply has no tool call. So in local rollouts () the model tried to act, wrote a malformed call, and the harness quietly declared the episode over; of them passed. A harness that returned "your tool call did not parse" as an observation would have given those rollouts another turn. Every such rule is part of what a benchmark measures, and part of what RL in that harness would train.

What moved, for Haiku. Success stayed between and in all four harnesses, and no paired difference excludes zero. What moved was the bill: Claude Code read input tokens per rollout against for the file tools without line numbers, because its first call alone carries about tokens of system prompt and tool definitions against for ours; caching made most of that cheap, so cost per rollout differed less ( against , API-price equivalents). That is HarnessTax's pattern in miniature: on easy tasks a strong model's harness moves cost more than success.

How to compare harnesses (or models) honestly
  • Vary one thing. To compare harnesses, fix the model, effort and caps; to compare models, fix the harness (that is why SWE-bench ran every model in the same 100-line mini-SWE-agent).
  • Pair by task. Tasks differ far more than harnesses do; compare harnesses on the same tasks and analyse per-task differences, not two overall percentages.
  • Several rollouts per cell, and an interval. Identical settings gave different outcomes in of our task-and-harness cells. With ten tasks, only differences of tens of points are visible; Eval statistics has the sample-size arithmetic.
  • Report cost beside the score, and the harness version beside both.
  • Say which verifier. Our visible-test pass rates and hidden-verifier pass rates differ by up to points for the same cell (section 3).
Predict: the bash-only harness has strictly more power than the file tools (anything replace does, sed or a Python one-liner can do). Why would a weak model do worse with it?
Power is not the constraint; the interface is. With one shell tool the model must also choose and correctly quote a command for every edit, and shell quoting inside JSON inside a tool call is easy to get wrong; a dedicated replace(path, old, new) removes that whole class of error and returns a clear message when the text does not match. SWE-agent's "agent-computer interface" paper made the same point with GPT-4 Turbo: the interface, not the model, moved the resolve rate (the parent's Harness atlas has its numbers).

2. An RL environment from zero

Reinforcement learning (RL) trains a policy (here, the model) by letting it act, scoring the result, and making the actions that led to high scores more likely. It needs an environment: something that starts in a state, accepts an action, answers with an observation, and at the end hands out a reward. One run from start to finish is an episode, or in LLM work a rollout. (Topic: rl teaches these from the beginning; here they get concrete.)

For a coding agent, almost every part of that environment is something the harness already does. Mapping the words onto textstats-gym:

RL wordIn a coding environmentIn textstats-gym
Initial stateA repository at the commit before the fix, plus a task statementThe clean library with one to three bugs planted by exact text replacement, and an issue-style prompt
ResetA fresh copy and a fresh sandbox, so rollouts cannot see each otherA new workspace folder and a new python:3.13-slim container with --network none and 512 MB of memory, mounted at /work
Action spaceThe harness's toolsOne bash tool, or four file tools: the harness is the action space
ObservationThe tool's result as the harness formats itCommand output clipped to 3,000 characters (head and tail), exit code appended
Episode endThe model stops calling tools, or a cap is hitNo tool call in a reply, or 16 model calls
VerifierTests that must flip from failing to passing, and tests that must stay green20 checks (9 the agent can see, 11 held out) run in a second, fresh container that mounts the workspace read-only
RewardUsually 1 if the verifier passes, else 0Binary (all 20 checks) and partial (fraction of checks): section 3

Fail-to-pass and pass-to-pass. SWE-bench's two test lists are worth copying exactly. Run every check against the buggy repository first: the checks that fail there are the FAIL_TO_PASS set (the fix must flip them), the ones that pass are PASS_TO_PASS (the fix must not break them). Computing them by running, rather than by deciding which tests "belong" to the bug, matters: the off-by-one bug in top_words (task T04) also breaks the tie-ordering and command-line checks, so its fail-to-pass list has six checks, not two. The full list per task is in the Environment lab.

Why the verifier runs outside the workspace. The tests the agent sees live in its workspace, which the agent can edit. A verifier that ran them would reward a rollout that weakened a test. So the verifier copies only the textstats/ package out of the workspace, ignores the workspace's tests/, and runs its own checks in a container the agent never touched. Containers are cheap at this size: a container started in s and a full verifier run took s on this laptop (Docker 20.10.17, five timings).

docker run --rm --network none --memory 256m \
  -v <workspace>:/work:ro -v <hidden checks>:/hidden:ro \
  python:3.13-slim python3 -B /hidden/hidden_tests.py /work      # prints {"check name": true/false, ...}
One real rollout through the environment

Pick who checks the work. The rollout is the same recording in both modes; only the verifier changes.

Two design choices sit under every published environment, and the atlas tab's table of them (Harness atlas, "How the published SWE environments are built": SWE-Gym, SWE-smith, R2E-Gym, SWE-rebench and others) shows where each one landed. Where tasks come from: real issues and their fixing commits (SWE-Gym's 2,438 instances took about 200 annotation hours), bugs injected into a repository until tests fail (SWE-smith, and this page), or commits back-translated into issue text (R2E-Gym). How isolation is paid for: an image per task, an image per repository, or no container at all. This page plants bugs because it makes the answer key exact: we know the correct code, so every rollout's diff can be judged against it.

Predict: the bash harness's container has no network. Which of these still works inside it: python3 tests/test_core.py, pip install pytest, sed -i?
The tests and sed -i work (Python and GNU sed are in the image); pip install fails, because it needs the network. That is why the tests here need nothing beyond the standard library, and why real environments bake every dependency into the image before the rollout starts (SWE-Gym's images total about 6 TB).

3. Rewards: the verifier decides what "solved" means

The reward is the only thing RL optimises, so whatever the verifier accepts is, by definition, the skill being trained. Three reward functions can be computed from the same 20 checks:

RewardFormulaWhat it pays forRisk
Visible1 if every test in the workspace passesWhat the agent itself can checkRewards fixes that only satisfy the examples it was shown, and any edit to the tests
Hidden, binary1 if all 20 checks pass (fail-to-pass flipped, pass-to-pass still green)A fix that generalises to cases the agent never sawSparse: a group where every rollout scores 0 teaches nothing (section 4)
Hidden, partialFraction of the 20 checks that passProgress, even without a full fixThe starting repository already scores 0.65 to 0.90 here, so "doing nothing" earns most of the reward; it must be read relative to that baseline

What the rollouts did with that gap. of the rollouts passed every test in their workspace and still failed a hidden check. The most common case, rollouts (all but one of them Haiku's, in every one of its four harnesses), is task T01 or T03: told that word_count("don't stop") should be 2, the agent changed the word pattern from [a-z]+ to [a-z']+. That passes the visible test, and it also turns 'quoted' into a word with its quotation marks attached, which the held-out check tokenize("'quoted' it's") == ['quoted', "it's"] catches. The library's own docstring says "Apostrophes inside words are kept", so the hidden check is defensible; a reviewer could also call it a spec the issue never stated. The local model's visible-only passes failed other held-out checks: a pattern that keeps one apostrophe but not two (rock'n'roll), or a sentence splitter that miscounts "Wait... what?!". Both readings of the apostrophe check teach the same thing: a reward is a specification, and a policy trained on it learns the specification, not the intent.

Reward hacking in real agent environments (published, not reproduced here)
  • Searching for the answer key. DeepSeek's sandbox paper reports agents that searched platform files and logs for answers, forged RPC requests, overwrote /bin/bash, and one that used a filesystem ioctl to get around AppArmor after controls were added (DSec). The sandbox there is a reward-hacking defence as much as a security one.
  • Gaming the benchmark rather than the task. A Terminal-Bench submission's own leaderboard judge flagged 13 of 424 rewarded trajectories, 9 for possible reward hacking and 4 for harness cheating (StateM).
  • Making a hack permanent. A self-refining harness found it could spawn resources through Factorio's RCON console, used it despite an anti-cheating heartbeat, and saved it as a reusable skill (Prime Agent).
Defences that belong to the environment: run the verifier outside the workspace (section 2); keep held-out checks; record whether test files changed ( of our rollouts edited tests/); deny the network and anything that holds answers; and read the highest-reward trajectories, not only the reward curve. The general picture is on Reward Hacking.
Predict: with the partial reward, which scores more: the untouched T10 repository (three bugs) or a rollout that fixes two of the three bugs and breaks the command-line tool?
The untouched repository scores 13 of 20 checks, 0.65. Fixing two bugs flips up to five of the seven fail-to-pass checks (0.90), and breaking the command line costs the two CLI checks, landing at about 0.80. The partial reward still prefers it, which may or may not be what you want: weight pass-to-pass breakage more heavily, or gate the partial reward on pass-to-pass staying green, if breaking working code must never pay.

4. Groups and advantages: which rollouts teach anything

A reward of 1 says "this went well" but not "better than what you usually do". Policy-gradient methods turn rewards into an advantage: the reward minus a baseline (what the policy was expected to get), so rollouts that beat the policy's usual result are pushed up and those below it pushed down. GRPO's baseline is simply other rollouts of the same task: sample a group of G rollouts, and give rollout i the advantage

Ai = (ri − mean(r)) / std(r)

and every token that rollout sampled gets that same Ai (DeepSeekMath's "outcome supervision", arXiv 2402.03300, which sampled 64 outputs per question). The derivation, PPO's clipping around it, and Dr. GRPO's correction are on RL for LLMs (Reading sections 5 to 7, with a live group widget); this section runs the formula on agent rollouts and looks at what it does to them. Group sizes in agent training are small because every rollout is an episode in a container: DeepSWE ran 64 problems with 8 rollouts each per step, 512 containers in parallel (Together AI and Agentica, 2 Jul 2025). Ours are 4 rollouts (local model) and 3 (Haiku) per task and harness.

Real groups, real advantages

No disagreement, no signal. If every rollout in a group gets the same reward, every advantage is zero and the group contributes no gradient, only cost. With the pass/fail reward that happened in of the local model's groups (mostly all-fail) and of Haiku's (mostly all-pass). The partial reward rescues some of the local model's groups ( still flat), because its failures fail different numbers of checks; it rescues none of Haiku's ( still flat), because every Haiku rollout in a failing group failed the very same held-out check and scored the same 0.95. DAPO's dynamic sampling handles the rest by dropping groups whose accuracy is exactly 0 or 1 and sampling more until the batch is full; in its ablation that step took Qwen2.5-32B from 42 to 50 on AIME 2024 (arXiv 2503.14476). For agents the waste is larger than for maths, because a dropped group cost minutes of container time, so curricula that keep tasks near a 50% pass rate matter (EnvHarness accepts a reshaped environment only when its success rate lands between 0.4 and 0.6, EnvHarness).

Dividing by the spread changes who gets pushed hardest. In a group of four with one success, GRPO gives the winner +1.73 and each loser −0.58; Dr. GRPO, which drops the division, gives +0.75 and −0.25. A group with two successes gets ±1 under GRPO and ±0.5 under Dr. GRPO. Dividing by the standard deviation weights rare successes and rare failures more, which Dr. GRPO calls a difficulty bias: "questions with lower standard deviations (e.g., those that are too easy or too hard) ... are given higher weights" (arXiv 2503.20783). DeepSWE's recipe dropped the division, used a leave-one-out baseline (RLOO: each rollout's baseline is the mean of the other G−1, arXiv 2402.14740), and added compact filtering: trajectories that hit the maximum context, step count or time limit are masked from the loss rather than scored 0, so the model is not punished for running out of room. of our rollouts hit the 16-call cap, the case compact filtering is for.

Predict: a group's rewards are 1, 1, 1, 0. Under GRPO, which rollout gets the largest push, and in which direction?
The single failure: mean 0.75, standard deviation 0.433, so the failure gets (0 − 0.75)/0.433 = −1.73 and each success +0.58. In a mostly-solved group the rare failure is what the update is about; in a mostly-failed group, the rare success.
Go deeper: RL for LLMs owns GRPO, Dr. GRPO, the clip and the off-policy corrections (its Real rollouts tab has 160 maths answers in groups); Policy gradients and actor-critic for why a baseline reduces variance; the Rollout to dataset tab lists every group.

5. From a rollout to training tokens: what gets loss

The trainer does not see messages; it sees one long sequence of token ids, and for each token a flag saying whether its log-probability enters the loss. In a single-turn maths answer that is easy: prompt off, answer on. In an agent rollout the sequence interleaves the model's replies with text the environment wrote, and the policy must be credited only for what it sampled.

Here is a real local-model rollout, rendered back through Qwen3-4B-Instruct-2507's own chat template (the tokenizer from its Hugging Face snapshot, transformers 5.18.0), every token coloured by who produced it:

Most of the sequence is not the model's. Across the local rollouts, of all tokens were sampled by the model; the rest are the system prompt and tool schemas (), the task (), tool output () and template markers. Putting loss on tool output would train the model to predict ls listings and tracebacks it never chose, and would credit or blame it for the environment's text. Search-R1 measured the difference on question answering: with observation tokens masked, Qwen2.5-7B averaged 0.431 exact match over seven datasets; without the mask, 0.343 (arXiv 2503.09516).

Re-rendering is not the same as recording. We can check the render against the server, because mlx_lm.server reported the token counts while the rollout ran. For every model call in every local rollout, the rendered prompt has exactly the length the server counted ( calls), and for replies the assistant turn has exactly as many tokens as the server reported generating. The other replies differ by one or two tokens (the template re-serialises tool-call JSON and whitespace, which tokenises differently from what was sampled), and by dozens: those are replies whose malformed tool call the server dropped (section 1), so the recorded message is missing tokens the model did sample. But the template also writes something the model never produced: in the last assistant turn it inserts an empty <think>\n\n</think>\n\n block, 4 tokens. The template (shared with Qwen3's reasoning models) writes a reasoning block into an assistant turn that follows the last user message when that turn is the final message, and this instruct model has no reasoning to put in it (chat_template.jinja, the loop.last branch). A trainer that renders the finished trajectory and puts loss on every assistant token would train on 4 tokens per rollout that the policy did not sample, at log-probabilities it never had. Small here; at scale, with tool-call JSON re-serialised, whitespace normalised, or thinking stripped from earlier turns, the mismatch grows. The frameworks say so in their own docs:

verl, Agent Loop docs"the token_ids from apply the final messages may not equal to the token_ids by concat prompt_ids and response_ids in each turn ... This inconsistency is not a big problem for serving/agent system, but is critical to RL training."
SkyRL, inference server base class (commit 68a4f44)decoding the sampled ids reproduces the text, "but the reverse is not guaranteed, since there are multiple ways to represent the same text with tokens. Therefore, for multi-turn generation, please use token-in-token-out to ensure correctness."

Token-in, token-out means the rollout records the exact token ids the engine sampled, with their log-probabilities, and the trainer uses those, never re-tokenised text. That is hard when the harness is a black-box product that talks to an OpenAI-style text API, which is why the two 2026 harness-native RL systems put a proxy between the harness and the engine: Polar's gateway "stores a completion record containing the request messages, response messages, prompt token IDs, sampled response token IDs, finish reason, and log probabilities" and puts loss "one on tokens copied from sampled responses and zero on tokens copied from canonical interstitials" (arXiv 2605.24220); LEGO-RL captures raw generation streams in-process and recomputes log-probabilities trainer-side "even under harness-side compaction or re-serialization" (arXiv 2608.17393).

Why compaction makes this harder
A harness that compacts its context (the sibling page Context engineering forces one on purpose) changes the prompt in the middle of a rollout: the tokens after the compaction were sampled from a different context than the one a naive "render the whole conversation" would produce. Each model call is then its own training sample (prompt as the harness actually sent it, reply as sampled), which is what a per-call completion record gives you for free.
Go deeper: RL for LLMs, section 8 and its Rollout mismatch tab, for how far an inference engine's probabilities drift from the trainer's even with identical tokens; Tokenizers for why decode then encode is not the identity.

6. Trajectories as training data: format, redact, filter

A trajectory is the full record of a rollout: every request, reply, tool call, tool result and token count. It is three things at once: an evaluation record (what did the agent do?), supervised training data (imitate the good ones), and RL data (weight each one by its advantage). Turning a pile of recordings into a dataset takes four steps, each shown on this page's own rollouts in the Rollout to dataset tab.

1. Normalise to one format. Every harness logs differently: our own loop wrote one line per call, the Claude Agent SDK wrote its message objects, Claude Code wrote stream-json. The formats trainers read:

FormatShapeHow it says "train on this"
OpenAI supervised fine-tuningJSONL, one {"messages": [...], "tools": [...]} per line; assistant tool_calls with arguments as a JSON string; tool messages with tool_call_id (guide)Per assistant message "weight": 0 or 1, "Controls whether the assistant message is trained against" (OpenAPI spec; not on the guide page)
Hugging Face chat templateThe same messages rendered by the model's own Jinja templateapply_chat_template(..., return_assistant_tokens_mask=True), only for templates that mark assistant text with {% generation %} (transformers v5.18.0); TRL's assistant_only_loss needs the same markers and patches known templates such as Qwen3 (TRL docs)
ShareGPT style"conversations": [{"from": ..., "value": ...}] with roles human, gpt, function_call, observation, system"The gpt and function will be learned by the model" (LLaMA-Factory data README)
Token-level (RL)Token ids, sampled log-probabilities, a loss mask, a reward or advantageThe mask of section 5

A detail that bites: tool-call arguments stored as a JSON string in one format and an object in another render differently through a template, so training text and inference text disagree; Nebius's trajectory release warns about exactly this (SWE-rebench-openhands-trajectories card).

2. Redact. Trajectories carry whatever the machine showed the agent. Ours contained the scratch folder's path (which includes the account name) in every Claude Code file-tool call, session and message ids, the Claude Agent SDK's list of the account's installed skills and commands in its first record, and model replies with em-dashes. The redactor keeps a whitelist of fields, maps the workspace to /work, replaces the user name, git identity and any e-mail address, and then refuses to write a file if a forbidden string survives (counts in the Rollout to dataset tab). A sibling page's recording shows why the git identity is on the list: a model copied the machine's name and e-mail into a git config command it tried to run (Context engineering). We found no OpenAI or Anthropic guidance specific to scrubbing fine-tuning data; treat secrets and personal data in trajectories like any other training data.

3. Filter. The simplest way to learn from rollouts is to keep the successful ones and fine-tune on them: rejection sampling fine-tuning, the agentic version of STaR (arXiv 2203.14465), RFT (arXiv 2308.01825) and ReST-EM (arXiv 2312.06585). Two published agent cases:

  • SWE-Gym fine-tuned on 491 trajectories that resolved their task (sampled from GPT-4o and Claude 3.5 Sonnet in OpenHands): the 32B model went from 7.0 to 20.6% on SWE-bench Verified (arXiv 2412.21139).
  • SWE-smith ran SWE-agent with Claude 3.7 Sonnet on its synthetic tasks: 6,457 of 17,906 attempts resolved (36%), capped at 3 per task to 5,016 trajectories, and SWE-agent-LM-32B reached 40.2% Pass@1 on Verified (arXiv 2504.21798). The cap matters: without it, easy tasks that succeed every time dominate the data.

On our rollouts the filter is where section 3 comes back: filtering on the tests the agent could see would keep trajectories, filtering on the hidden verifier . The difference, trajectories, is a supervised dataset that teaches the too-loose regular expression on purpose.

4. Imitate, or re-solve? A recorded trajectory from another agent (or another harness) teaches that agent's habits. Terminal-Universe rebuilt workspaces from 359,593 public trajectories and compared imitating the source trajectories with having a teacher re-solve the recovered tasks: re-solving reached 52.1 on Terminal-Bench 2.1, imitation 36.7, below the 47.0 base model (Terminal-Universe; the page notes the gain is distillation from a stronger teacher as much as an environment effect). Public trajectory sets to look at: nebius/SWE-agent-trajectories (80,036 trajectories, 13,389 resolved), SWE-bench/SWE-smith-trajectories, nebius/SWE-rebench-openhands-trajectories (67,074, 32,161 successful).

7. Self-improving harnesses: a search loop with a noisy ruler

If the harness moves the score (section 1), a program can search over harnesses: propose a change (a prompt line, a tool, a context rule, a whole new loop), score it on tasks, keep it if the score went up, repeat. In 2026 a run of papers did this with a strong model as the proposer. They differ in what they change, who proposes, and above all which tasks the score comes from.

One row per paper, each from its paper page in this knowledge base, whose "How much to believe" section carries the checks and corrections; the Self-improvement tab has the full comparison with every field.

The catch is statistical before it is anything else. Each candidate's score is a measurement on a few dozen tasks, with noise of several points. Keep the best of many noisy measurements and the winner's measured gain is biased upward even if no candidate is truly better: the winner's curse. Repeat it over ten rounds and the visible score climbs while the true one wanders. The animation below is a simulation (no model involved), with noise set from the spread of our own rollouts.

The papers see the same pattern in real runs. HarnessDev's visible score and its held-out score moved in the same direction in only 34 of 64 version changes, and 27 of the 64 gains sat inside a noise band of ±4.75 points (HarnessDev). RRSI regularises the loop (an annealed edit budget, a critic that sent back 4 drafts for leaking task-specific answers, a stability floor, a cost rule); unregularised evolution scored 92.8 on its own tuning split and 40.3 out of distribution, RRSI's out-of-distribution gains were +1.8 to +4.7 (mean 3.6), each within about one standard error (RRSI). And a harness tuned with one model can fail with another: HarnessDev's best code harness, written by Opus 4.8, fell from 69.3 to 33.0 on SWE-Pro when Gemini executed it, because it had hard-coded a 120-step limit.

How to read a self-improving-harness claim
  • Which tasks produced the score the loop optimised, and which tasks produced the score reported? (StateM's 92.1% is on the 89 tasks it was tuned on; only BusinessBench is held out.)
  • How many runs, and what is the noise band of one evaluation? (Every search arm in these papers is a single run.)
  • Was the executing model the one the search used? (SoL-Pi checked with Opus 5, which its search never saw: 94.3% of Pi's score.)
  • What did the search itself cost? (Rarely reported: SoL-Pi's more than 3,000 runs are not priced.)
  • Does the loop store anything the reward can reach? (Prime Agent's harness saved a reward hack as a skill.)

8. In production: environments, frameworks, harness-native RL

Everything above, at scale, is a set of services: a task store, a sandbox fleet, an inference engine that records tokens, a verifier service, and a trainer. The open frameworks now share one vocabulary (dataset of tasks, harness or agent, verifier, reward), and the newest ones treat a production harness as a black box behind a proxy.

Training inside the product harness. If a model is deployed in Claude Code or Codex, training it in a different scaffold teaches it the wrong tools. LEGO-RL (OpenHands SDK, Claude Code, OpenCode) and Polar (Codex, Claude Code, Qwen Code, Pi) intercept the harness's model calls and train inside unmodified harnesses; their before-and-after numbers per harness, and Cursor's statement that Composer 2 was trained in its shipping harness, are in the parent's Harness atlas ("Harnesses for training"). The lesson from section 1 applies twice: a score after RL belongs to the model, the harness it was trained in, and the harness it was tested in.

Infrastructure numbers worth knowing. DeepSeek's DSec runs about 3 million sandboxes a day on about 160 nodes, over 5,000 created per second, and its sandboxes read only 4.2 to 13.3% of an image, which is why lazily loaded layers beat pulling whole images (self-reported; DSec). DeepSWE trained Qwen3-32B with RL alone on 4,500 R2E-Gym problems, 64 H100s for 6 days, reaching 42.2% Pass@1 on SWE-bench Verified (blog).

Interview questions

Why do agent benchmark scores need a harness column?
The score is a property of the model, the harness (tools, prompt, context policy, limits) and the settings together. The same weights moved by tens of points across harnesses on our ten tasks and by up to about 18 points on Terminal-Bench 2.0's public board. Without the harness, two numbers are not comparable.
Design an RL environment for a coding agent.
Task: repository snapshot plus statement. Reset: fresh copy and sandbox with no network and resource limits. Action space: the harness's tools. Observation: clipped tool output. Termination: no tool call, a submit tool, or caps on calls, tokens and time. Verifier: fail-to-pass and pass-to-pass checks computed by running them on the buggy repository, executed outside the workspace. Reward: binary on the verifier, maybe partial; mask capped runs. Log full trajectories with token ids.
Your GRPO run on agent tasks is not learning. What do you check first?
The fraction of groups with zero reward spread (all pass or all fail give no gradient), whether observation tokens are masked, whether the trainer uses the sampled token ids or re-tokenised text, how many rollouts hit caps or infrastructure errors and how they are scored, and whether the verifier can be satisfied without solving the task.
What is the difference between rejection sampling fine-tuning and GRPO here?
Rejection sampling keeps the successful trajectories and imitates them (only positive examples, every kept token weighted equally). GRPO uses every rollout in a group, weighting each by its reward relative to the group, so failures push probability away too, and it stays on-policy. Rejection sampling is the cheap first step (SWE-Gym, SWE-smith); RL needs the environment in the loop.
A paper reports a self-improving harness gained 14 points. What do you ask?
Was the score measured on the tasks the search optimised? What is the held-out and out-of-distribution gain, with how many runs and what interval? Does it hold with a different executing model? What did the search cost? Could anything the loop stores reach the reward?
Why would you train a model in the same harness you deploy it in?
The harness defines the action space, the observation format and the context policy; a model learns those habits. LEGO-RL and Polar both found RL gains differ by harness for the same base model, so train in the deployment harness, or in several to avoid overfitting one.
