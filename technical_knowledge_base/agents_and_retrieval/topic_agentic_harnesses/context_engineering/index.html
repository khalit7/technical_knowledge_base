Context engineering in one picture

A model reads nothing between calls: on every step of an agent the harness rebuilds the whole request, so context engineering is choosing what goes into that one request, in what order, and what stays outside it, so that it fits, stays cacheable, and holds what the next step needs.

1. The window is a budget

Models read and write tokens, about four characters of English prose each and fewer for code and logs. The window is 200,000 tokens for Claude Haiku 4.5 and 1,000,000 for Sonnet 5.5 as Claude Code configures them (model configuration, read 5 Oct 2026). A request that does not fit is refused: "Prompt is too long" came back when this page sent Haiku a 491 KB log in one piece MEASURED.

Four numbers make the budget: the startup context S, the growth per call g (the model's last reply plus the tool result it triggered), a reply reserve (Claude Code reports a 32,000-token output cap for Haiku 4.5), and a buffer before the harness acts. Claude Code's /context prints the window by category without calling the model. In a fresh session with six tools it reported 12.6k tokens, 6.3k of system prompt and 6.3k of tool definitions; the first real call read 13,320, so its figures are estimates within about 6% MEASURED (the parent's lab measured 13,242 on 2.1.289). With the auto-compact window set to 100K, a 33k "Autocompact buffer", a third of the window, was held free MEASURED.

2. Assembly order decides the cache bill

Call 12 of an agent is call 11 plus one reply and one tool result. To read a prompt the model computes a key and a value vector per token per layer (the KV cache; how big it is per model is Long context's subject), and those vectors depend only on the tokens before them. A prompt cache keeps the computed prefix, keyed by a hash of its content, and a later request that starts with exactly the same tokens reads it back instead of recomputing. Two consequences, both about order: a match must be exact from the first token, so one changed byte early invalidates everything after it; and whatever changes most often must come last.

The same rule at production scale. Cloudflare's AI code reviewer gave every review the same long system prompt followed by review-specific text, with one breakpoint after both, so each review's first request missed. Splitting the prompt at a marker so the shared part got its own breakpoint raised the first-request cache hit rate from 14 to 26% to 91 to 99.5%; cache writes had been 43% of spend, and with this and other changes the cost per review fell from $2.43 to $0.77, 68% (Cloudflare, 19 Oct 2026; the company's own figures). Whatever many requests share needs a breakpoint of its own, placed before the first byte that differs.

Anthropic's rules, which Claude Code inherits

  • Order: the prefix is tools, then system, then messages. A changed tool definition invalidates all three; a changed system prompt, system and messages; a changed tool choice or an added image, only messages DOCUMENTED.
  • Breakpoints: a cache breakpoint (cache_control on a block) marks where an entry is written: up to four per request, or one automatic one on the last block. A read looks back from each breakpoint at most 20 block positions (consecutive tool_use or tool_result blocks count as one), so a turn that adds more than 20 blocks misses the last turn's entry unless a second breakpoint sits earlier DOCUMENTED.
  • Lifetime and price: 5 minutes by default or 1 hour, from the last use. Writing costs 1.25x the input price (5 minutes) or 2x (1 hour); reading 0.1x (0.05x on Opus 5.5). On Haiku 4.5: $1.25 or $2 per million written, $0.10 read, $1 fresh DOCUMENTED.
Minimum lengths, timing and scope, usage fields, and other providers

A prefix shorter than the model's minimum is silently not cached: 4,096 tokens for Haiku 4.5 (and Opus 4.6 and 4.5), 1,024 for Sonnet 4.5, 4.6 and 5, 512 for Sonnet 5.5 and Opus 5.5. An entry can be read only after the response that wrote it has started, so parallel requests sent at once all pay to write; caches are never shared between organisations, and on the Claude API not between workspaces DOCUMENTED. Usage fields: cache_read_input_tokens, cache_creation_input_tokens, and input_tokens, which counts only what comes after the last breakpoint. Source: prompt caching and pricing, read 5 and 6 Oct 2026.

OpenAI caches automatically from 1,024 tokens; for GPT-5.6 and later it bills reads at 0.1x and writes at 1.25x and keeps entries at least 30 minutes after last use, and a prompt_cache_key helps route related requests to the same cache on earlier models (OpenAI prompt caching, read 6 Oct 2026). Gemini caches implicitly on 2.5 and newer models with "no cost saving guarantee", and offers explicit caches with a default one-hour lifetime billed for storage time; minimums are 4,096 tokens on the 3.x models and 2,048 on 2.5 (Gemini caching, read 6 Oct 2026; its discount rate not checked here). Local servers do the same in memory: mlx_lm.server keeps a prompt cache bounded by --prompt-cache-bytes.

Rules that follow
Stable content first, volatile last; no timestamp, request id or random order in the system prompt or tool list; append only, never edit earlier messages; a fixed tool set for the whole session (Manus's "mask, don't remove": keep every tool defined and constrain which may be chosen, 18 Jul 2025); and when the prefix must change, change it once, together with compaction, so the rewrite is paid once. Claude Code 2.1.290's --system-prompt-snapshot on (the default) resends the first system prompt verbatim "until the conversation is compacted" (claude --help).

3. Tool outputs: clip, filter, page, summarise, clear

The system prompt is fixed and a few thousand tokens; tool results are unbounded, arrive every call, and stay in the history, re-read on every later call, until something removes them. A tool-output policy decides what of a result the model sees now and what it sees of it later. The parent's Trace and context lab planted a 491 KB ci.log: 6,005 lines of heartbeat noise with five relevant lines at 3,101 to 3,105. Each policy below was applied to it by a script and the result's size counted by Claude Haiku 4.5 (one call each, tools off, minus the 529 tokens of an empty prompt).

  • Summarising with one Sonnet 5.5 call: a 471-token summary that kept the five lines verbatim because it was asked to, at a cost of 304,996 tokens read and $1.23 at list price (the CLI wrote the prompt to the 1-hour cache, for nothing) MEASURED: the only policy that costs more than the raw output.
  • Clearing after use (masking): a 27-token stub on every later call; right once the model has acted on a result, useless as the first view.

Masking beats summarising as a default. On SWE-bench Verified with SWE-agent, keeping the last 10 turns' observations and replacing older ones with a placeholder roughly halved cost against an unmanaged context and matched or beat LLM summarisation's solve rate in four of five model settings (Qwen3-Coder 480B: 54.8% at $0.61 per instance masked, 53.8% at $0.64 summarised, 53.4% at $1.29 unmanaged) (Lindenbauer et al., arXiv 2508.21433, 29 Aug 2025; the four-of-five count from the JetBrains blog post, Dec 2025). Anthropic's API does it server-side: context editing's clear_tool_uses_20250919 strategy, once the prompt passes a trigger (100,000 input tokens by default), replaces the oldest tool results with a placeholder, keeps the most recent 3 tool uses, can exclude tools, and has clear_at_least because every clearing invalidates the cache and should free enough to be worth the rewrite (context editing, read 6 Oct 2026). Claude Code clears older tool outputs first when the window fills, before it compacts (how Claude Code works).

For the tools you write
Verdict first, evidence after (Python's -v output put the test results at lines 92 to 95 of about 240, which head-and-tail clipping cut in the parent's Loop lab); cap every result and say what was cut and how to get the rest; offer a search or filter parameter; keep errors in the history, since a failed attempt is information (Manus: "keep the wrong stuff in"); clear old results with a stub that names the call, so the model can rerun it.

4. Compaction, forced on purpose

Clearing keeps single results small, but the history still grows by every reply and action. Compaction replaces it: the harness asks a model to summarise the conversation, then starts a fresh window with the startup context, the summary and whatever it chooses to carry over. The designs, from crudest to most engineered:

  1. Drop the oldest turns (a sliding window): free; silently loses the task statement unless it is pinned.
  2. Clear old tool results (section 3): "one of the safest lightest touch forms of compaction" (Anthropic, 29 Sep 2025).
  3. Summarise everything into one structured message and restart from it.
  4. Summarise the older part, keep the recent tail verbatim. Claude Code 2.1.290 does this: every compaction record here carries a "preserved segment" of five messages MEASURED; the JetBrains summariser kept the last 10 turns. The common choice; Codex triggers at 90% of the window and other harnesses at other thresholds (Gemini CLI at 50%), read from source on Other coding harnesses, section 5.
  5. Edit the cache instead of the text. Every design above rewrites the prefix, so everything after the first changed token is prefilled again. Cache engineering lets the agent call drop (exclude chosen tokens' cached keys and values from attention) and repos (re-position the kept keys) instead; the serving engine must then track cache state, because the same token sequence can now have different caches. Dropping old tool responses on a rolling basis scored 1.7 points higher at 27.7% lower cost than summarising at a threshold, on the authors' benchmarks (Cache Engineering for Agents (arXiv 2610.28577)); it needs that engine, not a hosted API.
  6. On the provider's side or inside the model: the Claude API's compact_20260112 edit summarises past a trigger (150,000 input tokens by default); trained compressors and models that rewrite their own context go further (closed block below).

Compaction on the provider's side and inside the model: the API, trained compressors, models that manage their own context


Server-side. The Claude API's compact_20260112 edit (beta header compact-2026-01-12) summarises when the prompt passes a trigger, 150,000 input tokens by default and at least 50,000, takes your own instructions for the summary, and returns a compaction block that replaces everything before it; a newer on-demand form (beta compact-2026-09-04) is now the recommended one (compaction docs, read 6 Oct 2026).


Trained compressors. Cognition describes fine-tuning a smaller model whose only job is compressing history (12 Jun 2025); End-to-End Context Compression at Scale (the Latent Context Language Models paper) compresses the context into soft tokens inside the model. A lighter hybrid keeps the text summary and adds what it loses: REMORY trains a small network to append a bounded run of soft memory tokens after the summary so a frozen model continues as it would with the full history; on SummHay it approached the full-context joint score with 5.2% of the input positions, and Qwen3.8-27B and GLM-5.3-Flash repeated fewer tool outputs and made fewer tool errors on BrowseComp and Terminal-Bench 2.1 (REMORY (arXiv 2610.11287)).


The model manages its own context. A Context Language Model (CLM) is given its context as a file it may rewrite without restriction, so what to keep becomes model behaviour, and several agents' contexts become several files. Built zero-shot from existing models, CLMs beat the best harness-side strategies the authors compared: 11.4% higher accuracy with 21.5% fewer FLOPs on BrowseComp-Plus, 5% higher scores with 59% fewer FLOPs on 12-hour EdgeBench. The policy can be taught: evolved natural-language instructions added up to 35.9 points on a held-out context-management task, and online RL raised Qwen3.5-9B on BrowseComp-Plus by 47.6% over its untrained start with 12% fewer FLOPs, though a summary harness trained the same way ends within noise of it, so the trained advantage is mainly cost (Context Language Models; arXiv 2609.37725; not the Latent Context Language Models above). Training any compacting agent has a credit problem: one trajectory spans several sessions, and broadcasting one trajectory-level advantage to every session cannot tell which helped; Mosaic shapes each session's advantage by its estimated contribution and beat broadcasting on BrowseComp with Qwen3.5-4B, in compaction and subagent-forking runs, using fewer sessions (Mosaic (arXiv 2610.22174)).








5. Memory files and skills: always loaded against loaded when needed


Some instructions must reach every task (how to run the tests, what never to touch); others matter for one kind of task (how to write release notes). Anything in the startup context is paid on every call and competes for attention; anything outside must be found. Memory files are plain text loaded into every session: Claude Code reads CLAUDE.md (and, per its docs, AGENTS.md, the cross-vendor name). Skills use progressive disclosure: a folder with a SKILL.md whose short description sits in the startup context; the body is read only when the model calls the Skill tool, and files it links only if needed (the three levels in Anthropic's Equipping agents for the real world with Agent Skills, 16 Oct 2025). 6. Subagents: a second window for the reading


Some subtasks read a lot and answer briefly: "which module defines a class?" over a whole package. Done in the main loop, every file read stays in the main history. A subagent is a second agent loop with its own fresh window: the parent writes it a task, it reads, and only its final text returns as one tool result. Measured on a 30-module Python package (121 KB) with "Read every module in service/ in full ... which module defines a class, and which module has the largest number of functions?", twice without the Agent tool and twice told to delegate to one general-purpose subagent (Haiku 4.5 throughout).


A subagent keeps the parent's window at a quarter, and processes two to three times the tokens




Per run: tokens in the main loop's last request (what the parent carries forward), in the subagent's last request, and all input processed in the session (from the result's per-model usage); API-price equivalent of the whole session beside each run.


Without a subagent Haiku read all 30 files in one turn of parallel Reads and the main window ended at 62,442 and 64,533 tokens; with one, at 16,351 and 16,409, while the subagent's own window grew to 43,503 and 52,694 and then disappeared MEASURED. Cost was about the same ($0.130 and $0.134 against $0.134 and $0.139) because nearly all of it was cache reads; on a question one grep answers, the subagent only added cost: $0.057 against $0.020, 2.8x MEASURED.


So a subagent buys isolation, not savings: the parent's later calls stay small, its attention is not spent on 46,000 tokens of code it no longer needs, and it compacts later. Anthropic's guidance has subagents return "a condensed, distilled summary" of about 1,000 to 2,000 tokens (29 Sep 2025). Two traps: the subagent sees nothing of the parent's history, so the task message must carry everything; and the CLI's result.usage leaves the subagent's calls out while modelUsage includes them (measured on the parent page). When several agents must make decisions that agree, isolation becomes a coordination problem: Multi-agent patterns owns that, including Anthropic's advice to fold most subagents back into one loop that discloses skills and tools progressively, since tool choice degrades beyond 30 to 50 tool definitions.







7. Notes outside the window: state that survives


A task longer than one window or one session must leave its state where the next window can read it, and the history is not that place: compaction rewrites it and a new session starts without it.


    

  • Progress files and handoff notes. Anthropic's long-running harness has an initializer agent write a feature list (every feature initially failing) and a progress log; each later session reads them, does one feature, tests it, commits and updates the log (26 Nov 2025).   • Todo lists as recitation. Manus has the agent rewrite a todo.md as it goes, keeping the plan in the most recent part of the context, where it is least likely to be lost (18 Jul 2025); Claude Code's TodoWrite tool plays the same role.
    • 

  • A memory directory as a tool. The Claude API's memory tool (memory_20250818) gives the model file commands (view, create, str_replace, insert, delete, rename) on a /memories directory your application stores, with system-prompt text telling it to check the directory first and assume the window may be reset at any moment (memory tool, read 6 Oct 2026).     • 

  • The file system as context. Keep a pointer instead of the content: a path, a URL, a query. Manus calls the file system "the ultimate context" and makes every compression restorable this way; Anthropic calls it just-in-time context.
    •

8. Memory layers: Mem0, Zep's Graphiti, Letta


Notes (section 7) are files the agent writes and reads itself. A memory layer is a store a framework plugs in, where a model derives something smaller than the history (facts, a graph, a self-edited block) and decides what to do when new information contradicts old. Two policies define every one: a write policy (what is extracted, in what form, and whether a contradicted memory is overwritten, kept beside the new one, or closed with a date) and a read policy (who decides to look, the harness on every answer or the model when it chooses, with what query, and how many results go back into the prompt).


answer correct ⇒ fact written ∧ fact retrieved ∧ fact read correctly


Every failure in the experiment below sits at one of the three links. Checking whether the evidence reached the prompt (no model needed) separates the first two from the third.


Four ways carry knowledge across sessions, in rising machinery: paste the full history (the baseline every product must beat, while it fits); notes the agent keeps (section 7); search the raw history, which is retrieval over your own chat log (rag-and-retrieval owns the mechanics) and keeps "tests run with test_core.py" beside "the test command is now pytest"; and a memory layer, which consolidates. LangGraph's store is the bare key-value form (LangChain and LangGraph, section 10). Three designs dominate:




Facts: Mem0
Store what was learnt, not what was said: a model turns each conversation into short sentences ("User's tests run with pytest"), each embedded; before an answer the closest sentences are pasted into the prompt. Cheap to read, easy to inspect. Since v2.0.0 (16 April 2026) the open-source library is "single-pass, ADD-only": a changed fact becomes a second sentence beside the old one.


Temporal graph: Zep, Graphiti
A model turns each conversation into entities and dated relations; a newer relation that contradicts an older one closes the older one's validity window: nothing is deleted, so the graph answers both "what now" and "what before". Built for "what changed, and when".


Paging: MemGPT, Letta
The model manages its memory with tools: a small block always in the prompt plus archives it writes to and searches, like an operating system paging between RAM and disk. Nothing is stored or found unless the model decides to.

Mem0: the paper's extract-then-update loop, the 2.x library, and how it ranks


The paper (Apr 2025) and Mem0 1.x (Chhikara et al., arXiv 2504.19413, section 2.1): two phases with GPT-4o-mini. Extraction: a model sees the new message pair, a running summary and the last m = 10 messages, and lists candidate facts. Update: for each candidate the s = 10 most similar stored memories are retrieved and a model picks one operation by tool call: ADD, UPDATE ("augmentation of existing memories with complementary information"), DELETE ("removal of memories contradicted by new information") or NOOP. The store holds the current truth; a history table logs the edits. The Topic: agentic-frameworks root's Production stack tab implements this loop, showing the whole store to the update call instead of the top 10; with a Haiku writer it made 40 ADDs, 11 UPDATEs and 5 NOOPs over the twelve sessions.


The library since v2.0.0 (16 Apr 2026), run here at 2.2.1: "Single-pass, ADD-only": one call per add(), "No separate UPDATE/DELETE pass ... Hash-based deduplication prevents exact duplicates; ranking at retrieval time handles the rest" (v2.0.0 release). The call sees the 10 stored memories most similar to the new messages (their ids replaced by small integers, "anti-hallucination"), the last 10 messages of the scope, and an observation date (main.py, _add_to_vector_store). The docs: "Nothing is overwritten or deleted" (memory evaluation). Memories are scoped by user_id, agent_id and run_id; there are no "layers with promotion between layers", as an old note here claimed (docs).


Reading in 2.2.1 is hybrid (score_and_rank): a vector search over-fetches max(4 × k, 60) candidates; BM25 runs on spaCy-lemmatised text; named entities in the question boost memories linked to the same entity; candidates under 0.1 cosine similarity are dropped, and the rest ranked by


score = (cos + bm25̂ + entity boost) / (1 + 1bm25 + 0.5entity)


cos
cosine similarity of question and memory embeddings (here bge-small-en-v1.5, 384 dimensions)
bm25̂
BM25 score squashed into 0 to 1 by a sigmoid whose midpoint depends on query length
divisor
1, plus 1 if any BM25 hit, plus the entity weight 0.5 if any entity hit, so a memory found by all three signals can reach 1.0


Two limits of the open-source library. add() takes a timestamp documented as "Platform-only temporal parameter. Not supported in OSS", so the prompt's "Observation Date", the anchor for "yesterday", is the machine's current date: right in live use, wrong for every message of an imported history (this run patched the date to each session's). And the extraction system prompt alone is 7,924 tokens with the Qwen3 tokenizer, over the shared local server's limit, so the library's writes used Haiku.




Graphiti: bi-temporal edges, the add_episode pipeline, how invalidation and search work


Who is who. Zep published the design (Rasmussen et al., arXiv 2501.13956, 20 Jan 2025); its open-source engine is Graphiti (Apache-2.0, 31,489 GitHub stars on 6 Oct 2026). Zep stopped maintaining its self-hosted Community Edition on 2 April 2025 (announcement); Zep Cloud runs a proprietary engine. Graphiti 0.30.2 needs a graph database: Neo4j, FalkorDB, Amazon Neptune, or the embedded Kuzu, deprecated ("the upstream Kuzu project is no longer maintained"), which here failed on the first episode ('KuzuDriver' object has no attribute '_database'); this run used FalkorDB 4.22 in Docker.


Four timestamps per fact. The model is bi-temporal: "t'_created and t'_expired ... monitor when facts are created or invalidated in the system, while t_valid and t_invalid track the temporal range during which facts held true"; in Graphiti, created_at, expired_at, valid_at, invalid_at. In this replay every closed edge has expired_at 6 October 2026 (the day of the run) but invalid_at in September: the system's clock against the world's.


One add_episode (each session went in as one episode, the raw text kept as "a non-lossy data store", with reference_time set to its date) runs these prompts; calls for 12 episodes with Haiku: extract_nodes.extract_message (find the entities) 12, dedupe_nodes.nodes (is this "Sam" the node already there?) 11, extract_edges.edge (facts as relations, one sentence each) 12, extract_edges.extract_timestamps (valid_at and invalid_at relative to the reference time) 7, dedupe_edges.resolve_edge (which existing facts the new one duplicates or contradicts) 26, extract_nodes.extract_summaries_batch (rewrite the touched entities' summaries) 3; 71 in all.


Invalidation is a model's judgement. For each new edge Graphiti finds similar existing edges and asks a model which are duplicates and which the new fact contradicts (dedupe_edges.py); code then sets each contradicted edge's invalid_at to the new edge's valid_at, provided the old edge started earlier (resolve_edge_contradictions). An edge with no valid_at is never closed by that rule. Search combines cosine similarity over edge embeddings with BM25 and merges them by reciprocal rank fusion; the paper adds breadth-first graph search and rerankers (maximal marginal relevance, distance from a centre node, episode mentions, a cross-encoder). Only edges come back, so a detail that landed in an entity summary is invisible to it.




MemGPT and Letta: virtual context, and what is left of the server


MemGPT (Packer et al., arXiv 2310.08560, 12 Oct 2023) splits the prompt into system instructions, a working context the model edits with function calls, and a queue of recent messages; outside sit recall storage (every past message, searchable) and archival storage (what the model chose to file, searched by embedding). Past a warning threshold ("e.g. 70% of the context window") the system tells the model; at the flush threshold it evicts about half the queue into recall storage and replaces it with a recursive summary. The analogy is operating-system paging (Virtual memory). On its own Deep Memory Retrieval test GPT-4 alone with a fixed window and recursive summaries answered 32.1%, inside MemGPT 92.5%; GPT-4 Turbo 35.3% against 93.4%; Zep later reported the full conversation pasted in at 94.4%: the baseline MemGPT beat was a deliberately small window.


Letta. In Sep 2024 MemGPT became Letta; "MemGPT should refer to the original agent design pattern" (Letta blog, 23 Sep 2024). The V1 server kept memory blocks (a label such as human or persona, a text value, a character limit) always in the prompt, tools to edit them (memory_insert, memory_replace), conversation_search, archival_memory_insert and archival_memory_search, over Postgres and pgvector. Its last PyPI release, 0.16.8 (14 May 2026), is the one run here; the repository was archived on 16 Aug 2026, and from 0.32.13 (17 Sep 2026) the PyPI name letta installs Letta Code, a terminal agent whose memory is MemFS: "a git repository that belongs to the agent", root files in the system prompt every turn, other folders read on demand, no vector index by default, background "dreaming" subagents consolidating (MemFS docs, read 6 Oct 2026). That is section 7's memory-files design, run by the agent itself.


Running the archived server took three repairs: pip install letta==0.16.8 resolves today to dependency versions that break its imports (installing with dependencies as of its release date fixed that); its database layer only speaks Postgres, though its settings still mention SQLite; and the wheel ships no migrations, so the tables came from its ORM and the message sequence default was added by hand. The agent was letta_v1_agent with archival tools, an 8,192-token window, temperature 0 and the local Qwen3-4B, the only model here that can drive its tool loop over an OpenAI-compatible endpoint; each question went to a fresh conversation with the blocks copied.




The question set, the vocabulary, and how to check a memory layer before trusting it


LongMemEval's five abilities (Wu et al., arXiv 2410.10813, ICLR 2025; 500 questions over histories of about 115K tokens in setting S), used for the 25 questions here: information extraction (one fact said once, by the user or the assistant: "In the talk outline you drafted for me, what was the second point?"), multi-session reasoning ("How many times in total did the fallback kick in?", 37 in one session and 12 in another), knowledge update ("What gateway setup do we use right now?"), temporal reasoning ("On what date did the agent delete the tests folder?", said as "yesterday" on 17 September), and abstention ("When is the team offsite in Tokyo?"; it is in Lisbon). With the whole history pasted (about 1,400 tokens) Haiku got 23 of 25: it dated the deletion to the day Sam reported it and put the OpenRouter outage on the wrong Saturday.


Vocabulary. LangMem's guide splits long-term memory into semantic (facts and preferences), episodic (past experiences, summaries, few-shot examples) and procedural (how to behave: prompt rules), and memory formation into "in the hot path" (the agent saves while it talks, adding latency) and in the background (LangMem conceptual guide, read 6 Oct 2026). Mem0 and Graphiti are semantic memory formed in the background; Letta forms it in the hot path.


Before trusting a memory layer: (1) write a question set like this one on your own data, all five abilities, with the full-history baseline while history fits; (2) measure evidence before answers: if the evidence is not in the prompt, no reader model fixes it; (3) read the store after every session for a while: duplicates, wrong dates and wrongly closed facts show long before they cause a wrong answer; (4) log write failures loudly: an extraction that fails to parse must be an alert, not an empty list; (5) swap the writer model and rerun: the same design with a 4B writer lost what the Haiku writer kept.


Rehearsal. "I moved from Austin to Seattle": what does each design store? Paper-style memory updates "lives in Austin" to "lives in Seattle" (history lost unless logged); Mem0 2.x adds the new fact beside the old and relies on ranking; a temporal graph closes the LIVES_IN Austin edge at the move date and opens one for Seattle; self-managed memory edits its core block if the model notices. Only the graph answers "where did I live in March" directly. Why can memory make an assistant worse? Stale or duplicated facts outrank current ones, wrong dates are repeated with confidence, retrieved snippets crowd out the instruction, and without a "say you don't know" rule abstention questions become confident answers built from near misses. Memory for a million support users? Scope per user and account; write in the background, not the hot path; short facts with source message ids and dates; hybrid search with a small top-k; raw transcripts kept for audit and re-extraction; explicit conflict resolution; a LongMemEval-style test set with abstention and updates; users can see and delete what is stored. Bi-temporal, why? When a fact was true in the world answers "what was true then"; when the system learnt or retired it audits what the agent knew when it acted.








9. Context rot: recall decays before the window is full


A 200,000-token window does not mean 200,000 tokens used equally well. Context rot is the name that stuck: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" (Anthropic, 29 Sep 2025). A needle test hides one fact at a chosen depth in long filler and asks for it back.   • State tracking: RETRY_LIMIT = N assigned five times at random depths; "What is the value of RETRY_LIMIT at the end of the file?" needs all five, in order.

At scale the literature finds the same shape: position matters (the 75.8% to 53.8% "lost in the middle" figures are on Agentic retrieval); literal lookup saturates while tracking and non-literal tasks degrade (RULER's GPT-4, advertised at 128K, was effective to 64K; NoLiMa took GPT-4o from 99.3% to 69.7% at 32K; both on Long-context and multimodal benchmarks); and Chroma's "Context Rot" report (Hong, Troynikov and Huber, 14 Jul 2025) found performance falling with input length on 18 models even on simple tasks, faster with distractors and with needles less similar to the question. Why effective context is shorter than the window is Long context's subject. An agent's context is the worst case: the facts it needs are scattered through tool results, rarely share the question's words, and sit among near-duplicates; section 4's 130K-token session that put a note in two log files is a small instance, and the reason to keep the window lean.






10. Your own context policy, in order


For a harness of your own the levers become a short list of decisions, cheapest and safest first, each with the measurement that tells you it works.


    

  1. Lay out the request for the cache. Tools, system prompt, memory files, then the history one block per message, append only; nothing volatile before the last message. Check: from the second call on, cache reads equal the previous call's whole prompt (section 2's static rows).
    2. 

  2. Bound every tool result. A size cap with a note on what was cut and how to get the rest; verdict first; a filter parameter. Check: the largest single result in your traces, against the window.
    3. 

  3. Clear old observations. Replace results older than the last few turns with a stub naming the call; keep the model's reasoning and actions. Check: per-call input flattens instead of growing linearly; solve rate unchanged on your task set.
    4. 

  4. Load instructions on demand. A short memory file for facts every task needs, skills for procedures. Check: startup context size, and whether the skill was invoked when it should have been.
    5. 

  5. Isolate wide reading. A subagent for any subtask with a large input and a small answer, with a complete task message. Check: the parent's window at the end, and total tokens from per-model usage.
    6. 

  6. Keep state outside the window. A progress file the agent updates, re-read at start and after compaction; a memory layer only once history stops fitting. Check: kill the session halfway and see whether a fresh one resumes correctly.
    7. 

  7. Compact last, and review what it writes. Summarise the old part, keep the recent tail, re-inject the files that define the task, test the summary for invented next steps. Check: ask after compaction what you asked before (section 4's probes).
    8. 



LangChain names the same moves in four words: write (outside the window), select (pull in what is needed), compress, isolate (2 Jul 2025); the 12-factor-agents list puts "Own your context window" third; Topic: agentic-frameworks discusses when a framework owns these decisions for you. Depth: mistakes worth a second look, and rehearsal


A timestamp, a random id or a changing tool list in the prompt prefix
Every call rewrites everything after it: about 8x the input-side cost of a stable prefix per call (section 2). Put volatile values in the last message.


Trusting /context or a character count as an exact token budget
/context estimated 12.6k where the API counted 13,320; the same log is 228,000 tokens to Haiku 4.5 and 304,996 to Sonnet 5.5. Budget against the provider's own counts, per model, with a margin.


Summarising big tool outputs by default
The summarising call reads the whole output: $1.23 for a 471-token summary of the 491 KB log, while a filter kept the same five lines in 148 tokens for nothing. Filter or clear first.


Putting rules that must survive into the chat or into nested, path-scoped files
After compaction only the project-root memory file and unscoped rules come back from disk; chat instructions survive only if the summary copies them, and nested or path-scoped files return only when a matching file is read again.


Reading a passing needle test as proof of long-context reliability
Literal retrieval is the easy case (Haiku 4.5: 20 of 20 up to 114K tokens). Tracking a changing value, or finding something phrased differently from the question, fails earlier, and on small models much earlier.


"Memory layer X scores 90% on LOCOMO, so it is the best"; "memory saves tokens"
Ask who ran it, with which answer model, at what retrieval budget, on which version, against full context: the same product spans 58.44% to 80.32% on the same benchmark (section 8's table). Memory saves tokens per answer but costs model calls per conversation (one per session for Mem0, several per episode for Graphiti); below tens of thousands of tokens of history, pasting it all is cheaper and more accurate.


Interview rehearsal: six design questions


Why does prompt order matter for cost, and what order do you use? Caches match exact prefixes, so a change invalidates everything after it. Tools, system prompt and memory files first, then the history appended one message at a time, anything volatile in the last message. On Anthropic's API a changed tool definition invalidates the whole cache; a read costs 0.1x, a 1-hour write 2x.


Your agent's 40th call costs ten times its 2nd. Where do you look? Per-call usage: is the cache read the previous prompt (if not, something early changes or a turn adds more than 20 blocks past the lookback); the largest tool results; whether old observations are ever cleared; then the startup context. Compaction only if the history itself is the cost.


Masking or summarisation for a coding agent? Masking by default: no extra model call, no invented summary, half the cost and the same solve rate in four of five JetBrains settings. Summarise when old observations hold something the agent still needs that a stub cannot point back to.


When does a subagent help? When a subtask's input is large, its answer small, and the parent will not need the raw input again; it keeps the parent's window small (16K against 64K here) but processes more tokens, and sees none of the parent's history.


How would you test for context rot on your own workload? Cases from your own data at several lengths and depths, with tasks beyond literal lookup (a needle phrased differently, a value that changes, several items to collect), graded automatically, several seeds, compared with the same task short.


How do you tell a memory failure from a model failure? Check whether the evidence reached the prompt. If not, the write or read policy failed; if it did, the reader failed. Section 8's evidence column separates the two without any model.
