In one screen

A language model reads nothing between calls. Every time an agent asks it for the next step, the harness (the program around the model) builds one request from scratch and the model sees exactly that request and nothing else. Context engineering is deciding what goes into that request, in what order, and what is left out, so that the model has what it needs, the bill stays small, and the request fits.

The parent page's section 3 (Reading tab, "Context: what the model sees on each call") lists the levers; its Trace and context lab measures the startup context, the caching bill and a budget model on 22 recorded runs. This page goes one level down: how each lever works, what it costs, and what it breaks, with every lever pulled on purpose in a recorded run.

1. The window is a budget

Tokens. Models read and write tokens, pieces of words; English prose runs about four characters per token, code and logs fewer. The context window is the most tokens one request may hold, prompt and reply together: 200,000 for Claude Haiku 4.5 and 1,000,000 for Sonnet 5.5 as Claude Code configures them (model configuration, read 5 Oct 2026). A request that does not fit is refused: "Prompt is too long" is what came back when this page sent Haiku a 491 KB log in one piece MEASURED.

What fills it before you type. Claude Code's /context command prints the window's contents by category, and it works in headless mode without calling the model, so it costs nothing. In a fresh session with six tools it reported 12.6k tokens: 6.3k of system prompt and 6.3k of tool definitions MEASURED. The first real call of the same configuration read 13,320 input tokens, so /context's figures are estimates within about 6% here. The parent's Trace and context lab breaks the same startup context down by tool set (13,242 tokens on 2.1.289); the figures agree.

Four numbers make the budget. The startup context S (system prompt, tool definitions, memory files, environment), the growth per call g (the model's last reply plus the tool result it triggered), a reply reserve (room the model needs to answer; Claude Code reports a 32,000-token output cap for Haiku 4.5), and a buffer before the harness acts. With the auto-compact window set to 100K, /context showed a 33k "Autocompact buffer", a third of the window kept free MEASURED. The parent's Trace and context lab turns S, g and the number of calls into a cost model checked against its recordings; it is not rebuilt here.

Predict, then reveal. A session read five log files of 75 KB each in one turn (five parallel Read calls). The window is 200K. Did the next call fit?
Yes: the next call held 126,544 tokens, 112,953 of them new, and at the end /context said 130.7k of 200k MEASURED. Five files of 75 KB are about 113,000 tokens of log, so a sixth would have taken it near the limit in one step. Harnesses check the budget between calls, and one turn of parallel tool calls can add more than the whole buffer.

2. Assembly order, and why it decides the cache bill

The problem. An agent's calls are almost identical: call 12 is call 11 plus one reply and one tool result. Reading the same 13,000-token prefix again on every call is wasted work, and the provider charges for it unless the prefix is cached.

How a prompt cache works, from zero. To read a prompt, the model computes a key and a value vector for every token at every layer (the KV cache; the inference and serving topic owns the details). Those vectors depend only on the tokens before them, so the work done for a prefix can be kept and reused by any later request that starts with exactly the same tokens. A prompt cache is that store: the provider keeps the computed prefix for a while, keyed by a hash of its content, and a later request that matches reads it back instead of recomputing. Two consequences follow, and both are about order. A match must be exact from the first token, so one changed byte early in the request invalidates everything after it. And whatever changes most often must come last.

Anthropic's rules, which Claude Code inherits

  • Order: the cached prefix is built in the fixed order tools, then system, then messages. Changing a tool definition invalidates all three; changing the system prompt invalidates system and messages; changing tool choice or adding an image invalidates only messages DOCUMENTED.
  • Breakpoints: a cache breakpoint (cache_control on a content block) marks where an entry is written: up to four per request, or one automatic breakpoint on the last block. A read looks backward from each breakpoint for an earlier write, checking at most 20 block positions (consecutive tool_use or tool_result blocks count as one). A turn that adds more than 20 blocks therefore misses the previous turn's entry unless a second breakpoint was placed earlier DOCUMENTED.
  • Minimum length: a prefix shorter than the model's minimum is silently not cached: 4,096 tokens for Haiku 4.5 (and Opus 4.6 and 4.5), 1,024 for Sonnet 4.5, 4.6 and 5, 512 for Sonnet 5.5 and Opus 5.5 DOCUMENTED.
  • Lifetime and price: entries live 5 minutes by default or 1 hour on request, measured from the last request that wrote or read them. Writing costs 1.25x the input price (5 minutes) or 2x (1 hour); reading costs 0.1x (0.05x on Opus 5.5) DOCUMENTED. On Haiku 4.5 that is $1.25 or $2 per million tokens written and $0.10 read, against $1 fresh.
  • Timing and scope: an entry can be read only after the response that wrote it has started, so parallel requests sent at once all pay to write; caches are never shared between organisations, and on the Claude API not between workspaces DOCUMENTED.

Source: prompt caching and pricing, read 5 and 6 Oct 2026. The usage fields map directly: cache_read_input_tokens, cache_creation_input_tokens, and input_tokens, which counts only what comes after the last breakpoint.

Other providers, same principle, different knobs. OpenAI caches automatically from 1,024 tokens; for GPT-5.6 and later it bills reads at 0.1x and writes at 1.25x and keeps entries at least 30 minutes after last use, and a prompt_cache_key helps route related requests to the same cache on earlier models (OpenAI prompt caching, read 6 Oct 2026). Gemini caches implicitly on 2.5 and newer models with "no cost saving guarantee", and offers explicit caches with a default one-hour lifetime that are billed for storage time; minimums are 4,096 tokens on the 3.x models and 2,048 on 2.5 (Gemini caching, read 6 Oct 2026; its discount rate is on the pricing page and not checked here). Local servers do the same thing in memory: mlx_lm.server, used elsewhere on this page, keeps a prompt cache bounded by --prompt-cache-bytes.

The experiment: one volatile line, three places

Eleven one-call Claude Code sessions (Haiku 4.5, six tools, "Reply with the single word OK."), run a few seconds apart in the same folder. Only one thing changes: where a value that differs on every run sits. "Static" appends a fixed line to the system prompt; "time in system prompt" appends the current time there instead; "time in user message" keeps the fixed system line and puts the time in the prompt; "one tool fewer" drops Glob from the tool list.

What the bars say. Every first call with the six tools found 8,344 tokens already cached, written by earlier sessions on the same account (the tools and the fixed part of the system prompt, identical across folders). With nothing volatile, the second and third calls read all 13,310 tokens from cache and wrote nothing. With the time in the system prompt, every call rewrote the same 4,973 tokens at the 1-hour write price: the input side cost about 8x the static case. With the time in the user message, only the last 1,124 tokens were rewritten, because the volatile part comes after everything else. Dropping one tool cost the most on its first call, 13,056 tokens written and none read: tools come first, so the shared 8,344-token entry no longer matched; its second call read everything again from the new entry.

Rules that follow
Put stable content first and volatile content last; never put a timestamp, a request id or a random order in the system prompt or tool list; never edit or reorder earlier messages (append only); keep the tool set fixed for the whole session (Manus's "mask, don't remove": they keep every tool defined and constrain which ones may be chosen instead, 18 Jul 2025); and when you must change the prefix, do it once, at a point where you also shrink the history (compaction) so you pay the rewrite once. Claude Code 2.1.290 adds a switch for the first rule: --system-prompt-snapshot on, the default, records the system prompt on the first request and resends that record verbatim "until the conversation is compacted", even if a later launch passes different text (claude --help, 2.1.290).
Predict, then reveal. The parent's Loop lab harness resent the whole transcript as one growing text block. Where does its first cache miss happen?
On every call. The block that holds the transcript changes at its end each time, and an entry is keyed on the whole prefix up to a breakpoint, so no earlier entry ever matches; once the prompt passed Haiku's 4,096-token minimum the CLI wrote the whole prompt each call at 2x and read nothing (measured on the parent page). Splitting the transcript into one block per message, in order, fixes it: the new call's prefix then ends exactly where the last call's did.

3. Tool outputs: clip, filter, page, summarise, clear

The problem. The system prompt is a few thousand tokens and fixed; tool results are unbounded and arrive every call. One cat of a log can be larger than the whole window, and whatever enters the history stays there, re-read on every later call, until something removes it. A tool-output policy decides what of a result the model sees now, and what it sees of it later.

Six policies on one real result. The parent's Trace and context lab planted a 491 KB ci.log (6,005 lines of heartbeat noise with five relevant lines at 3,101 to 3,105). Here each policy is applied to that log by a script, and the token count of what the model would see is measured by sending it to Claude Haiku 4.5 (one call each, tools off, minus the overhead of an empty prompt).

Log scale: from 27 to 227,987 tokens. A filled dot means all five relevant lines are in what the model sees; a hollow dot means none are. Measured 6 Oct 2026; script src/tool_policies.py, data src/inputs/policies.json.
  • Raw: about 228,000 Haiku tokens, more than the 200K window: the CLI refused the request before sending it ("Prompt is too long ... ~228537 tokens (limit 200000)") MEASURED. The same bytes are 304,996 tokens to Sonnet 5.5, whose tokenizer splits this log into a third more pieces MEASURED: a budget in tokens depends on the model.
  • Claude Code's own caps DOCUMENTED: a shell command that succeeds and prints more than about 30,000 characters reaches the model as a file path plus the first 2,000 characters; a failing one as a head-and-tail excerpt of about 10,000 characters; a Read of a file over its token limit returns a first page marked "PARTIAL view" with how to read more (tools reference, read 6 Oct 2026). On this log both shell cases cost 972 and 4,675 tokens and both miss the five lines, which sit in the middle. They are safety nets, not answers: they turn a flood into a cheap message that says where the rest is, and the model must search next. In the Trace and context lab's recordings that is what Haiku and Sonnet did.
  • Head and tail by lines (the Loop lab's naive clip): 1,139 tokens, misses them for the same reason.
  • Paging: 2,000 numbered lines per page cost 80,295 tokens, and the lines are on page 2. Paging bounds one result; it does not find anything.
  • Filtering: dropping heartbeat lines leaves 148 tokens with all five lines and a count of what was dropped. Best by far, but someone has to know the filter: the model writes it (grep), or the tool's author builds it in (return failures first, say what was cut).
  • Summarising: one Sonnet 5.5 call over the whole log returned a 471-token summary that kept all five lines verbatim, because it was asked to. That call read 304,996 tokens and cost $1.23 at list price (the CLI wrote the prompt to the 1-hour cache, at 2x, for nothing) MEASURED. Summarising is the only policy here that costs more than the raw output.
  • Clearing after use (masking): a 27-token stub on every later call. This is what you want once the model has acted on a result; it is useless as the first view.

Masking against summarising, at scale. JetBrains researchers compared the two on SWE-bench Verified with SWE-agent: keeping the last 10 turns' observations and replacing older ones with a placeholder roughly halved cost against an unmanaged context and matched or beat summarisation's solve rate in four of five model settings (Qwen3-Coder 480B: 54.8% at $0.61 per instance masked, 53.8% at $0.64 summarised, 53.4% at $1.29 unmanaged) (Lindenbauer et al., arXiv 2508.21433, 29 Aug 2025; the JetBrains blog post, Dec 2025, gives the four-of-five count). The cheapest policy that keeps the agent's reasoning and actions and drops old observations is a strong default.

Clearing as an API feature. Anthropic's context editing does the masking server-side: the clear_tool_uses_20250919 strategy, once the prompt passes a trigger (100,000 input tokens by default), replaces the oldest tool results with a placeholder, keeps the most recent 3 tool uses, can exclude tools, and has a clear_at_least setting because every clearing invalidates the cache and should free enough to be worth the rewrite (context editing, read 6 Oct 2026). Claude Code clears older tool outputs first when the window fills, before it compacts (how Claude Code works).

For the tools you write (goal 1: your own harness)
Return the verdict first and the evidence after (Python's -v output put the test results at lines 92 to 95 of about 240, which head-and-tail clipping cut in the parent's Loop lab); cap every result and say what was cut and how to get the rest; offer a search or filter parameter so the model can ask for less; keep errors in the history, since a failed attempt is information (Manus calls this "keep the wrong stuff in"); and clear old results by replacing them with a stub that names the call, so the model can rerun it.

4. Compaction, forced on purpose

The problem. Clipping and clearing keep single results small, but the history still grows by every reply and every action. Near the limit, something must replace it. Compaction is that replacement: the harness asks a model to summarise the conversation so far, then starts a fresh window holding the startup context, the summary, and whatever it chooses to carry over.

Five designs, from crudest to most engineered

  1. Drop the oldest turns (a sliding window). Free and simple; it silently loses the task statement unless that is pinned.
  2. Clear old tool results (section 3): Anthropic's engineering post calls tool-result clearing "one of the safest lightest touch forms of compaction" (29 Sep 2025).
  3. Summarise everything into one structured message and restart from it.
  4. Summarise the older part, keep the recent tail verbatim. Claude Code 2.1.290 does this: every compaction record in our runs carries a "preserved segment" of five messages next to the summary MEASURED. The JetBrains study's summariser kept the last 10 turns the same way.
  5. Server-side compaction. The Claude API can do it for you: the compact_20260112 edit (beta header compact-2026-01-12) summarises when the prompt passes a trigger, 150,000 input tokens by default and at least 50,000, takes your own instructions for the summary, and returns a compaction block that replaces everything before it; a newer on-demand form (beta compact-2026-09-04) is now the recommended one (compaction docs, read 6 Oct 2026). Further out: Cognition describes fine-tuning a smaller model whose only job is compressing history (12 Jun 2025), and End-to-End Context Compression at Scale compresses the context into soft tokens inside the model.

Forcing Claude Code to compact

The parent's Trace and context lab never saw a compaction: its sessions never came near a 200K window. Two ways force one. Manual: claude -p --input-format stream-json keeps one session open and reads user messages from standard input, one per line, so a script can send the task, then /compact, then a question, waiting for each turn's result record before sending the next (the SDK documents /compact and its compact_boundary message: commands in SDK sessions). Automatic: --autocompact 100000 shrinks the window Claude Code compacts against to its 100K minimum, and the task makes the agent read five 75 KB log files. (Setting CLAUDE_CODE_AUTOCOMPACT_PCT_OVERRIDE=16 as well left /context's buffer at 33k, so size, not the percentage, triggered it here MEASURED.)

Every session started with a first message that also said "note two things for later: the reviewer for this change is Ilse Marten, and the ticket number is TS-4471", and the folder's CLAUDE.md held the line "Release codename: KESTREL." After the task, each was asked, with tools forbidden, to recall those facts, quote what the test runner first printed, and say what it changed.

What happened. The three manual compactions took 18,968, 17,969 and 18,390 tokens down to 2,258, 2,357 and 2,472 in 23 to 32 seconds, and the turn that ran each cost $0.015 to $0.021 at list price MEASURED. The automatic one first failed ("too_few_groups": right after the five parallel reads the history had only one exchange to summarise), let the next call go out at 126,531 tokens, then succeeded: 127,242 tokens down to 1,971 in 27.7 seconds MEASURED. That summarising call read about 127,959 tokens, 113,729 of them as fresh input rather than from cache (derived: the session's input in modelUsage minus every streamed call), about $0.12 of input at list price, half of what writing the five logs to the cache had cost: on a big history the summarising call is a large cost of its own. The first call after every compaction read the startup prefix (about 12,200 tokens) from cache and wrote the rest again: the summary is a new prefix.

What survived (scores in the table, judged by hand against the recordings). The chat facts, the reviewer and ticket, survived every compaction: the summary has a section "All user messages" that copies them. The CLAUDE.md codename survived too, but not through the summary: Claude Code re-reads the project CLAUDE.md from disk after compacting. The change itself survived, with code snippets. What went was the verbatim tool output. All three uncompacted controls said correctly that the runner printed only "FAIL" lines and no assertion message; of the three manual compactions, two said they no longer had it and one confidently quoted its own later diagnostic output as what the tests printed. The automatic run answered (b) correctly, and the large uncompacted run, at 130K tokens, put the maintainer note in two log files when it was in one. One run of each: these show what can happen, not rates.

Read the summary: it can invent the next step
Claude Code's summary has nine fixed headings, from "1. Primary Request and Intent" to "9. Optional Next Step", and ends with an instruction to the model: "Continue the conversation from where it left off without asking the user any further questions ... Pick up the last task as if the break never happened." In two of the three manual runs the summary listed a git commit under "Pending Tasks". Nobody asked for one: the agent had tried git init on its own and the permission layer refused it. In the automatic run the summary merged an unrelated log line into the plan: "Identify and remove/fix any Python 3.8 compatibility code that breaks in 0.2". The agent in that run ignored the false lead and fixed the real bugs; the next one might not. Compaction is a model call writing instructions to the next model call, so it deserves the same review as any prompt. Claude Code lets you steer it (/compact focus on ...), and a PreCompact hook can save state first.

What Claude Code restores after compacting, per its context window page (read 6 Oct 2026): the system prompt and output style still apply; the project-root CLAUDE.md, unscoped rules and auto memory are re-injected from disk; a fresh git status is read; a plan written in plan mode is re-injected; path-scoped rules and nested CLAUDE.md files are not (they reload when a matching file is read again); up to five recently modified files are re-read, and one over 5,000 tokens comes back as a path only; invoked skill bodies are re-injected, at most 5,000 tokens each and 25,000 in all; output that hooks added earlier is summarised with everything else.

5. Memory files and skills: always loaded against loaded when needed

The problem. Some instructions must reach the model on every task (how to run the tests, what never to touch); others matter only for one kind of task (how to write release notes). Anything in the startup context is paid for on every call of every session and competes for attention; anything not there must be found.

Memory files are plain text the harness loads into every session: Claude Code reads CLAUDE.md files (and, per its docs, AGENTS.md, the cross-vendor name other harnesses use). Skills use progressive disclosure: a skill is a folder with a SKILL.md whose short description sits in the startup context; the body is read only when the model calls the Skill tool for it, and files the body links are read only if needed. Anthropic describes the three levels (metadata always, SKILL.md when relevant, linked files on demand) in Equipping agents for the real world with Agent Skills (16 Oct 2025). Who loads which file in what order, and the rule syntax, belong to Claude Code, taken apart; here the question is only what each costs in the window.

The same text, both ways. A 40-rule release-notes procedure (3,834 bytes) was put in a project's CLAUDE.md, and separately in .claude/skills/release-notes/SKILL.md with a one-sentence description. /context in fresh sessions:

Startup context by category, Claude Code 2.1.290, Haiku 4.5, tools Read, Edit, Write, Bash, Grep, Glob and Skill, from /context (estimates). The Skills row is the descriptions of 14 skills that ship with Claude Code (about 1.7k tokens) plus ours.

As CLAUDE.md the procedure costs about 1,000 tokens on every call; as a skill, about 40 until it is used MEASURED. Asked to "Write the release notes for textstats version 0.2", Haiku called the Skill tool on its first call, and the next call wrote 1,361 new tokens to the cache: the body, prefixed with the skill's base directory, delivered as a message in the history MEASURED. It then followed the procedure (ran the tests, listed the public functions, ended with "Reviewed-by: (pending)"). Enabling the Skill tool also changed the tool list, so that session's first call found nothing in cache and wrote all 15,584 tokens: section 2's rule again.

6. Subagents: a second window for the reading

The problem. Some subtasks need a lot of reading and return a small answer: "which module defines a class?" over a whole package. Done in the main loop, every file read stays in the main history for the rest of the session. A subagent is a second agent loop with its own fresh window: the parent writes it a task, the subagent reads, and only its final text comes back as one tool result.

Measured. A 30-module Python package (121 KB) and the question "Read every module in service/ in full ... which module defines a class, and which module has the largest number of functions?", twice without the Agent tool and twice told to delegate the reading to one general-purpose subagent (Haiku 4.5 throughout).

Top two rows per run: tokens in the main loop's last request (what the parent carries forward) and in the subagent's last request. Third row: all input tokens processed in the session, from the result's per-model usage. Right column: API-price equivalent of the whole session.

Without a subagent, Haiku read all 30 files in one turn of parallel Read calls, and the main window ended at 62,442 and 64,533 tokens. With one, the main window ended at 16,351 and 16,409; the subagent's own window grew to 43,503 and 52,694 and then disappeared MEASURED. Total tokens processed went up two to three times (the subagent re-reads its growing history on each of its calls), yet the cost was about the same ($0.130 and $0.134 against $0.134 and $0.139), because nearly all of it was cache reads. On a question one grep answers, the subagent only added cost: $0.057 against $0.020 MEASURED.

So a subagent buys isolation, not savings: the parent's later calls stay small, its attention is not spent on 46,000 tokens of code it no longer needs, and it compacts later. Anthropic's guidance has subagents return "a condensed, distilled summary" of about 1,000 to 2,000 tokens (29 Sep 2025). Two traps: the subagent sees nothing of the parent's history, so the parent's task message must carry everything it needs; and the CLI's result.usage leaves the subagent's calls out, while modelUsage includes them (measured on the parent page). When the work is several agents making decisions that must agree, isolation turns into a coordination problem: Multi-agent patterns owns that question.

7. Notes outside the window: state that survives

The problem. A task longer than one window, or one session, must leave its state somewhere the next window can read it. The history is not that place: compaction rewrites it (section 4) and a new session starts without it.

  • Progress files and handoff notes. Anthropic's long-running harness has an initializer agent write a feature list (every feature initially failing) and a progress log; each later session reads them, does one feature, tests it, commits and updates the log (26 Nov 2025). Git history is part of the note: the commit messages say what was done.
  • Todo lists as recitation. Manus has the agent rewrite a todo.md as it goes, which keeps the plan in the most recent part of the context, where it is least likely to be lost (18 Jul 2025); Claude Code's TodoWrite tool plays the same role.
  • A memory directory as a tool. The Claude API's memory tool (memory_20250818) gives the model file commands (view, create, str_replace, insert, delete, rename) on a /memories directory that your application stores, with system-prompt text telling it to check the directory first and to assume the window may be reset at any moment (memory tool, read 6 Oct 2026). Anthropic reported, on its own evaluation, that combining the memory tool with context editing improved performance by 39% over baseline and context editing alone by 29% (29 Sep 2025; vendor-reported).
  • The file system as context. Keep a pointer instead of the content: a path, a URL, a query. Manus calls the file system "the ultimate context" and makes every compression restorable this way; Anthropic's post calls it just-in-time context.

What the research adds. Two paper pages in this knowledge base test where such memory should be curated. Just-in-Time Memory (Salesforce, 23 Sep 2026) curates an agent's memory at read time, once the task is known, rather than when the earlier task ended; untrained read-time curation beat untrained write-time memory in 15 of 17 comparisons, though most of the headline +16 points comes from RL training. Proactive Memory Agent (Meta AI, 9 Jul 2026) runs a second model beside the agent that keeps a small memory bank and injects reminders; Sonnet 4.5 went from 37.6% to 45.9% on Terminal-Bench 2.0 with an Opus 4.6 memory agent, single runs. Memory products that store facts across users and sessions (Mem0, Zep, Letta) belong to Agent memory layers.

8. Context rot: recall decays before the window is full

The problem. A window of 200,000 tokens does not mean the model uses 200,000 tokens equally well. Context rot is the name that stuck for the drop: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" (Anthropic, 29 Sep 2025). For an agent it is the reason to keep the window lean even when it is far from full, and the reason the levers above are worth their trouble.

How it is measured. A needle test hides a fact in long filler at a chosen depth and asks for it back. The classic version saturates: a needle that repeats the question's words is a text search. Harder versions remove the shared words (the model must match by meaning), or ask for something that needs several lines (a value assigned five times, where only the last counts). The benchmarks are reviewed on Long-context and multimodal benchmarks; the Needle lab runs small versions of all three on real code.

Right answers per task and haystack length, Claude Haiku 4.5 (top) and a local 4B model (bottom; local model on Apple M1 Pro, a different and much smaller model). Lengths are measured prompt tokens. Recorded 6 Oct 2026.

Claude Haiku 4.5 found the literal needle in all 20 cases and the non-literal one in all 20, from 2,201 to 113,710 tokens MEASURED. Tracking was the weak task: 28 of 32 right, and the four misses (at 2K, 16K, 16K and 64K tokens) all named an earlier assignment instead of the last; at 64K and 120K, four of the nine replies that listed the assignments found only four of the five, and still named the right final value. Within these lengths the errors did not grow with length: this run does not show rot for Haiku, and says only that lookup is easy and keeping order is not.

The local 4B model (Qwen3-4B-Instruct-2507, 4-bit, on the shared mlx_lm.server) found the literal needle in all 13 cases, from 781 to 11,622 tokens (its tokenizer counts the same code in fewer tokens than Claude's). Asked directly "In which city is the Semperoper?" it answered Dresden. With the same fact as a comment inside 1K to 12K tokens of code, it answered Dresden in 4 of 13 cases and otherwise named Berlin, Boston, San Francisco, Seattle or Portland MEASURED: the code in front of it pushed aside knowledge it has. Drew Breunig calls this context distraction, "when a context grows so long that the model over-focuses on the context, neglecting what it learned during training" (22 Jun 2025); here it took only 781 tokens. On tracking it scored 10 of 20 with no trend in length (0 of 5 at the shortest, 5 of 5 at about 5,700 tokens), every miss naming an earlier assignment: a capability limit at any length, not rot.

What this means for a harness. The literature finds the same shape at scale: position matters (the middle of a long context is recalled worst), literal lookup holds while everything else degrades, and distractors make it worse (see the Needle lab's notes). An agent's context is the worst case on all three counts: the facts it needs are scattered through tool results, rarely share the question's words, and sit among near-duplicates (the same file read twice, five similar test runs). The large uncompacted session of section 4 is a small instance: at 130K tokens it placed a note in two log files when it was in one. Keeping the window small is not only about cost.

9. Your own context policy, in order

For goal 1 (a harness of your own), the levers become a short list of decisions, cheapest and safest first. Each line says what to measure to know it works.

  1. Lay out the request for the cache. Tools, then system prompt, then memory files, then the history as one block per message, append only; nothing volatile before the last message. Check: from the second call on, cache reads should be the previous call's whole prompt (section 2's static rows).
  2. Bound every tool result. A size cap with a note on what was cut and how to get the rest; verdict first; a filter or search parameter. Check: the largest single result in your traces, against the window.
  3. Clear old observations. Replace results older than the last few turns with a one-line stub naming the call; keep the model's own reasoning and actions. Check: per-call input should flatten instead of growing linearly; solve rate unchanged on your task set.
  4. Load instructions on demand. A short always-loaded memory file for facts every task needs, skills for procedures. Check: startup context size, and whether the skill was invoked when it should have been.
  5. Isolate wide reading. A subagent for any subtask whose input is large and whose answer is small, with a task message that carries everything it needs. Check: the parent's window at the end, and total tokens from per-model usage, not the main thread's.
  6. Keep state outside the window. A progress file the agent updates, re-read at start and after compaction. Check: kill the session halfway and see whether a fresh one resumes correctly.
  7. Compact last, and review what it writes. Summarise the old part, keep the recent tail, re-inject the files that define the task, and test the summary for invented next steps. Check: ask after compaction what you asked before (section 4's probes) and compare.

LangChain's write-up names the same moves in four words, write (outside the window), select (pull in what is needed), compress, and isolate (2 Jul 2025); the 12-factor-agents list puts "Own your context window" third, and the frameworks root's Topic: agentic-frameworks discusses when a framework owns these decisions for you. The parent's Loop lab (step 4) is a working example of points 2 and 3 in about 40 lines of Python.

Common mistakes

A timestamp, a random id or a changing tool list in the prompt prefix
Every call rewrites everything after it. Measured: about 8x the input-side cost of a stable prefix per call (section 2). Put volatile values in the last message.
Trusting /context or a character count as an exact token budget
/context estimated 12.6k where the API counted 13,320; the same log is 228,000 tokens to Haiku 4.5 and 304,996 to Sonnet 5.5. Budget against the provider's own counts, per model, with a margin.
Summarising big tool outputs by default
The summarising call reads the whole output; on the 491 KB log that was $1.23 for a 471-token summary, while a filter kept the same five lines in 148 tokens for nothing. Filter or clear first; summarise when nothing simpler keeps what matters.
Treating a compaction summary as a faithful record
It is a model's paraphrase with a "next step" that the next call is told to pick up. Two of three manual summaries listed a commit nobody asked for; one run quoted the wrong output as fact afterwards. Keep rules and task facts in files that are re-read from disk.
Putting rules that must survive into the chat or into nested, path-scoped files
After compaction only the project-root memory file and unscoped rules come back from disk; chat instructions survive only if the summary copies them, and nested or path-scoped files return only when a matching file is read again.
Using a subagent to save tokens
It processed two to three times the tokens in the recordings. It saves the parent's window, not the bill; on a grep-sized question it cost 2.8x.
Reading a passing needle test as proof of long-context reliability
Literal retrieval is the easy case (Haiku 4.5: 20 of 20 up to 114K tokens). Tracking a value that changes, or finding something phrased differently from the question, fails earlier and on smaller models much earlier.

Interview questions

Why does the order of a prompt matter for cost, and what order do you use?
Prompt caches match exact prefixes, so anything that changes invalidates everything after it. Tools, system prompt and memory files first (stable), then the history appended one message at a time, with anything volatile in the last message. On Anthropic's API a changed tool definition invalidates the whole cache; a cache read costs 0.1x input, a 1-hour write 2x.
Your agent's 40th call costs ten times its 2nd. Where do you look?
Per-call usage: is the cache read the previous prompt (if not, something early changes or a turn adds more than 20 blocks past the breakpoint lookback); which tool results are largest (clip, filter, clear); whether old observations are ever cleared; then the startup context (tools and memory files). Compaction only if the history itself is the cost.
Observation masking or LLM summarisation for a coding agent?
Masking by default: in the JetBrains study it roughly halved cost and matched summarisation's solve rate in four of five settings, with no extra model call and no risk of an invented summary. Summarise when the old observations hold information the agent still needs that a stub cannot point back to.
What survives Claude Code's compaction and what does not?
System prompt, project-root CLAUDE.md and unscoped rules, auto memory, the plan file, a fresh git status, up to five recent files (paths only if over 5,000 tokens), invoked skill bodies (5,000 tokens each, 25,000 total). Lost or paraphrased: exact tool outputs, intermediate reasoning, nested and path-scoped rules until re-triggered, and anything said in chat that the summary does not copy.
When does a subagent help?
When a subtask's input is large and its answer small and the parent will not need the raw input again: wide searches, reading many files, long logs. It keeps the parent's window small (16K against 64K in the recordings) but processes more tokens in total, and it sees none of the parent's history, so its task message must be complete.
How would you test a model for context rot on your own workload?
Build cases from your own data at several lengths and depths, with tasks beyond literal lookup: a needle phrased differently from the question, a value that changes several times, several items to collect. Grade automatically, run several seeds, and compare against the same task at short length. Literal needle tests saturate and say little.

Cache lab: what a prompt cache reads, writes and charges, call by call

This simulator applies Anthropic's documented caching rules (section 2 of the Reading tab) to an agent session you configure: the request is a row of blocks in the order tools, system, messages; a cache entry is written at each breakpoint and keyed on the exact prefix up to it; a read looks back at most 20 block positions from each breakpoint for an unexpired entry; a prefix below the model's minimum is not cached; entries expire after 5 minutes or 1 hour without use. Prices are the list prices of the chosen model. It is a model of the rules, not of Anthropic's servers: block sizes are inputs you set, and the first preset's are taken from the recorded runs.

What the presets teach

  • One growing text block (the parent's Loop lab harness): the transcript is a single block whose content changes every call, so no prefix ever matches past the system prompt; once past the minimum it is written in full every call.
  • 25 blocks per turn: a turn with many separate blocks (for example a harness that splits each tool result into several text blocks) pushes the previous turn's entry out of the 20-position lookback, and the automatic breakpoint finds nothing to read. A second breakpoint at the end of the system prompt limits the damage to the history; placing one at the start of each turn would fix it.
  • Pauses longer than the lifetime: with 5-minute entries and 6-minute gaps every call rewrites everything; the 1-hour lifetime costs more per write and wins as soon as a session pauses.

Not modelled: the delay before a new entry becomes readable (it matters only for parallel requests), thinking blocks, images and tool-choice changes.

Needle lab: recall at growing lengths, on real code


A needle test hides one fact (the needle) at a chosen depth inside long filler text (the haystack) and asks for it back. Here the haystack is real Python: files of the Python 3.9 standard library concatenated in a fixed shuffled order, cut to each length. Three tasks, each harder in a different way:


    

  • Literal: the line RELEASE_PORT = 8371  # port of the textstats release box; question "What value is RELEASE_PORT set to in the file above?" The question shares the needle's words, so it is a lookup.
    • 

  • Non-literal (in the style of NoLiMa): the comment # Ops note: the textstats release box sits in the rack right next to the Semperoper.; question "In which city is the textstats release box located? Use what the file says plus general knowledge." The answer, Dresden, is not in the file; the model must find the line by meaning and add one fact it knows.
    • 

  • State tracking: RETRY_LIMIT = N assigned five times with different values at random depths; question "The file above runs top to bottom. What is the value of RETRY_LIMIT at the end of the file?" Finding one line is not enough: the model must find all five and keep the order.
    • 



Every call is one request with tools off and a one-line system prompt asking for the answer only. Claude Haiku 4.5 ran through claude -p (Claude Code adds about 420 tokens of its own); the local model, Qwen3-4B-Instruct-2507 in 4-bit MLX on an Apple M1 Pro (local model on Apple M1 Pro; not comparable with Claude as the same model), through mlx_lm.server at temperature 0. What the literature adds


These are small runs on one haystack. The published work on the same question is reviewed in depth on Long-context and multimodal benchmarks; the points that matter for an agent's context:


    

  • Position matters. In "Lost in the Middle" (Liu et al., arXiv 2307.03172, 2023), GPT-3.5-Turbo answered 20-document questions at 75.8% with the answer first, 53.8% with it in the middle and 63.2% last; the middle was below its 56.1% with no documents at all.
    • 

  • Literal lookup saturates; everything else degrades. RULER (Hsieh et al., arXiv 2404.06654) adds multi-key, multi-value, tracking and aggregation tasks; of 17 models only about half held up at 32K, and GPT-4 claimed 128K but was effective to 64K. NoLiMa (arXiv 2502.05167) removes the shared words: at 32K, 11 of 13 models fell below half their short-context score, GPT-4o from 99.3% to 69.7%.
    • 

  • Content and structure matter, not only length. Chroma's "Context Rot" report (Hong, Troynikov and Huber, 14 Jul 2025) tested 18 models and found performance falling with input length even on simple tasks, faster when the needle is less similar to the question and when distractors are present.
    •
