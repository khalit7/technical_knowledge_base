4. Compaction, forced on purpose

The problem. Clipping and clearing keep single results small, but the history still grows by every reply and every action. Near the limit, something must replace it. Compaction is that replacement: the harness asks a model to summarise the conversation so far, then starts a fresh window holding the startup context, the summary, and whatever it chooses to carry over.

Five designs, from crudest to most engineered

  1. Drop the oldest turns (a sliding window). Free and simple; it silently loses the task statement unless that is pinned.
  2. Clear old tool results (section 3): Anthropic's engineering post calls tool-result clearing "one of the safest lightest touch forms of compaction" (29 Sep 2025).
  3. Summarise everything into one structured message and restart from it.
  4. Summarise the older part, keep the recent tail verbatim. Claude Code 2.1.290 does this: every compaction record in our runs carries a "preserved segment" of five messages next to the summary MEASURED. The JetBrains study's summariser kept the last 10 turns the same way.
  5. Server-side compaction. The Claude API can do it for you: the compact_20260112 edit (beta header compact-2026-01-12) summarises when the prompt passes a trigger, 150,000 input tokens by default and at least 50,000, takes your own instructions for the summary, and returns a compaction block that replaces everything before it; a newer on-demand form (beta compact-2026-09-04) is now the recommended one (compaction docs, read 6 Oct 2026). Further out: Cognition describes fine-tuning a smaller model whose only job is compressing history (12 Jun 2025), and {{End-to-End Context Compression at Scale|n:3d45c17b0d0d81eb90a8d70a5ce84d19}} compresses the context into soft tokens inside the model.

Where other harnesses set the trigger. Design 4 is the common choice; the thresholds differ. Read from source at pinned versions on {{Other coding harnesses: Codex, Gemini CLI, opencode, Aider, OpenHands, mini-SWE-agent|n:3c65c17b0d0d819fa3cefdcd2ccff2f7}} (6 Oct 2026): Codex compacts at 90% of the window (OpenAI models on the server); Gemini CLI summarises at 50% of the window, keeps the newest 30% verbatim, then runs a self-check call on the summary; opencode summarises at the usable window and keeps a recent tail of 25% of it (2,000 to 15,000 tokens), with its "prune old tool outputs" step off by default and compaction silently off for a custom model with no limit.context; the OpenHands condenser keeps the first 4 events and summarises the middle once the history passes 80; mini-SWE-agent has none, so a run that overflows fails.

Forcing Claude Code to compact

The parent's Trace and context lab never saw a compaction: its sessions never came near a 200K window. Two ways force one. Manual: claude -p --input-format stream-json keeps one session open and reads user messages from standard input, one per line, so a script can send the task, then /compact, then a question, waiting for each turn's result record before sending the next (the SDK documents /compact and its compact_boundary message: commands in SDK sessions). Automatic: --autocompact 100000 shrinks the window Claude Code compacts against to its 100K minimum, and the task makes the agent read five 75 KB log files. (Setting CLAUDE_CODE_AUTOCOMPACT_PCT_OVERRIDE=16 as well left /context's buffer at 33k, so size, not the percentage, triggered it here MEASURED.)

Every session started with a first message that also said "note two things for later: the reviewer for this change is Ilse Marten, and the ticket number is TS-4471", and the folder's CLAUDE.md held the line "Release codename: KESTREL." After the task, each was asked, with tools forbidden, to recall those facts, quote what the test runner first printed, and say what it changed.

Each column is one model call, to scale: the tokens the call's request held (cache read + cache write + fresh). Real per-call numbers from the recordings; the compaction call itself is hidden from the stream and shown as the marker. "Same task, no compaction" is a different run of the same task, so its path differs.

What happened. The three manual compactions took 18,968, 17,969 and 18,390 tokens down to 2,258, 2,357 and 2,472 in 23 to 32 seconds, and the turn that ran each cost $0.015 to $0.021 at list price MEASURED. The automatic one first failed ("too_few_groups": right after the five parallel reads the history had only one exchange to summarise), let the next call go out at 126,531 tokens, then succeeded: 127,242 tokens down to 1,971 in 27.7 seconds MEASURED. That summarising call read about 127,959 tokens, 113,729 of them as fresh input rather than from cache (derived: the session's input in modelUsage minus every streamed call), about $0.12 of input at list price, half of what writing the five logs to the cache had cost: on a big history the summarising call is a large cost of its own. The first call after every compaction read the startup prefix (about 12,200 tokens) from cache and wrote the rest again: the summary is a new prefix.

What survived (scores in the table, judged by hand against the recordings). The chat facts, the reviewer and ticket, survived every compaction: the summary has a section "All user messages" that copies them. The CLAUDE.md codename survived too, but not through the summary: Claude Code re-reads the project CLAUDE.md from disk after compacting. The change itself survived, with code snippets. What went was the verbatim tool output. All three uncompacted controls said correctly that the runner printed only "FAIL" lines and no assertion message; of the three manual compactions, two said they no longer had it and one confidently quoted its own later diagnostic output as what the tests printed. The automatic run answered (b) correctly, and the large uncompacted run, at 130K tokens, put the maintainer note in two log files when it was in one. One run of each: these show what can happen, not rates.

Read the summary: it can invent the next step
Claude Code's summary has nine fixed headings, from "1. Primary Request and Intent" to "9. Optional Next Step", and ends with an instruction to the model: "Continue the conversation from where it left off without asking the user any further questions ... Pick up the last task as if the break never happened." In two of the three manual runs the summary listed a git commit under "Pending Tasks". Nobody asked for one: the agent had tried git init on its own and the permission layer refused it. In the automatic run the summary merged an unrelated log line into the plan: "Identify and remove/fix any Python 3.8 compatibility code that breaks in 0.2". The agent in that run ignored the false lead and fixed the real bugs; the next one might not. Compaction is a model call writing instructions to the next model call, so it deserves the same review as any prompt. Claude Code lets you steer it (/compact focus on ...), and a PreCompact hook can save state first.

What Claude Code restores after compacting, per its {{context window page|https://code.claude.com/docs/en/context-window}} (read 6 Oct 2026): the system prompt and output style still apply; the project-root CLAUDE.md, unscoped rules and auto memory are re-injected from disk; a fresh git status is read; a plan written in plan mode is re-injected; path-scoped rules and nested CLAUDE.md files are not (they reload when a matching file is read again); up to five recently modified files are re-read, and one over 5,000 tokens comes back as a path only; invoked skill bodies are re-injected, at most 5,000 tokens each and 25,000 in all; output that hooks added earlier is summarised with everything else.
