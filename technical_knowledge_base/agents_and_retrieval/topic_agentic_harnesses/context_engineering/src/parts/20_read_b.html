2. Assembly order, and why it decides the cache bill

The problem. An agent's calls are almost identical: call 12 is call 11 plus one reply and one tool result. Reading the same 13,000-token prefix again on every call is wasted work, and the provider charges for it unless the prefix is cached.

How a prompt cache works, from zero. To read a prompt, the model computes a key and a value vector for every token at every layer (the KV cache; the {{inference and serving|n:3c65c17b0d0d81c08b3bc95ff45c7b13}} topic owns the details). Those vectors depend only on the tokens before them, so the work done for a prefix can be kept and reused by any later request that starts with exactly the same tokens. A prompt cache is that store: the provider keeps the computed prefix for a while, keyed by a hash of its content, and a later request that matches reads it back instead of recomputing. Two consequences follow, and both are about order. A match must be exact from the first token, so one changed byte early in the request invalidates everything after it. And whatever changes most often must come last.

Anthropic's rules, which Claude Code inherits

  • Order: the cached prefix is built in the fixed order tools, then system, then messages. Changing a tool definition invalidates all three; changing the system prompt invalidates system and messages; changing tool choice or adding an image invalidates only messages DOCUMENTED.
  • Breakpoints: a cache breakpoint (cache_control on a content block) marks where an entry is written: up to four per request, or one automatic breakpoint on the last block. A read looks backward from each breakpoint for an earlier write, checking at most 20 block positions (consecutive tool_use or tool_result blocks count as one). A turn that adds more than 20 blocks therefore misses the previous turn's entry unless a second breakpoint was placed earlier DOCUMENTED.
  • Minimum length: a prefix shorter than the model's minimum is silently not cached: 4,096 tokens for Haiku 4.5 (and Opus 4.6 and 4.5), 1,024 for Sonnet 4.5, 4.6 and 5, 512 for Sonnet 5.5 and Opus 5.5 DOCUMENTED.
  • Lifetime and price: entries live 5 minutes by default or 1 hour on request, measured from the last request that wrote or read them. Writing costs 1.25x the input price (5 minutes) or 2x (1 hour); reading costs 0.1x (0.05x on Opus 5.5) DOCUMENTED. On Haiku 4.5 that is $1.25 or $2 per million tokens written and $0.10 read, against $1 fresh.
  • Timing and scope: an entry can be read only after the response that wrote it has started, so parallel requests sent at once all pay to write; caches are never shared between organisations, and on the Claude API not between workspaces DOCUMENTED.

Source: {{prompt caching|https://platform.claude.com/docs/en/build-with-claude/prompt-caching}} and {{pricing|https://platform.claude.com/docs/en/about-claude/pricing}}, read 5 and 6 Oct 2026. The usage fields map directly: cache_read_input_tokens, cache_creation_input_tokens, and input_tokens, which counts only what comes after the last breakpoint.

Other providers, same principle, different knobs. OpenAI caches automatically from 1,024 tokens; for GPT-5.6 and later it bills reads at 0.1x and writes at 1.25x and keeps entries at least 30 minutes after last use, and a prompt_cache_key helps route related requests to the same cache on earlier models (OpenAI prompt caching, read 6 Oct 2026). Gemini caches implicitly on 2.5 and newer models with "no cost saving guarantee", and offers explicit caches with a default one-hour lifetime that are billed for storage time; minimums are 4,096 tokens on the 3.x models and 2,048 on 2.5 (Gemini caching, read 6 Oct 2026; its discount rate is on the pricing page and not checked here). Local servers do the same thing in memory: mlx_lm.server, used elsewhere on this page, keeps a prompt cache bounded by --prompt-cache-bytes.

The experiment: one volatile line, three places

Eleven one-call Claude Code sessions (Haiku 4.5, six tools, "Reply with the single word OK."), run a few seconds apart in the same folder. Only one thing changes: where a value that differs on every run sits. "Static" appends a fixed line to the system prompt; "time in system prompt" appends the current time there instead; "time in user message" keeps the fixed system line and puts the time in the prompt; "one tool fewer" drops Glob from the tool list.

Bar length is the input tokens of the one call, split as the API reported them; the right column is the input-side cost at Haiku 4.5 list prices. Recorded 6 Oct 2026, Claude Code 2.1.290.

What the bars say. Every first call with the six tools found 8,344 tokens already cached, written by earlier sessions on the same account (the tools and the fixed part of the system prompt, identical across folders). With nothing volatile, the second and third calls read all 13,310 tokens from cache and wrote nothing. With the time in the system prompt, every call rewrote the same 4,973 tokens at the 1-hour write price: the input side cost about 8x the static case. With the time in the user message, only the last 1,124 tokens were rewritten, because the volatile part comes after everything else. Dropping one tool cost the most on its first call, 13,056 tokens written and none read: tools come first, so the shared 8,344-token entry no longer matched; its second call read everything again from the new entry.

Rules that follow
Put stable content first and volatile content last; never put a timestamp, a request id or a random order in the system prompt or tool list; never edit or reorder earlier messages (append only); keep the tool set fixed for the whole session (Manus's "mask, don't remove": they keep every tool defined and constrain which ones may be chosen instead, 18 Jul 2025); and when you must change the prefix, do it once, at a point where you also shrink the history (compaction) so you pay the rewrite once. Claude Code 2.1.290 adds a switch for the first rule: --system-prompt-snapshot on, the default, records the system prompt on the first request and resends that record verbatim "until the conversation is compacted", even if a later launch passes different text (claude --help, 2.1.290).
Predict, then reveal. The parent's Loop lab harness resent the whole transcript as one growing text block. Where does its first cache miss happen?
On every call. The block that holds the transcript changes at its end each time, and an entry is keyed on the whole prefix up to a breakpoint, so no earlier entry ever matches; once the prompt passed Haiku's 4,096-token minimum the CLI wrote the whole prompt each call at 2x and read nothing (measured on the parent page). Splitting the transcript into one block per message, in order, fixes it: the new call's prefix then ends exactly where the last call's did.
