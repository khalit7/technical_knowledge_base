9. Your own context policy, in order

For goal 1 (a harness of your own), the levers become a short list of decisions, cheapest and safest first. Each line says what to measure to know it works.

  1. Lay out the request for the cache. Tools, then system prompt, then memory files, then the history as one block per message, append only; nothing volatile before the last message. Check: from the second call on, cache reads should be the previous call's whole prompt (section 2's static rows).
  2. Bound every tool result. A size cap with a note on what was cut and how to get the rest; verdict first; a filter or search parameter. Check: the largest single result in your traces, against the window.
  3. Clear old observations. Replace results older than the last few turns with a one-line stub naming the call; keep the model's own reasoning and actions. Check: per-call input should flatten instead of growing linearly; solve rate unchanged on your task set.
  4. Load instructions on demand. A short always-loaded memory file for facts every task needs, skills for procedures. Check: startup context size, and whether the skill was invoked when it should have been.
  5. Isolate wide reading. A subagent for any subtask whose input is large and whose answer is small, with a task message that carries everything it needs. Check: the parent's window at the end, and total tokens from per-model usage, not the main thread's.
  6. Keep state outside the window. A progress file the agent updates, re-read at start and after compaction. Check: kill the session halfway and see whether a fresh one resumes correctly.
  7. Compact last, and review what it writes. Summarise the old part, keep the recent tail, re-inject the files that define the task, and test the summary for invented next steps. Check: ask after compaction what you asked before (section 4's probes) and compare.

LangChain's write-up names the same moves in four words, write (outside the window), select (pull in what is needed), compress, and isolate (2 Jul 2025); the 12-factor-agents list puts "Own your context window" third, and the frameworks root's {{Topic: agentic-frameworks|n:3c65c17b0d0d81ab8432c54d65b7f8c7}} discusses when a framework owns these decisions for you. The parent's Loop lab (step 4) is a working example of points 2 and 3 in about 40 lines of Python.

Common mistakes

A timestamp, a random id or a changing tool list in the prompt prefix
Every call rewrites everything after it. Measured: about 8x the input-side cost of a stable prefix per call (section 2). Put volatile values in the last message.
Trusting /context or a character count as an exact token budget
/context estimated 12.6k where the API counted 13,320; the same log is 228,000 tokens to Haiku 4.5 and 304,996 to Sonnet 5.5. Budget against the provider's own counts, per model, with a margin.
Summarising big tool outputs by default
The summarising call reads the whole output; on the 491 KB log that was $1.23 for a 471-token summary, while a filter kept the same five lines in 148 tokens for nothing. Filter or clear first; summarise when nothing simpler keeps what matters.
Treating a compaction summary as a faithful record
It is a model's paraphrase with a "next step" that the next call is told to pick up. Two of three manual summaries listed a commit nobody asked for; one run quoted the wrong output as fact afterwards. Keep rules and task facts in files that are re-read from disk.
Putting rules that must survive into the chat or into nested, path-scoped files
After compaction only the project-root memory file and unscoped rules come back from disk; chat instructions survive only if the summary copies them, and nested or path-scoped files return only when a matching file is read again.
Using a subagent to save tokens
It processed two to three times the tokens in the recordings. It saves the parent's window, not the bill; on a grep-sized question it cost 2.8x.
Reading a passing needle test as proof of long-context reliability
Literal retrieval is the easy case (Haiku 4.5: 20 of 20 up to 114K tokens). Tracking a value that changes, or finding something phrased differently from the question, fails earlier and on smaller models much earlier.

Interview questions

Why does the order of a prompt matter for cost, and what order do you use?
Prompt caches match exact prefixes, so anything that changes invalidates everything after it. Tools, system prompt and memory files first (stable), then the history appended one message at a time, with anything volatile in the last message. On Anthropic's API a changed tool definition invalidates the whole cache; a cache read costs 0.1x input, a 1-hour write 2x.
Your agent's 40th call costs ten times its 2nd. Where do you look?
Per-call usage: is the cache read the previous prompt (if not, something early changes or a turn adds more than 20 blocks past the breakpoint lookback); which tool results are largest (clip, filter, clear); whether old observations are ever cleared; then the startup context (tools and memory files). Compaction only if the history itself is the cost.
Observation masking or LLM summarisation for a coding agent?
Masking by default: in the JetBrains study it roughly halved cost and matched summarisation's solve rate in four of five settings, with no extra model call and no risk of an invented summary. Summarise when the old observations hold information the agent still needs that a stub cannot point back to.
What survives Claude Code's compaction and what does not?
System prompt, project-root CLAUDE.md and unscoped rules, auto memory, the plan file, a fresh git status, up to five recent files (paths only if over 5,000 tokens), invoked skill bodies (5,000 tokens each, 25,000 total). Lost or paraphrased: exact tool outputs, intermediate reasoning, nested and path-scoped rules until re-triggered, and anything said in chat that the summary does not copy.
When does a subagent help?
When a subtask's input is large and its answer small and the parent will not need the raw input again: wide searches, reading many files, long logs. It keeps the parent's window small (16K against 64K in the recordings) but processes more tokens in total, and it sees none of the parent's history, so its task message must be complete.
How would you test a model for context rot on your own workload?
Build cases from your own data at several lengths and depths, with tasks beyond literal lookup: a needle phrased differently from the question, a value that changes several times, several items to collect. Grade automatically, run several seeds, and compare against the same task at short length. Literal needle tests saturate and say little.
