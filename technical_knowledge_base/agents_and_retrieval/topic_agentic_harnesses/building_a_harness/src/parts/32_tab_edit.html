Edit format bench: thirteen edits, five formats

An agent changes code by writing an edit in some format that the harness then applies. This bench fixes everything except the format: thirteen edit requests on six small files (the running example's two bugs, a 69-line inventory module, a 141-line report module, a Makefile, a JSON config and a file with Windows line endings), each asked for in five formats, one request per (edit, format), applied by that format's own applier and checked by a test that also fails if anything else in the file changed MEASURED. When the applier reports an error, the harness sends it back once and asks again, as a real loop would. A reply that applies but is wrong gets no retry: the applier cannot know. The local model ran the ten edits outside the 141-line report module: the shared server was producing a few tokens a second under other jobs' load, and a whole-file reply of that module would have taken many minutes.

Same reply, different appliers

A format is a contract between the model and an applier, and appliers differ in how forgiving they are. Every unified-diff reply was applied three ways (git apply, git apply --recount, which ignores the line counts in hunk headers, and Aider's udiff applier, which ignores line numbers and treats each hunk as a search and replace), and every SEARCH/REPLACE reply two ways (exact match, and Aider 0.86.2's own do_replace with its whitespace-tolerant fallbacks).

How the bench was built
Formats as each tool documents them, with the instructions condensed to one paragraph and one example on a different file: exact replacement as a real tool call (the local model got an edit_file tool; Claude got the same JSON schema through claude -p --json-schema, which turns it into a tool named StructuredOutput), Aider's SEARCH/REPLACE blocks, a standard unified diff, the whole file in a fence, and Codex's apply_patch envelope. Appliers: our exact replace (each old string must occur once), Aider 0.86.2's own parser and appliers (from its PyPI wheel), git apply, and a Python port of Codex's apply_patch (openai/codex at commit 8b6bb1c, 6 Oct 2026: exact, then trailing-whitespace, then whitespace-insensitive matching, first match wins). The harness reads and writes files as raw bytes, so CRLF endings survive unless a reply drops them; note that Aider itself reads files in text mode and writes them with the platform's line ending by default (--line-endings platform), which would turn the CRLF file into LF on macOS.
