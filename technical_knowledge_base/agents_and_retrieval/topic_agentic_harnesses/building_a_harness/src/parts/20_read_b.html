2. The action boundary: the turn must end at the call

A language model continues text. After it has written an action, the likeliest continuation of a transcript of actions and results is a result, so a model that is not stopped writes one. The harness must make the model's turn end exactly at its action and never read anything generated after it: the action boundary. Who enforces it depends on the protocol:

ProtocolWho ends the turn at the actionWhat can go wrong
Provider API with tools (Anthropic, OpenAI)The provider: stop_reason: "tool_use" / finish_reason: "tool_calls"Nothing at the boundary; a reply cut by max_tokens can hold an incomplete call (section 7)
Open model through its chat templateThe model, by writing its end-of-turn token, and the server, by stopping thereA raw-text endpoint, a misconfigured stop list, or a template whose end token is not in the server's EOS list
Your own text protocol (the Loop lab's ACTION {json} line)You: a stop sequence such as the result header your harness writes, or cutting the reply at the first action lineEverything, if you forget

Without it, recorded. In the parent page's Loop lab, Claude Haiku 4.5 driven through claude -p (which cannot take a stop sequence) wrote fake tool results after its own action and once kept going for 95,162 characters until the 32,000-token output cap; mini-SWE-agent's text mode through the same route invented command output in 7 of 11 replies (Harness atlas tab) MEASURED (parent page). The local model behaved differently:

The local model stopped at its action in every chat sample, and wrote the user's next turn when let past its end token

Red: samples in which the model kept writing after its action MEASURED. In the chat endpoint the local model ended its turn right after the ACTION line in 20 of 20 samples, with or without a stop sequence: its own end-of-turn token did the work. Let past that token, it wrote the next turn itself in 5 of 18 samples: all 5 after its first call, none of the 13 after its later calls, where it ended at once with an end-of-text or an empty turn.

The surprise past the end-of-turn token
It did not invent a tool result (none of the 18 continuations contained a <tool_response>). It wrote a user turn: 5 of 18 continuations opened with <|im_start|>user, all of them after its first call, usually restating the task, and 4 of them then asked for tool calls inside that user turn, which the server parsed as real tool_calls. The section 1 animation replays one ("Boundary ignored").
The rule
Enforce the boundary yourself whatever the model usually does (the provider's tool calls, the server's end-of-turn stop, or a stop sequence plus a cut at the first action) and never parse past it. A model that behaves on one route (the local model in a chat API) can misbehave on another (the same model on a raw endpoint, Haiku through a CLI without stop sequences): a model writing the other side's turn is a harness bug.
How the boundary experiment was run
Local model: Qwen3 4B Instruct 2507 (4-bit) on mlx-lm 0.32.0, temperature 0.7, seeds 1 to 5 per condition. Text protocol: the Loop lab's step-1 system prompt verbatim, sent through the chat endpoint, at turn 1 and at turn 2 (after a real read of textstats/core.py), with and without stop: ["--- turn"]. Native past the boundary: the recorded conversation of run careful_s1 (section 10), rendered through the template up to and including each of the model's four tool-calling turns and its <|im_end|>, sent as raw text to /v1/completions with token ids returned, so every generated token, special ones included, is visible. Two of the planned 20 samples were lost when the shared server crashed. Code: src/harness/boundary.py.

3. Several tool calls in one reply

A model may ask for more than one tool in a reply. Anthropic: "By default, Claude may call multiple tools in a single response"; disable_parallel_tool_use: true inside tool_choice limits it to one, and OpenAI has parallel_tool_calls: false ({{Parallel tool use|https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use}}; {{Function calling|https://developers.openai.com/api/docs/guides/function-calling}}, both read 6 Oct 2026) SOURCE. "Parallel" describes the request, not the execution: the API "doesn't prescribe an execution order". Running them is the harness's decision, and how often it arises depends on the model:

The same harness sees very different batch sizes depending on the model

Replies that contained at least one tool call, split by how many MEASURED. Claude: the parent page's 22 recorded Claude Code sessions (Trace and context lab), counted per model message: Sonnet 5.5 put several calls in 9 of its 29 tool-calling replies and Haiku 4.5 in 7 of 91. Local model: the 16 runs of section 10.

Two kinds of batch show up. Independent calls, such as two or three reads, are safe to run at the same time. Dependent calls are not: the local model asked for edit_file and run_tests together in 13 of its 29 multi-call replies, and Sonnet in Claude Code sent Edit, Edit, Bash (two edits, then the tests) three times. Run those concurrently and the tests may run on the old code; the model then reads a failure caused by the harness.

The rule native.py uses
If every call in the batch is read-only (read_file, run_tests), run them on a thread pool; otherwise one by one, in the order the model wrote them. Either way, return one result per call, in call order, in the next request. Anthropic adds two details: put all results in one user message, because splitting them "teaches" Claude to stop making parallel calls; and if you skip a call (say an earlier write failed), still return a result for it, marked is_error, such as "Not executed: the preceding write_file call failed." Its suggested system-prompt line for agents that batch too eagerly: "Only batch tool calls that are independent of each other." It also notes that Claude Fable 5.1 "may issue fewer parallel tool calls than earlier models" in long agent loops. Batches cut round trips, and every round trip re-reads the whole context (section 11).
Predict, then reveal: a batch of Read a.py, Edit a.py, Bash pytest where the Edit fails
Three results, in order: the Read's output; the Edit's error with an is_error flag and an instructive message (section 5); and for the tests either their real output (which shows the unfixed code failing) or "Not executed: the preceding Edit failed." The second is clearer: it saves a test run and stops the model from reading a failure that says nothing new.
