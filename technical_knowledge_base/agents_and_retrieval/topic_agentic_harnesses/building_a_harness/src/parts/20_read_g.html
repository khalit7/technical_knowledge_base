8. Planning: a todo tool and a plan phase

On a task of five or seven turns, like the running example, the loop needs no plan: native.py has none, and nothing on this page measures one. On long tasks two failures grow: steps drift out of view as the transcript grows, and the model declares victory early. Harnesses answer with two patterns, both built from parts this page already has (a tool, a gate, a verifier), not from a special model ability.

Planning is a tool set and a tool result, not a prompt

Illustrative. Left: a plan phase whose tool set is read-only, ending at a person's approval, then the act phase with every tool. Right: a todo tool whose only effect is its result, the current checklist, which therefore sits near the end of the transcript on every later turn.

  • A todo tool. A tool such as todo_write(items) that changes nothing outside the transcript: the harness stores the list and returns it as the result, so the plan stays in recent context and the person watching has something to supervise. The model ticks items off by calling it again. After compaction ({{Context engineering|n:3f15c17b0d0d811292cee46514370431}}), the harness re-inserts the current list.
  • Plan, then act. A phase in which the harness offers only read-only tools (read, search, run the tests) and ends when a person approves the plan; then all tools. Implement it as a switch of the tool list and a gate rule, not as a request in the prompt, so the model cannot edit during planning even if it wants to.
  • Across sessions. Past one context window the plan must live outside it. Anthropic's long-running harness (26 Nov 2025) has an initializer agent set up the environment, a progress log and a feature list with every feature initially marked failing; each later session reads them, implements one feature, tests it, commits and updates the log. It was built against premature completion and marking features done without proper testing ({{Effective harnesses for long-running agents|https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents}}) SOURCE. The feature list is a todo list the verifier, not the model, ticks.

9. The execution environment: where tools run

Every tool call runs somewhere, with somebody's rights. Whatever the isolation, the harness owns five things on every call, and native.py shows each in a line or two:

  • A working directory: every command runs with cwd set to the repository.
  • Paths resolved and fenced: inside() resolves a path to its real location and refuses anything outside the repository, so ../ and symlinks cannot escape (the poka-yoke of section 5, also a safety line).
  • A timeout: 60 seconds per command or test run, so a hung process becomes an error result instead of a hung agent; an interrupt must also be able to kill it (section 4).
  • Captured output: standard output and error together, the exit code on the first line (the verdict first, section 5).
  • Hygiene: PYTHONDONTWRITEBYTECODE=1 keeps __pycache__ out of what the model sees; for evaluation every run must start from the same repository state, or runs stop being comparable (section 12).

Isolation rises with autonomy: the more the agent may do unasked, the further out the boundary

Where a bad command is contained, from none to a machine you can throw away. A permission gate decides what may start; it does not contain what runs. An OS sandbox wraps each command (Claude Code's optional sandbox uses Seatbelt on macOS and bubblewrap on Linux); a container or virtual machine contains the whole session, and a cloud agent returns a branch or pull request for review instead of edits you watch. The trade, not measured here: each step out costs start-up time and copies of files and credentials, and tools the model expects may be missing inside.

The security analysis of each layer (what the sandbox lets through, egress control, prompt injection) is {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}'s; how namespaces and seccomp work is {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}'s.
