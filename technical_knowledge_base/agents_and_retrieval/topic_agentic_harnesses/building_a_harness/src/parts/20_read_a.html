1. A tool call on the wire

The parent page's {{Loop lab|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} built a harness whose model could only return text: tools described in prose, an ACTION line parsed by the harness. This page moves the same loop onto native tool calling and opens the layer the APIs hide. A tool call has three layers. The contract: the request carries tool definitions (name, description, JSON Schema of the arguments) and the reply a typed call (name, arguments, an id). The rendering: the provider turns definitions, messages and earlier calls into the text the model reads; Anthropic says "the API constructs a special system prompt from the tool definitions", a prompt that tells the model "The output is not expected to be valid XML and is parsed with regular expressions" ({{Define tools|https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools}}, read 6 Oct 2026) SOURCE, and OpenAI's functions are "injected into the system message" (parent page). The generation: the model writes the call as tokens it was trained to write and ends its turn with an end-of-turn token. With a closed model you see only the contract; with an open model all three, because the rendering is a published chat template.

The experiment. src/harness/native.py is the Loop lab's loop on native calls (the same four tools, read_file, run_tests, edit_file with exact replacement and run_command, and the same permission gate), sent to mlx_lm.server, which renders the request with the model's own template (a Jinja file shipped with the weights), generates, and parses the reply back into tool_calls. The key fact the stepper shows: to the model, a tool result is something the user said, rendered as a user turn of <tool_response> blocks without the call ids, matched to its call by order alone. Rendering the recorded conversation with the model's own template and tokenizer gives exactly the prompt sizes the server reported on every call: 486, 865, 926, 1,252 and 1,531 tokens MEASURED. So the tokens below are the model's real input.

The animation, step by step

  1. The harness sends JSON. Two messages (system, task) and four tool definitions, each a name, a description and a JSON Schema: read_file, run_tests, edit_file, run_command. Nothing here is text the model reads yet.
  2. The server renders the system turn. The chat template writes the system prompt, then "# Tools", the four definitions as JSON lines inside <tools></tools>, and the instruction to answer with <tool_call>{...}</tool_call>: 428 tokens, tools included. Blue tokens are special tokens (one id each).
  3. Then the task, and an open assistant turn. The user turn holds the task and the file list; the prompt ends with <|im_start|>assistant and a newline, inviting the model to speak. The prompt is 486 tokens, exactly what the server reported.
  4. The model generates two tool calls. Token by token: a newline, <tool_call>, a JSON object naming read_file and its path, </tool_call>, and a second call for the test file; 46 generated tokens by the server's count.
  5. <|im_end|>: the boundary. Like <tool_call> (id 151657), </tool_call> (151658) and <tool_response> (151665), it is a single added token. Token 151645 is one of the model's end-of-sequence ids (generation_config.json), so sampling stops here and the server reports finish_reason: "tool_calls". Nothing after the call is generated: the result can only come from the harness.
  6. The server parses the calls. mlx-lm cuts the text between the tags, runs json.loads on it and returns OpenAI-style tool_calls, 2 of them, with an id each. The harness never sees the tags.
  7. Results come back as a user turn. The harness runs both reads and appends two role tool messages. The template renders them inside one user turn, as <tool_response> blocks, without the ids; with the assistant turn and a new generation prompt, the next request is 865 tokens.
  1. The harness sends JSON. The same request as in the normal run: two messages and four tool definitions.
  2. The server renders the system turn. The same 428 tokens of system prompt and tools.
  3. Then the task, and an open assistant turn. The same 486-token prompt.
  4. The model generates two tool calls. The same 46 generated tokens, ending in <|im_end|>.
  5. Generation continues past <|im_end|>. The same prompt and reply, sent as raw text to /v1/completions so nothing stops at the end-of-turn token. The model goes straight on and opens the next turn itself with <|im_start|>user (red tokens are the continuation).
  6. It writes the user's turn, with calls inside. It rephrased the task as the user and asked for tool calls inside that user turn; the server parsed those as tool_calls and returned finish_reason "tool_calls". A harness reading this reply would execute calls the model wrote while pretending to be the user. It did this in 5 of 5 samples after this first call.
  7. Why it matters. A harness that read past the boundary would treat words the model wrote for the user as the user's. In the parent page's Loop lab the same failure took the other form: Claude Haiku, on a text protocol with no stop, wrote a fake tool result (a fake core.py) and then said the code "appears correct". The end-of-turn token, a stop sequence, or an API's stop_reason is what keeps observations honest (section 2).
A failure the client cannot see
mlx-lm 0.32.0 picks its tool parser from the template (here a plain json.loads). If the text between the tags is not valid JSON, server.py logs "Failed to parse tool call ... tool text was likely truncated mid-generation" and drops the call. The client receives an empty reply with finish_reason: "stop", which a naive harness reads as "the model is done". The sibling page {{Harnesses for training and evaluation|n:3f15c17b0d0d815ea579d6c80065aa36}} measured the cost: its loop ended an episode on any reply without a tool call, and 9 of its local rollouts ended on a dropped malformed call, none of them passing. Read your server's parser before trusting its finish reasons; native.py treats an empty reply as an error to report back (section 7).

Predict, then reveal. With two calls in one turn and no ids in the rendered results, how does this model know which result is which? By order only: the results are rendered in the order of the tool messages, which native.py keeps identical to the order of the calls. A harness that runs calls concurrently and appends results as they finish would silently swap them for this model. On the Anthropic API the tool_use_id does the matching, but the docs still require all results in one message, before any text.

Re-rendering history is not always token-identical
Call 1 ended with <|im_start|>assistant and a newline token. On call 2 the template rendered the model's reply after it (its text was a single newline, and the template puts another newline before a tool call), and the tokenizer merged the three newlines into one token, . So call 2's tokens are not call 1's tokens plus new ones: the 486th token changed. Any cache keyed on token prefixes (a local server's prompt cache, a provider's prompt cache) has to cope with that; keeping the rendered history byte-stable from call to call is the harness's job.
