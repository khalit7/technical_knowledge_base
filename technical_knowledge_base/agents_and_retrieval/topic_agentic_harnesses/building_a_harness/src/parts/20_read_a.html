1. A tool call on the wire, three ways

Where we start. The parent page's {{Loop lab|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} (tab "Loop lab") built a harness whose model could only return text: the tools were described in prose, the harness looked for a line starting ACTION, ran it and pasted the result back. Its section "How real tool calling works at the API level" shows one recorded turn rewritten in Anthropic's and OpenAI's shapes. This page moves the same loop onto native tool calling, where the tools travel as data and the model's call comes back as data, and then opens the layer underneath that the APIs hide.

Three layers. (1) The contract: the request carries tool definitions (name, description, JSON Schema of the arguments) and the reply carries a typed call (name, arguments, an id). (2) The rendering: the provider turns definitions, messages and earlier calls into the text the model actually reads. Anthropic says so plainly: "the API constructs a special system prompt from the tool definitions", and that prompt itself tells the model "The output is not expected to be valid XML and is parsed with regular expressions" ({{Define tools|https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools}}, read 6 Oct 2026) SOURCE. OpenAI's functions are "injected into the system message" (parent page). (3) The generation: the model writes the call as tokens it was trained to write, ending its turn with an end-of-turn token. With a closed model you only see layer 1. With an open model all three are visible, because the rendering is a published chat template.

The experiment. src/harness/native.py is the Loop lab's final loop rewritten for native calls: the same four tools (read_file, run_tests, edit_file with exact replacement, run_command) and the same permission gate, sent as an OpenAI-style chat-completions request to mlx_lm.server serving Qwen3 4B Instruct 2507 (4-bit) on the laptop. The server renders the request with the model's own template (a Jinja file shipped with the weights), generates, and parses the reply back into tool_calls. Rendering our recorded conversation with that same template and tokenizer gives exactly the prompt sizes the server reported on every call of the run: 486, 865, 926, 1,252 and 1,531 tokens MEASURED. So the picture below is the model's real input, not a reconstruction.

What the animation shows. The tools arrive as JSON lines inside <tools></tools> in the system turn, followed by an instruction to answer with <tool_call>{"name": ..., "arguments": ...}</tool_call>. The model's reply is a newline, then two such blocks (it asked for two files at once: section 3), then <|im_end|>. <tool_call> (id 151657), </tool_call> (151658), <tool_response> (151665) and <|im_end|> (151645) are single added tokens, not strings spelled out letter by letter, and <|im_end|> is listed as an end-of-sequence id in the model's generation_config.json, so sampling stops there. The server then cuts the text between the tags, runs json.loads on it and returns finish_reason: "tool_calls" with an id per call. The results go back as messages with role tool, and the template renders them as a user turn holding one <tool_response> block per result: to the model, a tool result is something the user said.

A failure the client cannot see
mlx-lm 0.32.0 picks its tool parser from the template (here a plain json.loads). If the text between the tags is not valid JSON, server.py logs "Failed to parse tool call ... tool text was likely truncated mid-generation" and drops the call. The client receives an empty reply with finish_reason: "stop", which a naive harness reads as "the model is done". Our harness treats an empty reply as an error to report back to the model (section 7). The sibling page {{Harnesses for training and evaluation: scaffold sensitivity, RL environments, trajectories, self-improving harnesses|n:3f15c17b0d0d815ea579d6c80065aa36}} measured the cost of not doing so: its loop ended an episode on any reply without a tool call, and 9 of its local rollouts ended on a dropped malformed call, none of them passing (its section 1 and "Scaffold experiment" tab). Read your server's parser before trusting its finish reasons.

Predict, then reveal. The template drops the call ids when it renders tool results. With two calls in one turn, how does the model know which result belongs to which call?
By order only: the results are rendered in the order of the tool messages, which our harness keeps identical to the order of the calls. A harness that runs calls concurrently and appends results as they finish would silently swap them for this model. On the Anthropic API the tool_use_id does the matching, but the docs still require all results in one message, before any text.
