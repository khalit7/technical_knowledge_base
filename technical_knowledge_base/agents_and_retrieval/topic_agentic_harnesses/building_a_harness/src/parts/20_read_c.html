4. Streaming and interrupts

Without streaming, nobody sees anything until the reply exists, and the harness cannot act on the first tool call while the model writes the second. Without interrupts, stopping a wrong turn means killing the process and losing the session. Both are harness features: the model does not know it is being streamed or stopped.

How a stream is shaped. A tool call streams its arguments as fragments of JSON that the harness concatenates and parses only when the block closes; errors can arrive inside a stream that has already started (details below).

Stream details per provider

On the Anthropic API a reply is a sequence of server-sent events: message_start; per content block a content_block_start, deltas and content_block_stop; then message_delta (with stop_reason and usage) and message_stop. A tool call streams its arguments as input_json_delta strings that you concatenate and parse at the block's stop. Errors such as overloaded_error can arrive inside a stream that has already started ({{Streaming messages|https://platform.claude.com/docs/en/build-with-claude/streaming}}, read 6 Oct 2026) SOURCE.

Anthropic: ping events can appear anywhere, and "current models only support emitting one complete key and value property from input at a time", so a tool call's stream pauses while each value is being produced. OpenAI's Responses API streams arguments as response.function_call_arguments.delta events, closed by .done. mlx-lm's server does not stream tool arguments at all: it buffers everything between <tool_call> and </tool_call> and sends the call whole when the closing tag arrives (server.py, 0.32.0). How the providers' APIs differ as designs (where the conversation lives, what a tool call is, how its result is paired back) is {{Service APIs|n:3c65c17b0d0d81cb88a3f1f63e85f27b#rd-s7}}, section 7.

Interrupts mean three things: stop generation (close the stream), stop any running tool (kill its process, which is why a harness keeps child process handles), and leave a transcript the API will accept. The last is the subtle part: on the Anthropic API every tool_use must be followed immediately by its tool_result, or the next request fails with "tool_use ids were found without tool_result blocks immediately after" ({{Handle tool calls|https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls}}). Design rules that follow
Parse tool arguments only at the block's end (or with a partial-JSON parser for display). Execute a call when its block closes, not when the whole message does, if you want the latency win Claude Code gets, and keep the result order equal to the call order. On interrupt, give every pending call a result that says plainly it was not run (Anthropic's parallel-tool docs suggest is_error: true with "Not executed: ..."), then let the person's next message steer. Never execute a half-streamed tool call: a call cut off by max_tokens must be retried with a larger limit ({{Handling stop reasons|https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons}}).
