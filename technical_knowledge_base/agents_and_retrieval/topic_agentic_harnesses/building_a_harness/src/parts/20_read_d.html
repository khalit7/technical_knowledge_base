4. Streaming and interrupts

The problem. A model call takes seconds; a turn of an agent can take minutes. Without streaming, the person watching sees nothing until the whole reply exists, and the harness cannot act on the first tool call while the model is still writing the second. Without interrupts, the only way to stop a wrong turn is to kill the process and lose the session. Both are harness features: the model does not know it is being streamed or stopped.

How a stream is shaped. On the Anthropic API a streamed reply is a sequence of server-sent events: message_start; then for each content block a content_block_start, its deltas and a content_block_stop; then message_delta (carrying stop_reason and cumulative usage) and message_stop, with ping events anywhere. A tool call streams its arguments as input_json_delta events whose partial_json strings you concatenate and parse at the block's stop. The docs warn that "current models only support emitting one complete key and value property from input at a time", so a tool call's stream pauses while each value is being produced, and that errors such as overloaded_error can arrive inside a stream that has already started ({{Streaming messages|https://platform.claude.com/docs/en/build-with-claude/streaming}}, read 6 Oct 2026) SOURCE. OpenAI's Responses API streams arguments as response.function_call_arguments.delta events, closed by .done. mlx-lm's server does not stream tool arguments at all: it buffers everything between <tool_call> and </tool_call> and sends the call whole when the closing tag arrives (server.py, 0.32.0).

Interrupts. Stopping a turn means three things: stop generation (close the stream), stop any tool that is running (kill its process, which is why a harness keeps child process handles), and leave the transcript in a state the API will accept. The last one is the subtle part: on the Anthropic API every tool_use must be followed immediately by its tool_result, or the next request fails with "tool_use ids were found without tool_result blocks immediately after" ({{Handle tool calls|https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls}}). So an interrupted call still needs a result, written by the harness.

Design rules that follow. Parse tool arguments only at the block's end (or with a partial-JSON parser for display). Execute a call when its block closes, not when the whole message does, if you want the latency win Claude Code gets, and keep the result order equal to the call order. On interrupt, give every pending call a result that says plainly it was not run (Anthropic's parallel-tool docs suggest is_error: true with "Not executed: ..."), then let the person's next message steer. Never resend a half-streamed tool call as if it were complete: a call cut off by max_tokens must be retried with a larger limit, not executed ({{Handling stop reasons|https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons}}).
