10. Stop conditions and budgets

The textbook loop stops when the model replies without a tool call. That means "the model thinks it is done", which is not "the task is done", and it is not even always the model's signal: a reply cut off by the output limit or emptied by a parser failure also has no tool call. The opposite failure, never stopping, needs limits the model cannot argue with.

The model's own stopend_turn / no tool calls. Necessary, not sufficient. Check the finish reason first: length, max_tokens, model_context_window_exceeded ("treat the response as truncated"), refusal and pause_turn ("send the response back as-is") are not completions ({{Handling stop reasons|https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons}}).
A verifierBefore accepting "done", run the check yourself (the tests, a linter, a build) and, if it fails, show the output and continue. In Claude Code this is a Stop hook ({{Claude Code, taken apart|n:3c65c17b0d0d81db9c7fc54987c1ab65}}, section 4); in native.py the "verify" rule.
Hard capsTurns, tokens, dollars, wall-clock time. Checked by the harness on every iteration, with the reason reported in a typed result, never by asking the model.
Loop detectorsThe same call with the same arguments asked for again and again; the same error several times in a row. Cheap to compute from the log; a hint that the model is stuck, not proof.

The experiment. Sixteen runs of native.py on the running example with the local model, under three stop rules: naive (any reply without a tool call ends the run: the parent page's loop and most tutorials), careful (a reply cut at the output limit, finish_reason: "length", or an empty reply is not a stop: the harness says so and calls again) and verify (careful, and before accepting a stop the harness runs the tests itself; if they fail it shows the output and continues, at most three times). Five seeds at temperature 0.7 per rule, plus one run at temperature 0; each logged after every turn whether the tests passed, so any rule can be replayed MEASURED.

Same seed, two rules: step through the turns

Each box is a turn: its tool calls, or the reply that ended the run; green edge when the tests passed after that turn, red when they failed. Pick "Seed 4" to see the verifier rescue a run, "Seed 2" to see it spend three nudges and still fail.

  • The naive rule ends runs that are not done. The model said it was done with a test still failing in 4 runs; in a 5th (temperature 0) its reply hit the 1,024-token output limit before any tool call, and the naive rule read the truncation as completion.
  • A verifier rescues some and costs on others. With the verify rule, seed 4 was told the tests still failed and fixed the remaining bug by turn 7; seed 2 used all three nudges and still failed after 13 turns, spending 36,177 tokens against 9,544 for the same seed under the naive rule. A cap on nudges is what ended it.

Replay a stricter rule on the record: predict first

Set the turn cap to 5. How many of the 16 runs still end with passing tests? A stricter rule can only cut a run earlier, so its outcome is read from the record at the cut (rules that would let a run go on longer cannot be replayed).

Each box is one run; each cell one turn: green when the tests passed after that turn, red when they failed, dashed where the replayed rule cut the run.

Reveal: a cap of 5

With a cap of 5, 10 of the 16 still pass (against 11 with no cap): the passing runs had fixed both bugs by turn 4 or 5, so the cap loses only the run that needed the verifier's extra turns. Caps lose exactly the runs still making progress, which is why a cap should be generous and the verifier strict, not the other way round.

A stop policy that holds up
Stop when the model says it is done and the verifier agrees, or when a hard cap is reached, whichever comes first. Treat truncated and empty replies as errors, not stops. Check budgets before each model call (so a cap is never overshot by a whole call) and cap the number of verifier nudges. Return the reason as data (finished, max_turns, budget, stuck), and keep the transcript so a capped run can be resumed rather than restarted. Replay your own logs under candidate rules, as above, before choosing the numbers.

A product reports why it stopped. Claude Code ended a --max-budget-usd 0.01 run at $0.0118, because the budget is checked after a call has been paid for (details below).
