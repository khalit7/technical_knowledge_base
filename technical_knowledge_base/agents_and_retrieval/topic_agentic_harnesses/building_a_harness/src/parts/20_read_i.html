11. Cost and latency

A model call reads its whole prompt again every turn: the system prompt, every tool definition, the task, every earlier reply and every result. So the cost of a run grows faster than its length, and most levers either cut round trips, cut what each one carries, or stop paying for turns that teach nothing.

Each call re-reads everything before it; the tool definitions are paid on every call

12. Measuring a harness, not the model

A harness is a program, and its decisions can be tested like one: hold the model fixed and change one decision at a time. Every comparison on this page has that shape, and the same decision can rank differently on another model:

A harness tuned on one model is not tuned for another.

How to test a harness change
(1) Fix the model and its settings, change one decision (SWE-agent's Table 3 in section 5 is the template: removing the edit command took 18.0% to 10.3%). (2) Use fixed tasks with checks that also catch an edit that applied but is wrong. (3) Run each cell more than once: same-seed runs diverged here (section 10). (4) Report cost beside success, in tokens and dollars. (5) Keep tasks no prompt or tool change was tuned on. (6) Read the trajectories, not only the score: the per-turn log is what every number on this page was computed from ({{Agent and trajectory evaluation|n:3ef5c17b0d0d81fdbabaf3582bff37f2}} grades them).

How big is the harness effect? On ordinary tasks, mostly the bill: Arena's HarnessTax study (16 Sep 2026) ran seven models in three harnesses (Claude Code, Codex CLI and Pi, a minimal four-tool harness) on 30 tasks each; the harness moved success by about ±2 points on SWE-bench Lite and ±5 on Terminal-Bench 2.0, while Claude Code cost about 2.0× Pi on SWE-bench Lite ({{HarnessTax|https://arena.ai/blog/coding-agents-harness-tax}}, as checked on {{Agentic benchmarks|n:3c65c17b0d0d811fb926d7b91ef8234e}}) SOURCE. On a small model, much more: {{Harnesses for training and evaluation|n:3f15c17b0d0d815ea579d6c80065aa36}} found the harness moved a 4B model's success a lot and Claude Haiku's little, while Haiku's input tokens per rollout varied several-fold across harnesses (its Scaffold experiment tab). Scores published for a model are scores for a model in a harness: the parent page's section 7 and {{Coding benchmarks|n:3ef5c17b0d0d81bfa09ad4ba5eef0c4e}} cover reading them.

Interview rehearsal: eight questions

Answer aloud first, then open.

What does an open model actually generate when it "calls a tool"?
Ordinary tokens in a format it was trained on, bracketed by special tokens: for Qwen3, <tool_call>, a JSON object with name and arguments, </tool_call>, then the end-of-turn token. The server stops at that token, parses the JSON and returns a structured call. Results go back as text (a user turn of <tool_response> blocks for Qwen3).
Why must the harness enforce the action boundary, and how?
Because a language model continues text: after an action, the likeliest continuation is an observation, so without a stop it writes one. Enforce it with the API's tool-use stop, the end-of-turn token for open models, or a stop sequence plus a cut at the first action for text protocols.
The model returns three tool calls. How do you execute them?
Classify them: independent read-only calls concurrently, writes and anything after a write sequentially in the given order; on a failure, mark later dependent calls "not executed"; return one result per call, in order, in a single message.
How would you implement an interrupt?
Cancel the stream, kill running tool processes, write a result for every pending call saying it was not run (Claude Code writes that the user rejected the tool use), append the user's new message, and continue the same session.
Which edit format would you choose, and how would you decide?
Exact string replacement as a tool call for strong models (fails safely, cheap), with lenient diff application if a model prefers diffs; then measure on a fixed set of edits with checks, including traps such as duplicated text, CRLF files and long files, and count refusals, wrong applies and tokens.
What makes a good tool error message?
It names what was wrong in the input the model wrote, gives the fact needed to fix it (the actual line number, the closest matching lines, the valid values), and says what to do next. It leads with that, and is short.
Design the stop conditions for a coding agent.
Model says done and the verifier passes; hard caps on turns, tokens, dollars and time checked before each call; truncation and empty replies treated as errors; a loop detector; a cap on verifier nudges; the reason returned as data; the transcript kept for resumption.
Your agent's success rate dropped after you switched to a cheaper model. Where do you look first?
The trajectories: edit refusals per format, malformed calls, truncations and early stops. A smaller model often fails mechanically before it fails at reasoning: here the 4B model broke the diff and patch formats that Claude handled, and did best rewriting whole files. The fix may be a different format per model plus a check after every edit, not a bigger model.
