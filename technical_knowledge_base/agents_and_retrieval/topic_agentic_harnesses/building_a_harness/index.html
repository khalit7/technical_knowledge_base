The page in one screen

A harness is the program around a model: it sends a request, gets back either text or a tool call, runs the call, and decides whether to go round again. The parent page, Topic: agentic-harnesses, explains what an agent loop is and builds one in seven steps (its Loop lab tab). This page is for writing your own: each decision inside the loop, with a default that works and the recorded evidence for it.

1. A tool call on the wire, three ways

Where we start. The parent page's Loop lab (tab "Loop lab") built a harness whose model could only return text: the tools were described in prose, the harness looked for a line starting ACTION, ran it and pasted the result back. Its section "How real tool calling works at the API level" shows one recorded turn rewritten in Anthropic's and OpenAI's shapes. This page moves the same loop onto native tool calling, where the tools travel as data and the model's call comes back as data, and then opens the layer underneath that the APIs hide.

Three layers. (1) The contract: the request carries tool definitions (name, description, JSON Schema of the arguments) and the reply carries a typed call (name, arguments, an id). (2) The rendering: the provider turns definitions, messages and earlier calls into the text the model actually reads. Anthropic says so plainly: "the API constructs a special system prompt from the tool definitions", and that prompt itself tells the model "The output is not expected to be valid XML and is parsed with regular expressions" (Define tools, read 6 Oct 2026) SOURCE. OpenAI's functions are "injected into the system message" (parent page). (3) The generation: the model writes the call as tokens it was trained to write, ending its turn with an end-of-turn token. With a closed model you only see layer 1. With an open model all three are visible, because the rendering is a published chat template.

The experiment. src/harness/native.py is the Loop lab's final loop rewritten for native calls: the same four tools (read_file, run_tests, edit_file with exact replacement, run_command) and the same permission gate, sent as an OpenAI-style chat-completions request to mlx_lm.server serving Qwen3 4B Instruct 2507 (4-bit) on the laptop. The server renders the request with the model's own template (a Jinja file shipped with the weights), generates, and parses the reply back into tool_calls. Rendering our recorded conversation with that same template and tokenizer gives exactly the prompt sizes the server reported on every call of the run: 486, 865, 926, 1,252 and 1,531 tokens MEASURED. So the picture below is the model's real input, not a reconstruction.

The results go back as messages with role tool, and the template renders them as a user turn holding one <tool_response> block per result: to the model, a tool result is something the user said.

A failure the client cannot see
mlx-lm 0.32.0 picks its tool parser from the template (here a plain json.loads). If the text between the tags is not valid JSON, server.py logs "Failed to parse tool call ... tool text was likely truncated mid-generation" and drops the call. The client receives an empty reply with finish_reason: "stop", which a naive harness reads as "the model is done". Our harness treats an empty reply as an error to report back to the model (section 7). Read your server's parser before trusting its finish reasons.

2. The action boundary: the turn must end at the call

The problem. A language model continues text. After it has written an action, the likeliest continuation of a transcript of actions and results is a result, so a model that is not stopped writes one. The harness must make the model's turn end exactly at its action, and must never read anything generated after it. We call that point the action boundary.

ProtocolWho ends the turn at the actionWhat can go wrong
Provider API with tools (Anthropic, OpenAI)The provider: generation stops with stop_reason: "tool_use" / finish_reason: "tool_calls"Nothing at the boundary; a reply cut by max_tokens can hold an incomplete call (section 7)
Open model through its chat templateThe model, by writing its end-of-turn token (<|im_end|>, an end-of-sequence id), and the server, by stopping thereA raw-text endpoint, a misconfigured stop list, or a template whose end token is not in the server's EOS list
Your own text protocol (the Loop lab's ACTION {json} line)You: a stop sequence such as the result header your harness writes, or cutting the reply at the first action lineEverything, if you forget: the parent's recordings below

The surprise past the end-of-turn token
The rule
Enforce the boundary yourself whatever the model usually does: use the provider's tool calls, or keep the server's end-of-turn stop, or add a stop sequence and also cut the reply at the first action; never parse past it; and treat a model that writes the other side's turn as a harness bug, not a model quirk. A model that behaves on one route (the local model in a chat API) can misbehave on another (the same model on a raw endpoint, or Haiku through a CLI without stop sequences).

3. Several tool calls in one reply

What it is. A model may ask for more than one tool in a single reply: read three files, or edit a file and run the tests. Anthropic: "By default, Claude may call multiple tools in a single response"; you can turn it off with disable_parallel_tool_use: true inside tool_choice (then at most one call per reply), and OpenAI has parallel_tool_calls: false (Parallel tool use; Function calling, both read 6 Oct 2026) SOURCE. "Parallel" describes the request, not the execution: the API "doesn't prescribe an execution order". Running them is the harness's decision.

How often it happens. MEASURED

Replies that contained at least one tool call, split by how many. Claude: the parent page's 22 recorded Claude Code sessions (Trace and context lab), counted per model message. Local model: the 16 runs of this page's Stop lab.

Two different kinds of batch show up. Independent calls, such as two or three Reads, are safe to run at the same time. Dependent calls are not: the local model asked for edit_file and run_tests together in 13 of its 29 multi-call replies, and Sonnet in Claude Code sent Edit, Edit, Bash (two edits, then the tests) three times. Run those concurrently and the tests may run on the old code; the model then reads a failure caused by the harness, not by its fix.

The rule our harness uses (native.py)
If every call in the batch is read-only (read_file, run_tests), run them on a thread pool; otherwise run them one by one, in the order the model wrote them. Either way, return one result per call, in call order, in the next request. Anthropic adds two details: put all results in one user message, because splitting them into one message each "teaches" Claude to stop making parallel calls; and if you skip a call (say an earlier write failed), still return a result for it, marked is_error, such as "Not executed: the preceding write_file call failed." Its suggested system-prompt line for agents that batch too eagerly: "Only batch tool calls that are independent of each other."

Does batching change behaviour across models? In our recordings, Sonnet 5.5 put several calls in 9 of its 29 tool-calling replies and Haiku 4.5 in 7 of 91, so the same harness sees very different batch sizes depending on the model. Anthropic also notes that Claude Fable 5.1 "may issue fewer parallel tool calls than earlier models" in long agent loops and documents a prompt for it. Batches matter for latency (fewer model round trips) and for cost (each round trip re-reads the whole context, section 3 of the parent page), so it is worth measuring on your own harness rather than assuming.

Predict, then reveal. A batch of three calls arrives: Read a.py, Edit a.py, Bash pytest. The Edit fails (old string not found). What should the harness send back?
Three results, in order: the Read's output; the Edit's error with an is_error flag and an instructive message (section 5); and for the tests either their real output (if you ran them, which shows the unfixed code failing) or "Not executed: the preceding Edit failed." The second is clearer: it saves a test run and stops the model from reading a failure that says nothing new.

4. Streaming and interrupts

The problem. A model call takes seconds; a turn of an agent can take minutes. Without streaming, the person watching sees nothing until the whole reply exists, and the harness cannot act on the first tool call while the model is still writing the second. Without interrupts, the only way to stop a wrong turn is to kill the process and lose the session. Both are harness features: the model does not know it is being streamed or stopped.

How a stream is shaped. On the Anthropic API a streamed reply is a sequence of server-sent events: message_start; then for each content block a content_block_start, its deltas and a content_block_stop; then message_delta (carrying stop_reason and cumulative usage) and message_stop, with ping events anywhere. A tool call streams its arguments as input_json_delta events whose partial_json strings you concatenate and parse at the block's stop. The docs warn that "current models only support emitting one complete key and value property from input at a time", so a tool call's stream pauses while each value is being produced, and that errors such as overloaded_error can arrive inside a stream that has already started (Streaming messages, read 6 Oct 2026) SOURCE. OpenAI's Responses API streams arguments as response.function_call_arguments.delta events, closed by .done. mlx-lm's server does not stream tool arguments at all: it buffers everything between <tool_call> and </tool_call> and sends the call whole when the closing tag arrives (server.py, 0.32.0).

Interrupts. Stopping a turn means three things: stop generation (close the stream), stop any tool that is running (kill its process, which is why a harness keeps child process handles), and leave the transcript in a state the API will accept. The last one is the subtle part: on the Anthropic API every tool_use must be followed immediately by its tool_result, or the next request fails with "tool_use ids were found without tool_result blocks immediately after" (Handle tool calls). So an interrupted call still needs a result, written by the harness.

What Claude Code writes when you interrupt it

Claude Agent SDK 0.2.163 (it drives its bundled Claude Code 2.1.286), Claude Haiku 4.5, the running example; our script called client.interrupt() the instant the first tool call arrived, then asked a follow-up question in the same session MEASURED. The CLI's text contained one em-dash, shown here as ", ".

Design rules that follow. Parse tool arguments only at the block's end (or with a partial-JSON parser for display). Execute a call when its block closes, not when the whole message does, if you want the latency win Claude Code gets, and keep the result order equal to the call order. On interrupt, give every pending call a result that says plainly it was not run (Anthropic's parallel-tool docs suggest is_error: true with "Not executed: ..."), then let the person's next message steer. Never resend a half-streamed tool call as if it were complete: a call cut off by max_tokens must be retried with a larger limit, not executed (Handling stop reasons).

5. Designing tools for a model: the agent-computer interface

The idea. A tool is an interface whose user is a model that reads every word literally, cannot ask a colleague, and sees the world only through what the tool returns. The SWE-agent paper (Yang et al., May 2024) called this the agent-computer interface (ACI) and measured it by changing one interface choice at a time on a SWE-bench Lite subset, same model SOURCE (Table 3, arXiv 2405.15793):

Interface choiceResolvedChange against the default
Default SWE-agent: file viewer of 100 lines, summarised search, edit command with a linter18.0%
Edit command without the linter (syntax errors are accepted)15.0%-3.0 points
No edit command at all (shell only)10.3%-7.7
Viewer shows 30 lines14.3%-3.7
Viewer shows the whole file12.7%-5.3
Iterative search (one result at a time)12.0%-6.0
No search command15.7%-2.3

Two lessons hide in that table. More information is not better (the whole file did worse than 100 lines), and a guardrail, a check inside the tool that refuses a bad action and says why, pays for itself (the linter). Anthropic's account of its SWE-bench agent (Erik Schluntz; the post is dated 6 Jan 2025) adds a third: poka-yoke, making mistakes impossible. "Sometimes models could mess up relative file paths after the agent had moved out of the root directory. To prevent this, we simply made the tool always require an absolute path." The same post reports that of the edit strategies it tried, string replacement (old_str to new_str, failing when the old text occurs zero or several times) had "the highest reliability" (Raising the bar on SWE-bench Verified) SOURCE.

Names and descriptionsThe model chooses a tool from its name and description alone. Anthropic's tool docs call detailed descriptions "by far the most important factor in tool performance" and suggest "at least 3-4 sentences" per tool; OpenAI's suggest keeping fewer than 20 functions available at once ("a soft suggestion"). Overlapping tools invite wrong choices and cost tokens on every call.
Arguments that cannot be wrongAbsolute paths; enums instead of free strings; one required field rather than three optional ones that conflict. Strict schemas (Anthropic strict: true, OpenAI strict) guarantee arguments that parse; they cannot guarantee arguments that make sense.
Results that lead with the verdictExit code and pass or fail on the first line, the informative lines next, a note of what was cut. The parent page's Loop lab measured what happens otherwise: the test results sat at lines 92 to 95 of about 240 and a head-and-tail clip removed them.
Errors that say what to doAnthropic: "Instead of generic errors like "failed", include what went wrong and what Claude should try next." Measured below.

Does the wording of an error change the outcome?

The experiment: every edit in the Edit format bench whose first attempt could not be applied was retried three times from the same first reply, each time with a different error message: terse ("Edit failed."), native (what the applier itself says: git apply's "corrupt patch at line 8", Codex's "Failed to find expected lines", Aider's SearchReplaceNoExactMatch report), and instructive (a diagnosis our harness computes: the hunk header says 4 old lines but the body has 5, the old lines start at line 12 not 13; the @@ line is itself one of the removed lines; the closest lines in the file with numbers; the file uses CRLF line endings).

Claude Haiku 4.5 with thinking off, through claude -p MEASURED. Small numbers: read them as a direction, not a rate.

What to take from it
An error is the model's only view of what went wrong. git apply's "corrupt patch at line 8" is written for a person who will open the patch in an editor; the model, given only that, resent the same broken patch. A message that names the wrong number and the right one fixed some of the same failures. Some failures no wording fixes: a model that cannot see the carriage returns of a CRLF file cannot type them either, so the fix belongs in the tool (match lines without their line endings, as Codex's patch tool does) rather than in the message.

6. Edit formats, measured

The problem. A coding agent spends most of its effort deciding what to change; the edit format is how it writes that change down so a program can apply it. The format is part of the harness, and it fails mechanically: an edit can be right in intent and still refused because a line number is off by one, or applied in the wrong place because the text it searched for appears twice.

Exact replaceA tool call with an old string and a new one; the old string must occur exactly once. Claude Code's Edit, Anthropic's text-editor tool, our edit_file. Fails loudly on a typo or an ambiguous match; cannot land in the wrong place.
SEARCH/REPLACE blocksAider's main format: the same idea written as text between <<<<<<< SEARCH, =======, >>>>>>> REPLACE. No JSON escaping of code; Aider's applier forgives some whitespace and uses the first match.
Unified diffWhat diff -u and git diff write: hunks with line numbers and counts in @@ -a,b +c,d @@ headers. Familiar from training data; the numbers are where models slip.
Whole fileWrite the entire new file. Cannot fail to apply; costs output tokens in proportion to the file, and quietly loses whatever the model forgets or normalises.
apply_patchCodex's envelope: *** Begin Patch, *** Update File:, hunks anchored by an optional @@ line and context, no line numbers. Forgiving matcher (exact, then ignoring trailing or all surrounding whitespace); the first match wins.

The bench. Thirteen fixed edits on six small files, each requested in all five formats, one model call per (edit, format), applied by the format's own applier and checked by a test that also fails if anything else in the file changed; an applier error is sent back once for a retry. Full matrix, every reply and every verdict: the Edit format bench tab.

What failed, with Claude Haiku 4.5 (thinking off) MEASURED:

  • Unified diff, by the counts. 9 of 13 diffs were refused by git apply as "corrupt patch": the hunk headers announced 4 old lines where the body had 5, or started a line too early. The changes themselves were right: git apply --recount (which recomputes the counts) and Aider's applier (which ignores line numbers) applied 12 of the 13. Sent git's message back, the model mostly resent the same header. With thinking switched on (the default in these Claude Code runs), Haiku got 6 of the 13 diffs through git apply instead of 4 and spent 76,771 output tokens on them, thinking included, against 2,634 without thinking: it counted lines at length and still got most headers wrong.
  • apply_patch, by the anchor. Twice the model put the line it was changing on the @@ line (@@ def export_rows(sales, limit=10):, then -def export_rows(sales, limit=10):). Codex searches for the hunk only after the @@ line, so the line it wants to remove can never be found.
  • Windows line endings. On the CRLF file, the SEARCH block INCH_TO_CM = 2.5 plus its newline did not match 2.5\r\n; the unified diff failed the same way; the whole-file reply applied, changed the constant and silently converted every line ending to LF (the check caught it). Exact replace succeeded because Haiku's old string had no newline; Sonnet's included one ("INCH_TO_CM = 2.5\n") and was refused until the retry. Only apply_patch, which compares lines without their endings and writes new lines with the file's own ending, passed at the first attempt in all three Claude runs.
  • The model matters as much as the format. Sonnet 5.5 (thinking off) wrote unified diffs that git apply took in 11 of 13 cases, against Haiku's 4: the "numbers are where models slip" lesson is a property of the model, which is why a harness that serves several models (Aider does) chooses the format per model.
  • A small model ranks them the other way. Qwen3 4B (local, temperature 0, the ten edits on the short files) was correct at the first attempt in 7 of 10 whole-file replies, 5 of 10 SEARCH/REPLACE, 4 of 10 exact replacements, and 1 of 10 for both unified diffs and apply_patch: it broke the formats themselves (no filename line before a SEARCH block, a patch without its *** End Patch line, unprefixed lines inside a hunk). The format it could not get mechanically wrong won.
  • Lenient appliers apply wrong edits. On the same 4B diffs, Aider's forgiving udiff applier applied 8 of 10, but 6 of those 8 failed the check (wrong place, or other lines changed); git apply refused almost all of them. Leniency turns refusals into silent mistakes when the model is weak, which is why the check after the edit matters more than the applier.
  • The price of whole files. Changing limit=10 to limit=20 at the end of the 141-line report module took 1,409 output tokens as a whole file and 51 to 155 in the other formats (first attempts). It applied, but on a long file every rewrite is a chance to drop a line; the check would catch it here, and nothing would in production.
What this suggests for your harness
Prefer exact replacement as a tool call for frontier models: it had the fewest failures for Claude here (Haiku 13 of 13; Sonnet 12 of 13, the miss being the CRLF file, fixed on the retry), and it fails safely (an error, never a wrong place). If you accept diffs, apply them the forgiving way (recount, or match hunks by content as Aider does) and never trust model-written line numbers. Match lines without their line endings and write back the file's own ending. Keep whole-file writes for new or very small files, or for a small model that cannot hold a format, as long as a check runs after every write. And measure on your own model: the Edit format bench shows how much the ranking moves between Haiku, Sonnet and a 4B local model.

Published context: Aider reported that switching GPT-4 Turbo from SEARCH/REPLACE to its own line-number-free unified diffs raised its "laziness" benchmark score from 20% to 61%, and that disabling its flexible patching gave "a 9X increase in editing errors" (Unified diffs make GPT-4 Turbo 3X less lazy, 21 Dec 2023) SOURCE. Both point the same way as our appliers table: the applier's tolerance matters as much as the format. Aider's edit formats page lists six formats and its leaderboards record which one each model is run with.

7. Error recovery: every way a turn can go wrong

The rule. A harness never crashes on a bad turn and never hides one. Each failure is either turned into an observation the model can act on, or, if it is the infrastructure's fault rather than the model's, retried quietly and kept out of both the transcript and the score. The difficulty is telling the two apart, and noticing some failures at all.

Retry budgets. Every retry needs a ceiling: errors in a row (the Loop lab ended a run after three malformed replies), retries per edit (one in our bench), and the run's overall caps (section 8). Anthropic's docs describe Claude's own behaviour with invalid tool calls: it "will retry 2-3 times with corrections before apologizing to the user" (Handle tool calls). Retrying the infrastructure belongs in the client or a gateway; the frameworks root's Production stack tab measures LiteLLM's retry and fallback rules.

8. Stop conditions and budgets

The problem. The textbook loop stops when the model replies without a tool call. That signal means "the model thinks it is done", which is not the same as "the task is done", and it is not even always the model's signal: a reply cut off by the output limit or emptied by a parser failure also has no tool call. The opposite failure, never stopping, needs limits the model cannot argue with.

The model's own stopend_turn / no tool calls. Necessary, not sufficient. Check the finish reason first: length, max_tokens, model_context_window_exceeded ("treat the response as truncated"), refusal and pause_turn ("send the response back as-is") are not completions (Handling stop reasons).
A verifierBefore accepting "done", run the check yourself (the tests, a linter, a build) and, if it fails, show the output and continue. In Claude Code this is a Stop hook; in our harness the "verify" rule.
Hard capsTurns, tokens, dollars, wall-clock time. Checked by the harness on every iteration, with the reason reported in a typed result, never by asking the model.
Loop detectorsThe same call with the same arguments asked for again and again; the same error several times in a row. Cheap to compute from the log; a hint that the model is stuck, not proof.

What the recordings show

Read the per-rule counts with care: with five seeds each, one run moves a rule by a fifth, and careful's seed 4 failed for a reason unrelated to its rule (that run diverged from the naive one at turn 3, before any rule acted, because the shared server's batching broke determinism).

  • The naive rule ends runs that are not done. In the Stop lab's 16 runs, the model said it was done with a test still failing in 4 runs; in a 5th (temperature 0) its reply hit the 1,024-token output limit before any tool call, and the naive rule read the truncation as completion.
  • A verifier rescues some and costs on others. With the verify rule, seed 4 was told the tests still failed and fixed the remaining bug by turn 7; seed 2 used all three nudges and still failed, spending 36,177 tokens against 9,544 for the same seed under the naive rule. A cap on nudges is what ended it.
  • A product reports why it stopped. Claude Code with --max-turns 3 ended with subtype: "error_max_turns" after running three tool calls whose last result the model never saw; with --max-budget-usd 0.01 it ended with "error_max_budget_usd" at $0.0118, because the budget is checked after a call has been paid for, and the tool call that call asked for was never run.
A stop policy that holds up
Stop when the model says it is done and the verifier agrees, or when a hard cap is reached, whichever comes first. Treat truncated and empty replies as errors, not stops. Check budgets before each model call (so a cap is never overshot by a whole call) and cap the number of verifier nudges. Return the reason as data (finished, max_turns, budget, stuck), and keep the transcript so a capped run can be resumed rather than restarted. Replay your own logs under candidate rules, as the Stop lab does, before choosing the numbers.
Predict, then reveal. In the Stop lab, set the turn cap to 5. How many of the 16 runs still end with passing tests, and why so many?

Common mistakes

Treating "no tool call" as "done"
Truncated, empty and refused replies have no tool call either. Check the finish reason, and before accepting a real stop, run the verifier (section 8). One recorded run here stopped on a reply cut at 1,024 tokens.
Parsing text without a stop at the action
If the model writes in plain text, generation must end right after the action (a stop sequence, or cutting at the first action line). Otherwise the model writes the observation too (section 2).
Running a batch of calls concurrently without looking at it
An edit and a test run in the same reply are dependent. Run read-only batches in parallel, everything else in order, and return results in call order (section 3).
Leaving a tool call without a result after an interrupt or a skipped call
The next API request fails. Write a result that says the call was not run (section 4).
Error messages written for people
"corrupt patch at line 8" helped the model fix nothing. Say what is wrong in the model's own terms and what to change (section 5).
Trusting model-written line numbers
Hunk headers were wrong in most of Haiku's unified diffs; recount, or locate hunks by content (section 6).
Rewriting whole files to change a line
It always applies, which is the problem: dropped lines and normalised line endings go through silently, and output tokens grow with the file (section 6).
Retrying infrastructure errors inside the transcript
A 529 or a dropped connection is not the model's mistake. Retry it in the client, out of the model's sight, and keep it out of the score (section 7).

Interview questions

Answer aloud first, then open.

What does an open model actually generate when it "calls a tool"?
Ordinary tokens in a format it was trained on, bracketed by special tokens: for Qwen3, <tool_call>, a JSON object with name and arguments, </tool_call>, then the end-of-turn token. The server stops at that token, parses the JSON and returns a structured call. Results go back as text (a user turn of <tool_response> blocks for Qwen3).
Why must the harness enforce the action boundary, and how?
Because a language model continues text: after an action, the likeliest continuation is an observation, so without a stop it writes one. Enforce it with the API's tool-use stop, the end-of-turn token for open models, or a stop sequence / cut at the first action for text protocols.
The model returns three tool calls. How do you execute them?
Classify them: independent read-only calls concurrently, writes and anything after a write sequentially in the given order; on a failure, mark later dependent calls "not executed"; return one result per call, in order, in a single message.
How would you implement an interrupt?
Cancel the stream, kill running tool processes, write a result for every pending call saying it was not run (Claude Code writes that the user rejected the tool use), append the user's new message, and continue the same session.
Which edit format would you choose, and how would you decide?
Exact string replacement as a tool call for strong models (fails safely, cheap), with lenient diff application if a model prefers diffs; then measure on a fixed set of edits with checks, including traps such as duplicated text, CRLF files and long files, and count refusals, wrong applies and tokens.
What makes a good tool error message?
It names what was wrong in the input the model wrote, gives the fact needed to fix it (the actual line number, the closest matching lines, the valid values), and says what to do next. It leads with that, and is short.
Design the stop conditions for a coding agent.
Model says done and the verifier passes; hard caps on turns, tokens, dollars and time checked before each call; truncation and empty replies treated as errors; a loop detector; a cap on verifier nudges; the reason returned as data; the transcript kept for resumption.
Your agent's success rate dropped after you switched to a cheaper model. Where do you look first?
The trajectories: edit refusals per format, malformed calls, truncations and early stops. A smaller model often fails mechanically before it fails at reasoning: here the 4B model broke the diff and patch formats that Claude handled, and did best rewriting whole files. The fix may be a different format per model plus a check after every edit, not a bigger model.

Re-rendering history is not always token-identical
Call 1 ended with <|im_start|>assistant and a newline token. On call 2 the template rendered the model's reply after it (its text was a single newline, and the template puts another newline before a tool call), and the tokenizer merged the three newlines into one token, . So call 2's tokens are not call 1's tokens plus new ones: the 486th token changed. Edit format bench: thirteen edits, five formats

An agent changes code by writing an edit in some format that the harness then applies. This bench fixes everything except the format: thirteen edit requests on six small files (the running example's two bugs, a 69-line inventory module, a 141-line report module, a Makefile, a JSON config and a file with Windows line endings), each asked for in five formats, one request per (edit, format), applied by that format's own applier and checked by a test that also fails if anything else in the file changed MEASURED. When the applier reports an error, the harness sends it back once and asks again, as a real loop would. A reply that applies but is wrong gets no retry: the applier cannot know. The local model ran the ten edits outside the 141-line report module: the shared server was producing a few tokens a second under other jobs' load, and a whole-file reply of that module would have taken many minutes.

Same reply, different appliers

A format is a contract between the model and an applier, and appliers differ in how forgiving they are. How the bench was built
Formats as each tool documents them, with the instructions condensed to one paragraph and one example on a different file: exact replacement as a real tool call (the local model got an edit_file tool; Claude got the same JSON schema through claude -p --json-schema, which turns it into a tool named StructuredOutput), Aider's SEARCH/REPLACE blocks, a standard unified diff, the whole file in a fence, and Codex's apply_patch envelope. Stop lab: when should a loop end?

Sixteen recorded runs of src/harness/native.py (the Loop lab's loop on native tool calls, section 1 of the Reading tab) on the running example, with the local model (Qwen3 4B Instruct 2507, 4-bit, mlx-lm 0.32.0 on an Apple M1 Pro), under three stop rules. Each run logged, after every turn, whether the tests pass in the repository at that moment, so any stop rule can be replayed on the record afterwards MEASURED.

naive

Any reply without a tool call ends the run. This is the loop on the parent page and in most tutorials.

careful

As naive, but a reply cut off by the output limit (finish_reason: "length") or an empty reply is not a stop: the harness says so and calls again.

verify

As careful, and before accepting a stop the harness runs the tests itself; if they fail it shows the output and continues, at most three times.

Five seeds at temperature 0.7 per rule, plus the first run of all (temperature 0, before the rules existed). The same seed was sent with the same rule pair so the runs would be identical until the rule mattered; they were not always, because the shared server batched our requests with other clients' and batched arithmetic is not bit-identical (naive and careful with seed 4 diverge at turn 3, where no rule had acted). Seconds are wall time on a machine that was swapping under other work: compare tokens, not seconds.
