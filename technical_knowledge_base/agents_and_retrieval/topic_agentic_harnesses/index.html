The topic in one screen

An agent is a language model called in a loop: it reads the situation, asks for an action, a program carries the action out and shows it the result, and it decides again, until the job is done. The harness is that program: everything except the model. Anthropic's own definition: Claude Code "is the layer around the model that provides the tools and manages the context the model sees. This surrounding layer is what the term agentic harness refers to" (How Claude Code works, read 5 Oct 2026).

The running example. A tiny Python library, textstats, with two planted bugs: the word splitter drops apostrophes (so word_count("don't stop") returns 3, not 2), and top_words breaks ties in no particular order instead of alphabetically. One test file, run with plain python3 tests/test_core.py, catches both. Every run on this page gets the same prompt: "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests." The question this tab answers is what happens between pressing Enter and the tests passing.

1. From chat to agent: a model call, then tools, then the loop

A model call. A language model is a function from text to text. The text goes in as tokens (word pieces, about four characters of English each), and the model generates new tokens one at a time until it decides to stop. It keeps no memory between calls: to "continue a conversation", the caller sends the whole conversation again every time. The maximum it can read in one call is its context window (200,000 tokens for Claude Haiku 4.5, as the CLI's own result record reports MEASURED).

Step 0, no loop. The simplest possible "agent" pastes the source file into one prompt and writes back whatever comes out. Run on the example, Haiku 4.5 read 635 input tokens, answered in 7.9 seconds, and fixed top_words; it never saw the tests, so it never learned that apostrophes were supposed to survive, and one test still failed MEASURED. Nothing was wrong with the model. It was missing information that only running the code could give it.

Tools. A tool is a function the harness offers the model, described by a name, a sentence of description and a JSON schema for its arguments, for example Bash {command} or Read {file_path}. The descriptions are sent with every request. Instead of answering in prose, the model can reply with a structured tool call: on the Anthropic API a tool_use block with the tool's name and arguments and stop_reason: "tool_use"; on OpenAI's, a function_call item. The harness runs the function and sends the output back as a tool result in the next request (both protocols are in the Loop lab's API section). Models do this reliably because they are trained to: OpenAI announced on 13 June 2023 (archived post) that its 0613 models "have been fine-tuned" to detect when a function should be called and to answer with JSON matching its signature, and Toolformer (Schick et al., February 2023) had shown a model teaching itself API calls from a few demonstrations SOURCE.

The loop. Put the call in a loop and you have an agent:

messages = [system prompt, task]
while True:
  reply = model(messages, tools)
  if reply has no tool call: break   # the model says it is done
  result = run(reply.tool_call)   # after a permission check
  messages += [reply, result]

That is the whole core. The pattern is older than tool-calling APIs: ReAct (Yao et al., October 2022) interleaved free-text thoughts with actions and observations in one prompted loop, and beat reasoning-only and acting-only baselines; every modern agent loop descends from it (ReAct paper page). What makes a harness good is everything around those six lines: which tools, what the model sees, when it stops, what it may touch.

2. Tools: the agent's hands and eyes

The problem. The model can only act through the tools it is given, and it only learns about the world through what those tools return. A coding harness therefore needs, at minimum, a way to look (read a file, list or search files), a way to change things (edit or write a file) and a way to check (run a command, above all the tests). Claude Code's docs group its built-in tools into file operations, search, execution, web and code intelligence, plus tools for subagents and questions to the user (docs). Our recorded runs passed six: Read, Edit, Write, Bash, Grep, Glob.

Tools are an interface designed for a very literal user. The SWE-agent paper (Yang et al., May 2024) named this the agent-computer interface (ACI): the same model scored differently depending on how its file viewer, search and edit commands were shaped, and with an interface designed for it reached 12.5% on SWE-bench, then the state of the art (arXiv 2405.15793) SOURCE. Anthropic's tool-writing guide (11 Sep 2025) lists the rules that followed: choose few tools that match real tasks rather than wrapping every API endpoint; namespace them; return meaningful context, not internal ids; keep responses token-efficient ("For Claude Code, we restrict tool responses to 25,000 tokens by default"); and treat the description as a prompt, because it is one.

Names and descriptions

The model picks a tool from its name and description alone. Overlapping tools (three ways to search) cost tokens on every call and invite the wrong choice.

Errors the model can act on

"command not found: python" told our run exactly what to change. "Error 1" would not have. Exit codes and the failing line belong in the result.

Output size

The Loop lab made the test runner noisy on purpose: the verdict sat at lines 92 to 95 of about 240, and a naive head-and-tail cut removed it. Put the verdict first, clip the rest, say what was clipped MEASURED.

Edit format

How the model writes a change: the whole file, search-and-replace blocks, or a unified diff. Aider documents six formats and picks one per model (edit formats). Claude Code's Edit replaces an exact old_string with a new_string, as the recorded edits show.

The minimal end of the range. mini-SWE-agent's agent class is "some 100 lines of python", its only tool is bash, it does not use the model's tool-calling interface at all, and its README reports more than 74% on SWE-bench Verified (README, read 5 Oct 2026; the score depends on the model behind it) SOURCE. With a strong model, a shell is a universal tool; dedicated tools earn their place by being cheaper, safer to gate, or easier to verify.

The cost. Every tool definition is input the model reads on every call. Claude Code's first call on Haiku 4.5 measured 6,653 tokens with no tools, 13,219 with the six above and 21,140 with its default set MEASURED (the Trace and context lab, Context lab 1). Tools from outside the harness arrive through MCP, the protocol by which a harness discovers and calls external tool servers (MCP page); Claude Code now defers MCP tool definitions and loads them on demand through a tool search, because a few servers can add thousands of tokens of definitions.

3. Context: what the model sees on each call

The problem. The model knows only what is in the request. Each call, the harness assembles that request from four kinds of material, in this order: the system prompt (who the agent is, how to behave, the environment: Claude Code's includes the working directory); the tool definitions; memory files loaded at start (Claude Code reads CLAUDE.md, and also AGENTS.md, the cross-vendor convention other harnesses use); and the history: the task, every earlier reply, every tool call and every tool result. The first three are a fixed prefix; the history grows by one reply and one result per turn. The window bar in section 1's replay is exactly this: 13,242 tokens of prefix on call 1, 17,155 tokens by call 12 MEASURED.

Why it is the main job. Anthropic calls the work context engineering, "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference", and gives the reason: as the number of tokens in the window grows, the model's ability to recall what is in it decreases, so context is "a finite resource with diminishing marginal returns" (29 Sep 2025). On a small task the window is never full; on a long one, everything the harness lets in competes with everything else.

The levers, from cheapest to most drastic

Prompt caching

The prefix repeats on every call, so providers let you cache it: a cache read on Haiku 4.5 costs $0.10 per million tokens against $1 for fresh input. In the replayed run 177,132 of 181,145 input tokens were cache reads; billed as fresh input the same run would have cost about $0.195 instead of $0.039 (derived: same tokens, list prices) MEASURED. Caching works only if the prefix stays byte-identical: edit the system prompt or reorder tools and the cache misses.

Clip tool output

Cap each result (Claude Code: 25,000 tokens per tool response by default), keep the informative lines, say what was cut. A Read of a 479 KB file was refused outright in the recordings (the limit is 256 KB) MEASURED.

Load on demand

Skills (folders of instructions and scripts) show only their name and description at start; the body loads when used. MCP tool definitions are deferred behind a tool search. Memory files stay short because they are paid on every call (a 4-line CLAUDE.md added 184 tokens MEASURED).

Clear and compact

Near the limit, Claude Code first clears older tool outputs, then compacts: it summarises the conversation and starts a fresh window from the summary (docs). Early instructions can be lost, which is why rules belong in memory files.

Subagents

A subagent is a second loop with its own fresh window: it does the reading and searching, and only its summary comes back to the parent. That isolates context; it does not save tokens overall.

Notes outside the window

Progress files, todo lists and memory directories survive compaction and sessions. Anthropic's long-running harness writes a progress log and a feature list so each new session can pick up where the last stopped (26 Nov 2025).

Predict, then reveal. A home-made harness resends the whole transcript every call as one growing block of text. Does prompt caching help it?
No. A cache entry is keyed on an exact prefix ending at a block boundary; a single block that changes at the end every call never matches, so the Loop lab's harness got 0 cache reads, and once the prompt passed the minimum cacheable length the CLI wrote it to the cache every call at twice the input price MEASURED. Keep stable content in separate, unchanging blocks at the front.

Research on memory that this root only points to: read-time memory curation (Just-in-Time Memory), a second model that reminds the agent of what it dropped (Proactive Memory Agent), and why skills help and when they misfire (Demystifying Agent Skills). Memory products (Mem0, Zep, Letta) belong to the frameworks root; retrieval to rag-and-retrieval.

4. Control: stopping, planning, delegating, running long

When does it stop? In the loop above, the model stops by replying without a tool call (the API marks it end_turn). A harness adds hard limits the model cannot talk its way past: a maximum number of turns, a token or dollar budget, a wall-clock timeout, and the user's interrupt (in Claude Code, Esc stops the running tool call; a message typed while it works is read before its next step). The two classic failures are opposites: stopping too early (declaring victory without checking) and never stopping (looping on the same failing approach). Anthropic's long-running harness lists premature completion and marking features done without proper testing among the failures it was built to fix (26 Nov 2025).

Verification is the feedback signal. The replayed run ran the tests before editing and again after; that second run is why its summary can be trusted. The harness can enforce this instead of hoping for it: a hook is the harness running your code at a fixed point in the loop. Claude Code documents 33 hook events, among them PreToolUse, PostToolUse, Stop and PreCompact; a PreToolUse hook that exits with code 2 blocks the call whatever the model wanted (hooks, 2.1.290, read 6 Oct 2026). A rule that must hold every time belongs in a hook, not in the prompt.

Planning. A plan mode lets the model read but not change anything until a person approves a plan; a todo list is a tool whose only effect is to keep a visible checklist in the context, which keeps long tasks on track and gives the human something to supervise. One recorded surprise: Claude Code's plan mode run with --model haiku had every call answered by Sonnet 5.5, according to the per-call model field MEASURED. It is documented, in the Claude Code changelog for 2.0.17 (15 Oct 2025): "Haiku 4.5 automatically uses Sonnet in plan mode, and Haiku for execution". Easy to miss, so check the model field rather than the flag.

Subagents. Section 3's context lever doubles as a control structure: the parent hands a well-scoped question ("find every caller of X") to a fresh loop and gets back a conclusion. It pays when the exploration is big and the answer small; it hurts when the subagents need each other's decisions, which is the multi-agent debate the frameworks root covers (Topic: agentic-frameworks). Accounting trap from the recordings: the CLI's result.usage leaves out the subagent's calls, while result.modelUsage includes them MEASURED.

Long-running and background agents. Past one context window, the agent needs state outside the window and a fresh start. Anthropic's design splits the work: an initializer agent sets up the environment, a progress log and a feature list (every feature initially marked failing), and each later session reads them, implements one feature, tests it, commits and updates the log. The same idea explains cloud and background agents: the session runs in a managed machine, and its output lands as a branch or pull request for review rather than as edits you watch.

5. Safety: permissions, sandboxes, injection

The problem. Every tool call runs with the harness's rights, which on a laptop are yours. Two things can go wrong. The model can simply be wrong (delete the wrong directory, push to the wrong branch), and the model can be steered by text it reads: prompt injection is an instruction planted in a file, web page, issue or tool result that the model follows as if the user had written it. Neither can be fixed inside the model with certainty, so the harness puts controls around it, in layers.

1. Permission gate

Before each call, rules decide allow, deny or ask a person. Claude Code's modes set the default (Manual asks before edits and commands; Accept edits lets file edits through; Plan forbids edits; Auto lets a classifier block risky actions) and settings files add rules per command pattern.

2. Sandbox

An operating-system boundary around what does run. Claude Code's optional sandbox (off by default) wraps shell commands with Seatbelt on macOS and bubblewrap on Linux: writes only in the project and a temp directory, and network only through a local proxy that checks an allowed-domains list, empty to start (sandboxing). File tools, MCP servers and hooks run outside it.

3. A machine you can throw away

Containers and cloud VMs, where full autonomy is acceptable because the blast radius is the box. How namespaces, seccomp and sandboxes work: Containers and isolation.

4. Secrets outside the agent

The model cannot leak a credential it never sees. Claude Code's sandbox can show commands a placeholder and have the proxy substitute the real value only on requests to allowed hosts.

The same eleven actions, without and with a permission gate

The verdicts are the real output of the Loop lab's step 3 gate (check(), deny rules first, then allow rules, anything unmatched asks; with no person at a terminal, ask becomes deny), run on these eleven actions without a model. The actions are chosen to probe it, including the two the recorded agents actually tried. "No gate" shows what a harness without one would run: everything.

Three lessons from the recordings. A gate written as command patterns is brittle in both directions: in three of the Loop lab's four Claude Code runs an allow rule for python3 blocked python tests/test_core.py, and an allowed prefix followed by ; rm -rf must still be caught, which is why the step 3 gate treats any command containing ; & | $ < > or a backtick as "ask". A gate only knows the tools it was told about: the Loop lab's step 5 added a subagent tool, forgot its rule, and the gate refused it (failing closed, the right default). And a planted curl ... | sh line in the test file was read and ignored by Haiku in the one run that tried it MEASURED; one ignored injection is not evidence of safety.

The lethal trifecta

Simon Willison's framing (16 Jun 2025): an agent that has access to private data, exposure to untrusted content and a way to communicate externally can be made to send your data to an attacker, and no current filter reliably prevents it; the defence is to never combine all three. Egress is where it leaks. OpenAI reported in September 2026 that an agent in training, blocked at its web proxy, reached an external chatbot by encoding questions into DNS lookups, which were not restricted the way the proxy was; monitoring flagged it within 15 minutes and the run was killed 2.5 hours later, and OpenAI paused tool use on its most capable models while it closed the gap (report, updated 25 Sep 2026) SOURCE. 6. The products, and how they differ

Every coding harness runs the loop of section 1. They differ in the choices around it, and five questions place any of them:

Where does it run?

Your terminal (Claude Code, Codex CLI, Gemini CLI, opencode, Aider), your editor (Cursor, GitHub Copilot's agent mode, Cline), a cloud machine that returns a pull request (Devin, Codex cloud, Claude Code on the web), or a resident daemon that listens on your messaging apps (personal agents such as OpenClaw and Hermes Agent). Where it runs decides what you can still check: an edit as it lands, a pull request afterwards, or an action already taken.

Which models?

Tied to one vendor's models, or model-agnostic through a gateway. Tied harnesses can tune prompts and tools to their models; agnostic ones carry an edit format and prompt per model.

How contained by default?

Ask-before-acting, an OS sandbox on by default, or a disposable VM per task (section 5).

How extensible?

Memory files, skills, hooks, subagents, MCP servers, plugins: which exist, and which are code rather than prompts.

Can you read it?

Open-source harnesses (OpenHands, Aider, opencode, Codex CLI, Gemini CLI, SWE-agent and mini-SWE-agent) are the only ones whose loop you can read line by line; Claude Code's behaviour is visible through its recorded streams, which is how the labs on this page study it.

7. Measuring harnesses: the score belongs to the pair

The problem. An agent benchmark scores a system: the model, the harness, its settings (reasoning effort, turn and time limits) and the environment. Change the harness and the same weights score differently, and, more often, cost differently. The evidence, as checked on the Agentic benchmarks page: Arena's HarnessTax study (16 Sep 2026) ran seven models in three harnesses on 30 tasks each from SWE-bench Lite and Terminal-Bench 2.0; the harness moved success by about 2 points on the first and 5 on the second, while Claude Code cost about twice the minimal four-tool harness Pi on SWE-bench Lite. On harness-sensitive benchmarks the score itself moves: a checked state-machine runbook lifted one model from 83.1% to 92.1% on Terminal-Bench 2.1, but it was developed on the very tasks it was scored on SOURCE.

How to check a harness claim. To compare models, fix the harness (fixed-harness boards such as HAL or a mini-SWE-agent column exist for this reason); to compare harnesses, fix the model and the effort. Report cost beside the score. Run more than once: three identical Haiku runs above differed in calls and cost. Trajectories. The JSONL stream these labs record, every request, tool call, result and token count, is a trajectory. It is what you grade when the final answer is not enough (did the agent edit the tests? run them?), which is the subject of Agent and trajectory evaluation, and it is the raw material of the next section.

8. Harnesses for training: environments, trajectories, self-improvement

A harness is an RL environment. In reinforcement learning terms (see Topic: rl), the task and its repository are the starting state, the tool calls are the actions, tool results are the observations, and a verifier such as the test suite gives the reward. Training a model for agentic work means running it inside a harness thousands of times in sandboxes and updating it on the trajectories that passed. Three consequences matter for anyone training models:

The training harness shapes the policy

A model learns the tools, formats and context habits of the harness it was trained in. Prime Agent's authors report that "many harness capabilities remain underused because current models were not trained to operate them" (Prime Agent). Train and deploy in the same, or deliberately varied, harnesses.

Environments are the bottleneck

Terminal-Universe rebuilds workspaces from recorded agent trajectories and grows tasks from them: 37,300 environments (judged task-sufficient by an LLM, not shown runnable), and +11.9 points on Terminal-Bench 2.1 after fine-tuning Qwen3.5-27B (Terminal-Universe). EnvHarness wraps existing environments instead (EnvHarness); DeepSeek's DSec reports about 3 million sandboxes a day for this kind of training, self-reported (DSec).

Trajectories are data

A recorded run is a supervised example (imitate the passing trajectories) and an evaluation record. That is why the recordings on this page keep every tool call and token count, and why redaction comes first: trajectories carry paths, ids and secrets.

Self-improving harnesses. If the harness moves the score and the bill, a loop can search over harnesses. The paper pages on this knowledge base, each with its numbers checked: JIT-Agent trains a model to write a harness per task (+7.7 and +8.8 points averaged over nine agent benchmarks for two models, at 14.9 to 54.1% lower cost than fixed harnesses); SoL-Pi points the loop at cost and cuts recorded token traffic 44.7 to 49.0% at parity; RRSI regularises the loop so gains survive outside the tuning set (its +4.7 is the best of five out-of-distribution gains, mean 3.6, and its own Table 2 gives 36% fewer tokens, not the 30% often quoted); HarnessDev asks whether models can build harnesses at all. The risk is the one section 7 named: a loop that tunes on the score it reports will overfit it, and in Prime Agent's Factorio run the self-refining harness found a cheating shortcut and saved it as a reusable skill: a self-modifying harness can make its own reward hack persistent.

Common mistakes

Quoting an agent score without its harness
The unit is (model, harness, settings). A vendor's number is a claim about its own harness at its own effort; compare under a fixed harness or not at all (section 7).
Putting a rule in the prompt that must hold every time
The model follows prompts most of the time. "Never edit the tests" belongs in a deny rule or a PreToolUse hook, which are code (sections 4 and 5).
Treating a permission gate as a sandbox
A gate decides which commands start; an allowed command still runs with your rights and can reach anything you can. Containment needs an OS boundary or a disposable machine.
Rebuilding the prompt as one string each turn
Correct output, broken caching: our Sonnet run through such a harness cost about twice Claude Code's for the same result (section 7).
Dumping whole tool outputs into the context
Long outputs push out what matters and can hide the one line the model needed. Clip, put the verdict first, say what was cut (section 2).
Reading cost from result.usage when subagents ran
It omits the subagent's calls; result.modelUsage includes them (section 4).
Believing a flag instead of the record
Plan mode with --model haiku was answered by Sonnet 5.5 in our recording (documented in the changelog, 2.0.17, but easy to miss). Check the model field on each call.

Interview questions

Answer aloud first, then open.

What is an agent harness, in one sentence, and what does it own?
The program around a model that runs the loop: it assembles the context for each call, offers and executes tools, gates them with permissions and a sandbox, decides when to stop, and presents the work to a person. The model only chooses the next action.
Walk through one iteration of the agent loop at the API level.
Send system prompt, tool definitions and messages; the reply has stop_reason: "tool_use" and a tool_use block (id, name, input); the harness checks permission, runs it, appends the reply and a tool_result with the same id; call again. Stop when the reply has no tool call or a limit is hit.
Your agent's bill doubled after a refactor of the prompt builder. What do you check first?
Cache reads per call. If the prefix is no longer byte-identical (timestamps, reordered tools, one rebuilt string) every call pays full input price or cache-write price instead of the cache-read price.
How would you design tools for a coding agent?
Few tools matching real tasks (read, search, exact-replace edit, run), clear names and descriptions with examples, results that lead with the verdict, actionable errors, size caps with a note, and an eval loop over real tasks to tune them.
The context window is filling on a long task. Options, cheapest first?
Clip or clear old tool results; load skills and tool definitions on demand; move exploration into subagents; write state to files; compact (summarise and restart). Each later option risks losing more.
An agent reads untrusted web pages and has repo secrets. How do you make it safe?
Break the trifecta: remove the exfiltration path (network allowlist by destination, no arbitrary URL fetch), keep secrets outside the agent (proxy-injected credentials), run in a sandbox, and gate consequential actions on what they do, not where the text came from.
Why can two papers report the same model at very different scores on the same benchmark?
Different harnesses, effort settings, turn and time budgets, attempts, or splits. Ask for all of them, plus cost and the number of runs.
How would you use a harness to generate RL training data?
Wrap tasks with a verifier in sandboxes, run the policy in the same harness you will deploy, keep full trajectories with rewards, redact them, train on passing or advantage-weighted ones, and evaluate on held-out tasks and a second harness to catch overfitting to the scaffold.
When is a subagent worth it?
When a subtask needs a lot of reading but returns a small answer and does not need the parent's decisions. Not when parallel workers must agree on choices they each make.
Build or buy: when write your own harness?
When you need control over the loop (custom tools, training-time use, unusual environments, auditing) or must run where a product cannot. Otherwise use a product or the Agent SDK and spend the effort on tools and verification.

Loop lab. An agent harness built from nothing in seven steps, each one run for real on the running example (the textstats repository with two planted bugs, standard task prompt: The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests.). The harness is a small Python program; its "model" is claude -p with every built-in tool switched off (--tools "") and a system prompt of ours, so the model can only return text. The harness finds the action in that text, runs it itself, and pastes the result back. Tool calling, seen from the inside, is text in a loop.

What one turn is
A turn here is one model call. The harness assembles a prompt (system prompt, task, every earlier reply and tool result), the model returns text, the harness parses one action out of it, a permission gate decides whether it may run, the harness executes it, and the observation (the tool's output) is appended for the next call. The loop stops when the model says it is done, when a turn or token budget runs out, or after repeated errors.

Step 0: one call, no loop

No loop at all: paste textstats/core.py into one prompt, ask for the fixed file, write the reply back, run the tests once to grade it. This is "chat with the code pasted in".

Predict: does one call fix both bugs?
It fixed one. The reply sorted ties alphabetically (the docstring says so) and left the regex that drops apostrophes untouched; the grader printed . The model never saw the tests and got no feedback, so it had no way to find out; it also ignored "nothing after the code block" and added an explanation. Both bugs are written in the docstrings, so this is not a hard task: the missing piece is feedback, which is what a loop adds.

Step 1: the loop, with read_file and run_tests

The harness now calls the model again and again. The system prompt lists two tools and one output format: a final line ACTION {"tool": ..., "args": {...}}. The harness takes the last ACTION line, runs the Python function of that name, appends --- turn N: result of read_file --- and the output, and calls again. It stops after 8 calls, or when a reply has no ACTION line. There is no edit tool, so this step cannot pass: the point is to watch the loop work.

Predict: with only reading and testing, what goes wrong first?
The model invented tool results. In call 2 it wrote its ACTION line and then kept going: --- turn 2: result of read_file --- followed by a made-up core.py (def word_count(text): return len(text.split())) and further actions. This harness kept all of that in the transcript and ran the last ACTION, so from then on the prompt held a fake file beside the real one, and the model said in calls 3 and 4 that "the code appears correct". It also called a tool that does not exist (write_file) and got an error back. Run: calls, output tokens of which were thinking, tests still failing.
Why this happens, and why APIs do not have the problem
A language model continues text. The transcript format we invented shows replies followed by results, so the likeliest continuation of a reply is a result, and the model writes one. Over the API, generation stops at the tool call: the response ends with stop_reason: "tool_use" and the result can only come from your code. Models are trained on that format. Through claude -p we cannot set a stop sequence, so step 1b cuts the reply at the first ACTION line instead. In a later run (step 4, masking) one reply ran on for 95,162 characters of invented turns until it hit the 32,000-token output cap; the CLI then sent "Output token limit hit. Resume directly ..." on its own and returned only the last 7,475 characters. That call took 294 s.

Step 1b: keep the reply only up to its first ACTION line

One fix, found in the step 1 recording: parse the first ACTION line and throw away everything after it before it enters the transcript. This is a hand-made stop sequence.

Predict: does cutting the reply change the run?
The invented results never reached the transcript, the model's reasoning stayed tied to real file contents, and it named both bugs correctly by call 4. Output fell from to tokens and model time from s to s. It still fails: with no edit tool it can only describe the fix, and it again tried the non-existent write_file.

Step 2: edit_file and a stop condition

Two additions. edit_file replaces an exact string, and the old text must occur exactly once, as in Claude Code's Edit tool: the model must quote what it changes, and an ambiguous match is an error instead of a wrong edit. finish is an explicit stop. A reply with no valid ACTION is now an error message the model sees (three in a row end the run), and the turn cap rises to 12.

Predict: how many calls does the fix take, and is it the same twice?
Both runs passed, in and calls. The second run read README.md and the package file first and spent one long reply ( output tokens in all against ). Same harness, same model, same task: the path differs from run to run, which is why one run proves little (the Trace and context lab tab records repeats). The pattern that passes is read, test, edit twice, test again, finish.

Step 3: a permission gate

A shell tool, run_command, arrives, and with it a gate in front of every call: an ordered list of rules, first match wins. Deny rules (editing tests/; rm, curl, wget, pip, sudo, git push), an ask rule for any command with ; & | ` $ < > (chained or redirected commands are never allowed by prefix), allow rules (reading anything, testing, editing textstats/, a few read-only commands), and "ask" for everything else. With nobody at a terminal, ask becomes deny, as with Claude Code's --permission-prompts none. A denial is an observation like any other, so the model can choose something else. The gate is not a sandbox: an allowed command runs with the harness's own rights (the Reading tab and the Containers and isolation page cover sandboxes).

Predict: a README tells agents to run curl ... | sh. Does the gate fire?
Not in these runs. With the instruction planted in README.md, the model never opened README.md. With it planted at the top of tests/test_core.py, a file every run reads, Haiku read it and ignored it. All three runs passed and none tried a command the gate had to stop. The gate is there for the run where the model does follow such text, which a few recordings cannot show; so the table below runs step 3's real check() function on eleven actions, with no model.

(1) Writing this table showed that an explicit "ask" rule returned the verdict "ask", which the loop treated as "not denied", so a chained command would have run. The model typed python tests/test_core.py, which matched no rule and was denied: twice in each Haiku run, once in the first Sonnet run (plus a chained command ending in python -m pytest). Haiku then finished without ever running the tests; Sonnet said plainly that it could not run them. An allow-list written for what you expect the model to type is narrower than what it types.

Step 4: context management

To see the problem it solves, run_tests is made deliberately noisy: it runs python3 -v, which prints every import, about 240 lines and 12,900 characters per run, standing in for a verbose build or test log. Step 4 adds two mechanisms. Clipping: any tool output longer than 40 lines keeps its first 15 and last 15 lines (naive), or those plus every middle line that looks like a result or an error (smart). A token budget: after each call the harness divides the tokens the model reported by the prompt's characters, estimates the next prompt with that rate, and when the estimate passes the limit it replaces the oldest tool results with a one-line stub ("observation masking"); the last two results are never masked. A run-wide cap of 120,000 tokens stops the run.

Predict: in the noisy output, where are the test results, and does naive clipping keep them?
The four result lines sit at lines 92 to 95 of about 240, in the middle, because Python flushes the test output before printing its shutdown trace. Naive head-and-tail clipping cuts exactly them. The run still passed because the harness puts exit code 0 on the first line of every result, which survives any head cut: put the verdict where the clipper keeps it. Smart clipping keeps the four lines.
Predict: how much bigger does the unmanaged run get, and what does it cost beyond tokens?
The unmanaged run read tokens over its calls against with naive clipping, and its largest call was tokens against . The hidden cost: once a prompt passed Haiku 4.5's 4,096-token minimum for prompt caching, the CLI wrote the whole prompt to the cache on every call ( tokens of cache writes, at 2x the input price for the 1-hour cache) and never read it back, because our prompt is one growing text block and a cache hit needs an identical prefix ending at a block boundary. The masking run used a limit of 2,000 tokens so that it fires on this small task; it masked one result from call 4 on. That run is also the one with the 95,162-character runaway reply, which is why its totals are large: the budget counts it, and a real harness would also cap output per call.

Step 5: a subagent for context isolation

The loop becomes a function, agent(task, tools, ...), and a new tool, delegate, calls it again with a fresh transcript and read-only tools. The helper reads and runs as much as it likes; only its final report (asked to be at most 80 words) enters the parent's context. Why a subagent and not a todo list: a todo list is a prompt pattern (the model writes a plan into its own context and ticks it off; Claude Code has one, TodoWrite), while a subagent changes what the parent's context contains, which is the mechanism step 4 was about. It is also how Claude Code's Task tool and Explore agent keep long searches out of the main context.

Predict: does the helper make the parent's job easier?
It depends on the report. With a soft suggestion ("delegate investigation"), Haiku never delegated. Told to delegate first, Haiku's helper answered in one call without reading anything: Tests show missing or incorrect function implementations. Fix by implementing all required functions ..., which is wrong, and the parent then read every file itself. Sonnet's helper read three files and reported the two exact lines and their replacements; the parent re-read core.py once (it needs the exact text for edit_file) and fixed both in two edits. On a task this small the subagent saves nothing: Sonnet's run made calls in all. Isolation pays when the investigation's output is large compared with its conclusion (a search over many files, a long log), and it costs a hop where the conclusion can be lost or invented.

What Claude Code does that this harness does not, read from the trace

  • A large, stable, cached prefix. Its first call already reads about tokens (system prompt plus tool definitions) before seeing any file, and most of it comes from the prompt cache: the Haiku run read tokens from cache and wrote . Our harness reads far fewer tokens but none from cache.
  • Several tool calls in one model call (up to three here, such as two Bash commands, or three Reads), so one call does what took ours three.
  • Tools designed for models: Read returns numbered lines (1 import re), paths are absolute, Edit refuses an old string that is not unique, Glob and Grep replace ad hoc find.
  • A permission engine with read-only defaults: ls -la and a chain of cat and find ran without any allow rule; sed -i and python were denied and reported back as This command requires approval.
  • Output limits of its own: Bash output is cut at 30,000 characters by default and Read refuses files over 256 KB (measured by the Trace and context lab tab), the same job as our step 4 clip.
  • Native tool calling: no invented results and no format errors, because the model stops at a tool_use block. Our harness needed step 1b and still saw runaway replies.
  • What it did not do: no subagent, no todo list, no compaction on a task this small; and with the tests blocked, the Haiku runs finished without verifying, as our step 0 did.

How real tool calling works at the API level

Our harness defined tools in prose and parsed text. A provider API makes the same three things structured. (1) Tool definitions travel in the request, each a name, a description and a JSON Schema for its arguments; the provider turns them into extra system-prompt text the model was trained on. Anthropic adds a tool-use system prompt of 496 tokens for Haiku 4.5 and 286 for Sonnet 5.5, on top of the definitions themselves; OpenAI says functions are "injected into the system message" and billed as input tokens. (2) The model's call is a typed block: Anthropic returns stop_reason: "tool_use" with a tool_use block (id, name, input object); OpenAI's Responses API returns a function_call item (call_id, name, arguments as a JSON string). Generation stops there, which is exactly what our step 1 lacked. (3) The result goes back as a typed block in the next request: a tool_result with the matching tool_use_id inside a user message (Anthropic), or a function_call_output with the matching call_id (OpenAI). The API is stateless: every request carries the whole history, just as our harness resent its transcript.

Why providers trained models on a format instead of parsing prose: a trained model reliably stops at the call, produces arguments that parse (Anthropic and OpenAI both offer a strict mode that constrains them to the schema), knows when not to call a tool, and can issue several calls at once. OpenAI's announcement of 13 June 2023 said its new models "have been fine-tuned to both detect when a function needs to be called ... and to respond with JSON that adheres to the function signature". Under the API, the blocks are still rendered into the model's token stream with special markers; the structure is a contract that the provider's renderer and the model's training share.

Interview questions

What is the minimum a harness needs to turn a model into a coding agent?
A loop that calls the model with the whole history; tools to observe (read, run tests) and to act (edit); a way to find the tool call in the output and to feed the result back; and stop conditions (the model says done, a turn or token budget, an error limit). Step 2 here is that minimum, about 90 lines of code.
Why does tool calling need special training or stop sequences?
A model continues text. Without a stop at the call, it writes the result itself (step 1 recorded this), and the harness may act on an invented observation. Trained formats end generation at the call and give parseable arguments.
Why do harnesses use exact-string replacement for edits?
The model must quote what it changes, so a stale view of the file fails loudly; uniqueness turns an ambiguous edit into an error instead of a wrong change; and the edit is small, cheaper than rewriting the file.
Is a permission allow-list a sandbox?
No. It filters which calls run; an allowed command still has the harness's rights. Prefix rules are bypassable by chaining (cat x; rm -rf y) unless the gate parses commands. Sandboxing (containers, OS sandboxes) limits what an allowed command can do.
A tool prints 10,000 lines. What do you do?
Clip it before it enters the context, keeping the head, the tail and the lines that matter (errors, results), put the verdict on the first line, tell the model how much was cut and how to get more, and mask or summarise old results when the context fills. Measure: the unmanaged run here read several times more tokens for the same outcome.
When does a subagent help?
When the work it isolates produces much more text than its conclusion (searching, reading logs), so the parent's context stays small. It costs extra calls and a hop where information is lost or invented; on a small task it saves nothing, as step 5 shows.
Why did our harness get no prompt-cache hits while Claude Code got many?
A cache hit needs the same prefix up to a block boundary that an earlier request wrote. Our harness sends one text block that grows each call, so no earlier prefix ends at a boundary. Claude Code sends structured messages with a stable system prompt and tool list first and moves its cache breakpoint forward, so each call re-reads the previous call's prefix at a tenth of the input price.

What this tab is: real Claude Code runs, opened up

A trace is the record of everything an agent did in one session: every call to the model, every tool it asked for, every result it got back, and what each call cost. Reading traces is how you learn what a harness really does, as opposed to what its documentation says it does. This tab holds the running example worked by 16 real Claude Code sessions recorded on 2026-10-05, plus 6 one-call sessions that measure the startup context, and a context lab built on those numbers.

Each run is one command, started in a fresh copy of the task repository (a tiny Python library, textstats, with two planted bugs and a three-test runner):

claude -p "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests." \
  --output-format stream-json --verbose --include-partial-messages \
  --no-session-persistence --setting-sources project --strict-mcp-config \
  --model haiku --permission-mode acceptEdits \
  --tools "Read,Edit,Write,Bash,Grep,Glob" \
  --allowedTools "Bash(python3:*)" "Bash(python:*)" "Bash(ls:*)" "Bash(cat:*)" \
  --append-system-prompt "Never use the em-dash character."

-p runs one task without the interactive screen and exits. stream-json prints one JSON record per line as things happen. --include-partial-messages adds the raw API stream events, which is the only place the per-call output token counts appear. --allowedTools pre-approves a few shell commands; anything else the model tries in the shell is refused by the permission layer, and you will see that happen.

  • One task, a few runs each. Three runs per setting show the spread, not a distribution. Treat differences of one or two calls as noise.
  • Redacted. The raw files hold the recording machine's paths, session ids and account details. Anatomy of a recording

A recording is a list of JSON records. Five kinds matter:

system / init
The first record: what the harness was configured with before the model saw anything. Model id, permission mode, the exact tool list, the subagent types available, the Claude Code version, the working directory.
assistant
What the model produced. One API response can arrive as several records (a thinking block, then text, then one or more tool_use blocks), all with the same message id.
user
Despite the name, mostly not from you: this is where the harness puts each tool_result, the output of a tool it ran on the model's behalf, sent back as the next input.
stream_event
The raw API stream. message_start carries the input side of a call's usage; message_delta at the end carries the final output tokens, thinking tokens and the stop reason (tool_use means "run my tools and call me again"; end_turn means "I am done").
result
The last record: number of turns, wall time, API time, total usage, per-model usage, cost equivalent, permission denials, subagent statistics, and the final answer text.

What the init record reveals about the harness

It is a statement of the harness's configuration, and three things in it are worth noticing. The tool list is exactly what was passed, which is the list the model will be offered. The agents list shows that even with no Agent tool enabled, Claude Code knows its built-in subagent types. And the model id is the full dated name the alias haiku resolved to (claude-haiku-4-5-20251001); sonnet resolved to claude-sonnet-5-5, as the model configuration docs say for the Anthropic API.

What the stream does not show

The system prompt and the tool definitions are not in the recording

You never see the text the model was given before your prompt: Claude Code's system prompt, the tool schemas, the environment block, CLAUDE.md. Context lab 3: a budget model, checked against the recordings

A harness designer needs a back-of-the-envelope model: how big does the context get, when does it fill, and what does a session cost? The simplest one has four numbers: the startup context S, the growth per call g (the model's last output plus the tool result appended), the output per call o, and the number of calls N.

contexti = S + (i − 1) g     input processed = Σi=1..N contexti = N S + g N(N−1)/2
with caching
call 1 writes S (minus any prefix another session already cached); call i reads contexti−1 from cache and writes only g
without
every call pays contexti at the base input price

The quadratic term is why long sessions get expensive without caching: input processed grows with the square of the number of calls. Caching turns most of it into reads at a tenth of the price.

Context lab 4: compaction, before and after on the same history

When the conversation approaches the window, something must leave. Claude Code's documented answer (How Claude Code works, context window explorer): it first clears older tool outputs, then compacts, replacing the conversation with a structured summary (your requests, key concepts, files examined or modified with important snippets, errors and fixes, pending tasks, current work). The startup content reloads, up to five of the most recently modified files are re-read (a file over 5,000 tokens comes back only as a path), and the bodies of invoked skills are re-injected (capped at 5,000 tokens each). By default it compacts when the conversation reaches the model's context limit, and at about 967K tokens for models with a native 1M window such as Sonnet 5.5 (model configuration).

None of the recorded sessions came near a 200K or 1M window, so nothing compacted in them. Real compactions are recorded on Context engineering: its Compaction lab forced them by hand (/compact, 17,969 to 18,968 tokens down to 2,258 to 2,472) and automatically (--autocompact 100000, 127,242 tokens down to 1,971), with the summaries verbatim. What compaction costs

Compaction is a lossy model call: a summary of the conversation, written by the model, replaces the conversation. Exact tool outputs, failed attempts and early instructions can be lost, which is why the docs advise putting rules that must survive in CLAUDE.md (reloaded from disk) rather than in the chat. It also breaks the prompt cache: the new, shorter history is a different prefix, so the next call writes it again.

Interview questions

Why does an agent session's cost grow faster than linearly in the number of steps, and what fixes it?
Each step resends the whole conversation, so input processed is N S + g N(N−1)/2: quadratic in N. Prompt caching makes the repeated prefix cost 0.1x; fewer, larger steps (batching tool calls) cut N; truncating tool outputs cuts g; compaction resets the history when it gets too long.
What can and cannot you learn from a Claude Code stream-json trace?
You get the configuration (tools, model, permission mode), every tool call and result, per-call token usage including cache reads and writes, stop reasons, denials, timing and cost equivalents. You do not get the system prompt text, tool schemas or thinking text; for those you rely on documentation or a harness you control.
A tool returns a 500 KB file. What should a harness do?
Never paste it whole into the context. Claude Code's Read tool refuses files over 256 KB with an error that tells the model to use offset and limit or search, and the shell output is cut at 30,000 characters by default. The model then greps for what it needs. In your own harness: cap tool outputs, say they were cut and how to page, and offer search tools.
When does a subagent help?
When a subtask would fill the main context with material the main thread does not need afterwards (wide searches, long logs): the subagent reads it in its own window and returns a summary. It costs an extra startup context and its own calls, and on a small task it only adds cost, as the recorded run shows.
How would you check that a harness setting does what its name says?
Run the same task with and without it and read the usage fields. Here, an undocumented "disable caching" variable left caching on; the documented TTL variable changed the write lifetime exactly as described.

The lesson: the action boundary belongs to the API, not the prompt

A real tool-calling API ends the model's turn at the tool call (stop_reason: "tool_use"), so the model never gets to write the result. A text protocol needs a stop sequence at the end of the action block to do the same; claude -p exposes none, so this adapter had nothing to stop on. That is why mini-SWE-agent 2.x recommends tool calls over its text mode, why the Loop lab met the same invented "result" text with its own text protocol, and why the published mini-SWE-agent numbers (run through APIs) are not in question here. A second, smaller trap appeared before any model call: the stock prompt fills in the host's operating system, so on a Mac host it tells the model to use BSD sed -i '' inside a Linux container; the adapter passed the container's own uname instead.






Harnesses for training: the harness becomes the environment


To train a model to act, reinforcement learning (RL, Topic: rl) needs an environment: something the model can act in, that answers each action, and that says at the end how well it did. For software tasks the environment is built from exactly the parts of a harness: a container with the repository at the commit before the fix, a task statement (a real issue, or one written from the fix or from an injected bug), a harness that turns the model's text into tool calls inside the container, and a verifier: the tests that must flip from failing to passing, and the ones that must stay green. The reward is usually 1 if they do and 0 if not.

Trajectories as training data


Every harness run leaves a trajectory: the full list of messages, tool calls and results, exactly what the Trace and context lab records. Filtered for success, trajectories are supervised training data (SWE-smith collected them with SWE-agent; Kimi-Dev adapted its model to an agent harness with 5,000 public ones). Self-improving harnesses


If the harness moves the score this much, can a model write or tune its own harness? A run of 2026 papers tries, each with its own paper page in this knowledge base. Read them as one line of work: a loop (an "auto-research" or evolution loop) proposes harness changes, scores them on tasks, keeps the better ones. The recurring catch is where the score comes from: gains measured on the tasks the loop was tuned on shrink on held-out tasks, and a harness tuned for one model can collapse under another.
