Personal agents: OpenClaw, Hermes Agent, and how they differ from coding harnesses

An agent that never ends: it lives in a background process, hears you on the chat apps you already use, wakes itself on a timer, keeps notes about you for months, and acts on your mail, calendar and accounts. Taught from zero: what such a resident agent is made of, how OpenClaw and Hermes Agent build it (read from their docs and source at pinned versions), and why trust, verification and undo, not the agent loop, are what separate it from a coding harness. With a small resident agent built for this page and recorded against a fake inbox (no real account touched). A child of Topic: agentic-harnesses. Data as of 6 October 2026. About 35 min to read.

In one screen

A coding harness such as Claude Code (Claude Code, taken apart) is invoked: you open a session in a repository, it works, the session ends. A personal agent is resident: a background program that never ends, receives messages on the chat apps you already use, wakes itself on a timer to check whether anything needs doing, keeps notes about you for months, and acts on your accounts (mail, calendar, payments) rather than on a repository. Inside, it runs the same agent loop the parent page teaches (Topic: agentic-harnesses, Reading section 1). What changes is everything around the loop: who can write into its context, what authority it holds while nobody watches, and what can check or undo its work.

Three ideas to keep
  1. Same loop, different boundary. The loop, tools, compaction and skills are the coding-harness vocabulary; the difference is that the input channel is open to strangers and the output acts on accounts with no test suite and little undo.
  2. Put enforcement where text cannot reach it. A plain-code gate that knows which actions cannot be undone, approvals shown outside the conversation, and credentials the model never sees (sections 6 and 9).
  3. Never-ending sessions need tiers of memory and rules for interruptions. What stays in every prompt, what is searched when needed, and what happens to a message that arrives while the agent works (sections 4 and 5).

1. From invoked to resident: the pieces, from zero

The problem. An agent loop (call the model, run the tool it asks for, append the result, repeat until it stops) needs something to start it. In a coding harness that something is you, typing in a terminal. A personal agent should act when an email arrives at 07:40 or when you text it from a bus, and should notice on its own that a bill is due. So the loop has to live inside a program that is always running and that turns events from the outside world into runs.

The pieces, in the order a message meets them (names as OpenClaw uses them; Hermes Agent has the same shapes, section 3):

  1. Channel adapter: code that speaks one messaging platform's protocol and turns an incoming message into an event (OpenClaw uses the Baileys library for WhatsApp and grammY for Telegram). OpenClaw lists more than 20 channels, from Discord and iMessage to Signal, Slack and Teams DOCUMENTED.
  2. Gateway: one long-lived process that owns every channel and every session. In OpenClaw, "A single long-lived Gateway owns all messaging surfaces", there is one per host, and the apps, CLI and web UI talk to it over a WebSocket on 127.0.0.1:18789 by default DOCUMENTED (architecture).
  3. Trigger: what starts a run. Four kinds: a message from you (or from someone else), a heartbeat (a timer that wakes the agent to check a short checklist; OpenClaw's default is every 30 minutes, or 1 hour when it reuses an Anthropic subscription login, and a reply of NO_REPLY means nothing needed attention and is dropped), a scheduled job (cron), and a webhook DOCUMENTED (heartbeat).
  4. Session routing: which conversation history an event joins. OpenClaw's defaults: all direct messages share one main session, each group chat gets its own, each scheduled job starts a fresh session, each webhook is isolated. The docs warn: "If multiple people can message your agent, enable DM isolation. Without it, all users share the same conversation context, so Alice's private messages would be visible to Bob" (setting dmScope: per-channel-peer, the recommended value) DOCUMENTED (sessions).
  5. Agent runtime: the loop itself, with tools, a system prompt assembled from files, and compaction when the window fills. This is the part a coding harness already is; OpenClaw can even hand a turn to Claude Code or Codex as the runtime (section 2).
  6. Delivery: the reply goes back out on a channel; heartbeat alerts go to your own direct messages by default.
Animation, illustrative schedule (not a recording): the same six events of one day, met by an invoked harness (top) and by a resident agent (bottom).

What it costs. A process that must stay up (a laptop that sleeps misses its heartbeats; people use a small server), a model call on every heartbeat even when nothing happened (the reason heartbeats are checklists answered with one token, and why OpenClaw lengthens the interval on a subscription login), and an open door: a gateway listening on a network port, and channels that let anyone who knows your number put text in front of the model. Sections 6 to 8 are about that door.

Predict: a heartbeat fires every 30 minutes and its checklist prompt is about 3,000 tokens. Roughly how many input tokens a day does the heartbeat alone send, before anything is found?
48 heartbeats x 3,000 = 144,000 tokens a day, every day, for nothing found. Whether it matters depends on caching: a stable prefix (system prompt and checklist unchanged between ticks) is read from the prompt cache at a tenth of the input price on Anthropic models, but only if the cache entry is still alive; a 5-minute cache entry has expired by the next 30-minute tick, a 1-hour one has not, and a prefix shorter than the model's minimum (4,096 tokens on Haiku 4.5) is never cached at all (Context engineering, section 2, owns the cache rules). The 3,000-token prompt is an assumption for the drill.

2. OpenClaw, taken apart

Read from its docs (docs.openclaw.ai, every page also served as markdown) and repository on 6 Oct 2026, release v2026.9.8. The installer provisions Node.js itself; the npm route needs Node 24.16+ or 26.1+, then openclaw onboard --install-daemon, which "verifies model access, creates the workspace, and configures the Gateway" DOCUMENTED (README).

Four layers that can be swapped separately

OpenClaw separates the provider (who serves the model), the model (written provider/model, split on the first slash, so openrouter/moonshotai/kimi-k2 works), the agent runtime (who runs the loop) and the channel (where messages enter and leave) DOCUMENTED (agent runtimes). The runtime layer is the interesting one for this topic:

  • Embedded harnesses run inside OpenClaw's own prepared loop: the built-in openclaw runtime, plus plugin runtimes codex and copilot (the latter opt-in, never picked automatically).
  • CLI backends run a local CLI process: claude-cli means "select the Anthropic model, execute through Claude CLI". The bundled Codex CLI backend was removed in v2026.5.14.
  • External harnesses attach over ACP (the Agent Client Protocol): "Claude Code, Gemini CLI, OpenCode, Cursor, and similar external harnesses still use ACP."

For a runtime it does not own, the docs ask a fixed list of compatibility questions: who owns the model loop, who owns the canonical thread history, whether OpenClaw's own tools and its before_tool_call/after_tool_call hooks still fire, whether the context-engine lifecycle runs, what compaction data is exposed, and what is intentionally unsupported. With the Codex runtime, for example, Codex owns the loop and the thread (OpenClaw keeps a mirror) and compaction is Codex's own; channel delivery stays with OpenClaw DOCUMENTED. That list is the clearest statement anywhere of what "a harness hosted inside another harness" has to settle, and it makes the personal agent a host for coding harnesses rather than a rival (section 9).

The workspace: files that become the system prompt

Each agent owns one directory, its only working directory for tools. On the first turn of a new session OpenClaw injects these user-editable files into the system prompt's "Project Context" DOCUMENTED (agent, system prompt, workspace):

Caps: 20,000 characters per file and 60,000 across all of them (bootstrapMaxChars, bootstrapTotalMaxChars); a longer file is cut with a marker and the prompt says which files were truncated. Day-by-day notes live in memory/YYYY-MM-DD.md and are not injected: the agent reads them on demand through memory_search and memory_get DOCUMENTED. Two old files are gone: the heartbeat checklist moved from HEARTBEAT.md into a database "monitor scratch" ("The runtime never reads HEARTBEAT.md"), and TOOLS.md became a section of AGENTS.md.

Skills, sessions, and messages that arrive mid-run

  • Skills (a folder with a SKILL.md, loaded by description first and body on demand, as in Claude Code) resolve from seven tiers, highest first: workspace skills/, <workspace>/.agents/skills, ~/.agents/skills, managed skills in the state directory, the agent's "workshop" skills, bundled skills, then extra directories and plugin skills; the highest source wins a name clash DOCUMENTED (skills). ClawHub (clawhub.ai) is the public registry for skills and plugins; section 8 covers what happened there.
  • Sessions are owned by the gateway and stored in a per-agent SQLite database (~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite); JSONL transcripts are now only legacy imports and exports. The main session's key is agent:<agentId>:main DOCUMENTED.
  • Mid-run messages are "steered into the current run by default", with three alternatives (/queue followup, collect, interrupt). Section 4 has the exact rule and our recordings.

3. Hermes Agent, taken apart

Read at release v0.21.5 (git tag v2026.9.24, commit f97608f, 24 Sep 2026): its docs live in the repository under website/docs/. The release notes of v0.2.0 (12 Mar 2026) say it went "from a small internal project to a full-featured AI agent platform" in "just over two weeks"; that release already shipped the messaging gateway DOCUMENTED.

One agent class, many front doors

The architecture page's first design principle: "One AIAgent class serves CLI, gateway, ACP, batch, and API server. Platform differences live in the entry point, not the agent." (run_agent.py is now a facade; the loop lives in agent/conversation_loop.py.) Around it: a tool registry the architecture page counts as "70+ registered tools across ~28 toolsets" while the tools reference at the same tag says "~100 tools"; terminal commands can run on 7 backends (local, Docker, SSH, Daytona, Modal, Singularity, Vercel Sandbox); the gateway has "25+ platform adapters"; and "SQLite-based session storage with FTS5 full-text search" where sessions keep a parent/child lineage across compressions DOCUMENTED (architecture). Memory providers and context engines are plugins, one of each active at a time.

The learning loop: skills it writes for itself

The problem it attacks. A resident agent repeats the same chores for months. A coding harness forgets how it solved something when the session ends unless you write a skill by hand; Hermes tries to write and maintain them itself.

  1. Two kinds of note. "memory stores small durable facts that should always be in context, while skills store longer procedures that should load only when relevant." MEMORY.md is capped at 2,200 characters (about 800 tokens) and USER.md at 1,375 (about 500), both injected into the system prompt; memory "does not auto-compact" DOCUMENTED (memory).
  2. Two triggers for writing a skill. The system prompt asks the agent to record a workflow worth repeating, one where it hit dead ends, or one the user corrected, with the skill_manage tool. Separately, after a turn that used at least creation_nudge_interval tool iterations (default 10), the agent forks a copy of itself in a background thread that replays the conversation and asks whether any skill or memory should be saved or updated (up to 16 iterations, same model by default; the source notes "the fork costs ~30K tokens / event"; skipped for scheduled jobs and interrupted turns) SOURCE (agent/turn_finalizer.py, agent/background_review.py).
  3. Patching in use. skill_manage can create, patch, delete and write files; targeted patches are preferred; every change is appended to ~/.hermes/skills/.curator_ledger.jsonl.
  4. A curator for the pile. hermes curator tracks how often each agent-created skill is viewed, used and patched and moves unused ones active to stale (14 days) to archived (30 days; archived, never deleted), checked at most every 168 hours when the agent has been idle 2 hours. Merging overlapping skills with a model is off by default ("a full curation sweep typically takes 50-100 API calls"). Pinned skills and skills used by scheduled jobs are never touched DOCUMENTED (curator).
  5. Review before commit, if you ask for it. With skills.write_approval: true every skill write is staged under ~/.hermes/pending/skills/ for /skills pending, /skills diff, /skills approve; memory has the same switch. Both are off by default; so is scanning the agent's own new skills for risky content, because "the agent can run the same code via terminal() ungated" (config comment) SOURCE.

What it costs, and how to check it. Each background review is another model call over the whole conversation; a skill written from one lucky run can encode the wrong lesson, and a memory file the agent edits is a place where text it read can persist into every later prompt (the reason Hermes scans memory entries for injection and exfiltration patterns before accepting them). The check is the ledger: read what the agent wrote and why. The research version of this idea, agents that improve their own harness, belongs to Harnesses for training.

Never-ending context, scheduled work, trajectories

  • Compression runs at two levels: a gateway safety net at 85% of the window before a message is handled, and the agent's own compressor at a threshold of 0.50 of the window, raised to 0.75 for windows under 512K tokens and capped at 256,000 tokens. It first clears old tool outputs over 200 characters, keeps the first 3 messages and a recent tail, and summarises the middle with an auxiliary model into fixed headings (Goal, Constraints and Preferences, Progress, Key Decisions, Relevant Files, Next Steps, Critical Context) SOURCE (agent/context_compressor.py; the docs' own worked example of 100,000 tokens for a 200K window ignores the 0.75 floor in the code, which gives 150,000). Context engineering owns compaction in general.
  • Searching old sessions: the session_search tool runs FTS5 queries over ~/.hermes/state.db and "return[s] actual messages from the DB, no LLM summarization"; section 5 tests whether a model uses such a tool when it should.
  • Scheduled jobs are "first-class agent tasks (not shell tasks)": each runs in a fresh session, can attach skills, and delivers to any platform; "Cron-run sessions cannot recursively create more cron jobs." DOCUMENTED
  • Trajectories: sessions export as ShareGPT-format JSONL "for use as training data, debugging artifacts, and reinforcement learning datasets". The first releases (March 2026) also shipped Atropos RL environments and an optional Tinker training path; at v0.21.5 neither is in the dependency list or the source tree SOURCE. Trajectories as training data belong to Harnesses for training.
  • Moving from OpenClaw: hermes claw migrate imports persona, memory (daily notes merged into MEMORY.md), skills, model settings, MCP servers, channel tokens and allowlists, always with a preview and a backup; API keys only with --migrate-secrets, and only from an allowlist; heartbeat, cron jobs, plugins and hooks are archived, not imported DOCUMENTED (migration guide).

Usage signal, one day only: OpenRouter's "Top Apps by Token Volume" for 6 Oct 2026 ranked Hermes Agent first (1.86T tokens) and OpenClaw eleventh (208B) (openrouter.ai/apps). It counts only traffic routed through OpenRouter, so it says nothing about direct API use.

4. Messages that arrive while the agent is working

The problem. In a chat, a correction sent thirty seconds after a request is normal ("wait, not that one"). A coding harness was built for a person who types a task and watches; a resident agent receives messages whenever people send them, including while a run is halfway through. The harness has to decide where such a message goes, and the choice decides whether an irreversible action happens before the correction is read.

Four policies (OpenClaw's names):

  • steer: put the message into the current run at the next safe boundary, so the model reads it before its next decision;
  • followup (Hermes calls it queue): finish the current run, then run the message as a new turn;
  • collect: like followup, but merge several queued messages into one later turn after a short wait;
  • interrupt: abort the current run and start again with the new message.

Exactly where the boundary is. OpenClaw steers by default. It never interrupts a tool that is already running; in a reply with several sequential tool calls it starts the first one without checking, then checks before each later one and skips the rest with a synthetic result ("Skipped to process an incoming message."); after the batch settles "it appends the exact drained steering messages after the tool results, before the next LLM call"; parallel batches are never skipped DOCUMENTED (queue steering). Hermes defaults to a redirecting interrupt: "messaging a busy agent redirects its active turn (a running foreground terminal command is moved to the background rather than killed, so your message is read immediately)", applied "at the next tool-result boundary"; queue and steer are options, /stop is a hard stop DOCUMENTED (Hermes messaging). Both projects therefore make the same choice in different words: the newest message wins, at a tool boundary.

What the recordings show. With follow-up delivery and no gate, the booking reply went to the garage before the correction was read in all 4 runs (Haiku 3 of 3, Sonnet 1 of 1), and in 3 of those 4 the follow-up run sent a second message to undo it ("Please cancel my earlier confirmation"; the fourth only drafted one): an irreversible mistake, then an apology. A held action outlives its context

In both gate-on follow-up runs the agent, having read the correction, could not withdraw its own held reply: the approval queue still held "please book Thursday 10:00" at the end, waiting for Sam to tap approve. Sonnet noticed and messaged Sam to "reject A1"; Haiku wrote that since the reply "is held for approval and hasn't been sent yet, I won't confirm it", which changed nothing: this page's agent has no tool to withdraw a held action. Lessons for your own design: give the agent a way to withdraw a pending action, expire pending actions when a newer message in the same conversation arrives, and show the approval with the context that produced it.

One bug in this page's agent, found in the recordings and left visible: with the gate off, its remember tool had no implementation and answered "error: unknown tool" (the gate-on path stages the write instead). It affects only the memory notes of the no-gate runs, not whether anything was sent.

What the recordings show. Haiku never used the search tool when it was merely available (0 of 3 runs searched, 0 of 3 right; without the tool, also 0 of 3): it checked the calendar and answered as a scheduling question. One sentence in the system prompt ("Before advising on anything that recurs, search past sessions first") made it search every time and answer right every time (3 of 3). Gateway retrieval got 1 of 3 right: the gateway's top four hits included the August quotes and "Sam booked it for 3 September", but not the line saying the service had happened, and Haiku twice asked whether Sam still wanted Kwik Garage instead. Sonnet searched on its own and was right in every configuration except the one without history. Small samples (3 and 1 runs): read them as a demonstration of failure modes, not as rates.

  • "The model never searches" is a real failure mode for a cheap model with a tool it is not told to use; a rule in the prompt fixed it here.
  • Retrieval by the harness is only as good as its query and its cut-off: words taken from the message, the top four hits by BM25, and the deciding line ranked fifth.
  • Lexical search needs stemming. With FTS5's default tokenizer, "service" does not match "serviced"; this page's history uses the Porter stemmer (tokenize='porter'), found while testing before the runs.
  • A strict parser can fake an empty memory. In the first batch Haiku sometimes put its arguments next to "tool" instead of inside "args"; the first version of this page's parser dropped them silently, so a search ran with an empty query, returned "no matching past sessions", and Haiku told Sam "The search found no record of this year's service". That run is kept (s2_haiku_hintbug_1 in the list) as evidence; the parser now accepts both forms and logs which it saw, and all other runs were recorded after the fix.

6. The trust boundary: who can write into the context, and what the agent may do alone

The problem, in one sentence. Everything the model reads is text, and it cannot reliably tell an instruction from a fact; so whatever reaches its context can steer what it does with your authority. Agent security teaches this from zero (its sections 6 and 7: prompt injection, and the "lethal trifecta" of private data, untrusted content and a way to communicate out). A personal agent has all three legs by design: it reads your mail, anyone can send you mail, and it can send messages. That is the whole difference from a coding harness in one line, and it is why this section is about where to put enforcement, not about attacks.

Who can put text in front of the model

SourceTrusted?Typical control
You, in your own direct messagesYes, if the channel is really youPairing and allowlists; a stolen session or phone breaks it
Other people in a group chatPartlyMention gate, per-group sessions, fewer tools in groups
Anyone who emails or messages youNoTreat as data: mark it, never let it trigger an irreversible action
Web pages, documents, calendar invitesNoSame as above; restrict what the browsing part can do
Skills and plugins from a registryCode plus instructions from strangersReview, pinning, scanning, a sandbox (section 8)
Memory and skills the agent wrote earlierOnly as trusted as what it read thenStaged writes, a ledger, review (section 3)

Six controls, from the outside in

  1. Who may talk to it. OpenClaw's default dmPolicy is pairing: an unknown sender gets a code and is ignored until you approve it (codes expire after 1 hour, at most 3 pending per channel); open needs an explicit "*" in the allowlist. Hermes denies everyone unless an allowlist or an approved pairing (8-character codes) says otherwise DOCUMENTED (OpenClaw access control, Hermes security).
  2. Separate conversations. Per-sender sessions (dmScope, section 1) so one person's messages never sit in another's context.
  3. Classify every action by what it would take to undo it, and decide in plain code, using where the run came from. The agent on this page uses four classes: reading (allowed), reversible changes such as a draft or a calendar edit (allowed and logged with an undo step), memory writes (staged for review), irreversible actions such as sending or paying (held for approval when you started the run, refused outright on unattended heartbeat and scheduled runs). The Gate designer tab replays every action the recorded models proposed under any policy you choose.
  4. Ask for approval outside the conversation. If the approval is a chat message, text in the context can imitate or pre-empt it; an approval shown in the app's own interface, or in a separate queue as here, cannot be produced by the model. Meta's Muse does exactly this (section 9).
  5. Keep credentials out of the model's reach. The agent holds placeholders; a separate component swaps in the real token only for an allowed destination as the request leaves. Claude Code's sandbox masks credentials this way, and Muse's Sentinel does the same at its network boundary; Agent security section 5 owns the mechanism.
  6. Contain what runs. A sandbox around commands (an operating-system boundary; Containers and isolation) and a gateway that is not reachable from the internet.

Reading the defaults fairly. OpenClaw's SECURITY.md says it is "local-first agent infrastructure for trusted operators; it is not designed as a shared multi-tenant boundary between adversarial users", and lists "Prompt injection without a policy, auth, approval, sandbox, or tool-boundary bypass" as not a security bug. The old version of this page read that as negligence. It is better read as an engineering position: the model is assumed persuadable, so a report counts only when a boundary in code fails. The weak point is the defaults those boundaries ship with (commands on the host, sandbox off), which assume one careful operator rather than the way people deploy it (section 8). Hermes's smart mode is the opposite bet: a second model judging the first, which helps against accidents but is still text judging text.

Predict: a heartbeat run reads an email asking for an urgent reply and calls send_reply. Under this page's gate, what happens, and why is that rule about the trigger rather than the email?
Refused: irreversible actions are never allowed on unattended runs, whatever the text said. The gate does not try to judge whether the email was legitimate (that judgement is what text can manipulate); it uses facts the model cannot change: which tool, and whether you started the run. In the recorded days neither model even proposed a send on a heartbeat: both only messaged Sam a list of decisions (the A day, replayed tab). The rule is there for the day one does.

7. Verification and undo, when there is no test suite

The problem. Everything the parent page says about measuring and improving harnesses leans on a free verifier: the tests pass or they do not (Topic: agentic-harnesses, section 7). A personal agent's work has none. Did it answer the garage politely, at the right time, with the right facts, and should it have answered at all? Nobody computes that. And when it is wrong, git does not help: a sent message stays sent.

The design response is to move as much work as possible into the reversible column, and to make the irreversible column small, slow and visible:

It is not a generic model benchmark": ten YAML scenarios (a reminder round trip, a reply in a channel thread, recalling a stored preference, not leaking a secret while redacting, following through after a tool safety check, stopping after an approval is denied, reporting task status, sharing a diagnostics file safely, not faking progress, recovering from a failure), run against a mock model with "only fake users, fake preferences, fake secrets" DOCUMENTED (benchmark pack). 9. Hosted entrants, and the layering

Meta's Muse (announced 8 Sep 2026; US, on iOS, Android, muse.ai and inside WhatsApp) is the first big hosted personal agent, with mail, calendar, browser and payment connections. Its safety post is the clearest public design for the boundary of section 6 PRIMARY (newsroom, How we built safety into Muse):

  • "Muse runs on Muse Secure VM, a dedicated, virtual machine (VM) that houses both the agent and a person's data", and "the harness runs in its own isolated cell, it doesn't see real credentials".
  • A separate Sentinel agent on the same machine: "Nothing Muse does reaches the internet unless the Sentinel approves it"; after a request is authorised, Sentinel "will replace any surrogate tokens with the real credential ... at the network boundary".
  • Approvals: "A dialog is presented to the user directly within the client UI, not via their conversation with Muse".
  • The browsing sub-agent "sees an accessibility tree snapshot of the page, not the raw DOM" and "has no ability to run javascript in the page context"; the email connector filters one-time codes and password-reset links with deterministic filters and a classifier. No accuracy figures for any classifier are published.

The principle transfers to anything you build: assume the agent will sometimes be persuaded, and keep credentials, egress and consent in a component it cannot talk to. (Muse Spark 1.3 is the model, released 2 Sep 2026; the old page merged the two names.)

The layering. A personal agent is a router, scheduler, memory and delivery surface; a coding harness is the best executor for coding work (six of them read from source and run on one task: Other coding harnesses, its "Same task, every harness" tab). OpenClaw makes that explicit by running Codex as an embedded runtime and Claude Code, Gemini CLI, OpenCode or Cursor over ACP (section 2); Hermes exposes itself over ACP so an editor can host it. The MCP page and Agent-to-agent and beyond own the protocols. A claw asked to fix a bug should hand that turn to a coding harness, in a sandbox, with the repository as its world.

10. The old page, claim by claim

The previous version of this page (13 minutes, September 2026) was treated as unverified notes. Each claim, checked against a primary source on 6 Oct 2026, and the section that now carries it:

Common mistakes

Treating a personal agent as a coding harness with a chat front end
The loop is the same; the exposure is not. A coding harness's safety story assumes you watch, the input is mostly yours, and git undoes mistakes. None of the three holds for a resident agent (section 0).
Asking the model whether an action is safe
A gate that reads the email to decide whether replying is fine can be argued with by the email. Decide on facts text cannot change: the tool's class and who started the run (section 6). A second model judging risk (Hermes's smart mode) helps against accidents; it is still text judging text.
Approvals as chat messages
If "yes" arrives in the same conversation the model reads, the conversation can contain something that looks like a yes. Show approvals in the app's own interface or a separate queue, with the context that produced them, and let the agent withdraw them (section 4's held reply).
Queueing a correction behind an irreversible action
With follow-up delivery and no gate, every recorded run sent the booking before reading "do not book" (section 4). Steer or interrupt at tool boundaries, and hold irreversible actions.
Giving the agent a memory tool and assuming it is used
Haiku never searched its history unprompted in three runs (section 5). Either tell it when to search or retrieve for it, and check the retrieval's cut-off.
Putting the gateway on the internet, or running community skills unsandboxed
Over 30,000 exposed OpenClaw instances and over 800 malicious ClawHub skills in the first weeks of February 2026 (section 8). Private network, pinned and reviewed skills, sandboxed commands.
Quoting star counts and token rankings as settled
They move daily, and several old figures had no primary source or were someone else's testimonial (section 10). Date every number and name who counted it.

Interview questions

What is the difference between a coding harness and a personal agent, in one minute?
Same agent loop; different boundary. A personal agent is resident (gateway daemon, triggers from messages, heartbeats and schedules), holds standing access to live accounts, reads text from anyone who can message you, often acts with nobody watching, has no test suite to verify its work and little undo. So the engineering moves to session routing, memory tiers, mid-run message policy, and enforcement outside the model: a code gate by action class and trigger, out-of-band approvals, credentials it never sees, sandboxes.
Design the approval flow for an agent that can send email and pay bills.
Classify actions: read, reversible (draft, calendar), irreversible (send, pay). Reads run; reversible changes run with an undo record; irreversible ones become pending requests in a queue rendered by the app, not the chat, showing the exact payload and the conversation that led to it; unattended runs (heartbeat, cron) cannot create irreversible requests at all, only drafts and a message to the owner. Pending requests expire, can be withdrawn by the agent, and are invalidated by a newer message in the same conversation. Payment credentials live in a separate service that substitutes them on the way out for allowed payees only.
A user sends a correction while the agent is mid-task. What should happen?
Deliver it at the next tool boundary, before the next model call (steer), or abort and restart with it (interrupt); never queue it behind the current run if the run can take irreversible actions. Do not kill a running tool mid-write. OpenClaw steers by default and skips unstarted sequential calls; Hermes redirects by default.
How would you give a never-ending assistant memory?
Tiers: a small capped profile in every prompt, a searchable store of past sessions (full-text, with stemming, or embeddings) used through a tool and, for known patterns, retrieved by the harness, procedures as skills loaded on demand, and compaction of the live session. Then test whether retrieval actually happens: a cheap model may never call the search tool unless told when to.
How do you evaluate a personal agent with no verifier?
Scenario suites on fake accounts with checks on actions, not prose (OpenClaw's ten-scenario pack: reminders, approvals denied, no fake progress, no secret leaks); counters for irreversible actions taken without approval and for corrections that arrived too late; trajectory review with a rubric (Agent and trajectory evaluation).
