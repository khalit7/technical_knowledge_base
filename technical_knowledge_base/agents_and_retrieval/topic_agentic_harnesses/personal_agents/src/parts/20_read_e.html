4. Messages that arrive while the agent is working

The problem. In a chat, a correction sent thirty seconds after a request is normal ("wait, not that one"). A coding harness was built for a person who types a task and watches; a resident agent receives messages whenever people send them, including while a run is halfway through. The harness has to decide where such a message goes, and the choice decides whether an irreversible action happens before the correction is read.

Four policies (OpenClaw's names):

  • steer: put the message into the current run at the next safe boundary, so the model reads it before its next decision;
  • followup (Hermes calls it queue): finish the current run, then run the message as a new turn;
  • collect: like followup, but merge several queued messages into one later turn after a short wait;
  • interrupt: abort the current run and start again with the new message.

Exactly where the boundary is. OpenClaw steers by default. It never interrupts a tool that is already running; in a reply with several sequential tool calls it starts the first one without checking, then checks before each later one and skips the rest with a synthetic result ("Skipped to process an incoming message."); after the batch settles "it appends the exact drained steering messages after the tool results, before the next LLM call"; parallel batches are never skipped DOCUMENTED ({{queue steering|https://docs.openclaw.ai/concepts/queue-steering}}). Hermes defaults to a redirecting interrupt: "messaging a busy agent redirects its active turn (a running foreground terminal command is moved to the background rather than killed, so your message is read immediately)", applied "at the next tool-result boundary"; queue and steer are options, /stop is a hard stop DOCUMENTED ({{Hermes messaging|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/messaging/index.md}}). Both projects therefore make the same choice in different words: the newest message wins, at a tool boundary.

A held action outlives its context

In both gate-on follow-up runs the agent, having read the correction, could not withdraw its own held reply: the approval queue still held "please book Thursday 10:00" at the end, waiting for Sam to tap approve. Sonnet noticed and messaged Sam to "reject A1"; Haiku wrote that since the reply "is held for approval and hasn't been sent yet, I won't confirm it", which changed nothing: this page's agent has no tool to withdraw a held action. Lessons for your own design: give the agent a way to withdraw a pending action, expire pending actions when a newer message in the same conversation arrives, and show the approval with the context that produced it.

One bug in this page's agent, found in the recordings and left visible: with the gate off, its remember tool had no implementation and answered "error: unknown tool" (the gate-on path stages the write instead). It affects only the memory notes of the no-gate runs, not whether anything was sent.

5. Memory that lasts months, and who decides to look

The problem. A coding session ends; a resident agent's conversation never does. It cannot keep months of messages in the window (and recall degrades as the window fills: {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}, section 8), so it keeps tiers:

The middle tier only helps if something decides to search it. Either the model decides (it has a search tool) or the harness decides (it searches with the message's words and puts the hits in the prompt before the model sees anything). To see which works, the fake history here holds eleven past-session lines, among them "Car serviced at Kwik Garage, 260 pounds paid by Sam" (3 September). What the recordings show. Haiku never used the search tool when it was merely available (0 of 3 runs searched, 0 of 3 right; without the tool, also 0 of 3): it checked the calendar and answered as a scheduling question. One sentence in the system prompt ("Before advising on anything that recurs, search past sessions first") made it search every time and answer right every time (3 of 3). Gateway retrieval got 1 of 3 right: the gateway's top four hits included the August quotes and "Sam booked it for 3 September", but not the line saying the service had happened, and Haiku twice asked whether Sam still wanted Kwik Garage instead. Sonnet searched on its own and was right in every configuration except the one without history. Small samples (3 and 1 runs): read them as a demonstration of failure modes, not as rates.

  • "The model never searches" is a real failure mode for a cheap model with a tool it is not told to use; a rule in the prompt fixed it here.
  • Retrieval by the harness is only as good as its query and its cut-off: words taken from the message, the top four hits by BM25, and the deciding line ranked fifth.
  • Lexical search needs stemming. With FTS5's default tokenizer, "service" does not match "serviced"; this page's history uses the Porter stemmer (tokenize='porter'), found while testing before the runs.
  • A strict parser can fake an empty memory. In the first batch Haiku sometimes put its arguments next to "tool" instead of inside "args"; the first version of this page's parser dropped them silently, so a search ran with an empty query, returned "no matching past sessions", and Haiku told Sam "The search found no record of this year's service". That run is kept (s2_haiku_hintbug_1 in the list) as evidence; the parser now accepts both forms and logs which it saw, and all other runs were recorded after the fix.
