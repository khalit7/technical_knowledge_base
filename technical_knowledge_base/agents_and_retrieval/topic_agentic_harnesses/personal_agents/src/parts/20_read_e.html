4. Messages that arrive while the agent is working

In a chat, a correction thirty seconds after a request is normal ("wait, not that one"). A resident agent receives it while a run is halfway through, and where the harness delivers it decides whether an irreversible action happens first. Four policies (OpenClaw's names):

  • steer: put the message into the current run at the next safe boundary, so the model reads it before its next decision;
  • followup (Hermes calls it queue): finish the current run, then run the message as a new turn;
  • collect: like followup, but merge several queued messages into one later turn after a short wait;
  • interrupt: abort the current run and start again with the new message.

Sam asks the agent to reply to the garage and book Thursday 10:00. The rule in both projects: the newest message wins, at a tool boundary. OpenClaw steers by default. It never interrupts a running tool; in a reply with several sequential tool calls it starts the first without checking, checks before each later one and skips the rest with a synthetic result ("Skipped to process an incoming message."); then "it appends the exact drained steering messages after the tool results, before the next LLM call"; parallel batches are never skipped DOCUMENTED ({{queue steering|https://docs.openclaw.ai/concepts/queue-steering}}). Hermes defaults to a redirecting interrupt: "messaging a busy agent redirects its active turn (a running foreground terminal command is moved to the background rather than killed, so your message is read immediately)", applied "at the next tool-result boundary"; queue and steer are options, /stop a hard stop DOCUMENTED ({{Hermes messaging|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/messaging/index.md}}).

A held action outlives its context

In both gate-on follow-up runs the agent, having read the correction, could not withdraw its own held reply: the approval queue still held "please book Thursday 10:00" at the end, waiting for Sam to tap approve. Sonnet noticed and messaged Sam to "reject A1"; Haiku wrote that since the reply "is held for approval and hasn't been sent yet, I won't confirm it", which changed nothing: this page's agent has no tool to withdraw a held action. So: give the agent a way to withdraw a pending action, expire pending actions when a newer message in the same conversation arrives, and show the approval with the context that produced it.

One bug in this page's agent, left visible: with the gate off, its remember tool had no implementation and answered "error: unknown tool" (the gate-on path stages the write). It affects only the memory notes of the no-gate runs, not whether anything was sent.

Two traps found while building the history

Lexical search needs stemming. With FTS5's default tokenizer, "service" does not match "serviced"; this page's history uses the Porter stemmer (tokenize='porter'), found while testing before the runs.

A strict parser can fake an empty memory. In the first batch Haiku sometimes put its arguments next to "tool" instead of inside "args"; the first version of this page's parser dropped them silently, so a search ran with an empty query, returned "no matching past sessions", and Haiku told Sam "The search found no record of this year's service". That run is kept (s2_haiku_hintbug_1 in the list) as evidence; the parser now accepts both forms and logs which it saw, and all other runs were recorded after the fix.
