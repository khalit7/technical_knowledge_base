6. The trust boundary: who can write into the context, and what the agent may do alone

The problem, in one sentence. Everything the model reads is text, and it cannot reliably tell an instruction from a fact; so whatever reaches its context can steer what it does with your authority. {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}} teaches this from zero (its sections 6 and 7: prompt injection, and the "lethal trifecta" of private data, untrusted content and a way to communicate out). A personal agent has all three legs by design: it reads your mail, anyone can send you mail, and it can send messages. That is the whole difference from a coding harness in one line, and it is why this section is about where to put enforcement, not about attacks.

Six controls, from the outside in

  1. Who may talk to it. OpenClaw's default dmPolicy is pairing: an unknown sender gets a code and is ignored until you approve it (codes expire after 1 hour, at most 3 pending per channel); open needs an explicit "*" in the allowlist. Hermes denies everyone unless an allowlist or an approved pairing (8-character codes) says otherwise DOCUMENTED ({{OpenClaw access control|https://docs.openclaw.ai/gateway/security/access-control}}, {{Hermes security|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/security.md}}).
  2. Separate conversations. Per-sender sessions (dmScope, section 1) so one person's messages never sit in another's context.
  3. Classify every action by what it would take to undo it, and decide in plain code, using where the run came from. The agent on this page uses four classes: reading (allowed), reversible changes such as a draft or a calendar edit (allowed and logged with an undo step), memory writes (staged for review), irreversible actions such as sending or paying (held for approval when you started the run, refused outright on unattended heartbeat and scheduled runs). The {{Gate designer|#t-gate}} tab replays every action the recorded models proposed under any policy you choose.
  4. Ask for approval outside the conversation. If the approval is a chat message, text in the context can imitate or pre-empt it; an approval shown in the app's own interface, or in a separate queue as here, cannot be produced by the model. Meta's Muse does exactly this (section 9).
  5. Keep credentials out of the model's reach. The agent holds placeholders; a separate component swaps in the real token only for an allowed destination as the request leaves. Claude Code's sandbox masks credentials this way, and Muse's Sentinel does the same at its network boundary; {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}} section 5 owns the mechanism.
  6. Contain what runs. A sandbox around commands (an operating-system boundary; {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}) and a gateway that is not reachable from the internet.

Reading the defaults fairly. OpenClaw's SECURITY.md says it is "local-first agent infrastructure for trusted operators; it is not designed as a shared multi-tenant boundary between adversarial users", and lists "Prompt injection without a policy, auth, approval, sandbox, or tool-boundary bypass" as not a security bug. The old version of this page read that as negligence. It is better read as an engineering position: the model is assumed persuadable, so a report counts only when a boundary in code fails. The weak point is the defaults those boundaries ship with (commands on the host, sandbox off), which assume one careful operator rather than the way people deploy it (section 8). Hermes's smart mode is the opposite bet: a second model judging the first, which helps against accidents but is still text judging text.

Refused: irreversible actions are never allowed on unattended runs, whatever the text said. The gate does not try to judge whether the email was legitimate (that judgement is what text can manipulate); it uses facts the model cannot change: which tool, and whether you started the run.
