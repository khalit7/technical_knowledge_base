6. The gate: decide by what it would take to undo

A model cannot reliably tell an instruction from a fact in what it reads, so whatever reaches its context can steer what it does with your authority ({{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}, sections 1 and 2: the confused deputy and the "lethal trifecta" of private data, untrusted content and a way to send things out). A personal agent has all three legs by design: it reads your mail, anyone can send you mail, and it can send messages. So the question is not how to spot attacks but where to put enforcement that text cannot reach.

The gate this page's agent uses

Classify every action by what it would take to undo it, and decide in plain code from two facts the model cannot change: which tool, and who started the run. Four classes: reading (allowed), reversible changes such as a draft or a calendar edit (allowed and logged with an undo step), memory writes (staged for review), irreversible actions such as sending or paying (held for approval when you started the run, refused outright on unattended heartbeat and scheduled runs). Every action the recorded models proposed (all scenarios, both models) is re-decided below by whatever policy you set; no model is involved and nothing is re-run.

One exception is built in, as in the recorded gate: drafts and messages to Sam stay allowed on unattended runs under "This page's gate", since they only reach Sam. Predict before you press "No gate": how many known-wrong bookings go out?

A decision table, not a re-run: when the recorded gate held an action, the model's later steps reacted to that (it told Sam the reply was waiting), and under another policy it might have continued differently. The "known wrong" actions are the booking replies to the garage in the correction scenario (section 4), proposed before the agent read Sam's correction. "This page's gate" reproduces all 45 recorded gate-on decisions (src/check.py).

Refused: irreversible actions are never allowed on unattended runs, whatever the text said. The gate does not try to judge whether the email was legitimate (that judgement is what text can manipulate); it uses facts the model cannot change: which tool, and whether you started the run. In the recorded days neither model even proposed a send on a heartbeat: both only messaged Sam a list of decisions (the {{A day, replayed|#t-day}} tab). The rule is there for the day one does.

The rest of the boundary, briefly

  1. Who may talk to it. OpenClaw's default dmPolicy is pairing: an unknown sender gets a code and is ignored until you approve it (codes expire after 1 hour, at most 3 pending per channel); open needs an explicit "*" in the allowlist. Hermes denies everyone unless an allowlist or an approved pairing (8-character codes) says otherwise DOCUMENTED ({{OpenClaw access control|https://docs.openclaw.ai/gateway/security/access-control}}, {{Hermes security|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/security.md}}).
  2. Separate conversations: per-sender sessions (dmScope, section 1).
  3. Approvals outside the conversation. A "yes" that arrives as a chat message can be imitated by text in the context; one shown in the app's own interface, or in a separate queue as here, cannot be produced by the model. Muse does this (section 8); {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}} section 5 owns approval as a control and why it weakens at volume.
  4. Credentials out of the model's reach: placeholders swapped for the real token only for an allowed destination as the request leaves (Muse's Sentinel; Agent security section 8).
  5. Containment: a sandbox around commands (Agent security section 6; {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}) and a gateway that is not reachable from the internet (section 9).

Reading the defaults fairly. OpenClaw's SECURITY.md says it is "local-first agent infrastructure for trusted operators; it is not designed as a shared multi-tenant boundary between adversarial users", and lists "Prompt injection without a policy, auth, approval, sandbox, or tool-boundary bypass" as not a security bug. The old version of this page read that as negligence. It is better read as an engineering position: the model is assumed persuadable, so a report counts only when a boundary in code fails. The weak point is the defaults those boundaries ship with (commands on the host, sandbox off), which assume one careful operator rather than the way people deploy it (section 9). Hermes's smart mode is the opposite bet: a second model judging the first, which helps against accidents but is still text judging text.
