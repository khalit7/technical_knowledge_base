Muse: the clearest published design for the boundary

Meta's safety post PRIMARY ({{newsroom|https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/}}, {{How we built safety into Muse|https://security.muse.ai}}):

  • "Muse runs on Muse Secure VM, a dedicated, virtual machine (VM) that houses both the agent and a person's data", and "the harness runs in its own isolated cell, it doesn't see real credentials".
  • A separate Sentinel agent on the same machine: "Nothing Muse does reaches the internet unless the Sentinel approves it"; after a request is authorised, Sentinel "will replace any surrogate tokens with the real credential ... at the network boundary".
  • Approvals: "A dialog is presented to the user directly within the client UI, not via their conversation with Muse".
  • The browsing sub-agent "sees an accessibility tree snapshot of the page, not the raw DOM" and "has no ability to run javascript in the page context"; the email connector filters one-time codes and password-reset links with deterministic filters and a classifier. No accuracy figures for any classifier are published.

The principle transfers to anything you build: assume the agent will sometimes be persuaded, and keep credentials, egress and consent in a component it cannot talk to. (Muse Spark 1.3 is the model; the old page merged the two names.)

The layering. A personal agent is a router, scheduler, memory and delivery surface; a coding harness is the best executor for coding work (six of them read from source and run on one task: {{Other coding harnesses|n:3c65c17b0d0d819fa3cefdcd2ccff2f7}}, its "Same task, every harness" tab). OpenClaw makes that explicit by running Codex as an embedded runtime and Claude Code, Gemini CLI, OpenCode or Cursor over ACP (details below); Hermes exposes itself over ACP so an editor can host it. The {{MCP page|n:3c65c17b0d0d813f9695dc4175c44cbb}} and {{Agent-to-agent and beyond|n:3f05c17b0d0d81199373d4d0b18706d8}} own the protocols. A claw asked to fix a bug should hand that turn to a coding harness, in a sandbox, with the repository as its world.

Four layers that can be swapped separately

OpenClaw separates the provider (who serves the model), the model (written provider/model, split on the first slash, so openrouter/moonshotai/kimi-k2 works), the agent runtime (who runs the loop) and the channel (where messages enter and leave) DOCUMENTED ({{agent runtimes|https://docs.openclaw.ai/concepts/agent-runtimes}}). The runtime layer is the interesting one for this topic:

  • Embedded harnesses run inside OpenClaw's own prepared loop: the built-in openclaw runtime, plus plugin runtimes codex and copilot (the latter opt-in, never picked automatically).
  • CLI backends run a local CLI process: claude-cli means "select the Anthropic model, execute through Claude CLI". The bundled Codex CLI backend was removed in v2026.5.14.
  • External harnesses attach over ACP (the Agent Client Protocol): "Claude Code, Gemini CLI, OpenCode, Cursor, and similar external harnesses still use ACP."

For a runtime it does not own, the docs ask a fixed list of compatibility questions: who owns the model loop, who owns the canonical thread history, whether OpenClaw's own tools and its before_tool_call/after_tool_call hooks still fire, whether the context-engine lifecycle runs, what compaction data is exposed, and what is intentionally unsupported. With the Codex runtime, for example, Codex owns the loop and the thread (OpenClaw keeps a mirror) and compaction is Codex's own; channel delivery stays with OpenClaw DOCUMENTED. That list is the clearest statement anywhere of what "a harness hosted inside another harness" has to settle, and it makes the personal agent a host for coding harnesses rather than a rival (above).

The workspace: files that become the system prompt

Each agent owns one directory, its only working directory for tools. On the first turn of a new session OpenClaw injects these user-editable files into the system prompt's "Project Context" DOCUMENTED ({{agent|https://docs.openclaw.ai/concepts/agent}}, {{system prompt|https://docs.openclaw.ai/concepts/system-prompt}}, {{workspace|https://docs.openclaw.ai/concepts/agent-workspace}}):

Caps: 20,000 characters per file and 60,000 across all of them (bootstrapMaxChars, bootstrapTotalMaxChars); a longer file is cut with a marker and the prompt says which files were truncated. Day-by-day notes live in memory/YYYY-MM-DD.md and are not injected: the agent reads them on demand through memory_search and memory_get DOCUMENTED. Two old files are gone: the heartbeat checklist moved from HEARTBEAT.md into a database "monitor scratch" ("The runtime never reads HEARTBEAT.md"), and TOOLS.md became a section of AGENTS.md.

Skills, sessions, and messages that arrive mid-run

  • Skills (a folder with a SKILL.md, loaded by description first and body on demand, as in Claude Code) resolve from seven tiers, highest first: workspace skills/, <workspace>/.agents/skills, ~/.agents/skills, managed skills in the state directory, the agent's "workshop" skills, bundled skills, then extra directories and plugin skills; the highest source wins a name clash DOCUMENTED ({{skills|https://docs.openclaw.ai/tools/skills}}). ClawHub (clawhub.ai) is the public registry for skills and plugins; section 9 covers what happened there.
  • Sessions are owned by the gateway and stored in a per-agent SQLite database (~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite); JSONL transcripts are now only legacy imports and exports. The main session's key is agent:<agentId>:main DOCUMENTED.
  • Mid-run messages are "steered into the current run by default", with three alternatives (/queue followup, collect, interrupt). Section 4 has the exact rule and the recordings.

One agent class, many front doors

The architecture page's first design principle: "One AIAgent class serves CLI, gateway, ACP, batch, and API server. Platform differences live in the entry point, not the agent." (run_agent.py is now a facade; the loop lives in agent/conversation_loop.py.) Around it: a tool registry the architecture page counts as "70+ registered tools across ~28 toolsets" while the tools reference at the same tag says "~100 tools"; terminal commands can run on 7 backends (local, Docker, SSH, Daytona, Modal, Singularity, Vercel Sandbox); the gateway has "25+ platform adapters"; and "SQLite-based session storage with FTS5 full-text search" where sessions keep a parent/child lineage across compressions DOCUMENTED ({{architecture|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/developer-guide/architecture.md}}). Memory providers and context engines are plugins, one of each active at a time.

The learning loop: skills it writes for itself

The problem it attacks. A resident agent repeats the same chores for months. A coding harness forgets how it solved something when the session ends unless you write a skill by hand; Hermes tries to write and maintain them itself.

  1. Two kinds of note. "memory stores small durable facts that should always be in context, while skills store longer procedures that should load only when relevant." MEMORY.md is capped at 2,200 characters (about 800 tokens) and USER.md at 1,375 (about 500), both injected into the system prompt; memory "does not auto-compact" DOCUMENTED ({{memory|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/features/memory.md}}).
  2. Two triggers for writing a skill. The system prompt asks the agent to record a workflow worth repeating, one where it hit dead ends, or one the user corrected, with the skill_manage tool. Separately, after a turn that used at least creation_nudge_interval tool iterations (default 10), the agent forks a copy of itself in a background thread that replays the conversation and asks whether any skill or memory should be saved or updated (up to 16 iterations, same model by default; the source notes "the fork costs ~30K tokens / event"; skipped for scheduled jobs and interrupted turns) SOURCE (agent/turn_finalizer.py, agent/background_review.py).
  3. Patching in use. skill_manage can create, patch, delete and write files; targeted patches are preferred; every change is appended to ~/.hermes/skills/.curator_ledger.jsonl.
  4. A curator for the pile. hermes curator tracks how often each agent-created skill is viewed, used and patched and moves unused ones active to stale (14 days) to archived (30 days; archived, never deleted), checked at most every 168 hours when the agent has been idle 2 hours. Merging overlapping skills with a model is off by default ("a full curation sweep typically takes 50-100 API calls"). Pinned skills and skills used by scheduled jobs are never touched DOCUMENTED ({{curator|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/user-guide/features/curator.md}}).
  5. Review before commit, if you ask for it. With skills.write_approval: true every skill write is staged under ~/.hermes/pending/skills/ for /skills pending, /skills diff, /skills approve; memory has the same switch. Both are off by default; so is scanning the agent's own new skills for risky content, because "the agent can run the same code via terminal() ungated" (config comment) SOURCE.

What it costs, and how to check it. Each background review is another model call over the whole conversation; a skill written from one lucky run can encode the wrong lesson, and a memory file the agent edits is a place where text it read can persist into every later prompt (the reason Hermes scans memory entries for injection and exfiltration patterns before accepting them). The check is the ledger: read what the agent wrote and why. The research version of this idea, agents that improve their own harness, belongs to {{Harnesses for training|n:3f15c17b0d0d815ea579d6c80065aa36}}.

Never-ending context, scheduled work, trajectories

  • Compression runs at two levels: a gateway safety net at 85% of the window before a message is handled, and the agent's own compressor at a threshold of 0.50 of the window, raised to 0.75 for windows under 512K tokens and capped at 256,000 tokens. It first clears old tool outputs over 200 characters, keeps the first 3 messages and a recent tail, and summarises the middle with an auxiliary model into fixed headings (Goal, Constraints and Preferences, Progress, Key Decisions, Relevant Files, Next Steps, Critical Context) SOURCE (agent/context_compressor.py; the docs' own worked example of 100,000 tokens for a 200K window ignores the 0.75 floor in the code, which gives 150,000). {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} owns compaction in general.
  • Searching old sessions: the session_search tool runs FTS5 queries over ~/.hermes/state.db and "return[s] actual messages from the DB, no LLM summarization"; section 5 tests whether a model uses such a tool when it should.
  • Trajectories: sessions export as ShareGPT-format JSONL "for use as training data, debugging artifacts, and reinforcement learning datasets". The first releases (March 2026) also shipped Atropos RL environments and an optional Tinker training path; at v0.21.5 neither is in the dependency list or the source tree SOURCE. Trajectories as training data belong to {{Harnesses for training|n:3f15c17b0d0d815ea579d6c80065aa36}}.
  • Moving from OpenClaw: hermes claw migrate imports persona, memory (daily notes merged into MEMORY.md), skills, model settings, MCP servers, channel tokens and allowlists, always with a preview and a backup; API keys only with --migrate-secrets, and only from an allowlist; heartbeat, cron jobs, plugins and hooks are archived, not imported DOCUMENTED ({{migration guide|https://github.com/NousResearch/hermes-agent/blob/v2026.9.24/website/docs/guides/migrate-from-openclaw.md}}).

9. Incidents, 2026

The record so far teaches four things: do not put the gateway on the internet (over 30,000 OpenClaw instances were reachable in early February), treat a skill registry as untrusted code (824 malicious ClawHub skills of over 10,700 by 16 February), a loopback bind does not protect a control UI your own browser connects out from (CVE-2026-25253), and the agent's long-lived credentials are themselves the loot. Each entry below comes from the original report or advisory, read on 6 Oct 2026, described at the level of the published advisory.
