Claude Code in one screen

Claude Code is Anthropic's coding agent: a program that runs Claude in a loop with tools on your machine (a terminal app, IDE extensions, a desktop and web app and a GitHub integration share the same core). It was introduced as a limited research preview with Claude 3.7 Sonnet on 24 February 2025 (Anthropic) and declared generally available in version 1.0.0 on 22 May 2025 (changelog). This page takes apart version 2.1.290 (5 October 2026), the version installed on the recording machine.

The parent page explains what a harness is and builds one from zero (Topic: agentic-harnesses, its Reading tab and Loop lab). Its Trace and context lab already holds 22 recorded Claude Code runs of the running example (fix the two planted bugs in textstats) and measures startup context, prompt caching and run-to-run spread. This page does not repeat those. It asks a narrower question for each mechanism: what exactly does Claude Code do here, and what do the documentation and a real recording say? Every mechanism below was exercised in a recording made for this page (23 runs on 6 October 2026, Claude Haiku 4.5 unless a section says otherwise; open any of them in the Recordings tab).

1. The loop, as Claude Code runs it

The loop itself is the one the parent page builds: send the system prompt, the tool definitions and the conversation; if the reply asks for tools, run them, append the results and call again; stop when a reply asks for none. Anthropic's own description is three phases, "gather context, take action, and verify results", which "blend together" (How Claude Code works) DOCS. What this section adds is the behaviour you only see in a recording.

A reply can hold several tool calls. The model may ask for three tools in one reply (a parallel tool call); the harness runs them, returns all three results in the next request, and only then calls the model again. Whether the three actually run at the same time is the harness's choice, not the model's. Two recordings asked for exactly that:

In the first run each command printed its own start and end time, and they ran one after another: A from 930.00 to 932.01 seconds, B from 932.11 to 934.12, C from 934.19 to 936.19 (clock seconds modulo 1,000) MEASURED. In the second, three sleep 2 calls in one reply all returned within 0.04 s of each other, 3.0 s after the reply finished streaming: they ran together MEASURED. The timestamps show one more thing: execution does not wait for the whole reply. In the second half of that run, ls returned its result (at 9.82 s) before the model had finished streaming the next call, cat README.md (9.88 s). Claude Code can start a call as soon as its block of the reply is complete, and queues the ones it will not run alongside others. The sibling page Building a harness: the loop, tool calling, edit formats, stop conditions (section 4) saw the same with edits: on Sonnet 5.5 the first of two Edits ran 0.78 s before the second had finished streaming. The difference is the command, not the tool: sleep is a command the harness can tell has no side effects, a python3 -c script is not. The old page's rule, "read-only tools in parallel, mutating tools serially", is therefore right in spirit for Bash on 2.1.290; the documentation pages read do not state the rule itself, only that PostToolUse hooks "fire concurrently when Claude makes parallel tool calls" and that a PostToolBatch hook runs once the whole batch has resolved (hooks reference) DOCS.

A turn is not a model call. The CLI's num_turns counts something else than API requests (the parent's Trace and context lab shows the mismatch). Here the limit flag makes it concrete: with --max-turns 2 the run made two model calls, stopped before the third, and reported num_turns: 3 with subtype error_max_turns MEASURED (section 9). When you budget an agent by turns, test what your version counts.

Messages arriving mid-turn. In the terminal, a message you type while Claude works is queued and read before its next step; Esc stops the running tool; a send-now key (ctrl+enter) interrupts and sends the queue (added in 2.1.275, changelog) DOCS. In a headless run the same happens through --input-format stream-json: two user messages written to stdin at once produced a single result record, and the reply after the first tool call answered the first question and went straight on to the second MEASURED (run stream). A harness that only reads input between turns would have produced two results. What a hard interrupt leaves behind (a rejected tool_result with is_error for the pending call, then a result with subtype error_during_execution) is recorded through the Agent SDK on Building a harness: the loop, tool calling, edit formats, stop conditions, section 4.

Errors stay in the loop. Every failure in the recordings came back as an ordinary tool result marked is_error: a refused permission, a missing file, a non-unique edit string, a timed-out command (exit 143). The model reads it and decides what to do next; the harness never retries on its own. The parent page argues why that is the right design; the next section lists the exact messages.

Go deeper. The parent's Loop lab writes this loop from zero in seven recorded steps; the sibling page Building a harness: the loop, tool calling, edit formats, stop conditions takes tool-calling protocols, parallel calls, streaming and stop conditions further.

2. Tools: what each one returns, and where it stops

A tool is a function the harness offers the model: a name, a description and a JSON schema for its arguments, sent with every request. The model replies with a tool call; the harness checks permission, runs the function and sends back the output as text, which costs input tokens on every later call. So two questions decide how a tool behaves in practice: what exactly comes back, and what happens when the honest answer would be huge.

The built-in set in 2.1.290

The tools reference lists 46 built-in tools for this version, far more than the "small, sharp toolset" of the old page (tools reference) DOCS. A session gets a subset, and three defaults surprise people:

  • No Glob or Grep on macOS, Linux and WSL by default. Claude searches with find and grep through Bash instead; in Claude's shell those run embedded copies of bfs and ugrep, so searches reach your hooks and permission rules as Bash calls. Naming Glob or Grep in --tools or --allowedTools brings them back DOCS. The parent's recording with --tools default on this Mac listed 29 tools and neither of the two MEASURED.
  • No TodoWrite by default. It is replaced by TaskCreate, TaskGet, TaskList and TaskUpdate, and since 2.1.268 those four are offered by default only on older models (Claude 3.x, Opus 4 to 4.7, Sonnet 4 to 4.6, Haiku 4.5); "On newer models, Claude keeps track of multi-step work without a written checklist" DOCS. The old page's "TodoWrite keeps the model honest" is out of date.
  • The subagent tool is called Agent, renamed from Task in 2.1.63, with Task(...) kept as an alias in rules (subagents) DOCS. The init record of a headless run still lists it as Task while the model's calls say Agent MEASURED.

Two lessons for any harness
Every cap is a decision about what the model will never see, so the cap must say so. Claude Code does it well for Bash (a file path and a preview, so the model can read on) and for the oversized Read (an error that names the way out), and in this recording did not do it for the token-capped Read, where the model got 61% of a file and believed it had all of it. Second, the harness knows more than it tells: the tool_use_result metadata in the stream (line counts, truncation flags, structured patches) never reaches the model. When you build your own, decide which of those facts belong in the text.

Other documented limits, not exercised here: WebFetch caches 15 minutes, fails after 5 minutes (300 s since 2.1.268), refuses localhost, and passes the page through a second model call with your extraction prompt, so it is lossy by design; WebSearch is capped at 200 calls a session; background Bash commands in unattended sessions get 30 minutes, up to 2 hours; BASH_MAX_OUTPUT_LENGTH defaults to 30,000 with a ceiling of 150,000, and the bashOutputMaxChars setting raises the inline ceiling to 128,000 (tools reference) DOCS.

3. Permissions: modes, rules, and what the recordings refused

Every tool call passes a permission layer before it runs: code in the harness, not the model, that answers allow, ask (a person decides) or deny. In a headless run nobody is there to answer, so "ask" becomes a refusal ("This command requires approval") unless you give it a handler (--permission-prompt-tool, or the Agent SDK's callback) DOCS. The docs put the point plainly: rules "are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows" (permissions).

The two inputs: a mode and a list of rules

Mode (--permission-mode)Runs without asking (docs)Best for (docs)
default, shown as Manual (manual is an alias)Reads onlyReviewing every action yourself
acceptEditsReads, file edits, and common filesystem commands (mkdir, touch, rm, rmdir, mv, cp, sed) inside the working directoriesIterating on code you are reviewing
planReads, plus classifier-approved commands when auto mode is available; never edits until a plan is approvedExploring before changing
autoEverything, after a separate classifier model checks each action against your requestLong tasks with fewer prompts

From permission modes, read 6 Oct 2026 DOCS. The interactive terminal starts in auto since 2.1.283; claude -p starts in Manual in sessions that fetch feature flags, so pass the mode you want.

A rule is Tool or Tool(specifier) in an allow, ask or deny list, in a settings file or a flag. The specifier depends on the tool: a command pattern for Bash (Bash(npm run *)), a gitignore-style path for the file tools (Edit(/src/**) covers Edit, Write and NotebookEdit; Read(~/secrets/**) also covers Grep and Glob), a domain for WebFetch, a subagent type for Agent. "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order", so an allow rule can never carve an exception out of a deny, and a deny at any level (managed, user, project, flag) beats an allow at any other DOCS. Bash rules split compound commands on &&, ||, ;, |, & and newlines and require every part to match an allow; a deny or ask matches if any part does.

One call through the layers

Pick a recorded action and a configuration; the animation walks the call through the checks in order and stops where the decision was made, with the message the recording got. Change only the configuration and play it again: same input, different gate.

The stages and their order are a model built from the permissions, permission-modes and hooks pages (hook exit code 2 "stops the tool call before permission rules are evaluated"; then deny, ask, allow; the mode decides what nothing matched) plus two orderings the recordings show: a deny rule on a file path is enforced inside the file tool's own input check, before its read-before-edit check, and that check runs before the mode. The Permission lab compares this model with all 96 recorded decisions (it reproduces every one the classifier did not make, by construction, since part of the order was read off these recordings).

What twelve scripted actions met in eight configurations

The battery (prompt in the Recordings tab) asked Haiku to attempt twelve actions in order, one call each, and never work around a refusal: read a file, ls, run the tests with python3 and with python, edit the code, write a file, edit a test, sed -i, ls && rm, rm, curl, write outside the working directory. Six findings, each from those recordings MEASURED:

  1. Manual mode in -p ran 2 of 12: the read and ls, both in the read-only set. Running the tests was refused ("This command requires approval"), so a headless agent in the default mode cannot even check its own work unless you allow the test command.
  2. acceptEdits ran 7. It approved the edits, the new file and rm inside the working directory, as documented, but refused sed -i with "sed command requires approval (contains potentially dangerous operations)", although the docs list sed among the commands acceptEdits approves. The parent's trace lab met the same refusal on 2.1.289.
  3. Project allow rules are ignored in an untrusted folder. The same rules in .claude/settings.json and passed with --settings gave different results: from the project file, stderr said "Ignoring 2 permissions.allow entries from .claude/settings.json: this workspace has not been trusted", and the allowed test command was refused; the deny rules (Edit(tests/**), Bash(rm *)) and the ask rule (Bash(curl *)) applied either way. The docs say exactly this: allow rules "grant capability", so they wait for the trust dialog, which a -p run never shows (permissions).
  4. Variables are not trusted. In the tool probe, echo "PROBE=$PROBE" was refused with an allow rule for echo * in place: "A variable in this command can't be checked before it runs." A rule matches text; a variable makes the text unknowable.
  5. The python and python3 lesson, again. Haiku typed python in the parent's runs and here; an allow rule for python3 * does not cover it. In auto mode on Sonnet the classifier let it through and the shell answered "command not found: python" (exit 127).
  6. Auto mode decides by your request, not by a policy. Auto mode needs Opus 4.6, Sonnet 4.6 or later, or a Fable model on the Anthropic API; asked for with Haiku, the run silently started in Manual (its init record says default), as documented. On Sonnet 5.5 all twelve actions ran, including editing a test, curl to the internet and a write outside the working directory, because the prompt asked for each of them and the classifier checks that actions "align with your request". Run the same actions from an injected instruction and the classifier is meant to see the difference; that defence is the sibling page's subject (Agent security).
What "deny" covers, and what it does not
A Bash deny rule "covers the invocation Claude usually produces and isn't a security boundary around the program": Bash(rm *) stops rm -rf build/ but not /bin/rm -rf build/ or bash -c 'rm -rf build/', and a Read deny does not stop a Python script that opens the file itself (permissions) DOCS. For enforcement that does not depend on the command's text, the docs point to the OS sandbox (Seatbelt on macOS, bubblewrap on Linux, off by default, Bash only); when it is on, autoAllowBashIfSandboxed (default true) lets sandboxed commands run without prompts even in Manual mode. Sandboxes, egress and injection are on Agent security.

Actions no mode auto-approves, even bypassPermissions: tools matched by an explicit ask rule, AskUserQuestion, MCP tools marked as needing a person, and rm or rmdir aimed at a critical path (the filesystem root, your home directory, the working directory). Writes to protected paths (.git, .claude, .vscode, shell rc files, .mcp.json) are never pre-approved by allow rules. Project or local settings cannot set defaultMode to auto or bypassPermissions (permission modes) DOCS.

4. Hooks: your code at fixed points in the loop

A hook is a program the harness runs at a named moment, with a JSON description of the moment on its standard input. Its exit code and output can add context, change a tool's input, or stop what was about to happen. Hooks exist because a prompt is advice and a hook is enforcement: the docs put the rule in one line, "To block an action regardless of what Claude decides, use a PreToolUse hook" (memory) DOCS.

The mechanics

  • Where: a hooks block in any settings file (user, project, local, managed), a plugin's hooks/hooks.json, or the frontmatter of a skill or subagent (active while it runs). Entries merge across levels; identical handlers run once; all matching hooks run in parallel (hooks) DOCS.
  • Shape: event, then a matcher (for tool events, a tool name, a | list or a regular expression), then handlers. Five handler types: command (a shell command, the common case), http (POST the JSON to a URL), mcp_tool, prompt (a one-turn model call that returns ok or not) and agent (an experimental subagent that can read files before deciding).
  • Exit codes, for a command hook: 0 is success, and stdout is parsed as JSON if it starts with {; 2 blocks, and stderr is fed back (to the model for PreToolUse, Stop and the other blocking events); any other code is a non-blocking error and the action goes ahead. A mistyped script path exits 127 and therefore silently disables a policy hook.
  • JSON output: PreToolUse can answer permissionDecision allow, deny, ask or defer (defer only in -p), with a reason, an updatedInput that replaces the tool's input, and additionalContext. When hooks disagree, deny beats defer beats ask beats allow. A hook's allow never overrides a deny or ask rule: hooks can tighten permissions, not loosen them. A hook's deny holds even in bypassPermissions.
  • Timeouts: 600 s for command, http and mcp_tool handlers, 30 s for prompt, 60 s for agent; a timed-out PreToolUse hook does not block.
  • Trust: hooks run with your full user rights and outside the sandbox. In a -p run, a repository's .claude/settings.json hooks run without any trust prompt; the docs recommend --bare or --settings '{"disableAllHooks": true}' for repositories you do not trust (headless) DOCS.

What the two recordings show MEASURED:

5. Memory files: what loads, in what order, and when

Memory files are Markdown files of instructions that Claude Code puts into the context for you: CLAUDE.md and its relatives. They are not memory in the database sense; they are text paid for on every call, delivered "as a user message after the system prompt, not as part of the system prompt itself" (memory) DOCS. The documented rules:

  • Locations, broadest first: managed policy (/Library/Application Support/ClaudeCode/CLAUDE.md on macOS, /etc/claude-code/CLAUDE.md on Linux), user (~/.claude/CLAUDE.md), project (./CLAUDE.md or ./.claude/CLAUDE.md), local (./CLAUDE.local.md, meant to be git-ignored), and rules in .claude/rules/*.md.
  • Concatenated, not overridden: files in the working directory and every directory above it load at launch, ordered from the filesystem root down, CLAUDE.local.md after CLAUDE.md in each directory; if two instructions contradict each other, "Claude may pick one arbitrarily".
  • On demand: CLAUDE.md files in subdirectories, and rules with a paths: list in their frontmatter, load only when Claude reads, writes or edits a matching file.
  • Imports: @path inside a CLAUDE.md pulls in another file at launch, relative to the importing file, at most four hops deep. Imports organise a file; they do not save context.
  • AGENTS.md (the cross-tool convention other agents read) is read since 2.1.277, but by default only when there is no CLAUDE.md or CLAUDE.local.md at or above the working directory; a /config setting can load both.
  • Auto memory is the other half: notes Claude writes itself under ~/.claude/projects/<project>/memory/, whose index MEMORY.md loads at every start up to 200 lines or 25 KB. Subagents do not get it.
  • Size advice: under 200 lines per file; a file over 4 MiB is skipped. After /compact the project-root CLAUDE.md is re-read from disk; nested files and path rules load again on demand.

Eight canaries

To check the order rather than trust it, one recording planted eight files, each containing one unique word ("Canary: ALPHA-ROOT" and so on), then asked Haiku, with only the Read tool, to list every canary in its context, read textstats/core.py, and list them again (run memory). Step through what happened.

Every outcome matched the documentation MEASURED: four files at launch (the parent directory's CLAUDE.md, the project CLAUDE.md, its import and the rule without paths), two after the Read (the subdirectory's CLAUDE.md and the path-scoped rule), and two never. CLAUDE.local.md stayed out because these runs pass --setting-sources project, and "CLAUDE.local.md is skipped if you exclude local from --setting-sources"; AGENTS.md stayed out because a CLAUDE.md existed. The parent-directory canary is the one to remember: a CLAUDE.md anywhere above your project, in a home directory or a monorepo root, is in every session started below it.

A memory file is context, not configuration
The parent's trace lab measured a four-line CLAUDE.md stating the test command: 184 more tokens per call, and two of three Haiku runs used it while the third explored anyway (Trace and context lab) MEASURED. Instructions there are followed most of the time; anything that must hold every time is a hook or a permission rule (sections 3 and 4).

6. Skills: a description now, the body on demand

A skill is a folder with a SKILL.md: YAML frontmatter (a name and a description of when to use it) and Markdown instructions, plus any scripts or reference files it needs. Claude Code follows the Agent Skills open standard; custom slash commands in .claude/commands/ have been merged into skills (skills) DOCS. The design is progressive disclosure: only the name and description sit in context from the start; the body loads when the skill is invoked, through the Skill tool or by you typing /name, and then stays in the conversation.

  • Budget: each description is cut at 1,536 characters in the listing, and the whole listing gets 1% of the context window; past that, descriptions of the least-used skills are dropped (names stay) DOCS.
  • Control: disable-model-invocation: true keeps a skill out of Claude's view (you invoke it); user-invocable: false the opposite; allowed-tools pre-approves tools for the turn that invokes it; context: fork runs it in a fresh subagent; paths loads it only near matching files; !`command` in the body runs a shell command first and inlines its output.
  • After compaction the most recent invocation of each skill is re-attached, up to 5,000 tokens each and 25,000 in total.

Two one-call recordings measure the startup cost, identical except for one project skill (.claude/skills/run-tests/, a two-sentence description and a body containing the canary KILO-SKILLBODY), and a third gives the running example with the skill available MEASURED:

The skill's description cost 29 tokens at launch. 7. Subagents: a second loop with its own window

A subagent is another run of the loop that the main agent starts with the Agent tool: it gets a task message, works in its own context window, and only its final answer comes back. "The parent doesn't see the subagent's intermediate tool calls or outputs, only that final result" (tools reference) DOCS. What it starts with, per the subagents page DOCS:

  • Its own system prompt (the definition's Markdown body plus environment details), "not the Claude Code system prompt"; the delegation message Claude writes; the CLAUDE.md hierarchy and git status (the built-in Explore and Plan skip both); any skills listed in its definition, injected in full.
  • Not: the parent's conversation, the files it has read, the skills it invoked, its output style or its auto memory. "If a rule must [reach the subagent] ... restate it in the prompt you give Claude when delegating."
  • Definition: a Markdown file in .claude/agents/ (or ~/.claude/agents/, a plugin, or --agents JSON) with frontmatter: name, description (when to use it), tools or disallowedTools, model, permissionMode, maxTurns, skills, hooks, memory, isolation: worktree, omitClaudeMd (2.1.271).
  • Built-ins: Explore (read-only search), Plan (research during plan mode), general-purpose, claude, statusline-setup and claude-code-guide. Up to 20 run at once; by default a subagent may start its own, three levels deep; they run in the background by default and can be resumed with SendMessage. A fork (/subtask) is the exception that inherits the whole conversation and shares its prompt cache.

The recording (run subagent) defined a test-runner subagent (tools Bash and Read, model haiku, a five-line prompt: run the tests, report failures, edit nothing) and asked for the running example, "use the test-runner subagent to run the tests, once before your fix and once after it" MEASURED:

  • Background by default, even in -p. The Agent call returned at once ("Async agent launched successfully" with an id); the parent, rather than wait, went on reading the test file and the code itself, so the exploration was done twice. The final report arrived as a new turn, and the run ended with three result records, one per wake-up; the last one's totals are cumulative.
  • A smaller, separate window. Progress records put the subagent at 5,666 tokens after its first tool call, against 14,620 for the parent's first request: its own short system prompt instead of Claude Code's.
  • It did more than asked. Told to run the tests and report, the first instance made eight tool calls, including reading the source. A subagent's prompt is a request, like any other; its tools list is the enforcement (it had no Edit).
  • Its cost is visible only in the totals. The stream carries no usage records for subagent calls; the parent's eight calls add up to $0.062 at list prices, the result's modelUsage says $0.097, so the two subagent instances cost about $0.035, 36% of the run. That difference reproduces exactly only if the subagent's 9,884 cache-write tokens are 5-minute writes (1.25 times the input price) while the parent's were 1-hour writes (2 times): derived, since no record states the subagent's TTL. The parent's trace lab found the same with Explore: read cost from modelUsage, never from usage.
  • Naming. The init record lists the tool as Task; the call itself is named Agent.

Agent teams are different: separate Claude Code sessions with a shared task list and messages between them, experimental and off by default (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1), introduced as a research preview in 2.1.32 on 5 February 2026, not in 2.1.220 as the old page said (agent teams, changelog) DOCS. When several agents help or hurt is the subject of Multi-agent patterns; subagents as a context tool are on Context engineering.

8. Plan mode, and the model that answers it

Plan mode lets Claude read files and run read-only commands, write a plan, and edit nothing until a person approves it; in the terminal, Shift+Tab cycles into it. In -p runs and the Agent SDK "Plan mode keeps its blocks", and ExitPlanMode is disabled because nobody can approve (permission modes; the parent's trace lab) DOCS. In the permission battery, plan mode refused the edit and both writes with "Cannot write to ... while in plan mode", and refused the test command as needing approval MEASURED.

The same run asked for Haiku and its init record says Haiku, yet every one of its 13 calls was answered by claude-sonnet-5-5 MEASURED. The parent page recorded this on 2.1.289 and called it undocumented in the pages it had read; it is documented, in the changelog for 2.0.17 (15 October 2025): "Haiku 4.5 automatically uses Sonnet in plan mode, and Haiku for execution (i.e. SonnetPlan by default)" (changelog) DOCS. Its cousin is opusplan (1.0.77), which runs Opus while planning and Sonnet otherwise. The lesson stands: read the model field of each call, not the flag you passed, because the harness may route around it, and with it the price (Sonnet 5.5 costs twice Haiku 4.5 per token).

9. Headless runs: -p, the stream, the result

claude -p "task" runs one task without the interactive screen and exits: 0 on success, non-zero when the run fails, 143 on SIGTERM (headless) DOCS. Headless runs and trust
A -p run never shows the workspace trust dialog, so a repository's hooks, env, apiKeyHelper and .mcp.json servers are used anyway, while its permissions.allow rules are not (section 3) DOCS. The docs recommend --bare for scripts and CI: it skips discovery of hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md, and "will become the default for -p in a future release". It also reads only an API key or an apiKeyHelper passed with --settings, never OAuth, so it cannot run on a subscription login; the runs on this page instead pass --setting-sources project --strict-mcp-config and a throw-away directory.

Some slash commands work headless too. claude -p "/context" prints the window by category without calling the model (cost 0), and /compact runs inside a --input-format stream-json session, emitting a compact_boundary record whose preserved segment keeps the last 5 messages verbatim MEASURED; both are recorded on Context engineering: window budgets, caching, compaction, memory files, subagents, its "Compaction lab" tab. --system-prompt-snapshot (new in 2.1.290, on by default) records the system prompt on the first request and resends it verbatim until the conversation is compacted DOCS.

Other headless flags worth knowing: --json-schema for validated structured output (the frameworks root measured it: a tool named StructuredOutput, Topic: agentic-frameworks); --permission-prompt-tool to route approvals to an MCP tool; --permission-prompts none (2.1.259) to deny every prompt outright; --fallback-model; --no-session-persistence; --restricted (2.1.248) for evaluation harnesses, which removes command-running tools and ignores user and project settings.

11. Where the SDK begins

The Claude Agent SDK (Python claude-agent-sdk, TypeScript @anthropic-ai/claude-agent-sdk; renamed from the Claude Code SDK on 29 September 2025) runs this same loop, tools, permission system, hooks and MCP support as a library: your code supplies the prompt, the options and callbacks instead of a terminal. It drives a bundled copy of the CLI (version 0.2.163 bundled Claude Code 2.1.286 on 5 October), so everything on this page applies, with two differences that bite: hooks and permission prompts become Python or TypeScript callbacks, and unless you pass strict_mcp_config=True with explicit setting sources, a subscription login loads your connected apps as tools (measured by the frameworks root) MEASURED. A third catches people out: the SDK's system_prompt=None means an empty system prompt, not Claude Code's (the Python SDK passes --system-prompt ""), so the Claude Code preset must be asked for explicitly (Claude Agent SDK, its section 3). The library, its options and its deployment patterns are owned by Claude Agent SDK: the Claude Code loop as a library; when to use it instead of a framework is on Topic: agentic-frameworks.

Common mistakes

Running headless in the default mode and expecting the agent to test its work
In Manual mode -p refuses everything outside the read-only set, including the test command (section 3). Allow the exact test command with --allowedTools or --settings, or pick acceptEdits or dontAsk deliberately.
Putting allow rules in the repository's settings file for CI
In an untrusted folder a -p run ignores them, with only a line on stderr, while still running the repository's hooks. Pass rules on the command line (--settings, --allowedTools) or use managed settings.
Treating a Bash deny rule as a sandbox
It matches the command's text; /bin/rm, bash -c or a Python script get around it. Text rules stop mistakes, an OS sandbox or a container stops actions.
Writing an audit hook on PostToolUse only
Failed calls fire PostToolUseFailure instead; the recorded logger missed 4 of 11 calls (section 4).
Reading cost from usage
It misses subagent calls and, when a budget stops a run, the last call. Priced at the list prices, modelUsage reproduced total_cost_usd in 22 of the 23 recordings; the subagent run reproduces only if the subagent's 9,884 cache-write tokens are priced as 5-minute writes (the main thread's were 1-hour writes), a split modelUsage does not show. A resumed session's totals include the earlier session.
Trusting the model flag in plan mode
Haiku in plan mode is answered by Sonnet (since 2.0.17). Check the model on each call.
Assuming a capped Read says it was capped
In this recording a token-capped Read returned 1,821 of 3,001 lines with no notice the model could see. Ask for line ranges, or grep first, on long files.
Expecting a subagent to wait
Subagents run in the background by default; the parent may duplicate their work while waiting. Say in the delegation what the parent should do meanwhile, or ask for a foreground run.

Interview questions

Answer aloud first, then open.

In what order does Claude Code decide whether a tool call runs?
PreToolUse hooks first (exit 2 blocks before any rule); then deny, ask and allow rules in that order, first match wins, any scope; the tool's own checks; then the permission mode for whatever nothing matched (read-only set runs, acceptEdits approves edits, dontAsk denies, auto asks a classifier, plan blocks writes); anything left asks a person, which in -p means refused.
Why can a hook enforce a rule that CLAUDE.md cannot?
CLAUDE.md is text the model reads and may ignore; a hook is code the harness runs outside the model, whose exit code decides. In the recording the model even tried a different parameter to get past the guard; the hook did not care.
What does a subagent see when it starts, and what comes back?
Its own system prompt, the delegation message, CLAUDE.md files and git status (not for Explore and Plan), and any preloaded skills; not the parent's history. Only its final message returns. Its tokens show up in modelUsage, not in the stream.
A skill and a CLAUDE.md line both say "run python3 tests/test_core.py". What is the difference in cost and reliability?
The CLAUDE.md line is paid on every call and always visible; the skill costs its description (29 tokens here) until invoked, then its body once. Neither is enforced: both are context. Choose CLAUDE.md for facts needed every session, a skill for procedures needed sometimes, a hook or rule for anything that must always hold.
How would you run Claude Code safely in CI on untrusted pull requests?
--bare (no repo hooks, skills, MCP or CLAUDE.md) or at least --settings '{"disableAllHooks": true}' and --strict-mcp-config; an explicit --permission-mode (dontAsk) with exact allow rules on the command line; a container or the OS sandbox with no secrets and egress limited; --max-turns and --max-budget-usd (knowing the budget overshoots by one call); read the result's subtype and modelUsage.
Why did three python3 commands in one reply run one after another, but three sleeps at once?
The harness runs calls concurrently only when it can tell they have no side effects; sleep is classified read-only, an arbitrary script is not. Parallel tool calls are a request; concurrency is the harness's decision.
Where do the documented limits and the recordings disagree?
acceptEdits refused sed -i though the docs list sed as approved; a token-capped Read gave no visible "PARTIAL view" notice; Read has a hard 256 KB error not stated in the tools reference. Recordings are of one version and one model, so re-check on upgrade.
