3. Permissions: a mode, a list of rules, and what the recordings refused

Every tool call passes a permission layer before it runs: code in the harness, not the model, that answers allow, ask (a person decides) or deny. Rules "are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows" ({{permissions|https://code.claude.com/docs/en/permissions}}). In a headless run nobody is there to answer, so "ask" becomes a refusal ("This command requires approval") unless you give it a handler (--permission-prompt-tool, or the Agent SDK's callback) DOCS.

From {{permission modes|https://code.claude.com/docs/en/permission-modes}}, read 6 Oct 2026 DOCS. The interactive terminal and claude -p start in different modes, and the defaults have moved between versions (see Dated changes), so pass the mode you want.

A rule is Tool or Tool(specifier) in an allow, ask or deny list, in a settings file or a flag. The specifier depends on the tool: a command pattern for Bash (Bash(npm run *)), a gitignore-style path for the file tools (Edit(/src/**) covers Edit, Write and NotebookEdit; Read(~/secrets/**) also covers Grep and Glob), a domain for WebFetch, a subagent type for Agent. "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order", so an allow rule can never carve an exception out of a deny, and a deny at any level (managed, user, project, flag) beats an allow at any other DOCS. Bash rules split compound commands on &&, ||, ;, |, & and newlines and require every part to match an allow; a deny or ask matches if any part does.

What the grid shows MEASURED:

  1. Manual mode in -p ran 2 of 12: the read and ls, both in the read-only set. The test command was refused: a headless agent in the default mode cannot check its own work unless you allow that command or choose a mode deliberately.
  2. acceptEdits ran 7. It approved the edits, the new file and rm inside the working directory, but refused sed -i ("sed command requires approval (contains potentially dangerous operations)") although the docs list sed as approved; the parent's trace lab met the same refusal on 2.1.289.
  3. Project allow rules are ignored in an untrusted folder. From .claude/settings.json, stderr said "Ignoring 2 permissions.allow entries from .claude/settings.json: this workspace has not been trusted" and the allowed test command was refused; passed with --settings the same rules worked, and the deny rules (Edit(tests/**), Bash(rm *)) and ask rule (Bash(curl *)) applied either way. As documented: allow rules "grant capability", so they wait for the trust dialog a -p run never shows. For CI, pass rules on the command line or in managed settings.
  4. Variables are not trusted. In the tool probe, echo "PROBE=$PROBE" was refused with an allow rule for echo * in place: "A variable in this command can't be checked before it runs."
  5. python is not python3. An allow rule for python3 * does not cover the python Haiku kept typing; in auto mode on Sonnet the classifier let it through and the shell answered "command not found: python" (exit 127).
  6. Auto mode decides by your request, not by a policy. It needs Opus 4.6, Sonnet 4.6 or later, or a Fable model on the Anthropic API; asked for with Haiku, the run silently started in Manual (init record: default). On Sonnet 5.5 all twelve actions ran, test edit, curl and outside write included, because the prompt asked for each and the classifier checks that actions "align with your request". Whether it tells an injected instruction from yours is the sibling page's subject ({{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}).
What "deny" covers, and what it does not
A Bash deny rule "covers the invocation Claude usually produces and isn't a security boundary around the program": Bash(rm *) stops rm -rf build/ but not /bin/rm -rf build/ or bash -c 'rm -rf build/', and a Read deny does not stop a Python script that opens the file itself ({{permissions|https://code.claude.com/docs/en/permissions}}) DOCS. For enforcement that does not depend on the command's text, the docs point to the OS sandbox (Seatbelt on macOS, bubblewrap on Linux, off by default, Bash only); when it is on, autoAllowBashIfSandboxed (default true) lets sandboxed commands run without prompts even in Manual mode. Sandboxes, egress and injection are on {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}.
How the gate model was built, what no mode approves, and a playground for your own rules (depth)

The stages and their order are a model built from the permissions, permission-modes and hooks pages (hook exit code 2 "stops the tool call before permission rules are evaluated"; then deny, ask, allow; the mode decides what nothing matched) plus two orderings the recordings show: a deny rule on a file path is enforced inside the file tool's own input check, before its read-before-edit check, and that check runs before the mode. Actions no mode auto-approves, even bypassPermissions: tools matched by an explicit ask rule, AskUserQuestion, MCP tools marked as needing a person, and rm or rmdir aimed at a critical path (the filesystem root, your home directory, the working directory). Writes to protected paths (.git, .claude, .vscode, shell rc files, .mcp.json) are never pre-approved by allow rules. Project or local settings cannot set defaultMode to auto or bypassPermissions ({{permission modes|https://code.claude.com/docs/en/permission-modes}}) DOCS.

The playground runs the same model as the stepper and the grid's score. It encodes the documented order (hooks, then deny, ask and allow rules, then the mode) and the orderings the recordings showed; it is a teaching model, not Claude Code's code. Presets load the cases that surprised the recordings.

Bash rules split the command on &&, ||, ;, | and &; an allow must match every part, a deny or ask any part; Bash(x *) matches x and x ...; Edit(path) covers Edit and Write with ** and * globs.
