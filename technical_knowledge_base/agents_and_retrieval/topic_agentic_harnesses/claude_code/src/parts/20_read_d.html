3. Permissions: modes, rules, and what the recordings refused

Every tool call passes a permission layer before it runs: code in the harness, not the model, that answers allow, ask (a person decides) or deny. In a headless run nobody is there to answer, so "ask" becomes a refusal ("This command requires approval") unless you give it a handler (--permission-prompt-tool, or the Agent SDK's callback) DOCS. The docs put the point plainly: rules "are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows" ({{permissions|https://code.claude.com/docs/en/permissions}}).

The two inputs: a mode and a list of rules

Mode (--permission-mode)Runs without asking (docs)Best for (docs)
default, shown as Manual (manual is an alias)Reads onlyReviewing every action yourself
acceptEditsReads, file edits, and common filesystem commands (mkdir, touch, rm, rmdir, mv, cp, sed) inside the working directoriesIterating on code you are reviewing
planReads, plus classifier-approved commands when auto mode is available; never edits until a plan is approvedExploring before changing
autoEverything, after a separate classifier model checks each action against your requestLong tasks with fewer prompts
dontAskReads and pre-approved tools; anything that would prompt is deniedLocked-down CI and scripts
bypassPermissionsEverything except the few actions no mode approvesIsolated containers and VMs only

From {{permission modes|https://code.claude.com/docs/en/permission-modes}}, read 6 Oct 2026 DOCS. The interactive terminal starts in auto since 2.1.283; claude -p starts in Manual in sessions that fetch feature flags, so pass the mode you want.

A rule is Tool or Tool(specifier) in an allow, ask or deny list, in a settings file or a flag. The specifier depends on the tool: a command pattern for Bash (Bash(npm run *)), a gitignore-style path for the file tools (Edit(/src/**) covers Edit, Write and NotebookEdit; Read(~/secrets/**) also covers Grep and Glob), a domain for WebFetch, a subagent type for Agent. "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order", so an allow rule can never carve an exception out of a deny, and a deny at any level (managed, user, project, flag) beats an allow at any other DOCS. Bash rules split compound commands on &&, ||, ;, |, & and newlines and require every part to match an allow; a deny or ask matches if any part does.

One call through the layers

Pick a recorded action and a configuration; the animation walks the call through the checks in order and stops where the decision was made, with the message the recording got. Change only the configuration and play it again: same input, different gate.

The stages and their order are a model built from the permissions, permission-modes and hooks pages (hook exit code 2 "stops the tool call before permission rules are evaluated"; then deny, ask, allow; the mode decides what nothing matched) plus two orderings the recordings show: a deny rule on a file path is enforced inside the file tool's own input check, before its read-before-edit check, and that check runs before the mode. The {{Permission lab|#t-gate}} compares this model with all 96 recorded decisions (it reproduces every one the classifier did not make, by construction, since part of the order was read off these recordings).

What twelve scripted actions met in eight configurations

The battery (prompt in the {{Recordings|#t-runs}} tab) asked Haiku to attempt twelve actions in order, one call each, and never work around a refusal: read a file, ls, run the tests with python3 and with python, edit the code, write a file, edit a test, sed -i, ls && rm, rm, curl, write outside the working directory. Six findings, each from those recordings MEASURED:

  1. Manual mode in -p ran 2 of 12: the read and ls, both in the read-only set. Running the tests was refused ("This command requires approval"), so a headless agent in the default mode cannot even check its own work unless you allow the test command.
  2. acceptEdits ran 7. It approved the edits, the new file and rm inside the working directory, as documented, but refused sed -i with "sed command requires approval (contains potentially dangerous operations)", although the docs list sed among the commands acceptEdits approves. The parent's trace lab met the same refusal on 2.1.289.
  3. Project allow rules are ignored in an untrusted folder. The same rules in .claude/settings.json and passed with --settings gave different results: from the project file, stderr said "Ignoring 2 permissions.allow entries from .claude/settings.json: this workspace has not been trusted", and the allowed test command was refused; the deny rules (Edit(tests/**), Bash(rm *)) and the ask rule (Bash(curl *)) applied either way. The docs say exactly this: allow rules "grant capability", so they wait for the trust dialog, which a -p run never shows ({{permissions|https://code.claude.com/docs/en/permissions}}).
  4. Variables are not trusted. In the tool probe, echo "PROBE=$PROBE" was refused with an allow rule for echo * in place: "A variable in this command can't be checked before it runs." A rule matches text; a variable makes the text unknowable.
  5. The python and python3 lesson, again. Haiku typed python in the parent's runs and here; an allow rule for python3 * does not cover it. In auto mode on Sonnet the classifier let it through and the shell answered "command not found: python" (exit 127).
  6. Auto mode decides by your request, not by a policy. Auto mode needs Opus 4.6, Sonnet 4.6 or later, or a Fable model on the Anthropic API; asked for with Haiku, the run silently started in Manual (its init record says default), as documented. On Sonnet 5.5 all twelve actions ran, including editing a test, curl to the internet and a write outside the working directory, because the prompt asked for each of them and the classifier checks that actions "align with your request". Run the same actions from an injected instruction and the classifier is meant to see the difference; that defence is the sibling page's subject ({{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}).
What "deny" covers, and what it does not
A Bash deny rule "covers the invocation Claude usually produces and isn't a security boundary around the program": Bash(rm *) stops rm -rf build/ but not /bin/rm -rf build/ or bash -c 'rm -rf build/', and a Read deny does not stop a Python script that opens the file itself ({{permissions|https://code.claude.com/docs/en/permissions}}) DOCS. For enforcement that does not depend on the command's text, the docs point to the OS sandbox (Seatbelt on macOS, bubblewrap on Linux, off by default, Bash only); when it is on, autoAllowBashIfSandboxed (default true) lets sandboxed commands run without prompts even in Manual mode. Sandboxes, egress and injection are on {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}.

Actions no mode auto-approves, even bypassPermissions: tools matched by an explicit ask rule, AskUserQuestion, MCP tools marked as needing a person, and rm or rmdir aimed at a critical path (the filesystem root, your home directory, the working directory). Writes to protected paths (.git, .claude, .vscode, shell rc files, .mcp.json) are never pre-approved by allow rules. Project or local settings cannot set defaultMode to auto or bypassPermissions ({{permission modes|https://code.claude.com/docs/en/permission-modes}}) DOCS.
