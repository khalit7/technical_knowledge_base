1. The loop, as Claude Code runs it

The loop itself is the one the parent page builds: send the system prompt, the tool definitions and the conversation; if the reply asks for tools, run them, append the results and call again; stop when a reply asks for none. Anthropic's own description is three phases, "gather context, take action, and verify results", which "blend together" ({{How Claude Code works|https://code.claude.com/docs/en/how-claude-code-works}}) DOCS. What this section adds is the behaviour you only see in a recording.

A reply can hold several tool calls. The model may ask for three tools in one reply (a parallel tool call); the harness runs them, returns all three results in the next request, and only then calls the model again. Whether the three actually run at the same time is the harness's choice, not the model's. Two recordings asked for exactly that:

In the first run each command printed its own start and end time, and they ran one after another: A from 930.00 to 932.01 seconds, B from 932.11 to 934.12, C from 934.19 to 936.19 (clock seconds modulo 1,000) MEASURED. In the second, three sleep 2 calls in one reply all returned within 0.04 s of each other, 3.0 s after the reply finished streaming: they ran together MEASURED. The timestamps show one more thing: execution does not wait for the whole reply. In the second half of that run, ls returned its result (at 9.82 s) before the model had finished streaming the next call, cat README.md (9.88 s). Claude Code can start a call as soon as its block of the reply is complete, and queues the ones it will not run alongside others. The difference is the command, not the tool: sleep is a command the harness can tell has no side effects, a python3 -c script is not. The old page's rule, "read-only tools in parallel, mutating tools serially", is therefore right in spirit for Bash on 2.1.290; the documentation pages read do not state the rule itself, only that PostToolUse hooks "fire concurrently when Claude makes parallel tool calls" and that a PostToolBatch hook runs once the whole batch has resolved ({{hooks reference|https://code.claude.com/docs/en/hooks}}) DOCS.

A turn is not a model call. The CLI's num_turns counts something else than API requests (the parent's {{Trace and context lab|n:3c65c17b0d0d81d881a8fe98b4cff7bb}} shows the mismatch). Here the limit flag makes it concrete: with --max-turns 2 the run made two model calls, stopped before the third, and reported num_turns: 3 with subtype error_max_turns MEASURED (section 9). When you budget an agent by turns, test what your version counts.

Messages arriving mid-turn. In the terminal, a message you type while Claude works is queued and read before its next step; Esc stops the running tool; a send-now key (ctrl+enter) interrupts and sends the queue (added in 2.1.275, {{changelog|https://code.claude.com/docs/en/changelog}}) DOCS. In a headless run the same happens through --input-format stream-json: two user messages written to stdin at once produced a single result record, and the reply after the first tool call answered the first question and went straight on to the second MEASURED (run stream). A harness that only reads input between turns would have produced two results.

Errors stay in the loop. Every failure in the recordings came back as an ordinary tool result marked is_error: a refused permission, a missing file, a non-unique edit string, a timed-out command (exit 143). The model reads it and decides what to do next; the harness never retries on its own. The parent page argues why that is the right design; the next section lists the exact messages.
