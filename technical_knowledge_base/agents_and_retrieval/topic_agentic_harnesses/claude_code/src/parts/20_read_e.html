4. Hooks: your code at fixed points in the loop

A hook is a program the harness runs at a named moment, with a JSON description of the moment on its standard input. Its exit code and output can add context, change a tool's input, or stop what was about to happen. Hooks exist because a prompt is advice and a hook is enforcement: the docs put the rule in one line, "To block an action regardless of what Claude decides, use a PreToolUse hook" ({{memory|https://code.claude.com/docs/en/memory}}) DOCS.

The mechanics

  • Where: a hooks block in any settings file (user, project, local, managed), a plugin's hooks/hooks.json, or the frontmatter of a skill or subagent (active while it runs). Entries merge across levels; identical handlers run once; all matching hooks run in parallel ({{hooks|https://code.claude.com/docs/en/hooks}}) DOCS.
  • Shape: event, then a matcher (for tool events, a tool name, a | list or a regular expression), then handlers. Five handler types: command (a shell command, the common case), http (POST the JSON to a URL), mcp_tool, prompt (a one-turn model call that returns ok or not) and agent (an experimental subagent that can read files before deciding).
  • Exit codes, for a command hook: 0 is success, and stdout is parsed as JSON if it starts with {; 2 blocks, and stderr is fed back (to the model for PreToolUse, Stop and the other blocking events); any other code is a non-blocking error and the action goes ahead. A mistyped script path exits 127 and therefore silently disables a policy hook.
  • JSON output: PreToolUse can answer permissionDecision allow, deny, ask or defer (defer only in -p), with a reason, an updatedInput that replaces the tool's input, and additionalContext. When hooks disagree, deny beats defer beats ask beats allow. A hook's allow never overrides a deny or ask rule: hooks can tighten permissions, not loosen them. A hook's deny holds even in bypassPermissions.
  • Timeouts: 600 s for command, http and mcp_tool handlers, 30 s for prompt, 60 s for agent; a timed-out PreToolUse hook does not block.
  • Trust: hooks run with your full user rights and outside the sandbox. In a -p run, a repository's .claude/settings.json hooks run without any trust prompt; the docs recommend --bare or --settings '{"disableAllHooks": true}' for repositories you do not trust ({{headless|https://code.claude.com/docs/en/headless}}) DOCS.

Four hooks, same prompt, before and after

Two Haiku runs got the same prompt: fix the apostrophe bug, keep the change minimal, and delete notes_old.txt with rm (allowed by --allowedTools "Bash(rm *)"). The second run's project had four hooks: a SessionStart hook that prints the test command (its stdout becomes context), a PreToolUse guard on Bash that exits 2 on rm or sed -i, a PostToolUse logger that appends every call to a file, and a Stop hook that runs the tests and returns {"decision": "block"} while any fail (once: it checks stop_hook_active so it cannot loop). Play both lanes together; the hook events are the purple ones.

What the two recordings show MEASURED:

  • Without hooks the run stopped half done. Haiku fixed the apostrophe bug, deleted the file, tried to run the tests as python (refused: only python3 and rm were allowed), never ran them, and reported success with one test still failing.
  • The SessionStart line changed behaviour at no cost to the model. With the hook, Haiku ran python3 tests/test_core.py on its first try.
  • The Stop hook turned "done" into "not done". At the first attempt to finish, the hook's reason ("the test suite still fails ... FAIL test_top_words_ties_alphabetical") came back as a user message; Haiku fixed the second bug, reran the tests (0 failed) and stopped. The hook ran a second time and let it.
  • The guard held twice, and the second time it mattered. The first rm was blocked with the hook's stderr as the reason. After the tests passed, Haiku wrote "let me try with the dangerously flag since you explicitly requested it" and reissued the command with dangerouslyDisableSandbox: true, a parameter meant for retrying outside the OS sandbox. The hook does not care about that flag, so the call was blocked again, and the final summary said the file was left in place. A rule the model can argue with is not a rule.
  • The logger missed the failures. PostToolUse fires "after a tool call succeeds"; the test runs that exited 1 and the blocked calls went to PostToolUseFailure, which had no handler, so the log holds 7 of the 11 tool calls. An audit hook needs both events.

The hook scripts and settings are in this page's src/hooks/; the log's first line shows the input every PostToolUse hook receives: cwd, duration_ms, hook_event_name, permission_mode, prompt_id, session_id, tool_input, tool_name, tool_response, tool_use_id, transcript_path. With --include-hook-events, -p streams a hook_started and a hook_response record (with stdout, stderr and exit code) for each.
