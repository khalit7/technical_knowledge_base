7. Subagents: a second loop with its own window

A subagent is another run of the loop that the main agent starts with the Agent tool: it gets a task message, works in its own context window, and only its final answer comes back. "The parent doesn't see the subagent's intermediate tool calls or outputs, only that final result" ({{tools reference|https://code.claude.com/docs/en/tools-reference}}) DOCS. What it starts with, per the {{subagents page|https://code.claude.com/docs/en/sub-agents}} DOCS:

  • Its own system prompt (the definition's Markdown body plus environment details), "not the Claude Code system prompt"; the delegation message Claude writes; the CLAUDE.md hierarchy and git status (the built-in Explore and Plan skip both); any skills listed in its definition, injected in full.
  • Not: the parent's conversation, the files it has read, the skills it invoked, its output style or its auto memory. "If a rule must [reach the subagent] ... restate it in the prompt you give Claude when delegating."
  • Definition: a Markdown file in .claude/agents/ (or ~/.claude/agents/, a plugin, or --agents JSON) with frontmatter: name, description (when to use it), tools or disallowedTools, model, permissionMode, maxTurns, skills, hooks, memory, isolation: worktree, omitClaudeMd (2.1.271).
  • Built-ins: Explore (read-only search), Plan (research during plan mode), general-purpose, claude, statusline-setup and claude-code-guide. Up to 20 run at once; by default a subagent may start its own, three levels deep; they run in the background by default and can be resumed with SendMessage. A fork (/subtask) is the exception that inherits the whole conversation and shares its prompt cache.

The recording (run subagent) defined a test-runner subagent (tools Bash and Read, model haiku, a five-line prompt: run the tests, report failures, edit nothing) and asked for the running example, "use the test-runner subagent to run the tests, once before your fix and once after it" MEASURED:

  • Background by default, even in -p. The Agent call returned at once ("Async agent launched successfully" with an id); the parent, rather than wait, went on reading the test file and the code itself, so the exploration was done twice. The final report arrived as a new turn, and the run ended with three result records, one per wake-up; the last one's totals are cumulative.
  • A smaller, separate window. Progress records put the subagent at 5,666 tokens after its first tool call, against 14,620 for the parent's first request: its own short system prompt instead of Claude Code's.
  • It did more than asked. Told to run the tests and report, the first instance made eight tool calls, including reading the source. A subagent's prompt is a request, like any other; its tools list is the enforcement (it had no Edit).
  • Its cost is visible only in the totals. The stream carries no usage records for subagent calls; the parent's eight calls add up to $0.062 at list prices, the result's modelUsage says $0.097, so the two subagent instances cost about $0.035, 36% of the run. That difference reproduces exactly only if the subagent's 9,884 cache-write tokens are 5-minute writes (1.25 times the input price) while the parent's were 1-hour writes (2 times): derived, since no record states the subagent's TTL. The parent's trace lab found the same with Explore: read cost from modelUsage, never from usage.
  • Naming. The init record lists the tool as Task; the call itself is named Agent.

Agent teams are different: separate Claude Code sessions with a shared task list and messages between them, experimental and off by default (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1), introduced as a research preview in 2.1.32 on 5 February 2026, not in 2.1.220 as the old page said ({{agent teams|https://code.claude.com/docs/en/agent-teams}}, {{changelog|https://code.claude.com/docs/en/changelog}}) DOCS. When several agents help or hurt is the subject of {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}; subagents as a context tool are on {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}.

8. Plan mode, and the model that answers it

Plan mode lets Claude read files and run read-only commands, write a plan, and edit nothing until a person approves it; in the terminal, Shift+Tab cycles into it. In -p runs and the Agent SDK "Plan mode keeps its blocks", and ExitPlanMode is disabled because nobody can approve ({{permission modes|https://code.claude.com/docs/en/permission-modes}}; the parent's trace lab) DOCS. In the permission battery, plan mode refused the edit and both writes with "Cannot write to ... while in plan mode", and refused the test command as needing approval MEASURED.

The same run asked for Haiku and its init record says Haiku, yet every one of its 13 calls was answered by claude-sonnet-5-5 MEASURED. The parent page recorded this on 2.1.289 and called it undocumented in the pages it had read; it is documented, in the changelog for 2.0.17 (15 October 2025): "Haiku 4.5 automatically uses Sonnet in plan mode, and Haiku for execution (i.e. SonnetPlan by default)" ({{changelog|https://code.claude.com/docs/en/changelog}}) DOCS. Its cousin is opusplan (1.0.77), which runs Opus while planning and Sonnet otherwise. The lesson stands: read the model field of each call, not the flag you passed, because the harness may route around it, and with it the price (Sonnet 5.5 costs twice Haiku 4.5 per token).
