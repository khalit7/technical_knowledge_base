4. Control: stopping, planning, delegating

In the loop of section 1 the model stops by replying without a tool call (the API marks it end_turn). A harness adds hard limits the model cannot talk its way past: a maximum number of turns, a token or dollar budget, a wall-clock timeout, and the user's interrupt. The two classic failures are opposites: stopping too early (declaring victory without checking) and never stopping (looping on the same failing approach). Four mechanisms recur across harnesses, each defined in a sentence here and owned elsewhere:

Hooks

A hook is the harness running your code at a fixed point in the loop. Claude Code documents 33 hook events; a PreToolUse hook that exits with code 2 blocks the call whatever the model wanted. A rule that must hold every time belongs in a hook, not in the prompt. {{Claude Code|n:3c65c17b0d0d81db9c7fc54987c1ab65}} section 4.

Planning

A plan mode lets the model read but not change anything until a person approves a plan; a todo list is a tool whose only effect is a visible checklist in the context. {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}} section 8; Claude Code's plan mode, and the Sonnet model that answers it when you asked for Haiku, in {{Claude Code|n:3c65c17b0d0d81db9c7fc54987c1ab65}} section 8.

Subagents

A subagent is a second loop with its own fresh window: it does the reading, and only its summary comes back. It isolates context; it does not save tokens. {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} section 6; when several agents help or hurt, {{Multi-agent patterns|n:3c65c17b0d0d8194a306c37803387bf3}}.

Long-running agents

Past one context window the agent needs state outside it: Anthropic's long-running harness has an initializer agent write a progress log and a feature list that each later session reads. Cloud and background agents are the same idea on a managed machine, returning a branch or pull request. {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}} section 8; {{Context engineering|n:3f15c17b0d0d811292cee46514370431}} section 7.

5. Safety: permissions, sandboxes, injection

Every tool call runs with the harness's rights, which on a laptop are yours. Two things can go wrong: the model can simply be wrong (delete the wrong directory, push to the wrong branch), and it can be steered by text it reads. Prompt injection is an instruction planted in a file, web page, issue or tool result that the model follows as if the user had written it. Neither can be fixed inside the model with certainty, so the harness puts controls around it, in layers, each owned by a section of {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}:

1. Permission gate

Before each call, rules decide allow, deny or ask a person, and anything unknown fails closed. A gate decides which commands start; an allowed command still runs with your rights. Agent security section 4 runs the {{Loop lab|#t-loop}}'s gate on eleven actions; Claude Code's rules and modes are {{Claude Code|n:3c65c17b0d0d81db9c7fc54987c1ab65}} section 3.

2. Sandbox

An operating-system boundary around what does run: which files it may write and which hosts it may reach. Agent security section 6; how namespaces, seccomp and Seatbelt work, {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}.

3. A machine you can throw away

Containers and cloud VMs, where full autonomy is acceptable because the blast radius is the box.

4. Egress and secrets

The one path out, written over destinations rather than tools, and credentials the model never sees. Agent security sections 7 and 8.

The lethal trifecta. Simon Willison's framing (16 Jun 2025): an agent that has access to private data, exposure to untrusted content and a way to communicate externally can be made to send your data to an attacker, and no current filter reliably prevents it; the defence is to never combine all three. {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}} section 1 turns it into a design tool: tick the controls your agent has and see which leg goes.
