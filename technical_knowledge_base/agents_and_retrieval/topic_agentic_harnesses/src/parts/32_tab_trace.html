What this tab is: real Claude Code runs, opened up

A trace is the record of everything an agent did in one session: every call to the model, every tool it asked for, every result it got back, and what each call cost. Reading traces is how you learn what a harness really does, as opposed to what its documentation says it does. This tab holds {{the running example|#t-read}} worked by 16 real Claude Code sessions recorded on 2026-10-05, plus 6 one-call sessions that measure the startup context, and a context lab built on those numbers.

Each run is one command, started in a fresh copy of the task repository (a tiny Python library, textstats, with two planted bugs and a three-test runner):

claude -p "The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests." \
  --output-format stream-json --verbose --include-partial-messages \
  --no-session-persistence --setting-sources project --strict-mcp-config \
  --model haiku --permission-mode acceptEdits \
  --tools "Read,Edit,Write,Bash,Grep,Glob" \
  --allowedTools "Bash(python3:*)" "Bash(python:*)" "Bash(ls:*)" "Bash(cat:*)" \
  --append-system-prompt "Never use the em-dash character."

-p runs one task without the interactive screen and exits. stream-json prints one JSON record per line as things happen. --include-partial-messages adds the raw API stream events, which is the only place the per-call output token counts appear. --allowedTools pre-approves a few shell commands; anything else the model tries in the shell is refused by the permission layer, and you will see that happen.

Three things to keep in mind while reading the numbers
  • "API-price equivalent" is not what these runs cost. They ran on a Claude subscription. The CLI still reports total_cost_usd, the price the same tokens would have at Anthropic's list prices; every figure here was recomputed from the token counts and the {{pricing page|https://platform.claude.com/docs/en/about-claude/pricing}} (read 2026-10-05) and matches the CLI's figure to the cent in all runs but one, the subagent run, explained below.
  • One task, a few runs each. Three runs per setting show the spread, not a distribution. Treat differences of one or two calls as noise.
  • Redacted. The raw files hold the recording machine's paths, session ids and account details. The copies in src/trace/recordings/ replace the task directory with /work, keep only a whitelist of the init record, relabel ids and drop thinking signatures; a scan proves no home path, user name or token prefix remains. Claude Code's own tool messages contain em-dashes (for example "file state is current in your context"); in the copies each is replaced by a comma.

Anatomy of a recording

A recording is a list of JSON records. Five kinds matter:

system / init
The first record: what the harness was configured with before the model saw anything. Model id, permission mode, the exact tool list, the subagent types available, the Claude Code version, the working directory.
assistant
What the model produced. One API response can arrive as several records (a thinking block, then text, then one or more tool_use blocks), all with the same message id.
user
Despite the name, mostly not from you: this is where the harness puts each tool_result, the output of a tool it ran on the model's behalf, sent back as the next input.
stream_event
The raw API stream. message_start carries the input side of a call's usage; message_delta at the end carries the final output tokens, thinking tokens and the stop reason (tool_use means "run my tools and call me again"; end_turn means "I am done").
result
The last record: number of turns, wall time, API time, total usage, per-model usage, cost equivalent, permission denials, subagent statistics, and the final answer text.

What the init record reveals about the harness

It is a statement of the harness's configuration, and three things in it are worth noticing. The tool list is exactly what was passed, which is the list the model will be offered. The agents list shows that even with no Agent tool enabled, Claude Code knows its built-in subagent types. And the model id is the full dated name the alias haiku resolved to (claude-haiku-4-5-20251001); sonnet resolved to claude-sonnet-5-5, as the {{model configuration docs|https://code.claude.com/docs/en/model-config}} say for the Anthropic API.

What the stream does not show

The system prompt and the tool definitions are not in the recording

You never see the text the model was given before your prompt: Claude Code's system prompt, the tool schemas, the environment block, CLAUDE.md. You only see its size, as the input tokens of the first call (13,242 for these Haiku runs, measured below). For what it contains, the source is Anthropic's documentation, not a guess: the {{context window explorer|https://code.claude.com/docs/en/context-window}} lists the system prompt ("core instructions for behavior, tool use, and response formatting"), auto memory, environment info (working directory, platform, git state), deferred MCP tool names, skill descriptions, and the user and project CLAUDE.md files, each with a representative size; the {{pricing page|https://platform.claude.com/docs/en/about-claude/pricing}} adds that any request with tools also carries a tool-use system prompt (496 tokens for Haiku 4.5) plus the tool names, descriptions and schemas. Thinking is the same: the stream says thinking happened and how many tokens it used, but the text arrives empty with only an encrypted signature.

Experiments, each read from its trace

A CLAUDE.md that states the test command

The task repository got a four-line CLAUDE.md ("All code is in textstats/core.py ... Run the tests with: python3 tests/test_core.py"). It costs tokens of startup context against without it, so about 184 tokens. Two of three Haiku runs then started by running the tests and finished in and calls, against 11 to 12 without the file; the third explored anyway and used . A memory file saves turns when it answers the question the agent would otherwise spend calls on, and it is not obeyed every time.

Plan mode against acceptEdits

With --permission-mode plan the run read the code, wrote its plan to a file under Claude Code's own plans folder, then called ExitPlanMode, which a non-interactive run cannot use ("ExitPlanMode is disabled for this session"); it changed no code and said so. One surprise in the trace: every call in that run was answered by claude-sonnet-5-5, although the run asked for Haiku and the init record says Haiku. The per-call model field and the result's per-model usage both show it; the documentation pages read for this tab do not describe a model switch in plan mode, so treat it as observed on version 2.1.289, not as a documented rule. The {{permission modes page|https://code.claude.com/docs/en/permission-modes}} does say plan mode keeps its blocks in -p runs.

A 491 KB file in the way

The prompt pointed at ci.log, 6,005 lines of heartbeat noise with five relevant lines in the middle. Haiku tried to Read it whole and got an error result ("File content (479.4KB) exceeds maximum allowed size (256KB). Use offset and limit parameters ... or search for specific content"), then did exactly that: one Grep for FAIL|ERROR|failed|error returned the four lines it needed. Sonnet went through the shell (grep -v heartbeat ci.log | head -60). Neither run put the log into its context, which is the point of the harness's limits: the Read tool's size cap and the shell's 30,000-character output cap (default of BASH_MAX_OUTPUT_LENGTH, {{env-vars docs|https://code.claude.com/docs/en/env-vars}}) turn a context-flooding mistake into a cheap error message the model can act on.

A subagent

Asked to "use a subagent to investigate the failures before you edit anything", Haiku called the Agent tool with the built-in Explore type, which ran in the background. The subagent's own tool calls appear in the stream (tagged with the parent tool id and indented in the viewer); its model calls carry no usage records, and the result record's usage covers only the main thread. The per-model totals do include it: in all, of which the main thread's calls account for $0.0619, so the subagent cost about $0.033. Adding the Agent tool also changed the cached prefix (its definition is about 2,700 tokens, measured below), so the first call found nothing in cache. A subagent buys context isolation, not savings, on a task this small.

Prompt caching and its time to live

Claude Code caches the conversation prefix on every call. On this subscription it wrote with the 1-hour lifetime (1-hour writes cost 2x base input, 5-minute writes 1.25x, reads 0.1x: {{prompt caching prices|https://platform.claude.com/docs/en/about-claude/pricing}}). With CLAUDE_CODE_PROMPT_CACHE_TTL=5m (documented on the env-vars page) the same task cost , cheaper per write, and the run still hit the cache on every call after the first. Setting DISABLE_PROMPT_CACHING=1, a variable the current env-vars page does not list, did not disable caching on this version: the run still read of its input from cache, with 5-minute writes. Read the trace before trusting a switch.

The harder task: add a CLI

Sonnet wrote textstats/__main__.py and tests/test_cli.py in calls. Its verification tells the most: python -m pytest failed (no python on this machine, then no pytest), a subshell wrapper was refused by the permission layer, and it fell back to the plain runner. The new test file has no runner of its own, so it imported the file and called both test functions in one shell command, which printed "cli ok"; calling them again after the run confirmed it. It left the two planted bugs alone and said so, which is correct: the task did not ask.

Context lab 1: what is in the window before the model reads a single file

The context window is everything the model reads on one call, measured in tokens (pieces of words, about four characters of English each). On the first call it holds only what the harness put there: system prompt, tool definitions, environment, memory files, and your prompt. The stream does not show that text, but it shows its size, so six one-call runs ("Reply with the single word OK.") with different tool sets measure what each piece costs.

Context lab 2: the same session with and without prompt caching

Prompt caching lets the API keep the processed form of a prompt prefix for a while; a later request that starts with the same bytes reads it back at a tenth of the input price instead of paying for it again. An agent is the ideal customer: each call resends the whole conversation, which differs from the previous call only by what was appended at the end. Context lab 3: a budget model, checked against the recordings

A harness designer needs a back-of-the-envelope model: how big does the context get, when does it fill, and what does a session cost? The simplest one has four numbers: the startup context S, the growth per call g (the model's last output plus the tool result appended), the output per call o, and the number of calls N.

contexti = S + (i − 1) g     input processed = Σi=1..N contexti = N S + g N(N−1)/2
with caching
call 1 writes S (minus any prefix another session already cached); call i reads contexti−1 from cache and writes only g
without
every call pays contexti at the base input price

The quadratic term is why long sessions get expensive without caching: input processed grows with the square of the number of calls. Caching turns most of it into reads at a tenth of the price.

Context lab 4: compaction, before and after on the same history

When the conversation approaches the window, something must leave. Claude Code's documented answer (How Claude Code works, context window explorer): it first clears older tool outputs, then compacts, replacing the conversation with a structured summary (your requests, key concepts, files examined or modified with important snippets, errors and fixes, pending tasks, current work). The startup content reloads, up to five of the most recently modified files are re-read (a file over 5,000 tokens comes back only as a path), and the bodies of invoked skills are re-injected (capped at 5,000 tokens each). By default it compacts when the conversation reaches the model's context limit, and at about 967K tokens for models with a native 1M window such as Sonnet 5.5 (model configuration).

None of the recorded sessions came near a 200K or 1M window, so nothing compacted in them. What compaction costs

Compaction is a lossy model call: a summary of the conversation, written by the model, replaces the conversation. Exact tool outputs, failed attempts and early instructions can be lost, which is why the docs advise putting rules that must survive in CLAUDE.md (reloaded from disk) rather than in the chat. It also breaks the prompt cache: the new, shorter history is a different prefix, so the next call writes it again.

Interview questions

Why does an agent session's cost grow faster than linearly in the number of steps, and what fixes it?
Each step resends the whole conversation, so input processed is N S + g N(N−1)/2: quadratic in N. Prompt caching makes the repeated prefix cost 0.1x; fewer, larger steps (batching tool calls) cut N; truncating tool outputs cuts g; compaction resets the history when it gets too long.
What can and cannot you learn from a Claude Code stream-json trace?
You get the configuration (tools, model, permission mode), every tool call and result, per-call token usage including cache reads and writes, stop reasons, denials, timing and cost equivalents. You do not get the system prompt text, tool schemas or thinking text; for those you rely on documentation or a harness you control.
A tool returns a 500 KB file. What should a harness do?
Never paste it whole into the context. Claude Code's Read tool refuses files over 256 KB with an error that tells the model to use offset and limit or search, and the shell output is cut at 30,000 characters by default. The model then greps for what it needs. In your own harness: cap tool outputs, say they were cut and how to page, and offer search tools.
When does a subagent help?
When a subtask would fill the main context with material the main thread does not need afterwards (wide searches, long logs): the subagent reads it in its own window and returns a summary. It costs an extra startup context and its own calls, and on a small task it only adds cost, as the recorded run shows.
How would you check that a harness setting does what its name says?
Run the same task with and without it and read the usage fields. Here, an undocumented "disable caching" variable left caching on; the documented TTL variable changed the write lifetime exactly as described.
