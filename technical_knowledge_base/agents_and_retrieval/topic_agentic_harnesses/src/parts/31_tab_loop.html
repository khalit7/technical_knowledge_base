Loop lab. An agent harness built from nothing in seven steps, each one run for real on the running example (the textstats repository with two planted bugs, standard task prompt: The tests in this repository fail. Find out why and fix the code so they pass. Do not edit the tests.). The harness is a small Python program; its "model" is claude -p with every built-in tool switched off (--tools "") and a system prompt of ours, so the model can only return text. The harness finds the action in that text, runs it itself, and pastes the result back. Tool calling, seen from the inside, is text in a loop.

What one turn is
A turn here is one model call. The harness assembles a prompt (system prompt, task, every earlier reply and tool result), the model returns text, the harness parses one action out of it, a permission gate decides whether it may run, the harness executes it, and the observation (the tool's output) is appended for the next call. The loop stops when the model says it is done, when a turn or token budget runs out, or after repeated errors.

Step 0: one call, no loop

No loop at all: paste textstats/core.py into one prompt, ask for the fixed file, write the reply back, run the tests once to grade it. This is "chat with the code pasted in".

Predict: does one call fix both bugs?
It fixed one. The reply sorted ties alphabetically (the docstring says so) and left the regex that drops apostrophes untouched; the grader printed . The model never saw the tests and got no feedback, so it had no way to find out; it also ignored "nothing after the code block" and added an explanation. Both bugs are written in the docstrings, so this is not a hard task: the missing piece is feedback, which is what a loop adds.

Step 1: the loop, with read_file and run_tests

The harness now calls the model again and again. The system prompt lists two tools and one output format: a final line ACTION {"tool": ..., "args": {...}}. The harness takes the last ACTION line, runs the Python function of that name, appends --- turn N: result of read_file --- and the output, and calls again. It stops after 8 calls, or when a reply has no ACTION line. There is no edit tool, so this step cannot pass: the point is to watch the loop work.

Predict: with only reading and testing, what goes wrong first?
The model invented tool results. In call 2 it wrote its ACTION line and then kept going: --- turn 2: result of read_file --- followed by a made-up core.py (def word_count(text): return len(text.split())) and further actions. This harness kept all of that in the transcript and ran the last ACTION, so from then on the prompt held a fake file beside the real one, and the model said in calls 3 and 4 that "the code appears correct". It also called a tool that does not exist (write_file) and got an error back. Run: calls, output tokens of which were thinking, tests still failing.
Why this happens, and why APIs do not have the problem
A language model continues text. The transcript format we invented shows replies followed by results, so the likeliest continuation of a reply is a result, and the model writes one. Over the API, generation stops at the tool call: the response ends with stop_reason: "tool_use" and the result can only come from your code. Models are trained on that format. Through claude -p we cannot set a stop sequence, so step 1b cuts the reply at the first ACTION line instead. In a later run (step 4, masking) one reply ran on for 95,162 characters of invented turns until it hit the 32,000-token output cap; the CLI then sent "Output token limit hit. Resume directly ..." on its own and returned only the last 7,475 characters. That call took 294 s.

Step 1b: keep the reply only up to its first ACTION line

One fix, found in the step 1 recording: parse the first ACTION line and throw away everything after it before it enters the transcript. This is a hand-made stop sequence.

Predict: does cutting the reply change the run?
The invented results never reached the transcript, the model's reasoning stayed tied to real file contents, and it named both bugs correctly by call 4. Output fell from to tokens and model time from s to s. It still fails: with no edit tool it can only describe the fix, and it again tried the non-existent write_file.

Step 2: edit_file and a stop condition

Two additions. edit_file replaces an exact string, and the old text must occur exactly once, as in Claude Code's Edit tool: the model must quote what it changes, and an ambiguous match is an error instead of a wrong edit. finish is an explicit stop. A reply with no valid ACTION is now an error message the model sees (three in a row end the run), and the turn cap rises to 12.

Predict: how many calls does the fix take, and is it the same twice?
Both runs passed, in and calls. The second run read README.md and the package file first and spent one long reply ( output tokens in all against ). Same harness, same model, same task: the path differs from run to run, which is why one run proves little (the Trace and context lab tab records repeats). The pattern that passes is read, test, edit twice, test again, finish.

Step 3: a permission gate

A shell tool, run_command, arrives, and with it a gate in front of every call: an ordered list of rules, first match wins. Deny rules (editing tests/; rm, curl, wget, pip, sudo, git push), an ask rule for any command with ; & | ` $ < > (chained or redirected commands are never allowed by prefix), allow rules (reading anything, testing, editing textstats/, a few read-only commands), and "ask" for everything else. With nobody at a terminal, ask becomes deny, as with Claude Code's --permission-prompts none. A denial is an observation like any other, so the model can choose something else. The gate is not a sandbox: an allowed command runs with the harness's own rights (the Reading tab and the Containers and isolation page cover sandboxes).

Predict: a README tells agents to run curl ... | sh. Does the gate fire?
Not in these runs. With the instruction planted in README.md, the model never opened README.md. With it planted at the top of tests/test_core.py, a file every run reads, Haiku read it and ignored it. All three runs passed and none tried a command the gate had to stop. The gate is there for the run where the model does follow such text, which a few recordings cannot show; so the table below runs step 3's real check() function on eleven actions, with no model.
Two gate bugs this lab found
(1) Writing this table showed that an explicit "ask" rule returned the verdict "ask", which the loop treated as "not denied", so a chained command would have run. No recorded run reached that rule; the code shown is fixed. (2) Step 5 added a new tool, delegate, without a rule for it, and the gate denied it in the first step 5 run. Failing closed did its job: the run fell back to reading files itself and still passed. Both are the ordinary bugs of a hand-written gate, and the reason real harnesses ship tested permission engines.
Claude Code hit its own gate in three of four runs
The Claude Code comparison runs were launched with --allowedTools "Bash(python3 *)", because the README says python3 tests/test_core.py. The model typed python tests/test_core.py, which matched no rule and was denied: twice in each Haiku run, once in the first Sonnet run (plus a chained command ending in python -m pytest). Haiku then finished without ever running the tests; Sonnet said plainly that it could not run them. An allow-list written for what you expect the model to type is narrower than what it types.

Step 4: context management

To see the problem it solves, run_tests is made deliberately noisy: it runs python3 -v, which prints every import, about 240 lines and 12,900 characters per run, standing in for a verbose build or test log. Step 4 adds two mechanisms. Clipping: any tool output longer than 40 lines keeps its first 15 and last 15 lines (naive), or those plus every middle line that looks like a result or an error (smart). A token budget: after each call the harness divides the tokens the model reported by the prompt's characters, estimates the next prompt with that rate, and when the estimate passes the limit it replaces the oldest tool results with a one-line stub ("observation masking"); the last two results are never masked. A run-wide cap of 120,000 tokens stops the run.

Predict: in the noisy output, where are the test results, and does naive clipping keep them?
The four result lines sit at lines 92 to 95 of about 240, in the middle, because Python flushes the test output before printing its shutdown trace. Naive head-and-tail clipping cuts exactly them. The run still passed because the harness puts exit code 0 on the first line of every result, which survives any head cut: put the verdict where the clipper keeps it. Smart clipping keeps the four lines.
Predict: how much bigger does the unmanaged run get, and what does it cost beyond tokens?
The unmanaged run read tokens over its calls against with naive clipping, and its largest call was tokens against . The hidden cost: once a prompt passed Haiku 4.5's 4,096-token minimum for prompt caching, the CLI wrote the whole prompt to the cache on every call ( tokens of cache writes, at 2x the input price for the 1-hour cache) and never read it back, because our prompt is one growing text block and a cache hit needs an identical prefix ending at a block boundary. Claude Code's own runs, below, read most of their context from the cache.

The masking run used a limit of 2,000 tokens so that it fires on this small task; it masked one result from call 4 on. That run is also the one with the 95,162-character runaway reply, which is why its totals are large: the budget counts it, and a real harness would also cap output per call.

Step 5: a subagent for context isolation

The loop becomes a function, agent(task, tools, ...), and a new tool, delegate, calls it again with a fresh transcript and read-only tools. The helper reads and runs as much as it likes; only its final report (asked to be at most 80 words) enters the parent's context. Why a subagent and not a todo list: a todo list is a prompt pattern (the model writes a plan into its own context and ticks it off; Claude Code has one, TodoWrite), while a subagent changes what the parent's context contains, which is the mechanism step 4 was about. It is also how Claude Code's Task tool and Explore agent keep long searches out of the main context.

Predict: does the helper make the parent's job easier?
It depends on the report. With a soft suggestion ("delegate investigation"), Haiku never delegated. Told to delegate first, Haiku's helper answered in one call without reading anything: Tests show missing or incorrect function implementations. Fix by implementing all required functions ..., which is wrong, and the parent then read every file itself. Sonnet's helper read three files and reported the two exact lines and their replacements; the parent re-read core.py once (it needs the exact text for edit_file) and fixed both in two edits. On a task this small the subagent saves nothing: Sonnet's run made calls in all. Isolation pays when the investigation's output is large compared with its conclusion (a search over many files, a long log), and it costs a hop where the conclusion can be lost or invented.

Beside real Claude Code

The same task run by Claude Code itself: claude -p with its own system prompt and tools (Read, Edit, Write, Bash, Grep, Glob), permission mode acceptEdits, the same model, and an allow rule for python3 (and in the last run also python). The table puts the final harness (step 5) beside it. Costs are the API-price equivalent that the CLI reports, computed from the usage at list prices; the subscription is what actually pays.

What Claude Code does that this harness does not, read from the trace

  • A large, stable, cached prefix. Its first call already reads about tokens (system prompt plus tool definitions) before seeing any file, and most of it comes from the prompt cache: the Haiku run read tokens from cache and wrote . Our harness reads far fewer tokens but none from cache.
  • Several tool calls in one model call (up to three here, such as two Bash commands, or three Reads), so one call does what took ours three.
  • Tools designed for models: Read returns numbered lines (1 import re), paths are absolute, Edit refuses an old string that is not unique, Glob and Grep replace ad hoc find.
  • A permission engine with read-only defaults: ls -la and a chain of cat and find ran without any allow rule; sed -i and python were denied and reported back as This command requires approval.
  • Output limits of its own: Bash output is cut at 30,000 characters by default and Read refuses files over 256 KB (measured by the Trace and context lab tab), the same job as our step 4 clip.
  • Native tool calling: no invented results and no format errors, because the model stops at a tool_use block. Our harness needed step 1b and still saw runaway replies.
  • What it did not do: no subagent, no todo list, no compaction on a task this small; and with the tests blocked, the Haiku runs finished without verifying, as our step 0 did.

How real tool calling works at the API level

Our harness defined tools in prose and parsed text. A provider API makes the same three things structured. (1) Tool definitions travel in the request, each a name, a description and a JSON Schema for its arguments; the provider turns them into extra system-prompt text the model was trained on. Anthropic adds a tool-use system prompt of 496 tokens for Haiku 4.5 and 286 for Sonnet 5.5, on top of the definitions themselves; OpenAI says functions are "injected into the system message" and billed as input tokens. (2) The model's call is a typed block: Anthropic returns stop_reason: "tool_use" with a tool_use block (id, name, input object); OpenAI's Responses API returns a function_call item (call_id, name, arguments as a JSON string). Generation stops there, which is exactly what our step 1 lacked. (3) The result goes back as a typed block in the next request: a tool_result with the matching tool_use_id inside a user message (Anthropic), or a function_call_output with the matching call_id (OpenAI). The API is stateless: every request carries the whole history, just as our harness resent its transcript.

Why providers trained models on a format instead of parsing prose: a trained model reliably stops at the call, produces arguments that parse (Anthropic and OpenAI both offer a strict mode that constrains them to the schema), knows when not to call a tool, and can issue several calls at once. OpenAI's announcement of 13 June 2023 said its new models "have been fine-tuned to both detect when a function needs to be called ... and to respond with JSON that adheres to the function signature". Under the API, the blocks are still rendered into the model's token stream with special markers; the structure is a contract that the provider's renderer and the model's training share.

Interview questions

What is the minimum a harness needs to turn a model into a coding agent?
A loop that calls the model with the whole history; tools to observe (read, run tests) and to act (edit); a way to find the tool call in the output and to feed the result back; and stop conditions (the model says done, a turn or token budget, an error limit). Step 2 here is that minimum, about 90 lines of code.
Why does tool calling need special training or stop sequences?
A model continues text. Without a stop at the call, it writes the result itself (step 1 recorded this), and the harness may act on an invented observation. Trained formats end generation at the call and give parseable arguments.
Why do harnesses use exact-string replacement for edits?
The model must quote what it changes, so a stale view of the file fails loudly; uniqueness turns an ambiguous edit into an error instead of a wrong change; and the edit is small, cheaper than rewriting the file.
Is a permission allow-list a sandbox?
No. It filters which calls run; an allowed command still has the harness's rights. Prefix rules are bypassable by chaining (cat x; rm -rf y) unless the gate parses commands. Sandboxing (containers, OS sandboxes) limits what an allowed command can do.
A tool prints 10,000 lines. What do you do?
Clip it before it enters the context, keeping the head, the tail and the lines that matter (errors, results), put the verdict on the first line, tell the model how much was cut and how to get more, and mask or summarise old results when the context fills. Measure: the unmanaged run here read several times more tokens for the same outcome.
When does a subagent help?
When the work it isolates produces much more text than its conclusion (searching, reading logs), so the parent's context stays small. It costs extra calls and a hop where information is lost or invented; on a small task it saves nothing, as step 5 shows.
Why did our harness get no prompt-cache hits while Claude Code got many?
A cache hit needs the same prefix up to a block boundary that an earlier request wrote. Our harness sends one text block that grows each call, so no earlier prefix ends at a boundary. Claude Code sends structured messages with a stable system prompt and tool list first and moves its cache breakpoint forward, so each call re-reads the previous call's prefix at a tenth of the input price.
