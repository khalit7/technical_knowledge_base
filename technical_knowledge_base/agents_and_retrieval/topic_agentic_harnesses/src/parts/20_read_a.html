1. From chat to agent: a model call, then tools, then the loop

A model call. A language model is a function from text to text. The text goes in as tokens (word pieces, about four characters of English each), and the model generates new tokens one at a time until it decides to stop. It keeps no memory between calls: to "continue a conversation", the caller sends the whole conversation again every time. The maximum it can read in one call is its context window (200,000 tokens for Claude Haiku 4.5, as the CLI's own result record reports MEASURED).

Step 0, no loop. The simplest possible "agent" pastes the source file into one prompt and writes back whatever comes out. Run on the example, Haiku 4.5 read 635 input tokens, answered in 7.9 seconds, and fixed top_words; it never saw the tests, so it never learned that apostrophes were supposed to survive, and one test still failed MEASURED. Nothing was wrong with the model. It was missing information that only running the code could give it.

Tools. A tool is a function the harness offers the model, described by a name, a sentence of description and a JSON schema for its arguments, for example Bash {command} or Read {file_path}. The descriptions are sent with every request. Instead of answering in prose, the model can reply with a structured tool call: on the Anthropic API a tool_use block with the tool's name and arguments and stop_reason: "tool_use"; on OpenAI's, a function_call item. The harness runs the function and sends the output back as a tool result in the next request (both protocols are in {{the Loop lab's API section|#t-loop}}). Models do this reliably because they are trained to: OpenAI announced on 13 June 2023 (archived post) that its 0613 models "have been fine-tuned" to detect when a function should be called and to answer with JSON matching its signature, and Toolformer (Schick et al., February 2023) had shown a model teaching itself API calls from a few demonstrations SOURCE.

The loop. Put the call in a loop and you have an agent:

messages = [system prompt, task]
while True:
  reply = model(messages, tools)
  if reply has no tool call: break   # the model says it is done
  result = run(reply.tool_call)   # after a permission check
  messages += [reply, result]

That is the whole core. The pattern is older than tool-calling APIs: ReAct (Yao et al., October 2022) interleaved free-text thoughts with actions and observations in one prompted loop, and beat reasoning-only and acting-only baselines; every modern agent loop descends from it ({{ReAct paper page|n:3c65c17b0d0d816b9a24c28de8f08ea8}}). What makes a harness good is everything around those six lines: which tools, what the model sees, when it stops, what it may touch.

Same task, same model: one call against the loop

Real recordings, Claude Haiku 4.5 (claude-haiku-4-5-20251001) both times. Loop: Claude Code 2.1.289, claude -p, tools Read, Edit, Write, Bash, Grep, Glob, permission mode acceptEdits (trace std_haiku_1). One call: the Loop lab's step 0 (s0_haiku). The window bar shows each call's input: the part read from the prompt cache, the part newly written to it, and fresh input. Tool results are cut to a few lines here; the full trace is in the {{Trace and context lab|#t-trace}}.

Predict, then reveal. In the loop run, call 7 typed python tests/test_core.py and got command not found: python. What did the harness do with that error, and what should it do?
It did nothing special: the error went back to the model as an ordinary tool result marked is_error, and on call 8 the model typed python3. That is the right design. A harness that crashes, retries silently or hides errors takes away the one signal the model needs to correct itself; making failure visible and specific is part of tool design (section 2).

Reading the replay: the loop spent six calls finding its way around (listing files, reading the tests and the code) before running anything, recovered from one error, fixed both bugs in two edits, ran the tests again and stopped with a summary. Twelve model calls, 31 seconds, about $0.039 at list prices MEASURED. The first call already read 13,242 tokens before the model had seen a single file: that is the system prompt and the six tool definitions, the fixed cost of this harness, mostly served from the prompt cache (section 3).

Go deeper: the {{Loop lab|#t-loop}} builds this loop from zero in seven recorded steps (and shows a model inventing its own tool results when the harness forgets to stop it at the tool call); the {{Trace and context lab|#t-trace}} has a viewer for every recorded Claude Code session. Past the action boundary a model writes the other side's turn: Haiku wrote fake tool results here, and on {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}} a local model let past its end-of-turn token wrote a fake user turn with tool calls inside, in 5 of 18 samples (its Tool call, token by token tab replays one).
