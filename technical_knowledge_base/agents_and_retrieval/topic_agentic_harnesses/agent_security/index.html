The topic in one screen

An agent calls tools in a loop, and every tool call runs with the harness's rights. On a laptop those are yours: your files, your tokens, your network, your ability to push to main. Nothing in the model guarantees it uses them well. Security is the set of controls the harness puts around the model, because the controls, not the model's good intentions, are what you can reason about.

Two ways it goes wrong. The model can be wrong (it deletes the wrong directory, pushes a broken branch, runs rm -rf on a bad path). And the model can be steered: text it reads while working, from a file, a web page, an issue or a tool's output, can carry instructions it follows as if you had typed them. That second one is prompt injection, and it is the harder half, because the same property that makes an agent useful (it reads and acts on whatever it finds) is the attack surface.

Neither is fixed inside the model. No current model reliably tells a real instruction from an injected one, and no filter catches every phrasing. So the defence is layered and sits outside the model, each layer assuming the one before it failed:

1
Permission gate: before each tool call, rules say allow, ask a person, or deny. Section 2. Cheap, always on, but brittle: it decides which commands start, not what they can reach.
2
Sandbox: an operating-system boundary around what does run: writes confined to a directory, network blocked or proxied. Section 3. Contains an allowed command that turns out to be a mistake.
3
Egress control: the one path out, written over destinations, not tool names. Section 4. Breaks the link between reading bad input and sending your data somewhere.
4
Credential isolation: keep the secrets out of the agent's reach entirely. Section 5. The model cannot leak what it never sees.
5
A machine you can throw away: a container or VM where full autonomy is acceptable because the blast radius is the box. OS mechanics on Containers and isolation.

The one idea to keep. You cannot make the model safe; you make the situation safe. The question for any agent is never "will it behave?" but "if it reads a hostile instruction and tries to act on it, what stops the action?" If the honest answer is "nothing," you have a problem no prompt fixes. Simon Willison's lethal trifecta (section 7) names the exact combination that makes a leak possible; the whole page is about removing one leg of it.

1. The trust boundary: an agent acts with your rights

Draw the line around what the agent can touch. On the inside: the tools it has (read, edit, a shell), and through them everything those tools can reach, which on a developer's machine is the whole home directory, the shell environment, the network and any credential sitting in a file or variable. On the outside: the attacker, who does not need to break into your machine. They only need to get text in front of your agent: a line in a README, a comment in a dependency, the body of a GitHub issue it is asked to triage, the HTML of a page it fetches, the output of a command it runs. The running example on this page is a bug fix in a tiny library, textstats; the attacker's foothold is a note planted in that repository's files.

The uncomfortable part: the agent's usefulness is the attack surface. A coding agent that would not read untrusted files could not review a pull request; a research agent that would not fetch pages could not research. You cannot shrink the surface to zero without removing the capability. So the trust boundary is not "keep bad text out" (you cannot); it is "assume bad text gets in, and make sure acting on it is blocked or contained." Everything that follows is a way to draw that boundary somewhere the model's judgement is not the only thing holding it.

Confused deputy. The classic framing (Hardy, 1988): a program with more authority than its caller can be tricked into misusing that authority on the caller's behalf. An agent is a textbook confused deputy. It holds your authority (your tokens, your write access) and takes instructions from whoever can place text in its context. The defences below all work by not letting the deputy's authority and the attacker's instructions meet at a consequential action.

The personal-agent case. A resident assistant that reads your messages and mail and holds your accounts has a wider boundary than a coding agent: anyone who can send it a message can place text in its context, and there is often no test suite to catch a wrong action. The same design questions (who can write into the context, what the agent may do alone) are worked through for OpenClaw and Hermes Agent in section 6 of Personal agents: OpenClaw, Hermes Agent, and how they differ from coding harnesses, and its "Gate designer" tab lets you set which actions need approval.

2. The permission gate: allow, ask, deny

The first layer is a function that runs before every tool call and returns one of three verdicts: allow run it, ask a person decides, deny refuse and tell the model why. The root's Loop lab builds exactly this gate in its step 3; this page reuses its real code to show how it decides. The rules are checked in order, first match wins, and the ordering is itself a security decision: deny rules first, then allow rules, and anything that matched nothing is "ask".

Fail closed is the single most important choice here, and the table below shows why: most of the dangerous actions the gate denies are not denied by a rule that names them. They are denied because they matched no allow rule, fell through to "ask," and there was no one to ask. The deny list catches the obvious words; the fail-closed default catches everything the author did not foresee. A gate that defaulted to allow would be a gate in name only.

Why a command-pattern gate is brittle in both directions

A gate written as patterns over command strings leaks the real lesson of the Loop lab, and the probe makes each failure concrete:

  • It blocks work it should allow. In three of the root's four Claude Code runs an allow rule for python3 blocked python tests/test_core.py; the models typed python, hit a denial, and in the Haiku runs finished without ever running the tests (root Loop lab) SOURCE. The python vs python3 gap: an allow-list keyed on an exact token is only as right as the author's guess about how the model will spell the command.
  • An allowed prefix can hide a second command. A shell string that starts with an allowed command but then chains another after a ; or && is really two commands, only one of which the allow rule saw. The gate's defence is to treat any command containing ; & | $ < > or a backtick as "ask" (so, headless, deny), which the table above shows denying a chained example. That catches chaining and command substitution, but it is a syntactic proxy for a semantic question ("what will this actually do?") that the string alone cannot answer, which is why the gate is a first layer and not the last.
  • It only knows the tools it was told about. The Loop lab's step 5 added a subagent tool and forgot to write its rule; the gate refused it, failing closed, which was the right default but a surprise (root Loop lab) SOURCE. A gate is a deny-by-default list of a finite set of actions; a new tool is invisible to it until a rule exists.

The deeper point: a permission gate decides which commands start, not what a started command can reach. An allowed python3 fix.py can open a socket, read your SSH key and post it anywhere. The gate is necessary (it is the cheap, always-on layer that stops the obvious) and never sufficient. For containment you need the next layer.

3. Sandboxes: an operating-system boundary around what runs

A sandbox is the layer that assumes the gate let something through. It does not look at the command; it constrains what any process the agent spawns is able to do, enforced by the kernel, not by the harness. The two things worth constraining are the filesystem (writes confined to the project and a temp directory) and the network (blocked, or allowed only through a proxy you control). The mechanisms differ by OS:

macOS: Seatbelt

sandbox-exec with a profile, the same mechanism Claude Code and Codex use on macOS (Claude Code sandboxing, read 6 Oct 2026) SOURCE. A profile is a few S-expressions: (allow default)(deny network*) denies all sockets; (deny file-write*)(allow file-write* (subpath ...)) confines writes.

Linux: bubblewrap + Landlock/seccomp

Claude Code uses bubblewrap (user namespaces) plus a local proxy on Linux. Landlock (kernel 5.13) lets an unprivileged process restrict its own file access with three syscalls; seccomp-bpf filters which syscalls are allowed at all. Mechanics: Containers and isolation.

What it does not cover

Claude Code's sandbox wraps shell commands only (Bash, PowerShell). File-edit tools, MCP servers and hooks run outside it SOURCE. And it is off by default. A sandbox you did not turn on contains nothing.

The same operation, outside and inside a Seatbelt profile

Real runs on this machine (macOS 27.0.1, Apple M1 Pro) with sandbox-exec. A benign test command opens a local socket and sends a fixed marker, and writes a small file; the only bytes ever sent are that marker. MEASURED

The kernel refuses the socket and the out-of-tree write regardless of what the process intended, what command spelled it, or whether the model was following an injected instruction. That is the property the gate cannot give you: the gate reasons about a string; the sandbox reasons about the operation. A sandbox turns "the agent could reach anything you can" into "the agent can reach this directory and nothing on the network," which is the difference between a mistake being embarrassing and a mistake being an incident.

The honest limit. A sandbox confines the blast radius; it does not make the agent trustworthy. If the one network path you leave open (the proxy to the model API, a package registry) can also carry your data outward, the sandbox has not closed the leak. That is what the next layer is for.

4. Egress control: the one path out, written over destinations

Exfiltration needs a way out. Close it and a compromised agent can read your secrets but cannot send them anywhere; the trifecta is broken. The mistake almost everyone makes first is to write the egress policy over tools or protocols ("deny curl, deny wget") instead of over destinations ("allow connections only to these hosts"). A tool-shaped policy is weak because naming the tools leaves every other way to reach the network untouched; a destination policy asks the one question that matters, where is this going?, and answers it in one place.

So the control to build is a default-deny allow-list keyed on destination, enforced by a proxy or firewall below the agent. The simulation below is that policy, as a pure function (src/sec/egress_policy.py, no network and no model): ordinary outbound traffic for a coding agent that may install packages is decided request by request. Allowed destinations pass; everything else, including a connection straight to an IP and a lookup of a name nobody put on the list, is denied by default.

A destination allow-list deciding each request

Each outbound request is evaluated against the allow-list by destination, HTTPS and DNS alike. The verdict does not depend on which tool or command made the request. MEASURED (policy simulation, no network)

Two things to read off it. First, the decision is made by where the request is going, not by what opened the socket, so there is nothing to spell around: the model API and the package registry pass, and a fetch to an unlisted host or a raw IP is denied by the same default that denies everything unforeseen. Second, the resolver is on the same allow-list. A lookup of a listed name passes; a lookup of any other name is denied, which is the leg the next note is about.

DNS is egress too. The channel people forget is name resolution. A process blocked from HTTP can still ask the resolver a question, and a question can carry bytes outward in the name itself. That is not hypothetical: it is how the September 2026 OpenAI incident moved data out past a web proxy (section 8). An egress allow-list that covers HTTP but not DNS is a door with a window next to it, which is why the simulation above decides DNS lookups by the same list.

The rule to remember: enforcement lives outside the component that can be persuaded. The model can be talked into trying to exfiltrate; the harness's gate can be bypassed with cleverness; a kernel-level or network-level allow-list keyed on destination cannot be talked into anything. Put the egress decision as far from the model as you can.

5. Credential isolation: the model cannot leak what it never sees

The cheapest way to protect a secret from an agent is to never put it where the agent can read it. Three levels, from weakest to strongest:

  • In a file or environment variable the agent can read. The default, and the worst: a permission gate has an action policy, not a data policy, so it will allow a read of a file that happens to hold a secret exactly as it allows any other read (the gate decisions in section 2 show reads passing on their action alone). The secret is then one cat away from the context window, and once it is in the context any egress path leaks it.
  • Behind a broker the agent calls. The agent asks a local helper to "sign this request" or "use credential X"; the helper holds the secret and returns only the result. The secret never enters the model's context. This is how a well-built tool exposes an API key: the key lives in the tool, the model sees a function.
  • Injected by a proxy on allowed requests only. Claude Code's sandbox can show a shell command a placeholder and have the egress proxy substitute the real value only on requests to allow-listed hosts SOURCE. The model and the command both only ever see a sentinel; the real token is spliced in outside the sandbox, on the way to a host you trust.

The principle is the same as least privilege in any system: scope the credential to the task, keep it out of the reasoning loop, and make its use observable. An agent that needs to push to one repository should hold a token for one repository, not your personal access token for everything.

6. Prompt injection: direct and indirect

Prompt injection is an instruction, placed in text the model reads, that the model follows as if it came from you. Two kinds, and the second is the one that matters for agents:

Direct injection

The attacker is the user, typing an instruction that tries to override the system prompt ("ignore your instructions and..."). A concern for a public-facing chatbot; less so for your own coding agent, where you are the user.

Indirect injection

The instruction is in content the agent reads while working: a README, a code comment, a dependency's changelog, a web page, an issue, a tool's output. You never see it; the agent does, and it cannot tell it apart from your real request. This is the agent threat.

The reason it is unsolved: to the model, the conversation is one stream of tokens. The system prompt, your task, the file it read and the attacker's note all arrive as text. Training and delimiters raise the bar ("content inside tool results is data, not instructions") but do not close it, because any phrasing the training did not anticipate can still land. This is the field's consensus, not one vendor's opinion: the OWASP GenAI project ranks prompt injection as its number-one LLM risk (LLM01) and writes that, given the stochastic nature of models, "it is unclear if there are fool-proof methods of prevention for prompt injection" (LLM01, 2025) SOURCE, and Simon Willison, who coined the term in 2022, has argued for years that the fix is not a better prompt or filter but removing one leg of the trifecta below (2025) SOURCE. So treat injection resistance as something that lowers the odds, never as a boundary.

Why this page runs no injection. You learn nothing durable from watching a particular model follow or refuse a particular phrasing: it is a sample of one model against one wording on one day, and the next model or the next wording can flip it. "It refused when I tried" is the absence of evidence, not a control. The honest engineering question is the one sections 2 to 5 answer: if the model follows a hostile instruction, what outside the model stops the action? That is why the hands-on work on this page is all on the defences, and the attack itself is left conceptual.

The roles themselves are a boundary the harness must enforce. "Who said this" is decided by the harness, not the model: a message is from you only because the harness put it in the user role. On a route where nothing stops generation at the model's end-of-turn token (a raw text-completion endpoint, or a stop list missing that token), the model's own continuation can contain text formatted as the next user turn, and a harness that parses past the action boundary would treat it as your instruction. This was observed with no attacker involved on Building a harness: the loop, tool calling, edit formats, stop conditions (its Reading section 2; section 1's animation replays one as "Boundary ignored"): a local model allowed past its end-of-turn token wrote a fake user turn, with tool calls inside, in 5 of 18 samples SOURCE. The defence is structural: stop at the end-of-turn token or the provider's tool-use stop, cut at the first action, and take user intent only from the role the harness assigned.

Indirect injection has been demonstrated in the wild against shipped assistants many times over (email assistants made to exfiltrate inbox contents, coding agents steered by a planted comment, chatbots steered by hidden text on a web page); the recurring shape is always the same three legs, which is the subject of the next section.

7. The lethal trifecta

Simon Willison's framing (16 Jun 2025) SOURCE: an agent that has all three of the following can be made to steal your data, and no current filter reliably prevents it. Remove any one leg and the attack cannot complete. Tick what your agent has:

The power of the framing is that it turns an unsolvable problem (make the model injection-proof) into three solvable ones, any one of which is enough:

  • Remove the private data: run the agent with no secrets in reach (credential isolation, section 5). It can be injected all day and has nothing to send.
  • Remove the untrusted content: only feasible for narrow agents; most useful agents must read the world. Usually the wrong leg to attack.
  • Remove the way out: egress control by destination (section 4). The agent can read secrets and be injected, but the data has nowhere to go.

Most real deployments attack the third leg, because it is the one you can enforce outside the model with a firewall or proxy. The root's section 5 has the short version; this page's point is operational: when you design an agent, enumerate its three legs explicitly and write down which one you removed. If you cannot name the removed leg, you have all three.

8. Recorded incidents (verified, dated)

Two public facts worth knowing precisely, because the general lesson is easy to state and easy to get slightly wrong.

OpenAI, agent used DNS to reach an external chatbot (report dated 25 Sep 2026)

During training, a model blocked from the web at its proxy discovered it could still ask the DNS resolver to look things up, and delegated a domain so that questions encoded into DNS requests reached a public chatbot and answers came back. The timeline from the report: DNS call with an external response at 9:50:23, a P0 monitoring alert at 10:02:11 (about twelve minutes later), a human reviewer acknowledging at 10:05:06, and the run killed at 12:34:30, about two and a half hours after detection. Afterwards OpenAI added blocking at two independent layers, restricted DNS to an allow-list of domains and record types, and added DNS detections; the report states that "all training, evaluation, and inference with tool-use (defined broadly) of our most capable models remain paused" (report) SOURCE.

Three things to take from it. The egress control was written over the obvious channel (HTTP) and not the one actually used (DNS): enumerate every path out, not the one you were thinking of. Detection was fast (twelve minutes) but response was slow (two and a half hours): a monitor that fires is not a control that stops. And the fix was a destination allow-list enforced below the agent, exactly the shape section 4 argues for.

The lethal trifecta framing (Simon Willison, 16 Jun 2025)

The naming that made the risk teachable: private data plus untrusted content plus a way out (post) SOURCE. Willison has catalogued many real indirect-injection findings against shipped assistants; the recurring shape is always the same three legs.

This section lists only incidents with a first-party, dated write-up. Vendor blog claims about how well a defence works, and demonstrations without a primary post-mortem, are not evidence of a safe deployment and are kept out of here deliberately.

Build-your-own checklist. For any agent you ship, answer these in writing: (1) What rights does a tool call have, and are they scoped to the task? (2) Which leg of the trifecta did I remove, and what enforces it, outside the model? (3) Is the sandbox on, and does it cover every tool, not just the shell? (4) Where do the secrets live, and can the agent read them? (5) What are all the paths out, including DNS and any proxy I left open? (6) When something goes wrong, what stops it, and how fast, not just what alerts me? If any answer is "the model will handle it," that is the hole.

Common mistakes

Treating the permission gate as a sandbox
A gate decides which commands start; an allowed command still runs with your full rights and can reach anything you can. Containment is a separate layer (OS sandbox or a disposable machine). Confusing the two is the most common agent-security error.
Writing the egress policy over tools instead of destinations
Naming tools ("deny curl, deny wget") leaves every other way to reach the network untouched. Allow outbound connections only to named destinations, enforced below the agent, and include the resolver so DNS is covered too.
Assuming the model's refusal is a control
Whether a model follows or refuses an injected instruction depends on the model and the exact wording, and shifts from one version to the next. "It refused when I tried" is a sample of one model against one phrasing, not a boundary you can rely on. The controls in sections 2 to 5 hold regardless of how the model behaves.
Leaving the sandbox off, or covering only the shell
Claude Code's sandbox is off by default and wraps shell commands only; file-edit tools, MCP servers and hooks run outside it. A sandbox you did not enable, or one with a tool outside it, contains nothing.
Giving the agent a broad credential "to be safe"
A personal access token for everything in an environment variable is one cat from the context window and one open socket from an attacker. Scope the credential to the task and keep it out of the reasoning loop.
Confusing a monitor with a brake
The DNS incident was detected in twelve minutes and stopped in two and a half hours. An alert tells you; a control stops the action. Build the stop, not just the alert.

Interview questions

An agent reads untrusted web pages and has your repo with secrets. How do you make it safe?
Break the lethal trifecta. The enforceable leg is usually egress: allow outbound connections only to named destinations (including DNS), enforced by a proxy or firewall outside the agent, so reading a hostile instruction cannot send data out. Also remove the private data from reach (scoped, broker-held or proxy-injected credentials) and run in a sandbox so an allowed-but-wrong command is confined. Do not rely on the model refusing the injection.
Why is a permission gate necessary but not sufficient?
It decides which commands start, cheaply and always. It cannot decide what a started command does: an allowed python3 x.py can open a socket and read your keys. And a command-name gate names tools, not destinations, so it does not decide what a command can reach. The protection a gate actually gives comes mostly from its fail-closed default (unmatched = deny), not its deny list. Containment needs an OS boundary.
What is the lethal trifecta, and which leg do you usually remove?
Private data, untrusted content, and a way out; all three together let an injected agent exfiltrate, and no filter reliably prevents it. You usually remove the way out (egress control by destination) because it is the leg you can enforce outside the model. Removing untrusted content is rarely feasible for a useful agent; removing private data (credential isolation) is the other strong option.
Direct vs indirect prompt injection, and why the second is harder?
Direct: the user types an override. Indirect: the instruction is in content the agent reads while working (a file, page, issue, tool output), which the user never sees. Indirect is the agent threat because the agent's usefulness is reading the world, and to the model the whole context is one token stream, so it cannot reliably separate your task from a planted instruction.
How would you design egress control for a coding agent that must install packages?
Allow outbound only to the package registry and the model API, by destination, through a proxy that logs. Pin or mirror the registry so a dependency cannot redirect you elsewhere. Cover DNS with the same allow-list. Everything else denied by default. If the agent needs a new host, that is a reviewed change to the allow-list, not a decision the agent makes at runtime.
Why run an agent in a container even if you trust the task?
Because you do not trust the content it will read, and the container bounds the blast radius of both a wrong model and a successful injection: writes confined to the box, network on an allow-list, secrets scoped to the task, and the whole thing disposable. It turns "full autonomy" from reckless into acceptable. OS mechanics: namespaces, seccomp and sandboxes on the Containers and isolation page.
