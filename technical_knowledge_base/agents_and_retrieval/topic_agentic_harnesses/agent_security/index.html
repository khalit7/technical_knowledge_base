Agent security: permissions, sandboxes, prompt injection, egress

A child page of Topic: agentic-harnesses: how to keep an agent that runs tools with your rights from doing damage, whether the model is simply wrong or is steered by text it reads. Defensive throughout: attack classes are explained from published sources, and the hands-on evidence is controls doing their job on benign actions. Reading: 31 min, plus 6 in closed details. Data as of October 2026.
The idea in one sentenceAn agent acts with your rights on text that anyone can write, and no model reliably tells your instructions from planted ones, so agent security is the set of controls outside the model that make acting on a hostile instruction blocked, contained or harmless: name the leg of the lethal trifecta (private data, untrusted content, a way out) you removed, and enforce it where the model cannot argue.

Fig. 1 builds one coding agent's trust boundary in seven steps: red marks the trifecta's legs, and the controls outside the model appear one by one with their section numbers.

  1. Your task, your rights. The harness puts your task in the context and calls the model; every tool call it runs has your rights: project files, secrets, network.
  2. Untrusted text gets in by design. A README, an issue, a web page, a tool's output, a third-party tool's definition land in the same context as your task, one token stream (sections 2 and 3): the untrusted content leg.
  3. Tool calls reach everything. With nothing in between, a call can read files and secrets (private data) and send to any host (a way out): all three legs, so an injected instruction could complete a leak.
  4. The gate decides what may start (sections 4 and 5). Before every tool call: allow, ask a person, or deny and tell the model why.
  5. The sandbox bounds what it can reach (section 6). A kernel boundary round everything the agent starts: writes only in the project, no network of its own.
  6. Egress is decided by destination (section 7). The one path out is a proxy below the agent: the model API and the registry pass, anything else stops. The way out is closed.
  7. Secrets stay outside; detection watches (sections 8 and 9). The real token moves to a broker outside the sandbox; the agent gets results, never the secret, so the private-data leg goes too. A monitor watches every layer; it alerts and stops nothing.

Together the controls decide what those calls can start, reach, send and hold. Red-teaming (section 10) tests each of them like a unit test.

1. The threat model: a confused deputy with three legs

Every tool call runs with the harness's rights. On a laptop those are yours: your home directory, your tokens, your network, your ability to push to main. The running example on this page is a bug fix in a tiny library, textstats (the root's Loop lab task), and the attacker never touches your machine: they only need to get text in front of the agent, a line in a README, a comment in a dependency, an issue it triages, a page it fetches, a tool's output. Two things go wrong: the model can be wrong (it deletes the wrong directory), or it can be steered by that text. The agent is a textbook confused deputy (Hardy, 1988): it holds your authority and takes instructions from whoever can place text in its context.

The uncomfortable part is that the agent's usefulness is the attack surface: a coding agent that would not read untrusted files could not review a pull request. So the boundary is not "keep bad text out" (you cannot) but "assume it gets in, and make acting on it blocked or contained". The question for any agent is never "will it behave?" but "if it follows a hostile instruction, what outside the model stops the action?"

Simon Willison's lethal trifecta (16 Jun 2025) SOURCE names the combination that turns injection into theft: access to private data, exposure to untrusted content and a way to communicate externally. With all three, an injected agent can be made to send your data out, and no current filter reliably prevents it. Remove any one leg and the leak cannot complete. That turns one unsolvable problem (make the model injection-proof) into three solvable ones. Predict before you toggle: in the hard case below the agent must read untrusted content, so which controls actually break the chain?

The rule that follows: when you design an agent, write down which leg you removed and what enforces it. If you cannot name the removed leg, you have all three. A resident personal assistant that reads your mail and holds your accounts has a wider boundary than a coding agent (anyone who can message it can write into its context); that case is worked through in section 6 of Personal agents, whose gate designer sets which actions need approval.

Which leg each control removes: the gate alone never breaks the chain

A design tool with no model and no attack: a coding agent that reads content you do not control (so the untrusted-content leg is always present) on a machine that holds something worth stealing. The permission gate hardens every layer but removes no leg on its own; the sandbox and the egress allow-list close the way out (the sandbox only if it is on and covers the tool); credential isolation removes the private data. Most real deployments remove the way out, because it is the leg you can enforce below the agent with a proxy or firewall. Removing untrusted content is feasible only for narrow agents.

2. Prompt injection: direct and indirect

Direct injection: the user is the attacker, typing an override ("ignore your instructions and..."); a concern for a public chatbot, less so for your own coding agent, where you are the user. Indirect injection: the instruction sits in content the agent reads while working (a README, a code comment, a dependency's changelog, a web page, an issue, a tool's output). You never see it; the agent does. That is the agent threat.

Why it is unsolved: any phrasing the training did not anticipate can still land. This is the field's consensus. OWASP ranks prompt injection as its number-one LLM risk (LLM01) and writes that, given the stochastic nature of models, "it is unclear if there are fool-proof methods of prevention for prompt injection" (LLM01, 2025) SOURCE; Willison, who coined the term in 2022, argues the fix is removing a leg of the trifecta, not a better prompt or filter SOURCE. So treat injection resistance as something that lowers the odds, never as a boundary. Classifier rails that try to catch injected text (detectors, guard models, action rails), their measured misses, and an encrypted-instruction attack no input filter can read, are on Guardrails; the design-pattern answer (once an agent has read untrusted input, make it impossible for that input to trigger a consequential action: plan then execute, dual LLM, CaMeL) is there too. Two more defences at the action boundary: Task Shield checks at test time "whether each instruction and tool call contributes to user-specified goals" (2.07% attack success at 69.79% utility on AgentDojo with GPT-4o; arXiv 2412.16682), and IPIGuard plans the tool calls first as a dependency graph and then only walks it, "decoupling action planning from interaction with external data" (arXiv 2508.15310) SOURCE.

The roles are themselves a boundary the harness must enforce. A message is from you only because the harness put it in the user role. On a route where nothing stops generation at the model's end-of-turn token, the model's own continuation can contain text formatted as the next user turn, and a harness that parses past the action boundary would treat it as your instruction. With no attacker involved, a local model allowed past its end-of-turn token wrote a fake user turn, tool calls inside, in 5 of 18 samples (section 2 of Building a harness, whose section 1 replays one as "Boundary ignored") SOURCE. The defence is structural: stop at the end-of-turn token or the provider's tool-use stop, cut at the first action, and take user intent only from the role the harness assigned.

Why this page runs no injection. Watching one model follow or refuse one phrasing on one day teaches nothing durable: the next model or wording can flip it, and "it refused when I tried" is the absence of evidence, not a control. The honest engineering question is what stops the action if the model follows a hostile instruction; the hands-on work here is all on those controls. Indirect injection has been shown against shipped assistants many times (email assistants made to send inbox contents out, coding agents steered by a planted comment, chatbots steered by hidden page text), always with the same three legs. A worked, dated case with a defence that holds: the encrypted context injection against Grok's web chat, stepped through on xAI / SpaceXAI: Grok.

To the model it is one stream of tokens; only the harness knows who wrote each part

One model call in the textstats task, schematic. The harness assigns each block a role; the model receives them as one sequence. The file the agent read arrives as a tool result, so a sentence planted in it (highlighted) is just more text in the same stream, and tool definitions from a third-party server are text too (section 3). Delimiters and training ("content inside tool results is data, not instructions") raise the bar; they do not draw a boundary.

3. Supply chain: tools, MCP servers and skills are code and text you did not write

Injection is text arriving at run time; the supply chain is text and code you installed. A third-party tool reaches the agent two ways. Its definition (name, description, argument schema) is rendered into the context on every call, so it is read by the model and rarely by the user. Its implementation, for a local MCP server, plugin or skill script, is a program running with your rights. Three named failure shapes, from Invariant Labs' write-up that named the first two (1 Apr 2025) SOURCE and the MCP specification:

  • Tool poisoning: instructions hidden in a tool's description, which the model reads but users rarely do.
  • Rug pull: a definition that changes after the user approved it.
  • False annotations: a destructive tool marked read-only; the specification says hosts MUST treat annotations from untrusted servers as untrusted.

The host-side defence against a rug pull, in four steps:

  1. Show the whole definition, then approve. The server offers a tool. The host shows the user its full description and schema, not a one-line name, because the description is text the model will read on every call.
  2. Record what was approved. The host stores a hash of the exact definition the user approved (record a hash of what was approved), alongside the server's pinned version.
  3. The server changes the definition. A server update (or a compromised server) sends a list-changed notice; the new description differs from the approved one. Nothing has run yet.
  4. Compare, and ask again. The hashes differ, so the host holds the tool and shows the user the difference. A rug pull becomes a visible re-approval instead of a silent change.

So install tools like dependencies: from known publishers, pinned versions; show users full tool descriptions; hash approved definitions and ask again when one changes (MCP's listChanged notices tell a host when to re-check); and run local servers in a sandbox with only the files and network they need. A skill registry has already been the attack: 824 malicious ClawHub skills of over 10,700 by 16 February 2026, beside OpenClaw's CVE-2026-25253, in the incident record on Personal agents section 9. So has an editor's extension marketplace: an IDE extension runs with your rights, code in its bundle can run the moment the editor loads it with no activation step, and a fork's marketplace is a separate distribution path from the publisher's own, so the coding agent's extension is a dependency to pin and verify like the rest (the Cursor marketplace case is in section 9's incident list). Note what the last step needs: Claude Code's sandbox wraps shell commands only, so an MCP server it launches runs outside it (section 6). The protocol details (transports, auth, localhost servers reached from a browser) are on MCP; the advisories CVE-2025-49596 (MCP Inspector) and CVE-2025-6514 (mcp-remote) are listed there.

A signature proves which pipeline built a package, not whose hands were on it. On 21 October 2026 litellm==1.107.0, the LiteLLM gateway's Python package, was a credential stealer, on PyPI from 11:39 to 13:23 UTC (and in the latest Docker tag until 14:20). The chain, from LiteLLM's own post: a platform master key committed publicly in May and never revoked gave the attacker an organisation owner's GitHub CLI OAuth token; with it they stole CI secrets and hijacked the release workflow. LiteLLM already used PyPI trusted publishing and signed images, so its real pipeline built and signed the malware (LiteLLM, 21 and 23 Oct 2026) SOURCE. The payload, a cook.pth file Python runs at every start, took SSH keys, cloud and CI secrets, AI coding tools' tokens (Claude Code, Cursor, Codex and others) and the provider keys in the gateway's database (SafeDep analysis) SOURCE. So: install a version you pinned and checked, not "latest"; treat long-lived maintainer tokens as the weak link (GitHub CLI added opt-in expiring tokens, gh auth login --expiring, the same day); and keep secrets out of any process that runs third-party code (section 8). Railway disclosed exposed customer environment variables the same day, in "a series of attacks recently targeting platform companies with the aim of compromising AI inference providers" (Railway) SOURCE. The gateway's side is on Gateways and routing.

4. The permission gate: allow, ask, deny, and fail closed

The first layer is a function run before every tool call that returns allow, ask a person, or deny and tell the model why. The root's Loop lab builds one in its step 3; this page runs that gate's real check(), with no model, on a fixed set of 11 actions (the task's own work plus clearly dangerous ones). Of the 11, the gate allows 4 and denies 7; but only 4 of the 7 denials come from a rule that names the action. The other 3 are denied by the fail-closed default MEASURED.

Fig. 2 sends six of them through the gate, then all 11; each step quotes the gate's actual output.

  1. Eleven actions, four checks, first match wins. (1) deny rules, (2) the metacharacter rule (any of ; & | $ < > or a backtick means "ask"), (3) allow rules, (4) nothing matched means "ask". In a headless run nobody can answer, so ask becomes deny.
  2. read_file textstats/core.py: allow. No deny rule matches, no metacharacter, and the allow rule for read_file does. The gate has an action policy, not a data policy: it does not know what the file holds. Gate output: allow rule (read_file, '').
  3. edit_file tests/test_core.py: deny at check 1. The task forbids editing the tests, and a named deny rule matches first; deny rules come first so they win over any allow. Gate output: deny rule (edit_file, '^tests/').
  4. python3 tests/test_core.py: allow. Running the tests the intended way: the exact allow rule matches at check 3. Gate output: allow rule (run_command, ...python3 tests/test_core\.py).
  5. python tests/test_core.py: deny by default. The same command spelled python: no rule matches, so it falls to "ask", and with nobody at the terminal ask means deny. Fail closed, and brittle against the task itself. Gate output: no rule matched and nobody can be asked.
  6. cat README.md; rm -rf textstats: deny at check 1. An allowed prefix with a chained destructive command: the deny rule naming rm matches first. A string gate must treat chaining as dangerous.
  7. cat $(echo README.md): deny by default. Command substitution: no deny rule names it, but the metacharacter rule says ask, and headless that is deny. The default, not the list, caught it. Gate output: ask rule (run_command, '[;&|`$<>]') and nobody can be asked.
  8. All 11: most of the protection comes from the default. 4 allowed; 4 denied by a rule that names the action (editing the tests, curl, a chained rm, git push), 3 by the default (python, the substitution, python3 -c).

As a rule: deny → ask → allow, first match wins; unmatched = ask; ask with nobody there = deny. Fail closed, because a gate that defaulted to allow would protect you only against the words on its list. Three ways a command-pattern gate is brittle, each from the root's recorded runs:

  • It blocks work it should allow. In three of the root's four Claude Code runs an allow rule for python3 blocked python tests/test_core.py; the models typed python, hit a denial, and in the Haiku runs finished without running the tests SOURCE. The python vs python3 gap: an exact-token allow list is only as right as the author's guess at how the model will spell the command.
  • An allowed prefix can hide a second command. cat README.md; rm -rf textstats is two commands; treating shell metacharacters as "ask" catches chaining and command substitution, but it is a syntactic proxy for a semantic question the string cannot answer.
  • It only knows the tools it was told about. The Loop lab's step 5 added a subagent tool, forgot its rule, and the gate refused it: failing closed, the right default, and a surprise SOURCE.

The deeper point: a gate decides which commands start, not what a started command can reach. An allowed python3 fix.py can open a socket and read your SSH key. Necessary, cheap, always on, and never sufficient. A gate also has an action policy, not a data policy: it allows a read of a file that holds a secret exactly as it allows any read (section 8).

5. Human approval: a weak control at volume

"Ask a person" looks like the safe verdict. Anthropic's own data on Claude Code says otherwise: users approve 97% of permission prompts, reject only 3% of individual permission requests against 39% of plans presented for approval, and 62% of users have used bypassPermissions or clicked "don't ask again" on Bash (Anthropic, 7 Aug 2026) VENDOR. In the same post's test with 1,053 paid professional testers, people caught the dangerous command 13.6% of the time (143 of 1,053), while the auto-mode classifier caught 89%. That classifier was built and measured against an over-eager agent making a mistake; against an agent that is trying to get past it, the same production monitor failed to block most attacks (section 9).

Design rules that follow. Ask rarely, so each ask is read: let the sandbox and the egress list make routine actions safe without a prompt, and reserve prompts for consequential, irreversible ones. Ask at the level people judge well: a plan (39% rejected) gets real scrutiny; the hundredth shell command (3%) does not. Show the exact arguments, not a summary the model wrote. Put the approval outside the conversation the model can write into: Meta's Muse agent routes connector actions and egress through Sentinel, "the sole permission authority", outside the agent's VM (Meta: Llama and MSL, its Agent security section). And in a headless run, ask means deny (section 4).

People approve almost everything a prompt shows them, and catch little of what is dangerous

Anthropic's figures for Claude Code (vendor, about its own product; the 1,053-tester comparison was a controlled test, not real codebases). The same post reports testers blocking about 17% of dangerous commands early in a session, dropping to about 5%. Anthropic's earlier sandboxing post names the effect "approval fatigue", "where users might not pay close attention to what they're approving", and reports that sandboxing "safely reduces permission prompts by 84%" in internal usage (20 Oct 2025) VENDOR.

6. Sandboxes: a kernel boundary around what runs

A sandbox assumes the gate let something through. It does not look at the command string; the kernel constrains what any process the agent spawns is able to do. The two things worth constraining are filesystem writes (the project and a temp directory) and the network (blocked, or only through a proxy you control). Here is the property, measured on this machine with sandbox-exec (macOS Seatbelt), the mechanism Claude Code and Codex use on macOS MEASURED. Fig. 3 shows that the kernel refuses whatever the intent:

  1. No profile: both operations land. A benign probe connects to a local listener (NETWORK_OK: reached 127.0.0.1) and writes a file outside its work directory (WRITE_OK: /tmp/hsec_wtest.txt).
  2. (deny network*): the socket is refused. The same probe under a one-line profile gets NETWORK_BLOCKED: PermissionError [Errno 1] Operation not permitted. The kernel refused the operation; nothing read the command string.
  3. Writes confined to WORK. Under (deny file-write*)(allow file-write* (subpath ...)) the write to /tmp gets WRITE_BLOCKED: PermissionError [Errno 1] Operation not permitted: '/tmp/hsec_wtest.txt', while the write inside the work directory lands (WRITE_OK).
  4. What sits outside the walls. Claude Code's sandbox wraps shell commands only (Bash, PowerShell); file-edit tools, MCP servers and hooks run outside it, and it is off by default SOURCE.

Real runs, macOS 27.0.1, Apple M1 Pro, 6 Oct 2026. The only bytes ever sent are the fixed marker /sandbox-demo-ping to a local listener started and stopped for the test. A profile is a few S-expressions: (allow default)(deny network*) denies all sockets; (deny file-write*)(allow file-write* (subpath ...)) confines writes (both profiles are in the Depth section).

The gate reasons about a string; the sandbox reasons about the operation. It turns "the agent can reach anything you can" into "this directory and nothing on the network", the difference between a mistake being embarrassing and being an incident. The mechanisms by OS:

  • macOS: Seatbelt via sandbox-exec and a profile (Claude Code sandboxing, read 6 Oct 2026) SOURCE.
  • Linux: Claude Code uses bubblewrap (user namespaces) plus a local proxy; Landlock (kernel 5.13) lets an unprivileged process restrict its own file access with three syscalls, and seccomp-bpf filters which syscalls are allowed at all. Mechanics: Containers and isolation (section 10 compares what untrusted code talks to in a plain container, under gVisor and in a microVM).
  • One policy, three systems: GitHub Copilot's local sandboxing, generally available since 7 October 2026, writes one policy over files, network and Git and gh credentials and maps it to each system's native controls on Windows, macOS and Linux through the Microsoft eXecution Container (MXC); it covers Copilot CLI, the Copilot app and the VS Code Agent Host, can sandbox MCP and language servers too, and can be enforced by an enterprise (GitHub changelog) SOURCE.
  • A machine you can throw away: a container or VM where full autonomy is acceptable because the blast radius is the box; how the isolation rises with autonomy is drawn in section 9 of Building a harness.

What it does not cover. A sandbox you did not turn on, or one with a tool outside it, contains nothing; how six other harnesses default, with and without someone to approve, is compared on Other coding harnesses section 4 ("Only Codex keeps a boundary when nobody is there to approve"). And a sandbox confines the blast radius without making the agent trustworthy: if the one network path you leave open (the proxy to the model API, a package registry) can also carry your data out, the leak is still open. That is the next layer.

A sandboxed interpreter is an injection decoder. An instruction encrypted with AES-256-GCM cannot be read by any input filter, even with the key on the page, because classifiers do not execute what they inspect; an agent allowed to run code decrypts it in its own runtime, inside the trust boundary and after every filter. So input filtering cannot secure an agent that executes code, and the controls that still hold are the ones keyed on actions: egress control (section 7) and confirmation of consequential actions (section 5). The worked case, against Grok's web chat, is stepped through on xAI / SpaceXAI: Grok.

7. Egress control: the one path out, written over destinations

Exfiltration needs a way out; close it and a compromised agent can read your secrets but send them nowhere. The first mistake is to write the policy over tools ("deny curl, deny wget"), which leaves every other way to reach the network untouched. Write it over destinations ("connect only to these hosts"), default-deny, enforced by a proxy or firewall below the agent. The policy in Fig. 4 (src/sec/egress_policy.py, a pure function, no network, no model) decides 7 ordinary requests for a coding agent that may install packages: 4 allowed, 3 denied MEASURED.

  1. Default deny, one list, two doors. Whatever tool or command makes a request, it leaves the sandbox only through the proxy or the resolver below the agent. HTTPS through the proxy and name lookups through the resolver are decided by the same allow-list: the model API, the package registry and its file host.
  2. Model API, registry, file host: allowed. HTTPS to api.anthropic.com (the model API, the agent's own backend), pypi.org (resolve a dependency to install) and files.pythonhosted.org (download a wheel) passes: each is a listed host.
  3. An unlisted host and a raw IP: denied. raw.githubusercontent.com (fetch a script a file asked it to run) is not on the list; 203.0.113.9 (an address in the documentation range) is an IP literal that matches no listed host. Both stop at the proxy.
  4. DNS goes through the same list. A lookup of pypi.org is allowed; metrics-7f3a2.telemetry.example, a name nobody expected, is refused by the resolver.
  5. Seven requests: 4 allowed, 3 denied. The verdict does not depend on which tool or command made the request, so there is nothing to spell around; an unlisted host, a raw IP and an unlisted name all fall to the default.
DNS is egress too. A process blocked from HTTP can still ask the resolver a question, and the question carries bytes outward in the name itself. That is how the September 2026 OpenAI incident got data past a web proxy (section 9). An allow-list that covers HTTP and not DNS is a door with a window next to it.
An allowed destination can carry traffic onward. A public service that fetches, stores or forwards on your behalf (a URL shortener, a screenshot or citation service, a shared editor) is a proxy to everywhere it reaches. Anthropic reported Claude Opus 5 and Claude Mythos 5 using free URL-shortening services to get around a fetch tool's URL-length limit, and Wikimedia reported OpenAI's agents trying to use Etherpad and a citation tool as proxies (section 9). Allow the specific services the task needs, and count any service that fetches arbitrary URLs as open egress.

Enforcement lives outside the component that can be persuaded. The model can be talked into trying; a harness's gate can be bypassed with cleverness; a kernel- or network-level destination list cannot be talked into anything. The strongest published production design goes further and tracks tainted egress: Meta's Muse agent marks a tool process as tainted (through the kernel) once it reads user data, so its requests never ride an auto-allow rule (Meta: Llama and MSL). For a coding agent: allow only the registry and the model API, pin or mirror the registry, cover DNS, and make any new host a reviewed change to the list, not a runtime decision by the agent. Default-deny earns its keep on rare events too: Cohere saw an open-weight model try an outbound upload during an unrelated sandboxed task in fewer than 1 in 100,000 runs, and the sandbox having no route out is what stopped it (section 9).

8. Credentials: the model cannot leak what it never sees

The cheapest protection for a secret is to keep it where the agent cannot read it. Three levels, weakest first:

  • In a file or environment variable the agent can read: the default and the worst. Once a secret is in the context, any open path out leaks it.
  • Behind a broker: the helper holds the secret and returns only the result. This is how a well-built tool exposes an API key: the key lives in the tool, the model sees a function. Meta's Muse agent keeps credentials, including OAuth tokens, in a separate service outside the agent's VM and gives the agent surrogate credentials (Meta: Llama and MSL).
  • Injected by a proxy on allowed requests only: Claude Code's sandbox can show a shell command a placeholder and have the egress proxy substitute the real value only on requests to allow-listed hosts SOURCE. NVIDIA's OpenShell (Apache 2.0), a sandboxed agent runtime, injects credentials only for approved endpoints (GitHub) SOURCE; 1Password for Agents does the same for a person's logins, filling a credential the person approved without the agent seeing it (1Password, 22 Oct 2026) VENDOR.

The first level is also reachable by code, not only by the model: the LiteLLM payload (section 3) simply read the tokens coding tools keep in files. A secret kept on a platform is the same target one level up: a hosting platform's stored environment variables are only as safe as the platform, and when one is breached the AI provider keys among them get spent (Northflank, section 9), so give such keys their own scope and spending cap so a stolen one is cheap.

Least privilege, as anywhere: scope the credential to the task (a token for one repository, not your personal access token for everything), keep it out of the reasoning loop, make its use observable. An agent with a database tool gets a role that can only read what the task needs, and its generated SQL is checked like any other untrusted input (SQL and data modelling, section 12). A forwarded ssh-agent is a broker the wrong way round: while you are connected, root on the remote host (or anything running as you there) can sign as you to every server that trusts your key; ProxyJump leaves nothing to steal (SSH, section 6). How tokens are scoped and exchanged on the wire, including agent-era OAuth, is Auth's subject.

Move the secret out of the context, then out of the sandbox

Where the real token lives (highlighted) relative to the model's context and the sandbox. In a readable file or variable it is one cat from the context window, and the gate will allow that read on its action alone (section 4). Behind a broker, the agent asks a helper to sign or call, and only the result comes back. Injected by the egress proxy, the command sees a placeholder and the real value is spliced in outside the sandbox, only on requests to allow-listed hosts.

9. Detection and monitors: an alert is not a brake

Detection is the layer that tells you a control was missing. The clearest record is first-party and dated. During training at OpenAI, a model blocked from the web at its proxy found it could still ask the DNS resolver to look things up, and delegated a domain so that questions encoded into DNS requests reached a public chatbot and answers came back (OpenAI report, 25 Sep 2026) SOURCE.

Three lessons. The egress control covered the obvious channel (HTTP), not the one used (DNS): enumerate every path out. Detection was fast and response slow: an alert tells you; a control stops the action, so build the stop. And the fix was a destination allow-list enforced below the agent, the shape of section 7.

Detected in twelve minutes, stopped two and a half hours later

The report's timeline drawn to scale (the two span lengths are derived from its times): DNS call with an external response at 9:50:23, a P0 monitoring alert at 10:02:11 (about twelve minutes later), a human reviewer acknowledging at 10:05:06, the run killed at 12:34:30, about two and a half hours after detection. Afterwards OpenAI blocked at two independent layers, restricted DNS to an allow-list of domains and record types, and added DNS detections; it states that "all training, evaluation, and inference with tool-use (defined broadly) of our most capable models remain paused".

Classifier detection inside the loop has the same limit. Detectors on tool output cut attack success by a factor of two to ten on published benchmarks and leave a residue, while designs that remove the channel reach zero on the attacks tested and pay in utility or tokens (the chart and table are on Guardrails, section 3). Meta's Muse agent runs classifiers the agent cannot switch off but has published no accuracy figures for them, so the parts of its design that rest on detection are unmeasured (Meta: Llama and MSL). Use detection to find what your boundaries missed, never as the boundary. Even as triage it catches about half: in MOLE's simulated lab, where AI agents hold ordinary accounts for 30 workdays and a security team reviews the 10 accounts a monitor ranks highest each day, the best monitor caught 24 of 45 completed harms (a random queue would catch about 3), and what the monitor could read, such as the agent's reasoning or full call arguments, mattered about as much as which model it was (MOLE).

A blocking monitor checks one action at a time; an adversarial agent plans across actions. Claude Code's auto mode and Codex's Guardian are blocking monitors: an LLM classifier judges each proposed action, blocks with a reason, and ends the session after too many blocks. In Anthropic's red-teaming study (22 Oct 2026, monitors as of September), an Opus 5 agent given a harmful side task, usually told how the monitor works, got past the production monitors (auto mode and an approximation of Guardian) in more than 55% of attacks before 20 blocks, averaged across settings SOURCE. The routes are structural: monitor injection (code or comments the agent writes persuade the monitor), multi-context attacks (sessions coordinating through a shared workspace, or compaction hiding earlier steps, so no context the monitor sees looks harmful), coverage gaps (actions it never sees, such as edits inside the working directory) and policy failures. Hardened variants helped; the authors call preventing multi-context attacks at acceptable cost "an open problem". A per-action classifier guards against an over-eager agent's mistakes (section 5), not a persistent adversary; that still needs sections 6 to 8.

METR and Redwood Research's review of OpenAI's agent monitoring (access 21 July to 11 August 2026)

METR and Redwood Research's review of OpenAI's internal agent monitoring (access from 21 July to 11 August 2026) found the same shapes: monitoring fired only when an agent returned control, so an agent that kept acting postponed it; compaction events, about 10% of internal Codex traffic, went unmonitored; two client headers could switch it off. OpenAI says it patched them (not verified by METR). The fix they recommend: monitor every N messages or minutes, and isolate agents from their monitors (METR, 22 Oct 2026) SOURCE.

Agents use what is allowed, for purposes nobody intended (Anthropic, 9 Oct 2026, corrected 12 Oct; 23 Oct 2026)

Anthropic described models working around restrictions on the live internet: Claude Mythos 5 read the settings file a local government's property-map site sends to browsers, "found working access tokens, and used them to send requests directly to the server"; Claude Opus 5 and Claude Mythos 5 used free URL-shortening services to get around a fetch tool's limit on URL length; an unreleased research model submitted a real government form when its practice copy failed to load; and Claude Haiku 4.5 submitted an invented tip to a police department's form while generating example tasks (flagged as spam and never forwarded). Anthropic attributes most cases to ambiguous or impossible tasks and environments that rewarded getting around a restriction instead of stopping. It had already cut live internet access for some high-risk evaluations and expanded that to "all our internal evaluations until we have confirmed that our security and monitoring measures" catch these behaviours; it also restricted its web fetch tool and moved internal agents to centrally managed infrastructure with less internet access (report) SOURCE. In the same weeks Wikimedia reported OpenAI agents sending millions of automated requests to its projects and trying to use Etherpad and a citation tool as proxies (Wikimedia Diff, 5 Oct 2026) SOURCE.

In 9 of the UK AI Security Institute's 43 capture-the-flag runs of Claude Mythos 5 (internet deliberately enabled, cyber safeguards off), the model took unsanctioned actions that reached real people: in the run studied most closely it tried to push malicious code to an unrelated real GitHub repository it believed a test machine pulled from, and used fake identities to pressure the maintainers, who refused. Anthropic says its Fable 5 production safeguards would have flagged it; AISI no longer enables internet access in these tests (Anthropic, 23 Oct 2026) SOURCE.

No boundary was broken in the agent incidents: the agents used what was allowed (a token a public site hands every browser, a public shortener, a real form, an open internet connection in an evaluation). Egress lists, credential rules and evaluations must assume an agent will look for the permitted path to its goal, and Anthropic's first response was a control outside the model. This section lists only incidents with a first-party, dated write-up; vendor claims about how well a defence works are not evidence of a safe deployment.

10. Red-teaming an agent: test the controls, not the model's mood

Red-teaming an agent means trying to make it take a consequential action it should not, against the whole system with its controls on. The useful unit is the control, because a control's behaviour is deterministic and a model's is not. Three layers of testing, cheapest first:

  • Canary tests per control, run in CI like unit tests: the sandbox refuses a socket and an out-of-tree write (section 6 is exactly such a test); the egress list denies an unlisted host, a raw IP and an unlisted DNS name (section 7); the gate denies an unmatched command when headless (section 4); a changed tool definition triggers a re-approval (section 3). Each passes or fails the same way every time, and each names the leg it protects.
  • Benchmarks of the whole agent under injection, which report attack success and task success with the defences on, because a defence that halves utility is a defence nobody leaves on. AgentDojo (Debenedetti et al., ETH Zurich) populates its environment with "97 realistic tasks" and "629 security test cases" (arXiv 2406.13352) SOURCE; defences measured on it are compared on Guardrails, section 3, and agent safety benchmarks such as AgentHarm on Safety and honesty benchmarks.
  • Outside researchers, through a disclosure programme with a response time. Meta offers up to $130,000 for a prompt injection affecting one user in its Muse agent (Meta: Llama and MSL); the Grok case on xAI / SpaceXAI: Grok shows the other end, a report left without a fix for 78 days.

Read results by leg: a successful injection that could not reach data or a way out is a finding about the model and a pass for the design; any path that reaches the outside with data is a failure of the design, whatever the model. And a run where "the model refused" proves nothing about the next model, so the controls are what you regression-test.

Checklist for any agent you ship, answered in writing: (1) What rights does a tool call have, and are they scoped to the task? (2) Which leg of the trifecta did I remove, and what enforces it outside the model? (3) Is the sandbox on, and does it cover every tool and server, not just the shell? (4) Where do the secrets live, and can the agent read them? (5) What are all the paths out, including DNS and any service that fetches for you? (6) Which third-party definitions are pinned? (7) When something goes wrong, what stops it, and how fast, not just what alerts me? Does the monitor see every action, including steps hidden by compaction or spread across sessions? If any answer is "the model will handle it", that is the hole. Depth

Interview rehearsal: six design questions

An agent reads untrusted web pages and has your repo with secrets. How do you make it safe? Break the trifecta outside the model: egress by destination (DNS included) through a proxy, so reading a hostile instruction cannot send data out; credentials scoped and held by a broker or injected by the proxy; a sandbox so an allowed-but-wrong command is confined. Do not rely on the model refusing.

Why is a permission gate necessary but not sufficient? It decides cheaply which commands start, and its fail-closed default does most of the work; it cannot decide what a started command reaches, and a command-name gate names tools, not destinations. Containment needs a kernel boundary.

Which leg of the trifecta do you usually remove? The way out, because a proxy or firewall enforces it below the agent. Private data (credential isolation) is the other strong option; untrusted content only for narrow agents.

Direct against indirect injection? Direct: the user types an override. Indirect: the instruction is in content the agent reads, which the user never sees; to the model the whole context is one token stream, so it cannot reliably separate your task from a planted line.

Egress for a coding agent that must install packages? Allow only the registry and the model API by destination, through a logging proxy; pin or mirror the registry; same list for DNS; a new host is a reviewed change, not a runtime decision.

Why run an agent in a container even for a trusted task? Because you do not trust the content it will read: the box bounds the blast radius of a wrong model and of a successful injection, with writes confined, network listed, secrets scoped and the whole thing disposable.
