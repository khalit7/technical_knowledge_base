Common mistakes

Treating the permission gate as a sandbox
A gate decides which commands start; an allowed command still runs with your full rights and can reach anything you can. Containment is a separate layer (OS sandbox or a disposable machine). Confusing the two is the most common agent-security error.
Writing the egress policy over tools instead of destinations
Naming tools ("deny curl, deny wget") leaves every other way to reach the network untouched. Allow outbound connections only to named destinations, enforced below the agent, and include the resolver so DNS is covered too.
Assuming the model's refusal is a control
Whether a model follows or refuses an injected instruction depends on the model and the exact wording, and shifts from one version to the next. "It refused when I tried" is a sample of one model against one phrasing, not a boundary you can rely on. The controls in sections 2 to 5 hold regardless of how the model behaves.
Leaving the sandbox off, or covering only the shell
Claude Code's sandbox is off by default and wraps shell commands only; file-edit tools, MCP servers and hooks run outside it. A sandbox you did not enable, or one with a tool outside it, contains nothing.
Giving the agent a broad credential "to be safe"
A personal access token for everything in an environment variable is one cat from the context window and one open socket from an attacker. Scope the credential to the task and keep it out of the reasoning loop.
Confusing a monitor with a brake
The DNS incident was detected in twelve minutes and stopped in two and a half hours. An alert tells you; a control stops the action. Build the stop, not just the alert.

Interview questions

An agent reads untrusted web pages and has your repo with secrets. How do you make it safe?
Break the lethal trifecta. The enforceable leg is usually egress: allow outbound connections only to named destinations (including DNS), enforced by a proxy or firewall outside the agent, so reading a hostile instruction cannot send data out. Also remove the private data from reach (scoped, broker-held or proxy-injected credentials) and run in a sandbox so an allowed-but-wrong command is confined. Do not rely on the model refusing the injection.
Why is a permission gate necessary but not sufficient?
It decides which commands start, cheaply and always. It cannot decide what a started command does: an allowed python3 x.py can open a socket and read your keys. And a command-name gate names tools, not destinations, so it does not decide what a command can reach. The protection a gate actually gives comes mostly from its fail-closed default (unmatched = deny), not its deny list. Containment needs an OS boundary.
What is the lethal trifecta, and which leg do you usually remove?
Private data, untrusted content, and a way out; all three together let an injected agent exfiltrate, and no filter reliably prevents it. You usually remove the way out (egress control by destination) because it is the leg you can enforce outside the model. Removing untrusted content is rarely feasible for a useful agent; removing private data (credential isolation) is the other strong option.
Direct vs indirect prompt injection, and why the second is harder?
Direct: the user types an override. Indirect: the instruction is in content the agent reads while working (a file, page, issue, tool output), which the user never sees. Indirect is the agent threat because the agent's usefulness is reading the world, and to the model the whole context is one token stream, so it cannot reliably separate your task from a planted instruction.
How would you design egress control for a coding agent that must install packages?
Allow outbound only to the package registry and the model API, by destination, through a proxy that logs. Pin or mirror the registry so a dependency cannot redirect you elsewhere. Cover DNS with the same allow-list. Everything else denied by default. If the agent needs a new host, that is a reviewed change to the allow-list, not a decision the agent makes at runtime.
Why run an agent in a container even if you trust the task?
Because you do not trust the content it will read, and the container bounds the blast radius of both a wrong model and a successful injection: writes confined to the box, network on an allow-list, secrets scoped to the task, and the whole thing disposable. It turns "full autonomy" from reckless into acceptable. OS mechanics: namespaces, seccomp and sandboxes on the Containers and isolation page.
