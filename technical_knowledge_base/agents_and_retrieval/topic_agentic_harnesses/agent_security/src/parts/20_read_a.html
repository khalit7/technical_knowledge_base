The topic in one screen

An agent calls tools in a loop, and every tool call runs with the harness's rights. On a laptop those are yours: your files, your tokens, your network, your ability to push to main. Nothing in the model guarantees it uses them well. Security is the set of controls the harness puts around the model, because the controls, not the model's good intentions, are what you can reason about.

Two ways it goes wrong. The model can be wrong (it deletes the wrong directory, pushes a broken branch, runs rm -rf on a bad path). And the model can be steered: text it reads while working, from a file, a web page, an issue or a tool's output, can carry instructions it follows as if you had typed them. That second one is prompt injection, and it is the harder half, because the same property that makes an agent useful (it reads and acts on whatever it finds) is the attack surface.

Neither is fixed inside the model. No current model reliably tells a real instruction from an injected one, and no filter catches every phrasing. So the defence is layered and sits outside the model, each layer assuming the one before it failed:

1
Permission gate: before each tool call, rules say allow, ask a person, or deny. Section 2. Cheap, always on, but brittle: it decides which commands start, not what they can reach.
2
Sandbox: an operating-system boundary around what does run: writes confined to a directory, network blocked or proxied. Section 3. Contains an allowed command that turns out to be a mistake.
3
Egress control: the one path out, written over destinations, not tool names. Section 4. Breaks the link between reading bad input and sending your data somewhere.
4
Credential isolation: keep the secrets out of the agent's reach entirely. Section 5. The model cannot leak what it never sees.
5
A machine you can throw away: a container or VM where full autonomy is acceptable because the blast radius is the box. OS mechanics on {{Containers and isolation|n:3f05c17b0d0d8156a841e4bf28f11293}}.

The one idea to keep. You cannot make the model safe; you make the situation safe. The question for any agent is never "will it behave?" but "if it reads a hostile instruction and tries to act on it, what stops the action?" If the honest answer is "nothing," you have a problem no prompt fixes. Simon Willison's lethal trifecta (section 7) names the exact combination that makes a leak possible; the whole page is about removing one leg of it.

1. The trust boundary: an agent acts with your rights

Draw the line around what the agent can touch. On the inside: the tools it has (read, edit, a shell), and through them everything those tools can reach, which on a developer's machine is the whole home directory, the shell environment, the network and any credential sitting in a file or variable. On the outside: the attacker, who does not need to break into your machine. They only need to get text in front of your agent: a line in a README, a comment in a dependency, the body of a GitHub issue it is asked to triage, the HTML of a page it fetches, the output of a command it runs. The running example on this page is a bug fix in a tiny library, textstats; the attacker's foothold is a note planted in that repository's files.

The uncomfortable part: the agent's usefulness is the attack surface. A coding agent that would not read untrusted files could not review a pull request; a research agent that would not fetch pages could not research. You cannot shrink the surface to zero without removing the capability. So the trust boundary is not "keep bad text out" (you cannot); it is "assume bad text gets in, and make sure acting on it is blocked or contained." Everything that follows is a way to draw that boundary somewhere the model's judgement is not the only thing holding it.

Confused deputy. The classic framing (Hardy, 1988): a program with more authority than its caller can be tricked into misusing that authority on the caller's behalf. An agent is a textbook confused deputy. It holds your authority (your tokens, your write access) and takes instructions from whoever can place text in its context. The defences below all work by not letting the deputy's authority and the attacker's instructions meet at a consequential action.

The personal-agent case. A resident assistant that reads your messages and mail and holds your accounts has a wider boundary than a coding agent: anyone who can send it a message can place text in its context, and there is often no test suite to catch a wrong action. The same design questions (who can write into the context, what the agent may do alone) are worked through for OpenClaw and Hermes Agent in section 6 of {{Personal agents: OpenClaw, Hermes Agent, and how they differ from coding harnesses|n:3c75c17b0d0d81bf9462fbeb09593e1c}}, and its "Gate designer" tab lets you set which actions need approval.
