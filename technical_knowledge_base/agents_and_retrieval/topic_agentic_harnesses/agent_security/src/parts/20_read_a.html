1. The threat model: a confused deputy with three legs

Every tool call runs with the harness's rights. On a laptop those are yours: your home directory, your tokens, your network, your ability to push to main. The running example on this page is a bug fix in a tiny library, textstats (the root's Loop lab task), and the attacker never touches your machine: they only need to get text in front of the agent, a line in a README, a comment in a dependency, an issue it triages, a page it fetches, a tool's output. Two things go wrong: the model can be wrong (it deletes the wrong directory), or it can be steered by that text. The agent is a textbook confused deputy (Hardy, 1988): it holds your authority and takes instructions from whoever can place text in its context.

The uncomfortable part is that the agent's usefulness is the attack surface: a coding agent that would not read untrusted files could not review a pull request. So the boundary is not "keep bad text out" (you cannot) but "assume it gets in, and make acting on it blocked or contained". The question for any agent is never "will it behave?" but "if it follows a hostile instruction, what outside the model stops the action?"

Simon Willison's lethal trifecta (16 Jun 2025) SOURCE names the combination that turns injection into theft: access to private data, exposure to untrusted content and a way to communicate externally. With all three, an injected agent can be made to send your data out, and no current filter reliably prevents it. Remove any one leg and the leak cannot complete. That turns one unsolvable problem (make the model injection-proof) into three solvable ones. Predict before you toggle: in the hard case below the agent must read untrusted content, so which controls actually break the chain?

Which leg each control removes: the gate alone never breaks the chain

A design tool with no model and no attack: a coding agent that reads content you do not control (so the untrusted-content leg is always present) on a machine that holds something worth stealing. The permission gate hardens every layer but removes no leg on its own; the sandbox and the egress allow-list close the way out (the sandbox only if it is on and covers the tool); credential isolation removes the private data. Most real deployments remove the way out, because it is the leg you can enforce below the agent with a proxy or firewall. Removing untrusted content is feasible only for narrow agents.

The rule that follows: when you design an agent, write down which leg you removed and what enforces it. If you cannot name the removed leg, you have all three. A resident personal assistant that reads your mail and holds your accounts has a wider boundary than a coding agent (anyone who can message it can write into its context); that case is worked through in section 6 of {{Personal agents|n:3c75c17b0d0d81bf9462fbeb09593e1c}}, whose gate designer sets which actions need approval.

2. Prompt injection: direct and indirect

Direct injection: the user is the attacker, typing an override ("ignore your instructions and..."); a concern for a public chatbot, less so for your own coding agent, where you are the user. Indirect injection: the instruction sits in content the agent reads while working (a README, a code comment, a dependency's changelog, a web page, an issue, a tool's output). You never see it; the agent does. That is the agent threat.

To the model it is one stream of tokens; only the harness knows who wrote each part

One model call in the textstats task, schematic. The harness assigns each block a role; the model receives them as one sequence. The file the agent read arrives as a tool result, so a sentence planted in it (highlighted) is just more text in the same stream, and tool definitions from a third-party server are text too (section 3). Delimiters and training ("content inside tool results is data, not instructions") raise the bar; they do not draw a boundary.

Why it is unsolved: any phrasing the training did not anticipate can still land. This is the field's consensus. OWASP ranks prompt injection as its number-one LLM risk (LLM01) and writes that, given the stochastic nature of models, "it is unclear if there are fool-proof methods of prevention for prompt injection" (LLM01, 2025) SOURCE; Willison, who coined the term in 2022, argues the fix is removing a leg of the trifecta, not a better prompt or filter SOURCE. So treat injection resistance as something that lowers the odds, never as a boundary. Classifier rails that try to catch injected text (detectors, guard models, action rails), their measured misses, and an encrypted-instruction attack no input filter can read, are on {{Guardrails|n:3c65c17b0d0d819bbfa5dffa9246c297}}; the design-pattern answer (once an agent has read untrusted input, make it impossible for that input to trigger a consequential action: plan then execute, dual LLM, CaMeL) is there too.

The roles are themselves a boundary the harness must enforce. A message is from you only because the harness put it in the user role. On a route where nothing stops generation at the model's end-of-turn token, the model's own continuation can contain text formatted as the next user turn, and a harness that parses past the action boundary would treat it as your instruction. With no attacker involved, a local model allowed past its end-of-turn token wrote a fake user turn, tool calls inside, in 5 of 18 samples (section 2 of {{Building a harness|n:3c65c17b0d0d817ca14fc32338707c2f}}, whose section 1 replays one as "Boundary ignored") SOURCE. The defence is structural: stop at the end-of-turn token or the provider's tool-use stop, cut at the first action, and take user intent only from the role the harness assigned.

Why this page runs no injection. Watching one model follow or refuse one phrasing on one day teaches nothing durable: the next model or wording can flip it, and "it refused when I tried" is the absence of evidence, not a control. The honest engineering question is what stops the action if the model follows a hostile instruction; the hands-on work here is all on those controls. Indirect injection has been shown against shipped assistants many times (email assistants made to send inbox contents out, coding agents steered by a planted comment, chatbots steered by hidden page text), always with the same three legs. A worked, dated case with a defence that holds: the encrypted context injection against Grok's web chat, stepped through on {{xAI / SpaceXAI: Grok|n:3c65c17b0d0d81f2ac36c873a854007f}}.

3. Supply chain: tools, MCP servers and skills are code and text you did not write

Injection is text arriving at run time; the supply chain is text and code you installed. A third-party tool reaches the agent two ways. Its definition (name, description, argument schema) is rendered into the context on every call, so it is read by the model and rarely by the user. Its implementation, for a local MCP server, plugin or skill script, is a program running with your rights. Three named failure shapes, from Invariant Labs' write-up that named the first two (1 Apr 2025) SOURCE and the MCP specification:

  • Tool poisoning: instructions hidden in a tool's description, which the model reads but users rarely do.
  • Rug pull: a definition that changes after the user approved it.
  • False annotations: a destructive tool marked read-only; the specification says hosts MUST treat annotations from untrusted servers as untrusted.

Pin what you approved: a changed definition must be approved again

The host-side defence against a rug pull, in four steps: show the full definition, record a hash of what was approved, re-check when the server says its tool list changed, and ask again on any difference. Schematic; the hashes are illustrative.

So install tools like dependencies: from known publishers, pinned versions; show users full tool descriptions; hash approved definitions and ask again when one changes (MCP's listChanged notices tell a host when to re-check); and run local servers in a sandbox with only the files and network they need. A skill registry has already been the attack: 824 malicious ClawHub skills of over 10,700 by 16 February 2026, beside OpenClaw's CVE-2026-25253, in the incident record on {{Personal agents|n:3c75c17b0d0d81bf9462fbeb09593e1c}} section 9. Note what the last step needs: Claude Code's sandbox wraps shell commands only, so an MCP server it launches runs outside it (section 6). The protocol details (transports, auth, localhost servers reached from a browser) are on {{MCP|n:3c65c17b0d0d813f9695dc4175c44cbb}}; the advisories CVE-2025-49596 (MCP Inspector) and CVE-2025-6514 (mcp-remote) are listed there.

A signature proves which pipeline built a package, not whose hands were on it. On 21 October 2026 litellm==1.107.0, the LiteLLM gateway's Python package, was a credential stealer, on PyPI from 11:39 to 13:23 UTC (and in the latest Docker tag until 14:20). The chain, from LiteLLM's own post: a platform master key committed publicly in May and never revoked gave the attacker an organisation owner's GitHub CLI OAuth token; with it they stole CI secrets and hijacked the release workflow. LiteLLM already used PyPI trusted publishing and signed images, so its real pipeline built and signed the malware (LiteLLM, 21 and 23 Oct 2026) SOURCE. The payload, a cook.pth file Python runs at every start, took SSH keys, cloud and CI secrets, AI coding tools' tokens (Claude Code, Cursor, Codex and others) and the provider keys in the gateway's database (SafeDep analysis) SOURCE. So: install a version you pinned and checked, not "latest"; treat long-lived maintainer tokens as the weak link (GitHub CLI added opt-in expiring tokens, gh auth login --expiring, the same day); and keep secrets out of any process that runs third-party code (section 8). Railway disclosed exposed customer environment variables the same day, in "a series of attacks recently targeting platform companies with the aim of compromising AI inference providers" (Railway) SOURCE.
