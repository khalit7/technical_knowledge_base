Other coding harnesses: Codex, Gemini CLI, opencode, Aider, OpenHands, mini-SWE-agent

Six open-source coding agents compared by design choice, read from source at pinned versions and run on the same task. Child page of Topic: agentic-harnesses. Data as of October 2026. Reading: 26 min, plus 22 in closed details.
The idea in one sentenceEvery coding harness runs the same loop; what differs is five choices around it (how the model writes an action, what stops the loop, how an edit is applied, what contains a command, and what the model sees next), and on the same task those choices, not the task, decided where a small model failed.

One loop, five choices; every failure in our runs sat at one of them

Beside it (below on a phone): the same task (two planted bugs in the running example) given to each harness with the same local 4B model MEASURED; a filled dot is a bug fixed, and the number is the choice at which the run went wrong. Only Aider, the harness that takes the most decisions away from the model, fixed both. One run per setting: a demonstration of mechanisms, not a ranking.

You need: the agent loop (model call, tool call, result, repeat), built from zero in the parent's Loop lab. Not here, each owned by its own page: Claude Code itself (Claude Code, taken apart); how to build a harness, the action boundary, tool design and the edit-format bench (Building a harness); window budgets, caching and compaction in general (Context engineering); the threat model behind sandboxes (Agent security); benchmark scores and how much a harness moves them (Coding benchmarks, Harnesses for training and evaluation); 23 harnesses on nine axes (the parent's Harness atlas tab).

Text actions: the model writes its action inside the reply in an agreed format and the harness finds it with a regular expression; the alternative is a native tool call.
Matcher ladder: the sequence of ever looser ways an edit tool tries to find the text it must replace.
Loop detector: a harness check that notices repeated calls or text and nudges or stops the model.
Sandbox mode and approval policy: what a command can touch, and who must say yes before it runs; two separate settings.
Compaction (or condensation): replacing older history with a model-written summary when the window fills.
Repository map: Aider's ranked summary of a repository's definitions, sent up front instead of letting the model search.

1. How the model writes an action: tool calls or text

Five of the six send tool definitions (name, description, JSON schema) and get back a structured call; the API ends the reply there with a finish reason (tool_calls in the OpenAI format, tool_use in Anthropic's), so the inference server enforces the action boundary. Aider, and mini-SWE-agent's opt-in text mode, use text actions instead: Aider's SEARCH/REPLACE blocks, or exactly one ```mswea_bash_command block per reply, found by a regex. Text works with any model that writes text, which is why Aider chose it in 2023, before OpenAI shipped function calling on 13 June 2023 (OpenAI). The cost: now the harness must stop the model at its action. Why and how is Building a harness' section 2; here is what each choice did on our task.

Aider does not need the stop: its protocol is "reply once, with the edits", so the model never waits for an observation inside a reply. A loop that does (run ls, see the listing, decide) needs a server-side stop: a stop sequence, or the chat template's end-of-turn token, which an open model emits after an action because it was trained to. claude -p, the only route to Claude here (a subscription, no API key), has no stop-sequence option. So mini-SWE-agent's text mode ran with Claude Haiku 4.5 twice through a small adapter: reply passed through untouched, and reply cut right after the first action block.

What it buys. A client-side cut stops the harness from acting on invented output; it does not stop the model from believing it. Only a real message list with a server-side stop does. Aider, whose protocol needs no observation inside a reply, fixed both bugs through the same adapter in 3 calls and 25 s (section 3). The local 4B model never invented output in text mode: it ran behind a chat server whose template ends the turn with an end-of-turn token after one action, so training plus the template gave the boundary, not the harness. The parent's Loop lab met the same wall (Haiku once ran on for 95,162 characters until the harness kept only the text up to the first action).


The cost on the tool-call side is schema surface: every optional field with a rule attached is one more way for a weak model to fail. Codex gave our local model 12 tools; on its first call the model filled the optional justification argument of exec_command with an empty string, Codex answered "justification requires an explicit sandbox_permissions" (handlers/mod.rs line 101), and the model resent the same call three more times. OpenHands injects a required security_risk field into every tool that changes something; our model once misspelt it security_rika, which the schema rejected.






2. What stops the loop, and what catches a loop that will not stop


Three of the six end when a reply has no tool call (Codex, Gemini CLI, opencode), with no step cap by default. OpenHands ends on a finish tool or plain text, caps at 500 iterations, and answers an empty reply with "Please use a tool to proceed with the task." mini-SWE-agent ends when a command's output starts with the line COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT and exits 0 (the check is on the output, not the command text: local.py 45 to 56). Aider has no agent loop: one reply, its edits applied, then lint and tests, and at most 3 "reflected" retries carrying the errors (base_coder.py 924 to 945); the human is the outer loop.


The guards differ more than the stop rules. Gemini CLI counts the same tool call five times in a row, or a 50-character chunk of text repeated ten times, as a loop; after 30 turns a separate model call checks for "unproductive" loops every 5 to 15 turns and needs 0.9 confidence; the first detection injects a nudge, the second stops the turn (loopDetectionService.ts). opencode's doom-loop guard turns three identical tool calls in a row into a permission question (processor.ts). OpenHands' stuck detector scans the last 20 events for repeated action and observation pairs, nudges once, then stops. mini-SWE-agent ends a run after three consecutive format errors and at a $3 cost limit. Codex has none: nothing stops a repeating call.


How each recorded run ended: the stop rule decided more outcomes than the model did




One square per model call, in order MEASURED, classified from the recordings by src/derive_ends.py: acted and got a real result; acted and got an error or a refusal; acted with a sed that exited 0 and printed nothing (a silent no-op); replied with prose or nothing; a side call (session title, commit message, history summary); a subagent's call. The end reason is on the right. Codex: four refused calls, then prose hit the 2,048-token cap. Gemini CLI: an empty reply ends the loop. opencode: prose describing the fix, no edit call. OpenHands: our 30-iteration cap. mini-SWE-agent (tool calls): three replies in a row with no tool call. Click a row to open the run call by call.


What it buys. "A reply with no tool call means done" is cheap and model-agnostic, but it cannot tell finishing from explaining: opencode and Codex both ended our runs on prose with both tests still failing, and Gemini CLI on an empty reply with one left. Aider's rule is the opposite, the harness runs the tests (--auto-test) and feeds back only the failure, and it was the only one to finish. A stop rule that consults a verifier is worth more than a smarter model here; the general case is Building a harness' section 10. And a guard needs a cheap first stage: Codex's repeated justification call (section 1) is exactly what opencode's three-in-a-row rule or Gemini CLI's five-in-a-row rule would have caught.


Each loop, read from source




Codex CLI
run_turn samples the model, runs any tool calls, sends their output back and repeats; a reply with no tool call ends the turn, unless a Stop hook objects and injects a continuation (turn.rs 150 to 170). There is no step or turn limit; when the window fills mid-task it compacts and keeps going (lines 601 to 650). Every request allows parallel tool calls; a read-write lock lets tools that declare themselves parallel-safe run together (parallel.rs).


Gemini CLI
Split in two: GeminiClient runs one streamed model turn (compress if needed, check for loops, pick a model, stream), and the caller runs the tools and sends results back; in headless mode that caller is a while (true) in nonInteractiveCli.ts. Session turns are unlimited by default (maxSessionTurns -1). Tools run in parallel by default; every tool schema gets an injected wait_for_previous argument the model sets to serialise a call, and file edits always run one at a time (scheduler.ts).


opencode
runLoop reloads the session's messages from its database on every pass, makes one streamed model call, runs the tool calls, and stops when the last reply has no tool call (prompt.ts). No step limit unless an agent sets steps. Malformed calls are repaired: wrong-case tool names are fixed; unknown ones go to a hidden invalid tool that returns an error instead of crashing the turn.


Aider
Coder.run() takes one user message; run_one() sends it, applies the edits in the reply, commits, runs the linter and (if asked) the tests, and if anything failed sends a "reflected" message with the errors. The model never calls a tool, and shell commands it suggests in a ```bash block need an explicit yes: --yes-always answers no to them (io.py).


OpenHands SDK
A Conversation owns a list of typed events (messages, actions, observations, condensations), and LocalConversation._run() repeats: check status, check the stuck detector, call agent.step(), check confirmation, budget and the iteration cap (local_conversation.py). Because state is an event log, a conversation can be persisted, resumed and replayed.


mini-SWE-agent
DefaultAgent.run() renders two messages (system, task), then repeats step() = execute_actions(query()) until a message with role exit appears (default.py 88 to 128). The whole agent class is 190 lines at v2.4.6 (the README still says "some 100 lines"). Limits: steps unlimited by default, cost limit $3, three consecutive format errors (lines 26 to 33). Control flow is by exceptions: a format error, a limit or a submission each raises, and its message is appended to the history.








3. How an edit is applied: the format and the matcher ladder


An edit names text to find and text to put in its place. Models copy the "find" text imperfectly (indentation, trailing spaces, typographic quotes), so each harness tries a matcher ladder, ever looser ways to find it, and differs in what it does when every rung fails. That second choice decided two of our runs.


From nine fallbacks to none: how hard each harness tries to find the text, and what it says when it cannot




One square per matcher, tried left to right until one finds a unique match; on the right, what the model is told when none does. Read from source at the pinned versions (links below).


    

  • Codex apply_patch: exact, then ignoring trailing spaces, then trimmed, then with typographic dashes and quotes mapped to ASCII (seek_sequence.rs). The first match wins, and a hunk is searched for only after its @@ line.
    • 

  • Gemini CLI replace: exact; "flexible" (each line compared with its whitespace trimmed, the replacement re-indented); a regular expression with \s* between tokens; then a fuzzy sliding window accepting a weighted Levenshtein distance of up to 10% of the search length (edit.ts). The second-model "edit correction" older write-ups describe exists but is off by default (disableLLMCorrection: true, config.ts).
    • 

  • opencode edit: nine matchers: exact, line-trimmed, block-anchor (first and last line fixed, the middle scored by Levenshtein similarity, threshold 0.65), whitespace-normalised, indentation-flexible, escape-normalised, trimmed-boundary, context-aware and multi-occurrence (edit.ts); a comment credits Cline and Gemini CLI for the ideas. After each edit, language-server diagnostics for the file are appended to the tool result, so the model sees a type error in the same turn.
    • 

  • Aider SEARCH/REPLACE: exact, or after small fixes (leading whitespace, a stray blank line, ... elision); the edit-distance matcher many describe sits after an unconditional return and never runs (editblock_coder.py 157 to 187). A block that fails comes back with a "Did you mean" snippet of the closest lines.
    • 

  • OpenHands file_editor str_replace: old_str must match once; the only retry strips surrounding whitespace (editor.py). The tool also does view, create, insert and undo_edit.
    • 

  • mini-SWE-agent: no edit tool; files are edited with sed and heredocs, as the prompt teaches. A pattern that matches nothing exits 0 and prints nothing.
    • 



What the recordings show MEASURED. OpenHands' model found both bugs, then sent str_replace five times with an old_str indented one level too deep and missing two of the docstring's three closing quotes; each came back "No replacement was performed, old_str ... did not appear verbatim", a clear error the model could not act on, until our 30-iteration cap. mini-SWE-agent's model ran sed -i 's/return sorted(counts.items(), key=lambda kv: -kv[1])[:n]/.../' six times: in sed's pattern language [1] and [:n] are character classes, not literal brackets, so nothing matched, sed exited 0, and the model never learned why. A loud refusal at least tells the model something; a silent no-op tells it nothing. This is the agent-computer-interface argument (tools designed for a model as the user: Building a harness' section 5): a bash-only harness relies on the model knowing sed; strong models do, a 4B model did not.


Forgiving has a cost too: on a 4B model's unified diffs, Aider's udiff applier applied 8 of 10 where git apply refused almost all, but 6 of those 8 failed the check (Building a harness, its "Edit format bench" tab, which also ran Codex's matcher and saw a model put the line it was changing on the @@ line, so the line to remove could never be found).

Aider's edit formats, and what whole-file against diff cost on our task


Aider picks the format per model: diff (SEARCH/REPLACE), whole (reprint the file), udiff, diff-fenced, a V4A patch format like Codex's, and editor-* variants for architect mode (edit formats); an unknown model, such as a local one, defaults to whole (models.py). 4. What contains a command: sandbox and approval defaults


Two separate questions: what can a command touch (an operating-system sandbox, a container, or your whole machine) and who says yes before it runs (nobody, a human, a policy that denies). The six sit at every corner, and the corner moves when nobody is there to approve, in headless runs and CI.


Only Codex keeps a boundary when nobody is there to approve




Each harness at its default (solid) and where its headless or "yes to everything" mode moves it (dashed, with the flag). Read from source at the pinned versions. Codex's codex exec forces the approval policy to never, but the sandbox stays on; Gemini CLI's gemini -p denies anything that would need approval; Aider's --yes-always answers no to the shell commands the model suggests; mini-SWE-agent's --yolo stops asking. Why both dials are needed, and what an attacker does with each gap, is Agent security.


Each harness's sandbox and approval model, read from source




Codex CLI
Two independent dials: a sandbox mode (read-only by default, workspace-write for a trusted folder, danger-full-access) and an approval policy (on-request by default, never, or granular) (config_toml.rs). On macOS the sandbox is Seatbelt (sandbox-exec with four .sbpl profiles, deny by default); on Linux, bubblewrap for files plus seccomp for the network, with Landlock kept only as a deprecated fallback (linux-sandbox). In workspace-write the network stays off unless you enable it. codex exec (headless) forces the approval policy to never, so the sandbox is all that stands between the model and your machine (exec).


Gemini CLI
Approval modes default, auto_edit, plan and yolo, decided by TOML policy files: read-only tools are allowed, edits and the shell ask (write.toml). Headless, the engine's default is deny: gemini -p without --yolo or --approval-mode auto_edit cannot edit or run anything (policy-engine.ts). The sandbox is off by default; -s relaunches the whole CLI inside macOS Seatbelt (profile permissive-open: writes only to the project, temp and cache folders, network open), or Docker, Podman, gVisor or LXC on Linux (sandbox.ts).


opencode
Rules of the form permission, pattern, action (allow, ask, deny); the last matching rule wins. Defaults allow almost everything: only reading .env files, touching paths outside the project and doom loops ask (agent.ts). Shell commands are parsed with tree-sitter so an "always allow" can be stored as a prefix such as git checkout *. There is no OS sandbox. In opencode run, any question is rejected unless you pass --auto.


Aider
No sandbox. The safety net is git: dirty files are committed first, every applied edit becomes its own commit with a model-written message, and /undo checks out the previous version of the changed files and soft-resets that commit (git docs). That undoes edits; it isolates nothing.


OpenHands SDK
Confirmation policy NeverConfirm by default; ConfirmRisky asks at HIGH risk and for UNKNOWN. The LLMSecurityAnalyzer does no analysis of its own: it returns the security_risk value the acting model wrote into its own call (llm_analyzer.py, field injected by tool.py), so the agent grades itself; a regex analyser for patterns such as rm -rf exists as a second layer. LocalWorkspace runs commands on your machine; isolation comes from DockerWorkspace, which starts an agent-server container and drives it over HTTP. In our run the model rated reads LOW and pip install pytest MEDIUM, which it ran inside the container when pytest was missing, although the test file runs with plain python3.


mini-SWE-agent
The mini command asks before each command unless you pass --yolo, and runs on your machine; Docker, Podman, Singularity and bubblewrap environments are one setting away. Every action is a fresh subprocess (local.py), so cd and export do not persist between steps; in exchange sandboxing is "literally just switch out subprocess.run with docker exec", and runs are trivial to parallelise.




What it buys. A sandbox on by default (Codex) means the prompt does not have to be trusted and headless mode stays safe; a deny-by-default headless policy (Gemini CLI) is safe but surprises people ("why did nothing get edited?"); allow-by-default with no sandbox (opencode) is fastest and trusts the model with your machine; git (Aider) makes edits reversible but not commands; a self-graded risk field (OpenHands) is not a reviewer. Codex no longer keeps a hard-coded list of safe commands: Starlark execpolicy rules decide allow, prompt or forbid, and the built-in "dangerous" check only knows forced rm (is_dangerous_command.rs).


How our runs were contained, and two Gemini CLI traps met on the way


opencode and OpenHands ran inside throwaway Docker containers we started (opencode has no sandbox; the OpenHands SDK used its local workspace inside the container), mini-SWE-agent with its Docker environment, Codex with its own Seatbelt workspace-write, Gemini CLI with its own Seatbelt (-s), and Aider with no sandbox (it runs no model-suggested command under --yes-always; only our test command).


In a folder it does not trust, Gemini CLI printed "Approval mode overridden to "default" because the current folder is not trusted", which in headless mode means every edit is denied, --yolo or not. And setting GOOGLE_GEMINI_BASE_URL makes the CLI pick its "gateway" sign-in type, which its own validator then rejects ("Invalid auth method selected"; auth.ts); choosing the API-key sign-in in the settings keeps the custom base URL.


A Codex process that outlives the session


Since 0.157.0 an interactive codex session starts codex app-server --managed-daemon by default (the release note: "Enabled automatic background-server startup for eligible interactive sessions"). Per a user report (issue #48195, opened 25 September 2026; still open, with no maintainer reply and no change to the default, when read on 26 October, while downstream packagers switch auto-start off themselves), the daemon keeps running after every Codex window is closed, runs from a copy of the roughly 374 MB platform package under ~/.codex/packages/, keeps the environment of the session that started it, and a detached loop checks for updates five minutes after start and then hourly, restarting the backend. codex features disable daemon_auto_start (or daemon_auto_start = false in config.toml) turns it off. The sandbox confines tool calls; it says nothing about what the harness itself leaves running.






5. What the model sees: the first request, compaction and the repository map


Context is paid for before the model has done anything. The first request of each run carries the harness's system prompt and every tool definition, and every later call resends it all with the history appended. The principles (window budgets, caching, what to compact) are Context engineering's; here is what each harness actually sends and keeps.


Before reading a single file, Gemini CLI sent 11,452 tokens and mini-SWE-agent under 900




The first request of each local-model run, in characters as sent on the wire, split into system prompt, tool definitions and user content (task, plus Aider's repository map and files), with the prompt tokens the server counted MEASURED. Gemini CLI: 32,924 characters of system prompt and 15 tools in 17,722 characters (counted afterwards with the model's own chat template, because the gateway's stream carried no usage; the same count reproduces the server's numbers on the opencode run exactly). opencode: 9,602 characters of system prompt and 21,144 characters of tool definitions for 10 tools, the bash description alone 4,628, so 7,247 prompt tokens (Codex's, at 9,210, and Gemini CLI's, at 11,452, were larger). OpenHands: 15,228 characters of system prompt and 17,056 characters of tools (the task_tracker description alone is 5,051), 7,196 tokens. Every tool's description and the full prompt text are in the Same task, every harness tab.


Prompts and tools are chosen per model family: Codex gives an unknown model a fallback prompt and 12 tools, opencode picks its system prompt and even its edit tool by matching the model id; a provider-agnostic harness has to carry a dialect per family.


Per-model prompts and tools, and which project instruction files each reads


Prompts and tools are per model. Codex gives an unknown model the 20,903-byte fallback prompt (model_info.rs) and 12 tools, among them five multi-agent tools and three "goal" tools but no apply_patch: unknown models are expected to call it through the shell. For OpenAI's own models a test pins the default set: exec_command and write_stdin (a shell, long-running processes on a pseudo-terminal), update_plan, request_user_input, apply_patch, view_image, tool_search (which loads MCP and multi-agent tools on demand) and web_search (prompt_caching.rs). opencode chooses its system prompt by matching the model id: anthropic.txt for Claude, gemini.txt, codex.txt, beast.txt for older GPT models, default.txt (8,528 bytes) for anything else (system.ts); ids containing gpt- get a Codex-style apply_patch instead of edit and write (registry.ts). A provider-agnostic harness has to carry a dialect per model family. OpenHands assembles its prompt from Python sections (28,492 bytes of static text, with dynamic repository, skills and date sections).


Tool sets. Gemini CLI: about 17 tools reach the model in a default interactive session (15 in our headless run): read_file, list_directory, glob, grep_search (ripgrep), replace, write_file, run_shell_command, web_fetch, google_web_search, write_todos, invoke_agent (subagents), activate_skill and others (config.ts). Two often-listed tools are not model-visible in this version: read_many_files serves only the @file syntax, and save_memory is gone: the prompt tells the model to edit GEMINI.md with the ordinary file tools. OpenHands' default coding preset gives terminal (a tmux session), file_editor, task_tracker, plus the built-ins finish and think: five tools (default preset); every tool schema gets two injected fields, summary and, for tools that change something, security_risk, so the model must classify the risk of its own action on every call. opencode sent our model 10 tools, mini-SWE-agent one (bash), Aider none.


Project instruction files. Codex reads AGENTS.md, one per directory from the git root down to the working directory (an AGENTS.override.md wins in its directory), 32 KiB in total (agents_md.rs). Gemini CLI reads GEMINI.md from ~/.gemini, then from each trusted root up to the git root; one in a subdirectory loads only when a tool first touches that directory, and files can @import others five levels deep. opencode takes the first of AGENTS.md, CLAUDE.md, CONTEXT.md between the working directory and the project root (and ~/.claude/CLAUDE.md globally), plus nested AGENTS.md files attached when the read tool opens a file below them. OpenHands ignores AGENTS.md or CLAUDE.md unless load_project_skills=True. Aider reads no memory file automatically (conventions are a file you add with --read); mini-SWE-agent reads none.




When the window fills: Gemini CLI compacts at half the window and keeps the newest 30%; mini-SWE-agent never compacts




The history at the moment each harness compacts, and what survives: kept verbatim against summarised by a model call. Widths are to scale for Gemini CLI (oldest 70% summarised) and opencode (a recent tail of 25% of the usable window, clamped to 2,000 to 15,000 tokens); the others are drawn schematically, since their split is counted in messages or events, not tokens. Triggers: Codex at 90% of the window, Gemini CLI at 50% with a second call that critiques the summary, opencode at the usable window, OpenHands past 80 events, Aider when the chat passes a budget; mini-SWE-agent never compacts, so a run that overflows fails.


Each compaction design, read from source, with its output limits


    

  • Codex compacts at 90% of the window: OpenAI models compact on the server; others get a 426-byte "CONTEXT CHECKPOINT COMPACTION" prompt and a rebuilt history of the summary plus the most recent user messages (compact prompt). Aider's repository map: choosing for the model instead of letting it search


A repository does not fit in a prompt. Three answers are in use: search on demand (the model runs grep, glob and read itself: Claude Code, Codex, opencode, mini-SWE-agent), an embedding index (chunks retrieved by similarity: Cursor), and a ranked summary sent up front, Aider's repository map. Aider was built in 2023 for models with small windows and no tool calls, so it could not let the model search; it chooses for it. Files you add are sent in full; everything else is summarised by the map, cut to a token budget (--map-tokens, 1,024 by default when the model's window is unknown, as for a local model).


    

  1. Tags. tree-sitter parses every file into definitions (class, function and method names, with lines) and references (uses of a name).
    2. 

  2. A graph of files. For every name both defined and referenced, an edge runs from each using file to each defining file, weighted mul × √(number of uses); mul starts at 1 and is multiplied by 10 if your message mentions the name, by 10 if it is a long (8 or more characters) snake_case, kebab-case or camelCase name, by 0.1 if it starts with an underscore, by 0.1 if more than five files define it, and by 50 if the using file is in the chat (repomap.py lines 487 to 514).
    3. 

  3. Personalised PageRank (the random-surfer score, restarting at the files you care about): each file in the chat, each file whose name you typed and each file whose path contains a word you typed gets 100/N added to its restart weight (N files; here 100/59 = 1.69) (lines 383 to 445).
    4. 

  4. Rank flows to definitions: each file's rank is split across its outgoing edges by weight and summed per (defining file, name), so the map lists the most important definitions. Files already in the chat are skipped: their full text is sent anyway.
    5. 

  5. Fit the budget: a binary search finds how many ranked definitions fit, stopping once the map is within 15 percent of the budget, above or below (lines 676 to 703). That is why a 2,048-token budget produced a 2,233-token map below.
    6.

Interview rehearsal: seven design questions


What is the action boundary, and who enforces it?
The point where the model must stop generating so the harness can run the action and return the real result. With native tool calls the inference server enforces it (the reply ends with a tool-call finish reason); with text actions the harness must, by a stop sequence or by training plus the chat template. Without it, the model writes invented results.


mini-SWE-agent runs every command in a fresh subprocess. Why, and what does it cost?
Independent actions make sandboxing a one-line swap (docker exec) and runs easy to parallelise and replay. The cost: no persistent shell state, so cd and export must be repeated in each command.


Compare three compaction designs.
Codex: summarise at 90% of the window, keep recent user messages (server-side for OpenAI models). Gemini CLI: at 50%, summarise the oldest 70% into a state snapshot, then a second call critiques it. opencode: at the usable window, keep a recent tail of 25% (2k to 15k tokens) verbatim. Earlier and two-pass costs tokens but keeps more working room and a better summary.


How would you sandbox an agent's shell on macOS and on Linux?
macOS: Seatbelt profiles via sandbox-exec, deny by default, write only to the workspace, network off (Codex, Gemini CLI -s). Linux: bubblewrap for the file system plus seccomp for the network (Codex), or a container. Keep it on in headless mode, where nobody approves.


SEARCH/REPLACE text, a str_replace tool, or a patch grammar?
Text blocks work with any model and batch many edits in one reply but need a parser and a format per model. A str_replace tool is simple and exact but fails on whitespace drift unless the harness adds matchers (opencode has nine, Gemini CLI four). A patch grammar (Codex) is compact for multi-file changes and can be enforced at decoding time, but the model must be trained on it.


Your agent repeats the same failing tool call. What do you add?
Detection in the harness: identical-call counting (Gemini CLI after 5, opencode after 3), then a nudge, then a stop or a question to the user; a step limit as the last resort. Also look at the tool: a clearer error message or a smaller schema may remove the cause (Codex's justification rule in section 2).


How does Aider decide what to show the model of a repository it cannot fit?
tree-sitter tags, a file graph weighted by identifier references, personalised PageRank toward the files in the chat and the names in the message, then a binary search for the most ranked definitions that fit the token budget. See section 5.

One task, every harness, the wire in between


Every model request of every run went through a logging proxy, so all runs are shown the same way: what the harness sent (system prompt, tool schemas, the conversation) and what the model answered (text, tool calls, token counts). For the Claude runs the "model" is claude -p with every Claude Code tool switched off, and the log is our adapter's. The task and how the runs were made are in the Reading tab's Depth section. One task, mostly one run per setting, a small local model shared with other jobs: a demonstration of what each harness does when the model goes wrong, not a benchmark.
