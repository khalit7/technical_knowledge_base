1. Two ways to ask a model for an action, and the boundary between them

Every harness on this page must get an action out of the model (run this command, change these lines) and feed back an observation (what the command printed). There are two ways to do it, and the difference explains more failures than any other design choice.

Native tool calls

The harness sends tool definitions (a name, a description, a JSON schema for the arguments) with the request. The model answers with a structured tool_calls item and the API ends the reply there, marking it with a finish reason (tool_calls in the OpenAI format, tool_use in Anthropic's). The inference server enforces the boundary: the model cannot write the result of its own call, because generation has stopped. Codex, Gemini CLI, opencode, OpenHands and mini-SWE-agent's default mode work this way.

Text actions

The model writes the action inside its prose in an agreed format, and the harness finds it with a regular expression: Aider's SEARCH/REPLACE blocks, or mini-SWE-agent's text mode, which wants exactly one ```mswea_bash_command block per reply ({{regex|https://github.com/SWE-agent/mini-swe-agent/blob/a83fcae82d2a08f0ee0c688f9d137b3566c097f8/src/minisweagent/models/litellm_textbased_model.py#L8}}). This works with any model that writes text, which is why Aider chose it in 2023, before OpenAI shipped function calling on 13 June 2023 ({{OpenAI|https://openai.com/index/function-calling-and-other-api-updates/}}). But now the harness must stop the model at the action.

Aider does not need that stop: its whole protocol is "reply once, with the edits"; the model never waits for an observation inside a reply. A loop that does need observations (run ls, see the listing, decide) must end generation right after the action. With a model API you pass a stop sequence, a string at which the server stops generating; with an open model the chat template's end-of-turn token usually does it, because the model was trained to stop after a tool call. claude -p, the only way this page could reach Claude (a subscription, no API key), has no stop-sequence option. So we ran mini-SWE-agent's text mode with Claude Haiku 4.5 twice, through a small adapter that puts claude -p behind an OpenAI-style endpoint: once passing the reply through untouched, once cutting it right after the first action block.

What the recordings show


Without the cut, Haiku wrote one action and then kept going: it invented the command's output, wrote its next thought, the next action, the next output, up to  action blocks in one reply, ending with "All tests passed!" and the submit command. mini-SWE-agent's parser refused every reply with more than one block ("Expected exactly 1 action"),  times in  calls, and the run finally ended on a reply whose single action was the submit command. No file was changed; both tests still failed.


With the cut, every command that ran was one the model asked for and every observation was real, yet the run also ended with no edit: the model wrote its invented exchange before its first action ("The core.py file appears to be empty", a file it never read), so the cut kept that reasoning, and the last reply claimed the tests passed and submitted. The cut text was thrown away, but it was still generated and paid for:  output tokens for  calls.


The lesson for your own harness: a client-side cut stops the harness from acting on invented output; it does not stop the model from believing it. The fix is structural: a real message list with roles and a server-side stop (native tool calls, or a stop sequence), which is exactly what claude -p with tools off cannot give. Drill. Why did the local 4B model not invent output in mini-SWE-agent's text mode, through the same text protocol?
It ran behind a real chat-completions server: Qwen's chat template ends the assistant turn with an end-of-turn token, and the model was trained to emit it after a single action, so generation stopped at the right place without any stop sequence. The boundary came from training plus the template, not from the harness.
