5. What the model sees: the first request, compaction and the repository map

Context is paid for before the model has done anything. The first request of each run carries the harness's system prompt and every tool definition, and every later call resends it all with the history appended. The principles (window budgets, caching, what to compact) are {{Context engineering|n:3f15c17b0d0d811292cee46514370431}}'s; here is what each harness actually sends and keeps.

Prompts and tools are chosen per model family: Codex gives an unknown model a fallback prompt and 12 tools, opencode picks its system prompt and even its edit tool by matching the model id; a provider-agnostic harness has to carry a dialect per family.

Per-model prompts and tools, and which project instruction files each reads

Prompts and tools are per model. Codex gives an unknown model the 20,903-byte fallback prompt ({{model_info.rs|cx:codex-rs/models-manager/src/model_info.rs#L98-L157}}) and 12 tools, among them five multi-agent tools and three "goal" tools but no apply_patch: unknown models are expected to call it through the shell. For OpenAI's own models a test pins the default set: exec_command and write_stdin (a shell, long-running processes on a pseudo-terminal), update_plan, request_user_input, apply_patch, view_image, tool_search (which loads MCP and multi-agent tools on demand) and web_search ({{prompt_caching.rs|cx:codex-rs/core/tests/suite/prompt_caching.rs#L268-L279}}). opencode chooses its system prompt by matching the model id: anthropic.txt for Claude, gemini.txt, codex.txt, beast.txt for older GPT models, default.txt (8,528 bytes) for anything else ({{system.ts|oc:packages/opencode/src/session/system.ts}}); ids containing gpt- get a Codex-style apply_patch instead of edit and write ({{registry.ts|oc:packages/opencode/src/tool/registry.ts#L292-L301}}). A provider-agnostic harness has to carry a dialect per model family. OpenHands assembles its prompt from Python sections (28,492 bytes of static text, with dynamic repository, skills and date sections).

Tool sets. Gemini CLI: about 17 tools reach the model in a default interactive session (15 in our headless run): read_file, list_directory, glob, grep_search (ripgrep), replace, write_file, run_shell_command, web_fetch, google_web_search, write_todos, invoke_agent (subagents), activate_skill and others ({{config.ts|gm:packages/core/src/config/config.ts#L4008-L4125}}). Two often-listed tools are not model-visible in this version: read_many_files serves only the @file syntax, and save_memory is gone: the prompt tells the model to edit GEMINI.md with the ordinary file tools. OpenHands' default coding preset gives terminal (a tmux session), file_editor, task_tracker, plus the built-ins finish and think: five tools ({{default preset|oh:openhands-tools/openhands/tools/preset/default.py}}); every tool schema gets two injected fields, summary and, for tools that change something, security_risk, so the model must classify the risk of its own action on every call. opencode sent our model 10 tools, mini-SWE-agent one (bash), Aider none.

Project instruction files. Codex reads AGENTS.md, one per directory from the git root down to the working directory (an AGENTS.override.md wins in its directory), 32 KiB in total ({{agents_md.rs|cx:codex-rs/core/src/agents_md.rs#L1-L18}}). Gemini CLI reads GEMINI.md from ~/.gemini, then from each trusted root up to the git root; one in a subdirectory loads only when a tool first touches that directory, and files can @import others five levels deep. opencode takes the first of AGENTS.md, CLAUDE.md, CONTEXT.md between the working directory and the project root (and ~/.claude/CLAUDE.md globally), plus nested AGENTS.md files attached when the read tool opens a file below them. OpenHands ignores AGENTS.md or CLAUDE.md unless load_project_skills=True. Aider reads no memory file automatically (conventions are a file you add with --read); mini-SWE-agent reads none.

When the window fills: Gemini CLI compacts at half the window and keeps the newest 30%; mini-SWE-agent never compacts

The history at the moment each harness compacts, and what survives: kept verbatim against summarised by a model call. Widths are to scale for Gemini CLI (oldest 70% summarised) and opencode (a recent tail of 25% of the usable window, clamped to 2,000 to 15,000 tokens); the others are drawn schematically, since their split is counted in messages or events, not tokens. Triggers: Codex at 90% of the window, Gemini CLI at 50% with a second call that critiques the summary, opencode at the usable window, OpenHands past 80 events, Aider when the chat passes a budget; mini-SWE-agent never compacts, so a run that overflows fails.

Each compaction design, read from source, with its output limits
  • Codex compacts at 90% of the window: OpenAI models compact on the server; others get a 426-byte "CONTEXT CHECKPOINT COMPACTION" prompt and a rebuilt history of the summary plus the most recent user messages ({{compact prompt|cx:codex-rs/prompts/templates/compact/prompt.md}}). Tool output kept in history is cut to the model's limit (10,000 tokens for bundled models) plus 20%, keeping head and tail ({{history.rs|cx:codex-rs/core/src/context_manager/history.rs#L546-L554}}).
  • Gemini CLI starts at 50%: the oldest 70% of the history becomes an XML <state_snapshot>, then a second "probe" call asks the model to critique and improve its own summary ({{chatCompressionService.ts|gm:packages/core/src/context/chatCompressionService.ts#L332-L410}}). Two calls per compression, at half the window: Google trades tokens for a better summary. Shell output over 40,000 characters is saved to a file and truncated; read_file stops at 2,000 lines.
  • opencode summarises the older part when the last turn's tokens reach the usable window ({{compaction.ts|oc:packages/opencode/src/session/compaction.ts#L115-L120}}). Two traps: compaction is silently off for a custom model with no limit.context in the config (the session then fails when the window fills), and the cheap "prune old tool outputs" step is off by default. Tool output is cut at 2,000 lines or 50 KB, with the full text saved to a file.
  • OpenHands' condenser in the default preset keeps the first 4 events and a recent tail, and has a model summarise the middle once the history passes 80 events or the token cap, into a state summary with fields such as COMPLETED, PENDING, CODE_STATE and TESTS ({{llm_summarizing_condenser.py|oh:openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py#L554-L562}}). A bare Agent has no condenser. Terminal output over 30,000 characters is cut in the middle and saved to a file.
  • Aider summarises older chat in a background call ("*Briefly* summarize this partial conversation about programming") once it passes a budget.
  • mini-SWE-agent: none, on purpose. The history is linear, every step appends and the whole list is sent each time, so the trajectory is exactly the prompt, easy to read and to train on. Long outputs are cut in the observation template (over 10,000 characters: the first and last 5,000). A run that overflows the window fails.

Aider's repository map: choosing for the model instead of letting it search

A repository does not fit in a prompt. Three answers are in use: search on demand (the model runs grep, glob and read itself: Claude Code, Codex, opencode, mini-SWE-agent), an embedding index (chunks retrieved by similarity: Cursor), and a ranked summary sent up front, Aider's repository map. Aider was built in 2023 for models with small windows and no tool calls, so it could not let the model search; it chooses for it. Files you add are sent in full; everything else is summarised by the map, cut to a token budget (--map-tokens, 1,024 by default when the model's window is unknown, as for a local model).

  1. Tags. tree-sitter parses every file into definitions (class, function and method names, with lines) and references (uses of a name).
  2. A graph of files. For every name both defined and referenced, an edge runs from each using file to each defining file, weighted mul × √(number of uses); mul starts at 1 and is multiplied by 10 if your message mentions the name, by 10 if it is a long (8 or more characters) snake_case, kebab-case or camelCase name, by 0.1 if it starts with an underscore, by 0.1 if more than five files define it, and by 50 if the using file is in the chat ({{repomap.py lines 487 to 514|ai:aider/repomap.py#L487-L514}}).
  3. Personalised PageRank (the random-surfer score, restarting at the files you care about): each file in the chat, each file whose name you typed and each file whose path contains a word you typed gets 100/N added to its restart weight (N files; here 100/59 = 1.69) ({{lines 383 to 445|ai:aider/repomap.py#L383-L445}}).
  4. Rank flows to definitions: each file's rank is split across its outgoing edges by weight and summed per (defining file, name), so the map lists the most important definitions. Files already in the chat are skipped: their full text is sent anyway.
  5. Fit the budget: a binary search finds how many ranked definitions fit, stopping once the map is within 15 percent of the budget, above or below ({{lines 676 to 703|ai:aider/repomap.py#L676-L703}}). That is why a 2,048-token budget produced a 2,233-token map below.

What it buys. The map costs no model calls (a parser and a graph library, then input tokens on each request), where agentic search pays a model call per grep; it is recomputed when files change (--map-refresh) but ranks only what the parser sees (strings, configs and dynamic dispatch carry no tags). Every tool-calling harness here lets the model search instead; Aider's idea survives as a cheap first message, a few hundred tokens of "what is where" before the first grep.
