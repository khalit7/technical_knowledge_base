4. What contains a command: sandbox and approval defaults

Two separate questions: what can a command touch (an operating-system sandbox, a container, or your whole machine) and who says yes before it runs (nobody, a human, a policy that denies). The six sit at every corner, and the corner moves when nobody is there to approve, in headless runs and CI.

Only Codex keeps a boundary when nobody is there to approve

Each harness at its default (solid) and where its headless or "yes to everything" mode moves it (dashed, with the flag). Read from source at the pinned versions. Codex's codex exec forces the approval policy to never, but the sandbox stays on; Gemini CLI's gemini -p denies anything that would need approval; Aider's --yes-always answers no to the shell commands the model suggests; mini-SWE-agent's --yolo stops asking. Why both dials are needed, and what an attacker does with each gap, is {{Agent security|n:3f15c17b0d0d81ad9fb7d1dd74217335}}.

Each harness's sandbox and approval model, read from source
Codex CLI
Two independent dials: a sandbox mode (read-only by default, workspace-write for a trusted folder, danger-full-access) and an approval policy (on-request by default, never, or granular) ({{config_toml.rs|cx:codex-rs/config/src/config_toml.rs#L826-L856}}). On macOS the sandbox is Seatbelt (sandbox-exec with four .sbpl profiles, deny by default); on Linux, bubblewrap for files plus seccomp for the network, with Landlock kept only as a deprecated fallback ({{linux-sandbox|cx:codex-rs/linux-sandbox/src/lib.rs#L1-L5}}). In workspace-write the network stays off unless you enable it. codex exec (headless) forces the approval policy to never, so the sandbox is all that stands between the model and your machine ({{exec|cx:codex-rs/exec/src/lib.rs#L574-L576}}).
Gemini CLI
Approval modes default, auto_edit, plan and yolo, decided by TOML policy files: read-only tools are allowed, edits and the shell ask ({{write.toml|gm:packages/core/src/policy/policies/write.toml#L52-L55}}). Headless, the engine's default is deny: gemini -p without --yolo or --approval-mode auto_edit cannot edit or run anything ({{policy-engine.ts|gm:packages/core/src/policy/policy-engine.ts#L298-L301}}). The sandbox is off by default; -s relaunches the whole CLI inside macOS Seatbelt (profile permissive-open: writes only to the project, temp and cache folders, network open), or Docker, Podman, gVisor or LXC on Linux ({{sandbox.ts|gm:packages/cli/src/utils/sandbox.ts#L121-L130}}).
opencode
Rules of the form permission, pattern, action (allow, ask, deny); the last matching rule wins. Defaults allow almost everything: only reading .env files, touching paths outside the project and doom loops ask ({{agent.ts|oc:packages/opencode/src/agent/agent.ts#L119-L136}}). Shell commands are parsed with tree-sitter so an "always allow" can be stored as a prefix such as git checkout *. There is no OS sandbox. In opencode run, any question is rejected unless you pass --auto.
Aider
No sandbox. The safety net is git: dirty files are committed first, every applied edit becomes its own commit with a model-written message, and /undo checks out the previous version of the changed files and soft-resets that commit ({{git docs|https://aider.chat/docs/git.html}}). That undoes edits; it isolates nothing.
OpenHands SDK
Confirmation policy NeverConfirm by default; ConfirmRisky asks at HIGH risk and for UNKNOWN. The LLMSecurityAnalyzer does no analysis of its own: it returns the security_risk value the acting model wrote into its own call ({{llm_analyzer.py|oh:openhands-sdk/openhands/sdk/security/llm_analyzer.py#L20-L29}}, field injected by {{tool.py|oh:openhands-sdk/openhands/sdk/tool/tool.py#L712-L731}}), so the agent grades itself; a regex analyser for patterns such as rm -rf exists as a second layer. LocalWorkspace runs commands on your machine; isolation comes from DockerWorkspace, which starts an agent-server container and drives it over HTTP. In our run the model rated reads LOW and pip install pytest MEDIUM, which it ran inside the container when pytest was missing, although the test file runs with plain python3.
mini-SWE-agent
The mini command asks before each command unless you pass --yolo, and runs on your machine; Docker, Podman, Singularity and bubblewrap environments are one setting away. Every action is a fresh subprocess ({{local.py|ms:src/minisweagent/environments/local.py#L13-L56}}), so cd and export do not persist between steps; in exchange sandboxing is "literally just switch out subprocess.run with docker exec", and runs are trivial to parallelise.

What it buys. A sandbox on by default (Codex) means the prompt does not have to be trusted and headless mode stays safe; a deny-by-default headless policy (Gemini CLI) is safe but surprises people ("why did nothing get edited?"); allow-by-default with no sandbox (opencode) is fastest and trusts the model with your machine; git (Aider) makes edits reversible but not commands; a self-graded risk field (OpenHands) is not a reviewer. Codex no longer keeps a hard-coded list of safe commands: Starlark execpolicy rules decide allow, prompt or forbid, and the built-in "dangerous" check only knows forced rm ({{is_dangerous_command.rs|cx:codex-rs/shell-command/src/command_safety/is_dangerous_command.rs#L123-L151}}).

How our runs were contained, and two Gemini CLI traps met on the way

opencode and OpenHands ran inside throwaway Docker containers we started (opencode has no sandbox; the OpenHands SDK used its local workspace inside the container), mini-SWE-agent with its Docker environment, Codex with its own Seatbelt workspace-write, Gemini CLI with its own Seatbelt (-s), and Aider with no sandbox (it runs no model-suggested command under --yes-always; only our test command).

In a folder it does not trust, Gemini CLI printed "Approval mode overridden to "default" because the current folder is not trusted", which in headless mode means every edit is denied, --yolo or not. And setting GOOGLE_GEMINI_BASE_URL makes the CLI pick its "gateway" sign-in type, which its own validator then rejects ("Invalid auth method selected"; {{auth.ts|gm:packages/cli/src/config/auth.ts#L10-L48}}); choosing the API-key sign-in in the settings keeps the custom base URL.

A Codex process that outlives the session

Since 0.157.0 an interactive codex session starts codex app-server --managed-daemon by default (the release note: "Enabled automatic background-server startup for eligible interactive sessions"). Per a user report ({{issue #48195|https://github.com/openai/codex/issues/48195}}, opened 25 September 2026; still open, with no maintainer reply and no change to the default, when read on 26 October, while downstream packagers switch auto-start off themselves), the daemon keeps running after every Codex window is closed, runs from a copy of the roughly 374 MB platform package under ~/.codex/packages/, keeps the environment of the session that started it, and a detached loop checks for updates five minutes after start and then hourly, restarting the backend. codex features disable daemon_auto_start (or daemon_auto_start = false in config.toml) turns it off. The sandbox confines tool calls; it says nothing about what the harness itself leaves running.
